## Y2-T04 · Add docs/setup.md reproducible in ≤10 min; submit bridge plan

*Session 4 · phase E1 · 3 points*

### The ticket in plain words

CityPulse is a shared project. Your squad of about five students writes scripts that must run the same way on the lab computer and on every laptop. Those scripts need Python, pip (the installer for Python libraries) and a virtual environment (a venv), a private folder of libraries for one project. Without this, code often works on one machine and fails on another. Engineers call that problem "works on my machine", and it costs teams hours.

This ticket has two jobs. The first is `docs/setup.md`, a guide that a teammate who did not write it can follow from a fresh copy of the repository to a working Python setup in ten minutes or less. The second is a personal bridge plan. The A-03 baseline gap report showed your three weakest areas from T0, the start of the course. A bridge plan names a resource for each area, a weekly time and a check date, so the gaps close before the D02 defence on 12 December.

A guide is finished only when a stranger can run it. The trainer times a cold run in a new folder and then runs test commands. Your job is to make the guide pass that test, and to explain every line in the viva.

### How your trainer checks it

The trainer checks six acceptance criteria through five test cases and a live cold run. You are also asked to explain any line of setup.md, so know what each line does.

**TC1: the cold run**

```bash
cd /tmp && rm -rf st && git clone https://github.com/citypulse-y2/citypulse-<squad>.git st && cd st
```

Then the trainer follows docs/setup.md word for word with a stopwatch.

- `cd /tmp` moves to a temporary folder. Git Bash maps `/tmp` to a Windows temp folder, so this works there too.
- `&&` runs the next command only if the previous one succeeded.
- `rm -rf st` deletes the folder `st` without asking. It is safe only because `st` is a throwaway folder. Never run it in your real repository.
- `git clone URL st` downloads the repository into a new folder called `st`.

Passing: every verify command succeeds and the stopwatch shows 10:00 or less. Failing: `fatal: repository ... not found` means the squad name in the URL is wrong. A stop with an error means setup.md is missing a step, or relies on your own shell state.

**TC2: Python and requests**

```bash
source .venv/bin/activate && which python && python -c 'import requests,sys;print(sys.version.split()[0],requests.__version__)'
```

- `source .venv/bin/activate` activates the venv in this shell.
- `which python` prints the path of the Python the shell now finds first.
- `python -c '...'` runs the quoted code. `sys.version.split()[0]` keeps the first word of the version, and `requests.__version__` is the installed version.

A passing run looks like this:

```term
$ source .venv/bin/activate && which python && python -c 'import requests,sys;print(sys.version.split()[0],requests.__version__)'
/home/student/st/.venv/bin/python
3.12.3 2.32.3
```

The path ends in `/.venv/bin/python`. The version line shows your squad's pin, and `2.32.3` here is only an example. Failing: `/usr/bin/python` means the venv is not active. `ModuleNotFoundError: No module named 'requests'` means the install was skipped or ran under another Python.

**TC3: ignored paths and no tracked secrets**

```bash
git check-ignore -v .venv .env; git ls-files | grep -E '(^|/)\.env$'
```

- `git check-ignore -v` prints each path a rule matches, with the rule's file and line number.
- `;` runs the next command whatever the first one returned.
- `git ls-files` lists every tracked file, and `|` sends that list to `grep`.
- `grep -E '(^|/)\.env$'` keeps lines that are exactly `.env` or end in `/.env`. `\.` is a literal dot and `$` is the end of the line.

Passing output is one line per path, and `grep` prints nothing:

```text
.gitignore:3:.venv/    .venv
.gitignore:4:.env      .env
```

Failing: a `.env` line printed by `grep` means a secret was committed. If `check-ignore` prints nothing for a path, the rule is missing or misspelt. For `.venv` it also prints nothing if the `.venv` folder does not exist yet, because the rule `.venv/` matches only a directory, so run TC3 after creating the venv.

**TC4: the PR body and its review**

```bash
gh pr view <n> --json body,reviews --jq '.body, [.reviews[].state]'
```

`gh pr view <n>` shows PR number `<n>`. `--json body,reviews` returns those two fields as JSON, and `--jq` filters them. `.body` prints the description, and `[.reviews[].state]` lists each review's state. Passing: the body contains `Tested by @`, and the list includes `"APPROVED"`. Failing: `[]` means no review yet.

**TC5: the bridge plan on the LMS**

The trainer opens your submission and checks three rows, each with a resource (a URL or course name), a weekly time and a check date. Failing: fewer than three rows, a vague resource such as "videos", or a date on or after 12 December 2026.

### Do it, step by step

#### Y2-T04.1 Branch, ignore rules and .env.example

Goal: a branch, two ignore rules and a placeholder file. Run this in Git Bash on your laptop.

Stage 1 starts the branch.

```bash
git switch main
git pull
git switch -c docs/setup
```

`git switch main` moves to main and `git pull` updates it. `git switch -c` creates the branch and moves onto it.

Stage 2 adds the ignore rules, after checking the file.

```bash
grep -n '' .gitignore
printf '\n.venv/\n.env\n' >> .gitignore
tail -n 2 .gitignore
```

`grep -n ''` prints every line with its number. `printf` writes text, and `\n` is a new line (the first one guards against a last line with no ending, and may leave one blank line). `>>` appends, where a single `>` would overwrite. `tail -n 2` should show `.venv/` and `.env`. If they are already there, skip the `printf`. The rule `.env` matches only a file named exactly `.env`, so `.env.example` stays tracked.

Stage 3 creates the placeholder file.

```bash
printf 'API_KEY_NAME=replace-me\nDATA_URL=replace-me\n' > .env.example
cat .env.example
```

Choose the names your squad's data source needs. Values are placeholders only, and no real key goes in this file. `cat` shows what you wrote.

Stage 4 tests the rules, then commits.

```bash
mkdir .venv
touch .env
git check-ignore -v .venv .env .env.example
rm .env
rmdir .venv
git status --short
```

`mkdir .venv` and `touch .env` create temporary stand-ins, because the rule `.venv/` (with a trailing slash) matches only a directory that exists. `rm .env` and `rmdir .venv` remove them again. Expect lines for `.venv` and `.env`, and no line for `.env.example`. `git status --short` should list only `.gitignore` and `.env.example`. Commit each file separately: `git add .gitignore && git commit -m 'chore: ignore .venv and .env'`, then the same for `.env.example`.

#### Y2-T04.2 requirements.txt and a fresh venv

Goal: one line, `requests==<pinned>`, that installs into a clean venv. Run this on the lab, inside the repository.

Stage 1 creates and activates the venv.

```bash
pwd
python3 -m venv .venv
source .venv/bin/activate
which python
```

`pwd` confirms the folder. Expect `which python` to end in `.venv/bin/python`. On Git Bash, use `python -m venv .venv`, and the activation script is `.venv/Scripts/activate`.

Stage 2 upgrades pip and lists versions.

```bash
python -m pip install --upgrade pip
python -m pip index versions requests
```

`python -m pip` runs the pip of the active Python. `index versions` lists releases, newest first. Your squad chooses one version and writes it down. If `index` is not available, check pypi.org in a browser.

Stage 3 installs the pin and checks it.

```bash
python -m pip install requests==<pinned>
python -m pip show requests
```

Replace `<pinned>` with your number. `show` prints a `Version:` line that must match.

Stage 4 writes the file. Replace `<pinned>` before you press Enter, because a placeholder left in the file makes pip fail.

```bash
printf 'requests==<pinned>\n' > requirements.txt
cat requirements.txt
```

`pip freeze` would also list requests' own dependencies, such as urllib3. The ticket names only `requests`, so agree any other choice with your squad.

Stage 5 proves the file in a fresh venv.

```bash
pwd
deactivate
rm -rf .venv
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -c 'import requests; print(requests.__version__)'
```

Check `pwd` first, because `rm -rf .venv` deletes the `.venv` folder in the current directory. `-r` reads the list from the file. Expect `Successfully installed` and your pinned version. Then `git status --short` should list only `requirements.txt`, because the ignore rule hides `.venv`.

:::trap Installing before activating
Without `source .venv/bin/activate`, pip installs into the system Python. TC2 then fails. Run `which python` before any install.
:::

#### Y2-T04.3 Write docs/setup.md

Goal: six sections a stranger can follow. Run each command on the lab first, then write what you saw. Do not copy commands from the book without running them.

Stage 1 creates the skeleton.

```bash
mkdir -p docs
nano docs/setup.md
```

Type these headings, then save with Ctrl+O and Enter, and exit with Ctrl+X.

```text
# Setup

## 1 Prerequisites
## 2 Clone
## 3 Venv
## 4 Secrets
## 5 Verify
## 6 Troubleshooting
```

`mkdir -p` creates the folder, or does nothing if it exists. A single `#` is the title, and `##` marks each section. Test with `grep -c '^## ' docs/setup.md`, which should print `6`.

Stage 2 fills sections 1 and 2. Section 1 lists the tools from Before you start. Section 2 gives the clone command with your squad's name:

```bash
git clone https://github.com/citypulse-y2/citypulse-<squad>.git
cd citypulse-<squad>
```

`git clone` downloads the repository into a new folder, and `cd` moves into it. Explain each code block in one sentence.

Stage 3 fills section 3 with the venv commands from Y2-T04.2. Explain each line, because a cold-call may ask about any of them.

Stage 4 fills section 4.

```bash
cp .env.example .env
chmod 600 .env
```

`cp` copies the placeholder file. `chmod 600` gives the owner read and write and nobody else anything, and `ls -l` should show `-rw-------`. Git Bash on Windows handles permissions differently, so say so in the section.

Stage 5 fills section 5 with the checks from TC2 and TC3, each followed by its expected output.

Stage 6 fills section 6 with at least three entries: the exact error text, the cause and the fix, copied from your cold-run log. Test it with `sed -n '/^## 6/,$p' docs/setup.md`.

#### Y2-T04.4 Practise on the lab

Goal: explain background jobs, PATH and activation before you teach them. Run this on the lab, because `ps` output differs on Windows.

Stage 1 starts a background process and finds it.

```bash
ps aux | grep '[s]leep 600'
sleep 600 &
jobs
ps aux | grep '[s]leep 600'
```

`ps aux` lists every process, and `|` sends the list to `grep`. The brackets in `[s]leep` stop grep from matching its own command line. The `&` starts the sleep in the background. Expect the first search to print nothing, `[1] 12345` after the `&` (12345 is a PID), and `jobs` to show `[1]+ Running sleep 600 &`.

Stage 2 stops it.

```bash
kill %1
jobs
```

`%1` means job number 1, not a PID. Plain `kill` sends the TERM signal, which lets the program clean up. Expect `Terminated` once, then nothing from `jobs` (the exact wording and the moment it appears depend on your shell). Use `kill -9` only as a last resort, because it skips cleanup.

Stage 3 looks at PATH and activation.

```bash
echo "$PATH"
which python
source .venv/bin/activate
which python
deactivate
```

`echo "$PATH"` prints the folders the shell searches, separated by colons. After activation, `which python` ends in `.venv/bin/python`. `deactivate` restores the old PATH. Test yourself: say what each line printed, without looking.

#### Y2-T04.5 The timed cold run

Goal: a teammate who did not write setup.md follows it in a new folder while you log each failure. You do not run it yourself.

Stage 1 starts the clock. Your teammate sets it first, then runs the TC1 commands in a new folder in the same terminal:

```bash
SECONDS=0
```

`SECONDS` is a Bash variable that counts seconds since it was last set, and it keeps counting in that terminal, so do not close it. The teammate then follows setup.md, reading it only.

Stage 2 reads the time at the end.

```bash
m=$((SECONDS / 60)); s=$((SECONDS % 60)); echo "${m}m${s}s"
```

`$(( ))` does arithmetic: `/` gives whole minutes and `%` the remaining seconds. The output, such as `9m42s`, is the format the PR needs.

Stage 3 logs each failure, with its step number and the exact error.

```bash
echo "step 4: pip install -r requirements.txt failed: No matching distribution found" >> ~/cold-run.log
cat ~/cold-run.log
```

`>>` appends a line to a file in the home folder. Write what happened, not what you expected. This log is your work list for Y2-T04.6. Never put a real secret in it.

#### Y2-T04.6 Fix, open the PR and get approval

Goal: each logged failure is fixed, and a squad-mate approves the PR.

Stage 1 fixes and commits.

```bash
git diff docs/setup.md
git add docs/setup.md
git commit -m 'docs: fix steps that failed in cold run'
```

`git diff` shows removed lines starting with `-` and added lines starting with `+`. Check each fix against one log line.

Stage 2 pushes the branch.

```bash
git push -u origin docs/setup
```

`origin` is the GitHub remote. `-u` links your branch to it, so later pushes need no extra words.

Stage 3 opens the PR. Write the description in `~/pr-body.md`, using the template in Prove it before review, then run:

```bash
gh pr create --base main --title 'docs: add reproducible setup' --body-file ~/pr-body.md
```

`--base main` names the target branch, `--title` sets the title, and `--body-file` reads the description. The output is the PR's URL, which ends in the number you need for TC4.

Stage 4 gets the approval. A squad-mate runs `gh pr review <n> --approve` on their own account. You do not approve your own PR, and a squad-mate merges it after approval.

```flow
TITLE: How your change reaches main
NODES: Your branch | GitHub pull request | Squad-mate
STEPS:
1>2 :: git push :: Your commits reach GitHub and a pull request opens.
2>3 :: request review :: A squad-mate reads the diff and the Tested by line.
3>2 :: approve :: The review is recorded as APPROVED.
2>1 :: merge :: After approval, the change joins main.
```

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| `which python` prints `/usr/bin/python` after activation | Activation did not run in this shell | Run `source .venv/bin/activate` again in the same shell |
| `No module named venv` or `ensurepip is not available` | The venv support package is missing on the lab | Ask QA/DevOps to install it, then recreate `.venv` |
| `No matching distribution found for requests==...` | A typo in the pin, or the version does not exist | Run `python -m pip index versions requests`, then fix the line |
| `git check-ignore -v` prints nothing for `.venv` | The rule is missing or misspelt | Run `grep -n venv .gitignore`, then correct and commit it |
| `git ls-files` lists `.env` | The file was committed before the rule existed | Run `git rm --cached .env`, commit, and replace any exposed key |
| The reviews list in TC4 is `[]` | No squad-mate has reviewed | Ask a squad-mate. Never approve your own PR |

### Defend it in the viva

**1. Why does setup.md check `which python` before any install?**

:::answer Model answer
The shell runs the first `python` on PATH. If the venv is not active, packages install into the system Python instead, and the venv cannot see them. `which python` is a cheap check that the venv is in charge before anything is installed.
:::

**2. Trade-off: why pin `requests` instead of installing the latest?**

:::answer Model answer
A pin makes every machine install the same code, so a teammate's cold run matches yours. The cost is missing fixes in newer releases, so the pin must be updated on purpose, for example for a security fix.
:::

**3. What did you personally do in this ticket, and how can the trainer see it?**

:::answer Model answer
Name the subtask you owned, your commits to it, and your cold-run log lines. Describe only work that the history supports, because the trainer checks it.
:::

**4. Why is `.env` ignored but `.env.example` committed?**

:::answer Model answer
`.env` holds real secrets, and a secret that reaches GitHub must be treated as leaked. `.env.example` shows the names with placeholder values. The trade-off is that each teammate fills in their own copy.
:::

**5. What does `pip install -r requirements.txt` do?**

:::answer Model answer
pip reads the file line by line, and each line names a library and a pinned version. pip installs those into the active venv, so the activation check must come first.
:::

### Check yourself

```quiz
Q: After you run source .venv/bin/activate, which python still prints /usr/bin/python. What is the most likely cause?
- The package requests is missing from requirements.txt
* The activation did not take effect in this shell, so the system Python is still first on PATH
- Git has not ignored the .venv folder
- The Python version is older than 3.10
WHY: which prints the first python on PATH. If activation failed, the system copy comes first. The tempting wrong answer is the requirements file, which has nothing to do with which.

Q: Which command shows whether a secret file has been committed to the repository?
- git check-ignore .env
- ls -a .env
- chmod 600 .env
* git ls-files | grep -E '(^|/)\.env$'
WHY: git ls-files lists tracked files, and grep keeps any path that is exactly .env or ends in /.env. The tempting wrong answer is git check-ignore, which says only whether a path is ignored, and a file can be ignored yet still tracked.

Q: Your teammate's cold run took 12 minutes and failed at step 4. What should you do first?
* Read the step 4 error in the log, reproduce it, fix that line in setup.md, then time a new cold run
- Delete the repository and clone it again under a new name
```

`TMP="$(mktemp)"` runs `mktemp`, which creates an empty file with a unique name, and stores its path in `TMP`. `trap '...' EXIT` registers a command that runs whenever the script exits, whether it succeeds or fails. The single quotes stop the shell from expanding `$TMP` too early.

Stage 3. Fetch the body and check the status. This is the core of the ticket:

```bash
STATUS="$(curl -s --max-time 20 -o "$TMP" -w '%{http_code}' "$URL")"
if [ "$STATUS" != "200" ]; then
  echo "ERROR: HTTP $STATUS from $URL" >&2
  exit 1
fi
echo "body bytes: $(wc -c < "$TMP")"
```

Line by line:

- `curl -s` runs quietly. `--max-time 20` gives up after 20 seconds, so a silent server cannot hang the script.
- `-o "$TMP"` writes the body into the temporary file, so it never reaches the screen.
- `-w '%{http_code}'` prints only the status code. `STATUS="$(...)"` captures that code.
- `if [ "$STATUS" != "200" ]; then` is true for any status other than 200. This includes `000`, which means curl could not reach the server at all.
- `echo "ERROR: ..." >&2` writes the message to standard error, so it cannot be mistaken for data.
- `exit 1` stops the script before anything is written.
- The last `echo` line is temporary. It proves the body arrived. Remove it in stage 5.

```bash
  exit 2
fi
```

Line by line:

- `jq -e` sets jq's exit code from the result. If the filter returns `false` or `null`, the exit code is not 0. Without `-e`, jq exits with 0 even for a null result.
- The filter is true only when both fields exist and are not null. Replace `FIELD_1` and `FIELD_2` with the metric names from Y2-T05.1, and add the time field too if you wish.
- `! ... > /dev/null` inverts the result, so the block runs when the check fails. `> /dev/null` hides jq's output, because you only need the exit code.
- `exit 2` gives this failure its own code, so a caller can tell a bad body (2) from a bad status (1).

Test without the network. Use a here-string, which feeds text to a command as if it were a file:


Expected output: `false` on one line, then `1` on the next, because `pm2_5` is missing (jq prints the result of the filter, and `-e` sets the exit code from it). Change the filter and the input to see the `0` case too. Replace `pm2_5` in this test with your own field name.

Line by line:

- `OUT="data/raw/$(date +%F).csv"` builds one file per day, named by today's date.
- `mkdir -p data/raw` creates the folder if it is missing. A fresh clone does not have it. `-p` means "no error if it exists".
- `[ -s "$OUT" ] || echo '...' > "$OUT"` writes the header only when the file is missing or empty. `-s` is true for a file with content. `||` runs the right side only when the left side is false. This is why the header appears once.

### Defend it in the viva

**Q1. Why does the script read the status code before it looks at the body?**

:::answer Model answer
A body from an error response is not the data you asked for. A 404 or 500 can still come with an HTML or JSON error message. If the script parsed it, jq would fail in a confusing way, or worse, a valid-looking row could be written. Reading the status first lets the script stop with a clear message that names the status, and it writes nothing.
:::

**Q2. What is the trade-off between checking the status yourself and using curl's `--fail` option?**

:::answer Model answer
`--fail` makes curl exit with an error on any HTTP error, which is short and simple. The cost is that with `-s` curl prints no message, and its exit code (22) is the same for every HTTP error, so it does not tell you which status it was. Capturing the status with `-w '%{http_code}'` costs a few more lines, but it lets the script print the exact code, such as `ERROR: HTTP 404`, which the ticket asks for. It also lets the script treat code 000 as a failure in its own way.
:::

**Q3. Why does the script use two different exit codes, 1 and 2?**

:::answer Model answer
Exit code 1 means the request failed, so the source did not answer with 200. Exit code 2 means the request succeeded but the body did not have the fields we need. A caller, such as a future cron job or a monitor, can tell these apart. A bad status may be a temporary outage, while a missing field may mean the source changed its format. Different codes lead to different responses.
:::

**Q4. The script appends a row on every run, with no check for duplicates. What is the cost, and where is it fixed?**

:::answer Model answer
If the source has not updated since the last run, the new row repeats the same timestamp and values. That makes the file noisy and can distort counts later. This ticket only needs one append per run. Duplicate removal is part of Y2-T06, which adds retries, a lock and deduplication to the same script. Saying this clearly shows you know the limit of your own work.
:::

**Q5. Walk me through what you personally did on this ticket.**

:::answer Model answer
Point to your own commits and the stage each one covers, using the output of `git log --author` with your name. A strong answer names one stage you wrote, says what it does, shows the test output that proved it, and says what you would change. Do not describe work that is not in your commits. The trainer checks the history, so a true and specific answer is the only kind that scores.
:::

#### Y2-T06.2: retry, schema check and dedup

**Goal.** Retry up to three times, log each failure, exit 1 when all tries fail, and skip saved rows.

**Stage 1. The function.** Put this above the place where the fetch happens. The loop keeps retrying while curl fails, and the counter and wait double each time:

```bash
fetch_with_retry() {
  local attempt=1 delay=5
  until curl -sSf --max-time 20 -o "$TMP" "$URL"; do
    if [ "$attempt" -ge 3 ]; then
      log ERROR "HTTP fetch failed after 3 attempts: $URL"
      return 1
    fi
    log WARN "attempt $attempt failed; retrying in ${delay}s"
    sleep "$delay"
    attempt=$((attempt + 1))
    delay=$((delay * 2))
  done
}
fetch_with_retry || exit 1
```

`-s` hides the progress bar, `-S` shows errors, `-f` fails on HTTP errors such as 404, and `--max-time 20` gives up after 20 seconds. `local` keeps the variables inside the function. The last line makes the script exit 1 when the function fails, which is what TC2 checks.

#### Y2-T06.3: the lock and the kill switch

**Goal.** Stop two copies from running at once, and stop the job when `ops/STOP` exists.

**A short lesson on `flock`.** `flock` locks an open file. The lock lasts while the process runs, and Linux releases it when the process ends, even after a crash.

```flow
TITLE: Two copies start at the same time
NODES: First run | flock lock | Second run | logs/fetch.log
STEPS:
1>2 :: takes lock :: The first run holds the lock on file descriptor 9 while it works.
3>2 :: asks for lock :: A second copy starts while the first is still busy.
2>3 :: lock held :: flock -n refuses at once, because -n means do not wait.
3>4 :: WARN previous run active :: The second copy logs one WARN line and exits 0.
```

**Stage 1. The lock.** Put these lines after the `log` function, and before any fetch:

```bash
exec 9>"/tmp/citypulse-$(whoami).lock"
if ! flock -n 9; then
  log WARN "previous run active; skipping"
  exit 0
fi
```

### Defend it in the viva

**1. Why does the script exit 0 when another run is active, but exit 1 when the HTTP request fails?**

:::answer Model answer
An overlap is expected, so exit 0 says the job is fine. A failed request means no data was collected, so exit 1 tells cron and anything watching the exit code that the run failed. Mixing the two would hide failures or raise false alarms.
:::

**2. What trade-off did you accept by retrying three times instead of retrying until the request works?**

:::answer Model answer
Three short tries fix brief network faults and finish in a known time. Retrying forever could hold the lock for hours and block every later run. The cost is that a longer outage leaves a gap, which the log shows and the next scheduled run does not fill.
:::

**3. Which part did you write yourself, and how did you prove it works?**

:::answer Model answer
Name the subtask you owned, the stage you wrote and the test that proves it, with the command you ran and the log line it produced. Do not describe work you did not do.
:::

**4. Why does the dedup check use timestamp and location, and not the whole row?**

:::answer Model answer
A repeated reading can differ in another column, such as number formatting, so a whole-row comparison would miss it. Timestamp and location identify one reading at one time. The trade-off is that a genuine correction for the same time and place is skipped.
:::

**5. How do you know the job runs without you?**

:::answer Model answer
The evidence is in the logs. `crontab -l` shows the schedule, and the `grep -c` count shows the successes. WARN and ERROR lines explain failures.
:::

**TC1: healthcheck reports a broken source.**

#### Stage 1 (Y2-T07.1): check the 48-hour gate

**Goal.** Show that the job has run long enough and that the data holds at least 96 rows.

First, learn `wc -l`, which counts lines:

```bash
printf 'a\nb\nc\n' | wc -l
```

`printf` writes three lines, and the pipe `|` sends them to `wc -l`. Expect `3`.

Each CSV has a header line, so data rows are the line count minus one. `tail -n +2` prints from line 2 onwards, which skips the header:

```bash
for f in data/raw/*.csv; do echo "$f $(tail -n +2 "$f" | wc -l)"; done
```

The loop visits each CSV. `echo` prints the file name and its row count, for example `data/raw/2026-11-15.csv 48`. Your numbers will differ. Once `merge.sh` has produced `merged_*.csv` files in the same folder, leave them out of the loop, or you will count rows twice.

#### Stage 2 (Y2-T07.2): write scripts/healthcheck.sh

**Goal.** Measure how many minutes ago the last success was, and print `OK`, `WARN` or `CRIT` with a matching exit code.

**2a. Time arithmetic.** Two commands turn dates into numbers:

```bash
date +%s
date -d "2026-11-17 09:30" +%s
```

`date +%s` prints the current time as seconds since 1 January 1970. `date -d "..."` reads a date you give it. The `-d` option is GNU date, which the lab and Git Bash have, but not every Mac does. Check your log's timestamp format with `head -2 logs/fetch.log`, and make sure `date -d` can read it.

**2b. The top of the script.**

```bash
#!/usr/bin/env bash
set -uo pipefail
WARN_MIN="${WARN_MIN:-60}"
CRIT_MIN="${CRIT_MIN:-120}"
LOG="${LOG:-logs/fetch.log}"
```

The first line tells the system to run the file with Bash. `set -uo pipefail` makes an unset variable an error and makes a pipeline fail if any part fails. There is no `-e` on purpose: the healthcheck must still print its status after a failed command. Each `${VAR:-default}` keeps a value passed in the environment, which is how TC1 sets `WARN_MIN=0`.

Test with `bash -n scripts/healthcheck.sh`. It checks syntax and prints nothing when the syntax is fine.

**2c. Find the last success.** Build the pipeline one command at a time:

```bash
grep ' INFO appended' "$LOG" | tail -1 | cut -d' ' -f1
```

`grep` keeps the success lines. `tail -1` keeps the newest one. `cut -d' ' -f1` splits the line at spaces and keeps field 1. That is the whole timestamp only if your log writes it without a space, such as `2026-11-17T09:30:00`. If it is `2026-11-17 09:30:00`, use `-f1,2`. Run the pipeline without the last part first, to see the line. Then store the result:

```bash
last="$(grep ' INFO appended' "$LOG" | tail -1 | cut -d' ' -f1 || true)"
```

`$(...)` runs the command and stores its output in `last`. `|| true` stops a failing pipeline from ending the script when there is no success yet. Test `[ -z "$last" ]` before using `last`: if it is empty, `date -d ""` silently means midnight today, not an error. Decide what the script prints when there is no success yet, and write that decision in the README, because the ticket leaves it to you.

**2d. Compute the age.**

```bash
now=$(date +%s)
last_ts=$(date -d "$last" +%s)
age=$(( (now - last_ts) / 60 ))
echo "age ${age} min"
```

`$(( ... ))` does integer arithmetic. Division rounds down, which is fine for minutes. Expect a line such as `age 14 min`.

**2e. Choose the status.** The trace shows how one age becomes one status.

```trace
TITLE: Choosing the status from the age
CODE:
age=75
WARN_MIN=60
CRIT_MIN=120
if [ "$age" -ge "$CRIT_MIN" ]; then echo CRIT; exit 2
elif [ "$age" -ge "$WARN_MIN" ]; then echo WARN; exit 1
else echo OK; exit 0; fi
STEPS:
1 :: age=75 :: The age of the last success is 75 minutes.
2 :: age=75; WARN_MIN=60 :: The warning threshold came from the default or the environment.
3 :: age=75; WARN_MIN=60; CRIT_MIN=120 :: The critical threshold is set the same way.
4 :: age=75; WARN_MIN=60; CRIT_MIN=120 :: Is 75 at least 120? No, so the CRIT branch is skipped.
5 :: age=75; WARN_MIN=60; CRIT_MIN=120 :: Is 75 at least 60? Yes, so this branch runs.
5 :: age=75; WARN_MIN=60; CRIT_MIN=120 :: echo prints WARN.
5 :: age=75; WARN_MIN=60; CRIT_MIN=120 :: exit 1 ends the script with code 1, and the else branch is never reached.
```

Now write your own `if`, `elif` and `else`. Test CRIT first, because a large age also passes the WARN test. Each branch prints one line starting with the status word and exits with 2, 1 or 0. Getting this order wrong is the most common mistake in this stage.

**Test this stage.** After `chmod +x scripts/healthcheck.sh`, run:

```bash

WARN_MIN=0 CRIT_MIN=0 scripts/healthcheck.sh; echo $?
```

The first should print OK and `0` after a fetch. The second should print CRIT and `2`.

**2f. Run it hourly.** Add this line with `crontab -e` on the lab, replacing the path with the output of `pwd`:

```bash
0 * * * * cd /home/yourname/citypulse-squad && scripts/healthcheck.sh >> logs/health.log 2>&1
```

`0 * * * *` runs at minute 0 of every hour. Cron starts in your home folder, so `cd` changes into the repository first. `&&` runs the rest only if the `cd` worked. `>> logs/health.log 2>&1` appends the output and any errors to the health log.

```flow
TITLE: One hourly healthcheck run
NODES: cron | scripts/healthcheck.sh | logs/fetch.log | logs/health.log
STEPS:
1>2 :: minute 0 :: cron starts the healthcheck with a minimal environment.
2>3 :: read last line :: The script searches the log for the newest INFO appended line.
3>2 :: timestamp :: The log returns the time of the last success.
2>4 :: OK, WARN or CRIT :: The status line is appended to the health log.
```

#### Stage 3 (Y2-T07.3): disk guard and log rotation

**Goal.** Stop `fetch.sh` writing when the disk is nearly full, and keep logs small.

**3a. Read the disk usage.**

```bash
df -P . | awk 'NR==2 {print $5}' | tr -d '%'
```

`df -P .` reports the disk holding the current folder, in a fixed layout. Line 2 is the disk you want. `awk 'NR==2 {print $5}'` prints field 5, the percentage used. `tr -d '%'` deletes the percent sign so you can compare numbers. Expect `42`.

**3b. Add the guard to fetch.sh.** Choose a threshold, for example 90, and keep it in a variable near the top of the script that an environment value can override, such as `DISK_MAX="${DISK_MAX:-90}"`. Then write an `if` that compares the number with the threshold using `-ge`, which means "greater than or equal". When the test is true, write a line to the log and exit with 1 before the fetch starts.

The log line must not contain `INFO appended`, or it would count as a success and hide the failure from the healthcheck. Use `ERROR` or `WARN`, following the format of your other lines.

**Test this stage.** Set the threshold to 0 for one run:

```bash

tail -1 logs/fetch.log
```

Expect exit code `1` and the disk message in the log. Make sure `ops/STOP` is absent first, or the script may stop before reaching the guard. The variable name is your choice, but the test above assumes it can be set from the environment.

**3c. The logrotate configuration.** This file describes what to rotate and how:

```
logs/*.log {
    weekly
    rotate 4
    compress
    missingok
    notifempty
    copytruncate
}
```

`weekly` rotates once a week, `rotate 4` keeps four old copies, `compress` gzips them, `missingok` ignores an absent file, and `notifempty` skips empty logs. `copytruncate` matters if a process keeps the log file open while it runs (for example a script that starts with `exec >> logs/fetch.log`). Without it, a rename would leave that process writing to the moved file. It is a safe choice for any log that scripts append to. Choose your own values, and run the commands from the repository root.

**3d. Dry run.** The ticket's check is:

```bash
logrotate -d -s ops/logrotate.state ops/logrotate.conf
```

`-d` is debug mode: it prints what logrotate would do and changes no file. `-s` names the state file that records past rotations. Expect lines that mention each log, such as `considering log logs/fetch.log`. Wording varies by version. Any message about a missing file or a bad directive is a failure. Some logrotate versions also complain about file permissions, for example a config or log folder that others can write to, or a path that is not absolute. If you see such a message, `chmod 644 ops/logrotate.conf` and `chmod go-w logs` often fix it. If it still fails, or if the lab's version rejects the relative `logs/*.log` pattern, ask your trainer rather than guessing.

**3e. Schedule it.** The ticket gives the command, and you choose the time. For example, `30 3 * * * cd /home/yourname/citypulse-squad && logrotate -s ops/logrotate.state ops/logrotate.conf` runs at 03:30 each day, outside the fetch times. Cron's PATH is short (usually `/usr/bin:/bin`) and `logrotate` often lives in `/usr/sbin`, so put the full path from `command -v logrotate` in the cron line.

#### Stage 4 (Y2-T07.4): second source and merge

**Goal.** Fetch a second source and join its rows to the air-quality rows by timestamp and location.

**4a. Look at the data first.** The ticket leaves the source to your squad and gives Open-Meteo as an example. Check its parameter names in the provider's documentation, then look at one reply:

```bash

```

Use the names you see, not the ones in this example. Open-Meteo times are in GMT unless you add a `timezone` parameter, and the `current` time is a 15-minute slot, so check how it lines up with your air-quality timestamps before you join. Then `jq -r '... | @csv'` turns chosen fields into one CSV line, where `@csv` builds the quoted line and `-r` removes the quotes around the whole output.

**4b. Learn the join with two small files.** Practise in a folder outside the repository, such as `$HOME/join-practice`:

```bash
printf 'time,temp,humidity\n2026-11-17T09:00,24.1,58\n2026-11-17T10:00,24.8,55\n' > meteo.csv
printf 'time,station,pm25\n2026-11-17T09:00,S1,41\n2026-11-17T10:00,S1,44\n2026-11-17T11:00,S1,47\n' > air.csv
```

`printf` writes text, with `\n` for new lines, and `>` writes it to a file. The values are made up for practice.

```bash
awk -F, 'FNR==1 {next}
NR==FNR { temp[$1]=$2; hum[$1]=$3; next }
$1 in temp { print $0","temp[$1]","hum[$1]; next }
{ unmatched++ }
END { print "unmatched", unmatched+0 > "/dev/stderr" }' meteo.csv air.csv
```

`-F,` sets the separator to a comma. `FNR==1 {next}` skips each header. `NR==FNR` is true only while awk reads the first file, because `NR` counts all lines so far and `FNR` counts lines in the current file. The first file is stored in arrays keyed by time. For the second file, `$1 in temp` asks whether its time exists; if so, the row is printed with the extra columns, and if not, `unmatched` goes up. `END` runs once and prints the count to standard error, so it does not mix with the data. The ticket wants unmatched counts for both sources, so also count first-file rows that never matched, for example by marking keys in a `used` array.

Expected output:

```
2026-11-17T09:00,S1,41,24.1,58
2026-11-17T10:00,S1,44,24.8,55
unmatched 1
```

The 11:00 row has no partner, so it is unmatched.

**4c. Build merge.sh in three stages.** First, the argument. This stops with a usage message if the date is missing:

```bash

day="${1:?usage: scripts/merge.sh YYYY-MM-DD}"
```

`${1:?message}` uses the first argument, or prints the message and exits. Test with `scripts/merge.sh; echo $?`.

Second, the input files. Use the names your earlier tickets already write, and check each file exists, printing a clear error if one does not.

Third, the join and output. Use the awk pattern from 4b with the real key, which is timestamp and location together. Write a header with the column names from both sources yourself, then send the joined rows into `data/raw/merged_$day.csv`.

**Test this stage.** Run `scripts/merge.sh $(date +%F)` and then `head -3 data/raw/merged_$(date +%F).csv`. If nothing matches, the two timestamp formats probably differ, for example one has `+05:30` and the other `Z`.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| Healthcheck prints OK while fetching has stopped | It checks that the log file exists, not the age of the last success line | Measure the age of the last `INFO appended` line |
| `WARN_MIN=0 CRIT_MIN=0` has no effect | Thresholds are hard-coded, so the environment is ignored | Use `${WARN_MIN:-60}` style defaults |
| `echo $?` always shows 0 | The script ends with `exit 0`, or the branches do not call `exit` | Put `exit 2`, `exit 1` and `exit 0` inside the matching branches |
| Healthcheck is OK right after a guard error | The guard wrote a line containing `INFO appended` | Log guard errors as `ERROR` or `WARN` |
| `date -d` fails, or the age is huge or negative | The timestamp format or timezone is not what `date -d` expects | Check `head -2 logs/fetch.log` and adjust the parsing |
| Logs stop growing after rotation | The file was renamed while `fetch.sh` kept writing to it | Add `copytruncate` to the config |
| merge.sh joins zero rows | Timestamps differ in format or timezone between sources | Print one line from each file and make the formats match |
| `git shortlog` shows commits under another email | `git config user.email` was not set before committing | Set it, redo the commits on your branch, and tell your trainer |
| `git cat-file -t v0.1-p1` prints `commit` | The tag is lightweight, made without `-a` | Delete it (`git tag -d v0.1-p1`, then `git push origin :refs/tags/v0.1-p1`), then recreate it with `-a` |

### Defend it in the viva

The viva scores your understanding and contribution. Answer in your own words, and use your own commits as evidence.

**1. Why does the healthcheck measure the age of the last success instead of checking that cron is running?**

:::answer Model answer
Cron can run happily while every fetch fails, for example with a bad URL or a blanked key. The client cares about data, so the healthcheck measures how old the last successful line is. If that age passes a threshold, the data is stale, whatever the cause. The check looks at the outcome, not the mechanism.
:::

**2. What is the trade-off between a 60-minute WARN and a 120-minute CRIT?**

:::answer Model answer
Lower thresholds find problems sooner but can raise false alarms, for example from one slow reply. Higher thresholds reduce noise but leave the data stale longer before anyone hears. With fetches every 30 minutes, 60 minutes means two missed runs, a reasonable first warning, and 120 minutes means four, which is serious. A strong answer says how many missed runs each threshold represents.
:::

**3. Why does logrotate need copytruncate for a log that fetch.sh writes with `>>`?**

:::answer Model answer
The script keeps appending to the same path. If logrotate only renamed the file, the running process could keep writing to the renamed copy, and the new file would stay empty. `copytruncate` copies the log and then empties the original, so writes continue to the same path. A strong answer also admits that a few lines written during the copy can be lost, and says why that is acceptable here.
:::

**4. Describe one commit you made. Why is it atomic, and what does its message tell a reviewer?**

:::answer Model answer
Your answer must describe your own commit. A good answer names the one thing it changes, says why it can be read or reverted alone, and quotes the subject and the first sentence of the body. It should show that the message explains the reason for the change, not only what changed. Practise with your own `git log` output.
:::

**5. How did you check that your work reached `main`, and what would you do if a PR was not reviewed?**

:::answer Model answer
Name the checks you ran, for example `git shortlog -sne origin/main` showing your commits under your email, and each PR showing a squad-mate's approval. If a PR is not reviewed, ask the reviewer directly or raise it with the Tech Lead. Never merge your own PR. A strong answer names that rule.
:::
