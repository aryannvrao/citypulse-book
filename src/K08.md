## Y2-T23 · Deploy scheduled serverless fetch to bucket + cost comparison

*Session 23 · phase M4 · 5 points*

### The ticket in plain words

Until now, the CityPulse fetch step has run on a virtual machine (a rented computer that is switched on all the time). That machine sits idle most of the day and someone has to patch it. This ticket asks a plain question: for a job that runs every 30 minutes, is a serverless function cheaper and simpler? The honest answer is that it depends, so the client wants numbers rather than opinions.

You will move the fetch into an AWS Lambda function. Lambda runs your code only when something calls it. A timer will call it every 30 minutes. The function asks the Open-Meteo air-quality API for Bengaluru readings, checks the reply, and saves the raw JSON into your CityPulse bucket (a private storage container in S3). The function uses a role, which is a set of permissions AWS hands to the function for a short time. That means no password or access key is stored in its settings.

Then you prove it works from the logs. Two runs started by the timer, not by you, must leave lines in the logs and files in the bucket. Last, you compare the monthly cost of the virtual machine with the monthly cost of the function, using AWS's own pricing calculator. You then work out how many runs it would take before the two costs are equal.

The description does not name a specific failure. Its point is that teams have moved in both directions, so the decision must rest on measured cost.

### How your trainer checks it

The trainer runs five test cases and checks five acceptance criteria. The criteria are: at least two scheduled runs in the logs, each with a matching object in the bucket; the role is `citypulse-fetch-fn` and no access key appears; both monthly figures come from the calculator with arithmetic and a break-even statement; the account ID in the evidence is your own; and the schedule is `rate(30 minutes)` or disabled.

**TC1, the function configuration.**

```
aws lambda get-function-configuration --function-name citypulse-fetch --query '{Role:Role,Env:Environment.Variables,Timeout:Timeout,Mem:MemorySize}'
```

- `aws lambda get-function-configuration` reads the settings of the function.
- `--function-name citypulse-fetch` names the function.
- `--query` picks out fields. Inside the braces, `Role:Role` means "a field called Role, taken from the Role setting". The same pattern applies to the other fields.

Passing output:

```
{
    "Role": "arn:aws:iam::123456789012:role/citypulse-fetch-fn",
    "Env": {
        "CITYPULSE_BUCKET": "citypulse-example-k9x2"
    },
    "Timeout": 60,
    "Mem": 256
}
```

The role must end with `role/citypulse-fetch-fn`. `Env` must hold only `CITYPULSE_BUCKET`, and `AQI_URL` is allowed too. `Timeout` must be 60 and `Mem` must be 256. The bucket name and account number above are made up. Yours will differ.

A failing output usually has one of three causes. If `Env` contains `AWS_ACCESS_KEY_ID`, you stored a key, so remove it. If `Env` is `null`, the variable was never set, which means `deploy.sh` missed the `--environment` flag. If `Timeout` is 3, you created the function without `--timeout 60`.

**TC2, the scheduled runs in the logs.**

```
aws logs tail /aws/lambda/citypulse-fetch --since 1h | grep -c 'wrote s3://'
```

- `aws logs tail` prints the recent lines in one log group.
- `--since 1h` limits the output to the last hour.
- `|` is the pipe. It sends the lines into the next command as input.
- `grep -c` counts the lines that match the text.
- `'wrote s3://'` is the text to match. This is why your handler must print that exact text.

Passing output (the trainer needs a number of at least 2):

```term
$ aws logs tail /aws/lambda/citypulse-fetch --since 1h | grep -c 'wrote s3://'
2
```

A result of 0 means the handler does not print that text, or no run has happened. A result of 1 usually means only your manual invoke ran, so the schedule has not fired yet.

**TC3, the objects in the bucket.**

```
aws s3 ls s3://<bucket>/raw/openmeteo-aq/ --recursive
```

- `aws s3 ls` lists objects under a prefix.
- `--recursive` goes into every sub-folder, which here are the `date=` folders.

Passing output has at least two lines ending in `fetch_HHMM.json`, about five or thirty minutes apart. An example line looks like `2027-01-12 09:00:03  12345 raw/openmeteo-aq/date=2027-01-12/fetch_0900.json`. Replace `<bucket>` with your own bucket name. An empty result means the wrong bucket or a wrong prefix. One line only means both runs wrote the same minute, or only one run has happened.

**TC4, the schedule.**

```
aws scheduler get-schedule --name citypulse-fetch-30m --query '{s:ScheduleExpression,st:State}'
```

- `aws scheduler get-schedule` reads one schedule by name.
- The query returns the expression as `s` and the state as `st`.

Passing output is `{"s": "rate(30 minutes)", "st": "ENABLED"}` or the same with `"st": "DISABLED"`. If you see `rate(5 minutes)`, you forgot step Y2-T23.7. If you see `ResourceNotFoundException`, the name does not match exactly.

**TC5, the cost document.** Open `docs/cloud-cost.md` and check by eye. There must be two calculator links, two monthly totals in rupees or US dollars, arithmetic lines and a break-even statement. A missing date next to the links is a fail.

### Do it, step by step

#### Y2-T23.1: Create the function's role

**Goal.** A role named `citypulse-fetch-fn` that Lambda can take on, with permission to write the bucket prefix and to write logs. There is no access key.

**The idea.** A role has two parts. The trust policy says who may wear the role. The permission policies say what the role may do.

**Stage 1, the trust policy.** Save this as `infra/function/trust.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "lambda.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}
```

Each line says the following. `Effect` allows the statement. `Principal` names Lambda as the service allowed to wear the role. `Action` names the wearing action, `sts:AssumeRole`. Test it with `python -m json.tool infra/function/trust.json`. Expected output is the same JSON, reformatted. An error with a line number means a missing comma.

**Stage 2, create the role.**

```bash
aws iam create-role --role-name citypulse-fetch-fn \
  --assume-role-policy-document file://infra/function/trust.json \
  --query Role.Arn --output text
```

`create-role` makes the role. `file://` tells the CLI to read the JSON from a file. `--query Role.Arn --output text` prints only the ARN. Expected output: one line such as `arn:aws:iam::<your account>:role/citypulse-fetch-fn`.

**Stage 3, the logging permission.**

```bash
aws iam attach-role-policy --role-name citypulse-fetch-fn \
  --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole
```

This attaches AWS's standard logging policy. It prints nothing when it succeeds.

**Stage 4, the bucket permission.** Paste the ARN from the Before you start check into the command:

```bash
aws iam attach-role-policy --role-name citypulse-fetch-fn --policy-arn <ARN of citypulse-pipeline-s3>
```

The D15 walk-through writes an inline policy instead. Your ticket names the policy `citypulse-pipeline-s3`, so attach that one. Check that it allows `s3:PutObject` only on the `raw/openmeteo-aq/` prefix.

**Test.** Run `aws iam list-attached-role-policies --role-name citypulse-fetch-fn --query "AttachedPolicies[].PolicyName" --output text`. Expected output: both policy names. A role has no access key, so none is created.

:::trap A new role is refused
Lambda sometimes rejects a role that was created seconds ago. If `create-function` later says the role cannot be assumed, wait 20 seconds and run the command again.
:::

#### Y2-T23.2: Write the handler and its test

**Goal.** `infra/function/handler.py` that fetches, checks, saves and logs. `tests/test_handler_key.py` that tests the key format.

**Technique first: a date to text.** `strftime` turns a date into text using codes. `%Y` is the four-digit year, `%m` the month, `%d` the day, `%H` the hour and `%M` the minute.

```python
from datetime import datetime, timezone
now = datetime(2027, 1, 12, 9, 0, tzinfo=timezone.utc)
print(now.strftime("fetch_%H%M.json"))
```

Expected output: `fetch_0900.json`. The code is standard library only.

**Stage 1, imports and client.** Create `infra/function/handler.py` with these lines. Copy the API address string from your `src/citypulse/fetch.py` into `AQI_URL`:

```python
import json
import os
import urllib.request
from datetime import datetime, timezone

import boto3

AQI_URL = "<paste the address from fetch.py>"
s3 = boto3.client("s3")  # created once per container, reused on warm starts
```

`os.environ` reads the settings that Lambda passes in. `boto3.client("s3")` sits at module level, so it is built once when the container starts. Test with `python -c "import ast; ast.parse(open('infra/function/handler.py').read())"`. No output means the syntax is valid.

**Stage 2, the key.** Add this function. It is separate so that the test can call it without making a network request:

```python
def make_key(now):
    return now.strftime("raw/openmeteo-aq/date=%Y-%m-%d/fetch_%H%M.json")
```

The function takes a time and returns the key as text. The key depends only on the minute, so two runs in the same minute write the same object.

**Stage 3, fetch and check.** Add this function:

```python
def fetch_body():
    with urllib.request.urlopen(AQI_URL, timeout=20) as r:
        if r.status != 200:
            raise RuntimeError(f"API returned {r.status}")
        body = r.read()
    json.loads(body)  # raises ValueError if the body is not JSON
    return body
```

`urlopen` raises an error for most failed HTTP codes already. The `if` check makes the rule explicit for any non-200 reply. The `json.loads` line is only a check, and it raises an error if the body is not JSON. Errors must be raised, not caught, so that the run is marked as failed.

**Stage 4, the handler.** Fill in the three TODO lines. Try them yourself before you use the hints after the code:

```python
def handler(event, context):
    body = fetch_body()
    key = make_key(datetime.now(timezone.utc))
    bucket = os.environ["CITYPULSE_BUCKET"]
    # TODO 1: call s3.put_object with Bucket=bucket, Key=key and Body=body
    # TODO 2: print one line in this exact shape: wrote s3://<bucket>/<key> bytes=<n>
    # TODO 3: return {"key": key, "bytes": len(body)}
```

The printed text must start with `wrote s3://`, because TC2 counts that text. Hints: `put_object` takes keyword arguments, and `len(body)` gives the byte count. An f-string can build the printed line.

**Stage 5, the test.** Create `tests/test_handler_key.py` at the repository root:

```python
from datetime import datetime, timezone
from handler import make_key

def test_key_for_0900_utc():
    now = datetime(2027, 1, 12, 9, 0, tzinfo=timezone.utc)
    assert make_key(now) == "raw/openmeteo-aq/date=2027-01-12/fetch_0900.json"
```

Add two more tests yourself, one for 17:05 UTC and one for 00:00 UTC. Run them from the repository root with `PYTHONPATH=infra/function python -m pytest tests/test_handler_key.py -q`. `PYTHONPATH` tells Python where to find `handler.py`. Expected output: `3 passed`. Pytest must have `boto3` installed, because the test imports the handler. Install it with `pip install boto3 pytest`.

#### Y2-T23.3: Write the deploy script

**Goal.** `infra/function/deploy.sh` that zips the handler, creates the function the first time, updates it afterwards, and waits until it is active.

**Technique first: `set -euo pipefail`.** The three flags make a script stricter. `-e` stops at the first failing command. `-u` stops if you use a variable that is not set. `-o pipefail` makes a pipeline fail if any step fails. Without them, a broken deploy can look like a success.

**Stage 1, the header.** Create the file with:

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")"
FN=citypulse-fetch
```

`cd "$(dirname "$0")"` moves into the folder that holds the script, so the zip paths are right whatever folder you run it from. `FN` stores the function name in one place.

**Stage 2, the zip.**

```bash
python -m zipfile -c function.zip handler.py
```

`-c` creates an archive called `function.zip` containing `handler.py`. Test it with `python -m zipfile -l function.zip`. Expected output lists `handler.py`. Add `function.zip` to `.gitignore`, because the zip is a build product and should not be committed.

**Stage 3, create or update.** Lambda needs a different command the first time and every time after. Fill in the TODO:

```bash
if aws lambda get-function --function-name "$FN" >/dev/null 2>&1; then
  aws lambda update-function-code --function-name "$FN" --zip-file fileb://function.zip
else
  # TODO: aws lambda create-function with these flags:
  #   --runtime python3.12  --handler handler.handler
  #   --role <ARN of citypulse-fetch-fn>  --memory-size 256  --timeout 60
  #   --environment "Variables={CITYPULSE_BUCKET=<your bucket>}"
  #   --zip-file fileb://function.zip
fi
```

`get-function` succeeds if the function exists. The `>/dev/null 2>&1` part hides its output. `--handler handler.handler` means file `handler`, function `handler`. Get the role ARN with `aws iam get-role --role-name citypulse-fetch-fn --query Role.Arn --output text`. The `Variables={...}` syntax sets one environment variable. Do not add any AWS key here.

**Stage 4, wait.**

```bash
aws lambda wait function-updated-v2 --function-name "$FN"
echo "deployed $FN"
```

`wait` blocks until Lambda has finished creating or updating the function. This matters on the update path, because the function is already "active" while the new code is still being installed. Expected last line: `deployed citypulse-fetch`.

**Test.** Run `bash -n infra/function/deploy.sh`. It checks syntax only and prints nothing when the syntax is valid. Then run `shellcheck infra/function/deploy.sh`. It must print nothing. A warning such as `SC2086` usually means a variable needs double quotes.

#### Y2-T23.4: Deploy and invoke once

**Goal.** Your function exists in your account, runs once by hand, and you have recorded its REPORT line and your account ID.

**Stage 1, deploy.** Run `bash infra/function/deploy.sh`. The first run creates the function. Run it again later to see the update path.

**Stage 2, check the state.** Run `aws lambda get-function-configuration --function-name citypulse-fetch --query State --output text`. Expected output: `Active`.

**Stage 3, invoke.**

```bash

cat out.json
```

`invoke` calls the function once and waits for the answer. The terminal shows `"StatusCode": 200` when the call succeeded, and no `FunctionError` line. `out.json` holds the returned value, such as `{"key": "...", "bytes": 12345}`. `cat` prints the file.

**Stage 4, the REPORT line.**


The `grep REPORT` part keeps only the lines with that word. Expected output is one line with `Duration`, `Billed Duration`, `Memory Size` and `Max Memory Used`. Copy the billed duration and max memory into your notes for T23.6.

**Stage 5, your account ID.** Save the identity for the evidence: `mkdir -p docs/evidence/<name>` and then `aws sts get-caller-identity > docs/evidence/<name>/T23-account.txt`. Replace `<name>` with your folder name.

**Test.** `aws s3 ls s3://<bucket>/raw/openmeteo-aq/ --recursive` lists the new object.

#### Y2-T23.5: Schedule two runs and save evidence

**Goal.** A schedule that calls the function every five minutes, two scheduled runs in the logs and bucket listing, and the evidence files.

**Technique first: an invoke role.** The scheduler calls the function with its own role. That role must trust `scheduler.amazonaws.com`. Its permission policy allows only `lambda:InvokeFunction` on your function.

```flow
TITLE: One scheduled run, end to end
NODES: EventBridge Scheduler | Lambda function | Open-Meteo | S3 bucket | CloudWatch Logs
STEPS:
1>2 :: invoke :: The scheduler calls the function with its scheduler role.
2>3 :: GET air quality :: The handler asks the API for Bengaluru readings.
3>2 :: JSON body :: The API returns the hourly values.
2>4 :: put_object :: The handler saves the body under raw/openmeteo-aq/.
2>5 :: log lines :: The handler prints the wrote line, and Lambda writes the REPORT line.
```

**Stage 1, the scheduler role.** Save this trust policy as `sched-trust.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "scheduler.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}
```

Then run `aws iam create-role --role-name citypulse-scheduler --assume-role-policy-document file://sched-trust.json`. Write a policy file `sched-invoke.json` with `"Action": "lambda:InvokeFunction"` and `"Resource"` set to your function's ARN, then attach it with `aws iam put-role-policy --role-name citypulse-scheduler --policy-name invoke-fetch --policy-document file://sched-invoke.json`.

**Stage 2, the schedule.** Set the two ARNs as variables and create the schedule:

```bash
FN_ARN=$(aws lambda get-function --function-name citypulse-fetch --query Configuration.FunctionArn --output text)
ROLE_ARN=$(aws iam get-role --role-name citypulse-scheduler --query Role.Arn --output text)
aws scheduler create-schedule --name citypulse-fetch-30m \
  --schedule-expression "rate(5 minutes)" --flexible-time-window Mode=OFF \
  --target "Arn=$FN_ARN,RoleArn=$ROLE_ARN"
```

`$(...)` runs a command and stores its output in a variable. `Mode=OFF` means the run happens at the exact time. Expected output: a `ScheduleArn`. The name `citypulse-fetch-30m` is required by the ticket, even though the rate starts at five minutes.

**Stage 3, wait and look.** Wait at least ten minutes. Then run `aws logs tail /aws/lambda/citypulse-fetch --since 30m`. Look for `wrote s3://` lines about five minutes apart. Your manual invoke from T23.4 happened before the schedule existed, so the scheduled runs are the later ones.

**Stage 4, save the evidence.**

```bash
aws logs tail /aws/lambda/citypulse-fetch --since 30m > docs/evidence/<name>/T23-logs.txt
aws s3 ls s3://<bucket>/raw/openmeteo-aq/ --recursive > docs/evidence/<name>/T23-bucket.txt
```

`>` writes the output into a file instead of the screen. Take a screenshot of the log lines as well, and save it in the same folder.

**Test.** Open both files. The log file must hold at least two scheduled `wrote s3://` lines. The bucket file must list objects with `fetch_HHMM.json` names.

:::trap Reusing the function's role

### Defend it in the viva

**Q1 (why). Why is a scheduled function cheaper than a virtual machine for this fetch?**

:::answer Model answer
The fetch runs for about two seconds every 30 minutes. Lambda bills only for the GB-seconds and requests used, so the monthly cost is a small number. A virtual machine is billed for every hour it is switched on, which is about 730 hours a month, and it still needs patching when idle. For this workload, pay-per-use is much cheaper. The calculator figures show it, and the break-even count shows how far the workload is from the point where the VM would win.
:::

**Q2 (trade-off). What do you trade away by choosing Lambda, and how would you decide if the workload changed?**

:::answer Model answer
Lambda caps a run at 15 minutes and gives less control of the environment. Each cold start also adds a delay. In return you get no server to patch and no idle cost. If the job grew to run for longer than 15 minutes, or ran nearly all day, I would compare the monthly figures again and consider a container service or a VM. I would base that choice on the calculator numbers, not on habit.
:::

**Q3 (what you did). Which part did you build, and how do you know it works?**

:::answer Model answer
Describe the subtask you owned in your own words, name the file and the test that covers it, and give the command that proves it. For example, you might say you wrote the key function and its test, ran `pytest` in CI, and then checked TC3 in the bucket listing. Your viva answer should match your own commits in the PR, so review them before the viva.
:::

**Q4 (why). Why does the object key depend only on the minute, and what happens on a retry?**

:::answer Model answer
The key is built from the date and the minute. If a retry happens in the same minute, the same key is written again and the object is replaced, so the bucket does not fill with duplicates. This makes the write idempotent, meaning running it twice leaves the same result. A retry in a later minute does create a new object, and that is expected, because it is a new reading.
:::

**Q5 (why). Why must the handler raise an error on bad data, rather than catch it and return success?**

:::answer Model answer
If the handler catches the error and returns success, CloudWatch records a successful run, and the bad data goes unnoticed. When the handler raises the error, the invocation is marked as failed. The failure then shows in the logs and in the error metric. An honest failure is more useful than a quiet success, because the team can see it and fix it.
:::

#### Y2-T24.4: Write the teardown and recreate scripts

The goal is a script that removes your resources in the order schedule, function, instances, bucket versions, then roles and policies. The recreate script does the reverse. The full order matters because some resources depend on others. A role cannot be deleted while a policy is attached to it.

Run this on the lab machine (Linux bash) or in Git Bash. Build the script in the stages below. Each stage is a fragment to add to the same file, `infra/teardown.sh`.

**Stage 1: the header and the dry-run switch.**

```bash
#!/usr/bin/env bash
set -euo pipefail

NAME="${1:?usage: teardown.sh <name> [--apply]}"
APPLY="no"
if [[ "${2:-}" == "--apply" ]]; then
  APPLY="yes"
fi
```

- `#!/usr/bin/env bash` tells the system to run the file with bash.
- `set -euo pipefail` makes the script stop on the first error (`-e`), stop on an unset variable (`-u`), and treat a failed command inside a pipe as a failure (`-o pipefail`).
- `NAME="${1:?...}"` stores the first argument, your name. The `:?` stops the script with the message if no argument is given.
- `APPLY="no"` is the default. Only `--apply` as the second argument changes it.
- `[[ "${2:-}" == "--apply" ]]` tests the second argument. The `:-` gives an empty value when no second argument exists, which avoids the error from `set -u`.

Test: run `bash infra/teardown.sh` with no argument. You should see your usage message and the script should stop.

**Stage 2: the run helper.** This is the key idea. Every change goes through one function, which either prints or does the change.

```bash
run() {
  local label="$1"; shift
  if [[ "$APPLY" == "yes" ]]; then
    echo "APPLY [$label]"
    "$@"
  else
    echo "DRY [$label] $*"
  fi
}
```

- `run()` defines a function named `run`.
- `local label="$1"; shift` stores the first argument as a label, such as `schedule`, and then removes it from the list. `shift` moves the other arguments down by one.
- In dry-run mode the `else` branch prints `DRY [label]` and the command. `$*` expands to the whole command as text.
- In apply mode, `"$@"` runs the command with its arguments kept separate.

Test: add one line below the function, `run schedule echo hello`, then run `bash infra/teardown.sh ananya`. You should see `DRY [schedule] echo hello`. Remove the test line before you go on.

**Stage 3: the schedule.** A rule must lose its targets before you delete it. Find the rule name first:

`aws events list-rules --name-prefix citypulse --region ap-south-1 --query 'Rules[].Name' --output text`

- `aws events list-rules` lists scheduled rules.
- `--name-prefix citypulse` keeps only rules whose name starts with `citypulse`.
- `--query 'Rules[].Name' --output text` prints the names one per line, without JSON.

Use the name from your T23 deployment. Then add the calls below, with your rule name in place of `citypulse-fetch-schedule`:

```bash
SCHEDULE="citypulse-fetch-schedule"
run schedule aws events remove-targets --rule "$SCHEDULE" --ids fetch-target --region ap-south-1
run schedule aws events delete-rule --name "$SCHEDULE" --region ap-south-1
```

- `SCHEDULE="..."` stores the rule name once, so you change it in one place.
- `remove-targets` detaches the function from the rule. `--ids` names the target; use the ID you saw with `aws events list-targets-by-rule --rule "$SCHEDULE"`.
- `delete-rule` removes the rule. It must come after `remove-targets`, or AWS refuses.

Test: run the script with a name. You should see two `DRY [schedule]` lines in that order.

**Stage 4: the function and the instances.** Deleting the function is one call:

```bash
run function aws lambda delete-function --function-name citypulse-fetch --region ap-south-1
```

- `delete-function` removes the function. Its name is the one from `get-function` in TC2.

For instances, look up your own VMs by their tag. This is a read-only lookup, so it is safe in dry-run mode:

```bash
mapfile -t IDS < <(aws ec2 describe-instances --region ap-south-1 --filters "Name=tag:Owner,Values=$NAME" "Name=instance-state-name,Values=running,stopped" --query 'Reservations[].Instances[].InstanceId' --output text | tr '\t' '\n')
for id in "${IDS[@]}"; do
  [ -n "$id" ] || continue
  run instances aws ec2 terminate-instances --region ap-south-1 --instance-ids "$id"
done
```

- `describe-instances` lists instances. `--filters "Name=tag:Owner,Values=$NAME"` keeps only instances tagged with your name, so the lookup depends on your T24.2 work.
- `Name=instance-state-name,Values=running,stopped` keeps only instances that are running or stopped.
- `--output text | tr '\t' '\n'` turns the tab-separated output into one ID per line.
- `mapfile -t IDS < <(...)` reads those lines into an array called `IDS`. `mapfile` needs bash 4 or newer, which the lab machine and Git Bash have.
- `[ -n "$id" ] || continue` skips an empty line, which some AWS CLI versions print when nothing matches.
- `for id in "${IDS[@]}"` loops over each ID. The quotes keep each ID as one word.

Warning: `terminate-instances` deletes the VM, unlike a stop. The ticket allows terminating only the T19 VM, and only when your D03 compute evidence is complete. Remember that as written, `--apply` would run every stage of the script, including the function, bucket and roles, so do not use it for this decision (see T24.5).

Test: run the dry-run. You should see one `DRY [instances]` line per instance, and none if the lookup finds no instance.

**Stage 5: the bucket versions.** In a versioned bucket, `aws s3 rm` only adds delete markers. The old versions remain, and S3 refuses to delete the bucket while they exist. `aws s3api list-object-versions --bucket "$BUCKET" --query 'Versions[].[Key,VersionId]' --output text | head -5`

- `list-object-versions` lists every stored version of every object.
- `--query 'Versions[].[Key,VersionId]'` prints the object key and version ID as a pair.
- `--output text` prints one pair per line.
- `| head -5` shows only the first five lines, so you can see the shape of the output.

Write your loop with `run bucket aws s3api delete-object --bucket "$BUCKET" --key <key> --version-id <id>` for each pair, then one final line with `run bucket aws s3api delete-bucket --bucket "$BUCKET" --region ap-south-1`. Set `BUCKET` near the top of your script, as you did for `SCHEDULE`. In dry-run mode the loop prints one line per version, and an empty bucket prints none for the versions.

Test: run the dry-run. The `DRY [bucket]` lines must come after the instance lines, and the delete-bucket line must come last among the bucket lines.

**Stage 6: roles and policies.** AWS refuses to delete a role that still has attached or inline policies, so detach them first. Find your roles with a tag filter:

`aws iam list-role-tags --role-name "$ROLE" --query "Tags[?Key=='Owner' && Value=='$NAME'].Value" --output text`

- `aws iam list-roles --query 'Roles[].RoleName' --output text` first gives every role name in the account; loop over those as `$ROLE`.
- `list-role-tags` returns one role's tags. The `Tags[?...]` part is a filter that keeps the `Owner` tag only if its value equals your name. The `$NAME` is expanded by the shell inside the double quotes.
- If this prints your name, the role is yours; if it prints nothing, skip that role. Use this check inside your loop.

For each role, you then need the commands:

```bash
run roles aws iam detach-role-policy --role-name "$ROLE" --policy-arn "$POLICY_ARN"
run roles aws iam delete-role-policy --role-name "$ROLE" --policy-name "$INLINE"
run roles aws iam delete-role --role-name "$ROLE"
```

- `detach-role-policy` removes a managed policy from the role. Its ARN comes from `aws iam list-attached-role-policies --role-name "$ROLE"`.
- `delete-role-policy` removes an inline policy, which is written in the role itself. Names come from `aws iam list-role-policies --role-name "$ROLE"`.
- `delete-role` removes the role. It must come last for that role.

Note that `list-roles` does not return tags, so a filter on tags inside it matches nothing. Use this instead: list the role names, then keep those whose `Owner` tag matches.

Write the loop over roles yourself, in the same style as the instances loop (read `Owner` for each role, then run the three commands only for yours). In dry-run mode you should see every detach and delete printed, in that order for each role.

#### Y2-T24.6: The notebook skeleton with a coverage table

The goal is `notebooks/eda.ipynb` with cell 1 as a coverage table. Coverage shows rows per location per day, so a day with gaps is not compared unfairly with a complete one.

Start Jupyter with `jupyter notebook` from the repository root, then create `notebooks/eda.ipynb` with the New menu. Here is the coverage code for cell 1. It assumes your columns are named `location_id` and `ts_utc`. Check with `print(df.columns)` first, and change names to match yours.

```python
import pandas as pd

df = pd.read_parquet("../data/clean/aq_clean.parquet")
df["ts_ist"] = pd.to_datetime(df["ts_utc"], utc=True).dt.tz_convert("Asia/Kolkata")
coverage = (df.groupby(["location_id", df["ts_ist"].dt.date])
              .size().unstack(fill_value=0))

print("incomplete location-days:", int((coverage < 24).sum().sum()))
```

- `groupby([...])` groups rows by location and by the IST calendar date. `.size()` counts the rows in each group.
- `.unstack(fill_value=0)` makes one row per location and one column per date. Missing combinations show 0.
- `print(coverage.iloc[:, -7:])` prints the last seven date columns. `iloc` selects by position.
- `(coverage < 24).sum().sum()` counts the cells with fewer than 24 readings. It is a count of incomplete location-days.
- This assumes one row per location per hour. If your clean data holds several pollutants per hour in separate rows, the counts will exceed 24 and hide gaps, so count distinct hours per day instead (for example with `nunique` on the hour).

**Q1. Why does the teardown script run a dry run first, and why does it use the order it does?**

:::answer Model answer
The dry run prints every change without making it, so you can check each name against your tag list before anything is deleted. The order follows dependencies. The schedule goes first so nothing starts a new run while you remove things. Deleting the function while its trigger still exists would leave a rule firing at nothing, and roles go last because a role is still in use until the resources that depend on it are gone. The `--apply` switch makes the destructive step a deliberate second action.
:::

**Q2. What is the trade-off between stopping a VM and terminating it?**

:::answer Model answer
Stopping keeps the disk and the configuration, so you can start it again, but it still costs for storage. Terminating deletes the VM and its root disk, which stops most charges, but you cannot get it back, and you must recreate it from the scripts. This ticket allows terminate only for the T19 VM, and only after the compute evidence is complete, because that choice cannot be undone.
:::

**Q3. Why convert the timestamps to IST before grouping by hour, and how does the chart show that?**

:::answer Model answer

#### TC1: identity works and cannot write to the secret prefix

The trainer's steps are in two commands, which you run in your own account on screen.

```bash
aws sts get-caller-identity --profile citypulse-pipeline
aws s3 cp x s3://<bucket>/secret/x --profile citypulse-pipeline
```

- `aws` starts the AWS command-line tool.
- `sts` is the security token service. `get-caller-identity` asks AWS who you are right now. It is the first thing to show, so the trainer knows which identity is speaking.
- `--profile citypulse-pipeline` tells the tool to use the named set of credentials, not the default ones. Without it you may run as an administrator, which proves nothing.
- `s3 cp x s3://<bucket>/secret/x` copies the local file `x` into the bucket under the `secret/` prefix. The `<bucket>` is your bucket's name from your README.

Create the local file first with `echo "test" > x`. The copy must be refused. Lines starting with `$` are commands you type.

```term
$ aws sts get-caller-identity --profile citypulse-pipeline
{
    "UserId": "AIDAEXAMPLEID",
    "Account": "123456789012",
```

#### TC2: anonymous access to an object returns 403

The trainer runs this command on a private object in your bucket, using the object's web address.

```bash
curl -s -o /dev/null -w '%{http_code}' <object-url>
```

- `curl` sends a web request with no login, so it is anonymous.
- `-s` hides the progress meter.
- `-o /dev/null` discards the response body. `/dev/null` is a place that throws away anything written to it.
- `-w '%{http_code}'` prints only the three-digit status code. The quotes stop the shell reading the braces.
- `<object-url>` has the form `https://<bucket>.s3.<region>.amazonaws.com/<key>`.

A passing run prints exactly this and nothing else:

```text
403
```

A 200 means the public can read the object, the public-bucket mistake from the case study. A 404 usually means the bucket name or address is wrong, so the test proved nothing. Note that on a private bucket a missing key also gives 403, so copy the URL of an object that really exists. `000` usually means no network or a mistyped domain.

#### TC3: gitleaks finds nothing in the whole history

The trainer runs the scan from the repository root.

```bash
gitleaks detect --source . --log-opts=--all
```

- `gitleaks detect` scans the contents and history of a repository for secrets.

- `--log-opts=--all` passes `--all` to `git log`, so every branch and commit is scanned. A key deleted later is still in the history.

A passing run prints a log line ending `no leaks found`. A failing run prints a line such as `leaks found: 1` with the file and commit. Never copy the secret into evidence. The fix is in the T25.3 section below: deactivate the key and show the rotation outside Git.

#### Y2-T25.3: gitleaks and the pre-commit hook

Do this first. A scanner that runs only once at the end finds mistakes too late.

**Stage 1. Check the scanner.** Run `gitleaks version`. If it fails, install gitleaks from its official releases page and reopen Git Bash.

**Stage 2. Write the hook configuration.** Create `.pre-commit-config.yaml` at the repository root. A pre-commit configuration lists the external hook repositories to run. Here is the structure. You fill in the two values marked with angle brackets.

```yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: <release tag from the gitleaks releases page>
    hooks:
      - id: gitleaks
```

- `repos:` lists the hook sources. `repo:` is the address of one of them.
- `rev:` pins the hook to one release tag, so it cannot change without notice. Copy the tag from the gitleaks releases page.
- `hooks:` and `id: gitleaks` name the hook to run.

**Stage 3. Install the hook and test it.** Install pre-commit once, then install the hook into your local clone:

```bash
pip install pre-commit
pre-commit install
pre-commit run --all-files
```

- `pip install pre-commit` installs the tool.
- `pre-commit install` writes a hook into `.git/hooks`, so every commit runs the checks first.
- `pre-commit run --all-files` runs every hook now. The gitleaks line should end `Passed`.

**Stage 4. Run the scan on full history.** This is TC3. Run `gitleaks detect --source . --log-opts=--all`. The last line should end `no leaks found`. Run it live in front of the trainer, then paste the result into the pull request description.

**If gitleaks finds a leak.** Do not paste the secret anywhere. Use the AWS command line to find the key by its ID, deactivate it, and create a replacement outside Git:

```bash
aws iam list-access-keys --user-name <user> --profile <admin-profile>
aws iam update-access-key --user-name <user> --access-key-id <key-id> --status Inactive --profile <admin-profile>
```

- `list-access-keys` prints the key IDs and their status for one user. It never prints the secret part.
- `update-access-key` with `--status Inactive` turns the key off. The old value no longer works, even though it is still in the history.
- `--profile <admin-profile>` names a profile that has permission to manage keys. Your pipeline profile usually cannot do this, which is correct.

| gitleaks prints `leaks found: 1`. | A key was committed earlier and is still in the history. | Deactivate the key, show the rotation outside Git, rerun gitleaks. |
| `$'\r': command not found` from a script. | The script has Windows line endings. | Ask the squad to fix the file in the repository. Do not commit a private copy. |
| teardown_check.sh lists a stopped instance. | The owner tag does not match the name passed to the teardown. | Check the tag with `aws ec2 describe-instances`, then dry run and apply again. |
| teardown_check.sh shows a bucket line ending `False`. | The public-access block is off for that bucket. | Turn the block on, then rerun the check. |
| TC5 prints nothing for `git tag -l v0.4.0`. | The tag was never pushed, or never created. | Create it on main and run `git push origin v0.4.0`. |
| `gh release view v0.4.0` says release not found. | The tag exists but the Release does not. | Run `gh release create v0.4.0`, then rerun TC5. |

The trainer asks five questions. Answer in your own words, and use your own evidence. Do not copy the model answers as your personal history.

**Question 1: Why must the identity test show AccessDenied, rather than just a successful sign-in?**

:::answer Model answer
A sign-in shows only that the identity exists. AccessDenied shows that AWS actually refused a forbidden action, so the limit is proven, not assumed.
:::

**Question 2: Why do you keep the bucket but delete the function and the virtual machine? Name the trade-off.**

:::answer Model answer
The bucket holds data the analytics sprint needs. The function and VM cost money while idle. The trade-off is a small storage cost in exchange for keeping the data. The teardown check proves nothing else remains.
:::

**Question 3: Walk me through what you personally did in this ticket.**

:::answer Model answer
Name your own commits by SHA, the file each one changed, and the command you ran to check it. Prepare these from your own git log before the viva.
:::

**Question 4: Why is removing a leaked key in a new commit not enough?**

:::answer Model answer
Git keeps every earlier commit, so anyone who clones the repository can recover the key. Deactivating it in AWS stops it signing in. Rewriting history is a team decision and does not replace rotation.
:::

**Question 5: What does the 403 in TC2 prove, and what would a 200 mean?**

:::answer Model answer
The 403 means AWS refused a request with no identity, so the public cannot read the object. A 200 would repeat the public-bucket mistake from the case study.
:::
