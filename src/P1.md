TITLE: Project 1 — Air-Quality Monitor
SUB: You will be able to run, explain and extend a small app that cleans sensor data, predicts pollution, serves it over HTTP, shows it on a dashboard and ships it through an automated pipeline.

## What you are building

Someone opens a web page. It shows a title, a table of four air-quality monitoring stations, and a bar chart that compares their average pollution. Below the chart is a small form. The visitor picks an hour of the day and types the last pollution reading they saw. When they press the button, the page shows a predicted PM2.5 value (PM2.5 means fine dust particles, measured in micrograms per cubic metre), a label such as "Unhealthy", and one sentence of advice written by a language model that runs on the same computer.

The same numbers are also available from a web address, so other programs can use them. When you push your changes to GitHub, an automatic service tests the code, packages it, and puts the new version online. You do this without copying files to a server by hand.

## The architecture

The project is a set of small Python files. Each file does one job. Read the animation first to see how data moves between them. The table after it says what every file is for.

```flow
TITLE: How one reading becomes a table, a prediction and a dashboard
NODES: Files on disk | pipeline.py and train.py | main.py (FastAPI) | dashboard.py (Streamlit)
STEPS:
1>2 :: readings.csv :: pipeline.py reads the raw CSV, removes the bad rows and works out the station statistics.
2>3 :: model.joblib :: train.py saves the trained model to a file. main.py loads that file when the server starts.

4>3 :: POST /predict :: The dashboard sends an hour and a last reading to the API.
3>4 :: pm25 and category :: The API checks the input, runs the model and sends back the prediction.

After the animation, the arrows mean "sends data to". Node 1 is not a program. It is a set of files on your disk. Node 2 runs in your terminal when you type `python` commands. ## Starting from zero

**Terminal and command line.** A terminal is a text window where you type instructions to your computer. Each instruction is a command, such as `cd citypulse`, which means change directory: move into the folder called `citypulse`. A folder (also called a directory) holds files and other folders. On Windows, use Git Bash, which comes with Git for Windows. On macOS and Linux, use the built-in Terminal. The commands in this chapter are written for that kind of shell.

**Python and scripts.** Python is a programming language. A script is a file of Python code that you run with `python filename.py`. A function is a named block of code you call by its name, with values in brackets. A variable is a name that holds a value, such as `before = 675`. A module is a Python file that other files import.

**Libraries and pip.** A library is code written by someone else that you install and use. A package is the same idea, packaged for installation. `pip` is the tool that installs Python packages. It reads a list in `requirements.txt`, and each line of that list names one library.

**pandas.** pandas is a library for working with tables. Its main type is the DataFrame: a table with named columns and numbered rows. Filtering keeps some rows, `groupby` puts rows into groups, and `agg` works out a summary for each group. The earlier Day chapters cover pandas in depth. In this project it reads the CSV, cleans it and computes the station statistics.

**scikit-learn and the model.** scikit-learn is a library of machine-learning tools. A model is a rule that turns inputs into a predicted output. Training means showing the model examples so it can learn the rule. Here the model is `LinearRegression`, which finds the best straight-line formula that maps the inputs (hour and previous reading) to the output (the next reading). It is simple and fast, which makes it a good first model.

**joblib.** joblib saves a Python object, such as a trained model, to a file, and loads it back later. The file is `model.joblib`. Training and serving use the same saved file, so the API uses exactly the model that you tested.

**matplotlib.** matplotlib is a plotting library. It draws charts and can save them as image files, such as PNG. `Agg` is a drawing mode that does not need a screen, so it runs on a server too.

**FastAPI, uvicorn and Pydantic.** An API is a set of addresses that programs call to ask for data or actions. HTTP is the protocol used for these calls. A request has a method, such as GET (ask for data) or POST (send data). FastAPI is a library that lets you write these addresses, called endpoints, as Python functions. uvicorn is the server program that listens for requests and runs your FastAPI app. Pydantic checks that incoming data has the right type and range before your code runs.

**JSON.** JSON is a text format for structured data, written with curly brackets for objects and square brackets for lists. The API sends its answers as JSON, and the dashboard reads them.

**curl and jq.** curl is a command that sends HTTP requests from a terminal. jq is a command that reads JSON and prints parts of it. You use both to test the API before you build the dashboard.

**Streamlit and requests.** Streamlit is a library that turns a Python script into a web page. Each time a visitor changes a widget, Streamlit runs the script again from the top. requests is a library that sends HTTP requests from Python code. The dashboard uses it to call the API.

**Hugging Face transformers, torch and the LLM.** An LLM (large language model) is a model that generates text. transformers is a library that downloads and runs such models. torch is the numerical engine it runs on. Qwen2.5-0.5B-Instruct is a small free model with about half a billion parameters, which is small enough to run on a normal CPU. A parameter is one of the numbers inside the model that were learned during training.

**pytest and assert.** pytest is a test runner. It finds functions whose names start with `test_` and runs them. Inside a test, `assert` checks a condition. If the condition is false, the test fails. FastAPI's `TestClient` lets a test send requests to the app without starting a real server.

**Git and GitHub.** Git records the history of your files. Each saved snapshot is a commit. GitHub is a website that stores Git repositories (projects tracked with Git) online. `git push origin main` sends your commits to the `main` branch on the remote copy called `origin`.

**Docker and containers.** A container is a sealed box that holds your app together with everything it needs to run. Docker builds a container image from a Dockerfile, and runs images as containers. The same image runs the same way on your laptop and on a cloud machine.

**GitHub Actions and CI/CD.** GitHub Actions runs a list of steps on a fresh virtual machine every time an event happens, such as a push. The list lives in a YAML file. YAML is a text format where indentation shows structure. CI (continuous integration) means test every change automatically. CD (continuous deployment) means ship the tested change automatically.

**Step 2 of 20: Ingest the raw readings.** Your goal is a file with a week of hourly PM2.5 readings for four stations. The file must include a few bad rows on purpose, because the cleaner in Step 3 has to find them.

The course code for the generator is shown below. Two things are not shown in the source: the lines that create the list `rows` and the timestamp `ts`, and the full values in the three extra rows, which the slide writes as `...`. You must fill those in yourself. Any hourly timestamp works, as long as each station has 168 different hours.

```python
STATIONS = {"ST-01":42,"ST-02":55,"ST-03":38,"ST-04":61}   # baselines
for h in range(168):                       # 7 days, hourly
    rush = 1.3 if (6<=h%24<=10 or 17<=h%24<=21) else 0.8
    for s,base in STATIONS.items():
        val = base + 8*gauss(1,.2)*rush + gauss(0,4)
        rows.append([s, ts, "pm25", round(val,1)])
rows += [["ST-02",...,-3.0], ["ST-09",...], ["ST-01","bad-ts",...]]
```

`STATIONS` is a dictionary, which maps each station id to its baseline pollution level. The first `for` loop runs 168 times, once per hour, because 7 days times 24 hours is 168. `h%24` is the remainder when `h` is divided by 24, so it gives the hour of the day from 0 to 23. The line with `rush` sets a multiplier of 1.3 for the morning hours from 6 to 10 and the evening hours from 17 to 21, and 0.8 otherwise. The rush-hour peak is what you will see later on the chart. The inner loop runs once per station. `gauss(1,.2)` draws a random number from a bell curve centred on 1 with spread 0.2. `gauss(0,4)` adds random noise of spread 4. `round(val,1)` keeps one decimal place. `rows.append([...])` adds one reading as a list of four values: station, time, pollutant name, and value.

The last line adds three faulty rows. A negative value (-3.0) at ST-02, a station name that is not in the list (ST-09), and a timestamp that cannot be read (`bad-ts`). These are the faults the cleaner must catch.

```

**Step 3 of 20: Clean and validate.** Your goal is a function `load` that returns only trustworthy rows. This is the most important step in Part A, because every number later depends on it.

```python
def load(path="data/readings.csv"):
    df = pd.read_csv(path)
    df["ts"] = pd.to_datetime(df["ts"], errors="coerce")
    df = df[df.station_id.isin(STATIONS)]
    df = df[df.value.between(0, 500)]
    df = df.dropna(subset=["ts"]).drop_duplicates(["station_id","ts","pollutant"])
    print(f"clean: {before} -> {len(df)} rows ({before-len(df)} dropped)")
    return df
```

`def load(path=...)` defines a function called `load`. The value in brackets is a default: if you call `load()` with no argument, it reads `data/readings.csv`. Line 2 reads the file into a DataFrame called `df`. Line 3 turns the `ts` column from text into real date-times. `errors="coerce"` tells pandas to replace any value it cannot read with `NaT` (Not a Time) instead of stopping. Line 4 keeps only rows whose `station_id` appears in `STATIONS`. `isin` means "is one of". Line 5 keeps rows whose value is from 0 to 500. `between` includes both ends. Line 6 removes rows with no valid time, using `dropna`, and then removes repeated rows with the same station, time and pollutant, keeping the first. Line 7 prints the row count, and `return df` gives the cleaned table back to whoever called the function.

The slide's `print` line uses a variable called `before`, but the slide does not define it. Add `before = len(df)` directly after line 2, so the number of rows is recorded before any filtering. Without it, Python stops with `NameError: name 'before' is not defined`.

The line `print(f"clean: ...")` starts with `f`, which makes it an f-string. Anything inside `{ }` is replaced with its value. Expected output:

It shows 675 rows before cleaning and 672 after, so the three planted faults were removed. You know it worked when the numbers match. The trace below follows the four filtering lines on a table of four rows, so you can see what each line removes.

def per_station(df):
    return (df.groupby("station_id")["value"]
              .agg(["count", "mean", "max"]).round(1))

`def per_station(df)` takes a cleaned table. The brackets around the whole return expression let the chain span several lines.

**Step 7 of 20: Engineer features.** Your goal is a table where every row has the hour of day and the previous reading at the same station. These are the inputs to the model.

```python
def features(df):
    df = df.sort_values(["station_id","ts"]).copy()
    df["hour"] = df.ts.dt.hour
    df["prev"] = df.groupby("station_id").value.shift(1)   # lag-1
    return df.dropna(subset=["prev"])
```

`sort_values` puts rows in order by station and then by time, so that the previous row really is the previous hour. `.copy()` makes a separate table, so the original is not changed. `df.ts.dt.hour` reads the hour from each timestamp: `.dt` gives access to the date and time parts of a column. `shift(1)` moves each value down by one row. Grouped by station, that means each row gets the previous reading from the same station. This is called a lag. The first reading of each station has no previous value, so it becomes `NaN` (missing). The last line removes those rows.

```term
$ python -c "from train import *; print(features(load())[['station_id','hour','prev','value']].head())"
station_id  hour  prev  value
     ST-01     1  50.1   50.7
     ST-01     2  50.7   39.3
     ST-01     3  39.3   50.4
     ST-01     4  50.4   47.5
     ST-01     5  47.5   48.3

The command selects four columns with `[[...]]` and prints the first five rows with `head()`. Each row now has the hour, the previous reading, and the actual value to predict. The first row is hour 1, not hour 0, because hour 0 had no previous reading and was dropped. The `prev` of row two is 50.7, which is the `value` of row one. That is the lag at work.

### Part C: Serve it with FastAPI

**Step 10 of 20: The API skeleton.** Your goal is a running server with a health check, a station-stats endpoint and a validated input model.

```python
app = FastAPI(title="CityPulse Air-Quality Monitor")
_df = load(); _model = joblib.load("model.joblib")
class PredictIn(BaseModel):
    hour: int = Field(ge=0, le=23)
    prev: float = Field(ge=0, le=500)
@app.get("/health")
def health(): return {"status": "ok"}
@app.get("/stations")
def stations(): return per_station(_df).reset_index().to_dict("records")
```

Put these imports at the top of `main.py`, because the source does not show them: `import joblib`, `import pandas as pd`, `from fastapi import FastAPI`, `from pydantic import BaseModel, Field`, and `from pipeline import load, per_station`.

Line 1 creates the application object `app`. The `title` text appears on the automatic documentation page. Line 2 loads the cleaned data and the model once, when the file is imported, and stores them in variables that begin with an underscore. The underscore is a convention that says "private to this file". This happens once at startup, not on every request, which keeps the service fast. `class PredictIn(BaseModel)` defines the shape of a prediction request. `hour` must be a whole number from 0 to 23, and `prev` must be a decimal number from 0 to 500. `Field(ge=0, le=23)` means greater than or equal to 0 and less than or equal to 23. Line `@app.get("/health")` is a decorator. It connects the function below it to a URL and an HTTP method. ### Part D: Plain-English advice

**Step 13 of 20: Advisory from a free CPU model.** Your goal is a function that takes a station, a value and a category, and returns one sentence of advice from a language model that runs on your computer.

```python
from transformers import AutoTokenizer, AutoModelForCausalLM
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
def advisory(station, pm25, category):
    msgs = [{"role":"system","content":"Answer in ONE short sentence."},
            {"role":"user","content":f"PM2.5 at {station} is {pm25} ({category}). Advise residents."}]
    ids = tok(tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True), return_tensors="pt")
    out = llm.generate(**ids, max_new_tokens=50)
    return tok.decode(out[0][ids.input_ids.shape[1]:], skip_special_tokens=True)
```

The source splits the two long lines of the function across several lines. In Python, a normal string cannot run across a line break, so the message and the `tok(...)` call above are joined back into one line each. The first two lines load a tokenizer and the model. A tokenizer turns text into numbers the model understands, and the model is the network that generates the reply. `from_pretrained` downloads the files the first time it runs, which needs internet access once. After that, the files are read from your disk.

`advisory` builds a conversation as a list of messages. The system message is an instruction for the model: answer in one short sentence. The user message contains the station, value and category, so the answer is specific. `apply_chat_template` formats the messages into the exact text layout this model was trained to read. `add_generation_prompt=True` adds the marker that tells the model it is now its turn to speak. `return_tensors="pt"` returns the numbers as PyTorch tensors, which is the format the model expects. `llm.generate(..., max_new_tokens=50)` lets the model write at most 50 tokens. A token is a small piece of text, often a word or part of one. By default this model samples each token from the likely choices, so its answers can vary. The last line removes the prompt from the output and returns only the newly generated tokens as text. `skip_special_tokens=True` hides the internal markers.

The course output shows two calls to this function:

```term

ST-03 (46.4, Moderate): Residents should reduce outdoor activities and use air purifiers.
```

The lines are printed by calls you add at the bottom of `insight.py`, such as `print(advisory("ST-04", 68.8, "Unhealthy"))`. You know it worked when you get one sentence per call. The model runs on the CPU, so each call can take several seconds, and the first call is slower because the model is loaded from disk.

:::trap Model answers vary
The same question can produce a different sentence on each run, and a sentence can be cut off at 50 tokens. Do not write a test that expects an exact sentence. Check instead that the result is a non-empty string.
:::

### Challenge 2: Better features, lower error (MODEL, medium)

**What is asked.** Add humidity and a rolling 3-hour mean to the features in `train.py`, and retrain to beat the baseline.

**Done when:** "train.py prints an MAE below 4.89 µg/m³ and the tests still pass."

**Ideas it needs.** A rolling mean is an average over the last few rows. It must be calculated within each station, so readings from different stations never mix. The most important idea is data leakage: a feature must not use the value you are trying to predict. A rolling mean that includes the current row gives the model the answer.

**Plan of attack.**

1. Note that the data has no humidity column. You must add it in `make_data.py`, using the same method as the other columns, before you can use it as a feature.
2. Add the 3-hour rolling mean within each station. Shift the values by one row first, so that each row uses only earlier readings.
3. Decide how to handle the first few rows, which have no full 3-hour window, and make sure the row count still makes sense.
4. Retrain and compare MAE using the same 80/20 split and the same random seed in `train_test_split`.
5. Check that `/predict` still works. The API builds its own input table with only `hour` and `prev`, so a model trained on more columns will fail until you update `main.py` and `PredictIn` as well.

**Mistakes that fail the test.**

- Leakage, described above. The MAE looks very low, which is a warning sign rather than a success.
- Forgetting to group by station in the rolling mean, so the average crosses from one station into the next.
- Comparing your MAE with a different split or a different data set. The test compares your number to 4.89, so both must come from the same kind of data.
- Retraining and breaking `/predict`, because the API still sends only two inputs.

### Challenge 5: Guard the pipeline in CI (CI/CD, hard)

**What is asked.** Add a `ruff` lint step, and a CI check that fails the build when the test MAE is above 6.0. Deploy only when everything is green.

**Done when:** "A deliberately-bad model fails the Actions run; a good one deploys."

**Ideas it needs.** `ruff` is a fast Python linter, a tool that checks code for common problems. A step in a workflow fails when its command exits with a non-zero status code, which is how the shell reports an error. `sys.exit(1)` in Python exits with status 1. A pipe `|` takes the status of its last command, so a failure earlier in the pipe is hidden. The `needs:` rule from Step 19 keeps deployment waiting for the tests.

**Plan of attack.**

1. Add `ruff` to the install step, and run `ruff check .` locally on the project. Fix or configure the warnings it reports before you add it to CI.
2. Decide how the MAE reaches the CI step. Good options are to make `train.py` write the number to a file, or to exit with a non-zero status when the MAE is above 6.0. Each has a different place for the check to live.
3. Add a workflow step after the training step, which fails the job when the MAE is too high. Make sure the step uses the test set MAE, not a training number.
4. Test the check locally first by making the model deliberately worse, for example by removing a feature, and confirming the check fails.
5. Confirm that `deploy` still has `needs: test`, so a failed check stops the deployment.
6. Push a good model, and confirm the deploy job runs.

**Mistakes that fail the test.**

- Checking the wrong number. The 6.0 limit applies to the test set MAE.
- Hiding the failure with a pipe. Something like `python train.py | tee log.txt` reports the status of `tee`, which succeeds. Check the exit status without a pipe, or use `set -o pipefail` in the shell.
- Forgetting that the workflow in Step 18 runs on pushes to `main` only. Each trial with a bad model is therefore a push to `main`. Test the check locally first, so you do not push broken code to the live branch.
- Turning on ruff without fixing the existing warnings. The lint step then fails before any model check runs.
- Using `>` where the rule needs `>=`, or the other way round. Read the requirement carefully: "exceeds 6.0" is a strict comparison.

## Viva preparation

In the capstone viva, the examiner scores four things from 0 to 5: whether the acceptance criteria are met, your technical depth, your contribution and ownership, and your understanding. Each question below is one the examiner might ask about this project. Answer in your own words, and use the model answers only to check your reasoning.

**Question 1. Walk me through what happens when someone calls `/predict`.**

:::answer Model answer
The request body is parsed as JSON and checked against the `PredictIn` class. If `hour` or `prev` is out of range, FastAPI returns a 422 error and the model never runs. If the input is valid, the function builds a one-row table with the same column names used in training. The model that was loaded at startup predicts the value, which is rounded to one decimal place. The category is then chosen from the thresholds, and the result is returned as JSON.
:::

**Question 2. Why did you split the data 80/20 and report the error on the test set?**

:::answer Model answer
The test set contains rows the model never saw during training. Its error estimates how the model will behave on new readings. If I measured the error on the training rows, the model could look good simply by memorising them. The fixed random seed makes the split repeatable, so my numbers can be compared fairly with later changes.
:::

**Question 3. Why does the cleaner drop rows instead of repairing them?**

:::answer Model answer
A reading with an unknown station, an impossible value or an unreadable time cannot be trusted, and guessing a repair would invent data. Dropping the row keeps the data honest, and the count of dropped rows is printed so that a change in the number is noticed. The data-quality gate then checks the result, so a bad feed stops the pipeline instead of reaching the dashboard.
:::

**Question 4. Why does the API load the data and the model once at startup?**

:::answer Model answer
Loading takes time and memory, and it does not change between requests. If the server loaded the model on every request, each prediction would be slow. Loading once at import time means every request reuses the same objects. The trade-off is that a new model file needs a server restart, which `--reload` handles during development.
:::

**Question 5. What does MAE mean, and is 4.89 a good result?**

:::answer Model answer
MAE is the mean absolute error, the average size of the difference between the predicted and the real value, in the same units as the data. A value of 4.89 micrograms per cubic metre means a typical prediction is about that far from the real reading. Whether that is good depends on the purpose. The course treats it as a useful baseline to improve on, which is a fair position: it was measured on held-out data, and the next step is to try better features and compare fairly.
:::

**Question 6. Trace what happens between `git push` and the live app.**

:::answer Model answer
The push sends the commits to GitHub, which starts the workflow on `main`. The `test` job checks out the code, installs the libraries, builds the data and the model, and runs pytest. If the tests pass, the `deploy` job starts because of `needs: test`. It logs in to the container registry with a secret, builds the image, pushes it under the commit id, and runs the deploy script. The live service then runs the new image.
:::

**Question 7. Why does CI run `make_data.py` and `train.py` before the tests?**

:::answer Model answer
Each CI run starts on a fresh machine that has only the files in the repository. The tests load `readings.csv` and import `main.py`, which loads `model.joblib`. Neither file exists until the scripts create it. Running them in CI also checks that the whole pipeline still works from scratch, not just on my own laptop.
:::

**Question 8. What would you improve first, and how would you know it is better?**

:::answer Model answer
I would improve the features first, because the course notes say good features matter more than fancy models. I would add a rolling mean and check for leakage, then retrain on the same split and compare the test MAE with the baseline. I would only keep the change if the error is lower and the tests still pass. I would also check that the change does not break the API, because the prediction inputs must match the training inputs.
:::

## What goes wrong

| Mistake | Symptom | Fix |
|---|---|---|
| Starting the server before train.py | `FileNotFoundError` for `model.joblib` when uvicorn starts | Run `python train.py` first, then start uvicorn |
| Leaving out `before = len(df)` in load() | `NameError: name 'before' is not defined` | Add the line directly after `read_csv` |
| Copying a multi-line string from the slides | `SyntaxError` at the message line | Join the lines so each string sits on one line |
| Using Windows PowerShell for curl commands | Different options, or an error about `-s` | Use Git Bash, macOS Terminal or a Linux terminal |
| Sending JSON without the content-type header | A 422 error that mentions the body | Add `-H "Content-Type: application/json"` to the curl command |
| Starting the dashboard without the API | Connection refused errors on the page | Keep uvicorn running in its own terminal |
| Building the Docker image before train.py | The container stops at startup | Run `python train.py`, then build |
| Indenting the workflow with tabs | GitHub reports a YAML error, and the workflow does not run | Use spaces, and align each level |
| Trusting pytest after editing without re-running | An old result shown, or a missing model file | Re-run `pytest -q` after each change |
| Expecting 4 passed with only 3 tests | Output shows `3 passed` | Add a fourth test of your own |
| Pushing an image name with capital letters | `docker push` fails with a naming error | Use a lowercase repository name |
| Changing the features without changing the API | `/predict` fails after retraining | Update the input table and the request model together |
