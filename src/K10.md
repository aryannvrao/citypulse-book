## Y2-T31 · Build leak-free feature table, time-based split and naive baseline

*Session 31 · phase M6 · 3 points*

### The ticket in plain words

A model can look brilliant in a notebook and still fail in use. Medical imaging models were once found to recognise the hospital a scan came from, not the disease. For a time series, a random split lets the future leak into training, and the score looks great for the wrong reason.

CityPulse wants to predict tomorrow's PM2.5 (fine dust, in µg/m³) for each station. Before any model is trained, three things must exist.

First, a **feature table**: one row per station and day, where every column could have been known at the moment the prediction is made.

Second, a **time-based split**: the oldest days train the model, the next days validate it, and the newest days test it. A gap day is dropped at each boundary.

Third, a **naive baseline**: a simple guess, such as "tomorrow equals today", scored on the test days. Every later model must beat this number.

This ticket does not train a model. It builds the table, the split and the baseline, so later results can be trusted and compared fairly.

### How your trainer checks it

The trainer checks five acceptance criteria:

1. **Split by date.** Each boundary must satisfy `max(train.date) < train_end < min(val.date)` and `max(val.date) < val_end < min(test.date)`. No shuffled random split may appear (TC2, TC5).
2. **Features look only backwards.** The trainer reads the `LAG` and frame code and your comments. Only `y_next` uses `LEAD` (TC3).
3. **Manifest committed.** It records `train_end`, `val_end`, row counts per split and `test_sha256`. `git ls-files data/splits/manifest.json` must print that path.
4. **Baseline on test only.** `docs/ml-log.md` holds the metric, the row count and the commit SHA. TC4 checks the number.
5. **One feature audited per student.** Your entry names one feature, its availability time and a query that proves it.

Run the five test cases in order, from the squad repository on the lab machine.

**TC1: build the splits and print the manifest.**
Command: `python -m citypulse.features && cat data/splits/manifest.json`

- `python -m citypulse.features` runs your module as a program. The file needs an `if __name__ == "__main__":` block that calls your main function. If you see import errors, run `pip install -e .` once from the repo root.
- `&&` runs the second command only if the first succeeds.
- `cat` prints the manifest.

Passing output has no error, three files `train.parquet`, `val.parquet` and `test.parquet` in `data/splits/`, and a JSON object like this one. The numbers are invented:

```json
{"train_end": "2024-06-30", "val_end": "2024-09-30", "rows": {"train": 1000, "val": 200, "test": 200}, "test_sha256": "3f2a..."}
```

Failing output: `ModuleNotFoundError: No module named 'citypulse'` means the package is not installed or you are in the wrong folder. `KeyError: ['y_next']` means the view lacks the target.

**TC2: run the feature tests.**
Command: `pytest -q tests/test_features.py`

- `pytest` finds and runs the test functions.
- `-q` prints less text.
- The path names the file.

Passing output is a row of dots and a line such as `4 passed`. Failing output shows `F` and a line such as `FAILED tests/test_features.py::test_train_before_val`, with the `assert` line above it.

**TC3: find every use of `LEAD(`.**
Command: `grep -n 'LEAD(' sql/views.sql`

- `grep` searches for the text in quotes. The quotes stop the shell from reading the bracket.
- `-n` prints the line number of each match.

Passing output is exactly one line, in the `y_next` definition. Your line number will differ:

```term
$ grep -n 'LEAD(' sql/views.sql
41:       LEAD(pm25, 1) OVER w AS y_next
```

A second line on a feature column means that feature reads tomorrow. Do not write the text `LEAD(` inside a comment either, because grep would list it. No output at all means `y_next` lost its `LEAD`.

**TC4: recompute the persistence error on test.**
Command: `python -c "import pandas as pd;t=pd.read_parquet('data/splits/test.parquet');from sklearn.metrics import mean_absolute_error as m;print(round(m(t.y_next,t.pm25_d0),2))"`

- `python -c "..."` runs the quoted code as a short program. Semicolons separate statements.
- `pd.read_parquet(...)` loads the test file into `t`.
- `m(t.y_next, t.pm25_d0)` compares tomorrow's true value with today's. That is persistence.
- `round(..., 2)` keeps two decimals.

Passing output is one number equal to the persistence MAE in `docs/ml-log.md`. A different number usually means the log came from validation rows, or the rounding differs.

**TC5: search for random splits.**
Command: `grep -rn 'shuffle=True\|train_test_split' src/`

- `-r` searches every file under `src/`. `\|` means "or". `-n` prints line numbers.

Passing output is nothing. Run `echo $?` straight after: it prints `1`, meaning grep found no match. A printed line names a file and line where a random split is used. Replace it with your date split. A comment that mentions `train_test_split` also matches, so reword it.

### Do it, step by step

#### T31.1 Build the feature view (Data)

**Goal.** A view `v_features_daily` with one row per station and day, holding features known at the end of day d0 and the target `y_next`.

**New technique: a recursive CTE.** A recursive CTE repeats its own step until a stop condition is met. This small example lists the numbers 1 to 7:

```sql
WITH RECURSIVE nums(n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM nums WHERE n < 7
)
SELECT n FROM nums;
```

- `WITH RECURSIVE nums(n) AS (` names a list with one column, `n`.
- `SELECT 1` is the first row. `UNION ALL` adds the rows from the second part.
- `SELECT n + 1 ... WHERE n < 7` adds one to the last row and stops at 7.

Expect seven rows, from 1 to 7.

**Stage 1: a calendar.** Find your date column and range first:

```sql
PRAGMA table_info(fact_air_quality);
SELECT MIN(date), MAX(date) FROM fact_air_quality;
```

Use the date column name that `PRAGMA` shows. Then write a recursive CTE that yields every day between the two dates, using `DATE(d, '+1 day')`. Test it alone and check the first and last dates.

**Stage 2: attach the readings.** First `CROSS JOIN` the calendar with the list of stations (`SELECT DISTINCT location_id FROM fact_air_quality`), so every station has a row for every day. Then `LEFT JOIN` the readings onto that. This keeps every day, even when a reading is missing, and the station id is never empty. The lag columns count rows, so a missing day must still have a row.

**Stage 3: window features.** Define the window once with `WINDOW w AS (PARTITION BY location_id ORDER BY date)` after your `FROM`/`WHERE`. `PARTITION BY location_id ORDER BY date` restarts the window for each station in date order. Add one column at a time:

- `LAG(pm25, 1) OVER w` gives yesterday's value.
- `LAG(pm25, 7) OVER w` gives the value one week earlier.
- `AVG(pm25) OVER (w ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)` averages the last seven days, ending today.
- `LEAD(pm25, 1) OVER w AS y_next` is the one allowed forward look.

Name today's value `pm25_d0` and yesterday's `pm25_d1`, as the trainer's tests and TC4 expect. Use your own column names if your squad's `fact_air_quality` differs (this guide says `location_id` and `station` loosely for the station column).

:::trap A frame that reads tomorrow
A frame such as `1 PRECEDING AND 1 FOLLOWING` averages tomorrow into today. Every feature frame must end at `CURRENT ROW`.
:::

**Stage 4: comments.** Beside each feature, write a comment with its availability time, such as `-- known at end of d-1`.

**Apply and test.** Put `DROP VIEW IF EXISTS v_features_daily;` above your `CREATE VIEW`. Apply `sql/views.sql` the way the README says, then run:

```term
$ sqlite3 citypulse.db "SELECT * FROM v_features_daily LIMIT 5;"
```

Expect five rows with your column names. Empty lag values at the start of each station are correct.

#### T31.2 Write features.py (Backend)

**Goal.** A module that loads the view, drops unusable rows, splits by date, and writes the files. Build it in four stages and test each one before moving on.

**Stage 1: load.** Write one function that reads the view:

```python
import sqlite3

import pandas as pd

from citypulse import config


def load_features() -> pd.DataFrame:
    con = sqlite3.connect(config.SQLITE_PATH)
    df = pd.read_sql("SELECT * FROM v_features_daily", con, parse_dates=["date"])
    con.close()
    return df.dropna(subset=["y_next", "pm25_d0"])
```

- `sqlite3.connect` opens the database. `config.SQLITE_PATH` is your squad's setting for its location.
- `parse_dates=["date"]` turns the text into real dates, so comparisons work.
- `dropna(subset=[...])` removes rows whose target or `pm25_d0` is missing.

Test it with `python -c "from citypulse.features import load_features as f; print(len(f()))"`. It prints a row count, and it must not be zero.

**Stage 2: the split with gap days.** Read the cut-offs from `config/ml.yaml`. The course chapter uses `train_end` and `val_end` as the key names. Use the names your squad chose. First, the rule on a tiny example:

```trace
TITLE: Splitting eight days with a gap on each side
CODE:
dates = [1, 2, 3, 4, 5, 6, 7, 8]
train_end, val_end = 3, 6
train = [d for d in dates if d < train_end]
val = [d for d in dates if train_end < d < val_end]
test = [d for d in dates if d > val_end]
STEPS:
1 :: dates=[1, 2, 3, 4, 5, 6, 7, 8] :: Eight days in date order.
2 :: dates=[1, 2, 3, 4, 5, 6, 7, 8]; train_end=3; val_end=6 :: The two cut-off days are set. Each one is a gap day.
3 :: train=[1, 2] :: Days before train_end. Day 3 is left out.
4 :: train=[1, 2]; val=[4, 5] :: Days strictly between the cut-offs. Days 3 and 6 are left out.
5 :: train=[1, 2]; val=[4, 5]; test=[7, 8] :: Days after val_end. Day 6 is left out.
5 :: train=[1, 2]; val=[4, 5]; test=[7, 8] :: Each day sits in at most one split, in date order.
```

Now write the three filters on your DataFrame. The placeholders are a guide:

```python
def split_by_date(df, train_end, val_end):
    train = df[df["date"] < <train_end>]
    val = df[(df["date"] > <train_end>) & (df["date"] < <val_end>)]
    test = df[df["date"] > <val_end>]
    return train, val, test
```

Turn the cut-offs into timestamps with `pd.Timestamp(...)`. Test the function on a small DataFrame of eight dates, and check the lengths against the trace.

:::tip Assert the rule in code
Write `assert train["date"].max() < train_end` in your tests, so the rule is checked by a machine and not only by you.
:::

**Stage 3: write the files and manifest.** Write each part with `to_parquet(path, index=False)`. `index=False` stops pandas writing row numbers as an extra column. Then take a fingerprint of the test file and write the JSON:

```python
import hashlib
import json
from pathlib import Path

def write_outputs(train, val, test, cfg, out_dir: Path):
    out_dir.mkdir(parents=True, exist_ok=True)
    train.to_parquet(out_dir / "train.parquet", index=False)
    val.to_parquet(out_dir / "val.parquet", index=False)
    test.to_parquet(out_dir / "test.parquet", index=False)
    digest = hashlib.sha256((out_dir / "test.parquet").read_bytes()).hexdigest()
    manifest = {"train_end": str(cfg["train_end"]), "val_end": str(cfg["val_end"]),
                "rows": {"train": len(train), "val": len(val), "test": len(test)},
                "test_sha256": digest}
    (out_dir / "manifest.json").write_text(json.dumps(manifest, indent=2))
```

- `read_bytes()` reads the raw bytes, and `sha256(...).hexdigest()` turns them into 64 hex characters.
- `json.dumps(..., indent=2)` writes readable JSON.

`str(...)` is needed because YAML turns an unquoted date such as `2024-06-30` into a date object, which `json.dumps` cannot write. Check with `sha256sum data/splits/test.parquet` that the digest matches the manifest.

**Stage 4: entry point.** Add `if __name__ == "__main__":` at the bottom and call your functions inside it. TC1 now works.

#### T31.3 Tests and the .gitignore exception (QA/DevOps)

**Goal.** Tests that fail when the split or the target is wrong.

**A pytest test, from zero.** A test is a function whose name starts with `test_`. It uses `assert`, which fails when its condition is false:

```python
def test_addition():
    assert 2 + 2 == 4
```

Run `pytest -q` on it. Change the `4` to `5` and it reports `F`. Your tests work the same way.

**Stage 1: date tests.** Read the three parquet files and write one test for each rule: `max(train.date) < train_end`, `min(val.date) > train_end`, and `min(test.date) > val_end`. Keep the cut-offs in variables at the top of the file.

**Stage 2: target test.** No feature may equal the target. Loop over your feature columns and assert that each one differs from `y_next`:

```python
for col in ["pm25_d0", "pm25_d1"]:
    assert not (test[col] == test["y_next"]).all()
```

`test[col] == test["y_next"]` gives one True or False per row, and `.all()` is True only when every row matches. `not` makes the assert pass when they differ. Replace the list with your own feature names.

**Stage 3: the .gitignore exception.** Check whether Git ignores the manifest:

```term
$ git check-ignore -v data/splits/manifest.json
```

A printed line names the rule that ignores the file. Add `!data/splits/manifest.json` to `.gitignore`, then run `git status --short`. The manifest must now appear as a new file.

:::trap An exception that does nothing
Git cannot re-include a file when its whole folder is ignored. If `data/` is ignored as a folder, ignore only the files inside it, such as `data/splits/*.parquet`, and then re-include the manifest.
:::

#### T31.5 Compute the baselines on test only (every student)

**Goal.** Persistence and seasonal-naive MAE on the test split. Reproduce them yourself.

**New technique: a shift inside groups.** `shift(1)` moves each value down one row, and `groupby` keeps the moves inside each station:

```python
import pandas as pd

df = pd.DataFrame({"station": ["A", "A", "A", "B", "B"], "pm": [10, 20, 30, 40, 50]})
df["yesterday"] = df.groupby("station")["pm"].shift(1)
print(df)
```

- `groupby("station")` splits the rows into one group per station.
- `["pm"].shift(1)` moves each value one row down inside its group.

Expect `yesterday` to read empty, 10, 20, empty, 40. Without `groupby`, station B's first row would wrongly read 30, which is station A's last value.

**Stage 1: load and sort.** Read `data/splits/test.parquet` and sort by `station` and `date`. The shift depends on that order.

**Stage 2: the baselines.** Persistence is `df["persistence"] = df["pm25_d0"]`. Seasonal-naive is the `pm25_d0` value six rows earlier in each station, because day d-6 has the same weekday as the target day d+1. Write it with `groupby` and `shift(6)`. `shift` counts rows, not days, so it is right only while each station's test rows are consecutive days. Check this, and note any gap in the log.

**Stage 3: score.** For each baseline, keep rows where it has a value, compute MAE with scikit-learn's `mean_absolute_error`, and print the name, the MAE and the row count.

:::trap Scoring on other rows
Score the baselines only on test, and on the same rows the model uses. Do not drop rows silently.
:::

Your persistence MAE must match TC4.

### Defend it in the viva

**1. Why must the split be by date and not random?**

:::answer Model answer
A random split puts future days into training. Time-series rows depend on their neighbours, so the model can learn from a day that comes after the day it predicts. The score then looks better than it will be in use. A date split matches reality, where the model only sees the past.
:::

**2. What does the gap day cost, and what does it buy?**

:::answer Model answer
The gap costs one day at each boundary, which is one row per station. It buys safety: the last training day's target is the next day's value, which would be the first validation day if there were no gap. The cost is small.
:::

**3. Show me how you proved that one feature uses only earlier rows.**

:::answer Model answer
A good answer names the feature and its availability time, then shows the query that counts rows read after the prediction time, and the count, which must be zero. A comment is a claim. A query is evidence.
:::

**4. Why is the baseline scored on test only?**

:::answer Model answer
Test is the only data that has not guided any choice. Scoring the baseline on validation rows, then tuning models against it there, would favour the models. Test keeps the comparison fair.
:::

**5. What would you do if the TC4 number did not match the log?**

:::answer Model answer
I would check the inputs first: the split file, the row set, the sort order and the rounding. I would recompute on test only, then correct the log if it is wrong, and say why in the pull request.
:::

```python
import hashlib

def file_sha256(path):
    h = hashlib.sha256()
    with open(path, "rb") as f:
```

#### Y2-T33.2 Feature functions in src/features.py

**Goal.** Write two pure functions: they take a table, return a new one, and read no files and print nothing.

**Technique: groupby and shift.** Shifting inside each group stops values crossing from one group into another. Here is a fictional example with two shops:

```python
import pandas as pd

shops = pd.DataFrame({"shop": ["Bakery", "Bakery", "Florist", "Florist"], "sales": [10, 14, 3, 5]})
shops["next_sales"] = shops.groupby("shop")["sales"].shift(-1)

```

`groupby("shop")` makes one group per shop. `shift(-1)` moves each value up one row inside its group, so the last row of each group gets `NaN`, a marker for a missing value. Expect `next_sales` to be 14, NaN, 5 and NaN. Without `groupby`, the first Bakery row would receive a Florist value. The trace shows the same idea step by step.

1. Why does the baseline use a time split and not a random shuffle?

:::answer Model answer
PM2.5 is a time series, so each hour depends on earlier hours. A random shuffle puts future rows into training, so the model learns from information it would not have when forecasting. A time split matches real use, so the score is honest.
:::

:::answer Model answer
Committing the file makes a clean clone work offline with identical data, but the repository grows. A fetch script keeps the repository small, but it depends on the source staying available and unchanged. A good answer names both costs, the squad's choice and the fingerprint that proves the copy.

3. Walk me through the leakage test you wrote. What does it prove?

:::answer Model answer

:::answer Model answer
Naive persistence uses only the current value, so any model must beat it to be worth using. MAE is the average error in PM2.5 units. A lower MAE on the same rows means the model adds something. If it does not, the ticket requires the gap to be explained.

### The ticket in plain words

CityPulse is a Bengaluru city-data platform. One job it does is forecast PM2.5 for the next hour. PM2.5 is fine dust in the air, measured in micrograms per cubic metre. The Project 6 baseline model sees only current readings and simple time parts, such as the hour.

Bengaluru air depends on what happened in the last few hours, on rush-hour traffic and on events such as Diwali. So you will add five new features. A feature is an input column the model reads. Examples are the reading from one hour ago, or a festival flag that is 1 on a festival day and 0 otherwise.

The analyst wants evidence, not guesses. For each feature you remove it, retrain on the same data and measure how much the error grows. That check is an ablation. A feature that does not move the error beyond random noise has not earned its place.

The second rule is about where the work happens. The API receives raw rows straight from the data file. If features are built in a notebook and rebuilt by hand in the API, the two copies drift apart and predictions degrade with no error message. This is called training/serving skew. So every feature must live inside one Pipeline, a chain of named steps that is fitted once and then runs the same way on new rows.

#### Y2-T34.3 Add TimeFeatures inside the Pipeline

**Goal.** A class `TimeFeatures` that adds your columns and is the first step of the Pipeline, named `time_features`.

**Stage 1: an empty step.** The base classes from scikit-learn make your class act as a step.

```python
from sklearn.base import BaseEstimator, TransformerMixin

class TimeFeatures(BaseEstimator, TransformerMixin):
    def fit(self, X, y=None):
        return self

    def transform(self, X):
        X = X.copy()
        return X
```

`fit` learns nothing, so it returns `self`. `transform` copies the table so the caller's table is never changed. Test it on a one-row table, and check the output is unchanged.

**Stage 2: lags inside each station.**

```python
g = X.groupby("station")["pm25"]
X["pm25_lag1"] = g.shift(1)
X["pm25_lag24"] = g.shift(24)
```

`groupby` makes one group per station, and `shift` moves values down inside each group. Without `groupby`, the first row of one station would receive the last value of the station above, which your test in T34.5 catches.

**Stage 3: a rolling mean that does not see the answer.** The P6 pattern `s.rolling(3).mean()` includes the current row, which holds the answer. Shift first:

```python
X["pm25_roll3_mean"] = g.transform(lambda s: s.shift(1).rolling(3).mean())
```

Inside the function, `shift(1)` moves the series down one row, so the window holds only earlier hours.

:::trap Rolling over the current row
Without `shift(1)`, the window includes the current hour. The model then learns from the answer, and the ablation shows a gain that will not hold on new data.
:::

**Stage 4: hour features in Indian time.**

```python
import numpy as np
hour = pd.to_datetime(X["ts"]).dt.tz_convert("Asia/Kolkata").dt.hour
X["hour_sin"] = np.sin(2 * np.pi * hour / 24)
X["hour_cos"] = np.cos(2 * np.pi * hour / 24)
```

`tz_convert` changes the time zone first, then `.dt.hour` reads the hour. The sine and cosine place each hour on a circle.
**Stage 5: insert the step.** Put the step first in the Pipeline list, before the ColumnTransformer:

**1. Why must the lag features live inside the Pipeline rather than in pandas before the split?**

:::answer Model answer
If lags are built in a notebook, the API must rebuild them by hand, and the copies can drift apart silently. Inside the Pipeline there is one set of steps, and the step checks the row order it depends on, so mistakes fail loudly.
:::

**2. What is the trade-off of estimating the noise floor from five seeds?**

:::answer Model answer
Five seeds give a rough spread, and the estimate itself moves when the seeds change. Too few seeds can make the floor too small, so a weak feature looks like a win, or too large, so a real feature looks like no evidence. More seeds cost more training time. State the seed count and the std type in the table, so a reviewer can judge the verdicts.
:::

**3. What did you personally do in this ticket, and how would the trainer see it in Git?**

:::answer Model answer
Name the feature you owned, the commit that added it, the test that covers it, and the row in the ablation table that shows its delta. Then explain one decision you made and why. Write your own version with your own commit and numbers.
:::

**4. Why convert to Asia/Kolkata before taking the hour?**

:::answer Model answer
02:30 UTC is 08:00 in India. Reading the UTC hour shifts the daily cycle by five and a half hours.
:::

**5. Why does the rolling mean need `shift(1)` first?**

:::answer Model answer
The feature may use only values known before the hour being predicted. Without the shift, the window contains the current PM2.5, which is the target, so the ablation shows a gain that disappears on new data.
:::

### The ticket in plain words

#### Y2-T35.1 Sort the training rows and build time-ordered folds

**Goal.** Build five folds where each validation part comes after its training part, and record their date ranges.

**Technique first: `TimeSeriesSplit`.** This class gives you index positions, not rows. For each fold it returns two lists of positions: the training positions and the validation positions. Here is a small example on ten numbers:

```python
from sklearn.model_selection import TimeSeriesSplit
import numpy as np

X = np.arange(10).reshape(-1, 1)
cv = TimeSeriesSplit(n_splits=3)
for train_pos, val_pos in cv.split(X):
    print("train", train_pos, "validate", val_pos)
```

Line by line:

- `X = np.arange(10).reshape(-1, 1)` makes ten rows, numbered 0 to 9.
- `cv = TimeSeriesSplit(n_splits=3)` asks for three folds. The validation part always comes after the training part.
- `for train_pos, val_pos in cv.split(X):` loops over the folds. Each fold gives two arrays of positions.
- The `print` line shows the positions for each fold.

Expected output is three lines. The first fold trains on positions 0 to 3 and validates on positions 4 and 5, and the last validates on positions 8 and 9. Training positions grow with each fold, and no validation position appears in its own training part.

#### Y2-T35.3 Write `tune.py` with two searches

**Goal.** One script that runs a grid search for the Ridge pipeline and a randomised search for a tree pipeline, both on training rows only, and prints the top five rows.

**Technique first: `GridSearchCV` and `RandomizedSearchCV`.** A grid search fits every combination. A randomised search fits `n_iter` combinations drawn at random. Both score each candidate with cross-validation and keep the best. Here is a small example with a Pipeline and a grid:

```python
from sklearn.linear_model import Ridge
from sklearn.model_selection import GridSearchCV
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
import numpy as np

X = np.arange(20, dtype=float).reshape(-1, 1)
y = 3.0 * X[:, 0] + 1.0
grid = GridSearchCV(make_pipeline(StandardScaler(), Ridge()),
                    {"ridge__alpha": [0.1, 1.0, 10.0]}, cv=4,
                    scoring="neg_mean_absolute_error")
grid.fit(X, y)
print(grid.best_params_)
```

Line by line:

- `make_pipeline(StandardScaler(), Ridge())` chains a scaler and the model. The step name for Ridge is `ridge`, the lowercase class name.
- `{"ridge__alpha": [0.1, 1.0, 10.0]}` is the grid. The key is the step name, two underscores, then the setting.
- `scoring="neg_mean_absolute_error"` makes the search score by negative MAE, so the best score is the closest to zero.
- `grid.fit(X, y)` runs the search. It fits 3 candidates on 4 folds, then refits the winner on all rows.
- `print(grid.best_params_)` shows the winning setting.

Expected output is a dictionary such as `{'ridge__alpha': 0.1}`. Any winning value is acceptable here, because this is only practice.

**Stage 1: the Ridge grid in `tune.py`.** Use the grid you pre-registered, not the example values. Build the Pipeline with your `build_pipeline` from `src/pipeline.py`, which the Features v2 PR already provides.

Line by line:

- The import brings in the two search tools and the Pipeline builder.
- `cv = TimeSeriesSplit(n_splits=5, gap=24)` uses the same folds you checked in T35.1.
- `build_pipeline(cfg)` returns the Ridge Pipeline. The key `model__alpha` addresses the Ridge step, which the chapter names `model`.
- `cv=cv` passes the time-ordered folds. The grid search must never use `KFold`.
- Nothing runs yet. This line only builds the search object.

```python
                                 n_iter=20, random_state=seed, cv=cv,
                                 scoring="neg_mean_absolute_error")
```

Line by line:

- `clone(...)` makes an unfitted copy of the Pipeline.
- `.set_params(model=RandomForestRegressor(...))` replaces the step named `model` with a random forest. The Pipeline keeps the same preprocessing steps.
- The distributions list the values each setting may take. `None` for `max_depth` means no depth limit.
- `n_iter=20` asks for 20 random candidates out of the 27 possible combinations.
- `random_state=seed` makes the random draws repeatable.


Line by line:

- `pd.DataFrame(ridge_search.cv_results_)` turns the results into a table with one row per candidate.

#### Y2-T35.4 Choose the simplest config within one std

**Goal.** Apply the pre-registered rule to the top five and save the chosen candidate with its metrics.

**Technique first: the decision rule as a trace.** The rule has three steps. Find the best mean MAE, add its standard deviation to get a limit, then keep the simplest candidate under that limit. Here is the rule written as a tiny program, with each candidate as `(complexity, mean MAE, std)`:

```trace
TITLE: Simplest config within one std
CODE:
rows = [(1, 12.5, 0.4), (2, 12.2, 0.3), (3, 12.0, 0.5)]
best = min(rows, key=lambda r: r[1])
limit = best[1] + best[2]
eligible = [r for r in rows if r[1] <= limit]
```

```python test
    # each row is (complexity, mean_mae, std_mae); a lower complexity means simpler
    best = min(rows, key=lambda r: r[1])
```

### Defend it in the viva

Each answer shows the reasoning you should give out loud. Use your own work in your own words, and name the commit or file you changed.

**1. Why did you use `TimeSeriesSplit` and not `KFold` with shuffling?**

:::answer Model answer
Hourly readings sit close to their neighbours in time, so a shuffled split can train on hour 10 and validate on hour 11. The score then looks better than the model is on future data. `TimeSeriesSplit` trains only on earlier rows and validates on the period after them, which matches how the model will be used. The grep in TC1 proves the shuffled version is absent.
:::

**2. What is the trade-off in your gap setting?**

:::answer Model answer
A larger gap keeps lag features in the validation part from reaching into the training part, so the validation score is more honest. It also removes more rows from each fold. The ticket sets `gap=24`, but the splitter counts rows, not hours. With several stations, 24 rows covers less than a day. I would state which value I used, why, and what it would change, rather than hide it.
:::

**3. What did you personally do, and how can we see it?**

:::answer Model answer
A good answer names the subtask you owned, the file you changed and the commit message that shows it. It describes one decision you made, such as the grid values, the complexity definition or the run sheet timing, and why. The trainer checks this against your commits, so name only what your commits show.
:::

**4. Why did you open the test window only once?**

:::answer Model answer
Each time the test score changes a choice, the test rows act as a training set, and the reported score becomes too optimistic. The honest number is the first and only look. I logged that single result with its timestamp and git SHA, so anyone can check it did not change.
:::

**5. Why does the rule choose the simplest config within one standard deviation rather than the best one?**

:::answer Model answer
The best mean MAE is partly luck of the folds. Two settings within one standard deviation of each other cannot be told apart reliably. The simpler setting usually generalises at least as well and is easier to explain, so I choose it. Because I wrote the rule before running anything, the choice is not a judgement made after seeing the result.
:::

#### Subtask Y2-T36.4: compare the models on the same folds

The goal is to train three models on the same folds and record the numbers. Two techniques are new here: cross-validation and the mean ± std summary.

First, cross-validation. Cross-validation splits the training rows into folds. For each fold, the model trains on the other folds and is tested on that one. You get one score per fold. Now the mean and the spread tell you how the model behaves across data it has not seen. A small mean with a small spread is a stable model.

Second, `TimeSeriesSplit` keeps time order. Each fold trains on earlier rows and tests on later ones, so the model never sees the future. Here is a tiny example of the splitter on twelve numbers:

```python
from sklearn.model_selection import TimeSeriesSplit
import numpy as np

X = np.arange(12).reshape(-1, 1)
for i, (train_idx, test_idx) in enumerate(TimeSeriesSplit(n_splits=3).split(X)):
    print(f"fold {i}: train {train_idx.min()}..{train_idx.max()}  test {test_idx.min()}..{test_idx.max()}")
```

Line by line: `np.arange(12).reshape(-1, 1)` makes twelve rows of one column. `TimeSeriesSplit(n_splits=3)` creates the splitter. `.split(X)` yields a training index list and a test index list for each fold. The loop prints the first and last row of each. Expected output:

```term
$ python3 tss_demo.py
fold 0: train 0..2  test 3..5
fold 1: train 0..5  test 6..8
fold 2: train 0..8  test 9..11
```

You know it worked when each test range starts right after its training range ends, and the training range grows with each fold. Your squad's `cv` object from Y2-T35 is a `TimeSeriesSplit` too. Reuse that same object, and never build a new one with different settings for one model.

Third, the models. The ticket asks for RandomForest with `min_samples_leaf` of 5 or more (for example `RandomForestRegressor(min_samples_leaf=5, random_state=42)`, which stops each tree growing a leaf for a single row and so limits overfitting) and HistGradientBoosting (`HistGradientBoostingRegressor(random_state=42)`), both from `sklearn.ensemble`, beside your tuned Ridge from Y2-T35. The slice tables in the next subtask use the leading model, which is the one with the best CV MAE once ties are accounted for.

Now the pipelines. The course's Demo Day comparison uses the same pipeline shape for each model, and changes only the model step. The pattern is the same loop as the example in the course chapter: build the pipeline once per model, then score each one with the same `cv`. Write the loop yourself, with the names your squad uses. The key idea is that only the model changes. Here is the shape with placeholders, so you can see where each piece goes:

```python
from sklearn.model_selection import cross_validate

for name, est in models.items():
    pipe = make_pipeline_for(est)
    r = cross_validate(pipe, X_train, y_train, cv=cv, scoring="neg_mean_absolute_error")
    mae = -r["test_score"]
    print(name, round(mae.mean(), 2), round(mae.std(), 2), round(r["fit_time"].mean(), 1))
```

This block is a shape, not your solution. `make_pipeline_for`, `models`, `X_train` and `y_train` are names you must fill in from your own code. Line by line: `cross_validate` scores the pipeline on each fold. `cv=cv` reuses the same folds for every model. `scoring="neg_mean_absolute_error"` returns MAE as a negative number, because scikit-learn treats higher scores as better, so the line `-r["test_score"]` flips the sign back. `fit_time` holds the seconds each fold took to train.

Now a trap about the spread. NumPy's `.std()` divides by the number of folds, which is the population standard deviation. `statistics.stdev` divides by one less, which is the sample standard deviation. The two give different numbers for the same list. Pick the convention that matches the course output you were given, and write it in the table header. Here is a small, tested helper so you can check the arithmetic on paper.

```python test
import statistics

def mean_std(values):
    """Return the mean and the sample standard deviation, rounded to 2 places."""
    return round(statistics.mean(values), 2), round(statistics.stdev(values), 2)

assert mean_std([2.0, 4.0, 6.0]) == (4.0, 2.0)
assert mean_std([5.0, 5.0, 5.0]) == (5.0, 0.0)
```

Line by line: `statistics.mean` and `statistics.stdev` are standard-library functions. The function rounds both results. The first `assert` checks a list whose sample standard deviation is 2.0. The second checks a list with no spread. `assert` stops the program with an error if the condition is false. A silent run means every check passed. The block prints nothing when it passes.

Artefact size, the last column, is the size of the saved file in kilobytes. Save each model with joblib and read the size with the standard library:

```python

joblib.dump(est, "models/rf_candidate.joblib")
size_kb = os.path.getsize("models/rf_candidate.joblib") / 1024
print(f"artefact {size_kb:.0f} KB")
```

Line by line: `joblib.dump` writes the fitted model to a file. `os.path.getsize` returns the file size in bytes. Dividing by 1024 converts to kilobytes. `:.0f` prints the number with no decimal places. Run it only after you have fitted the model on the full training window. Do not save an unfitted model.

#### Subtask Y2-T36.5: build the slice tables

The goal is a table for each grouping, computed on test-window rows only, with the hour in IST. Two techniques are new: `groupby` and time-zone conversion.

`groupby` splits rows into groups by one column, then computes a summary for each group. Here is a tiny example with three rows:

```trace
TITLE: Grouping errors by station
CODE:
rows = [("ST-01", 4), ("ST-02", 9), ("ST-01", 2)]
totals = {}
counts = {}
for station, err in rows:
    totals[station] = totals.get(station, 0) + err
    counts[station] = counts.get(station, 0) + 1
STEPS:
1 :: rows=[("ST-01", 4), ("ST-02", 9), ("ST-01", 2)] :: Three rows, each a station and an absolute error.
2 :: totals={} :: The running totals start empty.
3 :: totals={}; counts={} :: The running counts start empty.
4 :: station="ST-01"; err=4; totals={}; counts={} :: The loop takes the first row, which belongs to ST-01.
5 :: station="ST-01"; err=4; totals={"ST-01": 4}; counts={} :: get returns 0 for a new key, so 4 is stored.
6 :: station="ST-01"; err=4; totals={"ST-01": 4}; counts={"ST-01": 1} :: The count for ST-01 starts at 1.
4 :: station="ST-02"; err=9; totals={"ST-01": 4}; counts={"ST-01": 1} :: The second row belongs to ST-02.
5 :: station="ST-02"; err=9; totals={"ST-01": 4, "ST-02": 9}; counts={"ST-01": 1} :: ST-02 is new, so its total starts at 9.
6 :: station="ST-02"; err=9; totals={"ST-01": 4, "ST-02": 9}; counts={"ST-01": 1, "ST-02": 1} :: ST-02 count starts at 1.
4 :: station="ST-01"; err=2; totals={"ST-01": 4, "ST-02": 9}; counts={"ST-01": 1, "ST-02": 1} :: The third row is ST-01 again.
5 :: station="ST-01"; err=2; totals={"ST-01": 6, "ST-02": 9}; counts={"ST-01": 1, "ST-02": 1} :: The ST-01 total grows to 6.
6 :: station="ST-01"; err=2; totals={"ST-01": 6, "ST-02": 9}; counts={"ST-01": 2, "ST-02": 1} :: The ST-01 count goes up to 2.
```

Pandas does the same job in one line with `groupby`. The idea is identical, so you can check the pandas result against this trace. Next, the time conversion. A timestamp in the data is usually in UTC, the standard reference time. Officers read clocks in IST, which is UTC plus five and a half hours. Convert before you take the hour:

```python
import pandas as pd

ts = pd.Series(pd.to_datetime(["2026-02-16 12:30:00"]))
ist = ts.dt.tz_localize("UTC").dt.tz_convert("Asia/Kolkata")
print(ist.dt.hour.iloc[0])
```

Line by line: `pd.to_datetime` turns the text into date-time values. `tz_localize("UTC")` marks the values as UTC. This step is needed when the timestamps have no time zone. If they already have one, skip it. `tz_convert("Asia/Kolkata")` moves them to IST. `.dt.hour` keeps the hour. The expected output is `18`, because 12:30 UTC is 18:00 IST. Pandas raises an error if you call `tz_convert` on timestamps that have no time zone, which is why the `tz_localize` line comes first.

Now the table. Here is the core idea, shown with the column names used in the course chapter. Replace them with your own columns:

```python

pred = pd.read_parquet("reports/ml/test_predictions.parquet")
pred["err"] = pred["y_pred"] - pred["y_true"]
```

### Defend it in the viva

1. **Why did you compare the models on the same folds, and what would go wrong if you did not?**

:::answer Model answer
If each model is scored on different folds, a difference in the scores could come from the split, not from the model. The fair test is to reuse the same cross-validation object for every model, so each one trains and tests on the same rows. I would also say that a difference smaller than the fold standard deviation is a tie, because the folds vary by that much anyway.
:::

2. **What is the trade-off between a random forest and gradient boosting for this problem?**

:::answer Model answer
A random forest builds many independent trees and averages them, which reduces variance and is hard to overfit badly. Gradient boosting builds trees one after another, each correcting the last, which can reduce bias and often scores better, but it is more sensitive to its settings. The trade-off is accuracy against training time and tuning effort. For this ticket, the comparison table records both fit time and MAE, so the trade-off is visible.
:::

3. **Why must the slice tables use test-window rows only?**

:::answer Model answer
The model was trained on the training window, so its predictions there are too good. A slice built from those rows would hide the places where the model really fails. The test window holds rows the model has not seen, so the error per slice is an honest estimate of how it will behave on new data. The slice counts also tell you how much to trust each group.

#### Y2-T37.3 Build the slice tables

Goal: one table per slice type, with n, MAE and bias, computed only on the test window.

First, a small idea. `groupby` splits rows into groups by a column, and `agg` computes numbers for each group. With a made-up table of three rows and two stations, `df.groupby("station")["err"].mean()` returns one average per station. You will add counts and MAE to that idea.

Stage 1: load the test predictions and define the error. Use the test-prediction file your pipeline writes. The course example uses `reports/ml/test_predictions.parquet`, but your squad may use a different path.

```python
import pandas as pd
pred = pd.read_parquet("reports/ml/test_predictions.parquet")  # use your squad's file
pred["err"] = pred["y_pred"] - pred["y_true"]                  # bias sign: positive = over-predicts
```

- `pd.read_parquet` loads the file into a DataFrame called `pred`.
- The second line creates a column that holds predicted minus actual. In this ticket, a positive value means over-prediction. Write that sign in the card, because the opposite sign is also common.

Stage 2: add the IST hour. Timestamps must be converted to IST before you take the hour, or the bands will be shifted by five and a half hours.

```python
pred["hour_ist"] = pd.to_datetime(pred["ts"]).dt.tz_convert("Asia/Kolkata").dt.hour
```

- `pd.to_datetime` turns text timestamps into date-time values.
- `.dt.tz_convert("Asia/Kolkata")` converts them to IST. If your timestamps have no timezone, use `.dt.tz_localize` first.
- `.dt.hour` keeps only the hour, from 0 to 23.

Stage 3: aggregate by station, with n, MAE and bias.

```python
t = pred.groupby("station").agg(n=("y_true", "size"), mae=("err", lambda e: e.abs().mean()), bias=("err", "mean")).round(2)
t["note"] = (t["n"] < 100).map({True: "insufficient", False: ""})
print(t.to_string())
```

- `agg(n=("y_true", "size"))` counts the rows in each group.
- `mae=("err", lambda e: e.abs().mean())` averages the absolute errors. The `lambda` is a small unnamed function.
- `bias=("err", "mean")` averages the signed errors.
- `.round(2)` rounds the table to two decimal places.
- The `t["note"]` line marks groups with fewer than 100 rows as insufficient, using the same `map` pattern as the course example.
- `print(t.to_string())` shows the whole table in the terminal.

Expected output is one row per station. Test this stage by checking that the counts add up to the test set:

#### Y2-T37.4 Permutation importance and a PDP

Goal: a top-five table of permutation importance on raw test inputs, and one PDP saved to `docs/img/`.

The idea of permutation importance is simple. Shuffle one input column in the test data, keep the other columns as they are, and measure how much the MAE rises. A big rise means the model relies on that column. Repeating the shuffle ten times gives a mean and a standard deviation.

Stage 1: load the saved pipeline and rebuild the test inputs exactly as `train.py` does. The course example below uses `add_target` and a `test_start` date from `config.yaml`. Replace the names with your own loader and keys, so the test window matches your training code.

```python
import joblib, yaml
import pandas as pd
pipe = joblib.load("models/<your_T36_candidate>.joblib")  # the chosen candidate; model_v1 is saved from it in T37.6
cfg = yaml.safe_load(open("config.yaml"))
df = add_target(pd.read_parquet(cfg["data"]["path"])).dropna(subset=[cfg["target"]])
test = df[df["ts"] >= pd.Timestamp(cfg["split"]["test_start"], tz="Asia/Kolkata")]
X, y = test.drop(columns=[cfg["target"]]), test[cfg["target"]]
```

- `joblib.load` reads a saved candidate back. Replace the placeholder with the candidate file your squad picked from `models/` in T36 (the Tech Lead's decision in T37.6 makes it `model_v1`). The API will use the same call.
- `yaml.safe_load` turns `config.yaml` into a dictionary.
- The `test` line keeps only rows at or after the test start, in IST.
- `X` holds the raw inputs and `y` holds the answers. `X` must have the raw columns, because the Pipeline does its own preprocessing.

Stage 2: shuffle and measure.

```python
from sklearn.inspection import permutation_importance
r = permutation_importance(pipe, X, y, n_repeats=10, random_state=42, scoring="neg_mean_absolute_error")
imp = pd.DataFrame({"mean": r.importances_mean, "std": r.importances_std}, index=X.columns)
print(imp.sort_values("mean", ascending=False).head(5).round(3))
```

- `permutation_importance` shuffles each column ten times and scores the model each time.
- `random_state=42` fixes the shuffles, so the table can be repeated.
- The scoring is negative MAE, as scikit-learn expects. The importances are therefore positive when shuffling makes the MAE worse.
- The DataFrame stores the mean and standard deviation for each column, with the column names as row labels.
- `sort_values` puts the largest reliance first, and `head(5)` keeps five rows.

Expected output is five rows, each with a mean and a std. If the top value is negative, shuffling a column made the model better, which is worth explaining in the card.

Stage 3: draw one PDP for a continuous input, such as humidity. Create the folder first, because the save fails without it.


`mkdir -p` creates the folder and does nothing if it already exists. It works in both Linux and Git Bash.

```python
disp.figure_.savefig("docs/img/pdp_humidity.png", dpi=150, bbox_inches="tight")
```

- `from_estimator` varies humidity across its range, averages the predictions at each value and draws the curve.
- It needs the raw column name `humidity`, because the pipeline takes raw inputs.
- `savefig` writes a PNG file. `dpi=150` sets the resolution, and `bbox_inches="tight"` trims the white border.

### Defend it in the viva

Each question is one a trainer might ask about this ticket. The model answers show the reasoning. Your own answers must use your own commits and numbers.

**Q1. Why does the card need slices when the overall MAE is already known?**

:::answer Model answer
An overall MAE averages the errors across all rows, so a model can look reasonable while it is badly wrong for one station or one hour band. A slice table shows where the failures are, and the n column shows how much evidence supports each finding. Officers act per ward and per hour, so the slice is the level at which the risk matters.
:::

**Q2. What is the trade-off in choosing the final candidate?**

:::answer Model answer
A more complex model may lower the test MAE a little, but it usually costs more fit time and a larger file. A sensible rule is to pick the cheapest model whose MAE is within one fold standard deviation of the best, because a smaller gain than that may be noise. The decision record must show both the accuracy and the cost, so the reader can see what was traded.
:::

**Q3. What did you personally do in this ticket, and how can Git show it?**

:::answer Model answer
Name the subtask you owned, then point to the commits that carry your name, quoting their messages. Say which review you received and what you changed after it. Explain one of your numbers, such as where it came from in the test window. Your trainer checks the commit history, so make sure each claim matches a commit. If you cannot explain a commit, learn it before the viva.
:::

**Q4. Why does permutation importance not prove that an input causes the forecast?**

:::answer Model answer
Permutation importance measures how much this model relies on an input when predicting on held-out data. It does not show that changing the input would change air quality in the real world. Two inputs can be linked to the same cause, and the model may use either one. The card should say that the importance describes the model, not the world.
:::

**Q5. Why must the card name `models/model_v1.joblib` exactly?**

:::answer Model answer
The API will load that exact file, so the card must describe the file that will serve forecasts. A card that names another file documents a model nobody is using. The trainer checks the name with grep, and the metrics file must come from the same run, so the numbers match what the API serves.
:::
