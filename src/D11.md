TITLE: Day 11 — Data pipelines and data-quality checks
SUB: You will be able to build a three-stage pipeline with data-quality gates that stops before bad data is loaded, prove the stop with an exit code, and count rejected records by reason.

## The idea in one minute

A pipeline is a set of steps that run one after another, where each step uses the output of the step before it. Today you build one for air-quality readings. The steps are extract (read the raw file), validate (test the data against rules) and load (write the good data into a database table).

Between the steps you place data-quality checks. A data-quality check is a test on the data, such as "no reading is negative". If a blocking check fails, the run stops, and the bad readings never reach the database or the dashboard.

The analogy is an assembly line with a stop cord. Any worker can pull the cord and halt the line before a faulty part moves on.

By the end you will be able to write a pipeline script, write checks that return pass or fail, show the exit code that proves a failure, and count rejected records by reason.

## Starting from zero

Every term used in this chapter is explained here or at the first place it appears.

**Terminal and shell.** A terminal is a window where you type text commands to the computer. The program that reads those commands and runs them is a shell. Bash is a common shell, and this course uses it for its `.sh` scripts. On Windows, Git Bash is the usual way to run them. If your course names a different terminal, use that one.

**Command.** A command is one line you type, and the computer runs it when you press Enter. `ls` is a command that lists the files in the folder you are in.

**File, folder and path.** A file holds data or code. A folder (also called a directory) holds files and other folders. A path is the address of a file. `data/raw/batch_good.csv` means the file `batch_good.csv` inside `raw`, which is inside `data`.

**Working directory.** This is the folder your terminal is in right now. The command `pwd` prints its full path. A relative path such as `data/raw` is measured from the working directory. The same file has a different relative path from a different folder, which is why scripts must move to a known folder first.

**Script.** A script is a file of commands that the computer runs from top to bottom. A `.sh` file is a bash script. A `.py` file is a Python script.

**Variable.** A variable is a name that stores a value. In bash, `DB="citypulse.db"` stores text, and `"$DB"` reads it back. In Python, `count = 3` does the same job.

**Function.** A function is a named block of code you can call by name. It can take inputs (arguments) and give back an output (a return value). In Python, `def double(x): return x * 2` defines it, and `double(4)` gives `8`.

**Module.** A module is a Python file that other code can load with `import`. The command `python -m citypulse.fetch` runs one module as a program.

**Server.** A server is a program that waits for requests and answers them. A database server answers questions about its data. SQLite, which you use today, does not need a server: the whole database is one file on disk.

**Exit code.** Every program ends by returning a number called its exit code. `0` means success. Any other number means failure. The shell stores the last exit code in a special variable called `$?`. The command `echo $?` prints it.

**Pipe.** The symbol `|` sends the output of one command into the next command. You will meet it in a warning in the tools section.

**Cron.** Cron is the Linux scheduler that runs a command at set times, for example every morning at 06:00.

**CSV.** CSV means comma-separated values. It is a plain text table: each line is a row, commas separate the columns, and the first line holds the column names.

**Table, row and SQL.** A database table holds rows with named columns. SQL (Structured Query Language) is the language for asking a database questions. `SELECT COUNT(*) FROM readings` asks how many rows the table `readings` has. A view is a saved SQL query that you can read like a table.

**Python list, dictionary and tuple.** A list is an ordered collection written in square brackets: `[1, 2, 3]`. A dictionary maps keys to values written in curly brackets: `{"S1": 2}` maps the key `"S1"` to the value `2`. A tuple is a fixed group of values in round brackets: `("S1", 2)`. The dictionary method `get(key, default)` returns the value for the key, or the default if the key is missing.

**pandas and DataFrame.** pandas is a Python library for tables. It is installed with `python3 -m pip install pandas`, where `pip` is Python's installer for libraries. A DataFrame is a table held in memory, with rows and named columns.

**Regular expression (regex).** A regular expression is a pattern that describes text. The pattern `[0-9]+` matches one or more digits. The pattern `[A-Z]{2}` matches exactly two capital letters.

**Timestamp.** A timestamp is a date and time value, such as `2026-03-01T08:00`, which means 8 am on 1 March 2026.

## The tools

### Pipeline orchestration with shell

Orchestration means deciding which steps run, in what order, and what happens when one fails. CityPulse uses a bash script for this. The alternatives are a Makefile (a file that lists build steps and what each one depends on, which suits compiled software and is awkward for a plain sequence with logs), Prefect or Airflow (workflow tools with retries and a web interface, which are too heavy for five stages) and a Python driver script (which works, but bash keeps each stage a plain command you can run by hand).

Bash is already on every lab machine, and the shellcheck check (an automatic tool that reviews shell scripts for common mistakes) reviews it. The same script later runs from cron on a virtual machine, so it must work from any folder.

This is the pipeline script from the course slides, with its indentation restored:

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."   # repo root, works from any cwd
if [ -f .env ]; then set -a; . ./.env; set +a; fi
DB="${SQLITE_PATH:-citypulse.db}"
log() { echo "$(date -u +%FT%TZ) [pipeline] $*"; }
run() { local name=$1; shift; log "START $name"; "$@"; log "END $name"; }
run fetch python -m citypulse.fetch
run clean python -m citypulse.clean
run load  python -m citypulse.load
run views sqlite3 "$DB" ".read sql/views.sql"
run dq    python -m citypulse.dq_checks
log "pipeline OK"
```

Line by line:

1. `#!/usr/bin/env bash` is the shebang. It tells the system to run this file with bash.
2. `set -euo pipefail` is strict mode. `-e` stops the script at the first command that fails. `-u` treats an unset variable as an error. `pipefail` makes a pipeline (`a | b`) fail if any part fails, not only the last part.
3. `cd "$(dirname "$0")/.."` moves into the repository root. `$0` is the path of the script, `dirname` gives its folder, and `..` goes up one level. The `$( ... )` form runs a command and puts its output in place. The quotes keep folder names with spaces working.
4. If a file called `.env` exists, this line loads its settings. `set -a` marks each variable it creates for export, `. ./.env` reads the file, and `set +a` turns that behaviour off again.
5. `DB` takes the value of `SQLITE_PATH` if it is set and not empty, and `citypulse.db` otherwise. The `:-` is the "use this default" form.
6. `log` is a function. It prints a UTC timestamp, the tag `[pipeline]` and its arguments (`$*`).
7. `run` takes a stage name, drops it with `shift`, logs START, runs the rest of the line as a command (`"$@"`), and logs END. Because of `set -e`, a failing stage stops the script before END is printed. That is what makes the log show where the run stopped.
8. Lines 8 to 12 each run one stage. `sqlite3 "$DB" ".read sql/views.sql"` runs an SQL file of saved views against the database.
9. The last line prints `pipeline OK`. You see it only if every earlier stage succeeded.

A normal run prints a START and END line for each stage, then `pipeline OK`. If a stage fails, you see its START line, its error text, and no END line.

The next animation shows where the message travels. Your lab uses the same shape.

```flow
TITLE: One run of the pipeline script
NODES: run_pipeline.sh | Extract and clean | DQ gate | Load
STEPS:
1>2 :: run the stage :: The script starts the first stage and waits for its exit code.
2>1 :: exit 0 :: The stage succeeded, so the script moves on.
1>3 :: run the gate :: The script starts the data-quality checks.
3>1 :: exit 1 :: A blocking check failed, so the gate returns 1. Under set -e the script stops here, and Load never runs.
```

:::trap Forgetting pipefail
Without `pipefail`, a command such as `python -m citypulse.clean | tee clean.log` reports the exit code of `tee`, which is `0`. The failure of `clean` is hidden, and the script carries on. Always write `set -euo pipefail` on the second line.
:::

:::trap Relative paths break under cron
A script that opens `sql/views.sql` works when you run it from the repo root and fails from `/tmp` or from cron. The line `cd "$(dirname "$0")/.."` fixes this. Also, `python` may point to a different Python under cron. Call `.venv/bin/python` explicitly, or activate the virtual environment first.
:::

### Data-quality assertions

A data-quality check is a query that returns one number, plus a rule that judges that number. For example, "rows in the last 24 hours must be at least 40". Each check belongs to a dimension, which is the kind of problem it looks for:

- Completeness: the data you expect is present.
- Validity: values follow the rules, such as a non-negative PM2.5 reading.
- Uniqueness: no key appears twice when it should be unique.
- Freshness: the newest data is recent enough to trust.

A blocking check stops the pipeline when it fails. A warning is reported but lets the run continue. Use blocking only for data you must not publish.

This is the core of the course's checks file, with the rest of the checks left out to keep it short:

```python
import os, sqlite3, sys
CHECKS = [  # name, dimension, SQL -> one number, pass rule, blocking?
    ("negative_pm25", "validity", "SELECT COUNT(*) FROM fact_air_quality WHERE pm2_5 < 0", lambda v: v == 0, True),
    ("rows_last_24h", "completeness", "SELECT COUNT(*) FROM fact_air_quality WHERE ts_utc >= strftime('%Y-%m-%dT%H:%M:%SZ','now','-1 day')", lambda v: v >= 40, True),
    ("hours_since_newest", "freshness", "SELECT (julianday('now') - julianday(MAX(ts_utc))) * 24 FROM fact_air_quality", lambda v: v is not None and v <= 3, False),
]
def main() -> int:
    con = sqlite3.connect(os.environ.get("SQLITE_PATH", "citypulse.db"))
    results = [(n, b, ok(con.execute(sql).fetchone()[0])) for n, _, sql, ok, b in CHECKS]
    for n, b, good in results: print(f"{'PASS' if good else 'FAIL' if b else 'WARN'} {n}")
    failed = sum(1 for _, b, g in results if b and not g)
    warned = sum(1 for _, b, g in results if not b and not g)
    print(f"DQ: {len(results) - failed - warned} passed, {failed} failed, {warned} warnings"); return 1 if failed else 0
if __name__ == "__main__": sys.exit(main())
```

Line by line:

1. `import` brings in three standard-library modules: `os` for environment variables, `sqlite3` for the database and `sys` for exiting with a code.
2. `CHECKS` is a list. Each entry is a tuple of five items: a name, a dimension, an SQL query that returns one number, a pass rule and a blocking flag. The comment on this line explains the order.
3. `negative_pm25` counts rows where `pm2_5` is below zero. The rule `lambda v: v == 0` is a small unnamed function that is passed in. It returns True when the count is zero. `True` at the end makes it blocking.
4. `rows_last_24h` counts rows with a timestamp in the last day. The rule needs at least 40. This check is blocking.
5. `hours_since_newest` returns the age of the newest row in hours. `julianday` converts a date to a day number, so the subtraction gives days, and `* 24` converts to hours. The rule `v is not None and v <= 3` first checks that there is a value, because `MAX` on an empty table returns NULL. The `False` makes this a warning, not a blocking check.
6. `main()` opens the database, using `SQLITE_PATH` if it is set. The `-> int` tells the reader it returns a number.
7. This line runs every check. `con.execute(sql)` runs the query, `.fetchone()` returns one row as a tuple, and `[0]` takes its first value. `ok(...)` applies the pass rule. The result is a list of `(name, blocking, passed)` tuples.
8. This loop prints one line per check. The nested `if` picks the label: PASS if it passed, FAIL if it failed and is blocking, and WARN otherwise.
9. `failed` counts the blocking checks that did not pass.
10. `warned` counts the non-blocking checks that did not pass.
11. This line prints the summary and returns `1` if any blocking check failed, or `0` otherwise.
12. `sys.exit(main())` passes that number to the operating system as the exit code. The `if __name__ == "__main__"` guard means the code runs only when you start the file directly, not when another file imports it.

The loop logic on lines 8 to 11 is the part most worth understanding. The animation below uses three checks: one blocking failure in the middle.

```trace
TITLE: Counting blocking failures
CODE:
results = [("negative_pm25", True, True), ("rows_last_24h", True, False), ("hours_since_newest", False, True)]
failed = 0
for name, blocking, passed in results:
    if blocking and not passed:
        failed += 1
status = 1 if failed else 0
STEPS:
1 :: results=[3 items] :: The three check results are stored in a list.
2 :: results=[3 items]; failed=0 :: The failure counter starts at zero.
3 :: name="negative_pm25"; blocking=True; passed=True; failed=0 :: The loop takes the first check.
4 :: name="negative_pm25"; blocking=True; passed=True; failed=0 :: It passed, so the test is False and nothing changes.
3 :: name="rows_last_24h"; blocking=True; passed=False; failed=0 :: The next check is a blocking failure.
4 :: name="rows_last_24h"; blocking=True; passed=False; failed=0 :: Blocking is True and passed is False, so the test is True.
5 :: name="rows_last_24h"; blocking=True; passed=False; failed=1 :: The counter goes up by one.
3 :: name="hours_since_newest"; blocking=False; passed=True; failed=1 :: The last check passed.
6 :: name="hours_since_newest"; blocking=False; passed=True; failed=1; status=1 :: One blocking failure is enough, so the status is 1.
```

Run the checks and you see something like this. The output is illustrative, but the line formats match the course code.

```term
$ python -m citypulse.dq_checks
PASS negative_pm25
FAIL rows_last_24h
PASS hours_since_newest
DQ: 2 passed, 1 failed, 0 warnings
$ echo $?
1
```

Each line of the output comes from line 8 of the code, and the summary comes from line 11. The final `1` is the exit code, which is what the pipeline reads.

:::trap An empty table breaks the freshness check
`MAX(ts_utc)` on an empty table is NULL. In Python that arrives as `None`, and `None <= 3` raises an error. Always handle `None` in the pass rule, as the `v is not None and` part does.
:::

:::trap Thresholds picked at random
A threshold of 40 rows is only sensible if you measured normal daily coverage first and wrote the reason in a comment. A threshold that is too high fails every day, and one that is too low never fails. Both make the check useless.
:::

:::trap Making every check blocking
If every check is blocking, one cosmetic issue stops the whole pipeline. Keep blocking for data you must not publish, and use warnings for the rest.
:::

### Exit codes and fail-fast

Fail-fast means stopping at the first real error instead of passing bad data to later stages. The exit code is the signal that tells the shell, cron and CI (automatic checks that run on every change to the code) that a step failed. Your script does not need to read any message: it only needs the number.

This is the sabotage check from the course. It deletes today's rows, expects the checks to fail, and then reloads and expects a pass:

```bash
if python -m citypulse.dq_checks; then
  echo "UNEXPECTED: dq passed after sabotage"; exit 1
fi
echo "OK: dq failed with non-zero exit as expected"
```

Line by line:

1. `if` runs the command and branches on its exit code. A command that returns `0` takes the `then` branch, and any other code skips it. Here, a pass is the unexpected result.
2. This line runs only if the checks passed. It prints a message and exits with `1`, so the sabotage run is reported as broken.
3. `fi` closes the `if`.
4. This line runs when the checks failed, which is the expected result.

The `if` is the reason this works under `set -e`. A bare failing command would stop the script at once. Wrapping it in `if` tells bash that the failure is expected.

Running the checks on the sabotaged data produces a non-zero exit code:

:::trap A bare failing command under set -e
`set -e` stops the script at the first failing command, so `python -m citypulse.dq_checks` on its own would end the script before your message printed. Wrap an expected failure in `if`. Also check `$?` immediately after the command you care about, because the next command overwrites it.
:::

:::trap A main that prints FAIL but returns nothing
If `main()` prints `FAIL` and ends without a `return`, Python returns `None`. The process exits with code `0`, and the pipeline passes bad data. Return `1` from `main()` and call `sys.exit(main())`, as the course code does.
:::

## The worked example

The course workbook builds a small version of the same idea in five steps. The goal is to show that a batch with one bad reading halts the run, and that a cleaned batch goes through. You will reuse these ideas in the lab.

**Step 1: stage a raw batch.** The batch is a CSV file with six readings, one of them negative:

```text
station_id,ts,pollutant,value
S1,2026-03-01T08:00,pm25,42.1
S1,2026-03-01T09:00,pm25,38.7
S2,2026-03-01T08:00,no2,19.4
S2,2026-03-01T09:00,no2,-3.0
S3,2026-03-01T08:00,o3,61.2
S3,2026-03-01T09:00,o3,58.0
```

The line `S2,2026-03-01T09:00,no2,-3.0` is the bad row. The command `python3 -c "import pandas as pd; print(len(pd.read_csv('readings_raw.csv')),'rows')"` prints `6 rows`. The `-c` flag runs the Python text that follows it as a one-line program.

**Step 2: read the batch into typed columns.**

```python
import pandas as pd
df = pd.read_csv("readings_raw.csv", parse_dates=["ts"])
print(df.dtypes.to_string())
print("shape:", df.shape)
```

Line by line: line 1 imports pandas under the short name `pd`. Line 2 reads the CSV into a DataFrame. The `parse_dates=["ts"]` option turns the `ts` column from text into real dates. Line 3 prints the type of each column, and line 4 prints the number of rows and columns.

The output is `station_id` as `object` (text), `ts` as `datetime64[ns]` (a date), `pollutant` as `object`, `value` as `float64` (a decimal number), and `shape: (6, 4)`. Types matter because a value stored as text compares wrongly with a number.

**Step 3: assert the four checks.** An `assert` is a Python statement that stops the program with an error if its condition is false. The batch needs one assert per check:

```python
assert df["value"].notna().all(), "null values found"
assert (df["value"] >= 0).all(), "negative readings"
assert df["pollutant"].isin({"pm25", "no2", "o3"}).all(), "bad pollutant"
assert df.duplicated(["station_id", "ts", "pollutant"]).sum() == 0, "duplicate rows"
```

Line by line: each line tests one pillar. `notna().all()` is the completeness test: it is True only if no value is missing. `(df["value"] >= 0).all()` is the validity test for negative readings. `isin` checks the pollutant against a set of allowed codes. The last line counts repeated keys and checks that the count is zero. When a condition is false, Python raises `AssertionError` with the message after the comma.

Running this on the raw batch prints `AssertionError: negative readings`, and `echo $?` prints `1`.

**Step 4: quarantine the bad row.** The file `clean.py` keeps the rows that pass the rule:

```python
import pandas as pd
df = pd.read_csv("readings_raw.csv")
good = df[df["value"] >= 0]
good.to_csv("readings_clean.csv", index=False)
print("kept", len(good), "of", len(df), "rows")
```

Line by line: line 2 reads the batch. Line 3 keeps only the rows where the test is True, which is the filter in square brackets. Line 4 writes the kept rows to a new file, and `index=False` stops pandas adding a numbered first column. Line 5 prints `kept 5 of 6 rows`. The rejected row is not deleted from the raw file, so you can still investigate it.

**Step 5: run it end to end.** Running the raw batch through the pipeline stops at validation. Running the clean batch goes all the way through to load. The workbook prints `PIPELINE OK` only for the clean batch. The exit code is `1` for the raw batch and `0` for the clean one.

:::trap assert can be switched off
Python ignores every `assert` when it runs with the `-O` flag. A check written as an assert then silently passes. For a check that guards production data, use an `if` that returns or exits with a code, as the course's `dq_checks.py` does.
:::

### Step 3: write the data-quality checks

Create `checks.py`:

```python
def run_checks(df, config):
    failures = []
    if df["value"].isna().any():
        failures.append("null_value")
    if (df["value"] < config["min_value"]).any():
        failures.append("value_below_min")
    if not df["pollutant"].isin(config["pollutants"]).all():
        failures.append("bad_pollutant")
    if df.duplicated(["station_id", "ts", "pollutant"]).any():
        failures.append("duplicate_key")
    return failures
```

Line by line: `run_checks` takes the table and the config dictionary. It starts with an empty list of failures. Each `if` tests one rule and adds a short name to the list when the rule is broken. The names are what you will see in the output. `.any()` is True if at least one row breaks the rule. The function returns the list, so an empty list means the batch is clean.

Test the checks on the bad batch:

```bash
python3 -c "import json; from extract import extract; from checks import run_checks; print(run_checks(extract('batch_bad.csv'), json.load(open('config.json'))))"
```

The output is the extract line, then `['value_below_min']`. An empty list `[]` would mean the check did not fire, so find out why before you go on.

### Step 4: build the validate gate

The gate decides whether a batch may continue. Create `validate.py`:

```python
import json
import sys
from extract import extract
from checks import run_checks


def main(path):
    with open("config.json") as f:
        config = json.load(f)
    df = extract(path)
    failures = run_checks(df, config)
    if failures:
        print("BLOCKED", path, failures)
        return 1
    print("validation OK", path)
    return 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1]))
```

Line by line: lines 1 to 4 import the libraries and the two functions you wrote. `main` loads the config, extracts the batch, and runs the checks. If the list is not empty, it prints `BLOCKED`, the file and the reasons, and returns `1`. Otherwise it prints `validation OK` and returns `0`. The last line passes the return value to `sys.exit`, so the program's exit code is `0` or `1`. The file name `config.json` is opened relative to the working directory, so run this from the `dq-lab` folder.

Run both batches:

```bash
python3 validate.py batch_good.csv; echo "exit $?"
python3 validate.py batch_bad.csv; echo "exit $?"
```

The good batch prints `validation OK batch_good.csv` and `exit 0`. The bad batch prints `BLOCKED batch_bad.csv ['value_below_min']` and `exit 1`.

### Step 5: write the load stage

Create `load.py`:

```python
import sqlite3
import sys
from extract import extract


def main(path):
    df = extract(path)
    con = sqlite3.connect("citypulse_lab.db")
    df.to_sql("readings", con, if_exists="replace", index=False)
    con.close()
    print("loaded", len(df), "rows into readings")
    return 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1]))
```

Line by line: `sqlite3.connect` opens the database file, and it is created if it does not exist. `to_sql` writes the table to the database. `if_exists="replace"` drops the old `readings` table and writes a new one. Running the load twice therefore gives the same table, which is the idempotent behaviour the quiz covers. `con.close()` closes the connection. The function returns `0` to say it succeeded.

### Step 6: run the good batch

Create `run_pipeline.sh`:

```bash
#!/usr/bin/env bash

cd "$(dirname "$0")"
BATCH="$1"
```

Line by line: lines 1 and 2 are the shebang and strict mode. Line 3 moves to the folder that holds the script. Line 4 stores the first argument, the batch file name, in `BATCH`. Lines 5 and 6 run the gate and then the load. Because of `set -e`, a non-zero exit from the gate stops the script before the load. The last line runs only if both succeeded.

Run it on the good batch:


## What the quiz tests

The real quiz is the student's own work. Each topic below says what you must know, and then the practice question at the end of this section covers the same topic.

### pipeline-dag

A pipeline is often drawn as a DAG, a directed acyclic graph. Each box is a step, each arrow shows that one step needs another step's output, and "acyclic" means no arrow loops back to an earlier step. The CityPulse pipeline is a straight line, which is the simplest possible DAG. The examiner's trap is to assume that a DAG must be complicated, or that a loop is harmless because it "eventually stops". A loop means the run has no defined start or end.

### idempotency

An operation is idempotent if running it twice leaves the same result as running it once. For a load, this means running the pipeline again must not double the rows. The course asks you to run the pipeline twice and show an identical fact count. You achieve this either by replacing the table, as `if_exists="replace"` does in the lab, or by deleting the rows for a key before inserting them again. The trap is an append load: every re-run adds the same rows again.

### data-quality-dimensions

The slides name four dimensions: completeness, validity, uniqueness and freshness. Completeness asks whether the expected data is present, such as enough rows in the last 24 hours. Validity asks whether the values follow the rules, such as a non-negative PM2.5 reading. Uniqueness asks whether a key appears only once, and freshness asks whether the newest data is recent. The course requires at least five checks across at least three of the four dimensions. The trap is to file every time-based check under freshness. The count of rows in the last 24 hours is labelled completeness on the course slides, because it tests coverage, not age.

### range-validation

Range validation checks that a value lies between a lower and an upper bound. Pay attention to whether each bound is inclusive. The rule `value >= 0` accepts zero, and `value > 0` rejects it. Bounds should come from the meaning of the data: PM2.5 cannot be negative. In code, put the bounds in configuration, as the lab does with `min_value`. The trap is a missing value: in pandas, a comparison with a missing value is False, so range checks ignore it. Check for missing values with a separate completeness check.

### dead-letter-quarantine

A rejected record should be kept, not thrown away. A quarantine (also called a dead-letter store) holds rejected rows with the reason they were rejected, so someone can investigate the faulty sensor. The good rows go on to be loaded. The course slide says that bad data is quarantined, not silently dropped. The trap has two parts: deleting rejects without a record, and quarantining rows without a reason, which makes the quarantine useless for diagnosis.

### incremental-loading

Incremental loading loads only the records that are new since the last run, instead of reloading everything. The job stores a high-water mark, which is the largest event timestamp it has safely loaded, and takes only the rows above that value next time. A full reload is simpler and safer, so incremental loading is chosen when data is too large to reload. The trap is to use the time the job ran as the mark. Records that arrive late, with older timestamps, are then skipped for ever.

### schema-validation

Schema validation checks the structure of the data before any row is checked: the required column names, and where needed their types. It comes first because a renamed or missing column makes every value check crash or report misleading results. For example, if an export renames `pollutant` to `pollutant_code`, the schema check should say exactly that. The trap is to check the values and assume the columns are right, so the failure appears as a confusing error deep in a row check.

### drift-detection

Drift is a change in the data's pattern over time. A batch can pass every validity rule and still be unusual, for instance when the average PM2.5 is three times last month's average. A drift check compares a statistic from today's batch with a baseline and fires when the difference is too large. Drift checks are usually warnings, and their thresholds need a stated reason. The trap is to believe that passing the rules means the data is normal.

### retry-backoff

A transient failure, such as a network timeout or a busy database, may succeed if you try again. Retry with backoff means waiting longer after each attempt, for example 1, 2 and then 4 seconds, with a maximum number of attempts. Some systems add a small random delay (jitter) so that many clients do not retry at the same moment. Retries are for transient failures only. A validation failure fails the same way each time, so retrying it wastes time. The trap is to retry a data-quality failure, or to retry with no limit.

### atomic-publish

An atomic publish means readers see either the complete old version or the complete new version, and never a half-written state. A common way to do this is to load into a new table or inside a transaction (a group of database changes that either all succeed or all roll back), and then switch readers to the new version in one step. The lab's `to_sql` with `replace` is not fully atomic: a crash in the middle could leave the table partly written. Know the pattern even though the lab uses the simpler form. The trap is to write straight into the live table, where the dashboard can read a partial load.

## The graded lab skill

The graded lab asks you to write Python functions that check records against several rules and count the rejections. The techniques below are the ones you need.

**Functions and return values.** A function groups code under a name. `def check_record(record):` defines a function that takes one argument. `return` sends a value back to the caller and ends the function. A function that reaches the end without `return` gives back `None`, which is Python's word for "no value".

**Dictionaries and missing keys.** `record["email"]` raises a `KeyError` if the key is absent. `record.get("email")` returns `None` instead. Use `get` when a field may be missing, and check for `None` yourself.

**Strings.** `value.strip()` removes spaces from both ends of a string. `""` is an empty string, and `"   "` is not empty until you strip it. A missing value often arrives as either `None` or a blank string, so test for both.

**Types and `isinstance`.** `isinstance(value, str)` is True if the value is text. Test the type before you use a string method, because `(42).strip()` raises an error. In Python, `True` and `False` are a kind of integer, so `isinstance(True, int)` is True. Exclude booleans first when a number is wanted.

**Regular expressions.** The module `re` matches text against a pattern. `re.fullmatch(pattern, text)` returns a match object only if the whole text fits the pattern, and `None` otherwise. The email pattern used below is `[^@\s]+@[^@\s]+\.[^@\s]+`. It reads: one or more characters that are not `@` or a space, then `@`, then one or more of the same, then a dot, then one or more of the same. The square brackets mean "any one character from this set", `^` inside them means "not", `\s` means a space-like character, and `+` means one or more.

**Dates.** `datetime.strptime(text, "%Y-%m-%d")` parses text in the format year-month-day. It raises `ValueError` if the text does not parse, including impossible dates such as `2026-02-30`. Catch the error with `try` and `except`.

**Lists, dictionaries and counts.** To count reasons, start with `reasons = {}` and use `reasons[reason] = reasons.get(reason, 0) + 1`. The first time a reason appears, `get` returns `0`, and the count starts at one.

**Edge-case checklist.** Before you submit any solution, check each case:

- Empty input: the list is empty, so every count is `0` and the reasons dictionary is empty.
- Missing fields: a key that is absent, a value that is `None`, and a blank string.
- Ordering: accepted and quarantined records keep the input order.
- Ties: when two rules are broken, the first rule in the order you were given decides the reason.
- Types: a number sent as text, a boolean, and a value of the wrong type.
- Boundaries: the lowest and highest allowed ages, both included.
- Rounding and format: `24.5` is not a whole number, and `2026-02-30` is not a real date.
- Duplicates: the task counts each record once, so do not deduplicate.

**The practice problem.** Write these functions in one file:

- `check_record(record)` returns the reason a sign-up record breaks a rule, or `None` if the record is accepted.
- `split_signups(records)` returns a dictionary with the keys `accepted`, `quarantined`, `accepted_count`, `quarantined_count` and `reasons`.

Each record is a dictionary with the keys `email`, `age`, `country` and `joined`. Apply the rules in this order, and stop at the first one the record breaks:

1. `missing_field`: any of the four fields is absent, `None`, or blank text.
2. `bad_email`: the email is not text matching `[^@\s]+@[^@\s]+\.[^@\s]+` after stripping spaces.
3. `bad_age`: the age is an integer, or text made only of digits, from 13 to 120 inclusive. Booleans and decimals are rejected.
4. `bad_country`: the country is exactly two capital letters after stripping spaces.
5. `bad_joined`: the date is text in the form `YYYY-MM-DD` and is a real calendar date.

In `quarantined`, each entry is a dictionary with the keys `record` and `reason`. In `reasons`, count each rejected record once, under the first rule it breaks. Keep the input order in both lists.

Example input:

```python
records = [
    {"email": "ana@example.com", "age": "24", "country": "IN", "joined": "2026-03-01"},
    {"email": "bad-email", "age": 30, "country": "US", "joined": "2026-03-02"},
    {"email": "", "age": "41", "country": "GB", "joined": "2026-03-03"},
]
```

Expected result: `accepted_count` is `1`, `quarantined_count` is `2`, and `reasons` is `{"bad_email": 1, "missing_field": 1}`. The first record is accepted. The second fails on `bad_email`, and the third fails on `missing_field`, because its email is blank.

:::answer Solution and line-by-line explanation
```python test
import re
from datetime import datetime

REQUIRED = ("email", "age", "country", "joined")
EMAIL_PATTERN = r"[^@\s]+@[^@\s]+\.[^@\s]+"
COUNTRY_PATTERN = r"[A-Z]{2}"
DATE_PATTERN = r"[0-9]{4}-[0-9]{2}-[0-9]{2}"


def is_missing(value):
    if value is None:
        return True
    return isinstance(value, str) and value.strip() == ""


def as_age(value):
    # bool is a subclass of int in Python, so reject it first
    if isinstance(value, bool):
        return None
    if isinstance(value, int):
        return value
    if isinstance(value, str) and re.fullmatch(r"[0-9]+", value.strip()):
        return int(value.strip())
    return None


def check_record(record):
    for field in REQUIRED:
        if is_missing(record.get(field)):
            return "missing_field"
    email = record["email"]
    if not (isinstance(email, str) and re.fullmatch(EMAIL_PATTERN, email.strip())):
        return "bad_email"
    age = as_age(record["age"])
    if age is None or not (13 <= age <= 120):
        return "bad_age"
    country = record["country"]
    if not (isinstance(country, str) and re.fullmatch(COUNTRY_PATTERN, country.strip())):
        return "bad_country"
    joined = record["joined"]
    if not (isinstance(joined, str) and re.fullmatch(DATE_PATTERN, joined.strip())):
        return "bad_joined"
    try:
        datetime.strptime(joined.strip(), "%Y-%m-%d")
    except ValueError:
        return "bad_joined"
    return None


def split_signups(records):
    accepted = []
    quarantined = []
    reasons = {}
    for record in records:
        reason = check_record(record)
        if reason is None:
            accepted.append(record)
        else:
            quarantined.append({"record": record, "reason": reason})
            reasons[reason] = reasons.get(reason, 0) + 1
    return {
        "accepted": accepted,
        "quarantined": quarantined,
        "accepted_count": len(accepted),
        "quarantined_count": len(quarantined),
        "reasons": reasons,
    }


GOOD = {"email": "ana@example.com", "age": "24", "country": "IN", "joined": "2026-03-01"}

# empty input and a single good record
empty = split_signups([])
assert empty["accepted_count"] == 0 and empty["quarantined_count"] == 0
assert empty["reasons"] == {}
one = split_signups([GOOD])
assert one["accepted"] == [GOOD] and one["reasons"] == {}

# missing and blank fields
assert check_record({"age": "24", "country": "IN", "joined": "2026-03-01"}) == "missing_field"
assert check_record({**GOOD, "email": "   "}) == "missing_field"
assert check_record({**GOOD, "email": None}) == "missing_field"

# email
assert check_record({**GOOD, "email": "ana@example"}) == "bad_email"
assert check_record({**GOOD, "email": 42}) == "bad_email"

# age: boundaries, booleans, decimals, text
assert check_record({**GOOD, "age": "12"}) == "bad_age"
assert check_record({**GOOD, "age": "13"}) is None
assert check_record({**GOOD, "age": "120"}) is None
assert check_record({**GOOD, "age": "121"}) == "bad_age"
assert check_record({**GOOD, "age": True}) == "bad_age"
assert check_record({**GOOD, "age": "24.5"}) == "bad_age"

# country
assert check_record({**GOOD, "country": "in"}) == "bad_country"
assert check_record({**GOOD, "country": "IND"}) == "bad_country"
assert check_record({**GOOD, "country": " IN "}) is None

# joined date
assert check_record({**GOOD, "joined": "2026-02-30"}) == "bad_joined"
assert check_record({**GOOD, "joined": "01/03/2026"}) == "bad_joined"

# the first broken rule decides the reason
assert check_record({**GOOD, "email": "bad", "age": "5"}) == "bad_email"
assert check_record({**GOOD, "age": "5", "email": ""}) == "missing_field"

# a mixed batch: counts, reasons and order
batch = [
    {**GOOD, "age": "5"},
    GOOD,
    {**GOOD, "email": "x"},
    {**GOOD, "age": "7"},
    {**GOOD, "country": "u"},
]
result = split_signups(batch)
assert result["accepted"] == [GOOD]
assert result["accepted_count"] == 1
assert result["quarantined_count"] == 4
assert result["reasons"] == {"bad_age": 2, "bad_email": 1, "bad_country": 1}
assert [q["reason"] for q in result["quarantined"]] == ["bad_age", "bad_email", "bad_age", "bad_country"]
```

Line by line:

1. `import re` loads the regular expression module. `from datetime import datetime` loads the date parser.
2. `REQUIRED` is a tuple of the four field names. Keeping them in one place means the required check and the lookups use the same list.
3. `EMAIL_PATTERN` is the pattern explained in the skill section. The `r` before the string stops Python treating `\s` as an escape.
4. `COUNTRY_PATTERN` matches exactly two capital letters, and `DATE_PATTERN` matches four digits, a dash, two digits, a dash and two digits. These are checked before the real date parser.
5. `is_missing` returns `True` for `None`, and for text that is blank after stripping. The `isinstance` test stops it calling `strip` on a number.
6. `as_age` turns a valid age into an integer and returns `None` for anything else. Booleans are rejected first, because `True` would otherwise pass as `1`.
7. `check_record` runs the rules in the order given. The first `return` that fires is the reason. If every rule passes, the last line returns `None`.
8. The `for` loop checks that each required field is present. A single missing field returns `missing_field` straight away.
9. The email line uses `record["email"]` safely, because the loop above has already confirmed the key exists. The `isinstance` test rejects numbers, and `fullmatch` requires the whole string to fit the pattern.
10. `as_age` returns `None` for bad input. The test `not (13 <= age <= 120)` is a chained comparison, which means the age must be at least 13 and at most 120.
11. The country check follows the same pattern as the email check.
12. The joined check does the pattern test first, then `strptime` in a `try` block. `strptime` rejects `2026-02-30`, and `except ValueError` turns that error into the `bad_joined` reason.
13. `split_signups` loops over every record. An accepted record goes into `accepted`. A rejected one goes into `quarantined` with its reason, and its reason is counted with `get`.
14. The function returns one dictionary holding both lists, both counts and the reason counts. The counts are the lengths of the lists.
15. The first test block covers empty input and one good record. An empty list must give zero counts and an empty dictionary, not a dictionary full of zeros.
16. The next tests cover blank and missing fields. Each `assert` checks one result, and an assert that fails stops the file with an error.
17. The age tests cover the lower boundary (12 fails, 13 passes), the upper boundary (120 passes, 121 fails), a boolean, and a decimal written as text.
18. The country tests cover lower case, a three-letter code, and surrounding spaces, which are stripped and then accepted.
19. The date tests cover an impossible date and a date written in the wrong order.
20. The tests for the first broken rule show that `bad_email` wins over `bad_age`, and that `missing_field` wins over the rest.
21. The mixed batch has five records. Four are rejected, and each is counted once under its first broken rule. The last assert checks that the quarantined list keeps the input order.

When the file runs without an error, it prints nothing and exits normally. An `AssertionError` shows which line failed.

## Say it out loud

Interviewers and viva examiners will ask you to explain your choices. Practise answering in full sentences.

**Why does your pipeline stop before the load step, and not after it?**

:::answer Model answer
The load step writes data that other people and systems read, so it must only run on data that has passed the checks. If the checks ran after the load, the bad readings would already be in the database and the dashboard. The gate sits between validate and load, so a blocking failure stops the run before anything is written. A bad batch then costs us a rerun, not a corrupted dashboard.
:::

**What does `set -euo pipefail` do, and what goes wrong without it?**

:::answer Model answer
The `-e` option stops the script at the first command that fails, so later stages do not run on bad input. The `-u` option makes an unset variable an error, which catches typing mistakes in names. The `pipefail` option makes a pipeline fail if any part fails, not only the last command. Without `pipefail`, a command piped into `tee` can fail silently, because `tee` returns zero, and the script carries on as though the stage succeeded.
:::

**What is the difference between a blocking check and a warning, and how do you choose?**

:::answer Model answer
A blocking check stops the pipeline when it fails, and a warning is reported while the run continues. I choose blocking for data we must never publish, such as negative PM2.5 readings or duplicate keys, because those would corrupt every view that depends on them. A check on something that is only unusual, such as a drift in the average, is a warning, because stopping the pipeline for it would delay good data. Each threshold needs a reason written beside it.
:::

**What makes your load idempotent?**

:::answer Model answer
Running the load twice leaves the same table as running it once. In the lab, `to_sql` with `if_exists="replace"` drops the old table and writes the new one, so a second run overwrites rather than adds. The course's version runs the pipeline twice from a fresh clone and compares the fact count, which must not change between runs. I would also mention that the replace form is not fully atomic, so a crash mid-load could leave a partial table, and the production fix is to load into a new table and switch.
:::

**Walk me through how a rejected sign-up record is counted.**

:::answer Model answer
The record goes through the rules in a fixed order: missing fields, email, age, country, then joined date. The first rule it breaks gives its reason, and the function stops checking it. The record is added to the quarantined list with that reason, and the count for that reason goes up by one. A record that breaks several rules is counted only once, under the first, so the reason counts always add up to the quarantined count.
:::

```cards
blocking check :: A check whose failure stops the pipeline with a non-zero exit code.
exit code :: A number a program returns on finishing: 0 means success, anything else means failure.
set -euo pipefail :: Strict mode: stop on any failing command, unset variable or failed pipe part.
idempotent :: Running it twice leaves the same result as running it once.
high-water mark :: The largest event timestamp already loaded, used to find new rows next time.
quarantine :: A store for rejected rows, kept with the reason so they can be investigated.
drift :: A change in the data's pattern over time, even when every rule still passes.
schema validation :: Checking that the required columns exist, before any row checks run.
retry with backoff :: Retrying a transient failure with longer waits and a fixed maximum number of attempts.
atomic publish :: Readers see either the complete old version or the complete new version, never a partial one.
fail-fast :: Stopping at the first real error instead of carrying bad data into later stages.
```
