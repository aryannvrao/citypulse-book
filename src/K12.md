## Y2-T42 · P8: sign off API with tests and containerise it with a Dockerfile

*Session 42 · phase E8 · 8 points*

### The ticket in plain words

Until now CityPulse ran on your laptop, because you had installed Python, the packages and the model file by hand. This ticket finishes the API phase with two jobs.

The first job is to make the API understandable to a stranger. The client must read the README, paste each `curl` command and get the answer the README promises. You also add a collection file, which is a saved set of every request that an API tool such as Postman can run, and you measure how fast the prediction endpoint answers.

The second job removes the phrase "works on my machine". Code runs for its author, who has the right Python and a package installed months ago, and then fails for everyone else. A container carries its own operating system, Python and packages in one image, so the only thing another machine needs is Docker.

The test is strict. Another squad will run your container using only your README. The client's platform engineer will not guess a missing step. They will run one `docker run` command and expect the API to answer on port 8000 within 20 seconds.

### Before you start

These must already be merged on main:

- Y2-T39: the `POST /v1/predict` endpoint.
- Y2-T40: stricter request checks, one error envelope and JSON log lines.
- Y2-T41: at least 10 API tests and a CI coverage gate of 60 per cent.
- The merged pull request "Tests in CI", with the `api/` folder, `models/model_v1.joblib`, `docs/api.md`, and Docker on every laptop.

You need a GitHub account with write access to the squad repository, the GitHub command line tool `gh` (logged in with `gh auth login`), Docker Desktop running, Git for Windows (which gives you Git Bash), the load tester `hey`, and Postman or Bruno. Run every command in this guide in Git Bash, not in Windows PowerShell, where `curl` is a different program.

```term
$ docker info --format '{{.ServerVersion}}'
27.0.3
```

`docker info` describes the Docker engine. `--format '{{.ServerVersion}}'` prints only the engine's version number. An error about connecting to the Docker daemon means Docker Desktop is not running.

```term
$ command -v hey
/c/Users/you/go/bin/hey
```

`command -v` prints where a program lives. A path means `hey` is on your path. No output means it is missing. Check `git`, `curl` and `gh` the same way.

### How your trainer checks it

The trainer checks six acceptance criteria: CI green on tag `v0.8-p8` with at least 10 tests and 60 per cent coverage; every README curl returning the documented result; a collection file and the latency numbers in `docs/api.md`; a fresh clone that builds and serves `/v1/health` within 20 seconds; a non-root user in the container; and a swap test with at most one README fix. You prove the first one by reading the GitHub Actions run for the tagged commit. The test cases below check the rest.

#### TC1: fresh clone, build and run

The trainer runs this in Git Bash:

`git clone ... && git checkout v0.8-p8 && docker build -t cp-test . && docker run -d --name cp -p 8000:8000 --env-file .env.example cp-test && sleep 8 && curl -i localhost:8000/v1/health`

- `git clone ...` copies the repository into a new folder. (Run `cd` into that folder before the next command.) The dots stand for its address. Only committed files arrive, so an uncommitted model file on your laptop would not exist here.
- `&&` runs the next command only if the previous one succeeded.
- `git checkout v0.8-p8` switches to the commit carrying the tag. Git reports a detached HEAD, which is expected for a tag.
- `docker build -t cp-test .` builds an image named `cp-test` from the Dockerfile in the current folder.
- `docker run -d --name cp -p 8000:8000 --env-file .env.example cp-test` starts a container in the background, named `cp`. `-p 8000:8000` forwards machine port 8000 to container port 8000. `--env-file` loads the settings in the example file.
- `sleep 8` waits eight seconds for the server to start.
- `curl -i localhost:8000/v1/health` asks for the health check. `-i` prints the status line too.

Passing output looks like this:

```term
$ docker run -d --name cp -p 8000:8000 --env-file .env.example cp-test
3f9c2a7d1b44e0f58c2a91d7e6b3c4d5a6f7e8d9c0b1a2f3e4d5c6b7a8f9e0d1
$ sleep 8 && curl -i localhost:8000/v1/health
HTTP/1.1 200 OK
content-type: application/json
```

The container ID is different on every run. The line that counts is `HTTP/1.1 200 OK`.

Failing output and its usual cause:

- `curl: (7) Failed to connect to localhost port 8000` means nothing listens on port 8000. The container stopped, `-p` is missing, or the server needs longer than eight seconds. Run `docker ps -a` and `docker logs cp`.
- `Conflict. The container name "/cp" is already in use` means an old container named `cp` exists. Remove it with `docker rm -f cp`.
- `Bind for 0.0.0.0:8000 failed: port is already allocated` means another program or container holds the port.
- An error about opening `.env.example` means the file is not committed.
- A 500 status or an empty reply means the server failed on a request. Read `docker logs cp`.

#### TC2: prediction request

`curl -s -X POST localhost:8000/v1/predict -H 'Content-Type: application/json' -d @docs/api/predict_example.json`

- `-s` hides the progress meter and also hides errors, so remove it when you debug.
- `-X POST` sets the method.
- `-H 'Content-Type: application/json'` tells the server the body is JSON.
- `-d @docs/api/predict_example.json` sends the file as the body. The `@` means "read from this file". Without it, curl sends the file name as text.

Passing: status 200 with a JSON body holding a prediction and `model_version`.

Failing: `422` means the body does not match the schema, so compare its keys with the schema in `api/`. `500` means the prediction code failed, so read the logs. `curl: (26) Failed to open/read local data` means the path is wrong; run the command from the repository's top folder.

#### TC3: user and logs

`docker exec cp whoami` and `docker logs cp | tail -3`

- `docker exec cp whoami` runs `whoami` inside the running container.
- `docker logs cp` prints what the container wrote.
- `|` sends that output into `tail -3`, which keeps only the last three lines.

Passing: a user name other than `root`, and three JSON log lines.

Failing: `whoami: cannot find name for user ID 10001` means the user has a number but no name. It is not root, but a named user is cleaner, as stage 4 below shows. `root` means the Dockerfile has no `USER` line. Empty logs mean no request has arrived yet, so run TC2 first.

#### TC4: collection

The trainer imports `docs/api/` into Postman or Bruno, sets `baseUrl` to `http://localhost:8000` and runs everything. Each request writes `{{baseUrl}}` in its address, and the tool replaces it with the variable's value before sending.

Passing: each request returns its documented status, and the invalid request returns 422. A 404 on a valid request means the collection path does not match the route. A 400 or 500 on the invalid request means the error handling from Y2-T40 changed the status, so fix the handler, not the collection.

### Do it, step by step

#### Y2-T42.1: the gate check

Goal: know, before anything else, that main is green with at least 10 tests and 60 per cent coverage. Fix red first, because you cannot tag a red commit.

Stage 1. Read the latest main run:

```term
$ gh run list --branch main --limit 1
STATUS  TITLE                  WORKFLOW  BRANCH  EVENT  ID          ELAPSED  AGE
✓       Merge pull request 41  CI        main    push   1234567890  2m       3h
```

`gh run list` asks GitHub for recent Actions runs. `--branch main` keeps main, and `--limit 1` shows only the latest. The first column is the result, and the ID opens the log with `gh run view <ID> --log`.

Stage 2. Find the numbers in the log. The pytest summary says something like `12 passed`. The coverage table ends with a `TOTAL` line whose last column is the percentage. Example layout, with made-up numbers:

```term
TOTAL    412     98    76%
```

Stage 3. If it is green with at least 10 tests and 60 per cent, post the run ID and both numbers to your squad. If it is red, fix the first failing test on a branch and merge it before continuing.

#### Y2-T42.2: route metadata

Goal: `/docs` shows each route with a title, a description and a pre-filled example. FastAPI builds that page from your routes, so you edit the routes.

Technique first, in a scratch folder, not in the repository:

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/v1/ping", summary="Check that the service is up")
def ping():
    return {"status": "ok"}
```

`app = FastAPI()` creates the object that `uvicorn` will find by name. `@app.get(...)` ties the function below to GET `/v1/ping`. `summary=` is the text `/docs` shows for that route. The function's return value becomes the JSON reply. Save it as `demo.py`, run `python -m uvicorn demo:app --port 8000` in that folder, then open `http://localhost:8000/docs` to see the summary.

Stage 1. Add `summary=` and `description=` to the decorator for `/v1/predict` in `api/`. Write the text yourself, describing what the route does.

Stage 2. Add `response_model=` naming your reply schema class. It tells FastAPI and `/docs` the reply shape. Restart the API and check `/docs`.

Stage 3. Attach an example to the schema class. In Pydantic version 2 you do it with `model_config`:

```python
from pydantic import BaseModel, ConfigDict


class Reading(BaseModel):
    model_config = ConfigDict(
        json_schema_extra={"examples": [{"station": "S1", "pm25": 14.2}]}
    )

    station: str
    pm25: float
```

`ConfigDict` holds the model's settings. `json_schema_extra` adds extra entries to the schema that `/docs` builds, and `"examples"` is a list of example bodies, of which `/docs` pre-fills the first. The example must use the class's field names. This class is an illustration; use your own schema.

Test: open `/docs`, choose `/v1/predict`, press "Try it out" and then "Execute". The example should be filled in and return 200. A 422 means the example does not match the schema.

#### Y2-T42.3: the README "API" section

Goal: a stranger can call every endpoint by pasting your curl commands.

Stage 1. Write the base URL, `http://localhost:8000` for a local run, and a table with one row per endpoint: method, path and one sentence.

Stage 2. Under the table, give one curl block per endpoint, followed by the expected status and the start of the body.

Stage 3. Paste every curl into a fresh Git Bash window, with the API running, exactly as written. If one fails, fix the README unless the command itself is wrong. Keep a count of fixes, because the swap test depends on it.

#### Y2-T42.4: the collection

Goal: one file that runs every endpoint and one invalid request.

Technique first: a variable. If a request address is `{{baseUrl}}/v1/health` and the environment sets `baseUrl` to `http://localhost:8000`, the same collection can point at any server by changing one value.

Stage 1. Create an environment with a variable named `baseUrl`. Do not type the address into each request.

Stage 2. Add one request per endpoint, with `{{baseUrl}}` in front of the path, and the body from `docs/api/predict_example.json` where needed.

Stage 3. Copy the prediction request, remove a required field and save it as an invalid request. Its expected status is 422.

Stage 4. Export to `docs/api/citypulse.postman_collection.json`, or to `docs/api/bruno/` if you use Bruno. Menu names vary between versions, so look for "Export" in the collection menu. Do not commit secret values.

#### Y2-T42.5: latency and the tag

Goal: measure `/v1/predict`, record the result and tag the release.

Technique first: percentiles. If ten requests took 0.10, 0.11, 0.11, 0.12, 0.12, 0.13, 0.13, 0.14, 0.16 and 0.45 seconds, the p50 is the middle value, about 0.12 seconds. The p95 sits near the slowest request, and it shows how bad the slow cases get.

Stage 1. With the API running, run the command from the ticket:

```term
$ hey -n 200 -c 10 -m POST -T application/json -D docs/api/predict_example.json http://localhost:8000/v1/predict
```

`-n 200` sends 200 requests. `-c 10` keeps 10 in flight. `-m POST` sets the method. `-T` sets the Content-Type. `-D` reads the body from the file, the same as `@` in curl.

Stage 2. In the "Latency distribution" block, read the lines marked `50%` and `95%`. Record them with the full command in `docs/api.md`, so someone else can repeat it.

Stage 3. Answer each review comment on the PR. Change the code or text where the comment is right, and resolve a comment only after answering it.

Stage 4. Confirm the commit is on main and its run is green, then tag it:

```term
$ git checkout main && git pull
$ git tag v0.8-p8
$ git push origin v0.8-p8
```

`git pull` brings in the latest commits. `git tag` names the current commit, and `git push origin` sends that one tag to GitHub.

#### Y2-T42.6: the Dockerfile and .dockerignore

Goal: a Dockerfile that builds the API image, and a .dockerignore that keeps unwanted files out.

Docker runs the Dockerfile's lines top to bottom. Each line that changes the image is a layer, and Docker reuses a layer while its line and its input files are unchanged. So you put the slow package install before the code. Write the file yourself, one stage at a time, building after each stage. The fragments below are not a finished file.

Stage 1. The base image and the working folder:

```dockerfile
FROM python:3.11-slim
WORKDIR /app
```

`FROM` names the base image, a small Linux with Python 3.11. `WORKDIR /app` sets the folder for later lines. Build with `docker build -t citypulse-api:p8 .`. The build should finish.

Stage 2. Install the packages before the code:

```dockerfile
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
```

`COPY requirements.txt .` copies that file into `/app`. `RUN` runs a command during the build. `--no-cache-dir` stops pip keeping a download cache. Build again. A second build with no change prints `CACHED` on these steps.

:::trap COPY . . above the install
If `COPY . .` comes before `pip install`, any code edit changes the layer above the install, and every build reinstalls all packages. Copy requirements first.
:::

Stage 3. Copy the code and the model:

```dockerfile
COPY api/ api/
COPY src/ src/
COPY models/ models/
```

Each line copies one folder with the same name. A missing folder fails the build, so check the names with `ls`. `models/model_v1.joblib` must be committed, or TC1 fails on the trainer's fresh clone.

Stage 4. A named non-root user:

```dockerfile
RUN useradd --create-home --uid 10001 appuser
COPY --chown=10001:10001 api/ api/
COPY --chown=10001:10001 src/ src/
COPY --chown=10001:10001 models/ models/
USER 10001
```

`useradd` creates a user with number 10001 and the name `appuser`. `--chown` makes that user the owner of the copied files, so the app can read them. Replace the Stage 3 copy lines with these, rather than keeping both. `USER 10001` makes the container's commands run as that user, not root. Check:

```term
$ docker run --rm citypulse-api:p8 id -u
10001
```

`docker run --rm` starts a container for one command and removes it. `id -u` prints the numeric user. It is the safe check, because `whoami` needs the name to exist.

Stage 5. The port and the start command:

```dockerfile
EXPOSE 8000
CMD ["uvicorn", "api.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

`EXPOSE` documents the port but does not publish it, so `-p` is still needed. `CMD` is the command that starts the container. `api.main:app` names the `app` object in `api/main.py`. `--host 0.0.0.0` lets connections in from outside the container.

Stage 6. Create `.dockerignore`, one path per line:

```text
.git
.venv
data/raw
__pycache__
.env
```

These paths stay out of the build context. `.env` holds real secrets, so it must never reach the image. Test with `docker build --no-cache -t citypulse-api:p8 .`, then `docker run --rm citypulse-api:p8 ls -a /app`. The listing must not show `.env` or `.git`.

#### Y2-T42.7: run on your laptop

Goal: the image runs on your machine, and you show the evidence.

Stage 1. Build and run:

```term
$ docker build -t citypulse-api:p8 .
$ docker run --rm -p 8000:8000 -e DATABASE_URL=... citypulse-api:p8
```

`--rm` removes the container when it stops. Replace the dots with your real value in your own terminal only. Never paste it into a commit, a file or a PR, because a database address can hold a password.

Stage 2. From a second window, check the same things the trainer checks:

```term
$ docker ps
$ curl -i localhost:8000/v1/health
```

`docker ps` lists running containers with their ports and names. The request travels this route:

```flow
TITLE: One request, from your terminal to the API
NODES: Git Bash | Port 8000 on your laptop | Container | FastAPI route
STEPS:
1>2 :: curl localhost:8000 :: Your terminal sends the request to your own machine.
2>3 :: forward to container :: Docker passes it through the port that -p published.
3>4 :: call the route :: uvicorn hands the request to the matching function.
4>3 :: JSON reply :: The function returns its reply with a status code.
3>1 :: HTTP 200 :: The reply comes back to your terminal.
```

Stage 3. Paste the `docker ps` output and both curl outputs into the pull request.

#### Y2-T42.8: "Run with Docker" and the swap test

Goal: write steps that work for a stranger, then prove them on someone else's repository.

Stage 1. Under "Run with Docker", list each command in order: clone, check out the tag, build, run with the environment file, and check health. For each, state the correct result. Name each environment variable and where its value comes from, but never write a real value.

Stage 2. Clone the paired squad's repository into an empty folder, for example `git clone <their address> swap-test`. Follow only their README steps. Do not use anything from your own machine.

Stage 3. Each time a step fails or needs a guess, record its number, the command, the output and what you expected. File the first problem as an Issue on their repository:

```term
$ gh issue create --title "Run with Docker: step 3 fails" --body "Command, output and expected result, in your own words."
```

Do not change their code. The swap test checks their README, and your target is at most one fix to it. Record the count on the scorecard.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| Every build reinstalls packages | A broad `COPY` sits above the install line | Copy `requirements.txt`, install, then copy the folders |
| Build fails with "not found" on `models/` | The folder or file is missing or not committed | Check names with `ls`, then commit and recheck with `git status` |
| `curl: (7) Failed to connect` | Container not running, `-p` missing, or server still starting | Run `docker ps -a` and `docker logs cp`, then wait longer |
| Container stops at once | Wrong `CMD` path or a missing setting | Read `docker logs cp` and check `api.main:app` |
| `whoami` says cannot find name for user ID 10001 | The user has no name in the image | Create it with `useradd --uid 10001` and use `id -u` |
| `whoami` prints `root` | No `USER` line after the copies | Add `USER 10001` after the copy stages |
| Prediction returns 422 | Body does not match the schema, or the header is missing | Compare keys with the schema and check the `-H` and `@` parts |

### Defend it in the viva

Answer in your own words. The model answers show the reasoning, and you should not learn them by heart or claim work your commits do not show.

**1. Why does the Dockerfile install packages before copying the code?**

:::answer Model answer
Docker reuses a layer while its instruction and inputs are unchanged. Installs are slow and change rarely, while code changes often. Installing first means a code edit reuses the install layer, so the build takes seconds instead of minutes.
:::

**2. What is the trade-off of pinning `python:3.11-slim` instead of `latest`?**

:::answer Model answer
A pinned tag means the image moves only within Python 3.11 patch releases, never to a new major version unexpectedly, so the build is far more repeatable. A fully fixed digest would be stricter still. The cost is that you must update the tag yourself to get security fixes. `latest` moves on its own and can break a model or package without warning. The slim variant has fewer packages to patch, but it may lack a tool a build step needs.
:::

**3. What does `-p 8000:8000` do, and why does TC1 need it?**

:::answer Model answer
It publishes a port. The left number is the machine's port and the right is the container's. Without it the server runs but nothing outside the container can reach it, so `curl localhost:8000` is refused. `EXPOSE` documents the port and does not publish it.
:::

**4. Why not run as root, and how do you prove the user?**

:::answer Model answer
A root process has more rights than it needs, so any bug that runs commands runs them with those rights. A non-root user limits the damage. Prove it with `docker exec` and `id -u`, which should not print 0. Explain why `id -u` is safer than `whoami` when the user has no name.
:::

**5. Describe what you personally did, and how you proved each part.**

:::answer Model answer
Name the subtask you owned and the commits you made, then the test you ran for each one. Say which test case you ran from a fresh clone, what it showed, and what you would change if it failed. Name the reviewer who approved your PR. Build this from your own Git history, not from memory.
:::

**TC1: size.** The steps are `docker build -t cp:h . && docker images cp:h --format '{{.Size}}'`.

- `docker build -t cp:h .` builds the image from the Dockerfile in the current folder and tags it `cp:h`.


**TC2: non-root.** The steps are `docker run --rm cp:h id -u`.

- `docker run --rm` starts a container and deletes it when the command finishes.
- `cp:h` names the image.
- `id -u` prints the numeric user ID the command runs as.

Passing output is a single number that is not zero, for example `10001`. A failing output is `0`. The usual cause is a Dockerfile with no `USER` line, or a `USER` line placed in the wrong stage.

**TC3: scan.** The steps are `docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy image --severity CRITICAL cp:h`.

- `docker run --rm` runs Trivy in a temporary container.
- `-v /var/run/docker.sock:/var/run/docker.sock` gives Trivy access to Docker, so it can read the image on your machine.
- `aquasec/trivy` is the Trivy image.
- `image --severity CRITICAL cp:h` scans the image and shows only CRITICAL findings.

On Git Bash, put `MSYS_NO_PATHCONV=1` in front of the command. Without it, Git Bash rewrites the socket path and Docker cannot find it. On Linux, leave it out.

Passing output lists zero CRITICAL findings, or lists each one, and every listed CVE ID appears in `docs/security/README.md` with an action. A failing output shows a CVE that is not in the README. The usual cause is that the README was not updated after the last scan.

**TC4: compose.** The steps are `cp .env.example .env && docker compose up --build -d && sleep 20 && curl -s localhost:8000/v1/stats && docker compose ps`.

- `cp .env.example .env` creates the real settings file from the template.
- `docker compose up --build -d` builds the images and starts the services in the background.
- `sleep 20` waits 20 seconds so the database and the API can start.
- `curl -s localhost:8000/v1/stats` requests the stats page. `-s` hides the progress meter.
- `docker compose ps` lists both services with their health.

Passing output is JSON from `/v1/stats`, and the `STATUS` column shows `(healthy)` for both `db` and `api`. A failing output is a connection refused error, or `(unhealthy)`, or a JSON error from the API. The usual causes are a wrong host in `DATABASE_URL` (see the troubleshooting table) or a database that was still starting after 20 seconds. The API health check runs every 15 seconds, so `api` can still say `(health: starting)` at the 20-second mark. If so, run `docker compose ps` again a few seconds later.

**TC5: git.** The steps are `git ls-files | grep -x .env`.

- `git ls-files` lists every file Git tracks.
- `|` sends that list to `grep`.
- `grep -x .env` keeps only lines that match `.env` exactly.

Passing output is nothing at all. Failing output prints `.env`, which means the file is committed. Remove it from Git without deleting your copy with `git rm --cached .env`, add it to `.gitignore`, and commit the change. A password that was committed stays in Git history, so change that password as well.

**Stage B: record the size.**

This prints one size, for example `312MB`. Write it down next to the build time.

**Stage C: record the scan counts.**

- The first line scans the image and shows only HIGH and CRITICAL findings. `| tee` shows the report on screen and saves it to `docs/security/trivy-before.txt`. Create the folder first with `mkdir -p docs/security`.

#### Y2-T43.2: pin the dependencies

**Goal.** Every line in `requirements.txt` has `==` and an exact version. Test-only packages move to a second file.

**Stage A: make a clean environment.** A clean virtual environment shows what installs from a fresh start, without packages left over from your machine.

```bash
python -m venv .venv-pin
source .venv-pin/bin/activate
pip install -r requirements.txt
pip freeze
deactivate
```

- `python -m venv .venv-pin` creates a new environment in the folder `.venv-pin`.
- `source .venv-pin/bin/activate` switches your shell to use that environment. On Git Bash on Windows, use `source .venv-pin/Scripts/activate` instead.
- `pip install -r requirements.txt` installs what the file names.
- `pip freeze` prints every installed package as `name==version`, including packages that other packages need.
- `deactivate` switches back to your normal Python.

Expected output lines look like `fastapi==0.115.4`. Do not copy every line blindly. Pin the versions your team tested. For scikit-learn, use the version the model was trained with, from your squad's notes. A wrong version can stop the saved model loading.

**Stage B: edit the file.** Each line becomes `name==version`. Move `pytest` and `httpx` out of `requirements.txt` into `requirements-dev.txt`. They are needed for tests, not for running the server. Start `requirements-dev.txt` with the line `-r requirements.txt`, so installing the dev file also installs the runtime packages that pytest needs. Also add `.venv-pin/` to `.gitignore` so the test environment is never committed.

**Stage C: pin the base image.** Use the base tag your T42 Dockerfile used, or the one your team agrees, and make sure it is a patch-level tag with three numbers, such as `python:3.11.9-slim` (the example used in this guide). Check that Docker can fetch it.

```bash

```

Expected output ends with `Status: Downloaded newer image` or `Status: Image is up to date`.

**Stage test.** The first command must print nothing. It finds lines that are not comments or blank, and that have no `==`. The second installs the test tools and runs the tests.

```bash

```

Expected output: the first command prints nothing. The second ends with a line such as `12 passed`. If it prints a failure, the pin for one package is wrong.

#### Y2-T43.3: write the Dockerfile in two stages

**Goal.** A builder stage makes the virtual environment. A runtime stage copies only that environment and the code, runs as user 10001, and checks its own health.

Build the file in stages. Type each stage yourself and save it into one `Dockerfile`. Do not paste a whole file from elsewhere.

**Stage A: the builder.** The first `FROM` names the builder with `AS`.

```dockerfile
FROM python:3.11.9-slim AS builder
COPY requirements.txt .
RUN python -m venv /opt/venv && /opt/venv/bin/pip install --no-cache-dir -r requirements.txt
```

- `FROM ... AS builder` starts the first stage and names it, so a later line can copy from it.
- `COPY requirements.txt .` copies only the requirements file. It comes before the code, so this layer stays cached when code changes.
- `RUN python -m venv /opt/venv` creates the virtual environment at `/opt/venv`.
- `&& /opt/venv/bin/pip install ...` runs the install with the pip that belongs to that environment. `&&` runs it only if the first command succeeded.
- `--no-cache-dir` stops pip keeping a download cache, which would make the layer bigger.

Expected output when you build later: a line saying the install step `DONE`.

**Stage B: the runtime stage starts clean.** A second `FROM` starts from an empty base again. Nothing from the builder comes with it.

```dockerfile
FROM python:3.11.9-slim
ENV PATH="/opt/venv/bin:$PATH" PYTHONUNBUFFERED=1
COPY --from=builder /opt/venv /opt/venv
WORKDIR /app
```

- `FROM python:3.11.9-slim` with no `AS` starts the final stage. Only this stage becomes the image.
- `ENV PATH=...` puts `/opt/venv/bin` first, so `python` and `uvicorn` come from the virtual environment. `PYTHONUNBUFFERED=1` makes logs appear at once.
- `COPY --from=builder /opt/venv /opt/venv` copies only the environment from the builder. The compiler and the pip cache stay behind.
- `WORKDIR /app` sets the working folder for the next lines and creates it.

**Stage C: the code, owned by the app user.** The code folders must be owned by user 10001, or the app cannot write files it needs.

```dockerfile
COPY --chown=10001:10001 api/ api/
COPY --chown=10001:10001 src/ src/
COPY --chown=10001:10001 models/ models/
```

The folder names above (`api/`, `src/`, `models/`) are only examples. Use the folder names that are really in your repository, and copy only what the app needs at run time. `--chown` sets the owner and group of copied files. A `COPY` without it leaves files owned by root.

**Stage D: the user and the health check.**

```dockerfile
USER 10001
HEALTHCHECK --interval=15s --timeout=3s CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/v1/health', timeout=2)"
CMD ["uvicorn", "api.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

- `USER 10001` runs everything after this line, and the container's process, as user 10001.
- `HEALTHCHECK --interval=15s --timeout=3s` runs the check every 15 seconds. Each check must finish within 3 seconds.
- `CMD python -c "..."` runs Python with a one-line program. `urlopen` requests `/v1/health` on localhost, inside the container. If the request fails or the server returns an error code, Python raises an error and exits non-zero. Docker then marks the container unhealthy.
- The check uses Python because `python:3.11.9-slim` does not normally include `curl`.
- `CMD ["uvicorn", ...]` starts the server. `--host 0.0.0.0` lets traffic from outside the container reach it.

Optionally add `--start-period=10s` to the `HEALTHCHECK` line, to ignore failures while the app starts. If you add it, be ready to explain it in the viva.

**Stage D2: keep the build context small.** Create a `.dockerignore` file next to the Dockerfile. It lists paths Docker must not send into the build, so they cannot leak into an image and builds start faster. Example lines, one per line:

```text
.git
.env
.venv*
__pycache__/
docs/
```

Each line is a path pattern. `.env` here matters: real passwords must never be baked into an image. Add what else your repository holds that the app does not need. Do not ignore a folder your `COPY` lines use.

**Stage E: build and test.**

```bash
docker build -t citypulse-api:hardened .
docker run --rm citypulse-api:hardened id -u
```

Expected output of the second command: `10001`. If you see `0`, the `USER` line is missing or placed in the wrong stage. If the build fails on a `COPY` line, check the folder names against the folders on disk.

**Stage test.** Run `docker history citypulse-api:hardened` in Y2-T43.4, where you compare sizes. Here, the build and the `id -u` check are enough.

#### Y2-T43.5: the scan report, the SBOM and the decisions

**Goal.** Commit the evidence, and give each remaining finding one decision.

**Stage A: the SBOM.** Trivy can print the SBOM to standard output. Redirecting that output to a file avoids mounting folders, which is simpler on Git Bash.

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy image --format cyclonedx citypulse-api:hardened > docs/security/sbom.cdx.json
```

`--format cyclonedx` writes the CycloneDX format. The `>` sends the output into `docs/security/sbom.cdx.json`. Test it with `python -m json.tool docs/security/sbom.cdx.json > /dev/null && echo valid`. Expected output: `valid`.

### Defend it in the viva

**1. Why does the runtime stage start from a fresh base image instead of the builder?**

:::answer Model answer
The runtime stage is the only stage that becomes the shipped image. Starting it from a clean base means the compiler, the pip cache and build tools from the builder are not in the image, even though the builder used them. Copying with `COPY --from=builder` takes only the finished virtual environment. This makes the image smaller, and it removes tools an attacker could use if they got into the container.
:::

**2. What is the trade-off of pinning exact versions?**

:::answer Model answer
Exact pins make builds repeatable. The same code installs the same packages, so a test result today still holds next month. The cost is that pins do not receive security fixes automatically. You must rescan with Trivy on each release, raise the pins that have a fix, and rerun the tests after each change. A pin that is never updated is a known risk, which is why the scan report exists.
:::

**3. What did you personally do in this ticket?**

:::answer Model answer
Name the subtask you owned, the commits you made, and the command that proved each one. A strong answer is specific: which stage of the Dockerfile you wrote, which line you explained in the comment, and which output you checked, for example the `id -u` result. Do not describe work you did not do. The trainer checks commits, so your answer should match them.
:::

**4. How does the API find Postgres in compose, and why does the health condition matter?**

:::answer Model answer
Compose puts both services on a private network where each service name is a host name. The API uses `db` in `DATABASE_URL`, not `localhost`, because `localhost` inside the API container means the API container itself. `depends_on` with `condition: service_healthy` waits until `pg_isready` passes. Without the condition, Compose only sets the start order, and the API can start while Postgres is still starting and fail to connect.
:::

**5. A scan shows a CRITICAL finding with no fixed version. What do you do?**

:::answer Model answer
You do not ignore it. You add a row to `docs/security/README.md` with the CVE ID, the package, the severity, the action "no fix available", and a reason. The reason should say whether the vulnerable code is reachable from the API, and when you will check again. The finding is rescanned on each release, because a fix may appear later.
:::

## Y2-T44 · CI: lint → test → build and push SHA-tagged image on merge to main

*Session 44 · phase E8 · 5 points*

### The ticket in plain words

Right now CityPulse images are built by hand, on whichever laptop happens to be free. Nobody can prove which code is inside a given image. This ticket replaces that habit with one automatic pipeline. A pipeline is a set of steps that a machine runs for you every time the code changes.

The pipeline runs in three stages, in order. First it checks the code style (lint). Then it runs the tests. Only if both pass does it build the container image, which is a packaged copy of the app, and push it to a registry, which is a storage shelf for images. The image is labelled with the git commit SHA, the unique code name of the exact code it was built from.

Why does this matter before cloud deployment? The team must know that what goes live is exactly what was tested. The ticket names the Knight Capital failure of 2012, where a trading firm's new code reached only some of its servers and the old code kept running on the rest. Deploying one SHA everywhere prevents that kind of mismatch.

The pipeline also logs in to the registry with a temporary token that GitHub creates for each run. No password is ever typed into a file that Git stores.

When you finish, the main branch has a green run, the registry holds an image tagged with the commit SHA, the health endpoint reports that SHA, and the README tells anyone how to pull and run it.

#### Subtask Y2-T44.1: Default permissions and concurrency

**Goal.** Give every job the smallest rights by default, and stop old runs of the same branch from wasting time.

**Stage 1: add two top-level keys.** Open `.github/workflows/ci.yml`. Keys at column zero sit beside `on:` and `jobs:`. Add these lines. Do not replace the file:

```yaml
permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

Line by line:

- `permissions:` at the top level sets the default rights for every job. `contents: read` lets jobs read the code and nothing else.
- `concurrency:` controls runs that share a group.
- `group: ci-${{ github.ref }}` gives each branch its own group. `github.ref` is the full ref of the run: `refs/heads/main` for a push to main, and `refs/pull/<number>/merge` for a pull request.
- `cancel-in-progress: true` cancels an older run in the same group when a new run starts.

:::trap Cancelling main
On `main`, a newer push cancels the older run. The older commit may never reach build-push. Keep this in mind for the viva.
:::

**Stage 2: test the file.** Run this on your laptop:

```bash
python3 -c "import yaml;d=yaml.safe_load(open('.github/workflows/ci.yml'));print(d['permissions'], d['concurrency'])"
```

Expected output:

```text
{'contents': 'read'} {'group': 'ci-${{ github.ref }}', 'cancel-in-progress': True}
```

`yaml.safe_load` reads the file and returns Python dictionaries. Python prints `True` with a capital T. A traceback instead means the indentation is wrong. Fix it before going on.

#### Subtask Y2-T44.2: The lint job, and test waits for lint

**Goal.** Make code style and Dockerfile errors stop the pipeline before tests run.

**The two linters.** ruff checks Python code. hadolint checks Dockerfiles. You will not install hadolint. The project publishes it as a container image, so Docker runs it:

```bash
docker run --rm -i hadolint/hadolint < Dockerfile
```

Line by line: `docker run` starts a container. `--rm` deletes the container when it finishes. `-i` keeps input open, so the file can be fed in. `hadolint/hadolint` is the image name. `< Dockerfile` sends the file into the container. A clean Dockerfile prints nothing. A problem prints a code such as `DL3008` with a line number.

**Stage 1: check locally.** Run:

```bash
ruff check .
```

Expected output is either a line saying `All checks passed!`, or a list of problems followed by a count. Fix each one. `ruff check . --fix` repairs the safe ones automatically. Read the diff before you commit it. Do not switch rules off to hide errors. Check your local version with `ruff --version`, and pin the same version in CI as in the `pip install` line, because different versions report different things.

**Stage 2: add the lint job.** Under `jobs:`, at the same indentation as `test:`:

```yaml
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install ruff==<your-version>
      - run: ruff check .
      - run: docker run --rm -i hadolint/hadolint < Dockerfile
```

Line by line: `lint:` names the job. `runs-on` gives it a fresh Ubuntu machine. `actions/checkout@v4` copies the repository onto the machine. The `pip install` line installs ruff. The next two `run:` lines are the checks from Stage 1. Each command exits with zero on success, and any other exit code fails the step.

**Stage 3: make test wait.** Under `test:`, add one line:

```yaml
  test:
    needs: lint
    runs-on: ubuntu-latest
```

`needs: lint` means test starts only after lint succeeds. Check the order with the same yaml command you used in subtask 44.1, but print `d['jobs']['test']['needs']`. Expected output is `lint`.

#### Subtask Y2-T44.3: The build-push job

**Goal.** Build the image and push it under its full SHA, but only for a push to `main` after tests pass.

**Stage A: the gate.** Add the job header. It names the job, says what it waits for, says when to run, and sets the rights:

```yaml
  build-push:
    needs: test
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
```

Line by line: `needs: test` makes the job wait for tests. `if:` is a condition. `github.event_name` is the event, `github.ref` is the branch, `==` means "equals", and `&&` means "and". On a pull request the condition is false, so the job is skipped. `permissions:` here is job level, which adds `packages: write` for this job only.

**Stage B: checkout and login.** Add these steps under `steps:`:

```yaml
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
```

`setup-buildx-action` prepares the builder that supports the cache options. `login-action` logs in to `ghcr.io`. `username` is the person who started the run. The `password` is the short-lived GITHUB_TOKEN, which you never type.

**Stage C: the tag names.** Add a step with an `id`, so later steps can read its output:

```yaml
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha,format=long,prefix=
            type=sha
```

Line by line: `id: meta` names the step. `images:` is the registry path, which must be lowercase. `github.repository` is `owner/repo-name`, so the image is `ghcr.io/owner/repo-name`; with a repository called `citypulse-squadnn` that gives `ghcr.io/org/citypulse-squadnn`. `tags: |` is a YAML block: each indented line is one rule. `type=sha,format=long,prefix=` gives the full 40-character SHA with no prefix, which is what TC2 pulls. `type=sha` gives the short form, which by default gets the prefix `sha-`, as the ticket expects.

:::trap Forgetting prefix=
Without `prefix=`, the full tag becomes `sha-<40 characters>`. TC2 pulls the bare SHA, so the pull fails with `manifest unknown`.
:::

**Stage D: build and push.** Add the last step:

```yaml
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          build-args: GIT_SHA=${{ github.sha }}
```

Line by line: `context: .` uses the current folder. `push: true` sends the image after building. `steps.meta.outputs.tags` reads the tags from step C. `cache-from` and `cache-to` with `type=gha` store the build layers in GitHub's cache, so the next run is faster. `build-args` passes the commit SHA into the Dockerfile as `GIT_SHA`.

**Test each stage.** Push the branch after each stage and run `gh run list --limit 1`. Each push must parse. Build-push will not push from a branch, which is correct. Check the dependency with:

```bash
python3 -c "import yaml;d=yaml.safe_load(open('.github/workflows/ci.yml'));j=d['jobs']['build-push'];print(list(d['jobs']), j['needs'], j['if'])"
```

Expected output, if you placed `lint` first in the file (the list follows file order): `['lint', 'test', 'build-push'] test github.event_name == 'push' && github.ref == 'refs/heads/main'`.

#### Subtask Y2-T44.4: Return git_sha from /v1/health

**Goal.** Let a running container say which commit it was built from.

**The idea.** An environment variable is a named value that a program reads when it runs. A build argument is a value passed while the image is built. The Dockerfile copies the first into the image so the app can read it. Watch how the value moves:

```trace
TITLE: Reading GIT_SHA when the route runs
CODE:
import os
def health():
    sha = os.environ.get("GIT_SHA", "unknown")
    return {"status": "ok", "git_sha": sha}
result = health()
STEPS:
1 :: env_GIT_SHA="4b1e9d0c" :: The os module is loaded. The container's environment already holds GIT_SHA, set by the Dockerfile ENV line.
2 :: env_GIT_SHA="4b1e9d0c" :: def stores the function, but nothing inside it runs yet.
5 :: env_GIT_SHA="4b1e9d0c" :: A request arrives, so health() is called.
3 :: sha="4b1e9d0c" :: os.environ.get finds the value, because it is read now, at request time.
4 :: sha="4b1e9d0c"; return={"status": "ok", "git_sha": "4b1e9d0c"} :: The dictionary is built with the SHA inside it.
5 :: result={"status": "ok", "git_sha": "4b1e9d0c"} :: The caller receives the dictionary.
```

**Stage 1: the Dockerfile.** Find the `FROM` line of the runtime stage, the last stage. Add these two lines directly below it:

```dockerfile
ARG GIT_SHA=unknown
ENV GIT_SHA=${GIT_SHA}
```

Line by line: `ARG GIT_SHA=unknown` declares a build argument with a fallback. `ENV GIT_SHA=${GIT_SHA}` copies it into an environment variable that the running app can read. Both lines must be in the runtime stage, because each stage starts empty.

**Stage 2: the route.** Keep the fields the route already returns, and add `git_sha`. Read the variable inside the function, not at the top of the module:

```python
import os

@app.get("/v1/health")
def health():
    return {"status": "ok", "git_sha": os.environ.get("GIT_SHA", "unknown")}
```

Line by line: `import os` loads the module. `@app.get("/v1/health")` connects the function to the address. `os.environ.get("GIT_SHA", "unknown")` returns the value, or `unknown` if it is not set.

**Stage 3: the test.** Add this test beside your existing TestClient tests from Y2-T41. Use your squad's module path in the import:

```python
from fastapi.testclient import TestClient
from app.main import app  # use your squad's module path

def test_health_has_git_sha(monkeypatch):
    monkeypatch.setenv("GIT_SHA", "abc123")
    client = TestClient(app)
    body = client.get("/v1/health").json()
    assert "git_sha" in body
    assert body["git_sha"] == "abc123"
```

`monkeypatch` is a pytest fixture that sets an environment variable for one test only. `TestClient` sends a request to the app without starting a server. Run `pytest -q` and expect a line such as `12 passed`.

**Stage 4: a real request.** Start the app in one terminal, then ask it in another:

```bash
GIT_SHA=abc123 uvicorn app.main:app --port 8000
curl -s localhost:8000/v1/health | jq -r .git_sha
```

Expected output of the second command: `abc123`. `-r` (raw) removes the quotes. `uvicorn` runs the ASGI app, and `app.main:app` is your squad's module and variable name.

:::trap Reading the variable at import time
If the line `GIT_SHA = os.environ.get(...)` sits at the top of the module and the test sets the variable afterwards, the test still sees `unknown`. Reading inside the function avoids this.
:::

### Defend it in the viva

**Question 1: Why must build-push wait for test, and not just run on the same trigger?**

:::answer Model answer
Both jobs would start on the same push, so without `needs: test` a build could push an image before the tests finish. The `needs` line makes GitHub skip build-push when test fails, so a broken change never reaches the registry. That is the gate. Tests decide whether a part is allowed past inspection.
:::

**Question 2: What is a trade-off of `cancel-in-progress: true`?**

:::answer Model answer
It saves runner time and stops stale runs from finishing. The cost is that on `main`, a newer push can cancel an older run before its build-push job finishes, so that older commit never gets an image. For a release branch you might choose to keep every run, and accept the extra time, because every commit should be traceable.
:::

**Question 3: What did you personally do in this ticket?**

:::answer Model answer
Name the subtask you owned, the commits you made, and what each one changed. Then point to the evidence: the commit hash, the run id, and the output of the check you ran. A strong answer is specific and can be checked in Git. Do not describe work you did not do.
:::

**Question 4: Why tag the image with the full SHA rather than `latest`?**

:::answer Model answer
A SHA always points to one commit, so you can say exactly which code runs in a container. `latest` moves on every push, so two servers may run different code under the same name. The full SHA also makes rollback exact, because you redeploy the previous SHA rather than a guess.
:::

**Question 5: How does the pipeline log in to the registry without a password in the repository?**

:::answer Model answer
GitHub creates `secrets.GITHUB_TOKEN` for each run. It is short-lived, and it expires when the run ends. The workflow refers to it by name, so no value appears in the YAML, and GitHub hides it from logs. The rule is that a secret is never typed into a file that Git stores, because Git keeps history even after a line is deleted.
:::

## Y2-T45 · Deploy v1: API live on HTTPS, deploy on tag, smoke test, rollback

*Session 45 · phase E8 · 8 points*

### The ticket in plain words

So far CityPulse runs only on your laptops, so nobody outside your team can use it. The client's ward dashboard team needs a public address they can call over HTTPS. HTTPS is the secure form of a web address, where traffic between their computer and yours is encrypted.

This ticket asks for three things. First, the API must run on a cloud platform with a public address. Second, pushing a version tag such as `v0.9.0-rc1` must deploy the image CI already built and tested, and a smoke test (a quick check that the live app answers correctly) must pass before the job turns green. Third, the squad must be able to return to the previous version within minutes.

The third point comes from a famous failure. In July 2024 a faulty update to security software from CrowdStrike crashed many Windows computers worldwide, and fixing each machine took hours. The lesson is that a bad release must be easy to undo.

Secrets matter too. The database address `DATABASE_URL` contains a password, so it lives in the platform's secret manager, never in the image, the workflow file or a plain setting. Costs must be bounded: the service may scale to zero (stop when idle) and must never run more than two servers at once.

### Before you start

**Must already be merged.** Y2-T42 (the tested API with a Dockerfile), Y2-T43 (the hardened image) and Y2-T44 (CI that pushes an image tagged with the commit SHA on every merge to `main`).

**Tools and accounts.** Git, a GitHub account with write access to the squad repository, the GitHub command-line tool `gh`, Docker, the Google Cloud command-line tool `gcloud` with a billing-enabled project, `curl` and `jq`. This guide uses Google Cloud Run because the course's deploy example does. If your Tech Lead picks App Runner, Azure Container Apps or Render, the ideas stay the same but the flags differ, so read that platform's documentation.

**Where commands run.** Git Bash on your Windows laptop, unless a step says otherwise. Git Bash does not include `jq`, so install it first.

**Quick checks.** Each command shows what ready looks like.

- `gh auth status` prints `Logged in to github.com`.
- `docker version` prints both a Client and a Server section.
- `gcloud auth list` prints your account with a `*` in front.

### How your trainer checks it

The trainer checks six acceptance criteria and runs five test cases.

**Criterion 1: the live URL.** The README 'Live' URL answers `curl -i https://<url>/v1/health` with HTTP 200, and `git_sha` equals the deployed commit. TC1 and TC2 prove this.

**Criterion 2: deploy on tag.** A `v*` tag on a `main` commit deploys that SHA without rebuilding, and the smoke step passes. A failing smoke test must fail the job. TC3 and TC4 prove this.

**Criterion 3: secrets.** `DATABASE_URL` comes from the secret manager and appears in neither `deploy.yml`, the image, nor a plain environment listing. The checks are in T45.3 and T45.5.

**Criterion 4: runbook.** `docs/cloud-runbook.md` records at least one completed rollback, with exact commands, start and end timestamps, duration, and the command that lists previous revisions. TC5 proves this.

**Criterion 5: limits.** Maximum instances are 2 or fewer, and a budget alert or spending limit exists.

**Criterion 6: contribution.** Your handle appears on a rollback drill entry as driver or navigator.

**TC1: the health code.** The command is `curl -s -o /dev/null -w '%{http_code}' https://<url>/v1/health`.

- `curl` sends the request.
- `-s` runs silently, hiding the progress meter.
- `-o /dev/null` discards the body, because only the code matters.
- `-w '%{http_code}'` prints the status code after the request.

Passing output is `200`. `000` means curl could not connect, usually a wrong URL or no deployment. `403` means the service is not public. `500` or `503` means the app failed to start, often because it cannot read its secret. The Cloud Run logs in the console show why.

```term
$ curl -s -o /dev/null -w '%{http_code}' https://<url>/v1/health
200
```

**TC2: the commit match.** The command is `curl -s https://<url>/v1/health | jq -r .git_sha`, compared with `git rev-parse <latest v* tag>^{commit}`.

- `|` is a pipe. It sends the JSON reply into `jq`.
- `jq -r .git_sha` prints the `git_sha` field without quotes.
- `git tag --sort=-v:refname | head -n 1` finds the latest `v*` tag. The sort puts the highest version first. Once a final tag such as `v0.9.0` exists next to `v0.9.0-rc1`, git ranks the `-rc1` tag higher by default, so check the result by eye.
- `^{commit}` resolves the tag to the commit it points at.

Passing output is the same 40-character SHA printed twice. A different SHA means an older revision still serves traffic. An empty line means the build argument did not reach the runtime stage of the Dockerfile.

**TC3: the workflow run.** The command is `gh run list --workflow deploy.yml --limit 1 --json conclusion,event,headBranch`. `--workflow` picks the deploy workflow, `--limit 1` keeps the newest run, and `--json` prints the three named fields. Passing output looks like `[{"conclusion":"success","event":"push","headBranch":"v0.9.0-rc1"}]`. An empty list means the tag did not match `v*`, for example `0.9.0` without the `v`.

**TC4: the smoke script.** The command is `BASE_URL=https://<url> bash scripts/smoke.sh https://<url> <sha>`. The first argument becomes `$1` in the script and the SHA becomes `$2`. Passing output ends with `smoke OK`, and `echo $?` straight after prints `0`. Failing output ends with a `FAIL:` line and exit code `1`.

**TC5: the rollback.** The trainer runs the `Rollback` commands in your runbook word for word. Passing means the previous revision serves within the recorded time and the smoke test passes. Failing usually means a placeholder was not replaced or a name was copied wrongly.

### Do it, step by step

**How the pieces fit.** Cloud Run runs an image as a revision, and older revisions stay stored. The workflow builds nothing. It tells Cloud Run which image to run.

```flow
TITLE: One tag push, from laptop to live service
NODES: Your laptop | GitHub Actions | Cloud Run
STEPS:
1>2 :: git push origin v0.9.0-rc1 :: The tag travels to GitHub, which matches v* and starts deploy.yml.
2>3 :: deploy image by SHA :: The job asks for a new revision that runs the image stored under the commit SHA.
3>2 :: revision live :: Cloud Run reports the new revision as serving traffic.
2>3 :: run smoke.sh :: The job calls the public URL and checks git_sha and a prediction.
3>2 :: smoke result :: Exit zero keeps the job green. Any failure turns it red.
```

#### Y2-T45.1: Make the image pullable and create the service identity

**Stage 1. Check the SHA-tagged image exists.**

```bash
docker manifest inspect ghcr.io/ORG/citypulse-squadnn:$(git rev-parse origin/main)
```

`docker manifest inspect` reads the image description from the registry without downloading the image. `git rev-parse origin/main` prints the full SHA of GitHub's newest `main` commit, and `$( )` places it in the tag. Replace `ORG` and the image name with your squad's values. Expected output is JSON with a `mediaType` line. An "unknown manifest" error means CI did not push that tag.

**Stage 2. Copy the image to a registry Cloud Run can read.** Cloud Run reads Google's Artifact Registry, not GHCR, so create a repository and copy the image:

```bash
gcloud artifacts repositories create citypulse --repository-format=docker --location=asia-south1
gcloud auth configure-docker asia-south1-docker.pkg.dev
docker pull ghcr.io/ORG/citypulse-squadnn:<sha>
docker tag ghcr.io/ORG/citypulse-squadnn:<sha> asia-south1-docker.pkg.dev/<project>/citypulse/citypulse-api:<sha>
docker push asia-south1-docker.pkg.dev/<project>/citypulse/citypulse-api:<sha>
```

`repositories create` makes a Docker repository in the `asia-south1` region. `configure-docker` lets Docker log in through your Google account. `pull` downloads from GHCR, `tag` gives the image the registry address, and `push` uploads it. The last command ends with a confirmation line.

**Stage 3. Create the service identity.**

```bash
gcloud iam service-accounts create citypulse-api-sa --display-name="CityPulse API"
```

It prints `Created service account [citypulse-api-sa].` Grant roles only when a step needs them, so a misused identity does limited damage.

**Two things to plan.** First, the copy in Stage 2 must exist for every SHA that a tag can point at, not just one. Either extend your CI push step so it also pushes to Artifact Registry, or add a copy step (pull, tag, push, no rebuild) at the start of `deploy.yml`. Second, the identity that `deploy.yml` logs in as (the `DEPLOY_SA` variable in T45.5) is a different account from `citypulse-api-sa`. It needs permission to deploy Cloud Run services (for example `roles/run.admin`) and to act as `citypulse-api-sa` (`roles/iam.serviceAccountUser` on that account). Agree both with your Tech Lead.

**How to test.** `gcloud artifacts docker images list asia-south1-docker.pkg.dev/<project>/citypulse` lists your SHA tag. `gcloud iam service-accounts describe citypulse-api-sa@<project>.iam.gserviceaccount.com --format="value(email)"` prints the email when the identity exists.

#### Y2-T45.2: Store DATABASE_URL in the secret manager

**Stage 1. Create the secret.**

```bash
gcloud secrets create database-url --replication-policy=automatic
```

It prints `Created secret [database-url].`

**Stage 2. Add the value without typing it into history.** Your `DATABASE_URL` is already in an environment variable:

```bash
printf '%s' "$DATABASE_URL" | gcloud secrets versions add database-url --data-file=-
```

`printf '%s'` prints the text exactly, with no added newline. `--data-file=-` tells `gcloud` to read standard input. The value never appears in the command you type. Expected output reports `Created version [1]`.

**Stage 3. Grant read access on this secret only.**

```bash
gcloud secrets add-iam-policy-binding database-url --member="serviceAccount:citypulse-api-sa@<project>.iam.gserviceaccount.com" --role="roles/secretmanager.secretAccessor"
```

Binding the role to the secret, not the project, means the identity can read this secret and no others.

**How to test.** `gcloud secrets get-iam-policy database-url` lists your service account under `secretAccessor`. Do not run `gcloud secrets versions access` in a shared terminal, because it prints the password.

Reading a secret to check it prints the password into your terminal and your history. Check the access policy instead.

#### Y2-T45.3: Manual deploy and checks

**Stage 1. Deploy with explicit flags.** Your Tech Lead agrees the values with the squad.

```bash
gcloud run deploy citypulse-api --image asia-south1-docker.pkg.dev/<project>/citypulse/citypulse-api:<sha> --region asia-south1 --port 8000 --service-account citypulse-api-sa@<project>.iam.gserviceaccount.com --allow-unauthenticated --min-instances 0 --max-instances 2 --set-secrets DATABASE_URL=database-url:latest
```

`--port 8000` names the container door that receives requests. `--service-account` sets the identity from T45.1. `--allow-unauthenticated` makes the service public. `--min-instances 0` allows scale to zero, and `--max-instances 2` caps it. `--set-secrets DATABASE_URL=database-url:latest` makes the variable read the latest secret version.

**Stage 2. Check the answers over HTTPS.** `curl -s https://<url>/v1/health` prints JSON containing `git_sha`. For the prediction, send a POST with `curl -s -X POST https://<url>/v1/predict -H "Content-Type: application/json" -d '<body from your API spec>'`. `-X POST` sets the method, `-H` declares a JSON body, and `-d` carries it.

**Stage 3. Confirm the secret is not plain text.**

```bash
gcloud run services describe citypulse-api --region asia-south1 --format="yaml(spec.template.spec.containers[0].env)"
```

For `DATABASE_URL` you should see a secret reference naming `database-url`, and no `value:` line holding the address. If the address is visible, redeploy with `--set-secrets` and remove the plain setting.

**Stage 4.** Add the HTTPS address under 'Live' in the README. Get it with `gcloud run services describe citypulse-api --region asia-south1 --format="value(status.url)"`.

#### Y2-T45.4: Write scripts/smoke.sh

**Technique first: exit codes.** A script ends with `exit 1` to report failure, and the calling workflow then fails. Put these lines at the top:

```bash
#!/usr/bin/env bash
set -euo pipefail
```

`set -e` stops at the first failing command. `set -u` treats an unset variable as an error. `set -o pipefail` makes a pipeline fail if any part fails, so `curl | jq` cannot hide a curl error.

**Stage 1. Read the arguments.**

```bash
BASE_URL="${1:?usage: smoke.sh BASE_URL EXPECTED_SHA}"
EXPECTED_SHA="${2:?usage: smoke.sh BASE_URL EXPECTED_SHA}"
```

`${1:?message}` stops with the message if an argument is missing, so a forgotten argument cannot pass silently.

**Stage 2. Check health with retries.**

```bash
check_health() {
  local body
  body=$(curl -sf --max-time 10 "$BASE_URL/v1/health") || return 1
  echo "$body" | jq -e --arg sha "$EXPECTED_SHA" '.git_sha == $sha' > /dev/null
}

for attempt in 1 2 3 4 5; do
  if check_health; then
    echo "health ok on attempt $attempt"
    break
  fi
  echo "health not ready (attempt $attempt of 5)"
  if [ "$attempt" -eq 5 ]; then
    echo "FAIL: health never returned the expected git_sha" >&2
    exit 1
  fi
  sleep 5
done
```

`curl -sf` fails on 4xx and 5xx replies. `jq -e` sets its exit code from the comparison, so a wrong SHA counts as failure. `--arg` passes the SHA into jq safely. The loop waits five seconds between attempts, because a new service can take a moment to start. The message goes to standard error (`>&2`).

**Stage 3. Check one numeric prediction.**

```bash
PREDICT_BODY='<request body from your API spec>'
predict=$(curl -sf --max-time 10 -H "Content-Type: application/json" -d "$PREDICT_BODY" "$BASE_URL/v1/predict") || { echo "FAIL: predict request failed" >&2; exit 1; }
echo "$predict" | jq -e '.prediction | type == "number"' > /dev/null || { echo "FAIL: no numeric prediction" >&2; exit 1; }
echo "smoke OK"
```

`.prediction` is an example field name. Use the one your API returns. Each `||` runs its block only when the command before failed.

**How to test.** Run the script with a SHA that cannot match. You should see five `health not ready` lines, then `FAIL: health never returned the expected git_sha` and `exit 1`. Then run it with the real SHA and expect `smoke OK` and exit 0.

:::tip Test the failure first
A smoke script that always exits 0 is the most dangerous bug in this ticket, because it lets broken releases go green.
:::

#### Y2-T45.5: Write deploy.yml

**Goal.** A workflow that starts only on `v*` tags, deploys that commit's image, runs the smoke script, and never builds.

**Stage 1. Trigger on version tags.** Start the file with:

```yaml
name: deploy
on:
  push:
    tags: ["v*"]
```

The `*` matches any ending, so `v0.9.0-rc1` matches and `0.9.0` does not.

**Stage 2. Set permissions and log in without a key.** Add a job:

```yaml
permissions: {contents: read, id-token: write}
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: google-github-actions/auth@v2
        with: {workload_identity_provider: "${{ vars.WIF_PROVIDER }}", service_account: "${{ vars.DEPLOY_SA }}"}
```

`id-token: write` lets the job request a short-lived token from GitHub, which the `auth` action exchanges for Google credentials. Your Tech Lead sets up the trust in advance, so no key file exists.

**Stage 3. Deploy the SHA, not a rebuild.**

```yaml
      - uses: google-github-actions/setup-gcloud@v2
      - run: gcloud run deploy citypulse-api --image "${{ vars.IMAGE }}:${{ github.sha }}" --region asia-south1 --quiet
```

`github.sha` is the commit the tag points at, so the deployed image is the one CI tested. `--quiet` stops the command waiting for an answer, which would hang the runner.

**Stage 4. Smoke test as the last step.**

```yaml
      - run: ./scripts/smoke.sh "${{ vars.BASE_URL }}" "${{ github.sha }}"
```

A step whose command exits non-zero fails, and a failed step fails the job. Make the script executable in Git with `git update-index --chmod=+x scripts/smoke.sh`.

**Stage 5. Check the rules with grep.**

```bash
grep -n "docker build" .github/workflows/deploy.yml
grep -n "DATABASE_URL" .github/workflows/deploy.yml
```

`grep -n` prints matching lines with their numbers. Both must print nothing. A `docker build` line means the workflow rebuilds code CI never tested.

**Stage 6. Push a release candidate tag.**

```bash
git fetch origin main
git tag v0.9.0-rc1 origin/main
git push origin v0.9.0-rc1
gh run watch
```

The tag must sit on a `main` commit, or the image will not exist. A normal `git push` does not send tags, so the last push is needed. `gh run watch` follows the run live and should end with green ticks.

**How to test.** `gh run list --workflow deploy.yml --limit 1` shows the run as green. The failing path is proved by the wrong-SHA run of `smoke.sh` in T45.4: the script exits 1, so the step and the job fail.

:::trap Tag created but not pushed
A tag that exists only on your laptop starts nothing. Run `git push origin <tag>` and check `gh run list`.
:::

#### Y2-T45.6: The rollback drill

**Stage 1. Record the start time in UTC.**

```bash
date -u +%Y-%m-%dT%H:%M:%SZ
```

`date -u` prints UTC, the same clock for everyone. Copy the output into the runbook.

**Stage 2. List the revisions.**

```bash
gcloud run revisions list --service citypulse-api --region asia-south1
```

The table lists revisions newest first. To see which one serves traffic, run `gcloud run services describe citypulse-api --region asia-south1 --format="yaml(status.traffic)"`, which shows the revision name and its percentage. Write the serving revision's name down. That is the revision you will roll back to.

**Stage 3. Deploy a visible change.** Change the health message in a pull request, merge after review, wait for CI, then tag as in T45.5 with `v0.9.1-rc1`. Afterwards the health endpoint shows the new message and SHA.

**Stage 4. Roll back.**

```bash
gcloud run services update-traffic citypulse-api --region asia-south1 --to-revisions=<previous-revision-name>=100
```

`--to-revisions=NAME=100` sends 100% of traffic to the named revision. Copy the name from stage 2.

**Stage 5. Verify.** `curl -s https://<url>/v1/health | jq -r .git_sha` should print the previous SHA, and `bash scripts/smoke.sh https://<url> <previous-sha>` should print `smoke OK` and exit 0.

**Stage 6. Record the end time and duration.** Run `date -u +%Y-%m-%dT%H:%M:%SZ` again as soon as the smoke test passes and note it as the end time. Then work out the duration:

```bash
echo $(( $(date -u -d "2026-11-17T10:21:30Z" +%s) - $(date -u -d "2026-11-17T10:15:00Z" +%s) ))
```

`date -d` reads a time, and `+%s` prints it as seconds since 1970. Subtracting the start from the end gives the duration in seconds. Replace the example times with yours. The example prints `390`.

**How to test.** The runbook entry has start, end, duration, both revision names and your handle, and the health check shows the previous SHA.

### Defend it in the viva

**1. Why does deploy.yml deploy the SHA instead of building again?**

:::answer Model answer
The image CI built is the only artifact that passed the gate. A rebuild creates an image no test saw, so the deployed code might differ from the tested code. Deploying the SHA also lets the health check compare the running `git_sha` with the tagged commit, which proves the match.
:::

**2. What is the trade-off of scale to zero with a maximum of two instances?**

:::answer Model answer
Scale to zero saves money while idle, but the first request after a quiet period waits for a cold start. A maximum of two caps spending, but it also caps how many requests run at once, so a spike can queue or fail. The budget alert is the safety net for cost.
:::

**3. What did you personally do in this ticket, and how do you show it?**

:::answer Model answer
Name the subtask you owned, the commits you made in that area, the test that proved the piece worked, and one change you made after review. Your commits and review comments must support every claim.
:::

**4. Why must DATABASE_URL never appear in deploy.yml or a plain environment listing?**

:::answer Model answer
The address holds a password, and Git keeps committed values in history even after the line is deleted. A plain environment listing can be read by anyone with access to the service. The secret manager stores the value once and lets only the named identity read it, and the workflow refers to it by name only.
:::

**5. How do you know a rollback worked, and what does it not fix?**

:::answer Model answer
I check three things: the traffic split names the previous revision at 100%, the health endpoint returns the previous SHA, and the smoke script exits 0 against that SHA. A rollback moves traffic only, so it does not undo database changes the newer version made. A schema change must work for both versions before a release that might be rolled back.
:::

### Check yourself

```quiz
Q: The deploy job for a v* tag must not rebuild the image. Which line in deploy.yml breaks that rule?
- gcloud run deploy citypulse-api --region asia-south1 --quiet
- ./scripts/smoke.sh "https://example.run.app" "abc1234"

- gh run list --workflow deploy.yml --limit 1
WHY: docker build creates a new image from code that CI never tested. The tempting mistake is thinking gcloud run deploy builds code, but it deploys only the image you name.

Q: A rollback sends 100 percent of traffic to an older revision. Which statement is true?
* The older revision is still stored, so moving traffic back takes seconds.
- The older revision must be rebuilt from its commit before traffic can move.
- The database schema is reverted automatically with the traffic change.
- The rollback works only after the tag is deleted from GitHub.
WHY: Revisions are stored, so a rollback changes only where traffic goes. The tempting mistake is assuming a rollback rebuilds code or reverts the database.

Q: A smoke script must fail when git_sha does not match the expected SHA. Which tool makes a false comparison stop the script?
- curl without any flags, because it prints the reply.
- set -u, because it reports unset variables.
- Printing the health reply and continuing, so a reader can judge it.
* jq -e, because its exit code is 1 when the comparison is false.
WHY: jq -e sets the exit code from the answer, so a false comparison fails the script. The tempting mistake is printing the reply and hoping someone reads it, which lets a broken release pass.
```

## Y2-T46 · Add uptime alert (&lt;5 min), saved log queries and one measurable SLO

### The ticket in plain words

CityPulse is now public, and the ward dashboard team is building on it. If the service stops overnight, the first person to find out is an angry client. This ticket makes the squad find out first.

Three things change. An outside checker calls the API's health address every minute. If it fails twice in a row, an alert goes to a shared channel, and a recovery notice follows when the service works again. This is uptime monitoring.

**Stage 2: count a small window.** This trace counts four invented requests:

```trace
TITLE: Counting valid and good requests
CODE:
seen = [("/health", 200, 5), ("/trips", 200, 120), ("/trips", 404, 30), ("/trips", 503, 900)]
valid = [s for s in seen if s[0] == "/trips" and not 400 <= s[1] <= 499]
good = [s for s in valid if s[1] < 500 and s[2] < 300]
sli = len(good) / len(valid)
STEPS:
1 :: seen has 4 rows of (path, status, latency_ms) :: Each row is one request, and the health row is still in the list.
2 :: valid=[("/trips", 200, 120), ("/trips", 503, 900)] :: The health row fails the path test and the 404 is a client error, so both are dropped.
3 :: valid=[("/trips", 200, 120), ("/trips", 503, 900)]; good=[("/trips", 200, 120)] :: The 200 is fast enough. The 503 is a server error, so it is not good.
4 :: good has 1 row; sli=0.5 :: One good request out of two valid ones.
```

Line 2 keeps rows with the right path and no 4xx status. The `not 400 <= s[1] <= 499` test is a chained comparison, flipped by `not`. Line 4 divides good by valid.

### Defend it in the viva

**Why does the alert wait for two failed checks?**

:::answer Model answer
One failed check can come from a network blip outside the service. Requiring two in a row filters most false alarms, so the team trusts the alert. The check still runs every minute, so a real outage is reported well inside the 5-minute target.
:::

**What is the trade-off of an outside checker compared with logs inside the service?**

:::answer Model answer
An outside checker sees what a real client sees, including DNS and encryption problems. A service that stops writing logs cannot report its own failure. The cost is that the check tests one URL, so it does not say which feature broke. Logs give that detail once the alarm has sounded.
:::

**What did you personally do in this ticket?**

:::answer Model answer
Name the subtask you owned and the commits you made from the list. Then explain one decision in it, such as the host you chose or how you checked the query. A good answer names a file, a command and a result that a trainer can find in Git.
:::

**Why is the error budget a count and not only a percentage?**

:::answer Model answer
The budget is the number of failures the team can still spend. A 99% target over 40,000 valid requests allows 400 failures, a count the team can watch run down. A percentage alone does not show how close the team is to the limit when traffic changes.
:::

**Why is `/v1/health` excluded from the latency SLI?**

:::answer Model answer
The health check is fast and always succeeds. Counting it adds many easy good events and makes the SLI look better than users experience it. The SLI should measure the requests users make, such as `/v1/predict`.
:::
