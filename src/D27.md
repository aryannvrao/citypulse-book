TITLE: Day 27 — Observability: logs, uptime and SLOs
SUB: You will be able to make an API write queryable request logs, check its uptime from outside, and turn a log file into an SLI, an error budget and a p99 latency.

## The idea in one minute

Observability means working out what a running program is doing from the records it leaves behind. CityPulse is an API, a program that other programs call over the internet to ask for data. Today you make it observable in three ways. Every request writes one structured log line that a tool can count. An outside checker calls the API every minute and alerts the team when it stops answering. The logs then feed numbers that score reliability: an SLI (the measured success rate), an SLO (the target you promise) and an error budget (the failures that target still allows).

Think of a monthly mobile data plan. The SLO is the plan, the error budget is the data you have left, and when it runs out you stop streaming until next month.

## Starting from zero

**File and command.** A file is a named block of text or data kept on your disk, such as `access.log`. A command is a line of text you type into a terminal, the window where you give instructions to the computer. On Windows the course uses Git Bash, a terminal that understands the commands in this chapter.

**Program, script, variable, function.** A program is a set of instructions a computer follows. A script is a short program kept in a file, such as `sli.py`. A variable is a name that stores a value: after `total = 5000`, the name `total` stands for 5000. A function is a named, reusable block of code. You call it with brackets, so `len(rows)` returns how many items the list `rows` holds. A list is an ordered group of values in square brackets, such as `[200, 503, 201]`.

**Server, request, response, URL.** A server is a program that waits for requests and answers them. A request is a message a client sends, and the answer is the response. Each request goes to a URL, a web address such as `https://citypulse-api-xxxxxxxx-el.a.run.app/v1/health`. The part after the host name, `/v1/health`, is the path. A path the server handles is an endpoint.

**Status codes.** Every response carries a three-digit HTTP status code. Codes starting with 2 mean success, such as 200 (OK) and 201 (created). Codes starting with 4 mean the caller made a mistake, such as 404 (not found). Codes starting with 5 mean the server failed, such as 500 (internal error) or 503 (service unavailable). This split decides who is to blame, and therefore which failures count against the service.

**Latency.** Latency is the time one request takes. It is measured in milliseconds (ms), thousandths of a second.

**JSON.** JSON (JavaScript Object Notation) is a text format for structured data. A JSON object is a set of named fields inside curly braces, such as `{"path": "/v1/predict", "status": 200}`. Each name is a key, and the quotes are required. A line that is valid JSON can be read by a tool field by field.

**Logs.** A log is a record a program writes about what it did, usually one line per event. A text log reads like a sentence. A structured log uses a fixed format, such as JSON, so tools can search by field.

**Average and percentile.** The average (mean) adds all the values and divides by how many there are. A percentile is the value below which a given share of values fall. The p99 is the latency that 99 out of 100 requests beat. The median is the p50. Percentiles expose the slow tail that a few users suffer, which an average hides.

**Monitoring, probe, health check.** Monitoring means watching a system over time. A probe is an automatic request sent to check something. A health check is a probe of a special endpoint that reports whether the service is working.

**Production.** Production is the live system that real users depend on. A copy on your laptop is not production.

**Command-line tools used here.** `curl` sends a request from the terminal and prints the response. `jq` reads JSON and prints the parts you select. `grep` searches text for a pattern. `wc -l` counts lines. `sort` puts lines in order, and `uniq -c` counts repeated lines. A pipe, written `|`, sends the output of one command into the next. An exit code is the number a command returns when it finishes: 0 means success and anything else means failure.

## The tools

### Structured logging and log queries

**What it is.** Structured logging means each log line is a JSON object with named fields such as `path`, `status` and `latency_ms`. A cloud log explorer parses those fields, so you can filter and count requests exactly instead of reading text by eye. A saved query is a filter kept in the console and also in a text file in the repository, so anyone can run it again.

**Why CityPulse uses it.** The CityPulse API runs on Google Cloud Run, a service that runs your program in a container (a sealed package holding the program and what it needs). The request-logging middleware (code that wraps every request) already writes `path`, `status`, `latency_ms` and `request_id`. Cloud Logging turns each line into fields under `jsonPayload`. The alternatives are CloudWatch Logs Insights, the same idea on AWS with different query syntax; ELK or OpenSearch, which is powerful but a cluster you must run and pay for; and `grep` on downloaded logs, which is fine once but cannot be saved or shared.

**How it works.** The container writes JSON to standard output, the text stream a program prints to. The platform ships each line to a log store. Because each line is valid JSON, its keys become searchable fields.

The two saved queries from the course are stored as text:

```text
# docs/queries/errors_5xx.txt  (Logs Explorer, last 24 h, summarise by jsonPayload.path)
resource.type="cloud_run_revision"
resource.labels.service_name="citypulse-api"
jsonPayload.status>=500
```

The first line is a comment. The Logs Explorer ignores it, and it tells the reader what the query is for. The second line keeps only entries from Cloud Run revisions (the versions of a deployed service). The third line keeps only entries for the service `citypulse-api`. The fourth line keeps entries whose `status` field is 500 or more, written `>=`. Lines in this language are combined with AND, so an entry must pass every line. Summarising by `jsonPayload.path` groups the matches by path. An empty result means no server errors in the last 24 hours.

```text
# docs/queries/slow_predict.txt
resource.type="cloud_run_revision"
resource.labels.service_name="citypulse-api"
jsonPayload.path="/v1/predict"
jsonPayload.latency_ms>500
```

The first three lines work as before. `jsonPayload.path="/v1/predict"` uses `=` for equality and quotes around text. `jsonPayload.latency_ms>500` uses `>` for greater than, with no quotes because the value is a number. The result is every prediction request slower than 500 ms.

The same kind of filter works on a local file. In the terminal:

```term
$ jq -c 'select(.status>=500)' access.log | wc -l
3
```

`jq` reads each line of `access.log` as JSON. The quoted program `select(.status>=500)` keeps only the lines whose `status` field is 500 or more, where `.status` means "the status field of this object". The `-c` flag prints each kept object on one line (without it jq spreads an object over several lines and `wc -l` would overcount). The pipe passes the kept lines to `wc -l`, which counts them. The output `3` means three server errors are in the file.

:::key Logs are a table
Each JSON line is one row, and each key is one column. Filtering and counting are then ordinary table operations.
:::

:::trap Mixing print text with JSON
A plain `print("cache warmed")` line is not JSON. The platform stores it in `textPayload`, so a filter on `jsonPayload.status` never sees it. Log only JSON from request handlers.
:::

:::trap Buffered output
Python can hold printed text in memory before sending it, so logs can go missing after a crash. Set `PYTHONUNBUFFERED=1` in the environment or pass `flush=True` to `print`.
:::

:::trap Logging secrets
Never log request bodies, passwords or keys. Log only ids, status, latency and version.
:::

### Uptime monitoring and alerting

**What it is.** An uptime check is an external probe. It calls a URL on a schedule and records whether the answer was correct. An alert policy turns repeated failures into a notification to people, and sends a recovery notice when the check passes again. Because the probe runs outside the service, it sees what a client sees, including DNS problems (the system that turns a name into an address) and TLS problems (the encryption used by https).

**Why CityPulse uses it.** If CityPulse stops overnight, the squad currently learns about it from an angry dashboard team at BBMP, the Bengaluru city corporation. The course setup checks `/v1/health` every minute, requires the response body to contain `ok`, uses a 10-second timeout, and alerts after 2 consecutive failures. The alert goes to a shared email alias and the squad channel, with a runbook link (a document saying what to do). The alternatives are UptimeRobot, a free outside checker that is independent of the cloud; CloudWatch Synthetics or Azure Availability tests, which are the native versions on other platforms; and manual checking, which fails at 2 a.m.

```flow
TITLE: One uptime check, seen from outside
NODES: Uptime checker | CityPulse API | Squad channel
STEPS:
1>2 :: GET /v1/health :: Every minute the checker calls the health URL from outside the service.
2>1 :: 200 with ok in body :: The API answers. The check passes only if the status is 200 and the body contains ok.
1>3 :: 2 failures in a row :: After two failed checks the alert posts to the shared channel with a runbook link.
1>3 :: check passes again :: A recovery notice tells the team the service is back.
```

The flow shows one probe travelling out and back, and the alert travelling to people. Each arrow is a message: the request, the answer, and the two notifications. Only the third arrow waits for two failures.

**How the alert test works.** To prove the alert fires, you take public access away, time how long the alert takes, and restore access. The course runs it with these commands, which are rejoined here from lines the slides split:

```bash
URL=https://citypulse-api-xxxxxxxx-el.a.run.app   # from the README, the Live link
curl -fsS -m 10 "$URL/v1/health" | grep -q '"ok"' && echo UP
echo "stop: $(date -Iseconds)" | tee -a docs/alert-test.md
gcloud run services remove-iam-policy-binding citypulse-api --region asia-south1 --member=allUsers --role=roles/run.invoker
echo "alert: <time from notification>" >> docs/alert-test.md
gcloud run services add-iam-policy-binding citypulse-api --region asia-south1 --member=allUsers --role=roles/run.invoker
echo "restored: $(date -Iseconds)" | tee -a docs/alert-test.md
```

Line by line. `URL=...` stores the address in a variable called `URL`; there must be no spaces around the `=` in bash. The text after `#` is a comment. `curl -fsS -m 10 "$URL/v1/health"` sends the request. `-f` makes curl exit with an error on a 4xx or 5xx reply. `-s` hides the progress meter, and `-S` still shows error messages. `-m 10` gives up after 10 seconds. The double quotes keep the URL in one piece, and `$URL` inserts the variable's value. The pipe `|` sends the body to `grep -q '"ok"'`, which looks for the text `"ok"` and stays silent (`-q`). It exits with 0 only if it finds it. `&& echo UP` prints `UP` only when the previous command exited with 0. You should see `UP` while the service is public.

`echo "stop: $(date -Iseconds)"` prints a line containing the current time; `$(...)` runs `date` and inserts its output, and `-Iseconds` prints a timestamp such as `2027-03-09T10:15:00+05:30`. `| tee -a docs/alert-test.md` shows the line on screen and appends it (`-a`) to the file. `remove-iam-policy-binding` removes the permission that lets everyone (`allUsers`) call the service, using the role `roles/run.invoker`. `--region` names the Google Cloud region and `--member` names who the permission is for. `>>` appends a line to a file, whereas a single `>` would overwrite it. The add command restores the permission. After the removal, the curl line does not print `UP`, because a refused request fails the `-f` check (`-S` still shows curl's error message).

:::trap Checking only for status 200
An error page can come back with status 200. Match the body too, as the `grep` in the test does.
:::

:::trap Alerting one person
An alert in one student's inbox is lost when that person is ill. Use a shared alias and the squad channel.
:::

:::trap Never testing the alert
An alert you have not triggered may not work. Run the fire test and record the stop and alert timestamps.
:::

### SLIs, SLOs and error budgets

**What they are.** An SLI (service-level indicator) is a measured ratio, such as the share of `/v1/predict` requests answered successfully under 500 ms. An SLO (service-level objective) is the target for that ratio over a stated window, such as 99% over 7 days. The error budget is the amount of failure the target still allows: 100% minus the target, applied to the number of valid requests. CityPulse writes the SLO as a promise for the dashboard team, and the budget as a rule for the squad: when the budget is spent, stop new features and fix reliability.

**The course's definitions.** Good events are requests that are not 5xx and finish under 500 ms. Valid requests are all `/v1/predict` requests except client errors (4xx), and `/v1/health` is excluded entirely. Three alternatives were rejected. A raw uptime percentage ignores slow answers and errors while the server is up. An average latency hides the slow tail. A 100% target is impossible and leaves no budget for any change.

The window's data is exported with this command:

```bash
gcloud logging read 'resource.labels.service_name="citypulse-api" AND jsonPayload.path="/v1/predict"' --freshness=7d --format=json > logs/predict_7d.json
```

`gcloud logging read` fetches log entries. The quoted text is the filter, and `AND` joins its two conditions. `--freshness=7d` keeps only the last seven days. `--format=json` prints the result as a JSON list. The `>` sends the output to `logs/predict_7d.json`, replacing the file if it exists. The `logs` folder must already exist.

The script that computes the SLI and budget from that file is:

```python
import json
rows = [e["jsonPayload"] for e in json.load(open("logs/predict_7d.json")) if "jsonPayload" in e]
valid = [r for r in rows if r["status"] < 400 or r["status"] >= 500]   # client 4xx excluded
good = sum(1 for r in valid if r["status"] < 500 and r["latency_ms"] < 500)
target = 0.99
sli = good / len(valid)
budget = (1 - target) * len(valid)          # bad requests allowed in this window
used = len(valid) - good
print(f"SLI {sli:.2%} (target {target:.0%}); budget {budget:.0f} requests, used {used} ({used / budget:.0%})")
```

Line by line. `import json` loads the JSON tools. The first assignment reads the file, which is a list of log entries. `json.load(open(...))` turns the file into Python lists and dictionaries, and `open` returns the file for reading. The list comprehension keeps only entries with a `jsonPayload` field, then keeps that field's contents as `rows`. `valid` keeps a row if its status is below 400 (not a client error) or 500 and above (a server error). The `# client 4xx excluded` text after the `#` is a comment. `good` counts the valid rows that are under 500 and faster than 500 ms; `sum(1 for ...)` adds 1 for each match. `target = 0.99` stores the SLO as a fraction. `sli = good / len(valid)` divides good requests by valid ones. `budget` is the number of bad requests allowed, that is 1% of the valid total. `used` is the number of valid requests that were bad. The final `print` builds one line with f-string braces that insert values; `:.2%` shows a fraction as a percentage with two decimals, and `:.0f` shows a number with no decimals. With 20,000 valid requests the budget is 200, so if 116 are used the last part of the output reads `(58%)`.

```trace
TITLE: Counting good and valid requests
CODE:
statuses = [200, 503, 404, 200]
valid = [s for s in statuses if s < 400 or s >= 500]
good = sum(1 for s in valid if s < 500)
sli = good / len(valid)
used = len(valid) - good
print(f"SLI {sli:.1%}; failed {used}")
STEPS:
1 :: statuses=[200, 503, 404, 200] :: Four requests arrive. Their status codes are stored in a list.
2 :: statuses=[200, 503, 404, 200]; valid=[200, 503, 200] :: The 404 is a client error, so it is dropped from the valid list.
3 :: statuses=[200, 503, 404, 200]; valid=[200, 503, 200]; good=2 :: The two 200 responses are good. The 503 is a server error.
4 :: statuses=[200, 503, 404, 200]; valid=[200, 503, 200]; good=2; sli=0.6666666666666666 :: Two good out of three valid requests, as a fraction.
5 :: statuses=[200, 503, 404, 200]; valid=[200, 503, 200]; good=2; sli=0.6666666666666666; used=1 :: One valid request failed. That is the budget spent.
6 :: statuses=[200, 503, 404, 200]; valid=[200, 503, 200]; good=2; sli=0.6666666666666666; used=1 :: The print line shows SLI 66.7%; failed 1 in the terminal.
```

Watch the variables change as the lines run. Each step shows the state after its line has run, so `valid` is filled in at step 2 and `good` is first set at step 3. Notice that the 404 never appears in `valid`, so it cannot count as a failure.

:::trap Including the health check
`/v1/health` is fast and always succeeds, so it inflates the SLI. Exclude it before counting.
:::

:::trap Counting client 422s as failures
A 422 means the caller sent bad input. The service behaved correctly, so the response does not spend the budget.
:::

:::trap An SLO with no query
A target written without the query that measures it cannot be checked. Write the exact query and today's measured value next to the target in `docs/slo.md`.
:::

:::tip Say which definition you used
The worked example below counts 4xx responses as good, but the course SLI leaves them out. In the viva, state the definition first, then the number.
:::

## The worked example

The course workbook takes one window of 5,000 requests from `access.log` and produces a reliability read-out. Its goal is to answer four questions: what was the request mix, what was the SLI, how much budget is left, and what does latency look like? Each step below is one file from the workbook. The code is shown once, in the step where it runs.

**Step 1: write one JSON line per request.**

```python
import logging, json, time, sys

logging.basicConfig(stream=sys.stdout, level=logging.INFO, format="%(message)s")
log = logging.getLogger("citypulse")

def log_request(path, status, start):
    log.info(json.dumps({
        # one structured line
        "path": path, "status": status,
        "latency_ms": round((time.time() - start) * 1000, 1),
    }))

if __name__ == "__main__":
    t = time.time() - 0.0472      # pretend the request started 47.2 ms ago
    log_request("/readings", 201, t)
    log_request("/stations", 200, t)
```

Line by line. `import logging, json, time, sys` loads four standard modules: logging for records, json for text, time for clocks and sys for the standard output stream. `basicConfig` sets up logging. `stream=sys.stdout` sends records to the screen, `level=logging.INFO` lets info messages through, and `format="%(message)s"` prints only the message, with no timestamp or level, so the output stays valid JSON. `log = logging.getLogger("citypulse")` gets a named logger. `def log_request(path, status, start):` defines a function that takes three values. Inside it, `json.dumps({...})` turns a dictionary into a JSON string, and `log.info(...)` writes that string as one line. The `latency_ms` value is the current time minus `start`, in seconds, multiplied by 1000 to get milliseconds, and `round(..., 1)` keeps one decimal. The `if __name__ == "__main__":` line means the lines below run only when you start this file directly. `t = time.time() - 0.0472` pretends the request began 47.2 ms ago. The last two lines write one event each.

Running it with `python3 observability.py` prints two lines. The last digit may differ on your machine:

```text
{"path": "/readings", "status": 201, "latency_ms": 47.2}
{"path": "/stations", "status": 200, "latency_ms": 47.3}
```

**Step 2: collect a window of traffic.** The server appends one line per request to `access.log`. Then you check the file:

```term
$ wc -l < access.log
5000
$ head -1 access.log
{"path": "/stations", "status": 200, "latency_ms": 58.2}
```

`wc -l` counts lines. The `<` feeds the file into `wc` as input, so the output is a plain number. `head -1` prints the first line of the file. The output shows 5,000 request events on disk, each one a JSON line.

**Step 3: count requests by status.**

```bash
# count requests by HTTP status
jq -r '.status' access.log | sort | uniq -c | sort -rn
```

Line by line. The first line is a comment. `jq -r '.status' access.log` reads each line and prints its `status` field; `-r` prints the raw value without quotes. The pipe sends those values to `sort`, which puts identical codes next to each other. `uniq -c` collapses each run into one line and writes the count in front. The final `sort -rn` orders the lines by count, largest first, reading the counts as numbers (`-n`) and reversing (`-r`). Expected output:

```term
$ jq -r '.status' access.log | sort | uniq -c | sort -rn
2955 201
1953 200
  89 400
   3 503
```

That is 4,908 successful requests, 89 client errors and 3 server errors. The first thing to read is the 5xx count, because server errors belong to the team to fix.

**Step 4: measure the SLI.** This version counts a response as good if it is not a 5xx.

```python
import json
rows = [json.loads(l) for l in open("access.log")]
total = len(rows)
good = sum(1 for r in rows if r["status"] < 500)    # non-5xx = served OK
sli = good / total * 100
print(f"requests: {total}")
print(f"good (non-5xx): {good}")
print(f"errors (5xx): {total - good}")
print(f"SLI (success): {sli:.2f}%")
```

Line by line. `rows = [json.loads(l) for l in open("access.log")]` reads each line, turns it from JSON text into a dictionary, and collects the dictionaries in a list. `total = len(rows)` counts them. `good` counts rows whose status is below 500, and the comment says that means served OK. `sli = good / total * 100` gives a percentage. The four `print` lines show the numbers. `{sli:.2f}` shows two decimal places. Expected output:

```text
requests: 5000
good (non-5xx): 4997
errors (5xx): 3
SLI (success): 99.94%
```

:::trap Two definitions of good
This step counts 4xx responses as good, so the denominator includes the 89 client errors. The course SLI in the tools section leaves them out. Both are legitimate, but the number you publish must name the one you used.
:::

**Step 5: set the SLO and track the error budget.**

```python
TOTAL = 5000
SLO = 99.5                                   # the target we commit to
failures = 3                                 # observed 5xx this window
allowed = round(TOTAL * (100 - SLO) / 100)   # budget, in requests
remaining = allowed - failures
print(f"SLO target: {SLO}%")
print(f"error budget: {allowed} failed requests")
print(f"spent: {failures}")
print(f"remaining: {remaining} ({remaining/allowed*100:.0f}% of budget)")
print("status: HEALTHY — ship features" if remaining > 0 else "status: FREEZE")
```

Line by line. `TOTAL = 5000` is the number of requests in the window. Capital letters are a convention for values that do not change. `SLO = 99.5` is the commitment, written as a percentage. `failures = 3` is the observed 5xx count, typed in by hand here. `allowed` is the budget: `100 - SLO` is the failure percentage, dividing by 100 turns it into a fraction, and multiplying by `TOTAL` gives a count of requests. `round(...)` turns 25.0 into a whole 25. `remaining` subtracts the spent failures from the budget. The `print` lines show the values, and `remaining/allowed*100:.0f` shows the share left. The last line uses a conditional expression, written `value if test else other`, to print one of two words. Expected output:

```text
SLO target: 99.5%
error budget: 25 failed requests
spent: 3
remaining: 22 (88% of budget)
status: HEALTHY — ship features
```

Twenty-two failures remain, so the team keeps shipping. In the lab you replace the hand-typed `failures` value with the real 5xx count from step 3.

**Step 6: read the latency tail.**

```python
import json
lat = sorted(json.loads(l)["latency_ms"] for l in open("access.log"))
def pct(p):
    return lat[int(len(lat) * p) - 1]
print(f"n: {len(lat)}")
print(f"p50: {pct(0.50):.1f} ms")
print(f"p95: {pct(0.95):.1f} ms")
print(f"p99: {pct(0.99):.1f} ms")
print(f"max: {lat[-1]:.1f} ms")
```

Line by line. The first two lines read the file and collect every `latency_ms` value into one list, which `sorted` puts in ascending order. `def pct(p):` defines a function that takes a fraction such as 0.95. `int(len(lat) * p) - 1` works out the position of the value to return, counting from zero. For 5,000 values and p95 that is position 4749, the 4,750th smallest value. `print` shows each percentile, and `lat[-1]` is the last item, the largest value. Expected output:

```text
n: 5000
p50: 47.6 ms
p95: 74.2 ms
p99: 85.7 ms
max: 1894.7 ms
```

The p95 is healthy at 74 ms, but the max shows the three slow 5xx calls. The mean would have hidden them.

:::trap The index rule
`int(n * p) - 1` agrees with the nearest-rank rule only when `n * p` is a whole number. For nine values at p99 it returns the 8th value (70 ms), but nearest rank asks for `ceil(9 * 0.99)`, which is 9, so the answer is the largest value (900 ms). Use `ceil`, as the graded-lab solution does.
:::

**Step 7: run the whole read-out.**

```bash
jq -r '.status' access.log | sort | uniq -c
python3 sli.py
python3 budget.py
python3 p95.py
```

Each line runs in turn. The first is the status count from step 3. The next three run the Python scripts with `python3`, which runs a Python file. The output is the four blocks shown above, one after the other. One command gives the whole picture, which means anyone can rerun it on a new window of logs.

## The hands-on lab, step by step

Do these on your own copy of CityPulse, in Git Bash. Before you start, set the address once in each new terminal window with `URL=` followed by the Live address from your README. Steps 1 to 5 are checks; steps 6 and 7 write the SLO document.

### Step 1: Structured request logging

**What you do.** Confirm that the API writes one JSON object per request. First run the example from the worked example:

```bash
python3 observability.py
```

`python3` runs the file. You should see two lines, each starting with `{` and ending with `}`. Then check that every line parses as JSON:

```bash
python3 observability.py | python3 -c "import sys, json; [json.loads(l) for l in sys.stdin]; print('all lines are JSON')"
```

The pipe sends the output into the second command. `python3 -c` runs the code in quotes. `sys.stdin` is the stream of lines coming in. `json.loads(l)` converts each line and raises an error if one is not JSON, and the list brackets run the loop and the resulting list is thrown away. The last statement prints a message when no error occurred.

**How you know it worked.** The message `all lines are JSON` appears. A traceback (Python's error report) means one line is not JSON, usually a stray `print`. On CityPulse, the request-logging middleware writes the same kind of line for each real request.

### Step 2: Count requests and errors

**What you do.** Save the API's JSON lines to `access.log`, then count them by status:

```bash
jq -r '.status' access.log | sort | uniq -c | sort -rn
jq -c 'select(.status>=500)' access.log | wc -l
```

The first command prints a count for each status code. The second prints the number of server errors, using the filter from the tools section.

**How you know it worked.** The counts in the first command add up to the number printed by `wc -l < access.log`, and the number in the second command equals the 5xx lines in the first. If the file is empty, nothing is printed and the API has not been called yet.

### Step 3: Expose /metrics

**What you do.** Check that the API answers a `/metrics` endpoint with plain-text counters:

```bash
curl -fsS "$URL/metrics"
```

`curl` sends a GET request, `-f` fails on an HTTP error, and `-s` hides the progress bar. The flags are the same as in the alert test.

**How you know it worked.** The response is a list of lines, each with a name and a number, such as a total count of requests. The exact names and the code that writes them come from your lab sheet, which is not reproduced in this book's sources. The check here only confirms that the endpoint answers. A counter is explained in the quiz section.

### Step 4: Generate traffic and a few errors

**What you do.** Send twenty healthy requests and one request to a path that does not exist:

```bash
for i in $(seq 1 20); do curl -s -o /dev/null -w "%{http_code}\n" "$URL/v1/health"; done | sort | uniq -c
curl -s -o /dev/null -w "%{http_code}\n" "$URL/v1/does-not-exist"
```

`for i in $(seq 1 20); do ... done` runs the body twenty times, with `i` counting from 1 to 20. `-o /dev/null` throws away the response body. `-w "%{http_code}\n"` prints only the status code and a newline. The pipe then counts the codes, as in step 2.

**How you know it worked.** The first command prints `20 200`, and the second prints `404` if the server follows the usual convention for a missing path. Run step 2 again and the counts have gone up. The 404 is a client error, so it appears in the 4xx count and not the 5xx count.

### Step 5: Probe uptime and latency

**What you do.** Time one health check from outside the service:

```bash
curl -fsS -m 10 -o /dev/null -w "%{http_code} %{time_total}s\n" "$URL/v1/health"
```

The flags `-fsS -m 10` are explained in the alert test. `-o /dev/null` discards the body, and `-w` prints the status code followed by `%{time_total}`, the seconds the whole request took.

**How you know it worked.** The output looks like `200 0.084s`, with a 200 status and a time under the 10-second timeout. Run the command five times. The times vary, and each value is one latency sample. Also confirm the alert check passes: `curl -fsS -m 10 "$URL/v1/health" | grep -q '"ok"' && echo UP` prints `UP`.

### Step 6: Define the SLO and error budget

**What you do.** Create `docs/slo.md`. Copy the `sli.py` and `budget.py` code from the worked example into the folder you are working in, then run them:

```bash
mkdir -p docs
python3 sli.py
python3 budget.py
```

`mkdir -p docs` creates the folder, and does nothing if it already exists. Before running `budget.py`, change its `failures` line to the 5xx count from step 2. Then write in `docs/slo.md`: the SLI definition in words, the numeric SLO and its window, the error budget in requests, the exact command that measures it, and the measured value.

**How you know it worked.** The file names the SLI, the SLO, the budget and the command. Someone who runs the command again on the same logs gets the same numbers you wrote down. A number with no command beside it does not count.

### Step 7: Decide using the budget

**What you do.** Read the `status` line from `budget.py`. If it says `HEALTHY`, the squad keeps shipping features. If it says `FREEZE`, the rule is to stop new features and fix reliability. Write one line in `docs/slo.md` that states the decision and the number behind it, for example: `Decision: ship features, 22 of 25 failures left.`

**How you know it worked.** Run `grep -n "Decision" docs/slo.md`. The line prints with its line number, and the decision matches the status line from the script. If they disagree, the file is wrong, not the script.

## What the quiz tests

The quiz is ten case-study questions, one per topic below, in the same order. Each topic gives the rule and the trap examiners set.

### Structured logging

A structured log line is a JSON object, so each named field becomes a searchable column in the log explorer. A line that is plain text is stored in a different field and cannot be filtered by `jsonPayload`. Examiners often describe a count that is lower than the server's own log and ask why. The usual cause is a `print()` statement mixed into the logs, or a log written in a format the platform cannot parse.

### Correlation id

A correlation id is a value attached to every log line that one request produces, so the story of that request can be gathered from many lines. In CityPulse this is the `request_id` field. It is not a count, a rate or a percentile, and it is the first thing to search when one user reports one failure. Trap: thinking that a `request_id` groups all requests from one user. It groups the lines of a single request.

### SLO definition

An SLO is a numeric target for an SLI, over a stated window. A complete SLO has three parts: the measure, the number, and the time window, for example 99% of `/v1/predict` requests not 5xx and under 500 ms over 7 days. It should also name the query that measures it, so the number can be reproduced. Trap: a target of 100%, which sounds safe but cannot be met and leaves no budget for any change.

### SLI definition

An SLI is a measured ratio: good events divided by valid events, usually shown as a percentage. The course defines valid events as `/v1/predict` requests excluding client errors, and it excludes `/v1/health` entirely. An average latency is not an SLI in this sense, because it does not count events. Trap: counting the health check, or counting 4xx responses as failures.

### Error budget

The error budget is the failure allowed by the SLO. It equals `(100 - SLO)` percent of the valid requests in the window, and failures already spent are subtracted from it. The remainder tells the team whether to ship or fix reliability. Trap: reading the budget as a percentage instead of a count. A 99.5% SLO over 5,000 requests allows 0.5% of 5,000, which is 25 requests, not 0.5 requests.

### Latency percentiles

A percentile is the value below which a given share of sorted values falls. The p99 is the value that 99 out of 100 requests beat, so it shows the slow tail that users feel. Nearest rank works in three steps: sort the values, compute `rank = ceil(p * n / 100)`, and take the value at that position, counting from 1. Alerts and SLOs use p95 or p99 rather than the mean. Trap: using `int` where `ceil` is needed, which picks a different value for small samples.

### Alerting and burn rate

Burn rate is how fast the error budget is being spent, compared with the steady pace that would use exactly the whole budget by the end of the window. A burn rate of 1 means the budget ends on schedule, and a burn rate of 10 means it would run out in a tenth of the time. Burn-rate alerts are the usual way to alert on an SLO, but the lesson's own alert is simpler: two consecutive failed uptime checks. Trap: alerting on one bad minute, which creates noise, or waiting until the budget is gone, which is too late.

### Observability pillars

Logs, metrics and traces are the three commonly named pillars. Logs record individual events, metrics are numbers summed over time and cheap to chart, and traces follow one request across several services. This lesson uses logs and metrics, plus the outside view given by an uptime check. Trap: using logs to chart a trend over months, when a metric is cheaper and faster, or using a metric to find out what one request did.

### Health checks

A health check is an endpoint that an outside checker calls to test whether the service works, here `/v1/health`. A status code alone is not enough, because an error page can arrive with status 200. The course check also requires the body to contain `ok`, runs every minute with a 10-second timeout, and needs two failures in a row before it alerts. Trap: a health endpoint that always answers ok without checking anything the service depends on, so the check passes while users fail.

### Counter versus gauge

A counter only goes up, such as the total number of requests, and it resets to zero when the process restarts, so you look at its rate of change. A gauge goes up and down, such as the number of jobs waiting in a queue, and you read its current value. Trap: using a gauge for a running total, or a counter for something that falls, such as open connections.

## The graded lab skill

The graded lab is a Python problem marked by visible and hidden tests. Hidden tests check the edge cases, so this section teaches the Python you need and then sets a practice problem. Read the checklist before you write any code.

**Lists and sorting.** A list keeps values in order. `len(values)` counts them. `sorted(values)` returns a new list in ascending order and leaves the original unchanged. Sorting is needed before taking a percentile, because a percentile is a position in ordered values.

**Dictionaries.** A dictionary (dict) holds key-value pairs. `record["status"]` reads the value stored under the key `"status"`, just as a JSON object does. A missing key raises a `KeyError`, which is why the problem says both keys are present.

**Loops, comprehensions and counting.** `for x in items:` repeats a block for each item. A list comprehension builds a new list in one line: `[x for x in items if test]` keeps the items that pass the test. `sum(1 for x in items if test)` counts the matches, because each match adds 1 and nothing else is added.

**Functions, return values and None.** `def name(args):` defines a function, and `return value` sends a value back to the caller. The word `None` means no value. Returning `None` is the clear signal that there is no answer, and it is different from returning 0.

**Integer division and ceiling.** `//` divides and drops the remainder, so `7 // 2` is 3. The ceiling of a positive whole-number division `a / b` can be written `(a + b - 1) // b`. For example, `(99 * 9 + 99) // 100` is 9, which is `ceil(8.91)`. Integer arithmetic avoids floating-point surprises.

**Floating-point numbers.** Computer decimals are approximate. `0.1 + 0.2` is not exactly `0.3`. Never compare two floats with `==`. Compare them with a tolerance, such as `abs(a - b) < 1e-9`, which means "closer than a billionth".

**assert.** `assert condition` does nothing if the condition is true, and stops the program with an error if it is false. Tests are a list of assert lines.

**The practice problem.** A payments API writes a request log. Each record is a dictionary with `status` (an integer HTTP status code) and `latency_ms` (a number). Write four functions:

1. `success_rate_percent(records)` returns the share of valid requests that are not 5xx, as a percentage. It returns `None` when there are no valid requests.
2. `error_budget_spent(records, target_percent=99.9)` returns the fraction of the error budget already spent: failed valid requests divided by the failures the target allows. It returns `None` when there are no valid requests or when the target is 100. 1.0 means exactly spent, and above 1.0 means overspent.
3. `latency_percentile(records, percent)` returns the nearest-rank percentile of `latency_ms` over valid requests. It returns `None` when there are no valid requests.
4. `p99_latency_ms(records)` returns `latency_percentile(records, 99)`.

A valid request has a status that is not 4xx, so 400 to 499 are excluded. Return unrounded values; the caller rounds when printing.

Example log, ten requests:

```text
200, 40 ms     200, 55 ms     201, 60 ms     404, 30 ms     200, 45 ms
503, 900 ms    200, 52 ms     200, 61 ms     200, 48 ms     200, 70 ms
```

The 404 is excluded, which leaves nine valid requests. Eight are not 5xx, so the success rate is 800/9, about 88.89%. The 503 is the only failure, but nine requests allow only 0.009 failures for a 99.9% target, so one failure spends about 111 times the whole budget. The p99 is 900 ms. A window this small shows why the budget must be read with the number of requests beside it.

**Edge-case checklist.**

- Empty input: all four functions return `None` without an error.
- Only 4xx records: the valid list is empty, so the result is `None`.
- A 4xx record with a huge latency must not change the p99.
- Boundary statuses: 499 is excluded and 500 is a failure. 399 is valid and not a failure.
- Ties: equal latencies count as separate values, so sorting keeps all of them.
- Unsorted input: sort before taking a percentile.
- Exact multiples: 100 values at p99 give the 99th value, and 101 values at p99 give the 100th.
- A single record: its latency is the p99.
- A target of 100: there is no budget, so return `None` instead of dividing by zero.
- Types: keep latencies as the numbers given. Do not convert them to strings.
- Rounding: do not round inside the functions.
- Missing fields: assume both keys exist, and do not invent defaults.

:::answer Model solution and line-by-line explanation

```python test
def valid_records(records):
    """Keep the requests that count against the service. 4xx responses are the caller's fault."""
    return [r for r in records if not 400 <= r["status"] <= 499]


def success_rate_percent(records):
    """Share of valid requests that were not 5xx, as a percentage."""
    valid = valid_records(records)
    if not valid:
        return None
    good = sum(1 for r in valid if r["status"] < 500)
    return good * 100 / len(valid)


def error_budget_spent(records, target_percent=99.9):
    """Failed valid requests divided by the failures the target allows. 1.0 means fully spent."""
    valid = valid_records(records)
    if not valid:
        return None
    allowed = len(valid) * (100 - target_percent) / 100
    if allowed <= 0:
        return None
    bad = sum(1 for r in valid if r["status"] >= 500)
    return bad / allowed


def latency_percentile(records, percent):
    """Nearest-rank percentile of latency_ms over valid requests."""
    valid = valid_records(records)
    if not valid:
        return None
    ordered = sorted(r["latency_ms"] for r in valid)
    rank = max(1, (percent * len(ordered) + 99) // 100)
    return ordered[rank - 1]


def p99_latency_ms(records):
    return latency_percentile(records, 99)


EXAMPLE = [
    {"status": 200, "latency_ms": 40},
    {"status": 200, "latency_ms": 55},
    {"status": 201, "latency_ms": 60},
    {"status": 404, "latency_ms": 30},
    {"status": 200, "latency_ms": 45},
    {"status": 503, "latency_ms": 900},
    {"status": 200, "latency_ms": 52},
    {"status": 200, "latency_ms": 61},
    {"status": 200, "latency_ms": 48},
    {"status": 200, "latency_ms": 70},
]


def close(a, b):
    return abs(a - b) < 1e-9


assert len(valid_records(EXAMPLE)) == 9
assert close(success_rate_percent(EXAMPLE), 800 / 9)
assert close(error_budget_spent(EXAMPLE, 99.9), 1 / 0.009)
assert p99_latency_ms(EXAMPLE) == 900

assert success_rate_percent([]) is None
assert error_budget_spent([]) is None
assert p99_latency_ms([]) is None
only_client = [{"status": 404, "latency_ms": 5}]
assert success_rate_percent(only_client) is None
assert p99_latency_ms(only_client) is None

ok = [{"status": 200, "latency_ms": 10}] * 50
assert error_budget_spent(ok) == 0
assert success_rate_percent(ok) == 100.0
assert error_budget_spent(ok, 100) is None

thousand = [{"status": 200, "latency_ms": 10}] * 999 + [{"status": 500, "latency_ms": 10}]
assert close(error_budget_spent(thousand, 99.9), 1.0)

mixed = [{"status": 499, "latency_ms": 1}, {"status": 500, "latency_ms": 1}]
assert success_rate_percent(mixed) == 0.0

hundred = [{"status": 200, "latency_ms": v} for v in range(100, 0, -1)]
assert p99_latency_ms(hundred) == 99

hundred_one = [{"status": 200, "latency_ms": v} for v in range(1, 102)]
assert p99_latency_ms(hundred_one) == 100

three = [{"status": 200, "latency_ms": v} for v in (30, 10, 20)]
assert p99_latency_ms(three) == 30
assert latency_percentile(three + [{"status": 200, "latency_ms": 40}], 50) == 20

ties = [{"status": 200, "latency_ms": 50}] * 4
assert p99_latency_ms(ties) == 50

slow_client = [{"status": 200, "latency_ms": 10}, {"status": 404, "latency_ms": 99999}]
assert p99_latency_ms(slow_client) == 10

assert valid_records(EXAMPLE)[0] == {"status": 200, "latency_ms": 40}
```

**Line by line.**

- `valid_records` returns a new list. `400 <= r["status"] <= 499` is a chained comparison, and `not` flips it, so the list keeps every status outside 4xx. The docstring is the text in triple quotes; it documents the function and does nothing when run.
- `success_rate_percent` first returns `None` if `valid` is empty, which covers the empty input and the all-4xx input. `good` counts the non-5xx records. `good * 100 / len(valid)` gives a percentage; multiplying before dividing keeps the arithmetic exact for these small numbers.
- `error_budget_spent` has the same empty check. `allowed` is `(100 - target_percent) / 100` of the valid count, which is the number of failures the target allows. If the target is 100, `allowed` is 0, so the function returns `None` rather than dividing by zero. `bad` counts the 5xx records, and `bad / allowed` is the fraction spent.
- `latency_percentile` sorts the valid latencies. The rank line is nearest rank written with integers: `(percent * n + 99) // 100` equals `ceil(percent * n / 100)` for positive numbers, and `max(1, ...)` stops a zero rank from producing index -1. `ordered[rank - 1]` converts the 1-based rank into a 0-based index.
- `p99_latency_ms` is a single call with 99 as the percentage.
- `EXAMPLE` is the ten-request log from the problem. The helper `close` compares floats with a tolerance.
- The first block of asserts checks the worked example. Nine valid requests; success 800/9; budget spent 1/0.009; p99 900 ms.
- The next asserts check empty and all-4xx input, the zero-failure case, and the target of 100.
- The thousand-request assert checks that one failure spends exactly the budget at 99.9%, so the result is 1.0.
- The `mixed` case checks the boundary: 499 is excluded, and 500 is a failure.
- The `hundred` and `hundred_one` asserts check the exact-multiple boundary. With 100 values the 99th is taken, and with 101 values the 100th.
- `three` shows that the function sorts unsorted input, and the p50 assert checks the median rank of an even count.
- `ties` checks equal values, and `slow_client` checks that a 4xx latency cannot change the result.
- The last assert checks that `valid_records` keeps the original dictionary, not a copy with changed fields.

The file runs in well under a second. Running it with `python3` prints nothing when every assert passes, and stops with an `AssertionError` on the first failure.

## Say it out loud

:::answer What is the difference between an SLI and an SLO?
An SLI is the measured value, such as the share of `/v1/predict` requests that are not 5xx and finish under 500 ms. An SLO is the target that value is judged against, such as 99% over seven days. The SLI tells you where the service is, and the SLO tells you where it has promised to be. Without a measured SLI, an SLO is only a hope.
:::

:::answer Your error budget is nearly spent with three weeks left. What do you do?
I would stop starting new features and move the squad to reliability work. The budget says how many failures the promise still allows, and nearly none is left. I would look at the 5xx query by path to find the source of the failures. I would also tell the dashboard team the current SLI and what the team is doing about it.
:::

:::answer Why alert on p99 latency and not on the average?
An average can look healthy while a small share of requests is very slow. The p99 is the value that 99% of requests beat, so it shows the slow tail real users feel. Alerts and SLOs on tail percentiles catch problems that averages hide. The average is still useful for trends, but it should not be the alert.
:::

:::answer Why does the uptime alert wait for two failed checks?
A single failed check can come from a network blip that has nothing to do with the service. Requiring two failures in a row filters most of those false alarms. The check still runs every minute, so the alert fires within about two minutes of a real outage, which meets the five-minute requirement. Fewer false alarms mean the squad trusts the alert and acts on it.
:::

:::answer Why are 4xx responses left out of the SLI?
A 4xx response means the caller sent a bad request, such as a missing field, and the service answered correctly. Counting it as a failure would penalise the service for behaviour it should have. It would also make the budget depend on what clients send, not on how reliable the service is. Say this out loud, and name the definition you used.
:::
