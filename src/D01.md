SUB: You will be able to create a Git repository, push it to a private GitHub repository over SSH, recover from a committed secret, and explain each step out loud.

## The idea in one minute

Git keeps your project as a series of saved snapshots called commits. Each commit records what changed, who made the change, when, and a short message saying why. GitHub is a website that holds a shared copy of the repository so your team can work on it together. Two protections keep that copy safe: an SSH key, which proves that the computer pushing the code is yours, and two-factor authentication (2FA), which asks for a code from your phone as well as your password.

Git is a lab notebook where every page is dated and signed, and no page can be silently torn out.

Today you will set up your identity, create a repository, publish it privately, protect the main line of work, and undo a secret that was saved by mistake.

## Starting from zero

This section defines every technical word the day uses. Read it once before the tools section, and come back to it when a word stops making sense.

### The terminal and commands

A **terminal** is a window where you type text instructions and the computer answers with text. An instruction typed into the terminal is a **command**. For example, `ls` is a command that lists the files in the current folder. The terminal is also called the **command line**, and tools that run there are called **CLI** tools (command-line interface).

On Windows, install Git for Windows. It includes **Git Bash**, a terminal that accepts the same commands as Linux and macOS. Every command in this book is written for that kind of terminal.

In this book, a line that starts with `$` shows something you type. The `$` itself is not part of the command. When you see `$ git status`, type `git status` and press Enter.

### Files, folders and paths

A **file** holds data, such as text or code. A **folder** (also called a **directory**) holds files and other folders. A **path** is the address of a file. The path `src/app.py` means the file `app.py` inside the folder `src`.

Your terminal always works inside one folder, called the **current directory**. The command `pwd` prints its path. The command `cd` changes it: `cd src` moves you into `src`, and `cd ..` moves you back up one level.

A **text editor** is a program for writing files that contain plain text, such as Visual Studio Code or Notepad. A **variable** is a name that holds a value. In `rows = 5`, the name `rows` holds the number 5. A **function** is a named block of code that you can call by its name, such as `load(path)`, to run it with a value you supply.

A **server** is a computer that provides a service to other computers over a network. GitHub runs servers that store your repository. Your laptop is a client: it asks those servers for things and sends them changes.

### Version control, repository and commit

**Version control** is a system that records every change to a set of files. **Git** is the most widely used version control system. It stores its records in a hidden folder called `.git` inside your project.

A **repository** (or **repo**) is a project folder that Git is tracking, together with its `.git` history folder.

A **commit** is a saved snapshot of the project with a message attached. Every commit gets an identifier called a **hash**, such as `05a9471`. You only need the first seven characters to refer to a commit.

### Branch, remote, clone, push and pull

A **branch** is a separate line of commits. The default main line is called `main`. You create a branch when you want to work on something without touching `main`.

A **remote** is a copy of the repository on another server, usually GitHub. By convention the main remote is named `origin`. A **clone** is a copy of a remote repository made on your computer. A **push** sends your new commits to a remote. A **pull** fetches new commits from a remote and merges them into your current branch.

### Passwords, SSH keys and 2FA

**Authentication** means proving who you are. A password is a secret you type. An **SSH key** is a different method: it is a pair of files. The **private key** stays on your computer and must never be shared. The **public key** ends in `.pub` and can be given to anyone, including GitHub. SSH stands for **Secure Shell**, a protocol for connecting to another computer securely. When you push, GitHub sends a challenge that only the holder of the private key can answer.

**Two-factor authentication (2FA)** asks for a second proof in addition to your password. The usual second proof is a short code from an **authenticator app**, which is a program on your phone that creates a new code every 30 seconds.

:::key Private and public keys
Give the `.pub` file to GitHub. Never give the file without `.pub`. That file is the private key, and anyone who has it can act as you.
:::

## The tools

### Git

**What it is.** Git is a distributed version control system. Distributed means that every clone holds the full history, so you can compare, revert and audit changes without asking a server every time.

**Why CityPulse uses it.** Every CityPulse ticket is scored from commit evidence, so the authorship of each change must be real and traceable. Git gives every commit an author name, a time and a message. The course's CHARTER check also depends on Git: it counts distinct authors for a file, which only works when each person commits with their own identity.

The course compares Git with two alternatives. A shared Google Drive folder is easy for documents, but it has no line-by-line history, no branches and no reviewable diffs for code. Subversion (SVN) is centralised and simpler, but most current teams do not use it, and it needs the server for most operations.

**How it works.** Git tracks files in three places. The **working tree** is the set of files you can see and edit. The **staging area**, also called the **index**, is a holding area where you choose which changes go into the next commit. The **repository** is the history of commits.

The sequence is: edit files in the working tree, use `git add` to move chosen changes into the staging area, then use `git commit` to record them as a commit. `git push` then copies the new commits to the remote.

:::key Commit identity
Git stamps every commit with the name and email stored in its settings. Git does not check these values against your GitHub account. They are a label you set yourself, which is why the course also requires SSH and 2FA for pushing.
:::

```flow
TITLE: What happens when you push
NODES: Your laptop | GitHub | Teammate's laptop
STEPS:
1>2 :: git push origin main :: Your new commits travel over SSH to the GitHub repository.
2>3 :: git pull :: Your teammate asks GitHub for the commits they do not have yet.
3>2 :: git push origin main :: The teammate's own commits are sent back the same way.
2>1 :: git pull :: GitHub sends you any commits your teammate has added.
```

The flow above shows the basic cycle. Node 1 is your laptop, node 2 is GitHub, and node 3 is a teammate's laptop. Each step is one movement, and the label on the arrow is the command that starts it. Read the arrows in order: first you push, then your teammate pulls, pushes and pulls back. The message never travels to a teammate directly; GitHub is always in the middle.

Now watch the commands that make a commit. In the terminal below, a new file `notes.txt` goes from untracked to committed.

```term
$ git status --short
?? notes.txt
$ git add notes.txt
$ git status --short
A  notes.txt
$ git commit -m "Add notes"
[main 3f2a9c1] Add notes
 1 file changed, 1 insertion(+)
 create mode 100644 notes.txt
```

The first line runs `git status --short`. The `--short` flag shortens the output to one line per file. The `??` in front of `notes.txt` means Git can see the file but is not tracking it. The second line stages the file with `git add`. The third command shows `A  notes.txt`, where `A` means the file is added to the staging area. The `git commit -m "Add notes"` line creates the commit. The `-m` flag gives the message in the same command, so Git does not open an editor. The output line `[main 3f2a9c1]` shows the branch and the new hash. The remaining lines say that one file changed and that the file was created.

The course's slide commands show how to set up identity and create the first commit:

```bash
SQUAD=squad3   # your squad name
git clone https://github.com/citypulse-y2/citypulse-$SQUAD.git
cd citypulse-$SQUAD
git config user.name "Asha Rao"
git config user.email "asha.rao@example.com"   # email on your GitHub account
mkdir -p src data docs tests
touch src/.gitkeep data/.gitkeep docs/.gitkeep tests/.gitkeep
printf 'data/*\n!data/.gitkeep\n.env\n__pycache__/\n' > .gitignore
git add .
git status --short
git commit -m "Add folder layout and .gitignore"
git push origin main
git log --format='%h %an %s' -3
```

Line by line, the commands do the following. `SQUAD=squad3` stores the text `squad3` in a variable called `SQUAD`. The `# your squad name` part is a comment, which the shell ignores. The `$SQUAD` in the next line puts the variable's value into the address. `git clone` copies the remote repository to your laptop, and `cd` moves into the new folder. `git config user.name` and `git config user.email` store your identity. Use the same email as your GitHub account, and replace the example name with your own.

`mkdir -p src data docs tests` creates four folders. The `-p` flag creates parent folders if needed and does not complain if a folder exists already. `touch` creates empty files. Git does not track empty folders, so each folder gets an empty file named `.gitkeep` to keep it in the repository. The `.gitkeep` name is a convention, not something Git enforces.

`printf` writes text into a file. The `\n` symbols mean a new line. The `>` sign writes into `.gitignore`, replacing whatever was there. The four lines are the rules for ignored files. `data/*` ignores everything in `data/`. `!data/.gitkeep` is an exception that brings back the `.gitkeep` file. `.env` and `__pycache__/` ignore a secrets file and Python's cache folder.

`git add .` stages every change that is not ignored. The dot means the current folder. `git status --short` shows the result. `git commit` records it. `git push origin main` sends `main` to the remote called `origin`. The last command, `git log --format='%h %an %s' -3`, prints the last three commits. `%h` is the short hash, `%an` is the author's name and `%s` is the message.

You should see the `git log` output list three lines, each with a hash, a name and a message. If the name is not yours, your identity was not set before the commit.

:::trap Committing with someone else's identity
A commit made on a shared laptop, or after copying a teammate's settings, carries the wrong name. Check with `git config user.name` before every session that matters. The course counts authorship from these names.
:::

:::trap Ignoring a whole folder
Writing `data/` in `.gitignore` hides `data/.gitkeep` too, so the folder disappears from the repository. Use `data/*` followed by `!data/.gitkeep` instead.
:::

:::trap git commit -am and new files
The `-a` flag stages changes to files Git already tracks. It does not add a brand-new file. If you create `.gitignore` and run `git commit -am`, the new file is left out. Run `git add .gitignore` first. The TIA example in the course shows `git commit -am` for a new `.gitignore`, which only works when the file was already tracked.
:::

### GitHub, organisations and 2FA

**What it is.** GitHub hosts Git repositories on the internet. It also adds issues, projects, pull requests and access control. An **organisation** groups people and repositories under one owner. The course uses one organisation, `citypulse-y2`, where every squad repository lives.

**Why CityPulse uses it.** The course compares GitHub with GitLab and with personal repositories shared with collaborators. GitLab has strong built-in CI and can be self-hosted, but the course's programme, workflows and command-line tools are built around GitHub. Personal repositories are quick to set up, but they give no central member list, no 2FA enforcement and no team-wide audit. With an organisation, trainers can see every repository and member in one place. They can also list members who have 2FA disabled.

**How it works.** Your GitHub account is your identity for the whole course. You protect it with 2FA before anything else. Access to a repository comes from membership in the organisation. The course sends you an invitation, and you accept it before the organisation grants access to your squad's repository.

The course recommends an authenticator app for 2FA. It warns against SMS codes, and it warns you to download your recovery codes before logging out. Without recovery codes, a lost phone can lock you out.

The course's verification commands use the GitHub command-line tool `gh`:

```bash
gh auth login --hostname github.com --git-protocol https --web
gh auth status
gh api user --jq '.login, .name, .two_factor_authentication'
gh api user/memberships/orgs/citypulse-y2 --jq '.state'
gh api -X PATCH user/memberships/orgs/citypulse-y2 -f state=active --jq '.state'
gh repo list citypulse-y2 --limit 20
```

`gh auth login` starts the login. `--hostname github.com` names the GitHub website. `--git-protocol https` tells `gh` to use HTTPS for Git operations. `--web` opens a browser for the sign-in. The output of a successful login says you are logged in.

`gh auth status` prints the account that is logged in. `gh api user` asks GitHub for information about your account. `--jq` filters the answer with a small query language, so only the three fields you need are printed: the username, the display name, and whether 2FA is on. The value you want is `true`.

`gh api user/memberships/orgs/citypulse-y2` asks for your membership state in the organisation. It should print `pending` until you accept the invitation, and `active` afterwards. The next command, with `-X PATCH`, changes the membership. The `-X` flag sets the HTTP method, which is the kind of request being sent. `-f state=active` sends the field `state` with the value `active`. The last command lists repositories in the organisation.

You should see `true` on the 2FA line and `active` once the invitation is accepted. If `two_factor_authentication` is `false`, go back to your security settings before you continue.

```flow
TITLE: Logging in with 2FA
NODES: Your laptop | GitHub | Authenticator app
STEPS:
1>2 :: password :: Your laptop sends your username and password to GitHub.
2>1 :: second step required :: GitHub will not finish the login until a second proof arrives.
3>1 :: current code :: The code shown by the app is typed into the login page.
```

The flow shows that a password alone is not enough. GitHub stops after the first step and waits for the second. The authenticator app does not connect to GitHub at all. It shows a code, and you type that code yourself. Because the code changes every 30 seconds, a copy stolen from a shoulder or a leaked password does not help an attacker for long.

:::trap Recovery codes
If you do not save recovery codes when you enable 2FA, a lost phone can lock you out of your account. Download them before you log out, and store them somewhere other than the phone that holds the authenticator app.
:::

:::trap SMS as a second factor
Text-message codes are weaker than an authenticator app. The course asks you to use an app such as Google Authenticator. Follow the ticket's instructions for the exact setup.
:::

:::trap A second account
If you accept the organisation invitation with a second GitHub account, the membership is attached to the wrong login. The course requires the account that matches your onboarding form.
:::

### Markdown

**What it is.** Markdown is a lightweight syntax for headings, lists, links, tables and code blocks, written in plain text. A file with the extension `.md` is a Markdown file. GitHub renders `.md` files as formatted pages, so the text you write becomes a document.

**Why CityPulse uses it.** The course uses Markdown for `README.md`, which is the first page an auditor reads, and for `CHARTER.md`, which holds the squad's success metric and signatures. Word and Google Docs offer richer formatting, but their files live outside the repository, so they cannot be compared line by line in a pull request. reStructuredText is powerful for documentation websites, but its syntax is heavier than a squad needs.

**How it works.** You write a heading with `#`, a second-level heading with `##`, a list with `-` and a checklist with `- [ ]`. Because each line is plain text, a later change shows up as a readable line diff. Here is the charter from the course, with its signature lines removed:

```text
# CityPulse squad3 Charter
## Success metric
At least 95% of hourly PM2.5 readings for Bengaluru captured per week by 2026-12-12.
## Process controls
- [ ] No direct deletes on shared data without a second person present
- [ ] Backups are restored and checked, not only taken
```

The first line is a level-one heading, which is the title of the document. The second line starts a level-two heading. The metric line is one sentence, with a number, a unit (PM2.5 readings in micrograms per cubic metre are measured per hour), a time window (per week) and a target date. The `- [ ]` lines are checklist items. GitHub draws an empty box for each one. The course's rule for the metric is to always state a number, a unit and a target date.

The course's signature line format is `Signed: <name> (@<username>), <date>`. Each member adds their own line in their own commit, so `git log` can show who signed.

:::trap Writing a line that starts with >
In Markdown, a line that starts with `>` becomes a quotation. A line that starts with `>=` is therefore not shown as written. Write the symbol ≥ or the words "At least" instead.
:::

:::trap A missing blank line
A list or heading needs a blank line before it. Without one, GitHub joins the list into the paragraph above and shows plain text.
:::

## The worked example

The course's example follows one small project through its history: the `ingest.py` script that reads a CSV file of air-quality readings. The goal is to create a repository, add a secrets rule, review a change, work on a feature in a branch, push, and read the history.

Here is the script at the start. The course writes it on one line in the slides, but the layout below is the same code with each statement on its own line.

```python
import csv
import sys


def load(path):
    with open(path) as f:
        return [r for r in csv.DictReader(f)]


if __name__ == "__main__":
    rows = load(sys.argv[1])
    print(f"ingested {len(rows)} readings")
```

Line by line: `import csv` and `import sys` bring in two standard Python modules. `csv` reads comma-separated files, and `sys` gives access to the command-line arguments. `def load(path):` defines a function called `load` that takes one argument, the file path. The `with open(path) as f:` line opens the file, and `as f` gives it the name `f` for the block below. `csv.DictReader(f)` reads each line as a dictionary whose keys come from the header row. The list comprehension `[r for r in ...]` collects those rows into a list. The `if __name__ == "__main__":` line means the lines below run only when you start this file directly, not when another file imports it. `sys.argv[1]` is the first argument typed after the script name. The final `print` shows how many rows were read.

To run it, you would type `python ingest.py readings.csv`, where `readings.csv` is a file you have on disk. The output would be a line such as `ingested 24 readings`. The number depends on your file.

The first commit records this file:

```text
$ git init -b main && git add ingest.py && git commit -m 'Add CSV ingest script'
Initialized empty Git repository in /home/priya/citypulse/.git/
[main (root-commit) 05a9471] Add CSV ingest script
 1 file changed, 12 insertions(+)
 create mode 100644 ingest.py
```

`git init -b main` creates the `.git` folder and names the first branch `main`. The `&&` between commands means run the next command only if the previous one succeeded. `git commit` records the file. The label `root-commit` means this is the first commit in the repository.

Next, the course adds a `.gitignore` so that secrets and local data stay out of the repository, and it checks the result with `git status --ignored --short`. The `--ignored` flag adds files that are being ignored. Lines starting with `!!` are ignored, and lines starting with `??` are untracked but not ignored. The private key `id_city` shows as `!!`, which means it cannot be pushed by accident.

Then the script changes. The change drops negative sensor readings. The `git diff ingest.py` command shows the change before it is committed:

```text
@@ -4,4 +4,5 @@ def load(path):
 if __name__ == "__main__": rows = load(sys.argv[1])
-    print(f"ingested {len(rows)} readings")
+    rows = [r for r in rows if float(r["value"]) >= 0]
+    print(f"ingested {len(rows)} valid readings")
```

The `@@` line is a hunk header: it says the change starts near line 4 of the file. A line that starts with `-` was removed, and a line starting with `+` was added. Lines with no sign are unchanged context. The new line keeps only rows whose `value` field is zero or greater. The commit is `git commit -am 'Drop negative sensor readings on ingest'`, which works here because `ingest.py` is already tracked.

The commit output is `[main aa76664] Drop negative sensor readings on ingest`. Each commit gets its own hash.

The feature step creates a branch for a station filter, so `main` stays releasable:

```bash
git checkout -b feature/station-filter
git commit -am 'Scaffold station allowlist filter'
git checkout main
git merge --no-ff feature/station-filter -m 'Merge station-filter feature'
```

`git checkout -b feature/station-filter` creates a new branch and switches to it. The `-b` flag means create. The slash in the name is allowed, and it groups related branches. `git checkout main` switches back. `git merge --no-ff` joins the feature into `main`. The `--no-ff` flag, short for no fast-forward, forces a merge commit even when Git could simply move the pointer. That leaves a visible record that a feature existed.

The output says `Merge made by the 'ort' strategy`. Your version of Git may use a different merge strategy name, but the commit is the same kind of record.

Then the course pushes and reads the history:

```text
$ git push -u origin main
branch 'main' set up to track 'origin/main'.
$ git log --oneline --graph --decorate
* 2a661c5 (HEAD -> main, origin/main) Merge station-filter feature
|\
| * b94777d (feature/station-filter) Scaffold station allowlist filter
|/
* aa76664 Drop negative sensor readings on ingest
* 4329bc9 Ignore secrets and local sensor dumps
* 05a9471 Add CSV ingest script
```

The `-u` flag on `git push` sets `origin/main` as the place that `main` tracks, so later `git push` and `git pull` need no extra words. `git log --oneline` shows one line per commit. `--graph` draws the branch lines, and `--decorate` shows branch names. `HEAD` is the commit you currently have checked out. `origin/main` is what GitHub has. In this output they point to the same commit, so your local main and GitHub's main agree.

Read the graph from the bottom up. The first commit is at the bottom, and the merge is at the top. Every line is a snapshot you can return to with `git checkout <hash> -- ingest.py` to restore one file, or undo with `git revert <hash>`.

## The hands-on lab, step by step

Your course ticket may name a slightly different sequence, and it may use `gh auth login` over HTTPS rather than SSH. Follow the ticket where it differs. The steps below cover the same skills and are the ones the graded checks rely on.

### Step 1 — Tell Git who you are

**What you do.** Store your name and email in Git's global settings. These values go into every commit you make.

**What you type.**

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --list --show-origin
```

`git config --global` writes the setting for your whole user account, not a single project. `user.name` and `user.email` are the keys. The last command lists every setting and the file it comes from.

**What you should see.** The list includes a line starting with `file:` that ends with `user.name=Your Name` and another with `user.email=you@example.com`.

**How you know it worked.** Both lines appear, and the email matches the one on your GitHub account.

### Step 2 — Create the repository and your first commit

**What you do.** Make a new folder, start a repository in it, add a script, and commit it. Then add a `.gitignore` and commit that separately.

**What you type.**

```bash
mkdir citypulse-practice
cd citypulse-practice
git init -b main
```

Open a text editor, paste the `ingest.py` code from the worked example, and save it as `ingest.py` inside `citypulse-practice`. Then continue in the terminal:

```bash
git add ingest.py
git commit -m "Add CSV ingest script"
printf '.env\n*.key\nid_city\n__pycache__/\ndata/*.csv\n' > .gitignore
git add .gitignore
git commit -m "Ignore secrets and local sensor dumps"
git log --oneline
```

`mkdir` creates the folder and `cd` moves into it. `git init -b main` creates the repository with `main` as the first branch. `git add` stages the file and `git commit -m` records it. The `printf` line writes five ignore rules into `.gitignore`. `*.key` ignores any file ending in `.key`, and `id_city` is an example name for a private key file that must never be committed. Then `.gitignore` is added and committed on its own. The last command prints one line per commit.

**What you should see.** `git init` prints `Initialized empty Git repository`. Each commit prints a line starting with `[main` and a hash. `git log --oneline` shows two commits, each with its hash and message.

**How you know it worked.** `git status` reports `nothing to commit, working tree clean`. The `.gitignore` file is listed in `git log` as its own commit.

### Step 3 — Authenticate to GitHub over SSH

**What you do.** Create an SSH key pair, give the public half to GitHub, and check that GitHub accepts the connection.

**What you type.**

```bash
ssh-keygen -t ed25519 -C "you@example.com"
cat ~/.ssh/id_ed25519.pub
ssh -T git@github.com
```

`ssh-keygen` creates the key pair. `-t ed25519` chooses the modern Ed25519 algorithm. `-C` attaches a label, which is usually your email, so you can recognise the key later. The tool asks where to save the key. Press Enter to accept the default. It also asks for a passphrase. Choose one on a laptop, because the passphrase protects the private key if the laptop is stolen. The `~` symbol means your home folder. `cat` prints a file, so `cat ~/.ssh/id_ed25519.pub` shows the public key. `ssh -T git@github.com` tests the connection without opening a shell.

Copy the single line printed by `cat`. In GitHub, go to Settings, then SSH and GPG keys, choose New SSH key, paste the line, and save. Then run the `ssh -T` command again.

**What you should see.** The first time, SSH asks whether you want to continue connecting. Type `yes`. The final message reads `Hi <your-username>! You've successfully authenticated, but GitHub does not provide shell access.`

**How you know it worked.** The message includes your username. If you see `Permission denied (publickey)`, the key is not on GitHub or you pasted the wrong file.

### Step 4 — Create a private remote and push

**What you do.** Create an empty private repository on GitHub, connect your folder to it, and push `main`.

**What you do on GitHub.** Choose New repository, name it `citypulse-practice`, set the visibility to Private, and do not tick any option to add a README or `.gitignore`. Those files already exist in your folder, and adding them on GitHub would create a conflict.

**What you type.**

```bash
git remote add origin git@github.com:YOUR-USERNAME/citypulse-practice.git
git push -u origin main
gh repo view --json visibility
```

`git remote add origin` saves the address of the remote under the name `origin`. The address `git@github.com:...` is an SSH address, so the push uses your key. Replace `YOUR-USERNAME` with your GitHub username. `git push -u origin main` sends the commits and sets the upstream. `gh repo view --json visibility` asks GitHub for the visibility of the repository.

**What you should see.** The push prints a line with `* [new branch]` and `main -> main`, then `branch 'main' set up to track 'origin/main'.` The last command prints `{"visibility":"PRIVATE"}`.

**How you know it worked.** The repository page on GitHub shows your commits, and the Private label is visible on the page.

### Step 5 — Branch, change, and open a pull request

**What you do.** Make a branch, add a README, push the branch and open a pull request. A pull request is a request to merge one branch into another, with a page where people can review the changes.

**What you type.**

```bash
git checkout -b feature/add-readme
echo "# CityPulse practice" > README.md
git add README.md
git commit -m "Add README"
git push -u origin feature/add-readme
gh pr create --fill
```

`git checkout -b feature/add-readme` creates the branch and switches to it. `echo "..." > README.md` writes one line of text into a new file. Then the file is staged and committed. `git push -u origin feature/add-readme` pushes the branch. `gh pr create --fill` opens a pull request, and `--fill` copies the title and description from the commit message.

**What you should see.** The push output includes a link to create a pull request. `gh pr create` prints the URL of the new pull request.

**How you know it worked.** Opening the URL shows the pull request with the README in the changed files.

### Step 6 — Protect main and prove it works

**What you do.** Ask GitHub to refuse direct pushes to `main`, and then try one to see the refusal.

**What you do on GitHub.** Open the repository's Settings, choose Branches, and add a branch protection rule for the pattern `main`. Tick the option that requires a pull request before merging. The exact labels may vary, so follow the ticket if they differ. If your plan does not offer branch protection for private repositories, ask your trainer.

**What you type.**

```bash
git switch main
git commit --allow-empty -m "Test direct push"
git push origin main
git reset --hard origin/main
```

`git switch main` changes to `main`. `git commit --allow-empty` records a commit that changes no files, which is enough to test the push. `git push origin main` tries to send it. The final command, `git reset --hard origin/main`, moves your local `main` back to match GitHub and removes the test commit. This is safe only because the test commit holds nothing else. The `--hard` flag throws away local changes, so never use it when you have uncommitted work you want to keep.

**What you should see.** The push is rejected, and the message mentions a protected branch. After the reset, `git log --oneline -1` no longer shows `Test direct push`.

**How you know it worked.** The rejection appears, and the test commit is gone from your local history.

### Step 7 — Recover from a committed secret

**What you do.** Commit a fake secret on purpose, then remove it from the project and stop it being tracked. This practice uses a fake value. A real secret needs one more step, covered in the trap box below.

**What you type.**

```bash
git switch feature/add-readme
echo "API_KEY=test-123" > .env
git add -f .env
git commit -m "Add config"
git push
git rm --cached .env
echo ".env" >> .gitignore
git add .gitignore
git commit -m "Stop tracking .env"
git push
```

`git switch feature/add-readme` returns to the branch you used in step 5. `echo ... > .env` creates a file called `.env` with a fake key. `git add -f .env` forces Git to stage a file that is ignored, because the `-f` flag overrides the ignore rule. The commit and push record the mistake. Then `git rm --cached .env` removes the file from the repository and keeps it on your disk. The `--cached` flag is what makes this safe. `echo ".env" >> .gitignore` adds `.env` to the end of the ignore file. The `>>` sign appends instead of overwriting. The last commit and push record the fix.

**What you should see.** `git rm --cached .env` prints `rm '.env'`, and the file stays on your disk. After the second push, GitHub shows `.env` no longer in the latest commit.

**How you know it worked.** Running `git status --ignored --short` shows `!! .env`, which means the file exists locally and Git ignores it.

:::trap A real secret needs more than a commit
Removing a secret in a new commit does not remove it from history. The old commit still holds the value, and anyone who cloned the repository already has a copy. For a real key, first revoke it or create a new one in the service that issued it. Then clean the history with a tool such as git-filter-repo, which rewrites commits and needs a force push. That is a team decision, so ask your trainer before doing it.
:::

## What the quiz tests

Each subsection covers one topic from the day's quiz. The questions you face in the platform are your own work to answer. The practice questions below are original, written to test the same ideas.

### git-status

You must know what each two-letter code in `git status --short` means. `??` means untracked, `A` means added to the staging area, `M` means modified, and `!!` means ignored. The first letter describes the staging area and the second describes the working tree, so `MM` means a file was staged and then edited again. Examiners set the trap by asking what `git status` shows after a commit, when the answer is that the commit changes nothing you can see until you edit again.

### git-untrack-secret

Adding a file to `.gitignore` does not remove a file Git already tracks. The file must first be removed from the index with `git rm --cached`, then committed. The trap is the belief that ignore rules erase history. They only affect files that are not yet tracked, and they do not touch past commits. Examiners also ask what happens to the file on disk, which stays because of `--cached`.

### git-commit

A commit records only what is in the staging area, unless you use `-a`, which also stages changes to tracked files. You must know that `git commit -m` takes the message on the command line, that a commit has an author and a timestamp, and that a commit is local until you push it. The trap is thinking that committing sends code to GitHub.

### github-auth

GitHub accepts an SSH key or a token to prove you are the account owner. You upload the public key, keep the private key on your machine, and Git proves possession of the private key with a challenge. The trap is uploading the wrong file, the private key, which gives away your identity. Examiners also ask why a password alone cannot push when SSH is set up, because SSH does not send your password.

### signed-commits

A commit's author name is only a label that you set with `git config`. A signature adds proof that the commit was made by a holder of a particular key. Git can sign commits with `git commit -S` when a signing key is configured. The trap is believing that a signed commit proves its code is correct. A signature proves who signed, not that the content is good.

### secret-leak-response

When a secret reaches GitHub, treat it as compromised. Revoke or rotate the credential first, because any clone or fork made in the meantime holds a copy. Then remove the file and, if the team agrees, rewrite history. The trap is choosing to rewrite history first, which leaves the secret valid and still available to anyone who already copied it.

### git-pull

`git pull` fetches new commits from the remote and merges them into your current branch. It is a fetch followed by a merge. A conflict happens when the same lines changed in two places, and Git stops until you fix them. The trap is treating `git pull` as an upload. Uploading is `git push`.

### git-tags

A tag is a fixed name for one commit, often used for a release. An annotated tag, made with `git tag -a v1.0 -m "..."`, stores a message and the author. A tag does not move when new commits arrive, which is why it marks a release. The trap is creating a branch to mark a release, which moves as soon as anyone commits to it.

### staging-index-semantics

`git add` copies the content of a file into the staging area at that moment. Edits made after `git add` are not in the commit. You must add the file again to include them. The trap is expecting the commit to include the newest version. Examiners often show `git status` with `MM` and ask what will be committed, which is the staged version.

### github-2fa

Two-factor authentication means that a password alone does not let anyone log in. The second factor, an authenticator app code, is needed at login. Recovery codes are the backup if you lose the phone. The trap is treating SMS as equal to an app, or forgetting to save recovery codes before logging out. The course also uses an organisation to see who has 2FA disabled.

### Splitting text with str.split

A **string** is a piece of text in Python, written inside quotes. A **method** is a function that belongs to a value, and you call it with a dot. `str.split` is the string method that cuts text into a list of pieces.

```python
line = " M src/app.py"
parts = line.split()
print(parts)
```

`line = " M src/app.py"` stores the text, including its leading space, in a variable called `line`. `line.split()` with no arguments splits on any run of spaces, so `parts` becomes a list. `print(parts)` shows the list. The output is `['M', 'src/app.py']`. The leading space is gone, because the split ignores empty pieces at the ends. That is a problem for `git status`, where the first column is meaningful. You need the position of each character instead.

```python
line = "R  old.py -> src/new.py"
status = line[:2]
rest = line[3:]
print(status, "|", rest)
```

`line[:2]` takes the characters from position 0 up to, but not including, position 2. Python counts positions from 0. `line[3:]` takes everything from position 3 to the end. The output is `R  | old.py -> src/new.py`, with the first two characters, `R` and a space, before the bar. Position 2 is a space that separates the status from the path, so it is skipped.

Sometimes you want only the first split. `str.split` takes a second argument, `maxsplit`, which limits how many cuts are made:

```python
text = "old.py -> src/new.py"
old, new = text.split(" -> ", 1)
print(new)
```

The first argument `" -> "` is the separator. The second argument `1` means make at most one cut. The result is a list of two pieces, `old` and `new`, assigned in one line. Without `1`, a path with a second arrow in its name would split into more pieces, and the unpacking would fail. The output is `src/new.py`.

:::trap maxsplit and unpacking
If the text contains more separators than you expect, `a, b = text.split(sep)` raises an error. Pass `maxsplit` when you want the first cut only.
:::

### Lists of tuples

A **list** is an ordered collection, written in square brackets. A **tuple** is a small fixed group of values, written in round brackets. A list of tuples is a common shape for records: each tuple is one row.

```python
entries = [(" M", "src/app.py"), ("??", "notes.txt")]
for status, path in entries:
    print(status, path)
```

`entries` is a list of two tuples. Each tuple has two values: a status and a path. The `for` loop takes one tuple at a time. The part `status, path` on the loop line is called **unpacking**: Python assigns the first value of each tuple to `status` and the second to `path`. The output is two lines, `  M src/app.py` and `?? notes.txt`. The space in front of `M` is part of the status and is printed.

Tuples cannot be changed after they are created. That makes them safe to use as records.

### Matching paths with fnmatch

A **glob pattern** is a short pattern that matches file names. `*` matches any run of characters, so `*.log` matches `app.log`. The standard library module `fnmatch` provides this matching in Python.

```python
import fnmatch

print(fnmatch.fnmatchcase("src/app.py", "*.py"))
print(fnmatch.fnmatchcase("notes.txt", "*.py"))
```

`import fnmatch` loads the module, which is a file of ready-made code. `fnmatch.fnmatchcase(name, pattern)` returns `True` if the name matches the pattern. The first call prints `True`, because `*` matches `src/app`. The second prints `False`. The `case` in `fnmatchcase` means the match is case-sensitive. The plain `fnmatch.fnmatch` function is not case-sensitive on Windows, because it first changes both sides to the same case. You need the predictable version for tests.

Note that `*` also matches `/`. So `*.log` matches `logs/app.log`. fnmatch does not understand folders. A pattern such as `data/` is not a glob, and a plain `fnmatch` check of `data/` would match only the literal text `data/`. You must handle a trailing slash yourself, which the solution below does.

### Counting matches

Counting is a loop with a variable that starts at zero and goes up by one for each match.

```python
count = 0
for path in ["a.py", "b.txt", "c.py"]:
    if path.endswith(".py"):
        count += 1
print(count)
```

`count = 0` sets the starting value. `path.endswith(".py")` is a string method that returns `True` when the text ends with the given suffix. `count += 1` means `count = count + 1`. The output is `2`. When you need the number of items that match, you can also write `sum(1 for p in paths if p.endswith(".py"))`, which does the same thing in one line.

:::trap Off-by-one counting
If you count unmatched items as matched, or count each item once per pattern, the numbers are wrong. Decide what each count means before you write the loop.
:::

### The practice problem

Write two functions and a report step.

`parse_status(text)` takes the output of `git status --short` as one string. It returns a list of `(status, path)` tuples, one per line. The `status` is the two characters Git prints, kept exactly, including any leading space, so `" M"` stays `" M"`. The `path` is the file path. If the line is a rename, written as `old -> new`, the path is the new name. Blank lines are skipped.

`matches_pattern(path, pattern)` returns `True` or `False`. A pattern that ends with `/` matches every path that starts with that folder name. Any other pattern is matched with `fnmatchcase`, so `*` also matches `/`. Matching is case-sensitive.

`report(entries, patterns)` takes the list from `parse_status` and a list of patterns. It returns a tuple `(matched, unmatched)`. `matched` is the list of paths that match at least one pattern, in the same order as the input. A path that matches two patterns is listed once. `unmatched` is the number of entries that match no pattern.

Example. Given this text:

```text
 M src/app.py
?? notes.txt
M  data/readings.csv
?? data/tmp.csv
R  old.py -> src/new.py
```

and the patterns `["*.py", "data/"]`, the parsed entries are `(" M", "src/app.py")`, `("??", "notes.txt")`, `("M ", "data/readings.csv")`, `("??", "data/tmp.csv")` and `("R ", "src/new.py")`. The matched paths are `src/app.py`, `data/readings.csv`, `data/tmp.csv` and `src/new.py`. One entry, `notes.txt`, is unmatched, so the count is `1`.

Edge-case checklist. Work through each one before you look at the solution.

- Empty input: what does `parse_status("")` return, and what does `report([], patterns)` return?
- Blank lines and trailing newlines in the text.
- Ties: a path that matches two patterns must appear once.
- Ordering: matched paths keep the order of the input, not the order of the patterns.
- Types: the status keeps its spaces, so `" M"` and `"M "` are different values.
- Missing fields: a line with only a status and no path should not crash your code. Decide what to do and say so in a comment.
- Case: `Src.PY` does not match `*.py` when matching is case-sensitive.
- Prefixes: `data2/x.csv` must not match `data/`.
- Empty pattern list: nothing matches, so every entry is unmatched.
- Rounding does not apply here, but counting does: check that the count is an integer, not a list.

:::answer Full solution and explanation

```python test
import fnmatch


def parse_status(text):
    entries = []
    for line in text.splitlines():
        if not line.strip():
            continue
        status = line[:2]
        path = line[3:]
        if " -> " in path:
            path = path.split(" -> ", 1)[1]
        entries.append((status, path))
    return entries


def matches_pattern(path, pattern):
    if pattern.endswith("/"):
        return path.startswith(pattern)
    return fnmatch.fnmatchcase(path, pattern)


def report(entries, patterns):
    matched = []
    unmatched = 0
    for status, path in entries:
        if any(matches_pattern(path, p) for p in patterns):
            matched.append(path)
        else:
            unmatched += 1
    return matched, unmatched

Any other pattern goes to `fnmatch.fnmatchcase`. `report` loops over the entries. `any(...)` with a generator checks all patterns and stops at the first match. ## Say it out loud

Your viva examiner or an interviewer may ask these questions. Answer them in your own words, and use the model answer to check that you covered the same points.

**Why does CityPulse use Git rather than a shared folder?**

:::answer Model answer
A shared folder keeps only the latest copy of each file, so it cannot show who changed a line or why. Git records every change as a commit with an author, a time and a message. Each commit can be compared, reverted and audited, and the history is kept on every clone. That is what lets trainers score each ticket from the work itself.
:::

**What is the difference between git add and git commit?**

:::answer Model answer
`git add` copies the chosen changes into the staging area, which is a holding area for the next commit. `git commit` takes what is in the staging area and records it as one snapshot with a message. Nothing is saved to history until you commit, and changes made after `git add` are not included until you add them again. Pushing comes after both steps and sends the commits to GitHub.
:::

**How can you tell who made a commit?**

:::answer Model answer
Each commit stores the author name and email from the Git settings on the machine that made it. You can see them with `git log --format='%h %an %s'`. The name is a label that you set yourself, so it is not proof on its own. The course adds SSH keys and 2FA so that only the account owner can push under that identity.
:::

**What do you do when a secret is pushed to GitHub?**

:::answer Model answer
I treat the secret as compromised. First I revoke or rotate it in the service that issued it, because copies may already exist. Then I remove the file from the project with `git rm --cached` and add it to `.gitignore`. Rewriting history to remove the secret is a team decision that needs a force push, and it does not undo any copy that was already taken. I tell the team and my trainer straight away.
:::

**Why use an SSH key and 2FA instead of a password?**

:::answer Model answer
A password can be guessed, reused or leaked, and anyone who has it can act as you. An SSH key stays on your machine, and GitHub checks it with a challenge that only the private key can answer, so no password crosses the network. 2FA adds a second proof at login, so a stolen password alone is not enough. Together they mean a leaked password cannot push code to a squad repository.
:::
