TITLE: Day 15 — Serverless and cost awareness
SUB: You will be able to deploy a scheduled Lambda function, read its billed cost from the logs, price it against a virtual machine, and tear everything down safely.

## The idea in one minute

Today you run a small program in the cloud that wakes up every 30 minutes, fetches air-quality data for Bengaluru, and saves it to a storage bucket. Then you measure what it cost and compare that with keeping a virtual machine switched on all month.

Think of a taxi. You hail one for each trip and pay for the ride. A private car sits in the car park all day and you pay for it whether you drive or not. Lambda is the taxi and a virtual machine is the car. For a job that takes two seconds every half hour, the taxi is much cheaper.

By the end you will be able to write a handler, schedule it, read its billing line, do the cost sums by hand, and delete everything except what you meant to keep.

## Starting from zero

**The terminal.** The terminal is a window where you type instructions to the computer instead of clicking. Each instruction is a **command**. Lines in this book that start with `$` are commands you type. The `$` is the prompt, a marker that says "type here". You do not type the `$` itself.

**Flags.** Most commands take extra options called **flags**. A flag starts with `-` or `--`. In `aws logs tail /aws/lambda/citypulse-fetch --since 30m`, the flag `--since 30m` means "show the last 30 minutes". Flags tell the command how to behave.

**A file and a folder.** A **file** is a named block of stored text or data. A **folder** (also called a directory) holds files and other folders. Paths such as `infra/function/handler.py` mean: start in `infra`, go into `function`, and open `handler.py`.

**A variable.** A **variable** is a name that stores a value, such as `size = 318`. The name `size` now stands for 318 until you change it. Python programs use variables for almost everything.

**A function.** A **function** is a named block of code that takes inputs and gives back a result. `def` starts a function definition in Python. `def handler(event, context):` defines a function called `handler` that takes two inputs.

**A server.** A **server** is a computer that waits for requests and answers them. Your laptop is not a server. A virtual machine on a cloud provider is a server, and you pay for it while it is switched on, even when it is idle.

**The cloud and AWS.** The **cloud** means rented computers and services in someone else's data centre. **AWS** (Amazon Web Services) is Amazon's cloud. Each service has a name. **S3** is the file storage service. A **bucket** is a container in S3, and an **object** is one file stored in a bucket. An object is identified by its **key**, which is its full path inside the bucket, such as `raw/openmeteo-aq/date=2027-01-12/fetch_0900.json`.

**JSON.** **JSON** (JavaScript Object Notation) is a text format for structured data. It uses `{"key": "value"}` pairs and lists in square brackets. Python reads it with the `json` module.

**An API.** An **API** (Application Programming Interface) is a defined way for one program to ask another for something. The Open-Meteo air-quality API answers a web request with JSON.

**Billing by time.** Compute is billed in units of memory multiplied by time. A **GB-second** is one gigabyte of memory used for one second. Running 1 GB for 10 seconds costs 10 GB-seconds. Lambda uses this unit, so the cost depends on how long your code runs and how much memory you give it.

**IAM and roles.** **IAM** (Identity and Access Management) controls who can do what in AWS. A **role** is an identity that a service can take on for a while. It comes with temporary credentials (a short-lived username and password pair made by AWS) and a list of allowed actions.

## The tools

### AWS Lambda

**What it is.** Lambda runs your code only when something triggers it. You give it a handler function, a runtime (the language version, here `python3.12`), a memory size, a timeout (the longest one run may last), and an execution role. AWS looks after the servers, patching and scaling.

**Why CityPulse uses it.** The fetch runs for about two seconds every 30 minutes. An always-on virtual machine would be idle for over 99% of its hours and would need patching. The course also compares Lambda with a scheduled GitHub Actions workflow, which is free but can start late and needs extra set-up to reach the bucket, and with an ECS Fargate scheduled task, which suits containers that run longer than 15 minutes.

**How it works.** When an event arrives, Lambda starts a container or reuses one that is already running. It gives the container temporary credentials for the execution role and calls `handler(event, context)`. When the handler returns or raises an error, Lambda writes a `REPORT` line to the logs. That line decides the bill.

**The slide code, line by line.** This is `infra/function/handler.py`, with indentation restored:

```python
import json, os, urllib.request
from datetime import datetime, timezone
import boto3

URL = ("https://air-quality-api.open-meteo.com/v1/air-quality?latitude=12.97"
       "&longitude=77.59&hourly=pm2_5,pm10,us_aqi&timezone=Asia%2FKolkata")

s3 = boto3.client("s3")  # created once per cold start, reused when warm

def handler(event, context):
    with urllib.request.urlopen(URL, timeout=20) as r:  # raises HTTPError on non-2xx
        body = r.read(); json.loads(body)               # raises if body is not JSON
    key = datetime.now(timezone.utc).strftime("raw/openmeteo-aq/date=%Y-%m-%d/fetch_%H%M.json")
    s3.put_object(Bucket=os.environ["CITYPULSE_BUCKET"], Key=key, Body=body)
    print(json.dumps({"key": key, "bytes": len(body)}))
    return {"key": key, "bytes": len(body)}
```

- `import json, os, urllib.request` loads three standard library modules. `json` reads and writes JSON, `os` reads environment variables, and `urllib.request` makes web requests. Standard library means it ships with Python, so there is nothing to install.
- `from datetime import datetime, timezone` takes two names from the `datetime` module, for the current time and the UTC time zone.
- `import boto3` loads the AWS SDK for Python. **boto3** is the library that lets Python call AWS services.
- `URL = (...)` stores the address of the API in a variable. The parentheses let the string continue over two lines. Python joins the two pieces into one string.
- `s3 = boto3.client("s3")` creates an S3 client. It sits outside the handler on purpose. Code at module level runs once when the container starts, not on every call.
- `def handler(event, context):` is the entry point Lambda calls. `event` holds the input data, and `context` holds information about the run.
- `with urllib.request.urlopen(URL, timeout=20) as r:` fetches the page and gives up after 20 seconds. `with` makes sure the connection closes afterwards. `as r` names the response `r`.
- `body = r.read(); json.loads(body)` reads the response bytes, and then parses them. The parse is only a check. If the body is not JSON, the call raises an error, and the run fails rather than saving bad data.
- `key = ...strftime(...)` builds the object key from the current UTC time. `%Y-%m-%d` gives the date and `%H%M` gives the hour and minute. So a run at 09:00 UTC writes `fetch_0900.json`.
- `s3.put_object(...)` saves the body into the bucket. `Bucket` reads the bucket name from the environment variable `CITYPULSE_BUCKET`. `Key` is the path inside the bucket. `Body` is the data.
- `print(...)` writes one line to the logs. The `json.dumps` call turns the Python dictionary into JSON text first.
- `return {...}` gives a result back to Lambda, which is also recorded.

:::trap Keys in environment variables
Do not put AWS access keys into environment variables or into the code. The execution role gives the function temporary credentials automatically. If you store a long-lived key, it can leak, and it stays valid until someone deletes it.
:::

:::trap The default 3-second timeout
Lambda's default timeout is 3 seconds. The course sets 60 seconds, so that a slow API response does not kill a run. The handler above also has its own 20-second limit on the web request.
:::

:::trap Swallowing errors
If you catch every exception and return success, CloudWatch records a successful run and you never see the failure. Let errors raise, so the invocation is marked as failed.
:::

### EventBridge Scheduler

**What it is.** EventBridge Scheduler is a managed cron service. You give it a timing rule, such as `rate(30 minutes)`, and a target, such as the Lambda function. At each tick it calls the target. **Cron** is the old Unix name for a scheduler. You will also see `cron(...)` expressions, which use a different syntax.

**Why CityPulse uses it.** It replaces the crontab on the old virtual machine from Day 19. A crontab is a list of timed commands kept on one machine. Once that machine is stopped, the schedule stops too, and the machine still costs money while it waits. The scheduler has no server to patch.

**How it works.** The scheduler assumes its own role. That role must trust `scheduler.amazonaws.com`. Because the scheduler can only do what its role allows, you give it the permission to invoke one function and nothing more. The call is asynchronous, which means the scheduler does not wait for the answer. You therefore prove that a run happened by reading the function's CloudWatch logs, not the schedule's status.

**The slide code, line by line.** The commands below come from the course slides. Indentation and the backslashes at the end of lines are kept.

```bash
export AWS_REGION=ap-south-1
FN_ARN=$(aws lambda get-function --function-name citypulse-fetch --query Configuration.FunctionArn --output text)
ROLE_ARN=$(aws iam get-role --role-name citypulse-scheduler --query Role.Arn --output text)
aws scheduler create-schedule --name citypulse-fetch-30m \
  --schedule-expression "rate(5 minutes)" --flexible-time-window Mode=OFF \
  --target "Arn=$FN_ARN,RoleArn=$ROLE_ARN"
aws logs tail /aws/lambda/citypulse-fetch --since 30m   # after 10+ minutes: 2 runs
aws scheduler update-schedule --name citypulse-fetch-30m \
  --schedule-expression "rate(30 minutes)" --flexible-time-window Mode=OFF \
  --target "Arn=$FN_ARN,RoleArn=$ROLE_ARN" --state DISABLED
aws scheduler get-schedule --name citypulse-fetch-30m > docs/evidence/$USER/T23-schedule.txt
```

- `export AWS_REGION=ap-south-1` sets an environment variable for this terminal session. It tells every later AWS command to use the Mumbai region.
- `FN_ARN=$(...)` runs a command and stores its output in a variable. `Configuration.FunctionArn` is the path inside the returned JSON to the function's ARN, its unique Amazon Resource Name. `--output text` prints the bare value without JSON around it.
- `ROLE_ARN=$(...)` does the same for the scheduler's role.
- `aws scheduler create-schedule` creates the schedule. `--name` is a label you choose. `--schedule-expression "rate(5 minutes)"` sets the timing. `--flexible-time-window Mode=OFF` means the run happens at the exact time, not somewhere within a window.
- `--target "Arn=...,RoleArn=..."` tells the scheduler which function to call and which role to use.
- `aws logs tail ... --since 30m` shows the last 30 minutes of log lines for the function. After ten minutes at a five-minute rate you should see two runs.
- `update-schedule` changes the rate to 30 minutes and adds `--state DISABLED`. This command replaces the whole definition, so you must pass the expression, the window and the target again. Leave out `--state DISABLED` if you want the schedule to keep running at the slower rate.
- `get-schedule ... > docs/evidence/...` saves the schedule's details to a text file. `>` sends the output into a file rather than the screen.

:::trap Reusing the execution role
Do not give the scheduler the function's execution role. The scheduler needs a role that trusts `scheduler.amazonaws.com`. A role that trusts only `lambda.amazonaws.com` will be refused.
:::

:::trap Counting manual invokes
A manual `aws lambda invoke` proves the function works, but it is not scheduled evidence. The course needs two runs started by the scheduler, visible in the logs.
:::

### Cost estimation and teardown scripts

**What it is.** Cost estimation turns usage into a monthly figure. Usage means hours, invocations, duration, memory and storage. You multiply each by the provider's published price. The AWS Pricing Calculator (calculator.aws) does this for you. A teardown script deletes resources in dependency order, so nothing keeps billing. A **dry run** prints what the script would delete without deleting anything.

**Why CityPulse uses it.** The client asked for numbers. Forty-eight runs a day for 30 days, at about two seconds each and 0.25 GB, come to about 720 GB-seconds a month. That is far less than the 730 hours a month a virtual machine runs. Teardown also matters for assessment. If a virtual machine or a schedule is still running, the account keeps billing, and the course fails that student.

**How it works.** Measured duration and memory, taken from the `REPORT` line, go into the calculator. This gives a monthly Lambda figure next to the virtual machine figure. The break-even count is the number of invocations at which the two costs are equal. Teardown runs schedule first, then function, then role, so nothing is left pointing at something that no longer exists.

**The slide code, line by line.** This is `infra/teardown.sh`, with indentation restored.

```bash
#!/usr/bin/env bash
set -euo pipefail
OWNER="${1:?usage: teardown.sh <owner> [--apply]}"; APPLY="${2:-}"
export AWS_REGION=ap-south-1
run() { if [[ "$APPLY" == "--apply" ]]; then "$@"; else echo "DRY: $*"; fi; }
run aws scheduler delete-schedule --name citypulse-fetch-30m
run aws lambda delete-function --function-name citypulse-fetch
ids=$(aws ec2 describe-instances --output text \
  --filters "Name=tag:Owner,Values=$OWNER" "Name=instance-state-name,Values=running,stopped" \
  --query 'Reservations[].Instances[].InstanceId')
for id in $ids; do run aws ec2 terminate-instances --instance-ids "$id"; done
echo "Kept: bucket, citypulse-pipeline user and policy (see README)"
```

- `#!/usr/bin/env bash` is the first line of a script. It tells the system to run the file with the Bash shell.
- `set -euo pipefail` makes the script stricter. `-e` stops at the first failing command. `-u` stops if an unset variable is used. `-o pipefail` makes a pipeline fail if any part of it fails.
- `OWNER="${1:?usage: ...}"` stores the first argument (the word after the script name) in `OWNER`. If it is missing, the `:?` part stops the script and prints the usage message.
- `APPLY="${2:-}"` stores the second argument, or an empty string if there is none.
- `run() { ... }` defines a small function called `run`. If `APPLY` is exactly `--apply`, it runs the command. Otherwise it prints `DRY:` followed by the command.
- `run aws scheduler delete-schedule ...` deletes the schedule first. This stops the scheduler firing at a function that is about to be deleted.
- `run aws lambda delete-function ...` deletes the function.
- `ids=$(...)` finds every EC2 virtual machine tagged with your owner name that is running or stopped. `--filters` narrows the list, and `--query` extracts only the instance IDs.
- `for id in $ids; do ...; done` loops over the IDs and terminates each one. The `$ids` is left unquoted on purpose, so that the shell splits the list into separate IDs.
- `echo "Kept: ..."` reminds you what is deliberately left behind.

:::trap Stopped machines still bill
A stopped virtual machine stops charging for compute, but its disk (the EBS volume) and any Elastic IP address keep billing. Price the volume too, and make sure the teardown terminates the machine.
:::

:::trap Using another region's prices
Prices differ by region. Select Asia Pacific (Mumbai), `ap-south-1`, in the calculator, and write the date next to the link, because prices change.
:::

:::trap Running --apply without reading the dry run
Read every `DRY:` line before you add `--apply`. Each line should name a resource tagged with your own owner name. If a line names something you do not recognise, stop and ask.
:::

## The worked example

**Goal.** A function validates each air-quality reading as it lands in S3, and the team wants to know what each run costs. The Technology in Action walk-through builds this example in seven steps. The account number `123456789012` is an example, so replace it with your own.

**Step 1, the handler.** Restored from the walk-through:

```python
def handler(event, context):
    rec = event["Records"][0]["s3"]
    key = rec["object"]["key"]
    size = rec["object"]["size"]
    print(f"validating {key} ({size} bytes)")
    return {"ok": size > 0, "key": key}
```

The handler reads the first record from the event, which is the list S3 sends with each object. It takes the object's key and size, prints a line, and returns `ok` when the object is not empty. `f"..."` is an f-string, which puts variables inside text. Its output is a line such as `validating raw/2026/11/03/S1-0900.json (318 bytes)`.

**Step 2, a local test.** You can test the logic on your own computer before you spend anything in AWS:

```python
import json
from validate_reading import handler

event = {"Records": [{"s3": {
    "bucket": {"name": "citypulse-readings"},
    "object": {"key": "raw/2026/11/03/S1-0900.json", "size": 318}}}]}

class Ctx:
    function_name = "citypulse-validate"

print(json.dumps(handler(event, Ctx())))
```

`from validate_reading import handler` loads the function from the file `validate_reading.py`. `event` is a dictionary that copies the shape of a real S3 event. `class Ctx` builds a stand-in for the `context` object. The last line calls the handler and prints its result. Run it with `python3 test_local.py`. The expected output is the print line from the handler, followed by `{"ok": true, "key": "raw/2026/11/03/S1-0900.json"}`.

**Step 3, package and deploy.** Zip the file, then create the function:

```bash
zip -q function.zip validate_reading.py
aws lambda create-function \
  --function-name citypulse-validate \
  --runtime python3.12 \
  --handler validate_reading.handler \
  --memory-size 128 --timeout 10 \
  --role arn:aws:iam::123456789012:role/citypulse-lambda \
  --zip-file fileb://function.zip
```

`zip -q` builds `function.zip` quietly. `--handler validate_reading.handler` means "file `validate_reading`, function `handler`". `--memory-size 128` and `--timeout 10` cap the cost. `--role` gives the execution role ARN, and `fileb://` tells the CLI to read the zip as binary data. The expected output is JSON that usually shows `"State": "Pending"`, which becomes `Active` within a few seconds.

**Step 4, the S3 trigger.** S3 must be allowed to call the function, and the bucket must notify the function:

```bash
aws lambda add-permission \
  --function-name citypulse-validate \
  --statement-id s3invoke --action lambda:InvokeFunction \
  --principal s3.amazonaws.com \
  --source-arn arn:aws:s3:::citypulse-readings
aws s3api put-bucket-notification-configuration \
  --bucket citypulse-readings \
  --notification-configuration file://notify.json
```

`add-permission` adds a rule to the function's resource policy. The rule says that S3 may call `InvokeFunction` for this bucket. `--statement-id` is a label for that rule. The second command turns on bucket notifications, reading the rules from `notify.json`. That file names the function and the event type `s3:ObjectCreated`. The course file is the authority here, so use it rather than writing your own.

**Step 5, trigger it.** Upload a reading:

```bash
aws s3 cp S1-0900.json s3://citypulse-readings/raw/2026/11/03/S1-0900.json
```

`aws s3 cp` copies a local file to a destination. The `s3://` prefix marks the destination as a bucket path. The expected output is `upload: ./S1-0900.json to s3://citypulse-readings/...`. The function then runs with no server involved.

**Step 6, read the logs.** Run `aws logs tail /aws/lambda/citypulse-validate --since 1m`. The log group `/aws/lambda/<function name>` is created automatically. You should see `START`, your print line, `END` and `REPORT`. The `REPORT` line shows `Billed Duration: 43 ms` and `Max Memory Used: 61 MB`.

**Step 7, right-size and guard.** Raise the memory and add an alarm:

```bash
aws lambda update-function-configuration \
  --function-name citypulse-validate --memory-size 256
aws cloudwatch put-metric-alarm \
  --alarm-name citypulse-validate-errors \
  --namespace AWS/Lambda --metric-name Errors \
  --statistic Sum --period 300 --threshold 1 \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --evaluation-periods 1
```

`update-function-configuration` changes settings without touching the code. The walk-through shows the flag as `--memorysize`, which is a typo. The correct flag is `--memory-size`. `put-metric-alarm` watches the `Errors` metric in the `AWS/Lambda` namespace. `--period 300` sums errors over 300 seconds. `--threshold 1` with `GreaterThanOrEqualToThreshold` raises the alarm when there is at least one error. `--evaluation-periods 1` means one period is enough. Note that this alarm has no action attached, so it only shows in the console until you add a notification. The walk-through says 256 MB "roughly halves" the duration. Treat that as something to measure, not something to assume.

## The hands-on lab, step by step

The lab uses the course function `citypulse-fetch`. Run commands from the folder that holds your project, and use the exact names in your README if they differ.

### Step 1: Write the handler

**What you do.** Create `infra/function/handler.py` with the code from the AWS Lambda section above.

**What you type.** Open the file in your editor and paste the code. Then check that Python reads it without errors:

python3 -c "import ast; ast.parse(open('infra/function/handler.py').read())"

**How you know it worked.** The command ends with no error text, and the file still contains the line `def handler(event, context):`.

### Step 2: Create a least-privilege execution role

**What you do.** Create a role that Lambda can take on, and give it only the permissions it needs: write to the raw prefix of the bucket, and write logs. "Least privilege" means granting only what is needed.

**What you type.** First, a trust policy saying that Lambda may take on this role. Save it as `trust.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "lambda.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}
```

Then run:

```bash
aws iam create-role --role-name citypulse-fetch-fn --assume-role-policy-document file://trust.json
aws iam attach-role-policy --role-name citypulse-fetch-fn \
  --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole
```

The second command gives the role the standard permission to write logs. Next, save a policy that allows writes to one prefix only, as `s3-write.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:PutObject",
    "Resource": "arn:aws:s3:::citypulse-pipeline-s3/raw/openmeteo-aq/*"
  }]
}
```

Then attach it with `aws iam put-role-policy --role-name citypulse-fetch-fn --policy-name citypulse-pipeline-s3 --policy-document file://s3-write.json`. Replace `citypulse-pipeline-s3` with your bucket name from the README if it differs.

**What you should see.** `create-role` prints the role's ARN. The other two commands print nothing when they succeed.

**How you know it worked.** `aws iam get-role --role-name citypulse-fetch-fn` returns the role, and the policy has `s3:PutObject` on the `raw/openmeteo-aq/` prefix only. No access key appears anywhere.

### Step 3: Package and deploy

**What you do.** Zip the handler and deliver it with the course script.

**What you should see.** The first run creates the function. A later run updates the code instead. The slides say the first run shows `create-function` and the second shows `update-function-code`. Check the output on each run.

### Step 6: Do the cost math

**What you do.** Turn the measured numbers into a monthly figure, and compare it with the virtual machine.

invocations = 48 * 30

:::trap A failed rerun

## What the quiz tests

Each topic below names the exact idea the platform's quiz checks. The questions in the quiz after the topics are original practice, not the platform's questions.

### s3-lambda-trigger: how a file upload starts the function

You must know that an S3 event notification pushes an event to Lambda when a new object is created, so no code has to poll the bucket. The function also needs a resource policy that allows S3 to invoke it, added with `add-permission`. The event arrives as a dictionary with a `Records` list, and each record holds the bucket name, the object key and the size. Examiners test whether you know there is no polling loop and no cost between uploads. The trap is answering with a cron job that lists the bucket, which works but keeps a schedule and a server in play.

### lambda-pricing: GB-seconds and requests

You must know that Lambda charges for compute as GB-seconds, which is invocations times seconds times memory in GB, plus a charge per request. Memory in megabytes becomes gigabytes by dividing by 1,024. Examiners give you a workload and ask for the monthly GB-seconds, so the working must be exact. The trap is forgetting to convert megabytes to gigabytes, which inflates the answer by a factor of 1,024.

### lambda-tuning: memory sets CPU and price

You must know that memory is the one setting that changes both the price per millisecond and the CPU available to the function. More memory can make a run finish faster, so the total cost may fall, or it may rise. The only reliable method is to measure the `REPORT` line at two or more memory sizes and compare the billed cost. The trap is assuming the largest setting is cheapest, or that memory has no effect on cost.

### lambda-limits: what Lambda will not do

You must know that a single Lambda run can last at most 15 minutes, which is the maximum timeout. Memory can be set between 128 MB and 10,240 MB. A job that needs longer, or needs its own long-running server, belongs on a container service or a virtual machine. Raising memory does not extend the time limit. The trap is trying to fix a long job by raising memory or by setting an ever-larger timeout.

### idempotency-retries: running twice must be safe

You must know that an operation is idempotent when running it again leaves the same result. Lambda can retry asynchronous invocations, and a schedule can retry a failed invoke, so the handler may run more than once for the same event. In the fetch, the key is built from the minute, so a second run in the same minute overwrites the same object. The trap is a unique key per run, which creates duplicates whenever a retry happens.

### lambda-execution-role: access without keys

You must know that the execution role is an IAM role that Lambda assumes. Lambda gives the function temporary credentials for that role, so no long-term key is stored in the code or the environment. The role's policy should grant only the actions and resources the function needs. The trap is believing that the role must have full access to be useful, or that the function needs an access key to reach S3.

### cold-starts: the first call is slower

You must know that a cold start happens when Lambda creates a new container. Lambda then loads the code, starts the runtime and runs module-level code, such as creating the boto3 client. A warm start reuses the container, so the module-level work does not run again. Shortening the start-up code and keeping heavy work out of the handler reduce the effect. The trap is blaming a cold start for a slow call without checking whether the handler itself is slow.

### concurrency-control: how many copies run at once

You must know that Lambda can run many copies of a function in parallel. AWS caps the total per account and region, and you can reserve a limit for one function with reserved concurrency. Invocations beyond the limit are throttled, and asynchronous ones are retried. The trap is trying to limit parallel runs by changing memory or timeout, which does nothing to the number of copies.

### batching-strategy: fewer invocations, lower cost

You must know that each invocation has a fixed cost per request and some per-run overhead. Grouping many small items into one run reduces the number of invocations. The cost is latency, because a batch waits until it is full or until a time limit passes, and a batch that is too large risks the timeout. The trap is batching so far that data arrives too late to be useful, or processing one record at a time when the work is small and frequent.

### lambda-observability: reading the bill and the errors

You must know that Lambda writes to a CloudWatch log group named `/aws/lambda/<function name>`. Each run writes `START` and `END` lines, your own print output, and a `REPORT` line with the billed duration and maximum memory used. Metrics such as `Errors` and `Throttles` can drive an alarm. The trap is reading only the `print` output and missing the `REPORT` line, which is the only place the billed duration appears.

- A loop inside the function that sleeps and then polls the bucket
- A public bucket policy that lets the function read every object

- 72
- 7,200

* 720

* At these numbers the 128 MB setting is cheaper, at 0.25 GB-seconds against 0.30 GB-seconds.
- The 512 MB setting is always cheaper because it runs faster.
- Memory has no effect on cost, only on speed.
- Cost depends only on the timeout, not on the duration.
WHY: 128 MB is 0.125 GB, times 2.0 seconds is 0.25 GB-seconds. 512 MB is 0.5 GB, times 0.6 seconds is 0.30 GB-seconds. Faster is not automatically cheaper, because the price rises with memory.

- Call the function repeatedly with a fresh event every minute to reset the clock
WHY: Lambda's maximum timeout is 15 minutes, and memory does not change that. Splitting the work into repeated calls leaves each piece limited by the same rule and adds overhead. A container service is the right tool for longer runs.

- Two objects are created with random names
* The same key is overwritten, so the bucket holds one object for that minute
- The bucket refuses the second write
- Lambda deletes the first object automatically
WHY: put_object with an existing key replaces the object. Because the key depends only on the minute, a retry in that minute does not create a duplicate. A retry in a later minute does create a new object, which is the trap.

Q: Which statement about a Lambda execution role is correct?
- The role must hold a permanent access key that the function reads from an environment variable
- The role is only for scheduled functions, not for triggers
- The role must have full administrator access for the function to run
* Lambda gives the function temporary credentials for the role, so no long-term key needs to be stored
WHY: The role is an identity that Lambda assumes. The credentials are temporary and are issued by AWS. Administrator access is the wrong choice because the role should be least privilege.

Q: A function's first call after a quiet period takes 1.5 seconds longer than later calls. What is the most likely cause, and which practice reduces its effect?
* A cold start. Keeping the boto3 client at module level means warm starts reuse it instead of creating it again.
- A bug in the bucket policy that slows every upload
- The function's memory was reset to zero after the quiet period
- The schedule created a duplicate copy of the function

WHY: Reserved concurrency caps how many copies of one function can run at once. Memory and timeout do not limit parallel copies. A lifecycle rule manages stored objects, not invocations.

- One invocation per reading
* Grouping readings into batches, for example up to 100 records per invocation

- Disabling the trigger and reading the data by hand
WHY: Batching cuts the number of invocations, which lowers request charges. Invoking once a day is cheap but the data is a day old. The batch size is a tuning choice that must stay within the time and memory limits.

WHY: The REPORT line is the only line with the billing figures. START and END only mark the boundaries of the run, and your print output shows what the code did, not what it cost.

## The graded lab skill

The graded lab asks you to write several small Python functions and pass visible and hidden tests. Hidden tests check the cases you did not think of, so this section teaches the techniques first.

**Integer and float arithmetic.** Python numbers come in two kinds. `int` holds whole numbers, such as `1440`. `float` holds decimals, such as `0.25`. Dividing with `/` always gives a float. Floats are binary approximations, so `0.1 + 0.2` gives `0.30000000000000004`. For money, this error matters.

**Decimal.** The `decimal` module stores decimal numbers exactly, as you would write them on paper. `Decimal("0.1") + Decimal("0.2")` gives `Decimal('0.3')`. Build each `Decimal` from a string, such as `Decimal(str(0.1))`, so that you do not inherit the float error.

**Rounding.** `round(2.5)` returns `2` in Python, because it rounds halves to the nearest even number. Money usually rounds half up, so 2.5 becomes 3. The `quantize` method with `ROUND_HALF_UP` does this for `Decimal`.

**Tuples and tie-breaks.** A tuple such as `(cost, memory, seconds)` is compared item by item from the left. `min` over a list of tuples therefore picks the lowest cost, and if costs are equal, the lowest memory. This is how "prefer less memory on a tie" works in one line.

**Raising errors.** `raise ValueError("...")` stops a function and reports a problem. Use it when the input cannot give a sensible answer, such as an empty list of configurations.

**Practice problem.** A thumbnail service is billed per GB-second and per million requests. Write three functions.

1. `gb_seconds(invocations, seconds_each, memory_mb)` returns the GB-seconds for one month. Use 1 GB = 1,024 MB.
2. `monthly_cost(invocations, seconds_each, memory_mb, price_per_gb_second, price_per_million_requests)` returns the total cost in money, rounded half up to 4 decimal places. The cost is GB-seconds times the GB-second price, plus invocations divided by one million times the request price.
3. `cheapest(configs, invocations, price_per_gb_second, price_per_million_requests)` takes a list of `(memory_mb, seconds_each)` pairs. It returns the tuple `(memory_mb, seconds_each, cost)` for the cheapest pair. Compare costs after rounding. If two configurations tie on cost, return the one with less memory. If the list is empty, raise `ValueError`.

Example: with 100,000 invocations, a price of 0.00002 per GB-second and 0.20 per million requests, the configuration `(256, 1.0)` costs 25,000 GB-seconds times 0.00002, which is 0.5, plus 0.1 million requests times 0.20, which is 0.02. The total is 0.52. Calling `cheapest([(128, 2.5), (256, 1.0), (512, 0.6), (1024, 0.3)], 100000, 0.00002, 0.20)` returns `(256, 1.0, 0.52)`.

**Edge-case checklist.**

- Empty input: zero invocations gives a cost of 0, and an empty configuration list raises an error.
- Ties: equal costs return the lower memory, not the first in the list.
- Ordering: the input order must not change the answer.
- Types: integers and floats both work for memory and seconds.
- Rounding: a cost of exactly 0.00005 rounds up to 0.0001, not down.
- Money arithmetic: use `Decimal`, so that float errors do not change a rounded result.
- Missing fields: a pair with the wrong number of items will raise an error, which is acceptable.

:::answer Full solution and walk-through
The solution below runs with `python test` when the book is built. Copy it into a file and run it to check your own version.

```python test
from decimal import Decimal, ROUND_HALF_UP


def gb_seconds(invocations, seconds_each, memory_mb):
    """Monthly GB-seconds: invocations x seconds x (MB / 1024)."""
    return Decimal(invocations) * Decimal(str(seconds_each)) * Decimal(memory_mb) / Decimal(1024)


def monthly_cost(invocations, seconds_each, memory_mb,
                 price_per_gb_second, price_per_million_requests):
    gbs = gb_seconds(invocations, seconds_each, memory_mb)
    requests = Decimal(invocations) / Decimal(1000000)
    cost = (gbs * Decimal(str(price_per_gb_second))
            + requests * Decimal(str(price_per_million_requests)))
    return float(cost.quantize(Decimal("0.0001"), rounding=ROUND_HALF_UP))


def cheapest(configs, invocations, price_per_gb_second, price_per_million_requests):
    if not configs:
        raise ValueError("no configurations given")
    scored = []
    for memory_mb, seconds_each in configs:
        cost = monthly_cost(invocations, seconds_each, memory_mb,
                            price_per_gb_second, price_per_million_requests)
        scored.append((cost, memory_mb, seconds_each))
    cost, memory_mb, seconds_each = min(scored)
    return (memory_mb, seconds_each, cost)


# gb_seconds
assert gb_seconds(1440, 2, 256) == 720
assert gb_seconds(0, 2, 256) == 0

# monthly_cost: the worked example, and a zero-invocation case
assert monthly_cost(100000, 0.5, 512, 0.00002, 0.20) == 0.52
assert monthly_cost(0, 2, 256, 0.00002, 0.20) == 0.0

# rounding half up: exactly 0.00005 becomes 0.0001
assert monthly_cost(1, 1, 1024, 0.00005, 0) == 0.0001

# cheapest: the main example
configs = [(128, 2.5), (256, 1.0), (512, 0.6), (1024, 0.3)]
assert cheapest(configs, 100000, 0.00002, 0.20) == (256, 1.0, 0.52)

# cheapest: a tie on cost goes to the lower memory
assert cheapest([(1024, 0.3), (512, 0.6)], 100000, 0.00002, 0.20) == (512, 0.6, 0.62)

# cheapest: an empty list raises ValueError
try:
    cheapest([], 1, 0.1, 0.1)
except ValueError:
    pass
else:
    raise AssertionError("expected ValueError for an empty list")
```

Explanation, line by line:

- `from decimal import Decimal, ROUND_HALF_UP` brings in the exact decimal type and the rounding mode for money.
- `gb_seconds` multiplies invocations, seconds and memory in gigabytes. `Decimal(str(seconds_each))` converts the float through its string form, so `0.5` becomes exactly `0.5`. Dividing by `Decimal(1024)` converts megabytes to gigabytes.
- In `monthly_cost`, `gbs` is the compute part of the bill. `requests` is the number of millions of invocations, so `1440 / 1000000` gives the request count in millions.
- `cost.quantize(Decimal("0.0001"), rounding=ROUND_HALF_UP)` rounds the total to four places, with halves going up. `float(...)` turns the result back into a normal number for the caller.
- `cheapest` raises an error for an empty list, so the function never tries to take a minimum of nothing.
- The loop computes the cost of every configuration. Each entry is `(cost, memory_mb, seconds_each)`.
- `min(scored)` compares the tuples from left to right. The lowest cost wins. If two costs match, the lower memory wins. This is the tie-break the task asks for.
- Each `assert` checks one rule: the formula, the zero case, the half-up rounding, the main example, the tie-break and the empty list.
- The `try` and `except` block checks that the error is raised. If no error occurs, `raise AssertionError` fails the build.

Expected output when the block runs: nothing. A failed assertion would stop the build with an error.
:::

## Say it out loud

Viva examiners and interviewers ask these questions about today's work. Answer in your own words, and use the model answers only as a check on the facts.

### Question 1: Why is Lambda cheaper than a virtual machine for this fetch?

:::answer Model answer
The fetch runs for about two seconds every 30 minutes, so the function is active for a tiny share of the month. Lambda bills only for the GB-seconds and requests used, so the monthly cost is a few hundred GB-seconds. A virtual machine is billed for every hour it is switched on, which is about 730 hours a month, and it needs patching even when idle. For this workload the pay-per-use model wins by a wide margin.
:::

### Question 2: Why does the function use an execution role instead of access keys?

:::answer Model answer
The execution role is an IAM role that Lambda assumes, and AWS gives the function temporary credentials for it. No long-term key is stored in the code, the environment or the repository, so there is nothing to leak. The role's policy allows only the actions the function needs, such as writing to the raw prefix. If the function's permissions must change, I edit the policy, not the code.
:::

### Question 3: What does the REPORT line tell you, and how do you use it?

:::answer Model answer
The REPORT line gives the duration, the billed duration, the memory size and the maximum memory used for one invocation. The billed duration times the memory is the cost driver, so it is the measured input to the calculator. The max memory used shows whether the memory setting is too large or too small. I compare these numbers across memory sizes before I choose one.
:::

### Question 4: Why should teardown delete the schedule before the function?

:::answer Model answer
If the function is deleted first, the scheduler keeps firing invocations at a target that no longer exists, and those failed attempts are noise in the logs and in the retry logic. Deleting the schedule first stops the trigger cleanly. The order is schedule, then function, then role, so each resource is removed before the thing it depends on. I also run the script as a dry run first, to check the list.
:::

### Question 5: How would you explain the break-even invocation count?

:::answer Model answer
The break-even count is the number of Lambda invocations at which the monthly Lambda cost equals the fixed monthly cost of the virtual machine. I find it by dividing the VM's monthly cost by the cost of one invocation, which I measure from the REPORT line. Below that count, Lambda is cheaper. Above it, the VM may be cheaper if the workload is steady and heavy. I would check the number against the calculator before I rely on it.
:::
