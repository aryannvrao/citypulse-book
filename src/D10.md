TITLE: Day 10 — Analytical SQL
SUB: You will be able to write JOIN, CTE, view and window-function queries in SQLite, run them from the terminal, and explain each one out loud.

## The idea in one minute

CityPulse stores every air-quality reading as one row in a database table. Clients ask questions about those rows: "Which hour of the day is worst for PM2.5 at each location?" or "What is the smoothed pollution trend at each station?" SQL is the language you use to ask. Think of it as a written request to a records clerk who knows where every file is. You say what you want, and the clerk returns a table of answers.

Today you will join tables together, name intermediate steps, save a query as a view, and use window functions to calculate rolling averages and changes over time. You will run each query from the terminal and check the output by hand.

## Starting from zero

This section explains the words the rest of the chapter depends on.

**Terminal.** The terminal is a text window where you type commands and the computer prints the answer. Every command you type is a single line, and you press Enter to run it.

**Command.** A command is an instruction you type into the terminal, such as `sqlite3`. The first word is the program name. The words after it are arguments, which tell the program what to work on.

**File.** A file is a named piece of stored text or data on your disk. The SQL files in this chapter end in `.sql`. The `.sql` part is only a convention that tells people and tools the file holds SQL.

**Database.** A database is a file that stores structured data in a form a program can query. CityPulse uses SQLite, which keeps the whole database in one file called `citypulse.db`. SQLite is a small database engine, and `sqlite3` is the program you run to talk to it.

**Table.** A table is a grid of data with named columns and numbered rows. A table called `reading` might have the columns `station_id`, `ts` and `value`.

**Row and column.** A row is one record, such as one reading. A column is one kind of value stored for every row, such as the time of the reading.

**SQL.** SQL stands for Structured Query Language. It is the language for asking databases questions. You write statements such as `SELECT`, which asks for rows, and `CREATE TABLE`, which makes a new table.

**Query.** A query is one SQL statement that asks the database for data. The answer comes back as a result table.

**Keyword.** A keyword is a word with a fixed meaning in SQL, such as `SELECT`, `FROM`, `WHERE` and `GROUP BY`. Keywords are not case-sensitive, but the convention is to write them in capitals so you can see where each clause starts.

**Function.** A function takes values in and gives one value back. `ROUND(x, 1)` takes a number and returns it rounded to one decimal place. `AVG(x)` is an aggregate function: it takes many rows and returns one average.

**Alias.** An alias is a temporary name you give a column or table with `AS`. `ROUND(AVG(value), 1) AS avg_value` shows the result under the name `avg_value`. An alias is also used for tables, as in `FROM fact_air_quality AS f`, which lets you write `f.pm2_5` instead of the full name.

**NULL.** NULL means "no value recorded". It is not zero and it is not an empty string. A sensor that failed to report has a NULL reading. Most functions ignore NULL, and comparisons such as `value = NULL` never match.

**GROUP BY.** GROUP BY collects rows that share a value into one group, and an aggregate function such as `COUNT(*)` then works per group. Ten readings for one station become one summary row.

**Subquery.** A subquery is a complete `SELECT` placed inside another query, usually inside brackets. The outer query then treats the subquery's result as if it were a table.

**Timestamp and time zones.** A timestamp is a date and time, such as `2026-03-01 08:00:00`. UTC is the world reference time. IST, Indian Standard Time, is UTC plus five hours and thirty minutes. CityPulse stores times in UTC and converts them to IST for reports. The number of minutes to add is written as `+330 minutes`.

**Sample size.** The number of readings behind an average. An average from 1 reading is much less reliable than an average from 500, so the answers in this course carry the count alongside the value.

## The tools

Today has three technologies: JOINs with CTEs, views, and window functions. All three run inside SQLite.

### JOINs and CTEs

**What it is.** A JOIN combines rows from two tables where a condition matches. CityPulse stores the readings in `fact_air_quality` and the location names in `dim_location`. The reading table holds `location_id`, a number, while the names live in the other table. A JOIN matches the two using that number.

A CTE is a named intermediate result, written with `WITH`. It lets a long query read as a sequence of named steps. The keyword `WITH` introduces the CTE, the name comes next, and the body is a `SELECT` in brackets.

**Why CityPulse uses it.** Every question about a location needs its name, so the readings must be joined to the location table. A CTE lets you calculate something once, such as the IST hour, and then aggregate it. The slides compare JOINs with nested subqueries, joins in pandas and a single wide table. Nested subqueries give the same result but are hard to review line by line. Pandas joins are fine for one-off analysis, but a SQL view keeps the answer inside the database, where the dashboard and the API can read it. A wide table avoids joins but gives up the integrity rules built in the earlier days.

**How it works.** The database takes each row of the fact table, finds the matching row in the location table by the integer key, and forms one combined row. Rows with no match are dropped in an inner JOIN. A LEFT JOIN keeps every row from the left table even when nothing matches on the right.

**The slide code, line by line.** This is the worst-hour query from the slides, with the indentation restored:

```sql
WITH hourly AS (
  SELECT l.name AS location,
         CAST(strftime('%H', f.ts_utc, '+330 minutes') AS INTEGER) AS hour_ist,
         f.pm2_5
  FROM fact_air_quality AS f
  JOIN dim_location AS l ON l.location_id = f.location_id
  WHERE f.pm2_5 IS NOT NULL
)
SELECT location, hour_ist, ROUND(AVG(pm2_5), 1) AS avg_pm25,
       COUNT(*) AS n
FROM hourly
GROUP BY location, hour_ist
ORDER BY avg_pm25 DESC
LIMIT 5;
```

- `WITH hourly AS (` starts a named step called `hourly`. The brackets hold its query.
- `SELECT l.name AS location` picks the name from the location table and calls it `location`. The `l.` prefix says which table the column comes from.
- `strftime('%H', f.ts_utc, '+330 minutes')` takes the timestamp, adds 330 minutes, and returns only the hour as text, such as `'08'`. The `%H` is the format code for a two-digit hour.
- `CAST(... AS INTEGER)` turns the text `'08'` into the number 8, so that hours sort as numbers.
- `f.pm2_5` passes the PM2.5 value through unchanged.
- `FROM fact_air_quality AS f` names the fact table and calls it `f`.
- `JOIN dim_location AS l ON l.location_id = f.location_id` matches each reading to its location using the integer key. The `ON` part is the matching condition.
- `WHERE f.pm2_5 IS NOT NULL` drops readings where the sensor reported nothing. You use `IS NOT NULL`, not `!= NULL`, because NULL never equals anything.
- The `)` closes the CTE. The outer `SELECT` then works on `hourly` as if it were a table.
- `GROUP BY location, hour_ist` makes one group per location and hour.
- `AVG(pm2_5)` averages the PM2.5 values in each group. `ROUND(..., 1)` keeps one decimal place.
- `COUNT(*)` counts the rows in each group and is the sample size `n`.
- `ORDER BY avg_pm25 DESC` sorts the highest averages first. `DESC` means descending.
- `LIMIT 5` returns only the first five rows.

The expected output is five rows, each showing a location, an IST hour, an average and a count. The exact numbers depend on the data loaded.

The slides also show a LEFT JOIN used for a coverage check. In `FROM dim_location AS l LEFT JOIN fact_air_quality AS f ON f.location_id = l.location_id`, every location appears even if it has no readings. The unmatched columns from the fact table are filled with NULL.

:::trap Filtering the right table in WHERE
If you filter the right-hand table of a LEFT JOIN in `WHERE`, the rows with no match are removed and the LEFT JOIN quietly becomes an inner JOIN. Put the condition on the right-hand table in the `ON` clause instead.
:::

:::trap Grouping by UTC hour
Grouping by the raw UTC hour gives the wrong "rush hour". Add `'+330 minutes'` before you extract the hour, as the query above does.
:::

:::trap Joining on the name
Joining on `name` instead of `location_id` breaks when a name is spelled differently or changed. Join on the integer key.
:::

The flow below shows what happens to one query. Read it as a pipeline: your text goes in, SQLite does the work, and rows come back.

```flow
TITLE: What happens when you run a query
NODES: Your query | SQLite engine | Result table
STEPS:
1>2 :: SELECT ... FROM ... JOIN :: The text of the query is handed to SQLite, which decides which tables to read and in what order. EXPLAIN QUERY PLAN shows that decision.
2>3 :: rows :: SQLite builds the rows of the answer and passes them out.
3>1 :: printed table :: The terminal prints the rows.
```

### Views

**What it is.** A view is a named `SELECT` stored in the database. You create it once with `CREATE VIEW`. Later, when you query the view, SQLite runs the stored `SELECT` on the current data. No copy of the rows is kept, so the answer stays up to date.

**Why CityPulse uses it.** Views turn one-off queries into an interface other parts of the system can reuse. The Y2-T14 ticket asks for eight named views beginning with `v_`. The defence, the dashboard and the API will all call those names. The slides compare views with three alternatives. Materialised summary tables are faster to read but must be refreshed and can go stale, and SQLite has no materialised views. Queries saved in a notebook are easy to run once but the dashboard cannot call them. Queries hard-coded in Python couple the SQL to the application code and hide it from SQL review.

**How it works.** A view is stored as text. When you query it, SQLite expands the stored `SELECT` and runs it as part of your query. Because the file `sql/views.sql` contains every view, it is the single source of truth for them.

**The slide code, line by line.** This is `v_coverage_by_location` from the slides:

```sql
-- Q: How many readings does each location have per IST day?
-- Who decides: ops lead decides which stations' numbers to trust.
-- IST: ts_utc + 330 minutes.
DROP VIEW IF EXISTS v_coverage_by_location;
CREATE VIEW v_coverage_by_location AS
SELECT l.name                          AS location,
       date(f.ts_utc, '+330 minutes')  AS day_ist,
       COUNT(f.fact_id)                AS n_readings
FROM dim_location AS l
LEFT JOIN fact_air_quality AS f ON f.location_id = l.location_id
GROUP BY l.name, day_ist;
-- check: SELECT * FROM v_coverage_by_location ORDER BY day_ist DESC LIMIT 5;
```

- Lines beginning with `--` are comments. SQLite ignores them. The comments state the client question, who relies on the answer, and the time zone rule. Writing them down is part of the deliverable.
- `DROP VIEW IF EXISTS v_coverage_by_location;` deletes the view if it already exists, and does nothing if it does not. This is what lets the whole file run again without an error.
- `CREATE VIEW v_coverage_by_location AS` creates the view with that name. Everything after `AS` is the stored query.
- `date(f.ts_utc, '+330 minutes')` adds 330 minutes to the UTC timestamp and returns only the date. That is the IST day.
- `COUNT(f.fact_id)` counts the non-NULL fact IDs in each group. For a location with no readings, the unmatched fact columns are NULL, so this count is 0.
- `FROM dim_location AS l LEFT JOIN fact_air_quality AS f` keeps every location, so locations with no data still appear.
- `GROUP BY l.name, day_ist` makes one row per location and IST day. The alias `day_ist` may be used here because SQLite accepts column aliases in `GROUP BY`.
- The final comment is a check you can run after creating the view. It shows the five most recent days.

The expected result of the check is up to five rows, each with a location, a day and a count. If a location with no data appears with `n_readings` equal to 0, the view is correct.

:::trap CREATE VIEW without DROP
`CREATE VIEW` without `DROP VIEW IF EXISTS` works the first time and fails the second time, because the view already exists. Always write the two as a pair.
:::

:::trap COUNT(*) in a LEFT JOIN
`COUNT(*)` counts the row itself, even when the row has no match. A location with no readings would show 1, which is wrong. Count a column from the right-hand table, such as `COUNT(f.fact_id)`, which counts only real matches.
:::

:::trap Views over views
A view built on another view built on another view can get slow. Run `EXPLAIN QUERY PLAN` on the slowest one. If the output says `SCAN` on a large table, an index may help. If it says `SEARCH` using an index, leave it alone.
:::

### Window functions

**What it is.** A window function calculates a value for each row by looking at a set of related rows. Unlike `GROUP BY`, it does not collapse the rows. Every reading keeps its own line in the output and gains an extra column.

A window function has three parts. `OVER` introduces it. `PARTITION BY` splits the rows into separate groups, one per location in CityPulse. `ORDER BY` sets the sequence of rows inside each group, usually time. A frame such as `ROWS BETWEEN 23 PRECEDING AND CURRENT ROW` then limits which rows are considered for each row.

**Why CityPulse uses it.** Health officers care about sustained exposure, measured as a 24-hour average, rather than single spikes. The Y2-T15 ticket needs a rolling 24-hour view and a day-over-day change view. The slides also note that the reference used to check the Python algorithm in a later ticket (Y2-T21) is a SQL rolling average of 6 hours. The slides compare window functions with self-joins on time ranges, which work but are verbose and slow on large tables, with pandas `rolling()`, which is great in a notebook but not available to every consumer, and with RANGE time windows, which handle gaps in time better but are harder to write. The team chose `ROWS` for the reference, and documents that choice.

**How it works.** For each reading, SQLite gathers the rows of the same partition, sorts them by time, keeps only the rows in the frame, and computes the aggregate. For the first few rows, the frame contains fewer rows than the full size. This is why a rolling average at the start of a series is based on fewer readings.

The flow below shows the idea as a moving part. A single pass over the table produces the window results, and the frame limits which neighbours each row can see.

```flow
TITLE: How a rolling window is computed
NODES: reading table | PARTITION BY | ROWS frame | Result row
STEPS:
1>2 :: split by station :: Rows are grouped so that each station is handled on its own.
2>3 :: sort by ts :: Inside one station, rows are put in time order.
3>4 :: last 3 rows :: The frame keeps the current row and the two rows before it, and AVG and COUNT are calculated over them. The row is returned with its extra columns intact.
```

The slide sequence is easiest to see as text output. The command below runs a saved script. The expected output is a table with the same rows as the input, each with a rolling average called `ma3`:

```term
$ sqlite3 -header -column citypulse.db < trends.sql
station_id ts                  value  ma3   rnk
---------- ------------------- -----  ----  ---
S1         2026-03-01 08:00:00 40.0   40.0  5
S1         2026-03-01 09:00:00 44.0   42.0  4
S1         2026-03-01 10:00:00 52.0   45.3  3
S1         2026-03-01 11:00:00 60.0   52.0  1
S1         2026-03-01 12:00:00 55.0   55.7  2
S2         2026-03-01 08:00:00 30.0   30.0  3
S2         2026-03-01 09:00:00 36.0   33.0  1
...
(8 rows)
```

- `sqlite3` runs the SQLite program.
- `-header` prints the column names as the first line of output.
- `-column` lines the output up in aligned columns, which is easier to read.
- `citypulse.db` is the database file to open.
- `<` is a redirect. It feeds the contents of `trends.sql` into `sqlite3` as if you had typed it, so SQLite runs the file.
- The output shows the rows from station S1 and then station S2, because the saved query ends with `ORDER BY station_id, ts`.
- The `...` line and the `(8 rows)` line show that the output is shortened here. The full run returns 8 rows.

The `ma3` column for the first row of S1 is 40.0 because it is the only row so far. Its second row, 42.0, is the average of 40.0 and 44.0, which is two rows, not three. This is the partial-window effect.

The step-through below shows the same idea in Python, which is easier to follow one line at a time. The code keeps a plain list and removes the oldest value when the list grows past three.

```trace
TITLE: Sliding a three-row window over Asha's scores
CODE:
scores = [60, 75, 90, 80, 70]
window = []
results = []
for score in scores:
    window.append(score)
    if len(window) > 3:
        window.pop(0)
    if len(window) == 3:
        results.append(round(sum(window) / 3, 2))
STEPS:
1 :: scores=[60, 75, 90, 80, 70] :: Five exam scores for Asha, in exam order.
2 :: scores=[60, 75, 90, 80, 70]; window=[] :: The window starts empty.
4 :: score=60; window=[]; results=[] :: The loop takes the first score.
5 :: score=60; window=[60]; results=[] :: The score joins the window.
8 :: score=60; window=[60]; results=[] :: Only one value, so the window is not full and nothing is stored.
4 :: score=75; window=[60]; results=[] :: The second score.
5 :: score=75; window=[60, 75]; results=[] :: Two values, still not full.
8 :: score=75; window=[60, 75]; results=[] :: Still not full, so nothing is stored.
4 :: score=90; window=[60, 75]; results=[] :: The third score.
5 :: score=90; window=[60, 75, 90]; results=[] :: The window now holds three values.
8 :: score=90; window=[60, 75, 90]; results=[] :: Full, so the average can be taken.
9 :: score=90; window=[60, 75, 90]; results=[75.0] :: (60 + 75 + 90) / 3 is 75.0, which is stored.
```

The loop only ever keeps the last three values, which is exactly what `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` means in SQL. The trace stops at the first full window. The remaining scores follow the same pattern.

:::trap Forgetting PARTITION BY
Without `PARTITION BY station_id`, the window runs across all stations in one long sequence. The last reading of S1 and the first reading of S2 would be averaged together. Always partition by the station.
:::

:::trap ROWS counts rows, not hours
`ROWS` counts rows. If a sensor misses two hours, `ROWS BETWEEN 23 PRECEDING AND CURRENT ROW` reaches back over 26 clock hours, not 24. The slides therefore expose `n_in_window`, the count of readings in the window, so that a short window can be seen.
:::

:::trap psql in older examples
Some examples in the reading show `psql`. That is the client for PostgreSQL, a different database. This course uses `sqlite3` and the `citypulse.db` file. The SQL is close, but the commands are not interchangeable.
:::

## The worked example

The worked example uses the course's 11-row sample. It has two stations, S1 and S2. S1 has five PM2.5 readings and one NO2 set of three readings. S2 has three PM2.5 readings. Times are stored in UTC.

The goal is to show why `GROUP BY` is not enough for a trend, and then to add a rolling average without losing a row.

**Step 1. Load the table.** The schema is a single `CREATE TABLE`. The first command creates the table and the second inserts the sample rows:

```bash
sqlite3 citypulse.db < schema.sql
sqlite3 citypulse.db < load.sql
```

The schema defines the table `reading` with four columns: `station_id` as text, `ts` as text holding an ISO timestamp, `pollutant` as text, and `value` as a real number, measured in micrograms per cubic metre.

**Step 2. Collapse with GROUP BY.** The query below averages each station and pollutant:

```sql
SELECT station_id, pollutant,
       ROUND(AVG(value), 1) AS avg_value,
       COUNT(*) AS n
FROM reading
GROUP BY station_id, pollutant
ORDER BY station_id, pollutant;
```

The output has three rows:

```text
station_id pollutant avg_value n
---------- --------- --------- -
S1         no2       21.7      3
S1         pm25      50.2      5
S2         pm25      33.0      3
```

The average for S1 PM2.5 is 50.2, which is the mean of 40, 44, 52, 60 and 55 (251 divided by 5). The eleven original rows have gone. You can answer "what is the average?" but not "how did the air change hour by hour?"

**Step 3. Keep the rows with a window.** Replace `GROUP BY` with a window function:

```sql
SELECT station_id, ts, value,
       ROUND(AVG(value) OVER (
         PARTITION BY station_id, pollutant
         ORDER BY ts
         ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
       ), 1) AS ma3
FROM reading
WHERE pollutant = 'pm25'
ORDER BY station_id, ts;
```

The output keeps every reading. For S1 the column `ma3` reads 40.0, 42.0, 45.3, 52.0 and 55.7. The 45.3 is the average of 40, 44 and 52. The 52.0 is the average of 44, 52 and 60. The 55.7 is the average of 52, 60 and 55, rounded to one decimal place.

**Step 4. Compare the bounded window with a running average.** The frame changes the answer. The query below puts a three-row window beside a cumulative average over the whole partition:

```sql
SELECT ts, value,
       ROUND(AVG(value) OVER w3, 1) AS ma3,
       ROUND(AVG(value) OVER wall, 1) AS cum_avg
FROM reading
WHERE pollutant = 'pm25' AND station_id = 'S1'
WINDOW w3 AS (ORDER BY ts ROWS BETWEEN 2 PRECEDING AND CURRENT ROW),
       wall AS (ORDER BY ts)
ORDER BY ts;
```

The first three rows of `ma3` and `cum_avg` are identical. From the fourth row, `cum_avg` lags behind the recent air, because it still carries the early, lower readings. In the output at 12:00, `ma3` is 55.7 and `cum_avg` is 50.2.

`WINDOW w3 AS (...)` gives the window a name. The name is used in `OVER w3`. The second window, `wall`, has no frame, so it covers all rows from the start up to the current row. The comma separates the two named windows.

**Step 5. Rank and compare with LAG.** The query below calculates the change from the previous hour and a rank of each reading inside its station:

```sql
SELECT station_id, ts, value,
       value - LAG(value) OVER w AS delta,
       RANK() OVER (PARTITION BY station_id ORDER BY value DESC) AS rnk
FROM reading
WHERE pollutant = 'pm25'
WINDOW w AS (PARTITION BY station_id ORDER BY ts)
ORDER BY station_id, ts;
```

For S1 at 11:00 the rank is 1 because 60.0 is the highest reading. The delta is 8.0 because 60.0 minus the previous value 52.0 is 8.0. The first row of each station has an empty delta because there is no earlier row to subtract. In SQLite, the empty cell is NULL.

**Step 6. Filter on the rank.** You cannot write `WHERE rnk = 1` in the same query, because `WHERE` runs before window functions are calculated. Wrap the ranked query in a subquery:

```sql
SELECT station_id, ts, value
FROM (
  SELECT station_id, ts, value,
         RANK() OVER (PARTITION BY station_id ORDER BY value DESC) AS rnk
  FROM reading
  WHERE pollutant = 'pm25'
)
WHERE rnk = 1
ORDER BY station_id;
```

The output has two rows: S1 at 11:00 with 60.0, and S2 at 09:00 with 36.0. These are the peak readings per station.

## The hands-on lab, step by step

The lab has seven steps. Do them in order, because each step uses the table or the query from the step before. Run every command from the folder that holds `citypulse.db` and your `.sql` files. To open that folder in the terminal, use the file manager's address bar or the `cd` command followed by the folder path.

### Step 1. Load a richer readings sample

**What you do.** Create the `reading` table and load the sample rows. If your instructor gives you a richer set of readings that spans several days, load that instead. The rest of the steps do not change, but the day-over-day changes in step 5 only show something when the data covers more than one day.

**What you type.**

```bash
sqlite3 citypulse.db < schema.sql
sqlite3 citypulse.db < load.sql
sqlite3 citypulse.db "SELECT COUNT(*) FROM reading;"
```

**What you should see.** The last command prints one number, `11`, for the course sample.

**How you know it worked.** The count matches the number of `INSERT` rows in `load.sql`. If the count is 0, the second command did not run, or it ran against a different file. If you see "no such table: reading", run the schema file first.

### Step 2. Order within each station

**What you do.** Read the PM2.5 readings in time order within each station, so that you can see the sequence the window functions will use.

**What you type.**

```sql
SELECT station_id, ts, value
FROM reading
WHERE pollutant = 'pm25'
ORDER BY station_id, ts;
```

**What you should see.** Eight rows. All the S1 rows come first, in time order from 08:00 to 12:00, then the S2 rows from 08:00.

**How you know it worked.** `ORDER BY station_id, ts` sorts by station first, and by time inside each station. If the S2 rows appear before S1, or the times are out of order, check that you typed `station_id, ts` in that order.

### Step 3. Compute a 3-point rolling average

**What you do.** Add a rolling average over the current reading and the two before it, inside each station.

**What you type.** Use the query from the worked example, step 3. Save it as `rolling.sql` and run it with `sqlite3 -header -column citypulse.db < rolling.sql`.

**What you should see.** S1 at 08:00 has `ma3` equal to 40.0, at 09:00 equal to 42.0, at 10:00 equal to 45.3, and at 11:00 equal to 52.0.

**How you know it worked.** The first row of each station equals its own value, because the window contains only that row. The S2 values start again at 08:00, which shows the partition is working.

### Step 4. Period-over-period change with LAG

**What you do.** Calculate the change from the previous reading in each station. This is the period-over-period change for hourly data. The same pattern on daily averages gives day-over-day change.

**What you type.**

```sql
SELECT station_id, ts, value,
       value - LAG(value) OVER (PARTITION BY station_id ORDER BY ts) AS delta
FROM reading
WHERE pollutant = 'pm25'
ORDER BY station_id, ts;
```

**What you should see.** S1 at 08:00 has an empty delta. S1 at 09:00 has 4.0, at 10:00 has 8.0, at 11:00 has 8.0, and at 12:00 has -5.0. S2 at 08:00 is empty and S2 at 09:00 has 6.0.

**How you know it worked.** The first row of each station is empty, because `LAG` has no earlier row to read. The 12:00 value is negative because the reading fell from 60.0 to 55.0.

### Step 5. Daily averages per station

**What you do.** Average the readings for each station on each day. The day must be the IST day, so add 330 minutes before taking the date.

**What you type.**

```sql
SELECT station_id,
       date(ts, '+330 minutes') AS day_ist,
       ROUND(AVG(value), 1) AS avg_value,
       COUNT(*) AS n
FROM reading
WHERE pollutant = 'pm25'
GROUP BY station_id, day_ist
ORDER BY station_id, day_ist;
```

**What you should see.** Two rows for the course sample: S1 on 2026-03-01 with average 50.2 and count 5, and S2 on 2026-03-01 with average 33.0 and count 3.

**How you know it worked.** The count column adds up to the number of PM2.5 rows in step 2, which is 8. If you grouped by `date(ts)` without the 330 minutes, the answer may look correct for this sample, but it breaks for readings made after 18:30 UTC, which fall on the next IST day.

### Step 6. Rank the most-polluted stations per pollutant

**What you do.** Average each station per pollutant, then rank the stations within each pollutant. Window functions run after `GROUP BY`, so the aggregate can be the input to the rank.

**What you type.**

```sql
SELECT pollutant, station_id,
       ROUND(avg_value, 1) AS avg_rounded,
       RANK() OVER (PARTITION BY pollutant ORDER BY avg_value DESC) AS rnk
FROM (
  SELECT station_id, pollutant, AVG(value) AS avg_value
  FROM reading
  GROUP BY station_id, pollutant
)
ORDER BY pollutant, rnk;
```

**What you should see.** Three rows. For `no2`, S1 with 21.7 and rank 1. For `pm25`, S1 with 50.2 and rank 1, then S2 with 33.0 and rank 2.

**How you know it worked.** Each pollutant restarts its rank at 1. The rank is calculated on the unrounded average, and rounding is applied only to the displayed value, which is good practice.

### Step 7. Keep only the worst per pollutant

**What you do.** Wrap the ranked query from step 6 in an outer query and keep only rank 1.

**What you type.**

```sql
SELECT pollutant, station_id, avg_rounded
FROM (
  SELECT pollutant, station_id,
         ROUND(avg_value, 1) AS avg_rounded,
         RANK() OVER (PARTITION BY pollutant ORDER BY avg_value DESC) AS rnk
  FROM (
    SELECT station_id, pollutant, AVG(value) AS avg_value
    FROM reading
    GROUP BY station_id, pollutant
  )
)
WHERE rnk = 1
ORDER BY pollutant;
```

**What you should see.** Two rows: `no2` at S1 with 21.7, and `pm25` at S1 with 50.2.

**How you know it worked.** Only one row per pollutant is returned. If you see S2 in the output, the filter `WHERE rnk = 1` is missing or misplaced. Check that it sits in the outer query, after the closing bracket of the subquery.

## What the quiz tests

The quiz is ten multiple-choice case-study questions. Your first attempt is the one that counts, so read each topic below before you start, and pay attention to the trap examiners set.

### Window frames

A window frame decides which rows around the current row are included in a window calculation. `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` means the current row and the two rows before it, counted by position. If you change the frame, every rolling number changes, even though the query still runs. The usual trap is to confuse the frame with the partition: `PARTITION BY` decides which groups exist, while the frame decides how many neighbours each row sees inside its group.

### Ranking functions

`ROW_NUMBER()`, `RANK()` and `DENSE_RANK()` all number rows inside a partition, but they treat ties differently. `ROW_NUMBER()` gives every row a unique number, and breaks ties arbitrarily unless the `ORDER BY` decides the tie. `RANK()` gives tied rows the same number and then skips numbers, so after two rows tied at 1 the next number is 3. `DENSE_RANK()` gives tied rows the same number without skipping. Examiners set the trap by giving tied values and asking for the next number.

### LAG and LEAD

`LAG(value)` returns the value from the previous row inside the partition, and `LEAD(value)` returns the value from the next row. The first row of a partition has no previous row, so `LAG` returns NULL there. The trap is the sign of a change: `value - LAG(value)` gives the current value minus the previous one, which is the usual change. Reversing the subtraction gives the same size of change with the wrong sign. `LEAD` looks forward in time, which is wrong for a change from the previous period.

### Window functions versus GROUP BY

`GROUP BY` produces one row per group. A window function produces one row per input row and keeps all of them. To attach each station's average to every reading, you use `AVG(value) OVER (PARTITION BY station_id)`. The trap is the query that uses `GROUP BY station_id` and then tries to list individual readings, which is not allowed unless the readings are also grouped.

### Top N per group

To keep the top N rows for each group, number the rows with `ROW_NUMBER()` inside a subquery, then filter `rn <= N` in the outer query. A window function cannot be placed in `WHERE` in the same query, so the subquery is required. The trap is using `ORDER BY ... LIMIT N` on the whole table, which gives the top N across all stations rather than N per station.

### The default frame

When a window has an `ORDER BY` and no frame, SQLite uses `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. That frame includes every row that ties with the current row on the ordering value. The trap is that two rows with the same timestamp both receive the total for both of them, not a separate running total. If you want a strict row-by-row running total, write `ROWS` explicitly.

### Percentiles

`PERCENT_RANK()` returns a value between 0 and 1 for each row, calculated as (rank minus 1) divided by (the number of rows minus 1). The lowest row gets 0 and the highest gets 1. `CUME_DIST()` returns the share of rows that are less than or equal to the current row, so the lowest row of 100 gets 0.01. The trap is confusing the two, which differ by one row at the bottom of the scale.

### RANGE and INTERVAL frames

A `RANGE` frame defines the window by the value of the ordering column rather than by the count of rows. Standard SQL can write a RANGE frame with an `INTERVAL`, such as one hour, but SQLite does not accept `INTERVAL` in a window frame. In SQLite, a `RANGE` frame works with a plain number when the ordering column is a number, such as Unix epoch seconds. The course uses `ROWS` for the reference, because `ROWS` is simpler to check by hand. The trap is to copy an `INTERVAL` frame from another database and expect it to run here.

### NTILE buckets

`NTILE(n)` divides the rows of a partition into `n` buckets and returns the bucket number for each row. When the rows do not divide evenly, the first buckets receive one extra row each. Ten rows in `NTILE(4)` give bucket sizes of 3, 3, 2 and 2. The trap is to assume each bucket holds the same number of rows, or to treat the bucket number as a value.

### Clause evaluation order

SQL processes a query in a fixed order: `FROM` and `JOIN` first, then `WHERE`, then `GROUP BY`, then `HAVING`, and then the window functions in the `SELECT` list. `ORDER BY` and `LIMIT` come after the windows. Because the window functions are calculated after `WHERE`, you cannot filter on a window result in the same `WHERE`. The trap is the query that puts `WHERE rnk = 1` beside the `RANK()` that defines `rnk`, which fails.

## The graded lab skill

The graded lab is a Python problem marked by visible tests and hidden tests. Hidden tests punish missed edge cases, so this section teaches the two techniques you need, and then sets a practice problem that uses the same skills.

### Running SQL from Python with sqlite3

Python has a built-in module called `sqlite3`. A module is a file of ready-made code that you load with `import`. Your code opens a connection to a database, runs SQL against it, and reads the rows.

The usual steps are these. You call `sqlite3.connect(":memory:")` to create a temporary database that lives only in memory and vanishes when the connection closes. You run `CREATE TABLE` to define the table. You load rows with `executemany`, which runs the same statement once for each row in a list. You run the query with `execute`, which returns a cursor. A cursor is an object you loop over to read result rows one at a time.

Placeholders are question marks. In `conn.execute(sql, (student,))`, the `?` in the SQL is replaced by the value in the tuple. Never build SQL by joining strings with user input, because that opens the door to SQL injection, where input changes the meaning of the query. Placeholders are safer and also handle quotes correctly.

### Top N per group with ROW_NUMBER

The pattern is always the same. You number the rows inside each group with `ROW_NUMBER() OVER (PARTITION BY group ORDER BY score DESC, tie_breaker ASC)`, and then keep the rows whose number is at most N in an outer query. The tie-breaker makes the choice repeatable. Without it, two rows with the same score may be numbered in either order.

### Rolling averages with ROWS BETWEEN

The pattern for a rolling average over N rows is `AVG(score) OVER (ORDER BY exam_no ROWS BETWEEN n-1 PRECEDING AND CURRENT ROW)`. For three exams, `n-1` is 2. Because the first rows of a series have fewer than three neighbours, you need a way to tell full windows from partial ones. A count of the rows in the same window does this. `COUNT(*) OVER (...)` with the same frame returns 1 for the first row, 2 for the second, and 3 from the third onwards.

### The practice problem

Write two functions. Both use SQL in an in-memory SQLite database and the Python standard library only.

The input is a list of rows, each one a tuple `(student, exam_no, score)`. Here `student` is text, `exam_no` is a whole number and `score` is a number.

1. `top_two_scores(rows)` returns a dictionary. Each key is a student and each value is a list of that student's top two scores, highest first. A student with only one score gets a list of one. An empty input returns an empty dictionary.
2. `rolling_three(rows, student)` returns a list of that student's rolling 3-exam averages in exam order, each rounded to 2 places. Only full windows count, so the first two exams produce no value. A student with fewer than three exams, or an unknown student, returns an empty list.

For example, if Asha has scores 60, 75, 90, 80 and 70 for exams 1 to 5, then `top_two_scores` gives `[90.0, 80.0]` for Asha, and `rolling_three` gives `[75.0, 81.67, 80.0]`.

### The edge-case checklist

Before you write any code, go through this list. Hidden tests check these cases.

- **Empty input.** `top_two_scores([])` must return `{}`, and `rolling_three([], "Asha")` must return `[]`. Your code must not crash on an empty table.
- **Fewer than two scores.** A student with one score must appear with a list of length one.
- **Ties.** If two scores tie for first place, both appear, because `ROW_NUMBER` with the tie-breaker numbers them 1 and 2. If a tie straddles second place, `ROW_NUMBER` keeps only one of the tied rows, so the list never has more than two scores. `RANK()` would keep every tied row. Think about which one the task wants before you choose.
- **Ordering.** Input rows may come in any order. Sort by `exam_no` inside the window, and do not rely on the order the rows were given.
- **Partial windows.** The first two exams of a student produce no rolling value. Use the count of rows in the window to decide.
- **Types.** Scores may be whole numbers or decimals. Make sure the output uses decimal values, such as `90.0`, if the test compares with `90.0`.
- **Rounding.** Round in SQL with `ROUND(x, 2)` so that the result matches the database. Python's `round` can behave differently on values that end exactly in 5.
- **Missing values.** A NULL score is not a score. Decide whether to exclude it with `WHERE score IS NOT NULL`, and do the same in the count, so that a window containing a NULL is not treated as full.
- **Unknown names.** A student who is not in the data must give an empty result, not an error.

:::answer Model solution
The test block below is run automatically when the book is built. It must pass without errors.

```python test
import sqlite3


def make_db(rows):
    conn = sqlite3.connect(":memory:")
    conn.execute(
        "CREATE TABLE exam_score (student TEXT, exam_no INTEGER, score REAL)"
    )
    conn.executemany("INSERT INTO exam_score VALUES (?, ?, ?)", rows)
    return conn


def top_two_scores(rows):
    conn = make_db(rows)
    sql = """
        SELECT student, score
        FROM (
            SELECT student, score,
                   ROW_NUMBER() OVER (
                       PARTITION BY student
                       ORDER BY score DESC, exam_no ASC
                   ) AS rn
            FROM exam_score
        )
        WHERE rn <= 2
        ORDER BY student, score DESC
    """
    result = {}
    for student, score in conn.execute(sql):
        result.setdefault(student, []).append(score)
    conn.close()
    return result


def rolling_three(rows, student):
    conn = make_db(rows)
    sql = """
        SELECT exam_no, ROUND(avg_3, 2)
        FROM (
            SELECT exam_no,
                   AVG(score) OVER (
                       ORDER BY exam_no
                       ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
                   ) AS avg_3,
                   COUNT(*) OVER (
                       ORDER BY exam_no
                       ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
                   ) AS n_in_window
            FROM exam_score
            WHERE student = ?
        )
        WHERE n_in_window = 3
        ORDER BY exam_no
    """
    values = [row[1] for row in conn.execute(sql, (student,))]
    conn.close()
    return values


rows = [
    ("Asha", 1, 60.0), ("Asha", 2, 75.0), ("Asha", 3, 90.0),
    ("Asha", 4, 80.0), ("Asha", 5, 70.0),
    ("Ravi", 1, 88.0), ("Ravi", 2, 88.0), ("Ravi", 3, 50.0),
    ("Meena", 1, 95.0),
]

top = top_two_scores(rows)
assert top["Asha"] == [90.0, 80.0]
assert top["Ravi"] == [88.0, 88.0]
assert top["Meena"] == [95.0]
assert top_two_scores([]) == {}

assert rolling_three(rows, "Asha") == [75.0, 81.67, 80.0]
assert rolling_three(rows, "Ravi") == [75.33]
assert rolling_three(rows, "Meena") == []
assert rolling_three(rows, "Nobody") == []
```

**Explanation, line by line.**

- `import sqlite3` loads the standard library module for SQLite. No installation is needed.
- `make_db` opens a fresh in-memory database for each call, so the tests never share state. `":memory:"` is a special name that means "keep the database in memory only".
- `CREATE TABLE exam_score (...)` defines three columns. `REAL` stores decimal numbers.
- `executemany` inserts every tuple in `rows`. Each `?` takes one value from the tuple.
- In `top_two_scores`, the inner query numbers each student's scores from highest to lowest. `PARTITION BY student` restarts the numbering for each student. `ORDER BY score DESC, exam_no ASC` puts the highest score first and breaks ties by the earlier exam, so the result is repeatable.
- `WHERE rn <= 2` in the outer query keeps the top two for each student. This is why Ravi's two 88s are both returned: they are numbered 1 and 2.
- The loop turns the rows into a dictionary. `setdefault` creates an empty list the first time a student appears, and `append` adds each score to it. The outer `ORDER BY student, score DESC` gives the lists highest first.
- In `rolling_three`, `WHERE student = ?` filters to one student before the windows are calculated, so the window never sees another student's scores.
- `AVG(score) OVER (ORDER BY exam_no ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)` is the rolling average. `COUNT(*)` with the same frame counts the rows in the window.
- The outer `WHERE n_in_window = 3` keeps only full windows. This is the rule that the first two exams produce no value.
- `ROUND(avg_3, 2)` rounds in SQL. The loop keeps `row[1]`, which is the rounded value, because `row[0]` is the exam number.
- The assertions check the main case, a tie, a student with one score, empty input, a student with too few exams, and an unknown name. An `assert` that fails stops the build with an error, which is what the course relies on.

**Expected result.** The file runs without printing anything when every assertion passes. If an assertion fails, Python shows the line number and the values it compared.

## Say it out loud

Interviewers and viva examiners ask these questions to see whether you understand the query, not just whether you can run it. Answer in your own words, and use the words you have seen in this chapter.

:::answer Why use a window function instead of GROUP BY for a trend?
A `GROUP BY` collapses each station into one row, so you lose the timeline that a trend needs. A window function calculates a value for each reading using its neighbours, and keeps every row. For CityPulse, that means each reading can carry a smoothed value next to its raw value. The frame decides how many neighbours are used.
:::

:::answer What does PARTITION BY do, and what goes wrong without it?
`PARTITION BY` splits the rows into separate groups, and the window is calculated inside each group only. In CityPulse the partition is the station and pollutant, so readings from different stations never mix. Without it, the window runs across the whole table in one sequence, and the last reading of one station is averaged with the first reading of another.
:::

:::answer Why does the view expose n_in_window?
A rolling average near the start of a series is based on fewer readings than its label suggests. Also, `ROWS` counts rows rather than hours, so a missing hour stretches the window over more time. Exposing the count tells the dashboard and the reader how many readings sit behind each value, so a partial or gappy window can be flagged.
:::

:::answer Why can you not filter on a window result in WHERE?
SQL evaluates `WHERE` before window functions are calculated. At the point `WHERE` runs, the rank or the rolling average does not yet exist. To keep only rows with rank 1, you calculate the rank in a subquery or CTE, and then filter on it in the outer query. This pattern is the standard way to get the top N per group.
:::

:::answer Why does the reference for the Python algorithm use ROWS rather than RANGE?
`ROWS` counts a fixed number of readings, so the window size is easy to check by hand and identical in every database. `RANGE` defines the window by time, which handles gaps correctly, but it is harder to write and not supported in the same way everywhere, and SQLite does not accept `INTERVAL` in a frame. The course accepts the gap problem and documents the choice, so that the Python result can be compared with the SQL result on the same definition.
:::
