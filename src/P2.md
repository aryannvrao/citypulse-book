## What you are building

You are building a small service that watches hourly PM2.5 readings from four air-quality stations. PM2.5 is the amount of very fine dust in the air, measured in micrograms per cubic metre. When a station suddenly reports a value far above its own recent normal, the service flags it as a spike.

A team member opens a web page. The page shows a bar chart of each station's average reading and a table of the confirmed spikes, with the largest value highlighted. They can ask the service whether a new reading at a given station would breach that station's limit. For each spike, a small language model writes one plain sentence that says what happened and what residents should do.

Every push to the main branch of the code repository runs the tests. If they pass, the service is rebuilt and published automatically. You do not start any of these steps by hand.

## The architecture

Data moves through the project in one direction. Each file handles one job, and each job's output is the next job's input.


## Starting from zero

**The terminal.** The terminal is a text window where you type commands and the computer prints the results. In this book, a line that starts with `$` is something you type. The lines under it are what the computer prints. A command is a program name followed by options, called flags, that change how it behaves. Flags usually start with one or two dashes, such as `-q` or `--reload`.

**Python, pip and packages.** Python is the programming language used throughout the project. A package is a ready-made library that someone else wrote and published. `pip` is the tool that downloads packages from the Python Package Index. A file named `requirements.txt` lists the packages a project needs, and `pip install -r requirements.txt` installs everything in it. The `-r` flag means "read the list from this file".

**Files, folders and CSV.** A file is a named block of data stored on disk. A folder holds files. CSV stands for comma-separated values. A CSV file is plain text where each line is a row and commas separate the columns. The first line normally holds the column names.

**pandas and the DataFrame.** pandas is a library for working with tables. Its main object is the DataFrame, a table held in memory with named columns. Each row also has an index label. You will use DataFrames to read the CSV, filter rows, add columns and group values by station. The earlier Day chapter on pandas covers this in depth.

**Statistics you need.** The median is the middle value when a list is sorted. The mean is the average. The standard deviation measures how spread out values are. A quantile is the value below which a given share of the data falls; the 0.25 quantile is the first quartile, Q1, and the 0.75 quantile is Q3. The interquartile range, IQR, is Q3 minus Q1. The median absolute deviation, MAD, is the median of the distances from the median. Unlike the mean and standard deviation, the median and MAD are not pulled around by one extreme value.

**SQL, SQLite and window functions.** SQL is the language for asking questions of a database. SQLite is a small database that lives in one file, or in memory with no file at all. A window function calculates a value for each row using a set of neighbouring rows called the window. `PARTITION BY` splits the rows into groups, such as one group per station. `ORDER BY` sets the order inside each group. `ROWS BETWEEN` picks which neighbouring rows count.

**scikit-learn and IsolationForest.** scikit-learn is a free library of machine-learning tools. Machine learning means letting a program find patterns in data rather than writing every rule by hand. An IsolationForest is a model that finds unusual points. It works by splitting the data at random many times. Unusual points get isolated after fewer splits, and the model turns that into a score.

**HTTP, endpoints, JSON and FastAPI.** HTTP is the protocol a browser and a server use to talk. A client sends a request, such as `GET /anomalies`, and the server returns a response. An endpoint is a path that the server answers, such as `/anomalies`. JSON is a text format for structured data, made of keys and values in curly braces and square brackets. FastAPI is a Python library that turns functions into endpoints. Pydantic is the library FastAPI uses to check incoming data against a declared shape. uvicorn is the server program that runs the FastAPI app and listens for requests on a port, which is a numbered door on the computer. Port 8000 is the one this project uses.

**Language models on a CPU.** A language model generates text one piece at a time. The pieces are called tokens. A transformer is the neural network design behind most modern models. The transformers library, from Hugging Face, loads these models. torch is the numerical library the models run on. CPU means the central processor of your computer, as opposed to a graphics card. The project uses Qwen2.5-0.5B-Instruct, a small model that is free to download and runs on a CPU, though slowly.

**Streamlit and matplotlib.** Streamlit turns a Python script into a web page with titles, tables and charts, without any web programming. matplotlib is a plotting library. It draws a figure and can save it as a PNG image file.

**pytest and assert.** pytest is a test runner. It finds functions whose names begin with `test_` and runs them. Inside a test, `assert` is a statement that checks a condition. If the condition is false, the test fails. A TestClient is a helper that sends requests to a FastAPI app inside the test, so no real server needs to run.

**Git, GitHub and Actions.** Git records the history of a project's files as commits. A push sends your commits to a shared copy on GitHub. GitHub Actions runs jobs on GitHub's machines when an event happens, such as a push. The jobs are described in a YAML file. YAML is a text format that uses indentation to show structure, so spaces matter. A secret is a value, such as a password, stored in GitHub and passed to a job without appearing in the file.

**Docker, images and containers.** A Docker image is a packed snapshot of an app and everything it needs. A container is a running copy of an image. A Dockerfile is the text recipe that builds an image, one instruction per line.

**curl and jq.** curl sends HTTP requests from the terminal. jq reads JSON and prints parts of it. You will use both to check the API without a browser.

## The tools

### pandas: cleaning and aggregating

pandas is the right tool here because the data is a table of 675 rows that needs filtering, typing and grouping. Writing those loops by hand in plain Python is slower and easier to get wrong. The alternatives are a spreadsheet, which you cannot test automatically, and a database, which adds setup for a file this small.

The cleaner in `pipeline.py` is the most important function in Part A:

```python
def load(path="data/readings.csv"):
    df = pd.read_csv(path)
    df["ts"] = pd.to_datetime(df.ts, errors="coerce")
    df = df[df.station_id.isin(STATIONS)]
    df = df[df.value.between(0, 500)]
    df = df.dropna(subset=["ts"]).drop_duplicates(
        ["station_id","ts","pollutant"])
    return df.sort_values(["station_id","ts"])
```

`def load(path="data/readings.csv"):` defines a function called `load`. Its single argument, `path`, has a default value, so calling `load()` reads the standard file. `pd.read_csv(path)` reads the file into a DataFrame, which is stored in `df`. Each row becomes a row in the table, and the first line of the file supplies the column names.

`df["ts"] = pd.to_datetime(df.ts, errors="coerce")` converts the text in the `ts` column into real date-and-time values. `errors="coerce"` turns anything it cannot read into a special empty value, `NaT`, instead of stopping the program.

`df = df[df.station_id.isin(STATIONS)]` keeps only rows whose station is in the known list `STATIONS`. The square brackets select rows that match a condition. `isin` checks membership.

`df = df[df.value.between(0, 500)]` keeps rows whose value is from 0 to 500 inclusive. A negative or enormous reading cannot be a real measurement.

`df = df.dropna(subset=["ts"])` removes rows where the timestamp is empty. `.drop_duplicates([...])` then removes repeated rows that have the same station, time and pollutant. Method calls can be chained with dots, and the result of each call is passed to the next.

`return df.sort_values(["station_id","ts"])` sorts by station first, then by time. This order matters for the SQL step later.

:::trap Sorting is not optional
The SQL window in Step 6 assumes readings are in time order inside each station. If `sort_values` is removed, the rolling baselines will mix up neighbouring hours without any error message. Your tests may still pass, which is why the sort needs to stay in the function.
:::

### SQLite window functions: rolling baselines

The baseline for a reading is the average of the six hours before it, per station. SQL window functions are the right tool, because they compute this for every row in one query, and the same query can be read and explained by anyone who knows SQL. A Python loop would be longer and easier to get wrong at the start of each station.

```sql
SELECT station_id, ts, value,
  AVG(value) OVER w AS roll_mean,
  COUNT(*)   OVER w AS win_n
FROM readings
WINDOW w AS (PARTITION BY station_id ORDER BY ts
  ROWS BETWEEN 6 PRECEDING AND 1 PRECEDING)
```

`SELECT` lists the columns to return. `AVG(value) OVER w` computes the average of `value` over the window named `w`. `AS roll_mean` names the result. `COUNT(*) OVER w AS win_n` counts how many rows the window contained, which tells you whether the baseline is based on a full six hours.

`WINDOW w AS (...)` defines the window once, so both functions can reuse it. `PARTITION BY station_id` restarts the calculation for each station, so a station never borrows another station's readings. `ORDER BY ts` puts each station's readings in time order.

`ROWS BETWEEN 6 PRECEDING AND 1 PRECEDING` says the window is the six rows before the current one, and it stops at the row immediately before. The current row is excluded. That exclusion is the key design point. If the current reading were included, a large spike would raise its own baseline and partly hide itself.

:::trap The first readings have a short window
The first row of each station has no earlier rows, so its `roll_mean` is empty (NULL) and `win_n` is 0. The second row has one earlier row, and so on until the seventh row, the first with a full six. Code that assumes `win_n` is always 6 will give wrong results near the start of each station.
:::

### pandas and statistics: the robust z-score and the IQR fence

A plain z-score measures how many standard deviations a value sits from the mean. The problem is that the spike being searched for also inflates the mean and the standard deviation, so it partly hides itself. The robust version uses the median and the MAD, which a single spike barely moves. The IQR fence is a second, independent test: a value must sit above Q3 plus 1.5 times the IQR. Requiring both tests keeps out noise that is only slightly high.

```python
grp = r.groupby("station_id")["value"]
med = grp.transform("median")
mad = grp.transform(lambda s:
        (s-s.median()).abs().median()) + 1e-6
r["z"] = (0.6745*(r.value-med)/mad).round(2)
q1,q3 = grp.transform(lambda s:s.quantile(.25)),\
        grp.transform(lambda s:s.quantile(.75))
r["iqr_hi"] = (q3 + 1.5*(q3-q1)).round(1)
r["stat_flag"] = (r.z>=3) & (r.value>r.iqr_hi)
```

`grp = r.groupby("station_id")["value"]` splits the readings into one group per station and selects the `value` column. Nothing is calculated yet. `grp` is a recipe for the next steps.

`med = grp.transform("median")` computes each station's median and puts it on every row of that station. `transform` returns a result the same length as the original table, which is why it can be stored as a new column.

`mad = grp.transform(lambda s: ...) + 1e-6` computes the MAD for each station. The `lambda` is a small unnamed function. Inside it, `s` is one station's values, `(s-s.median()).abs()` is each distance from the median, and `.median()` of those distances is the MAD. `+ 1e-6` adds 0.000001 so the division below never divides by zero.

`r["z"] = (0.6745*(r.value-med)/mad).round(2)` computes the robust z-score. The constant 0.6745 rescales the MAD so the result is comparable to a normal z-score. `round(2)` keeps two decimal places.

`q1,q3 = ...` computes the first and third quartiles per station. The backslash at the end of the line tells Python the statement continues on the next line.

`r["iqr_hi"] = (q3 + 1.5*(q3-q1)).round(1)` computes the upper fence for each station.

`r["stat_flag"] = (r.z>=3) & (r.value>r.iqr_hi)` marks a reading when both tests fire. The `&` operator combines two columns of true and false values, one answer per row. The brackets are required because `&` binds more tightly than `>=`.

:::trap Use & and not and
Writing `(r.z>=3) and (r.value>r.iqr_hi)` raises `ValueError: The truth value of a Series is ambiguous`. The word `and` works on single values; a column holds many values, so pandas needs the element-wise `&` and the brackets around each test.
:::

Here is the robust z-score calculated on five readings for one station. These numbers are invented for this explanation so you can follow each step. They are not course output.

```trace
TITLE: One station's robust z-score
CODE:
import statistics
vals = [50, 52, 49, 51, 180]
med = statistics.median(vals)
dev = [abs(v - med) for v in vals]
mad = statistics.median(dev) + 1e-6
z = 0.6745 * (180 - med) / mad
is_spike = z >= 3
STEPS:
1 :: (no variables yet) :: The statistics module provides median, so it is imported first.
2 :: vals=[50, 52, 49, 51, 180] :: The five readings of one station are stored in a list.
3 :: vals=[50, 52, 49, 51, 180]; med=51 :: The middle value of the sorted list (49, 50, 51, 52, 180) is 51.
4 :: vals=[50, 52, 49, 51, 180]; med=51; dev=[1, 1, 2, 0, 129] :: Each reading's distance from the median. The 180 is 129 away.
5 :: vals=[50, 52, 49, 51, 180]; med=51; dev=[1, 1, 2, 0, 129]; mad=1.000001 :: The median of the distances is 1. Adding 1e-6 means the division never divides by zero.
6 :: vals=[50, 52, 49, 51, 180]; med=51; mad=1.000001; z=87.0 :: 0.6745 rescales the result, and the spike sits 87 robust units above the median.
7 :: vals=[50, 52, 49, 51, 180]; med=51; mad=1.000001; z=87.0; is_spike=True :: 87.0 is at least 3, so the statistical test fires for this reading.
```

Notice that the spike did not change the median or the MAD much. A plain mean would have been pulled up to 76.4 by the single 180, and a standard deviation would have been inflated the same way. That is the whole reason for the robust version.

### scikit-learn: IsolationForest as the second opinion

The statistical test looks at each value against its own station. The IsolationForest looks at the whole picture, using two features: the value itself and how far it sits above the rolling baseline. Two methods that work in different ways, when they agree, are much stronger evidence than either one alone. The IsolationForest is the right second method for this job because it needs no hand-written thresholds for the second feature. The `contamination` setting tells it how rare anomalies are expected to be.

:::tip Explain why the two methods differ
In a viva, say that the z-score and IQR fence use only per-station distributions, while the IsolationForest sees the joint pattern of value and deviation. Then say why requiring agreement lowers false alarms.
:::

**Step 2: Ingest readings with real spikes.** The goal is a dataset where you know exactly which spikes exist, so you can test the detector against them. The script writes 168 hourly readings for each of four stations, which is seven days, and it injects four spikes.

```python
SPIKES = {("ST-04",44):3.2, ("ST-01",92):2.8,
          ("ST-02",93):2.9, ("ST-03",140):3.5}
for h in range(168):                 # 7 days, hourly
    rush = 1.3 if 6<=h%24<=10 or 17<=h%24<=21 else 0.8
    for s,base in STATIONS.items():
        val = base + 8*gauss(1,.2)*rush + gauss(0,4)
        val *= SPIKES.get((s,h), 1.0)   # inject spike
        rows.append([s, ts, "pm25", round(val,1)])
```

`SPIKES` is a dictionary. A dictionary maps keys to values inside braces. Each key here is a pair `(station, hour)`, written in round brackets, and each value is the multiplier for that reading. The spike at ST-04 hour 44 multiplies the normal reading by 3.2.

`for h in range(168):` repeats the inner code for hour numbers 0 to 167. `range(168)` stops before 168, so it gives exactly 168 hours.

`rush = 1.3 if ... else 0.8` sets a rush-hour multiplier. `h%24` is the remainder when `h` is divided by 24, which gives the hour of the day. The condition `6<=h%24<=10` is a chained comparison and means the hour is from 6 to 10 inclusive. The `or` joins the morning and evening rush periods.

`for s,base in STATIONS.items():` loops over each station. `STATIONS` is a dictionary that maps each station id to its normal base level. The excerpt does not show how `STATIONS`, `rows` and `ts` are created. Take those lines from the workbook.

`val = base + 8*gauss(1,.2)*rush + gauss(0,4)` builds a random reading. `gauss(mean, spread)` draws a random number from a bell curve, so the readings look like real noise.

`val *= SPIKES.get((s,h), 1.0)` multiplies the reading by the spike factor if there is one. `.get` returns the default, 1.0, when the key is missing, so most readings are unchanged.

`rows.append([...])` adds one row to the list `rows`.

### Part B: Detect the spikes

**Step 6: Rolling baselines with SQL windows.** The goal is to load the clean data into SQLite and compute each reading's trailing six-hour average. The window was explained above. The excerpt does not show the lines that create the connection `con` and load the data into a table named `readings`. Those lines are needed before the query runs.

```python
ROLL_SQL = '''
SELECT station_id, ts, value,
  AVG(value) OVER w AS roll_mean,
  COUNT(*)   OVER w AS win_n
FROM readings
WINDOW w AS (PARTITION BY station_id ORDER BY ts
  ROWS BETWEEN 6 PRECEDING AND 1 PRECEDING)'''
out = pd.read_sql(ROLL_SQL, con)
```

`ROLL_SQL = '''...'''` stores a multi-line text in a variable. Three single quotes start and end a multi-line string. `pd.read_sql(ROLL_SQL, con)` sends the query to the database through the connection `con` and returns the result as a DataFrame called `out`.

**Step 9: Cross-check with IsolationForest.** The goal is a second, model-based flag, and a rule that only confirms a spike when both methods agree.

```python
feats = r[["value"]].assign(
    dev = r.value - r.roll_mean)
iso = IsolationForest(contamination=0.02,
        random_state=11).fit(feats)
r["iso_flag"] = iso.predict(feats) == -1
r["anomaly"]  = r.stat_flag & r.iso_flag
```

`feats = r[["value"]].assign(dev = ...)` builds a table with two features. The double square brackets select a column as a table, not as a single series, which the model expects. `assign` adds the `dev` column, the reading's distance above its rolling baseline.

`IsolationForest(contamination=0.02, random_state=11)` creates the model. `contamination=0.02` tells it to expect about 2 per cent of readings to be unusual. `random_state=11` fixes the random choices inside the model, so the same data always gives the same result. `.fit(feats)` learns from the data.

`iso.predict(feats)` returns 1 for normal and -1 for unusual. `== -1` turns that into true and false. `r.stat_flag & r.iso_flag` sets `anomaly` only when both are true.

The model flags 13 readings. The check is simple arithmetic: 2 per cent of 672 is 13.4, so 13 is what contamination predicts. The model casts a wider net than the statistics, and the `&` keeps only the four readings that both methods agree on.

**Step 11: The API skeleton.** The goal is an app with a health endpoint that reports the anomaly count, and a Pydantic model for checked input.

```python
app = FastAPI(title="CityPulse Anomaly Detector")

_anom = anomalies(_df)

    station_id: str = Field(pattern=r"^ST-0[1-4]$")
    value: float = Field(ge=0, le=500)

```

`app = FastAPI(title=...)` creates the application. The title appears in the automatic documentation. `_df = load()` and `_anom = anomalies(_df)` run once when the file is loaded. The leading underscore is a convention meaning "private to this file".

`class CheckIn(BaseModel):` defines the shape of a valid request. A class is a blueprint for an object with named fields. `BaseModel` is Pydantic's base class.

`station_id: str = Field(pattern=r"^ST-0[1-4]$")` says the field is text and must match a pattern. The pattern `^ST-0[1-4]$` means: start with `ST-0`, then one digit from 1 to 4, then the end. The `r` before the string means a raw string, so the backslashes in a pattern are not treated as escape characters. `value: float = Field(ge=0, le=500)` says the value is a decimal number from 0 to 500. `ge` means greater than or equal to, and `le` means less than or equal to.

`@app.get("/health")` is a decorator. It tells FastAPI that the function below answers GET requests to `/health`. `return {...}` returns a dictionary, which FastAPI sends as JSON.

`uvicorn main:app` means "run the object called `app` inside the file `main.py`". `--reload` restarts the server whenever you save a change, which is convenient while you work. The line ending in `200 OK` proves a request was answered successfully. Status 200 means success.

**Step 13: Live spike check, with validation.** The goal is an endpoint that accepts a new reading for a station and says whether it would breach that station's fence.

```python
@app.post("/check")
def check(c: CheckIn):
    s = _scored[_scored.station_id==c.station_id]
    hi = float(s.iqr_hi.iloc[-1])
```

`@app.post("/check")` answers POST requests, which carry data in the body. The parameter `c: CheckIn` tells FastAPI to read the body, check it against the model, and pass it in as `c`. If the check fails, the function never runs.

`bool(c.value > hi)` compares the value to the fence and converts the answer to plain True or False, which JSON can represent.

### Part D: Explain the spikes

**Step 14: Explain anomalies with a free CPU language model.** The goal is one plain-English sentence per spike, grounded in the real numbers.

```python
tok = AutoTokenizer.from_pretrained(M)
llm = AutoModelForCausalLM.from_pretrained(M)
def explain(station, value, roll_mean, z):
    msgs=[{"role":"system","content":"Analyst. "
      "ONE sentence: explain the spike, advise."},
     {"role":"user","content":f"{station} PM2.5 hit "
      f"{value}, ~{value/roll_mean:.1f}x its {roll_mean} "
      f"average (z={z})."}]
    ids = tok(tok.apply_chat_template(msgs,
      tokenize=False, add_generation_prompt=True),
      return_tensors="pt")
    out = llm.generate(**ids, max_new_tokens=48)
    return tok.decode(out[0][ids.input_ids
      .shape[1]:], skip_special_tokens=True)
```

`AutoTokenizer.from_pretrained(M)` downloads and loads the tokenizer, which converts text into token numbers. `AutoModelForCausalLM.from_pretrained(M)` loads the model that generates text. `M` holds the model's name. The excerpt does not show its value; the course names it as Qwen2.5-0.5B-Instruct. Both lines run once at import time, so the model is loaded once and reused.

`msgs` is a list of messages in chat format. The `system` message tells the model its role and the rule, one sentence. The `user` message contains the numbers. The f-string, written `f"..."`, puts the variables into the text. `{value/roll_mean:.1f}` divides the two numbers and formats the result with one decimal place.

`tok.apply_chat_template(...)` wraps the messages in the special markers the model was trained to expect. `add_generation_prompt=True` adds the marker that means "the assistant speaks next". `return_tensors="pt"` returns PyTorch tensors, which the model needs.

`llm.generate(**ids, max_new_tokens=48)` produces the reply. `**ids` unpacks the tokenised input as keyword arguments. `max_new_tokens=48` caps the reply at 48 new tokens, which keeps generation short on a CPU.

`out[0][ids.input_ids.shape[1]:]` removes the prompt from the output. `ids.input_ids.shape[1]` is the length of the prompt, and the slice keeps only what comes after it. `tok.decode(..., skip_special_tokens=True)` turns the tokens back into text and removes the markers.

```term
$ python explain.py
ST-04 215.6: Residents should monitor PM2.5 levels
  closely; it spiked to 215.6 ug/m3, ~3.1x the
  recent 68.5 average.
ST-03 180.5: Residents should monitor PM2.5 levels
  closely; it spiked to 180.5 ug/m3, ~3.9x the
  recent 45.9 average.
```

Check the arithmetic in the output. 215.6 divided by 68.5 is 3.15, which rounds to 3.1. 180.5 divided by 45.9 is 3.93, which rounds to 3.9. The numbers in the reply come from the prompt, so they are reliable. The wording does not come from the data, and a model can drift from the facts. That is why the numbers should always be checked against the API, and why the sentence is treated as explanation, not detection.

:::trap The model explains; it does not detect
The language model never decides whether a reading is a spike. Detection is done by Part B. If you let the model decide, the alerts depend on the model's mood on the day. Keep the decision in code and use the model only for wording.
:::

**Step 19: CD: build, push and deploy.** The goal is a second job that runs only when tests pass, builds the image, pushes it to a registry, and deploys it.

The line `echo "${{ secrets.REGISTRY_TOKEN }}"` prints the token into the step's log. GitHub masks secrets it knows about, but the safer habit is to pass the secret straight to `docker login` without echoing it. ## The Part G challenges

Each challenge below has a "Done when" test. That test is the marking standard, so read it carefully before you start. The plans give you a route and the reasoning. Write the code yourself.

### Challenge 1: Add a severity column (data, easy)

**What is asked.** In `detect.py`, add a severity value, defined as the reading divided by the rolling mean, to the anomaly table. Sort the output so the highest severity comes first.

**Done when.** "Done when: detect.py prints the 4 spikes ordered by severity, highest first."

**Ideas you need.** Column arithmetic in pandas, `sort_values` with `ascending=False`, and the fact that `anomalies` returns a table you can modify before it is printed.

**Plan of attack.**

1. Open `detect.py` and find where `anomalies` selects its columns. Decide whether severity must be computed before or after the `anomaly` filter.
2. Compute severity as a new column from `value` and `roll_mean`. Watch the first reading of each station, where `roll_mean` is empty, and make sure it cannot crash the sort.
3. Add severity to the list of columns that are kept and rounded.
4. Sort the result by severity, descending. Check the sort direction by reading the printed order, not by trusting the code.
5. Run `python detect.py`. Confirm it prints four rows, highest severity first, and that the existing four tests still pass.

**Mistakes that fail the test.** Sorting by value instead of severity. Forgetting that `ascending=False` is needed, which gives lowest first. Printing before sorting, so the order looks random. Computing severity on the whole table, then letting the NaN from the first readings sort to the top or bottom.

### Challenge 2: Tune the detector's sensitivity (model, medium)

**What is asked.** Make the z-score threshold and the IsolationForest contamination configurable. Show a setting that also flags a fifth, milder spike you plant.

**Done when.** "Done when: A documented config catches 5 spikes while the original 4 tests still pass."

**Ideas you need.** Named constants or a configuration structure, the effect of `contamination` and of the z threshold, and the difference between the default data and a data set you change on purpose.

**Plan of attack.**

1. List every number that controls sensitivity: the z threshold, the IQR multiplier, and contamination. Move each into a named setting with a documented default.
2. Think about the conflict first. The four existing tests expect exactly four spikes on the generated data. If you add a fifth spike to `make_data.py`, those tests fail. So the default configuration must still produce four, and the fifth spike must come from a separate setting or data run.
3. Plant the milder spike in a way that is switched on by configuration, not by changing the default data.
4. Choose a configuration in which the detector finds five. Measure it by running the detector, not by reasoning about it alone.
5. Document both settings in a short text file or docstring, stating what each one does and what value gives four and what value gives five.
6. Run the tests and confirm all four still pass with the default settings.

**Mistakes that fail the test.** Changing the default data, which breaks the count of four. Making the threshold so low that the model flags noise, so the count is five for the wrong reasons. Documenting the settings but not showing the five-spike run. Hard-coding the fifth spike into the detector instead of the data.

### Challenge 3: Per-station explanation endpoint (API and LLM, medium)

**What is asked.** Add `GET /explain/{station}`. It runs the LLM from `explain.py` on that station's latest confirmed anomaly and returns the sentence.

**Done when.** "Done when: curl /explain/ST-04 returns one grounded plain-English sentence."

**Ideas you need.** Path parameters, which are the `{station}` part of the URL, and how a route can return an HTTP 404 for an unknown station. Also the cost of loading a model: the model should load once, not per request.

**Plan of attack.**

1. Read the `explain` function in `explain.py` and list its inputs. Work out which values for a station you must find: the station, the value, the rolling mean and the z-score.
2. Decide where the model is loaded. The tokenizer and model should be loaded once when the program starts, not inside the request handler.
3. Write the route with a path parameter. Look up the station's latest confirmed anomaly from the list you already have. Think about what to do when the station has no anomaly.
4. Call the explanation function with those values, and return the sentence in a JSON object.
5. Test with `curl` on the valid station and on one with no anomaly. Confirm the response codes are different.

**Mistakes that fail the test.** Loading the model inside the route, which makes every call take many seconds. Returning the latest reading instead of the latest confirmed anomaly. Returning a server error for an unknown station instead of a clear 404. Ignoring the case where a station has several anomalies, and not saying which one was used.

### Challenge 4: Interactive spike drill-down (UI, medium)

**What is asked.** Add a station selector and a 24-hour line chart to the Streamlit app. The chart rings any spikes in that window, and the data comes from the API.

**Done when.** "Done when: Picking a station redraws its last-24h trend with spikes marked."

### Challenge 5: Alert gate in CI (CI/CD, hard)

**What is asked.** Add a `ruff` lint step to the pipeline. Add a check that fails the build if the detector's recall on the planted spikes drops below 100 per cent. Deploy only on green.

**Done when.** "Done when: A detector that misses a planted spike fails the Actions run; a correct one deploys."

**Ideas you need.** Recall, which is the share of true positives among all real spikes. Exit codes: a program returns 0 for success and a non-zero number for failure, and CI reads only that number. The ruff linter, which checks code style and common errors. The fact that the planted spikes are known, because `make_data.py` defines them.

**Plan of attack.**

1. Add a `ruff` step to the workflow before the tests. Run `ruff check` locally first, and fix or configure any existing findings so the step is meaningful.
2. Decide how the check knows the true spikes. The planted spikes are defined in the generator, so think about whether the check should import that list, read it from a file, or derive it from the data.
3. Write a small script that compares the detected spikes with the planted spikes. Compare identities, meaning the station and hour pairs, not just the count.
4. Make the script compute recall and exit with a non-zero code if recall is below 1.0. Print the result so the log explains the failure.
5. Add the script as a CI step after the tests. Confirm the existing `needs: test` ordering still makes deploy wait for it.
6. Test the gate both ways. Temporarily raise the threshold so a spike is missed, confirm the run fails, then restore it and confirm the run passes and deploys.

**Mistakes that fail the test.** Printing "FAIL" but returning exit code 0, so CI shows green. Comparing only the number of spikes, so a detector that finds five wrong readings passes. Adding `ruff` after the tests so a lint error is never reported before the deploy decision. Leaving existing lint findings unfixed, so the step fails for reasons unrelated to the detector.

## Viva preparation

The capstone viva scores four things, each from 0 to 5. The first is acceptance criteria met: did your project do what the brief asked, and can you show it? The second is technical depth: can you explain how the statistics, SQL and model work, and why? The third is contribution and ownership: can you say which parts you built and which decisions were yours? The fourth is understanding: can you answer a question you have not seen before, and admit the limits of what you built?

Answer each question in your own words, aloud. The model answers below show the content and the length, not a script to memorise.

:::answer Why does the rolling baseline exclude the current reading?
Because a spike would otherwise raise its own baseline and hide itself. The window is the six rows before the current one, set by `ROWS BETWEEN 6 PRECEDING AND 1 PRECEDING`. This keeps the comparison honest: each reading is judged against what came just before it. The cost is that the first readings of each station have a short or empty window, and I handle that explicitly.
:::

:::answer Why use the median and MAD instead of the mean and standard deviation?
The median and MAD are robust, meaning one extreme value barely moves them. A spike inflates the mean and standard deviation, which makes it harder to detect. With the median and MAD, the spike stands out clearly. The 0.6745 constant rescales the MAD so the score reads like a normal z-score. I added a tiny constant to the MAD so the code never divides by zero.
:::

:::answer Why do you need both the robust z-score and the IQR fence?
Each test catches a different kind of false alarm. The z-score is sensitive to how far a value sits from its station's median, and the IQR fence sets an upper limit from the middle of the distribution. Requiring both means a reading must be unusual by two independent measures. The result is fewer false alarms from noise that is only slightly high.
:::

:::answer Why add an IsolationForest if the statistics already find the spikes?
The statistics find four candidates on this data, and the model finds thirteen. The model looks at the joint pattern of value and deviation from the baseline, which the univariate tests do not. Requiring agreement keeps only the readings both methods support. The trade-off is that a real spike that only one method sees will be missed, and I would rather report that honestly than hide it.
:::

:::answer Why compute the anomalies once at startup rather than on each request?
The detection depends only on the data, which is fixed for the life of the process. Computing it once makes every request fast, because the API only reads a stored table. The cost is that new data needs a restart, which is acceptable for this project. In a production system with changing data, I would recompute on a schedule and store the results.
:::

:::answer What does Pydantic validation protect against, and what does a 422 mean?
It protects the detector from input it cannot handle, such as a station that does not exist or a value outside 0 to 500. The 422 status means the request was understood but its data failed validation. The response says which rule failed, so the caller can correct the request. A 500 would mean my code broke, which is a different problem.
:::

:::answer Why does the language model only explain, rather than detect?
Detection must be deterministic, so the same data always gives the same alerts, and it must be testable. A language model's output can vary and can drift from the facts. So the decision stays in code and is covered by tests, and the model only turns the confirmed numbers into a sentence. I also check that the numbers in the sentence match the API.
:::

:::answer What does CI/CD guarantee, and what does it not guarantee?
It guarantees that every push to main runs the tests on a fresh machine, and that the image is deployed only after those tests pass. It does not guarantee the detector is correct. It only checks what the tests check. A spike that the tests never cover can still be missed, which is why the planned recall gate matters.
:::

## What goes wrong

| Mistake | Symptom | Fix |
|---|---|---|
| Running `pytest` before `make_data.py` | `FileNotFoundError` for `data/readings.csv` | Run `python make_data.py` first, as CI does |
| Using `and` instead of `&` on pandas columns | `ValueError: The truth value of a Series is ambiguous` | Use `&` with brackets around each test |
| Removing `sort_values` from `load` | Rolling baselines mix neighbouring hours, with no error | Keep the sort, and check the `win_n` column |
| Including the current row in the window | Spikes look smaller than they are, and may be missed | Use `ROWS BETWEEN 6 PRECEDING AND 1 PRECEDING` |
| Plain mean and standard deviation for the z-score | A spike is less visible, and fewer spikes are flagged | Use the median and MAD |
| Returning raw timestamps from `/anomalies` | A 500 error that says the timestamp is not JSON serialisable | Convert with `astype(str)` before returning |
| Binding the server to `127.0.0.1` inside Docker | The container runs, but the port cannot be reached | Use `--host 0.0.0.0` in the `CMD` line |
| Loading the model inside a request handler | Each call takes many seconds, and the server looks frozen | Load the tokenizer and model once at startup |
| A lint or recall check that prints FAIL but exits with 0 | CI shows green, and a broken detector deploys | Exit with a non-zero code on failure |
| Dashboard calls `/stations` with no such endpoint | The page shows an error where the bar chart should be | Add the endpoint, or remove the call |
