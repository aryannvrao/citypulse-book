TITLE: Day 25 — Containers with Docker
SUB: You will be able to package the CityPulse API into a hardened Docker image, run it with a published port, start it together with Postgres using Compose, and scan the image with Trivy.

## The idea in one minute

Today you put the CityPulse API into a box that carries everything it needs: the Python version, the libraries at the exact versions you tested, the code, and the command that starts the server. Anyone with Docker can open that box and get the same behaviour you see, so "it works on my laptop" stops being a problem. Think of an image as a sealed lunch tiffin packed at home. A container is that tiffin opened and eaten anywhere, tasting the same. By the end you will be able to build the image, run it, check that it answers, make it small and safe, start the API and its database with one command, and list the known security holes in it.

## Starting from zero

**Terminal and command.** A terminal is a text window where you type instructions for the computer. Each instruction is a command. In this chapter a command is shown after a dollar sign, such as `$ docker ps`. You type only the text after the dollar sign. The lines underneath are the output the computer prints back.

**Flag.** A flag is an option that changes how a command behaves. Flags start with a dash. A single dash and one letter, such as `-p`, is a short flag. Two dashes and a word, such as `--rm`, is a long flag.

**File, folder and path.** A file holds data, for example `requirements.txt`. A folder (also called a directory) holds files and other folders. A path names a file by its location, so `api/main.py` means the file `main.py` inside the folder `api`.

**Variable.** A variable is a name that stores a value. In a terminal, `DATABASE_URL="postgresql://..."` stores text under the name `DATABASE_URL`. Writing `$DATABASE_URL` later reads the stored value back.

**Environment variable.** An environment variable is a variable that a program reads when it starts. The same program can therefore behave differently on two machines without any code change. The database address is the usual example.

**Function.** A function is a named piece of code that takes inputs, does some work and gives back a result. For example, `len("abc")` is a call to the built-in function `len`, and it returns `3`.

**Server, host, localhost and port.** A server is a program that waits for requests and sends answers. The CityPulse API is a server. A host is a machine. `localhost` means "this machine". A port is a numbered entry point on a machine. The address `localhost:8000` means port 8000 on this machine, which is where the API listens.

**Process and PID.** A process is a running program. Each process has a number called a PID (process ID). The first process started inside a container gets PID 1.

**User and root.** Every process runs as a user. The user `root` can change anything on the system. A process that runs as a normal user has fewer powers, and that limits the damage if the program is attacked. Users can be shown by name or by number. The number 10001 is simply a user ID.

**Package, dependency and pip.** A package is a ready-made library of code. A dependency is a package your code needs. `pip` is the tool that installs Python packages. Writing `fastapi==0.115.4` pins the version, so the same version is installed every time.

**Virtual environment.** A virtual environment is a folder with its own copy of Python packages, kept apart from the rest of the machine. `python -m venv /opt/venv` creates one in the folder `/opt/venv`.

**Container and virtual machine.** A virtual machine runs a complete second operating system, which is heavy and slow to start. A container shares the host's Linux kernel but is isolated from everything else. It is much lighter.

**YAML and JSON.** Both are text formats for structured data. JSON uses braces, brackets and quotes. YAML uses indentation to show structure. In YAML, indentation must use spaces, not tabs, and the number of spaces matters.

**Exit code.** When a program finishes, it returns a number. Zero means success. Any other number means failure. Docker and scripts use this number to decide what to do next.

**Git.** Git records the history of changes to a project. The hidden folder `.git` holds that history. It is useful to developers, but it does not belong inside a running application.

## The tools

### Docker images and containers

Docker builds an **image** from a text recipe called a **Dockerfile**. An image is a read-only package made of layers. Each instruction in the Dockerfile adds one layer. A **container** is a running copy of an image. You can start many containers from one image, and stopping a container does not change the image.

CityPulse uses Docker because the client's platform engineer must start the service with one `docker run` command on a machine nobody has configured. The alternatives fail that test in different ways. A virtual environment plus a setup script depends on the host's operating system and Python version, so the swap test usually fails on a different laptop. A virtual machine image works, but it is gigabytes in size and takes minutes to boot. Podman is daemonless and Docker-compatible, which makes it a fine choice in general, but the course standardises on Docker.

The flow below shows the life of an image.

```flow
TITLE: From recipe to running container
NODES: Dockerfile | Image | Container
STEPS:
1>2 :: docker build :: Docker reads the Dockerfile top to bottom and turns each instruction into a cached layer. The result is one image.
2>3 :: docker run :: Docker starts a container from the image, maps host port 8000 to container port 8000 and sets environment variables.
3>2 :: docker stop :: The container stops and, because of --rm, is deleted. The image is unchanged.
```

The flow shows three stages. Node 1 is the text recipe. Node 2 is the image, the stored package. Node 3 is the running container. The message labels name the Docker command that moves the work from one stage to the next.

Here is a build of the simple image from the slides.

```term
$ docker build -t citypulse:1.0 .
#5 [1/5] FROM docker.io/library/python:3.12-slim
#8 [4/5] RUN pip install --no-cache-dir -r requirements.txt
#8 DONE 10.2s
#10 naming to docker.io/library/citypulse:1.0 done
```

The command is `docker build`, which reads a Dockerfile and creates an image. `-t citypulse:1.0` is a tag. The part before the colon is the image name and the part after it is the version label. The single dot at the end is the **build context**. It is the folder that Docker can read files from during the build, and the dot means "the current folder". Each numbered line starting with `#` is one build step. The `[1/5]` means step 1 of 5. `DONE 10.2s` says the pip install took 10.2 seconds. The last line confirms the image name and tag.

:::trap Editing files inside a running container
Changes you make inside a container disappear when the container is removed. The fix belongs in the Dockerfile, followed by a new build. Examiners often ask why a change "vanished", and the answer is always that the container was thrown away and the image was never edited.
:::

### Dockerfile best practice and multi-stage builds

A Dockerfile is a list of instructions that Docker runs top to bottom. A **multi-stage build** uses more than one `FROM` line. The first stage, called the **builder**, installs everything needed to prepare the app. The second stage starts clean and copies in only the results. The final image therefore does not contain compilers, pip caches or other tools used only during the build.

The course's hardened Dockerfile is below. The line breaks have been restored, because the source extraction split some lines.

```dockerfile
FROM python:3.11.9-slim AS builder
COPY requirements.txt .
RUN python -m venv /opt/venv && /opt/venv/bin/pip install --no-cache-dir -r requirements.txt

FROM python:3.11.9-slim
ENV PATH="/opt/venv/bin:$PATH" PYTHONUNBUFFERED=1
COPY --from=builder /opt/venv /opt/venv
WORKDIR /app
COPY --chown=10001:10001 models/ models/
COPY --chown=10001:10001 src/ src/
COPY --chown=10001:10001 api/ api/
USER 10001
HEALTHCHECK --interval=15s --timeout=3s CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/v1/health', timeout=2)"
CMD ["uvicorn", "api.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Line by line:

- `FROM python:3.11.9-slim AS builder` starts the first stage. `FROM` names the base image, which is a ready-made Linux with Python already installed. The tag `3.11.9` pins the exact Python version, and `slim` picks a smaller variant with fewer packages. `AS builder` gives the stage a name so later lines can refer to it.
- `COPY requirements.txt .` copies that one file from the build context into the image. The dot is the destination, which is the current working folder. In this stage no `WORKDIR` has been set, so that folder is the root `/`.
- `RUN python -m venv /opt/venv && /opt/venv/bin/pip install ...` runs commands during the build. `python -m venv /opt/venv` creates a virtual environment in `/opt/venv`. The `&&` runs the second command only if the first succeeds. `/opt/venv/bin/pip` is the pip belonging to that environment. `--no-cache-dir` stops pip keeping its download cache, which keeps the layer small. `-r requirements.txt` installs every package listed in the file.
- `FROM python:3.11.9-slim` starts the second stage. It begins empty, with only the base image.
- `ENV PATH="/opt/venv/bin:$PATH" PYTHONUNBUFFERED=1` sets two environment variables inside the image. Putting `/opt/venv/bin` first in `PATH` means that `python` and `uvicorn` are found in the virtual environment. `PYTHONUNBUFFERED=1` makes Python send logs immediately, so `docker logs` shows them without delay.
- `COPY --from=builder /opt/venv /opt/venv` copies only the virtual environment from the builder stage. `--from=builder` names the source stage.
- `WORKDIR /app` sets the working folder for the following lines and creates it if it does not exist.
- The three `COPY --chown=10001:10001` lines copy the model, source and API folders. `--chown` sets the owner and group of the copied files to user and group 10001, so the non-root user owns them and can write to them.
- `USER 10001` means the container's process runs as user 10001 instead of root.
- `HEALTHCHECK --interval=15s --timeout=3s CMD ...` tells Docker to run the check every 15 seconds, and each check must finish within 3 seconds. The Python command tries to open `/v1/health`. If the request fails or returns an error code, `urlopen` raises an error, the script exits with a non-zero code, and Docker marks the container unhealthy.
- `CMD ["uvicorn", "api.main:app", "--host", "0.0.0.0", "--port", "8000"]` is the command that starts when the container starts. `api.main:app` names the `app` object in the file `api/main.py`. `--host 0.0.0.0` makes the server accept connections from outside the container. `--port 8000` sets the port.

When you build this file, the build output is long and you should see no errors. Nothing is printed when the container starts except the server's startup lines.

Next is the cache. The term block shows a rebuild after a code change.

```term
$ docker build -t citypulse:1.1 .
#6 [3/5] COPY requirements.txt .
#6 CACHED
#8 [4/5] RUN pip install --no-cache-dir -r requirements.txt
#8 CACHED
#10 naming to docker.io/library/citypulse:1.1 done
```

`CACHED` means Docker found an identical layer from an earlier build and reused it instead of running the step again. Docker decides this from the instruction and the files it reads. Because `requirements.txt` did not change, the pip install is skipped. Only the layers below a changed file must run again. The reader can see the payoff: the pip install does not run again after a change to application code.

:::trap COPY . . before pip install
If you write `COPY . .` above the `pip install` line, every edit to any code file changes the layer above the install. Docker then reinstalls all dependencies on every build. Copy `requirements.txt` first, install, and copy the code afterwards.
:::

:::trap Two versions of the course recipe
The slides use Python `3.11.9-slim`, the folders `api/`, `src/` and `models/`, and the health path `/v1/health`. The walkthrough uses `python:3.12-slim`, a single `app/` folder and `/health`. Use the tag, folders and paths in your ticket and the slides. The lab in this chapter follows the slides.
:::

### Docker Compose

Docker Compose runs several containers from one file called `docker-compose.yml`. CityPulse needs two services: the API and Postgres, which is the database. Compose creates a private network between them, starts them in the right order and gives each service a name that the other containers can use as a hostname.

Compose is used instead of separate `docker run` commands. Separate commands work, but you must create the network, set the order and type long commands into the README, which is error-prone. Kubernetes (for example minikube or kind) is far beyond two containers on a laptop. A local Postgres install differs between laptops. The compose file below is the course's version, with line breaks restored.

```yaml
services:
  db:
    image: postgres:16-alpine
    environment: {POSTGRES_USER: "${POSTGRES_USER}", POSTGRES_PASSWORD: "${POSTGRES_PASSWORD}", POSTGRES_DB: citypulse}
    volumes: ["pgdata:/var/lib/postgresql/data", "./sql/init.sql:/docker-entrypoint-initdb.d/init.sql:ro"]
    healthcheck: {test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d citypulse"], interval: 5s, retries: 10}
  api:
    build: .
    ports: ["8000:8000"]
    environment: {DATABASE_URL: "postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/citypulse"}
    depends_on: {db: {condition: service_healthy}}
volumes:
  pgdata: {}
```

Line by line:

- `services:` starts the list of containers. Each key below it, here `db` and `api`, is one service, and the indented lines belong to it.
- `db:` defines the database service. `image: postgres:16-alpine` uses the ready-made Postgres image, version 16, based on the small Alpine Linux.
- `environment:` sets environment variables inside the container. `POSTGRES_USER` and `POSTGRES_PASSWORD` are read by the Postgres image at first start. `${POSTGRES_USER}` is replaced by the value in your `.env` file before Compose starts anything. `POSTGRES_DB: citypulse` creates a database named `citypulse`.
- `volumes:` has two entries. `pgdata:/var/lib/postgresql/data` stores the database files in a named volume called `pgdata`, so the data survives when the container is removed. The second entry copies `sql/init.sql` into a folder that Postgres runs on first start. The suffix `:ro` means read-only.
- `healthcheck:` asks Postgres every 5 seconds whether it is ready. `pg_isready` is a Postgres tool that exits with zero when the server accepts connections. The double dollar sign `$$` stops Compose replacing the variable itself, so the shell inside the container reads it. `retries: 10` allows ten failed checks before the service counts as unhealthy.
- `api:` defines the API service. `build: .` builds the image from the Dockerfile in the current folder.
- `ports: ["8000:8000"]` publishes port 8000, the same as `-p 8000:8000` in `docker run`.
- `DATABASE_URL` is the connection address. The host part is `db`, the service name. Inside the Compose network, `db` points to the Postgres container. It does not mean `localhost`, which would point to the API container itself.
- `depends_on: {db: {condition: service_healthy}}` makes Compose wait until the `db` healthcheck passes before it starts the API.
- `volumes: pgdata: {}` at the top level declares the named volume. The empty braces mean "default settings".

The commands are short. Copy the example file for the secrets first:

```term
$ cp .env.example .env
$ docker compose up --build -d
$ docker compose ps
NAME            SERVICE  STATUS                     PORTS
citypulse-db-1  db       Up 40 seconds (healthy)    5432/tcp
citypulse-api-1 api      Up 20 seconds              0.0.0.0:8000->8000/tcp
```

`cp .env.example .env` copies the template file to `.env`, the real file that holds your passwords. `docker compose up` starts the services. `--build` rebuilds the API image first. `-d` runs everything in the background. `docker compose ps` lists the services. The exact spacing and container names vary, but `(healthy)` next to `db` shows the healthcheck passed. The `0.0.0.0:8000->8000/tcp` text means port 8000 on your machine is connected to port 8000 in the API container.

:::trap Commit the template, not the secrets
Commit `.env.example` with placeholder values and add `.env` to `.gitignore`. A real password committed to Git stays in the history even after you delete it.
:::

:::trap Changing init.sql and expecting it to run again
The init script runs only when the volume is empty, which means the first start. Editing `init.sql` does nothing to an existing volume. `docker compose down -v` removes the volume and its data, so use it only when losing the data is acceptable.
:::

### Trivy scanning

Trivy is an open-source scanner. It lists known security weaknesses, called CVEs (Common Vulnerabilities and Exposures), in the operating-system packages and Python libraries inside an image. Each finding has a severity such as LOW, MEDIUM, HIGH or CRITICAL. Trivy can also write a software bill of materials, called an SBOM, which is a list of every component in the image.

CityPulse uses Trivy because the client's security team will not run an image without a report and a decision for every HIGH or CRITICAL finding. The alternatives are Docker Scout, which needs a Docker account and is less common in CI pipelines, Grype, which is equally valid but does not also scan configuration and secrets, and Snyk, which needs an account and token and has usage limits on the free plan.

Trivy downloads a vulnerability database, lists every package in the image layers and reports the ones with known CVEs. The commands below save the reports to `docs/security`.

```bash
mkdir -p docs/security
TRIVY="docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v $PWD/docs/security:/out aquasec/trivy"
$TRIVY image --severity HIGH,CRITICAL citypulse-api:before | tee docs/security/trivy-before.txt
$TRIVY image --severity HIGH,CRITICAL citypulse-api:hardened | tee docs/security/trivy-$(date +%F).txt
$TRIVY image --format cyclonedx --output /out/sbom.cdx.json citypulse-api:hardened
# show only findings that have an upgrade available
$TRIVY image --severity HIGH,CRITICAL --ignore-unfixed citypulse-api:hardened
```

Line by line:

- `mkdir -p docs/security` creates the folder, and `-p` means "no error if it already exists".
- `TRIVY="..."` stores the long `docker run` command in a variable, so the later lines are short. Trivy is itself a container, `aquasec/trivy`.
- `-v /var/run/docker.sock:/var/run/docker.sock` gives Trivy access to Docker so it can read the image. `-v $PWD/docs/security:/out` shares your report folder with the container. `$PWD` is the current folder.
- `$TRIVY image --severity HIGH,CRITICAL citypulse-api:before` scans the image and shows only HIGH and CRITICAL findings.
- `| tee docs/security/trivy-before.txt` sends the output to the screen and to a file at the same time. `tee` is the tool that does both.
- `$(date +%F)` prints today's date in the form `2027-03-01`, which goes into the file name.
- `--format cyclonedx --output /out/sbom.cdx.json` writes the SBOM in the CycloneDX format to the shared folder.
- `--ignore-unfixed` hides findings where no fixed version exists yet.

The scan output is a table with columns such as Library, Vulnerability, Severity, Installed Version and Fixed Version. Each remaining finding needs a decision in `docs/security/README.md`: upgrade the package, accept it with a reason, or note that no fix exists.

:::trap No fix available does not mean ignore
A finding with no fixed version still needs a line in `docs/security/README.md` with a reason. Also rescan on every release, because new CVEs appear every day.
:::

:::trap Upgrading without re-testing
A package upgrade to clear a CVE can break the model. A scikit-learn bump can stop the saved model loading, so run the tests again after any upgrade.
:::

## The worked example

The walkthrough in the course workbook takes a simple Dockerfile through to a working container. Its goal is to show the three things you do with any image: build it, run it and check it, and prove that the cache works.

**Step A: build the image.** The Dockerfile in this step has the same logic as the hardened version, but is simpler.

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

`FROM` picks the base, `WORKDIR` sets the folder, the `COPY requirements.txt` and `RUN pip install` pair installs the dependencies in their own layer, and `COPY . .` copies the rest of the project. `EXPOSE 8000` documents the port but does not open it. `CMD` starts the server. Run `docker build -t citypulse:1.0 .` and the last line of the output names the new image.

**Step B: run it and check it answers.**

```bash
docker run -p 8000:8000 citypulse:1.0
```

`-p 8000:8000` publishes port 8000. Without this flag the server runs, but your machine cannot reach it. Leave this terminal open. In a second terminal, run:

```bash
curl -s http://localhost:8000/readings
```

`curl` sends a request to the address. `-s` (silent) hides the progress meter, so you see only the answer. The expected output is one line of JSON:

```text
{"count":2,"readings":[{"station_id":"S1","pollutant":"pm25","value":42.1},{"station_id":"S2","pollutant":"no2","value":18.5}]}
```

Each reading has a station ID, a pollutant and a value. Matching output on your laptop and in the container shows that the packaged app behaves like the development version.

**Step C: prove the cache and check the size.** Change one line of code in `app/main.py`, then rebuild with the tag `1.1`. The output shows `CACHED` on the dependency steps, as in the term block earlier. Then run:

```bash
docker images citypulse
```

The output lists the repository, tag, image ID, creation time and size. The walkthrough shows two images of 238MB each, one for `1.0` and one for `1.1`. The size is the same because only the code layer changed. Your size can be different, and the T43 table records the size you measure.

## The hands-on lab, step by step

Work through the steps in order. Each one ends with a check. Do not move on until the check passes.

### 1. A minimal API to containerise

**What you do.** Confirm that the CityPulse API folder has a file called `main.py` inside a folder called `api`, and that the file creates an application object called `app` with a route `/v1/health`.

**What you type.**

```bash
ls api
```

`ls` lists the files in a folder. The output should include `main.py`.

**What you should see.** `main.py` is listed. If it is not, stop and ask your mentor which folder your ticket uses.

**How you know it worked.** Once the dependencies are installed in step 2, `python -m uvicorn api.main:app --port 8000` starts the server locally, and `curl -i http://localhost:8000/v1/health` returns `HTTP/1.1 200 OK`. Use `Ctrl+C` in the server terminal to stop it. This proves the app works before you wrap it in a container.

### 2. Pin dependencies

**What you do.** Make sure `requirements.txt` lists every package the API uses, each with an exact version. The slides name `scikit-learn` pinned to the version used to train the model. Copy that version from your team's notes. Do not guess it.

**What you type.**

```bash
cat requirements.txt
```

`cat` prints the contents of a file.

**What you should see.** Lines in the form `name==version`, for example:

```text
fastapi==0.115.4
uvicorn==0.32.0
```

**How you know it worked.** Every line has `==` followed by a number. A line such as `fastapi>=0.100` is not pinned and must be changed. The lint problem later in this chapter checks this exact rule.

### 3. Write the Dockerfile

**What you do.** In the project's top folder, create a file named exactly `Dockerfile`, with no extension. Use a plain text editor. Write the single-stage version below. The multi-stage version is the T43 ticket.

```dockerfile
FROM python:3.11.9-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY models/ models/
COPY src/ src/
COPY api/ api/
EXPOSE 8000
CMD ["uvicorn", "api.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

`FROM` sets the base image with a pinned tag. `WORKDIR /app` sets the folder for the next lines. The two lines starting `COPY requirements.txt` and `RUN pip install` come before the code, so the dependency layer is cached. The three `COPY` lines copy the named folders, one line each, into the same paths inside the image. `EXPOSE` documents port 8000. `CMD` starts the server and `--host 0.0.0.0` lets outside traffic in.

**What you should see.** The file appears in the folder listing as `Dockerfile`, with no extra extension. Windows Notepad sometimes adds `.txt` to new files, so check the name.

**How you know it worked.** The build in step 5 finishes without an error.

### 4. Add a .dockerignore and a non-root user

**What you do.** Create a file named `.dockerignore` in the same folder. Add the lines below. Then add `USER 10001` and make the copied files owned by user 10001 by changing the three `COPY` lines to `COPY --chown=10001:10001 ...`.

```text
.git
.venv
.env
data/raw
```

Each line names a path to leave out of the build context. A `.dockerignore` file uses the same path rules as `.gitignore`, which is a file that tells Git what to ignore.

**What you should see.** The `.dockerignore` file exists, and the Dockerfile has a `USER 10001` line below the `COPY` lines.

**How you know it worked.** Build the image in step 5, then run `docker run --rm citypulse-api:p8 id -u`. It prints `10001`. Using `id -u` is the right check, because `whoami` may print an error for a user number that has no name.

Note that your single-stage Dockerfile copies only named folders, so `.git` would not have been copied anyway. The `.dockerignore` file is a safety net that also makes the build faster. It matters the moment someone writes `COPY . .`.

### 5. Build and tag

**What you do.** Build the image and give it a tag.

**What you type.**

```bash
docker build -t citypulse-api:p8 .
docker images citypulse-api
```

`docker build` reads the Dockerfile and creates the image. `-t citypulse-api:p8` gives it the name `citypulse-api` and the tag `p8`. The final `.` is the build context, the current folder. `docker images citypulse-api` lists the images with that name.

**What you should see.** The build output ends with a line that names `citypulse-api:p8` as done. The `docker images` output shows one row with the tag `p8` and a size column. Write the size down for the T43 table.

**How you know it worked.** The row with `p8` appears. If the build fails on `COPY`, check the folder names in your Dockerfile against the folder names on disk.

### 6. Run and publish the port

**What you do.** Start the container in the background, publish its port and check that it answers.

**What you type.**

```bash
docker run --rm -d --name cp-api -p 8000:8000 -e DATABASE_URL="$DATABASE_URL" citypulse-api:p8
docker ps
sleep 5 && curl -i localhost:8000/v1/health
```

Line by line: `docker run` starts a container. `--rm` deletes it when it stops. `-d` runs it in the background, so the prompt returns. `--name cp-api` gives it a name you can use in later commands. `-p 8000:8000` publishes port 8000, with the host port on the left and the container port on the right. `-e DATABASE_URL="$DATABASE_URL"` passes your shell's `DATABASE_URL` into the container. `sleep 5` waits five seconds for the server to start, and `&&` runs `curl` only if the wait succeeded. `curl -i` prints the response headers as well as the body.

**What you should see.** `docker ps` shows the container `cp-api` with `0.0.0.0:8000->8000/tcp` under PORTS. `curl -i` prints `HTTP/1.1 200 OK` followed by a small JSON body.

**How you know it worked.** The status line is `200`. If `curl` says the connection was refused, the port flag is missing or the server is bound to `127.0.0.1` inside the container.

:::trap Localhost inside the container
If `DATABASE_URL` says `localhost`, the API looks for Postgres inside its own container and fails. Use `host.docker.internal` when Postgres runs on your laptop, or the service name `db` inside Compose. If `$DATABASE_URL` is not set in your terminal, the `-e` flag passes an empty value.
:::

### 7. Healthcheck and logs

**What you do.** Check the container's health status and read its logs, then stop it. The health status exists only if the Dockerfile has a `HEALTHCHECK` line, so add the one from the hardened Dockerfile above and rebuild before step 6.

**What you type.**

```bash
docker inspect --format '{{.State.Health.Status}}' cp-api
docker logs cp-api | tail -5
docker exec cp-api id -u
docker stop cp-api
```

`docker inspect --format` prints one field from the container's details. `{{.State.Health.Status}}` is the path to the health status. `docker logs cp-api` prints what the server wrote. The `|` sends that output to `tail -5`, which keeps only the last five lines. `docker exec cp-api id -u` runs a command inside the running container and prints the user number. `docker stop cp-api` stops the container, and because you used `--rm`, it is removed.

**What you should see.** The first command prints `starting` straight after start-up and `healthy` after the first 15-second check. The log lines are JSON request lines, for example one line per request to `/v1/health`. `id -u` prints `10001`.

**How you know it worked.** The status is `healthy`, the logs show your requests, and the user is not `0`. `0` is the number for root. Then `docker ps` no longer lists `cp-api`.

## What the quiz tests

Each topic below has a short explanation, the trap examiners set, and a question in the quiz block at the end of this section.

### dockerfile-from

`FROM` names the base image that every later instruction builds on. It must be the first instruction, apart from an optional `ARG` line. A tag such as `python:3.11.9-slim` pins the exact version, while `slim` gives a smaller image without compilers. A tag like `latest` points to whatever release is newest, so the same Dockerfile can build a different image next month. Writing `FROM` a second time starts a new stage, which is how multi-stage builds work.

**Examiner's trap:** a candidate chooses `python:latest` because it "always has the newest version". The question asks why the build changed, and the answer is that the moving tag changed under the same recipe.

### docker-port-publishing

`EXPOSE 8000` in a Dockerfile only documents which port the app uses. It does not make the port reachable from your machine. The `-p host:container` flag in `docker run` publishes the port, and the host port always comes first. The server also has to listen on `0.0.0.0` inside the container, otherwise traffic from outside cannot reach it.

**Examiner's trap:** `EXPOSE` is treated as if it published the port. The question gives you an `EXPOSE` line and no `-p` flag, and the correct answer is to add `-p`.

### docker-volumes

A volume keeps data outside the container's own filesystem, so the data survives when the container is removed. In `docker-compose.yml`, `pgdata:/var/lib/postgresql/data` stores the database files in a named volume. A bind mount such as `./sql/init.sql:/docker-entrypoint-initdb.d/init.sql:ro` maps a file from your folder into the container. The suffix `:ro` makes it read-only. Postgres runs the init scripts only when the data folder is empty.

**Examiner's trap:** a candidate edits `init.sql`, restarts, and expects the new table. Nothing changes because the volume already holds data. Deleting the volume with `docker compose down -v` fixes it, but deletes the data.

### docker-layer-caching

Each Dockerfile instruction creates a layer, and Docker reuses a layer when the instruction and its inputs have not changed. When one layer changes, every layer below it must run again, even if those lower instructions are unchanged. This is why `requirements.txt` is copied and installed before the application code. Code edits then leave the pip layer intact.

**Examiner's trap:** a candidate thinks Docker caches each line independently. It does not. A change high in the file invalidates every line after it.

### docker-multistage-build

A multi-stage build has a builder stage that installs tools and a runtime stage that copies only the results. `COPY --from=builder` copies named files or folders from the earlier stage and nothing else. The compiler, the pip cache and the build tools stay behind in the builder. The virtual environment must be copied to the same path it was created in, here `/opt/venv`, so its scripts still work.

**Examiner's trap:** a candidate believes the final image keeps every stage. Only the final stage becomes the image, and the builder is discarded unless you copy from it.

### docker-entrypoint-cmd

`CMD` sets the default command that runs when a container starts. If you pass arguments after the image name in `docker run`, they replace the `CMD` entirely. `ENTRYPOINT` is a fixed program that always runs, and `CMD` then supplies its default arguments. The JSON form, such as `CMD ["uvicorn", ...]`, runs the program directly. The shell form runs it through `/bin/sh`, which can stop signals such as Ctrl+C from reaching the server.

**Examiner's trap:** a candidate adds `--port 9000` after the image name and expects uvicorn to use port 9000. The arguments replace the whole `CMD`, so Docker tries to run `--port` as a program and fails.

### docker-runtime-env

`ENV` in a Dockerfile sets a variable inside the image, so it is baked in for every container from that image. `-e` in `docker run` sets a variable for one container at start, and it overrides the image's value. Secrets such as passwords should be passed at run time, not written into the Dockerfile, because anyone with the image can read its settings. A `localhost` address inside a container means the container itself.

**Examiner's trap:** a candidate writes the real database password into `ENV`. The password is then stored in the image and visible to anyone who pulls it.

### docker-compose

Compose describes several services in one YAML file and starts them together with `docker compose up`. Services reach each other by service name, so the API connects to `db` and not to `localhost`. `depends_on` with `condition: service_healthy` makes Compose wait until the `db` healthcheck passes before starting the API. A healthcheck on the database is required for this to work.

**Examiner's trap:** `depends_on` without a condition is treated as a guarantee that the database is ready. It only sets the start order. The database may still be starting when the API connects.

### dockerignore

A `.dockerignore` file lists paths that are never sent to Docker as part of the build context. Files left out of the context cannot be copied into the image by `COPY . .`. Listing `.git`, `.venv`, `.env` and `data/raw` keeps secrets and large folders out of the image and speeds up the build. It does not delete anything from your own folder.

**Examiner's trap:** a candidate expects a file to be removed from the image by adding it to `.dockerignore` after it has already been committed to Git. The file still exists in Git's history, and `.dockerignore` only changes what goes into the build.

### docker-nonroot-user

`USER 10001` makes the container's processes run as user number 10001 instead of root. A numeric user works even when that number has no name in the image. Files copied into the image are owned by root unless you add `--chown`, so the non-root user cannot write to them. The check is `docker exec cp-api id -u`, which must not print `0`.

**Examiner's trap:** a candidate adds `USER 10001` after the `COPY` lines without `--chown`. The app then fails when it tries to write a file, because the copied folders belong to root.

## The graded lab skill

The graded lab is a Python problem. You write a few functions, and the platform runs visible tests and hidden tests. Hidden tests check edge cases, so think about empty input, missing values and unusual formats as you write. This section teaches the techniques from scratch.

### Strings, lines and cleaning

A **string** is text in quotes. `"fastapi==0.115.4"` is a string. The method `splitlines()` cuts a long string into a list of lines, one item per line. A **method** is a function attached to a value, called with a dot. `strip()` removes spaces and line-break characters from both ends of a string. `startswith("#")` returns `True` when the string begins with `#`, and `endswith("\\")` checks the end. `lower()` converts text to lowercase, which lets you compare `Flask` and `flask`.

A **list** is an ordered collection written in square brackets. `items.append(x)` adds `x` to the end. A **loop** repeats a block for each item: `for raw in lines:` runs the indented block once per line. `enumerate(lines, start=1)` gives each line its number, starting at 1. Note the difference between `=` and `==`: a single equals sign stores a value, and a double equals sign compares two values.

A **set** holds unique items, with no order. `seen.add(key)` adds an item, and `key in seen` returns `True` when it is already there. Sets are the usual way to detect duplicates.

An **if** statement runs a block only when a condition is true. `elif` checks the next condition when the earlier ones are false, and `else` runs when none is true. The order of the checks matters.

A **function** starts with `def`, takes parameters and returns a value with `return`. A function that reaches the end without `return` gives back `None`, which is a value that means "nothing".

### Joining continuation lines

Long instructions are often split with a backslash at the end of a line, so a reader can see them in full. The parser must join those pieces into one logical line. Here is a short example.

```python
def join_continuations(text):
    logical = []
    current = ""
    for raw in text.splitlines():
        line = raw.strip()
        if line.endswith("\\"):
            current += line[:-1].rstrip() + " "
        else:
            logical.append(current + line)
            current = ""
    if current:
        logical.append(current.strip())
    return logical
```

Line by line: `logical` collects finished lines. `current` holds the piece being built. `text.splitlines()` splits the input into physical lines. `raw.strip()` removes the surrounding spaces. `line.endswith("\\")` is true when the last character is a backslash. The two backslashes in the code mean one real backslash, because `\` on its own starts an escape. `line[:-1]` takes the line without its last character. `rstrip()` removes spaces left before the backslash, and the `+ " "` adds one space back. The `else` branch finishes a logical line and resets `current`. The final `if` catches a backslash on the very last line.

For this input:

```text
FROM python:3.11.9-slim AS builder \
  AS builder
COPY requirements.txt .
```

the function returns `["FROM python:3.11.9-slim AS builder AS builder", "COPY requirements.txt ."]`. Notice that the spaces are tidied, but the words are kept.

### Practice problem: a requirements linter

Write a function `lint_requirements(text)`. The input is the full text of a `requirements.txt` file. It returns a list of warning strings in line order.

Rules:

- Lines are numbered from 1, and blank lines and comment lines still count in the numbering.
- A blank line, or a line whose first non-space character is `#`, is skipped.
- A line starts with a package name. A line that does not start with a name is skipped.
- A line with a name and no `==` is unpinned. So is a name followed by an operator such as `>=`. Report `line N: unpinned package 'NAME'`.
- A line with `==` and a version that does not match digits separated by dots, such as `1.5.2.x` or an empty version, is an invalid version. Report `line N: invalid version 'VERSION' for 'NAME'`.
- A line with a valid pinned version whose name, compared without case, appeared on an earlier named line is a duplicate. Report `line N: duplicate package 'NAME'` with the name as written on this line.
- Each line produces at most one warning. The rules are checked in the order unpinned, then invalid version, then duplicate. The first rule that matches wins.
- Every named line counts as seen for duplicates, even when it produced a warning.

Example input:

```text
# pinned for CityPulse
fastapi==0.115.4

uvicorn>=0.32
Fastapi==0.115.4
pandas==2.2.x
```

Expected output:

```text
["line 4: unpinned package 'uvicorn'", "line 5: duplicate package 'Fastapi'", "line 6: invalid version '2.2.x' for 'pandas'"]
```

Edge-case checklist:

- Empty input returns an empty list.
- Input that is only comments and blank lines returns an empty list.
- Blank and comment lines are counted in the line numbers.
- Windows line endings (`\r\n`) do not add extra lines or warnings.
- Spaces around `==` are allowed, as in `flask == 3.0.0`.
- Duplicates are detected without regard to case.
- The first occurrence of a name is never reported as a duplicate.
- A version of `1.0` is valid, and `1.0.x` is not.
- An empty version after `==` is invalid.
- Warnings appear in line order, not grouped by type.
- A line with both an unpinned name and a duplicate name produces only the unpinned warning.
- Extras such as `[standard]` are outside this problem. Do not add tests for them.

:::answer Model solution and explanation
```python test
import re

NAME_RE = re.compile(r"^([A-Za-z0-9][A-Za-z0-9._-]*)")
VERSION_RE = re.compile(r"^\d+(\.\d+)*$")


def lint_requirements(text):
    warnings = []
    seen = set()
    for number, raw in enumerate(text.splitlines(), start=1):
        line = raw.strip()
        if line == "" or line.startswith("#"):
            continue
        match = NAME_RE.match(line)
        if match is None:
            continue
        name = match.group(1)
        key = name.lower()
        rest = line[len(name):].strip()
        if rest == "" or not rest.startswith("=="):
            warnings.append(f"line {number}: unpinned package '{name}'")
        elif not VERSION_RE.match(rest[2:].strip()):
            version = rest[2:].strip()
            warnings.append(f"line {number}: invalid version '{version}' for '{name}'")
        elif key in seen:
            warnings.append(f"line {number}: duplicate package '{name}'")
        seen.add(key)
    return warnings


assert lint_requirements("") == []
assert lint_requirements("# only a comment\n\n   \n") == []
assert lint_requirements("fastapi==0.115.4\nuvicorn==0.32.0\n") == []
assert lint_requirements("requests\n") == ["line 1: unpinned package 'requests'"]
assert lint_requirements("numpy>=1.26\n") == ["line 1: unpinned package 'numpy'"]
assert lint_requirements("scikit-learn==1.5.2.x\n") == ["line 1: invalid version '1.5.2.x' for 'scikit-learn'"]
assert lint_requirements("pandas==\n") == ["line 1: invalid version '' for 'pandas'"]
assert lint_requirements("Flask==3.0.0\nflask==3.0.0\n") == ["line 2: duplicate package 'flask'"]
assert lint_requirements("a==1\n\n# note\nA==2\n") == ["line 4: duplicate package 'A'"]
assert lint_requirements("fastapi==0.115.4\r\nuvicorn\r\n") == ["line 2: unpinned package 'uvicorn'"]
assert lint_requirements("b\na==x\n# c\na==1\nc==1.0\nc==1.0\n") == [
    "line 1: unpinned package 'b'",
    "line 2: invalid version 'x' for 'a'",
    "line 4: duplicate package 'a'",
    "line 6: duplicate package 'c'",
]
assert lint_requirements("flask == 3.0.0\n") == []
```

Line by line:

- `import re` loads the regular-expression module. A regular expression is a pattern that matches text.
- `NAME_RE` matches a package name at the start of a line. `^` means the start, `[A-Za-z0-9]` is one letter or digit, and `[A-Za-z0-9._-]*` is zero or more letters, digits, dots, underscores or hyphens. The parentheses capture the name so you can read it with `group(1)`.
- `VERSION_RE` matches a version made of digits separated by dots. `\d` is a digit, `+` means one or more, `(\.\d+)*` means zero or more groups of a dot and digits, and `$` means the end.
- `enumerate(text.splitlines(), start=1)` gives each line its physical number.
- The first `if` skips blank lines and comments.
- `NAME_RE.match(line)` returns `None` when the line does not start with a name. The `continue` skips such a line.
- `rest` is everything after the name, with spaces removed. For `fastapi==0.115.4` it is `==0.115.4`.
- The first branch covers unpinned lines. It catches a name with nothing after it, and a name followed by an operator such as `>=`.
- The second branch reports an invalid version. `rest[2:]` removes the two equals signs.
- The third branch reports a duplicate. It runs only when the version is valid, which matches the priority rule.
- `seen.add(key)` runs for every named line, so a later repeat is caught even if the first line had a warning.
- The asserts check the rules, the edge cases and the order. The last one shows that a line with a warning is still counted as seen, and that the ordering follows line numbers.

For the example input, the output is the three warnings shown in the practice problem. Run the block and nothing is printed, because every assert passes.

## Say it out loud

:::answer What is the difference between an image and a container?
An image is a read-only package made of layers, built from a Dockerfile, and it does not change when you run it. A container is a running copy of an image, with its own process, network connection and writable layer on top. You can start many containers from one image, and stopping a container leaves the image untouched. This is why the image can be tested and then shipped unchanged.
:::

:::answer Why is requirements.txt copied before the app code?
Docker reuses a layer only when the layer above it is also reused. Copying requirements.txt and running pip install first means that the dependency layer stays cached when only application code changes. Copying the code first would invalidate the pip step on every edit. The result is a rebuild in seconds instead of minutes.
:::

:::answer Why does the container run as user 10001?
A process running as root can change any file in the container and the host's mounted folders if the container is misconfigured. Running as a normal user limits what an attacker gets if the app is compromised. The client's security reviewer requires it before approving the image. The Dockerfile sets it with USER 10001 and copies the files with --chown so the user owns them.
:::

:::answer How does the API find Postgres in Compose, and why does the condition matter?
Compose puts both services on a private network where each service is reachable by its name, so the API uses db as the host in DATABASE_URL. A plain localhost would point to the API container itself. The depends_on condition service_healthy makes Compose wait until Postgres passes its pg_isready check. Without that condition, the API can start before the database accepts connections and fail.
:::

:::answer What does Trivy tell you, and what do you do with a finding that has no fix?
Trivy lists known CVEs in the operating-system packages and Python libraries of an image, with a severity for each. You filter to HIGH and CRITICAL so the list is actionable, and you scan again on every release because new CVEs appear daily. For a finding with no fixed version, you do not ignore it. You record it in docs/security/README.md with a reason, and you note that no fix exists.
:::
