TITLE: Beating hidden tests and first-attempt marking
SUB: By the end you will be able to turn a problem statement into a list of edge cases, write asserts for them, and check your Python function against all of them before you press submit.

## How your work is marked

Each graded lab is a Python problem. The platform gives you a starter file that contains function signatures with docstrings. A function is a named block of code that takes inputs, does some work, and gives back a result. A signature is the first line of the function, and it names the function and lists its inputs. A docstring is the text in triple quotes under the signature, and it describes what the function should do. An input to a function is called a parameter. In this line, `values` is the parameter:

```python
def average_reading(values):
```

The platform gives you a description with one example, and a few visible tests. A test is a check. It calls your function with one input, compares what your function returns with the answer it expects, and reports pass or fail. Visible tests are the checks you can read. Hidden tests are checks you cannot read. They use inputs that the course team chose on purpose, usually the awkward ones.

The mark split matters. Visible tests carry roughly 50 to 85 per cent of the marks, and hidden tests carry the rest. A function that passes every visible test can still lose a third of the marks or more. Hidden tests are where missed edge cases cost you points.

The platform also limits how your code runs. The time limit is 30 seconds and the memory limit is 128 MB. Memory is the working space your program uses while it runs. If your solution uses a loop inside another loop over a large input, it can run out of time on the hidden tests even though it gives correct answers on the small visible ones. The section on speed explains how to avoid that.

Day quizzes are different in format. A day quiz has 10 multiple-choice questions, each about a short case study. The pass mark is 70 per cent, which means you need at least 7 correct answers. The skill score uses your first attempt. If you submit once, learn from the result, and submit again, the second attempt does not replace the first in the skill score. Preparation before the first submission therefore matters more than retrying.

:::trap Passing the visible tests is not the finish line
Students often read the visible tests, make the code pass them, and submit. The visible tests tell you the shape of the answer. They do not show the inputs that break it. Write your own checks for the awkward inputs before you submit.
:::

## Reading a problem statement

A problem statement is the text that tells you what the function must do. Most lost marks come from a misreading of the statement, not from a Python mistake. Read the statement with the method below. Write the answers on paper or in a comment before you type any code.

1. **Inputs and their types.** Write down the name of each parameter and the type of the data it holds. A type is the kind of value: `int` is a whole number such as 7, `float` is a number with a decimal point such as 7.5, `str` is text such as "S1", `list` is an ordered collection in square brackets such as `[1, 2, 3]`, `tuple` is a fixed group of values in round brackets such as `("S1", 20)`, `dict` is a collection of key and value pairs in curly brackets such as `{"S1": 20}`, and `None` is Python's word for "no value".
2. **Output type and exact shape.** Decide what the function returns and in what form. A list of tuples, such as `[("S1", 20.0)]`, is not the same as a list of lists, such as `[["S1", 20.0]]`. A checker that compares the two will fail one of them.
3. **Ordering.** Does the statement say highest first, lowest first, or in the order the input arrived? If it says nothing, assume the output order matters and ask yourself what the most natural order is.
4. **Ties.** If two items have the same value, which one comes first? The statement often says "ties broken by name". If it does not say, you cannot guess safely, so look at the example.
5. **Rounding.** Does the answer need a fixed number of decimal places? Write down how many places and whether you round or truncate.
6. **Empty input.** What should the function return for an empty list or an empty string? Look for a sentence such as "return None if there are no readings". If there is no sentence, the example may show it. Otherwise, write down your decision and test it.
7. **Return or print.** Does the function return a value, or does it print one? A function that prints a number returns `None` to the caller. The grader calls your function and checks the returned value. Printing does not count as returning.
8. **Changing the caller's data.** Does the statement allow you to change the input? If it does not, assume you must not. The caller may use the same list later. Build a new list instead of changing the old one. To change a list means to alter its contents in place, which Python calls mutating it.

:::tip Write the answers before the code
Put the eight answers in a comment at the top of your function. A comment is a line that starts with `#`, and Python ignores it when it runs. If your code later breaks one of the answers, the comment reminds you which rule it broke.
:::

## The edge-case catalogue

An edge case is an input at the boundary of what a function should handle, such as an empty list, a single item, or a number of zero. Code is often correct for ordinary inputs and wrong at the edges. The table lists the edge cases that appear most often in graded labs. For each one, decide what your function should do and write an assert for it, as explained in the next section.

| Edge case | Input type | Example | What it tests |
|---|---|---|---|
| Empty | list, text, dict | `[]`, `""` | Division by zero, index errors, a wrong return for nothing |
| One element | list | `[5]` | Loops that assume at least two items, averages that need pairs |
| Duplicates | list, tuples | `[3, 3, 3]` | Whether your code counts or removes repeats correctly |
| Ties | list of pairs | `("S1", 20)` and `("S2", 20)` | Whether your sort uses the second rule when the first is equal |
| Negative and zero | numbers | `-5`, `0` | Sign errors, division by zero, `if value:` treating 0 as false |
| Missing keys | dict | looking up `"S9"` when it is not there | `KeyError` crashes; use `in` or `get` |
| None | any | `None` inside a list | Calling `.strip()` on `None` crashes |
| Wrong type | any | a number where text is expected | Only handle this if the statement asks for it |
| Whitespace | text | `"  S1 "` | Spaces at the start or end that make `"S1"` and `"  S1 "` differ |
| Upper and lower case | text | `"s1"` and `"S1"` | Whether the same station is counted twice |
| Already sorted | list | `[1, 2, 3]` | Code that only works when the input is in a random order |
| Very large | list | a list of 100,000 items | Slow loops that pass small tests but time out on hidden tests |

Not every edge case applies to every problem. A problem that says "the input is always a non-empty list" removes the empty-input case from your list. Write down which cases apply and which the statement rules out. A rule in the statement is a fact you can rely on. A case you assume without checking is a guess.

:::key Ask what the caller expects, not what you expect
For each edge case, the question is what the statement says the function should return. Your job is not to make the code run without an error. Your job is to return the value the statement asks for.
:::

## Write your own tests first

An assert is a Python statement that checks a condition. If the condition is `True`, Python continues. If the condition is `False`, Python stops the program and raises an `AssertionError`, which is an error that says a check failed. Here is the simplest form:

```python
assert 2 + 2 == 4
```

The `==` symbol means "is equal to". It is a comparison, and it is not the same as `=`, which stores a value in a name. The line above runs silently because `2 + 2 == 4` is true. If you wrote `assert 2 + 2 == 5`, Python would stop with an error.

Turn the example from the statement into an assert first. Suppose the statement says `average_reading([10, 20, 30])` should return `20.0`. Your first assert is:

```python
assert average_reading([10, 20, 30]) == 20.0
```

Then add one assert for each edge case you chose. Do this before you write the function, so the test is not shaped by your code. A test you write after the code often checks what the code already does, not what the statement asks for.

Run the asserts against your function. When they all pass, the program ends with no output. If you add `print("all tests passed")` at the end, you see that line only when every assert passes. Here is what a failed assert looks like when you run the file:

```text
Traceback (most recent call last):
  File "stations.py", line 12, in <module>
    assert average_reading([]) is None
AssertionError
```

The traceback names the file and the line number of the failed assert. Read the line, and then ask what the function returned for that input. You will meet this in the debugging section.

:::trap Using = instead of ==
`assert average_reading([]) = None` is a syntax error, because a single `=` tries to store a value, not compare two values. Use `==` for equal, and `is` when you compare with `None`.
:::

## A full worked example

Here is an original problem in the style of a graded lab. It has three functions. Read the statement first, then the edge-case list, then the asserts, and only then the solution. Do not look at the solution first. The skill being tested is the order of the steps, not the final code.

**The statement.** A city has air-quality sensors at stations with ids such as "S1". Write three functions.

1. `average_reading(values)` takes a list of numbers. It returns the average as a float rounded to one decimal place. If the list is empty, it returns `None`.
2. `top_stations(pairs, n)` takes a list of `(station_id, value)` tuples, and an integer `n`. For each station it computes the average of its values, using `average_reading`. It returns a list of `(station_id, average)` tuples sorted by average, highest first. Ties are ordered by station id, from A to Z. It returns at most `n` tuples. If `n` is zero or less, it returns an empty list. It must not change `pairs`.
3. `clean_ids(ids)` takes a list of strings, which may also contain `None`. It returns a new list. Each id has its surrounding spaces removed and is converted to upper case. Empty ids are dropped, and so are `None` values. An id that appears again is kept only at its first position. The input list must not change.

**The edge-case checklist.** Work through the list before you write code.

- `average_reading`: an empty list (the statement says `None`), one value, a list with a negative and a positive value that sum to zero, and a value that needs rounding to one decimal place. The rounding case is `[1, 1, 2]`, which averages 1.333 and should give 1.3.
- `top_stations`: a tie in average, where the station ids decide the order, and `n` larger than the number of stations. Also `n` equal to zero, `n` negative, an empty input, and a check that the input list is unchanged after the call.
- `clean_ids`: spaces at the start and end, lower-case ids that match upper-case ids, an empty string, a string that is only spaces, a `None`, a duplicate, an empty input, and a check that the input list is unchanged.

**The asserts.** These are the tests you write before the code.

```python
assert average_reading([10, 20, 30]) == 20.0
assert average_reading([1, 2]) == 1.5
assert average_reading([1, 1, 2]) == 1.3
assert average_reading([-5, 5]) == 0.0
assert average_reading([0]) == 0.0
assert average_reading([]) is None

pairs = [("S2", 10), ("S1", 20), ("S3", 15), ("S2", 30)]
copy_of_pairs = list(pairs)
assert top_stations(pairs, 2) == [("S1", 20.0), ("S2", 20.0)]
assert top_stations(pairs, 10) == [("S1", 20.0), ("S2", 20.0), ("S3", 15.0)]
assert top_stations(pairs, 0) == []
assert top_stations(pairs, -1) == []
assert top_stations([], 3) == []
assert pairs == copy_of_pairs

assert clean_ids([" s1 ", "S1", "s2", "", "   ", None, "s3"]) == ["S1", "S2", "S3"]
assert clean_ids([]) == []
raw = [" a "]
assert clean_ids(raw) == ["A"]
assert raw == [" a "]
```

Read the asserts carefully. The line `assert pairs == copy_of_pairs` checks that `top_stations` left the caller's list alone. The `list(pairs)` on the line above it makes a second list with the same contents, so you can compare the two later. The line `assert clean_ids([" s1 ", "S1", ...])` covers five edge cases at once: a lower-case id, a duplicate after upper-casing, an empty string, a string of spaces, and a `None`.

**The solution.** Here is the complete code. It is a tested solution, so the build runs it, and the file must pass all the asserts above.

```python test
def average_reading(values):
    if len(values) == 0:
        return None
    return round(sum(values) / len(values), 1)


def top_stations(pairs, n):
    if n <= 0:
        return []
    by_station = {}
    for station, value in pairs:
        if station not in by_station:
            by_station[station] = []
        by_station[station].append(value)
    averages = []
    for station, values in by_station.items():
        averages.append((station, average_reading(values)))
    averages.sort(key=lambda item: (-item[1], item[0]))
    return averages[:n]


def clean_ids(ids):
    seen = set()
    result = []
    for raw in ids:
        if raw is None:
            continue
        cleaned = raw.strip().upper()
        if cleaned == "" or cleaned in seen:
            continue
        seen.add(cleaned)
        result.append(cleaned)
    return result


assert average_reading([10, 20, 30]) == 20.0
assert average_reading([1, 2]) == 1.5
assert average_reading([1, 1, 2]) == 1.3
assert average_reading([-5, 5]) == 0.0
assert average_reading([0]) == 0.0
assert average_reading([]) is None

pairs = [("S2", 10), ("S1", 20), ("S3", 15), ("S2", 30)]
copy_of_pairs = list(pairs)
assert top_stations(pairs, 2) == [("S1", 20.0), ("S2", 20.0)]
assert top_stations(pairs, 10) == [("S1", 20.0), ("S2", 20.0), ("S3", 15.0)]
assert top_stations(pairs, 0) == []
assert top_stations(pairs, -1) == []
assert top_stations([], 3) == []
assert pairs == copy_of_pairs

assert clean_ids([" s1 ", "S1", "s2", "", "   ", None, "s3"]) == ["S1", "S2", "S3"]
assert clean_ids([]) == []
raw = [" a "]
assert clean_ids(raw) == ["A"]
assert raw == [" a "]

print("all tests passed")
```

**Explanation of the solution, line by line.**

- `def average_reading(values):` starts the function. `values` is the list the caller passes in.
- `if len(values) == 0:` asks the built-in function `len` how many items the list holds. If that number is zero, the condition is true.
- `return None` ends the function at once and gives back `None`. This is the edge-case rule from the statement.
- `return round(sum(values) / len(values), 1)` adds the values with `sum`, divides by the count, and rounds the result to one decimal place. The `/` operator always gives a float in Python 3, so `20.0` is returned and not `20`.
- `def top_stations(pairs, n):` starts the second function. `pairs` is a list of tuples, and `n` is the number of results wanted.
- `if n <= 0:` covers the rule for zero and negative `n`. The symbol `<=` means "less than or equal to".
- `by_station = {}` creates an empty dictionary. A dictionary stores values under keys, here the station id as the key and a list of readings as the value.
- `for station, value in pairs:` loops over the tuples. Python unpacks each tuple into two names, one for the station and one for the value.
- `if station not in by_station:` checks whether the key is already in the dictionary. If not, `by_station[station] = []` creates an empty list for it. Without this check, `by_station[station]` would raise a `KeyError`, which is the missing-key error from the table.
- `by_station[station].append(value)` adds the value to that station's list. `append` puts an item at the end of a list.
- `averages = []` starts an empty list for the results.
- `for station, values in by_station.items():` loops over each key and value pair in the dictionary.
- `averages.append((station, average_reading(values)))` calculates the average for the station and stores it as a tuple. Reusing `average_reading` means the rounding and the empty-list rule are applied in one place.
- `averages.sort(key=lambda item: (-item[1], item[0]))` sorts the list in place. A `lambda` is a short, unnamed function written on one line. Here it tells `sort` what to compare for each item. The key is a tuple. Python compares tuples one element at a time. The first element is the negative average, so a larger average comes first. The second element is the station id, which is used only when two averages are equal. The minus sign turns the highest average into the smallest key, which sorts first.
- `return averages[:n]` returns the first `n` items. The notation `[:n]` is called a slice. If `n` is larger than the list, the slice returns the whole list.
- `def clean_ids(ids):` starts the third function.
- `seen = set()` creates an empty set. A set stores each value at most once, and checking whether a value is in a set is fast.
- `for raw in ids:` loops over the input without changing it.
- `if raw is None: continue` skips `None` values. `continue` jumps to the next item of the loop.
- `cleaned = raw.strip().upper()` removes the spaces at both ends with `strip`, then converts the text to upper case with `upper`. The two methods are chained, so the result of `strip` is passed to `upper`.
- `if cleaned == "" or cleaned in seen: continue` skips empty ids and ids already seen. The word `or` means that either condition can cause the skip.
- `seen.add(cleaned)` remembers the id, and `result.append(cleaned)` adds it to the new list.
- `return result` gives back the new list. The input list was never changed.
- The asserts at the end check the functions. The final `print` runs only if every assert passed, and it prints `all tests passed`.

**Expected output.** Running the file prints one line:

```text
all tests passed
```

If any assert fails, you see a traceback and no final line.

## Debugging when a test fails

A failed test is information, not a disaster. Work through the same steps each time, so you do not guess.

1. **Read the failing line.** The traceback names the line number of the assert. Look at the inputs in that assert, and nothing else.
2. **Print the inputs and the result.** Put a `print` line before the assert that shows what the function returns. A `print` statement shows a value on the screen while the program runs. For example, `print(average_reading([]))` shows `None` if the guard works, or an error if it does not.
3. **Shrink the case.** Replace a large input with the smallest input that still fails. If `top_stations` fails on ten pairs, try with two. A small case is easier to reason about by hand.
4. **Check the types.** Ask Python what kind of value it has. `print(type(value))` shows the type. Many failures come from getting a tuple when you expected a list, or a float when you expected an int.
5. **Walk through the code by hand.** Write down the variables after each line, as the trace below does. Most bugs show up in the first few lines where the value changes unexpectedly.

The animation below follows a function on the empty list. Before the guard was added, the same call stopped the program. Here is what that run prints:

```term
$ python mean_demo.py
Traceback (most recent call last):
  File "mean_demo.py", line 5, in mean
    return total / len(values)
ZeroDivisionError: division by zero
```

The error happens because `len(values)` is zero, and dividing by zero is not allowed. The fix is a guard, which is an `if` check placed before the risky line. The animation below uses the function with the guard added. It shows the empty call returning `None` at line 3, and the non-empty call passing.

```trace
TITLE: Empty list fails without a guard, passes with one
CODE:
def mean(values):
    if len(values) == 0:
        return None
    total = sum(values)
    return total / len(values)
result = mean([])
print(result)
result = mean([2, 4])
print(result)
STEPS:
6 :: values not set yet; result not set yet :: Line 6 calls mean with an empty list.
1 :: values=[] :: Python enters mean and binds values to the empty list.
2 :: values=[] :: len(values) is 0, so the test is True.
3 :: values=[] :: The guard returns None. Without line 2, line 5 would divide by zero.
6 :: values=[]; result=None :: The returned None is stored in result.
7 :: result=None :: print shows None on the screen.
8 :: result=None :: Second call, this time with a list that has two values.
1 :: values=[2, 4] :: Python enters mean again with a new list.
2 :: values=[2, 4] :: len is 2, so the test is False and the guard is skipped.
4 :: values=[2, 4]; total=6 :: sum adds 2 and 4.
5 :: values=[2, 4]; total=6 :: 6 divided by 2 gives 3.0, which is returned.
8 :: values=[2, 4]; result=3.0 :: The returned value is stored in result.
9 :: result=3.0 :: print shows 3.0. Both the empty and the non-empty call now pass.
```

:::key A guard is a check, not a patch
A guard does not hide the problem. It makes the function return the value the statement asks for in a case the arithmetic cannot handle. Always decide what the guard should return, based on the statement, before you add it.
:::

:::trap Printing instead of returning
If your function prints the answer and does not return it, the visible tests may show nothing wrong when you run the file yourself, yet every test fails. The grader reads the value from `return`. Use `print` only for debugging, and remove it before you submit.
:::

## Fast enough

The 30-second limit means your code must scale. Scaling describes how the work grows when the input grows. Computer scientists write this as O(n), read "big O of n", where n is the number of items. An O(n) function does roughly n steps for n items. Doubling the input roughly doubles the work. An O(n squared) function does roughly n times n steps. Doubling the input roughly quadruples the work.

In practice, a list of 100 items means 10,000 steps for O(n squared). A list of 100,000 items means about 10,000,000,000 steps. A typical computer runs far fewer steps than that in 30 seconds in Python. The same code with a single loop needs only 100,000 steps for the same list.

The most common cause of a slow solution is a loop inside another loop over the same list. Here is a check for duplicates written that way:

```python
def has_duplicate_slow(items):
    for i in range(len(items)):
        for j in range(len(items)):
            if i != j and items[i] == items[j]:
                return True
    return False
```

The outer loop picks each position `i`. The inner loop checks every other position `j` against it. The expression `range(len(items))` makes the numbers 0, 1, 2, and so on up to the last index. The `!=` symbol means "is not equal to". The function is correct, but it is O(n squared).

The faster version uses a set. A set answers the question "have I seen this value?" in roughly one step, no matter how big the set is.

```python
def has_duplicate_fast(items):
    seen = set()
    for item in items:
        if item in seen:
            return True
        seen.add(item)
    return False
```

The loop runs once over the items. For each item, `in seen` checks the set, and `seen.add(item)` stores it for later. The work grows in line with n, so this is O(n). Both functions return `True` for `[1, 2, 1]` and `False` for `[1, 2, 3]`, but only the second one finishes on a 100,000-item hidden test.

Dictionaries work the same way. A dictionary lookup such as `by_station[station]` takes about one step, so counting or grouping with a dictionary is much faster than searching a list again for each item.

:::tip Name the cost before you submit
Before you press submit, look at each loop in your code and ask how many times it runs. If one loop sits inside another over the same list, look for a set or a dictionary that removes the inner loop.
:::

## Multiple-choice technique for case-study questions

A case-study question gives you a short scenario and then asks what to do, what happens, or which design is right. The scenario usually contains one constraint that decides the answer. Find that constraint first.

Read the scenario for the constraint. Words such as "first attempt", "at least", "no more than", "without changing", and "during the test" are constraints. An answer that ignores the constraint may sound sensible and still be wrong.

Eliminate before you choose. Read all four options, and cross out any that contradict the scenario. Two options are often close. Ask which one fits the constraint exactly, and which one only sounds reasonable.

Watch for absolute words. Options that use "always", "never", "only", "all", or "every" are often false, because real systems usually have exceptions. Options with "usually", "often", or "may" are more often true. This is a tendency, not a rule, so check the option against the scenario.

Use two passes. On the first pass, answer every question you can answer quickly, and mark the rest with a note, if the interface allows marking. On the second pass, spend your remaining time on the marked questions. Do not spend a long time on one question at the start of the quiz, because the questions at the end need the same care.

:::trap Choosing the option you can explain best
Students often pick the option that uses the most familiar word. Examiners write a tempting wrong option that uses the right vocabulary but answers a different question. Check that the option answers the question in the scenario, not a neighbouring question.
:::

## The first-attempt routine

Use the numbered checklists below. They are short on purpose, so you can run them every time.

**For a graded lab.** Work through these steps before you press submit.

1. Read the problem statement with the eight questions from the section on reading statements.
2. Write the edge-case list for each function, and note which cases the statement rules out.
3. Write the asserts for the examples and the edge cases, before you write the function.
4. Write each function, one at a time, and run the asserts after each one.
5. Check the speed. Look at each loop, and remove any loop nested inside another over the same data.
6. Check that no function prints the answer instead of returning it, and remove leftover `print` lines that you used for debugging.
7. Check that no function changes its input, by running the `copy_of_pairs` style check for each input list.
8. Run the whole file once more, from the top, in a fresh run. A fresh run catches a function that only worked because of an earlier one.
9. Only then press submit.

**For a day quiz.** Work through these steps during the quiz.

1. Read the first question's scenario and find the constraint before you read the options.
2. Eliminate options that contradict the scenario.
3. Check the absolute words in the options that remain.
4. Choose one answer and move on, or mark the question if you are unsure.
5. In the second pass, return to the marked questions and make a final decision.
6. Before you press submit, check that every question has an answer. A blank answer is always wrong.

:::key The first attempt is the one that counts
Because the skill score uses the first attempt, the routines above are designed to run before submission. Use the time you have before the first press to reduce the errors you can find yourself.
:::

Answer each question without looking back at the chapter. The explanation follows each answer, so you can see why the right option is right.

```quiz
Q: A graded lab has visible tests and hidden tests. Which statement about the marks is correct?

- Hidden tests only check the speed, so they carry no marks.
- The split changes every time you submit, so it cannot be planned for.
WHY: Visible tests carry roughly 50 to 85 per cent of the marks, and hidden tests carry the rest. The first option is tempting because the visible tests look like the whole task, but the rest of the marks sit with the hidden tests.

Q: A student's function prints the average instead of returning it. Why does this lose marks?
- Printing is faster, so the grader prefers it.
- Printed text is saved to a database automatically.
- The grader does not run the function at all.
* The grader calls the function and reads the returned value, and print returns None.
WHY: A function that only prints gives the caller None, so the check on the returned value fails. Printing is useful for debugging, but it is not how the grader reads the answer.

Q: A function must not change the list the caller passes in. Which approach meets this?
* Build and return a new list, and leave the input list untouched.
- Call sort on the input list and return it.
- Remove duplicates from the input list with remove inside a loop over the same list.
- Change every item to upper case in the input list and return that list.
WHY: Methods such as sort and remove change the list in place, so the caller sees the change. The correct approach builds a new list. The sort option is tempting because it returns a sorted list, but it also changes the caller's list.

Q: The statement says that for an empty list the function must return None. Which guard does this?
- if len(values) == 0: return 0
- if values == "": return None
* if len(values) == 0: return None
- if values is None: return []
WHY: Checking the length of the list and returning None matches the statement. Returning 0 is the most tempting wrong option, because it sounds like an average of nothing, but the statement asks for None.

Q: Which description of an edge case is best?
- A case the program handles every day without any thought.
* An unusual input, such as an empty list, a duplicate, or a zero, where code often goes wrong.
- A test that runs for longer than 30 seconds.
- A bug that appears only in the terminal.
WHY: An edge case is a boundary input. It is where code tends to fail, so you test it on purpose. The option about time is tempting because the time limit matters, but it describes speed, not an edge case.

Q: A function has a loop inside another loop, and both loops run over the same list of 100,000 items. What is the main concern?
- It uses too little memory to be correct.
- It always returns the wrong answer for lists of that size.
- It needs no tests because the loops cancel each other out.
* It does roughly n times n steps, so it may exceed the 30-second limit on the hidden tests.
WHY: A nested loop over the same list is O(n squared), which means about 10 billion steps for 100,000 items. The first option is a distractor about memory, which is not the issue here.

Q: You need results sorted by average, highest first, with ties ordered by station id from A to Z. Which sort key is right?
* key=lambda item: (-item[1], item[0])
- key=lambda item: (item[1], item[0])
- key=lambda item: (-item[1], -item[0])
- key=lambda item: item[0]
WHY: The minus sign on the average puts the highest first. The station id without a minus sign sorts A to Z for the ties. The second option is the most tempting, because it looks almost the same, but it sorts the averages lowest first.

Q: You have a lab you could submit now, but you have not checked your edge cases. What is the right use of the first attempt?
- Submit now to see what happens, then fix the problems.
- Skip the visible tests and go straight to the hidden tests.
* Write and run the edge-case checks first, then submit.
- Submit three times with small changes until the score improves.
WHY: The skill score uses your first attempt, and a second attempt does not replace it. Checking edge cases before the first submission is the only way to make that attempt count. The option about submitting now is tempting because it looks like learning, but it uses up the attempt that counts.
```

## Flashcards

```cards
visible test :: A check you can read. It calls your function, compares the result with the expected value, and reports pass or fail.
hidden test :: A check you cannot read. It uses inputs the course team chose, often the edge cases, and carries the rest of the marks.
assert :: A Python statement that stops the program with AssertionError when its condition is false.
edge case :: An input at the boundary of what a function should handle, such as an empty list, a zero or a duplicate.
guard :: An if check placed before a risky line, which returns early or handles the bad case first.
None :: Python's word for no value. A function that prints but does not return gives back None.
tuple :: A fixed group of values in round brackets, such as ("S1", 20.0). Tuples are compared one element at a time.
O(n squared) :: A running time that grows with the square of the input size. Nested loops over the same list often cause it.
set :: A collection that stores each value once, and checks membership quickly with the in keyword.
first attempt :: The submission that counts for the skill score. Preparing before the first submission matters more than retrying.
```
