## Y2-T26 · Build chart pack v1: 3 insight-titled charts with safe limits

*Session 26 · phase M5 · 3 points*

### The ticket in plain words

CityPulse is the Bengaluru city-data platform your squad is building. It turns raw air-quality readings into information that city officials can act on. Your squad has already cleaned the data (T14 and T15), explored it (T24) and checked the pipeline (T25). This ticket turns that exploration into charts other people can read.

You will make three charts, one for each strongest observation. Each uses the right chart type, has no clutter, uses colour-blind safe colours, draws the national PM2.5 limit as a reference line, and has a title that states the takeaway with a number computed from the data.

The reason is a famous failure. In 1986 the Space Shuttle Challenger was launched in cold weather, despite engineers' concerns about its seals, and it broke apart after take-off. The right data in the wrong chart can hide a fatal risk. Your readers, such as the ward health officer, have seconds per chart. If they must study the axes to find the risk, the chart has failed.

### How your trainer checks it

The trainer runs the four test cases from the repository root on the lab Linux machine. The commands also work in Git Bash. Run each one yourself first.

**Acceptance criteria.**

- **AC1.** Exactly three PNGs exist in `reports/charts/`, each made by a function in `src/citypulse/charts.py`, and `python reports/charts/make_charts.py` regenerates them from the repo root. Checked by TC1.
- **AC2.** Each title is a full-sentence insight with a number computed from the data. Checked by TC2 and by reading the titles.
- **AC3.** Each chart that plots PM2.5 has a reference line at the config key `pm25_24h_limit`, labelled with its source. Checked by looking at the PNG.
- **AC4.** A stranger from another squad states each insight within five seconds, recorded in `reports/charts/README.md`. Checked by TC4.
- **AC5.** One accent on a grey base, from a colour-blind safe palette, with no rainbow colormap. Checked in the colour constants of `charts.py`.

**TC1: the count of PNG files.** The command is:

```
rm reports/charts/*.png && python reports/charts/make_charts.py && ls reports/charts/*.png | wc -l
```

- `rm reports/charts/*.png` deletes every PNG in the folder. The `*` wildcard is expanded by the shell into the matching file names.
- `&&` runs the next command only if the previous one succeeded.
- `python reports/charts/make_charts.py` rebuilds the PNGs. It prints nothing.
- `ls reports/charts/*.png | wc -l` lists the PNGs and counts the lines, one per file.

Passing output is a single number, 3:

```term
$ rm reports/charts/*.png && python reports/charts/make_charts.py && ls reports/charts/*.png | wc -l
3
```

Failing output and its usual cause:

- `rm: cannot remove 'reports/charts/*.png': No such file or directory`. No PNG existed yet, so the chain stopped. Run `python reports/charts/make_charts.py` once, then TC1 again.
- `2` or `4`. A `savefig` call is missing, or two charts share a file name.
- `ModuleNotFoundError: No module named 'citypulse'`. The script cannot find `src`. See Stage 2 of Y2-T26.5.

**TC2: the titles are f-strings.** The command is:

```
grep -n 'set_title(' src/citypulse/charts.py
```

- `grep` searches a file for text. `-n` prints line numbers.
- `'set_title('` is the text to find. The quotes stop the shell from reading the bracket.
- `src/citypulse/charts.py` is the file searched.

Passing output has one line per chart, such as `21:    ax.set_title(f"Daily PM2.5 went over the limit on {over} of {total} days")`. No output means the titles use another method, such as `ax.set(title=...)`. A line with plain quotes and no `f` means a hard-coded title.

**TC3: the tests pass.** The command is:

```
pytest -q tests/test_charts.py
```

- `pytest` runs the tests in the file. `-q` prints one dot per passing test instead of a full report.

Passing output ends with a summary such as `3 passed in 0.42s`. Failing outputs: `AssertionError` means a title has no digit. `AttributeError: 'NoneType' object has no attribute 'axes'` means the function does not `return fig`. `ERROR collecting` followed by `ModuleNotFoundError` means pytest cannot find `src`.

**TC4: the 5-second test.** The trainer shows one PNG to a student from another squad for five seconds, then asks for the takeaway. A pass sounds like "the limit was passed on nine of thirty days". A fail sounds like "it is about pollution". Practise it in Y2-T26.6.

#### Y2-T26.2 The limits file

**Goal.** Create `config/limits.yaml` with the limit and its source.

**Stage 1: the format.** YAML stores `key: value` lines. A `#` starts a comment, which is where the source goes:

```yaml
pm25_24h_limit: 60   # µg/m³, 24-hour PM2.5 standard; cite the source your squad uses
```

The key `pm25_24h_limit` is the name your code asks for. [Day 18 — Exploratory analysis and data visualisation](D18.html) gives the course's source for the 60 µg/m³ value, the CPCB National Ambient Air Quality Standards (2009).

**Stage 2: check that it reads.**

```
python -c "import yaml; print(yaml.safe_load(open('config/limits.yaml', encoding='utf-8'))['pm25_24h_limit'])"
```

`encoding='utf-8'` matters on Windows, because the comment contains the character µ. `yaml.safe_load` reads the file into a dictionary, and `['pm25_24h_limit']` picks the value. Expected output: `60`.

**Check.** The command prints `60`. Then write one insight sentence per chart in your PR draft, with blanks for numbers you will compute later.

#### Y2-T26.3 The charts module

**Goal.** Create `src/citypulse/charts.py` with `style(ax)` and chart functions that take a DataFrame and a limit.

**Stage 1: the style helper.**

```python
GREY = "#8C8C8C"    # neutral base colour
ACCENT = "#0072B2"  # the one emphasis colour, from the Okabe-Ito palette
INK = "#222222"     # text and the reference line

def style(ax):
    ax.spines[["top", "right"]].set_visible(False)
    ax.tick_params(colors=INK)
```

`def style(ax):` takes one axes. The first body line hides the top and right borders, which is decluttering. The second makes the tick labels dark grey.

Check it compiles with `python -m py_compile src/citypulse/charts.py`. Expected output: nothing.

**Stage 2: a function skeleton.** Each chart creates its own figure, so no state leaks between charts. [Day 18](D18.html) explains that trap.

```python
import matplotlib.pyplot as plt
import pandas as pd

def days_over_limit_chart(daily: pd.DataFrame, limit: float):
    fig, ax = plt.subplots(figsize=(8, 4))
    style(ax)
    # your drawing lines go here (Y2-T26.4)
    return fig
```

`plt.subplots(...)` creates one figure and one axes, sized in inches. `style(ax)` applies the helper. `return fig` hands the figure back, so the caller can save or test it.

**Stage 3: no file paths.** The function never opens or saves a file, so the dashboard (Y2-T28) and the report (Y2-T29) can reuse it. Check with `python -m py_compile src/citypulse/charts.py`, which prints nothing.

#### Y2-T26.4 Own one chart

**Goal.** Pick the type from the question, declutter, draw the limit line with its source, and compute the title.

**Stage 1: choose the type.** Change over time needs a line, comparing categories needs a sorted bar, and two numbers' relation needs a scatter.

**Stage 2: count the days over the limit.** The title needs a number, so write a small helper. This block is run by the check command.

```python test
def count_over_limit(values, limit):
    """How many values are strictly above the limit."""
    return sum(1 for v in values if v > limit)

assert count_over_limit([50, 65, 60, 72], 60) == 2
assert count_over_limit([], 60) == 0
assert count_over_limit([60, 60], 60) == 0
```

`sum(1 for v in values if v > limit)` adds 1 for each value above the limit. `>` is strict, so a value on the limit does not count. A passing run prints nothing.

```trace
TITLE: Counting the days over the limit
CODE:
values = [50, 65, 60, 72]
limit = 60
over = 0
for v in values:
    if v > limit:
        over += 1
STEPS:
1 :: values=[50, 65, 60, 72] :: Four daily means, one per day.
2 :: values=[50, 65, 60, 72]; limit=60 :: The limit comes from the config file, not typed into the chart.
3 :: values=[50, 65, 60, 72]; limit=60; over=0 :: The count starts at zero.
4 :: v=50; over=0 :: The loop takes the first day.
5 :: v=50; over=0 :: 50 is not above 60, so the test is false.
4 :: v=65; over=0 :: The loop takes the second day.
5 :: v=65; over=0 :: 65 is above 60, so the test is true.
6 :: v=65; over=1 :: The count goes up by one.
4 :: v=60; over=1 :: The third day is exactly 60.
5 :: v=60; over=1 :: 60 is not above 60, so the count stays at 1.
4 :: v=72; over=1 :: The loop takes the fourth day.
5 :: v=72; over=1 :: 72 is above 60.
6 :: v=72; over=2 :: The count reaches 2.
```

**Stage 3: the limit line and the title.** Put `count_over_limit` (without the `assert` lines) in `charts.py`, above your chart functions. Then add these lines inside your function, after your own drawing code:

```python
over = count_over_limit(daily["pm25_mean"], limit)
ax.axhline(limit, color=INK, linestyle="--",
           label=f"CPCB 24-hour limit {limit:g} µg/m³ (source: limits.yaml)")
ax.set_title(f"Daily PM2.5 went over the limit on {over} of {len(daily)} days")
ax.legend(frameon=False)
```

`count_over_limit` computes the number from the data, so the title is never typed by hand. `axhline` draws the horizontal limit line. A dark dashed line keeps the palette to one accent. `:g` prints 60 rather than 60.0. `set_title(f"...")` puts the number into the title. Use your own column name in place of `daily["pm25_mean"]`.

**Stage 4: declutter and colour.** Draw the data in `GREY` and the emphasis in `ACCENT`. Then run `grep -n 'set_title(' src/citypulse/charts.py` and confirm your line is an f-string.

### Defend it in the viva

**Why must each title be computed from the data rather than typed?**

:::answer Model answer
A typed number goes false when the data is refreshed, so the chart then misleads officials. A title built from the same variables as the plot stays in step with it. This is why TC2 looks for f-strings on the `set_title` lines.
:::

**What trade-off did you make by using daily averages for the limit line instead of hourly readings?**

:::answer Model answer
The 24-hour standard applies to a 24-hour average, so daily means are the fair comparison. The cost is that a one-hour spike averages away. I would say so in the README rather than hide it.
:::

**Why does `charts.py` take a DataFrame and a limit rather than a file path?**

:::answer Model answer
A function with no file paths can be tested with a small table in memory, and the dashboard in T28 and the report in T29 can reuse it. Only `make_charts.py` knows where files live.
:::

**Why one accent colour on a grey base?**

:::answer Model answer
One accent tells the reader where to look, and a colour-blind safe palette has few distinct colours.
:::

**Walk me through a chart you made, and which commit added it.**

:::answer Model answer
A fictional example: for bus delays, the question was how delays change over the day, so I chose a line. I removed the borders, drew one dashed limit line with its source, and computed the title from the count of late buses. Give your own chart and your commit id from `git log --oneline`.
:::

## Y2-T27 · DSA-4: trees, graphs, heaps + proctored DSA 1–4 checkpoint

*Session 27 · phase DSA · 5 points*

### The ticket in plain words

CityPulse is the Bengaluru city-data platform your squad builds. Two of its features need data structures that are not simple lists.

The first is a shortest bus route between wards. A city's roads, stops or sensor links form a **graph**: a set of points (called **nodes**) joined by lines (called **edges**). To find the route with the fewest stops, you walk the graph outwards from the start, one layer at a time. That method is called **breadth-first search (BFS)**.

The second is a live widget that shows the five most polluted stations. Sorting every station to find five of them does more work than you need. A **heap** is a structure that always gives you the smallest item at the front, so you can keep only the largest k values while you read through the data. That is the **top-k** method.

**Stage 3. Learn the technique with a worked example.** BFS works by keeping a queue of stops to visit, and a record of stops already reached. The test below is a complete, small, tested version for a different network. Read it, then write your own from the idea, not from this text:

```python test
from collections import deque

def fewest_hops(links, start, goal):
    if start == goal:
        return 0
    seen = {start}
    q = deque([(start, 0)])
    while q:
        stop, hops = q.popleft()
        for nxt in links.get(stop, []):
            if nxt == goal:
                return hops + 1
            if nxt not in seen:
                seen.add(nxt)
                q.append((nxt, hops + 1))
    return None

links = {"A": ["B", "C"], "B": ["D"], "C": ["D"], "D": ["E"], "X": []}
assert fewest_hops(links, "A", "E") == 3
assert fewest_hops(links, "A", "A") == 0
assert fewest_hops(links, "A", "X") is None
assert fewest_hops({}, "A", "B") is None
```

Line by line. `deque` gives a queue whose `popleft()` is fast. `seen` marks each stop the moment it is queued, so no stop enters twice. Each queue item carries its hop count. `links.get(stop, [])` returns an empty list for a stop with no links, so a missing stop does not crash. The four `assert` lines check a route, a start equal to the goal, an unreachable stop, and an empty network. If all four pass, the program prints nothing and exits normally. Run it on Linux with `python3 file.py`, or in Git Bash with `python file.py`.

The queue moves like this:

```flow
TITLE: How the queue finds the fewest hops from A to E
NODES: Queue | Stop checked | Seen record | Answer
STEPS:
1>2 :: pop A :: A leaves the front. Its neighbours are B and C.
2>3 :: B and C are new :: Both are marked seen and queued with 1 hop.
3>1 :: queue B, C :: The queue now holds B then C.
1>2 :: pop B :: B leaves the front. Its neighbour D is new.
2>3 :: D is new :: D is marked seen and queued with 2 hops.
1>2 :: pop C :: C is next. Its neighbour D is already seen, so it is skipped.
1>2 :: pop D :: D leaves the front. Its neighbour E is the goal.
2>4 :: E found, 3 hops :: The search returns 3 without checking anything else.
```

:::trap Marking stops as seen only when they leave the queue
If you mark a stop when it is popped, the same stop can enter the queue many times, and the search gets slow. Mark it the moment you queue it, as the example does.
:::

**Stage 3. Keep a size-k min-heap.** A min-heap keeps the smallest item at index 0. Push each reading. When the heap holds more than k items, pop the smallest, because it cannot be in the top k. This sets the size to k, which gives O(n log k). Here is a worked example on a different set of four readings, with k set to 2:

```trace
TITLE: Keeping the two largest of four readings
CODE:
1 import heapq
2 heap = []
3 for v, s in [(30, "A"), (75, "B"), (52, "C"), (18, "D")]:
4     heapq.heappush(heap, (v, s))
5     if len(heap) > 2:
6         heapq.heappop(heap)
7 print(sorted(heap, reverse=True))
STEPS:
2 :: heap=[] :: Start with an empty list. heapq treats it as a min-heap.
3 :: v=30; s="A"; heap=[] :: The loop takes the first pair.
4 :: v=30; s="A"; heap=[(30, "A")] :: Pushed. Line 5 then finds 1 item, which is not more than 2, so nothing is removed.
3 :: v=75; s="B"; heap=[(30, "A")] :: The loop takes the second pair.
4 :: v=75; s="B"; heap=[(30, "A"), (75, "B")] :: Pushed. 30 stays at index 0. Line 5 finds 2 items, not more than 2, so nothing is removed.
3 :: v=52; s="C"; heap=[(30, "A"), (75, "B")] :: The loop takes the third pair.
4 :: v=52; s="C"; heap=[(30, "A"), (75, "B"), (52, "C")] :: Pushed. The smallest, 30, is still at the root.
5 :: v=52; s="C"; heap=[(30, "A"), (75, "B"), (52, "C")] :: Three items is more than 2, so the smallest must go.
6 :: v=52; s="C"; heap=[(52, "C"), (75, "B")] :: heappop removes 30 from the root. The two largest so far remain.
3 :: v=18; s="D"; heap=[(52, "C"), (75, "B")] :: The loop takes the fourth pair.
4 :: v=18; s="D"; heap=[(18, "D"), (75, "B"), (52, "C")] :: Pushed. 18 is the smallest, so it moves up to the root.
6 :: v=18; s="D"; heap=[(52, "C"), (75, "B")] :: Line 5 sees 3 items, so heappop removes 18 straight away.
7 :: heap=[(52, "C"), (75, "B")] :: sorted(..., reverse=True) lists the pairs largest first and prints them.
```

Line by line, the key points are these. `heapq.heappush` adds an item and keeps the smallest at the root. `heapq.heappop` removes and returns the root. Because the heap holds at most k+1 items at any moment, it never grows with the number of readings. Running the trace prints `[(75, 'B'), (52, 'C')]`.

Now write the same loop in your script, with `(pm25, station)` tuples and `k = 5`. Feed it from your `latest` dictionary, so each station is counted once: loop over `latest.items()` and build each tuple from the stored number. Tuples compare by their first item, so the heap orders by reading.

:::trap Using a heap of every reading
Pushing all readings into one heap and never popping costs O(n log n) and keeps every reading in memory. Pop whenever the heap grows past k.
:::

### Defend it in the viva

**1. Why does BFS give the fewest hops, when DFS does not?**

:::answer Model answer
BFS visits every stop at distance one before any stop at distance two, because the queue holds stops in the order they were reached. So the first time it dequeues the goal, the route has the fewest edges. DFS follows one branch deeply before it backs up, so the first route it finds can be longer than the shortest one. The key idea is the order of the queue, not the code layout.
:::

**2. What is the trade-off between a size-k heap and sorting every reading?**

:::answer Model answer
Sorting all n readings costs O(n log n) and keeps every reading in memory. A size-k min-heap costs O(n log k) and holds at most k+1 items. The trade-off is that the heap gives you the top k only. If you later need the full ranking of every station, you have to sort, so the choice depends on what the widget needs to show.
:::

**3. What did you write yourself in topk_heap.py, and how did you prove it works?**

:::answer Model answer
Give the stage you wrote, the test that proved it, and one fix you made. A good shape is: "I wrote the skip condition and the heap loop. I proved the blank handling by running the script on a file with a blank row and confirming no ValueError. I proved the order with the sorted assertion and the TC2 command, which printed five descending lines." Use your own stage and your own evidence.
:::

**4. What do heappush and heappop keep true, and why is the smallest item at index 0?**

:::answer Model answer
A heap is a list arranged so that each parent is no larger than its children. heappush adds an item and moves it up until the rule holds. heappop removes the root, which is the smallest item, then moves the last item to the root and sifts it down. Because of that rule, the root is always the smallest, so the heap can discard it in one step when it holds more than k items.
:::

**5. Which edge cases did you test, and why do they matter for a graph?**

:::answer Model answer
An empty graph, a single node and a disconnected graph. An empty graph checks that the code does not crash when there is nothing to visit. A single node checks that a start equal to the goal returns the right answer without a loop. A disconnected graph checks the path that returns None when the goal cannot be reached, which is the case most often forgotten.
:::

#### Y2-T28.1 Aggregate the hourly data into daily station means

**Goal.** Produce one file, `daily_station.parquet`, with one row for each station and each IST day. Each row holds the mean PM2.5 for that day and `n_hours`, the number of real hourly readings behind it. Upload the file to `clean/agg/daily_station/`.

**Technique 1: IST dates.** Stored timestamps are in UTC. A reading at 20:00 UTC on 16 November happened at 01:30 IST on 17 November. If you group by the UTC date, that reading lands on the wrong day. So you convert to IST first. The trace below follows one such timestamp.

```trace

CODE:

IST = timezone(timedelta(hours=5, minutes=30))
moment = datetime.fromisoformat("2026-11-16T20:00:00").replace(tzinfo=timezone.utc)
local = moment.astimezone(IST)
day = local.date().isoformat()
STEPS:
1 :: none yet :: The import brings in the datetime tools.
2 :: IST=UTC+05:30 :: IST is a fixed offset of five and a half hours. India has no daylight saving.
3 :: IST=UTC+05:30; moment=2026-11-16 20:00 UTC :: The text is read as a time and labelled as UTC.
4 :: IST=UTC+05:30; moment=2026-11-16 20:00 UTC; local=2026-11-17 01:30 +05:30 :: The same instant is shown in IST, so the clock moves past midnight.
5 :: local=2026-11-17 01:30 +05:30; day="2026-11-17" :: The date that comes out is 17 November.
```

**Technique: how Streamlit reruns.** Streamlit runs the whole script from the top every time a control changes. Caching stops the slow S3 read from repeating each time. Section Y2-T28.4 relies on the cache, so keep the S3 read inside a function.

**Stage 1: a page that renders.**

**Stage 2: the cached loader.**

```python
import pandas as pd

@st.cache_data(ttl=600)
def load_daily():
    aws = st.secrets["aws"]

        f"s3://{aws['bucket']}/clean/agg/daily_station/daily_station.parquet",
```

**Stage 3: a date filter with a guard.** Add these lines after `daily = load_daily()`. The guard handles an incomplete selection.

```python
from datetime import timedelta

daily["day"] = pd.to_datetime(daily["day_ist"]).dt.date
latest = daily["day"].max()
picked = st.date_input(
    "Date range",
    value=(max(daily["day"].min(), latest - timedelta(days=6)), latest),
    min_value=daily["day"].min(),

)

    st.info("Pick a start date and an end date to see the numbers.")

```

The `max(...)` in the default keeps the start date inside the data, so the page still opens if the data covers fewer than seven days. `st.date_input` with a pair of default dates returns a tuple. `view` keeps the rows inside the selected range. The comparison `>=` and `<=` includes both ends. Never change `daily` in place. Create a new variable instead, so the cached table stays intact.

### Defend it in the viva

**Q1. Why does the dashboard read the daily aggregate, and not the hourly table?**

:::answer Model answer
The daily table has one row per station per day, so the file is much smaller and the page loads inside the five-second limit on a phone. The KPIs are defined per day, so the daily table already has the level of detail they need. Reading the hourly table would make every click slower for no gain in what the officer sees. The trade-off is that an hourly spike is averaged into its day, so the dashboard cannot show it. That is acceptable here because the advisory decision is made per day.
:::

**Q2. What is the trade-off in setting the cache time to 600 seconds?**

:::answer Model answer
A longer time saves more S3 reads and makes the page faster for everyone. The cost is freshness: the dashboard can show data up to ten minutes old. A shorter time keeps data fresher but reads S3 more often. For a daily advisory, ten minutes is a sensible balance, and you should say so out loud. The choice is a decision you can explain, not a fact to memorise.
:::

**Q3. Which part of this ticket did you personally build, and how did you test it?**

:::answer Model answer
A strong answer names one subtask, the commits you made for it, and the test you ran for each stage. It also points to the exact output you pasted into the pull request. It does not claim work that a teammate did, and it does not say you did something you did not. Practise by naming your subtask, your commit messages in order, and the test case that proves your part.
:::

**Q4. Why does the dashboard use a read-only identity, and why must its keys stay out of Git?**

:::answer Model answer
The principle is least privilege. A dashboard only needs to read, so if its keys leak, the damage is limited to reading the aggregate files. If it used the pipeline keys, a leak could overwrite the data. Keys in Git are copied to every clone and stay in the history even after deletion, so rotation would be needed. The `AccessDenied` test and gitleaks check both parts of this.
:::

**Q5. How do you know the three KPIs really change when the date range changes?**

:::answer Model answer
Each KPI is computed from the filtered table `view`, not from the full daily table, so a new range gives new inputs. The comparison uses the previous block of equal length, which the `previous_window` rule computes. The trainer's TC5 check, and your own run in Y2-T28.5, show the values changing. If the numbers stayed the same, the code would be reading the unfiltered table.
:::

Break it into parts:

- `v_[a-z0-9_]+` matches a view name: `v_` followed by lower-case letters, digits or underscores.
- `KPI` matches the word KPI.

### Defend it in the viva

**1. Why does the report open with the recommendation rather than the method?**

:::answer Model answer
The report follows the pyramid principle: answer first, then reasons, then detail. The reader is a decision-maker who must act on the report or reject it, so they need the action, the owner and the measure first. The reasons and method then show why the recommendation holds. If the method came first, a busy reader might stop before reaching the action.
:::

**2. What is the trade-off of one clear recommendation?**

:::answer Model answer
A single recommendation is clear and owned, so it can be acted on. The cost is that it can hide other options and the uncertainty behind it. The report handles this with a limitations section that names each limitation and its effect on the conclusion, and with next steps that would test the recommendation. A clear message and an honest limitations section work together.
:::

**3. What did you personally do in this ticket?**

:::answer Model answer
Answer with facts from your own work. Name the section you wrote, the commits you made and their messages, the numbers you checked against the dashboard or view, and the review comments you wrote with the criterion each one used. The answer should match the Git history and the PR page. Describe only work you did. The trainer checks the commits against what you say.
:::

**4. How does a reader check that a number in your report is supported?**

:::answer Model answer
Every line with a digit links to a chart file, names a SQL view or cites a KPI. The reader opens the link or runs the named view and compares the figure. TC1 checks that every such line has one of the three. A person then checks that the link or view really shows that figure. A link that exists but shows a different number is still a failure.
:::

**5. Which limitation would most change your conclusion, and why?**

:::answer Model answer
Pick the limitation that would reverse the recommendation if it were wrong. For example, if the data covers one season, a seasonal effect could explain the trend, and the recommendation would then be unsafe. Explain the likely effect, how large it could be, and what data would settle it. A limitation with a named effect helps the reader; a list of caveats with no effect does not.
:::

**TC1: no unresolved review threads on the report PR.**

```
gh pr view <report-pr> --json reviewThreads --jq '[.reviewThreads[] | select(.isResolved | not)] | length'
```

- `gh pr view <report-pr>` asks GitHub for one PR. Replace `<report-pr>` with its number.
- `--json reviewThreads` asks for the review threads as JSON text.
- `--jq '...'` passes that JSON through a filter, which is a small language for picking out values.
- `.reviewThreads[]` steps through each thread. `select(.isResolved | not)` keeps the open ones.
- `| length` counts what is left.

A pass prints `0`. A fail prints a number above zero. The usual cause is a reply that was sent but never resolved.

Some versions of `gh` do not list `reviewThreads` as a field of `gh pr view` and answer `Unknown JSON field`. If that happens, the GitHub page ("Unresolved conversations") is the check, or you can ask GitHub's GraphQL interface for the same count:

```
gh api graphql -f query='query($o:String!,$r:String!,$n:Int!){repository(owner:$o,name:$r){pullRequest(number:$n){reviewThreads(first:100){nodes{isResolved}}}}}' -F o=<owner> -F r=<repo> -F n=<report-pr> --jq '[.data.repository.pullRequest.reviewThreads.nodes[] | select(.isResolved | not)] | length'
```

It prints the same number: `0` is a pass.

**TC2: the number in your summary matches its view.**

```

```

- `sqlite3` is the database tool, and `citypulse.db` is the file in the current folder.
- The text in single quotes is the SQL query. `SELECT *` means all columns, and `FROM <view>` names the view.

A pass means the number in your sentence appears in the output, within the rounding you used. A fail shows `Error: no such table` (wrong view name) or a different number (the report and the view disagree).

**TC3: the ML-problem file has the eight required headings.**

```term
$ grep -nE '^## (Question|Target|Prediction time|Features|Data|Metric|Naive baseline|Risks)' docs/ml-problem.md | wc -l
8
```

- `grep` prints lines that match a pattern. `-E` allows `|` to mean "or" inside the brackets.
- `^## (...)` matches a line that starts with two hash signs, a space and one of the eight names. `^` means "start of line".
- `| wc -l` counts the matching lines. The pipe `|` sends grep's output into `wc`.

A pass prints `8`. A fail prints less, usually because a heading is spelled differently (the match is case-sensitive, so `## Naive Baseline` fails) or uses one hash sign. More than 8 usually means a heading is repeated.

```trace
TITLE: Counting unresolved threads
CODE:
threads = [{"id": 1, "resolved": True}, {"id": 2, "resolved": False}, {"id": 3, "resolved": False}]
open_threads = [t for t in threads if not t["resolved"]]
count = len(open_threads)
STEPS:
1 :: threads=[3 dictionaries] :: The list holds one dictionary per review thread.
2 :: t={"id": 1, "resolved": True}; open_threads=[] :: Thread 1 is resolved, so it is skipped.
2 :: t={"id": 2, "resolved": False}; open_threads=[{"id": 2, "resolved": False}] :: Thread 2 is open, so it is kept.
2 :: t={"id": 3, "resolved": False}; open_threads=[{"id": 2, "resolved": False}, {"id": 3, "resolved": False}] :: Thread 3 is open, so it is kept too.
3 :: count=2 :: len counts the kept items, so two threads remain open.
```

### Defend it in the viva

**Q1 (why).** Why does the ML problem need a prediction time, and why is it written down before modelling?

:::answer Model answer
A prediction time fixes the moment up to which the model may use information. Every feature must be known at or before that moment. If the time is not written first, the team can pick features that look good in testing but are not known in use, which is target leakage. Writing it first means the trainer can check each feature against it.
:::

**Q2 (trade-off).** Why might a squad choose MAE over RMSE, and what does it give up?

:::answer Model answer
MAE is the average size of the errors, in the same units as the target, so it is easy to read. RMSE squares each error before averaging, so one very large miss counts for much more. Choose MAE when every unit of error costs about the same, and RMSE when large misses are much worse. MAE hides rare big misses, and RMSE is harder to explain. A good answer applies this to the squad's own target and says which fits.
:::

**Q3 (what you did).** Which part of the ML problem did you write, and how did you check it?

:::answer Model answer
A strong answer names the section you wrote, the commit that added it, and one check you ran, such as TC3 or the availability-time checklist. It then names one thing you would change with more time. Use facts from your own Git history, because the trainer can check the commits.
:::

**Q4 (evidence).** Which view produced the number in your executive summary, and how can someone check it?

:::answer Model answer
Name the view, then the query, then the number. Say what the view counts, and that running `SELECT * FROM` that view returns the same figure within the rounding used. A good answer also says what the view leaves out, so the number is not overstated.
:::

**Q5 (limitation).** Name one representation risk in your data, and say how it could harm someone.

:::answer Model answer
A representation risk is a way the data does not fairly reflect the people or places the model will affect. For example, if sensors sit mostly in some wards, the model learns those wards well and the others poorly, so officers in the quiet wards get worse advice. A strong answer names a risk from its own data, says who would be harmed, and names a step to reduce it.
:::
