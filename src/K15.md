The guides teach you how to do each ticket yourself and how your trainer will check it.

How the board works:

- A ticket moves Backlog, To Do, In Progress, Review, Done. **Only a trainer can move it to Done**, after running its test cases, and gives it a gate score from 0 to 3.
- Every ticket is judged from commit evidence: your commits, pull requests and reviews in the squad repository. Work done on someone else's laptop does not count for you.

- Your viva scores acceptance criteria met, technical depth, contribution and ownership, and understanding, each 0 to 5. The final capstone grade shown on the platform is 60% your own contribution and 40% your team's.

## Y2-T55 · Gap-bridge: log measured before/after on your weakest CRI dimension

*Session 55 · phase E12 · 2 points*

### The ticket in plain words

Ticket Y2-T55 asks you to find your weakest skill, measure it, practise it with feedback, measure again, and log both numbers with links anyone can open. The idea behind it comes from the research the ticket cites by Ericsson: you improve fastest by working on your weaknesses with feedback, not by doing more of what you already do well.

CityPulse needs this for CRI checkpoint 2 on Demo Day 2 (24 Apr), which targets 68 or more. The trainer needs a fair "before" and "after" number for every student, taken the same way under the same time limit.

You produce a gap-log entry in the LMS with seven fields, a mistake log (a notes file of each error and the rule that fixes it), and a booked check-in with your accountability partner. Your trainer will click your links and ask what changed.

### Before you start

These tickets must already be merged in your squad repository: Y2-T52, Y2-T53 and Y2-T54. T54's scores help you pick your weakness.

You need Git Bash (a Linux-style command line that comes with Git for Windows; every command here runs in it unless stated), Python 3, a GitHub account with access to `dsa-<name>` and `citypulse-<squad>`, and your LMS login.

Run these checks. Each one says where to run it and what a ready result looks like.

### How your trainer checks it

The ticket has four acceptance criteria (what must be true) and three test cases (what the trainer does to check it).

**Acceptance criterion 1: the gap log has all the fields.** The log must hold the dimension, your CRI 1 score, a specific goal, the before measure, the after measure and the evidence links.

**Acceptance criterion 2: comparable measures.** The before and after measures must use twin sets A and B, or the same scoring card, under the same time limit.

**Acceptance criterion 3: evidence links open.** Each link opens a platform attempt, a recording or a pull request.

**Acceptance criterion 4: check-in booked.** A check-in date before Saturday 17 April is recorded.

**Test case TC1.** The trainer opens the LMS gap-log export, filtered by squad. The expected result is five entries with every field filled in by 20:30. You can rehearse this with your own checker script. The command below runs in Git Bash, in the folder that holds `check_gap_log.py` and your exported `gap_log.csv`:

```term
$ python check_gap_log.py gap_log.csv
5 rows read
OK
```

`python` starts Python. `check_gap_log.py` is the script you write in Y2-T55.5. `gap_log.csv` is the export it reads. The first line is the row count, and `OK` appears only when no field is empty.

If the output looks like this instead, the check has failed:

```term
$ python check_gap_log.py gap_log.csv
5 rows read
row 3 empty after_measure
```

The usual cause is a blank LMS field, or an export that includes another squad's rows.

**Test case TC2.** The trainer clicks the before and after links for three random students. Both must open, the set IDs must differ (A against B), and the difficulty tags must match. Open your own links in a fresh private window. A link to the course list, or a login page, fails.

**Test case TC3.** The trainer asks: "What changed between before and after, and what is next?" A passing answer names a measured change and the next item from your mistake log. "I practised more" fails, because it has no numbers.

### Do it, step by step

#### Y2-T55.1 State your weakest dimension and CRI 1 score

Goal: one dimension, one CRI 1 score, and one written goal in the LMS gap log.

Stage 1. Find your numbers in your CRI 1 report and T54 scores. Pick the lowest dimension. If two tie, pick the one your mentor flagged. You are choosing a weakness to practise, not a score to defend.

Stage 2. Write the goal. A good goal has a number, a pattern and a time limit, such as the ticket's "4/5 sliding-window, each under 20 min". Write it in the LMS goal field.

Stage 3. Create your notes folder. Run these commands in Git Bash:

```
$ cd ~/dsa-yourname
$ mkdir -p notes
$ ls notes
```

`cd` moves into your personal repository. In Git Bash, `~` means your Windows home folder, so replace `yourname` with your repository folder name. `mkdir -p notes` creates a folder called `notes`. The `-p` flag means "create it if needed, and do not fail if it already exists". `ls notes` lists the folder. It prints nothing, which is correct for an empty folder.

Stage 4. Create the mistake log file. Name it after your pattern, using the ticket's pattern name if it is yours:

```
$ touch notes/sliding-window.md
$ ls notes
sliding-window.md
```

`touch` creates an empty file. If the file exists, `touch` only updates its timestamp, so it is safe to run twice.

Test this stage: read your goal aloud in under ten seconds. It must have a number, a pattern and a time limit.

#### Y2-T55.2 Take the before measure

Goal: one scored, timed attempt, with its score and time written in the log, before you practise anything.

First, the timing technique, with a small example. Type these lines in Git Bash:

```
$ start=$(date +%s)
$ sleep 3
$ end=$(date +%s)
$ echo "$((end - start)) seconds"
3 seconds
```

`start=$(date +%s)` stores the current time in seconds. `sleep 3` stands in for your work. The second `date` call stores the end time, and `$((end - start))` does the subtraction. Use the LMS timer if your set has one.

Now the measure itself. Pick one option and use the same one after practice:

- Timed set A on the LMS, scored by the platform.
- Three answers you record, scored with a scoring card.
- An old pull request or README, scored against a checklist.

A scoring card is a fixed list of one-point checks, applied the same way each time. Write down the score and the maximum, for example `3/5`.

Stage. Start the timer, do set A, stop the timer. Record the score, the maximum, the time limit you used and the seconds taken in the gap-log before field. Keep the attempt link from the LMS for the evidence.

Test this stage: the entry has a score, a maximum, a time limit, the seconds taken and an attempt link.

#### Y2-T55.3 Practise 30 minutes with feedback

Goal: 30 minutes of practice where every wrong answer is checked, written in the mistake log and fixed.

Feedback means you learn the result of each attempt straight away, from the LMS tests, a reference answer, a pair or a trainer hint.

Start your practice timer:

```
$ start=$(date +%s)
```

After each wrong item, add one line to the mistake log. Here is how appending works, using a fictional item:

```
$ printf '%s\n' "- Item A3: window end off by one. Rule: stop when end is the last index." >> notes/sliding-window.md
$ cat notes/sliding-window.md
- Item A3: window end off by one. Rule: stop when end is the last index.
```

`printf '%s\n' "..."` prints the text and adds a newline. `>>` appends the output to the file, instead of replacing it (a single `>` would overwrite the file). `cat` prints the file so you can check it.

To understand the technique, here is a small worked example of a sliding window. It is a teaching example, not one of your practice items, so do not copy it into your answers:

```python
def max_window_sum(nums, k):
    window = sum(nums[:k])
    best = window
    for end in range(k, len(nums)):
        window += nums[end] - nums[end - k]
        best = max(best, window)
    return best

print(max_window_sum([4, 0, 3, 7, 1], 2))
```

Line by line: `window` holds the sum of the first `k` values, and `best` the largest sum seen. Each loop step moves the window one place right, adding the new value and removing the one that fell off the left. The `print` line should show `10`, the window `3, 7`.

Check the time when you stop practising:

```
$ echo "$(( ($(date +%s) - start) / 60 )) minutes"
30 minutes
```

`/ 60` converts seconds into minutes. Bash arithmetic drops the remainder, so 1187 seconds shows as 19 minutes. You need at least 30 minutes on the timer.

Test this stage: your mistake log has one line for every wrong item, and the timer shows 30 or more minutes.

#### Y2-T55.4 Redo failed items, then take the after measure

Goal: redo the items you got wrong without notes, then measure again under the same conditions.

Stage 1. Redo without notes. Close your mistake log and reference, redo each failed item from memory, and time yourself. Write down what stopped you on any item you cannot solve.

Stage 2. Build the twin set. Set B must match set A in pattern, size, time limit and difficulty tag. Only the values change. If set A has eight numbers and a window of three, set B also has eight numbers and a window of three. If you are unsure whether set B is comparable, ask your trainer.

Stage 3. Take the after measure on set B. Use the same scoring card or platform score, the same time limit and the same timer method as the before measure. Record the score, the maximum, the time limit, the seconds taken and the attempt link in the after field.

Test this stage: compare the two entries. The maximum, time limit and difficulty tag must match.

#### Y2-T55.5 Log the numbers, the evidence and the check-in

Goal: a complete gap-log entry, evidence links that open, a mistake log committed to your repository and a booked check-in.

Stage 1. Fill every field, using the names your LMS shows: dimension, CRI 1 score, goal, before measure, after measure, and the before and after evidence links.

Stage 2. Download the gap-log export as a CSV file and save it as `gap_log.csv`. If the LMS gives another format, ask your trainer before converting it.

Stage 3. Write the checker, a small Python script that reads the export. Save this first part as `check_gap_log.py`:

```python
import csv
import sys

with open(sys.argv[1], newline="", encoding="utf-8") as f:
    rows = list(csv.DictReader(f))

print(len(rows), "rows read")
```

`csv` and `sys` are standard-library tools. `sys.argv[1]` is the file name you type after the script. `csv.DictReader` gives each row as a dictionary keyed by column header. Run it:

```
$ python check_gap_log.py gap_log.csv
5 rows read
```

Stage 4. Find empty fields. Step through this worked example of two invented rows, then add the same loop to your script:

```trace
TITLE: Finding empty gap-log fields
CODE:
rows = [{"dimension": "sliding-window", "before": "3/5"}, {"dimension": "", "before": "4/5"}]
for number, row in enumerate(rows, start=1):
    for field, value in row.items():
        if not value.strip():
            print("row", number, "empty", field)
STEPS:
1 :: rows=2 dicts :: Build a list with two rows. Each row is a dictionary keyed by column name.
2 :: number=1; row={"dimension": "sliding-window", "before": "3/5"} :: enumerate pairs each row with a number that starts at 1.
3 :: number=1; field="dimension"; value="sliding-window" :: The inner loop visits each field of row 1. Filled fields print nothing.
2 :: number=2; row={"dimension": "", "before": "4/5"} :: Move on to row 2.
3 :: number=2; field="dimension"; value="" :: The first field of row 2 is empty.
4 :: number=2; field="dimension"; value="" :: The test is true for an empty value.
5 :: number=2; field="dimension"; value="" :: print shows the row number and the empty field.
```

`value.strip()` removes spaces at both ends, so a cell with only spaces counts as empty. Add `bad = 0` before the loop, and `bad += 1` after the `print` inside the `if`, at the same indentation as the `print`. Then, after the loop, add:

```python
if bad == 0:
    print("OK")
```

Stage 5. Run the check on your export. If it reports empty fields, fix them in the LMS and re-export. Do not edit the CSV by hand, because the trainer checks the LMS export.

Stage 6. Open each evidence link in a fresh private window. The before link must show set A, the after link set B.

Stage 7. Commit the mistake log and checker on your branch, in Git Bash:

```
$ cd ~/dsa-yourname
$ git checkout -b y2-t55-gap-log-yourname
$ git add notes check_gap_log.py
$ git status
$ git commit -m "Add mistake log for sliding-window practice"
$ git push -u origin y2-t55-gap-log-yourname
```

`git checkout -b` creates and switches to a new branch. `git add` stages files, and `git status` shows what is staged (expect `new file:` lines for `notes/sliding-window.md` and `check_gap_log.py`). `git commit -m` saves a snapshot with a message. `git push -u origin` sends the branch to GitHub. If Git asks for your name and email, set them to match your GitHub account.

Stage 8. Book the check-in before Saturday 17 April. Confirm the weekday with `date -d "2027-04-17" +%A`, which should print `Saturday` if 2027 is your course year. Agree the date with your partner, then write it in your mistake log and the LMS. Commit and push the mistake log again (`git add notes`, `git commit -m "Add check-in date to the mistake log"`, `git push`) so the date is on your branch.

Open a pull request from your branch in your personal repository, and ask one squad-mate to approve it. Do not merge your own pull request.

Test this stage: the check prints `OK`, every evidence link opens to your attempt, the pull request exists and the check-in date is written down.

### Defend it in the viva

**1. Why did you choose this dimension and not your highest one?**

:::answer Model answer
The ticket's logic is that focused practice on a weakness gives more improvement than more practice on a strength. My CRI 1 and T54 scores both pointed to this dimension, so the choice rests on evidence. The goal has a number, a pattern and a time limit, so I can measure whether the practice worked.
:::

**2. Why did you use a twin set instead of retaking the same set?**

:::answer Model answer
This is a trade-off. Retaking set A is quicker, but it measures memory of the answers, not skill. A twin set costs time to check comparability, and that cost buys a fair comparison.
:::

**3. Walk me through what you personally did in this ticket.**

:::answer Model answer
Walk through your steps in order, and name the file or commit that shows each one. Your answer must match your own `git log`, so practise it against that before the viva.
:::

**4. How do you know the improvement is real, and not because set B was easier?**

:::answer Model answer
I checked comparability first: same pattern, size, limit, tag and scoring card. One pair of measures is still a small sample, so I would repeat the measure before a strong claim.
:::

**5. What is your next practice item, and where did it come from?**

:::answer Model answer
The next item comes from the mistake log, not from memory. I name the error I made most often, the rule that fixes it, and the item I will use to check it next.
:::

```quiz
Q1: Which command creates a folder called notes, and does not fail if the folder already exists?
- mkdir notes
* mkdir -p notes
- touch notes
- ls -p notes
WHY: -p means create the folder if needed and do not fail if it exists. Plain mkdir fails on an existing folder, and touch makes a file.

Q2: Your timer shows 1187 seconds. Using Bash arithmetic with / 60, how many whole minutes does it show?
- 1187
- 20
- 0
* 19
WHY: Bash integer division drops the remainder: 1187 divided by 60 is 19, remainder 47. Rounding up to 20 is the tempting mistake.

Q3: What makes a before and after comparison fair under the ticket's rules?
* The two sets share the same pattern, size, time limit and difficulty tag, but the values differ
- The second set is easier, so the score is higher
- You use a different scoring card for the after measure to show new skills
- You repeat set A exactly, so the score can be compared word for word
WHY: Twin sets must be comparable, meaning the same pattern, size, limit and difficulty tag, with different values. Repeating set A measures memory of the answers, and a deliberately easier set makes the comparison meaningless.
```

## Y2-T56 · Résumé v2: one page, 3 quantified project bullets with live links

*Session 56 · phase E14 · 2 points*

### The ticket in plain words

Recruiters decide very quickly whether a résumé is worth reading. The Ladders eye-tracking study, cited on the capstone board, puts that first decision at about six seconds. In that time a recruiter looks for a name, a role, and one or two things that prove the candidate can do the job.

Your squad has built real evidence this year: a CityPulse repository with continuous integration (automatic checks that run each time code changes), a deployed dashboard and API, an industry mini-project signed off at D07, and a DSA repository. This ticket turns your old résumé into a one-page version 2. Projects come first. Each project bullet follows the pattern "did X using Y, resulting in Z", and every number in it comes from a file in your repository. Every link must open for a stranger who is not logged in.

The reason for the checks is trust. A recruiter who clicks a link and finds a 404 error, or a number that is not in the project, stops trusting the whole page. Your job is to make every claim one click away from its proof.

### Before you start

These must already be merged or done, as the spec says:

- Y2-T53, Y2-T54 and Y2-T55. Y2-T55 gave you résumé v1 as homework; it should be on the LMS (the course learning system).
- Y2-T46 to Y2-T48, which gave you the deployed dashboard and API URLs.
- A `metrics.json` file in both `citypulse-<squad>` and `industry-<squad>`.
- The industry project tagged `v1.0` and `v1.0.1`, and a public `dsa-<name>` repository.

Tools and accounts you need: a GitHub account with access to your squad repository, your LMS login, and a PDF tool set (described below).

Quick checks. Run each one and compare with the expected output.

1. Command-line tools. Run `command -v pdfinfo pdftotext curl jq`. You should see four paths, for example `/usr/bin/pdfinfo`. If one is missing on Linux, install the PDF tools with `sudo apt install poppler-utils` and jq with `sudo apt install jq`. Git Bash on Windows does not include `pdfinfo` or `pdftotext`. ### How your trainer checks it

The trainer reads each acceptance criterion and runs each test case. Here is what each criterion means in practice.

- **One page with Projects above Education and Experience.** Open the PDF. There must be one page, and the Projects section must appear first, above Education and Experience.
- **Each of the three project bullets has a number and a link that returns HTTP 200 publicly.** Every bullet needs a figure and a link. The link must open in an incognito window and return 200 from a command-line check.
- **Numbers match metrics.json or the README.** Pick any number on the résumé and find it in the file it came from.
- **pdftotext output has sections in the right reading order, with no lost text.** Extract the text and read it top to bottom. Sections must appear in order, and no sentence may be missing.
- **The peer rubric scores at least 3 out of 5, with no unverifiable claims.** A squad-mate scores your résumé, and the score is on the LMS.

Now the four test cases, one by one.

**TC1: page count.** Steps: `pdfinfo Firstname_Lastname_Track.pdf | grep Pages`. Expected: `Pages: 1`.

Break the command into parts:

- `pdfinfo` reads the PDF and prints facts about it, such as the title, the page size and the number of pages.
- `Firstname_Lastname_Track.pdf` is the file name. Your name and track replace the placeholders. The spacing and capitals must match the ticket exactly.
- `|` is the pipe. It sends everything `pdfinfo` printed into the next command.
- `grep Pages` keeps only the line that contains the word `Pages`, so the output is short.

What passing looks like:

```term
$ pdfinfo Sample_Student_Data.pdf | grep Pages
Pages:          1
```

What failing looks like: `Pages: 2`. The usual cause is content that spilled onto a second sheet, often because of a large font, wide margins or a long bullet. Another failure is `Couldn't open file` or `No such file`, which means the file name is wrong, the capitals differ, or you are in the wrong folder.

**TC2: links.** Steps: `python scripts/check_links.py Firstname_Lastname_Track.pdf`. Expected: every URL prints with the status 200.

Parts:

- `python` runs a Python program. On the lab machine you may need `python3`.
- `scripts/check_links.py` is the program, inside the `scripts` folder of your repository. The ticket names it, so the trainer runs the same file. If your repository does not have it yet, raise that with your QA/DevOps owner. Step 5 shows the same checks as plain commands, so you can test your links now.
- `Firstname_Lastname_Track.pdf` is the file it reads. The program looks for URLs in the text of that file.

What passing looks like (the exact layout of the script's output may differ, but every URL must show 200):

```term
$ python scripts/check_links.py Sample_Student_Data.pdf
200 https://github.com/your-squad/citypulse-squad
200 https://example.org/dashboard
200 https://example.org/demo-video
```

What failing looks like: a line such as `404 https://...`. The usual causes are a mistyped address, a deleted page, or a private repository, which shows as 403 or 404 to a stranger. A 301 or 302 means the address redirects; fix it by pasting the final address into the résumé.

**TC3: numbers trace to a file.** Steps: pick one number from a bullet, open the linked repository's `metrics.json` or README, and check that the same number is there. Expected: the same number is present.

For speed, you can search a local copy of the file. The command is:

```bash
grep -n "1240" metrics.json README.md
```

- `grep` searches for the text in quotes.
- `-n` prints the line number, so you can point to the line in your notes.
- `metrics.json README.md` are the two files to search.

Passing output looks like `metrics.json:14:  "tests_run": 1240`. Failing output is nothing at all, which means the number is not in the file as you wrote it. Common causes are a comma, so `1,240` does not match `1240`, a README that was not updated after the last metrics run, or a number you rounded in the résumé. Fix the résumé, or update the file and then the résumé, but never let the two disagree.

**TC4: peer score.** Steps: open the LMS peer-review score column. Expected: a score of at least 3 out of 5, with the reviewer's name recorded. This is a manual check in the browser. Nothing is typed in a terminal.

### Do it, step by step

#### Step 1: Remove what the ticket says to remove (T56.1)

Goal: a clean copy of résumé v1 with nothing unverifiable left in it.

Start a branch from the latest main branch:

```bash
git checkout main
git pull
git checkout -b docs/resume-v2-yourname
git branch --show-current
```

- `git checkout main` switches to the main branch.
- `git pull` fetches the latest changes from GitHub and merges them in.
- `git checkout -b` creates a new branch and switches to it.
- `git branch --show-current` prints the branch you are on.

Expected last line: `docs/resume-v2-yourname`.

If your résumé source is in the repository, copy the v1 file to a new name, for example `cp resume_v1.md resume_v2.md`. If it is only on the LMS, download it and work on a copy.

Now search your copy for the words the ticket says to remove:

```bash
grep -inE "objective|skill|photo|date of birth|DOB|expert" resume_v2.md
```

- `-i` ignores capitals.
- `-n` prints line numbers.
- `-E` turns on extended patterns, so the vertical bars mean "or".

Expected output after cleaning: nothing, apart from a harmless match such as a plain "Skills" heading (the word "skill" also matches "skills you can show") or a word that merely contains "dob" such as "Adobe". Any other line that appears is a candidate for removal. Also read every remaining claim and ask: can I point to a file or link that shows this? If not, delete it. The phrase "expert in ML" is an example of a claim that fails this test.

Test before moving on: run the grep again. It must print nothing, or only the harmless matches described above.

#### Step 2: Reorder and write the summary (T56.2)

Goal: one page, in this order: name and contact line, one-line summary, Projects, Education, Experience, and skills you can show.

Put sections in the template order. Keep the summary to one line, and make it say what you are and what you built, not how you feel about it. The shape is:

```text
[Your role track] student who built [project] using [main tool]
```

Replace each bracket with your own words. Choose the role track your squad agreed, and use the same name everywhere in the résumé.

After each change, export the PDF and count pages. Do not wait until the end. The loop is: edit, export, run `pdfinfo` on the file, and repeat. If the count goes to 2, shorten a bullet or the summary before you change the font size. A smaller font makes the page hard to read, and the six-second scan depends on readable text.

Test before moving on: TC1 must print `Pages: 1` with the sections in the right order.

#### Step 3: Write the three project bullets (T56.3)

Goal: three bullets, each in the form "did X using Y, resulting in Z", where Z has a number from a file.

The pattern, with placeholders only:

```text
Built [what you did] using [tool or method], resulting in [number] [unit] (source: [file] [key]).
```

The source note is for you. Keep it in a private notes file, not on the résumé.

A clearly fictional example about a different project, not for copying, shows the shape. A student built a bus-arrival lookup for an imaginary town using Python and a public timetable service, resulting in 35 fewer manual lookups per day. The source would be `metrics.json`, key `daily_lookups_saved`.

Now find your own numbers. First, list the keys in the file. Teach this with a small example first. `jq` reads JSON from the input you give it and prints the part you ask for:

```bash
echo '{"runs": 12}' | jq '.runs'
```

- `echo` prints the JSON text into the pipe.
- `jq '.runs'` asks for the value of the key `runs`.

Expected output: `12`.

Now apply it to your file:

```bash
jq 'keys' metrics.json
```

- `keys` prints the names of the top-level keys as a list.

Expected output: a list of names, printed one per line inside square brackets and sorted alphabetically, for example `"daily_requests"` then `"tests_run"`. Those names are yours to read. Do not copy the example names.

Next, print the value you need:

```bash
jq '.YOUR_KEY_NAME' metrics.json
```

Replace `YOUR_KEY_NAME` with a key from the list. Expected output: one number. If the key is nested, use a path such as `.section.key` and read the JSON shape with `jq '.' metrics.json` first.

Write each bullet only after you have the number and its source. Use the number exactly as the file writes it, or round it in a way the reader can see, such as "about 1,200". The trainer's TC3 test compares the two, so an unexplained rounding will fail it.

Test before moving on: pick one bullet and run `grep -n "NUMBER" metrics.json README.md`. The number must appear in one of the files.

Trap: a number in the README can be older than the number in metrics.json. Use the file the bullet's source note names, and update the other one if they disagree.

#### Step 4: Add visible links (T56.4)

Goal: each bullet has a link a stranger can open, and the link text is the full web address.

Put the full address in the PDF as plain visible text. Do not hide the address behind a word such as "dashboard". The reason is that the link check in Step 5 reads visible text, and a hidden address will not be found. Links to add: the repository, the deployed dashboard or API, and the demo video.

Test each link in an incognito window. In Chrome or Edge on Windows, press Ctrl+Shift+N, paste each address, and check that the page loads without a login. Then check the status code from the command line:

```bash
curl -s -o /dev/null -w "%{http_code}\n" -L --max-time 10 "https://example.org/dashboard"
```

- `-s` hides the progress meter.
- `-o /dev/null` throws away the page body, because you only want the code.
- `-w "%{http_code}\n"` prints the status code and a new line.
- `-L` follows redirects, so the code you see is the final page's code.
- `--max-time 10` gives up after 10 seconds.
- The quoted URL is the address to check.

Expected output: `200`. Use the same address in the résumé as the one you tested.

Trap: curl does not use your browser's logins, so a private repository returns 403 or 404 to curl even when you can see it in your own account. The incognito check and the curl check together show what a stranger sees.

#### Step 5: Export the PDF and check every link (T56.5)

Goal: one PDF, named `Firstname_Lastname_Track.pdf`, whose links all return 200.

Stage A, export. Use the export or save-as-PDF option in the editor you used (for example File, then Download, then PDF in Google Docs, or Save as PDF in Word). Name the file exactly as the ticket says, with your name and track.

Stage B, count pages. Run `pdfinfo Firstname_Lastname_Track.pdf | grep Pages`. Expected: `Pages: 1`. This is TC1.

Stage C, read the text. Run:

```bash
pdftotext Firstname_Lastname_Track.pdf - | head -n 40
```

- `pdftotext` extracts the text of the PDF.
- The final `-` tells it to write to stdout, the screen, rather than to a file.
- `| head -n 40` shows only the first 40 lines.

Read the output top to bottom. Sections must appear in order and no sentence should be missing. This is the reading-order check.

Stage D, pull out the URLs. Teach this with a small example first. `grep -o` prints only the part of each line that matches, and the pattern below matches the start of a web address up to the next space:

```bash
echo "See https://example.org/x)." | grep -oE 'https?://[^[:space:]]+'
```

Expected output: `https://example.org/x).`. The full stop and bracket were captured because they are not spaces. The `sed` command below removes them:

```bash
echo "See https://example.org/x)." | grep -oE 'https?://[^[:space:]]+' | sed 's/[.,;)]*$//'
```

Expected output: `https://example.org/x`. Here `sed 's/[.,;)]*$//'` deletes any run of full stops, commas, semicolons or closing brackets at the end of the line.

Stage E, check each link. Put the parts together. Run this inside the folder that holds your PDF:

```bash
pdftotext Firstname_Lastname_Track.pdf - \
  | grep -oE 'https?://[^[:space:]]+' \
  | sed 's/[.,;)]*$//' \
  | sort -u \
  | while read -r url; do
      code=$(curl -s -o /dev/null -w "%{http_code}" -L --max-time 10 "$url")
      echo "$code $url"
    done
```

- The first line extracts the text and the pipe sends it on.
- `grep` and `sed` leave one clean URL per line, as in Stage D.
- `sort -u` removes duplicates, so a link that appears twice is tested once.
- `while read -r url` takes one URL at a time and runs the loop body for it.
- `code=$(...)` stores the status code in a variable. The `$(...)` runs the curl command and captures what it prints.
- `echo "$code $url"` prints the code followed by the address, so you can read the results.

Expected output: every line starts with `200`. A line with any other number needs fixing. Fix it in the source, re-export, and run this stage again. The loop does not write a file, so re-export before you rerun the check.

If a very long address wraps onto two lines in the `pdftotext` output, the loop tests only the first half and shows a wrong code. Check that line by pasting the full address into a browser, and consider a shorter link.

Windows note: this runs in Git Bash, which includes curl. Install poppler for `pdftotext` as described in Before you start. The `\` at the end of a line continues the command onto the next line in both Git Bash and Linux.

Your squad's `scripts/check_links.py` checks the same things (TC2). If the two disagree, trust the one you can read and raise the difference with your QA/DevOps owner.

Here is the flow of one URL through the check:

```flow
TITLE: From your PDF to a verdict
NODES: Your PDF | pdftotext | curl | Public website
STEPS:
1>2 :: extract text :: pdftotext prints the visible text of the PDF to the screen.
2>3 :: one URL at a time :: grep and sed pass one clean address to curl for each link.
3>4 :: GET request :: curl asks the public website for the page, following any redirects.
4>3 :: 200 :: The site answers with its status code, and curl prints it back to you.
3>1 :: fix and re-export :: Any code other than 200 means you fix the source and export again.
```

Note: the last step points back to your PDF because a broken link is fixed in the source, then the PDF is exported again.

#### Step 6: Peer swap and upload (T56.6)

Goal: a score of at least 3 out of 5 from a squad-mate, recorded on the LMS with their name, and your own upload.

Six-second scan. Open your squad-mate's PDF for six seconds, timing yourself, then close it. Write down, from memory, what you saw: their name, their role track, the three numbers and the places the links appeared. If you cannot write it, the résumé is not scannable, and that is a finding worth reporting.

Score the résumé against the five-point rubric your trainer published on the LMS. Score each item from 1 to 5. Give your squad-mate a short written reason for the lowest item. Use your own words.

Fix your own lowest item. Choose the item that scored lowest on your own résumé from your squad-mate's notes, or ask them what they would change. Edit the source, re-export, and run Step 5 again. The check must still pass.

Upload the PDF to the LMS with your peer score. The LMS records the reviewer's name next to the score. TC4 checks that name.

Scrum/Docs owner: check that five uploads with peer scores exist before 23:59. Other students: check that your upload appears in the LMS column and that your reviewer's name is shown. If something is missing, message the Scrum/Docs owner before the deadline.

- `.` means the current folder.
- `|` pipes the matching lines into `wc -l`.

#### Y2-T57.3: Profile the slow job and name the O(n²) function

**Goal.** Find the hot function in `citypulse-slowjob`, name its complexity and propose a faster version.

**Stage 1: learn the profiler on a toy.** A profiler records how long each function call took. Python's built-in one is `cProfile`. You run it as a module with `python -m cProfile`. The flag `-s cumtime` sorts the output by cumulative time, which is time spent in a function plus the functions it calls.

Make a tiny file called `toy.py` in a scratch folder:

```python
def count_pairs(values):
    total = 0
    for i in range(len(values)):
        for j in range(len(values)):
            total += 1
    return total

print(count_pairs(list(range(2000))))
```

Run it with the profiler:

```term
$ python -m cProfile -s cumtime toy.py
4000000
         4010 function calls in 0.250 seconds
   Ordered by: cumulative time
```

The first line is the program's own output, `4000000`. The count is 2000 times 2000. The number of function calls (about 4,000) and the seconds will differ on your machine; loop steps are not function calls, so they are not counted there. The output then lists the functions by cumulative time. The column `ncalls` is the number of calls and `tottime` is time spent inside the function's own body, excluding functions it calls. `cumtime` includes those calls. The row for `count_pairs` shows the time for the whole nested loop.

**Stage 2: find the hot function in the real job.** Run the profiler on the job's entry file, which the `citypulse-slowjob` README names. Run it on the lab machine, where the data is. Look at the top rows and skip the lines `<module>` and any built-in functions, since those wrap your code. The hot function is the first row that belongs to the job's own code. Write down its name, file, and its `cumtime`.

**Stage 3: read the complexity from the loops.** Look at the code of the hot function. A loop nested inside another loop, where both run over the same n items, is O(n²). Count the operations by hand. For `count_pairs`, the inner loop runs n times for each of n outer steps, so there are n × n steps. Your job's function may be different, but the reasoning is the same.

**Stage 4: a faster version of the same question.** A common O(n²) pattern is an inner loop that searches for a value. A hash set answers "is this present?" in about constant time, so one pass with a set replaces the search. Here is a fictional question, separate from the job, that asks whether any two values are equal:

```python
def has_duplicate_slow(values):
    for i in range(len(values)):
        for j in range(i + 1, len(values)):
            if values[i] == values[j]:
                return True
    return False
```

The two loops compare every pair, which is O(n²). Now the set version:

```python
def has_duplicate_fast(values):
    seen = set()
    for value in values:
        if value in seen:
            return True
        seen.add(value)
    return False
```

The single loop checks each value once. `value in seen` is the membership test that costs about constant time, and `seen.add(value)` remembers it. Together that is O(n). The trade-off is memory: the set holds up to n values.

Here is the same idea shown step by step on a three-value list:

```trace
TITLE: Checking a small list for a duplicate with a set
CODE:
seen = set()
for value in [4, 9, 4]:
    if value in seen:
        print("duplicate", value)
    seen.add(value)
STEPS:
1 :: seen=set() :: Start with an empty set.
2 :: value=4; seen=set() :: The loop takes the first value.
3 :: value=4; seen=set() :: 4 is not in the set, so the if is false.
5 :: value=4; seen={4} :: Remember 4 for later.
2 :: value=9; seen={4} :: The second value.
3 :: value=9; seen={4} :: 9 is not in the set yet.
5 :: value=9; seen={4, 9} :: Remember 9.
2 :: value=4; seen={4, 9} :: The third value is 4 again.
3 :: value=4; seen={4, 9} :: 4 is already in the set, so the if is true.
4 :: value=4; seen={4, 9} :: Report the duplicate.
```

Each step names the line that ran and the values at that moment. The third value finds 4 already in the set, which is the moment the answer is known.

**Stage 5: test that your fix is equal to the slow one.** Run both versions on the same small lists and check they agree. Add an assertion for each case, so a mismatch stops the program:

```python
assert has_duplicate_slow([1, 2, 3]) == has_duplicate_fast([1, 2, 3]) == False
assert has_duplicate_slow([1, 2, 1]) == has_duplicate_fast([1, 2, 1]) == True
```

Equal results do not prove speed, so also time the job before and after your change. Your write-up needs the function name, its file, its `cumtime` before the change, its complexity and the proposed fix in your own words. Save it as a notes file of your choice in the repository and commit it.

### Defend it in the viva

The trainer asks you questions to check you understand the ticket. Answer from your own output and your own commits. Each model answer below shows the reasoning, not your personal details.

**1. Why does a complexity note matter if the tests already pass?**

Tests tell you that a function returns the right answer on the inputs you chose. They do not tell you how it behaves when the input grows. The complexity note records the growth rate, so a reader can see that a loop nested over the same n items will become slow, and can judge whether that matters for the data.

:::answer Model answer
Tests check correctness on chosen inputs. A complexity note tells you how the cost grows with n. A solution can pass every test and still be too slow for the real data. CityPulse's nightly job is the example: it was correct but took 90 minutes. Writing the growth rate down makes the risk visible before the job gets slow.
:::

**2. What is the trade-off in replacing a nested loop with a set?**

A set makes each membership check fast, about constant time, so the whole check becomes linear. The cost is memory, because the set stores the values it has seen. For n values that is roughly n stored items, which is the price for the speed.

:::answer Model answer
The set trades memory for time. The nested loop uses almost no extra memory but does n squared comparisons. The set version does about n checks and stores up to n values. For most data the saving in time is worth the extra memory, but if memory were the limit, the answer would change. You would name that limit and explain the choice.
:::

**3. Walk me through your profiling result. Which function was hot, and why?**

Answer from your own profile output. Say the command you ran, the function name from the `cumtime` column, the file it is in, and the loop structure that gives its complexity. Then say what you would change.

:::answer Model answer
Start with the command, `python -m cProfile -s cumtime` on the job's entry file. Name the first row that belongs to your job's own code, not `<module>`. Give its cumulative time from your run. Then explain the loop: which loop is nested inside which, over which list, so the cost is n squared. Finish with the fix you would try and why it is linear. Use only numbers from your own output.
:::

**4. How do you know your fix is O(n) and not just faster on your sample?**

Speed on one sample proves little, because a small sample hides growth. You reason from the code: count how many times each line runs as n grows. Then you check the timing on larger inputs, to see the curve bend.

:::answer Model answer
A faster result on one input does not prove the growth rate. I count the operations: a single loop with a constant-time membership test runs about n times. Then I test with inputs of increasing size, such as 1,000, 10,000 and 100,000 values, and check that the time grows roughly in step with n, not with n squared. The reasoning and the measurements together support the claim.
:::

**5. In your mock, what did you do when you got stuck?**

The answer should describe your own steps. Say which stage you were in, what you did first, and whether you asked for a hint. Explain that you went back to the clarify step or to the brute-force version when stuck, because a correct slow solution is a safe place to return to.

:::answer Model answer
When stuck, I say out loud where I am, such as "I am stuck choosing the data structure." Then I return to the brute-force version, which I know is correct, and look for the repeated work in it. If I still cannot see the next step, I ask a tier-1 hint that names the stage. I explain why I asked, because the trainer scores my reasoning, not only the final code.
:::

```quiz
- About 1,000
- About 2,000
```

| A Result has no number. | You described it in words only, such as "it was better". | Find the figure in the CI run, data check or pull request, and write it with its unit. |

| Trainer's "What did YOU do?" gets "the team" as the answer. | You learned the story from the squad, not from your own actions. | Go back to your commits and reviews and name the exact thing you did, or choose another story. |

### Defend it in the viva

Question 1: Why does each story need a number and an evidence link, rather than a clear description alone?

:::answer Model answer
A description can be true or false, and the interviewer cannot check it. A number makes the result specific, and a link lets someone open the pull request or CI run and see it. Together they show the story is real and that you measure your own work. The trainer clicks links at random for the same reason: to test the claim against the evidence.
:::

Question 2: What is the trade-off between a short Situation and a long one?

:::answer Model answer
A short Situation reaches the Action quickly, which suits a two-minute answer, but the listener may not see why the problem mattered. A longer Situation gives context and uses time that should go to your Action and Result. Keep the Situation to one or two sentences, and give the Action most of the time. Judge the balance by timing your practice runs.
:::

Question 3: What did you personally do in your strongest story?

:::answer Model answer
Answer with specific steps in the first person, and tie each step to evidence. Name what you ran, found, wrote and reviewed. Do not describe team steps as your own, and do not add steps you did not take. The trainer will ask follow-up questions, and only real detail holds up.
:::

Question 4: Why do the partner and the rubric matter?

:::answer Model answer
The partner is a second listener who measures the answer against a fixed scale, so the score is less of a personal opinion. Practice with a partner also shows where an answer is unclear, such as a missing Result or a long Situation. A score of at least 3 out of 5 shows the answer is clear, and the feedback shows what to improve.
:::

Question 5: What would you do if asked about a failure you caused?

:::answer Model answer
Choose a story where you caused the problem. Say what you got wrong without blaming the team, then explain how you found and fixed it, and what check or review you added so it does not happen again. Show the evidence for each step. Interviewers often value an honest failure story, because it shows how you respond when things go wrong.
:::

#### TC1: the number matches its source

The trainer opens the note, picks one number, and opens the source file. Your number must match the file exactly.

The command below prints one line of a file. Run it in Git Bash in your repository. Replace `docs/cloud-cost.md` and `42` with your own file and line number. Your file name and line will be different.

```bash
# Runs in Git Bash, in the repository folder
sed -n '42p' docs/cloud-cost.md
```

The parts:

- `sed` is a stream editor. Here it only reads and prints.
- `-n` stops `sed` printing every line. Without it, the whole file would print.
- `'42p'` means "print line 42 only". The `p` is the print command.
- `docs/cloud-cost.md` is the file to read.

Passing output looks like this. The line contains the number from your card, unchanged. The example below is made up for the shape of the output; your line will hold your own figure.

```term
$ sed -n '42p' docs/cloud-cost.md

```

Failing output has two usual causes. If the line is blank or shows different text, the line number has moved, because someone added or removed lines above it. #### TC2: the sketch in 60 seconds, owned parts starred

The trainer says "Draw your architecture" and starts a 60-second timer. You must draw a complete data-flow sketch in time, with your owned parts starred.

Passing means every box has an arrow in data-flow order, the sketch is finished before the timer stops, and each part you built carries a star. Failing means the drawing is missing arrows, is not finished, or has no stars. The usual cause is drawing without a timer, so the drawing grows to twenty small boxes. Practise with the timer below.

```bash
# Runs in Git Bash
start=$(date +%s)
# ...draw your sketch on paper now...
echo "$(( $(date +%s) - start )) seconds"
```

The parts:

- `start=$(date +%s)` saves the current time as a number of seconds since 1 January 1970. `date +%s` prints that number, and `$( )` puts the output into `start`.
- The comment line is a reminder that you draw between the two commands. A comment starts with `#` and does nothing.
- `$(( ... ))` does arithmetic. Here it subtracts `start` from the current time.

Expected output: a line such as `47 seconds`. Aim for 50 seconds or less in practice, so you have a margin in the live test. Run the commands in the same Git Bash window, because the variable `start` is kept only while that window stays open.

### Do it, step by step

#### 1. Fill the numbers card (Y2-T59.1)

Goal: a table in one file, where every number you will quote has a row, a value, a source file and a line number.

Stage 1: find the files. Run this in Git Bash, inside the repository.

```bash
ls docs
```

The parts: `ls` lists the names in a folder. `docs` is the folder to list.

Expected output: the file names in your docs folder. Look for the cost doc and the model report. If you cannot find one, check the README, which links to the other documents.

Stage 2: find the numbers. Teach this first with a small example. Suppose a file contains two lines, `Runs per day: 48` and `Memory: 128 MB`. Searching with `grep -nE "[0-9]+"` prints both lines with their line numbers, because the pattern `[0-9]+` means "one or more digits". Now run it on your own file.

```bash
grep -nE "[0-9]+" docs/cloud-cost.md
```

The parts: `[0-9]+` matches one or more digits. `-n` prints the line number. The output has the form `line-number:text`. For the example file above, the output would be `1:Runs per day: 48` and `2:Memory: 128 MB`. For your file, the output is longer. Pick the lines you want to quote.

Stage 3: read the exact line. Use `sed -n` with the line number, as in TC1.

```bash
sed -n '1p' docs/cloud-cost.md
```

Expected output: the text of line 1. If it matches the text you saw in the search, the line number is right.

Stage 4: write the card. Create a Markdown file for the card, for example `docs/deep-dive-numbers.md`. Use one row for each figure, in this shape:

| Figure | Value | Source file | Line |
|---|---|---|---|
| What the number measures | The number, with its unit | The path in the repository | The line number from grep |

Test before moving on. For each row, run `sed -n 'LINEp' PATH` and check that the output contains the value. Fix any row that does not match.

#### 2. Write the six-part arc (Y2-T59.2)

Goal: a one-page note with six sections in the order of the arc template. Each section uses one number from the card, and the "my part" section links to your merged PRs.

Start by listing your own merged PRs. Run this in Git Bash.

```bash
gh pr list --author @me --state merged --limit 30 --json number,title,url --jq '.[] | "#\(.number) \(.title) \(.url)"'
```

The parts:

- `gh pr list` lists pull requests in the repository you are in.
- `--author @me` keeps only the PRs you opened. `@me` means you.
- `--state merged` keeps only merged PRs.
- `--limit 30` shows at most 30.
- `--json number,title,url` asks for those three fields as JSON, which is structured text.
- `--jq '...'` is built into `gh`, so you do not need to install the separate `jq` tool (Git Bash on Windows does not include it). It reads the JSON and prints plain text. `.[] | ...` takes each PR and formats it with the `#` number, the title and the link.

Expected output: one line per PR, such as `#12 Add cost doc table https://github.com/...`. Copy the lines for the PRs that belong to your layer into the "my part" section.

Teach the shape of one section with a fictional example, about a different project, a library book-loan app. Your sections must use your own project's numbers.

> Section: Reliability. Claim: the overdue-reminder job sends each reminder once, even when it is run twice. Evidence: in the last 40 runs, 0 reminders were sent twice (source: `docs/reminder-log.md`, line 18). Trade-off: each run now checks a log before sending, which adds about a second per run.

Each section has the same three parts: a claim in one sentence, one number with its source, and a trade-off where one applies. Fill the six sections from your card.

Test before moving on. Open each link in your "my part" section and check it opens the right PR. Export the note to PDF from your editor, then open the PDF and check that it is one page. If it runs onto a second page, cut words, not sections.

#### 3. Draw the architecture sketch (Y2-T59.3)

Stage 2: draw in order. Start with the source on the left or at the top. Draw one box per part and one arrow per hand-over. Label each arrow with what travels along it, such as "request" or "rows". Do not draw parts that are not in the data path, such as a document folder, unless the trainer asks for them.

#### 4. Write the why questions (Y2-T59.4)

Goal: five questions, one for each layer you touched, each with a 2 to 3 sentence answer, and one answer of 45 seconds for a trade-off.

A layer is one part of the data path, such as the source, the fetch, the storage, the report or the monitoring. Write a question that asks "why" about a choice in that layer. Interviewers ask "why" again and again, so write your answers so that each one can be followed by a further question.

Stage 1: write five questions, one for each layer. Stage 2: write each answer in 2 to 3 sentences, with one number where you can. Stage 3: choose one question that is about a trade-off, and write its answer so you can say it in 45 seconds.

Test before moving on. Read each answer aloud with a stopwatch. The 2 to 3 sentence answers should take 15 to 25 seconds. The trade-off answer must finish within 45 seconds.

#### 5. Run the grill (Y2-T59.5)

Goal: deliver the deep-dive, take five peer why questions, receive the rubric score, and revise the weak answers.


- `echo` prints the text it is given.
- `"$(date +%F)"` prints today's date in the form `2026-11-17`.

Expected output: nothing on screen. Then `cat ~/grill-notes.txt` prints every line you have saved. Check that the list has one line per question.

#### TC1: the address answers with HTTP 200

The step is `curl -sI https://<username>.github.io | head -1`. The expected result is `HTTP/2 200`.

- `curl` fetches the address.
- `-s` (silent) hides the progress meter.
- `-I` asks for the headers only. The server still sends its status line.
- `|` sends the output to the next command.
- `head -1` keeps only the first line, which is the status line.

Passing looks like this:

```term
$ curl -sI https://<username>.github.io | head -1
HTTP/2 200
```

`HTTP/2` names the protocol version. `200` means the page loaded, so this is a pass.

Failing looks like one of these. `HTTP/2 404`: Pages is not enabled or is still building, the repository name is wrong, or there is no `index.html` in the root of the `main` branch. Nothing printed: curl could not connect, so check your internet connection. `curl: (6) Could not resolve host`: the username is mistyped.

```flow
TITLE: What TC1 checks
NODES: Your laptop | GitHub Pages | Your repository
STEPS:
1>2 :: request the page :: curl asks for https://<username>.github.io over HTTPS.
2>3 :: read main :: Pages finds the files on the main branch.
3>2 :: send the files :: The repository hands its files to Pages.
2>1 :: HTTP/2 200 :: The page is served, and curl prints the status line.
```

#### TC2: the demo plays on a phone, with no sideways scroll

The trainer opens the page on a phone in a private window and scrolls to the first project. The demo must play, and the page must not slide sideways. A GIF plays by itself. An MP4 needs its play button to work.

The HTML for an MP4 that plays on a phone looks like this. You will place it in your own page in Y2-T61.4.

```html
<video src="assets/citypulse-demo.mp4" controls muted playsinline></video>
```

- `<video>` is the video player tag.
- `src` names the file. Its spelling and capital letters must match the file exactly.
- `controls` shows the play button. `muted` removes sound, which phones require if a video is ever set to autoplay. `playsinline` stops iPhones forcing the video to full screen.

Failing looks like a blank box, usually a wrong `src`. Or the page slides sideways, usually because one picture is wider than the screen. The fix is a style rule, `img, video { max-width: 100%; height: auto; }`, which keeps pictures and videos inside the screen width. Your page also needs this line inside `<head>`, or phones draw it at desktop width: `<meta name="viewport" content="width=device-width, initial-scale=1">`. A complete page needs `<!doctype html>`, `<html>`, `<head>` (with that meta line and a `<title>`) and `<body>`; put your hero and case studies inside `<body>`.

#### TC4: every link opens

The trainer clicks each link or runs a link checker. You can run the same check with this loop, in the site folder on your laptop. Save it as `check-links.sh` there (keep it out of your pull request if the squad prefers).

```bash
for url in $(grep -oE 'https://[^" ]+' index.html | sort -u); do
  code=$(curl -s -o /dev/null -w "%{http_code}" -L "$url")
  echo "$code $url"
done
```

- `grep -oE 'https://[^" ]+'` finds every `https://` address in `index.html`. `-o` prints only the match.
- `sort -u` removes duplicates.
- `for ... do ... done` runs the lines between them once for each link, with the link in the variable `url`.
- `code=$(...)` stores the status code. `-o /dev/null` discards the page body, and `-w "%{http_code}"` prints only the code.
- `-L` follows redirects, so the final address is checked.

Passing output has `200` at the start of every line:

```term
$ bash check-links.sh
200 https://github.com/your-username/citypulse-squad
200 https://github.com/your-username/industry-squad
```

A `404` means the link points at nothing. A private repository often shows `404` to a visitor who is not signed in. A `403` can mean the site refuses automated requests, so open that link in a browser. LinkedIn often answers automated requests with `999`, so open your LinkedIn link in a browser instead. `000` means the link could not be reached. The loop only checks `https://` links, so your local `assets/` files are checked by eye on the phone.

#### Subtask Y2-T62.1: run the checklist and link check

Goal: know exactly which items fail before you change anything.

Stage 1: make a working folder outside the repository. This keeps your scratch files out of Git.

```bash
mkdir -p ~/linkcheck
cd ~/linkcheck
```

`mkdir -p` creates the folder and does nothing if it already exists. `cd` changes into it. Your prompt is now inside `linkcheck`, so every file you create stays there.

Stage 2: list the checklist items. Open the D08 checklist on the LMS and copy each item into `~/linkcheck/checklist-notes.txt`. Keeping the notes outside the portfolio folder means they are never committed by accident.

Stage 3: list the pages to check. Create `pages.txt` with one full address per line, one for each page of your portfolio. For example:

```text
https://<username>.github.io/
https://<username>.github.io/projects.html
```

Write each address in full, starting with `https://`. Check that each line has no spaces at the end, since Windows editors sometimes add invisible carriage-return characters. Save the file in an editor set to LF line endings, such as VS Code, and not in an older Notepad setting that writes CRLF.

Stage 4: fetch each page and collect its links. A link in HTML looks like `<a href="https://...">`. The commands below download each page and collect the value of every `href`. Type them into a file called `check_links.sh` in `~/linkcheck`; you will add the later stages to the same file, so that `bash check_links.sh` runs everything in order.

```bash
: > links.txt
while read -r page; do
  curl -sS --fail "$page" -o tmp.html
  grep -o 'href="[^"]*"' tmp.html | sed 's/^href="//; s/"$//' >> links.txt
done < pages.txt
sort -u links.txt -o links.txt
```

Line by line:

- `: > links.txt` empties the file, or creates it if it does not exist. The colon is a command that does nothing, and `>` replaces the file's contents.
- `while read -r page; do` reads one line from the input at a time into the variable `page`. `-r` stops `read` from treating backslashes as special.
- `curl -sS --fail "$page" -o tmp.html` fetches the page and saves it as `tmp.html`. `-s` hides the progress meter, `-S` still shows errors, and `--fail` makes curl report an error for a page that does not exist.
- `grep -o 'href="[^"]*"' tmp.html` prints only the matching part of each line, which is each `href="..."` value.
- `sed 's/^href="//; s/"$//'` removes the `href="` at the start and the closing quote at the end, leaving only the address.
- `>> links.txt` appends the addresses to the file.
- `done < pages.txt` feeds the list of pages to the loop.
- `sort -u links.txt -o links.txt` sorts the file and removes duplicate lines, writing the result back to the same file.

Expected output: no message if every page loads. Then `links.txt` contains one address per line. Open it with `cat links.txt` to check it. You should see the links you expect. If a page fails, curl prints an error and the loop continues with the next page.

Stage 5: keep only the web links. Links like `mailto:` (an email link) or `#top` (a link within the same page) are not checked by the status test. Note that relative links such as `href="projects.html"` also do not start with `https://`, so this filter drops them. That is why every page of your site is listed in `pages.txt`: each one is checked as a page in its own right. Add `src="..."` links (images) to the grep yourself if your portfolio uses them.

```bash
grep '^https://' links.txt > web.txt
wc -l < web.txt
```

`grep '^https://'` keeps only lines that start with `https://`. `wc -l` counts the lines. Expected output: a number, which is how many web links you have.

Stage 6: check each link in the list. You will add this to `check_links.sh` in Subtask Y2-T62.2, and then run the complete check.

Stage 7: mark each checklist item. For each item on your notes, write down one evidence link that shows the item is true. Open each link in a private browser window. #### Subtask Y2-T62.2: fix every failed item

Goal: make each item that failed in Subtask 1 pass, and keep a record of what you changed.

Before any fix, create your branch in the portfolio folder: `git switch -c y2-t62-freeze`. All your fix commits go on it.

First, the link checker. Add this stage to `check_links.sh`, after the stage 5 commands. It checks each link in `web.txt` and records the status code.

```bash
: > results.txt
while read -r link; do
  code=$(curl -sL -o /dev/null -w '%{http_code}' --max-time 20 "$link")
  echo "$code $link" >> results.txt
done < web.txt
```

Line by line:

- `: > results.txt` empties the results file before you start.
- `while read -r link; do` reads one web link at a time.
- `curl -sL` fetches the link silently and follows redirects. `-L` is the important flag: without it, a `301` is reported as the final answer, and the check fails although the link works.
- `-o /dev/null` throws the page body away, because you need only the status.
- `-w '%{http_code}'` prints only the status code, and `code=$(...)` stores it in the variable `code`.
- `--max-time 20` stops curl after 20 seconds, so one slow link does not hang the run.
- `echo "$code $link" >> results.txt` writes the code and the link on one line.

Expected output: nothing is printed while it runs. Open `results.txt` with `cat results.txt`. Each line starts with a code, for example `200 https://<username>.github.io/`.

Now the summary. Add the three lines below at the end of `check_links.sh`, and run it from `~/linkcheck` with `bash check_links.sh`. The script runs all the stages in order.

```bash
echo "checked $(wc -l < web.txt) links"
echo "non-200 links: $(grep -vc '^200 ' results.txt)"
grep -v '^200 ' results.txt
```

Line by line: the first line counts the web links. The second counts the lines in `results.txt` that do not start with `200 `. `grep -v` inverts the match, and `-c` counts the matches. The third line prints the bad lines, so you can see which links to fix.

### Defend it in the viva

Your trainer will ask you about this ticket. Each answer below shows the reasoning. Your own answers must use your own facts.

1. **Why do you freeze at a SHA instead of at a date?** A date does not identify content. Two commits can share the same day, and a later commit can be made on the same day. The SHA identifies one exact set of files, so the panel sees a version that cannot change under them.

:::answer Model answer
A date is a moment, not a version. More than one commit can land on the same day, and a commit made after the freeze would still carry that date. A SHA is a fingerprint of the exact content and history, so it names one version. Git can check that a remote tip still equals it. That is why the freeze check compares SHAs and not dates. The reasoning is that the panel reviews exactly what the trainer approved.
:::

2. **What is the trade-off in merging your fixes through a pull request before the freeze?** A pull request adds a review step, which takes time and needs a squad-mate. It also means the default branch only moves when a reviewer has approved the change, so your SHA is the tip that the freeze check reads. Skipping the review would be faster, but it would break the team rule that nobody merges their own work.

:::answer Model answer
The trade-off is time against trust. Review takes a squad-mate's attention and can delay the freeze, so you plan the merge early. In exchange, the default branch holds only reviewed changes, and the SHA you freeze is the one a reviewer approved. Self-merging would save minutes but would remove the check that the team relies on. A good answer names the cost and says why it is worth paying.
:::

3. **What did you personally do to make your portfolio pass?** A strong answer names the specific links, pages or items you fixed, the commit that fixed each one, and the evidence you produced. It does not describe the team's work as your own.

:::answer Model answer
A strong answer is specific. It names the failed item, the file that held the problem, the commit message and SHA that fixed it, and the output that proves it now passes, such as the link checker summary. It also says which parts were your decision, such as the wording of the plan. The shape is what counts here. Replace every detail with your own facts before you answer.
:::

4. **How does the link checker decide a link is broken, and why use `-L`?** The checker sends a request and reads the status code. A `200` means the page loaded. A `404` means the page is missing. A `301` means the address moved, and the browser would follow it. Without `-L`, curl stops at the `301` and the checker would report a failure that a visitor never sees.

:::answer Model answer
A checker treats the status code as the signal. Only a `200` after any redirects counts as a working link. `-L` tells curl to follow each redirect to its final answer, which matches what a visitor's browser does. Without it, a moved page looks broken. The reasoning is that the check should measure what the reader experiences, not what one server reply says.
:::

5. **Why keep scratch files outside the repository?** Git tracks every file in the folder unless it is ignored. Scratch files such as `tmp.html` and `links.txt` would appear in `git status`, and a careless `git add .` could commit them. A clean working tree is the proof that the commit contains only what you meant.

:::answer Model answer
Git records whatever is in the folder, so scratch files would blur what the freeze contains. Keeping them in a separate folder keeps `git status` clean, and `git status` showing a clean tree is the evidence that the frozen commit holds only reviewed work. The reasoning is about making the frozen version easy to verify.
:::

#### TC2: the second trainer recomputes the CRI

```trace

components = {"a": 80, "b": 60}
```

```python test
def weighted_total(components, weights):
    """Weighted average of component scores. The weights are fictional here."""
    total_weight = sum(weights.values())
    return sum(components[k] * weights[k] for k in weights) / total_weight

def matches_workbook(recomputed, workbook_value, tolerance=0.05):
    return abs(recomputed - workbook_value) <= tolerance

assert round(weighted_total({"a": 80, "b": 60}, {"a": 0.5, "b": 0.5}), 2) == 70.0
assert matches_workbook(70.02, 70.0)
assert not matches_workbook(71.0, 70.0)
assert weighted_total({"a": 100}, {"a": 2}) == 100.0
```

#### Y2-T63.3: Round 2, deep-dive, SQL and Python, and one DSA problem

The goal is a clear three-minute talk, quick answers on SQL and Python, and a problem solved out loud with tests.

Stage 1: build a three-minute outline with four parts: the problem CityPulse solves, what you built, one number from your work, and what you would do next.

Stage 2: practise SQL on a small fictional table, using Python's built-in `sqlite3` module.

```python
import sqlite3
con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE readings (station TEXT, pm25 REAL)")
con.executemany("INSERT INTO readings VALUES (?, ?)", [("East", 42.0), ("East", 55.5), ("West", 30.0)])
for row in con.execute("SELECT station, AVG(pm25) FROM readings GROUP BY station ORDER BY station"):
    print(row)
```

Line by line: `connect(":memory:")` makes a database that lives only in memory. `CREATE TABLE` makes the table. `executemany` inserts three fictional rows. The `?` marks keep the values separate from the SQL text. The final `SELECT` groups by station and averages the values. Expected output:

```
('East', 48.75)
('West', 30.0)
```

Stage 3: practise the DSA habit of tests first. Write small asserts for the edge cases before you write the function. This example uses fictional data, and it is not a known problem.

```python test
def count_above(values, limit):
    return sum(1 for v in values if v > limit)

assert count_above([], 10) == 0
assert count_above([5, 12, 12], 10) == 2
assert count_above([10], 10) == 0
```

Line by line: the function counts values strictly greater than the limit. The first assert tests an empty list, the second a normal case, and the third the boundary, where a value equal to the limit must not count.

Test: run the file with `python`. No output means the asserts passed.

- Situation: one sentence on the setting.
- Task: one sentence on what you had to achieve.
- Action: two or three sentences on what you did, using "I" for your own part.
- Result: one or two sentences with a measurable outcome, such as a number, a time saved or a count of users.

- Action: I added a simple check that compared counts at the end of each shift.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| The awk check prints a `missing:` line for one student | A score was never entered, or the export has its columns in another order. | Read the header with `head -n 1`, then ask the trainer to re-export or record an exception. |
| The awk check prints a pass line or `missing:` lines that do not match what you see in the file | The field numbers do not match the file, so awk tests the wrong columns. | Print the first two lines, and change `$2` to `$3` (and so on) to match the columns. |
| grep finds nothing for your roll | The roll is typed differently, with extra spaces, leading zeros, or different case. | Copy the roll exactly from the trainer's record. |
| grep finds two lines for your roll | The roll is duplicated, or a longer roll contains yours. | Report the duplicate to the trainer. Do not edit the file. |
| The last column fails to match in grep or awk | The file has Windows line endings, which add a hidden character. | Make a cleaned copy with `tr -d '\r' < freeze_audit.csv > freeze_clean.csv`. |
| Your rebuilt CRI is off by a tiny amount | Rounding was applied at a different stage. | Round only when you display the result, and compare within the agreed tolerance. |
| The LMS letter has no 30-day plan | The letter was opened before it was finished. | Do not tick the acknowledgement. Tell the trainer which item is missing. |

### Defend it in the viva

Each model answer explains the reasoning. Do not memorise it. Use your own words and evidence.

**Q1 (why): Why does the CRI use a weighted total rather than a plain average?**

:::answer Model answer
A plain average treats every component as equally important. A weighted total lets the workbook favour the components that best show internship readiness. The weights are a judgement, so they must be written down, so anyone can rebuild the number from the same inputs.
:::

**Q2 (trade-off): Why is the CRI checked by a second trainer?**

:::answer Model answer
A second check catches formula errors and mistyped scores before the number is issued. The trade-off is time, because the result waits until 15:00. For a record that partners use to make hiring decisions, that delay is worth it, since an error is harder to fix after the letter is out.
:::

**Q3 (what you did): Which part of this ticket did you prepare, and how can someone check it?**

:::answer Model answer
Name one subtask, the commits on your branch that show the preparation, and the check you ran on your own record. The commits show the work and the outputs show the checks.
:::

**Q4 (why): Why does TC3 use `grep -F` with the roll?**

:::answer Model answer
The roll is treated as plain text, so a full stop or other character cannot change what is matched. The output shows the line number, so the trainer can see the exact match. The trade-off is that grep matches substrings, so a longer roll can match too, and the output must be read with care.
:::

**Q5 (understanding): What does the freeze SHA prove?**

:::answer Model answer
The SHA names one exact commit. If it matches the current commit of the same repository that the freeze row names, the portfolio has not changed since it was frozen. A match in a different repository proves nothing. If it does not match, raise it with the trainer and record a dated exception, rather than editing the freeze to match.
:::
