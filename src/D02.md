TITLE: Day 2 — Linux and the command line
SUB: You will be able to find, inspect, filter and count sensor readings from a terminal, lock down a secret file, and rebuild the same logic as a Python function.

## The idea in one minute

The CityPulse sensors write their readings to CSV files, and those files land on a Linux server. You cannot scroll through thousands of rows to check that every station reported, so you ask questions by typing commands. Think of the terminal as a counter at a records office: you hand the clerk a short written request such as "count the PM2.5 rows", and the clerk hands back one answer.

Today you learn to find files, look inside them, filter them, count them, lock them down, and chain small tools into one line that answers a real question. These are the skills behind the course tickets Y2-T03 (a 20-task scavenger hunt) and Y2-T04 (a setup document a teammate must follow cold).

## Starting from zero

**Terminal.** A window where you type text commands and read text replies. It is not a special kind of computer. It is only a text window onto one.

**Shell.** The program inside the terminal that reads what you type and runs it. The shell used in this course is called Bash. Bash is the common shell on Linux.

**Prompt.** The short text the shell prints when it is waiting for you, for example `city@server:~$`. In this book, a line that starts with `$ ` is something you type. The `$ ` is the prompt, not part of the command.

**Command.** A program name, followed by optional flags and arguments. In `ls -lh /data/readings` the program is `ls`, `-lh` is a flag and `/data/readings` is an argument.

**Flag (option).** A switch that changes how a command behaves. Flags usually start with a dash. A single dash can carry several letters: `-lh` means `-l` and `-h`.

**Argument.** The thing a command works on, such as a file name or a directory name.

**File.** A named block of data stored on disk. A CSV file is a plain-text file in which each line is one row and commas separate the columns.

**Directory.** A container that holds files and other directories. Most people call it a folder.

**Filesystem.** The whole organised set of files and directories on one machine. Linux presents all of it as one tree that starts at a single top point called the root, written `/`.

**Path.** The address of a file or directory, written as names separated by `/`. An **absolute path** starts at the root, for example `/data/readings/jan.csv`. A **relative path** starts from wherever you currently are, for example `raw/jan.csv`. Two special names exist in every directory: `.` means "this directory" and `..` means "the directory above".

**Working directory.** The directory you are currently in. Relative paths are measured from it.

**Server.** A computer that provides a service to other computers. The CityPulse lab server stores the raw sensor files, and several students use it at the same time.

**Header row.** The first line of a CSV file, which names the columns instead of holding a reading. In the sensor files it is `station_id,ts,pollutant,value`.

**Field.** One value inside a row, for example `ST-01` or `53.3`. A field is one column in one row.

**Process.** A program that is running right now. Every process has a number, its process ID (PID).

**Function.** A named piece of code that takes inputs, does work and gives back a result. You will write your own functions in the graded-lab section.

## The tools

### Moving around and listing files: pwd, cd, ls

Your first three commands answer three questions: where am I, where can I go, and what is here.

```bash
pwd
cd /data/readings
ls -lh
```

Line by line:

- `pwd` stands for "print working directory". It prints the absolute path of the directory you are in. Expect output such as `/home/city`.
- `cd /data/readings` changes directory. `cd` is short for "change directory". The path is absolute, so it works from anywhere. Nothing is printed when `cd` succeeds.
- `ls -lh` lists the contents of the current directory. `ls` is short for "list". The `-l` flag asks for a long listing, with one line per file. The `-h` flag asks for human-readable sizes, so 140K is printed instead of 143360.

A long-listing line looks like this:

```text
-rw-r--r-- 1 city city 140K Nov 11 09:14 jan.csv
```

The first column, `-rw-r--r--`, holds the permissions, explained below. The number `1` is the count of hard links, which you can ignore for now. `city city` are the owner and the group. `140K` is the size. The date and time show the last change, and `jan.csv` is the name.

Two more flags matter. `-a` shows hidden files, which are files whose names start with a dot, such as `.env`. `ls` alone hides them. You combine flags as `ls -la`.

### Finding files and text: find and grep

`find` searches the file tree by name, type, size or date. `grep` searches the contents of files for a piece of text.

```bash
find /srv/hunt -type f -name '*.log' -size +1k
grep -rn 'pm2_5' /srv/hunt | head -5
man find | head -20
```

Line by line, first command:

- `find` is the program.
- `/srv/hunt` is the starting directory. `find` searches it and everything below it.
- `-type f` keeps only regular files. `f` means file. `d` would mean directory.
- `-name '*.log'` keeps names that match the pattern. The quotes stop the shell from changing `*` before `find` sees it. You will meet this trap in the quiz section.
- `-size +1k` keeps files larger than one kilobyte. The plus sign means "larger than".

Second command:

- `grep` prints every line that contains the text you give it.
- `-r` searches recursively, which means it goes into every subdirectory.
- `-n` prints the line number next to each match.
- `'pm2_5'` is the text to find. Quotes keep the command clear and protect characters the shell would otherwise interpret.
- `/srv/hunt` is where to search.
- `| head -5` sends the output into `head`, which keeps only the first five lines. The vertical bar is explained in the redirection section below.

Expect output such as `/srv/hunt/site3/notes.txt:12:pm2_5 sensor offline`. The text before the first colon is the file, the number is the line, and the rest is the line itself.

Third command: `man` opens the manual page for a command. Press `q` to leave it. Piping it into `head -20` shows only the first twenty lines, which is useful when a manual page is long.

### Reading parts of a file: head, tail and wc

A 140 KB file is too big to read in an editor, and you rarely need all of it. These three tools let you look at the parts you need.

```bash
head -n 2 jan.csv
wc -l jan.csv
tail -n +2 jan.csv
```

Line by line:

- `head -n 2 jan.csv` prints the first two lines of the file. `-n 2` means "two lines". The first line is the header and the second is the first reading, so you see the column layout. Expect:

```text
station_id,ts,pollutant,value
ST-01,2025-01-01T00:00:00,PM2.5,53.3
```

- `wc -l jan.csv` counts lines. `wc` means "word count", and `-l` restricts it to lines. Expect a number and the file name, such as `4033 jan.csv`.
- `tail -n +2 jan.csv` prints the file starting at line 2. The plus sign is the important part. `tail -n 2` would mean "the last two lines", which is a different thing.

The count includes the header. A file with 4,033 lines has 4,032 readings.

### Redirection and pipes

Every command has three default streams. Standard input (number 0) is where it reads from, which is normally the keyboard. Standard output (number 1) is where normal results go, which is normally the screen. Standard error (number 2) is where error messages go, also the screen by default.

You can redirect these streams to files or to other programs:

```bash
grep ',PM2.5,' jan.csv > pm25.csv
grep ',NO2,' jan.csv >> pm25.csv
sort < pm25.csv
ls /no/such/place 2> errors.txt
grep ',PM2.5,' jan.csv | wc -l
```

Line by line:

- `>` sends standard output into a file. It creates the file, or replaces the file if it already exists. The result goes into `pm25.csv` and nothing appears on screen.
- `>>` sends output into a file and adds it at the end. The NO2 rows are appended after the PM2.5 rows.
- `<` feeds a file into a command as standard input. `sort < pm25.csv` sorts the lines of that file.
- `2>` sends standard error into a file. Here the "no such file" message goes into `errors.txt`, so the screen stays clean.
- `|` is the pipe. It sends the standard output of the command on the left into the standard input of the command on the right. Here, `grep` finds the PM2.5 rows and `wc -l` counts them. Expect a single number such as `1008`.

A pipe lets small tools cooperate. Each tool does one job, and the pipeline does the whole task.

### Permissions: ls -l, chmod

Every file has an owner, a group and a set of permissions. Permissions say who may read the file (`r`), change it (`w`) or run it as a program (`x`). The permission string has ten characters:

| Position | Meaning |
|---|---|
| 1 | File type. `-` is a normal file, `d` is a directory. |
| 2–4 | What the owner may do: read, write, execute. |
| 5–7 | What members of the group may do. |
| 8–10 | What everyone else may do. |

So `-rw-r--r--` means a normal file that the owner can read and write, the group can read, and everyone else can read.

`chmod` changes permissions. It is short for "change mode". You can use symbols or numbers. Numbers are the faster way to remember:

- `r` is 4, `w` is 2 and `x` is 1.
- You add the numbers for each group. Owner, group and others each get one digit.

So `600` means owner gets 4+2 = read and write, group gets 0, others get 0.

```bash
ls -l .env
chmod 600 .env
ls -l .env
chmod +x scripts/fetch_once.sh
```

Line by line:

- `ls -l .env` shows the current permissions of the file `.env`, which holds API keys.
- `chmod 600 .env` sets the permissions to owner read and write, and nothing for anyone else. `chmod` takes the mode first and the file second.
- The second `ls -l .env` shows the change.
- `chmod +x scripts/fetch_once.sh` adds the execute permission for everyone. `+x` means "add execute". Without this, `./fetch_once.sh` fails with "Permission denied".

Expected output before and after:

```term
$ ls -l .env
-rw-r--r-- 1 city city 22 Nov 11 09:14 .env
$ chmod 600 .env
$ ls -l .env
-rw------- 1 city city 22 Nov 11 09:14 .env
```

The first line of the output shows `-rw-r--r--` and the second shows `-rw-------`. Your size and date will differ. The change in the permission string is what matters.

### Cutting columns, sorting and counting: cut, sort, uniq

These three tools together are the shell's version of "group by". They are the most-used pipeline in data work.

```bash
tail -n +2 jan.csv | cut -d, -f1 | sort | uniq -c
```

Line by line:

- `tail -n +2 jan.csv` starts from line 2, which skips the header.
- `cut -d, -f1` keeps only field 1. `-d,` sets the delimiter to a comma. `-f1` means field 1.
- `sort` puts the lines in alphabetical order. Identical lines end up next to each other.
- `uniq -c` collapses runs of identical adjacent lines into one line, and `-c` puts the count in front.

Expected output:

```text
    672 ST-01
    672 ST-02
    672 ST-03
    672 ST-04
    672 ST-05
    672 ST-06
```

The counts are padded with spaces, so the numbers line up. Each station reports 672 rows in the course data.

The pipeline below shows how each stage hands its output to the next.

```flow
TITLE: One pipeline, four stages
NODES: grep | cut | sort | uniq -c | Terminal output
STEPS:
1>2 :: matching lines :: grep keeps only the rows that contain ,PM2.5, and passes them on.
2>3 :: one column each :: cut keeps the station id from each row, so each line is now just an id.
3>4 :: ids in order :: sort puts identical ids next to each other, which uniq needs.
4>5 :: counts per id :: uniq -c writes one line per id with its count, and the result appears on screen.
```

Two rules follow from this. `uniq` only merges lines that are next to each other, so you must `sort` first. And `cut` splits on the delimiter you name, so a wrong delimiter gives you the wrong column without any error message.

### Disk space: df

`df` reports how full each disk is. `df -h` prints sizes in human-readable units.

```bash
df -h /data
```

Line by line:

- `df` is short for "disk free".
- `-h` prints sizes as K, M, G.
- `/data` asks about the filesystem that holds the directory `/data`. Without a path, `df` lists every mounted filesystem.

Expect a table with the columns Filesystem, Size, Used, Avail, Use% and Mounted on. The row whose last column is `/data` tells you how much room is left. `Avail` is the free space you can use. `Use%` is how full the disk is as a percentage.

`df` reports whole disks. To ask how large a directory is, use `du`. The two answer different questions.

### Processes and packages: &, jobs, ps, kill, which, apt

A process is a running program. Some processes run in the foreground, so the prompt waits for them. A command followed by `&` runs in the background, and the prompt returns at once. Background work is how cron jobs and long-running tasks behave on a server.

```bash
sleep 600 &
jobs
ps aux | grep '[s]leep 600'
kill %1
jobs
```

Line by line:

- `sleep 600 &` starts the program `sleep`, which does nothing for 600 seconds. The `&` at the end sends it to the background. The shell prints a job number and a PID, and you get your prompt back.
- `jobs` lists the background jobs started from this shell. Expect a line such as `[1]+  Running    sleep 600 &`.
- `ps aux` lists all processes. The `a` flag includes other users' processes, `u` uses the readable column layout, and `x` includes processes that have no terminal. The `grep '[s]leep 600'` part keeps only the line you care about. The square brackets are a trick. The pattern `[s]leep 600` matches the text "sleep 600", but the command that grep itself is running contains "[s]leep 600", and that text does not match the pattern. So grep does not match its own process.
- `kill %1` sends a stop signal to job number 1. The `%` marks a job number rather than a PID. By default, `kill` sends the TERM signal, which asks a program to finish cleanly.
- The last `jobs` prints nothing, which shows the job has stopped.

Two more commands complete the picture:

```bash
echo "$PATH"
which python3 jq curl
dpkg -s jq | grep '^Status'
```

- `echo "$PATH"` prints the value of the shell variable `PATH`. A variable is a named container for a value, and `$PATH` reads it. `PATH` is a colon-separated list of folders. When you type `python3`, the shell searches those folders in order and runs the first match.
- `which python3 jq curl` prints the full path of the program each name resolves to. If a name prints nothing, the shell cannot find it.
- `dpkg -s jq` asks the package system whether `jq` is installed. `grep '^Status'` keeps the status line. Expect `Status: install ok installed` if it is present.

If a tool is missing and you are allowed to install it on the lab, the course uses:

```bash
sudo apt-get install -y jq
```

`sudo` runs the command with administrator rights. `apt-get` is the package manager on Ubuntu. `install` names the action, `-y` answers "yes" to the confirmation question, and `jq` is the package. Use `sudo` only for system tools, never for Python packages.

:::trap Using kill -9 first
`kill -9` uses the KILL signal, which the program cannot catch. It stops at once and skips any cleanup code, so files may be left half-written. Send the plain `kill` first. Use `kill -9` only when the process has not stopped after a reasonable wait.
:::

:::trap Grepping ps and matching yourself
`ps aux | grep sleep` always shows one extra line, which is grep itself. Use the `[s]leep` trick above, or `pgrep -a sleep`.
:::

### Python venv and pip

A **virtual environment** (venv) is a private copy of Python and its package installer, kept inside one project folder. **pip** is the Python package installer. It downloads libraries such as `requests` from the internet. CityPulse uses both so that every teammate gets the same library versions.

The setup block below is the one in the course document. Read it in order.

```bash
python3 -m venv .venv
source .venv/bin/activate
which python
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -c 'import requests; print(requests.__version__)'
printf '.venv/\n.env\n' >> .gitignore
git check-ignore .venv .env
deactivate
```

Line by line:

- `python3 -m venv .venv` runs the Python module `venv` and creates a folder called `.venv`. The `-m` flag means "run this module as a program". The name `.venv` starts with a dot, so `ls` hides it by default.
- `source .venv/bin/activate` loads the activation script. It puts `.venv/bin` at the front of `PATH`, so `python` and `pip` now refer to the copies inside `.venv`. `source` runs the file in the current shell.
- `which python` should print a path that ends in `.venv/bin/python`. If it prints `/usr/bin/python`, the environment is not active.
- `python -m pip install --upgrade pip` updates pip inside the environment. Running pip as `python -m pip` guarantees that you use the pip that matches the active Python.
- `python -m pip install -r requirements.txt` installs every package listed in `requirements.txt`. `-r` means "read the list from this file". The file pins versions, for example `requests==2.32.3`.
- `python -c '...'` runs a short piece of Python passed on the command line. `-c` means "command". The code imports `requests` and prints its version. A silent success followed by the version number means the import works.
- `printf '.venv/\n.env\n' >> .gitignore` appends two lines to `.gitignore`, which tells Git to ignore those files. `\n` is a new line. The `>>` appends rather than replaces.
- `git check-ignore .venv .env` prints the paths that Git ignores. Both should appear.
- `deactivate` leaves the environment and restores the normal `PATH`.

Expected output from the version check is a number such as `2.32.3`.

:::trap Forgetting to activate
If you skip `source .venv/bin/activate`, pip installs the packages into the system Python. The import then fails later, in a different terminal. Run `which python` before any install.
:::

:::trap Committing the .venv folder
A `.venv` folder holds thousands of files. Add `.venv/` to `.gitignore` before your first `git add`.
:::

### Saving a recipe as a script

A script is a text file that contains commands, which the shell runs in order. You run it by name. The course script for the lab looks like this:

```bash
#!/usr/bin/env bash
# flag.sh — flag stations over the 55 ug/m3 PM2.5 limit
set -euo pipefail
file=${1:-jan.csv}
grep ',PM2.5,' "$file" \
  | awk -F, '{s[$1]+=$4; n[$1]++} END{for(k in s) printf "%s %.1f\n", k, s[k]/n[k]}' \
  | sort -k2 -nr \
  | awk '$2>55 {print $1, $2, "BREACH"}'
```

Line by line:

- `#!/usr/bin/env bash` is the first line, called the shebang. It tells the system to run this file with Bash. `env` finds Bash on the current PATH.
- `# flag.sh — ...` is a comment. The shell ignores any line starting with `#` (apart from the shebang).
- `set -euo pipefail` sets three safety rules. `-e` stops the script when a command fails. `-u` treats an unset variable as an error. `-o pipefail` makes a pipeline fail if any stage fails, not only the last one. Without these, a broken `grep` could pass silently.
- `file=${1:-jan.csv}` stores the first argument in `file`. `$1` means argument number 1. The `:-jan.csv` part is a default: if no argument is given, use `jan.csv`.
- The `grep` line keeps the PM2.5 rows from `"$file"`. The quotes around `$file` keep the value safe even if the name contains spaces.
- The `awk` line adds up the value column per station and prints each station's average. `-F,` splits on commas. `$1` is the station, `$4` is the value. `s[$1]` is a total for each station and `n[$1]` counts its rows. `END{...}` runs once after the last line.
- `sort -k2 -nr` sorts on the second field, which is the average, numerically and in reverse. Highest first.
- The last `awk` prints a line only when the second field is greater than 55, and labels it `BREACH`.

Running the script requires the execute permission from the permissions section, plus a path to it:

```bash
chmod +x flag.sh
./flag.sh jan.csv
```

Expected output is one line per station over the limit, such as `ST-04 56.1 BREACH`.

## The worked example

The workbook's example asks one question: which stations had the worst PM2.5 readings in January? You will rebuild the answer one step at a time. The data file is `jan.csv` and its header is `station_id,ts,pollutant,value`.

**Goal.** Look at the file, check it is complete, compute the average PM2.5, rank the stations, and save the result as a script.

**Step 1. Go to the data and list it.**

```bash
cd /data/readings
pwd
ls -lh
```

Output:

```text
/data/readings
-rw-r--r-- 1 city city 140K jan.csv
```

`cd` moves into the drop zone, `pwd` confirms the location, and `ls -lh` shows that one file, `jan.csv`, is present at 140 KB. Checking the location first matters because a relative path run from the wrong directory will fail or, worse, find the wrong file.

**Step 2. Look at the header and count the lines.**

```bash
head -n 2 jan.csv && wc -l jan.csv
```

Output:

```text
station_id,ts,pollutant,value
ST-01,2025-01-01T00:00:00,PM2.5,53.3
4033 jan.csv
```

`&&` runs the second command only if the first one succeeds. The header shows four columns. The count of 4,033 means 4,032 readings plus the header.

**Step 3. Count the PM2.5 rows.**

```bash
grep ',PM2.5,' jan.csv | wc -l
```

Output: `1008`

The pattern includes the commas on both sides. That stops `grep` matching a value such as `PM2.5X` in some other column. `wc -l` counts the matching lines, and the header is not counted because it contains the word `pollutant`, not `PM2.5`.

**Step 4. Tally the readings per station.**

```bash
tail -n +2 jan.csv | cut -d, -f1 | sort | uniq -c
```

Output: six lines, each `672 ST-0n` for `n` from 1 to 6.

Every station reported 672 rows, so coverage is complete. An uneven count would point to a sensor that has gone quiet.

**Step 5. Average the PM2.5 values with awk.**

```bash
grep ',PM2.5,' jan.csv \
  | awk -F, '{s+=$4; n++} END{printf "PM2.5 avg over %d readings: %.1f ug/m3\n", n, s/n}'
```

Output:

```text
PM2.5 avg over 1008 readings: 54.9 ug/m3
```

The backslash at the end of the first line tells Bash that the command continues on the next line. `awk` is a small programming language for working on columns. `-F,` sets the field separator to a comma. In the braces before `END`, `s+=$4` adds the fourth field (the value) to `s`, and `n++` adds one to `n` for each line. The `END` block runs once, after the last line, and `printf` prints the result. `%d` prints an integer, `%.1f` prints a decimal with one place after the point, and `\n` ends the line. The unit `ug/m3` means micrograms per cubic metre.

**Step 6. Rank the stations by their average.**

```bash
grep ',PM2.5,' jan.csv \
  | awk -F, '{s[$1]+=$4; n[$1]++} END{for(k in s) printf "%s %.1f\n", k, s[k]/n[k]}' \
  | sort -k2 -nr \
  | head -n 3
```

Output:

```text
ST-04 56.1
ST-02 55.3
ST-05 54.9
```

This time `s` and `n` are arrays, which work like the dictionaries you will meet in Python. `s[$1]` is a total per station, keyed by the station id. `for(k in s)` loops over the keys, and the averages come out in no particular order. That is why the `sort -k2 -nr` stage is needed. `head -n 3` keeps the three highest.

**Step 7. Save the recipe as a script.**

The `flag.sh` script shown earlier does step 6 and then flags any station above 55 ug/m3. Run it with `bash flag.sh jan.csv`. Output:

```text
ST-04 56.1 BREACH
ST-02 55.3 BREACH
```

Running it as `bash flag.sh` avoids needing the execute bit, but the course lab uses `chmod +x` and `./flag.sh`, which is what you should learn.

## The hands-on lab, step by step

The lab uses a small sample file that you create yourself, so you can check every answer. Work in a new, empty directory. Create it with `mkdir lab2` and move into it with `cd lab2`.

### Step 1. Find your bearings

**What you do.** Confirm where you are, then list what is there.

**Type.**

```bash
pwd
ls -la
```

**You should see.** An absolute path ending in `lab2`, and a listing that contains only the entries `.` and `..`, because the directory is new.

**How you know it worked.** The path from `pwd` ends in `/lab2`. If it does not, run `cd` to the directory you created before going on.

### Step 2. Create a sample readings file

**What you do.** Write a small CSV file called `sample.csv`. The `printf` command prints the text you give it. The `>` sends that text into the file.

**Type.**

```bash
printf 'station_id,ts,pollutant,value\nST-01,2025-01-01T00:00:00,PM2.5,53.3\nST-01,2025-01-01T01:00:00,NO2,21.0\nST-02,2025-01-01T00:00:00,PM2.5,58.9\nST-02,2025-01-01T01:00:00,PM2.5,48.1\nST-03,2025-01-01T00:00:00,PM2.5,61.4\n' > sample.csv
```

`printf` interprets `\n` as a new line, so one long string becomes six lines. The single quotes stop Bash from reading the commas or the dots as anything special.

**You should see.** No output, because the text went into the file.

**How you know it worked.** Run `wc -l sample.csv`. The answer must be `6`: one header and five readings.

### Step 3. Inspect without opening an editor

**What you do.** Look at the header and the first row, then count the lines.

**Type.**

```bash
head -n 2 sample.csv
wc -l sample.csv
```

**You should see.**

```text
station_id,ts,pollutant,value
ST-01,2025-01-01T00:00:00,PM2.5,53.3
6 sample.csv
```

**How you know it worked.** The count is 6 and the header has four names. If the count is off, your `printf` text was mistyped. Recreate the file with the same command.

### Step 4. Filter rows that matter

**What you do.** Keep only the PM2.5 rows and count them.

**Type.**

```bash
grep ',PM2.5,' sample.csv
grep ',PM2.5,' sample.csv | wc -l
```

**You should see.** Four rows, for ST-01, ST-02 (twice) and ST-03. The count is `4`. The NO2 row is excluded.

**How you know it worked.** The count is 4. If you see 5, the NO2 row has been included, which means the pattern is wrong. Check it has commas on both sides.

### Step 5. Pull out a single column

**What you do.** Print the station column and tally it, skipping the header.

**Type.**

```bash
tail -n +2 sample.csv | cut -d, -f1 | sort | uniq -c
```

**You should see.**

```text
      2 ST-01
      2 ST-02
      1 ST-03
```

**How you know it worked.** The three counts add up to 5, which is the number of data rows. If the header appears as a row, you left out `+2` in `tail`.

### Step 6. Build a pipeline that answers a question

**What you do.** Answer the question "which two stations have the highest average PM2.5?"

**Type.**

```bash
grep ',PM2.5,' sample.csv \
  | awk -F, '{s[$1]+=$4; n[$1]++} END{for(k in s) printf "%s %.1f\n", k, s[k]/n[k]}' \
  | sort -k2 -nr \
  | head -n 2
```

**You should see.**

```text

ST-02 53.5
```

**How you know it worked.** ST-02 averages 58.9 and 48.1, which is 53.5. ST-01 has only one PM2.5 row, at 53.3, so it is third and is cut off by `head -n 2`. If your answer lists the stations in the wrong order, check that `sort` has `-nr`. Without `-n`, sort compares text, and "61.4" would be ranked below "9.0".

## What the quiz tests

The platform quiz has ten questions, one per topic below, and a pass mark of 70%. Only the first attempt counts. The questions below are practice questions of your own, written for these topics.

### ls-glob

**What you must know.** `ls` lists files, and `*` is a wildcard that matches any run of characters. The shell expands `*.csv` into the matching file names in the current directory before `ls` runs. So `ls -lh *.csv` lists every file ending in `.csv` in the directory you are in. `?` matches one character and `[ab]` matches one of the listed characters. Expansion only looks in the current directory, not in subdirectories.

**The trap.** Writing `find /data -name *.csv` without quotes. The shell expands `*.csv` in the current directory first, so `find` receives a list of file names instead of a pattern. Quote the pattern: `find /data -name '*.csv'`.

### head-tail

**What you must know.** `head -n N` prints the first N lines and `tail -n N` prints the last N lines. `tail -n +N` prints from line N onward. In a CSV file, `tail -n +2` skips the header, which is the most common use.

**The trap.** Confusing `tail -n 2` (last two lines) with `tail -n +2` (everything from line two). The plus sign changes the meaning completely.

### wc-line-count

**What you must know.** `wc -l` counts lines, and each line is counted once for every newline character it ends with. The header is a line, so a file with a header and 4,032 readings reports 4,033. To count readings you subtract the header or skip it with `tail -n +2` before counting.

**The trap.** Reporting the `wc -l` figure as the number of readings without removing the header.

### grep-recursive

**What you must know.** `grep 'text' file` prints matching lines from one file. `-r` searches a whole directory tree, `-n` shows line numbers, and `-i` ignores case. Combined, `grep -rin 'pm2_5' /srv/hunt` finds the text in any case, in any file below `/srv/hunt`. The pattern is a regular expression, so a dot matches any single character. `PM2.5` therefore also matches `PM205`. Quoting the pattern and adding commas, as in `',PM2.5,'`, makes the match exact.

**The trap.** Running `grep` on a directory without `-r`. The error is `Is a directory`, and nothing is searched.

### io-redirection

**What you must know.** `>` writes standard output to a file and replaces the file. `>>` appends to the file. `<` reads a file as input. `2>` redirects standard error. `|` sends standard output into the next command. Each stream is separate, which is why an error message can go to a file while the normal results still appear on screen.

**The trap.** Writing `sort data.csv > data.csv`. The shell truncates `data.csv` to empty before `sort` reads it, so the file is destroyed. Write to a new file, or use `sort -o data.csv data.csv`.

### chmod-permissions

**What you must know.** The permission string has three groups of `rwx`, for owner, group and others. The numbers are r=4, w=2, x=1. `600` gives the owner read and write and nothing to anyone else, which is right for `.env`. `644` gives everyone read access, which is normal for public files. `+x` adds execute for scripts. Never use `777` to fix an error, because it allows everyone to change the file.

**The trap.** Choosing `644` or `777` for a file that holds API keys. Both expose the secret to other users on the server.

### cut-sort-uniq-pipeline

**What you must know.** `cut -d, -f1` keeps the first field of each comma-separated line. `sort` orders lines, and `sort -n` orders them as numbers, `-r` reverses the order, and `-k2` sorts on the second field. `uniq -c` counts runs of identical adjacent lines. The full chain `cut | sort | uniq -c` is the shell's group-by.

**The trap.** Running `uniq -c` without `sort` first. `uniq` only merges neighbouring duplicates, so unsorted input gives many small counts instead of one count per station.

### df-disk-space

**What you must know.** `df -h` reports the total, used and free space for each filesystem in human units. It answers "how full is the disk?" `du -h` reports how much space a directory takes up. It answers "which folder is big?". Both are used together when a disk fills up.

**The trap.** Using `free -h` for disk space. It reports memory (RAM), not disk.

### pwd

**What you must know.** `pwd` prints the absolute path of the working directory. Relative paths and commands such as `find` or `cp` depend on it, so you check it before running them. A wrong working directory is a common reason for "No such file or directory".

**The trap.** Assuming `cd` changed the directory for the whole session. It changes only the current shell, and a script you run starts in the directory where you run it.

### process-kill

**What you must know.** `jobs` lists background jobs in the current shell, and `kill %N` stops job number N. `ps aux` lists all processes with their PIDs. `kill PID` sends the TERM signal, which asks a program to stop cleanly. `kill -9` uses KILL, which cannot be caught and skips cleanup. Use the plain signal first.

**The trap.** Reaching for `kill -9` immediately. It works, but it can leave files half-written, and it is not the first step.

## The graded lab skill

The graded lab is a Python problem. You write functions, the platform runs visible tests and then hidden tests, and the hidden tests check the edge cases you missed. This section teaches the Python you need from nothing, then sets a practice problem of the same kind.

### Python from nothing

A **function** is a named block of code. You write it with `def`, give it parameters (the inputs) and return a value:

```python
def double(x):
    return x * 2
```

`def` starts a function definition, `double` is its name and `x` is its parameter. The indented line does the work, and `return` sends the result back. Calling `double(4)` gives `8`.

A **list** is an ordered collection, written with square brackets: `["ST-01", "ST-02"]`. A **for loop** visits each item in turn:

```python
for line in ["a", "b"]:
    print(line)
```

This prints `a` and then `b`. The indentation under `for` shows which lines belong to the loop.

An **if** statement runs code only when a condition is true. `continue` jumps to the next loop item, skipping the rest of the current one.

Strings have methods. `text.strip()` removes spaces and newlines from both ends. `text.split(",")` cuts a string at each comma and returns a list of pieces. So `"a, b".split(",")` gives `["a", " b"]`, and `.strip()` on each piece gives `["a", "b"]`.

A **dictionary** stores key and value pairs in braces. `counts = {}` makes an empty one. `counts.get(key, 0)` returns the value for a key, or `0` if the key is missing. Writing `counts[key] = counts.get(key, 0) + 1` is the Python form of `uniq -c`.

A **tuple** is a fixed pair written in brackets, such as `("10.0.0.2", 2)`. `dictionary.items()` gives a list of such pairs.

`list.sort(key=...)` sorts a list using a rule. A **lambda** is a short unnamed function. `key=lambda pair: (-pair[1], pair[0])` sorts by the second item of each pair, largest first because of the minus sign, and by the first item when two counts are equal. Tuples compare item by item, which makes this two-level sort possible.

A slice `items[:n]` returns the first n items. An `assert` line checks a condition and stops with an error if it is false. The tests in this book use `assert` so that a wrong result fails the build.

### The practice problem

Each line of a web-server log has four comma-separated fields: `ip,timestamp,path,status`. For example:

```text
10.0.0.2,2025-01-01T00:00:00,/home,200
```

Write the following functions in one file:

1. `filter_by_status(lines, status)` returns the lines whose fourth field equals `status`, in their original order.
2. `extract_column(lines, index)` returns the field at position `index` from each line, in order.
3. `count_items(items)` returns a list of `(item, count)` tuples, sorted by count from highest to lowest, and for equal counts by item in ascending order.
4. `top_n(pairs, n)` returns the first `n` pairs.
5. `top_ips_for_status(lines, status, n)` chains the four above and returns the top `n` `(ip, count)` pairs for that status.

This is the same job as `grep ',200,' | cut -d, -f1 | sort | uniq -c | sort -rn | head -n 2`, written as small functions that you can test one by one.

**Example.** For these three lines with status `200`, the ips are `10.0.0.2`, `10.0.0.1` and `10.0.0.2`. So `top_ips_for_status(lines, "200", 2)` returns `[("10.0.0.2", 2), ("10.0.0.1", 1)]`.

### Edge-case checklist

Work through this list before you submit. The hidden tests use these cases.

- **Empty input.** An empty list of lines must return an empty list from every function, not an error.
- **Ties.** When two items have the same count, the item that comes first alphabetically must come first.
- **Ordering.** Ordering of IP addresses is text order, not numeric order. So `"10.0.0.10"` sorts before `"10.0.0.2"`. The rule is text order, so do not convert the IPs to numbers.
- **Types.** The status might arrive as the number `200` or the text `"200"`. Convert it with `str(status)` before comparing.
- **Rounding.** Nothing is rounded here, because the results are counts. If a task asks for averages, decide the rounding rule before you write any code.
- **Missing fields.** A line with fewer than four fields must be skipped, not allowed to crash the function.
- **Blank lines.** An empty line or a line of spaces must be ignored.
- **The number n.** Zero or a negative number returns an empty list. A number larger than the number of pairs returns every pair.

:::answer Show the full solution and the explanation
```python test
def split_fields(line):
    """Split one CSV line into stripped fields."""
    return [field.strip() for field in line.strip().split(",")]


def filter_by_status(lines, status):
    """Keep lines whose fourth field equals status."""
    kept = []
    for line in lines:
        fields = split_fields(line)
        if len(fields) < 4:
            continue
        if fields[3] == str(status).strip():
            kept.append(line)
    return kept


def extract_column(lines, index):
    """Return the field at index from each non-blank line."""
    values = []
    for line in lines:
        if not line.strip():
            continue
        fields = split_fields(line)
        if index < len(fields):
            values.append(fields[index])
    return values


def count_items(items):
    """Return (item, count) pairs, highest count first, then item ascending."""
    counts = {}
    for item in items:
        counts[item] = counts.get(item, 0) + 1
    pairs = list(counts.items())
    pairs.sort(key=lambda pair: (-pair[1], pair[0]))
    return pairs


def top_n(pairs, n):
    """Return the first n pairs, or an empty list if n is not positive."""
    if n <= 0:
        return []
    return pairs[:n]


def top_ips_for_status(lines, status, n):
    """Chain the helpers: filter, extract the ip, count, then take the top n."""
    kept = filter_by_status(lines, status)
    ips = extract_column(kept, 0)
    return top_n(count_items(ips), n)


lines = [
    "10.0.0.2,2025-01-01T00:00:00,/home,200",
    "10.0.0.1,2025-01-01T00:00:01,/home,404",
    "10.0.0.2,2025-01-01T00:00:02,/api,200",
    "10.0.0.3,2025-01-01T00:00:03,/api,200",
    "10.0.0.1,2025-01-01T00:00:04,/home,200",
    "10.0.0.3,2025-01-01T00:00:05,/api,200",
    "",
    "bad line",
]

# filter_by_status keeps only the 200 rows and skips blank and malformed lines
assert len(filter_by_status(lines, "200")) == 5
assert len(filter_by_status(lines, 200)) == 5
assert filter_by_status(lines, "500") == []
assert filter_by_status([], "200") == []
assert filter_by_status(["1.1.1.1,t,/x"], "200") == []
assert filter_by_status(["1.1.1.1,t,/x, 200 "], "200") == ["1.1.1.1,t,/x, 200 "]

# extract_column
assert extract_column(["a,b,c", "", "d,e,f"], 1) == ["b", "e"]
assert extract_column(["a,b"], 5) == []
assert extract_column([], 0) == []

# count_items: highest count first, then item in ascending text order
assert count_items(["x", "y", "x"]) == [("x", 2), ("y", 1)]
assert count_items([]) == []
assert count_items(["10.0.0.2", "10.0.0.10"]) == [("10.0.0.10", 1), ("10.0.0.2", 1)]

# top_n
assert top_n([("a", 3), ("b", 1)], 0) == []
assert top_n([("a", 3), ("b", 1)], -2) == []
assert top_n([("a", 3), ("b", 1)], 5) == [("a", 3), ("b", 1)]

# the full pipeline
assert top_ips_for_status(lines, "200", 2) == [("10.0.0.2", 2), ("10.0.0.3", 2)]
assert top_ips_for_status(lines, "200", 3) == [("10.0.0.2", 2), ("10.0.0.3", 2), ("10.0.0.1", 1)]
assert top_ips_for_status(lines, "404", 5) == [("10.0.0.1", 1)]
assert top_ips_for_status([], "200", 3) == []
assert top_ips_for_status(lines, "200", 0) == []
```

**Explanation, line by line.**

- `split_fields` strips the line of its outer spaces and newline, splits it at each comma, and strips each piece. A blank line becomes a list with one empty string.
- `filter_by_status` loops over the lines. `len(fields) < 4` skips short lines, which handles the missing-field case. `fields[3]` is the status, because counting starts at zero. `str(status).strip()` turns `200` into `"200"`, so both number and text work. The original line is appended, not the split version, so the output matches the input format.
- `extract_column` skips blank lines first. The `index < len(fields)` check prevents an error on short lines.
- `count_items` builds a dictionary of counts, using `get` so that a new item starts at zero. `counts.items()` gives the pairs. The sort key `(-pair[1], pair[0])` sorts by count descending, because of the minus sign, and then by item ascending, because the first item is compared as text.
- `top_n` returns nothing for zero or a negative number. `pairs[:n]` returns at most `n` pairs, so a large `n` simply returns everything.
- `top_ips_for_status` is the pipeline. Each step does one thing and passes its result to the next, the same way the shell does.

The first assertion counts 5 kept lines. The IP `10.0.0.2` appears twice and `10.0.0.3` appears twice, so they are tied, and text order puts `10.0.0.2` first. The `10.0.0.1` line with status 404 is excluded from the 200 results, but it is the only line for the 404 test.

## Say it out loud

Interviewers and viva examiners ask these questions to see whether you understand the tools or only remember the commands.

**1. What does `grep ',PM2.5,' jan.csv | cut -d, -f1 | sort | uniq -c` do, and why is `sort` needed?**

:::answer Model answer
The command keeps only the PM2.5 rows, takes the station id from the first column of each row, and counts how many rows each station has. `sort` is needed because `uniq -c` only merges lines that sit next to each other. Without sorting, the rows for one station are scattered, so `uniq` would print many small counts instead of one total per station.
:::

**2. What is the difference between an absolute and a relative path, and why does it matter for a script?**

:::answer Model answer
An absolute path starts at the root `/` and means the same place wherever you run from, such as `/data/readings/jan.csv`. A relative path starts from the current working directory, such as `raw/jan.csv`, so it points somewhere different if you run the script from another folder. For a script, absolute paths or a check with `pwd` first make the results repeatable. Relative paths are fine when the script is designed to run from one known location.
:::

**3. Why set `.env` to `600` rather than `644`?**

:::answer Model answer
The `.env` file holds API keys, which are secrets. Mode `600` gives read and write to the owner and nothing to the group or to other users. Mode `644` lets every user on the shared server read the file, and anyone who reads the keys can use them. Permissions are the only thing protecting a file on a multi-user machine, so you grant only what is needed.
:::

**4. How do you stop a process that is running in the background, and why not `kill -9` first?**

:::answer Model answer
First find it with `jobs` for a job started in your shell, or with `ps aux` and a filtered grep for any process. Then send the plain `kill` command, which sends the TERM signal and lets the program finish cleanly. `kill -9` sends KILL, which the program cannot catch, so it stops at once without running cleanup code and may leave files half-written. Use `-9` only when the program ignores TERM.
:::

**5. Why use a virtual environment instead of installing packages globally with pip?**

:::answer Model answer
A virtual environment keeps each project's packages in its own folder, so two projects can use different versions of the same library without conflict. Global installs share one set of packages, so a change for one project can break another. On the shared lab server, global installs also need administrator rights and change the system Python for everyone. The venv also records exact versions in `requirements.txt`, so a teammate gets the same setup.
:::
