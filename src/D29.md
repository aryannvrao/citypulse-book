SUB: You will be able to rank a backlog with MoSCoW, state a model's impact in business units, cut a tagged release with a handover document, and write a tested Python function that plans a sprint.

## The idea in one minute

Building a project and delivering it are different jobs. Delivery means that someone who did not write the code can run it, explain it and keep it alive after you leave. Today you practise the four steps that make that possible. You sort your to-do list into what must ship and what waits. You translate your model's error into minutes or rupees that a client can act on. You name the release with a version tag, and you write a handover document that a stranger can follow.

Think of a cook opening a restaurant. The menu needs an order and prices, the owner needs to know what each dish costs in rupees rather than grams, the kitchen needs a recipe card for each dish, and the restaurant needs a way to go back to last week's menu if tonight's goes wrong.

## Starting from zero

**Project, client and stakeholder.** A project is a piece of work with a goal and an end date. The client is the person or organisation the work is for. A stakeholder is anyone with a stake in the result, such as the client, the mentor who marks the work, or the people who will run it after you.

**Backlog, sprint and story point.** A backlog is a list of work items, often called tickets. A sprint is a fixed period, usually one or two weeks, in which the team commits to some of those items. A story point is a number the team agrees on to compare the effort of two items. It is not an hour count.

**File, folder, terminal and command.** A file is a named piece of stored text or data. A folder (also called a directory) holds files and other folders. The terminal is a text window where you type commands, which are instructions the computer runs when you press Enter. A flag is an option that changes what a command does. In `git log --oneline`, the word `--oneline` is a flag.

**Git vocabulary.** Git records the history of a folder of files. A repository (repo) is a folder that Git tracks. A commit is a saved snapshot with a message. A tag is a permanent name attached to one commit. A remote is a copy of the repository on another machine, and `origin` is the usual name for the main one. To clone is to copy a remote repository to your machine.

**Code vocabulary.** A variable is a name that holds a value, such as `remaining = 3`. A function is a named block of code that you call with inputs, such as `advise(12.0)`. A server is a program that waits for requests and sends replies. A port is a numbered door on a machine, such as 8000, where a server listens. An endpoint is one address a server answers, such as `/predict`. HTTP is the request-and-reply protocol the web uses. A status code is the number in the reply: 200 means success and 422 means the input was rejected. JSON is a text format for structured data, written with braces and square brackets.

**Docker vocabulary.** An image is a packaged copy of an app with everything it needs to run. A container is one running copy of an image. A registry is a shared store where images are kept so that other people can pull them.

**Model vocabulary.** A model is a program that has learned patterns from data. A baseline is the simple rule you compare against, such as "use the median wait time of past patients". MAE (mean absolute error) is the average size of the model's mistake, in the same units as the thing predicted. A holdout is data kept aside during training and used only for testing. Data leakage happens when the model learns from information it would not have at prediction time.

**Bus factor.** The number of people who would have to leave a project before it could no longer be maintained. A bus factor of 1 means one person holds the knowledge.

## The tools

### MoSCoW prioritisation

MoSCoW sorts every backlog item into one of four buckets: Must have, Should have, Could have, and Won't have (this time). The name is an acronym made from the first letter of each bucket and the vowels added for pronunciation.

CityPulse uses it because the course gives you a fixed deadline and no usage data. The slides compare three alternatives. RICE scoring gives numeric scores for reach, impact, confidence and effort, but it needs data you will not have in a three-week project. The Kano model is useful for customer delight, but it is heavier than a fixed deadline needs. An unordered to-do list has no overhead, but everything looks equally urgent, so the core chain of work slips. MoSCoW forces an explicit decision about what the product cannot ship without, and it records what you left out, so that scope creep can be seen.

The rule is simple. For each candidate item, ask: does the product fail without it? Only the items where the answer is yes become Musts, and the course caps them at five. Each Must gets an owner, a one-line acceptance test and a ticket number. Each Won't gets a written reason, so that you can point to it when someone asks again.

Musts come first, so the sprint is filled with the core work before anything else. The following trace shows the selection loop in a small form. You will write a version of it in the graded lab skill section.

```trace
TITLE: Filling a sprint with a capacity of 3
CODE:
remaining = 3
selected = []
for effort in [2, 3, 1]:
    if effort <= remaining:
        selected.append(effort)
        remaining -= effort
STEPS:
1 :: remaining=3 :: Set the free capacity to 3 story points.
2 :: remaining=3; selected=[] :: Nothing has been chosen yet.
3 :: effort=2; remaining=3; selected=[] :: The loop takes the first item, which costs 2.
4 :: effort=2; remaining=3; selected=[] :: Is 2 at most 3? Yes, so the test passes.
5 :: effort=2; remaining=3; selected=[2] :: The item is added to the list.
6 :: effort=2; remaining=1; selected=[2] :: Its effort is taken off the capacity, leaving 1.
3 :: effort=3; remaining=1; selected=[2] :: The next item costs 3.
4 :: effort=3; remaining=1; selected=[2] :: Is 3 at most 1? No, so the item is skipped.
3 :: effort=1; remaining=1; selected=[2] :: The last item costs 1.
5 :: effort=1; remaining=1; selected=[2, 1] :: 1 fits, so it is added.
6 :: effort=1; remaining=0; selected=[2, 1] :: Capacity is now used up.
```

The loop does not stop at the first item that does not fit. It keeps going, so a small item later in the list can still be chosen. This is the behaviour that lets a sprint use its capacity fully.

:::trap Six or more Musts
If everything is a Must, nothing is. The slides say that a list of six or more Musts means the list has not been sorted. Move the extras to Should, and keep the Musts to five or fewer.
:::

:::trap Vague acceptance lines
"Works well" cannot be checked, so it cannot be a Must's acceptance line. Write a command or a number that someone else can run. The slides use `curl -d @tests/sample.json` returns 200.
:::

### Business metrics from ML metrics

An ML metric such as MAE, recall or precision describes how wrong the model is. A client does not decide in those units. A client decides in minutes, cases caught or rupees. Translating the metric means stating the improvement over the current way of working, in those units, with the assumption that connects them.

The course uses a hospital outpatient (OPD) brief as the example. The model predicts how long a patient will wait. The current rule is the median wait of past patients, which is the baseline. The model's MAE is 12.1 minutes and the baseline's error is 18.4 minutes, so the model is about 6.3 minutes closer per patient on the holdout. That is the sentence the client needs, and the slides want it in the README.

The slides also require a sensitivity check. You multiply the MAE by 1.10, which models a production model that is 10% worse than the test result. If the worse number still beats the baseline, the claim survives a bad day.

The code below writes the numbers to `metrics.json`, so that every slide and report can copy them from one place.

```python
import json, joblib, pandas as pd, yaml
from sklearn.metrics import mean_absolute_error
cfg = yaml.safe_load(open("config.yaml")); base = json.load(open("reports/baseline.json"))
df = pd.read_parquet("data/clean/dataset.parquet")
test = df[df[cfg["data"]["date_col"]] >= cfg["split"]["holdout_from"]]
model, target = joblib.load("models/model.joblib"), cfg["data"]["target"]
mae = mean_absolute_error(test[target], model.predict(test.drop(columns=[target])))
sens = mae * 1.10                                   # what if production is 10% worse?
metrics = {"model": {"mae": round(mae, 2)}, "baseline": base,
           "improvement_pct": round((base["value"] - mae) / base["value"] * 100, 1),
           "sensitivity_10pct": {"mae": round(sens, 2), "beats_baseline": bool(sens < base["value"])},
           "segments_worse_than_baseline": []}      # fill from the per-department loop
json.dump(metrics, open("metrics.json", "w"), indent=2)
print(f"Wait-time estimates are off by {mae:.1f} min per patient, versus {base['value']:.1f} min today.")
```

Line by line:

- `import json, joblib, pandas as pd, yaml` loads four libraries. `json` reads and writes JSON, `joblib` loads a saved model, `pandas` handles tables and `yaml` reads configuration files. `as pd` gives pandas the short name `pd`.
- `from sklearn.metrics import mean_absolute_error` loads one function from the scikit-learn library, the function that computes MAE.
- `cfg = yaml.safe_load(open("config.yaml"))` opens the configuration file and turns it into a dictionary, a named collection of values. `base = json.load(...)` does the same for the baseline's result.
- `df = pd.read_parquet(...)` reads the cleaned dataset into a table called a data frame.
- `test = df[...]` keeps only the rows whose date is on or after the start of the holdout. The condition inside the square brackets is a true-or-false test for each row.
- `model, target = joblib.load(...), cfg[...]` loads the saved model and reads the name of the column to predict.
- `mae = mean_absolute_error(...)` asks the model for predictions on the test rows, with the target column removed (`drop`), and compares them with the true values.
- `sens = mae * 1.10` is the 10% worse scenario. The comment after `#` is ignored by Python.
- `improvement_pct` is the gain as a percentage of the baseline. `round(..., 1)` keeps one decimal place. With the slide numbers, (18.4 − 12.1) / 18.4 × 100 gives 34.2.
- `beats_baseline` is `True` when the worse scenario is still lower than the baseline. `bool(...)` turns the result into `true` or `false` for the JSON file.
- `segments_worse_than_baseline` is an empty list here. You must fill it with the departments where the model loses.
- `json.dump(..., indent=2)` writes the dictionary to `metrics.json` with two spaces of indentation, which makes the file easy to read.
- The last `print` line uses an f-string, a text with `{}` slots filled by variables. `{mae:.1f}` shows the MAE with one decimal place.

With the slide values, the output is `Wait-time estimates are off by 12.1 min per patient, versus 18.4 min today.`

:::trap Claiming minutes saved
The model reduces estimate error. It does not save anyone minutes by itself. Write exactly what changes: "wait estimates are closer by 6.3 minutes per patient". Do not write "the hospital saves six hours a day" unless you have measured that.
:::

:::trap Improvement over 40 per cent
A large gain is a warning sign. Check for leakage first, such as a feature that is only known after the outcome. The slides ask you to re-check before you celebrate.
:::

:::trap Hiding the segments where the model loses
If the model is worse than the baseline for one department, list it in `segments_worse_than_baseline` and in the Known limits section. Leaving it out is an overclaim, and the slides treat that as a failure.
:::

### HANDOVER.md and bus factor

A HANDOVER.md file gives a newcomer the architecture, a runbook of exact commands, the known issues and the next steps. It is the document that lets a project continue without its original authors. The slides list three alternatives: a README alone is fine for users but does not hold the runbook or the ownership a maintainer needs; a wiki drifts from the code and is not reviewed in pull requests; a recorded video cannot be searched or copied, and commands must be text.

Bus factor is measured from git history. The question is not "how many commits did each person make?" but "how many distinct people have changed this module?" A module with one author has a bus factor of 1, and the course asks you to assign a non-author as a second owner.

The following term block shows the basic count for one folder. The command lines start with `$`. The line below the command is what the terminal prints.

```term
$ git log --format='%an' -- api/ | sort -u | wc -l
1
```

The output means that only one distinct author name appears in the history of `api/`. The loop below repeats this check for each module and writes a table to a file.

```bash
for m in src/ingest src/train.py api ui tests; do
  n=$(git log --format='%an' -- "$m" | sort -u | wc -l)
  flag=$([ "$n" -lt 2 ] && echo "BUS FACTOR 1: assign second owner")
  echo "| $m | $n authors | $flag |"
done | tee -a docs/module-owners.md
git shortlog -sn --no-merges                 # commits per person
git log --author="Asha" --oneline -- api/    # verify a contribution statement
gh pr list --state merged --author @me --json number,title   # PR links for your statement
```

Line by line:

- `for m in src/ingest src/train.py api ui tests; do` starts a loop. The variable `m` takes each module path in turn, and the loop ends at `done`.
- `n=$(...)` runs the commands inside the brackets and stores their output in `n`. `$(...)` is command substitution.
- Inside the brackets, `git log --format='%an' -- "$m"` prints the author name of every commit that touched the path. `--format='%an'` prints only the author name. The `--` tells git that what follows is a path, not an option.
- `sort -u` sorts the names and removes duplicates. `wc -l` counts the lines that remain. The result is the number of distinct authors.
- `flag=$([ "$n" -lt 2 ] && echo "...")` tests whether `n` is less than 2 with `-lt`. If the test is true, `echo` prints the warning. If it is false, the flag stays empty.
- `echo "| $m | $n authors | $flag |"` prints one table row in Markdown format.
- `done | tee -a docs/module-owners.md` sends the output of the loop into `tee`, which shows it on the screen and appends it to the file. `-a` means append, so an earlier table is not overwritten.
- `git shortlog -sn --no-merges` prints commit counts per person. `-s` shows only the counts, `-n` sorts them from largest to smallest, and `--no-merges` leaves out merge commits.
- `git log --author="Asha" --oneline -- api/` lists Asha's commits to `api/`, one per line. Use it to check a claim before you write it down.
- `gh pr list --state merged --author @me --json number,title` asks GitHub's command-line tool for your merged pull requests and prints their number and title as JSON. `@me` means the account you are logged in with.

:::trap Commit count is not bus factor
A person with 200 commits and a second person with one commit can still leave a bus factor of 1, if the second person cannot explain or run the module. What counts is whether a second person can explain and run the module. The slides say the test is a second person who can explain and run it.
:::

:::trap Runbook commands that were never run
Each command in the runbook must be run on a clean clone before the document is merged. A command that has never been run is a guess.
:::

:::trap Contribution statements that overclaim
Every pull request you list must exist, and it must be yours or one you reviewed. The trainers check statements against `git log`.
:::

### Git tags and semantic versions

A tag is a permanent name for one commit. An annotated tag, made with `git tag -a`, also stores who made it, when, and a message. The course uses annotated tags with names like `v1.0.0`. The number follows the semantic versioning pattern of MAJOR.MINOR.PATCH, where a larger number means a bigger change. A tag makes a deploy or a rollback precise. "Deploy the latest" is vague. "Deploy v1.0.0" names one commit that anyone can check out again.

The flow below shows how the release leaves your laptop. Two things travel: the tag, which goes to GitHub, and the image, which goes to the registry.

```flow
TITLE: Moving a release from your laptop to the team
NODES: Your laptop | GitHub | Container registry | Receiving team
STEPS:
1>2 :: git push origin v1.0.0 :: The annotated tag travels to GitHub, where it names the commit.
1>3 :: docker push :: The container image travels to the registry.
4>2 :: git clone --branch v1.0.0 :: The team fetches the tagged source.
4>3 :: docker pull :: The team fetches the exact image you built.
```

The tagging commands from the slides are these.

```bash
git tag -a v1.0.0 -m "CityPulse v1.0.0: ingest, validate, advise"
git show v1.0.0 --no-patch
git describe --tags
```

Line by line:

- `git tag -a v1.0.0` creates an annotated tag called `v1.0.0` on the current commit. `-a` makes it annotated.
- `-m "..."` gives the tag its message in double quotes. The message is required for an annotated tag, so the tag records why it was made.
- `git show v1.0.0 --no-patch` displays the tag and the commit it points to. `--no-patch` hides the list of file changes, so you see only the summary.
- `git describe --tags` prints the nearest tag name for the current commit. Right after tagging, it prints `v1.0.0`.

The slide output for the first command shows the tag's tagger, date and message, followed by the commit hash `a01db2c...`, which is the exact commit the tag pins. Pushing the tag is a separate step. Until you run `git push origin v1.0.0`, the tag exists only on your machine.

:::trap Forgetting to push the tag
A tag created on your laptop is invisible to the team. Check that the tag is on GitHub, not only on your machine, before you announce the release.
:::

:::trap Rolling back with a detached HEAD
`git checkout v1.0.0` shows the old code, but git will say you are in a "detached HEAD" state. Do not commit there unless you create a branch first. To run the old version, rebuild or pull the old image tag instead.
:::

### Docker images for a release

Docker packages the service and its pinned dependencies into an image. A dependency is a library your code uses, such as a web framework. Pinned means you fix the exact version, so the same image is produced on every machine. The course gives the reason: handing over an image, not a "works on my machine" setup, removes environment drift, and the receiving team runs the exact bytes you tested.

The alternative to Docker that the course mentions indirectly is a README that asks the receiver to install everything. That works until one library version differs, and then the service behaves differently. An image does not depend on what is installed on the receiver's machine.

The Dockerfile is the recipe for the image. Each line adds a step.

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "service:app", "--host", "0.0.0.0", "--port", "8000"]
```

Line by line:

- `FROM python:3.11-slim` starts from a ready-made base image that has Python 3.11 installed. The `slim` version is a smaller build.
- `WORKDIR /app` sets `/app` as the folder that later commands run in. It is created if it does not exist.
- `COPY requirements.txt .` copies the dependency list from your computer into the image's `/app` folder. The `.` on the end means "the current folder".
- `RUN pip install --no-cache-dir -r requirements.txt` runs a command while the image is built. `pip` installs Python packages, `-r` reads the list from the file, and `--no-cache-dir` stops pip from keeping a download cache inside the image, which keeps the image smaller.
- `COPY . .` copies the rest of your project into the image. The dependency step comes before this line on purpose. Docker reuses saved steps when nothing above them has changed, so changing only your code does not reinstall every package.
- `EXPOSE 8000` documents that the service listens on port 8000. It does not open the port on its own.
- `CMD [...]` is the command that starts when a container runs. `uvicorn` is a web server for Python. `--host 0.0.0.0` makes it listen on all network interfaces inside the container, and `--port 8000` sets the port.

The build command and its output are below.

```term
$ docker build -t citypulse:1.0.0 .
[+] Building 14.2s (10/10) FINISHED
=> naming to docker.io/library/citypulse:1.0.0
```

Line by line: `docker build` creates an image from the Dockerfile in the current folder, which is the final `.`. `-t citypulse:1.0.0` gives the image a name, `citypulse`, and a tag, `1.0.0`. The first output line says the build finished in 14.2 seconds across 10 steps. The second line confirms the name the image was saved under. The slide output is shortened here, because the full build log is long.

:::trap Dockerfile and file list do not match
The slide's Dockerfile starts the server with `service:app`, which means a file called `service.py`. The file list in the Step 3 commit example does not include `service.py`. Before you build, check that the file the `CMD` line names exists in your repository. This is the kind of mismatch that a stranger finds in the first minute.
:::

:::trap Pushing a tag before the image builds
In the release script shown in the worked example, the tag is pushed before the Docker build runs. If the build then fails, the tag is already on GitHub. Decide the order before you run the script for real.
:::

### GitHub Pages portfolios

GitHub Pages publishes static files (HTML pages, CSS styling and media) from a GitHub repository as a free website over HTTPS. The course's portfolio uses the repository named `<username>.github.io`, and the site is published from its `main` branch. A portfolio must show who you are, what you built, proof that it works, and how to contact you, in a page that a hiring manager can scan in 30 seconds.

The slides compare the alternatives. Netlify and Vercel offer similar free hosting with previews, but they need another account, and Pages is enough for one page. A LinkedIn profile must be consistent with the portfolio, but it cannot embed demo media or structure case studies well. Drag-and-drop website builders charge for HTTPS on custom domains, and they keep no Git history.

The publishing commands are below. They create the repository, copy the starter files, compress a demo video, and push.

```bash
GH_USER=$(gh api user --jq .login)
gh repo create "$GH_USER.github.io" --public --clone && cd "$GH_USER.github.io"
cp -r ../portfolio-starter/. .
mkdir -p assets
ffmpeg -i ~/Videos/citypulse-demo.mov -t 45 -vf "scale=720:-2" -c:v libx264 -crf 28 -an -movflags +faststart assets/citypulse-demo.mp4
ls -lh assets/citypulse-demo.mp4
git add . && git commit -m "Portfolio: hero, CityPulse case study, demo" && git push -u origin main
sleep 60 && curl -sI "https://$GH_USER.github.io" | head -1
```

Line by line:

- `GH_USER=$(gh api user --jq .login)` stores your GitHub username in a variable. `gh api user` fetches your profile from GitHub, and `--jq .login` picks out only the `login` field.
- `gh repo create "$GH_USER.github.io" --public --clone` creates a public repository with that name and copies it to your machine. `--public` makes it visible to everyone, which Pages needs.
- `&& cd "$GH_USER.github.io"` runs only if the first command succeeded, and then moves into the new folder. `cd` means change directory.
- `cp -r ../portfolio-starter/. .` copies everything from the starter folder into the current folder. `-r` copies folders as well as files.
- `mkdir -p assets` creates the `assets` folder. `-p` means "create it, and do not fail if it already exists".
- `ffmpeg -i ~/Videos/citypulse-demo.mov` reads the input video. `~` means your home folder.
- `-t 45` keeps only the first 45 seconds.
- `-vf "scale=720:-2"` is a video filter. It sets the width to 720 pixels and calculates the height to keep the shape, and the `-2` makes the height an even number, which video codecs need.
- `-c:v libx264` chooses the H.264 video codec, which plays on almost every phone.
- `-crf 28` sets the quality. A higher number gives a smaller, lower-quality file.
- `-an` removes the audio track.
- `-movflags +faststart` moves the file's index to the front, so the video can start playing before it has fully downloaded.
- `assets/citypulse-demo.mp4` is the output file.
- `ls -lh` lists the file with a human-readable size. The slides require it to be under 5 MB. The output is a line such as `-rw-r--r-- ... 3.1M ... assets/citypulse-demo.mp4`, and the size is the figure you check.
- `git add . && git commit -m "..." && git push -u origin main` stages every file, commits it and pushes to GitHub. `-u` links your local `main` branch to the remote one, so later pushes need no extra words.
- `sleep 60` waits a minute, because Pages takes a short time to build the site after a push.
- `curl -sI "https://..." | head -1` asks for the headers only (`-I`), silently (`-s`), and shows the first line. The expected first line is `HTTP/2 200`.

:::trap Wrong repository name
The site is published only from a repository named exactly `<username>.github.io`. A repository with any other name gives a site at a different address.
:::

:::trap Video that stalls on a phone
Recruiters often open links on phones. Keep the demo under 5 MB and test it on a phone before you publish. A video that is fine on your laptop can stall on mobile data.
:::

:::trap Numbers that differ across documents
The résumé, LinkedIn profile and portfolio must show the same numbers. Copy them from `metrics.json` and keep all three the same.
:::

## The worked example

The workbook's example is the release of CityPulse v1.0.0. The goal is that a stranger can clone the repository, build the image and run the service, with a tag that names the exact tested commit. The full release script is below, with the line breaks that the slide extraction split put back together.

```bash
pytest -q || exit 1
git tag -a v1.0.0 -m "CityPulse v1.0.0"
git push origin v1.0.0
docker build -t citypulse:1.0.0 .
docker push registry.example.com/citypulse:1.0.0
echo "Release v1.0.0 published"
```

Line by line:

- `pytest -q` runs the tests in quiet mode. `pytest` is a Python testing tool that runs every test function in files whose names start with `test_`.
- `|| exit 1` means "if the command before this failed, stop the script with an error code of 1". The double bar `||` is the "or" that runs only when the left side fails. If a test fails, no tag or image is created.
- `git tag -a v1.0.0 -m "..."` creates the annotated tag, as explained above.
- `git push origin v1.0.0` sends the tag to the remote called `origin`.
- `docker build -t citypulse:1.0.0 .` builds the image from the Dockerfile.
- `docker push registry.example.com/citypulse:1.0.0` uploads the image to a registry. `registry.example.com` is a placeholder from the slides. Replace it with the registry your course gives you.
- `echo "..."` prints a final message, so you know the script reached the end.

The slide's test file is the first thing that runs. It checks the advisory bands that the service returns for pm2.5 readings. pm2.5 is a measure of fine particles in air, and the bands are the public-health categories built from it.

```python
from advisory import advise
def test_bands():
    assert advise(12.0) == "good"
    assert advise(49.7) == "moderate"
    assert advise(75.0) == "unhealthy"
    assert advise(140.0) == "hazardous"
```

Line by line, with the indentation restored: `from advisory import advise` loads the function `advise` from the file `advisory.py`. `def test_bands():` defines a test function, and pytest finds it because its name starts with `test_`. Each `assert` line states something that must be true. If one is false, pytest reports a failure. The four readings 12.0, 49.7, 75.0 and 140.0 are the test values. Only those four results are shown in the slides. The slides do not show `advisory.py` itself, so the thresholds are not given here.

Running `pytest -q .` in the project folder prints `1 passed in 0.00s`, which means the single test function passed. The `.` tells pytest to search the current folder.

The demo script is the last check, and it shows the service doing its job.

```python
from advisory import advise
for pm25 in [12.0, 49.7, 75.0, 140.0]:
    print(f"pm2.5={pm25:>6} -> {advise(pm25)}")
```

Line by line: the first line imports the same function. `for pm25 in [...]:` repeats the body once for each number in the list, and `pm25` holds the current number. The `print` line builds a sentence. `{pm25:>6}` right-aligns the number in a field six characters wide, which makes the arrows line up. `{advise(pm25)}` calls the function and inserts its answer. The slide extraction lost the spaces, but with this formatting the output is `pm2.5=  12.0 -> good`, then `pm2.5=  49.7 -> moderate`, then `pm2.5=  75.0 -> unhealthy`, then `pm2.5= 140.0 -> hazardous`. Run `python3 demo.py` in the project folder to see it for yourself.

## The hands-on lab, step by step

The slide material does not contain the exact commands for steps 1, 2, 3, 4 and 5, so the commands here are the standard ones for the tools named. ### Step 1: Compose the stack

**What you do.** Start every container the project needs, the service and its database, from one command.

**Type.** From the project folder, run `docker compose up -d --build`. `docker compose` reads the compose file in the folder and starts each service it describes. `-d` runs them in the background, so your terminal is free again. `--build` rebuilds the images first, so the code you have now is the code that runs.

**You should see.** One line per service, each saying that it was started or is running.

**You know it worked when.** `docker compose ps` lists every service with a state of running. The backlog's acceptance line for this step is "healthy in under 3 minutes on a spare laptop", so time it.

### Step 2: Wait for the database

**What you do.** Wait until the database accepts connections before you send it any data. A database container can be running while the database inside it is still starting.

**Type.** Run `docker compose ps` and look at the status column. If the database service has a health check, the status will change from `starting` to `healthy`. If it has none, run `docker compose logs <service-name>` and wait for the line that says the database is ready to accept connections. Replace `<service-name>` with the name from the compose file.

**You should see.** The database status changes to healthy, or its log says it is ready.

**You know it worked when.** The next step, which connects to the database, succeeds on the first try and not after an error about refused connections.

### Step 3: Seed cleaned readings

**What you do.** Load the cleaned air-quality readings into the database, so that the service has data to work from.

**Type.** The slides' backlog example names `make ingest`, which writes dated files into `data/raw/` and logs the number of rows. Your workbook gives the command that loads the cleaned readings into the database. Run that command from the project folder.

**You should see.** A log line that gives the number of rows loaded. The slides' example logs the row count, so a count of zero is a failure.

**You know it worked when.** The row count you see matches the number of readings in the file you started from.

### Step 4: Serve a prediction from stored data

**What you do.** Send a request to the running service and check that it returns a prediction.

**Type.** Run `curl -i -X POST -H "Content-Type: application/json" -d @tests/sample.json http://localhost:8000/predict`. `curl` sends the request, `-i` shows the reply headers, `-X POST` sends a POST request, `-H` sets the content type to JSON, `-d @tests/sample.json` sends the contents of that file as the body, and the address is the `/predict` endpoint on port 8000.

**You should see.** A first line of `HTTP/1.1 200 OK`, followed by JSON that contains the predicted wait in minutes.

**You know it worked when.** The status is 200. The backlog's acceptance line is "returns 200", so a 422 means the sample was rejected and you must fix the input, not the test.

### Step 5: End-to-end smoke test

**What you do.** Check the whole chain in one pass: the service runs, the test suite passes, and a request gets a 200.

**Type.** Run `pytest -q .` and then repeat the request from Step 4. A smoke test is a quick check that the main path works. It is not a full test.

**You should see.** `1 passed in 0.00s` or the number of tests in your suite, with the word `passed` and no `failed`, followed by the 200 status from the request.

**You know it worked when** both checks pass in the same session. If the test suite passes and the request fails, the problem is in the running service, not in the code the tests check.

**What you do.** Write a short script that feeds readings into the advisory function and prints the bands. The script is the proof that the service works.

**Type.** Create `demo.py` with the four lines from the worked example, then run `python3 demo.py`.

**You should see.** Four lines, one for each reading, each ending with a band word such as `good` or `hazardous`.

**You know it worked when** the output matches the bands in your test file. Use this script when you present, because it shows real readings turning into advisories in seconds.

### Step 7: Rollback plan

**What you do.** Write down how you will return to the last good version if the new release fails after it has been deployed.

**Type.** The plan has two parts. For the source code, check out the previous tag with `git checkout v1.0.0`. For the running service, start the previous image with `docker run -p 8000:8000 citypulse:1.0.0`. `-p 8000:8000` connects port 8000 on your machine to port 8000 in the container.

**You should see.** The plan written in your handover, with the tag name, the image tag, the exact commands, and the trigger, such as "the Step 5 smoke test fails after deploy".

**You know it worked when** someone else can read the plan and carry it out without asking you. The slides' rule is that a rollback is `git checkout` of a known tag, which is precise and reproducible.

## What the quiz tests

Each topic below is one of the ten you need for the day quiz. The slides for this lesson do not define these topics in detail, so the explanations come from standard project-management practice. Use the CityPulse examples to remember them.

### Requirements prioritisation

You must know how to rank requirements by necessity and value, and how to justify the ranking. MoSCoW is the method the course uses: a Must is an item the product cannot ship without, and everything else waits. A requirement is not a Must because the most senior person asked for it loudly. The examiner's trap is to treat importance as urgency, which lets a long list of Musts appear without a reason.

### Scope management

Scope is the set of work that will be delivered. Scope management means deciding what is in and what is out, and recording the decision so that it can be checked later. The Won't list is the record. The examiner's trap is accepting "one more feature" in a casual message, which adds work without removing anything from the sprint.

### Incremental delivery

Incremental delivery means shipping small pieces that work end-to-end, one after another, instead of finishing each layer before starting the next. A thin slice might go from ingesting one reading to returning one prediction. The examiner's trap is the team that builds the database for three weeks, then the model, then the interface, and finds the layers do not fit together at the end.

### Risk management

A risk is an event that may happen and would hurt the project. Good risk management records each risk, estimates how likely it is and how much damage it would do, assigns an owner, and writes what will be done about it. The course's own risk is that the data agreement may not arrive. The examiner's trap is a list of risks with no owner, no mitigation and no review date, which is a list of worries rather than a plan.

### Agile ceremonies

The main ceremonies are sprint planning, where the team chooses the work; the daily stand-up, a short status check; the sprint review, where the team shows working software to stakeholders; and the retrospective, where the team reviews how it worked. Each has a different audience and purpose. The examiner's trap is confusing the sprint review, which is about the product, with the retrospective, which is about the team's process.

### Acceptance criteria

Acceptance criteria are the conditions that prove a piece of work is done. They must be testable, which means someone can check them with a command or a number. "Returns 200 for the sample request" is testable. "Works well" is not. The examiner's trap is a criterion that sounds precise but has no way to fail.

### Handover runbook

A runbook is a document of exact steps for running and operating a system, including the expected output of each step, known issues and how to roll back. A handover runbook lets a stranger keep the system running. The examiner's trap is a runbook full of commands that its authors never ran, because the first real run then fails in front of the new owner.

### Roles and RACI

A RACI chart assigns each task a Responsible person, who does the work; an Accountable person, who signs off the result; those Consulted, who give input; and those Informed, who hear the outcome. Each task must have exactly one Accountable person. The examiner's trap is either two people marked Accountable, which means nobody is, or no Accountable person at all.

### Retrospective

A retrospective is a short meeting at the end of a sprint where the team asks what went well, what did not, and what it will change. Each change needs an owner and a date for the next sprint, or it will not happen. The examiner's trap is a retrospective that produces a list of complaints and no actions. The meeting should be blameless: it looks at the process, not at who made a mistake.

### Project charter

A project charter is a short document that starts a project. It states the purpose, the sponsor who authorises the work, the success measures, the main constraints and the main risks. A sprint plan is different: it lists the work for the next few weeks in detail. The examiner's trap is writing a day-by-day task list and calling it a charter, which leaves out why the project exists and who approved it.

## The graded lab skill

The graded lab asks you to write a few Python functions, which are then checked by visible tests and by hidden tests. The hidden tests look for edge cases you did not think of, so this section teaches the techniques first and then sets a practice problem that uses them.

**Functions that return values.** A function is defined with `def`, takes inputs in brackets and sends a result back with `return`. Your functions should return a value rather than print it, because a test can check a return value but cannot easily check printed text.

**Dictionaries and `.get`.** A dictionary is a collection of key-and-value pairs, written with braces, such as `{"id": "T1", "value": 9}`. You read a value with `ticket["value"]`, which fails with a `KeyError` if the key is missing. `ticket.get("rejected", False)` returns `False` when the key is missing, so it is safer for optional fields.

**Comparing tuples.** A tuple is a fixed group of values in round brackets, such as `(0, -9, 5, "T1")`. Python compares two tuples one position at a time, from the left. The first position that differs decides the order. This lets one tuple express a multi-level sort.

**Sorting with a key.** `sorted(items, key=f)` returns a new list in order of the value that `f` returns for each item. The original list is not changed. Negating a number, as in `-value`, makes a larger value sort first, because the smaller negative number comes earlier.

**Greedy selection.** A greedy method takes the best available option at each step and never reconsiders. For a capacity problem, you take each item in priority order if it fits in what is left. Greedy is not always optimal for every problem, but in this practice problem the priority order is the rule you are asked to follow.

**Raising errors.** `raise ValueError("...")` stops the function and reports that the input is invalid. Use it for inputs that cannot have a sensible answer, such as a negative capacity.

**Practice problem: sprint planning.** Write three functions for a sprint planner. Each ticket is a dictionary with the keys `id` (a string), `core` (True if the product fails without it), `value` (a whole number, higher is more valuable), `effort` (a whole number of story points) and an optional `rejected` key (True if the team has decided not to do it).

1. `bucket_of(ticket)` returns `"Won't"` if `rejected` is True. Otherwise it returns `"Must"` if `core` is True. Otherwise it returns `"Should"` if `value` is 5 or more, and `"Could"` if it is less than 5.
2. `sort_key(ticket)` returns a tuple that sorts the tickets by bucket in the order Must, Should, Could, Won't; then by value, highest first; then by effort, lowest first; then by `id` to break any remaining tie.
3. `plan_sprint(tickets, capacity)` walks through the tickets in sort order, skips every Won't, and adds each ticket whose effort fits in the remaining capacity. It returns the list of selected ids in the order they were chosen. A negative capacity raises `ValueError`.

Example. With the seven tickets in the solution's `tickets` list and a capacity of 10, the sort order is T1, T7, T2, T4, T3, T5, T6. The function selects T1 (5 points, 5 left), skips T7 (8 points does not fit), selects T2 (2 points, 3 left), selects T4 (1 point, 2 left), skips T3 (3 points does not fit), selects T5 (1 point, 1 left) and skips T6 (a Won't). The answer is `["T1", "T2", "T4", "T5"]`.

Edge-case checklist. Before you submit, check each of these.

- Empty input: an empty list returns an empty list, and capacity 0 selects nothing.
- Ties: two tickets in the same bucket with the same value are ordered by lower effort first, then by id. Your result must not depend on the order of the input list.
- Ordering: a Must that is low value still sorts before a high-value Should.
- Types: a ticket that is `rejected` and `core` at the same time is a Won't, because the rejection is checked first.
- Rounding: the inputs are whole numbers, so there is no rounding in this problem. If you find yourself rounding, something is wrong.
- Missing fields: decide what happens if `effort` is missing. The solution below raises a `KeyError` for missing required fields and uses `.get` only for `rejected`.
- Greedy stopping: a ticket that does not fit must not stop the loop. The loop must keep checking later, smaller tickets.
- Input safety: the function must not change the input list. `sorted` returns a new list, so the caller's list keeps its order.

:::answer Full solution and line-by-line explanation
```python test
MUST, SHOULD, COULD, WONT = "Must", "Should", "Could", "Won't"
BUCKET_ORDER = {MUST: 0, SHOULD: 1, COULD: 2, WONT: 3}


def bucket_of(ticket):
    if ticket.get("rejected", False):
        return WONT
    if ticket["core"]:
        return MUST
    if ticket["value"] >= 5:
        return SHOULD
    return COULD


def sort_key(ticket):
    return (BUCKET_ORDER[bucket_of(ticket)], -ticket["value"], ticket["effort"], ticket["id"])


def plan_sprint(tickets, capacity):
    if capacity < 0:
        raise ValueError("capacity cannot be negative")
    remaining = capacity
    selected = []
    for ticket in sorted(tickets, key=sort_key):
        if bucket_of(ticket) == WONT:
            continue
        if ticket["effort"] <= remaining:
            selected.append(ticket["id"])
            remaining -= ticket["effort"]
    return selected


tickets = [
    {"id": "T1", "core": True, "value": 9, "effort": 5},
    {"id": "T2", "core": True, "value": 3, "effort": 2},
    {"id": "T3", "core": False, "value": 8, "effort": 3},
    {"id": "T4", "core": False, "value": 8, "effort": 1},
    {"id": "T5", "core": False, "value": 2, "effort": 1},
    {"id": "T6", "core": False, "value": 9, "effort": 1, "rejected": True},
    {"id": "T7", "core": True, "value": 6, "effort": 8},
]

assert bucket_of(tickets[0]) == MUST
assert bucket_of(tickets[2]) == SHOULD
assert bucket_of(tickets[4]) == COULD
assert bucket_of(tickets[5]) == WONT
assert bucket_of({"id": "X", "core": True, "value": 9, "effort": 1, "rejected": True}) == WONT
assert bucket_of({"id": "X", "core": False, "value": 5, "effort": 1}) == SHOULD
assert bucket_of({"id": "X", "core": False, "value": 4, "effort": 1}) == COULD

order = [t["id"] for t in sorted(tickets, key=sort_key)]
assert order == ["T1", "T7", "T2", "T4", "T3", "T5", "T6"]

assert plan_sprint(tickets, 10) == ["T1", "T2", "T4", "T5"]
assert plan_sprint(tickets, 100) == ["T1", "T7", "T2", "T4", "T3", "T5"]
assert plan_sprint(tickets, 0) == []
assert plan_sprint([], 10) == []
assert [t["id"] for t in tickets] == ["T1", "T2", "T3", "T4", "T5", "T6", "T7"]

a = {"id": "A", "core": False, "value": 5, "effort": 3}
b = {"id": "B", "core": False, "value": 5, "effort": 2}
assert plan_sprint([a, b], 3) == ["B"]
assert plan_sprint([a, b], 5) == ["B", "A"]

try:
    plan_sprint(tickets, -1)
    raise SystemExit("expected ValueError")
except ValueError:
    pass
```

Line by line:

- `MUST, SHOULD, COULD, WONT = ...` gives the four bucket names one variable each. Using variables means a typo in a name is caught as an error rather than silently treated as a different bucket.
- `BUCKET_ORDER` maps each bucket to a number, so Must is 0 and Won't is 3. Sorting by these numbers puts the buckets in the required order.
- `bucket_of` checks the rules in order. The `rejected` check comes first, so a rejected core item is a Won't. `ticket["core"]` is required, so a missing key raises an error. `.get` is used only for `rejected`, which is optional.
- `sort_key` returns a tuple. The first item is the bucket number. The second is `-ticket["value"]`, so higher values sort first. The third is the effort, lower first. The fourth is the id, so the order is always the same for equal tickets.
- `plan_sprint` first rejects a negative capacity with `ValueError`.
- `sorted(tickets, key=sort_key)` returns a new list in sort order, so the input is not changed.
- The `continue` line skips every Won't. The `if` line adds a ticket only when its effort fits in what remains. The loop does not stop when a ticket does not fit, so smaller later tickets still get their chance.
- The `tickets` list is the example from the checklist. The `assert` lines check the bucket rules, the sort order, the selections at three capacities, the empty cases and the input safety check.
- The tie test uses two equal-value tickets. Ticket B has the smaller effort, so it sorts first, and it is chosen first even though it appears second in the list. With capacity 3, only B fits after it is chosen first. With capacity 5, both fit.
- The last block checks the negative capacity. It calls the function, which should raise `ValueError`. The `except` catches that error and does nothing, which means the test passes. If no error were raised, the `raise SystemExit` line would stop the program with a message, and the test would fail.

When you run this block, it prints nothing if every assert passes and finishes in well under a second.
:::
