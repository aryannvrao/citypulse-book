## The idea in one minute

A dashboard is a page of numbers and charts that a person can change with buttons and drop-down lists. Today you build one for CityPulse, the air-quality platform, so that a city officer can pick a date range and see three numbers that decide what to do next. The analogy is a car dashboard: it shows speed, fuel and an engine warning, not every sensor reading in the car.

By the end you will be able to explain how Streamlit reruns your script, cache a slow data load, add a sidebar filter, show KPIs with change arrows, and publish the app to a public web address without leaking a password.

## Starting from zero

This section explains the words the rest of the chapter uses. Skip what you already know.

A **file** is a named piece of stored data. A **folder** (also called a directory) holds files. A **terminal** is a text window where you type instructions to the computer. An instruction you type there is a **command**. For example, `ls` is a command that lists the files in the current folder.

A **script** is a file that contains instructions in order. Python is the language these scripts are written in. A **variable** is a name that holds a value, such as `total = 5`. A **function** is a named block of instructions you can run by writing its name and brackets. `len(x)` is a function call that returns the number of items in `x`.

A **library** (or package) is code someone else wrote that you can use. You add one with `pip install`. `pip` is the Python package installer. A **module** is a library or a file you bring in with `import`, as in `import pandas as pd`, which means "load pandas and call it `pd` in this file."

A **list** is an ordered collection written with square brackets: `["S1", "S2"]`. A **dictionary** (dict) maps keys to values, written with braces: `{"store": "S1", "amount": 10.0}`. You read a value with its key: `row["amount"]` gives `10.0`. A **tuple** is a fixed group of values in round brackets, such as `(2027, 1, 5)`.

A **DataFrame** is a table in memory, provided by the pandas library. It has named columns and numbered rows. A **parquet** file is a compact file format for tables. Pandas reads it with `pd.read_parquet`.

**S3** (Simple Storage Service) is Amazon's file storage. A **bucket** is a named container inside S3. A path such as `s3://my-bucket/clean/file.parquet` points at one file in one bucket.

A **server** is a program that waits for requests and answers them. A **browser** is the program you look at web pages in. A **URL** is a web address. `localhost` means "this computer", and `8501` is a **port**, a numbered door on a computer that a program listens on. So `http://localhost:8501` means "the program on this computer listening on door 8501."

**Git** records changes to a folder of files over time. That folder is a **repository**. A **commit** is one saved snapshot. A file named `.gitignore` lists files Git must never track. A **secret** is a password or key. Anyone who gets a secret can use the account it belongs to, so secrets must stay out of Git.

**Deploying** means putting an app on a machine that other people can reach. **Streamlit Community Cloud** is a free host for Streamlit apps. It runs your code from GitHub, which is a website that hosts Git repositories.

A **decorator** is a line starting with `@` placed above a function, such as `@st.cache_data`. It changes how the function behaves without you editing its body. A **cache** is a stored copy of a result, kept so that it does not have to be computed again.

A **widget** is a control on the page: a drop-down list, a date picker, a button. A **rerun** is one complete execution of your script from its first line to its last.

## The tools

### Streamlit apps and caching

**What it is.** Streamlit turns a Python script into an interactive web page. You write normal Python: call `st.title`, `st.selectbox`, `st.line_chart`. Streamlit draws each call as a part of the page. When the user changes a widget, Streamlit runs your whole script again from the top, and the page shows the new output.

**Why CityPulse uses it.** The team already writes pandas and Plotly code in Python, so the dashboard needs no HTML or JavaScript. The course compares it with three alternatives. Plotly Dash gives finer control through callbacks, but needs more code for a three-number dashboard. Power BI and Tableau are strong for business users, but the charts and logic already live in Python. FastAPI with React gives full control and scale, but is far more work than one ticket allows. Streamlit is the smallest correct choice for this ticket.

**How it works.** Here is the rerun model in plain terms. The browser shows widgets. Each widget has a current value. When you move the date picker, the browser sends the new value to the Streamlit server. The server runs `app/dashboard.py` from line 1 to the last line, with the widget now holding the new value, and sends the result back. Nothing is remembered between runs unless you store it on purpose, which the session-state topic covers in section 6.

Caching solves the cost problem. Every rerun repeats every line, including the line that reads a file from S3. A download on each click makes the app feel slow. `@st.cache_data(ttl=600)` tells Streamlit to store the return value of the function and reuse it for 600 seconds. `ttl` means "time to live", and its unit is seconds, so 600 is ten minutes.

The flow below shows what happens after a date change, both when the cache has an entry and when it has expired.

```flow
TITLE: One date change, one rerun
NODES: Browser | Streamlit server | Amazon S3
STEPS:
1>2 :: date changed :: The browser sends the new date range to the server.
2>2 :: cache hit :: The loader finds a copy younger than ten minutes and returns it.
2>3 :: cache miss :: Only when the copy is missing or expired, the loader asks S3 for the file.
3>2 :: file bytes :: S3 returns the daily aggregate file.
2>1 :: new page :: The script finishes and the browser redraws the page.
```

The flow has a self-loop (2 to 2) in the cache-hit step. Read it as "the server uses its own copy." The block accepts it because each step only needs a from and a to number.

Now watch the rerun happen. The code below is plain Python, not Streamlit. It simulates a cache with a counter, so you can see when a real read happens. Read it carefully and follow the steps.

```trace
TITLE: A cache stops repeated reads
CODE:
reads = 0
cache = {}
def load_daily():
    global reads
    if "daily" not in cache:
        reads += 1
        cache["daily"] = [1, 2, 3]
    return cache["daily"]
for click in range(2):
    data = load_daily()
STEPS:
1 :: reads=0 :: Create the read counter.
2 :: reads=0; cache={} :: Create an empty cache.
3 :: reads=0; cache={}; load_daily=<function> :: Define the function. Nothing is called yet.
9 :: click=0; reads=0; cache={} :: The loop starts with the first click.
10 :: click=0; reads=0; cache={} :: The function is called. Its body runs next.
5 :: click=0; reads=0; cache={} :: "daily" is not in the cache, so the if body runs.
6 :: click=0; reads=1; cache={} :: The counter goes up because a real read has happened.
7 :: click=0; reads=1; cache={"daily": [1, 2, 3]} :: The data is stored in the cache.
8 :: click=0; reads=1; cache={"daily": [1, 2, 3]} :: The function returns the stored list.
10 :: click=0; reads=1; data=[1, 2, 3] :: The returned list is stored in data.
9 :: click=1; reads=1; data=[1, 2, 3]; cache={"daily": [1, 2, 3]} :: The second click reruns the loop.
10 :: click=1; reads=1; data=[1, 2, 3]; cache={"daily": [1, 2, 3]} :: The function is called again.
5 :: click=1; reads=1; data=[1, 2, 3]; cache={"daily": [1, 2, 3]} :: "daily" is already in the cache, so the if body is skipped.
8 :: click=1; reads=1; data=[1, 2, 3]; cache={"daily": [1, 2, 3]} :: The stored list is returned with no new read.
```

The trace skips line 4 (`global reads`). That line is a declaration. It tells Python that `reads` inside the function means the outer variable, and it does nothing when it runs. After the trace, `reads` is still 1, and the second click did no read. That is exactly what `st.cache_data` does for your S3 file.

Streamlit's real decorator behaves the same way for this purpose. It keys the cache on the function and its arguments, and it returns a copy of the stored value, so changing the copy does not change the cache. The course still tells you to filter into a new variable and never change a cached DataFrame in place. Follow that rule, because it keeps the code easy to reason about.

:::trap Reading S3 outside a cached function
If you write `df = pd.read_parquet(...)` at the top level of the script, every click downloads the file again. The app then feels slow even though the code is correct. Put the read inside a function and decorate that function.
:::

:::trap Forgetting s3fs
Pandas reads `s3://` paths through a helper library called `s3fs`. If it is missing from `requirements.txt`, the dashboard fails on the cloud host even when it works on your laptop. Add it to the requirements file.
:::

:::trap Mutating a cached DataFrame
Writing `df["x"] = 0` on a cached DataFrame changes your working copy and makes later code hard to follow. Filter into a new variable such as `view = df[...]` and leave `df` alone.
:::

### KPI design

**What it is.** A KPI (key performance indicator) is one number with a clear formula, a unit and a "good" direction. It tells a user whether things are on track against a goal. A good dashboard shows few KPIs, each tied to the project's success metric, and each with a comparison, such as the change from the previous period.

**Why CityPulse uses three.** The client's earlier dashboard had 25 charts and was abandoned. Ticket T28 limits CityPulse to three KPIs and two charts. Two other designs were rejected. Showing all metrics feels complete, but users cannot tell what matters and stop opening the page. A single composite air-quality index gives one simple number, but hides which pollutant or station causes it.

**How it works.** Work backwards from the officer's daily decision to the few numbers that inform it. Write each KPI's formula and unit in the README KPI table before you write code. The dashboard then computes each KPI for the selected range and for the previous range of equal length. `st.metric` shows the value and the change.

The three KPIs for CityPulse are "Days over 60 µg/m³", "Mean PM2.5 (µg/m³)" and "Worst day (µg/m³)". The code below computes them from the daily table.

```python
from datetime import timedelta
import yaml

LIMIT = yaml.safe_load(open("config/limits.yaml"))["pm25_24h_limit"]

def kpis(df, start, end) -> dict:
    city = df[(df["date"] >= start) & (df["date"] <= end)].groupby("date")["pm25_mean"].mean()
    return {"over": int((city > LIMIT).sum()), "mean": round(city.mean(), 1), "worst": round(city.max(), 1)}

span = picked[1] - picked[0] + timedelta(days=1)
now, prev = kpis(df, picked[0], picked[1]), kpis(df, picked[0] - span, picked[0] - timedelta(days=1))
```

Line by line:

`from datetime import timedelta` brings in the `timedelta` type, which stores a length of time such as "3 days". `import yaml` loads the library that reads YAML, a text format for settings.

`LIMIT = yaml.safe_load(open("config/limits.yaml"))["pm25_24h_limit"]` opens the settings file, reads it, and takes out the value stored under `pm25_24h_limit`. `open` opens a file, and `safe_load` turns YAML text into Python values. The limit is 60 in the course. Reading it from the file means a change to the standard needs one edit, not a search through the code.

`def kpis(df, start, end) -> dict:` defines a function that takes a table and two dates. The `-> dict` note says it returns a dictionary. Python does not enforce it; it documents the intent.

`city = df[...].groupby("date")["pm25_mean"].mean()` keeps rows between the two dates, groups them by date, and averages the pollutant per day. The result is one city-wide value for each day.

`return {"over": ..., "mean": ..., "worst": ...}` returns a dictionary. `(city > LIMIT).sum()` counts the days above the limit: the comparison gives true or false for each day, and `sum` counts the trues. `int(...)` converts that count to a plain whole number.

`span = picked[1] - picked[0] + timedelta(days=1)` counts the days in the selected range. Both ends are included, so one day is added.

`prev = kpis(df, picked[0] - span, picked[0] - timedelta(days=1))` computes the same KPIs for the block of days just before the selection. The previous block ends the day before the selected start.

There is no output from this block on its own. Its results appear on the page through the metric cards in the next code block.

```python
c1, c2, c3 = st.columns(3)
c1.metric("Days over 60 µg/m³", now["over"], now["over"] - prev["over"], delta_color="inverse")
c2.metric("Mean PM2.5 (µg/m³)", now["mean"], round(now["mean"] - prev["mean"], 1), delta_color="inverse")
c3.metric("Worst day (µg/m³)", now["worst"], round(now["worst"] - prev["worst"], 1), delta_color="inverse")
```

`st.columns(3)` creates three side-by-side areas and returns them as three variables. `c1.metric(...)` draws a metric inside the first area. The first argument is the label. The second is the value shown big. The third is the change from the previous period, which Streamlit prints as an arrow with the number. `delta_color="inverse"` reverses the colour rule. With the default, a rise is green. For air quality, a rise is bad, so `inverse` makes a rise red.

On the page you should see three cards. The number on the first card is a whole number of days. The other two have one decimal place. Each shows an arrow and a change.

:::trap Default delta colours
Leaving out `delta_color="inverse"` shows a rise in PM2.5 as green. That tells the officer the wrong thing. Pollution metrics need `inverse`.
:::

:::trap Hard-coding the limit
Typing `60` inside the function means the code and the standard can drift apart. Read the value from `config/limits.yaml` the way the charts do.
:::

:::tip Name the formula in the viva
An examiner will ask what each KPI means. Say the formula in one sentence, the unit and the good direction. Three sentences of that per KPI covers the question.
:::

### secrets.toml and deployment

**What it is.** A secret is a value that proves who you are to a service, such as an AWS access key. The dashboard reads the S3 bucket with a read-only key called `citypulse-dashboard-ro`. Streamlit reads secrets from a file named `.streamlit/secrets.toml` on your laptop and exposes them to code as `st.secrets`. TOML is a plain-text settings format with `[section]` headings and `key = "value"` lines.

**Why CityPulse uses it.** On Streamlit Community Cloud you paste the same TOML text into the app's Secrets settings, so the cloud app gets its keys without them ever being in Git. The course lists alternatives. Environment variables are the standard for containers, and later tickets use them. EC2 or Lambda gives full control inside AWS, but the team already tore down that compute in T25 and would pay for it again. A tunnel from a laptop is a trainer-approved fallback only, because the URL dies when the laptop sleeps.

**How it works.** Deployment connects a GitHub repository, picks a branch (`main`) and the file to run (`app/dashboard.py`), and gives you a public URL. Before deploying, you prove that no secret is tracked by Git. The commands below do that.

```bash
mkdir -p .streamlit
echo ".streamlit/secrets.toml" >> .gitignore
cat > .streamlit/secrets.example.toml <<'EOF'
[aws]
access_key_id = "<citypulse-dashboard-ro access key id>"
secret_access_key = "<citypulse-dashboard-ro secret>"
bucket = "citypulse-<name>-<rand4>"
EOF
cp .streamlit/secrets.example.toml .streamlit/secrets.toml
git add .gitignore .streamlit/secrets.example.toml
git ls-files .streamlit
gitleaks detect --source . --log-opts=--all
```

Line by line:

`mkdir -p .streamlit` creates the folder `.streamlit`. The `-p` flag means "create it, and do not complain if it already exists."

`echo ".streamlit/secrets.toml" >> .gitignore` adds the real secrets file to `.gitignore`. `echo` prints text, and `>>` appends the output to the end of the file named after it, instead of replacing the file. The `>` and `>>` symbols are called redirection.

`cat > .streamlit/secrets.example.toml <<'EOF'` starts writing a file. `cat` prints files, and `>` sends the output into the named file. The `<<'EOF'` part means "take the following lines as input until a line that says EOF." The quotes around `EOF` stop the shell from changing the text.

The four lines between the markers are the example settings. Their values are placeholders in angle brackets. They show the shape of the file without exposing a real key.

`cp .streamlit/secrets.example.toml .streamlit/secrets.toml` copies the example to the real file. `cp` means copy. You then fill in the real values in the new file on your laptop only. The `#` comment that the slides place after this line is a note to you and is not run.

`git add ...` stages the two files so Git will record them in the next commit. The file `secrets.toml` is not listed, which is correct.

`git ls-files .streamlit` lists the files inside `.streamlit` that Git is tracking. The correct output is one line: `.streamlit/secrets.example.toml`. If you see `secrets.toml`, stop, because the real key is about to enter Git history.

`gitleaks detect --source . --log-opts=--all` scans the whole repository, including past commits, for things that look like keys. `--source .` means "the current folder". `--log-opts=--all` tells it to look at every branch and commit. The correct output says no leaks were found.

:::trap Adding secrets.toml to .gitignore after committing it
`.gitignore` only stops files that Git has not yet tracked. If the file was already committed, the key stays in history even after you delete it. Rotate the key in AWS at once, and remove the file from tracking.
:::

:::trap Using the pipeline user's keys
The dashboard must not use the keys of the pipeline user, which can write data. Create `citypulse-dashboard-ro` with read access on `clean/agg` only.
:::

:::trap Testing load time on a warm laptop tab
Your laptop has the page open and cached already, so it always looks fast. Use a phone in a private browser tab to measure a true cold load. The target is under five seconds.
:::

**Deploying.** After the checks pass, you push to `main`, create the app on Streamlit Community Cloud from the repository, paste the contents of your real `secrets.toml` into the app's Secrets box, and open the public URL. Run it locally first with this command.

```term
$ streamlit run app/dashboard.py
You can now view your Streamlit app in your browser.
Local URL: http://localhost:8501
Network URL: http://192.168.1.14:8501
```

Each line after the command is output. `Local URL` opens on your laptop only. `Network URL` opens on other devices on the same Wi-Fi. Your IP address will differ from the example. The command keeps running until you stop it with Ctrl+C.

The flow below shows how code, secrets and the public URL reach the cloud app. Notice that the secrets travel by a separate route from the code.

```flow
TITLE: Code goes through Git, secrets go by hand
NODES: Your laptop | GitHub | Streamlit Cloud
STEPS:
1>2 :: git push :: Your code commits travel to GitHub. The secrets file is not among them.
2>3 :: deploy from main :: Streamlit Cloud fetches the branch and the file app/dashboard.py.
1>3 :: paste secrets :: You paste the real TOML into the app's Secrets box directly.
3>1 :: public URL :: The app is running, and you can open the URL from any device.
```

## The worked example

The workbook builds a small dashboard step by step. You will work through it in order, and the explanation of each step follows the code.

**Goal.** Show the readings for one station and one pollutant, with the average as a headline number and a line chart of the values over time.

**Step A. Load the data once.** The code reads the readings file and wraps the read in a cached function.

```python
import streamlit as st, pandas as pd

@st.cache_data
def load():
    return pd.read_csv("readings.csv", parse_dates=["ts"])

df = load()
```

Line by line: `import streamlit as st, pandas as pd` loads both libraries, and `as` gives each a short name. `@st.cache_data` is the decorator from section 3, placed above the function. `def load():` defines the function with no inputs. `pd.read_csv("readings.csv", parse_dates=["ts"])` reads a comma-separated file. The `parse_dates` option turns the `ts` column into real date-and-time values instead of plain text. `df = load()` calls the function. On the first run it reads the file, and later runs reuse the stored copy. The course reports the first 1,392 rows loaded.

**Step B. Add two selectors.**

```python
st.title("CityPulse Air Quality")
station = st.selectbox("Station", df.station_id.unique())
poll = st.selectbox("Pollutant", df.pollutant.unique())
```

`st.title` draws the page heading. `st.selectbox(label, options)` draws a drop-down list and returns the chosen option. The chosen value is stored in `station` and `poll`. `df.station_id.unique()` returns each distinct station once. In this data the options are `CP-001`, `CP-002`, `CP-003` and `CP-004`. The first option is the default.

**Step C. Filter and show the result.**

```python
sel = df[(df.station_id == station) & (df.pollutant == poll)]
st.metric(f"Avg {poll}", f"{sel.value.mean():.1f}")
st.line_chart(sel, x="ts", y="value")
```

`sel = df[...]` keeps the rows where both conditions are true. The `&` symbol means "and". Each condition sits in its own round brackets because `&` binds more tightly than `==`. Without the brackets Python raises an error.

`st.metric(f"Avg {poll}", ...)` shows the average. The `f"..."` text is an f-string: the `{poll}` inside is replaced by the pollutant name. `sel.value.mean()` averages the `value` column, and `:.1f` formats the number with one decimal place.

`st.line_chart(sel, x="ts", y="value")` draws a line chart with time on the horizontal axis and the value on the vertical axis.

**Output.** Launch the app with `streamlit run app/dashboard.py` (the workbook uses `app.py`; the ticket uses the `app/` path). For the first station and the first pollutant, the card shows the average as a number with one decimal place. In the earlier metrics check, the CP-001 PM2.5 average over 116 samples is 49.7, so the card reads "Avg pm25" with the value 49.7 if the first pollutant is `pm25`. The chart shows the hourly line for the same selection. Changing either drop-down redraws both immediately.

The workbook also prints the number of points as a check. For `CP-001` and `pm25` there are 116 hourly points. If your chart shows fewer, the filter is wrong, so check the two conditions first.

### Step 2 — Cache the data load

**What you do.** Add the loader from section 4 to `app/dashboard.py`, decorated with `@st.cache_data(ttl=600)`. The loader reads the daily aggregate file from S3 with the keys in your local `.streamlit/secrets.toml`. Create that file first, using the commands in section 3, because the loader cannot run without it.

```python
import pandas as pd
import streamlit as st

@st.cache_data(ttl=600)
def load_daily() -> pd.DataFrame:
    aws = st.secrets["aws"]
    df = pd.read_parquet(
        f"s3://{aws['bucket']}/clean/agg/daily_station/daily_station.parquet",
        storage_options={"key": aws["access_key_id"], "secret": aws["secret_access_key"]},
    )
    return df.assign(date=pd.to_datetime(df["date"]).dt.date)

df = load_daily()
```

`st.secrets["aws"]` reads the `[aws]` section of the secrets file into a dictionary. `aws['bucket']` reads one value from it. The `f"..."` string puts that bucket name into the S3 address. `storage_options` passes the key pair to the S3 library, and `pd.read_parquet` reads the table. `df.assign(date=...)` returns a copy of the table with `date` converted to a date value, and `.dt.date` keeps only the day. `df = load_daily()` calls the cached function.

**What you should see.** The page loads. Refresh the browser a few times. The terminal does not show a new download on each refresh.

**How you know it worked.** Add a line `print("reading S3")` inside `load_daily`, above `aws = ...`. Refresh the page twice. The message prints once in the terminal, not on every refresh. Remove the print line afterwards.

### Step 3 — Add sidebar filters

**What you do.** Add a date range picker in the sidebar. The sidebar is the narrow column on the left of the page. Give the picker the earliest and latest dates in the data as the default.

```python
picked = st.sidebar.date_input("Date range", (df["date"].min(), df["date"].max()))
if len(picked) < 2:
    st.info("Select an end date.")
    st.stop()
```

`st.sidebar.date_input` draws the picker in the sidebar. Its second argument is a tuple of two dates, which sets the default range. The result is stored in `picked`, which holds two dates once the user has chosen both. While the user has picked only a start date, `picked` holds one date, so `len(picked)` is 1.

`if len(picked) < 2:` checks for that incomplete state. `st.info(...)` shows a blue message box. `st.stop()` ends this run cleanly, so the rest of the script does not run with bad input. Without the guard, the next lines would raise an error and show a traceback.

**What you should see.** The sidebar shows the date picker with the full range selected. Click the first date only and the page shows "Select an end date." with no red error.

**How you know it worked.** Click one date in the picker and confirm that the message appears instead of an error. Then pick the end date and confirm the message disappears.

### Step 4 — Apply the filters

**What you do.** Keep only the rows inside the chosen range and show them.

view = df[(df["date"] >= picked[0]) & (df["date"] <= picked[1])]
st.dataframe(view)

`picked[0]` is the first date and `picked[1]` is the last. The two conditions keep the rows from the first date to the last, including both ends. `view` is a new variable. The cached `df` is not changed. `st.dataframe(view)` draws the table as an interactive grid with sortable columns.

**What you should see.** The table shows only the days you selected. Change the range and the number of rows changes.

### Step 6 — Add a time-series chart

**What you do.** Draw one line for the city-wide daily mean of PM2.5 over the selected range. The two charts from the course are imported from `citypulse.charts` and shown with `st.plotly_chart`, but this step needs only one line chart.

```python
trend = view.groupby("date")["pm25_mean"].mean()
st.line_chart(trend)
```

`view.groupby("date")` gathers the rows for each day. `["pm25_mean"].mean()` averages the pollutant for each day. The result, `trend`, has one value per date, and `st.line_chart(trend)` draws it with dates along the horizontal axis.

## What the quiz tests

The platform quiz asks ten case-study questions, one per topic below. Each topic has the knowledge you need and the trap examiners set. The questions in the quiz block at the end of this section are practice questions, not the platform's.

### streamlit-text-elements

You must know which call draws which kind of text. `st.title` draws the largest heading, `st.header` and `st.subheader` draw smaller headings, `st.markdown` renders text written with Markdown symbols, and `st.caption` draws small grey text for notes. `st.write` is a general-purpose call that prints many kinds of value. Every one of these calls adds one visible element to the page, in the order the script calls them.

The trap is picking the wrong call for a note. Examiners give you a small note under a heading and offer `st.title` as an option. The title is the largest element on the page, so it is the wrong choice for a note.

### streamlit-selectbox

`st.selectbox(label, options)` draws a drop-down list and returns the value the user chose, not the position of that value. The first option is selected by default. You can pass `index=` to choose a different default position. The widget reruns the script when the choice changes, so the code after it always sees the current value.

The trap is thinking the widget returns an index or a label. It returns the option value itself. If the options are station ids, the variable holds a station id such as `CP-002`.

### streamlit-dataframe

`st.dataframe(df)` draws a table that the user can scroll, sort and resize. It is for exploring data. `st.table` draws a static table with no sorting. For a KPI or a single number, use `st.metric`, not a table. Passing a DataFrame to `st.dataframe` shows its index as the first column unless you hide it.

The trap is using the wrong call for the job. A dashboard that needs sorting uses `st.dataframe`, and a fixed printout uses `st.table`. Using `st.metric` for a whole table does not work, because a metric takes one value.

### streamlit-metric

`st.metric(label, value, delta=None, delta_color="normal")` draws a headline number. `delta` is the change, and Streamlit prints it with an arrow. `delta_color` controls the colour: `"normal"` shows a positive change in green, `"inverse"` shows it in red, and `"off"` shows it in grey without colour. `label_visibility` hides the label, which is a different option.

The trap is the colour option. For a value where a rise is bad, such as PM2.5, `"normal"` makes a bad rise look good. Use `"inverse"` for that metric.

### streamlit-caching

Use `st.cache_data` to store the return value of a function that computes data, such as a file read or a query. Use `st.cache_resource` for objects that cannot be copied, such as a database connection. Pass `ttl=` in seconds to make the cached value expire. Without `ttl`, the value stays until the server restarts or the code changes.

The trap is caching with no time limit, then wondering why the dashboard never shows new data. The course uses `ttl=600`, which means ten minutes. Another trap is putting the read outside the function, where it runs every rerun.

### streamlit-execution-model

Streamlit runs the whole script from the first line to the last on every interaction. Variables are created afresh on each run, so a value set at the top is reset to its starting value each time. `st.stop()` ends the current run immediately, without an error. Anything below the call does not run.

The trap is expecting a counter to keep counting. A variable such as `x = 0` followed by `x = x + 1` shows 1 on every rerun. The value does not survive between runs unless you store it in session state.

### streamlit-session-state

`st.session_state` is a dictionary-like store that belongs to one browser session. Its values survive reruns for that user. You write `st.session_state["clicks"] = 0` once, guarded by `if "clicks" not in st.session_state`, and update it afterwards. Each open browser tab has its own session state.

The trap is storing shared data in session state, or using a global variable for per-user data. A global variable is reset on every rerun, and a value in `st.cache_data` is shared by every user. Per-user values go in session state.

### streamlit-layout-sidebar

`st.sidebar.date_input(...)` draws a widget in the sidebar. `st.columns(3)` returns three areas that sit side by side in the main page, and each one takes ordinary calls such as `.metric`. Code placed in the sidebar is drawn on the left, regardless of where it appears in the script.

The trap is confusing `st.sidebar` with `st.columns`. A filter goes in the sidebar, and a row of cards goes in columns. Using `st.sidebar` for the cards puts them in the wrong place.

### streamlit-pyplot

`st.pyplot(fig)` draws a Matplotlib figure, which is a chart made with the Matplotlib library. You create the figure with Matplotlib, then pass it to `st.pyplot`. The course uses Plotly charts, which are drawn with `st.plotly_chart(fig, use_container_width=True)` instead, and the two are not interchangeable.

The trap is passing a Matplotlib figure to `st.plotly_chart`, or a Plotly figure to `st.pyplot`. Each call accepts only its own kind of figure.

### streamlit-forms

`st.form(key)` groups widgets so that the script does not rerun when a widget changes. The rerun happens only when the user presses a button created with `st.form_submit_button("Apply")`. Use a form when several filters should apply together, and the page should not flicker after each click.

The trap is forgetting the submit button. A form with no `st.form_submit_button` never sends its values, so the page never updates from it. The second trap is putting `st.button` inside a form, which does not do what the examiner expects.

## The graded lab skill

The graded lab asks you to write Python functions that work on a list of records. This section teaches the techniques from scratch. You will need all of them to solve the practice problem at the end.

**Records as dictionaries.** A list of sales is a list of dictionaries, one per sale:

```python
sale = {"store": "S1", "ts": "2027-01-05T14:30:00", "amount": 4.25}
print(sale["store"])
print(sale.get("note", "none"))
```

Line by line: `sale = {...}` creates a dictionary with three keys. `sale["store"]` reads the value under the key `"store"`. If the key is missing, Python raises a `KeyError` and the program stops. `sale.get("note", "none")` also reads a key, but if it is missing it returns the default `"none"` instead of raising an error.

Expected output: `S1` on the first line, then `none` on the second line, because the key `note` does not exist.

**Date from an ISO timestamp.** An ISO timestamp such as `2027-01-05T14:30:00` puts the date first, in the form year-month-day, then a `T`, then the time. Because the date always takes the first ten characters, you can take it with a slice:

```python
ts = "2027-01-05T14:30:00"
print(ts[:10])
print(ts[:10] == "2027-01-05")
```

Line by line: `ts[:10]` is a slice. It means "characters from the start up to position 10, not including 10." Positions count from 0, so this gives the first ten characters. `==` compares two values and gives `True` or `False`.

Expected output: `2027-01-05` on the first line and `True` on the second.

Slicing works because the format is fixed. Two timestamps in the same format also sort correctly as text, because the earlier year, month and day come first. Use this only when every timestamp uses the same format.

**Filtering with a list comprehension.** A list comprehension builds a new list from an old one, keeping only the items that pass a test:

```python
amounts = [s["amount"] for s in [{"amount": 3.0}, {"amount": 9.5}] if s["amount"] > 5]
print(amounts)
```

Line by line: `for s in [...]` steps through each dictionary. `if s["amount"] > 5` keeps only those with an amount above five. The part before `for` says what to put in the new list, here `s["amount"]`.

Expected output: `[9.5]`.

**Largest and latest with max and key.** `max(list)` returns the largest item. `max(items, key=...)` returns the item whose key value is largest:

```python
rows = [{"ts": "2027-01-05T09:00:00", "amount": 10.0}, {"ts": "2027-01-05T14:30:00", "amount": 4.25}]
print(max(r["amount"] for r in rows))
print(max(rows, key=lambda r: r["ts"])["amount"])
```

Line by line: the first `print` takes the largest amount from a generator, which is like a list comprehension without square brackets. The second `print` uses `lambda`, a short unnamed function. `lambda r: r["ts"]` says "for each row, compare its `ts`." `max` returns the whole row with the latest timestamp, and `["amount"]` reads its amount.

Expected output: `10.0` on the first line, then `4.25` on the second. The largest amount and the latest sale are different sales.

**Rounding.** `round(x, 2)` rounds to two decimal places. Python uses "round half to even" for values exactly halfway, so `round(0.125, 2)` gives `0.12`. This matters for the average in the practice problem. Round once, at the end, rather than at each step.

**Defaults for empty input.** If a list is empty, `sum` gives 0, but `max` raises an error. Check for emptiness first and return a fixed result. This is the pattern the practice problem needs.

**Practice problem.** Write `sales_kpis(rows, store, day)`.

`rows` is a list of dictionaries. Each has the keys `"store"` (text), `"ts"` (an ISO timestamp such as `"2027-01-05T14:30:00"`) and `"amount"` (a number). `store` is a store id, and `day` is a date as text in the form `"2027-01-05"`.

Keep the rows where the store equals `store` and the date part of `ts` equals `day`. Return a dictionary with five keys:

- `count`: the number of matching sales, as an integer.
- `total`: the sum of their amounts, rounded to 2 places.
- `average`: the total divided by the count, rounded to 2 places.
- `largest`: the largest amount.
- `latest`: the amount of the sale with the latest timestamp. If two sales share the latest timestamp, the one that comes first in the list is the latest.

If nothing matches, return `count` 0, `total` 0.0, `average` 0.0, and `largest` and `latest` as `None`.

Example: for the rows `[{"store": "S1", "ts": "2027-01-05T09:00:00", "amount": 10.0}, {"store": "S1", "ts": "2027-01-05T14:30:00", "amount": 4.25}, {"store": "S1", "ts": "2027-01-05T11:15:00", "amount": 25.5}]`, the call `sales_kpis(rows, "S1", "2027-01-05")` returns `{"count": 3, "total": 39.75, "average": 13.25, "largest": 25.5, "latest": 4.25}`. The latest sale is the one at 14:30, which is 4.25, not the largest.

**Edge-case checklist.** Test each of these before you submit:

- Empty input list: returns the zero result, not an error.
- No match for the store, and no match for the date: both return the zero result.
- The date boundary: a sale at `23:59:59` belongs to its own day, not the next.
- Ties: two sales with the same timestamp; the first in the list wins.
- Ordering: the input list may be in any order, so do not assume it is sorted by time.
- Types: amounts can be whole numbers or decimals. `sum` and `round` work with both.
- Rounding: round the total and the average to two places, and check one value that is exactly halfway.
- Missing fields: the practice problem assumes every row has all three keys, so a `KeyError` is acceptable here. Say so in your viva, and say how `.get` would change it.

## Say it out loud

**1. What happens in a Streamlit app when the user changes the date range?**

:::answer Model answer
Streamlit reruns the whole script from the first line to the last, with the widget now holding the new value. Lines that do not depend on the date are still run again, so anything expensive must be cached. The cached loader returns its stored DataFrame unless its time to live has passed, so only the filtering and drawing repeat. The page then shows the new output.
:::

**2. Why cache the loader, and what does `ttl=600` do?**

:::answer Model answer
Without a cache, every click downloads the daily file from S3 again, and the app feels slow on a phone. The decorator `@st.cache_data` stores the loader's result the first time, so later reruns reuse it. The `ttl` argument, short for time to live, sets how long the stored copy is valid, in seconds. With 600, the data is at most ten minutes old, which is fresh enough for an officer and keeps the cold load under five seconds.
:::

**3. Why are the S3 keys kept in `secrets.toml` and not in the code?**

:::answer Model answer
Anything committed to Git stays in its history even after deletion, and the repository could be shared or leaked. The secrets file is listed in `.gitignore`, so Git never tracks it, and `git ls-files` and `gitleaks` check that. The cloud app receives the same values through its Secrets settings. The key itself is read-only and limited to `clean/agg`, so if it did leak, the damage is limited.
:::

**4. Why does `delta_color="inverse"` matter for the PM2.5 card?**

:::answer Model answer
The default colours a rise green, which suggests good news. For air quality, a higher PM2.5 is worse, so a rise has to show red. The `inverse` option reverses the colour rule and keeps the card's message right. This is a design decision, so I would name the metric's "good" direction in the README KPI table.
:::

**5. Why Streamlit, and not Plotly Dash, Power BI or a React app?**

:::answer Model answer
The team already writes pandas and Plotly code in Python, so Streamlit needs no HTML or JavaScript and reuses the charts from the citypulse package. Dash offers finer control, but it needs more code than a three-number dashboard requires. Power BI and Tableau suit business users, but would move the logic out of Python and add licensing. A React app with FastAPI is far more work than one ticket allows.
:::
