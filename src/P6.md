## What you are building

Picture an air-quality team in a city office. Their sensors record fine particles in the air. The particles are called PM2.5, and the level is measured in micrograms per cubic metre (written µg/m³). The team wants one web page that shows what is happening.

Open the dashboard in your browser and you see a table with four monitoring stations, ST-01 to ST-04. Each row shows how many readings the station has, its average PM2.5 and its highest reading. A bar chart shows the averages, so the dirtiest station stands out at once.

Below the table is a question box. Type "Why is ST-01 high?" and press Ask. The platform searches the team's operations notes, uses a small language model to write one sentence, and tells you which notes it used.

A second part of the page takes three inputs: the hour of the day, the last reading and the recent average. It returns a predicted PM2.5 and a category such as Unhealthy. Behind the page, a monitoring address reports how long the service has been running and how many requests it has handled. Every push of new code runs the tests, builds a package called a container image and deploys it. If the new version fails its health check, the previous version is put back.

## Starting from zero

**Python** is the language the whole project is written in. A Python program is a plain text file ending in `.py`. You run it by typing `python` followed by the file name. A **library** is a set of ready-made code that you import into your own file. **pip** is the tool that downloads libraries from the Python package index, and `pip install -r requirements.txt` installs every library listed in a file. The **terminal** is the text window where you type these commands.

**pandas** holds tables in memory. Its main object is the **DataFrame**, a table with named columns (such as `station_id`, `ts` and `value`) and numbered rows. You can filter rows, group them and calculate totals in a few lines. The day chapter that covers pandas in depth is the earlier one on pandas, and it is the place to go if a call in this chapter feels unfamiliar.

**scikit-learn** is a library of machine-learning tools. **Machine learning** means the program learns a rule from examples instead of you writing the rule by hand. **GradientBoostingRegressor** builds many small decision trees one after another. Each new tree tries to correct the errors that the earlier trees made. A **regressor** predicts a number, here the PM2.5 value. You covered a simpler model, the linear baseline, on Day 5. The capstone compares the two.

**TF-IDF** (term frequency times inverse document frequency) turns each note into a list of word weights. A word counts for more if it appears often in one note and rarely in the others. **Cosine similarity** compares two of these lists. It measures the angle between them, so two notes that use the same words in similar amounts score close to 1, and unrelated notes score close to 0.

**Qwen2.5-0.5B-Instruct** is a small **language model**. It is a program that predicts text, and it has been trained to follow instructions. The 0.5 means about half a billion learned numbers, which is small enough to run on an ordinary computer processor (the CPU) with no paid service. The library **transformers** loads the model, and **torch** does the arithmetic underneath. **RAG** stands for retrieval-augmented generation. The program first retrieves relevant text, then gives that text to the model with the question, so the answer is grounded in your own notes.

**FastAPI** is a web framework. A **framework** is a library that gives you the standard structure, so you only write the parts specific to your project. An **API** (application programming interface) is a set of addresses a program can call to ask for data or an action. Each address is an **endpoint**. **Pydantic** checks that incoming data has the right type and range. **uvicorn** is the server program that listens for requests and passes them to FastAPI. **HTTP** is the protocol browsers and programs use to send requests, and **JSON** is the plain text format used for the replies.

**Streamlit** turns a Python script into a web page. You write normal Python, and the library draws widgets such as tables, charts, text boxes and buttons. **matplotlib** draws charts. The Agg setting draws to a file without opening a window, which is why it works on a server.

**pytest** runs functions whose names start with `test_` and reports which assertions failed. An **assertion** is a line that says a condition must be true, such as `assert r.status_code == 422`. **TestClient** lets a test send a request to the API in memory, so no server has to be running.

**Docker** packages an application with everything it needs into a **container image**. A container is a running copy of an image. **docker-compose** starts several containers together from one file. **Git** records changes to files, and **git push** sends your commits to the shared copy on GitHub. **GitHub Actions** runs a list of commands on GitHub's own machines whenever a trigger happens, such as a push. The list is written in a **YAML** file, which uses indentation to show structure. **curl** is a command-line tool that sends an HTTP request and prints the reply. Its `-s` flag hides the progress meter, and `-X` sets the method, such as POST.

**Step 2: Make the raw readings.** The goal is a reproducible week of hourly PM2.5 data for four stations, with a few deliberately bad rows.

```python
STATIONS = {"ST-01":42,"ST-02":55,"ST-03":38,"ST-04":61}   # baselines
for h in range(168):                       # 7 days, hourly
    rush = 1.3 if (6<=h%24<=10 or 17<=h%24<=21) else 0.8
    for s,base in STATIONS.items():
        val = base + 8*gauss(1,.2)*rush + gauss(0,4)

rows += [["ST-02",...,-3.0], ["ST-09",...], ["ST-01","bad-ts",...]]
```

`STATIONS` maps each station id to a baseline level. The `for h in range(168)` loop runs 168 times, one for each hour in seven days. `h%24` is the hour of the day, because `%` gives the remainder after dividing by 24. The `rush` line uses a higher multiplier of 1.3 during the morning and evening peaks, and 0.8 otherwise. That creates the rush-hour pattern. The inner loop makes one reading per station for each hour. `gauss` draws a random number from a bell curve, so each value is near the baseline with some noise. The last line adds three planted faults: a negative value, an unknown station `ST-09` and a broken timestamp `bad-ts`. The `...` marks are elisions in the course extract. **Step 3: Clean and validate.** The goal is to load the CSV, parse the timestamps and drop anything that is not trustworthy.

```python
def load(path="data/readings.csv"):
    df = pd.read_csv(path)
    df["ts"] = pd.to_datetime(df["ts"], errors="coerce")
    df = df[df.station_id.isin(STATIONS)]
    df = df[df.value.between(0, 500)]
    df = df.dropna(subset=["ts"]) \
           .drop_duplicates(["station_id","ts","pollutant"])
    print(f"clean: {before} -> {len(df)} rows")
    return df
```

`def load(path=...)` defines a function named `load`. It has one parameter, `path`, with a default value, so calling `load()` reads the standard file. `pd.read_csv` reads the file into a DataFrame, and `df` is the variable that holds it. `pd.to_datetime(..., errors="coerce")` converts the text in `ts` into real timestamps. Text that is not a date becomes `NaT`, which means "not a time". `df.station_id.isin(STATIONS)` keeps only rows whose station is in the list. `df.value.between(0, 500)` keeps values from 0 to 500, both included. `dropna(subset=["ts"])` removes rows whose timestamp is `NaT`. The backslash at the end of a line tells Python that the statement continues on the next line, and `drop_duplicates` removes repeated station and time pairs for the same pollutant. The `print` line reports the result in an f-string, where `{...}` puts a value inside the text. The course extract uses `before` in that line but does not show where it is set. Add `before = len(df)` straight after `read_csv`, so the message can report the starting count.

**Step 7: Engineer features.** The goal is to turn each reading into a row that carries its hour, the previous value and a recent average.

```python
def features(df):
    df = df.sort_values(["station_id","ts"]).copy()
    df["hour"] = df.ts.dt.hour
    g = df.groupby("station_id").value
    df["prev"]  = g.shift(1)               # lag-1
    df["roll3"] = g.shift(1).rolling(3).mean()
    return df.dropna(subset=["hour","prev","roll3"])
```

`sort_values` puts each station's readings in time order. `.copy()` makes a separate table, so the original is not changed. `df.ts.dt.hour` reads the hour from each timestamp. `g.shift(1)` moves each value down one row within its station, so each row sees the reading before it. That is the lag. `rolling(3).mean()` averages each set of three rows. Applied to the shifted values, it averages the three readings before the current one. The current value is never used as its own input. Groupby shifting leaves an empty value at the start of each station, and that empty value stops the rolling window reaching into the previous station. The final line drops the rows at the very start where the lag or the average does not exist yet.

**Step 9: Build a tiny RAG index.** The goal is a searchable index of the operations notes, with no database.

```python
_notes = pd.read_csv("data/notes.csv")
_vec = TfidfVectorizer(stop_words="english")
_mat = _vec.fit_transform(_notes.text)
def retrieve(question, k=2):
    sims = cosine_similarity(_vec.transform([question]), _mat)[0]
    top = sims.argsort()[::-1][:k]
    return _notes.iloc[top], sims[top]
```

The first line reads the notes into a table. The second creates a TF-IDF converter. `stop_words="english"` ignores common English words such as "the" and "is", which carry no meaning for search. `fit_transform` learns the vocabulary and the weights from all notes and turns every note into a vector. `retrieve` takes a question and turns it into a vector with the same vocabulary, using `transform`. `cosine_similarity` compares it with every note and returns one list of scores. `[0]` takes the first row of that result. `argsort()` gives the indexes of the scores in ascending order, `[::-1]` reverses the order to descending, and `[:k]` keeps the top k. The function returns those notes and their scores. Because the code runs at import time, the index is built once when the file is loaded.

**Step 10: Answer with the free LLM.** The goal is a one-sentence answer built only from the retrieved notes.

```python
def ask(question, k=2):
    hits, scores = retrieve(question, k)
    context = "\n".join(f"- {t}" for t in hits.text)
    prompt = (f"Use ONLY these ops notes to answer in one "
```

### Part C: Serve it with FastAPI

**Step 12: The API skeleton.** The goal is a running web service with a health check and a stations endpoint.

```python
app = FastAPI(title="CityPulse Capstone", version="6.0")
_df = load(); _model = joblib.load("model.joblib")
class PredictIn(BaseModel):
    hour: int = Field(ge=0, le=23)
    prev: float = Field(ge=0, le=500)
    roll3: float = Field(ge=0, le=500)
@app.get("/health")
def health(): return {"status": "ok"}
@app.get("/stations")

```

`app = FastAPI(...)` creates the service and gives it a title and version. `load()` and `joblib.load` run once at startup, so each request does not reload the data or the model. `class PredictIn(BaseModel)` defines the shape of a prediction request. `hour: int` must be an integer, and `Field(ge=0, le=23)` says it must be between 0 and 23 inclusive. `ge` means greater than or equal to, and `le` means less than or equal to. The `@app.get("/health")` line is a decorator. ## Viva preparation

The capstone viva scores four things from 0 to 5: acceptance criteria met, technical depth, contribution and ownership, and understanding. Acceptance criteria means you can show that the Done when tests pass. Technical depth means you can explain the mechanisms, such as how a lag or a cosine score works. Contribution and ownership means you can say which parts you wrote and changed yourself. Understanding means you can reason about what fails and why. The eight questions below cover all four. Practise saying each answer aloud in your own words.

**1. Walk me through what happens from a git push to a live service.**

:::answer Model answer
A push to main starts the GitHub Actions workflow on a fresh Linux machine. The test job installs the requirements, rebuilds the data and model, runs the data-quality gate and then the pytest suite. Only if the tests pass does the deploy job start, because it declares `needs: test`. The deploy job pushes the image, runs the rollout script, and then checks `/metrics`, and it rolls back to the previous tag if that check fails.
:::

**2. Why does the pipeline have a data-quality gate, and what does it stop?**

:::answer Model answer
The gate turns assumptions about the data into assertions that stop the run when they are false. It checks for negative values, values above 500, duplicate station and time pairs, and unknown stations. Without it, a bad feed would train the model and fill the dashboard with wrong numbers, and nobody would notice. Because the same gate runs in CI, a broken feed stops the release before it ships.
:::

**3. Why GradientBoosting, and how do you know the model is good enough to ship?**

:::answer Model answer
GradientBoosting builds many small trees, each correcting the errors of the earlier ones, which suits a small table with three numeric inputs. I measured it on a held-out 20 per cent of the rows, not on the rows it trained on. The result was a mean absolute error of 4.25 µg/m³ and an R² of 0.740, compared with 4.89 for the day 5 linear baseline. That gives a measured improvement, although a single split is a limited test.
:::

**4. Why TF-IDF and cosine similarity for retrieval instead of a vector database?**

:::answer Model answer
The notes are a small set of short texts, so TF-IDF with cosine similarity is accurate enough, fast, and needs no extra service or cost. A vector database makes sense at a much larger scale or when you need semantic matching beyond shared words. The trade-off is that TF-IDF only matches words, so a question with different wording can miss a note. I would say so openly in a viva.
:::

**5. How does the RAG answer stay grounded, and what does the language model actually see?**

:::answer Model answer
The retrieval step selects the top notes by score, and the prompt contains only those notes and the question, with an instruction to use only them. The model never sees the whole notes file. The reply also returns the note ids, so a person can check the source. The grounding is only as good as the retrieval, so a wrong top note produces a confident but wrong answer.
:::

**6. Why validate input with Pydantic, and what does a 422 tell the caller?**

:::answer Model answer
Pydantic checks each field's type and range before the endpoint runs, so the model never receives an impossible hour or a question that is too short. When the check fails, FastAPI returns status 422 with a message that names the rule, such as "Input should be less than or equal to 23". The caller can fix the request from that message. A 500 would mean the server itself broke, which is a different problem.
:::

**7. How does the rollback decide to act, and what could go wrong with it?**

:::answer Model answer
The deploy step calls `curl -f` on the `/metrics` address after rollout. The `-f` flag makes curl fail on an HTTP error, and the `||` then runs the redeploy of the previous tag. What can go wrong is a check that runs before the new version is ready, which causes a false rollback. Another risk is a missing or empty previous tag, so the rollback has nothing to deploy. A short retry and a stored last-good tag address both problems.
:::

**8. What would you monitor in production, and what does /metrics not tell you?**

:::answer Model answer
I would watch the request count, error rate and latency of each endpoint, plus the uptime and the model's error on recent data. `/metrics` gives uptime, row count and request counters, so it shows that the service is alive and busy. It does not show whether the predictions are accurate, how slow the answers are, or whether the data feed is fresh. Those need additional measurements, which is a useful point to raise in a viva.
:::

```quiz
- So the rows are sorted by station
- So pandas can skip the dropna step
WHY: If the current value were an input, the model would learn to copy it and would fail on new data. The shift moves every value down one row, so the average uses only earlier readings.

Q: A client sends hour 99 to /predict. Which status code should it receive?
- 200, because the request was received
- 404, because the endpoint was not found
- 500, because the server failed
* 422, because the data failed validation
WHY: 422 means the request was understood but its contents break a rule. 500 means the server itself broke, and the course test checks for 422 specifically.

Q: Why does test_app.py use TestClient instead of calling the live server?
- The live server cannot answer POST requests
- TestClient is needed to load the model
* TestClient sends requests to the app in memory, so no server has to be running
- The live server would delete the data
WHY: The tests run in CI with no server started, so the request must go straight to the app. The app still loads its data and model when the module is imported.

Q: A CI step prints "MAE 5.8 is too high" but the job still shows green. What is the cause?
- The print statement is not allowed in CI
- The MAE is measured on training rows
- The deploy job has not started yet
* The step exits with code zero, and only a non-zero exit code fails a CI step
WHY: CI judges a step by its exit code, not by its printed text. The check must call sys.exit with a non-zero value, or fail through an assertion, when the MAE is too high.

Q: In docker-compose.yml, what does depends_on: [api] guarantee?
- That the API has finished loading the model
- That the UI can always reach the API
* That the api service starts before the ui service
- That the two images are built in parallel
WHY: depends_on controls start order only. It does not wait for the API to be ready, so the UI can still start before the API has finished loading.

Q: A deploy step runs curl -f $URL/metrics || ./deploy.sh $PREV_TAG. What does -f do?
- It follows redirects to the final address
- It saves the reply to a file
* It makes curl fail on an HTTP error, which triggers the rollback after ||
- It forces the request to use HTTP/2
WHY: Without -f, curl returns success even for a 500 reply, so the rollback would never run. The -f flag makes an error reply count as a failed command.
```

## What goes wrong

| Mistake | Symptom | Fix |
|---|---|---|
| Starting the API before `train.py` has run | The service crashes at startup when it loads `model.joblib` | Run `python train.py` first, so the file exists. |
| Skipping `pip install -r requirements.txt` | `ModuleNotFoundError` naming a library | Install the requirements in the same Python environment you run from. |
| Using different feature names in `/predict` and in training | Wrong predictions or a server error | Use the single `FEATS` list everywhere. |
| Adding NO2 without changing the duplicate check | `dq_check` fails with "dup" | Include pollutant in the group key. |
| Editing `notes.csv` without restarting | The new note never appears in `sources` | Restart the server so the index is rebuilt. |
| Using `localhost` for the API inside compose | The UI shows connection errors | Use the service name `http://api:8000` inside the network. |
| Printing a failure without a non-zero exit | CI stays green on a bad model | Exit with a non-zero code or use an assertion. |
| Missing or empty `PREV_TAG` | The rollback deploys nothing or fails | Store the tag of each good deploy and read it in the rollback. |
| Health check run before the new version is up | A healthy release is rolled back | Retry the check for a short period before rolling back. |
| Forgetting `-f` on the health-check curl | The rollback never runs on a 500 reply | Use `curl -f` so HTTP errors count as failures. |
