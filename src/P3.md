TITLE: Project 3 — Serverless Ingest and Daily Brief
SUB: You will be able to build, test, containerise and schedule a serverless air-quality pipeline that stores readings in cloud storage, forecasts tomorrow's pollution and writes a plain-English daily brief.

## What you are building

Imagine a web page that a city team opens every morning. The page shows a table with the latest daily average of PM2.5 for four monitoring stations. PM2.5 means fine particles in the air, measured in micrograms per cubic metre (µg/m³). Beside the table, a bar chart shows which station is dirtiest. Underneath, you type in yesterday's numbers, press a button, and the page returns a forecast for tomorrow with a category such as "Good", "Moderate" or "Unhealthy". A two-sentence brief, written by a small language model (a program trained to write text) running on an ordinary processor, explains the day in plain English.

Behind the page, the work runs without anyone touching it. Readings are stored in a data lake (a storage area that holds files as they arrive). Here the lake lives in Amazon S3, an online storage service that holds named files called objects. A schedule, written as a cron timetable (a line of five numbers that says when a job runs), starts an ingest job every night. Every change pushed to the main branch of the code is tested automatically, packaged into a container and deployed. The whole project is serverless, which means you rent storage and short-lived computing from a cloud service rather than running your own always-on machine.

## The architecture

The flow below follows one reading from the raw file to the screen.

```flow
TITLE: How one reading travels through the project
NODES: readings.csv | ingest.py | S3 lake | pipeline and model | API and dashboard
STEPS:
1>2 :: read the CSV :: ingest.py opens the raw hourly file and fixes the timestamps.
2>3 :: put_object, one per day :: One Parquet file is written to S3 for each calendar day.
3>4 :: list and get_object :: pipeline.py asks S3 which parts exist and reads each one back.
4>5 :: daily table and model :: The cleaned data becomes a daily table, and the saved model is loaded for forecasts.
5>4 :: forecast request :: When someone presses the button, the API asks the model and returns a JSON answer.
```

## Starting from zero

Some words first. A **file** is a named block of data stored on disk, such as `ingest.py`, which holds Python code. A **command** is a line of text you type into the **terminal**, the window where you give instructions to the computer directly. A **variable** is a name that holds a value: after `prev = 60.0`, the name `prev` stands for 60.0. A **function** is a named, reusable block of code. You call it with brackets and inputs, such as `daily(df)`, and it returns a result. A **server** is a program that waits for requests and answers them. The program that sends requests is the **client**.

**Python** is the programming language used for the whole project. Its code is plain text in files ending in `.py`, and Python runs the lines from top to bottom. **pip** is Python's package installer. A package is a library, which is code someone else wrote and shared so you can use it without writing it yourself. The command `pip install -r requirements.txt` installs every package named in that file. The Day chapter that teaches Python in depth is the one you should revisit if any line below feels unfamiliar.

**pandas** is a library for tables. Its main object is a DataFrame, which holds rows and named columns in memory. Most of the project's data work happens on DataFrames. **Parquet** is a file format that stores a table column by column and compresses it, so it takes less space and can be read quickly. **pyarrow** is the library that reads and writes Parquet for pandas.

**S3** is Amazon's object storage. You put named objects into a bucket (a container), and you retrieve them by their key (the full name, which can contain slashes to look like folders). **boto3** is the Python library that sends S3 requests for you. **moto** is a library that imitates AWS inside your computer's memory, so tests can use S3 with no account and no cost.

**scikit-learn** is a library for machine learning, the practice of fitting a model to past examples so it can predict new ones. The project uses **LinearRegression**, which fits a straight-line relationship between inputs and a number. **joblib** saves a fitted Python object to a file and loads it back later, so the training step and the serving step can share one model.

**matplotlib** draws charts. **Streamlit** turns a short Python script into a web page with tables, charts and form inputs, without any front-end code.

**FastAPI** builds web endpoints. An endpoint is a URL path plus an HTTP method, such as `GET /health`. HTTP is the protocol browsers and programs use to ask servers for things, and `GET` asks for data while `POST` sends data. **Pydantic** is the library FastAPI uses to check incoming data against types and ranges. **Uvicorn** is the program that runs a FastAPI app and listens on a network port, which is the numbered door a server uses (8000 here). **JSON** is a plain-text format for structured data, such as `{"pm25": 60.5}`.

**transformers** and **PyTorch** load and run pretrained neural-network models. PyTorch does the arithmetic and transformers gives you the loading code. **Qwen2.5-0.5B-Instruct** is a small language model with about half a billion weights, which are the numbers the model learned. It was trained to follow instructions, and it can run on a CPU (the general-purpose processor in any computer), though slowly.

**pytest** runs tests, which are functions that use `assert` lines to check that a result is what you expect. **Docker** packages an app and everything it needs into an image, which is a sealed template. Running an image creates a container. **GitHub Actions** runs the jobs you describe in a YAML file (a plain-text file with indented key-value pairs) whenever an event happens, such as a push, or on a schedule. **Git** records changes to files in commits, and `git push` sends your commits to GitHub. **curl** sends HTTP requests from the terminal, and **jq** filters JSON so you can read it.

**Step 2: Ingest a month of readings.** The goal is to generate 30 days of hourly PM2.5 for four stations. The data has a slow upward trend, and three rows are deliberately broken, because real feeds drift and glitch. The slide shows this part of `make_data.py`:

```python
random.seed(15)
STATIONS = {"ST-01":42,"ST-02":55,"ST-03":38,"ST-04":61}
for h in range(24*30):                    # 30 days, hourly
    day = h//24; rush = 1.3 if h%24 in RUSH else 0.8
    trend = 1.0 + 0.012*day               # slow month-long rise
    for s,base in STATIONS.items():
        val = base*trend + 8*gauss(1,.2)*rush + gauss(0,4)
        rows.append([s, ts, "pm25", round(val,1)])
rows += [["ST-02",..,-3.0],["ST-09",..],["ST-01","bad-ts",..]]
```

Be careful here. The `..` marks stand for timestamp values that the slide leaves out. They are not valid Python, so do not paste the slide into a file as it stands. The names `RUSH`, `rows` and `ts` and the function `gauss` are defined elsewhere in the real file, and the slide does not show them. You take the code from the course files, not from this excerpt.

`random.seed(15)` fixes the random number generator, so every run produces the same numbers. `STATIONS` is a dictionary, a collection of key-value pairs, which maps each station id to a baseline. `for h in range(24*30)` loops over 720 hours, because 24 times 30 is 720. `day = h//24` uses integer division, so hours 0 to 23 give day 0. The `rush` value is a multiplier on the traffic term, 1.3 in rush hours and 0.8 at other times. `trend` grows by 1.2 per cent per day, which produces the monthly rise. The inner loop writes one row for each station in each hour. The last line adds the three faults: a negative value for ST-02, an unknown station ST-09, and a timestamp that cannot be read.

**Step 3: Land partitioned Parquet on S3.** The goal is to read the CSV, split it by date, and write one Parquet object per day to S3 with boto3. The slide shows this code from `ingest.py`:

```python
def ingest(path="data/readings.csv", bucket=BUCKET):
    s3 = boto3.client("s3", region_name="ap-south-1")
    df = pd.read_csv(path)
    df["ts"] = pd.to_datetime(df.ts, errors="coerce")
    df = df.dropna(subset=["ts"])          # bad ts -> NaT dropped
    df["dt"] = df.ts.dt.strftime("%Y-%m-%d")
    for dt, part in df.groupby("dt"):      # one object per day
        buf = io.BytesIO()
        part.drop(columns="dt").to_parquet(buf, index=False)
        key = f"readings/dt={dt}/part-0000.parquet"
        s3.put_object(Bucket=bucket, Key=key, Body=buf.getvalue())
```

`def ingest(...)` defines a function. The default values `path` and `bucket` are used if you do not pass your own. `boto3.client("s3", region_name="ap-south-1")` creates an S3 client for the Mumbai region. `pd.read_csv(path)` loads the CSV into a DataFrame. `pd.to_datetime(..., errors="coerce")` turns text into timestamps and changes anything it cannot read into NaT (not a time), instead of stopping. `dropna(subset=["ts"])` removes rows whose timestamp is NaT. `strftime("%Y-%m-%d")` formats a date as text such as `2026-03-02`, which becomes the partition name. `groupby("dt")` splits the table into one group per day. `io.BytesIO()` creates an in-memory file to hold the Parquet bytes. `to_parquet(buf, index=False)` writes the group into that buffer without the row index. The key is built with an f-string, which puts the value of `dt` inside the text. Finally, `put_object` uploads the bytes to the bucket under that key.

`python -c` runs the Python code written in quotes, instead of a file. The import line loads the function, and `ingest()` calls it with its default arguments. The output confirms 2882 rows, because the bad timestamp was removed. It also shows 30 partitions, one for each day, and the sizes of the files. This step proves that the lake holds one Parquet object per day under Hive-style keys. **Step 4: Read the lake back and clean it.** The goal is to list the Parquet objects under the prefix, read each one, join them into one table, and remove bad rows. The slide shows `pipeline.py`:

```python
def read_lake(bucket=BUCKET):
    s3 = boto3.client("s3", region_name="ap-south-1")
    keys = s3.list_objects_v2(Bucket=bucket,
                              Prefix=PREFIX)["Contents"]
    parts = [pd.read_parquet(io.BytesIO(
        s3.get_object(Bucket=bucket, Key=o["Key"])
          ["Body"].read())) for o in keys]
    return pd.concat(parts, ignore_index=True)
def clean(df):
    df = df[df.station_id.isin(STATIONS)]
    df = df[df.value.between(0, 500)]
    return df.drop_duplicates(["station_id","ts","pollutant"])
```

`list_objects_v2` asks S3 for the objects whose keys start with `PREFIX`, which is the folder-like text `readings/`. The answer comes back as a dictionary, and `["Contents"]` gives the list of objects. A list comprehension (the `[... for o in keys]` part) builds one DataFrame per object. For each object, `get_object` downloads it, `["Body"].read()` returns its bytes, `io.BytesIO` wraps the bytes as a file, and `pd.read_parquet` turns them back into a table. `pd.concat(parts, ignore_index=True)` stacks the 30 tables into one and renumbers the rows. In `clean`, `isin(STATIONS)` keeps only the known stations. `between(0, 500)` keeps values from 0 to 500 inclusive. `drop_duplicates` removes repeated readings that share the same station, timestamp and pollutant.

```term
$ python -c "from pipeline import *; clean(read_lake())"

```

The `from pipeline import *` line loads everything in the file. The output shows that 2882 rows came back from the lake and 2880 remained after cleaning. The two dropped rows are the negative reading and the unknown station, which is exactly what you expect. This step proves the round trip works and that the cleaner removes the faults you planted.

:::trap Empty bucket, missing Contents
If the bucket has no objects under the prefix, S3 returns a response with no `Contents` key, and `["Contents"]` raises `KeyError`. Run the ingest first. A more careful version would use `.get("Contents", [])`, which is one of the edge cases to think about in Part G.
:::

**Step 6: Aggregate to daily per station.** The goal is to turn 2880 hourly rows into one row per station per day, with a count, a mean and a maximum. The slide shows this `daily` function:

```python
def daily(df):

    df["date"] = pd.to_datetime(df.ts).dt.date
    return (df.groupby(["station_id","date"])["value"]
```

**Step 8: Engineer forecast features.** The goal is to turn each day's row into a row of inputs and a target. The slide shows `forecast.py`:

```python
FEATS = ["prev", "roll3", "dow"]
def features(daily_df):
    d = daily_df.sort_values(["station_id","date"]).copy()
    g = d.groupby("station_id")["mean"]
    d["prev"]  = g.shift(1)               # yesterday
    d["roll3"] = g.shift(1).rolling(3).mean()
    d["dow"]   = pd.to_datetime(d.date).dt.dayofweek
    d["target"] = d["mean"]               # today = next-day target
    return d.dropna(subset=FEATS)
```

`FEATS` is a list of column names. Keeping them in one list means the training code and the serving code cannot disagree about the order or the spelling. `sort_values` puts each station's days in date order, which the shifts depend on. `shift(1)` moves a column down one row inside each station group, so each row now holds the previous day's mean. `prev` is that yesterday's mean. `roll3` is the rolling mean of the last three of those shifted values, which gives the average of the three days before the current one. `dayofweek` gives 0 for Monday up to 6 for Sunday. The target is the day's own mean. Each row therefore pairs what was known before the day with what happened on the day. `dropna` removes the first rows of each station, which have no full history.

```term
    ST-01  2026-03-04  51.3   49.9    2    52.7
    ST-01  2026-03-05  52.7   51.5    3    52.4
    ST-01  2026-03-06  52.4   52.1    4    51.6
    ST-01  2026-03-07  51.6   52.2    5    52.8
```

The `...` in the command stands for the code that built the daily table on the slide, so the command is shortened. The output shows four rows for ST-01. Look at the first two rows. The `prev` value of 52.7 on 5 March is the `target` value of 4 March, which is what you expect from a shift. A `dow` of 2 is a Wednesday, because pandas counts Monday as 0. This step proves that each row carries the recent past and the day to predict.

:::trap Using the target's own day as a feature
If you give the model the mean of the day it is trying to predict, the test score looks perfect and the model is useless on new days. Every feature must come from days before the target. That is why `shift(1)` appears before `rolling`.
:::

**Step 9: Train and evaluate the forecast.** The goal is to fit a LinearRegression on the features, hold back 20 per cent of the rows for testing, and report two measures. The slide shows the body of a function called `train`. The header line is added here so the indentation makes sense:

```python
def train(daily_df):
    d = features(daily_df)
    X, y = d[FEATS], d["target"]
    Xtr,Xte,ytr,yte = train_test_split(X, y, test_size=.2,
                                       random_state=15)
    model = LinearRegression().fit(Xtr, ytr)
    pred = model.predict(Xte)
    print(f"MAE {mean_absolute_error(yte,pred):.2f} ug/m3",
          f"R2 {r2_score(yte,pred):.3f}")
    joblib.dump(model, "model.joblib")
```

`X` holds the feature columns and `y` holds the target. `train_test_split` splits both into training and test sets. `test_size=.2` gives 20 per cent to testing, and `random_state=15` makes the split repeatable. `LinearRegression().fit(Xtr, ytr)` learns one weight per feature, plus an offset. `predict` applies those weights to the test features. `mean_absolute_error` is the average size of the miss, in the same units as the target, which here means µg/m³. `r2_score` measures how much of the variation the model explains: 1.0 is perfect and 0 means no better than guessing the average. The f-strings put the two numbers into the printed text, with two decimal places for MAE and three for R². `joblib.dump` saves the trained model to `model.joblib`.

```term
$ python -c "from pipeline import *; from forecast import train; train(daily(clean(read_lake())))"
```

The output shows an average error of 0.89 µg/m³ and an R² of 0.992 on the test rows. The file is saved, so the API can load it later. This step proves that you measured the model, and that the forecast is accurate enough to ship as a baseline to improve on.

:::trap Trusting a score on shuffled rows
`train_test_split` shuffles rows by default, so the test rows can come from days in the middle of the month, mixed in with training rows from the same weeks. For a forecast, a strict time-ordered split is the honest test. The slide does not do this, so treat 0.89 as a baseline rather than a guarantee.
:::

**Step 13: Forecast, with validation.** The goal is to accept yesterday's mean, the three-day mean and the weekday, and return tomorrow's PM2.5 with a category. The slide shows:

### Part D — The daily brief

**Step 14: Daily brief from a free CPU model.** The goal is to give the model the day's facts and have it write a short public brief. The slide shows `brief.py`:

```python
_M = "Qwen/Qwen2.5-0.5B-Instruct"
_tok = AutoTokenizer.from_pretrained(_M)
_llm = AutoModelForCausalLM.from_pretrained(_M,
                                torch_dtype="auto")
def daily_brief(date, worst, worst_pm, city_mean, fcast):
    facts = (f"Date {date}. City mean {city_mean}. "
             f"Dirtiest {worst} at {worst_pm}. "
             f"Tomorrow forecast {fcast}.")
    msgs = [{"role":"system","content":"Write a 2-"
             "sentence public air-quality brief."},
            {"role":"user","content": facts+" Advise residents."}]
    ids = _tok(_tok.apply_chat_template(msgs,
          tokenize=False, add_generation_prompt=True),
          return_tensors="pt")
    out = _llm.generate(**ids, max_new_tokens=80, do_sample=False)
    return _tok.decode(out[0][ids.input_ids.shape[1]:],
                       skip_special_tokens=True).strip()
```

`_M` holds the name of the model on the Hugging Face model hub, a public library of models. The first time you run the code, the model is downloaded and then reused from a local cache. `AutoTokenizer` turns text into numbers the model can read, and `AutoModelForCausalLM` loads a model that writes text one token at a time. A token is a chunk of text, often a word or part of one. `torch_dtype="auto"` lets the library choose the number format stored in the model. `facts` is an f-string built from the day's values. `msgs` is the chat in the format the model expects: a system message that sets the task, and a user message that holds the facts. `apply_chat_template` wraps the chat in the model's own control markup, and `return_tensors="pt"` asks for PyTorch tensors. `generate` writes new tokens, and `max_new_tokens=80` stops it after 80 tokens. `do_sample=False` chooses the most likely token at each step, so the output does not change between runs. The final line removes the prompt tokens from the output, decodes the rest into text, and strips spaces at the ends.

```term
$ python brief.py   # date=2026-03-30, worst=ST-04 92.0
PM2.5 levels have reached 74.3 ug/m3, with the
dirtiest ST-04 station at 92.0. The next day's
forecast shows 60.5 ug/m3. Residents should take
precautions and stay indoors during this period.
```

The output is four lines of text because the wrapping is cosmetic. The brief uses the numbers from the facts, and it advises residents. This step proves that the brief is generated on your own machine without a paid API or a GPU, which is a graphics processor.

:::trap A fluent brief is not a checked brief
A language model writes text that sounds right, whether or not it is right. The brief above repeats numbers, but it also adds advice the facts never asked for. Before you post a brief, compare every number in it with the facts you passed in. Greedy decoding makes the output repeatable, not correct.
:::

## The Part G challenges

Part G has five assessed tasks, with rising difficulty. Each one builds on the code above, and each has a "Done when" test. For every challenge, the plan below gives you the steps and the reasons, not finished code. Write the code yourself, and keep the five tests green.

### Challenge 1: A second pollutant in the lake (data, easy)

**What is asked.** Extend `make_data.py` and `ingest.py` so they also write NO2 readings, and partition the lake by date and pollutant. Then make `daily()` group by station, pollutant and date.

**Done when:** "S3 has readings/dt=.../pollutant=no2/ objects and /stations returns both pm25 and no2 rows for every station."

**Ideas it needs.** Partitioning in Step 3 uses a key string, and the key must include the new `pollutant=` folder. `groupby` takes a list of column names, so adding `pollutant` to the list changes the groups. The `/stations` endpoint takes the latest row per group, so a station will have one row per pollutant.

**Plan of attack.**
1. Decide the key format first. Write it down as `readings/dt=.../pollutant=.../part-0000.parquet` and check that the pollutant name is lowercase, as the Done when text uses `no2`.
2. Change `make_data.py` so each hour writes a NO2 row next to each PM2.5 row. Keep the seed, so the numbers stay repeatable.
3. Change the groupby in `ingest` so each part holds one day and one pollutant.
4. Change `daily()` so it groups by station, pollutant and date, and carries the pollutant column through.
5. Run `read_lake()`, then `clean()`. Check that the number of rows is what you expect, given the two pollutants.
6. Check `/stations` and confirm that every station shows both pollutants.

**Mistakes that fail the test.** Writing the NO2 rows into the same key as the PM2.5 rows, so one overwrites the other. Forgetting that `clean()` filters on `pollutant` in the duplicate check. Leaving `pollutant` out of `daily()`, so the NO2 numbers are averaged in with PM2.5.

## Viva preparation

The capstone viva scores four things from 0 to 5 each: whether the acceptance criteria are met, your technical depth, your contribution and ownership of the work, and your understanding of the system. The questions below are the ones an examiner is likely to ask about this project. Answer them in your own words, and use the model answers as a check.

:::answer Why store the lake as one Parquet file per day, rather than one big CSV?
Parquet stores data by column and compresses it, so a reader can fetch only the columns it needs. Splitting by day with `dt=` keys means a later job can list and read just the days it needs, rather than the whole history. Each object is also a sensible unit to rewrite if one day's ingest goes wrong. A single CSV would force every reader to parse everything. The trade-off is that you must manage 30 objects instead of one.
:::

:::answer Why clean before aggregating, not after?
The daily mean is only as good as the rows inside it. A negative reading or an unknown station would pull the mean and the maximum away from the truth, and the forecast learns from those numbers. Cleaning first means every later step sees the same trusted rows. The data-quality gate then checks that the cleaning worked. Cleaning after aggregating would hide the bad rows inside averages.
:::

:::answer What does the data-quality gate protect against, and how does it fail?
It protects the forecast and the brief from silent data problems, such as a row count that drops because an ingest broke, or a value outside 0 to 500. Each check is an `assert`. A failed assert raises an error and stops the script with a message, so in CI the workflow goes red. The gate does not fix the data. It makes the failure visible before anything is deployed.
:::

:::answer Why LinearRegression, and what do MAE and R² tell you?
LinearRegression is a simple baseline that is fast, free, and easy to explain. With a strong lag feature, a straight line already fits a smooth daily series well. MAE is the average miss in µg/m³, so 0.89 means a typical forecast is within about 0.9 µg/m³. R² is the share of variation the model explains, so 0.992 means it explains almost all of it on the test rows. Both numbers are measured on held-out data, which is what makes them honest.
:::

:::answer Why load the model once at startup?
Loading a model takes time and memory, and a request should be quick. Loading at startup means each request only runs the prediction, which is fast. The model file is also the contract between training and serving. If it loads and forecasts when you test it alone, the API has the same code path to use. The cost is that you must restart the server to pick up a new model.
:::

:::answer What does Pydantic validation do for the /forecast endpoint?
The `ForecastIn` class checks the type and the range of each field before the function runs. A `dow` of 9 is rejected with a 422, and the message names the rule that failed. The model never sees impossible input, and the caller gets an actionable error instead of a crash. A 500 error would tell the caller nothing about what they did wrong. Validation is the reason the endpoint can be trusted by the dashboard and other callers.
:::

:::answer Why does the brief use greedy decoding, and what is the risk?
Greedy decoding picks the most likely next token at each step, so the same facts give the same brief every time. That makes the output testable and repeatable. The risk is that the model can still state wrong numbers or invent advice, because it writes text that sounds plausible. The fix is to check every number in the brief against the facts you passed in, and to keep a person in the loop before the brief is published.
:::

:::answer How do a push and the nightly cron differ, and why does deploy depend on test?
A push starts the workflow when someone sends a commit to main. The cron starts it at 01:30 UTC every night, on a schedule that is not tied to a change. The `needs: test` line means deploy waits for the test job and runs only if it passed. So a broken change cannot reach production, even if someone pushes it straight to main. A scheduled run still goes through the same chain, which is why you should check what it deploys.
:::

```quiz

- Read the whole lake in one request
- Convert the files back into CSV
- Lock the day so no one else can write to it
WHY: The Hive-style dt= folder lets a reader list and read only the days it needs. Reading the whole lake is what you want to avoid, not what the key gives you. The key does not convert or lock anything.

- The mean of the three days including day D
* The mean of the three days before day D
- The mean of the last three hours of day D
- The weekday of day D
WHY: roll3 is built from shift(1) followed by rolling(3), so it uses only days before the target. Including day D itself would leak the answer into the input, which is the most tempting wrong option.

- It is kept and set to 0
- It stops the program with an error
- It is kept, because it is a number
* The row is removed, because it is outside the range
WHY: between(0, 500) keeps only values in the range, so -3.0 is removed. Pandas does not raise an error or change the value, which is why the test expects 2880 rows after cleaning.

- 200
* 422
- 400

* At 01:30 UTC, every day
- Every 30 minutes, starting at 01:00
- Once a week, at 01:30 UTC
WHY: Cron reads minute, hour, day of month, month and day of week. Here it gives minute 30, hour 1, every day, in UTC. The option about a weekly run is tempting because it looks like a schedule, but the stars mean every day of the week.

Q: Why does the Dockerfile copy requirements.txt before copying the rest of the code?
* So Docker can reuse the cached library layer when only the code changes
- So the requirements file can be read by the browser
- So the port number is set before the image is built
- So the container runs without Python
WHY: Docker caches each step. Copying the requirements first and installing them before the code means a code edit does not reinstall every library. The other options describe things Docker does not do with that file.

Q: In the deploy job, what happens if the test job fails?
- Deploy runs anyway, and the failure is logged
- Deploy runs only on a Tuesday
* Deploy is skipped, because it needs test to pass
- The image is built but never pushed
WHY: The line needs: test makes the deploy job wait for test and run only when it passes. The option that says the image is built but not pushed is tempting, but the job is skipped entirely, so nothing is built.
```
