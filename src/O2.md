TITLE: Evidence that ranks you first: commits, reviews, portfolio and CV
SUB: You will be able to make your own work provable from Git history, open and review pull requests that pass the gates, and turn the project into CV lines that a recruiter can check.

## Why evidence beats effort

The course does not score how hard you worked. It scores what can be shown. Every CityPulse ticket is marked from commit evidence, which means the platform looks at the changes recorded in the project's history and asks whether they match the ticket. A commit is a saved snapshot of your changes, with the name, email and time of the person who made it attached. If the history shows your name on the work, the work counts for you. If it does not, the work might as well not exist for scoring, even if you spent a whole night on it.

This matters because the platform and the internship recruiters work the same way. A hiring manager cannot watch you type. They can read a repository, look at a pull request, or open a live page and check a claim. Your job in this course is to leave a trail that someone else can follow without asking you a single question.

Three things in this chapter produce that trail: commits (the saved snapshots), pull requests and reviews (the way changes are proposed and checked by another person), and documents plus a portfolio (the places where you explain what you built). The last part of the chapter turns the same evidence into lines for your CV.

:::key Evidence means the platform can find it
A claim with no commit, review, metric or link behind it scores nothing. Before you say "I built it", make sure the history, the pull request or the page shows that you did.
:::

## Commits that prove your work

A **terminal** is the window where you type commands instead of clicking. A **command** is one instruction you type into the terminal, followed by Enter. A **repository**, usually shortened to **repo**, is a project folder that Git tracks. Git is the version-control system that records every change. A **remote** is a copy of the repository on another machine, here GitHub. The name **origin** is the default label Git gives to the remote you cloned from.

### Your identity must be set correctly

Each commit carries an author name and an author email. Git takes these from two settings called `user.name` and `user.email`. If they are wrong, the commit is attributed to the wrong person, and the course cannot tell who did the work.

Run these commands once inside your squad repo, using your own real name and the email address on your GitHub account:

```bash
git config user.name "Asha Rao"
git config user.email "asha.rao@example.com"
```

Line by line:

- `git config` changes a Git setting. Git reads it every time you commit.
- `user.name` is the name field. Use the name you put on your GitHub profile.
- `"Asha Rao"` is the value, in double quotes because it contains a space. The name shown here is the course's example; type your own.
- `user.email` is the email field. It must be the email on your GitHub account, so GitHub links the commit to you.
- The second line does the same for the email address.

Git prints nothing when these work. To check them, run `git config --list --show-origin` and look for your name and email in the list.

:::trap Lab defaults
A lab computer or a shared machine can have a default identity already set. If you commit without changing it, your work is recorded under someone else's name. Set `user.name` and `user.email` before your first commit in each repo, and check them again if you use a different computer.
:::

### Small daily commits

Make a commit every time one piece of work is finished and still works. A commit that changes one thing with a clear message is easy for a reviewer and easy for the platform to match to a ticket. A commit that mixes five changes, or that has no message, is hard to read and easy to question.

The course slides show the pattern used throughout the year. You edit files, choose which changes go into the next snapshot, and record it:

- You edit files in your **working tree**. This is the folder on your disk where the files you can see live.
- `git add` moves selected changes into the **staging area**, the list of changes waiting for the next snapshot.
- `git commit` records the staging area as one snapshot, with your identity and a message.
- `git push` copies new commits from your computer to the remote, so the team and the platform can see them.

### Message format

A commit message is the one-line label for the snapshot. The course examples use the imperative mood, which means the message reads as an order to the codebase: "Add folder layout and .gitignore", not "Added folders" or "stuff". The convention keeps the first line short and clear; around 50 characters is a common guide.

Good examples from the course:

- `Add folder layout and .gitignore`
- `Add --loc flag to fetch.sh`
- `Write CHARTER.md with success metric`

Bad examples:

- `update` (says nothing about what changed)
- `fixed stuff` (vague, and "fixed" hides the reason)
- `final final v2` (a file history cannot use this)

If a change needs an explanation, add a second paragraph after a blank line. The course example for the `--loc` flag adds one sentence on why the flag exists. That sentence is what a reviewer reads later.

### A clean commit sequence

The animation below shows the commands for one small piece of work on its own branch. A **branch** is a movable label on a line of commits, so you can work on one change without disturbing the main line. The branch here is called `feat/12-loc-flag`; the `feat` prefix means a new feature, and the 12 is the number of the Issue it serves. An **Issue** is a task card on GitHub.

```term
$ git switch -c feat/12-loc-flag
Switched to a new branch 'feat/12-loc-flag'
$ git add scripts/fetch.sh
$ git commit -m "Add --loc flag to fetch.sh"
[feat/12-loc-flag 3f9a2c1] Add --loc flag to fetch.sh
 1 file changed, 9 insertions(+)
$ git log --format='%h %an %s' -2
3f9a2c1 Asha Rao Add --loc flag to fetch.sh
7b04e8d Asha Rao Add folder layout and .gitignore
```

Line by line:

- `git switch -c feat/12-loc-flag` creates a new branch and moves you onto it. `switch` changes branch; `-c` means create.
- The line `Switched to a new branch` is Git's confirmation.
- `git add scripts/fetch.sh` stages every change in that one file. Adding one named file keeps the commit to one job.
- `git commit -m "..."` records the snapshot. `-m` lets you give the message on the same line instead of opening an editor.
- Git prints `3f9a2c1`, a short ID for the commit, then the message. The `1 file changed` line is a summary of the snapshot.
- `git log --format='%h %an %s' -2` lists the last two commits. The `--format` flag controls the layout. `%h` is the short ID, `%an` is the author name, `%s` is the subject, which is the message line. `-2` limits the output to two commits.

Your IDs and numbers will differ; the important part is that `%an` shows your name on each commit you made. If it shows someone else's name, stop and fix the identity before you push.

:::trap Committing for a squad-mate
Do not commit a change that a teammate made, and do not commit their signature line. Each person's work must come from their own account, or the scoring breaks for both of you.
:::

## Pull requests that pass first time

A **pull request**, or **PR**, is a request to merge one branch into another. It shows the changes, the discussion and any checks in one page on GitHub. A **review** is when another person reads the change, runs it, and writes comments. A **merge** joins the branch into `main`, the main line of the project.

### Opening the PR

The course opens a PR from the terminal with the GitHub CLI. The **GitHub CLI** is a program called `gh` that lets you do GitHub actions by typing commands. Here is the course pattern:

```bash
gh pr create --base main --title "Add --loc flag to fetch.sh" \
  --body "Closes #12. How tested: ./scripts/fetch.sh --loc Whitefield appended 1 row." \
  --reviewer ravi-k,meera-s
```

Line by line:

- `gh pr create` opens a new pull request from the branch you are on.
- `--base main` says the branch should merge into `main`.
- `--title "..."` sets the title shown on the PR page.
- `--body "..."` sets the description. The text inside contains two important parts. `Closes #12` links the PR to Issue number 12 and closes that Issue when the PR is merged. The second sentence says how you tested the change.
- The backslash `\` at the end of a line tells the terminal the command continues on the next line. It is a line-joining symbol, not part of the text.
- `--reviewer ravi-k,meera-s` asks two squad-mates to review. The names are GitHub usernames, separated by a comma with no space.

Your description should answer three questions in plain words: what changed, why, and how you know it works. A reviewer should not have to guess.

### Making the reviewer's job easy

A reviewer needs to run your change, not only read it. The course shows the reviewer's steps:

```bash
gh pr checkout 14
./scripts/fetch.sh --loc Whitefield && tail -1 "data/raw/$(date +%F).csv"
```

Line by line:

- `gh pr checkout 14` downloads PR number 14 onto the reviewer's machine and switches to its branch.
- `./scripts/fetch.sh` runs the script. The `./` means "the file in this folder". `--loc Whitefield` passes the location as an option.
- `&&` means "run the next command only if this one succeeded".
- `tail -1` prints the last line of a file.
- `"data/raw/$(date +%F).csv"` builds the file name from today's date. `date +%F` prints the date as `2026-11-24`, and `$( ... )` runs the command inside and puts its output into the name.

The reviewer now sees the last line of the output file. If the row is there and the script did not crash, the change works for that input.

### Responding to a review

When a reviewer asks for changes, you do not start a new PR. You push a fix commit to the same branch. The PR updates by itself. Then you reply to each comment and resolve its thread, which means marking the discussion as settled. A thread left open can block a merge in the course rules, and it hides open questions from the trainer.

After the fix, the course sequence is:

```bash
gh pr review 14 --approve --body "Re-ran: 1 row appended, no duplicates."
gh pr merge 14 --squash --delete-branch
```

Line by line:

- `gh pr review 14` adds a review to PR 14.
- `--approve` means you agree the change can be merged. `--body` holds the message that goes with it.
- `gh pr merge 14` merges PR 14.
- `--squash` combines all the commits of the PR into one commit on `main`. The history stays tidy, and the squashed message comes from the PR.
- `--delete-branch` removes the feature branch on GitHub once it is merged, so old branches do not pile up.

:::trap Merging with open threads
A merge does not solve an open question. Answer each comment, resolve the thread, and only then merge. A reviewer who sees a merged PR with unanswered comments will mark it down.
:::

## Reviews that count as substantive

The word that matters in the course rules is **substantive**. A substantive review shows that you read the code and ran it, and it says what you saw. A review that only shows approval does not show that.

The rule in the course is short: "LGTM" alone scores zero. **LGTM** is an abbreviation for "looks good to me". It is common in industry, but on its own it is only an opinion with no evidence behind it.

Here are six review comments, weakest first.

1. `LGTM`. This scores zero. It says nothing about what you checked.
2. `Nice work!`. Friendly, but it is praise, not review. It does not show that you ran the code.
3. `Approved`. This records the decision but not the reason.
4. `Looks fine from the diff.` This is honest, but it tells the author you did not run the branch. The course warns that reading only the diff misses runtime errors.
5. `Re-ran with a date that already exists: 0 rows appended, no duplicates. Approve.` This is substantive. It names what you ran, what you saw, and why the result is acceptable.
6. `Ran with --loc and no value: the script stops with an unbound variable error at the line that reads the argument. Please add a usage check that prints a message and exits.` This is the strongest kind. It names the input you tried, the exact failure, and the change you want.

The pattern in 5 and 6 is the same: what you ran, what you saw, what should change. Use that pattern every time. If you are not sure whether a review is substantive, ask: could the author fix the problem from my comment alone? If yes, it is substantive.

Two other habits make a review count:

- Use the labelled comment types the course asks for, such as "Blocking" for a problem that must be fixed before merge. The example in the slides uses "Blocking:" at the start of the request.
- Review the PR as you would a real change, including the edge cases. An **edge case** is an unusual input, such as an empty value or a missing file. Most failures in real projects happen at edge cases.

:::tip Write the reviewer's evidence first
Before you write a review, note the command you ran and the result in one line. Then turn those two notes into the comment. This takes two minutes and turns a weak review into a strong one.
:::

## The capstone board and the daily log

The capstone is the final, large project of the course. Its work is tracked on a **board**, which is a GitHub Projects page with columns such as "To do", "In progress" and "Done". Each card on the board is a task, and each task has a scoring gate.

Three rules from the course govern the board:

- Only a trainer can move a task to **Done**. You can move your card to "In progress" or "Review", but the final step belongs to the trainer, after they have checked the evidence.
- Each task has a **scoring gate** scored from 0 to 3. A gate is a checkpoint where the work is measured against a stated test. The exact criteria for each gate are shown on the platform next to the task, so read them before you start. Do not rely on this chapter to tell you what the rubric says.
- Students log a **daily commit** with a summary and a link. This means that on each working day you make a commit (or point to one) and write a short summary of what it does, with a link that opens the commit on GitHub.

### Writing a daily summary

The daily log is where you prove that you worked on your own part, every day, in your own words. A good summary has three parts: what you did, what it changed, and where to see it. A weak summary says "worked on the project".

Compare these two entries.

- Weak: `Worked on fetch script. Link: github`. The link goes nowhere useful, and the summary does not say what changed.
- Strong: `Added the --loc flag to fetch.sh so a second location can be fetched without editing the script. Tested with Whitefield: one row appended. Commit: [link to the commit].`

The strong entry names the change, its purpose, the test and the link. A trainer can read it in ten seconds and check the commit in another ten.

### What earns a 3 at a gate

The gate scores run from 0 to 3, so the difference between a 2 and a 3 matters. The course slides do not give a general rubric in one place, so take the criteria from the gate text on the platform. The patterns in this chapter tell you what a strong gate submission looks like in practice:

- The evidence is in your name. The commits, reviews and PRs carry your identity.
- The claim is specific. You name the command or the page, and the number or result you saw.
- The evidence can be opened. Every link works, and the file or page shows what you say it shows.
- The result is consistent. If your summary says one row was added, the history shows one row added.

A score of 0 to 1 usually means a claim without evidence. A 2 usually means some evidence, but parts of the claim cannot be checked. A 3 means a stranger could confirm the claim from the links alone.

:::trap Overclaiming on a gate
Writing "improved the model by 40 per cent" with no file or number to check it against is an overclaim. The gate will mark it as unsupported. Write the number that the file shows, and nothing more.
:::

## The 60/40 grade: own your part and lift the team

The final capstone grade is split into two parts. **60 per cent** comes from your individual contribution, and **40 per cent** comes from the team's result. A **contribution** is the part of the work that you did, visible in the history. The team part is shared, so it moves with everyone's work.

The split has two consequences.

First, your own commits and reviews are worth more than anything else you can do. If you carry the team without your own visible work, the 60 per cent is small. If you do your part clearly and well, you protect the biggest share of your grade.

Second, the 40 per cent rewards a team that works. A squad that merges on time, reviews each other, and keeps the main line working gets the team marks. A single person who blocks everyone by hoarding the work, or who pushes broken code to `main`, drags the team's marks down.

What "own your part" means in practice:

- Pick Issues with your name on them, and say so on the board.
- Open PRs for your work, so each change has your name on it and a link.
- Review at least as much as you are reviewed, with evidence.
- Keep your daily log honest, so the trainer can match it against the history.

What "lift the team" means:

- Review squad-mates' PRs by running them, not by approving on a glance.
- Answer review comments on your own PRs quickly, so work does not stall.
- Write the README, CHARTER and HANDOVER parts that are yours, so the team's documents are complete.

:::key Your part is what is in the history
Describe your work in terms of commits, PRs and reviews that carry your name. Anything you did outside the history, like a discussion in a meeting, is not evidence for the individual part of the grade.
:::

## README, CHARTER and HANDOVER documents

Three documents explain a project to people who did not build it. They are written in **Markdown**, a plain-text format in which `#` makes a heading, `-` makes a list bullet, and `**text**` makes bold text. GitHub turns the file into a formatted page automatically. Because the file is plain text, a later change shows up as a line-by-line difference that a reviewer can read.

### README.md

The README is the first page anyone opens in the repo. The course says it is the first thing the client sponsor and peer auditors read. It should answer: what is this, how do I run it, and what does it prove? A skeleton looks like this:

```text
# CityPulse squad name

One sentence on what the project does and for whom.

## Quick start

Commands to run the project, one per line, in the order to run them.

## Business impact

One sentence with a number, a unit and the assumption behind it.

## Team

Each member's name, GitHub username and the part they own.
```

Line by line, what each part does:

- The `#` heading is the title of the whole document. Use one per file.
- The sentence under the title says what the project is in plain words. A reader decides in five seconds whether to read further.
- `## Quick start` is a level-two heading. The commands under it are the ones a stranger runs first.
- `## Business impact` has the number and unit that the client cares about. The course asks for one business-unit number, not a model score.
- `## Team` makes ownership visible. This section becomes evidence in the bus factor work later in the year.

### CHARTER.md

The CHARTER is a short agreement written by the squad. It sets the success metric and the process rules, and each member signs it with their own name. The course example looks like this:

```text
# CityPulse squad3 Charter
## Success metric
>= 95% of hourly PM2.5 readings for Bengaluru captured per week by 2026-12-12.
## Process controls
- [ ] No direct deletes on shared data without a second person present
- [ ] Backups are restored and checked, not only taken
## Signatures
Signed: Asha Rao (@asha-rao), 2026-11-07
Signed: Ravi Kumar (@ravi-k), 2026-11-07
```

Line by line:

- The first heading names the squad.
- The success metric has a number (95 per cent), a unit (hourly PM2.5 readings for Bengaluru captured per week) and a target date. Every metric needs all three. "Improve air awareness" fails the test.
- The `- [ ]` lines are checkboxes in Markdown. GitHub shows them as empty boxes that can be ticked. Leave a blank line before a list that follows a paragraph, so every Markdown renderer treats it as a list.
- The `## Signatures` section has one line per person. The course rule is that each member adds and commits only their own line, so `git log` can show who signed.

:::trap One commit for all signatures
If one person edits all five signature lines in one commit, the history shows one author for five signatures. Each member adds their own line in a commit made from their own account.
:::

### HANDOVER.md

HANDOVER.md is the document a newcomer uses when the original authors have left. It has the architecture, a runbook of exact commands, known issues and next steps. A **runbook** is a list of commands with the steps to run them in order.

```text
# HANDOVER: <module or project name>

## What this module does
Two or three sentences in plain words.

## Architecture
The parts, and how a request or file moves between them.

## Runbook
1. Command to run, with what it should print.
2. Command to run, with what it should print.

## Known issues
- Issue, and the workaround if one exists.

## Next steps
- The first thing a new owner should do.

## Owners
- Primary: name (GitHub username)
- Second owner: name (GitHub username)
```

Line by line:

- The top heading names the module, so a reader knows where they are.
- `## What this module does` is the reader's starting point. Keep it short.
- `## Architecture` explains the parts. It does not need a diagram, but it does need the order things happen in.
- `## Runbook` is numbered, because the order matters. Each command should be one you have run on a clean copy.
- `## Known issues` is honest. A handover with no known issues is not believable.
- `## Owners` names two people. The course rule is that every module needs a second owner who can explain it.

## A portfolio page on GitHub Pages

A **portfolio** is a page that shows who you are, what you built and how to contact you. **GitHub Pages** is a free GitHub service that publishes a website from a repository. The site is served over **HTTPS**, the secure version of the web protocol, so the address starts with `https://` and the browser shows the padlock.

The course address pattern is `https://<username>.github.io`, where `<username>` is your GitHub username. The site is made from a repository with that exact name. Every push to the main branch rebuilds the site.

### The 30-second test

A hiring manager gives a page about 30 seconds. The course test checks five things, in this order:

1. Who you are.
2. What you built.
3. Whether it works.
4. How to contact you.
5. Evidence for each claim.

Each item must be visible on the first screen or one click away. The evidence item is the one most people miss. Every skill you list should link to a repo, a PR or a demo. The course warns against listing a skill without evidence; if you cannot link it, delete it.

### Building the page

The course publishes the page with four commands. The first of them creates the repo on GitHub:

```bash
GH_USER=$(gh api user --jq .login)
gh repo create "$GH_USER.github.io" --public --clone && cd "$GH_USER.github.io"
```

Line by line:

- `GH_USER=$(...)` stores your GitHub username in a variable called `GH_USER`. A **variable** is a named box that holds a value so you can reuse it.
- `gh api user` asks GitHub for your account details. `--jq .login` picks out the `login` field, which is your username.
- `gh repo create` makes a new repository. `"$GH_USER.github.io"` uses the variable to build the required name.
- `--public` makes it visible to everyone, which GitHub Pages needs for a free site.
- `--clone` downloads the new empty repo to your computer.
- `&& cd "$GH_USER.github.io"` moves into the new folder, but only if the creation worked.

The demo video must stay small, so the course compresses it with `ffmpeg`, a free video tool:

```bash
ffmpeg -i ~/Videos/citypulse-demo.mov -t 45 -vf "scale=720:-2" -c:v libx264 -crf 28 -an -movflags +faststart assets/citypulse-demo.mp4
```

Line by line:

- `ffmpeg` is the video program. `-i` names the input file, here a recording in your Videos folder. `~` means your home folder.
- `-t 45` keeps only the first 45 seconds.
- `-vf "scale=720:-2"` resizes the picture to 720 pixels wide. The `-2` keeps the height in proportion and keeps it an even number, which video encoders need.
- `-c:v libx264` uses the H.264 video encoder, which plays on almost every phone.
- `-crf 28` sets the quality. A higher number means a smaller file and lower quality. 28 is the course's balance.
- `-an` removes the sound track, so the file is smaller.
- `-movflags +faststart` moves the file's information to the front, so the video starts quickly on a slow connection.
- `assets/citypulse-demo.mp4` is the output file.

Then check the size and publish:

```bash
ls -lh assets/citypulse-demo.mp4
git add . && git commit -m "Portfolio: hero, CityPulse case study, demo" && git push -u origin main
curl -sI "https://$GH_USER.github.io" | head -1
```

Line by line:

- `ls -lh` lists the file with a human-readable size. The course limit is under 5 MB.
- `git add .` stages every changed file in the folder. The dot means "this folder and everything in it".
- `&&` chains the three Git steps, so the next one runs only if the previous one worked.
- `git push -u origin main` sends the commit to GitHub and sets the link so later pushes need no extra words.
- `curl -sI` asks the site for its headers only. `-s` hides the progress bar, `-I` asks for headers only.
- `| head -1` shows only the first line of the response. You want `HTTP/2 200`, which means the page loaded.

The course tells you to wait about a minute after the push before running the `curl`, because Pages needs a short time to rebuild. If you see an error straight after pushing, wait and try again.

:::trap Numbers that differ
Copy every number on the portfolio from `metrics.json` or the commit history, and keep the same numbers on your CV and LinkedIn profile. A recruiter who sees two different figures will assume the weaker one is the true one.
:::

## Turning CityPulse into CV lines

A CV line is a short bullet that says what you did and what happened as a result. The strongest lines have a verb, a thing you built, a method, and a number that you can show.

### The formula

Use this shape:

**[Verb] [what you built] using [tool or method], [result with number and unit], [where to see it].**

For example: "Built a CityPulse ingest step in Python that writes one dated file per day, with the row count logged for each run; code in the squad repo." Each part of the formula does a job. The verb tells the reader what you did. The tool shows you can use it. The result is the proof. The location is the evidence.

The number must come from the record, not from memory. If you cannot point to the file or the history for a number, do not use it. The examples below use the targets and counts that the course itself sets. Replace each one with the real number from your own history before you use it.

### Ten example bullets

1. Built a CityPulse ingest step that writes dated files, with the row count logged on every run. Evidence: the squad repo, `src/ingest`.
2. Wrote a README, CHARTER and signed success metric for a five-person squad, with a weekly capture target of 95 per cent. Evidence: the CHARTER file in the repo.
3. Opened pull requests linked to Issues with `Closes #n`, merging each after a review. Evidence: the merged PR list on GitHub.
4. Gave substantive code reviews that ran each branch before approving, with the commands and results written in the review. Evidence: the review history on my PRs.
5. Set branch protection on `main` requiring one approval, including for administrators, and verified that a direct push was rejected. Evidence: the protection settings and the rejection message in my notes.
6. Published a tagged release v0.2.0 with a CHANGELOG entry and matching GitHub Release notes. Evidence: the release page.
7. Planned a backlog of five Must-haves, each with an owner and an acceptance test, and two Won'ts with reasons. Evidence: BACKLOG.md.
8. Measured the model against a baseline on the same holdout, improving on the baseline's error by a stated percentage, and tested a 10 per cent worse case. Evidence: metrics.json.
9. Calculated bus factor for each module from git history and assigned a second owner for each module with one author. Evidence: docs/module-owners.md.
10. Published a live HTTPS portfolio on GitHub Pages with three case studies, a demo under 5 MB and evidence links for each skill. Evidence: the portfolio URL.

Every bullet above has a number, a verb and an evidence location. Your version of each one should keep all three.

:::tip Test each bullet in the interview
For each CV line, ask yourself: could I open the link in front of an interviewer and show the number? If the answer is no, rewrite the line until it is yes.
:::

## A weekly routine for the whole course

Evidence does not come from a single big push at the end. It builds up week by week. The routine below is a suggested pattern, not a rule set by the course. It keeps your history steady and your log up to date.

| Day | Task | Evidence you should have by the end |
|---|---|---|
| Start of each session | Pull the latest `main` with `git pull --ff-only` | Your branch starts from current code |
| Each working day | Make one or more small commits with clear messages | Commits under your name in the history |
| Each working day | Write a daily log entry with summary and commit link | A dated, linked summary |
| Mid-week | Open a PR for finished work with `Closes #n` and a test note | One PR with a clear description |
| Mid-week | Review two squad-mates' PRs by running the branch | Two substantive reviews |
| End of week | Answer open review threads and resolve them | No open threads on your PRs |
| End of week | Check your board cards and the gate text for each open task | Cards in the right column, criteria met |
| End of week | Update one CV line with a real number from the week | One new number you can show |

Line by line, the logic is simple. The start-of-session step stops you building on old code, which is the stale-main mistake the course warns about. The commit and log steps happen every working day, because the daily log asks for them. The PR and review steps are timed mid-week so that feedback has time to come back before the end of the week. The end-of-week steps close the loop: no open threads, and the board matches the work.

## Check yourself

Answer these before you move on. Each question has exactly one correct option.

```quiz
Q: Which command shows the author name recorded on each of the last two commits?
- git status
* git log --format='%h %an %s' -2
- git add .
- git push origin main
WHY: git log with --format lists commits, and %an prints the author name. git status shows changed files, not authors, and git push sends commits without showing them.

Q: Your teammate committed your CHARTER signature line from their own account. What is the main risk?
- Nothing, the signature still counts because it is in the repo
- GitHub deletes the commit after one day
- The file is renamed to charter.txt by Git
* The commit is attributed to the teammate, so your individual score lacks your evidence

WHY: Scoring reads the author of each commit. Each signature must come from its owner's account. The first option is the most tempting, but the history would show the wrong name.

Q: A reviewer asks for changes on your open PR. What is the correct response?
* Push a fix commit to the same branch, answer the comments and resolve each thread
- Open a new PR from main with the same title
- Delete the branch and reopen the Issue
- Ask the reviewer to merge the PR themselves

WHY: The PR updates when you push to its branch, so a new PR is not needed. Opening a new PR splits the history, and deleting the branch loses the work that the review refers to.

Q: Which review comment is the most substantive?
- LGTM
- Approved after reading the diff only
* Ran the branch with an empty --loc value, saw the script crash at the argument line, and asked for a usage check
- Nice change, thanks

WHY: A substantive review names what was run, what was seen and what should change. The option about reading the diff is the strongest-looking wrong answer, but the course says a diff alone misses runtime errors.

Q: The final capstone grade is split between individual and team contribution. Which split is correct?
- 40 per cent individual and 60 per cent team
* 60 per cent individual and 40 per cent team
- 50 per cent individual and 50 per cent team
- 60 per cent team and 40 per cent individual

WHY: Individual contribution carries 60 per cent and the team result carries 40 per cent. The reversed option is the most common mistake, because it sounds like teamwork should count most.

Q: Your team has merged one PR and given one substantive review, and the gate needs one merged PR and two substantive reviews. Which statement is correct?
- It passes, because one merged PR is enough to cover the review requirement
- It passes, because the trainer can count the merged PR twice
- It passes, because you have more commits than the minimum
* It does not pass yet, because one review is short of the two that the gate needs

WHY: The gate needs two substantive reviews as well as one merged PR. Commit count does not replace reviews, so the missing review is the reason it fails.

Q: Why does each daily log entry need a link?
* So the trainer can open the evidence behind the summary and check it
- Because links make the entry longer and easier to read
- Because the link replaces the commit message
- Because the platform only accepts entries that are older than a week

WHY: The log is a claim, and the link is the proof. Length is not a rule, and the link does not replace the commit message. The age rule is an invented option.

Q: Which CV line is the strongest?
- Worked hard on a data project with a great team
- Passionate about air quality and clean code
* Wrote a README and CHARTER for a five-person squad, with a 95 per cent weekly capture target and a link to the signed file
- Helped the squad with many tasks throughout the course

WHY: The strongest line has a verb, a specific thing built, a number with a unit, and a link. The vague options are the usual mistake: they describe effort, which cannot be checked.
```

## Flashcards

```cards
Commit :: A saved snapshot of your changes, with an author name, an email and a message attached.
git config user.name :: The setting that sets the author name Git records on each commit you make.
Staging area :: The list of changes that git add has chosen for the next commit.
Pull request (PR) :: A request to merge one branch into another, with the diff, discussion and checks on one page.
Substantive review :: A review that says what you ran, what you saw and what should change.
LGTM :: "Looks good to me". On its own it scores zero under the course rules.
Closes #n :: A line in the PR description that closes Issue n when the PR is merged.
Scoring gate :: A checkpoint scored from 0 to 3 against stated criteria on the platform.
60/40 grade :: 60 per cent individual contribution and 40 per cent team result.
Markdown :: Plain-text format where # makes headings and - makes list bullets, rendered by GitHub.
GitHub Pages :: Free HTTPS hosting that publishes a site from a repository named username.github.io.
30-second test :: A check that a page shows who you are, what you built, whether it works, how to contact you, and evidence.
```
