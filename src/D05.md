TITLE: Day 5 — Team workflow: branches, pull requests and reviews
SUB: You will be able to create a focused branch, open a pull request that a teammate can review with evidence, enforce review on main, and publish a tagged release with matching notes.

## The idea in one minute

Five students work on the same program. If each person edits the shared copy of the code directly, one broken change can stop everyone. The team works the way a school newspaper does. Each story is drafted on its own sheet, an editor reads it and asks for changes, and only then does it go to print.

In CityPulse, your draft is a **branch**, the editor's request is a **pull request**, the printing rule is **branch protection**, and the printed edition is a **release** with a version number. By the end of this chapter you will be able to start a branch from an up-to-date main, open a pull request linked to an Issue, review a teammate's change by running it, block direct pushes to main, and publish v0.2.0 with an annotated tag and release notes.

## Starting from zero

**Terminal.** A text window where you type commands instead of clicking buttons. Everything in this chapter happens in a terminal, unless the text says otherwise.

**Command.** A line of text you type and run, such as `git status`. The first word names the program. The words after it tell the program what to do.

**File and folder.** A file holds data, for example a Python script or a CSV table. A folder (also called a directory) holds files and other folders.

**Flag.** An option that changes how a command behaves. Flags usually start with a dash. A short flag is one letter, such as `-m`. A long flag is a word, such as `--force`, and starts with two dashes.

**Argument.** A value you pass to a command or function. In `git switch -c feat/12-loc-flag`, the text `feat/12-loc-flag` is an argument.

**Git.** A version control system: a program that records saved states of your files, so you can see who changed what and return to an older state.

**Repository (repo).** A folder that Git tracks, including its full history.

**Commit.** One saved state of the files, with a message and an ID. The ID is a long code of letters and digits. Courses and tools often show a short form such as `6400cdb`.

**Branch.** A movable name that points at a line of commits. Adding a commit moves the name forward. Creating a new branch starts a second line from the commit you are on, so two lines of work can grow without touching each other.

**Remote and origin.** A remote is a copy of the repository on another computer, usually a server. `origin` is the default name for the main remote, here the copy on GitHub. `origin/main` means "the main branch as it was the last time Git downloaded it from origin".

**GitHub.** A website that hosts Git repositories and adds Issues, pull requests and releases on top.

**Issue.** A ticket on GitHub that describes a task or bug. Each Issue has a number, such as #12.

**Pull request (PR).** A request to merge one branch into another. It is a page that holds the diff, the discussion and the checks in one place.

**Diff.** The set of lines added and removed between two versions of the files.

**Tag.** A permanent name attached to one commit, such as `v0.2.0`.

**Release.** A published version on GitHub, built from a tag, with notes that describe what changed.

**Function.** A named block of Python code. It takes inputs (arguments) and returns a result with `return`.

**Variable.** A name that holds a value, for example `total = 0`.

**List.** An ordered collection written in square brackets: `[1, 2, 3]`.

**Dictionary (dict).** A collection of key-and-value pairs written in curly braces. You look up a value by its key: `{"name": "tests", "status": "pass"}` has the key `"status"` with the value `"pass"`.

**Set.** A collection with no order and no repeats: `{"S1", "S2"}`.

**Loop.** A block that repeats once for each item in a collection. In `for item in items:`, the indented lines run once per item.

**Assert.** A line that checks a condition. If the condition is false, Python stops with an error. The tests in this chapter use `assert` to check your functions.

**Server.** A computer that provides a service to other computers. GitHub is a server.

## The tools

### Git branches, merge and rebase

**What it is.** A branch lets you develop a change in isolation. When the change is ready, you join it back to main. Git has two ways to join. A **merge** creates a new commit that has two parents, so both histories stay visible. A **rebase** copies your commits so they sit on top of the latest main. The copies get new IDs, so the history looks as if you started from the newer main.

**Why CityPulse uses branches.** Five students will change `fetch.sh` in the same week. Branches keep each change separate until someone has reviewed it. Branch names such as `feat/12-loc-flag` also link the work to Issue #12 on the project board.

**Alternatives.** The first alternative is to commit everyone's work straight to main. It is the fastest at the start, but untested changes land directly on the shared line. The T08 gate forbids this. The second alternative is a long-lived `develop` branch, the approach called Git Flow. It suits teams that ship on a schedule at large companies. For a squad of five, the extra branches cost more than they save.

**How it works.** Start every branch from the latest main, so your diff contains only your change. Commit in small steps. When main moves on, bring its new work in. Rebase if only you use the branch. Merge if someone else has pulled it. Then push the branch and open a pull request.

**The slide code, explained.** The course shows this sequence for Issue #12. The lines are restored here to their normal form.

```bash
git switch main && git pull --ff-only
git switch -c feat/12-loc-flag
git add -p scripts/fetch.sh
git commit -m "Add --loc flag to fetch.sh" -m "Lets squads fetch a second Bengaluru location without editing the script."
git push -u origin feat/12-loc-flag
# later, main has moved and only you use this branch:
git fetch origin
git rebase origin/main
git push --force-with-lease
git log --oneline --graph --all -10
```

- `git switch main` changes the branch you are working on to `main`. The `&&` after it means "run the next command only if this one succeeded".
- `git pull --ff-only` downloads the latest main from origin and moves your local main forward. `--ff-only` means "fast-forward only". If your local main has commits that origin lacks, Git refuses, which stops you from creating an accidental merge commit on main.
- `git switch -c feat/12-loc-flag` creates a new branch and switches to it. `-c` means "create". The name follows the pattern type, Issue number, short description. `feat` stands for feature.
- `git add -p scripts/fetch.sh` stages changes in the file. Staging selects what goes into the next commit. `-p` (patch) shows you each changed block and asks whether to stage it. Type `y` to stage the block and `n` to leave it out.
- `git commit -m "..." -m "..."` creates the commit. Each `-m` adds one paragraph to the message. The first paragraph is the title and the second is the body.
- `git push -u origin feat/12-loc-flag` uploads the branch to origin. `-u` records the link, so later `git push` calls need no arguments.
- The line starting with `#` is a comment. Git and the shell ignore it.
- `git fetch origin` downloads new commits and updates `origin/main`. It does not change your files.
- `git rebase origin/main` replays your commits on top of the latest `origin/main`. Your commit IDs change.
- `git push --force-with-lease` overwrites the remote branch with the rewritten history. It refuses if someone has pushed to the branch since your last fetch.
- `git log --oneline --graph --all -10` prints the last ten commits, one per line, and draws the branch lines.

The last command gives output like this. The exact drawing depends on your history.

```term
$ git log --oneline --graph --all -10
* 5501ef2 Merge PR #42: drop duplicate station readings
|\
| * 6400cdb Drop duplicate station readings
|/
* a0a4240 CityPulse ingest: load + clean readings
```

Read the graph from the bottom up. The line at the bottom is the oldest commit. The two lines that split and join show a branch that was merged back.

:::trap Rebasing a branch someone else has pulled
A rebase rewrites the commits on the branch. A teammate who already has the old commits will get a tangle on their next pull. If anyone else has pulled your branch, merge main into it instead.
:::

:::trap Using plain --force
`git push --force` overwrites the remote branch even when a teammate has pushed new work to it. Use `git push --force-with-lease`, which refuses in that case.
:::

:::trap Branching from a stale main
If you skip `git pull --ff-only`, your branch starts from old code. Its diff then includes work that has already been merged, and you get conflicts that were avoidable.
:::

### Pull requests and code review

**What it is.** A pull request asks GitHub to merge one branch into another. The page shows the diff, the comments and the results of any checks. Code review means a squad-mate reads the change, runs it, and then comments, requests changes or approves.

**Why CityPulse uses pull requests.** The T08 gate scores each student on one merged PR and two substantive reviews. A closing keyword in the pull request description, `Closes #12`, closes Issue #12 automatically when the PR merges. Reviewers can also run the change with `gh pr checkout`, which catches bugs that a diff alone hides.

**Alternatives.** Pair programming gives fast feedback, but it leaves no written review trail for scoring or for future readers. Emailing patches is how the Linux kernel project works. It has no link to Issues, checks or branch protection, so CityPulse does not use it.

**How it works.** The author opens a PR that says what changed, why, and how it was tested. Reviewers check out the branch and run it, then leave labelled comments. The author answers with new commits and marks each thread as resolved. After approval, the PR is merged and the branch deleted.

```flow
TITLE: One pull request from push to merge
NODES: Author's laptop | GitHub | Reviewer's laptop
STEPS:
1>2 :: git push -u origin feat/12-loc-flag :: The branch travels to GitHub, and the PR is opened against main.
2>3 :: review requested :: GitHub tells the reviewer that PR #14 is waiting.
3>2 :: request changes :: The reviewer runs the branch, then posts a blocking comment with evidence.
1>2 :: fix commit pushed :: The author adds a commit to the same branch, and the PR updates by itself.
2>3 :: approve :: The reviewer runs the fix again and approves.
2>1 :: merged :: GitHub merges the PR and closes Issue #12, because the description said Closes #12.
```

**The author's commands, explained.** The course uses the GitHub command-line tool, `gh`. You need to sign in once with `gh auth login` before these work.

```bash
gh pr create --base main --title "Add --loc flag to fetch.sh" \
  --body "Closes #12. How tested: ./scripts/fetch.sh --loc Whitefield appended 1 row." \
  --reviewer ravi-k,meera-s
```

- `gh pr create` opens a pull request from the current branch.
- `--base main` says the PR should merge into `main`.
- `--title` sets the PR title, in quotes because it contains spaces.
- `--body` sets the description. `Closes #12` is the keyword that closes Issue #12 on merge. The backslash at the end of the first line tells the shell that the command continues on the next line.
- `--reviewer ravi-k,meera-s` asks two people to review. The names are separated by a comma and no spaces.

A successful run prints the address of the new PR. The course's example looks like this.

```term
$ gh pr create --fill --reviewer data-lead
Creating pull request for feat/dedup-step into main in you/citypulse
https://github.com/you/citypulse/pull/42
```

The `--fill` flag builds the title and body from your commit messages, instead of asking you for them.

**The reviewer's commands, explained.**

```bash
gh pr checkout 14
./scripts/fetch.sh --loc Whitefield && tail -1 "data/raw/$(date +%F).csv"
gh pr review 14 --request-changes --body "Blocking: --loc with no value crashes under set -u; add a usage check."
```

- `gh pr checkout 14` downloads PR #14's branch and switches your computer to it, so you can run the code.
- `./scripts/fetch.sh --loc Whitefield` runs the script. The `./` means "the script in this folder". The `--loc` flag passes the location name Whitefield.
- `&&` runs the next command only if the script succeeded.
- `tail -1` prints the last line of a file. Here it shows the row that was just appended.
- `$(date +%F)` runs `date +%F`, which prints today's date as `2026-11-11`, and puts the result into the file path.
- `gh pr review 14 --request-changes --body "..."` posts a review on PR #14 that blocks merging until the problem is fixed. `set -u` in the script makes an unset variable an error, so a missing `--loc` value stops the script with a message.

When the author has fixed the problem and the reviewer has checked it, the reviewer runs `gh pr review 14 --approve --body "Re-ran: 1 row appended, no duplicates."`. The author then merges with:

```bash
gh pr merge 14 --squash --delete-branch
```

`--squash` combines all the PR's commits into one commit on main. `--delete-branch` removes the branch on GitHub after the merge. The course's worked example uses a plain merge command instead. Both appear in the course material, so know the difference: `--squash` gives main one commit per PR, and a merge keeps every commit.

:::trap Writing LGTM and nothing else
"LGTM" means "looks good to me". On its own it scores zero under the T08 rules. Say what you ran, with what input, and what you saw.
:::

:::trap Reviewing the diff without running the code
A diff can look correct and still fail at runtime. Run the branch before you approve.
:::

:::trap Merging with open threads
An unresolved thread hides a question that nobody answered. Answer or resolve each thread before merging.
:::

### Branch protection

**What it is.** Branch protection is a GitHub setting. It blocks direct pushes to a branch and requires conditions, such as approvals or passing checks, before a PR can merge. It turns a team agreement into a rule that the server enforces.

**Why CityPulse uses it.** The T08 gate tests that `git push origin main` is rejected. Turning on "include administrators" stops the Tech Lead from bypassing review under deadline pressure. T09 adds a required shellcheck check to the same rule, and T10 audits it.

**Alternatives.** A team agreement costs nothing to set up, but it breaks under deadline pressure. The CHARTER controls need enforcement, so an agreement alone is not enough. Repository rulesets are newer and can cover many branches at once. Either approach works. Classic branch protection is simpler when you protect a single `main` branch.

**The command, explained.** This command sets the rule through GitHub's API. An API is the set of web addresses a program uses to read or change data on a server.

```bash
gh api -X PUT 'repos/{owner}/{repo}/branches/main/protection' --input - <<'EOF'
{
  "required_status_checks": null,
  "enforce_admins": true,
  "required_pull_request_reviews": {"required_approving_review_count": 1},
  "restrictions": null
}
EOF
```

- `gh api` sends a request to GitHub's API.
- `-X PUT` sets the request method to PUT, which replaces the current setting.
- `'repos/{owner}/{repo}/branches/main/protection'` is the address of the rule for `main`. `{owner}` and `{repo}` are filled in by `gh` from the repository in your current folder.
- `--input -` tells `gh` to read the request body from standard input, which is the text that follows.
- `<<'EOF'` starts a "here document". The shell feeds it every line up to the next line that says `EOF`. The quotes around `EOF` stop the shell from changing `$` or other symbols inside the text.
- `"required_status_checks": null` means no automated checks are required yet. T09 changes this later.
- `"enforce_admins": true` applies the rule to administrators as well. This is the setting the trap below is about.
- `"required_approving_review_count": 1` requires one approving review.
- `"restrictions": null` does not limit who may push, beyond the rules above.

Now check the setting:

```bash
gh api 'repos/{owner}/{repo}/branches/main/protection' --jq '.required_pull_request_reviews.required_approving_review_count'
```

`--jq` picks one value out of the JSON response. The expected output is `1`.

Next, prove that a direct push is refused. Make an empty commit, which records no file changes, and try to push it to main.

```bash
git commit --allow-empty -m "Test direct push"
git push origin main   # expect: protected branch hook declined
git reset --hard origin/main
```

- `git commit --allow-empty` creates a commit with no changes, which is enough to test a push.
- `git push origin main` should print a refusal with the words "protected branch hook declined". Copy this message into your lab notes as evidence.
- `git reset --hard origin/main` moves your local main back to the state of origin's main and discards the test commit. It throws away local changes, so run it only when the test commit is the only thing you want to discard.

:::trap Leaving out include administrators
Without `enforce_admins`, the rule applies to everyone except repository administrators. The Tech Lead could then push directly. Set `"enforce_admins": true`.
:::

:::trap Protecting main before the PR template is merged
If you protect main first, the template PR cannot be merged. Merge the template PR, then turn on protection.
:::

:::trap Forgetting the test commit
After the rejected push, the test commit still exists on your local main. Run `git reset --hard origin/main` to remove it.
:::

### Semantic versioning and releases

**What it is.** A semantic version has three numbers, MAJOR.MINOR.PATCH. A breaking change raises MAJOR. A new feature that stays compatible raises MINOR. A fix raises PATCH. A release is an annotated Git tag on one commit, with notes taken from a CHANGELOG file. An annotated tag stores the author, the date and a message. A CHANGELOG is a file that lists what changed in each version.

**Why CityPulse uses it.** The tags `v0.1-p1` and `v0.2.0` mark the exact commit that was demonstrated at each milestone. The CHANGELOG follows the Keep a Changelog format, so the client sponsor gets readable release notes. The T10 gate checks that the GitHub Release notes match the `[0.2.0]` section of CHANGELOG.md.

**Alternatives.** Date-based versions, such as 2026.11.28, are clear for scheduled releases. They say nothing about compatibility. Lightweight tags are only pointers. They carry no author, date or message, but an annotated tag is auditable.

**The release commands, explained.**

```bash
git switch main && git pull --ff-only
grep -n '^## \[0.2.0\]' CHANGELOG.md
git tag -a v0.2.0 -m "P2: team workflow"
git push origin v0.2.0
awk '/^## \[0.2.0\]/{f=1; next} /^## \[/{f=0} f' CHANGELOG.md > /tmp/notes-0.2.0.md
gh release create v0.2.0 --title "v0.2.0" --notes-file /tmp/notes-0.2.0.md
gh release view v0.2.0
git ls-remote --tags origin v0.2.0
```

- The first line makes sure you are tagging the latest main, not an old copy.
- `grep -n` searches a file for a pattern and prints matching lines with their line numbers. The pattern `'^## \[0.2.0\]'` means "a line that starts with `## [0.2.0]`". The `^` anchors the match to the start of the line, and `\[` matches a literal square bracket. The output is one line that shows where the heading is.
- `git tag -a v0.2.0 -m "P2: team workflow"` creates an annotated tag named `v0.2.0`. `-a` makes it annotated, and `-m` gives the message.
- `git push origin v0.2.0` sends the tag to origin. `git push` does not send tags unless you name them.
- `awk` is a text-processing tool. The first pattern, `/^## \[0.2.0\]/{f=1; next}`, switches a flag `f` on when it meets the heading and skips the heading line. The second pattern, `/^## \[/{f=0}`, switches the flag off at the next heading. The final `f` prints each line while the flag is on. The result is the text of the 0.2.0 section alone.
- `> /tmp/notes-0.2.0.md` writes the output into a file. The course uses `/tmp`, which Git Bash on Windows also understands. Any writable path works, as long as the same path is used in the next command.
- `gh release create v0.2.0 --title "v0.2.0" --notes-file /tmp/notes-0.2.0.md` creates the GitHub Release for the tag and fills its notes from the file.
- `gh release view v0.2.0` prints the release so you can check it.
- `git ls-remote --tags origin v0.2.0` asks origin which tag it holds and prints the ID of that tag. This proves the tag arrived on the server.

:::trap Tagging a stale main
If your local main is behind origin, the tag lands on an older commit. Always run `git pull --ff-only` first.
:::

:::trap Bumping MAJOR for a small change
Before version 1.0.0, a new feature raises MINOR. Going from v0.2.0 to v1.0.0 would signal a stable, compatibility-promising release that you have not made.
:::

## The worked example

**Goal.** Remove repeated station readings and zero readings from the data that `clean.py` reads. A repeated reading is one with the same station, timestamp and pollutant as an earlier row.

**The code.** The course's slides show these two functions. The indentation was lost in the extraction and has been restored.

```python
def dedup(rows):
    seen, out = set(), []
    for r in rows:
        key = (r["station_id"], r["ts"], r["pollutant"])
        if key not in seen:
            seen.add(key)
            out.append(r)
    return out

def clean(rows):
    rows = [r for r in rows if float(r["value"]) > 0]
    return dedup(rows)  # drop duplicate station readings
```

**Explanation, line by line.**

- `def dedup(rows):` defines a function named `dedup`. It takes one argument, `rows`, a list of readings. Each reading is a dictionary with keys such as `"station_id"`.
- `seen, out = set(), []` creates two variables at once. `seen` is an empty set that records keys already met. `out` is an empty list that will hold the kept rows.
- `for r in rows:` runs the indented lines once for each reading, with `r` holding the current one.
- `key = (r["station_id"], r["ts"], r["pollutant"])` builds a tuple, which is a fixed group of values in round brackets. Together, these three fields identify one reading.
- `if key not in seen:` checks whether this key has been seen before. It is true only for the first occurrence.
- `seen.add(key)` records the key, and `out.append(r)` keeps the reading.
- `return out` sends the kept rows back to the caller. Indentation shows which lines belong inside the function.
- `def clean(rows):` defines the second function.
- `rows = [r for r in rows if float(r["value"]) > 0]` is a list comprehension. It builds a new list with only the readings whose `value` field, converted to a number by `float`, is greater than zero.
- `return dedup(rows)` passes the filtered list to `dedup` and returns the result. The comment after `#` is ignored by Python.

**Tracing the loop.** The next animation uses the same loop pattern on a shorter list of keys, so you can see the set and the list change. Press play and watch each line light up.

```trace
TITLE: Keeping the first copy of each key
CODE:
seen, out = set(), []
for key in ["S1-pm25", "S2-no2", "S1-pm25"]:
    if key not in seen:
        seen.add(key)
        out.append(key)
STEPS:
1 :: seen=set(); out=[] :: Both names are created. seen is an empty set and out is an empty list.
2 :: key="S1-pm25"; seen=set(); out=[] :: The loop takes the first key.
3 :: key="S1-pm25"; seen=set(); out=[] :: The key is not in seen yet, so the test is true.
4 :: key="S1-pm25"; seen={"S1-pm25"}; out=[] :: The key is recorded.
5 :: key="S1-pm25"; seen={"S1-pm25"}; out=["S1-pm25"] :: The first copy is kept.
2 :: key="S2-no2"; seen={"S1-pm25"}; out=["S1-pm25"] :: Second time round the loop.
3 :: key="S2-no2"; seen={"S1-pm25"}; out=["S1-pm25"] :: This key is new, so the test is true.
4 :: key="S2-no2"; seen={"S1-pm25", "S2-no2"}; out=["S1-pm25"] :: The new key is recorded.
5 :: key="S2-no2"; seen={"S1-pm25", "S2-no2"}; out=["S1-pm25", "S2-no2"] :: The second key is kept.
2 :: key="S1-pm25"; seen={"S1-pm25", "S2-no2"}; out=["S1-pm25", "S2-no2"] :: Third time round, and the key is a repeat.
3 :: key="S1-pm25"; seen={"S1-pm25", "S2-no2"}; out=["S1-pm25", "S2-no2"] :: The test is false, so the indented lines are skipped.
```

The final `out` holds two keys. The repeat was dropped, and the order of the first occurrences was kept.

**The Git steps.** Create the branch, commit, and read the diff against main:

```term
$ git switch -c feat/dedup-step
Switched to a new branch 'feat/dedup-step'
$ git commit -m 'Drop duplicate station readings'
[feat/dedup-step 6400cdb] Drop duplicate station readings
1 file changed, 9 insertions(+), 2 deletions(-)
$ git diff --stat main..feat/dedup-step
clean.py | 11 +++++++++--
1 file changed, 9 insertions(+), 2 deletions(-)
```

The `--stat` form of `git diff` summarises the change. `main..feat/dedup-step` compares the tip of main with the tip of the branch. The line `1 file changed, 9 insertions(+), 2 deletions(-)` tells the reviewer that the change is small and self-contained. The `+` and `-` marks show the added and removed lines.

**The test run.** The course's sample file, `readings.csv`, has four rows. Two are identical, and one has a value of 0. The course shows the output after running `clean.py`: two rows remain, which are one reading from S1 and one from S2. The extract does not show the part of `clean.py` that reads the file from the command line, so your script may print the rows in a different form. What matters is the count.

**The review and the merge.** The author attaches this run to PR #42. A teammate runs the branch, sees two rows instead of four, and approves with evidence. Protected main then accepts only the merge through the PR. The course shows the final merge and graph like this:

```term
$ git log --oneline --graph -n 3
* 5501ef2 Merge PR #42: drop duplicate station readings
|\
| * 6400cdb Drop duplicate station readings
|/
* a0a4240 CityPulse ingest: load + clean readings
```

The change is on main through a reviewed PR, and the branch is gone. The commit `5501ef2` is the merge, and `6400cdb` is the original commit on the branch.

## The hands-on lab, step by step

Run the lab in the CityPulse repository that the course gives you. Your Issue number, branch name and PR number will differ from the examples. Use your own.

### Step 1: Start from a fresh main

**What you do.** Make sure your local main matches origin's main.

**Type.**

```bash
git switch main
git pull --ff-only
```

**You should see.** A line such as `Already up to date.` or a summary of the new commits that were downloaded.

**How you know it worked.** Running `git status` prints `On branch main` and `nothing to commit, working tree clean`. If `git pull --ff-only` refuses, your local main has commits that origin does not have. Ask for help before you continue, because you need to know where those commits came from.

### Step 2: Create a focused feature branch

**What you do.** Create one branch for one Issue, named after the Issue.

**Type.**

```bash
git switch -c feat/12-loc-flag
```

**You should see.** `Switched to a new branch 'feat/12-loc-flag'`.

**How you know it worked.** `git branch --show-current` prints `feat/12-loc-flag`. Main is unchanged, which you can check with `git log --oneline -1 main`.

### Step 3: Make a small, reviewable commit

**What you do.** Change one file, then stage only the lines that belong to this change and commit them.

**Type.**

```bash
git add -p scripts/fetch.sh
git commit -m "Add --loc flag to fetch.sh" -m "Lets squads fetch a second Bengaluru location without editing the script."
```

Answer `y` or `n` to each block that `git add -p` shows.

**You should see.** Git prints the short commit ID and a summary such as `1 file changed, 9 insertions(+)`.

**How you know it worked.** `git show --stat HEAD` lists only the file you meant to change. If the list shows other files, undo the commit with `git reset --soft HEAD~1`, which keeps your edits, and stage again.

### Step 4: Push and open a pull request

**What you do.** Upload the branch and open a PR that closes Issue #12.

**Type.**

```bash
git push -u origin feat/12-loc-flag
gh pr create --base main --title "Add --loc flag to fetch.sh" --body "Closes #12. How tested: ./scripts/fetch.sh --loc Whitefield appended 1 row." --reviewer ravi-k,meera-s
```

Use the reviewer names that the course gives you.

**You should see.** The push prints a summary and a link to create the PR. `gh pr create` prints the URL of the new PR.

**How you know it worked.** Open the URL. The PR's description contains `Closes #12`, and the reviewers are listed.

### Step 5: Respond to review feedback

**What you do.** Read each review comment. Fix the code if the comment is right. Push a new commit, reply to the thread and resolve it.

**Type.** Make the change in your editor, then:

```bash
git add scripts/fetch.sh
git commit -m "Add usage check for --loc without a value"
git push
```

**You should see.** The push adds the commit to the existing PR. The PR does not open a second one.

**How you know it worked.** Each comment thread on the PR shows either a reply from you or a resolved mark. The reviewer's `--approve` review appears after they re-run your code. Do not merge until every thread is resolved or answered.

### Step 6: Sync with main via rebase

**What you do.** Only if main moved while your PR was open and nobody else has pulled your branch, bring the new main work under your commits.

**Type.**

```bash
git fetch origin
git rebase origin/main
git push --force-with-lease
```

**You should see.** Git replays your commits one by one. If it stops with a conflict, the output names the file.

**How you know it worked.** `git log --oneline --graph -5` shows your commits sitting on top of the latest origin/main. The PR page updates on its own.

If a reviewer has already pulled your branch, do not rebase. Run `git merge origin/main` instead, then push normally with `git push`.

### Step 7: Merge the PR and clean up

**What you do.** Merge the approved PR and delete the branch, then update your local main.

**Type.**

```bash
gh pr merge 14 --squash --delete-branch
git switch main
git pull --ff-only
git branch --list feat/12-loc-flag
```

Use the PR number that your own PR shows.

**You should see.** `gh pr merge` reports the merge and, because of `--delete-branch`, deletes the branch on GitHub and your local copy of it. `git branch --list feat/12-loc-flag` prints nothing.

**How you know it worked.** Issue #12 is closed on GitHub, because the PR said `Closes #12`. `git log --oneline -3` shows the squashed commit at the top of main.

If the local branch is still listed, delete it with `git branch -D feat/12-loc-flag`. After a squash merge, `git branch -d` refuses, because the branch's original commits are not on main. Check with `git log main..feat/12-loc-flag` first if you are unsure.

## What the quiz tests

The day quiz has ten questions, one per topic below. You must pass with 70%, and the first attempt is the one that counts. Read each topic, then work the practice question that follows the list.

### Creating a branch (create-branch)

A new branch starts at the commit you are on, so `git switch -c` copies your current state. If you create the branch from a stale main, the diff will mix your change with old code and produce conflicts. The safe order is to switch to main, pull with `--ff-only`, and only then create the branch. Examiners test whether you know the starting point is what matters, not the name.

:::trap Thinking a branch name is the starting point
The name `feat/12-loc-flag` says nothing about where the branch starts. Only the commit you are on at creation time decides that.
:::

### Why a pull request exists (pull-request-purpose)

A pull request is a request to merge a branch, and the page holds the diff, discussion and checks together. It exists so that a teammate can review and run the change before it reaches main. Examiners ask why you do not merge your own branch, and the answer is that the review is the control that the T08 gate measures. A PR also links the work to an Issue through `Closes #n`.

:::trap Treating the PR as a backup
A PR is not a backup. Your branch on origin already holds the commits, and the PR is the proposal to merge them.
:::

### Resolving a merge conflict (merge-conflict-resolution)

A conflict happens when two lines of history changed the same lines of a file, and Git cannot choose between them. Git stops and marks the conflicting part of the file with `<<<<<<<`, `=======` and `>>>>>>>`. You edit the file to keep the correct code, delete the three marker lines, run `git add` on the file, and then continue the merge or rebase. A conflict is not an error in Git. It is a request for a human decision.

:::trap Force-pushing to get rid of a conflict
Force-pushing does not resolve a conflict. It overwrites the remote with your version and can erase a teammate's work.
:::

### Updating a PR with new commits (pr-update-commits)

A PR follows its branch. When you push a new commit to the branch, the PR updates on its own, and the reviewers see the new commit. You do not open a second PR. You answer each review thread, then resolve it, and the reviewer approves once they have re-run the code. Examiners ask whether you know that the PR is the branch, not a snapshot of it.

:::trap Opening a second PR for the fix
Opening a second PR splits the review history. Push to the same branch instead.
:::

### Branch protection rules (branch-protection)

Branch protection turns the team's process into a rule that GitHub enforces. In CityPulse, the rule requires a pull request with at least one approval, and it applies to administrators too. A direct push to main is refused, and you prove this by trying one and keeping the rejection message. Examiners expect you to know what `enforce_admins` does and why it matters.

:::trap Forgetting administrators
A rule that does not include administrators is not enforced for the Tech Lead. The T08 gate fails if the rule has no `enforce_admins` setting.
:::

### Rebasing onto main (rebase-onto-main)

A rebase replays your commits on top of the latest main and gives them new IDs. It is safe only when nobody else has pulled the branch, because their copy of the old commits would no longer match. After a rebase, a normal push is refused, so you use `--force-with-lease`, which refuses if someone has pushed since your last fetch. If others have pulled, merge main into the branch instead.

:::trap Rebasing a shared branch
The usual mistake is rebasing a branch a teammate has already pulled. Their next pull then produces duplicate or tangled history.
:::

### Writing a useful review (review-quality)

A review is useful when it states what the reviewer ran, what input they used and what they saw. The course rule is that "LGTM" on its own earns no credit, and neither does general praise. A substantive comment points at a specific problem and shows the evidence. Examiners look for a comment that a stranger could act on without asking questions.

:::trap Approving without running
An approval that does not mention a run is not evidence. A reviewer who only read the diff can miss runtime errors.
:::

### Squash merging (squash-merge)

A squash merge combines all the commits of a PR into one commit on main. It keeps main's history short and readable, with one commit per PR. It is done with `gh pr merge --squash`, and `--delete-branch` removes the branch afterwards. A normal merge keeps every commit from the branch, so main gets more history. Examiners test whether you can say which of these you want and why.

:::trap Assuming squash rewrites main's old history
A squash merge does not change the commits that are already on main. It adds one new commit for the PR.
:::

### The fork concept (fork-concept)

A fork is your own copy of someone else's repository on GitHub. You have full rights in your fork, but no rights in the original. To contribute, you push your branch to your fork and open a PR from the fork into the original repository. This is how an outside contributor works when they have no write access. The fork is not the same as a clone on your computer, which is only a local copy.

:::trap Confusing a fork with a clone
A clone is a download to your own machine. A fork is a copy on GitHub that belongs to your account.
:::

### Comparing branches (diff-branches)

The command `git diff main..feat/22-alerts` compares the tip of main with the tip of the branch. If main has moved on since the branch was created, this comparison also shows main's new work, reversed, as if the branch removed it. The three-dot form, `git diff main...feat/22-alerts`, compares the branch with the point where it split from main, so it shows only the branch's own changes. The `--stat` option summarises the result by file.

:::trap Using two dots when main has moved
Two dots show main's newer work as removed. Use three dots to see only what the branch adds.
:::

## The graded lab skill

The graded lab is a Python problem. You write a few functions, and automatic tests check them. Hidden tests use cases that the visible tests do not show, so you must think about the edge cases yourself. This section teaches three techniques that the problem needs.

### Summing fields across a list of dictionaries

A list of dictionaries is the usual shape of real data. Each dictionary is one record, such as one check in a release, and the keys are the field names. To add up one field, loop over the list and add the field of each record to a total.

```python
checks = [{"name": "tests", "status": "pass"}, {"name": "lint", "status": "fail"}]
passed = 0
for check in checks:
    if check["status"] == "pass":
        passed += 1
print(passed)
```

- `checks = [...]` creates a list with two dictionaries. Each has the keys `"name"` and `"status"`.
- `passed = 0` starts a counter at zero. Starting at zero matters: an empty list must give 0, not an error.
- `for check in checks:` runs the next lines once for each dictionary.
- `if check["status"] == "pass":` looks up the `"status"` key and compares it with the text `"pass"`. The double equals sign checks equality. A single equals sign would assign a value.
- `passed += 1` adds one to the counter. It is short for `passed = passed + 1`.
- `print(passed)` shows the result. The output is `1`.

The same result can be written in one line with `sum`: `passed = sum(1 for c in checks if c["status"] == "pass")`. Learn the loop first, because it is easier to add conditions to.

### Keeping only the latest entry per person

Sometimes a list has several records for the same person, and only the most recent one counts. Use a dictionary as a lookup table: the key is the person, and the value is the record you are keeping. When a new record arrives, keep it if it is newer than the one you have.

```python
latest = {}
for entry in [{"person": "ravi", "time": "09:00"}, {"person": "ravi", "time": "10:00"}]:
    current = latest.get(entry["person"])
    if current is None or entry["time"] >= current["time"]:
        latest[entry["person"]] = entry
print(latest["ravi"]["time"])
```

- `latest = {}` creates an empty dictionary to hold the best record for each person.
- `latest.get(entry["person"])` looks up the person. If the person is not there, `get` returns `None` instead of raising an error.
- `current is None` checks for the missing case. Use `is None`, not `== None`, for this check.
- `entry["time"] >= current["time"]` compares the two times. Text such as `"09:00"` compares correctly only when every value has the same format, such as `HH:MM` or a full ISO date like `2026-11-23T09:00`.
- The `>=` means that when two records have the same time, the later one in the list wins, because it is the one that replaces the earlier one.
- `latest[entry["person"]] = entry` stores the record under the person's name.
- `print(latest["ravi"]["time"])` prints `10:00`, the later time.

### Combining conditions and returning the reasons

A decision often needs several conditions at once, and the caller needs to know which one failed. Build a list of reasons. Add a message for each condition that fails. At the end, the decision is "allowed" exactly when the list is empty.

```python
reasons = []
if 0 == 0:
    reasons.append("first rule failed")
if 1 > 2:
    reasons.append("second rule failed")
can_go = not reasons
print(can_go, reasons)
```

- `reasons = []` starts with no failures.
- `if 0 == 0:` is a condition that is true here, so the message is added. In real code, the condition would test your data.
- `reasons.append("...")` adds one message to the end of the list.
- `if 1 > 2:` is false, so its message is not added.
- `can_go = not reasons` makes the decision. An empty list is treated as false, so `not` turns it into true. Any message makes the list non-empty and the decision false.
- `print(can_go, reasons)` prints `False ['first rule failed']`.

### The practice problem

This is an original problem that uses the same skills. It is not the graded lab.

**Task.** Write a function `check_release(release)`. The argument `release` is a dictionary with three optional keys.

- `"checks"` is a list of dictionaries. Each has `"name"`, and `"status"`, which is `"pass"`, `"fail"` or `"skip"`.
- `"signoffs"` is a list of dictionaries. Each has `"person"`, `"verdict"` (which is `"approve"` or `"reject"`), and `"time"`, an ISO text time such as `"2026-11-23T09:00"`.
- `"labels"` is a list of text labels.

The function must return a dictionary with these keys:

- `"passed"`, `"failed"` and `"skipped"`: the number of checks with each status.
- `"approvals"`: the number of people whose latest verdict is `"approve"`. Each person's latest verdict is the one with the latest time.
- `"can_ship"`: `True` only when `"reasons"` is empty.
- `"reasons"`: a list of blocking reasons, in this order. First, one `"check failed: NAME"` for each failed check, in input order. Second, `"needs at least one approval"` when `approvals` is 0. Third, one `"rejected by PERSON"` for each person whose latest verdict is `"reject"`, sorted by name. Fourth, `"label do-not-ship is set"` when that label is present.

**Example.**

```text
release = {"checks": [{"name": "tests", "status": "pass"}], "signoffs": [{"person": "meera", "verdict": "approve", "time": "2026-11-23T11:00"}], "labels": []}
check_release(release) gives passed 1, failed 0, skipped 0, approvals 1, can_ship True, reasons [].
```

**Edge-case checklist.**

- Empty input: `{}` must not crash. Missing keys mean empty lists.
- No checks and no sign-offs: approvals is 0, so the reason is present.
- Ties: two verdicts with the same time for one person. The later entry in the list wins.
- Order: the list order of sign-offs must not decide the latest verdict. Only the time does, with ties going to the later entry.
- Types: the `"time"` values are text in the same format. Do not convert them.
- Rounding: the problem has no decimal numbers, so no rounding is needed. Counts are whole numbers.
- Missing fields: a missing `"labels"` key must not crash the label check.
- Rejections: one rejection blocks shipping even when there are approvals.

The solution and its tests are below. The answer is hidden until you click it.

:::answer Solution and tests
The function uses all three techniques from this section. The tests are self-contained and check the edge cases in the checklist.

```python test
def check_release(release):
    checks = release.get("checks", [])
    signoffs = release.get("signoffs", [])
    labels = release.get("labels", [])

    passed = failed = skipped = 0
    failed_names = []
    for check in checks:
        status = check["status"]
        if status == "pass":
            passed += 1
        elif status == "fail":
            failed += 1
            failed_names.append(check["name"])
        elif status == "skip":
            skipped += 1

    latest = {}
    for signoff in signoffs:
        person = signoff["person"]
        current = latest.get(person)
        if current is None or signoff["time"] >= current["time"]:
            latest[person] = signoff

    approvals = sum(1 for s in latest.values() if s["verdict"] == "approve")
    rejected = sorted(p for p, s in latest.items() if s["verdict"] == "reject")

    reasons = [f"check failed: {name}" for name in failed_names]
    if approvals == 0:
        reasons.append("needs at least one approval")
    reasons += [f"rejected by {p}" for p in rejected]
    if "do-not-ship" in labels:
        reasons.append("label do-not-ship is set")

    return {
        "passed": passed,
        "failed": failed,
        "skipped": skipped,
        "approvals": approvals,
        "can_ship": not reasons,
        "reasons": reasons,
    }

release_ok = {
    "checks": [
        {"name": "tests", "status": "pass"},
        {"name": "shellcheck", "status": "pass"},
        {"name": "docs", "status": "skip"},
    ],
    "signoffs": [
        {"person": "ravi", "verdict": "reject", "time": "2026-11-23T10:00"},
        {"person": "ravi", "verdict": "approve", "time": "2026-11-23T12:00"},
        {"person": "meera", "verdict": "approve", "time": "2026-11-23T11:00"},
    ],
    "labels": ["v0.2.0"],
}
assert check_release(release_ok) == {
    "passed": 2, "failed": 0, "skipped": 1, "approvals": 2,
    "can_ship": True, "reasons": [],
}

release_blocked = {
    "checks": [
        {"name": "tests", "status": "fail"},
        {"name": "lint", "status": "pass"},
    ],
    "signoffs": [
        {"person": "ravi", "verdict": "approve", "time": "2026-11-23T09:00"},
        {"person": "ravi", "verdict": "reject", "time": "2026-11-23T10:00"},
    ],
    "labels": ["do-not-ship"],
}
assert check_release(release_blocked) == {
    "passed": 1, "failed": 1, "skipped": 0, "approvals": 0,
    "can_ship": False,
    "reasons": [
        "check failed: tests",
        "needs at least one approval",
        "rejected by ravi",
        "label do-not-ship is set",
    ],
}

assert check_release({}) == {
    "passed": 0, "failed": 0, "skipped": 0, "approvals": 0,
    "can_ship": False, "reasons": ["needs at least one approval"],
}

tie = {
    "signoffs": [
        {"person": "meera", "verdict": "approve", "time": "2026-11-23T11:00"},
        {"person": "meera", "verdict": "reject", "time": "2026-11-23T11:00"},
    ],
}
assert check_release(tie)["reasons"] == [
    "needs at least one approval",
    "rejected by meera",
]

order = {
    "signoffs": [
        {"person": "meera", "verdict": "approve", "time": "2026-11-23T13:00"},
        {"person": "ravi", "verdict": "reject", "time": "2026-11-23T09:00"},
        {"person": "ravi", "verdict": "reject", "time": "2026-11-23T08:00"},
    ],
}
result = check_release(order)
assert result["approvals"] == 1
assert result["reasons"] == ["rejected by ravi"]
assert result["can_ship"] is False
```

**Line-by-line explanation.**

- `def check_release(release):` defines the function. It takes one dictionary.
- `release.get("checks", [])` reads the `"checks"` key. If the key is missing, `get` returns the empty list in the second argument. This handles the missing-fields case without an error.
- The three `get` lines follow the same pattern for sign-offs and labels.
- `passed = failed = skipped = 0` sets three counters to zero in one line.
- The loop over `checks` adds to a counter for each status. `failed_names` keeps the names of failed checks, in input order, for the reasons list.
- `latest = {}` and the next loop keep the latest sign-off per person. `signoff["time"] >= current["time"]` replaces an earlier entry when the new one is at least as late, so the later entry in the list wins a tie.
- `approvals = sum(1 for s in latest.values() if s["verdict"] == "approve")` counts the people whose latest verdict is approval. `latest.values()` gives the kept sign-off for each person.
- `rejected = sorted(...)` lists the people whose latest verdict is rejection, sorted by name so the output is predictable.
- `reasons = [f"check failed: {name}" for name in failed_names]` builds the first group of messages. The `f` before the text makes it an f-string, which puts the value of `name` inside the braces.
- The `if approvals == 0:` line adds the approval message. The `+=` line adds one message for each rejected person.
- `if "do-not-ship" in labels:` checks whether the label is in the list.
- `"can_ship": not reasons` is `True` only when no reason was added.
- The first test covers the normal case: one reject is replaced by a later approve, so two approvals and no reasons.
- The second test checks that a failed check, a rejection and a label each add their own message, in the required order.
- The third test passes an empty dictionary, which proves the missing-keys handling.
- The tie test shows that equal times let the later entry win, which here is the rejection.
- The order test shows that the list order does not decide the latest verdict. Ravi's 08:00 rejection is earlier than his 09:00 one, so the 09:00 entry is kept, and only one rejection reason appears.
- The program prints nothing when every assert passes. A failed assert stops the program with an error that names the line.

**Q1. Why does the team never commit straight to main?**

:::answer Model answer
Main is the line that everyone builds from, so a broken change there stops everyone. Committing on a branch lets a change be tested and reviewed before it lands. Branch protection makes this a rule the server enforces, not a habit people can skip under deadline pressure. The T08 gate tests that a direct push is refused, so this is also checked.
:::

**Q2. When is a rebase safe, and why must you not use one on a branch that others have pulled?**

:::answer Model answer
A rebase is safe when only you use the branch, because it rewrites commit IDs and nobody else holds the old ones. After a rebase, you publish the branch with `--force-with-lease`, which refuses if someone pushed in the meantime. If a teammate has pulled the branch, a rebase leaves their copy pointing at commits that no longer exist on the branch. In that case, merge main into the branch and push normally.
:::

**Q3. What does "Closes #12" do in a pull request?**

:::answer Model answer
It is a closing keyword that GitHub reads from the PR description. When the PR merges into the default branch, GitHub closes Issue #12 automatically. This keeps the project board accurate without a manual step. The keyword only takes effect on merge, so an open PR leaves the Issue open.
:::

**Q4. How do you prove that branch protection works?**

:::answer Model answer
Create an empty commit and try to push it straight to main. GitHub must refuse the push, and the message to look for is "protected branch hook declined". Keep the rejection message as evidence. Then reset the local main to origin's main with `git reset --hard origin/main`, so the test commit does not stay on your machine.
:::

**Q5. How do you choose the next version number after v0.2.0?**

:::answer Model answer
Look at the size of the change. A fix raises the PATCH number, so v0.2.1. A new feature that stays compatible raises the MINOR number, so v0.3.0. A breaking change raises MAJOR, but before version 1.0.0 the course rule is that a new feature still raises MINOR. The number tells users how much they need to check before upgrading.
:::

## Flashcards

```cards
branch :: A movable name that points at a line of commits; new work on it moves the name forward.
pull request :: A request to merge one branch into another, with the diff, discussion and checks in one place.
rebase :: Replays your commits on top of a newer base, giving them new IDs; safe only when no one else has pulled the branch.
--force-with-lease :: A force push that refuses if someone has pushed to the remote branch since your last fetch.
branch protection :: A GitHub rule that blocks direct pushes to a branch and requires an approval before merge.
enforce_admins :: The protection setting that applies the rule to administrators as well.
Closes #12 :: A PR description keyword that closes Issue #12 automatically when the PR merges.
annotated tag :: A tag that stores the author, date and message, created with git tag -a.
semantic version :: MAJOR.MINOR.PATCH: breaking change, new feature, fix.
fork :: Your own copy of someone else's repository on GitHub, used to contribute without write access.
three-dot diff :: git diff main...branch shows only the branch's own changes since it split from main.
squash merge :: Combines all of a PR's commits into one commit on main with gh pr merge --squash.
```
