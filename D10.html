The idea in one minute

CityPulse stores every air-quality reading as one row in a database table. Clients ask questions about those rows: "Which hour of the day is worst for PM2.5 at each location?" or "What is the smoothed pollution trend at each station?" SQL is the language you use to ask. Think of it as a written request to a records clerk who knows where every file is. You say what you want, and the clerk returns a table of answers.

Today you will join tables together, name intermediate steps, save a query as a view, and use window functions to calculate rolling averages and changes over time. You will run each query from the terminal and check the output by hand.

Starting from zero

This section explains the words the rest of the chapter depends on.

Terminal. The terminal is a text window where you type commands and the computer prints the answer. Every command you type is a single line, and you press Enter to run it.

Command. A command is an instruction you type into the terminal, such as sqlite3. The first word is the program name. The words after it are arguments, which tell the program what to work on.

File. A file is a named piece of stored text or data on your disk. The SQL files in this chapter end in .sql. The .sql part is only a convention that tells people and tools the file holds SQL.

Database. A database is a file that stores structured data in a form a program can query. CityPulse uses SQLite, which keeps the whole database in one file called citypulse.db. SQLite is a small database engine, and sqlite3 is the program you run to talk to it.

Table. A table is a grid of data with named columns and numbered rows. A table called reading might have the columns station_id, ts and value.

Row and column. A row is one record, such as one reading. A column is one kind of value stored for every row, such as the time of the reading.

SQL. SQL stands for Structured Query Language. It is the language for asking databases questions. You write statements such as SELECT, which asks for rows, and CREATE TABLE, which makes a new table.

Query. A query is one SQL statement that asks the database for data. The answer comes back as a result table.

Keyword. A keyword is a word with a fixed meaning in SQL, such as SELECT, FROM, WHERE and GROUP BY. Keywords are not case-sensitive, but the convention is to write them in capitals so you can see where each clause starts.

Function. A function takes values in and gives one value back. ROUND(x, 1) takes a number and returns it rounded to one decimal place. AVG(x) is an aggregate function: it takes many rows and returns one average.

Alias. An alias is a temporary name you give a column or table with AS. ROUND(AVG(value), 1) AS avg_value shows the result under the name avg_value. An alias is also used for tables, as in FROM fact_air_quality AS f, which lets you write f.pm2_5 instead of the full name.

NULL. NULL means "no value recorded". It is not zero and it is not an empty string. A sensor that failed to report has a NULL reading. Most functions ignore NULL, and comparisons such as value = NULL never match.

GROUP BY. GROUP BY collects rows that share a value into one group, and an aggregate function such as COUNT(*) then works per group. Ten readings for one station become one summary row.

Subquery. A subquery is a complete SELECT placed inside another query, usually inside brackets. The outer query then treats the subquery's result as if it were a table.

Timestamp and time zones. A timestamp is a date and time, such as 2026-03-01 08:00:00. UTC is the world reference time. IST, Indian Standard Time, is UTC plus five hours and thirty minutes. CityPulse stores times in UTC and converts them to IST for reports. The number of minutes to add is written as +330 minutes.

Sample size. The number of readings behind an average. An average from 1 reading is much less reliable than an average from 500, so the answers in this course carry the count alongside the value.

The tools

Today has three technologies: JOINs with CTEs, views, and window functions. All three run inside SQLite.

JOINs and CTEs

What it is. A JOIN combines rows from two tables where a condition matches. CityPulse stores the readings in fact_air_quality and the location names in dim_location. The reading table holds location_id, a number, while the names live in the other table. A JOIN matches the two using that number.

A CTE is a named intermediate result, written with WITH. It lets a long query read as a sequence of named steps. The keyword WITH introduces the CTE, the name comes next, and the body is a SELECT in brackets.

Why CityPulse uses it. Every question about a location needs its name, so the readings must be joined to the location table. A CTE lets you calculate something once, such as the IST hour, and then aggregate it. The slides compare JOINs with nested subqueries, joins in pandas and a single wide table. Nested subqueries give the same result but are hard to review line by line. Pandas joins are fine for one-off analysis, but a SQL view keeps the answer inside the database, where the dashboard and the API can read it. A wide table avoids joins but gives up the integrity rules built in the earlier days.

How it works. The database takes each row of the fact table, finds the matching row in the location table by the integer key, and forms one combined row. Rows with no match are dropped in an inner JOIN. A LEFT JOIN keeps every row from the left table even when nothing matches on the right.

The slide code, line by line. This is the worst-hour query from the slides, with the indentation restored:

WITH hourly AS (
  SELECT l.name AS location,
         CAST(strftime('%H', f.ts_utc, '+330 minutes') AS INTEGER) AS hour_ist,
         f.pm2_5
  FROM fact_air_quality AS f
  JOIN dim_location AS l ON l.location_id = f.location_id
  WHERE f.pm2_5 IS NOT NULL
)
SELECT location, hour_ist, ROUND(AVG(pm2_5), 1) AS avg_pm25,
       COUNT(*) AS n
FROM hourly
GROUP BY location, hour_ist
ORDER BY avg_pm25 DESC
LIMIT 5;
  • WITH hourly AS ( starts a named step called hourly. The brackets hold its query.
  • SELECT l.name AS location picks the name from the location table and calls it location. The l. prefix says which table the column comes from.
  • strftime('%H', f.ts_utc, '+330 minutes') takes the timestamp, adds 330 minutes, and returns only the hour as text, such as '08'. The %H is the format code for a two-digit hour.
  • CAST(... AS INTEGER) turns the text '08' into the number 8, so that hours sort as numbers.
  • f.pm2_5 passes the PM2.5 value through unchanged.
  • FROM fact_air_quality AS f names the fact table and calls it f.
  • JOIN dim_location AS l ON l.location_id = f.location_id matches each reading to its location using the integer key. The ON part is the matching condition.
  • WHERE f.pm2_5 IS NOT NULL drops readings where the sensor reported nothing. You use IS NOT NULL, not != NULL, because NULL never equals anything.
  • The ) closes the CTE. The outer SELECT then works on hourly as if it were a table.
  • GROUP BY location, hour_ist makes one group per location and hour.
  • AVG(pm2_5) averages the PM2.5 values in each group. ROUND(..., 1) keeps one decimal place.
  • COUNT(*) counts the rows in each group and is the sample size n.
  • ORDER BY avg_pm25 DESC sorts the highest averages first. DESC means descending.
  • LIMIT 5 returns only the first five rows.

The expected output is five rows, each showing a location, an IST hour, an average and a count. The exact numbers depend on the data loaded.

The slides also show a LEFT JOIN used for a coverage check. In FROM dim_location AS l LEFT JOIN fact_air_quality AS f ON f.location_id = l.location_id, every location appears even if it has no readings. The unmatched columns from the fact table are filled with NULL.

Trap: Filtering the right table in WHERE

If you filter the right-hand table of a LEFT JOIN in WHERE, the rows with no match are removed and the LEFT JOIN quietly becomes an inner JOIN. Put the condition on the right-hand table in the ON clause instead.

Trap: Grouping by UTC hour

Grouping by the raw UTC hour gives the wrong "rush hour". Add '+330 minutes' before you extract the hour, as the query above does.

Trap: Joining on the name

Joining on name instead of location_id breaks when a name is spelled differently or changed. Join on the integer key.

Views

What it is. A view is a named SELECT stored in the database. You create it once with CREATE VIEW. Later, when you query the view, SQLite runs the stored SELECT on the current data. No copy of the rows is kept, so the answer stays up to date.

Why CityPulse uses it. Views turn one-off queries into an interface other parts of the system can reuse. The Y2-T14 ticket asks for eight named views beginning with v_. The defence, the dashboard and the API will all call those names. The slides compare views with three alternatives. Materialised summary tables are faster to read but must be refreshed and can go stale, and SQLite has no materialised views. Queries saved in a notebook are easy to run once but the dashboard cannot call them. Queries hard-coded in Python couple the SQL to the application code and hide it from SQL review.

How it works. A view is stored as text. When you query it, SQLite expands the stored SELECT and runs it as part of your query. Because the file sql/views.sql contains every view, it is the single source of truth for them.

The slide code, line by line. This is v_coverage_by_location from the slides:

-- Q: How many readings does each location have per IST day?
-- Who decides: ops lead decides which stations' numbers to trust.
-- IST: ts_utc + 330 minutes.
DROP VIEW IF EXISTS v_coverage_by_location;
CREATE VIEW v_coverage_by_location AS
SELECT l.name                          AS location,
       date(f.ts_utc, '+330 minutes')  AS day_ist,
       COUNT(f.fact_id)                AS n_readings
FROM dim_location AS l
LEFT JOIN fact_air_quality AS f ON f.location_id = l.location_id
GROUP BY l.name, day_ist;
-- check: SELECT * FROM v_coverage_by_location ORDER BY day_ist DESC LIMIT 5;
  • Lines beginning with -- are comments. SQLite ignores them. The comments state the client question, who relies on the answer, and the time zone rule. Writing them down is part of the deliverable.
  • DROP VIEW IF EXISTS v_coverage_by_location; deletes the view if it already exists, and does nothing if it does not. This is what lets the whole file run again without an error.
  • CREATE VIEW v_coverage_by_location AS creates the view with that name. Everything after AS is the stored query.
  • date(f.ts_utc, '+330 minutes') adds 330 minutes to the UTC timestamp and returns only the date. That is the IST day.
  • COUNT(f.fact_id) counts the non-NULL fact IDs in each group. For a location with no readings, the unmatched fact columns are NULL, so this count is 0.
  • FROM dim_location AS l LEFT JOIN fact_air_quality AS f keeps every location, so locations with no data still appear.
  • GROUP BY l.name, day_ist makes one row per location and IST day. The alias day_ist may be used here because SQLite accepts column aliases in GROUP BY.
  • The final comment is a check you can run after creating the view. It shows the five most recent days.

The expected result of the check is up to five rows, each with a location, a day and a count. If a location with no data appears with n_readings equal to 0, the view is correct.

Trap: CREATE VIEW without DROP

CREATE VIEW without DROP VIEW IF EXISTS works the first time and fails the second time, because the view already exists. Always write the two as a pair.

Trap: COUNT(*) in a LEFT JOIN

COUNT(*) counts the row itself, even when the row has no match. A location with no readings would show 1, which is wrong. Count a column from the right-hand table, such as COUNT(f.fact_id), which counts only real matches.

Trap: Views over views

A view built on another view built on another view can get slow. Run EXPLAIN QUERY PLAN on the slowest one. If the output says SCAN on a large table, an index may help. If it says SEARCH using an index, leave it alone.

Window functions

What it is. A window function calculates a value for each row by looking at a set of related rows. Unlike GROUP BY, it does not collapse the rows. Every reading keeps its own line in the output and gains an extra column.

A window function has three parts. OVER introduces it. PARTITION BY splits the rows into separate groups, one per location in CityPulse. ORDER BY sets the sequence of rows inside each group, usually time. A frame such as ROWS BETWEEN 23 PRECEDING AND CURRENT ROW then limits which rows are considered for each row.

Why CityPulse uses it. Health officers care about sustained exposure, measured as a 24-hour average, rather than single spikes. The Y2-T15 ticket needs a rolling 24-hour view and a day-over-day change view. The slides also note that the reference used to check the Python algorithm in a later ticket (Y2-T21) is a SQL rolling average of 6 hours. The slides compare window functions with self-joins on time ranges, which work but are verbose and slow on large tables, with pandas rolling(), which is great in a notebook but not available to every consumer, and with RANGE time windows, which handle gaps in time better but are harder to write. The team chose ROWS for the reference, and documents that choice.

How it works. For each reading, SQLite gathers the rows of the same partition, sorts them by time, keeps only the rows in the frame, and computes the aggregate. For the first few rows, the frame contains fewer rows than the full size. This is why a rolling average at the start of a series is based on fewer readings.

Trap: Forgetting PARTITION BY

Without PARTITION BY station_id, the window runs across all stations in one long sequence. The last reading of S1 and the first reading of S2 would be averaged together. Always partition by the station.

Trap: ROWS counts rows, not hours

ROWS counts rows. If a sensor misses two hours, ROWS BETWEEN 23 PRECEDING AND CURRENT ROW reaches back over 26 clock hours, not 24. The slides therefore expose n_in_window, the count of readings in the window, so that a short window can be seen.

Trap: psql in older examples

Some examples in the reading show psql. That is the client for PostgreSQL, a different database. This course uses sqlite3 and the citypulse.db file. The SQL is close, but the commands are not interchangeable.

The worked example

The worked example uses the course's 11-row sample. It has two stations, S1 and S2. S1 has five PM2.5 readings and one NO2 set of three readings. S2 has three PM2.5 readings. Times are stored in UTC.

The goal is to show why GROUP BY is not enough for a trend, and then to add a rolling average without losing a row.

Step 1. Load the table. The schema is a single CREATE TABLE. The first command creates the table and the second inserts the sample rows:

sqlite3 citypulse.db < schema.sql
sqlite3 citypulse.db < load.sql

The schema defines the table reading with four columns: station_id as text, ts as text holding an ISO timestamp, pollutant as text, and value as a real number, measured in micrograms per cubic metre.

Step 2. Collapse with GROUP BY. The query below averages each station and pollutant:

SELECT station_id, pollutant,
       ROUND(AVG(value), 1) AS avg_value,
       COUNT(*) AS n
FROM reading
GROUP BY station_id, pollutant
ORDER BY station_id, pollutant;

The output has three rows:

station_id pollutant avg_value n
---------- --------- --------- -
S1         no2       21.7      3
S1         pm25      50.2      5
S2         pm25      33.0      3

The average for S1 PM2.5 is 50.2, which is the mean of 40, 44, 52, 60 and 55 (251 divided by 5). The eleven original rows have gone. You can answer "what is the average?" but not "how did the air change hour by hour?"

Step 3. Keep the rows with a window. Replace GROUP BY with a window function:

SELECT station_id, ts, value,
       ROUND(AVG(value) OVER (
         PARTITION BY station_id, pollutant
         ORDER BY ts
         ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
       ), 1) AS ma3
FROM reading
WHERE pollutant = 'pm25'
ORDER BY station_id, ts;

The output keeps every reading. For S1 the column ma3 reads 40.0, 42.0, 45.3, 52.0 and 55.7. The 45.3 is the average of 40, 44 and 52. The 52.0 is the average of 44, 52 and 60. The 55.7 is the average of 52, 60 and 55, rounded to one decimal place.

Step 4. Compare the bounded window with a running average. The frame changes the answer. The query below puts a three-row window beside a cumulative average over the whole partition:

SELECT ts, value,
       ROUND(AVG(value) OVER w3, 1) AS ma3,
       ROUND(AVG(value) OVER wall, 1) AS cum_avg
FROM reading
WHERE pollutant = 'pm25' AND station_id = 'S1'
WINDOW w3 AS (ORDER BY ts ROWS BETWEEN 2 PRECEDING AND CURRENT ROW),
       wall AS (ORDER BY ts)
ORDER BY ts;

The first three rows of ma3 and cum_avg are identical. From the fourth row, cum_avg lags behind the recent air, because it still carries the early, lower readings. In the output at 12:00, ma3 is 55.7 and cum_avg is 50.2.

WINDOW w3 AS (...) gives the window a name. The name is used in OVER w3. The second window, wall, has no frame, so it covers all rows from the start up to the current row. The comma separates the two named windows.

Step 5. Rank and compare with LAG. The query below calculates the change from the previous hour and a rank of each reading inside its station:

SELECT station_id, ts, value,
       value - LAG(value) OVER w AS delta,
       RANK() OVER (PARTITION BY station_id ORDER BY value DESC) AS rnk
FROM reading
WHERE pollutant = 'pm25'
WINDOW w AS (PARTITION BY station_id ORDER BY ts)
ORDER BY station_id, ts;

For S1 at 11:00 the rank is 1 because 60.0 is the highest reading. The delta is 8.0 because 60.0 minus the previous value 52.0 is 8.0. The first row of each station has an empty delta because there is no earlier row to subtract. In SQLite, the empty cell is NULL.

Step 6. Filter on the rank. You cannot write WHERE rnk = 1 in the same query, because WHERE runs before window functions are calculated. Wrap the ranked query in a subquery:

SELECT station_id, ts, value
FROM (
  SELECT station_id, ts, value,
         RANK() OVER (PARTITION BY station_id ORDER BY value DESC) AS rnk
  FROM reading
  WHERE pollutant = 'pm25'
)
WHERE rnk = 1
ORDER BY station_id;

The output has two rows: S1 at 11:00 with 60.0, and S2 at 09:00 with 36.0. These are the peak readings per station.

The hands-on lab, step by step

The lab has seven steps. Do them in order, because each step uses the table or the query from the step before. Run every command from the folder that holds citypulse.db and your .sql files. To open that folder in the terminal, use the file manager's address bar or the cd command followed by the folder path.

Step 1. Load a richer readings sample

What you do. Create the reading table and load the sample rows. If your instructor gives you a richer set of readings that spans several days, load that instead. The rest of the steps do not change, but the day-over-day changes in step 5 only show something when the data covers more than one day.

What you type.

sqlite3 citypulse.db < schema.sql
sqlite3 citypulse.db < load.sql
sqlite3 citypulse.db "SELECT COUNT(*) FROM reading;"

What you should see. The last command prints one number, 11, for the course sample.

How you know it worked. The count matches the number of INSERT rows in load.sql. If the count is 0, the second command did not run, or it ran against a different file. If you see "no such table: reading", run the schema file first.

Step 2. Order within each station

What you do. Read the PM2.5 readings in time order within each station, so that you can see the sequence the window functions will use.

What you type.

SELECT station_id, ts, value
FROM reading
WHERE pollutant = 'pm25'
ORDER BY station_id, ts;

What you should see. Eight rows. All the S1 rows come first, in time order from 08:00 to 12:00, then the S2 rows from 08:00.

How you know it worked. ORDER BY station_id, ts sorts by station first, and by time inside each station. If the S2 rows appear before S1, or the times are out of order, check that you typed station_id, ts in that order.

Step 3. Compute a 3-point rolling average

What you do. Add a rolling average over the current reading and the two before it, inside each station.

What you type. Use the query from the worked example, step 3. Save it as rolling.sql and run it with sqlite3 -header -column citypulse.db < rolling.sql.

What you should see. S1 at 08:00 has ma3 equal to 40.0, at 09:00 equal to 42.0, at 10:00 equal to 45.3, and at 11:00 equal to 52.0.

How you know it worked. The first row of each station equals its own value, because the window contains only that row. The S2 values start again at 08:00, which shows the partition is working.

Step 4. Period-over-period change with LAG

What you do. Calculate the change from the previous reading in each station. This is the period-over-period change for hourly data. The same pattern on daily averages gives day-over-day change.

What you type.

SELECT station_id, ts, value,
       value - LAG(value) OVER (PARTITION BY station_id ORDER BY ts) AS delta
FROM reading
WHERE pollutant = 'pm25'
ORDER BY station_id, ts;

What you should see. S1 at 08:00 has an empty delta. S1 at 09:00 has 4.0, at 10:00 has 8.0, at 11:00 has 8.0, and at 12:00 has -5.0. S2 at 08:00 is empty and S2 at 09:00 has 6.0.

How you know it worked. The first row of each station is empty, because LAG has no earlier row to read. The 12:00 value is negative because the reading fell from 60.0 to 55.0.

Step 5. Daily averages per station

What you do. Average the readings for each station on each day. The day must be the IST day, so add 330 minutes before taking the date.

What you type.

SELECT station_id,
       date(ts, '+330 minutes') AS day_ist,
       ROUND(AVG(value), 1) AS avg_value,
       COUNT(*) AS n
FROM reading
WHERE pollutant = 'pm25'
GROUP BY station_id, day_ist
ORDER BY station_id, day_ist;

What you should see. Two rows for the course sample: S1 on 2026-03-01 with average 50.2 and count 5, and S2 on 2026-03-01 with average 33.0 and count 3.

How you know it worked. The count column adds up to the number of PM2.5 rows in step 2, which is 8. If you grouped by date(ts) without the 330 minutes, the answer may look correct for this sample, but it breaks for readings made after 18:30 UTC, which fall on the next IST day.

Step 6. Rank the most-polluted stations per pollutant

What you do. Average each station per pollutant, then rank the stations within each pollutant. Window functions run after GROUP BY, so the aggregate can be the input to the rank.

What you type.

SELECT pollutant, station_id,
       ROUND(avg_value, 1) AS avg_rounded,
       RANK() OVER (PARTITION BY pollutant ORDER BY avg_value DESC) AS rnk
FROM (
  SELECT station_id, pollutant, AVG(value) AS avg_value
  FROM reading
  GROUP BY station_id, pollutant
)
ORDER BY pollutant, rnk;

What you should see. Three rows. For no2, S1 with 21.7 and rank 1. For pm25, S1 with 50.2 and rank 1, then S2 with 33.0 and rank 2.

How you know it worked. Each pollutant restarts its rank at 1. The rank is calculated on the unrounded average, and rounding is applied only to the displayed value, which is good practice.

Step 7. Keep only the worst per pollutant

What you do. Wrap the ranked query from step 6 in an outer query and keep only rank 1.

What you type.

SELECT pollutant, station_id, avg_rounded
FROM (
  SELECT pollutant, station_id,
         ROUND(avg_value, 1) AS avg_rounded,
         RANK() OVER (PARTITION BY pollutant ORDER BY avg_value DESC) AS rnk
  FROM (
    SELECT station_id, pollutant, AVG(value) AS avg_value
    FROM reading
    GROUP BY station_id, pollutant
  )
)
WHERE rnk = 1
ORDER BY pollutant;

What you should see. Two rows: no2 at S1 with 21.7, and pm25 at S1 with 50.2.

How you know it worked. Only one row per pollutant is returned. If you see S2 in the output, the filter WHERE rnk = 1 is missing or misplaced. Check that it sits in the outer query, after the closing bracket of the subquery.

Window frames

What it is. A window function calculates a value using a set of rows around the current row. That set is called the frame. The frame is written inside OVER (...), after the ORDER BY. Here is a small example:

SELECT ts, value,
       AVG(value) OVER (ORDER BY ts ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS ma3
FROM reading;

ROWS BETWEEN 2 PRECEDING AND CURRENT ROW means the current row and the two rows before it. The count is by position in the order, not by clock time. Suppose the values in time order are 10, 20, 30 and 40. The first row has only itself, so ma3 is 10.0. The second row averages 10 and 20 to give 15.0. The third row averages 10, 20 and 30 to give 20.0. The fourth row averages 20, 30 and 40 to give 30.0. The output column therefore reads 10.0, 15.0, 20.0 and 30.0.

SQLite does not stop the calculation at the start of the series. It averages the rows that exist. That is why the early values in a rolling column rest on fewer readings than the later ones.

The frame is separate from the partition. PARTITION BY decides which groups of rows exist, so that one station never mixes with another. The frame decides how many neighbours each row sees inside its group. If you change the frame, every rolling number changes, even though the query still runs without an error.

How it shows up in a case study. The CityPulse team at a city council is checking a dashboard for station S3. The dashboard shows a "three-hour smoothed" PM2.5 value. Four hourly readings are 42, 47, 51 and 49. The query uses ROWS BETWEEN 3 PRECEDING AND CURRENT ROW. The team reads this as a three-hour window, but the frame holds four rows: the current row and three before it. The fourth row therefore averages all four values to give 47.25, not the three-hour average of 49.0. The decision is to change the frame to 2 PRECEDING, which holds exactly three rows. The reasoning is to count the current row first and then count back. The number after PRECEDING is one less than the number of rows you want.

Trap: Frame and partition are different jobs

Writing PARTITION BY station_id and expecting it to limit the window to three rows is a common mistake. The partition only separates the stations. Without a frame, a window with an ORDER BY uses the default frame, which runs from the first row up to the current row, so the window keeps growing. Keep the two ideas apart: the partition chooses the group, and the frame chooses the neighbours.

Ranking functions

What it is. Three window functions number the rows inside a partition: ROW_NUMBER(), RANK() and DENSE_RANK(). They differ only when two rows tie, which means their ORDER BY values are equal. Take three rows ordered by value, highest first, with values 80, 80 and 60:

value  row_number  rank  dense_rank
80     1           1     1
80     2           1     1
60     3           3     2

ROW_NUMBER() gives every row its own number. When values tie, the numbers 1 and 2 go to the tied rows in an order SQLite chooses, unless the ORDER BY has a tie-breaker. RANK() gives tied rows the same number and then skips the next number, so the 60 is third. DENSE_RANK() gives tied rows the same number and does not skip, so the 60 is second. All three keep every row, which is what makes them window functions.

To choose between them, ask one question: do you need unique numbers, a league where a tie shares a place and the next place is numbered with a gap, or a league with no gaps at all?

How it shows up in a case study. A city publishes a league table of stations by their daily peak PM2.5. Two stations tie at 92, and a third station has 85. The printed sheet needs a unique line number for every station, so the team uses ROW_NUMBER() and breaks the tie by station name. The public league must say that the 85 station is in second place after the tie, not third. The team uses DENSE_RANK() for that column. The reasoning is to ask what the number means to a reader: a line on a sheet, or a place in a league.

Trap: Reading RANK as a row count

RANK() skips numbers after a tie, so a result of 1, 1, 3 can look as if a row is missing. No row is missing. DENSE_RANK() would give 1, 1, 2. Choose the function by the meaning the question asks for, not by which output looks tidier.

LAG and LEAD

What it is. LAG(value) returns the value from the previous row in the same partition. LEAD(value) returns the value from the next row. The simplest use is one row back or one row forward, and both can take an optional offset and default. Here is a change calculation:

SELECT ts, value,
       value - LAG(value) OVER (ORDER BY ts) AS change
FROM reading;

Suppose the values in time order are 30, 36 and 33. The first row has no earlier row, so LAG returns NULL and the change is NULL. The second row gives 36 minus 30, which is 6. The third row gives 33 minus 36, which is -3. The output column reads NULL, 6 and -3.

Two points matter. The first row of each partition has no previous row, so its result is NULL, which SQLite prints as an empty cell. The sign of a change depends on the order of the subtraction. value - LAG(value) is the current value minus the earlier one, which is the usual change over time. LAG(value) - value has the same size with the opposite sign. LEAD looks forward, so it answers the question "what comes next?", and it is the wrong tool for a change from the previous period.

How it shows up in a case study. A health officer receives daily averages for station S7: 40.0 on Monday, 46.0 on Tuesday and 43.0 on Wednesday. The officer asks whether conditions got worse on Wednesday. The right expression reads the previous day, which is Tuesday's 46.0. The change is 43.0 minus 46.0, which is -3.0, so the air improved. A query that uses LEAD would look at Thursday, which is not in the data, and returns NULL. The reasoning is to ask which row comes before the current one, then subtract in the order that matches the question: current minus previous.

Trap: Reversing the subtraction

LAG(value) - value gives the right size of change with the wrong sign, so a fall in pollution looks like a rise. LEAD answers a different question, because it looks forward. Check the sign with a row you can work out by hand before you trust the column.

Window functions versus GROUP BY

What it is. GROUP BY collapses the rows that share a value into one row per group. A window function keeps every row and adds a column calculated from related rows. Compare two queries on the same table, which holds two readings for S1 and one reading for S2:

SELECT station_id, AVG(value) AS station_avg
FROM reading
GROUP BY station_id;

SELECT station_id, value,
       AVG(value) OVER (PARTITION BY station_id) AS station_avg
FROM reading;

If S1's readings are 40 and 60, and S2's reading is 30, the first query returns two rows: 50.0 for S1 and 30.0 for S2. The second query returns all three rows, with S1's average repeated beside each S1 reading: 40 with 50.0, 60 with 50.0, and 30 with 30.0. The readings are still there.

The window version puts an aggregate such as AVG, COUNT or MAX inside OVER. It does not need a GROUP BY. Because the window works row by row, you can show the reading and its group's summary side by side.

How it shows up in a case study. A city analyst is asked to show each reading beside its station's average, so that a reader can see which readings sit above the usual level. She writes GROUP BY station_id first, and the query returns three rows, one per station, so the individual readings have gone. The fix is the window version, which keeps every reading. The reasoning is to ask whether the question needs the individual readings or only a summary. If it needs the readings, the answer is a window function.

Trap: Bare columns after GROUP BY

If you write GROUP BY station_id and then list value without an aggregate, SQLite does not stop you. It returns the value of one arbitrary reading in each group, so the output looks valid and is wrong. Use a window function when you need every reading.

Top N per group

What it is. A top-N-per-group query keeps the best N rows inside each group, not the best N rows overall. The standard method has two steps. An inner query numbers the rows in each group with ROW_NUMBER(). An outer query keeps the rows whose number is at most N. Here is the shape, using a table of charging sessions:

SELECT zone, point, sessions
FROM (
  SELECT zone, point, sessions,
         ROW_NUMBER() OVER (PARTITION BY zone ORDER BY sessions DESC, point ASC) AS rn
  FROM charge
)
WHERE rn <= 2
ORDER BY zone, rn;

Suppose zone North has point A with 30 sessions, point B with 45 and point C with 20. The inner query numbers B as 1, A as 2 and C as 3. The outer query keeps B and A. The other zones are numbered in the same way, from their own rows, so the output has at most two rows per zone.

The tie-breaker point ASC makes the result repeatable. Without it, two points with the same number of sessions can swap places from one run to the next.

How it shows up in a case study. The city wants the two busiest charging points in each of four zones for a monthly report. An engineer proposes ORDER BY sessions DESC with LIMIT 8, reasoning that eight is two times four. The team checks the table and finds that one zone holds most of the busy points, so all eight rows come from that zone. The correct design numbers the points inside each zone and keeps two per zone. The reasoning is that the number of rows per group must come from a partition, not from a total you guess.

Trap: LIMIT on the whole table

ORDER BY ... LIMIT 8 returns the eight highest rows across all zones. It does not return two per zone, and the answer changes whenever the busy zone changes. Numbering the rows per group in a subquery is the fix.

The default frame

What it is. A window with an ORDER BY and no frame clause uses a default frame. In SQLite that default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. Read it as "from the first row of the partition up to the current row, and include every row that ties with the current row on the ORDER BY value". Rows that tie in this way are called peers.

SELECT ts, value,
       SUM(value) OVER (ORDER BY ts) AS running_total
FROM reading;

Suppose two readings share the timestamp 08:00 with values 10 and 20, and a third reading at 09:00 has the value 30. The two 08:00 rows are peers, so each one includes both values and shows 30. The 09:00 row includes everything above it and shows 60. The output column reads 30, 30 and 60, not 10, 30 and 60.

This matters whenever you want one line per reading with its own running total. If the order of tied rows should decide the result, you must ask for it explicitly with ROWS and add a tie-breaker to the ORDER BY.

How it shows up in a case study. A dashboard shows a cumulative count of PM2.5 alerts for each station. Two sensors at one station report at the same minute, and the count jumps by two on that line. The team first thinks the data is wrong. It is not: the default frame treats the two tied rows as peers. If the team wants a count that rises by one per reading, it must write ROWS with a tie-breaker. The reasoning is to ask whether the number should be shared by tied rows or separate for each row.

Trap: Peers share one running value

With the default RANGE frame, tied rows share one running total, so a running total can jump by two at a single timestamp. This is correct SQL behaviour, not a fault in the data. If you want a true row-by-row total, write ROWS and add a tie-breaker to ORDER BY.

Percentiles

What it is. Two window functions turn a row's position into a value between 0 and 1. PERCENT_RANK() gives (rank minus 1) divided by (the number of rows minus 1). CUME_DIST() gives the number of rows at or below the current row, divided by the number of rows. Here are four values in order: 10, 20, 30 and 40.

SELECT value,
       ROUND(PERCENT_RANK() OVER (ORDER BY value), 2) AS pr,
       ROUND(CUME_DIST() OVER (ORDER BY value), 2) AS cd
FROM reading;

The output is:

value  pr    cd
10     0.00  0.25
20     0.33  0.50
30     0.67  0.75
40     1.00  1.00

For PERCENT_RANK, the lowest row gets 0 and the highest gets 1. For CUME_DIST, the lowest row gets one quarter, because one of four rows is at or below it, and the highest gets 1. Both are measures on a 0 to 1 scale, but they answer different questions. PERCENT_RANK is a position between the two ends. CUME_DIST is a share of all the rows.

How it shows up in a case study. A city has fifty stations. The officer wants a public figure for each station that answers the question "what share of stations are at or below this station's PM2.5?" The lowest station should show 0.02, because one of fifty stations is at or below it. CUME_DIST gives that result. PERCENT_RANK would show 0.0 for the lowest station, which is a position and not the share the report asks for. The reasoning is to read the question as a share of rows, not as a place between the ends.

Trap: Confusing the two measures

PERCENT_RANK gives the lowest row 0.0, while CUME_DIST gives it one divided by the number of rows. The two differ by one row at the bottom of the scale, which is enough to change a public figure. Name the measure your report needs before you choose the function.

RANGE and INTERVAL frames

What it is. A RANGE frame defines the window by the value in the ORDER BY column, not by the number of rows. In SQLite the ORDER BY column must be a single number, such as Unix epoch seconds, and the offset is a plain number in the same unit. RANGE BETWEEN 3600 PRECEDING AND CURRENT ROW means every reading whose time is no more than 3600 seconds before the current reading, plus the current reading itself.

SELECT ts, value,
       AVG(value) OVER (ORDER BY ts RANGE BETWEEN 3600 PRECEDING AND CURRENT ROW) AS hour_avg
FROM reading;

Suppose three readings have times 0, 1800 and 5400 seconds, with values 10, 20 and 30. The first reading's frame holds only itself, so hour_avg is 10.0. The second reading's frame reaches back to 1800 seconds before its time, which is -1800, and holds both the first and second readings, so the average is 15.0. The third reading's frame starts at 5400 minus 3600, which is 1800, so it holds the second and third readings, and the average is 25.0. The output reads 10.0, 15.0 and 25.0.

A ROWS frame counts rows and ignores the gaps between them. A RANGE frame counts time, so a missing reading does not stretch the window. SQLite does not accept the INTERVAL keyword in a frame, so the time must be stored as a number.

How it shows up in a case study. A sensor at one station reports irregularly, sometimes after two hours and sometimes after ten minutes. The team wants a rolling one-hour average. A ROWS frame of four readings would cover different spans of time depending on the gaps. A RANGE frame over epoch seconds covers exactly one hour each time. The reasoning is to ask whether the window should be measured in readings or in time. The course uses ROWS for its reference, but when the window must be an exact span of time, RANGE with a number is the right tool.

Trap: Copying an INTERVAL frame

A frame such as RANGE BETWEEN INTERVAL '1 hour' PRECEDING AND CURRENT ROW comes from other databases. SQLite does not accept it, so the statement fails. Store time as a number, such as epoch seconds, and use 3600 for one hour.

NTILE buckets

What it is. NTILE(n) divides the rows of a partition into n buckets and returns the bucket number, from 1 to n, for each row. The rows are taken in the order of the ORDER BY. If the rows do not divide evenly, the first buckets each receive one extra row. Here are seven values in order.

SELECT value,
       NTILE(3) OVER (ORDER BY value) AS bucket
FROM reading;

With the values 4, 5, 6, 8, 9, 11 and 12, the output is:

value  bucket
4      1
5      1
6      1
8      2
9      2
11     3
12     3

Seven rows over three buckets gives a base size of two with one row left over. The first bucket takes the extra row, so the sizes are three, two and two. The bucket number is a label for the group, not a measurement that you can average. To compare the groups, count the rows in each bucket with GROUP BY on the bucket number.

How it shows up in a case study. A city ranks its ten stations into four bands by average PM2.5 for a league report. The report says each band holds two or three stations, so the team checks the bucket sizes. Ten over four gives a base of two with two left over, so the sizes are three, three, two and two. The reasoning is that buckets are as equal as whole rows allow, not that every bucket holds the same count. Band 1 holds the cleanest stations only if the ORDER BY is ascending.

Trap: Assuming equal buckets

NTILE does not make every bucket the same size. Ten rows in four buckets gives 3, 3, 2 and 2, so the first buckets are the larger ones. The bucket number is also a label for the group, not a value that you can average.

Clause evaluation order

What it is. SQL works through a query in a fixed order, which is not the order in which you write the clauses. In a typical query, the database first reads the tables named in FROM and JOIN, then applies WHERE, then GROUP BY, then HAVING. Window functions in the SELECT list are calculated after those steps. ORDER BY comes after the windows, and LIMIT comes last. A small query shows the effect:

SELECT station_id, value,
       ROW_NUMBER() OVER (ORDER BY value DESC) AS rn
FROM reading
WHERE pollutant = 'pm25';

The WHERE clause removes the NO2 rows before ROW_NUMBER is calculated, so the numbers run over PM2.5 readings only. If you moved the pollutant filter into an outer query, the window would number both pollutants first. The outer filter would then remove the NO2 rows from a numbering that already counted them, and the PM2.5 numbers would be wrong.

Because the windows come after WHERE, you cannot use a window alias such as rn in the WHERE clause of the same query.

How it shows up in a case study. An analyst wants a rolling three-reading average of PM2.5 only. She writes the window in a subquery with no pollutant filter, then adds WHERE pollutant = 'pm25' in the outer query. The averages near the NO2 readings are now wrong, because those readings were part of each frame. The fix is to filter inside the same SELECT that holds the window. The reasoning is to ask at which step a row disappears, and to make sure that step comes before the window is calculated.

Trap: Filtering a window result in the same WHERE

WHERE rnk = 1 beside the RANK() that defines rnk fails, because WHERE runs before the window exists. Put the window in a subquery or CTE, then filter in the outer query.

What each function needs

Each idea below comes with a small example that uses different data: cafe sales, sports scores, a step counter, a visit log. Do not copy these examples into the lab. Read each one, run it in your own editor and compare the output with what the text says.

1. Sorting a list of tuples with a key. sorted takes a key function that says what to compare. Here the list is sorted by score highest first, and by name for ties.

players = [("Ana", 14), ("Ben", 9), ("Cy", 14)]
ranked = sorted(players, key=lambda p: (-p[1], p[0]))
print(ranked)

The output is [('Ana', 14), ('Cy', 14), ('Ben', 9)]. The key (-p[1], p[0]) is a tuple. Python compares the first item, the negated score, so the largest score comes first. It compares the second item, the name, only when two scores are equal. The minus sign works for numbers only.

2. Rounding. round(x, 2) rounds to two decimal places, but the result can surprise you.

print(round(2.675, 2))
print(round(0.125, 2))
print(round(2.5))

The output is 2.67, then 0.12, then 2. The number 2.675 is stored in binary as a little less than 2.675, so it rounds down. The number 0.125 sits exactly halfway, and Python rounds halfway cases to the even digit. The rule for the lab is to round once, at the end, because rounding an intermediate average changes the later results.

3. Booleans are integers. In Python, bool is a subclass of int, so True behaves as the number 1.

print(isinstance(True, int))
print(isinstance(True, bool))
print(isinstance(5, bool))

The output is True, True and False. If a function must reject booleans while accepting whole numbers, check isinstance(x, bool) before you check for int.

4. Slicing. A slice start:stop:step takes part of a sequence. The stop index is not included.

word = "espresso"
print(word[:3])
print(word[-2:])
print(word[1:6:2])

The output is esp, so and srs. Index 0 is the first letter, and a negative index counts from the end. The step of 2 takes every second letter in the range.

5. Running SQL with placeholders. A ? in the SQL is replaced by a value from a tuple, which keeps quotes and user input out of the SQL text.

import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE sale (cafe TEXT, cups INTEGER)")
conn.executemany("INSERT INTO sale VALUES (?, ?)",
                 [("Market", 12), ("Harbour", 7), ("Market", 9)])
rows = conn.execute("SELECT cups FROM sale WHERE cafe = ? ORDER BY cups",
                    ("Market",)).fetchall()
print(rows)
conn.close()

The output is [(9,), (12,)]. executemany runs the same INSERT once for each tuple. Even with one value, the placeholder values must be in a tuple, which is why ("Market",) has a trailing comma. fetchall() returns a list of tuples, one tuple per row, even when the query asks for one column.

6. A window that numbers all rows. Without PARTITION BY, the whole result is one group.

import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE match_score (player TEXT, points INTEGER)")
conn.executemany("INSERT INTO match_score VALUES (?, ?)",
                 [("Asha", 30), ("Ravi", 45), ("Meena", 30)])
sql = """
    SELECT player, points,
           ROW_NUMBER() OVER (ORDER BY points DESC, player ASC) AS place
    FROM match_score
"""
print(conn.execute(sql).fetchall())
conn.close()

The output is [('Ravi', 45, 1), ('Asha', 30, 2), ('Meena', 30, 3)]. Every row gets a number, and the ORDER BY decides which row is first. The second key, player ASC, breaks the tie between the two 30s. Adding PARTITION BY would restart the numbering inside each group.

7. A moving average with a frame. A frame gives each row its own set of neighbours. This example uses a step counter, not the lab's data.

import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE steps (day INTEGER, count INTEGER)")
conn.executemany("INSERT INTO steps VALUES (?, ?)", [(1, 100), (2, 300), (3, 200)])
sql = """
    SELECT day,
           ROUND(AVG(count) OVER (
               ORDER BY day
               ROWS BETWEEN 1 PRECEDING AND CURRENT ROW
           ), 2) AS avg_2
    FROM steps
    ORDER BY day
"""
print(conn.execute(sql).fetchall())
conn.close()

The output is [(1, 100.0), (2, 200.0), (3, 250.0)]. Day 1 has no earlier row, so its average is its own count. Day 2 averages 100 and 300. Day 3 averages 300 and 200. The first row is not dropped, because the frame simply holds fewer rows at the start.

How the ideas map to the two functions. top_n_per_station needs items 1, 2, 5 and 6: a sort with several keys, a rounding step at the end, a placeholder if you filter, and a window numbered within each group. rolling_avg needs items 2, 5 and 7: a filter with a placeholder, a frame over ordered rows, and rounding at the end.

Worked twin problem

This problem is set in a different domain, with different data. It needs the same skills: a top-N per group, a frame over ordered rows, and a filter that keeps only full windows.

Scenario. A city bike scheme records how many bikes leave each dock in each hour. The planning team wants the busiest hours for each dock, and a trailing total that shows how many bikes left over a few hours in a row. Compute both in SQL with window functions, using the standard library sqlite3 module.

Write two functions.

  • busiest_hours(trips, n) takes trips, a list of (dock, hour, bikes) tuples, where hour and bikes are whole numbers. For each dock, it returns the top n hours by bikes, highest first. Ties on bikes go to the earlier hour. The result is a list of (dock, hour, bikes) tuples, ordered by dock ascending, then bikes descending, then hour ascending. Use ROW_NUMBER() inside a subquery.
  • trailing_sum(trips, dock, window) takes the same list, a dock name and a whole number window. For that dock only, it returns (hour, total) tuples in hour order, where total is the sum of bikes over the current hour and the window - 1 hours before it. Only full windows count, so the first window - 1 hours produce no tuple. An unknown dock, or a dock with too few hours, returns [].
import sqlite3


def make_db(trips):
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE trip (dock TEXT, hour INTEGER, bikes INTEGER)")
    conn.executemany("INSERT INTO trip VALUES (?, ?, ?)", trips)
    return conn


def busiest_hours(trips, n):
    conn = make_db(trips)
    sql = """
        SELECT dock, hour, bikes
        FROM (
            SELECT dock, hour, bikes,
                   ROW_NUMBER() OVER (
                       PARTITION BY dock
                       ORDER BY bikes DESC, hour ASC
                   ) AS rn
            FROM trip
        )
        WHERE rn <= ?
        ORDER BY dock ASC, bikes DESC, hour ASC
    """
    result = conn.execute(sql, (n,)).fetchall()
    conn.close()
    return result


def trailing_sum(trips, dock, window):
    conn = make_db(trips)
    sql = f"""
        SELECT hour, total
        FROM (
            SELECT hour,
                   SUM(bikes) OVER (
                       ORDER BY hour
                       ROWS BETWEEN {window - 1} PRECEDING AND CURRENT ROW
                   ) AS total,
                   COUNT(*) OVER (
                       ORDER BY hour
                       ROWS BETWEEN {window - 1} PRECEDING AND CURRENT ROW
                   ) AS n_in_window
            FROM trip
            WHERE dock = ?
        )
        WHERE n_in_window = ?
        ORDER BY hour
    """
    result = conn.execute(sql, (dock, window)).fetchall()
    conn.close()
    return result

Explanation, line by line.

  • import sqlite3 loads the standard library module. No installation is needed.
  • make_db opens a new in-memory database for each call, so the tests never share data. It creates the table trip with three columns, then loads every tuple with executemany. Each ? takes one value from the tuple.
  • In busiest_hours, the inner query numbers the rows of each dock. PARTITION BY dock restarts the numbering for each dock. ORDER BY bikes DESC, hour ASC puts the busiest hour first and gives the earlier hour the lower number when two hours tie. For Dock A, hours 8 and 9 both have 9 bikes, so hour 8 gets number 1 and hour 9 gets number 2.
  • WHERE rn <= ? keeps the top n rows. The tuple (n,) supplies the value for the placeholder.
  • The outer ORDER BY gives the output order the statement asks for. Running busiest_hours(trips, 2) returns four tuples, two for each dock.
  • In trailing_sum, the frame size depends on window, so an f-string places window - 1 into the SQL text. This is safe here because window is a whole number that the caller controls. The dock name never goes into the text. It is passed through a ? placeholder.
  • SUM and COUNT use the same frame. COUNT(*) counts the rows in each frame. For Dock A with window 3, hour 7 has one row in its frame, hour 8 has two, and hours 9 and 10 have three.
  • WHERE n_in_window = ? keeps only the rows whose frame is full. Dock A at hour 9 has the frame 5, 9 and 9, which sums to 23. Dock A at hour 10 has the frame 9, 9 and 4, which sums to 22. Those are the two values in the first assert.
  • The last asserts check the edge cases: an empty list, a window of 1, a dock with too few hours, and a dock that is not in the data.

import sqlite3


def longest_loan_per_shelf(loans):
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE loan (shelf TEXT, title TEXT, days INTEGER)")
    conn.executemany("INSERT INTO loan VALUES (?, ?, ?)", loans)
    sql = """
        SELECT shelf, title, days
        FROM (
            SELECT shelf, title, days,
                   ROW_NUMBER() OVER (
                       PARTITION BY shelf
                       ORDER BY days DESC, title ASC
                   ) AS rn
            FROM loan
        )
        WHERE rn = 1
        ORDER BY shelf
    """
    result = conn.execute(sql).fetchall()
    conn.close()
    return result


def gap_days(log, member):
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE visit (member TEXT, day INTEGER)")
    conn.executemany("INSERT INTO visit VALUES (?, ?)", log)
    sql = """
        SELECT day - LAG(day) OVER (ORDER BY day) AS gap
        FROM visit
        WHERE member = ?
        ORDER BY day
    """
    gaps = [row[0] for row in conn.execute(sql, (member,)) if row[0] is not None]
    conn.close()
    return gaps

Say it out loud

Interviewers and viva examiners ask these questions to see whether you understand the query, not just whether you can run it. Answer in your own words, and use the words you have seen in this chapter.

Why use a window function instead of GROUP BY for a trend?

A GROUP BY collapses each station into one row, so you lose the timeline that a trend needs. A window function calculates a value for each reading using its neighbours, and keeps every row. For CityPulse, that means each reading can carry a smoothed value next to its raw value. The frame decides how many neighbours are used.

What does PARTITION BY do, and what goes wrong without it?

PARTITION BY splits the rows into separate groups, and the window is calculated inside each group only. In CityPulse the partition is the station and pollutant, so readings from different stations never mix. Without it, the window runs across the whole table in one sequence, and the last reading of one station is averaged with the first reading of another.

Why does the view expose n_in_window?

A rolling average near the start of a series is based on fewer readings than its label suggests. Also, ROWS counts rows rather than hours, so a missing hour stretches the window over more time. Exposing the count tells the dashboard and the reader how many readings sit behind each value, so a partial or gappy window can be flagged.

Why can you not filter on a window result in WHERE?

SQL evaluates WHERE before window functions are calculated. At the point WHERE runs, the rank or the rolling average does not yet exist. To keep only rows with rank 1, you calculate the rank in a subquery or CTE, and then filter on it in the outer query. This pattern is the standard way to get the top N per group.

Why does the reference for the Python algorithm use ROWS rather than RANGE?

ROWS counts a fixed number of readings, so the window size is easy to check by hand and identical in every database. RANGE defines the window by time, which handles gaps correctly, but it is harder to write and not supported in the same way everywhere, and SQLite does not accept INTERVAL in a frame. The course accepts the gap problem and documents the choice, so that the Python result can be compared with the SQL result on the same definition.
