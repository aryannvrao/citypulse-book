The idea in one minute

Every reading that a sensor sends to CityPulse arrives as text, and some of it is wrong: a humidity of -5, a temperature sent as the word "abc", or a number that is not really a number at all, such as NaN (short for "not a number"). If that data reaches the database, the air-quality charts go wrong without anyone noticing.

Today you learn two tools that stop this. Pydantic checks each incoming value against rules you write down once. pytest runs small checks that prove those rules still hold after every change.

Think of an airport check-in desk. A wrong passport, an overweight bag or a missing ticket, and you never reach the plane. Pydantic is the desk. pytest is the pre-flight checklist that runs before every take-off.

By the end you will be able to write rules on a model, read a validation error, write tests that pass on good data and fail on bad data, and run a coverage check that can block a merge.

Starting from zero

Terminal. A text window where you type commands. On Windows you can use PowerShell or Git Bash. A command is one line you type, followed by Enter. In this book, lines that start with $ are commands. Type everything after the $, not the $ itself.

File and folder. A file holds text or data under a name, such as models.py. A folder (also called a directory) holds files. The ending .py tells your computer and your editor that the file contains Python code.

Python. A programming language. The Python interpreter reads a .py file and runs it. You start it from the terminal with the command python. Some systems need python3 instead.

Variable. A name that holds a value. The line value = 42.1 stores the number 42.1 under the name value. Here = means "store this", not "is equal to".

Types. Every value has a type. An int is a whole number such as 34. A float is a number with a decimal point, such as 34.5. A str (string) is text in quotes, such as "CP-001". A bool is either True or False. None means "no value at all". A list is an ordered collection in square brackets, such as [1, 2]. A dict (dictionary) is a set of key-value pairs in curly braces, such as {"age": 34}, where "age" is the key and 34 is the value.

The difference between 34 and "34" matters today. The first is an int. The second is text that looks like a number.

Function. A named block of code you can run by writing its name followed by brackets, such as len("abc"). That call returns 3, the number of characters. A function can take inputs, called parameters, and give back a result, called a return value. You define one with the word def.

Class and object. A class is a template. The class Reading describes what a sensor reading looks like. An object is one actual reading built from that template. In class Reading(BaseModel):, the words in brackets mean that Reading borrows all the abilities of BaseModel, a class that Pydantic provides.

Type hint. A note after a name that says what type is expected, such as value: float. Python does not enforce it by itself. Pydantic reads these hints and enforces them.

Module, import and pip. A .py file that you reuse from another file is a module. The line from models import Reading loads the name Reading from models.py. Third-party code, such as Pydantic, is installed with pip, Python's package installer. The command pip install pydantic downloads it.

Virtual environment. A folder that holds the packages for one project only, so that two projects do not clash. You create one with python -m venv .venv.

Exception. An error that stops normal running. Code raises an exception with the word raise. Code can catch one with try and except. Pydantic reports bad data by raising an exception called ValidationError.

assert. The line assert condition does nothing if the condition is True. If it is False, Python stops with an AssertionError. Tests are built from assert lines.

JSON. A text format for structured data. Keys are in double quotes: {"station_id": "CP-001", "value": 42.1}.

API, endpoint, HTTP, status code. An API is a contract that one program uses to ask another for something. An endpoint is one address that the API answers, such as POST /v1/predict. HTTP is the request and response protocol the web uses. POST means "send data". Every response carries a number called a status code: 200 means success, 404 means the thing was not found, 422 means the data you sent was invalid, and 500 means the server failed.

Server. A program that waits for requests and answers them. Tests can call an application in memory, without starting a real server. FastAPI's TestClient does this.

Test, test runner, fixture, parametrize. A test is a function whose name starts with test_ and that checks one behaviour. pytest is the test runner. It finds those functions, runs them and reports which passed. A fixture is a function that prepares shared setup, such as a valid sample payload. Parametrize means running one test with a list of different inputs.

Coverage. A measurement of which lines of your code ran while the tests ran. A line that never runs during tests is a line that no test has checked.

CI (continuous integration). A service that runs your checks automatically each time a change is pushed to the shared repository on GitHub. Merging a change means adding it to the main line of code. Branch protection is a GitHub setting that refuses a merge while a required check is red.

The tools

Pydantic models and constraints

Pydantic is a Python library that checks data against classes with type hints. A class that inherits from BaseModel is called a model. It declares which fields exist, what type each one has, and which values are allowed.

CityPulse uses it because the same model that checks a request in FastAPI can also check a nightly batch file. The slides compare it with three alternatives. Manual if checks need no library, but every endpoint repeats them, the messages differ, and the API documentation does not show the rules. marshmallow is a mature serialisation library, but FastAPI is built on Pydantic, so using marshmallow would lose the automatic 422 responses and the generated documentation. A JSON Schema validator is language-neutral, but its schemas live apart from your Python code, so your editor understands them less well.

Pydantic works in three steps, in this order. First it checks each field's type. Then it applies the Field constraints, such as minimum and maximum values. Then it runs your custom validators. If any step fails, it raises a ValidationError that lists every bad field. FastAPI turns that error into a 422 response before your function starts. Only a fully valid object reaches your code.

Pydantic does type coercion by default. Coercion means converting an input to the declared type when the conversion is exact. The string "34" becomes the int 34 for an int field. The string "42.5" becomes the float 42.5 for a float field. But "34.5" is refused for an int field, because converting it would lose the .5, and "abc" is refused for any number. A float field also accepts NaN and infinity unless you forbid them. That is why the slides add a finite-number check.

Here is the slide's model, with its indentation restored. The slide's text lost its indentation, so the spacing is rebuilt from the Python rules.

import math
from pydantic import BaseModel, ConfigDict, Field, field_validator

class PredictRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    station_id: str = Field(min_length=1, max_length=64)
    pm25: float = Field(ge=0, le=1000)           # ug/m3; above 1000 is a sensor fault
    humidity: float = Field(ge=0, le=100)        # relative humidity, %
    temperature_c: float = Field(ge=-10, le=50)  # Bengaluru range with margin

    @field_validator("pm25", "humidity", "temperature_c")
    @classmethod
    def must_be_finite(cls, v: float) -> float:
        if not math.isfinite(v):
            raise ValueError("must be a finite number")
        return v

Line by line:

  • import math loads Python's built-in maths module. You use it for math.isfinite.
  • from pydantic import BaseModel, ConfigDict, Field, field_validator takes four names out of the Pydantic package. You need them below.
  • class PredictRequest(BaseModel): defines the model. The indented lines under it belong to the class. The indentation is four spaces. Python needs it to know where the class body starts and ends.
  • model_config = ConfigDict(extra="forbid") sets one rule for the whole model. extra="forbid" means any key the model does not declare is an error. Without it, a misspelt key such as humidty is silently ignored.
  • station_id: str = Field(min_length=1, max_length=64) declares a text field. Field(...) adds rules: at least one character and at most 64. There is no default= argument, so the field is required.
  • pm25: float = Field(ge=0, le=1000) declares a number. ge means "greater than or equal to". le means "less than or equal to". So 0 to 1000 inclusive is allowed. The text after # is a comment. Python ignores comments.
  • humidity and temperature_c follow the same pattern with different limits.
  • @field_validator("pm25", "humidity", "temperature_c") is a decorator. The @ line attaches the function below it to these three fields, so Pydantic runs that function for each of them.
  • @classmethod says that the function receives the class itself, named cls, rather than one object.
  • def must_be_finite(cls, v: float) -> float: defines the function. v is the value being checked. -> float is a return type hint.
  • if not math.isfinite(v): is True when the value is NaN or infinity. The not turns False into True and True into False.
  • raise ValueError("must be a finite number") raises the error. Pydantic catches it and reports it as a validation error with that text.
  • return v passes the value on unchanged.

Send the model a humidity of -5 and Pydantic reports an error on the field humidity, saying the value must be greater than or equal to 0. FastAPI turns that into a 422.

Key fact: Coercion is not validation

Coercion changes the value to the declared type. Validation then decides whether the result is allowed. A value can be coerced successfully and still be refused by a Field rule.

The slides also say to use training minimum and maximum values only as warnings, not as hard limits. Reject a value only when it is physically impossible. A pollutant reading above the range seen in training can be real, so warn about it instead.

Trap: Forgetting extra='forbid'

A misspelt field name is dropped without an error. If the real field has a default value, the request succeeds using that default. The client thinks its value was used, and it was not.

Trap: Mixing old and new Pydantic syntax

Older Pydantic code uses @validator and class Config. Version 2, which this course uses, uses @field_validator and ConfigDict. Use the version 2 names so that the code matches the documentation you will read.

Error handling and structured logs

An exception handler is a function that runs whenever a certain kind of error happens. Middleware is code that runs around every request, before and after the handler. A structured log line is one line of JSON, so a log tool can filter it by field, for example "show every request slower than 300 ms".

CityPulse uses both so that every failure looks the same to the client. The slides compare them with three alternatives. FastAPI's default errors are easy but inconsistent: a 422 carries a list under detail, while a 404 carries a single string under detail. Plain logging.info text is readable by people but cannot be filtered by latency_ms or status. Sentry and paid tracking tools are rich, but they are out of scope for this course, and they still need structured request logs.

The envelope has one shape. Every error response looks like {"error": {"code": ..., "message": ..., "detail": ..., "request_id": ...}}. The request_id is a unique identifier per request. The same ID is sent back in the X-Request-ID header, so a support engineer can match a client complaint to one log line.

The slide's code is below, with the indentation restored. The slide assumes that app = FastAPI() was written earlier in the same file.

import json, time, uuid
from fastapi.responses import JSONResponse

def err(status, code, message, rid, detail=None):
    return JSONResponse(
        status_code=status,
        content={"error": {"code": code, "message": message,
                           "detail": detail, "request_id": rid}},
    )

@app.exception_handler(Exception)
async def on_500(request, exc):  # never put str(exc) in the client message
    return err(500, "internal_error", "Unexpected server error",
               getattr(request.state, "request_id", None))

@app.middleware("http")
async def log_requests(request, call_next):
    rid = request.state.request_id = str(uuid.uuid4())
    t0, status = time.perf_counter(), 500
    try:
        resp = await call_next(request)
        status = resp.status_code
        resp.headers["X-Request-ID"] = rid
        return resp
    finally:
        print(json.dumps({"method": request.method, "path": request.url.path,
                          "status": status,
                          "latency_ms": round((time.perf_counter() - t0) * 1000, 1),
                          "request_id": rid}), flush=True)

Line by line:

  • import json, time, uuid loads three built-in modules: one for JSON text, one for clocks, and one for random IDs. The comma lets one line import several modules.
  • from fastapi.responses import JSONResponse takes the class that builds a response with a JSON body.
  • def err(status, code, message, rid, detail=None): defines a helper. detail=None is a default. If the caller leaves it out, detail is None.
  • return JSONResponse(...) builds the response. status_code= sets the HTTP status. content= is the body. The body is a dictionary, and FastAPI converts it to JSON.
  • @app.exception_handler(Exception) registers the next function for every error that is a subclass of Exception. That covers almost everything.
  • async def makes a function that can wait for slow work. await pauses the function until the work is done. FastAPI needs both here.
  • getattr(request.state, "request_id", None) reads the attribute request_id from the request's state. If it is missing, it returns None instead of raising an error.
  • The handler never includes str(exc). That text can contain file paths or SQL, which must not reach a client.
  • rid = request.state.request_id = str(uuid.uuid4()) creates a random ID as text and stores it in two places in one line. uuid4() generates it.
  • t0, status = time.perf_counter(), 500 records the start time and sets a default status of 500. If the handler crashes, the status stays at 500.
  • try: and finally: are a pair. Code in finally runs even when the code in try raises an error. That is why the log line is always written.
  • resp = await call_next(request) runs the rest of the application and waits for its response.
  • resp.headers["X-Request-ID"] = rid adds the header. Square brackets set one entry in a dictionary-like object.
  • json.dumps({...}) turns a dictionary into a JSON string. flush=True makes Python write the text at once rather than keeping it in a buffer.
  • round(x, 1) rounds the latency to one decimal place. The expression * 1000 converts seconds to milliseconds.

A normal request writes a line such as {"method": "POST", "path": "/v1/predict", "status": 422, "latency_ms": 3.2, "request_id": "..."}. The exact latency and ID will differ on your machine.

Trap: Passing exc.errors() straight into JSONResponse

The list from exc.errors() can contain objects that JSON cannot write. Keep only the loc and msg keys of each item, and convert them to text.

Trap: Returning str(exc) in a 500 response

The text can leak paths and SQL. Log the details on the server, and return the generic message to the client.

Trap: Turning every failure into 400

This hides real bugs. Add proper validation, so that each case returns 404 or 422, and keep 500 for genuine server faults.

The slide shows the handler for 500 errors only. The same err() helper can also build the 404 and 422 envelopes. The slide does not print that code, so use your ticket's version when you write it.

pytest and TestClient

pytest is Python's standard test runner. It finds functions whose names start with test_, runs them, and reports the result. A test uses assert to state what must be true. Fixtures supply shared setup. pytest passes a fixture into a test by matching the fixture's name with a parameter's name.

TestClient is FastAPI's helper for tests. It sends a request to the application inside the same Python program, so the test does not need a running server and does not need a network connection.

CityPulse uses pytest because it is short to write and runs in CI. The slides compare it with three alternatives. unittest is in the standard library, but it needs class-based boilerplate and has no fixtures or parametrize as simple as pytest's. Manual curl scripts are fine for exploring, but nobody runs them on every change. Postman test scripts suit the shared collection, but they need a running server and a separate runner in CI.

pytest finds every test, builds the session client once, and runs each test. Each test sends a request and asserts on the response. A failing assert makes pytest exit with a non-zero code, and that turns the CI check red.

The first line shows one dot for each passed test. The second line is the summary. Timings vary from run to run.

The slides put shared fixtures in tests/conftest.py. Here is the slide's contract test, with indentation restored.

import json
import pytest

def test_predict_returns_model_version(client, valid_payload):
    r = client.post("/v1/predict", json=valid_payload)
    assert r.status_code == 200
    assert r.json()["model_version"] == json.load(open("models/metrics_v1.json"))["version"]

@pytest.mark.parametrize("field,value", [("humidity", -5), ("humidity", "abc"), ("pm25", 5000), ("temperature_c", None)])
def test_predict_rejects_bad_input_with_422(client, valid_payload, field, value):
    r = client.post("/v1/predict", json={**valid_payload, field: value})
    assert r.status_code == 422 and r.json()["error"]["code"] == "validation_error"

def test_unknown_station_returns_404(client, valid_payload):
    r = client.post("/v1/predict", json={**valid_payload, "station_id": "NOT_A_STATION"})
    assert r.status_code == 404

Line by line:

  • import json and import pytest load the JSON module and the pytest library.
  • def test_predict_returns_model_version(client, valid_payload): is a test. The parameters client and valid_payload are fixtures. pytest supplies them because the names match fixtures in conftest.py.
  • r = client.post("/v1/predict", json=valid_payload) sends a POST request. json= tells the client to send the dictionary as a JSON body. r holds the response.
  • assert r.status_code == 200 fails the test unless the status is exactly 200. == compares for equality. A single = would store a value instead.
  • r.json() converts the response body from JSON text into a dictionary, and ["model_version"] reads one key.
  • json.load(open(...)) reads the metrics file. The file is left open, which is a small untidiness. with open(...) as f: is the tidier form.
  • @pytest.mark.parametrize("field,value", [...]) runs the test once for each pair in the list. The first string names the two parameters, field and value.
  • {**valid_payload, field: value} makes a new dictionary. The ** copies every key from valid_payload. The key field is then set to value. The original dictionary is not changed.
  • r.status_code == 422 and r.json()["error"]["code"] == "validation_error" checks two things. Both must be True for the test to pass. and requires both sides to be True.
  • The third test uses an unknown station and expects a 404.
Trap: Creating TestClient(app) without with

Without the with statement, the application's startup code, called the lifespan, does not run. The model is then not loaded, and app.state.model does not exist. Write with TestClient(app) as c: in the fixture.

Trap: Sharing one payload dictionary between tests

If one test changes a shared dictionary, later tests get the changed data. Make valid_payload function-scoped, and copy it with {**payload} when you need a variant.

Trap: Testing 500 errors with the default client

The default TestClient re-raises server errors into the test, so the test crashes before it can check the response. Use TestClient(app, raise_server_exceptions=False) to test the 500 envelope.

Coverage

Coverage measures which lines and branches of your code run during the test suite. pytest-cov is a plugin that adds this measurement to pytest. It prints a table of files, the number of lines, the number missed, and the line numbers that were missed. It can also fail the whole run when the total falls below a threshold.

CityPulse uses it to force tests onto code that nobody has checked. The slides compare it with three alternatives. coverage.py run directly is the same engine, but it needs a longer command. Codecov and Coveralls give hosted reports and comments on pull requests, but they need extra accounts and tokens, which this course does not need for a single threshold. Having no coverage gate is less friction, but untested error handlers then reach production unnoticed. The ticket forbids that.

The gate works in four steps. pytest-cov records each executed line in the package you name. At the end it calculates a percentage for each file. If the total is under the threshold, pytest exits with a failure code, even when every test passed. CI then shows the check as red, and branch protection blocks the merge.

The slide's configuration is below. The file is pyproject.toml, and the text is shown with the slide's line breaks.

[tool.pytest.ini_options]
pythonpath = ["."]
addopts = "--cov=api --cov-report=term-missing --cov-fail-under=60"

Line by line:

  • [tool.pytest.ini_options] is a section header. pytest reads settings from this section of pyproject.toml.
  • pythonpath = ["."] adds the project's root folder to the list where Python looks for modules. Without it, from api.main import app can fail in CI even though it works on your laptop.
  • addopts holds extra options that pytest adds to every run. You do not type them each time.
  • --cov=api measures only the api package. Pass a folder name, not a dot, because --cov=. also measures the tests themselves.
  • --cov-report=term-missing prints the table in the terminal and adds a Missing column with the line numbers that did not run.
  • --cov-fail-under=60 makes pytest fail when the total coverage is below 60 per cent.

Run the suite and check the exit code. The exit code is the number the program returns to the operating system. Zero means success and any other number means failure.

In PowerShell, read the exit code with $LASTEXITCODE instead of echo $?. A line such as $ echo $? shows 0 after a success. After a coverage failure, pytest prints FAIL Required test coverage of 60% not reached and the code is 1.

The Missing column tells you what to test next. A line listed there ran in no test at all. The table below is a sample. Your numbers will differ. The layout is what you need to recognise.

Trap: Measuring the tests as well

--cov=. counts the test files, so the percentage looks higher than the code really is. Name the package instead.

Trap: Chasing 100 per cent with tests that assert nothing

A test with no assert raises coverage and proves nothing. Each test must check a result.

Trap: Forgetting pythonpath

Imports such as from api.main import app may fail only in CI. Set pythonpath = ["."], so that the same path works on every machine.

The worked example

The workbook builds one small model called Reading. It holds a sensor reading for one station and one pollutant. The goal is that a valid reading is accepted, and a negative value or an unknown pollutant is refused with a clear error. You then turn those checks into tests and run them.

Steps 1 and 2: the model and a good payload

Here is the final version of the model, which uses Literal for the pollutant. The earlier overview on the slide uses Field(pattern=...) with a set, which is not the version to copy.

from pydantic import BaseModel, Field
from datetime import datetime
from typing import Literal

Pollutant = Literal["pm25", "pm10", "no2", "o3"]

class Reading(BaseModel):
    station_id: str = Field(pattern=r"^CP-\d{3}$")
    ts: datetime
    pollutant: Pollutant
    value: float = Field(ge=0)  # concentration can't be negative
  • Literal["pm25", "pm10", "no2", "o3"] means the value must be exactly one of these four strings. Pydantic compares the text exactly.
  • Pollutant = Literal[...] stores the type under a name, so you can reuse it.
  • Field(pattern=r"^CP-\d{3}$") requires the text to match a pattern. ^ is the start, $ is the end, \d means one digit, and {3} means exactly three times. So CP-001 passes and CP-1 fails. The r before the quotes makes Python keep the backslash as typed.
  • ts: datetime accepts text such as "2026-11-03T14:00:00Z" and converts it into a real date and time.
  • value: float = Field(ge=0) requires zero or more.

The command below prints the field names, and the output confirms that the model loaded.

python3 -c runs the code in the quotes. from models import Reading loads the model from models.py. Reading.model_fields lists the declared fields.

Next, a valid payload. The ts text becomes a datetime, and the result is a typed object.

from models import Reading
r = Reading(station_id="CP-001", ts="2026-11-03T14:00:00Z", pollutant="pm25", value=42.1)
print(r.model_dump())

Reading(...) builds the object and checks every field. model_dump() turns it back into a dictionary. The output is {'station_id': 'CP-001', 'ts': datetime.datetime(2026, 11, 3, 14, 0, tzinfo=TzInfo(0)), 'pollutant': 'pm25', 'value': 42.1}. The ts value is now a datetime, not text. The tzinfo=TzInfo(0) part is the time zone, which is UTC here. The output format depends on the Pydantic version.

Steps 3 and 4: the failure paths

A negative value must be refused.

from pydantic import ValidationError
try:
    Reading(station_id="CP-002", ts="2026-11-03T14:00:00Z", pollutant="no2", value=-5)
except ValidationError as e:
    print(e)

Step 7: batch quarantine

The same model can check a whole file, one JSON line at a time. Good rows are counted. Bad rows are written to a quarantine file, so a person can review them. The program exits with code 1 if any row was bad, so the pipeline stops.

from models import Reading

        try:
            Reading(**json.loads(line))
            ok += 1
        except ValidationError:
            bad += 1
            q.write(line)

    """Return the number part of an id such as CP-007, as an int."""
    if not isinstance(station_id, str):
        raise TypeError("station_id must be a string")
    prefix, _, digits = station_id.partition("-")

    return int(digits)

Type coercion in Pydantic

What it is. Pydantic checks each value against the type you declared. Before it checks, it tries to convert the value, provided the conversion does not change its meaning. This conversion is called coercion. In its default mode, the text "12" becomes the integer 12 for an int field, and the text "42.5" becomes the float 42.5 for a float field. A conversion that would lose information is refused. The text "4.5" is refused for an int field, because the .5 would be lost, and "abc" is refused for any number.

from pydantic import BaseModel

class Pet(BaseModel):
    age: int
    weight: float

print(Pet(age="12", weight="42.5"))

The output is Pet(age=12, weight=42.5). The text has become real numbers. If you change age="12" to age="4.5", the same line raises a ValidationError that names the field age. A float field also accepts nan and infinity unless you forbid them with Field(allow_inf_nan=False). Coercion only changes the value. The field's other rules still apply to the converted value afterwards.

How it shows up in a case study. A canteen runs a feedback tablet. Every value arrives as text, and the model declares rating: int = Field(ge=1, le=5). The payload sends "rating": "4". A junior engineer asks whether the database will store the text "4" or the number 4, and whether the field should become a str. Pydantic converts "4" to the integer 4 in its default mode, then checks the range. The field stays an int, so the dashboard can average it. The team should not switch to str, because that removes the type check. If the tablet ever sends "4.5", the model refuses it, which is the behaviour the team wants.

Trap: Coercion is not validation

Coercion changes the value only. A value can convert correctly and still fail a rule. The text "7" becomes 7, and then le=5 refuses it. The tempting wrong idea is that a value which converts is therefore allowed.

Limiting a field to fixed values

What it is. Two tools restrict a field to a fixed set of values. A Literal lists the allowed values as text, such as Literal["bronze", "silver", "gold"]. An Enum is a class whose members are the allowed values, and your code can refer to them by name, such as Tier.GOLD. Both compare values exactly. A Literal does not change letter case, so a Literal that lists "gold" refuses "GOLD". The error message lists the allowed values, which tells the sender what to send.

from typing import Literal
from pydantic import BaseModel

class Membership(BaseModel):
    tier: Literal["bronze", "silver", "gold"]

print(Membership(tier="gold").tier)
Membership(tier="GOLD")

The first line prints gold. The second line raises a ValidationError, whose message reads Input should be 'bronze', 'silver' or 'gold'. If a business rule says that "GOLD" must be accepted, you must normalise the text yourself. Put a validator in mode="before" that lower-cases the text. A before validator runs before the set check, so the Literal then sees the cleaned text.

How it shows up in a case study. A loyalty app has an old version that sends the plan name as "Premium", with a capital P. The new model says plan: Literal["basic", "premium"], and the old app's requests fail with a literal error. The team asks whether the model is broken. It is not. The Literal compares exact text, so the decision depends on the rule the team agrees. If the team wants every capitalisation accepted, the right fix is a before validator that lower-cases the text, with the Literal kept strict. The wrong fix is to change the field to a plain str, which removes the check entirely.

Trap: Literal ignores case

A Literal does not ignore case. Listing "gold" does not accept "GOLD". You must normalise the text in a before validator if you want that behaviour.

Checks across two fields with a model validator

What it is. A field_validator looks at one field. A model_validator runs after the whole object has been built, so it can compare two fields. Use @model_validator(mode="after"). The method receives the built object as self, and it must return self. A rule such as "the end must be later than the start" belongs in a model validator.

from datetime import datetime
from pydantic import BaseModel, model_validator

class Booking(BaseModel):
    start: datetime
    end: datetime

    @model_validator(mode="after")
    def end_after_start(self):
        if self.end <= self.start:
            raise ValueError("end must be later than start")
        return self

Booking(start="2026-01-05T09:00", end="2026-01-05T08:00")

The last line raises a ValidationError. Its message contains Value error, end must be later than start. The raise inside the method is turned into a validation error. The return self line hands the checked object back to Pydantic. If the method finishes without that line, the method returns None, so the validated model becomes None or Pydantic raises an error, depending on the version. Either way the result is wrong.

How it shows up in a case study. A maintenance log stores opened_on and closed_on for each job. The rule is that a job cannot close before it opens. A teammate writes the check in a field validator on closed_on. That validator is built around one field and can reach other fields only through awkward extra access, so the comparison is fragile and in the wrong place, and the team finds that rules for other dates are missing. The right decision is to move the comparison into a model validator in mode="after". The validator then sees both values, returns the object, and the error names the job record. The wrong decision is to add a Field constraint to closed_on, because a constraint on one field cannot compare it with another.

Trap: Two-field rules on one field

A rule that compares two fields placed on one field's validator is either missing data or fragile. Put it on the model. Forgetting return self in an after validator is a second common mistake.

Sharing setup with fixtures

What it is. A fixture is a function marked with @pytest.fixture. It returns the setup that a test needs. A test asks for the fixture by naming a parameter with the same name, and pytest runs the fixture and passes its result in. The scope decides how often the fixture runs. The default scope is function, which runs the fixture again for each test. The scope session runs it once for the whole test run.

import pytest

@pytest.fixture
def basket():
    return {"items": ["apple"], "total": 2.5}

def test_basket_has_one_item(basket):
    assert len(basket["items"]) == 1

def test_add_item(basket):
    basket["items"].append("pear")
    assert len(basket["items"]) == 2

pytest reports both tests as passed. Each test receives a new dictionary, because the scope is function. The first test can change its copy without affecting the second test. If the scope were session, the append in the second test would change the same dictionary that a later test reads, and the order of the tests would start to matter.

How it shows up in a case study. A test suite has two costs. Starting the web application with its startup code takes ten seconds, and the application is read-only once started. Each test also needs a payload dictionary that some tests edit. A teammate sets the application fixture to function scope, so the start-up runs for every test, and the suite becomes slow. Another teammate keeps the payload at session scope, and tests begin to fail only when they run together. The right decision is session scope for the read-only application, and function scope for the mutable payload, so that each test gets a fresh copy of the data.

Trap: Wide scope on mutable data

A session-scoped dictionary is shared by every test in the run. One test that changes it changes the input for the next test, so the failure moves to a different test each time the order changes.

Checking that an error is raised

What it is. with pytest.raises(ValueError): is a block. The test passes when the code inside the block raises the named exception, and fails when nothing is raised. Adding match="text" also checks that the error message contains the text, using a pattern search. Adding as info stores the exception, so that you can read info.value.

import pytest

def copies_from(text):
    count = int(text)
    if count < 1:
        raise ValueError("copies must be at least 1")
    return count

def test_zero_copies_is_refused():
    with pytest.raises(ValueError, match="at least 1"):
        copies_from("0")

int("0") gives 0, the check fails, and ValueError is raised with the message copies must be at least 1. The test passes. If copies_from returned 0 instead of raising, pytest would report DID NOT RAISE, and the test would fail. The match text is searched inside the message, so "at least 1" is enough.

How it shows up in a case study. A library team has a function that refuses zero copies of a book. One teammate writes copies_from("0") on a line above the with block, so the exception is raised outside the block and fails the test with an error. Another teammate writes pytest.raises(Exception), and the test passes when a typing mistake inside the function raises a TypeError. The right decision is to put the call inside the block, and to name ValueError, which is the exact promise the rule makes. Adding match then proves that the message is the one the team intended.

Trap: Catching Exception

pytest.raises(Exception) passes for almost any error, including a bug such as a TypeError from a typo. Name the exact class that the rule promises.

Running one test on many inputs

What it is. @pytest.mark.parametrize("name", [values]) runs one test function once for each value. Each run is reported on its own line, so a failing run names its input. With several names, write them as one comma-separated string, and give each row as a tuple in the same order.

import pytest

@pytest.mark.parametrize("text, expected", [("1", 1), ("  7 ", 7), ("0", 0)])
def test_text_becomes_int(text, expected):
    assert int(text) == expected

pytest runs the test three times, once per row. The first run uses text="1" and expected=1. The second run uses the text with spaces around it, and int accepts those spaces. The report shows 3 passed. If the second row had a wrong expected value, the report would name that row, and the other two rows would still be reported as passed.

How it shows up in a case study. A courier team must check that a shipping function refuses a weight of 0, a negative weight, the text "abc" and None. One engineer writes a for loop inside a single test. The first failing value stops the test, so the team cannot see which other values also fail. The right decision is to parametrize the four values, so that each one is reported on its own line. The team should also add the boundary value and an awkward case such as an empty string, because those are where the bugs usually are.

Trap: A loop hides later failures

A for loop inside one test stops at the first failure. Each value needs its own run, which parametrize gives you.

Replacing a dependency with a mock

What it is. A mock is a stand-in object that records how it was called and returns a value that you choose. unittest.mock.patch replaces a name for the length of a with block, and the original is restored afterwards. The pytest-mock plugin offers the same idea as a mocker fixture, and its mocker.patch is undone automatically at the end of the test. Use a mock for things a test should not really do, such as a network call or a clock. Patch the name where the code uses it, not where the name is defined.

## weather.py
def fetch_temperature(city):
    ...  # a real network call would go here

def describe(city):
    temp = fetch_temperature(city)
    return f"{city}: {temp} C"

## test_weather.py
from unittest import mock
import weather

def test_describe_uses_fake_temperature():
    with mock.patch("weather.fetch_temperature", return_value=24) as fake:
        assert weather.describe("Pune") == "Pune: 24 C"
    fake.assert_called_once_with("Pune")

The test passes without any network call. The patch replaces weather.fetch_temperature with a stand-in that returns 24. The describe function calls the stand-in, builds the sentence, and the test checks it. The last line checks that the stand-in was called exactly once, with the city name "Pune".

How it shows up in a case study. A report generator calls a weather function, and its tests fail whenever the network is down. The team wants the tests to run offline, and to check that the city name is passed on correctly. A teammate proposes mocking describe itself, which is the function under test. The right decision is to mock only the outside call, fetch_temperature, in the module where the report code uses it, and to assert on the result of the real describe. This keeps the code under test real, and the network out of the test.

Trap: Mocking the code under test

If you mock the function you are testing, the test checks the stand-in and proves nothing about your code. Mock only the outside dependency.

Nested models and error paths

What it is. A field can have another model as its type. Pydantic validates the inner dictionary as well, and each error has a loc value. The loc is a tuple that gives the path from the top level to the bad field. A list of models adds a position number to the path, counting from 0.

from pydantic import BaseModel, ValidationError

class Address(BaseModel):
    city: str
    postcode: str

class Customer(BaseModel):
    name: str
    address: Address

try:
    Customer(name="Meera", address={"city": "Pune"})
except ValidationError as e:
    print(e.errors()[0]["loc"])

The output is ('address', 'postcode'). The path starts at the top-level field address, goes into the nested model, and ends at the missing field postcode. If Customer had a field orders: list[Address], a bad item in the third position would have a loc that includes the index 2, so the path would look like ('orders', 2, 'postcode').

How it shows up in a case study. A retail team receives customer records with nested addresses, and the error log shows a loc of ("address", "postcode"). A developer reads only the last part of the path, and looks for a top-level field called postcode in the customer model. The field does not exist there, so the developer changes the wrong code. The right decision is to read the whole path from left to right, go into address, and then fix the nested field in the sender's payload. For a list, the number in the path tells you which item to look at.

Trap: Reading only the last part of loc

The last element names the field, but the earlier elements tell you where that field lives. An error at ("address", "postcode") is inside address, not at the top level.

Constraints and serialisation

What it is. model_dump() returns a dictionary of the model's values. model_dump_json() returns a JSON string. model_dump(mode="json") returns a dictionary in which values such as dates have become text. Constraints such as ge=1 are checked when the object is created. Dumping the object does not check them again. The options exclude_none=True and exclude_unset=True leave keys out of the output, and they do different things. The first removes fields whose value is None. The second removes fields that the input did not supply at all.

from datetime import date
from pydantic import BaseModel, Field

class Book(BaseModel):
    title: str
    pages: int = Field(ge=1)
    published: date

b = Book(title="Dune", pages=412, published="1965-08-01")
print(b.model_dump())
print(b.model_dump_json())

The first line prints a dictionary whose published value is a date object, shown as datetime.date(1965, 8, 1). The second line prints the compact JSON string {"title":"Dune","pages":412,"published":"1965-08-01"}. A plain json.dumps(b) would raise a TypeError, because a model is not a dictionary and the date is not JSON-ready.

How it shows up in a case study. A books API must return each record as JSON, with the publication date written as text. A developer writes json.dumps(book) and gets a TypeError. A second developer changes pages on an existing object to 0, dumps it, and is surprised that no error appears. The right decision is to use model_dump_json() for the response, because it produces the text in one step. The second case needs a clear rule: dumping never runs the constraints again, so a value that breaks a rule must be stopped when the object is created, or by re-creating the model with the new values.

Trap: Believing model_dump checks ge=1

model_dump() only reads the values. A constraint such as ge=1 runs at creation, and a later change does not trigger it unless the model is set up to validate assignments.

Missing values and optional fields

What it is. In Pydantic version 2, a field with no default is required, even when its type allows None. The declaration city: str | None means that the key must be present, and its value may be None. The declaration nickname: str | None = None has a default, so the key may be absent. model_fields_set is a set of the field names that the input actually supplied. An empty string is a value, and it is not the same thing as an absent key.

from pydantic import BaseModel

class Profile(BaseModel):
    name: str
    city: str | None
    nickname: str | None = None

p = Profile(name="Ana", city=None)
print(p.model_fields_set)
Profile(name="Ana")

The first print shows the set {'name', 'city'}, in no particular order. The nickname field is missing from the set, because the input did not supply it. The second line raises a ValidationError with the message Field required for city, because city has no default, even though None is an allowed value for it.

How it shows up in a case study. A sign-up form sends "middle_name": "" for some users and leaves the key out for others. The team must decide what each case means. A blank string is a value the user typed, so it is stored as an empty string and the key counts as supplied. An absent key is not a value, so the field should use a default. A second problem is a field such as delivery_note: str | None with no default. The API rejects every request that leaves the key out, even though the team thinks the note is optional. The right decision is to give truly optional fields a default of None, and to treat an empty string as the value it is.

Trap: Allowing None is not the same as optional

The type str | None allows the value None. It does not make the field optional. Only a default makes a field optional, and an empty string is a value, not a missing one.

For validate_reading:

The output is True, because the cleaned text is red.

for text in ["2.5", "two"]:
    try:
        print(float(text))
    except ValueError:
        print("not a number:", text)

The output is 2.5, then not a number: two. The loop does not stop at the bad value, because the except block handles it.

  • Sorting a list. sorted(items) returns a new list in order. The list's own .sort() method changes the list it is called on.

print(sorted(fruit))
print(fruit)

The output is ['apple', 'fig', 'pear'], then ['pear', 'apple', 'fig']. The first line sorts a copy, so the original list is unchanged.

For normalize_reading:

  • Rounding to 2 decimal places. round(x, 2) rounds a number to 2 decimal places. Python rounds an exact half to the nearest even digit, so round(2.5) gives 2, not 3.
print(round(3.14159, 2))
print(round(2.5), round(3.5))

The output is 3.14, then 2 4. The second line shows the even-digit rule with two halves.

  • Building a new dictionary. {**old, "key": new} makes a copy of old with one key changed. The original dictionary is not touched.

print(item["colour"], changed["colour"])

The output is blue red. Your functions must behave in the same way toward the input they receive.

  • Type checks and the bool trap. isinstance(value, int) is True for True, because bool is a subclass of int. When you need to tell a boolean apart from a number, check for bool first.

The output is True True. Both checks are true for the same value, which is why the order of your checks matters.

import math


def to_number(value):
    """Return the value as a finite float, or None."""
    if isinstance(value, bool):
        return None
    if isinstance(value, str):
        try:
            value = float(value.strip())
        except ValueError:
            return None
    if not isinstance(value, (int, float)):
        return None
    if not math.isfinite(value):
        return None
    return float(value)


def normalise_profile(raw):
    """Return a clean dict, or a list of error messages."""
    errors = []
    clean = {}

    username = raw.get("username")
    if not isinstance(username, str) or username.strip() == "":
        errors.append("username: is required")
    elif not 3 <= len(username.strip()) <= 20:
        errors.append("username: must be 3 to 20 characters")
    else:
        clean["username"] = username.strip().lower()

    email = raw.get("email")
    if not isinstance(email, str) or "@" not in email:
        errors.append("email: must contain @")
    else:
        address = email.strip().lower()
        local, _, domain = address.partition("@")
        if local and "." in domain and "@" not in domain:
            clean["email"] = address
        else:
            errors.append("email: is not a valid address")

    age = to_number(raw.get("age"))
    if age is None or age != int(age):
        errors.append("age: must be a whole number")
    elif not 13 <= age <= 120:
        errors.append("age: must be between 13 and 120")
    else:
        clean["age"] = int(age)

    country = raw.get("country")
    if country is None or (isinstance(country, str) and country.strip() == ""):
        clean["country"] = "IN"
    elif (isinstance(country, str) and len(country.strip()) == 2
          and country.strip().isascii() and country.strip().isalpha()):
        clean["country"] = country.strip().upper()
    else:
        errors.append("country: must be a 2-letter code")

    if errors:
        return errors
    return clean

  • import math loads the standard maths module, which provides math.isfinite.
  • to_number turns a value into a finite float, or returns None. The bool check comes first, because True is an int in Python, and a checkbox value should not become the age 1.
  • In to_number, value.strip() removes the spaces, and float() converts the text. The try and except ValueError turn text such as "abc" or an empty string into None, instead of letting the error stop the program.
  • math.isfinite(value) rejects nan and infinity, so "nan" for an age is refused.
  • In normalise_profile, errors collects the messages and clean collects the cleaned values. Using two containers means the function can report every problem at once.
  • The username branch first checks that the value is text with something in it. The elif then checks the length after the spaces are removed. The else stores the cleaned, lower-case name.
  • The email branch checks for @ before it splits the text. partition("@") splits at the first @, and the _ name holds the separator, which the code does not use. A second @ makes the domain contain another @, so the check fails.
  • The age branch calls to_number, then compares the number with its own integer part. 34.0 passes, because 34.0 != 34 is False. 34.5 fails, because the test is True. The int(age) call is safe here, because to_number has already removed nan and infinity.

  • The tests that follow compare whole results. A list comparison checks both the messages and their order, which is the point of the rule.
  • The mutation check copies the input before the call, and compares it afterwards. A function that changes its input would fail this assert.

Say it out loud

Question 1: Why validate with Pydantic rather than with if checks inside each endpoint?

Model answer

Manual checks have to be repeated in every endpoint, and the messages drift apart over time. A Pydantic model declares the rules once, and FastAPI applies them to every request before your code runs. The same rules also show up in the generated API documentation, so the documentation and the code cannot disagree. That is why the course chose Pydantic over hand-written checks.

Question 2: What does extra='forbid' protect against, and why does it matter?

Model answer

It rejects any key that the model does not declare. Without it, a typo such as humidty is dropped silently. If the real field has a default, the request then succeeds with the default value, and the client never learns that its data was ignored. Forbidding extra keys turns that silent failure into a 422 that names the unknown field.

Question 3: Why must a 500 response contain a generic message?

Model answer

The exception text can contain file paths, database query fragments and internal names. Showing those to a client helps an attacker and tells nobody anything useful. The full details belong in the server log, where engineers can read them. The client receives a fixed message and a request ID, and the engineer uses that ID to find the matching log line.

Question 4: A coverage report says 85 per cent. What does that prove, and what does it not prove?

Model answer

It proves that 85 per cent of the lines in the measured package ran during the tests. It does not prove that the tests checked the right results, because a test without an assert can run every line and still prove nothing. It also says nothing about the lines that are missing from the total. Coverage shows where tests did not reach, so the Missing column is the place to start writing the next test.

Question 5: Why use pytest.raises rather than a try block that prints the error?

Model answer

pytest.raises makes the test fail when the error does not happen, and a printed message does not. A try block that prints and moves on always passes, so a broken validation rule would go unnoticed. The with block also marks exactly which line must raise, so the test cannot pass because of some other error. The check becomes part of the suite and runs on every change.
