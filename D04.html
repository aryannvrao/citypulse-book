Day 4 — Bash scripting and cron automation

The idea in one minute

Today you turn a command you type by hand into a recipe card that a machine follows. A Bash script is that card: a text file with the steps written in order, so anyone can run them the same way, every time. cron is the alarm clock. It wakes up at times you choose and tells the machine to follow the card. Together they let the CityPulse air-quality fetch run every 30 minutes while nobody is watching. By the end you will write a script that fails loudly instead of quietly, schedule it, and read its logs to see what happened.

Starting from zero

This section defines every word the day depends on. Read it once now, then come back to it when a term confuses you.

Terminal and shell. A terminal is a window where you type text instead of clicking. The program that reads what you type and runs it is called the shell. Bash (Bourne Again SHell) is the shell used in this course. The line that ends in a dollar sign, such as asha@lab:~$, is the prompt, which is the shell waiting for your next command.

Command, argument and flag. A command is a program name followed by words. In ls -l logs, ls is the command, -l is a flag (an option that changes how the command behaves) and logs is an argument (the thing the command acts on). A flag usually starts with a dash.

File and directory. A file holds data. A directory (also called a folder) holds files and other directories. logs/fetch.log means the file fetch.log inside the directory logs. A slash separates the directory names from the file name.

Variable. A variable is a named container that holds a value. You create one with name=value. There must be no spaces around the equals sign. You read it back with a dollar sign, so $name means "the value stored in name".

Function. A function is a named group of commands. You define it once and call it by name, as many times as you like. A function is the shell version of a reusable step.

Script. A script is a file of commands that the shell runs from top to bottom. Running bash fetch.sh reads the file and carries out each line in turn.

Exit code. Every command ends by reporting a number. 0 means success. Any other number means failure. The shell keeps the number from the most recent command in a special variable called $?.

Standard output, standard error and redirection. A command prints normal results to standard output (stream 1) and problems to standard error (stream 2). Redirection changes where those streams go. > writes output to a file and replaces what was there. >> adds output to the end of a file. 2> sends errors to a file. The | symbol, called a pipe, sends the output of one command into the next.

Server, HTTP and API. A server is a computer that answers requests from other computers. HTTP (Hypertext Transfer Protocol) is the request-and-reply language that web clients and servers use. An API (Application Programming Interface) is a defined set of web addresses and rules that one program uses to ask another for data. curl is a command that sends an HTTP request and prints or saves the reply.

JSON and jq. JSON is a text format for structured data, such as {"station_id": "CP-001"}. jq is a command-line tool that picks values out of JSON.

Process, lock and log. A process is a running program. A lock is a marker that tells other programs "I am busy, wait". A log is a file that records what a program did, one line per event.

cron and crontab. cron is a background program that starts commands at times you choose. Your list of those times is called a crontab (cron table). The crontab command shows or replaces that list.

Environment and PATH. The environment is a set of settings that a program inherits from the program that started it. PATH is one of those settings. It is a list of folders the shell searches, in order, when you type a command name such as jq. If jq is not in a folder on PATH, the shell says command not found.

The tools

Bash strict mode and functions

What it is. Bash is the shell you have just met, and it can also run scripts. Strict mode is three settings you switch on at the top of a script with set -euo pipefail. The set command changes how the shell behaves. Functions are the named steps described above.

Why CityPulse uses it. fetch.sh runs without anyone watching. If a step fails and the script carries on, the data has a gap that nobody notices until the P1 demo. A Bash script with strict mode stops at the first real failure. Two alternatives were considered. A Python script is better for complex logic, and the course moves to Python in a later lesson, but Bash keeps this step close to curl and jq. Plain Bash without strict mode is shorter, but it keeps going after an error and appends empty rows to the data.

How it works. When the shell reads a script, it runs each command and then checks its exit code. With -e the script stops when a command returns non-zero. With -u the script stops when it uses a variable that was never set. With -o pipefail a pipeline counts as failed if any command in it failed, not only the last one. Strict mode does not stop everything. A failure inside an if test is ignored by -e, because the if is designed to handle failure.

Here is the skeleton of scripts/fetch.sh from the lesson slides, with its line breaks restored:

#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.." && mkdir -p logs
log() { printf '%s %s %s\n' "$(date -u +%FT%TZ)" "$1" "$2" >> logs/fetch.log; }
exec 9>"/tmp/citypulse-$(whoami).lock"
if ! flock -n 9; then log WARN "previous run active; skipping"; exit 0; fi
if [ -f ops/STOP ]; then log WARN "ops/STOP present; not fetching"; exit 0; fi
fetch_with_retry() {
  local attempt=1 delay=5
  until curl -sSf --max-time 20 -o "$TMP" "$URL"; do
    if [ "$attempt" -ge 3 ]; then log ERROR "HTTP fetch failed after 3 attempts: $URL"; return 1; fi
    log WARN "attempt $attempt failed; retrying in ${delay}s"
    sleep "$delay"; attempt=$((attempt + 1)); delay=$((delay * 2))
  done
}

Line by line:

  • #!/usr/bin/env bash is the shebang. The two characters #! must be the first two characters of the file. The system reads the path after them and uses that program to run the file. env finds bash on PATH, so the line works on machines where Bash lives in a different folder.
  • set -euo pipefail switches on strict mode, as described above.
  • cd "$(dirname "$0")/.." && mkdir -p logs moves to the repository root. $0 is the path the script was started with, dirname strips the file name to leave the folder, and /.. steps up one level from scripts. The && runs mkdir only if the cd worked. mkdir -p creates logs if it is missing and does nothing if it already exists.
  • log() { ... } defines the log function. $1 is its first argument (the level, such as WARN) and $2 is its second (the message). printf prints the three parts in the format <timestamp> <LEVEL> <message>. date -u +%FT%TZ prints the current UTC time, for example 2026-11-03T14:00:01Z. The >> appends the line to logs/fetch.log.
  • exec 9>"/tmp/citypulse-$(whoami).lock" opens the file in /tmp for writing and attaches it to number 9. whoami prints your user name, so each user gets their own lock file.
  • if ! flock -n 9; then ... fi asks for the lock. flock with -n means "do not wait": if another run already holds the lock, it fails at once. The ! reverses the test, so the block runs when the lock was not obtained. The script logs a warning and exits with 0. The exit is deliberate: skipping an overlapping run is correct behaviour, not an error.
  • if [ -f ops/STOP ]; then ... fi is the kill switch. If someone creates a file called ops/STOP, the script logs a warning and exits before it touches the network. -f is true when the path is a regular file.
  • fetch_with_retry() { starts a function. local attempt=1 delay=5 creates two variables that exist only inside the function. The first attempt is numbered 1 and the first wait is 5 seconds.
  • until curl ...; do repeats the body while curl fails. -s hides the progress bar, -S still shows errors, -f makes curl fail on an HTTP error such as 404, and --max-time 20 gives up after 20 seconds. -o "$TMP" saves the reply to a file. The skeleton uses $TMP and $URL without setting them. In your full file you set both near the top, as lab step 2 describes.
  • The if block gives up after the third failed attempt. It logs one ERROR line and returns 1, which is the function's failure code.
  • The WARN line records each failed attempt before the wait.
  • sleep "$delay" waits, then attempt=$((attempt + 1)) and delay=$((delay * 2)) raise the counter and double the wait. The waits are 5 seconds, then 10 seconds.

Trace the function on a server that is always down. Attempt 1 fails and logs a WARN, then waits 5 seconds. Attempt 2 fails and logs a second WARN, then waits 10 seconds. Attempt 3 fails, the if is true, and the function logs one ERROR. That gives exactly two WARN lines and one ERROR line, which is what Y2-T06 asks you to show.

The next animation steps through a small loop. Each step shows the value of each variable after the line runs.

Trap: Using ((attempt++)) under set -e

In Bash, ((attempt++)) returns a status of 1 when the value before the increment was 0. Under set -e that status stops the script. Write attempt=$((attempt + 1)) instead, as the skeleton does.

Trap: Relative paths under cron

Your terminal may be open inside the repository, but cron starts in your home folder. A path such as logs/fetch.log that works by hand can fail under cron. Change to the repository root at the top of the script, as the skeleton does on its third line.

Trap: Variables inside functions are global

Without local, a variable set inside a function is visible to the whole script and can overwrite a value the rest of the script still needs. Declare variables inside functions with local.

cron

What it is. cron is a background program that starts commands at fixed times. Each line of a crontab has five time fields followed by a command. The five fields are minute (0 to 59), hour (0 to 23), day of month (1 to 31), month (1 to 12) and day of week (0 to 6, where 0 is Sunday). An asterisk * means "every value". */30 in the minute field means every 30 minutes. A comma separates a list, so 1,3,5 means 1, 3 and 5. A hyphen gives a range, so 9-17 means 9 to 17 inclusive.

Why CityPulse uses it. CityPulse needs a reading every 30 minutes for 48 hours before the P1 demo, and nobody can stay awake for that long. cron is already on the lab machines, so no extra service is needed. The alternatives were systemd timers, which give better logs but need system-level set-up that students cannot do on the shared lab, and GitHub Actions, which can be delayed under load and would not put data on the lab. A loop with while true; sleep 1800 dies when your terminal session ends.

How it works. cron wakes up every minute, reads each crontab line, and starts the command when all five fields match the current time. cron runs jobs with a short PATH, with no terminal, and in your home folder. That is why each line changes into the repository by its full path and redirects output to a file.

Here is the crontab line that runs the fetch every 30 minutes, from the lesson:

*/30 * * * * cd /home/asha/citypulse-squad3 && /usr/bin/env bash scripts/fetch.sh >> logs/cron.out 2>&1

Line by line:

  • */30 in the minute field means every 30 minutes, so the job fires at minute 0 and minute 30 of every hour.
  • The four * fields mean "every hour, every day of month, every month and every day of week".
  • cd /home/asha/citypulse-squad3 changes to the repository by its full path. Replace the path with the output of pwd in your own repository.
  • && runs the next command only if the cd succeeded.
  • /usr/bin/env bash scripts/fetch.sh runs the script with Bash. The full path to env is used because cron's PATH is short.
  • >> logs/cron.out appends everything the script prints to a file.
  • 2>&1 sends standard error to the same place as standard output. The order matters: it must come after >>.

You should expect nothing on the screen when cron runs the job. The results appear in logs/cron.out and logs/fetch.log.

Trap: Not redirecting output

Without >> logs/cron.out 2>&1, errors go to the place where cron sends mail or are lost. The job fails and nothing records why. Always append both streams to a file.

Trap: Leaving the test schedule in place

Testing often uses */2, which runs every two minutes. If it stays in the crontab it floods the API. Switch back to */30 when the test is over.

Logging, lock files, logrotate and health checks

What it is. These four pieces make an unattended job observable and safe to leave running. A log records what each run did. A lock file stops two runs from overlapping. logrotate archives old log files so they cannot fill the disk. A health check reads the log and reports, through its exit code, whether the job is still succeeding.

Why CityPulse uses them. The P1 demo injects failures, and the team must diagnose each one from logs/fetch.log in under two minutes. flock and ops/STOP give a kill switch and overlap protection. The alternatives are weaker. PID files are common, but they go stale after a crash. flock releases its lock automatically when the process exits, even after a crash. Manual log cleanup works once, but someone forgets, and the disk fills.

How it works. flock -n 9 in the skeleton holds the lock on file descriptor 9 for as long as the script runs. A health check measures the age of the newest successful line. The lesson's excerpt is:

last="$(grep ' INFO appended' logs/fetch.log | tail -1 | cut -d' ' -f1 || true)"
age=$(( ($(date +%s) - $(date -d "$last" +%s)) / 60 ))
if [ "$age" -ge 120 ]; then echo "CRIT: last success ${age} min ago"; exit 2
elif [ "$age" -ge 60 ]; then echo "WARN: last success ${age} min ago"; exit 1
else echo "OK: last success ${age} min ago"; exit 0; fi

Line by line:

  • grep ' INFO appended' logs/fetch.log keeps only the lines that record a success.
  • tail -1 keeps the last of those lines, which is the newest.
  • cut -d' ' -f1 splits the line on spaces and keeps field 1, the timestamp. || true stops a failure in this pipeline from ending the script when the file has no success lines yet.
  • date +%s prints the current time as seconds since 1970. date -d "$last" +%s converts the logged timestamp to the same unit. The difference, divided by 60, is the age in minutes.
  • The if maps age to status: 120 minutes or more is CRIT with exit code 2, 60 minutes or more is WARN with exit code 1, and anything less is OK with exit code 0. The lesson also defines exit code 3 for UNKNOWN, which is used when the log file does not exist.
Trap: Checking only that the log exists

A log file can exist and still hold nothing but failures. Measure the age of the last INFO appended line, not the file's existence.

Trap: Lock files inside the repository

A lock path inside the repository can be committed to version control or deleted by a cleanup. Use /tmp/citypulse-$(whoami).lock, as the skeleton does.

The worked example

This is the workbook's example, a script called pull_readings.sh that downloads the readings for one day, verifies them, logs the result and runs on a schedule. It has seven stages, and each stage adds one idea. Run them in order, and do not skip ahead.

Goal. Save today's readings to a dated file, log every run, and let cron run the script every hour.

Stage 1. The script with strict mode.

#!/usr/bin/env bash

set -euo pipefail

## stop on error/unset/pipe

curl -sS --fail \
  'https://api.city/v1/readings' \
  -o readings.json

echo "pulled $(wc -c < readings.json) bytes"

Line by line: the shebang picks Bash. set -euo pipefail stops the script at the first failure. The \ at the end of the curl line tells Bash that the command continues on the next line. -sS hides the progress meter but still shows errors. --fail turns an HTTP error such as 404 into a failure. -o readings.json saves the reply to a file. wc -c < readings.json counts the bytes in the file, and $( ... ) places that count into the echo line.

bash -n reads the script and checks its syntax without running it. The && prints syntax OK only if the check passed.

Stage 2. Variables and a dated file.

API_URL="${API_URL:-https://api.city/v1/readings}"
DATE=$(date +%F)
OUT="data/readings/${DATE}.json"
curl -sS --fail "$API_URL" -o "$OUT"
N=$(python3 -c "import json;print(len(json.load(open('$OUT'))))")
echo "ingested $N readings -> $OUT"

Line by line: ${API_URL:-https://...} uses the value of API_URL if one is set, and the default address otherwise. This lets you point the script at a test server without editing it. $(date +%F) prints today's date as 2026-11-03. OUT holds the file name for that day, so each day's pull has its own file and yesterday's data is never overwritten. The curl line is the same as before with the variables in place. The python3 line loads the file as JSON and prints the number of items in the list.

Note that ./pull_readings.sh runs the script only if the file is marked executable, which lab step 6 covers.

Stage 3. An error trap that records failures.

LOG="logs/ingest.log"
on_err() { rc=$?; echo "$(date '+%F %T') FAIL exit=$rc" >> "$LOG"; }
trap on_err ERR
curl -sS --fail "$API_URL" -o "$OUT"

Line by line: LOG holds the log's path. on_err() defines a function. Inside it, rc=$? copies the exit code of the failed command into rc, because $? changes with every command. The echo line writes a timestamped FAIL line. trap on_err ERR tells the shell to run on_err whenever a command fails. ERR is the name of that event. The curl line now has its failure recorded.

curl returns exit code 22 for an HTTP error. The trap copies that number into the log, so the failure is visible the next morning.

Stage 4. Verify the saved file. The workbook uses jq to check the file before anything downstream trusts it.

FILE="data/readings/$(date +%F).json"
jq -r '"readings: \(length)", (.[] | " \(.station_id) \(.pollutant) \(.value)")' "$FILE"

Line by line: FILE holds today's path. jq -r prints raw text without the JSON quotes. length counts the items in the array, and \(length) places that count inside a string. .[] takes each item in turn. .station_id, .pollutant and .value pick the named fields from each item. If the file is not valid JSON, jq fails, and strict mode stops the script.

Three well-formed readings were confirmed for stations CP-001 to CP-003.

Stage 5. A timestamped success line.

echo "$(date '+%F %T') saved $OUT ($N readings)" >>"$LOG"

Line by line: the echo writes the date and time, the word saved, the file path and the reading count. >> appends to the log, so history is kept. Run the script and read the newest line with tail -n 1.

Stage 6. Schedule it hourly. The workbook writes this crontab file:

## CityPulse hourly ingest
## min hour dom mon dow command
0 * * * * cd /opt/citypulse && ./pull_readings.sh >> logs/cron.log 2>&1

The first field is 0, so the job runs at minute 0 of every hour. The other fields are *, so it runs every day. cd /opt/citypulse makes the path absolute, and ./pull_readings.sh runs the script from that folder. >> logs/cron.log 2>&1 keeps both output streams. The workbook installs the file with crontab citypulse.cron. Be aware that this replaces your whole crontab, so the lab uses the append method in step 7 of the hands-on section instead.

Stage 7. Run the whole job once. Run exactly what cron will run, then check the three results.

./pull_readings.sh
bash verify.sh
tail -n 1 logs/ingest.log

Line by line: the first line runs the pull and logs it. The second checks the file's contents. The third shows the newest audit line. Because set -e is active in the scripts, a failure in the first line stops the sequence.

The hands-on lab, step by step

You work in the lab terminal, inside your team's repository. Create folders with mkdir -p scripts logs, and edit files in a plain text editor such as VS Code or nano. Type a command exactly as shown, including spaces and capitals.

Step 1. Start a safe script

Create scripts/fetch.sh and make its first three lines:

#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.." && mkdir -p logs

You should see the file saved with those lines and nothing else yet. Check the syntax with bash -n scripts/fetch.sh. It should print nothing and return to the prompt. Then run echo $?, which should print 0. You know the step worked when bash -n reports no error and the exit code is 0.

Step 2. Take arguments and set variables

Under the three lines, set URL and TMP:

URL="${1:-https://api.city/v1/readings}"
TMP="$(mktemp)"

$1 is the first argument, so bash scripts/fetch.sh https://example.org/x uses that address. If you run the script with no argument, the default is used. mktemp creates an empty temporary file and prints its path. You should see no output when you run bash -n again. You know it worked when echo "$URL" prints the default address after you have sourced the file with . scripts/fetch.sh.

Step 3. Guard preconditions

Add the lock and the kill switch, copying the skeleton from the tools section. Test the kill switch: run touch ops/STOP, then bash scripts/fetch.sh. You should see no network request and a new line in logs/fetch.log ending in ops/STOP present; not fetching. Then run rm ops/STOP. You know it worked when the warning appears only while the file exists.

Step 4. Loop over the stations

Add a station loop that fetches one reading per station:

for id in CP-001 CP-002 CP-003; do
  echo "station $id"
done

for id in takes each word in turn and stores it in id. echo prints the id. When you run bash scripts/fetch.sh, you should see station CP-001, then station CP-002, then station CP-003, in that order. You know it worked when all three appear, one per line.

Step 5. Log and report an exit code

Add the log function and the retry function from the tools section, then call the retry function inside the loop. Run the script against a broken address:

bash scripts/fetch.sh https://api.city/v1/nope
echo $?

The script should log two WARN lines and one ERROR line in logs/fetch.log, and echo $? should print 1. You know it worked when the three log lines are present and the exit code matches the failure.

Step 6. Make it executable and dry-run it

Run chmod +x scripts/fetch.sh. The command chmod +x adds the execute permission. Then run ls -l scripts/fetch.sh. The line should start with -rwxr-xr-x or similar, with x in the permission string. Run ./scripts/fetch.sh once with a valid URL, then tail -5 logs/fetch.log. You should see INFO appended and no ERROR lines.

To dry-run the script without a network call, run bash -n scripts/fetch.sh. It checks the syntax and makes no request. You know the dry run worked when no syntax error is printed.

Step 7. Schedule it with cron

First save the current crontab, then append the line. Replace the path with the output of pwd in your repository:

crontab -l 2>/dev/null > /tmp/cron.asha || true
cat >> /tmp/cron.asha <<EOF
*/30 * * * * cd /home/asha/citypulse-squad3 && /usr/bin/env bash scripts/fetch.sh >> logs/cron.out 2>&1
EOF
crontab /tmp/cron.asha
crontab -l

The first line saves your current crontab to a temporary file. 2>/dev/null hides the error that appears when you have no crontab yet. || true makes the line count as success even then. The cat line appends the job, and <<EOF says that everything up to the next line reading EOF is the text to append. The crontab line installs the file, and crontab -l prints the result. You should see your job in the output. You know it worked when that line appears and, after the next half hour, logs/cron.out has new content.

Tip: Prove the job runs

Do not wait in silence. Temporarily use */2 in the minute field, check one cycle with tail logs/cron.out, then change it back to */30 and run crontab -l again. Leaving */2 in place floods the API.

The shebang line

What it is. The shebang is the first line of a script. It starts with the two characters #! and is followed by the path of the program that should run the file. For a Bash script the line is #!/usr/bin/env bash. When you type ./pull.sh, the system reads those first two characters, starts the named program and gives it the file. The line must be the very first thing in the file. A blank line, a space or a comment above it means the system does not see a shebang at all. /usr/bin/env searches PATH for bash, so the line works on machines where Bash lives in a different folder.

#!/usr/bin/env bash
echo "pulled readings"

Running ./pull.sh prints pulled readings. Running bash pull.sh prints the same line, but there the shebang is ignored, because you have named Bash yourself. Bash also treats the shebang as a comment, since it starts with #.

How it shows up in a case study. The CityPulse squad keeps fetch.sh in Git. Ruth's laptop has Bash installed in a folder other than /bin, and the lab server has it in /bin. Ruth pastes the script into a chat message, and her editor adds a blank first line. On the lab server, Mohan runs ./fetch.sh and the file does not start with Bash through its first line, although bash fetch.sh still works. The right decision is to delete the blank line, so that #!/usr/bin/env bash is the first line again. Keep env, because it lets both machines find Bash.

Trap: A blank line above the shebang

It is tempting to think that Bash skips whitespace, so a blank line does no harm. For the shebang it does. The system reads the first two bytes of the file, so #! must be there and nothing else can come first.

Positional arguments

What it is. Arguments are the values typed after a script name. Inside the script they are numbered. $0 holds the script name, $1 the first argument, $2 the second, and so on. $# holds the number of arguments. "$@" holds all the arguments, each kept as its own word even when it contains a space. Positions above nine need braces, so the tenth argument is ${10}.

#!/usr/bin/env bash
echo "script: $0"
echo "station: $1"
echo "count: $#"

Running ./show.sh CP-001 pm25 prints script: ./show.sh, then station: CP-001, then count: 2. The script name is not counted in $#. The command shift drops $1 and moves every later argument down by one place, so the old $2 becomes $1.

How it shows up in a case study. The squad's backfill.sh takes a station id in $1 and a start date in $2. Priya runs ./backfill.sh CP-004 and forgets the date. Because the script runs with set -u, it stops with an error about an unbound variable at the point where $2 is used. The right decision is to check $# at the top of the script, print a usage line that shows both arguments, and exit with status 1 before the script touches the network or the data folder.

Trap: Writing $10 for the tenth argument

$10 means the first argument followed by a zero, so the script receives the value of $1 with a 0 added. Write ${10} when you need the tenth argument.

Strict mode with set -euo pipefail

What it is. set -e stops the script when a command returns a non-zero exit code. set -u stops it when a variable that was never set is used. set -o pipefail makes a pipeline fail when any command in it fails, not only the last one. Strict mode has one important exception: a failure inside the condition of an if is handled by the if, so -e does not stop the script there.

#!/usr/bin/env bash
set -euo pipefail
false | true
echo "still running"

This script prints nothing. The pipeline false | true fails because of pipefail, so -e stops the script on line 3 and the second echo never runs. Without pipefail, the pipeline would report the status of true, which is 0, and the script would print still running.

How it shows up in a case study. The nightly job runs curl -sS --fail "$URL" | jq '.readings' > data/today.json. The API returns a 404. curl fails, and jq receives nothing and exits with 0, so without pipefail the file is written as empty and the job reports success. The team needs the job to stop. With set -euo pipefail the pipeline fails as a whole, and -e stops the script at that line, so the empty file is never trusted.

Trap: Assuming -e stops for every failure

-e does not stop the script for a failing command used as an if test, and it does not see a failure inside the first command of a pipeline unless pipefail is on. The tempting belief is that strict mode catches everything. Check each case.

Looping over a list with for

What it is. A for loop runs its body once for each word in a list. for id in CP-001 CP-002; do echo "$id"; done prints two lines. The list can also be a pattern such as data/readings/*.json. Bash replaces an unquoted pattern with the names of the matching files before the loop starts, and each name becomes one word. The loop variable keeps its last value after the loop has finished.

for f in data/readings/*.json; do
  echo "$f"
done

If the folder holds 2026-11-01.json and 2026-11-02.json, the output is two lines, one per file, in sorted order. If you add a third file, the loop runs three times without any change to the script.

How it shows up in a case study. The squad counts readings for each station file in one folder. Sam writes for f in "data/readings/*.json" with quotes. The quotes stop the expansion, so the loop receives one word, the text with the star in it. It runs once and reports zero readings for a file that does not exist. The right decision is to remove the quotes around the pattern. Quote the variable inside the loop, as in "$f", to keep names with spaces intact.

Trap: Quoting the pattern

Quotes around a pattern stop the shell from expanding it. The loop then runs once with the literal text, not once per file. Remove the quotes around the pattern and keep quotes around the variable.

Reading a cron schedule

What it is. A crontab line has five schedule fields and then a command. The fields are minute (0 to 59), hour (0 to 23), day of month (1 to 31), month (1 to 12) and day of week (0 to 6, where 0 is Sunday). An asterisk means every value. */n means every n units, counted from zero, so */15 in the minute field fires at 0, 15, 30 and 45. A comma makes a list, and a hyphen makes an inclusive range that includes both ends.

*/30 9-17 * * 1-5 bash scripts/fetch.sh

This line runs the script at minutes 0 and 30 of hours 9 to 17, on Monday to Friday. That is 18 runs a day, from 09:00 to 17:30, and none at weekends.

How it shows up in a case study. The sponsor wants the ingest to run every 30 minutes from 08:00 to 17:30 on working days, and nothing outside those hours. Lee writes */30 8-17 * * 1-5. The minute field handles the 30-minute rhythm, the hour field holds the window, and the weekday field limits the job to Monday to Friday. The other two fields stay as stars, because the sponsor did not mention a day of the month or a month. The decision is to keep the five fields in order and to use the step only in the minute field.

Trap: A step in the wrong field

The line 0 */30 * * * looks like a half-hourly job, but the step is in the hour field. Hours only run from 0 to 23, so */30 matches hour 0 alone, and the job runs once a day at midnight.

The cron environment

What it is. cron starts each job in a minimal environment. The PATH is short, there is usually no terminal, settings in your .bashrc are not loaded, and the working directory is your home folder. A command that works when you type it may not be found under cron. A crontab line such as */30 * * * * jq --version >> logs/cron.out 2>&1 can write command not found to the log when jq is installed in a folder that cron's PATH does not search (on some systems jq is in /usr/bin, which cron does search, so the example depends on where your machine installs it). Three fixes are common: give the full path to the program, set PATH at the top of the script, or load settings from a file such as .env inside the script.

#!/usr/bin/env bash
export PATH="/usr/local/bin:/usr/bin:/bin"
command -v jq

command -v jq prints the path of jq when it can find it, and prints nothing with a failing status when it cannot. Put the PATH line before any command that needs a program, and cron finds the program in the same way your terminal does.

How it shows up in a case study. Dev's script render.sh uses the program convert, which the laptop installs in /usr/local/bin. The same script runs by hand on the laptop, but under cron the log says convert: command not found. The program is installed and works by hand, so the problem is cron's short PATH, not a missing program. The best decision is to set PATH in the script, or give the full path to convert, which needs no change to the crontab. Running cron as root is not needed and would not be safe.

Trap: Running cron as root

Running the job as root would let cron find more programs, but it is unnecessary and unsafe. The fix is a full path or a PATH line in the script, which works for any user.

Conditional operators in tests

What it is. A test written inside [ ] is a command that returns 0 when the condition is true and 1 when it is false. For numbers, the operators are -eq, -ne, -lt, -le, -gt and -ge. For text, use = and !=. && runs the second command only if the first succeeded, and || runs the second command only if the first failed.

attempt=3
if [ "$attempt" -ge 3 ]; then echo "give up"; fi

The output is give up, because 3 is greater than or equal to 3. Changing -ge to -gt would print nothing, because -gt is false for 3.

How it shows up in a case study. The healthcheck computes the age of the last successful fetch in minutes. The rule is that an age of 120 minutes or more is critical. Kofi writes [ "$age" -gt 120 ], and the team is surprised when an age of exactly 120 is reported as a warning. The decision is to use -ge, which includes the boundary value. The quotes around "$age" also protect the test if the variable is empty.

Trap: Using > inside brackets

> inside [ ] is not a comparison. Bash reads it as a redirection and writes the output of the test to a file named after the word on the right. Use -gt for numbers.

Redirecting cron output

What it is. Redirection changes where a command sends its streams. Standard output is stream 1 and standard error is stream 2. > writes to a file and replaces what was there. >> appends to the end of the file. 2>&1 sends stream 2 to wherever stream 1 is going at that point. Redirections are read from left to right, so the order matters.

echo "fetched" >> logs/cron.out 2>&1
ls /missing >> logs/cron.out 2>&1

After both lines, logs/cron.out contains fetched and the error from ls, which reads ls: cannot access '/missing': No such file or directory. Both streams reached the file. Had the second line been written as 2>&1 >> logs/cron.out, the error would have gone to the place where standard output pointed before the redirection, and the file would have held only standard output.

How it shows up in a case study. The cron job runs bash scripts/fetch.sh >> logs/cron.out. A fetch fails and prints an ERROR line on standard error. The log file has nothing new, so the team concludes that no run happened. The decision is to append standard error to the same file by writing >> logs/cron.out 2>&1. The team then reads the file and finds the error line that explains the failure.

Trap: Writing 2>1

2>1 does not mean "send errors to standard output". It writes standard error to a file named 1. To join the streams, write 2>&1.

Command substitution

What it is. $(command) runs the command and puts its output in place of the substitution. Trailing newlines are removed. You can store the result in a variable or put it inside a line of text. Single quotes stop the substitution, so '$(date)' is only the text. Substitution also carries the exit code of the command, which matters when the script uses set -e.

today=$(date +%F)
echo "Report for $today"

On 3 November 2026 the output is Report for 2026-11-03. The %F format prints the date as year, month and day. The command inside the brackets runs first, and its output replaces it before echo runs.

How it shows up in a case study. A script counts the readings in a file with rows=$(wc -l data/readings.csv). The report reads rows: 12 data/readings.csv instead of rows: 12. The problem is that wc prints the file name when the file is passed as an argument, but not when the file is given through input redirection. The decision is to write rows=$(wc -l < data/readings.csv), which gives the count alone, and to keep the substitution in a plain assignment, so set -e sees its exit code.

Trap: local hides the exit code

local status=$(curl -sf "$URL") looks like one step, but local succeeds whatever the command returns. Under set -e the failure is hidden. Declare the variable with local status on one line, then assign it with status=$(...) on the next.

File test conditions

What it is. A file test asks a question about a path and returns true or false. -e is true when the path exists, in any form. -f is true for a regular file. -d is true for a directory. -s is true for a file that is not empty. -x is true for a file with the execute permission. -n tests whether a string is not empty.

if [ -f ops/STOP ]; then echo "stopped"; fi

If ops/STOP exists as a regular file, the output is stopped. If it does not exist, nothing is printed. A directory named ops/STOP would not match -f, which is what you want for a kill switch that is meant to be a file.

How it shows up in a case study. The ingest must skip the run when the kill switch is on, and it must refuse to append to a daily file that is empty, because an empty file would hide the outage. Ines writes [ -e results/day1.csv ] for the empty-file check, and the test passes for an empty file. The correct decision is -s, which is false for an empty file. For the kill switch, the team uses -f, not -e, so a folder with the same name does not stop the job.

Trap: -n on a file path

-n tests whether a string is non-empty. A file path is always a non-empty string, so [ -n ops/STOP ] is always true. Use -f or -s to test the file itself.

The task in plain words

The scenario. The CityPulse ingest script runs from cron. You are porting two parts of its logic into Python, so that both can be tested without a server. The first part decides whether a cron line should run at a given minute and hour. The second part decides whether one air-quality reading is valid. The starter file already contains import re at the top. re is the standard regular expression module, which matches patterns in text.

The three functions. Each function must be written with exactly the name below.

  • parse_cron(line) takes one line of a crontab. It returns a tuple, which is a fixed group of values in parentheses, with six items in this order: minute, hour, dom, month, dow and command. The first five are the schedule fields, kept as text. The command is everything after the fifth field. It may contain spaces, and those spaces must be kept.
  • fires_at(line, minute, hour) returns True when the line's minute field and its hour field both match the numbers you are given, and False otherwise. A field can take one of these forms: * for every value, a plain number, a range a-b that includes both ends, a step */n for every n units counted from zero, or a comma-separated list of any of these. You assume that the day-of-month, month and day-of-week fields always match, so you do not need to check them.
  • valid_reading(reading) returns True only when all of these hold. reading is a dictionary, which is a collection of named values such as {"station_id": "ST1"}. Its station_id matches the pattern ^ST\d+$. Its pollutant is one of pm25, pm10, no2 or o3. Its value is a non-negative number, and a boolean is not accepted as a number. A boolean is the value True or False, and Python counts it as a whole number, which is why it needs its own check.

The statement gives this example, restated here:

line = "*/15 0-6 * * * /opt/citypulse/ingest.sh"
fires_at(line, 30, 3)  # True: 30 is a multiple of 15, and 3 is in 0-6
fires_at(line, 7, 3)   # False: 7 is not a multiple of 15

What each function needs

This section teaches the Python ideas each function uses. Every example is small and uses data that has nothing to do with the lab. Try each one in a Python file or an interpreter before you move on.

Splitting text with str.split. Called with no argument, split breaks text at any run of spaces and ignores leading and trailing spaces.

print("  red   green  blue ".split())  # ['red', 'green', 'blue']

Called with a second argument, split stops after that many splits. The rest of the text stays in the last piece, with its inner spaces intact.

print("red green blue black".split(None, 2))  # ['red', 'green', 'blue black']

Slicing a list. items[:2] takes the items before position 2, and items[2:] takes the items from position 2 to the end. Positions start at 0.

colours = ["red", "green", "blue", "black"]
print(colours[:2])  # ['red', 'green']
print(colours[2:])  # ['blue', 'black']

Returning several values. A function can return a tuple. The caller can unpack it into names in one line.

def shop_totals():
    return 3, 12
apples, pears = shop_totals()
print(apples, pears)  # 3 12

Converting text to a number with int. int("7") gives the number 7. Text that is not a whole number raises a ValueError, which is an error that Python raises when a value has the right type but a wrong content.

print(int("7") + 1)  # 8
## int("x") raises ValueError

Remainders with %. % gives the remainder after division. A remainder of 0 means the first number is an exact multiple of the second.

print(12 % 4)  # 0, so 12 is a multiple of 4
print(13 % 4)  # 1, so 13 is not

Splitting once with partition. text.partition("/") returns three pieces: the part before the first slash, the slash itself, and the part after. If there is no slash, the second and third pieces are empty text.

print("a-b/3".partition("/"))  # ('a-b', '/', '3')
print("a-b".partition("/"))    # ('a-b', '', '')

Sets and sorted. set.update adds many items at once, repeats are dropped, and sorted turns a set into an ordered list.

seen = set()
seen.update([3, 1, 3])
print(sorted(seen))  # [1, 3]

Ranges that include both ends. range(3, 6) gives 3, 4 and 5, because the end is excluded. Include the end by adding one to it.

print(list(range(3, 7)))  # [3, 4, 5, 6]
print(list(range(0, 10, 4)))  # [0, 4, 8], a third argument is the step
print(6 in range(3, 7))  # True
print(7 in range(3, 7))  # False

Checking any item in a list. any returns True when at least one item in a list is true. An empty list gives False.

print(any([False, True, False]))  # True
print(any([]))  # False

Reading a dictionary with get. d[key] raises a KeyError when the key is missing. d.get(key) returns None instead, and d.get(key, default) returns the default.

stock = {"apples": 3}
print(stock.get("pears"))     # None
print(stock.get("pears", 0))  # 0
print("apples" in stock)      # True

Checking a type with isinstance. isinstance(value, int) is True for a whole number. A boolean is also an int in Python, because bool is a subclass of int, which means it is a special kind of integer. So isinstance(True, int) is True, and you must check for bool separately when a boolean should not count.

print(isinstance(True, int))           # True
print(isinstance(True, bool))          # True
print(isinstance(2.5, (int, float)))   # True

Matching a whole pattern with re.fullmatch. re.compile prepares a pattern once. fullmatch returns a match object only when the pattern matches the entire text, and None otherwise.

word = re.compile(r"[a-z]{3}")
print(word.fullmatch("cat") is not None)   # True
print(word.fullmatch("cats") is not None)  # False

Checking membership in a set. A set is written in braces and holds unique values. in checks membership quickly.

print("tea" in {"tea", "coffee"})  # True
print("juice" in {"tea", "coffee"})  # False

A method that works for every graded lab

  1. Read the starter file from top to bottom. Note the names of the functions, the signatures and any imports. Do not change the names.
  2. Write the examples from the statement as assert lines before you write any function. The statement's example for fires_at is a good first set. The lines will fail at first, which is expected.
  3. Add your own assert lines for every row of the table in the previous section. Write the expected answer by hand before you run the code.
  4. Implement one function at a time. After each function, run the file, so that you see which asserts pass and which still fail. Do not start the next function until the current one passes its checks.
  5. Check the types last. This lab has no rounding, but it does have types. Make sure that booleans are rejected, that text is converted before it is compared with a number, and that the function returns True or False and not a value of another type.
  6. Run the visible tests. Read the failure message for each one, and fix the rule it names before you change anything else.
  7. Submit once, after the asserts you wrote yourself also pass. A second submission does not help if you have not found the cause of the first failure.

Worked twin problem

The twin problem. A small company runs a nightly backup scheduler. Each job is one line made of a minute field, an hour field, a weekday field and a command, for example */20 22 1-5 rsync -a /data /backup. Minutes run from 0 to 59, hours from 0 to 23 and weekdays from 0 to 6, where 0 is Sunday. Blank lines and lines that start with # are comments. This is a backup tool, not the CityPulse cron check, but it needs the same skills.

  • split_job(line) returns None for a blank line or a comment. Otherwise it returns a dictionary with the keys minute, hour, weekday and command. The first three fields are separated by spaces, and the command is everything after them, with its inner spaces kept. A line with fewer than four parts raises ValueError.
  • expand_field(spec, low, high) turns one field into the sorted list of the numbers it allows, without repeats. The forms are * (every number from low to high), a plain number, a range a-b that includes both ends, */n and a-b/n (every n-th number, counted from the start of the range), and comma lists of these. A step of zero or less, a number outside low to high, a range whose start is above its end, a step on a plain number and text that is not a number all raise ValueError.
  • runs_at(line, minute, hour, weekday) returns True when all three numbers are allowed by the job's fields. A comment or blank line never runs.
  • valid_log(record) returns True only when record is a dictionary and all of these hold. Its time is text in the form YYYY-MM-DDTHH:MM:SS with a real month (1 to 12), a day from 1 to 31, an hour up to 23, and a minute and second up to 59. Its level is one of INFO, WARN or ERROR. Its message is text that is not empty once spaces are removed. If the record has a size_kb key, it must be a whole number of zero or more and not a boolean.

The solution. Read the code once, then read the explanation. Run it, and check that the message all tests passed appears.

import re

LEVELS = {"INFO", "WARN", "ERROR"}
STAMP = re.compile(r"[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}")


def split_job(line):
    text = line.strip()
    if text == "" or text.startswith("#"):
        return None
    parts = text.split(None, 3)
    if len(parts) < 4:
        raise ValueError("a job needs minute, hour, weekday and a command")
    return {"minute": parts[0], "hour": parts[1], "weekday": parts[2], "command": parts[3]}


def expand_field(spec, low, high):
    allowed = set()
    for item in spec.split(","):
        body, slash, step_text = item.partition("/")
        step = 1
        if slash:
            step = int(step_text)
            if step <= 0:
                raise ValueError("step must be positive")
        if body == "*":
            start, end = low, high
        elif "-" in body:
            first, last = body.split("-", 1)
            start, end = int(first), int(last)
        else:
            if slash:
                raise ValueError("a step needs * or a range")
            start = end = int(body)
        if start < low or end > high or start > end:
            raise ValueError("number outside the allowed range")
        allowed.update(range(start, end + 1, step))
    return sorted(allowed)


def runs_at(line, minute, hour, weekday):
    job = split_job(line)
    if job is None:
        return False
    minutes = expand_field(job["minute"], 0, 59)
    hours = expand_field(job["hour"], 0, 23)
    days = expand_field(job["weekday"], 0, 6)
    return minute in minutes and hour in hours and weekday in days


def valid_log(record):
    if not isinstance(record, dict):
        return False
    stamp = record.get("time")
    if not isinstance(stamp, str) or STAMP.fullmatch(stamp) is None:
        return False
    month, day = int(stamp[5:7]), int(stamp[8:10])
    hour, minute, second = int(stamp[11:13]), int(stamp[14:16]), int(stamp[17:19])
    if not (1 <= month <= 12 and 1 <= day <= 31):
        return False
    if hour > 23 or minute > 59 or second > 59:
        return False
    level = record.get("level")
    if not isinstance(level, str) or level not in LEVELS:
        return False
    message = record.get("message")
    if not isinstance(message, str) or message.strip() == "":
        return False
    if "size_kb" in record:
        size = record["size_kb"]
        if isinstance(size, bool) or not isinstance(size, int) or size < 0:
            return False
    return True


def raises_value_error(function, *args):
    try:
        function(*args)
    except ValueError:
        return True
    return False

Explanation.

  • LEVELS is a set, so membership checks are quick. STAMP is compiled once. It checks only the shape of the time text, which is digits in the right places. The ranges of the numbers are checked separately, because a pattern cannot easily say "01 to 12".
  • split_job removes outer spaces with strip. A blank line becomes the empty text, and a comment starts with #, so both return None. Otherwise split(None, 3) gives at most four parts, and the fourth keeps its inner spaces. Fewer than four parts raises ValueError. The result is a dictionary, so the later code can say job["hour"] instead of remembering positions.
  • expand_field builds a set called allowed, which removes repeats on its own. For each comma-separated item, partition("/") gives the part before the slash, the slash itself and the part after it. When there is no slash, slash is the empty text, so the step stays 1. When there is one, int turns the step into a number, and a step of zero or less raises ValueError.
  • The body then picks the start and the end. A star means the whole range low to high. A hyphen means the two numbers around it. A plain number means start and end are the same number, but a step on a plain number is rejected.
  • The test start < low or end > high or start > end rejects numbers outside the bounds and ranges written backwards. range(start, end + 1, step) includes the end, because range stops before its second argument. sorted turns the set into an ordered list.
  • runs_at returns False for a comment. It expands all three fields before it compares, so a bad field raises an error even when the minute does not match. The final line uses and, so all three must allow their number.
  • valid_log checks the rules in order. It rejects a record that is not a dictionary, then checks that the time is text and has the right shape. It cuts the numbers out of the text by position, because the pattern guarantees where they are. Month, day, hour, minute and second are checked against their limits. The level must be text before the set lookup, so a list cannot crash it. The message must be text with something other than spaces in it. The size_kb key is optional, but when it is there it must be a whole number of zero or more, and a boolean is rejected.
  • raises_value_error is a small helper used only by the asserts. It returns True when the call raises ValueError, which keeps the test lines short.

def average_wait(minutes):
    if len(minutes) == 0:
        raise ValueError("no waits")
    for minute in minutes:
        if isinstance(minute, bool) or not isinstance(minute, int):
            raise ValueError("waits must be whole numbers")
    return round(sum(minutes) / len(minutes), 1)

Say it out loud

Question 1. Why does your script use set -euo pipefail?

Model answer

Strict mode makes the script stop at the first real failure instead of carrying on with bad data. Without it, a failed download can leave an empty file that looks like a success. The -e flag stops on a failing command, -u stops on an unset variable, and pipefail catches a failure anywhere in a pipeline. This matters because the job runs unattended and nobody sees the error until much later.

Question 2. How do you stop two runs from overlapping?

Model answer

The script opens a lock file in /tmp and asks for an exclusive lock with flock -n. The -n means the script does not wait, so a second run gives up at once and logs a warning. The kernel releases the lock when the process exits, even after a crash, so a stale lock cannot block future runs. A PID file would need manual cleanup after a crash.

Question 3. Why does the crontab line use absolute paths and redirect output?

Model answer

cron starts jobs in your home folder with a short PATH and no terminal, so a relative path or a command that you can run by hand may not be found under cron. The line changes into the repository by its full path and calls the script through /usr/bin/env bash. The >> logs/cron.out 2>&1 appends both output streams to a file, because with no terminal there is nowhere else for the errors to go.

Question 4. What does the healthcheck measure, and why not just check the log exists?

Model answer

The healthcheck measures the age, in minutes, of the newest line that records a successful fetch. A log file can exist and still contain only failures, so existence says nothing about success. Mapping the age to exit codes 0, 1, 2 and 3 makes the result readable by a script or a monitoring tool. The lesson's thresholds are 60 minutes for a warning and 120 minutes for critical.

Question 5. Why do you test the exact command cron will run?

Model answer

A script that works only when you run it by hand is not proof that the scheduled job works, because cron's environment differs from your terminal. Running the exact command, with the same arguments and in the same folder, is the only honest check. The workbook's run_all.sh does this, then verifies the file and shows the last log line, so you can see the whole job succeed in one go.
