How to use these ticket guides

These chapters walk through the real tickets on your squad's capstone board, in the order the board schedules them. The ticket text (story, acceptance criteria, test cases, subtasks and definition of done) comes from the course site. The guides teach you how to do each ticket yourself and how your trainer will check it.

How the board works:

  • A ticket moves Backlog, To Do, In Progress, Review, Done. Only a trainer can move it to Done, after running its test cases, and gives it a gate score from 0 to 3.
  • Every ticket is judged from commit evidence: your commits, pull requests and reviews in the squad repository. Work done on someone else's laptop does not count for you.
  • Each ticket has a points value (the "pts" column). Defence tickets (marked D01, D02 and so on) are where you present and answer questions.
  • Your viva scores acceptance criteria met, technical depth, contribution and ownership, and understanding, each 0 to 5. The final capstone grade shown on the platform is 60% your own contribution and 40% your team's.

Y2-T49 · Mini-project review 1: demo baseline, MoSCoW backlog, book mock

Session 49 · phase E11 · 3 points

The ticket in plain words

This ticket is a sprint review for your squad's industry mini-project. The mentor does not want a status update. They want three things: proof that the work done so far really runs, a live demo, and a short list of what comes next.

The ticket is about one danger. The description says past squads lost their deadline to scope creep. That means adding "one more feature" again and again, until the core chain of work is never finished. The core chain is simple to name: the data arrives, a simple baseline runs on it, and the squad has a model that beats that baseline. If that chain is not finished, nothing else matters.

So today the squad does three things. It proves the data and the baseline are real by running them from a clean copy of the repository. It cuts the Must-have items on the backlog to five or fewer, so the remaining sprints go to the core. It also asks every student to book one role-based technical mock interview slot. That booking is an individual task inside this ticket, and the sheet is checked per student.

A baseline is the simplest sensible guess, such as "always predict the median of past values". Your model has to beat it to be worth building. If you cannot say how much better the model is than the baseline, the mentor cannot tell whether the project works.

Before you start

These tickets must already be merged on your squad's main branch. Your trainer assumes them, so check them rather than redo them:

  • Y2-T46: an uptime alert, saved log queries and one measurable service-level objective (SLO).
  • Y2-T47: a grounded GenAI city bulletin prototype.
  • Y2-T48: the live API, the /v1/bulletin endpoint, and the approved mini-project brief.

From Y2-T48 the industry repository already exists. It should hold docs/plan.md, data/README.md, an ingest script (either scripts/fetch.sh or a make ingest target), raw data under data/raw/, and EDA work in notebooks/ or src/eda.py. The CityPulse repository citypulse-<squad> holds src/train.py and an API skeleton that you may reuse.

You need Git, a GitHub account that is a member of the squad's organisation, Python 3, curl and jq, Jupyter if your EDA is a notebook, and access to the LMS and the mock booking sheet.

Where commands run: the lab machine is Linux with bash. On your Windows laptop, use Git Bash. Git Bash maps /tmp to a folder inside your Windows temporary files, so /tmp/t49 still works. If python3 is not found on Windows, try python.

How your trainer checks it

The trainer checks five acceptance criteria. Each one is listed below with the test case that proves it.

Criterion 1: a fresh clone runs the README steps. This is test case TC1.

Criterion 2: reports/baseline.json holds the metric, the value, n_test above zero, and a split_date equal to split.holdout_from. This is test case TC2.

Criterion 3: BACKLOG.md has five or fewer Must-haves, each with an owner and an acceptance line, and at least two Won't-have items with reasons. This is test case TC3.

Criterion 4: docs/sprint-review-1.md quotes the mentor verbatim and has the re-plan for T50 to T52. The trainer reads the file and checks both parts by eye.

Criterion 5: the mock booking sheet (checked at 20:30), filtered by your squad, shows every student with a slot dated 30 March to 22 April and a role track. This is test case TC4.

TC1: fresh clone and README steps.

Command the trainer runs:

git clone https://github.com/citypulse-y2/industry-<squad> /tmp/t49 && cd /tmp/t49 && follow README ingest + EDA steps

Broken into parts:

  • git clone URL FOLDER copies the repository at that address into the folder you name. It fails if the folder already exists and is not empty.
  • /tmp/t49 is the new folder.
  • && runs the next command only if the previous one succeeded. If the clone fails, the trainer stops there.
  • cd /tmp/t49 moves into the new folder, so the next commands run inside the repository.
  • "Follow README ingest + EDA steps" means the trainer copies the commands from the README and runs them in order, with no extra steps.

Passing output: Git prints Cloning into '/tmp/t49'... and returns to the prompt. The ingest step prints its progress. A listing of data/raw/ shows files with today's date in their names. The EDA run ends without a traceback.

Failing output: fatal: destination path '/tmp/t49' already exists and is not an empty directory. The cause is an old folder from an earlier try. Fix it with rm -rf /tmp/t49, then clone again. A line such as ModuleNotFoundError: No module named 'pandas' means the README is missing an install step. Add the step to the README, which is the purpose of subtask T49.1.

TC2: baseline JSON.

Command the trainer runs: python src/baseline.py && cat reports/baseline.json

  • python src/baseline.py runs your script.
  • && runs the second command only when the script exits without an error.
  • cat prints the file's contents to the screen.

Passing output is a JSON object with the four keys metric, value, n_test and split_date. The split_date must match the date in config.yaml. Check it with grep holdout_from config.yaml.

Failing output: FileNotFoundError: [Errno 2] No such file or directory: 'config.yaml'. The script runs from the wrong folder. Run it from the repository root. A split_date that does not match means your script used a hard-coded date instead of reading the config.

TC3: Must-haves in BACKLOG.md.

Command the trainer runs, as the ticket writes it: grep -c '^- ' under the '## Must' heading of BACKLOG.md. The trainer means: count only the bullet lines inside the Must section. A plain grep -c counts the whole file, which would also count Should, Could and Won't items. So use this version, which does what the ticket describes:

sed -n '/^## Must/,/^## /p' BACKLOG.md | grep -c '^- '

  • sed -n prints only the lines it is told to print, and -n stops it printing everything else.
  • /^## Must/,/^## /p prints from the line starting with ## Must down to the next line starting with ##. That range includes the next heading, which is harmless because it is not a bullet.
  • | sends that text into the next command.
  • grep -c '^- ' counts the lines that start with a dash and a space. The ^ anchors the match to the start of the line.

Passing output is a single number of five or fewer, and every Must line shows owner and AC:.

Failing output: a number of six or more. The cause is that the Must section is too long. Move the extra items to Should. Another failure is a Must line without AC:. Add the acceptance line.

TC4: mock booking sheet.

The trainer opens the sheet, filters by your squad, and checks that five of five students are booked. Each slot date must fall between 30 March and 22 April, and each row needs a role track. Passing output is five complete rows. A failing row has no date, a date after 22 April, or no role track. Fix it by booking again within the allowed dates, before the sheet closes.

Do it, step by step

Y2-T49.1: clean-clone README check (QA/DevOps, 15 min)

Goal. A clean clone is a fresh copy of the repository in an empty folder. Nothing on your machine helps it. If the README works in a clean clone, a stranger can run the project. Every command you had to remember and did not write down is a gap to fix.

Stage 1: clone into a fresh folder. Run this on the lab Linux machine or in Git Bash:

git clone https://github.com/citypulse-y2/industry-<squad> /tmp/review
  • git clone copies the repository. The address is the one from the ticket with your squad name.
  • /tmp/review is the folder it creates. If it exists already, delete it first with rm -rf /tmp/review.

Expected output: Cloning into '/tmp/review'..., then the prompt returns. Check it with cd /tmp/review && git log --oneline -1, which prints the latest commit on the branch you cloned.

Stage 2: follow the README and write down every gap. Open /tmp/review/README.md and run each command in order, one at a time. Keep a note of every place where you had to guess, such as a missing install command, a missing folder or an unlisted environment variable. Each guess is a gap.

Stage 3: fix the README on a branch. Make a branch, edit, commit and push:

cd /tmp/review
git switch -c t49-readme-fixes

git switch -c NAME creates a new branch and moves onto it. Your edits then go on that branch, never straight onto main.

Edit README.md in any text editor and add each gap as a numbered step. Then:

git add README.md
git commit -m "docs: add missing README steps found in clean clone"
git push -u origin t49-readme-fixes
  • git add stages the changed file.
  • git commit -m saves it with a one-line message.
  • git push -u origin BRANCH uploads the branch to GitHub. The -u links it so later pushes need no extra words.

Open the pull request on GitHub, and request review from a squad-mate. Do not merge your own PR.

Stage 4: test the fix from another clean clone. Use a new folder, so nothing from the first try is left behind:

git clone https://github.com/citypulse-y2/industry-<squad> /tmp/review2

Follow the updated README from start to finish. Expected result: every step runs with no guessing. Your branch is not on main yet, so clone from the branch with git clone --branch t49-readme-fixes ... if the steps depend on your fix.

Stage 5: prove the trainer's test. Run TC1 exactly as written in the ticket, once the PR is merged.

Y2-T49.2: ingest and row counts (Data, 10 min)

Goal. Show that the raw data is dated and count the rows from each source. Raw data is kept as the source gave it. Counting rows tells you whether the ingest got everything.

Stage 1: run ingest as the README says. The README names the command. It is either bash scripts/fetch.sh or make ingest. A make target is a named command inside a Makefile, and make ingest runs the one called ingest.

Run it from the repository root, then look at the output folder:

ls -l data/raw/
  • ls -l lists files with their sizes and dates.
  • data/raw/ is where the raw files go.

Expected output: one or more files whose names contain today's date. Your ingest script decides the exact file names.

Stage 2: count the rows in one file. If your sources are CSV files, a CSV file has one header line at the top. The rows are the lines after it. Count them like this:

tail -n +2 data/raw/FILE.csv | wc -l
  • tail -n +2 prints the file starting at line 2, which skips the header.
  • | sends that text into wc -l.
  • wc -l counts the lines it receives.

Replace FILE.csv with one of your files. Expected output: a single number, the number of data rows. If the output is one more than you expect, the header was not skipped. Check the first line with head -n 1 data/raw/FILE.csv.

If your raw data is not CSV, change the method to suit the format, and say in the README how the count is made.

Stage 3: write the counts for every source. Make the reports folder, then write one line per file:

mkdir -p reports
for f in data/raw/*.csv; do echo "$f $(tail -n +2 "$f" | wc -l)"; done > reports/ingest_counts.txt
  • mkdir -p reports creates the folder if it does not exist, and does nothing if it does.
  • for f in data/raw/*.csv; do ... done runs the middle part once for each CSV file, with f set to its name.
  • $( ... ) runs the counting command and puts its output into the line.
  • > reports/ingest_counts.txt writes all the lines into that file, replacing its old contents.

Change *.csv if your sources use another extension.

Test this stage. Run cat reports/ingest_counts.txt. Expected: one line per source, each with a path and a row count. Then commit and open a PR:

git add reports/ingest_counts.txt
git commit -m "data: record ingest row counts per source"

Then push the branch and open the PR the same way as in T49.1: git push -u origin BRANCH, with a new branch name (create it first with git switch -c BRANCH if you are still on main, because main is protected). Only reports/ingest_counts.txt is committed. Raw files under data/raw/ may be listed in .gitignore. If your squad's repository ignores them, that is normal, and the README ingest step recreates them.

Y2-T49.3: EDA run top to bottom (Data, 15 min)

Goal. Your EDA must run from the first cell to the last without help. Hidden state is the main danger. A notebook cell can use a variable that an earlier cell, now deleted, once created. Running the notebook from the top in a fresh session reveals this.

Stage 1: Restart and Run All. In Jupyter, open the notebook, then choose Kernel and then Restart and Run All (the menu wording differs a little between JupyterLab and classic Notebook, so look for the Restart and Run All entry). This clears all variables and runs every cell in order. Expected: every cell shows a number in its brackets and no red error text. A red error means a cell depends on something that is not in the notebook.

If you run EDA as a script, use python src/eda.py instead, and check that it exits with no error.

To run the notebook from the command line, use nbconvert, which ships with Jupyter:

jupyter nbconvert --to notebook --execute --inplace notebooks/eda.ipynb
  • jupyter nbconvert converts a notebook. Here it converts a notebook to a notebook.
  • --execute runs every cell in order, in a fresh session.
  • --inplace writes the result back to the same file.

Replace notebooks/eda.ipynb with your notebook's name. Expected output: a line saying the notebook was converted and written. An error printed from a cell means that cell fails when run from the top.

Stage 2: write the findings. A finding is a fact from the data that changes how you would model it. It has three parts: what you saw, the number that shows it, and what it means for the model. Write each finding as one bullet, with the three parts in that order.

Here is a fictional example about a different project, to show the shape only. Do not copy it:

- Missing values: 14 percent of one sensor column are empty, and they cluster on weekends. The model needs a rule for those rows, or a weekend flag.

Write three or four findings from your own data in docs/eda-findings.md.

Test this stage. Run Restart and Run All once more after your edits. Then count the findings with grep -c '^- ' docs/eda-findings.md. Expected: three or four.

Y2-T49.4: the naive baseline (Backend, 20 min)

Goal. Write src/baseline.py. It reads the holdout date from the config, splits the data, predicts with the simplest rule, measures the error, and writes reports/baseline.json.

Two techniques are new, so learn each one first.

Technique A: reading YAML. YAML is a settings format. Reading it needs the PyYAML package, which is not in the standard library. Install it once:

python3 -m pip install pyyaml

On Windows, use python -m pip install pyyaml. Then try this small example, which reads one key:

import yaml

with open("config.yaml") as f:
    cfg = yaml.safe_load(f)

print(cfg["split"]["holdout_from"])
  • import yaml loads the package.
  • with open("config.yaml") as f: opens the file and closes it at the end of the block.
  • yaml.safe_load(f) turns the text into a Python dictionary, a named collection of values.
  • cfg["split"]["holdout_from"] goes into the split section and then reads the holdout_from key.

Expected output: the date exactly as written in config.yaml. Watch out for an unquoted date such as 2025-07-01. PyYAML turns that into a date object, not a string. If your JSON must hold a string, convert it with str(...).

Technique B: a naive baseline and writing JSON. A naive baseline predicts one simple value for every test row. The median of the training values is one common choice. Choose yours and write it in the README, so the trainer can see it.

The next example uses made-up numbers. It shows the arithmetic, not your answer:

import statistics

def naive_median(train_values):
    """Predict the median of the training values for every test row."""
    return statistics.median(train_values)

def mean_absolute_error(actual, predicted):
    """The average size of the mistake, in the same units as the values."""
    return sum(abs(a - predicted) for a in actual) / len(actual)

train = [10, 20, 30]
test = [12, 18, 40]
guess = naive_median(train)
assert guess == 20
assert mean_absolute_error(test, guess) == 10

Trace the loop in mean_absolute_error for the same example. Each error is the absolute difference from the guess of 20:

The abs function removes the sign, so that an error below the guess and an error above it both count. That is why MAE is the average size of the mistake.

Next, write the JSON. Python's json module writes a dictionary as JSON text:

import json

result = {"metric": "MAE", "value": 10.0, "n_test": 3, "split_date": "2025-06-01"}
print(json.dumps(result, indent=2))
  • json.dumps turns the dictionary into JSON text. json.dump with a file would write it straight to the file.
  • indent=2 puts each key on its own line, indented by two spaces, so a person can read it.

Expected output: the same four keys printed as JSON. The values here are made up. Your values come from your data.

Stage A: read the config. Use technique A to get split.holdout_from into a variable.

Stage B: load the data. Read your raw data with pandas, which is a data library. Install it with python3 -m pip install pandas. Then read the file you chose in T49.2, and print its first few rows with print(df.head()). Expected: a table of rows with your column names.

Stage C: split by date. Find the column with the dates, and keep the rows on or after the holdout date as the test set. The training set is everything before it. Your date column name is your own choice. Print len(test) and check that it is above zero.

Stage D: predict and measure. Compute the naive guess from the training values, then the MAE on the test rows.

Question 1: Why did you cap the Musts at five?

A Must is an item the product fails without. If every item is a Must, nothing is sorted, and the team has no way to choose what to drop when the deadline arrives. The limit of five forces a decision. Model answer

A naive baseline is cheap to build and easy to explain. Its weakness is that it is only a floor. A stronger baseline would take more time to build, which costs sprint capacity that the core chain needs. The trade-off is that a simple baseline is fast and honest, and the next ticket decides whether the gap between it and the model justifies the effort.

A notebook keeps variables in memory between cells, so a cell can work only because an earlier run left a value behind. Stage B: build the Pipeline. The model class is your squad's choice. Ridge is only an example.

from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import OneHotEncoder, StandardScaler
from sklearn.linear_model import Ridge
numeric = [c for c in features if pd.api.types.is_numeric_dtype(train[c])]
categorical = [c for c in features if c not in numeric]
preprocessor = ColumnTransformer([

])
model = Pipeline([("preprocessor", preprocessor), ("model", Ridge(alpha=1.0))])

Line by line: the numeric and categorical lists split the features by column type. Technique first: a FastAPI endpoint. Try this in a scratch folder, not the repository. It is a different problem.

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class Item(BaseModel):
    name: str
    count: int

@app.get("/ping")
def ping():
    return {"status": "ok"}

@app.post("/double")
def double(item: Item):
    return {"name": item.name, "double": item.count * 2}

The class lists the fields and their types. Each @app line attaches a function to an address, and FastAPI checks every request body against the class. Start it with uvicorn main:app --port 8000 from the folder that holds the file. Then in a second terminal:

A text value such as "four" for count would be rejected with a 422 and a detail list. That is the behaviour /predict relies on.

Stage 1: load the model once, at startup. Loading a model takes time, so do it once, not on every request. Open api/main.py and add this block above the route definitions. It needs pip install joblib in your environment if it is not there.

import os
from contextlib import asynccontextmanager
import joblib
from fastapi import FastAPI

state = {}

@asynccontextmanager
async def lifespan(app):
    path = os.environ.get("MODEL_PATH", "models/model.joblib")
    state["model"] = joblib.load(path)
    yield
    state.clear()

app = FastAPI(lifespan=lifespan)

Line by line: os.environ.get reads MODEL_PATH and falls back to the default if it is unset. Code before yield runs at startup, and joblib.load reads the model file once. state holds the model for the routes.

How your trainer checks it

Your trainer runs four test cases, TC1 to TC4, in order, and checks the five acceptance criteria against what they find. Here is each test case, broken into its parts.

TC1: no open blockers.

  • gh issue list asks GitHub for a list of issues.
  • -R atria-y2/industry-<squad> names the repository. -R means repository, so you do not need to be inside the clone.
  • -l blocker keeps only issues with the label blocker. -l is short for --label.
  • --state open keeps only issues that are still open.

Passing output is an empty list. The terminal prints nothing, or a message such as no issues match your search. Failing output is a list of issue numbers and titles. The usual cause is a blocker that was closed in your head but never closed on GitHub, or a blocker with no link to the PR that fixed it.

TC2: the tests pass on a fresh clone.

  • git clone <url> <folder> downloads the whole repository into a new folder. The folder must not exist yet.
  • cd moves into that folder.
  • pytest -q runs every test it finds. -q means quiet, so you see dots and a summary rather than every name.

Each dot is one passing test. The last line gives the count and the time. Your count will differ. Look for the words test_api and the 422 case in the verbose output if the trainer asks: pytest -v shows each name.

A failure tells you the name of the test and what it expected. Here, a request that should have been rejected was accepted. The usual cause is that the payload in the test is actually valid, or that the endpoint does not validate its input.

TC3: the runbook works on a clean clone.

The trainer deletes everything, clones the repository again and follows HANDOVER.md line by line. They do not ask anyone for help. Passing output is that the stack starts and make smoke ends with a success message. A failing step is usually a command that is missing from the runbook, a file that is created by a step you did not write down, or a command that works only on your laptop.

The exact message depends on your Makefile. What matters is that it ends without an error.

TC4: the contribution statement matches Git.

  • git log --author='<student>' lists only the commits made under that name. Use the name exactly as it appears in git log.
  • --oneline prints one line per commit.
  • | wc -l counts those lines. The pipe sends the output of the first command into the second.

Passing output is a number above zero. The trainer then opens each PR your statement cites. Failing output is zero, or a PR link that belongs to someone else, or a PR you only commented on and then described as authored.

Stage 2: loop over every module. First list the module folders your repository has, using ls in the clone. Then run a loop. Replace the folder names in the first line with your own.

for m in src api tests; do
  n=$(git log --format='%an' -- "$m" | sort -u | wc -l)
  echo "| $m | $n |"
done
  • for m in src api tests; do starts a loop. m takes each folder name in turn.
  • n=$(...) runs the command inside the brackets and stores its output in n. The $(...) form is called command substitution.
  • echo "| $m | $n |" prints one Markdown table row.
  • done ends the loop.

Expected output:

Any module with a number of 1 needs a second owner.

  echo "| $m | $n |  |  |"
done | tee -a docs/module-owners.md

The row now has four cells, so it matches the header below: the last two cells are empty for you to fill in by hand. tee -a appends, so running the loop again adds a second set of rows rather than replacing the first. Delete the old rows before you run it again. If the file is new, write the header first, with the columns Module, Distinct authors, Second owner and Notes, and the separator line under it:

| Module | Distinct authors | Second owner | Notes |
|---|---|---|---|

Y2-T52.4: tests in CI

Goal. Add three test files, run them in ci.yml, and make CI fail when they fail. The trainer's TC2 and the 422 criterion depend on this.

New technique: pytest. pytest finds every file named test_*.py and every function named test_*. Inside each function you write assert. If the condition is false, the test fails and pytest shows the values.

Here is a small example from a different project, so you can see the shape. It is not part of CityPulse.

## test_units.py, a toy example from a different project
def to_celsius(fahrenheit):
    return (fahrenheit - 32) * 5 / 9

def test_freezing_point():
    assert to_celsius(32) == 0
  • def to_celsius(...) is the function under test.
  • def test_freezing_point(): is one test. pytest runs it because the name starts with test_.
  • assert to_celsius(32) == 0 passes if the result is 0, and fails with the actual value if not.

Run it with pytest -q test_units.py. Expect one dot and 1 passed.

New technique: TestClient for the API. FastAPI provides a test client that sends requests straight to the app. It needs the httpx package, so install it first if the test complains about a missing module.

from fastapi.testclient import TestClient
from api.main import app

client = TestClient(app)
  • from fastapi.testclient import TestClient imports the helper.
  • from api.main import app imports the FastAPI application object from the file api/main.py.
  • client = TestClient(app) wraps the app so that client.post(...) and client.get(...) can be called from a test.

Stage 1: the data test. In tests/test_data.py, write one test at a time. Start with the row count, because it is the simplest:

import pandas as pd

def test_has_enough_rows():
    df = pd.read_parquet("<the file your pipeline writes>")
    assert len(df) >= 500
  • import pandas as pd loads the table library and gives it a short name.
  • pd.read_parquet(...) reads the file into a table. Replace the placeholder with the path your pipeline from Y2-T51 writes.
  • len(df) >= 500 counts the rows. The test fails if there are fewer than 500.

Then add the schema and the range checks, one test each. A schema test checks that the expected columns exist. A range test checks that each value lies between the limits your squad agreed. Write the limits in the test, not in your head, so the next person can see them.

Stage 2: the model test. In tests/test_model.py, pick one row whose correct output you know, and check the model returns it. Store the row in the test itself so it is always the same. The expected value must come from a run you recorded, not from a guess.

Stage 3: the API test. In tests/test_api.py, write two tests. The first sends a valid request and expects status code 200. The second sends a request with a missing field and expects 422.

def test_missing_field_returns_422():
    r = client.post("<your endpoint>", json={})
    assert r.status_code == 422
  • client.post("<your endpoint>", json={}) sends an empty JSON body to the endpoint.
  • r.status_code is the HTTP status code the server returned.
  • assert r.status_code == 422 passes only if the server rejects the body with 422.

422 means FastAPI checked the request and found required fields missing or of the wrong type. Use the endpoint name from api/main.py. The body must actually be invalid for your endpoint, or the test proves nothing.

Stage 4: run the tests locally.

If one fails, run pytest -q tests/test_api.py on its own, so the output is short, and read the message.

Why must the runbook be run on a clean clone before it is merged?

Model answer

A clean clone has none of your local files, environment variables or installed packages. If a command works only on your machine, the clone shows that. A command that has never been run is a guess, and a handover built on guesses fails the first time a stranger uses it. Running it fresh is the only test that matches what the next person will do.

What is the trade-off between leaving a known issue open and fixing it before handover?

Model answer

Fixing everything before handover can delay sign-off and add risk late in the project. Leaving a problem open is acceptable when it is written down with its cause, its effect and the next step, and when it is not a blocker. A blocker must be closed by a merged PR or a documented won't-fix, because it would stop the next person from running the system. A should or nice issue can stay open in Known issues, as long as the reader can see it.

Why is a second owner who did not write the module better than the module's most active author?

Model answer

The bus factor asks whether a second person can explain and run the module without the author. The most active author knows the module best, but that is the problem, because they are also the one who might leave. A second owner who did not write it has to read the code, the runbook and the tests to understand it. That is the test that proves the module can survive a departure, so the choice is deliberate.

Why does the test suite include a 422 case and not only a 200 case?

Model answer

A 200 case shows that the API works when the input is good. A 422 case shows that it refuses bad input, which is how a client learns that its request was wrong. Without the 422 test, a change could make the API accept anything and still pass, and the first person to send a bad request would find the fault in production. Testing the rejection path protects the contract the client depends on.

  • refs/tags/v1\.0 matches the tag name. The backslash makes the dot a literal dot, not "any character".
  • (\^\{\})? is an optional group that matches the text ^{}. The backslashes stop the brackets and the caret from having their special meaning. The ? makes the group optional.
  • $ means the end of the line, so v1.0.1 does not match.

The command prints two lines for an annotated tag: the tag object, and the peeled line that names the commit. A lightweight tag prints only one line, and that line is the commit. Then the trainer compares the commit with the remote HEAD:

git ls-remote "$REMOTE" HEAD

This prints one line, the SHA of the remote's HEAD. Its SHA must match the peeled SHA from the first command.

Passing means: the ^{} SHA and the HEAD SHA are identical. Git prints a tab between the code and the name, so the terminal shows them spaced out.

What a failing output looks like, and its usual cause:

  • No lines at all: the tag was never pushed. Someone created it locally but did not run git push origin v1.0.
  • Two different SHAs: someone committed to main after tagging. The fix is in the section on the release, not in a new tag.
  • No lines, but git ls-remote --tags "$REMOTE" (without the grep) shows a similar name such as V1.0 or v1: the tag was made under a different name. Check the spelling. The $ in the pattern stops v1.0.1 from matching.
  • A Permission denied or sign-in prompt: your Git sign-in is missing. Sign in yourself.

Y2-T54.1: confirm the tag and write the release

Goal. The tag v1.0 exists on the remote, it names the current main commit, and a GitHub Release page describes it. Nothing is committed after it.

Stage 1: fetch the remote tags and the latest main. Run these from inside your clone:

git fetch origin --tags
git switch main
git pull

Line by line: git fetch origin --tags downloads the remote's tags and commits without changing your files. git switch main moves you onto main, and git pull brings it up to date. You should see Already up to date. or a short list of new commits.

Stage 2: check that no commit comes after the tag. Run:

git log --oneline v1.0..origin/main

The v1.0..origin/main notation means "commits that are on origin/main but not on v1.0". The output must be empty. If lines appear, those commits came after the tag, and the tag does not match the code that the mentors will check.

Count them with git rev-list --count v1.0..origin/main, which must print 0.

Stage 3: create the annotated tag, if it is missing. Only do this if TC1 shows no v1.0 line. Run:

git tag -a v1.0 -m "CityPulse v1.0: frozen for the P10 mentor review"
git push origin v1.0

Line by line: git tag -a v1.0 creates a tag called v1.0 on the commit you are on, which is main. The -a makes it annotated. -m "..." gives the tag its message. git push origin v1.0 sends the tag to the remote called origin. Without the push, the tag exists only on your laptop, and the trainer cannot see it. The output of the push ends with a line that contains [new tag].

Trap: Never move a tag that was pushed

If v1.0 already exists on the remote and points at the wrong commit, do not run git tag -f and do not delete and recreate it. The mentors may already have seen the old commit. Tell your trainer, and the fix is a new tag such as v1.0.1 through the rework route.

Stage 4: write the GitHub Release. In the browser, choose Releases, then Draft a new release, pick the existing tag v1.0, and add a title and notes. Or use the command-line tool:

gh release create v1.0 --verify-tag --title "CityPulse v1.0" --generate-notes

Line by line: --verify-tag stops the command if the tag is not on the remote. --title sets the page title. --generate-notes fills in notes from merged pull requests, which you then edit so they say what the release contains and what it does not. You should see a URL at the end.

Test this stage. Run TC1 again. The two SHAs must still match.

Y2-T54.6: restructure your DSA repo, only if signed

Goal. Your dsa-<name> repo follows the D11 standard: a README index, one folder per pattern, a complexity docstring in each solution, and green pytest.

The technique: test first, then tidy. Run the tests before you move anything, then move files in small steps and test after each step.

Stage 1: run the tests and record the result.

cd dsa-<name>
python -m pytest -q

Line by line: cd moves you into your DSA folder, and python -m pytest -q runs every test quietly. Keep the last line, which says passed or failed. If pytest is missing, run python -m pip install pytest.

Stage 2: make a pattern folder and move one file with history. git mv moves a file and keeps its history:

mkdir -p two_pointers
git mv sum_pairs.py two_pointers/sum_pairs.py
python -m pytest -q

Line by line: mkdir -p two_pointers makes a folder, and -p means "no error if it already exists". The file name sum_pairs.py is an example, so use your real file names. git mv renames the file in Git's records, so git log --follow can still show its history. The final pytest run must still pass. If it fails with ModuleNotFoundError, an import in a test points at the old path. Fix the import, then run the tests again.

Stage 3: write a README index. List each pattern folder and its files, one line each, in the same format.

Stage 4: add a complexity docstring. A docstring sits right under the def line, in triple quotes. Here is a worked example with a different, simple task, counting vowels:

def count_vowels(text):
    """Return how many a, e, i, o, u letters are in text, in either case.

    Time: O(n), where n is the length of text.
    Space: O(1), because the string of vowels has a fixed size.
    """
    vowels = "aeiouAEIOU"
    total = 0
    for ch in text:
        if ch in vowels:
            total += 1
    return total

assert count_vowels("") == 0
assert count_vowels("CityPulse") == 3
assert count_vowels("AEIOU") == 5
assert count_vowels("rhythm") == 0

Line by line: def count_vowels(text): defines the function. The triple-quoted text under it is the docstring. Time: O(n) says the work grows in step with the length of the text. Space: O(1) says the extra memory does not grow. vowels = "aeiouAEIOU" stores the letters to look for. The for loop visits each character once, and the if adds one when it finds a vowel. The four assert lines are the checks. When the file runs, it prints nothing and the checks pass. An AssertionError would show that one check failed. Note that rhythm has no vowels, because y is not in the list.

Now do the same for your own solutions. Your docstring must state the pattern name and the complexity for every solution.

Stage 5: check the annotations. This command lists files that have no O( text, so you can find the gaps:

grep -L 'O(' */*.py

Line by line: grep -L lists files that do not match. 'O(' is the text to find. The */*.py pattern means every Python file one folder down. An empty output means every file has a complexity note. Test files may appear in the list. That is fine if they are not solutions.

Test this stage. Run python -m pytest -q again. It must end with passed and no failed.

Defend it in the viva

The viva is a short oral check. The trainer asks a question, you answer, and the trainer may ask a follow-up. The five questions below cover why, a trade-off, what you personally did, your understanding and the evidence.

1. Why does the tag have to name the same commit as main HEAD?

Model answer

The mentors judge one exact version, and the tag names it. If HEAD moves after the tag, a sign-off would cover code the mentors never saw. The check compares the two commits, so any drift shows at once.

2. What is the trade-off between a frozen tag and a quick fix after a review?

Model answer

Freezing keeps the reviewed code unchanged, so the review stays trustworthy. The cost is slower fixes: a new tag and a new review, inside the 72-hour rework window. A quick fix on main would hide the change from the mentors, so it is not acceptable.

3. What did you personally do in this ticket?

Model answer

A strong answer names one subtask, the commits you made for it and the pull request where a squad-mate reviewed them. It says what each commit changed and how you tested it. It never claims work that is not in git log.

4. How do you answer a mentor's question when you do not know the answer?

Model answer

Clarify first: restate the question and ask one short question if it is unclear. Then answer in two or three sentences, and say where your knowledge stops. Give evidence for the part you are sure of. An honest limit with a named check is better than a guess.

5. What does your DSA annotation prove, and what does it not prove?

Model answer

It proves you named the pattern and stated the time and space complexity, so a reader can check your reasoning. It does not prove speed on large inputs, because Big-O is a claim about growth, not a measured time. Correctness needs the tests.
