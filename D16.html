The idea in one minute

Today you learn to make a program fast by choosing the right container for the data. A sensor feed can hold millions of readings. A program that compares each new reading with every earlier one will run for hours, but the same job done with the right structure takes seconds. The fix is usually not faster hardware. It is a better structure: a set that remembers what you have seen, a dictionary that counts, a window that reuses its last sum, and a deque that keeps only the candidates that can still win.

Think of a school register. To find out whether Asha is present, you could read every name from the top of the list each time. Or you could look at a sign-in sheet that already groups the names. By the end of today you will name the right structure for a stream problem, state how much time and memory it needs, and check the answer with code the computer runs for you.

Starting from zero

This section explains the words used in the rest of the chapter. Read it once before the tools.

Terminal. A window where you type text instructions and press Enter. Each line you type is a command. The terminal prints the result underneath.

File. A named piece of text saved on disk. A Python file ends in .py and contains instructions for the Python language. readings.py is a file.

Program. A file of instructions that a computer runs. You run a Python program with the command python3 readings.py. python3 is the program that reads the Python file and carries out its lines in order.

Variable. A name that points at a value. total = 0 creates a variable called total holding the number 0. Later you can write total = total + 5 to change what it holds.

Function. A named block of code you run by writing its name with round brackets. def creates one. In def rolling_avg(values, k): the words values and k are parameters, the inputs the function receives. return sends a result back to whoever called the function.

List. An ordered collection written in square brackets, such as [40, 52, 61]. Each item has a position, called its index. Indexes start at 0, so values[0] is 40. The index -1 means the last item. values[1:4] is a slice: the items from index 1 up to, but not including, index 4.

Tuple. A fixed collection written in round brackets, such as ("S1", 0, "PM25", 40). Once made, a tuple cannot be changed. That property matters for sets and dictionaries.

Loop. Code that repeats for each item in a collection. for v in values: runs the indented lines once for each item, with v set to that item.

Dictionary (dict). A collection of key-value pairs written in curly brackets, such as {"S1": 5}. The key "S1" finds the value 5. counts[key] reads a value, and counts[key] = 6 writes one. counts.get(key, 0) returns the value, or 0 if the key is missing, and does not raise an error.

Hash. A whole number that Python computes from a key. Python uses the hash to decide where in memory to store the key, so it can find the key again without looking at every other key. A key must be hashable, meaning Python can compute a hash for it. Numbers, strings and tuples are hashable. Lists and dictionaries are not.

Set. A collection of unique items, written set() or {1, 2, 3}. Adding an item that is already present does nothing. The test key in seen asks whether the item is in the set.

Stack. A collection where you add and remove items at one end only. The last item added is the first one removed. This rule is called LIFO, last in, first out. A Python list works as a stack: append adds an item at the end, and pop removes and returns the last item.

Deque. Short for double-ended queue, written deque. It is a collection that adds and removes items at both ends quickly. You create one with from collections import deque. Its methods append, pop, appendleft and popleft each take constant time.

Window. A run of neighbouring items, such as values[2:5]. A sliding window is a fixed-size window that moves one place to the right at a time.

Stream. Data that arrives one item at a time, in order, and is too long to hold in your head. Sensor readings are a stream.

Import. A line such as from collections import Counter that brings a ready-made tool from the standard library into your file. You do not write these tools yourself.

Assert. A line such as assert total == 6 that checks a condition. If the condition is true, Python does nothing and moves on. If it is false, Python stops with an AssertionError.

Domain words. A station is a sensor site, identified by a station_id such as S1. A pollutant is a substance measured, such as PM25 (fine particles) or NO2 (nitrogen dioxide). A timestamp or ts is the hour of the reading. SQL is the query language for databases. A SQL window view is a saved query that computes a value over neighbouring rows, which the course uses as the reference answer.

The tools

Big-O notation

What it is. Big-O describes how the work an algorithm does grows as the input size n grows. It ignores constant factors and keeps only the fastest-growing term. Work that grows by 10 when n grows 10 times is O(n). Work that grows by 100 when n grows 10 times is O(n^2). The same idea applies to memory, which is called space.

Why CityPulse uses it. The CityPulse feed must be deduplicated on 10 million rows. An O(n^2) nested loop would not finish in a sensible time, but an O(n) pass over a set will. Every DSA solution in the course must carry a header comment such as # time: O(n) space: O(n), because examiners and interviewers ask for it. Big-O is the language you use to justify a choice.

Alternatives and trade-offs. You can simply time your code. Timing on small inputs hides growth, so use timing to confirm a Big-O prediction, not to replace it. A profiler such as cProfile finds the slow function in real code, but it does not tell you whether a better algorithm exists.

How it works. Count the basic operations each input element costs. Write the total as a function of n. Keep the fastest-growing term and drop constants. Then repeat for memory.

The timing code below is from the course. It shows why the choice of container matters.

import timeit

## membership: list scans every element O(n); set hashes O(1) on average
for n in (10_000, 100_000, 1_000_000):
    data = list(range(n))
    lookup = set(data)
    t_list = timeit.timeit(lambda: -1 in data, number=50)   # worst case: absent
    t_set = timeit.timeit(lambda: -1 in lookup, number=50)
    print(f"n={n:>9,}  list {t_list:.4f}s  set {t_set:.6f}s  ratio {t_list / t_set:,.0f}x")

Line by line:

  • import timeit brings in the standard timing tool.
  • The comment lines begin with #. Python ignores them. They are for the reader.
  • for n in (10_000, 100_000, 1_000_000): runs the block three times, with n set to each size. The underscores in numbers are only for readability.
  • data = list(range(n)) builds a list of the numbers 0 to n-1.
  • lookup = set(data) builds a set holding the same numbers.
  • timeit.timeit(lambda: -1 in data, number=50) times the test -1 in data fifty times and returns the total seconds. The lambda: creates a small unnamed function that holds the test. The number -1 is never in the data, so the list must check every item.
  • The same test on lookup is timed the same way.
  • The print line uses an f-string: text with values inside braces. {n:>9,} right-aligns n in nine spaces with commas between thousands. {t_list:.4f} prints four decimal places.

Expected output: three lines, one per size. The list time grows roughly tenfold each time n grows tenfold. The set time stays tiny. The exact numbers depend on your computer, but the ratio grows with n.

Trap: Hidden loops

x in my_list, my_list.index(x) and slices such as values[i-k:i] each scan many items. Inside a loop they quietly turn an O(n) program into O(n^2). Count these as loops when you write the Big-O.

Trap: Average is not guaranteed

Hash lookups are O(1) on average. In the worst case they can be much slower. Say "O(1) average" in a viva, and be ready to state the worst case.

Trap: Ignoring memory

A set of 10 million tuples can use gigabytes. Time is not the only cost. Always state the space as well.

Hash maps and sets

What it is. A hash map, written as a Python dict, stores key-value pairs. A set stores keys only. Both compute a hash of the key to jump straight to the slot where the key lives. Insert, lookup and delete take O(1) on average. This makes two questions cheap: "Have I seen this before?" and "How many of each do I have?"

Why CityPulse uses it. Duplicate readings are found by putting (station_id, timestamp, pollutant) tuples in a set during one pass. collections.Counter ranks the top five stations by reading count without sorting the whole file. The alternative is to sort the rows first. Sorting costs O(n log n) and needs only O(1) extra space, so it is useful when memory is tight, but it is slower than hashing. The pandas functions drop_duplicates and value_counts also use hashing internally. The course uses them only as a timing comparison.

How it works. Each row becomes a tuple key. Python hashes the key to pick a slot. If another key lands in the same slot, Python compares the keys for equality to resolve the clash. A membership test therefore does not scan the other keys. A new key is inserted, and a counter for its station goes up by one. most_common(k) returns the k most frequent pairs.

The course code below is the first real CityPulse program in this chapter. It is saved as applied/dedup_topk.py.

import csv, sys, time
from collections import Counter

def dedup_topk(path: str, k: int = 5) -> tuple[int, list[tuple[str, int]]]:
    # time: O(n)  space: O(n)  -- one pass, set/dict operations O(1) average
    seen, dupes, counts = set(), 0, Counter()
    with open(path, newline="") as f:
        for r in csv.DictReader(f):
            key = (r["station_id"], r["timestamp"], r["pollutant"])
            if key in seen:
                dupes += 1
                continue
            seen.add(key); counts[r["station_id"]] += 1
    return dupes, counts.most_common(k)

t = time.perf_counter()
print(dedup_topk(sys.argv[1]), f"{time.perf_counter() - t:.2f}s")

Line by line:

  • import csv, sys, time brings in three standard tools. csv reads comma-separated files, sys gives access to command-line arguments, and time measures elapsed seconds. The comma between the names is allowed on one line.
  • from collections import Counter imports the counting dictionary.
  • def dedup_topk(path: str, k: int = 5) defines a function. path is the file name, passed in as text. k: int = 5 means k is an integer that defaults to 5 if the caller does not give one.
  • The return annotation -> tuple[int, list[tuple[str, int]]] says the function returns a pair: a count of duplicates, and a list of (station, count) pairs. Annotations are notes for the reader and for tools; Python does not enforce them. The tuple[...] form needs Python 3.9 or later.
  • The comment states the cost. It is for the interviewer, not the computer.
  • seen, dupes, counts = set(), 0, Counter() creates three things in one line: an empty set, the number zero, and an empty counter.
  • with open(path, newline="") as f: opens the file and calls it f. The with block closes the file automatically at the end. newline="" stops Python from mangling line endings inside the csv module.
  • for r in csv.DictReader(f): reads one row at a time. Each row r is a dictionary whose keys are the column headings, so r["station_id"] reads the station column.
  • key = (r["station_id"], r["timestamp"], r["pollutant"]) builds the duplicate key as a tuple. A tuple is hashable, so it can go in a set. A list would fail.
  • if key in seen: asks whether this key has appeared before.
  • dupes += 1 adds one to the duplicate count. += means "add to what is already there".
  • continue skips the rest of the loop body and moves to the next row.
  • seen.add(key) records the new key. counts[r["station_id"]] += 1 adds one to that station's count. The semicolon lets two statements share one line.
  • return dupes, counts.most_common(k) returns the number of duplicates and the top k stations.
  • The last two lines time the call. sys.argv[1] is the first word typed after the script name on the command line, which is the file path. f"{...:.2f}" prints the seconds to two decimals.

Expected output when you run python3 applied/dedup_topk.py followed by a CSV path: one line showing a tuple, the duplicate count and a list of station pairs, then a time such as 0.12s. Your numbers will differ. The shape is what matters.

Trap: A list as the seen collection

If you write seen = [], then key in seen scans the whole list each time. The loop becomes O(n^2). Use set().

Trap: A list as a key

Dict and set keys must be hashable. Convert a row to a tuple before using it as a key.

Trap: The wrong key

Duplicates are defined by station, timestamp and pollutant together. A key of station_id alone would drop almost every reading.

Read the flow as a story. Node 2 is the only place where a row can stop. Duplicates leave the pipeline there, so everything after it does less work.

Two pointers and sliding windows

What it is. Two pointers move through a sequence from the ends, or at different speeds, so you avoid nested loops. A sliding window is a special case. You keep a running summary of the window, such as its sum, count or set of items. Each step adds the item entering the window and removes the item leaving it.

Why CityPulse uses it. A 6-hour rolling average over n hours drops from O(n*k) to O(n) with a running sum. The result must match the SQL window view AVG(value) OVER (ORDER BY ts ROWS BETWEEN 5 PRECEDING AND CURRENT ROW) to two decimal places, including the partial windows at the start. The alternatives are pandas rolling(), which is fast and correct for analysis, and SQL window functions, which are the ground truth in the course database but are not suited to a live stream. Week 21 asks you to write the algorithm yourself to show that you understand it.

How it works. The window starts with the sum of the first k values. Each later step adds the new value and subtracts the value that slid out. Every element is added once and removed once, so the pass is O(n). For partial windows at the start, the average divides by the number of values seen so far, which is min(i + 1, k).

The slide version of the function is below. It produces partial windows, which matches the SQL view.

def rolling_avg(values: list[float], k: int = 6) -> list[float]:
    # time: O(n)  space: O(n) output. Partial windows at the start, like
    # AVG(value) OVER (ORDER BY ts ROWS BETWEEN 5 PRECEDING AND CURRENT ROW)
    out, total = [], 0.0
    for i, v in enumerate(values):
        total += v
        if i >= k:
            total -= values[i - k]          # value that slid out of the window
        out.append(round(total / min(i + 1, k), 2))
    return out

assert rolling_avg([4, 2, 12, 3, 8, 1], k=3) == [4.0, 3.0, 6.0, 5.67, 7.67, 4.0]

Line by line:

  • def rolling_avg(values: list[float], k: int = 6) -> list[float]: defines the function. It takes a list of numbers and a window size k, which defaults to 6 hours. It returns a list of numbers.
  • The two comment lines state the cost and the SQL rule it copies.
  • out, total = [], 0.0 creates an empty output list and a running total. 0.0 is a float, a number with a decimal point.
  • for i, v in enumerate(values): loops over the values. enumerate gives both the position i and the value v at each step.
  • total += v adds the new value to the window sum.
  • if i >= k: is true once the window is full, so there is a value to drop.
  • total -= values[i - k] subtracts the value that is k positions back. That value has just left the window.
  • round(total / min(i + 1, k), 2) divides the sum by the number of values in the window. min(i + 1, k) is the smaller of "values seen so far" and "window size". round(..., 2) keeps two decimal places.
  • out.append(...) adds the result to the list.
  • return out sends the whole list back to the caller.
  • The assert line checks the function on the course's test input. If the result differs in any position, Python raises an error and stops. If it matches, nothing is printed.

Expected output: running the file prints nothing, because the assert passes. Printing rolling_avg([4, 2, 12, 3, 8, 1], k=3) shows [4.0, 3.0, 6.0, 5.67, 7.67, 4.0].

Trap: Dividing by k at the start

Dividing by k for the first k-1 rows gives a different answer from SQL. SQL averages the rows it has. Divide by min(i + 1, k).

Trap: Comparing floats with ==

Floating-point numbers are approximate. Round both sides to two decimal places before you compare them with the SQL export.

Trap: Assuming six rows equal six hours

A window of rows is not a window of time. If an hour is missing from the feed, the window quietly spans more than six hours. Document the gaps.

Stacks and deques

What it is. A stack adds and removes items at one end, in last-in-first-out order. A deque adds and removes at both ends in O(1). A monotonic structure keeps its items in a sorted order, increasing or decreasing, by removing the items that can never matter again.

Why CityPulse uses it. A stack answers "what was the most recent spike?" in O(1), because the newest item is on top. For the 6-hour rolling maximum of PM2.5, a monotonic deque gives O(n). The alternative, max(values[i-k+1:i+1]) at every position, is O(n*k) and wasteful on a stream. heapq can also find window maxima in O(n log k) with lazy deletion, but it is slower and fiddlier than the deque. A Python list with pop(0) is O(n) per call, because every remaining item shifts one place. deque.popleft() is O(1).

How it works. The deque stores indexes whose values decrease from front to back. A new value first removes every smaller value from the back, because those can never be the maximum again. Then it joins the back. The front index is dropped when it leaves the window. So the front is always the current maximum, and each index enters and leaves once.

First, the stack code from the course. It is saved as spike_stack.py.

from readings import READINGS

THRESH = 60

spikes = []  # list used as a stack

for station_id, ts, _p, v in READINGS:
    if v > THRESH:
        spikes.append((station_id, ts, v))  # push

print(f"{len(spikes)} spikes over {THRESH}")
print("most recent:", spikes[-1])  # peek, O(1)
print("pop ->", spikes.pop())
print("pop ->", spikes.pop())

Line by line:

  • from readings import READINGS brings in the list of 12 readings from the file readings.py. You build that file in the lab. A file's name without .py is its module name.
  • THRESH = 60 names the threshold. A capital name signals a value that does not change. It is a convention, not a rule.
  • spikes = [] creates an empty list, which will act as the stack.
  • The for line unpacks each four-item tuple into four names. _p is named with an underscore to show that it is not used. The pollutant is ignored in this program.
  • if v > THRESH: keeps only readings above 60.
  • spikes.append((station_id, ts, v)) is the push: it adds the reading on top of the stack.
  • len(spikes) returns the number of items. The f-string prints it.
  • spikes[-1] peeks at the top item without removing it.
  • spikes.pop() removes and returns the top item. The first pop returns the most recent spike, and the second pop returns the one before it.

Expected output, from the course:

Four readings are above 60: the two S1 PM25 readings of 61 and 70, and the two S3 NO2 readings of 90 and 88. The last one pushed is the one at hour 3 of S3, so it is on top.

Now the deque. This is the core of the day's graded skill. The slide version is saved in applied/rolling_window.py.

from collections import deque

def rolling_max(values: list[float], k: int = 6) -> list[float]:
    # time: O(n) -- each index is pushed and popped at most once; space: O(k)
    dq, out = deque(), []                    # indices; their values decrease front->back
    for i, v in enumerate(values):
        while dq and values[dq[-1]] <= v:
            dq.pop()                         # smaller values can never be the max again
        dq.append(i)
        if dq[0] <= i - k:
            dq.popleft()                     # front index has left the window
        out.append(values[dq[0]])
    return out

assert rolling_max([4, 2, 12, 3, 8, 1], k=3) == [4, 4, 12, 12, 12, 8]

Line by line:

  • from collections import deque imports the double-ended queue.
  • def rolling_max(values: list[float], k: int = 6) defines the function, with the same parameters as the average.
  • dq, out = deque(), [] creates an empty deque for indexes and an empty output list. The two names are assigned on one line.
  • for i, v in enumerate(values): loops over positions and values.
  • while dq and values[dq[-1]] <= v: repeats while the deque is not empty and the value at its back is no bigger than the new value. dq[-1] is the last index in the deque. values[dq[-1]] is the value stored there. and means both parts must be true.
  • dq.pop() removes the back index. That value can never again be the maximum, because the new value is bigger and will stay in the window longer.
  • dq.append(i) adds the current index to the back.
  • if dq[0] <= i - k: checks whether the front index is now outside the window. The window covers indexes from i - k + 1 to i, so an index less than or equal to i - k has left.
  • dq.popleft() removes that front index in O(1).
  • out.append(values[dq[0]]) records the front value, which is the maximum of the window.

Expected output: the assert passes, so nothing is printed. Calling rolling_max([4, 2, 12, 3, 8, 1], k=3) returns [4, 4, 12, 12, 12, 8].

Trap: Storing values instead of indexes

If the deque holds values, you cannot tell when the front has left the window. Store indexes and look up the values.

Trap: pop(0) on a list

list.pop(0) shifts every remaining item, which is O(n) per call. Use deque.popleft().

Trap: Expiry test with < instead of <=

The front expires when its index equals i - k. With < it would stay one step too long, and the window would be one item too big.

Now the timing claim from the course. The course benchmark compares a naive recalculation with the sliding window on 200,000 readings and a window of 720. The naive version re-adds each window, and the sliding version reuses the running sum. The readings here are integers, so the running sum is exact and the two answers compare equal with ==.

import time

def naive(v, k):
    return [sum(v[i-k:i]) / k for i in range(k, len(v) + 1)]

def windowed(v, k):
    w = sum(v[:k])
    out = [w / k]
    for i in range(k, len(v)):
        w += v[i] - v[i - k]
        out.append(w / k)
    return out

stream = [(i * 37) % 100 for i in range(200_000)]
k = 720

t = time.perf_counter(); a = naive(stream, k); tn = time.perf_counter() - t
t = time.perf_counter(); b = windowed(stream, k); tw = time.perf_counter() - t

print("same result?", a == b)
print(f"naive O(n*k): {tn*1000:7.1f} ms")
print(f"window O(n) : {tw*1000:7.1f} ms")
print(f"speedup:  {tn/tw:5.1f}x")

Line by line:

  • naive(v, k) builds each window from scratch with sum(v[i-k:i]). That slice is k items long, and sum adds them all, so the total work is O(n*k).
  • windowed(v, k) starts with the first window sum and then updates it once per step, as in rolling_avg.
  • stream = [(i * 37) % 100 for i in range(200_000)] builds a list comprehension, which is a short way to write a loop that builds a list. % gives the remainder after dividing, so the values are between 0 and 99.
  • t = time.perf_counter(); a = naive(stream, k); tn = ... records the start time, runs the naive function, and stores the elapsed seconds in tn. The semicolons put several statements on one line.
  • The two print lines show the comparison, the times in milliseconds, and the speedup.

Expected output, from the course:

The times depend on your machine. The 39x ratio is the point. The structure, not the code, made the difference.

Trap: Floats can drift

This benchmark is exact because the values are integers. If the readings were decimals, a running sum that adds and subtracts many floats can drift by tiny amounts. Compare with rounding, as in the trap in the sliding-window section.

def rolling_avg(values, k):
    window = sum(values[:k])               # first window sum
    out = [window / k]
    for i in range(k, len(values)):
        window += values[i] - values[i-k]  # add new, drop old
        out.append(window / k)
    return out

    print(round(a, 1))

    # time: O(n)  space: O(n)

Two-sum with a hash set

What it is. The two-sum problem asks whether any two numbers in a list add up to a target. The slow way compares every pair with two nested loops, which costs O(n squared). A set gives a faster way. For each number x, check whether target minus x is already in the set. Then add x to the set. A set lookup takes O(1) on average, so one pass costs O(n).

seen = set()
target = 10
for x in [3, 7, 4]:
    if target - x in seen:
        print("pair found:", target - x, x)
    seen.add(x)

Running this prints pair found: 3 7. When x is 7, the number 3 is already in the set, and 3 plus 7 makes 10. The number 4 finds nothing, because 6 has not appeared. The set does not keep the positions of the numbers, so it can tell you that a pair exists, but not where the pair sits in the list. If the question asks for positions, store a dictionary from value to index instead.

How it shows up in a case study. A calibration team has 50,000 readings from a sensor array. A fault code is raised when two different readings add up to a fixed correction value. A junior engineer writes a loop that compares each new reading with every earlier reading. On a laptop the first thousand rows finish quickly, but the full file takes many minutes. The team asks why the time grows so fast. The answer is the nested comparison: every new row causes a scan of all earlier rows. Replacing the scan with a set lookup makes each row a single check, so the work grows with n rather than n squared. The correct decision is to change the data structure, not to buy a faster machine.

Trap: Pairing an element with itself

If you add x to the set before checking, then a target of twice x finds x itself. Check first, then add.

Sliding windows with a running sum

What it is. A sliding window is a run of neighbouring items of fixed size k. A running sum keeps the total of the window. Each step adds the item that enters on the right and subtracts the item that leaves on the left. Every item is added once and removed once, so the whole pass is O(n). Recomputing the sum from scratch at each position costs O(n times k) instead.

data = [2, 5, 1, 6]
k = 2
window = sum(data[:k])
sums = [window]
for i in range(k, len(data)):
    window += data[i] - data[i - k]
    sums.append(window)
print(sums)

The first window is 2 plus 5, which is 7. At i equal to 2, the code adds 1 and removes 2, so the total becomes 6. At i equal to 3, it adds 6 and removes 5, so the total becomes 7. The output is [7, 6, 7]. The loop starts at k because that is the first index that has an item k places back to remove.

How it shows up in a case study. A noise monitor sends one value every minute, and the dashboard shows the 30-minute average at every minute. The team's script calls sum on a 30-item slice each minute. It works for an hour of data, but the nightly job over two days runs too long. The problem is not the average itself. Each minute repeats 30 additions that the previous minute already made, and the windows overlap almost completely. Keeping a running total turns the repeated work into one addition and one subtraction per minute. The right decision is to update the total, not to rebuild it.

Trap: Recomputing the window

If the loop calls sum(values[i - k:i]) at every step, the cost stays at O(n times k). The total has to be updated, not rebuilt.

Counting with a dictionary

What it is. A dictionary can count items in one pass. The code counts[key] = counts.get(key, 0) + 1 reads the current count, which is 0 if the key is new, adds one, and stores the result. The Counter class from the collections module does the same job and adds a method called most_common. Each update costs O(1) on average. The space needed is O(d), where d is the number of distinct keys, not the number of rows.

from collections import Counter

fruits = ["fig", "apple", "fig", "kiwi", "fig"]
counts = {}
for f in fruits:
    counts[f] = counts.get(f, 0) + 1
print(counts)
print(Counter(fruits).most_common(1))

The first print shows {'fig': 3, 'apple': 1, 'kiwi': 1}. Dictionaries keep the order in which keys first appeared. The second print shows [('fig', 3)], the single most frequent item. most_common(k) gives the k most frequent items, which is quicker than sorting the whole table when k is small.

How it shows up in a case study. A monitoring team wants to know which station and pollutant pairs raise the most alerts. Their first report counts alerts by station only, so the PM25 and NO2 alerts from the same station are added together, and the totals look wrong. The fix is to change the key. The question asks for totals per pair, so the key must contain both fields, as a tuple. Once the key is correct, the same single loop gives the right totals. A common mistake is to change the loop, when the real fault is in the key.

Trap: Using the wrong key

Counting by station when the question asks for station and pollutant together gives totals that look plausible and are wrong. Read the question for the exact grouping.

Matching pairs with a stack

What it is. A stack adds and removes items at one end only. The last item pushed is the first item popped, which is called last in, first out. Matching nested pairs such as brackets needs this order. Each opening symbol is pushed. Each closing symbol must match the item on top of the stack, and that item is popped. At the end the stack must be empty.

pairs = {")": "(", "]": "["}
stack = []
for ch in "([)]":
    if ch in "([":
        stack.append(ch)
    elif not stack or stack.pop() != pairs[ch]:
        print("mismatch at", ch)
        break
else:
    print("ok" if not stack else "unclosed")

The loop pushes the opening bracket ( and then [. When it meets ), the top of the stack is [, which does not match (. The program prints mismatch at ) and stops. The else block of the for loop runs only when the loop finishes without a break, which is how the program reports a valid line.

How it shows up in a case study. A calibration tool writes a log in which blocks can sit inside other blocks. Each block opens with ( and closes with ). The checker reports an error when a block closes before the blocks inside it. The team thinks the problem is a missing line in the log. The real fault is that the checker treats the blocks as a queue, so it pairs the oldest open block with the new close. Nested blocks need the most recent open block to close first, which is the stack rule. Once the checker uses a stack, the same log passes.

Trap: Forgetting the empty check

A closing symbol with an empty stack has nothing to match. Check that the stack is not empty before you pop, or the code raises an error.

Variable-size windows

What it is. A variable-size window changes its length while the program runs. The right end moves forward to add an item. The left end moves forward to remove items while a condition is true. This works when all values are zero or positive, because adding a value can only raise the total and removing a value can only lower it. Each index moves forward at most once, so the whole pass is O(n).

nums = [2, 1, 5, 2, 3, 2]
target = 7
left = 0
total = 0
best = None
for right, x in enumerate(nums):
    total += x
    while total >= target:
        size = right - left + 1
        best = size if best is None else min(best, size)
        total -= nums[left]
        left += 1
print(best)

The program prints 2. The shortest run with a total of at least 7 is the pair 5 and 2, which sums to 7. The loop records the length of each run that meets the target, then removes the leftmost value so the search can look for a shorter run. The check while total >= target is what allows the left end to move.

How it shows up in a case study. A health team wants the shortest stretch of consecutive hours in which the total dose of a pollutant reaches a safety limit. Doses are never negative, because the sensors only record exposure. An analyst tries every start hour and every end hour and sums each stretch from scratch. For a month of hourly data the run takes too long. The window method fits the question: grow the stretch at the right, and shrink it at the left while the total is still at the limit. Each hour is passed once by each end, so the cost is O(n). The key fact that makes this safe is that no dose is negative.

Trap: Negative values

The shrink-while-true rule assumes that removing a value lowers the total. A negative value breaks that assumption, so read the question for this condition before you pick the window method.

Prefix sums for range totals

What it is. A prefix array stores the running total up to each position. The usual layout is P[0] equal to 0, and P[i] equal to the sum of the first i values. The total of the values from index l to index r inclusive is then P[r + 1] minus P[l]. Building the array costs O(n) once. Each range total after that costs O(1).

values = [3, 1, 4, 1, 5]
P = [0]
for v in values:
    P.append(P[-1] + v)
print(P)
l, r = 1, 3
print(P[r + 1] - P[l])

The first print shows [0, 3, 4, 8, 9, 14]. The second print shows 6. The values from index 1 to index 3 are 1, 4 and 1, which add up to 6. The formula P[4] minus P[1] gives 9 minus 3, which is also 6. The line P.append(P[-1] + v) uses the last item of the array, so each new total is built from the one before it.

How it shows up in a case study. A city dashboard answers many questions about the total pollution between two hours, such as "from hour 2 to hour 5". The analysts ask about 500 different ranges each day. The first version adds the values again for every question. It is slow because the same readings are added over and over. A prefix array does the work once. After one pass to build it, each question is a subtraction. The decision is to precompute the running totals, because the same data is queried many times.

Trap: The off-by-one index

With P[0] equal to 0, the total from index l to index r inclusive is P[r + 1] minus P[l]. Subtracting P[r] drops the last value of the range.

Next greater with a monotonic stack

What it is. A monotonic stack is a stack that keeps its items in a sorted order by removing the items that can no longer matter. For a question such as "what is the next higher reading?", the stack holds the indexes of readings that are still waiting for a higher value. When a new reading arrives, every waiting index whose reading is smaller is answered and popped. Then the new index is pushed. Each index is pushed once and popped at most once, so the total cost is O(n).

temps = [3, 1, 4, 2]
answer = [-1] * len(temps)
stack = []
for i, t in enumerate(temps):
    while stack and temps[stack[-1]] < t:
        answer[stack.pop()] = t
    stack.append(i)
print(answer)

The output is [4, 4, -1, -1]. The reading 3 waits, then 1 waits above it. The reading 4 arrives and answers both waiting readings, so both get the answer 4. The readings 4 and 2 have no later higher value, so they keep the value -1. The answer list uses the position of each waiting reading, which is why the stack stores indexes and not values.

How it shows up in a case study. A monitoring team wants, for every day in a month, the next day that has a higher reading. A junior writes a nested loop that checks each later day. On a month of data, the first day may be compared with up to 29 later days, the second with up to 28, and so on, so the total grows with the square of the number of days. The stack method handles the same question in one pass. Each day waits on the stack until a higher day arrives, then it is answered and removed. The total number of pushes and pops is about twice the number of days, so the cost is O(n).

Trap: Storing values, not positions

If the stack stores readings instead of indexes, the answer cannot be written to the right position in the result list, because the stack no longer says where each reading sits.

Removing duplicates with a set

What it is. A set stores unique keys. Checking whether a key is already present, and adding it, each cost O(1) on average. To remove duplicates, build a key from the fields that define a duplicate, check the key against the set, and keep the row only when the key is new. The key must be hashable, which means Python can compute a stable hash for it. A tuple is hashable. A list is not.

rows = [("A", 1), ("B", 1), ("A", 1), ("A", 2)]
seen = set()
kept = []
for row in rows:
    if row in seen:
        continue
    seen.add(row)
    kept.append(row)
print(kept)

The output is [('A', 1), ('B', 1), ('A', 2)]. The third row is dropped because its tuple is already in the set. The fourth row is kept, because ('A', 2) is different from ('A', 1). The list kept keeps the rows in the order they first appeared, while the set does the checking.

How it shows up in a case study. A city alarm feed sometimes sends the same event twice. The support team wants a rule that counts each real event once. The first draft uses only the alarm code as the key, so two different alarms with the same code, raised in different minutes, are removed as duplicates. The cause is a key that is too coarse. The question defines a duplicate as the same source, code and minute together, so the key must hold all three fields. A tuple of those three fields goes into the set, and the events that differ in any field are kept.

Trap: A key that is too coarse

Using only the alarm code merges events from different minutes. The key must contain every field the question names.

Window extremes with a monotonic deque

What it is. A deque, short for double-ended queue, adds and removes items at both ends in O(1). Python provides it as collections.deque. A monotonic deque stores indexes in an order chosen by their values, and removes the items that can no longer win. For a window maximum, the values decrease from front to back. The front is always the largest value in the current window. The front is removed when its index is too old to be in the window. Each index enters and leaves the deque at most once.

from collections import deque

dq = deque([5, 6, 7])
dq.append(8)
dq.popleft()
print(dq)

The output is deque([6, 7, 8]). The method append adds 8 at the back. The method popleft removes 5 from the front in O(1). The method name pop with a left is the one to remember. A list's pop(0) also removes the front, but it shifts every other item and costs O(n).

How it shows up in a case study. A dashboard raises an alert when the highest PM2.5 reading in the last six hours passes a limit. The first version calls max on the six-hour slice at every hour. It is correct, but it repeats the same comparisons for overlapping slices and slows as the stream grows. A deque of indexes gives the answer more efficiently. The team must also store indexes rather than readings, so the code can tell when the front has left the window. Read the question for whether it asks for the maximum or the minimum, because the order inside the deque changes.

Trap: Expiry with the wrong comparison

The front expires when its index is at most i minus k. A strict less-than test keeps it one step too long, and the window becomes one item too big.

Amortised analysis

What it is. Amortised analysis averages the cost of operations over a whole sequence of steps. A single step can be expensive, but the total cost across all steps is what sets the bound. In a stack or a monotonic deque, one new item may pop many waiting items, so one step may cost O(n). Because each item is pushed once and popped at most once, the total number of pops over n steps is at most n. The average cost per step is therefore constant, and the whole run is O(n) amortised.

stack = []
pushes = 0
pops = 0
for x in [5, 6, 1, 7]:
    while stack and stack[-1] < x:
        stack.pop()
        pops += 1
    stack.append(x)
    pushes += 1
print(pushes, pops, len(stack))

The program prints 4 3 1. The value 6 pops one item, and the value 7 then pops two items (the 1 and the 6) in one step, which is the expensive step. Across all four steps, though, the pops total 3, and there were 4 pushes. The total work is bounded by a small multiple of the number of steps, which is the point of the analysis.

How it shows up in a case study. A monitoring tool processes a long stream of readings. One reading occasionally flushes a large batch of waiting items, and an engineer reports that the tool is quadratic because one step takes a long time. The claim is wrong. The flush removes items that were added earlier, and each item is removed once. Counting the total work across the run shows that the cost is linear. The correct wording for a report is that the whole run is O(n) amortised, while a single step may take O(n).

Trap: Confusing one expensive step with the total

"A step can take O(n)" does not mean the algorithm is O(n squared). Count the total operations across all steps.

What each function needs

Each function uses a few Python ideas. Each idea is taught below with a small example that has nothing to do with the lab's data. Try each example in a Python shell before you use the idea in the lab.

Overwriting a dictionary value. Assigning to a key that already exists replaces its value and keeps the key where it was:

prices = {}
prices["apple"] = 3
prices["apple"] = 5
prices["pear"] = 2
print(prices)

The output is {'apple': 5, 'pear': 2}. The apple key appears once, and its value is the last one assigned. A dictionary keeps keys in the order they were first added. This is useful when you want one record per key, and the newer record replaces the older one only when a rule says so.

Comparing tuples. Python compares two tuples item by item, from left to right. The first items decide the order unless they are equal, and only then are the second items compared:

print(("apple", 1) < ("apple", 9))
print(("apple", 9) < ("pear", 2))
print(sorted([("pear", 2), ("apple", 9), ("apple", 1)]))

The output is True, then True, then [('apple', 1), ('apple', 9), ('pear', 2)]. The first comparison is decided by the second item, because the first items are equal. The second comparison is decided by the first item alone. The sorted function returns a new list in this order and leaves the original list unchanged.

Sorting with a key. The sorted function accepts a key argument that tells it what to compare. This does not change the items, only the order:

words = ["banana", "fig", "cherry"]
print(sorted(words, key=len))
print(sorted(words))

The output is ['fig', 'banana', 'cherry'], then ['banana', 'cherry', 'fig']. Sorting by length puts fig first because it is shortest. Sorting without a key compares the words alphabetically. Use a key only when the order you need is not the default one.

Turning a dictionary into a list. The method values() gives the values of a dictionary, in insertion order, and list() turns that view into a list:

scores = {"a": 10, "b": 4}
scores["c"] = 7
print(list(scores.values()))

The output is [10, 4, 7]. The list follows the order in which the keys were first added. If you want a different order, you must sort the list yourself.

Using a deque as a queue. A deque adds and removes items at both ends in O(1). The methods append and popleft work at the two ends, and pop removes from the right end:

from collections import deque

queue = deque(["a", "b"])
queue.append("c")
first = queue.popleft()
print(first, queue)
print(queue[0], queue[-1])

The output is a deque(['b', 'c']), then b c. The method popleft removes the leftmost item, and queue[0] reads the front without removing it. The index queue[-1] reads the back. A deque can also hold numbers, such as the index positions your method may need to store.

Enumerating with positions. The function enumerate gives a position and an item for each step of a loop. Its positions start at 0 unless you change them:

letters = "xyz"
for pos, ch in enumerate(letters):
    print(pos, ch)

The output is 0 x, 1 y, 2 z, one line each. The loop variables are assigned in pairs, so the position and the item are available together. This is the usual way to know where you are in a list while you read its items.

Counting windows. A list of n items has n minus k plus 1 windows of size k, as long as k is at least 1 and no larger than n. Slicing takes a run of items from a list, with the start included and the end excluded:

items = [4, 9, 2, 7, 5]
print(items[1:4])
print(len(items) - 3 + 1)

The output is [9, 2, 7], then 3. The slice items[1:4] has three items, positions 1, 2 and 3. A list of five items has three windows of size three. Use this counting rule to check the length of your output, because a wrong length fails a test even when the values are right.

Checking for an empty collection. An empty list is false in a condition, and a non-empty list is true. This lets a loop or a test stop early without a separate length check:

for item in []:
    print("never printed")
print("empty loops do nothing")

The output is only empty loops do nothing. A loop over an empty list does not run at all. Code that reads an item by position, such as items[0], does fail on an empty list, so check for emptiness before you read the first item.

Worked twin problem

This twin uses a different domain. The data are stock ticks, not sensor readings. The skills are the same: keeping one record per key by a rule, and computing a rolling minimum with a monotonic deque. The twin is not the lab. Its rules differ on purpose, so solve it by understanding the rules, not by renaming the code from the lab.

The statement. A tick is a tuple (ticker, time, price). A ticker is a short name for a stock. Write two functions.

  1. last_price_per_ticker(ticks) returns a dictionary. Each key is a ticker, and each value is the price of that ticker's latest tick, meaning the tick with the largest time. If two ticks for the same ticker have the same time, the one that comes later in the input wins.
  2. rolling_min(prices, k) returns a list with the minimum of each full window of k consecutive prices, from left to right. A window must have exactly k prices. Use a monotonic deque. If k is less than 1, raise a ValueError.

The example is ticks = [("ACME", 1, 10.0), ("BOLT", 1, 5.0), ("ACME", 3, 11.0), ("BOLT", 2, 6.0), ("ACME", 2, 99.0)]. The result of last_price_per_ticker(ticks) is {"ACME": 11.0, "BOLT": 6.0}. The result of rolling_min([5, 3, 8, 1, 4, 2], 3) is [3, 1, 1, 1].

from collections import deque


def last_price_per_ticker(ticks):
    latest = {}
    for ticker, time, price in ticks:
        if ticker not in latest or time >= latest[ticker][0]:
            latest[ticker] = (time, price)
    return {ticker: price for ticker, (time, price) in latest.items()}


def rolling_min(prices, k):
    if k < 1:
        raise ValueError("k must be at least 1")
    dq = deque()
    out = []
    for i, price in enumerate(prices):
        while dq and prices[dq[-1]] >= price:
            dq.pop()
        dq.append(i)
        if dq[0] <= i - k:
            dq.popleft()
        if i >= k - 1:
            out.append(prices[dq[0]])
    return out

         ("BOLT", 2, 6.0), ("ACME", 2, 99.0)]

assert last_price_per_ticker([]) == {}
assert last_price_per_ticker([("X", 4, 1.0), ("X", 4, 2.0)]) == {"X": 2.0}
assert last_price_per_ticker([("X", 4, 1.0), ("X", 4, 2.0), ("X", 3, 9.0)]) == {"X": 2.0}

assert rolling_min([7, 7, 7], 1) == [7, 7, 7]
assert rolling_min([3, 1, 2], 3) == [1]

Explanation of last_price_per_ticker, line by line.

  • latest = {} creates an empty dictionary. Its keys are tickers, and each value is a pair of the time and the price of the best tick so far.
  • for ticker, time, price in ticks: unpacks each tick into three names.
  • if ticker not in latest or time >= latest[ticker][0]: is true for a ticker not seen before, or when the new tick's time is at least as late as the stored one. The >= makes the later row win a tie. The index [0] reads the stored time.
  • latest[ticker] = (time, price) stores the new pair. For a ticker that already exists, this replaces the value and keeps the key where it was.
  • The return line builds the final dictionary. The loop for ticker, (time, price) in latest.items() unpacks each key and each stored pair, and keeps only the price. Expect {"ACME": 11.0, "BOLT": 6.0} for the example.

Explanation of rolling_min, line by line.

  • if k < 1: raise ValueError(...) stops the function for an invalid window, with a message that explains why.
  • dq = deque() creates the deque of indexes. The prices at those indexes increase from front to back, so the front holds the minimum.
  • while dq and prices[dq[-1]] >= price: removes the back indexes whose prices are no smaller than the new price. They can never be the minimum again, because the new price is no larger and stays in any window at least as long.
  • dq.append(i) adds the new index at the back.
  • if dq[0] <= i - k: dq.popleft() removes the front when its index has left the window. An index at or below i - k is outside a window of size k.
  • if i >= k - 1: records a result only when the window is full. This is the rule that skips the partial windows at the start.
  • out.append(prices[dq[0]]) adds the minimum of the current window.

Say it out loud

Viva and interview questions are short. Answer in your own words, then check the model answer.

Q1. What is the time and space complexity of your dedup function, and why?

Model answer

The function makes one pass over the n rows, so the time is O(n). Each new key is stored in a set, so in the worst case every row is stored, which gives O(n) space. Each membership test and insert is O(1) on average, so the per-row cost is constant. I would say O(n) average time, and I would mention the worst case of hash collisions if asked.

Q2. Why is a list a poor choice for the seen collection?

Model answer

A list membership test checks every item one by one, so it costs O(n) each time. Over n rows the total becomes O(n^2), which will not finish on ten million rows. A set uses hashing to find the key directly, so each test is O(1) on average. The fix is a one-word change, but the complexity change is the whole lesson.

Q3. Why does the rolling average divide by min(i + 1, k) instead of k?

Model answer

At the start the window holds fewer than k values, so dividing by k would make the average too small. The SQL view averages the rows it has, so the Python code has to do the same. The value min(i + 1, k) is the number of values in the window at step i. Once the window is full, both expressions give k.

Q4. How does the monotonic deque give the maximum in O(1) per step?

Model answer

The deque keeps indexes whose values decrease from front to back, so its front is always the maximum of the current window. A new value removes smaller values from the back, because they can never be the maximum again. The front is removed when its index leaves the window. Each index enters and leaves once, so the whole pass is O(n) and the cost per step is constant on average.

Q5. When would you not use a hash map or a set?

Model answer

I would not use a hash map when memory is tight, because it stores every distinct key and can use a great deal of space. Sorting and then scanning uses O(n log n) time and O(1) extra space, so it is better when space is the constraint. I would also not use a hash map when the data must be processed in its original order without storing it. Hash maps are fast, but they trade memory for speed, so the choice depends on which resource is scarce.
