How to use these ticket guides

These chapters walk through the real tickets on your squad's capstone board, in the order the board schedules them. The ticket text (story, acceptance criteria, test cases, subtasks and definition of done) comes from the course site. The guides teach you how to do each ticket yourself and how your trainer will check it.

How the board works:

  • A ticket moves Backlog, To Do, In Progress, Review, Done. Only a trainer can move it to Done, after running its test cases, and gives it a gate score from 0 to 3.
  • Every ticket is judged from commit evidence: your commits, pull requests and reviews in the squad repository. Work done on someone else's laptop does not count for you.
  • Each ticket has a points value (the "pts" column). Defence tickets (marked D01, D02 and so on) are where you present and answer questions.
  • Your viva scores acceptance criteria met, technical depth, contribution and ownership, and understanding, each 0 to 5. The final capstone grade shown on the platform is 60% your own contribution and 40% your team's.
Tip: How to use a ticket guide

Read the guide the evening before the session that ticket is scheduled for. Do the work yourself, in your squad's repository, and run every test case in "How it is checked" before you ask the trainer to review it.

Y2-T01 · Onboard: GitHub with 2FA, org invite, lab access, start T0

Session 1 · phase E0 · 1 points

The ticket in plain words

CityPulse is a platform that holds data about Bengaluru city services, such as air quality and traffic. Your intern cohort builds it from November 2026 to May 2027, in squads of about five. Every ticket is scored from evidence on GitHub, the website where the team's code and discussions live. Each piece of evidence is tied to the GitHub account that made it.

So your account must be ready before any real work starts. It needs your real name and a photo, so the trainer can match you to your onboarding form. It needs two-factor authentication (2FA), so a stolen password alone cannot log in. And it must be a member of the course's organisation, citypulse-y2, where every squad repository lives. The ticket says an intern without these cannot be scored at all.

Lab access is the third requirement. You log in to the lab machine, run a few commands and show the result, so the trainer knows the tools work on the machine used for marking.

This ticket also starts the T0 baseline diagnostic, a short assessment that measures where each intern starts. Its results feed the gap report and the squad balancing in T02. You must start it and submit at least section 1 before 20:30. You answer its questions yourself.

If something fails today, tell your trainer early.

Before you start

Nothing from earlier tickets is needed, because this is the first ticket. Check that you have each of these, which the programme provides:

  • A GitHub account that you are willing to use for the whole course.
  • A phone with an authenticator app, such as Google Authenticator.
  • A lab-platform account, one per student.
  • The LMS onboarding form link.
  • A login for the assessment platform, where T0 is published.
  • Access to #cohort-y2 on Discord or Teams.
  • On your laptop, Git for Windows (which includes Git Bash) and the GitHub command-line tool gh. Install gh from cli.github.com.

Run these quick checks. Each one should print a version line, which means you are ready.

Runs on: your laptop, in Git Bash. The exact version numbers will differ. What matters is a version line instead of an error. Then open github.com in a browser while logged in. Your settings page should load. If it asks you to log in, do so now.

There is no squad repository yet, because Y2-T03 creates it. Your evidence comes from GitHub settings, the form, the lab, the platform and chat.

How your trainer checks it

The ticket has six acceptance criteria and five test cases. Some tests need the trainer's rights to the organisation or access to the assessment platform, so you cannot run them yourself. Learn what the trainer sees, so you are ready for it.

Criterion 1: 2FA is on, and you are a member. The trainer runs TC1 and TC2. TC1 looks for your login in the list of members with 2FA turned off.

Runs on: the trainer's laptop. example-student stands in for your real login. gh api sends a request to the GitHub API. The quotes around the endpoint stop the shell from reading ? as a special symbol. filter=2fa_disabled asks only for members with 2FA off. --paginate fetches every page. --jq '.[].login' prints each login on its own line. The pipe sends those lines to grep -x, which keeps only an exact match. echo $? prints the exit status, which is 1 when nothing matched.

Passing output is no output, then 1. Failing output is your login printed on a line, which means 2FA is off. Fix it in your security settings and ask the trainer to rerun the test. An error message from gh on screen means the test did not really run, so it proves nothing. The criterion also needs your login to appear in the full member list, which the trainer checks with gh api orgs/citypulse-y2/members --paginate --jq '.[].login'. Passing means your login is printed. If it is missing, you are not a member yet. TC2 uses the same shape with orgs/citypulse-y2/invitations, which lists pending invitations. Passing output is no output. If your login appears, accept the invitation in T01.3.

Criterion 2: the profile shows your real name and photo. The trainer runs TC3 and opens your profile URL from the form in a private window. Passing output is a public profile with your full real name, a photo and your bio. The username in the address bar must match your login. A "Page not found" message usually means a typo in the form.

Criterion 3: the lab screenshot. The trainer runs TC4, watches you run whoami && date in the lab, and compares the output with your screenshot. Passing output is your username on one line, then a date and time in IST. The screenshot must be dated 2026-11-03 and must also show a Python 3 version line and a Git version line (from the longer command in Y2-T01.4). The && means date runs only if whoami worked. Failing output is a different username, a date that does not match the screenshot, or a time that looks five and a half hours behind, which means UTC.

Criterion 4: T0 has started. The trainer runs TC5 and filters the assessment-platform report by your name. Passing output is started or completed, with a timestamp at or before 20:30. Failing output is not started or no row at all.

Criterion 5: your intro is in #cohort-y2. There is no test case. The trainer searches the channel for your name and checks that the post has all three items.

Criterion 6: the scorecard flag. This is a rule. If any of the first four criteria fails at 20:30, the scorecard shows the not onboarded flag. Report problems before the deadline.

Do it, step by step

Y2-T01.1: GitHub profile

Goal. Your profile shows your full real name, a photo and a short bio.

Stage 1: edit the profile. Runs on: your laptop, in a browser. Open Settings, then Public profile. Labels can change, so follow the page. Enter your full real name, upload a clear photo of your face, and write one true line in the Bio field. The ticket's example is Data/Cloud intern @ CityPulse | Atria DT. You may use it or write your own. Save.

Stage 2: check from the command line. Runs on: your laptop, in Git Bash. Sign in to gh once.

gh auth login --hostname github.com --git-protocol https --web

--hostname github.com names the GitHub website. --git-protocol https tells gh to use HTTPS for Git. --web opens a browser page for the sign-in. You should see a message that you are logged in.

gh api user --jq '.login, .name, .avatar_url'

gh api user asks for your account record. --jq prints three fields on separate lines: your username, your name and your photo address.

Stage 3: test it. The name line must match your full real name, and the photo address must not be empty.

Trap: Using a nickname

A nickname or initials fails TC3. The trainer matches you to your onboarding form, so use your full real name.

Y2-T01.2: Two-factor authentication

Goal. Your login needs a code from your phone as well as your password, and you can recover if you lose the phone.

Stage 1: turn on 2FA. Runs on: your laptop, in a browser. Open Settings, then Password and authentication, then Two-factor authentication. Choose the authenticator app option and scan the QR code with your phone app.

Stage 2: confirm the code. Type the six-digit code shown on your phone into GitHub. Codes change every 30 seconds, and they work only when your phone's clock is correct, so keep automatic time on.

Stage 3: save the recovery codes. Download them and store the file away from your phone, such as on an encrypted drive. Each code works once. Do not paste them anywhere.

Stage 4: prove it works. Log out in the browser, then log in again with your password and the app code. Then run this:

gh api user --jq '.two_factor_authentication'

You should see true. The command checks the setting, but only the log-out and log-in step proves that the code works.

Trap: Losing the phone

Without saved recovery codes, a lost phone can lock you out. Then you need the IT desk and a named recovery time.

Y2-T01.3: Invitation

Goal. Your GitHub account is a member of citypulse-y2, and it is the same account as your onboarding form.

Stage 1: send your username. Post your username in the chat named by the programme, as the ticket says. The ticket does not name the chat, so if you do not know which one, ask your trainer.

Stage 2: accept in the browser. Runs on: your laptop, logged in as that account. Open https://github.com/orgs/citypulse-y2/invitation and accept.

Stage 3: check the membership. Runs on: your laptop, in Git Bash.

gh api user/memberships/orgs/citypulse-y2 --jq '.state'

user/memberships/orgs/citypulse-y2 asks for your membership in the organisation. --jq '.state' prints one word. You should see active. pending means the invitation is not accepted yet.

The API can also accept it. Use this only if the browser page fails and your trainer agrees:

gh api -X PATCH user/memberships/orgs/citypulse-y2 -f state=active --jq '.state'

-X PATCH changes an existing record. -f state=active sends the field state with the value active. If it answers with a permission or scope error, your login lacks the right to do it, so stop and ask the trainer.

Trap: A second account

If you accepted with a second GitHub account, the membership sits on the wrong login, and TC1 and TC2 fail for the account in your form.

Y2-T01.4: Lab check

Goal. A screenshot that shows your lab username, the date and time, a Python 3 version and a Git version, plus a GitHub reachability check.

Stage 1: log in to the lab. Runs on: the lab machine. The ticket does not name the login method, so follow the lab's instructions.

Stage 2: run the check. Type this single line into the lab terminal:

whoami && date; hostname; python3 --version; git --version; curl -sI https://github.com | head -1

whoami && date prints your username, then the date, and date runs only if whoami worked. The semicolon runs the next command whatever happened before. hostname prints the machine name. python3 --version prints a line that starts Python 3.. git --version prints the Git version. curl -sI https://github.com asks GitHub for its headers only, silently. -s hides the progress meter, and -I asks for headers. | head -1 keeps the first line, such as HTTP/2 200.

Stage 3: check the time zone. Run TZ=Asia/Kolkata date. TZ= sets the timezone for that one command. Use this line in the screenshot if the first date shows UTC, and tell the trainer, because TC4 expects the lab's current IST time.

Stage 4: test it. Take the screenshot, with your username, the Python 3 line and the Git line all readable.

Y2-T01.5: LMS onboarding form

Goal. The form holds your profile URL and your lab screenshot.

Stage 1: check the URL. Build https://github.com/<username> and open it in a private window. Your name and photo should show.

Stage 2: fill and submit. Enter the URL, attach the Y2-T01.4 screenshot, read every field, then submit once and check the confirmation.

Y2-T01.6: T0 baseline

Goal. T0 has started before 20:30, with at least section 1 submitted.

Stage 1: open the platform. Runs on: your laptop, in a browser. Log in with the account the programme gave you and open the T0 baseline.

Stage 2: start and submit. Read the instructions, start, and work through section 1. The start timestamp is the evidence TC5 uses.

Stage 3: test it. Check that the status shows started or completed with a time at or before 20:30.

This guide does not give T0 answers. The skills here are reading instructions, starting on time and submitting a section.

Y2-T01.7: Intro post

Goal. One post in #cohort-y2 with your name, one thing you built and one thing you want to build at CityPulse.

Stage 1: use the checklist. The first line gives your full name. The second names one thing you built. The third names one thing you want to build at CityPulse.

Stage 2: look at a fictional shape. This example is about a different, made-up person and project. Copy the shape, never the words.

Hello, I am Example Name. I built a timetable app for a school club. At CityPulse I want to build a transport data check.

Stage 3: test it. Search #cohort-y2 for your name and check that the post has all three items.

Defend it in the viva

Why does the course need a verified GitHub account on Day 1?

Model answer

Every ticket is scored from evidence on GitHub, and each piece of evidence is tied to the account that made it. An unverified account cannot be linked to your work, so that work cannot be scored. Day 1 also starts the T0 baseline, which feeds the gap report.

What is the trade-off of an authenticator app compared with a text message?

Model answer

An authenticator app creates codes on the phone, so it does not travel over the phone network and is harder to intercept. Its cost is dependence on the phone's clock and the app, which is why recovery codes matter. A text message is easier to set up, but it can be redirected. The course chooses the app.

What did you personally do to make your account recoverable?

Model answer

A strong answer names each step you took and the check that proved it, such as turning on 2FA, saving recovery codes away from the phone, logging out and back in, and running the membership check. An untested recovery plan is not a plan. Use your own steps and your own results.

Why does the lab check print both whoami and date?

Model answer

whoami shows which account the session belongs to, so the screenshot links to a student. date shows when it was taken. The && means date runs only if whoami worked, so a failed login cannot produce a misleading screenshot.

Why does the trainer open your profile in a private window?

Model answer

A private window has none of your saved logins, so the trainer sees what any stranger sees. This proves your real name and photo are public, not just visible to you while logged in.

Y2-T02 · Form squad, assign roles, shortlist 2 domains with verified data URLs

Session 2 · phase E0 · 2 points

The ticket in plain words

CityPulse is a platform that shows Bengaluru city data. Each squad builds one product on top of public data from the city. Before anyone writes code, the company needs a team with clear roles, and a problem that is worth solving with data that really exists.

This ticket prevents two common failures. The first is a vague goal. "Analyse pollution" does not say who the product is for, what hurts them, which data you would use, or how you would know it worked. The second is a dead or HTML-only data URL. A URL is the web address your program asks for data. If the address is dead, it returns an error. If it returns an HTML web page (a page built for people to look at) instead of JSON (a text format for data, explained below), the automatic fetching work that starts in T05 cannot read it. You find both problems now, by checking the URLs yourself.

By tonight, your squad of five must set its first-month roles, shortlist two domains (broad topic areas), write a problem statement for each, and prove that both data sources answer with JSON. You also write a three-line working agreement and give a 60-second pitch.

Before you start

Y2-T01 must be complete for you: GitHub with two-factor authentication (2FA) switched on, membership of the citypulse-y2 organisation, and lab access. For this ticket, "complete" means done and confirmed. No pull request is needed.

You need an LMS account with access to the squad sheet, a GitHub account, Git Bash on your Windows laptop (installed with Git for Windows), and access to the Linux lab machine. Run each check where the table says.

How your trainer checks it

The trainer checks six acceptance criteria. You can check each one yourself first.

The trainer then runs five test cases. Each command is split into parts below.

TC1: the URL returns 200 and JSON. For each URL in the sheet:

curl -s -o /tmp/r.json -w '%{http_code}' --max-time 15 '<url>'; head -c 1 /tmp/r.json

  • curl sends the request.
  • -s (silent) hides the progress meter.
  • -o /tmp/r.json saves the response body to a file. Git Bash maps /tmp to a Windows folder; the lab uses the real /tmp.
  • -w '%{http_code}' (write-out) prints the status code after the request. The single quotes stop the shell reading the braces.
  • --max-time 15 gives up after 15 seconds.
  • '<url>' is the address. Keep the quotes, because an & in a URL would split the command.
  • ; runs the next command whether or not the first succeeded.
  • head -c 1 prints the first byte of the saved body.

Passing output is 200{ or 200[. curl prints no newline after the code, so the body's first byte sits on the same line. 200< means the source sent HTML. 404 followed by < means a not-found page. 000 means no answer within 15 seconds, a wrong host, or a blocked address. Without --fail, curl exits 0 even on a 404, so always read the status code.

TC2: the recorded field path exists.

jq -e '<recorded jq path>' /tmp/r.json

  • jq reads the JSON file.
  • -e sets the exit code from the value: 0 when the value is not null or false, 1 when it is, and 4 when nothing comes out.
  • The filter in single quotes is the path copied from the sheet.

Passing output is a value, and echo $? then prints 0. If the output is null with exit code 1, the path is wrong for this response. If you see Cannot index array with "name", the response is a list, so the path needs .[0] first.

TC3: 5 members, 5 distinct roles, no blanks. Copy the role column, without the header, into roles.txt, then run:

sort -u roles.txt | grep -c .

  • sort -u sorts the lines and keeps one copy of each.
  • | passes that output to the next command.
  • grep -c . counts lines containing at least one character, so blank lines are not counted.

Passing output is 5. A 6 means the header was copied. A 4 means two members share a role.

TC4: each outcome has a number and a unit. This is a read-through. Highlight the outcome. "Alert residents at least 2 h before PM2.5 exceeds 60 µg/m³" passes: it has 2 with h, and 60 with µg/m³. "Improve the air" fails, because it has no number. Vague ones go back for rewrite before 20:30. This is an example of the shape only. Do not copy it, because your statement must use your own user, pain and data source.

TC5: no keys or tokens. Export the sheet as CSV from the LMS, then run:

grep -n -i -E 'key=|token|apikey|[0-9a-f]{32,}' sheet-export.csv

  • grep prints lines that match a pattern.
  • -n adds line numbers.
  • -i ignores case, so TOKEN also matches.
  • -E enables extended patterns: | means "or", and {32,} means 32 or more repeats.

Passing output is nothing. Run echo $? straight after: exit code 1 means no match. Failing output shows a line number and the text. The usual cause is a URL containing apikey=, or a long hex string pasted into a cell.

Trap: Passing TC5 is not enough

TC5 searches the sheet export only. A key inside a URL you paste is still a key in the sheet, so check each URL before you paste it.

Defend it in the viva

1. Why check the URLs before writing any code?

Model answer

The fetching work in T05 expects JSON from a live address. A dead or HTML-only source blocks that work, and the team would find out late. A live check now tests the one thing the later work depends on, so it is the cheapest point to catch the failure.

2. Why is a 200 status code alone not enough?

Model answer

A 200 only says the request succeeded. It does not prove the body is JSON or that the field we need exists. So the check reads the first byte to confirm JSON, then uses jq -e to confirm the recorded path returns a non-null value.

3. What is the trade-off between a source that needs a key and one that does not?

Model answer

A keyed source may hold richer data, but its key is a secret that must stay out of the sheet, the repository and the URLs. An open source is simpler to share, but may lack the field the outcome needs. I would record "key required: yes" honestly and choose the source that can measure the outcome.

4. Why must the outcome have a number and a unit?

Model answer

Without a number and a unit, nobody can say whether the product succeeded. "Alert residents at least 2 h before PM2.5 exceeds 60 µg/m³" can be tested against data. The number sets the target and the unit makes it specific.

5. What did you personally do, and how do you show it?

Model answer

Name the step you owned, such as your own statement or your live curl. Show the exact command, the status code, the path you used and the cell where you recorded it. Describe only what you actually did, and let the output be the proof.

Y2-T03.8 Save your history and push it (every student)

Goal: docs/linux/<name>.txt holds your history, committed under your identity.

Stage 1, save the history. history prints numbered commands, so redirect it to a file in /tmp, a shared temporary folder:

wc -l counts lines. A count of 0 means this shell has no history, so run the commands in the same session. Files in /tmp can be removed on restart, so copy promptly.

<lab-user> and <lab-host> are the login details your trainer gave you. git status --short should show ?? docs/linux/ as untracked.

Search it for token, key and password, and remove any secret before you commit.

Defend it in the viva

Why does the metric need a number, a unit and a target date?

Model answer

The number sets the size of the goal, the unit says what is measured, and the date makes the goal testable. Without a date, a metric can never be marked as missed, which is why TC4 checks all three.

Why sign the charter with Git commits instead of a Word file with a signature image?

Model answer

This is a trade-off. Word gives richer formatting, but its file cannot be compared line by line in a pull request. A commit records who signed and when, and TC2 counts those authors. The cost is plainer formatting.

What did you personally contribute, and how can the trainer check it?

Model answer

Name the control you wrote, the pull request that reviewed it and the commit hash. Then point to the evidence: TC2 and git log on the file show your name against that commit. Use your own words, and claim only work you did.

Why does the ticket require process controls, and what does each one cost?

Model answer

The 2017 case shows that one mistake can destroy data when no second person checks the action and the backups are untested. A control is a checkable rule. Each one adds a small step, so choose the failures the team could realistically have.

Why might TC2 give a wrong answer, and how would you spot it?

Model answer

The command counts each name and email pair, so one person with two emails is counted twice. Run it without sort -u and wc -l to read the full list, and ask your trainer before changing old history.
