The idea in one minute

A pipeline is a set of steps that run one after another, where each step uses the output of the step before it. Today you build one for air-quality readings. The steps are extract (read the raw file), validate (test the data against rules) and load (write the good data into a database table).

Between the steps you place data-quality checks. A data-quality check is a test on the data, such as "no reading is negative". If a blocking check fails, the run stops, and the bad readings never reach the database or the dashboard.

The analogy is an assembly line with a stop cord. Any worker can pull the cord and halt the line before a faulty part moves on.

By the end you will be able to write a pipeline script, write checks that return pass or fail, show the exit code that proves a failure, and count rejected records by reason.

Starting from zero

Every term used in this chapter is explained here or at the first place it appears.

Terminal and shell. A terminal is a window where you type text commands to the computer. The program that reads those commands and runs them is a shell. Bash is a common shell, and this course uses it for its .sh scripts. On Windows, Git Bash is the usual way to run them. If your course names a different terminal, use that one.

Command. A command is one line you type, and the computer runs it when you press Enter. ls is a command that lists the files in the folder you are in.

File, folder and path. A file holds data or code. A folder (also called a directory) holds files and other folders. A path is the address of a file. data/raw/batch_good.csv means the file batch_good.csv inside raw, which is inside data.

Working directory. This is the folder your terminal is in right now. The command pwd prints its full path. A relative path such as data/raw is measured from the working directory. The same file has a different relative path from a different folder, which is why scripts must move to a known folder first.

Script. A script is a file of commands that the computer runs from top to bottom. A .sh file is a bash script. A .py file is a Python script.

Variable. A variable is a name that stores a value. In bash, DB="citypulse.db" stores text, and "$DB" reads it back. In Python, count = 3 does the same job.

Function. A function is a named block of code you can call by name. It can take inputs (arguments) and give back an output (a return value). In Python, def double(x): return x * 2 defines it, and double(4) gives 8.

Module. A module is a Python file that other code can load with import. The command python -m citypulse.fetch runs one module as a program.

Server. A server is a program that waits for requests and answers them. A database server answers questions about its data. SQLite, which you use today, does not need a server: the whole database is one file on disk.

Exit code. Every program ends by returning a number called its exit code. 0 means success. Any other number means failure. The shell stores the last exit code in a special variable called $?. The command echo $? prints it.

Pipe. The symbol | sends the output of one command into the next command. You will meet it in a warning in the tools section.

Cron. Cron is the Linux scheduler that runs a command at set times, for example every morning at 06:00.

CSV. CSV means comma-separated values. It is a plain text table: each line is a row, commas separate the columns, and the first line holds the column names.

Table, row and SQL. A database table holds rows with named columns. SQL (Structured Query Language) is the language for asking a database questions. SELECT COUNT(*) FROM readings asks how many rows the table readings has. A view is a saved SQL query that you can read like a table.

Python list, dictionary and tuple. A list is an ordered collection written in square brackets: [1, 2, 3]. A dictionary maps keys to values written in curly brackets: {"S1": 2} maps the key "S1" to the value 2. A tuple is a fixed group of values in round brackets: ("S1", 2). The dictionary method get(key, default) returns the value for the key, or the default if the key is missing.

pandas and DataFrame. pandas is a Python library for tables. It is installed with python3 -m pip install pandas, where pip is Python's installer for libraries. A DataFrame is a table held in memory, with rows and named columns.

Regular expression (regex). A regular expression is a pattern that describes text. The pattern [0-9]+ matches one or more digits. The pattern [A-Z]{2} matches exactly two capital letters.

Timestamp. A timestamp is a date and time value, such as 2026-03-01T08:00, which means 8 am on 1 March 2026.

The tools

Pipeline orchestration with shell

Orchestration means deciding which steps run, in what order, and what happens when one fails. CityPulse uses a bash script for this. The alternatives are a Makefile (a file that lists build steps and what each one depends on, which suits compiled software and is awkward for a plain sequence with logs), Prefect or Airflow (workflow tools with retries and a web interface, which are too heavy for five stages) and a Python driver script (which works, but bash keeps each stage a plain command you can run by hand).

Bash is already on every lab machine, and the shellcheck check (an automatic tool that reviews shell scripts for common mistakes) reviews it. The same script later runs from cron on a virtual machine, so it must work from any folder.

This is the pipeline script from the course slides, with its indentation restored:

#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."   # repo root, works from any cwd
if [ -f .env ]; then set -a; . ./.env; set +a; fi
DB="${SQLITE_PATH:-citypulse.db}"
log() { echo "$(date -u +%FT%TZ) [pipeline] $*"; }
run() { local name=$1; shift; log "START $name"; "$@"; log "END $name"; }
run fetch python -m citypulse.fetch
run clean python -m citypulse.clean
run load  python -m citypulse.load
run views sqlite3 "$DB" ".read sql/views.sql"
run dq    python -m citypulse.dq_checks
log "pipeline OK"

Line by line:

  1. #!/usr/bin/env bash is the shebang. It tells the system to run this file with bash.
  2. set -euo pipefail is strict mode. -e stops the script at the first command that fails. -u treats an unset variable as an error. pipefail makes a pipeline (a | b) fail if any part fails, not only the last part.
  3. cd "$(dirname "$0")/.." moves into the repository root. $0 is the path of the script, dirname gives its folder, and .. goes up one level. The $( ... ) form runs a command and puts its output in place. The quotes keep folder names with spaces working.
  4. If a file called .env exists, this line loads its settings. set -a marks each variable it creates for export, . ./.env reads the file, and set +a turns that behaviour off again.
  5. DB takes the value of SQLITE_PATH if it is set and not empty, and citypulse.db otherwise. The :- is the "use this default" form.
  6. log is a function. It prints a UTC timestamp, the tag [pipeline] and its arguments ($*).
  7. run takes a stage name, drops it with shift, logs START, runs the rest of the line as a command ("$@"), and logs END. Because of set -e, a failing stage stops the script before END is printed. That is what makes the log show where the run stopped.
  8. Lines 8 to 12 each run one stage. sqlite3 "$DB" ".read sql/views.sql" runs an SQL file of saved views against the database.
  9. The last line prints pipeline OK. You see it only if every earlier stage succeeded.

A normal run prints a START and END line for each stage, then pipeline OK. If a stage fails, you see its START line, its error text, and no END line.

Trap: Forgetting pipefail

Without pipefail, a command such as python -m citypulse.clean | tee clean.log reports the exit code of tee, which is 0. The failure of clean is hidden, and the script carries on. Always write set -euo pipefail on the second line.

Trap: Relative paths break under cron

A script that opens sql/views.sql works when you run it from the repo root and fails from /tmp or from cron. The line cd "$(dirname "$0")/.." fixes this. Also, python may point to a different Python under cron. Call .venv/bin/python explicitly, or activate the virtual environment first.

Data-quality assertions

A data-quality check is a query that returns one number, plus a rule that judges that number. For example, "rows in the last 24 hours must be at least 40". Each check belongs to a dimension, which is the kind of problem it looks for:

  • Completeness: the data you expect is present.
  • Validity: values follow the rules, such as a non-negative PM2.5 reading.
  • Uniqueness: no key appears twice when it should be unique.
  • Freshness: the newest data is recent enough to trust.

A blocking check stops the pipeline when it fails. A warning is reported but lets the run continue. Use blocking only for data you must not publish.

This is the core of the course's checks file, with the rest of the checks left out to keep it short:

import os, sqlite3, sys
CHECKS = [  # name, dimension, SQL -> one number, pass rule, blocking?
    ("negative_pm25", "validity", "SELECT COUNT(*) FROM fact_air_quality WHERE pm2_5 < 0", lambda v: v == 0, True),
    ("rows_last_24h", "completeness", "SELECT COUNT(*) FROM fact_air_quality WHERE ts_utc >= strftime('%Y-%m-%dT%H:%M:%SZ','now','-1 day')", lambda v: v >= 40, True),
    ("hours_since_newest", "freshness", "SELECT (julianday('now') - julianday(MAX(ts_utc))) * 24 FROM fact_air_quality", lambda v: v is not None and v <= 3, False),
]
def main() -> int:
    con = sqlite3.connect(os.environ.get("SQLITE_PATH", "citypulse.db"))
    results = [(n, b, ok(con.execute(sql).fetchone()[0])) for n, _, sql, ok, b in CHECKS]
    for n, b, good in results: print(f"{'PASS' if good else 'FAIL' if b else 'WARN'} {n}")
    failed = sum(1 for _, b, g in results if b and not g)
    warned = sum(1 for _, b, g in results if not b and not g)
    print(f"DQ: {len(results) - failed - warned} passed, {failed} failed, {warned} warnings"); return 1 if failed else 0
if __name__ == "__main__": sys.exit(main())

Line by line:

  1. import brings in three standard-library modules: os for environment variables, sqlite3 for the database and sys for exiting with a code.
  2. CHECKS is a list. Each entry is a tuple of five items: a name, a dimension, an SQL query that returns one number, a pass rule and a blocking flag. The comment on this line explains the order.
  3. negative_pm25 counts rows where pm2_5 is below zero. The rule lambda v: v == 0 is a small unnamed function that is passed in. It returns True when the count is zero. True at the end makes it blocking.
  4. rows_last_24h counts rows with a timestamp in the last day. The rule needs at least 40. This check is blocking.
  5. hours_since_newest returns the age of the newest row in hours. julianday converts a date to a day number, so the subtraction gives days, and * 24 converts to hours. The rule v is not None and v <= 3 first checks that there is a value, because MAX on an empty table returns NULL. The False makes this a warning, not a blocking check.
  6. main() opens the database, using SQLITE_PATH if it is set. The -> int tells the reader it returns a number.
  7. This line runs every check. con.execute(sql) runs the query, .fetchone() returns one row as a tuple, and [0] takes its first value. ok(...) applies the pass rule. The result is a list of (name, blocking, passed) tuples.
  8. This loop prints one line per check. The nested if picks the label: PASS if it passed, FAIL if it failed and is blocking, and WARN otherwise.
  9. failed counts the blocking checks that did not pass.
  10. warned counts the non-blocking checks that did not pass.
  11. This line prints the summary and returns 1 if any blocking check failed, or 0 otherwise.
  12. sys.exit(main()) passes that number to the operating system as the exit code. The if __name__ == "__main__" guard means the code runs only when you start the file directly, not when another file imports it.

The loop logic on lines 8 to 11 is the part most worth understanding. The animation below uses three checks: one blocking failure in the middle.

Trap: An empty table breaks the freshness check

MAX(ts_utc) on an empty table is NULL. In Python that arrives as None, and None <= 3 raises an error. Always handle None in the pass rule, as the v is not None and part does.

Trap: Thresholds picked at random

A threshold of 40 rows is only sensible if you measured normal daily coverage first and wrote the reason in a comment. A threshold that is too high fails every day, and one that is too low never fails. Both make the check useless.

Trap: Making every check blocking

If every check is blocking, one cosmetic issue stops the whole pipeline. Keep blocking for data you must not publish, and use warnings for the rest.

Exit codes and fail-fast

Fail-fast means stopping at the first real error instead of passing bad data to later stages. The exit code is the signal that tells the shell, cron and CI (automatic checks that run on every change to the code) that a step failed. Your script does not need to read any message: it only needs the number.

This is the sabotage check from the course. It deletes today's rows, expects the checks to fail, and then reloads and expects a pass:

if python -m citypulse.dq_checks; then
  echo "UNEXPECTED: dq passed after sabotage"; exit 1
fi
echo "OK: dq failed with non-zero exit as expected"

Line by line:

  1. if runs the command and branches on its exit code. A command that returns 0 takes the then branch, and any other code skips it. Here, a pass is the unexpected result.
  2. This line runs only if the checks passed. It prints a message and exits with 1, so the sabotage run is reported as broken.
  3. fi closes the if.
  4. This line runs when the checks failed, which is the expected result.

The if is the reason this works under set -e. A bare failing command would stop the script at once. Wrapping it in if tells bash that the failure is expected.

Trap: A bare failing command under set -e

set -e stops the script at the first failing command, so python -m citypulse.dq_checks on its own would end the script before your message printed. Wrap an expected failure in if. Also check $? immediately after the command you care about, because the next command overwrites it.

Trap: A main that prints FAIL but returns nothing

If main() prints FAIL and ends without a return, Python returns None. The process exits with code 0, and the pipeline passes bad data. Return 1 from main() and call sys.exit(main()), as the course code does.

The worked example

The course workbook builds a small version of the same idea in five steps. The goal is to show that a batch with one bad reading halts the run, and that a cleaned batch goes through. You will reuse these ideas in the lab.

Step 1: stage a raw batch. The batch is a CSV file with six readings, one of them negative:

station_id,ts,pollutant,value
S1,2026-03-01T08:00,pm25,42.1
S1,2026-03-01T09:00,pm25,38.7
S2,2026-03-01T08:00,no2,19.4
S2,2026-03-01T09:00,no2,-3.0
S3,2026-03-01T08:00,o3,61.2
S3,2026-03-01T09:00,o3,58.0

The line S2,2026-03-01T09:00,no2,-3.0 is the bad row. The command python3 -c "import pandas as pd; print(len(pd.read_csv('readings_raw.csv')),'rows')" prints 6 rows. The -c flag runs the Python text that follows it as a one-line program.

Step 2: read the batch into typed columns.

import pandas as pd
df = pd.read_csv("readings_raw.csv", parse_dates=["ts"])
print(df.dtypes.to_string())
print("shape:", df.shape)

Line by line: line 1 imports pandas under the short name pd. Line 2 reads the CSV into a DataFrame. The parse_dates=["ts"] option turns the ts column from text into real dates. Line 3 prints the type of each column, and line 4 prints the number of rows and columns.

The output is station_id as object (text), ts as datetime64[ns] (a date), pollutant as object, value as float64 (a decimal number), and shape: (6, 4). Types matter because a value stored as text compares wrongly with a number.

Step 3: assert the four checks. An assert is a Python statement that stops the program with an error if its condition is false. The batch needs one assert per check:

assert df["value"].notna().all(), "null values found"
assert (df["value"] >= 0).all(), "negative readings"
assert df["pollutant"].isin({"pm25", "no2", "o3"}).all(), "bad pollutant"
assert df.duplicated(["station_id", "ts", "pollutant"]).sum() == 0, "duplicate rows"

Line by line: each line tests one pillar. notna().all() is the completeness test: it is True only if no value is missing. (df["value"] >= 0).all() is the validity test for negative readings. isin checks the pollutant against a set of allowed codes. The last line counts repeated keys and checks that the count is zero. When a condition is false, Python raises AssertionError with the message after the comma.

Running this on the raw batch prints AssertionError: negative readings, and echo $? prints 1.

Step 4: quarantine the bad row. The file clean.py keeps the rows that pass the rule:

import pandas as pd
df = pd.read_csv("readings_raw.csv")
good = df[df["value"] >= 0]
good.to_csv("readings_clean.csv", index=False)
print("kept", len(good), "of", len(df), "rows")

Line by line: line 2 reads the batch. Line 3 keeps only the rows where the test is True, which is the filter in square brackets. Line 4 writes the kept rows to a new file, and index=False stops pandas adding a numbered first column. Line 5 prints kept 5 of 6 rows. The rejected row is not deleted from the raw file, so you can still investigate it.

Step 5: run it end to end. Running the raw batch through the pipeline stops at validation. Running the clean batch goes all the way through to load. The workbook prints PIPELINE OK only for the clean batch. The exit code is 1 for the raw batch and 0 for the clean one.

Trap: assert can be switched off

Python ignores every assert when it runs with the -O flag. A check written as an assert then silently passes. For a check that guards production data, use an if that returns or exits with a code, as the course's dq_checks.py does.

Step 2: write the extract stage

Create extract.py:

import sys
import pandas as pd


def extract(path):
    df = pd.read_csv(path, parse_dates=["ts"])
    print("extracted", len(df), "rows from", path)
    return df


if __name__ == "__main__":
    extract(sys.argv[1])

Line by line: line 1 imports sys, which gives access to the command-line arguments. Line 2 imports pandas. Lines 5 to 8 define the function extract. It reads the file and converts ts to dates, prints a count, and returns the table. The last two lines run only when you start this file directly. sys.argv[1] is the first argument after the script name, so python3 extract.py batch_good.csv passes batch_good.csv to the function.

You should see extracted 6 rows from batch_good.csv.

Step 3: write the data-quality checks

Create checks.py:

def run_checks(df, config):
    failures = []
    if df["value"].isna().any():
        failures.append("null_value")
    if (df["value"] < config["min_value"]).any():
        failures.append("value_below_min")
    if not df["pollutant"].isin(config["pollutants"]).all():
        failures.append("bad_pollutant")
    if df.duplicated(["station_id", "ts", "pollutant"]).any():
        failures.append("duplicate_key")
    return failures

Line by line: run_checks takes the table and the config dictionary. It starts with an empty list of failures. Each if tests one rule and adds a short name to the list when the rule is broken. The names are what you will see in the output. .any() is True if at least one row breaks the rule. The function returns the list, so an empty list means the batch is clean.

Test the checks on the bad batch:

python3 -c "import json; from extract import extract; from checks import run_checks; print(run_checks(extract('batch_bad.csv'), json.load(open('config.json'))))"

The output is the extract line, then ['value_below_min']. An empty list [] would mean the check did not fire, so find out why before you go on.

Step 4: build the validate gate

The gate decides whether a batch may continue. Create validate.py:

import json
import sys
from extract import extract
from checks import run_checks


def main(path):
    with open("config.json") as f:
        config = json.load(f)
    df = extract(path)
    failures = run_checks(df, config)
    if failures:
        print("BLOCKED", path, failures)
        return 1
    print("validation OK", path)
    return 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1]))

Line by line: lines 1 to 4 import the libraries and the two functions you wrote. main loads the config, extracts the batch, and runs the checks. If the list is not empty, it prints BLOCKED, the file and the reasons, and returns 1. Otherwise it prints validation OK and returns 0. The last line passes the return value to sys.exit, so the program's exit code is 0 or 1. The file name config.json is opened relative to the working directory, so run this from the dq-lab folder.

Run both batches:

python3 validate.py batch_good.csv; echo "exit $?"
python3 validate.py batch_bad.csv; echo "exit $?"

The good batch prints validation OK batch_good.csv and exit 0. The bad batch prints BLOCKED batch_bad.csv ['value_below_min'] and exit 1.

Step 5: write the load stage

Create load.py:

import sqlite3
import sys
from extract import extract


def main(path):
    df = extract(path)
    con = sqlite3.connect("citypulse_lab.db")
    df.to_sql("readings", con, if_exists="replace", index=False)
    con.close()
    print("loaded", len(df), "rows into readings")
    return 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1]))

Line by line: sqlite3.connect opens the database file, and it is created if it does not exist. to_sql writes the table to the database. if_exists="replace" drops the old readings table and writes a new one. Running the load twice therefore gives the same table, which is the idempotent behaviour the quiz covers. con.close() closes the connection. The function returns 0 to say it succeeded.

Step 6: run the good batch

Create run_pipeline.sh:

#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")"
BATCH="$1"
python3 validate.py "$BATCH"
python3 load.py "$BATCH"
echo "PIPELINE OK"

Line by line: lines 1 and 2 are the shebang and strict mode. Line 3 moves to the folder that holds the script. Line 4 stores the first argument, the batch file name, in BATCH. Lines 5 and 6 run the gate and then the load. Because of set -e, a non-zero exit from the gate stops the script before the load. The last line runs only if both succeeded.

Pipelines as a directed acyclic graph

A pipeline is a set of steps, and some steps need the output of other steps. You can draw this as a graph. Each step is a node, which is a box, and each arrow says that one step needs the output of another. The graph is called a DAG, which stands for directed acyclic graph. "Directed" means each arrow has a direction. "Acyclic" means there is no cycle, which is a route that starts at one step and comes back to it.

A small pipeline can be written as a Python dictionary. Each key is a step, and its value lists the steps it depends on:

deps = {"extract": [], "validate": ["extract"], "load": ["validate"]}
print(deps["load"])

The output is ['validate']. Load can run only after validate, and validate only after extract. There is no cycle, so the run has a clear start, which is extract, and a clear end, which is load.

A straight line of steps is still a DAG, and it is the simplest kind. Branches matter when two steps do not depend on each other. Those two steps can run in parallel, or in either order, as long as both finish before any step that needs them. A cycle is a real problem because no step can go first: each one waits for another one to finish.

How it shows up in a case study. A team's nightly job has four stages: fetch readings, clean them, load them, and rebuild the dashboard views. Someone adds an arrow from the views back to fetch, so that empty views can ask for a fresh download. The job now runs for hours and never finishes. The question asks what the new arrow has created. The reasoning is that the arrow closes a loop, so there is no first step and no defined end. The fix is to remove the arrow and let a separate check decide whether a new fetch is needed. You find cycles by reading the arrows, not only the boxes.

Trap: A loop is harmless because it eventually stops

A cycle has no start, so the run cannot be ordered, retried or reasoned about. Nothing guarantees that it stops at all. A pipeline that is a single line is also a DAG, so you do not need extra complexity to make one.

Idempotent loads

An operation is idempotent if running it twice leaves the same result as running it once. For a load, this means a rerun must not double the rows. The idea is simple, but it is the reason a crashed job can be restarted safely.

Compare two ways of writing the same day's readings into a store:

table = {}
table["2026-03-01"] = [42.1, 38.7]
table["2026-03-01"] = [42.1, 38.7]
print(len(table["2026-03-01"]))

log = []
log.extend([42.1, 38.7])
log.extend([42.1, 38.7])
print(len(log))

The first form replaces the rows for the key on each run, so the output is 2. The second form appends, so the output is 4. The first form is idempotent and the second is not. In the course's pipeline project (not today's graded lab), to_sql with if_exists="replace" drops the table and writes it again, so a second run gives the same row count. That replace method is not fully atomic, which you will meet later in this section.

How it shows up in a case study. CityPulse's daily job appends readings to a fact table. After a power cut, the scheduler reruns the job, and the dashboard now shows double the readings for that day. The team wants a rerun to be harmless. The reasoning is that the second run must find the day's rows and replace them, or delete them before it inserts, so the final table is the same either way. A job that succeeds once and then doubles data on a rerun is not safe to restart.

Trap: Rerunning after a success is the only test that matters

A load that works once can still double data on a rerun, and a rerun after a crash is exactly the case that matters. Logging the run, adding pauses or making the job faster does not change what the table holds afterwards. Only the way the second run treats existing rows does.

The four data-quality dimensions

A data-quality dimension is the kind of problem a check looks for. The course uses four: completeness, validity, uniqueness and freshness. Each check you write should belong to one of them, and the course requires at least five checks across at least three of the four.

Question the check asks Dimension Example rule
Did enough data arrive? Completeness At least 40 rows in the last 24 hours
Do the values follow the rules? Validity PM2.5 is at least 0
Does a key appear only once? Uniqueness No repeated station, time and pollutant
Is the newest data recent? Freshness Newest reading is at most 3 hours old

The difference between completeness and freshness causes most mistakes. Completeness counts how much data there is in a window, and freshness measures how old the newest item is. A count of rows in the last 24 hours tests coverage, so it is completeness even though it uses a time window. Freshness is the age of the latest row, measured in hours.

How it shows up in a case study. A dashboard shows an average PM2.5 for each station. The team has two checks: one fails when fewer than 40 rows arrived in the last day, and one fails when a reading is negative. A reviewer asks which dimensions the two checks cover. The reasoning is that the first asks whether enough data arrived, which is completeness, and the second asks whether values follow the rules, which is validity. Neither check measures how old the data is, so neither is freshness.

Trap: Filing every time-based check under freshness

Any check that mentions time is not automatically freshness. Ask what the number measures. The age of the newest row is freshness. The number of rows in a window is completeness.

Range validation with inclusive bounds

Range validation checks that a value lies between a lower bound and an upper bound. A bound is inclusive if the boundary value itself is allowed. The rule value >= 0 accepts zero, while value > 0 rejects it. Both choices are valid rules, but they are different rules, so you must choose on purpose.

readings = [0.0, -0.1, 1000.0, 1000.5]
accepted = [v for v in readings if 0 <= v <= 1000]
print(accepted)

The output is [0.0, 1000.0]. The chained comparison 0 <= v <= 1000 means both parts must be true, so both bounds are inclusive. The value -0.1 fails the lower bound and 1000.5 fails the upper bound.

There is one trap in this topic that the pandas course warns about. A comparison with a missing value is False. In Python, float("nan") behaves the same way, so 0 <= float("nan") <= 1000 gives False. A rule written as "reject if below zero or above 1000" does not fire for a missing value, so the missing value passes. A rule written as "accept only if inside the range" rejects it. Check for missing values with a separate completeness rule as well.

How it shows up in a case study. A cold-store logger must accept temperatures from 0 to 100 degrees, including both ends. A developer writes the rule as value > 0 and value < 100, and a reading of exactly 0.0 is rejected. The team then asks why a valid reading is missing. The reasoning is that the bounds are inclusive, so the rule must use >= and <=. The bounds should come from what the data means, and the reason should be written next to them.

Trap: Rejecting with the wrong comparison

A rule of "reject if below 0 or above 100" lets a missing value through, because a NaN fails both comparisons. A rule of "accept only if between 0 and 100" rejects it. Two rules that look like opposites can give different answers for the same input.

Quarantining rejected rows

A rejected record should be kept, not thrown away. A quarantine, which is also called a dead-letter store, holds rejected rows together with the reason each one was rejected. The good rows go on to the next stage. The reason is what makes the quarantine useful, because it lets someone find the faulty sensor later.

rows = [{"id": 1, "value": 4.0}, {"id": 2, "value": -3.0}]
good = [r for r in rows if r["value"] >= 0]
quarantine = [{"row": r, "reason": "negative_value"} for r in rows if r["value"] < 0]
print(len(good), len(quarantine), quarantine[0]["reason"])

The output is 1 1 negative_value. The good list keeps the accepted row, and the quarantine keeps the rejected row with its reason. Nothing was deleted, so the evidence is still there.

This design has two parts, and both matter. Keeping the rows gives you evidence. Keeping the reason gives you a way to group the evidence. A quarantine with rows but no reasons can show that something is wrong, but it cannot show what.

How it shows up in a case study. A regional manager asks why one station has no readings for a week. The cleaning step filtered out negative values with a plain filter and wrote nothing else. The reasoning is that the rejected rows were dropped with no record, so there is no way to see which rule removed them or whether the sensor is faulty. The fix is to write the rejected rows to a quarantine table with the reason for each, while the good rows continue to the load.

Trap: Deleting rejects, or quarantining without reasons

Deleting rejected rows removes the evidence. Quarantining rows with no reason keeps the rows but makes them hard to diagnose. Both are mistakes, and the first is the more serious.

Incremental loading and the high-water mark

Incremental loading loads only the records that are new since the last run, instead of loading everything again. To do this, the job stores a high-water mark. This is the largest event timestamp it has already loaded safely. On the next run it takes only the rows above that value.

events = [("2026-03-01T08:00", 1), ("2026-03-01T09:00", 2), ("2026-03-01T10:00", 3)]
mark = "2026-03-01T08:30"
new = [e for e in events if e[0] > mark]
print(new)

The output is [('2026-03-01T09:00', 2), ('2026-03-01T10:00', 3)]. ISO timestamps written in the same format compare correctly as text, so the comparison works here. After a successful load, the job stores the largest timestamp it loaded, which is 2026-03-01T10:00, as the new mark.

Incremental loading is worth its complexity only when the data is too large to reload in each run. For a small table, a full reload is simpler and cannot miss rows. Note that a full reload must still be idempotent, so the table is replaced rather than appended.

How it shows up in a case study. A job takes the time at which it last ran as its mark. A feed sometimes delivers readings several hours late. A reading recorded at 14:00 arrives at 16:00, after a 15:00 run. The reasoning is that the mark is 15:00, and 14:00 is not later than 15:00, so the row is never selected. It is skipped for ever. The fix is to use the event timestamp of the data as the mark, not the time the job ran.

Trap: Using the job's run time as the mark

Late records have older timestamps than the run that should have picked them up. A mark based on run time skips them silently, and the dashboard looks complete while it is not.

Schema validation before row checks

Schema validation checks the structure of the data before any row is checked. It asks whether the required column names are present, and where needed whether each column has the right type. It runs first because a renamed or missing column makes every row check crash or report misleading results.

required = {"station_id", "ts", "pollutant", "value"}
incoming = {"station_id", "ts", "pollutant_code", "value"}
print(sorted(required - incoming))

The output is ['pollutant']. The set difference lists the required names that the incoming file does not have. This is the kind of message a schema check should give: it names the exact column that is missing, instead of a KeyError in the middle of a value check.

Schema validation also covers types. If a numeric column arrives as text, every number is a string. A range check that compares strings to numbers then fails in confusing ways, so the structure check should catch this first.

How it shows up in a case study. A supplier's export renames station_id to station. The row checks start to run, and the first error the team sees is a KeyError deep inside a value check. The reasoning is that a schema check, run before the row checks, would have compared the column names and reported the missing station_id directly. The row checks were not wrong. They were given a file that did not have the structure they expect.

Trap: Checking values and assuming the columns are right

If you check the values first, a renamed column appears as a confusing crash deep in a row check. Confirm the structure before you trust any value test.

Drift detection against a baseline

Drift is a change in the pattern of the data over time. A batch can pass every rule and still be unusual. For example, its average PM2.5 can be three times last month's average while every single value is valid. A drift check compares a statistic from the new batch with a baseline, which is a reference value taken from earlier data, and it fires when the difference is too large.

baseline = [20.0, 22.0, 21.0, 19.0]
today = [60.0, 66.0, 63.0, 61.0]
print(sum(baseline) / len(baseline), sum(today) / len(today))
print(round((sum(today) / len(today)) / (sum(baseline) / len(baseline)), 2))

The output is 20.5 62.5 on the first line and 3.05 on the second. Every value in today's batch is a plausible reading, so a range check would pass it. The drift check compares the two averages and finds that today's average is about three times the baseline.

Drift checks are usually warnings rather than blocking checks. A drift is a reason to look, not always a reason to stop the pipeline. Each drift threshold needs a written reason, because a threshold picked at random either fires every day or never fires.

How it shows up in a case study. A batch passes the range, uniqueness and completeness checks. The team's average temperature is 5.5 degrees above the baseline, and the drift check warns. The reasoning is that the rules judge single rows, but drift compares a statistic with a baseline. The right first step is to review the warning and confirm whether the change is real, such as a heatwave or a sensor fault, before anyone changes the threshold.

Trap: Passing the rules means the data is normal

Rule checks cannot see a change in the overall pattern. A batch of valid values can still be the wrong batch. Drift checks exist for exactly that gap.

Retry with backoff for transient failures

A transient failure is a temporary problem, such as a network timeout or a busy database, that may succeed if you try again. Retry with backoff means waiting longer after each failed attempt, for example 1 second, then 2, then 4. A maximum number of attempts stops the retries from going on for ever.

delays = [2 ** n for n in range(3)]
print(delays)

The output is [1, 2, 4]. The expression 2 ** n doubles the wait each time. Some systems add a small random amount to each wait, called jitter, so that many clients do not retry at the same moment and overload the service again.

Retries are for transient failures only. A validation failure, such as a negative reading, fails the same way every time. Retrying it wastes time and hides the real problem. The rule is to retry a failure that might clear by itself, and to fail a data-quality failure straight away.

How it shows up in a case study. A sensor API sometimes returns a timeout, and a batch sometimes fails the negative-value check. The team wants one retry rule for both. The reasoning is that the timeout is transient, so a bounded retry with growing waits is right. The negative value is a data problem that will fail again, so it must not be retried. The two failures need different handling, and the case study tests whether you separate them.

Trap: Retrying data-quality failures, or retrying without a limit

Retrying a failed check repeats the same failure and delays the stop. A retry with no maximum can run for ever and load the service that is already struggling.

Atomic publish: all or nothing for readers

An atomic publish means that readers see either the complete old version or the complete new version of a table, and never a half-written state. A common way to achieve this is to load into a new table, or to write inside a transaction. A transaction is a group of database changes that either all succeed together or all roll back together. The new version is then made visible in one step.

import sqlite3
con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE readings (v REAL)")
con.execute("INSERT INTO readings VALUES (1.0)")
con.commit()
con.execute("INSERT INTO readings VALUES (2.0)")
con.rollback()
print(con.execute("SELECT COUNT(*) FROM readings").fetchone()[0])

The output is 1. The first insert is committed, so it is kept. The second insert is part of an open transaction, and rollback undoes it, so the table looks as if the second insert never happened. This is the all-or-nothing behaviour that a reader depends on.

The course's pipeline project uses to_sql with if_exists="replace". That is idempotent, because a rerun gives the same table. It is not guaranteed to be atomic: depending on the database, a crash in the middle of writing can leave the table partly written. The pattern that avoids this is to build the new table under another name and then switch readers to it in one step.

How it shows up in a case study. A dashboard reads the readings table while the pipeline loads 50,000 rows into it. Users sometimes see a chart with about half of the day's data. The reasoning is that the loader writes into the live table, so every partial state is visible to readers. Loading more slowly, or showing a warning banner, does not remove the partial state. The fix is to load into a new table or inside one transaction, and then switch readers to the complete version.

Trap: Writing straight into the live table

Writing row by row into the table that readers use exposes every partial state. A banner or a slower load only hides the problem for a while.

What each function needs

The lab needs a small set of Python ideas. Each one is taught below with an example that has nothing to do with the lab's data. Work out how each idea applies to the lab yourself.

Returning a tuple. A tuple is a fixed group of values in round brackets. A function returns two values by separating them with a comma. The caller can unpack them into two names.

def split_total(total):
    return total // 2, total - total // 2

halves, rest = split_total(7)
print(halves, rest)

The output is 3 4. The expression total // 2 is integer division, which drops the remainder. The caller's line halves, rest = ... unpacks the tuple into two names.

Dictionary lookups with a default. d[key] raises a KeyError if the key is missing. d.get(key) returns None in that case, and d.get(key, default) returns your default instead.

stock = {"apple": 3}
print(stock.get("apple"), stock.get("pear"), stock.get("kiwi", 0))

The output is 3 None 0. Use get when a key may be absent, and then test the result yourself.

Counting with a dictionary. To count items, start with an empty dictionary. For each item, read the current count with get and store one more.

counts = {}
for colour in ["red", "blue", "red"]:
    counts[colour] = counts.get(colour, 0) + 1
print(counts)

The output is {'red': 2, 'blue': 1}. The first time a colour appears, get returns 0, so the count starts at one.

Counter from collections. Counter does the same job as the loop above. Its items() method gives pairs, and sorted puts them in order.

from collections import Counter
c = Counter(["red", "blue", "red"])
print(sorted(c.items()))

The output is [('blue', 1), ('red', 2)]. sorted on a list of tuples compares the first item of each tuple, then the second if the first ties.

Sorting with a key. sorted(items) returns a new list in ascending order, and it leaves the original list unchanged. sorted(items, key=len) compares the lengths instead of the items themselves.

words = ["pear", "fig", "banana"]
print(sorted(words))
print(sorted(words, key=len))
print(words)

The output is ['banana', 'fig', 'pear'], then ['fig', 'pear', 'banana'], then ['pear', 'fig', 'banana']. The last line shows that sorted did not change the original list.

Types and booleans. isinstance(x, int) is True for integers, and isinstance(x, float) is True for floats. A boolean is a subclass of int in Python, so isinstance(True, int) is True. When a boolean must be rejected, test for it first.

for x in [5, 2.5, True, "7"]:
    if isinstance(x, bool) or not isinstance(x, (int, float)):
        print(repr(x), "rejected")
    else:
        print(repr(x), "accepted")

The output is 5 accepted, 2.5 accepted, True rejected and '7' rejected. The repr function shows the value with its quotes, so the text '7' is visibly a string.

Membership in a set. x in {"a", "b"} is True if x is one of the set's items. Membership in a set is fast, and it reads more clearly than a long chain of or tests.

flavours = {"sweet", "sour"}
print("sour" in flavours, "salty" in flavours)

The output is True False. The comparison is case sensitive, so "Sour" would not be found.

Chained comparisons. Python lets you write 0 <= x <= 10, which means the same as 0 <= x and x <= 10. Both ends are included in this form. To exclude an end, use < instead of <=.

for x in [0, 5, 10, 11]:
    print(x, 0 <= x <= 10)

The output is 0 True, 5 True, 10 True and 11 False. The test is inclusive at both ends.

Regular expressions. The module re matches text against a pattern. re.fullmatch(pattern, text) returns a match only if the whole text fits the pattern. re.match and re.search do not require that. There is a trap with the $ symbol: in Python, $ also matches just before a newline at the end of the text.

import re
print(bool(re.match(r"^[a-z]+$", "abc\n")))
print(bool(re.fullmatch(r"[a-z]+", "abc\n")))

The output is True, then False. The $ matched before the trailing newline in the first line. fullmatch requires the whole text, including the newline, to fit the pattern, so it fails.

Not changing the input. A function that returns a new value should not change the list or dictionary it was given. Build a new list for the result. Calling .sort() on a list changes that list in place, while sorted(...) returns a new one.

data = [3, 1, 2]
ordered = sorted(data)
print(data, ordered)

The output is [3, 1, 2] [1, 2, 3]. The original list is unchanged, and the test harness may reuse the same input list in several tests.

A method that works for every graded lab

Follow these steps in this order. They take longer than submitting a first guess, but they find the mistakes that cost hidden-test points.

  1. Read the starter file from top to bottom. Note the imports, the module-level names and the signature of each function. Do not change the names.
  2. Write the examples from the statement as assert lines before you write any function. An assert line stops the program with an error if its condition is false. Put the statement's own example first, because it is the one fact you are sure of.
  3. Add your own assert lines for every row of the table above. Each row should have at least one line that would fail for a careless solution.
  4. Implement one function at a time. Start with the one that is easier to test. Run the file after each change, and fix any failing assert before you move on.
  5. Check types and counts last. Make sure the functions return tuples and lists, that counts are ints, and that empty input gives the empty result.
  6. Run the visible tests. Read each failure message, because it names the test and the expected output.
  7. Submit once, when every assert you wrote passes and the visible tests pass.

Writing the asserts first makes the rules concrete. You will notice an unclear rule while you write the test, which is far cheaper than finding it after a hidden test fails.

Worked twin problem

The twin problem below has a different domain, different data and a different rule order, so it does not give you the lab's answer. It uses the same skills: rules checked in order, the first failing rule wins, a count per reason, and an accepted and quarantined total. The domain is a sign-up form for a community library app.

A sign-up record is a dictionary with four keys: email, age, country and joined. Write two functions.

  • triage_signups(records) returns a tuple (accepted_count, quarantined_count).
  • quarantine_counts(records) returns a dictionary that maps each reason to the number of quarantined records with that reason.

A record is quarantined for the first failing rule, checked in this order:

  • joined is not a string matching the pattern YYYY-MM-DD (digits only). The reason is "bad_joined". The pattern is the only test: you do not check the calendar.
  • age is not an int, and booleans are invalid. Floats such as 21.0 are also invalid here. The reason is "bad_age".
  • age is less than 16 or greater than 120. The reason is "age_range".
  • country is not one of "IN", "US", "GB" or "DE" (exact, capital letters). The reason is "bad_country".
  • email is missing, is not a string, or does not contain exactly one @. The reason is "bad_email".

Here is the solution:

import copy
import re

JOINED_RE = re.compile(r"\d{4}-\d{2}-\d{2}")
COUNTRIES = {"IN", "US", "GB", "DE"}


def signup_problem(record):
    joined = record.get("joined")
    if not isinstance(joined, str) or JOINED_RE.fullmatch(joined) is None:
        return "bad_joined"
    age = record.get("age")
    if isinstance(age, bool) or not isinstance(age, int):
        return "bad_age"
    if age < 16 or age > 120:
        return "age_range"
    if record.get("country") not in COUNTRIES:
        return "bad_country"
    email = record.get("email")
    if not isinstance(email, str) or email.count("@") != 1:
        return "bad_email"
    return None


def triage_signups(records):
    accepted = 0
    quarantined = 0
    for record in records:
        if signup_problem(record) is None:
            accepted += 1
        else:
            quarantined += 1
    return accepted, quarantined


def quarantine_counts(records):
    counts = {}
    for record in records:
        reason = signup_problem(record)
        if reason is not None:
            counts[reason] = counts.get(reason, 0) + 1
    return counts


GOOD = {"email": "asha@example.com", "age": 21, "country": "IN", "joined": "2026-02-14"}
NO_EMAIL = {k: v for k, v in GOOD.items() if k != "email"}

    GOOD,
    {**GOOD, "joined": "14/02/2026"},

The first lines import copy and re, then create a compiled pattern and a set of allowed countries. JOINED_RE is compiled once, so the pattern is not rebuilt for every record. COUNTRIES is a set, so the membership test is quick and clear.

signup_problem runs the rules in the order given. Each if returns a reason as soon as the record breaks that rule, so the first failing rule is the one reported. The .get calls read the fields without crashing when a key is missing. The isinstance(joined, str) test comes before fullmatch, because fullmatch on None raises a TypeError. When every rule passes, the last line returns None.

The boolean test comes before the number test. isinstance(True, int) is True, so without the first check a boolean age would be accepted as the number 1. In this twin a float age such as 21.0 is also invalid, because only int is allowed. That is a choice made by this twin's statement, so always read your own statement to see which types it allows.

The age rule uses age < 16 or age > 120. An age of exactly 16 or exactly 120 is accepted, because both bounds are inclusive, and 15 and 121 are quarantined. Because the age-range rule comes before the country rule, a record with age 5 and country "XX" is reported as age_range only.

The email rule is the last one. NO_EMAIL has no email key at all, so .get gives None, and None is not a string. The text "a@@b.com" has two @ signs, so it fails too.

triage_signups counts accepted and quarantined records in one loop. quarantine_counts builds the dictionary with the get counting pattern, and it adds a count only for quarantined records. The final asserts check empty input, the boundaries, the first-failing-rule behaviour and the fact that the input was not changed. Compare the totals by hand: 3 accepted and 10 quarantined make 13 records, and the reason counts 2, 2, 2, 1 and 3 also add up to 10.

Run the file. It prints nothing and exits normally, because every assert passes. If one assert fails, Python stops and shows the line number, which tells you which rule is wrong.

Say it out loud

Interviewers and viva examiners will ask you to explain your choices. Practise answering in full sentences.

Why does your pipeline stop before the load step, and not after it?

Model answer

The load step writes data that other people and systems read, so it must only run on data that has passed the checks. If the checks ran after the load, the bad readings would already be in the database and the dashboard. The gate sits between validate and load, so a blocking failure stops the run before anything is written. A bad batch then costs us a rerun, not a corrupted dashboard.

What does set -euo pipefail do, and what goes wrong without it?

Model answer

The -e option stops the script at the first command that fails, so later stages do not run on bad input. The -u option makes an unset variable an error, which catches typing mistakes in names. The pipefail option makes a pipeline fail if any part fails, not only the last command. Without pipefail, a command piped into tee can fail silently, because tee returns zero, and the script carries on as though the stage succeeded.

What is the difference between a blocking check and a warning, and how do you choose?

Model answer

A blocking check stops the pipeline when it fails, and a warning is reported while the run continues. I choose blocking for data we must never publish, such as negative PM2.5 readings or duplicate keys, because those would corrupt every view that depends on them. A check on something that is only unusual, such as a drift in the average, is a warning, because stopping the pipeline for it would delay good data. Each threshold needs a reason written beside it.

What makes your load idempotent?

Model answer

Running the load twice leaves the same table as running it once. In the lab, to_sql with if_exists="replace" drops the old table and writes the new one, so a second run overwrites rather than adds. The course's version runs the pipeline twice from a fresh clone and compares the fact count, which must not change between runs. I would also mention that the replace form is not fully atomic, so a crash mid-load could leave a partial table, and the production fix is to load into a new table and switch.

Walk me through how a rejected sign-up record is counted.

Model answer

The record goes through the rules in a fixed order: missing fields, email, age, country, then joined date. The first rule it breaks gives its reason, and the function stops checking it. The record is added to the quarantined list with that reason, and the count for that reason goes up by one. A record that breaks several rules is counted only once, under the first, so the reason counts always add up to the quarantined count.
