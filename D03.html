Day 3 — Talking to APIs: HTTP, curl and jq

The idea in one minute

Today you learn how a program asks another computer for data. A weather service, an air-quality service or a station network can publish readings at a web address, and your script can ask for them the same way a browser asks for a web page. You will use two command-line tools to do this. curl sends the request and collects the reply. jq opens the reply, which is structured data, and keeps only the fields you need. By the end you will be able to run a script that fetches air-quality readings for Bengaluru, refuses to write anything if the request failed, and appends one clean CSV row to a daily file.

Think of an HTTP call as ordering at a counter. You state what you want, you get a receipt code that says whether the order worked, and then you get a tray with the food on it. The receipt code is the status code. The tray is the body.

Starting from zero

This section explains the words you will meet today. Read it once before you open a terminal.

Terminal. A window where you type text commands and the computer types text back. On Windows the course uses a Bash shell inside Git Bash or a similar tool. The terminal is the only place you need for today.

Command. A line you type that asks the computer to run a program. The first word names the program. The rest are arguments, which tell the program what to do. In curl -s "https://example.com", the program is curl, -s is an option and the quoted text is an argument.

Flag. An option that changes how a program behaves. Flags usually start with one dash for a short form (-s) or two dashes for a long form (--fail). Each one changes a single behaviour. You will see many of them today.

File. A named block of data stored on disk. A script is a file of commands. A CSV file is a file of rows of text.

Variable. A name that holds a value. In Bash you write URL="https://example.com" to store the text, and you write $URL to read it back. The dollar sign means "the value stored under this name".

Function. A named piece of code that takes inputs, does work and gives back a result. You will write Python functions in the graded lab later in this chapter.

Server. A program that waits for requests and sends replies. An API is a server that is designed to be called by other programs. The server runs somewhere else, often in a data centre, and your script is the client.

API. Application Programming Interface. It is a set of agreed web addresses and rules for asking a program for data. Think of it as a menu with fixed item names.

URL. Uniform Resource Locator. The web address of one resource. A URL has a scheme (https), a host (the server name, such as air-quality-api.open-meteo.com), a path (/v1/air-quality) and an optional query string after a question mark.

Query string. The part of a URL after ?. It is a list of name=value pairs joined by &. For example, latitude=12.97&longitude=77.59 asks for data at one place.

HTTP. Hypertext Transfer Protocol. It is the set of rules that a client and a server follow when they exchange requests and replies. A request has a method (such as GET), a URL, headers and sometimes a body. A reply has a status code, headers and sometimes a body.

Method. The verb at the start of an HTTP request. GET asks for data. POST sends data to be created or processed. Most of today's examples use GET.

Status code. A three-digit number in the reply. 200 means OK. 401 means the server wants credentials you did not send or could not verify. 404 means the URL does not exist. 500 means the server failed. The number is the server's receipt.

Header. A line of metadata sent with a request or reply, written as Name: value. Examples are Content-Type: application/json, which says the body is JSON, and X-API-Key: ..., which carries a key.

Body. The main content of a request or reply. For a JSON API the body is usually a JSON document.

JSON. JavaScript Object Notation. It is a text format for structured data. It has objects written in curly braces with "key": value pairs, arrays written in square brackets, and values that are strings, numbers, true, false or null. A reading might look like {"pollutant": "PM2.5", "value": 42.1}.

CSV. Comma-Separated Values. A plain text file where each line is one row and commas separate the values. The first line is often a header with the column names.

stdout and stderr. Every program has two output channels. Standard output (stdout) carries the normal result. Standard error (stderr) carries messages. Keeping them apart stops error text from being mixed into your data. You send a message to stderr with >&2.

Pipe. The vertical bar |. It takes the stdout of the command on the left and feeds it to the stdin (standard input) of the command on the right. curl ... | jq ... means "send the body curl gets into jq".

Redirect. The > and >> symbols. > writes the output to a file and replaces the file. >> adds the output to the end of the file.

Exit code. A number a program returns when it finishes. 0 means success. Any other number means failure. Bash stores the exit code of the last command in $?. A script can stop with exit 1.

Environment variable. A named value that a program inherits from the shell it runs in. You read it with $NAME. Environment variables are the usual place to put secrets such as API keys, because the script can read them without the secret being written into the script.

Git and Git history. Git records every version of your files as commits. Anything committed, even if you delete it later, stays in the history unless you rewrite it. This matters for secrets.

.gitignore. A file that lists names Git must not track. A line .env in .gitignore tells Git to ignore your local secrets file.

The tools

HTTP and JSON

HTTP is the protocol and JSON is the data format. Together they are the usual way a modern web API works. CityPulse uses this pattern because the air-quality sources it needs, such as Open-Meteo and OpenAQ, publish their data only through HTTP JSON APIs. There is no file to download by hand and no page to scrape.

The alternatives have problems the course wants you to avoid. Downloading a CSV file by hand is fine for one analysis, but it cannot run every 30 minutes on a schedule. Scraping an HTML page works when no API exists, but it breaks whenever the page layout changes, and it may break the site's terms of use. An API gives you a stable contract, so the script can rely on it.

A request is made of a method, a URL with a query string, headers and sometimes a body. A reply has a status line, headers and the body. The lesson's rule is simple. Look at the status first. You trust the body only when the status is 200.

Key fact: Check the status before the body

A 404 or a 500 can still come with a body, often an error message in HTML or JSON. Reading that body as data gives you nonsense. Always check the status code first.

Here is the anatomy of the Open-Meteo request the lesson uses. The slide breaks the URL across lines for display. In a script it must be one line, or it must be held in a quoted variable:

https://air-quality-api.open-meteo.com/v1/air-quality?latitude=12.97&longitude=77.59&current=pm2_5,pm10&timezone=Asia%2FKolkata

Line by line, reading the URL from left to right:

  • https:// is the scheme. It means the request is encrypted with TLS, the same protection a bank website uses.
  • air-quality-api.open-meteo.com is the host. This is the server name.
  • /v1/air-quality is the path. It names the resource on that server.
  • ? starts the query string.
  • latitude=12.97 and longitude=77.59 are two parameters that select a place near Bengaluru.
  • current=pm2_5,pm10 asks for two values, PM2.5 and PM10, in the current block of the reply. The comma separates the two names.
  • timezone=Asia%2FKolkata asks for times in the Kolkata time zone. The slash in Asia/Kolkata is written as %2F. This is URL encoding: a slash has a special meaning in a URL, so it is replaced by its code.

The slide's warning covers two common mistakes. Forgetting to URL-encode values such as Asia/Kolkata gives the server a different request from the one you meant. Leaving a URL unquoted in the shell lets the shell read the & as "run this in the background", which cuts your URL in half. Always wrap the URL in double quotes.

Trap: Unquoted URLs

In curl https://example.com/a?x=1&y=2, the shell sees & and runs curl ... in the background with only part of the URL. Wrap every URL in quotes: curl "https://example.com/a?x=1&y=2".

curl

curl is a command-line HTTP client. You give it a URL and it sends a request, then prints or saves the reply. It is installed on the lab machines already, and it works inside cron, which is the scheduler you will use in the next lesson. That is why CityPulse uses it for the first fetcher instead of a Python library. The alternatives are Postman, which is good for exploring by hand but cannot run unattended, and wget, which handles simple downloads but is less convenient for capturing status codes and headers.

curl has many flags. Here are the ones the lesson uses, with what each does:

Flag Meaning
-s Silent. Hides the progress meter so the output is clean.
-o FILE Output. Saves the body to FILE. -o /dev/null throws the body away.
-w FORMAT Write-out. Prints information about the transfer after it ends. -w '%{http_code}' prints the status code.
-D - Dump headers. Writes the reply headers to stdout. The - means stdout.
--max-time 20 Gives up after 20 seconds in total.
-f or --fail Makes curl exit with an error when the server returns an HTTP error code.
-H 'Name: value' Adds a header to the request.

The slide's core command is this one:

curl -s -D - -o /dev/null "$URL" | head -5

Line by line:

  • curl is the program.
  • -s hides the progress meter, so only real output appears.
  • -D - prints the reply headers to stdout. The dash means "stdout".
  • -o /dev/null discards the body. /dev/null is a special file that accepts anything and keeps nothing.
  • "$URL" is the URL held in the variable URL, quoted so the shell does not split it.
  • | head -5 pipes the output into head, which shows only the first five lines.

Expect to see the status line first, such as HTTP/2 200, then a few header lines such as the content type. The exact headers depend on the server. The body is not shown because you discarded it.

The workbook's version of the same idea uses a status-only check:

curl -s -o /dev/null -w '%{http_code}\n' https://air-quality-api.open-meteo.com/v1/nope

Line by line: -o /dev/null throws the body away, -w '%{http_code}\n' prints only the status code followed by a newline, and the URL points at a path that does not exist. You should see a 404-style code on its own line, not a page of text. This tells you the endpoint is wrong, not that the data is missing.

The next example is the one the course gives for the first real fetcher. It is the core of scripts/fetch_once.sh:

#!/usr/bin/env bash
URL="${URL:-https://air-quality-api.open-meteo.com/v1/air-quality?latitude=12.97&longitude=77.59&current=pm2_5,pm10&timezone=Asia%2FKolkata}"
TMP="$(mktemp)"
trap 'rm -f "$TMP"' EXIT
STATUS="$(curl -s --max-time 20 -o "$TMP" -w '%{http_code}' "$URL")"
if [ "$STATUS" != "200" ]; then
  echo "ERROR: HTTP $STATUS from $URL" >&2
  exit 1
fi
echo "OK: $(wc -c < "$TMP") bytes"

Line by line:

  • #!/usr/bin/env bash is the "shebang". It tells the system to run this file with Bash.
  • URL="${URL:-...}" sets URL to the value already in the environment if there is one, and to the Open-Meteo address if there is not. The :- means "use the default when the variable is empty or unset". This lets a squad change the source without editing the script.
  • TMP="$(mktemp)" creates a new empty temporary file with a unique name and stores its path in TMP. The $(...) runs the command and substitutes its output.
  • trap 'rm -f "$TMP"' EXIT says: whenever this script exits, for any reason, delete the temporary file. This is cleanup that happens even when the script fails.
  • STATUS="$(curl ... -w '%{http_code}' "$URL")" runs curl. The body goes into $TMP because of -o. The status code goes to stdout because of -w, and the $(...) captures it into STATUS. --max-time 20 makes curl give up after 20 seconds.
  • if [ "$STATUS" != "200" ]; then checks whether the status is anything other than 200. The [ ... ] is the test command, and != means "not equal".
  • echo "ERROR: ..." >&2 writes the error to stderr, so it cannot be mistaken for data.
  • exit 1 stops the script with exit code 1. Nothing after this line runs, so the CSV is never touched.
  • echo "OK: $(wc -c < "$TMP") bytes" prints the byte count of the body. wc -c counts bytes and < feeds the file in.

Expected output on success is one line such as OK: 512 bytes. The exact number depends on the reply. On an unknown URL the script prints ERROR: HTTP 404 from ... on stderr and exits with code 1. You can check the exit code with echo $? straight after running it.

Trap: Status 000 is not a 0

When curl cannot reach the server at all, for example because the name cannot be resolved, the network is down or the request timed out, the status code it prints is 000. This is a failure, not a valid status. Report it as an error. Do not treat it as data.

Trap: No timeout means a stuck script

Without --max-time, a server that accepts the connection and then goes silent can hang your script for a very long time. A scheduled job that hangs is worse than one that fails. Always set a limit.

jq

jq reads JSON from stdin or from a file and runs a filter on it. A filter is a small expression that selects, checks or reshapes the data. jq can also print raw strings and CSV rows, which makes it the bridge between an API reply and a data file. CityPulse uses jq for the reshaping step because it keeps the fetcher in Bash with no extra runtime. The alternatives are grep and sed on raw JSON, which look quick but break when key order or whitespace changes, and the Python json module, which you will use from Day 10 onwards.

The main jq ideas are these:

  • . is the whole input.
  • .key is the value stored under key.
  • .key.inner goes down two levels.
  • .[] or .items[] loops over every element of an array and outputs each one.
  • | inside a filter pipes one filter's output into the next, in the same way as the shell pipe.
  • select(condition) keeps the input only when the condition is true.
  • -r prints strings without their JSON quotes.
  • -e makes jq set its exit code from the last output: a null or false result gives a non-zero exit.
  • --arg name value passes a shell value into the filter as $name.
  • @csv turns an array into one CSV line with quoting.

The lesson's validate-and-append code shows several of these together:

LOC="${LOC:-Bengaluru}"
OUT="data/raw/$(date +%F).csv"
mkdir -p data/raw
if ! jq -e '.current.pm2_5 != null and .current.pm10 != null' "$TMP" > /dev/null; then
  echo "ERROR: required field missing in response" >&2
  exit 2
fi
[ -s "$OUT" ] || echo 'timestamp,location,pm2_5,pm10' > "$OUT"
jq -r --arg loc "$LOC" '[.current.time, $loc, .current.pm2_5, .current.pm10] | @csv' "$TMP" >> "$OUT"
tail -3 "$OUT"

Line by line:

  • LOC="${LOC:-Bengaluru}" gives the location name a default, as with URL.
  • OUT="data/raw/$(date +%F).csv" builds a file name from today's date. date +%F prints the date as 2026-11-17, so the output file is one file per day.
  • mkdir -p data/raw creates the folder if it is missing. The -p means "no error if it exists, and create parent folders too".
  • if ! jq -e '...' "$TMP" > /dev/null; then runs jq on the body. The ! inverts the result, so the branch runs when jq fails. > /dev/null hides jq's output because you only want its exit code.
  • .current.pm2_5 != null and .current.pm10 != null is the filter. != means "not equal" and null is JSON's empty value. The filter is true only if both fields exist and have values.
  • exit 2 gives this failure its own code, so a caller can tell "bad body" from "bad status" (exit 1).
  • [ -s "$OUT" ] || echo '...' > "$OUT" writes the header row only if the file is missing or empty. -s is true when the file exists and has content. || runs the right side only when the left side fails.
  • jq -r --arg loc "$LOC" '...' "$TMP" >> "$OUT" runs the CSV filter. -r removes quotes from the output string, --arg loc makes $loc available inside the filter, and >> appends one line to the day file.
  • The filter [.current.time, $loc, .current.pm2_5, .current.pm10] | @csv builds an array of four values and turns it into one line.
  • tail -3 "$OUT" shows the last three lines so you can check what was written.

The expected output for a first run is the header followed by one row, such as timestamp,location,pm2_5,pm10 on one line and then a row beginning with the time string from the API. The row uses the values from that moment, so your numbers will differ.

Trap: Forgetting -r

Without -r, jq prints the CSV line as a JSON string, with escaped quotes and a surrounding pair of quotes. The file then contains lines that no CSV reader can parse. Add -r whenever the output is raw text.

Trap: Without -e, nulls slip through

Without -e, jq exits with 0 even when the filter returns null. The check then never fails, and rows with missing values are appended to the file. Use -e for every validation.

Trap: Shell variables inside the filter

Writing '[.current.time, "$LOC"]' puts the shell text into the filter with the quotes mixed up. Pass shell values with --arg and refer to them as $loc inside the filter.

Environment variables for secrets

An environment variable is a named value that a process inherits from its shell. A script reads it with $NAME. CityPulse keeps API keys in environment variables, not in scripts, because a key written into a script is copied into Git history the first time you commit it. The course's rule is that the repository contains only .env.example, which lists the variable names with empty values. Each person copies it to .env, fills in the real values and restricts the file so only they can read it.

The alternatives are the common real-world leak, a key hard-coded in the script, which is never acceptable here, and AWS Secrets Manager, which is right for production services later in the programme but is too much for a lab script.

The course's loading commands are these:

cp .env.example .env && chmod 600 .env
set -a; source .env; set +a
: "${OPENAQ_API_KEY:?set OPENAQ_API_KEY in .env}"

Line by line:

  • cp .env.example .env copies the template to a new file called .env. The && runs the next command only if the copy succeeds.
  • chmod 600 .env changes the file permissions so only the owner can read and write it. 600 is the octal code for that. Then edit the file to add your real key.
  • set -a turns on automatic export, so every variable assigned from now on is passed to child programs.
  • source .env runs the lines of .env in the current shell, so each NAME=value becomes a variable.
  • set +a turns automatic export off again.
  • : "${OPENAQ_API_KEY:?set OPENAQ_API_KEY in .env}" is a check. The colon is a command that does nothing. ${NAME:?message} makes Bash stop with the message if the variable is empty or unset. Expect the script to stop with your message if you forgot to fill in the key.

The lesson then sends the key in a header, not in the URL:

curl -s -H "X-API-Key: $OPENAQ_API_KEY" \
  'https://api.openaq.org/v3/locations?coordinates=12.97,77.59&radius=10000&limit=1' | jq '.results[0].name'

Line by line: -H "X-API-Key: $OPENAQ_API_KEY" adds the header with the key's value filled in by the shell. The backslash at the end of the first line joins it to the second line. The URL asks for one monitoring location near the centre of Bengaluru. The pipe sends the reply to jq, and .results[0].name takes the name of the first result. The output is one quoted name, such as "Some Station Name". The name depends on what the server returns.

Two checks prove the key is not in your repository:

git check-ignore .env
git log -p --all | grep -inE 'api[_-]?key|token' | head

Line by line: git check-ignore .env prints .env if Git ignores that file. If it prints nothing, the file is not ignored and you must fix .gitignore before you do anything else. The second command shows every change in every commit on every branch. git log -p --all prints the changes, grep -inE searches them for the words api_key, api-key, apikey or token, ignoring case (-i), showing line numbers (-n) and using extended patterns (-E). head shows the first matches. The course expects you to see variable names only, such as OPENAQ_API_KEY in .env.example, and never a key value.

Trap: Deleting a key does not remove it from history

If a key was committed, a later commit that deletes it still leaves the key in the history. Anyone who clones the repository can read it. Rotate the key with the provider straight away. Rotating means creating a new key and disabling the old one.

Trap: bash -x prints your secrets

bash -x prints every expanded command before it runs. A command that uses $OPENAQ_API_KEY is printed with the real key. Never paste traced output into a chat, a ticket or a public place.

Trap: Create .gitignore before .env

If you create .env before you add it to .gitignore, a quick git add . can stage it. Add .env to .gitignore first, then create the file.

The worked example

The workbook takes you through a station service with a short script. It is the clearest way to see the whole cycle once. The station service runs at http://localhost:8008, so start it before you begin. Each step below has a goal, the command, an explanation and the output.

Step 1: check the endpoint answers

Goal: confirm the endpoint and the station id are valid before you parse anything.

curl -s -o /dev/null -w 'HTTP %{http_code}\n' 'http://localhost:8008/v1/readings?station=7'

Line by line: -s hides the progress meter. -o /dev/null throws away the body, because you only need the status. -w 'HTTP %{http_code}\n' prints the word HTTP and the status code followed by a newline. The URL asks for station 7.

Output:

HTTP 200

A 200 means the endpoint and the station are valid.

Step 2: look at the raw body

Goal: see the shape of the data before you decide what to keep.

curl -s 'http://localhost:8008/v1/readings?station=7'

This time the body is printed, because there is no -o flag. Output begins like this:

{
  "station_id": 7, "name": "MG Road", "readings": [
    { "ts": "2026-06-01T08:00:00Z", "pollutant": "PM2.5", "value": 42.1, "unit": "ug/m3" },
    ...

The body is one object. It has a station_id, a name and a readings array. Each reading has a time stamp, a pollutant, a value and a unit. Knowing this structure tells you the jq path to use: .readings for the array, and .pollutant or .value for each item.

Step 3: pick two fields with jq

Goal: keep only the fields CityPulse stores from each reading.

curl -s 'http://localhost:8008/v1/readings?station=7' | jq -c '.readings[] | {pollutant, value}'

Line by line: curl -s fetches the body and sends it into the pipe. .readings[] loops over the array. {pollutant, value} builds a smaller object with only those two keys. The output is one small object per reading, as shown in the jq section above.

Step 4: filter with select

Goal: keep only the PM2.5 readings above the 40 watch level.

curl -s 'http://localhost:8008/v1/readings?station=7' \
  | jq '.readings[] | select(.pollutant=="PM2.5" and .value > 40) | .value'

Line by line: the first line fetches the readings. The second line loops over the readings, keeps only those where the pollutant is PM2.5 and the value is above 40, and then outputs just the value. The and joins the two conditions, so both must be true. The == in jq tests for equality. The > tests for greater than. The output is:

42.1
47.9

Only the two PM2.5 readings above 40 survive. The NO2 reading at 18.7 is dropped.

Step 5: reshape into CSV rows

Goal: flatten each reading into a row with the station id, time, pollutant and value.

curl -s 'http://localhost:8008/v1/readings?station=7' \
  | jq -r '.station_id as $s | .readings[] | [$s, .ts, .pollutant, .value] | @csv'

Line by line: .station_id as $s stores the station id in a jq variable called $s. The pipe then loops over the readings, and each reading is turned into an array of four values. The $s is repeated on every row because each reading needs it. @csv turns each array into one quoted CSV line. The -r stops jq from printing the lines as JSON strings. Output:

7,"2026-06-01T08:00:00Z","PM2.5",42.1
7,"2026-06-01T08:00:00Z","NO2",18.7
7,"2026-06-01T09:00:00Z","PM2.5",47.9

@csv puts quotes around every string, so the time stamps and pollutant names are quoted. The numbers are not quoted.

Step 6: loop over stations and skip failures

Goal: fetch several stations in one run and skip any that return an error.

for s in 7 42 9 99; do
  code=$(curl -s -o /tmp/r.json -w "%{http_code}" "http://localhost:8008/v1/readings?station=$s")
  if [ "$code" = "200" ]; then
    n=$(jq '.readings | length' /tmp/r.json)
    echo "station $s: $code ($n readings)"
  else
    echo "station $s: $code (skipped)"
  fi
done

Line by line: for s in 7 42 9 99; do runs the body once per station id. code=$(...) captures the status code. -w "%{http_code}" prints only the code, and $(...) stores it. The if branch runs when the code is 200. Inside it, jq '.readings | length' counts the readings. length is a jq function that counts the elements of an array. The else branch prints a skip message, which keeps one bad station from stopping the others. The done closes the loop.

Output:

station 7: 200 (3 readings)
station 42: 200 (2 readings)
station 9: 200 (2 readings)
station 99: 404 (skipped)

Station 99 is skipped because it returned 404, and the run carries on.

Note that the workbook writes to /tmp/r.json, which is a fixed name. A real script should use mktemp as the lesson's fetch_once.sh does.

Step 7: run the whole pull

Goal: fetch every station and append all the rows to one CSV file.

#!/usr/bin/env bash
set -euo pipefail
API="http://localhost:8008/v1/readings"
echo "station_id,ts,pollutant,value" > readings.csv
for s in 7 42 9; do
  curl -sf "$API?station=$s" \
    | jq -r '.station_id as $s | .readings[] | [$s,.ts,.pollutant,.value] | @csv' \
    >> readings.csv
done
echo "wrote $(( $(wc -l < readings.csv) - 1 )) rows"

Line by line: set -euo pipefail makes the script stop on any error (-e), on any unset variable (-u) and on any failure inside a pipe (pipefail). This is strict mode, and it stops a half-finished run from being reported as a success. API=... stores the endpoint. echo "station_id,ts,pollutant,value" > readings.csv writes the header and replaces any old file. The loop calls each station. curl -sf is silent and uses --fail, so an HTTP error makes curl exit non-zero, and set -e then stops the script. >> readings.csv appends each station's rows. The final line counts the lines in the file with wc -l and subtracts one for the header.

Output:

wrote 7 rows

Running head -3 readings.csv shows the header and the first two data rows, matching the workbook's sample.

Plain GET requests with curl

What it is. A GET request asks a server for data. It is curl's default method, so curl "$URL" with no method flag sends a GET. curl then prints the reply body to stdout, which is your terminal unless you send it somewhere else.

$ curl -s "https://api.example.org/v1/items"
{"items":[{"id":1,"name":"Pune"}]}

The output is the body exactly as the server sent it. curl has not created a file. Three flags are often confused here. -s hides the progress meter, and it changes only what you see. -o FILE saves the body to FILE. -O saves the body to a file named after the last part of the URL. A GET only reads data, so repeating it is safe.

How it shows up in a case study. The Y2 squad has a fetch step that runs curl -s "$URL" at the start of the day. The terminal shows a long JSON line, and the next step fails because items.json does not exist. The data is arriving, so the URL is right and the method is correct for reading. Nothing told curl where to put the body. Adding -o items.json writes the body to the file, and the next step finds it. Changing the method to POST would send a request the server does not expect.

Trap: Quiet does not mean saved

Adding -s does not save anything. It only hides the progress meter. Without -o, -O or a shell redirect, the body goes to the terminal and no file is written.

Pulling a field from every array item

What it is. jq reads JSON from a pipe or a file and applies a filter. .readings selects the array. [] breaks the array into its elements, and each element passes on to the rest of the filter. .value then picks one field from each element.

$ echo '{"readings":[{"value":42.1},{"value":18.7}]}' | jq '.readings[].value'
42.1
18.7

The output has one value per line, in array order. The field name comes after the element, not after the array. The filter .readings.value fails, because it asks an array for a key called value. jq reports Cannot index array with string "value". The filter .readings[] on its own prints whole objects, not the values.

How it shows up in a case study. Ana receives a readings payload, and she wants a list of pollutant names for a report. She writes jq '.readings.pollutant' and gets an error that mentions indexing an array. The error tells her the field name is in the wrong place. The fix is to loop first and then select the field: .readings[].pollutant. Her list then holds one name per reading, in the same order as the payload.

Trap: Missing brackets

.readings.value looks as if it should loop over the readings. It does not. Without [], jq asks the array for a key, and arrays do not have keys.

Sending a JSON body with POST

What it is. A POST request sends data to the server, usually to create or process something. In curl, -X POST sets the method, -H "Content-Type: application/json" tells the server that the body is JSON, and -d supplies the body. Using -d alone also sends a POST, but -X POST makes the intent clear.

$ curl -s -X POST -H "Content-Type: application/json" -d '{"city":"Pune"}' "$URL"

The body travels inside the request, not in the URL. The -G flag is the trap. With -G, every -d value is appended to the URL as a query string, and the request stays a GET. The server then receives no body.

How it shows up in a case study. A squad registers a new station by sending JSON to the stations endpoint. Their script runs curl -G -d '{"name":"MG Road"}' "$URL". The log shows the station name inside the URL, and no station is created. The request is a GET with the data in the query string. The fix is to remove -G, add -X POST and send the header, so the body travels in the request.

Trap: The -G flag

Adding -G because the command has data in it turns the data into a query string. A GET with a query string is still a GET, and the body is empty.

Reading a 401 status

What it is. The first digit of a status code is a class. 2xx means success, 4xx means the client sent something the server rejects, and 5xx means the server failed. A 401 Unauthorized reply means the server does not accept the credentials: none were sent, or they are wrong or expired. Despite its name, 401 is about who you are. A 403 Forbidden means the server knows who you are and refuses this action. A 404 means no resource lives at that URL.

The output is one number. A 401 tells you to check the key, not the jq filter, because the filter has not run yet.

How it shows up in a case study. The squad's fetch script worked last week. Today the same URL returns 401, and nobody has changed the script. The request reaches the server, which rejects the credentials. The body and the jq filter come after the status check, so they are not the cause. The likely reasons are an expired key, a key that was rotated, or an empty value in the .env file that the script loads.

Trap: 401 is not a jq problem

A typo in a jq filter appears only after a 200 status, and a wrong path usually gives 404. A 401 always points to credentials.

Sending keys in a header

What it is. Many APIs read a key from a request header, a line such as X-API-Key: value. In curl, -H adds one header. The header travels with the request, and it is not part of the address.

curl -s -H "X-API-Key: $OPENAQ_API_KEY" "https://api.openaq.org/v3/locations?limit=1"

The shell fills in the variable before curl runs, so the key value is sent in the header. Your shell history records the text you typed, which contains the variable name and not the value. Keys in the URL are different. A URL is written into server logs, proxy logs, browser history and shared links, so a key placed there can be read later. HTTPS protects the key while it travels between your computer and the server, but it does not protect a URL that is logged afterwards.

How it shows up in a case study. A developer copies an example that puts the key in the URL, as ?api_key=.... The squad's shared log then contains the key in plain text. The reasoning has two parts. First, move the key to a header so that future requests keep it out of the address. Second, treat the logged key as exposed and rotate it with the provider, because the log has already spread it.

Trap: Literal keys in commands or scripts

Typing the key value into a command puts it in your history. Writing it into a script puts it into Git history at the next commit. Use the variable name in both places.

Filtering with select

What it is. select(condition) passes its input through only when the condition is true, and drops it otherwise. Inside a filter, you usually loop first with [], so that select tests one element at a time. You can combine tests with and and or, compare with ==, !=, > and <, and then pipe the result to a field.

$ echo '{"readings":[{"pollutant":"PM2.5","value":42.1},{"pollutant":"NO2","value":18.7}]}' | jq '.readings[] | select(.value > 40) | .pollutant'
"PM2.5"

The loop sends each reading into select. Only the PM2.5 reading passes, and .pollutant prints its name. The output keeps quotes because there is no -r. Inside a filter, a single = is assignment, not a comparison. The filter select(.pollutant = "PM2.5") assigns, and the result of an assignment is the updated object, which jq treats as true, so every reading is kept.

How it shows up in a case study. Bilal writes jq '.readings | select(.value > 40) | .value' and gets an error that mentions indexing an array. He has applied select to the whole array, not to each reading. Adding [] after .readings sends each reading into the test separately. He then uses == to compare pollutant names.

Trap: One equals sign

In jq, = assigns and does not compare. A select built with = keeps everything, and the output looks plausible until you count the rows.

Viewing only the headers

What it is. Headers describe the reply: its type, its size and more. To see them without the body, use -D - to print the headers to stdout and -o /dev/null to throw the body away.

curl -s -D - -o /dev/null "$URL" | head -5

The output starts with a status line such as HTTP/2 200, followed by header lines such as content-type. The exact lines depend on the server. -I is a shorter option that sends a HEAD request, which asks for headers only. Some servers answer HEAD differently from GET, so -D - is the safer check when you need to match what a GET returns. -w '%{http_code}' prints only the status code, and it never prints headers.

How it shows up in a case study. Sana wants to check the content type before parsing a reply. She runs curl -s -o /dev/null -w '%{http_code}\n' "$URL" and sees only 200. The command is working, but -w prints the status and nothing else. She changes the command to -D - so the headers appear.

Trap: Status is not headers

-w '%{http_code}' prints one number, the status code. Headers need -D -.

Counting with length

What it is. length counts the elements of an array, the keys of an object, or the characters of a string. keys gives the names, not the count. For an array, keys gives the index numbers 0, 1, 2 and so on.

$ echo '{"readings":[{"v":1},{"v":2},{"v":3}]}' | jq '.readings | length'
3

The output is the count. If you replace length with keys, the output is a list of index numbers such as [0, 1, 2]. That list has three items, but it is not the count. .readings[] | length gives something else again: the number of keys inside each reading, one number per line.

How it shows up in a case study. Lina's log line should say how many readings a station returned. Her log reads [0,1,2]. She used keys, which prints index numbers. Changing the filter to .readings | length prints the count. Her reasoning is that the count must be one number, not a list.

Trap: Keys are not a count

keys on an array prints indices, so the output looks like a list of numbers that could be a count. Use length when you need the number.

Failing a script on HTTP errors with --fail

What it is. By default, curl treats any finished transfer as success, even when the server answers with an HTTP error. The exit code is 0. With -f or --fail, curl exits with code 22 when the status is 400 or above, and it does not print the error page as if it were data.

The first exit code is 0 because the transfer finished. The second is 22 because of -f. Under set -e, a non-zero exit stops the script. -s hides the progress meter and leaves the exit code alone.

How it shows up in a case study. Oscar's pull script runs curl -s "$API" and pipes the result to jq. The script uses set -euo pipefail. During an outage, the server returns HTTP 500 with an HTML page. The script does not stop at the HTTP step, and jq fails later with a parse error that does not name the cause. Oscar adds -f, so curl exits with 22 and the script stops at the right place.

Trap: Silent does not mean strict

-s only hides the progress output. A script with -s alone carries on after a 500, and that is the failure this trap describes.

The anatomy of an HTTP exchange

What it is. An HTTP request has a request line, headers and an optional body. The request line holds the method, the path and the query string. Each header is a Name: value line. A reply has a status line, headers and an optional body. A blank line separates the headers from the body.

GET /v1/items?city=Pune HTTP/1.1
Host: api.example.org
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{"items":[]}

The request tells the server what to fetch and which replies the client accepts. The reply tells the client whether the request worked and what the body is. HTTP/2 carries the same parts, and curl shows them with lowercase header names.

How it shows up in a case study. Ruth's script searches the JSON body for the word "error" to decide whether a request failed. One day the server returned a 500 status with a body that did not contain that word. The script treated the reply as good and wrote bad rows. The status line is the HTTP receipt, and the body is data. The script should check the status first, then check the fields it needs.

Trap: The status is not in the body

The status code lives in the status line. curl exposes it through -w '%{http_code}'. A body can contain any text, including words that look like errors.

What each function needs

The three functions need a small set of Python ideas. Each one is taught below with a tiny example that has nothing to do with the lab's data. Do not put these examples together to build the lab's functions. Their purpose is to show each idea on its own.

Parsing a JSON string. json.loads takes a string and returns Python objects. A JSON object becomes a dictionary, a JSON array becomes a list and a JSON number becomes an int or a float.

import json

shop = json.loads('{"aisles": [{"name": "dairy", "items": 4}]}')
print(shop["aisles"][0]["name"])   # dairy
print(type(shop["aisles"]))        # <class 'list'>

Expected output: dairy, then <class 'list'>.

Reading a key that may be missing. dict.get(key, default) returns the value when the key exists and the default when it does not. Plain d[key] raises a KeyError in that case.

stock = {"apples": 3}
print(stock.get("apples", 0))   # 3
print(stock.get("pears", 0))    # 0

Filtering a list with a comprehension. A list comprehension builds a new list in one line. The if part keeps only the items that pass the test, and the order stays the same.

numbers = [7, 2, 9, 4]
print([n for n in numbers if n % 2 == 0])   # [2, 4]

Dividing and rounding. / always gives a float in Python 3. round(x, 2) rounds to two decimal places. Python rounds a value that sits exactly halfway to the even neighbour, so round(2.5) gives 2 and round(3.5) gives 4.

print(sum([2, 4, 9]) / len([2, 4, 9]))   # 5.0
print(round(1 / 3, 2))                   # 0.33
print(round(2.5), round(3.5))            # 2 4

Checking for an empty collection. if not items: is true for an empty list, an empty dictionary and None. Use it before dividing by len, because dividing by zero raises ZeroDivisionError.

groups = []
if not groups:
    print("nothing to average")   # nothing to average

Sorting with a key and a tie-break. sorted(items, key=...) sorts by the value the key function returns. A tuple as the key sorts by its first part and then its second part. A minus sign flips a number to sort in descending order.

scores = [("bo", 5), ("al", 9), ("cy", 5)]
print(sorted(scores, key=lambda t: (-t[1], t[0])))
## [('al', 9), ('bo', 5), ('cy', 5)]

The first part sorts by score from high to low. The second part breaks ties by the name, from A to Z.

Testing types. isinstance(x, int) checks the type. bool is a subclass of int, so isinstance(True, int) is True. To exclude booleans from a number check, test for bool first.

print(isinstance(True, int))             # True
print(isinstance(True, bool))            # True
print(isinstance("3", (int, float)))     # False

Slicing and negative indexes. text[1:3] takes the characters from index 1 up to, but not including, index 3. A negative index counts from the end, so index -1 is the last item.

word = "harbour"
print(word[1:4])     # arb
print(word[-1])      # r

The median. statistics.median returns the middle value of a sorted list. With an even number of values it returns the average of the two middle values, as a float.

import statistics

Worked twin problem

The problem below is a different domain with the same skills. It is not the platform's problem. A parcel-tracking API returns a JSON string. Its top level is an object with a parcels list, and each parcel has a code (text), a status (text) and a weight_kg (a number).

Write three functions. Each takes one argument, the payload string.

  • delivered_codes(payload_json) returns a list of the code values of the parcels whose status is "delivered", in document order. It returns [] when there are no parcels.
  • mean_weight(payload_json) returns the mean weight_kg of the delivered parcels only, rounded with round(x, 2). It returns 0.0 when no parcel is delivered.
  • lightest_code(payload_json) returns the code of the delivered parcel with the lowest weight_kg. Parcels that are not delivered are ignored. If two delivered parcels share the lowest weight, the smaller code in ascending order wins. It returns None when no parcel is delivered.

The solution below is complete. Read it after you have tried the problem yourself.

import json


def delivered_codes(payload_json):
    data = json.loads(payload_json)
    codes = []
    for parcel in data.get("parcels", []):
        if parcel.get("status") == "delivered":
            codes.append(parcel["code"])
    return codes


def mean_weight(payload_json):
    data = json.loads(payload_json)
    weights = [p["weight_kg"] for p in data.get("parcels", [])
               if p.get("status") == "delivered"]
    if not weights:
        return 0.0
    return round(sum(weights) / len(weights), 2)


def lightest_code(payload_json):
    data = json.loads(payload_json)
    best_code = None
    best_weight = None
    for parcel in data.get("parcels", []):
        if parcel.get("status") != "delivered":
            continue
        w = parcel["weight_kg"]
        code = parcel["code"]
        if best_weight is None or w < best_weight or (w == best_weight and code < best_code):
            best_weight = w
            best_code = code
    return best_code


PAYLOAD = '{"parcels": [{"code": "P-14", "status": "delivered", "weight_kg": 2.5}, {"code": "P-02", "status": "lost", "weight_kg": 4.0}, {"code": "P-09", "status": "delivered", "weight_kg": 4.0}, {"code": "P-05", "status": "delivered", "weight_kg": 1.0}, {"code": "P-30", "status": "lost", "weight_kg": 0.5}]}'
TIE_ORDER = '{"parcels": [{"code": "P-88", "status": "delivered", "weight_kg": 3.0}, {"code": "P-11", "status": "delivered", "weight_kg": 3.0}]}'
THIRDS = '{"parcels": [{"code": "P-1", "status": "delivered", "weight_kg": 1.0}, {"code": "P-2", "status": "delivered", "weight_kg": 2.0}, {"code": "P-3", "status": "delivered", "weight_kg": 2.0}]}'

NO_KEY = '{}'
ONE = '{"parcels": [{"code": "P-7", "status": "lost", "weight_kg": 0.5}]}'

Line by line, the important parts are these.

  • import json gives the program the JSON reader, and json.loads(payload_json) turns the string into a dictionary. Each function starts with that line.
  • data.get("parcels", []) returns the list, or an empty list when the key is missing. That is why NO_KEY returns an empty result and does not crash.
  • In delivered_codes, parcel.get("status") == "delivered" keeps only the delivered parcels. Because the loop runs in array order, the codes come out in document order.
  • In mean_weight, the comprehension collects the weight of each delivered parcel only. The if not weights check comes before the division, so a payload with no delivered parcel returns 0.0 and never reaches ZeroDivisionError.
  • round(sum(weights) / len(weights), 2) rounds once, at the end. For PAYLOAD, the delivered weights are 2.5, 4.0 and 1.0. They add up to 7.5, and 7.5 divided by 3 is 2.5. For THIRDS, 5.0 divided by 3 is 1.666..., which rounds to 1.67.
  • In lightest_code, the continue skips any parcel that is not delivered, so a lighter lost parcel such as P-30 can never win. The first condition, best_weight is None, accepts the first delivered parcel. The second, w < best_weight, replaces the best when a parcel is lighter. The third handles a tie: a parcel with the same weight replaces the best only when its code is smaller.
  • The or order matters. When best_weight is None, Python stops at the first test and never compares code with best_code, which is also None at that point.
  • assert lines are the checks. Each one prints nothing when it passes and stops the program with an error when it fails. The is None test is used for empty results because None is compared by identity.

import json


def tally_points(payload_json):
    data = json.loads(payload_json)
    totals = {}
    for m in data.get("matches", []):
        team = m["team"]
        totals[team] = totals.get(team, 0) + m["points"]
    return totals


def top_team(payload_json):
    totals = tally_points(payload_json)
    if not totals:
        return None
    best = None
    for team in sorted(totals):
        if best is None or totals[team] > totals[best]:
            best = team
    return best

Say it out loud

These five questions are the kind an interviewer or viva examiner asks about this day. Answer them in your own words, and try to say each answer in under 30 seconds.

Why do you check the status code before reading the body?

Because an HTTP reply can carry a body whatever its status. A 404 or 500 often includes an error message, and if you parse that as data the script produces wrong rows without warning. Checking the status first means the script trusts the body only for a 200. Anything else is treated as a failure, the body is discarded and the script exits with code 1, so the CSV is never touched.

What does jq -e do, and why does the script use it?

The -e flag sets jq's exit code from the output. A null or false result gives a non-zero exit code, and a true result gives zero. Without it, jq returns zero even when a field is null, so bad rows would be appended. The script uses it to check that pm2_5 and pm10 exist before writing anything. When the check fails, the script exits with code 2, which is a different code from a bad status, so a caller can tell the two failures apart.

How do you keep an API key out of the repository?

The key lives in a .env file that Git ignores, and the repository contains only .env.example with the variable names. The script loads the file with set -a, source and set +a, then checks the variable is set with a default-error expansion. The key is sent in a header rather than the URL. Before you push, you check that git check-ignore .env prints the file name and that git log for key-like words shows only variable names, never values.

Why does the fetcher set a timeout and capture the status with -w?

A server that accepts a connection and then stops replying would hang a scheduled job forever, so --max-time gives curl a hard limit. The -w flag prints only the status code to stdout, which lets the script store it in a variable with command substitution, while the body goes to a temporary file. This keeps the status and the data separate, so the script can test the status and then read the body only when it is valid.

When would you use Python instead of curl and jq?

You would move to Python when the logic becomes too complex to read as a one-line filter, when you need to combine several sources, or when you need to test each part on its own. The course moves to Python from Day 10 onwards. A Python fetcher can use the standard library's HTTP tools and the json module and can be unit tested with assert statements. The curl and jq fetcher stays useful because it has no extra runtime and runs anywhere the shell does.
