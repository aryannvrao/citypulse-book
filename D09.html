The idea in one minute

Today you stop storing data in one big spreadsheet-like table and start storing it in linked tables. Each real-world fact gets one place. A station is stored once, and every reading points back to its station. The database itself refuses bad data, such as a duplicate sample or a reading for a station that does not exist. You will also load a file of 1,392 readings in a single step, and you will check that the load can be repeated without doubling the data.

Think of a library. The book catalogue lists each book once with its shelf location. Each loan slip carries only the book's catalogue number, not a copy of the title and author. If the library renames a shelf, only the catalogue changes.

Starting from zero

Read this section even if you think you know these words. The later sections use them without explaining them again.

Files, folders and the terminal

A file is a named block of data on your disk, such as readings.csv. A folder (also called a directory) holds files and other folders. The terminal is a window where you type text instructions to your computer. Each instruction is a command: a word, usually a program name, followed by options. An option (also called a flag) changes what the command does. For example, in ls -l, the program is ls and -l is an option.

A variable is a name that holds a value, such as count = 5. A function is a named block of code you call with brackets, such as len(rows). A server is a program that waits for requests from other programs. A client is a program that sends those requests.

Tables, rows, columns and keys

A database is a program that stores data safely and answers questions about it. A table holds one kind of thing. Each row is one item, such as one reading. Each column is one property of that item, such as pm2_5. A schema is the written plan of tables and columns, usually stored in a file of SQL statements.

A key is a column, or a set of columns, that identifies a row. A primary key must be unique and must not be empty. A foreign key says that a column's value must match a value in another table. A natural key is a key made from facts that already exist in the real world, such as a station id plus a timestamp. A surrogate key is a number the database invents, such as fact_id.

SQL

SQL (Structured Query Language) is the language you use to create tables, put rows in, change them and ask questions. A statement is one complete SQL instruction, normally ending with a semicolon. A query is a statement that asks for data, such as SELECT. DDL (data definition language) is the part of SQL that creates or changes structure, such as CREATE TABLE. The rest is about data, such as INSERT.

A constraint is a rule the database enforces on each row, such as "this value must not be empty". NULL is SQL's word for a missing value. It is not zero and it is not an empty string.

Transactions

A transaction is a group of changes that the database treats as one unit. It either commits (all changes are saved) or rolls back (all changes are undone). If your program crashes halfway, a rollback leaves the database as it was before the group started.

Words from Python and data files

Python is the programming language used in the course. A list is an ordered collection written with square brackets, such as [1, 2, 3]. A tuple is a fixed group of values written with round brackets, such as (1, "Hebbal", 51.3). A dictionary (dict) maps keys to values, such as {"S1": 3}. A loop repeats a block of code for each item in a collection.

CSV (comma-separated values) is a plain text file where each line is a row and commas separate the columns. The first line is often a header with the column names. pandas is a Python library for working with tables in memory. Parquet is a compressed file format for tables. You do not need pandas or Parquet for the lab, but the course's loader reads a Parquet file, so you will see them in the code.

Docker runs a program inside a container, an isolated package that carries everything the program needs. Postgres (PostgreSQL) is a database server, a program that other programs connect to over a network. SQLite is a database stored in a single file, with no server. Both understand SQL.

The tools

Relational model and star schema

What it is. The relational model stores data in tables that are linked by keys. A star schema is a layout for analytics. It has one fact table in the middle, holding measurements, and dimension tables around it, holding descriptions such as a location's name or a data source's name.

Why CityPulse uses it. CityPulse questions are always of the form "measure by place by time". The fact table fact_air_quality holds the measurements, and the dimensions dim_location and dim_source hold the places and sources. The alternatives are weaker. One wide flat table repeats the location text on every row and cannot enforce clean references. A fully normalised model suits apps that update data often, but CityPulse reads far more than it writes, so it needs more joins than it needs. A document store has weak joins and weak constraints for the aggregate questions asked in Day 14.

How it works. You write the grain first. The grain is a sentence that says what one row means. The course's grain is "one row per location per source per UTC hour". UTC is Coordinated Universal Time, a fixed clock standard that avoids daylight-saving confusion. The grain decides the natural key, and the natural key decides what counts as a duplicate.

The slide code. Here is the schema from the slides, with comments added by this book.

CREATE TABLE IF NOT EXISTS dim_location (
  location_id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE, lat REAL, lon REAL);
CREATE TABLE IF NOT EXISTS dim_source (
  source_id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE);
CREATE TABLE IF NOT EXISTS fact_air_quality (
  fact_id     INTEGER PRIMARY KEY,
  location_id INTEGER NOT NULL REFERENCES dim_location(location_id),
  source_id   INTEGER NOT NULL REFERENCES dim_source(source_id),
  ts_utc      TEXT NOT NULL,  -- ISO-8601 'YYYY-MM-DDTHH:MM:SSZ'
  pm2_5 REAL CHECK (pm2_5 >= 0), pm10 REAL CHECK (pm10 >= 0),
  temperature_2m REAL, relative_humidity_2m REAL,
  UNIQUE (location_id, source_id, ts_utc));
CREATE INDEX IF NOT EXISTS ix_fact_loc_ts ON fact_air_quality (location_id, ts_utc);

Line by line:

  • CREATE TABLE IF NOT EXISTS dim_location ( creates a table named dim_location. IF NOT EXISTS means "do nothing if the table is already there". That makes the script safe to run twice.
  • location_id INTEGER PRIMARY KEY is the table's key. In SQLite, an INTEGER PRIMARY KEY column gets a number automatically when you do not supply one.
  • name TEXT NOT NULL UNIQUE stores the station name as text. NOT NULL rejects an empty name. UNIQUE rejects a second station with the same name.
  • lat REAL, lon REAL store latitude and longitude as decimal numbers. REAL means a floating-point number.
  • dim_source follows the same pattern for the data source, such as openaq.
  • fact_air_quality is the fact table. Its fact_id is a surrogate key.
  • REFERENCES dim_location(location_id) is the foreign key. A location id that is not in dim_location is refused.
  • ts_utc TEXT NOT NULL stores the time as text such as 2026-12-05T03:00:00Z. The Z means UTC. Text in this format sorts in time order, which is why the course uses it.
  • The comment -- ISO-8601 ... is ignored by the database. Anything after -- on a line is a comment.
  • pm2_5 REAL CHECK (pm2_5 >= 0) rejects a negative particle reading. >= means "greater than or equal to".
  • UNIQUE (location_id, source_id, ts_utc) stops the same grain appearing twice.
  • CREATE INDEX IF NOT EXISTS ix_fact_loc_ts ON fact_air_quality (location_id, ts_utc); builds a lookup structure, described in Day 9's indexing topic below.
Trap: Putting the location name in the fact table

Writing location_name on every fact row duplicates text and breaks renames. Store location_id and join to dim_location when you need the name.

Trap: A table with no UNIQUE natural key

Without UNIQUE on the grain columns, a rerun of the loader inserts every row again and the data doubles. The database has no way to know the rows are the same.

Trap: CHECK passes NULL

CHECK (pm2_5 >= 0) accepts a missing value. The check only fails when the expression is false, and a NULL comparison is unknown, not false. Add NOT NULL only if your documented rule forbids missing values.

SQLite and PostgreSQL

What it is. SQLite is a complete SQL database stored in one file, and it is built into Python's sqlite3 module. PostgreSQL is a server database for many users at once. Both speak standard SQL, including constraints and ON CONFLICT upserts.

Why CityPulse uses SQLite first. SQLite needs no server and no password on the lab machines, so every student can build citypulse.db in seconds. Python's sqlite3 module plus ? placeholders is enough for the loader. The same schema and upsert syntax run on PostgreSQL when the platform needs concurrent users. MySQL was rejected because its upsert syntax (ON DUPLICATE KEY UPDATE) differs. DuckDB is strong for analytics on Parquet but weaker for a constrained, often-updated store.

How it works. A database file is opened by a connection. In SQLite, foreign-key checks are off by default for every connection. So each connection must turn them on with PRAGMA foreign_keys = ON. A PRAGMA is a SQLite command that changes a setting. The slide code makes this visible.

The slide code. This is the connection and load setup from the slides.

import os, sqlite3
from pathlib import Path
con = sqlite3.connect(os.environ.get("SQLITE_PATH", "citypulse.db"))
con.execute("PRAGMA foreign_keys = ON")
for _ in range(2):  # idempotent DDL: second run changes nothing
    con.executescript(Path("sql/schema.sql").read_text())
with con:
    con.execute("INSERT OR IGNORE INTO dim_location (location_id, name) VALUES (1, 'Hebbal')")
    con.execute("INSERT OR IGNORE INTO dim_source (source_id, name) VALUES (1, 'openaq')")
try:
    with con:
        con.execute("INSERT INTO fact_air_quality (location_id, source_id, ts_utc, pm2_5) VALUES (?, ?, ?, ?)", (1, 1, "2026-12-05T03:00:00Z", -5))
except sqlite3.IntegrityError as e:
    print("rejected:", e)  # CHECK constraint failed

Line by line:

  • import os, sqlite3 loads two standard modules. os reads environment variables, and sqlite3 talks to SQLite.
  • from pathlib import Path loads a helper for reading files.
  • con = sqlite3.connect(...) opens the database. os.environ.get("SQLITE_PATH", "citypulse.db") reads the environment variable SQLITE_PATH and falls back to citypulse.db if it is not set. Nothing is printed.
  • con.execute("PRAGMA foreign_keys = ON") turns on foreign-key checks for this connection only.
  • for _ in range(2): repeats the next line twice. The underscore means "I do not need the loop value".
  • con.executescript(...) runs every statement in the file. Because of IF NOT EXISTS, the second run changes nothing and prints nothing.
  • with con: opens a transaction. If the block ends normally, the changes are committed. If an error escapes, they are rolled back.
  • INSERT OR IGNORE adds the station and the source. If the row already exists, the insert is skipped without an error.
  • The second try block tries to insert a reading with pm2_5 set to -5. The ? marks are placeholders. Python fills them from the tuple in order, so the values never become part of the SQL text.
  • except sqlite3.IntegrityError as e: catches the error raised when a constraint fails. print shows the message.

Expected output, when the CHECK constraint is working:

rejected: CHECK constraint failed: ...

The exact wording of the message depends on the SQLite version. The important part is that the program prints rejected: and the row is not stored.

Trap: Foreign keys are off by default

In SQLite, a foreign key you wrote is only a promise until PRAGMA foreign_keys = ON runs on that connection. Run it every time you open a connection, not once in a script.

Trap: Building SQL with f-strings

Writing f"... VALUES ('{name}')" invites quoting errors and SQL injection, where text in the data changes the statement. Use ? placeholders and a tuple of values.

Trap: Committing the database file

Do not commit citypulse.db to Git. It leaks data and causes merge conflicts. Add the file name to .gitignore, a list of files Git should ignore.

Idempotent upserts

What it is. An upsert is an insert that becomes an update when the key already exists. An operation is idempotent if running it again leaves the same result as running it once. Together with a UNIQUE natural key and one transaction, an upsert makes the loader idempotent.

Why CityPulse uses it. Cron (a scheduler that runs programs at set times) and retries will rerun loads after partial failures. A corrected reading for an hour, from a fresh fetch, replaces the old value instead of creating a duplicate. The alternatives each fail one case. DELETE then INSERT rewrites everything and leaves an empty table if it fails halfway without a transaction. INSERT OR IGNORE never applies corrected values. A plain INSERT fails on the second run or doubles data.

How it works. The database looks at the proposed row. If it clashes with the UNIQUE key, the DO UPDATE branch runs. If not, a new row is added. The word excluded refers to the proposed row.

A stand-in in plain Python. The idea is easier to see in ordinary Python, with a dictionary playing the table. This is an illustration, not the course code.

The slide code. This is the core of load.py from the slides.

import os, sqlite3
import pandas as pd
SQL = """INSERT INTO fact_air_quality (location_id, source_id, ts_utc, pm2_5, pm10)
VALUES (?, ?, ?, ?, ?) ON CONFLICT (location_id, source_id, ts_utc)
DO UPDATE SET pm2_5 = excluded.pm2_5, pm10 = excluded.pm10"""
df = pd.read_parquet("data/clean/readings.parquet")
nn = lambda x: None if pd.isna(x) else float(x)  # NaN -> SQL NULL
con = sqlite3.connect(os.environ.get("SQLITE_PATH", "citypulse.db"))
con.execute("PRAGMA foreign_keys = ON")
loc, src = (dict(con.execute(f"SELECT name, {t}_id FROM dim_{t}")) for t in ("location", "source"))
rows = [(loc[r.location], src[r.source], r.ts_utc.strftime("%Y-%m-%dT%H:%M:%SZ"), nn(r.pm2_5), nn(r.pm10)) for r in df.itertuples()]
with con:  # one transaction: commit all or roll back all
    con.executemany(SQL, rows)
print(con.execute("SELECT COUNT(*) FROM fact_air_quality").fetchone()[0])

Line by line:

  • SQL = """...""" stores the upsert statement in a variable. Triple quotes let the text run over several lines.
  • ON CONFLICT (location_id, source_id, ts_utc) names the conflict target. It must match a UNIQUE constraint exactly, with the same columns in any order.
  • DO UPDATE SET pm2_5 = excluded.pm2_5, pm10 = excluded.pm10 says what to change when the row exists. excluded.pm2_5 is the new value from the proposed row.
  • df = pd.read_parquet(...) reads the cleaned file into a pandas table called df.
  • nn = lambda x: ... defines a short function. A lambda is a one-line function. It returns None when the value is missing (pd.isna is true for NaN) and otherwise converts the value to a plain number.
  • loc, src = (dict(...) for t in (...)) builds two dictionaries that map a station name to its location_id, and a source name to its source_id.
  • rows = [...] builds a list of tuples, one per reading, with names turned into ids and timestamps turned into ISO text.
  • r.ts_utc.strftime(...) formats the timestamp, for example 2026-12-05T03:00:00Z. %Y is the four-digit year, and each % code is one part of the date or time.
  • with con: opens one transaction for the whole load.
  • con.executemany(SQL, rows) runs the statement once per tuple in rows.
  • The last line counts the fact rows and prints the number. The expected output is a single number, which should be the same on the second run.
Trap: NaN is not NULL

Passing pandas NaN straight into a database can store a floating-point NaN rather than SQL NULL (Postgres does), which then breaks AVG. SQLite happens to turn NaN into NULL, but do not rely on that. Convert NaN to None before executemany, as nn does.

Trap: Committing per row

Committing after each row is slow and leaves a partial load if the program stops. Wrap the whole batch in one with con: block.

Trap: ON CONFLICT target mismatch

If the conflict target does not match a UNIQUE constraint, SQLite raises an error about the conflict clause. Use the same columns as the grain key.

The worked example

The workbook builds one small CityPulse database in eight steps. It uses SQLite, and the data is a station table and a reading table. The schema in the workbook differs from the star schema above. It is simpler, and it shows the same ideas.

Step 1: model the two entities

The goal is to separate where a sensor is (station) from what it measured (reading). The reading refers to the station by a foreign key, so each fact is stored once.

CREATE TABLE station (
  station_id TEXT PRIMARY KEY, name TEXT NOT NULL, lat REAL, lon REAL );
CREATE TABLE reading (
  station_id TEXT REFERENCES station(station_id),
  ts TEXT, pollutant TEXT, value REAL,
  PRIMARY KEY (station_id, ts, pollutant) );

The station table has a text key, station_id, such as CP-001. The reading table has a foreign key to it. Its primary key is three columns together, so one station can report several pollutants at the same time, but not the same pollutant twice. Notice ts TEXT. SQLite has no dedicated timestamp type, so the workbook stores time as text.

Expected output from sqlite3 :memory: ".read schema.sql" ".schema reading" is the CREATE TABLE reading statement printed back. That confirms the file parses.

Step 2: create the tables

The goal is a fresh database with both tables. The workbook's script is:

rm -f citypulse.db
sqlite3 citypulse.db ".read schema.sql"
sqlite3 citypulse.db ".tables"

Line by line: rm -f citypulse.db deletes the old file if there is one, and -f stops the command complaining when the file is missing. The second line opens a new database and runs the schema file. The third line lists the tables. Expected output is reading station. The table names are in alphabetical order, so the order is not a clue about which table was created first.

Step 3: stage the cleaned files

The goal is to check the file before loading it:

head -1 readings.csv
echo "rows: $(($(wc -l < readings.csv) - 1))"

head -1 prints the first line, which is the header. wc -l counts lines. $(( ... - 1)) subtracts the header line. The expected output is station_id,ts,pollutant,value and rows: 1392. The header must match the columns of the reading table exactly.

Step 4: bulk-load

The goal is to load both files in one pass. The workbook's SQL is:

.mode csv
.import --skip 1 stations.csv station
.import --skip 1 readings.csv reading
.mode list
SELECT 'stations: ' || count(*) FROM station;
SELECT 'readings: ' || count(*) FROM reading;

.mode csv tells the SQLite shell to read comma-separated text. .import --skip 1 stations.csv station loads the file into the station table and skips the first line, which is the header. .mode list switches output back to plain lines. The two SELECT statements count the rows, and || joins the label and the number. Expected output is stations: 4 and readings: 1392. The stations load first because the readings refer to them.

Step 5: block duplicate samples

The goal is to see the composite key refuse a second sample for the same station, time and pollutant. The workbook's statement is:

INSERT INTO reading VALUES ('CP-001', '2026-03-01T00:00:00Z', 'pm25', 51.3);

This row already exists, so the database refuses it. The output is an error that names the three key columns, and the row count stays at 1392.

Step 6: reject readings for unknown stations

The goal is to show that the foreign key blocks an orphan reading. The script turns the check on first:

PRAGMA foreign_keys = ON;
INSERT INTO reading VALUES ('CP-999', '2026-03-01T00:00:00Z', 'pm25', 44.0);

Expected output is Runtime error near line 2: FOREIGN KEY constraint failed (19). The (19) is SQLite's general constraint error code, and the message names the rule that failed.

Step 7: query across the join

The goal is a ranked picture of pm2.5 per station:

SELECT s.name, round(avg(r.value),1) AS avg_pm25, count(*) AS n
FROM reading r JOIN station s ON s.station_id = r.station_id
WHERE r.pollutant = 'pm25'
GROUP BY s.name ORDER BY avg_pm25 DESC;

Line by line: FROM reading r names the table and gives it the short name r. JOIN station s ON ... attaches each reading to its station. avg(r.value) averages the values in each group. round(..., 1) rounds to one decimal place. count(*) AS n counts rows, and AS names a column in the output. GROUP BY s.name makes one group per station. ORDER BY avg_pm25 DESC sorts from highest to lowest.

Run it with sqlite3 -header -column citypulse.db ".read hotspots.sql". The -header flag prints column names, and -column lines them up. Expected output:

name        avg_pm25  n
----------  --------  ---
Jayanagar   51.4      116
Hebbal      51.3      116
Whitefield  50.5      116
Indiranagar 49.7      116

The count is 116 for each station because each station has 116 pm2.5 readings. Four stations times three pollutants gives 1,392 rows in total.

Step 8: rebuild and verify end to end

The workbook's script runs every step from an empty file:

rm -f citypulse.db
sqlite3 citypulse.db ".read schema.sql" ".read load.sql" ".read verify.sql"

The first command clears the old database. The second runs the schema, the load, and a verification file. The verification file counts orphan readings and duplicate keys. Expected output is stations: 4, readings: 1392, orphans: 0, dup_keys: 0. Zero in both checks means the rules held.

The hands-on lab, step by step

The lab uses Postgres, a server database, with the psql command-line client. Your lab sheet gives the exact image tag, password, database name and file paths. The commands below show the general form. If a value in your lab sheet differs, use the lab sheet's value.

Step 1: launch Postgres in Docker

Start a Postgres container in the background:

docker run --name citypulse-pg -e POSTGRES_PASSWORD=your-lab-password -p 5432:5432 -d postgres:16

Line by line: docker run creates and starts a container. --name citypulse-pg gives it a name you can use later. -e POSTGRES_PASSWORD=... sets an environment variable inside the container, which Postgres reads for the password. -p 5432:5432 connects port 5432 on your computer to port 5432 in the container, which is the port Postgres listens on. -d runs it in the background. postgres:16 is the image, which is a packaged copy of Postgres version 16. You should see a long container id printed. Check with docker ps. The line for citypulse-pg should show Up in the status column. That means the server is running.

Step 2: design the schema

Write the grain sentence on paper before any SQL. For the lab, the grain is "one row per station, timestamp and pollutant". Then list the tables and their keys:

  • station: one row per site, keyed by station_id.
  • reading: one row per measurement, keyed by (station_id, ts, pollutant), with station_id pointing to station.

You know the design is right when every table has a key and every relationship has one arrow from the child to the parent. If you cannot say what one row means, the design is not ready.

Step 3: add the right types and constraints

Write sql/schema.sql. Use the types from the lab sheet. In Postgres, TIMESTAMPTZ stores an exact point in time (zone-aware, held as UTC), TEXT stores text, and REAL stores a decimal number. Then add the rules:

CREATE TABLE IF NOT EXISTS station (
  station_id TEXT PRIMARY KEY, name TEXT NOT NULL, lat REAL, lon REAL);
CREATE TABLE IF NOT EXISTS reading (
  station_id TEXT NOT NULL REFERENCES station(station_id),
  ts TIMESTAMPTZ NOT NULL, pollutant TEXT NOT NULL, value REAL,
  PRIMARY KEY (station_id, ts, pollutant));

Run it once with psql -h localhost -U postgres -d citypulse -f sql/schema.sql. The flags are -h (the host), -U (the user), -d (the database name) and -f (a file to run). Expected output is CREATE TABLE twice. Run it again. IF NOT EXISTS means the output says NOTICE lines but no new tables appear. You know it worked when \dt in psql lists both tables.

Trap: Two type names in the sources

The Day 9 sources show TIMESTAMPTZ for the Postgres schema and TEXT for the SQLite schema. Use the type your lab sheet names. Do not mix the two in one database.

Step 4: prepare the staging data

Check the CSV before loading. Use the same commands as the worked example:

head -1 readings.csv
echo "rows: $(($(wc -l < readings.csv) - 1))"

You should see the header station_id,ts,pollutant,value and the count rows: 1392. If the header is different, fix the file, not the table. A shifted column causes a type error part-way through a load, which is much harder to read.

Trap: Counting rows with wc

wc -l counts newline characters. If the last line of the file has no newline at the end, the count is one too low. Open the file and check the last line if the count looks wrong.

Step 5: bulk-load with COPY

Load the stations first, then the readings:

psql -h localhost -U postgres -d citypulse -c "\copy station from 'stations.csv' csv header"
psql -h localhost -U postgres -d citypulse -c "\copy reading from 'readings.csv' csv header"

The \copy command is read by psql on your computer. The file is read from your computer, not from inside the container. csv says the file is comma-separated, and header says the first line holds column names and must be skipped. You should see COPY 4 and then COPY 1392. That COPY line is the status message the database returns. The number is the number of rows stored.

If psql is not installed on your machine, your lab sheet gives the route to use. Do not copy the file into the container by guessing the path.

Step 6: verify integrity

Run the two checks. The orphan check looks for readings whose station is missing:

SELECT count(*) FROM reading r LEFT JOIN station s ON s.station_id = r.station_id WHERE s.station_id IS NULL;

A LEFT JOIN keeps every reading. Where no station matches, the station columns are NULL, so the WHERE ... IS NULL filter keeps only the orphans. Expected result: 0.

The duplicate check looks for keys that appear more than once:

SELECT count(*) FROM (SELECT station_id, ts, pollutant FROM reading GROUP BY station_id, ts, pollutant HAVING count(*) > 1) d;

Expected result: 0. Because the primary key forbids duplicates, this check is a safety net. It should never find anything.

To confirm the foreign key is active, insert a reading for CP-999. The lab sheet's example row is enough. You should see ERROR: insert or update on table "reading" violates foreign key constraint. That error is the proof you want.

Step 7: run a join query

Run the hotspot query from the worked example, adjusted for Postgres:

SELECT s.name, round(avg(r.value)::numeric, 1) AS avg_pm25, count(*) AS n
FROM reading r JOIN station s ON s.station_id = r.station_id
WHERE r.pollutant = 'pm25'
GROUP BY s.name ORDER BY avg_pm25 DESC;

You should see four rows, one per station, sorted from highest to lowest, with n equal to 116 for each. The ::numeric cast is needed in Postgres. Postgres's round with a number of decimal places expects a numeric value, and avg of a REAL column is not one. SQLite does not need the cast.

Trap: Postgres round on REAL

In Postgres, round(avg(r.value), 1) on a REAL column can fail with a message that round does not exist for those argument types. Cast the value with ::numeric, as in step 7.

Primary keys

What it is. A primary key is the column, or the combination of columns, that identifies one row in a table. Two rows cannot have the same primary key, and the key cannot be empty. A key can be built from facts that already exist in the real world, such as a station id plus a timestamp plus a pollutant name. That kind of key is called a natural key. A key can also be a number the database creates for you, which is called a surrogate key.

Here is a small table of library members, with a single-column key:

CREATE TABLE member (
  member_id INTEGER PRIMARY KEY,
  name TEXT NOT NULL
);
INSERT INTO member VALUES (1, 'Asha');
INSERT INTO member VALUES (1, 'Ravi');

The first insert works. The second fails with UNIQUE constraint failed: member.member_id, because the number 1 is already taken, so Ravi is not stored. In SQLite, an INTEGER PRIMARY KEY column is filled with the next free number when you leave it out of an insert.

When the rule is about a combination, the key must be the combination. A loan is one member borrowing one book on one day. Any single one of those columns repeats too often to identify a loan, so the primary key is the three columns together. The database then refuses a second copy of the same loan, but still accepts the same member borrowing a different book on the same day.

How it shows up in a case study. A sensor loader writes readings into a table. After a network problem, the sensor resends a batch, and the row count doubles. The team's first idea is to make the timestamp the key, because every reading has a time. That fails at once: all four stations report at 09:00, so the second station's reading clashes with the first and is refused. The right key is the combination that defines one measurement: the station, the time and the pollutant. Now a resent reading clashes with the stored one and is refused, while readings from other stations and other pollutants at the same time are kept.

Trap: Choosing a column that looks unique

A timestamp can look unique in a small sample, and so can a station name. The key must match the real rule, which here is one measurement per station, time and pollutant. A key on one column refuses valid rows as well as duplicates.

Foreign keys

What it is. A foreign key is a column whose value must already exist in a key of another table. The table that holds the foreign key is the child, and the table it points to is the parent. If a child row names a parent that does not exist, the database refuses the child row. A child row with no parent is called an orphan.

CREATE TABLE member (member_id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE loan (
  loan_id INTEGER PRIMARY KEY,
  member_id INTEGER NOT NULL REFERENCES member(member_id)
);
INSERT INTO loan (member_id) VALUES (99);

With foreign-key checks active, the last insert fails with FOREIGN KEY constraint failed, because member 99 does not exist. In SQLite, the checks run only after PRAGMA foreign_keys = ON has been run on that connection, and the setting is off by default. In Postgres, the check applies as soon as the constraint exists, unless the constraint was declared DEFERRABLE and the check is postponed to the end of the transaction.

To find orphans after the fact, use a LEFT JOIN. A LEFT JOIN keeps every child row. Where no parent matches, the parent's columns are NULL, so a filter for IS NULL on the parent's key keeps only the orphans. An INNER JOIN would drop the orphans and hide the problem.

How it shows up in a case study. A dashboard lists readings for each station, but one station's readings never appear on the map. The readings exist in the database and point to a station id that is missing from the station table. The loader ran for weeks on a connection that never switched foreign-key checks on. The fix has two parts. The loader must run the pragma on every connection, and the team must find and repair the existing orphans with a LEFT JOIN and an IS NULL filter before the foreign key can be trusted.

Trap: Assuming a foreign key is always enforced in SQLite

A foreign key written in the schema is only a promise until the connection enables checks. Two connections to the same file can behave differently, because the setting belongs to the connection, not to the file.

Postgres column types

What it is. A column type sets which values a column can hold and how the database stores, compares and adds them. The choice matters even when the query is right. Four types matter for this lesson. TEXT holds characters. REAL holds a four-byte floating-point number. NUMERIC holds exact decimal digits. TIMESTAMPTZ holds a point in time, and Postgres converts the input to UTC for storage. A plain TIMESTAMP holds a wall-clock date and time with no zone attached.

The difference between a floating-point type and an exact type shows up at once:

SELECT 0.1::double precision + 0.2::double precision = 0.3::double precision;
-- false
SELECT 0.1::numeric + 0.2::numeric = 0.3::numeric;
-- true

Binary floating-point types cannot store 0.1 exactly, so the sum is slightly off and the equality fails. NUMERIC stores the decimal digits themselves, so the sum is exact. This is why money uses NUMERIC, and why sensor values are usually stored as REAL when small errors do not matter.

How it shows up in a case study. A team loads readings from two cities. The sensors send local times without a zone, and the team stores them in a TIMESTAMP column. A chart then puts a morning reading from one city after an evening reading from another, because the stored values carry no zone. The fix is to store the instant as TIMESTAMPTZ, with each source's time converted to UTC on the way in. The database can then compare the two cities correctly, and the displayed time can still be shown in the local zone.

Trap: Choosing TIMESTAMP because it looks shorter

TIMESTAMP looks simpler, but it cannot tell two cities apart. TIMESTAMPTZ is the type that keeps an instant that can be compared across sources.

Bulk loading

What it is. Bulk loading sends a whole file of rows into a table in one operation, rather than running one INSERT statement for each row. Each row still goes through the same checks, but the database avoids a separate statement, a separate round trip and a separate parse for every row. In Postgres, the COPY command reads a file on the server. The \copy command in psql reads a file on your own computer and streams it to the server.

\copy station from 'stations.csv' csv header

The csv option says the file is comma-separated. The header option says the first line holds column names and must be skipped. A successful run prints COPY 4 when four rows were stored. The number is the count of rows stored, not the count of lines in the file.

The same idea appears in Python. A loop that calls execute once per row sends one statement for each row. A call to executemany with a list of tuples runs one prepared statement for all rows in one go, which is much faster for a large batch.

How it shows up in a case study. A team loads 1,392 readings with a Python loop, and the load takes several minutes. They switch to a bulk load, and it finishes in a fraction of a second. The next run fails with a foreign-key error on the readings, because the readings file was loaded before the stations file. The decision is to load the parent table first, so every reading's station exists when its row is checked. The speed does not change the rules, and the order does.

Trap: Skipping constraints to load faster

A bulk load is fast because of how rows are sent, not because it turns checks off. Keys, NOT NULL, CHECK and foreign keys still apply to every row. A load that is fast but wrong is a worse result than a slower correct one.

Normalisation

What it is. Normalisation is the process of arranging tables so that each fact is stored in one place. A table is in first normal form when each cell holds a single value and there are no repeating groups of columns. It is in third normal form when every non-key column depends on the key itself, and not on some other non-key column. Here is a table that breaks the third rule:

reading_id  station_id  station_name  value
1           CP-001      Hebbal        51.3
2           CP-001      Hebbal        52.0

The station name depends on the station, not on the reading. If the station is renamed, both rows must change. If a later update changes only one row, the table now gives two names for one station. Moving the name into a station table, and keeping only station_id in the reading table, removes the repeated fact.

Normalisation is not a rule that more tables are always better. Each extra table means more joins when you read the data. A transactional app with many small updates usually benefits from full normalisation. An analytics store that mostly reads large amounts of data can accept some repetition for speed and simplicity. CityPulse uses a star schema for that reason.

How it shows up in a case study. A reporting team stores the station name and the city on every reading. A station is renamed, and an update changes most of its rows but misses a batch that came from a second loader. Now one station appears under two names in the report. The team's question is which design stops this. The answer is a station table with a station key, and a reading table that holds only the station id. A rename then touches one row, and the reports join to the new name.

Trap: Thinking normalisation means more tables is always better

Normalisation removes repeated facts. It does not reward the number of tables. A star schema with repeated text can be the right design when the workload is read-heavy analytics.

Upserts and idempotency

What it is. An upsert is a single statement that inserts a row when its key is new and updates the existing row when the key is already present. In SQLite and Postgres, the syntax is INSERT ... ON CONFLICT (key columns) DO UPDATE SET .... An operation is idempotent when running it again leaves the same result as running it once. A load becomes idempotent when its rows are keyed by a UNIQUE constraint and the load uses an upsert.

INSERT INTO member_fee (member_id, fee) VALUES (1, 500)
ON CONFLICT (member_id) DO UPDATE SET fee = excluded.fee;

The word excluded refers to the row that you tried to insert. If you run this statement twice, the table still has one row for member 1, and its fee is the value from the latest run. The first run inserts the row. The second run hits the conflict and updates the fee to the same value. The row count does not change.

The conflict target, here (member_id), must match a UNIQUE or PRIMARY KEY constraint with exactly those columns. If it does not, the database raises an error rather than guessing.

How it shows up in a case study. A nightly job loads the same file every night. One night, the source corrects the fee for a member, and the job must store the corrected value. A plain INSERT fails on the second run because the key already exists. An INSERT OR IGNORE keeps the old fee, so the correction is lost. A DELETE followed by an INSERT works if both steps run inside one transaction, but without one, a crash in the middle leaves an empty table. The upsert with a transaction is the only option that is repeatable and applies the correction.

Trap: INSERT OR IGNORE for a value that can change

INSERT OR IGNORE is repeatable, but it keeps the first value it saw. A corrected reading for an existing key is silently discarded, and no error tells you so.

Indexing strategy

What it is. An index is a separate structure that lets the database find rows without reading the whole table. It works like the index at the back of a book, which lists each term with its pages. A UNIQUE constraint and a PRIMARY KEY both create an index automatically. An index on several columns is sorted by the first column, then the second, and so on.

CREATE INDEX ix_loan_member_date ON loan (member_id, borrowed_on);
SELECT * FROM loan
WHERE member_id = 7 AND borrowed_on BETWEEN '2026-01-01' AND '2026-01-31';

The index first narrows the search to member 7, because that is the first column. Within those rows, it finds the January dates, because the second column is sorted inside each member. A query that filters only on borrowed_on cannot use this index well, because the index is not sorted by date first. The column order is therefore part of the design. Put the column that you compare with equals first, and the column you compare with a range second.

Indexes are not free. Each index must be updated whenever a row is inserted, changed or deleted, and each one takes disk space.

How it shows up in a case study. An analyst asks for one station's readings across one week, and the query takes several seconds. The table has a UNIQUE key on location, source and time, but the time column is last, so the source column sits between them and the key helps little for a query that filters by location and then by time. The team adds an index on the location and then the time. The query now reads only the rows it needs. The team also decides not to index the value column, because nobody filters by it, and the inserts would slow down for no gain.

Trap: Indexing every column

An index on every column makes each insert slower and uses space, and most of those indexes are never used. Add an index for a query you actually run, and choose the column order to match that query.

Constraints

What it is. A constraint is a rule the database checks on every insert and update, so bad data is refused rather than stored. The common types are NOT NULL, which refuses a missing value, UNIQUE, which refuses a repeated value, CHECK, which refuses a row when an expression is false, and FOREIGN KEY, which refuses a value with no parent. A PRIMARY KEY is a combination of NOT NULL and UNIQUE on one set of columns.

CREATE TABLE hire (days INTEGER NOT NULL CHECK (days > 0));
INSERT INTO hire VALUES (5);
INSERT INTO hire VALUES (0);
INSERT INTO hire VALUES (NULL);

The first insert is stored. The second fails with CHECK constraint failed, because zero is not greater than zero. The third fails with NOT NULL constraint failed: hire.days, because the value is missing. A constraint error is the database saying that the data breaks a rule, and nothing from that statement is stored.

A CHECK fails only when its expression is false. When the value is NULL, the comparison is unknown, so the CHECK passes. The NOT NULL constraint is the rule that forbids the missing value.

How it shows up in a case study. A team validates readings in its Python code, and a bug in the code lets a negative particle value through. The bad value reaches the table, and a chart shows a dip below zero. The team's question is where the rule should live. The answer is in the database, as a CHECK constraint, because every program that writes to the table then obeys it. The team also notices that a few rows have a missing value, and that the CHECK does not catch them. They add NOT NULL to the column, because their documented rule says a reading must be present.

Trap: Believing a CHECK refuses NULL

CHECK (pm2_5 >= 0) accepts a missing value, because the comparison is unknown and only a false result fails. If the value must be present, add NOT NULL as well.

Transactions

What it is. A transaction is a group of changes that the database treats as one unit. The changes either commit together, which saves all of them, or roll back together, which undoes all of them. A change that is not yet committed is visible only to the connection that made it. If a program stops before the commit, the database undoes the uncommitted changes.

import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE tally (n INTEGER)")
try:
    with con:
        con.execute("INSERT INTO tally VALUES (1)")
        raise RuntimeError("stop")
except RuntimeError:
    pass
print(con.execute("SELECT COUNT(*) FROM tally").fetchone()[0])

The output is 0. The INSERT ran inside the with con: block, then the error left the block, so Python's sqlite3 module rolled the change back. Had the block ended normally, the insert would have been committed. The connection is still open after the rollback, so it can be used again.

How it shows up in a case study. A loader writes 5,000 rows, one commit for each row. The process stops at row 3,000. When the team looks at the table, it holds exactly 3,000 rows, which is a partial load that looks complete. A re-run then adds the rest, but only because the key stops the duplicates. The fix is to wrap the whole batch in one transaction. A stop in the middle then leaves the table as it was before the load, so the table is either complete or untouched.

Trap: Committing row by row

A commit after every row is slow, and it leaves a partial load if the program stops. Wrap the whole batch in one transaction, so the load is all or nothing.

Partitioning

What it is. Partitioning splits one large logical table into smaller physical parts, usually by a range of values such as a month or a year. Each part is stored separately, and the rows are routed to the right part when you insert them. A query that filters on the partition key can skip the parts that cannot match. Postgres supports this as declarative partitioning. SQLite has no built-in partitioning.

CREATE TABLE reading_log (
  ts TIMESTAMPTZ NOT NULL,
  value REAL
) PARTITION BY RANGE (ts);

CREATE TABLE reading_2026 PARTITION OF reading_log
  FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

Rows with a timestamp in 2026 go to reading_2026. A query with a filter such as WHERE ts >= '2026-03-01' AND ts < '2026-04-01' can skip the other parts when the planner knows their ranges do not match. Partitioning changes how the data is stored and read. It does not change the rules. Keys, constraints and foreign keys still apply to every row.

How it shows up in a case study. A team keeps ten years of hourly readings in one table, and most reports cover one year. Those reports have become slow, and the table is still growing. The team considers removing the primary key to make inserts faster. That would allow duplicate readings, which is the wrong fix. The better change is to partition the table by year, so a one-year report reads only one part. The key stays, so duplicates are still refused.

Trap: Using partitioning to replace keys

Partitioning is for speed and manageability. It does not make wrong data correct, and it does not stop duplicates unless the key does that job. Keep the keys and constraints in place when you partition.

What each function needs

Each Python idea below is taught with a small example that is not about the lab's data. The examples use a fruit stall, so you can learn the tool without being given the lab's solution. Opening an in-memory connection and creating a table. sqlite3.connect(":memory:") opens a database that lives only in memory. It disappears when the connection closes, which suits tests because nothing is written to disk. A table is created with CREATE TABLE, and a UNIQUE constraint is written as a clause in the table definition.

import sqlite3

stall = sqlite3.connect(":memory:")
stall.execute("CREATE TABLE fruit (name TEXT NOT NULL, kg REAL, UNIQUE (name))")

Nothing is printed. If you ran the CREATE TABLE statement a second time, it would fail with an error, because the table already exists. Adding IF NOT EXISTS makes the statement safe to repeat.

Inserting one row with placeholders. A ? in an SQL statement is a placeholder. Python fills each ? from a tuple, in order, so values are never pasted into the SQL text. INSERT OR IGNORE skips a row that breaks a UNIQUE constraint, and keeps the row that was stored first. It also skips a row that breaks a NOT NULL or CHECK rule, with no error, so use it only when skipping every bad row is what you want.

stall.execute("INSERT OR IGNORE INTO fruit (name, kg) VALUES (?, ?)", ("mango", 1.5))
stall.execute("INSERT OR IGNORE INTO fruit (name, kg) VALUES (?, ?)", ("mango", 9.0))

The second statement is skipped without an error, because mango is already there. The table still holds 1.5 for mango. executemany runs the same statement once for each tuple in a list, which is the tool to use when you have many rows.

Counting rows and reading one value. COUNT(*) counts the rows that a query returns. fetchone() returns the first row as a tuple, and the [0] picks the first item of that tuple, which is the number itself.

count = stall.execute("SELECT COUNT(*) FROM fruit").fetchone()[0]
print(count)  # 1

The result is an int. The fetchone() call returns (1,), a one-item tuple, and the index turns it into the plain number.

Distinct values in sorted order. DISTINCT removes repeated values from a result. ORDER BY sorts the result. fetchall() returns every row as a list of tuples, so a list comprehension turns the one-item tuples into plain values.

names = [row[0] for row in stall.execute("SELECT DISTINCT name FROM fruit ORDER BY name")]
print(names)  # ['mango']

Grouping, summing and rounding. GROUP BY makes one group for each distinct value. SUM adds up a column inside each group. ROUND(x, 2) rounds a number to two decimal places. Floating-point arithmetic can leave small errors, so a sum such as 0.1 plus 0.2 may come out as 0.30000000000000004, and rounding removes that noise.

stall.execute("CREATE TABLE weigh (name TEXT, kg REAL)")
stall.execute("INSERT INTO weigh VALUES ('fig', 0.1)")
stall.execute("INSERT INTO weigh VALUES ('fig', 0.2)")
rows = stall.execute(
    "SELECT name, ROUND(SUM(kg), 2) FROM weigh GROUP BY name ORDER BY name"
).fetchall()
print(rows)  # [('fig', 0.3)]

Python's own round works the same way for a single number: round(1.236, 2) gives 1.24. Round once, at the end of the calculation, so that the error from earlier steps does not build up.

Checking the type of a result. isinstance(x, int) is true for an int, and it is also true for a bool, because bool is a subclass of int. type(x) is int is true only for a true int. This matters when a function must return an integer and a True or False value would be wrong.

print(isinstance(True, int))   # True
print(type(True) is int)       # False
print(type(3) is int)          # True

Sorting with a key. sorted returns a new list and leaves the original unchanged. Its key argument decides what is compared. Python's sort is stable, so items that compare equal keep their original order.

words = ["pear", "fig", "kiwi"]
print(sorted(words, key=len))  # ['fig', 'pear', 'kiwi']
print(words)                   # ['pear', 'fig', 'kiwi'], unchanged

Never changing an input. A function that receives a list should not alter it, because the caller may use the list again. Use sorted(items) to get a new sorted list, rather than items.sort(), which changes the list in place. The same care applies to any list you were given as a parameter.

Worked twin problem

The twin problem below is about library loans, not about readings. It needs the same skills: a table with a composite UNIQUE rule, a load that refuses repeated keys, a count of stored rows, and a grouped average rounded to one decimal place. It adds a rule the real lab does not have, a CHECK constraint, so that you practise a second kind of refusal.

The task. Write load_loans(records). It receives a list of (member, book, borrowed_on, days) tuples. It creates an in-memory database with a table called loans, with the columns member, book, borrowed_on and days. The table has a composite primary key on member, book and borrowed_on, and the days column must be greater than zero. Each record is inserted. A record that the database refuses is not stored, and the function counts it. The function returns a tuple of the open connection and the number of refused records.

Write loan_count(conn), which returns the number of stored loans as an int. Write average_days_by_book(conn), which returns a list of (book, average_days) tuples, grouped by book, sorted by book ascending, with each average rounded to one decimal place.

Here is the full solution, with the asserts that check normal cases and every edge case.

import sqlite3

INSERT_SQL = "INSERT INTO loans (member, book, borrowed_on, days) VALUES (?, ?, ?, ?)"

def load_loans(records):
    conn = sqlite3.connect(":memory:")
    conn.execute(
        "CREATE TABLE loans ("
        " member TEXT NOT NULL,"
        " book TEXT NOT NULL,"
        " borrowed_on TEXT NOT NULL,"
        " days INTEGER NOT NULL CHECK (days > 0),"
        " PRIMARY KEY (member, book, borrowed_on))"
    )
    refused = 0
    for record in records:
        try:
            conn.execute(INSERT_SQL, record)
        except sqlite3.IntegrityError:
            refused += 1
    conn.commit()
    return conn, refused

def loan_count(conn):
    return conn.execute("SELECT COUNT(*) FROM loans").fetchone()[0]

def average_days_by_book(conn):
    return conn.execute(
        "SELECT book, ROUND(AVG(days), 1) FROM loans GROUP BY book ORDER BY book ASC"
    ).fetchall()

RECORDS = [
    ("Asha", "Dune", "2026-01-05", 14),
    ("Ravi", "Dune", "2026-01-09", 7),
    ("Asha", "Emma", "2026-01-12", 21),
    ("Asha", "Dune", "2026-01-05", 14),
    ("Mei", "Emma", "2026-02-01", 0),
    ("Mei", "Emma", "2026-02-01", 10),
    ("Ravi", "Ulysses", "2026-03-01", 1),
    ("Mei", "Ulysses", "2026-03-02", 1),
    ("Asha", "Ulysses", "2026-03-03", 2),
]

assert loan_count(conn) == 7
assert refused == 2
assert average_days_by_book(conn) == [("Dune", 10.5), ("Emma", 15.5), ("Ulysses", 1.3)]

assert loan_count(empty_conn) == 0
assert empty_refused == 0
assert average_days_by_book(empty_conn) == []

one_conn, one_refused = load_loans([("Mei", "Emma", "2026-02-01", 5)])
assert loan_count(one_conn) == 1 and one_refused == 0

Explanation, line by line.

  • import sqlite3 loads the standard library module. No installation is needed.
  • INSERT_SQL holds the insert statement once, with four ? placeholders. Each tuple in the list supplies the four values in order.
  • def load_loans(records): defines the loader. It takes the list of tuples and gives nothing else.
  • conn = sqlite3.connect(":memory:") opens a fresh in-memory database for each call, so one call cannot see another call's loans.
  • The CREATE TABLE statement has three parts that matter here. NOT NULL refuses a missing text value. CHECK (days > 0) refuses a loan of zero or fewer days. PRIMARY KEY (member, book, borrowed_on) refuses a second copy of the same loan.
  • refused = 0 starts the counter of refused records.
  • The for loop takes one record at a time. The try block runs the insert, and the except block catches the error that the database raises when a rule is broken.
  • refused += 1 adds one to the counter. The refused record is simply not stored, and the loop carries on with the next record.
  • conn.commit() saves the inserted rows. Without it, the changes would still be visible on this connection, but they would not be committed.
  • return conn, refused returns both values as one tuple. The connection is left open for the caller.
  • loan_count counts the rows in the table and returns the number as an int.
  • average_days_by_book groups the rows by book, averages the days in each group, rounds the average to one decimal place, and sorts by the book's name.

Now the asserts. The first block uses the nine records. Record 4 repeats record 1, so the database refuses it because the key already exists. Record 5 has zero days, so the CHECK refuses it. That gives 9 minus 2 equals 7 stored loans, and a refused count of 2. The averages are Dune with 14 and 7, which is 10.5, Emma with 21 and 10, which is 15.5, and Ulysses with 1, 1 and 2, which is 4 divided by 3, or 1.333, rounded to 1.3. The second block checks that an empty list gives zero loans and an empty result. The third block checks a single valid record.

Notice that the ROUND happens in the query, after the average is worked out. The average of the three Ulysses loans is rounded once, from the exact value. Rounding early, before the final average, is the habit to avoid.

import sqlite3

def load_scans(rows):
    conn = sqlite3.connect(":memory:")
    conn.execute(
        "CREATE TABLE scans ("
        " scan_id INTEGER PRIMARY KEY,"
        " courier TEXT NOT NULL,"
        " kg REAL NOT NULL CHECK (kg >= 0))"
    )
    conn.executemany(
        "INSERT OR IGNORE INTO scans (scan_id, courier, kg) VALUES (?, ?, ?)", rows
    )
    return conn

def scan_count(conn):
    return conn.execute("SELECT COUNT(*) FROM scans").fetchone()[0]

def heaviest_by_courier(conn):
    return conn.execute(
        "SELECT courier, ROUND(MAX(kg), 1) FROM scans GROUP BY courier ORDER BY courier ASC"
    ).fetchall()

rows = [(1, "Zed", 2.04), (2, "Ace", 0.5), (3, "Zed", 3.26), (1, "Zed", 9.9), (4, "Ace", 1.0)]

assert scan_count(conn) == 4
assert heaviest_by_courier(conn) == [("Ace", 1.0), ("Zed", 3.3)]

The executemany call runs the insert once per tuple, and INSERT OR IGNORE skips the repeat. The MAX function picks the largest value in each group, and ROUND rounds it once at the end. An empty input creates the table and returns nothing from the grouped query, which is why the last assert on the empty load is an empty list.

Say it out loud

Interviewers and viva examiners ask these questions to see whether you understand the design, not whether you can recite it.

What is the grain of your fact table, and why does it come first?

Model answer

The grain is one row per location, per source, per UTC hour. It comes first because it defines what one row means, and so it defines the natural key. The UNIQUE constraint on those columns is what makes a duplicate detectable. Without the grain, you cannot say whether two rows are the same measurement or two measurements.

Why does the loader turn on foreign keys for every connection?

Model answer

SQLite leaves foreign-key checks off by default, and the setting belongs to each connection. If the loader forgot the pragma, a reading for an unknown station would be stored without any error. Running PRAGMA foreign_keys = ON right after connect makes the rule hold for every insert from that process. You can prove it by inserting a bad row and seeing the error.

How do you prove that the load is idempotent?

Model answer

Run the load once, record COUNT(*) on the fact table, then run it again and record the count. The two numbers should be equal. The upsert is what makes this true, because a repeated row matches the UNIQUE key and updates instead of adding. The check should be repeatable from a fresh clone of the repository.

Why use one transaction for the whole load?

Model answer

One transaction makes the load all-or-nothing. If the process crashes halfway, the database rolls back to its state before the load, so no half-loaded state is left behind. Committing row by row would leave a partial load that a later run could not distinguish from a complete one. The cost is one commit, which is also much faster.

Why ON CONFLICT DO UPDATE rather than INSERT OR IGNORE?

Model answer

INSERT OR IGNORE keeps the old row when the key exists, so a corrected reading for the same hour is silently lost. ON CONFLICT DO UPDATE applies the new value to the existing row, which is what a corrected fetch needs. Both are repeatable, but only the upsert keeps the data correct when values change. The conflict target must match the UNIQUE key, or the statement is rejected.
