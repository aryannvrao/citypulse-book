The idea in one minute

Today you learn to ask a large language model (LLM, a program trained on very large amounts of text that writes new text) to produce something for you, and how to make that output trustworthy. CityPulse turns the day's air-quality readings into a short bulletin for residents. The model writes the sentences, but your code decides what is allowed to reach a resident.

By the end you will be able to send one request to an API (a defined way for one program to call a service over the internet), read the reply, check it with code, and fall back to a safe template when something fails.

Think of a fast junior writer who has never seen the data. You put the numbers on a sheet and ask for a paragraph. A fact-checker then circles every figure and asks where it came from. Your job is to be the fact-checker.

Starting from zero

This section explains the words the rest of the chapter uses. Skip what you already know.

Files, commands and the terminal

A file is a named piece of stored text or data. The terminal (also called the command line) is a window where you type instructions as text. Each typed instruction is a command. For example, python3 advisory.py means "run the Python program stored in the file advisory.py". A program is a file of instructions that a computer can run. A script is a short program.

On Windows, if python3 is not recognised, try python. Both mean the same thing in this chapter.

Variables, strings, lists, dictionaries and sets

A variable is a name that holds a value. pm = 82 stores the number 82 under the name pm. A string is text inside quotes, such as "PM2.5". A list is an ordered collection in square brackets, such as ["S1", "S2"]. A dictionary (dict) is a collection of key and value pairs in curly braces, such as {"city": "Riverside"}, where "city" is the key and "Riverside" is its value. A set is an unordered collection with no duplicates, such as {"2026-03-02"}.

Functions, modules and imports

A function is a named block of code you can call. def double(x): return x * 2 defines a function called double. The call double(4) gives 8. The words in brackets are parameters, the inputs the function receives.

A module is a Python file that other code can load. The standard library is the set of modules that comes with Python, such as json and re. import json loads the json module. A package is extra code you install. pip install anthropic installs the package that talks to the Anthropic API.

Servers, HTTP, HTTPS, JSON and SDKs

A server is a computer or program that waits for requests and sends back answers. HTTP is the set of rules that programs use to send requests and receive replies. HTTPS is HTTP with encryption, so others on the network cannot read the traffic. JSON (JavaScript Object Notation) is a text format for structured data, such as {"headline": "Clean air today"}.

An SDK (software development kit) is a library that wraps raw HTTP calls in ordinary Python functions. You call client.messages.create(...) instead of building the HTTP request yourself.

Secrets, API keys and environment variables

A secret is a value that proves who you are, such as an API key. The provider uses the key to identify you and to bill you. Anyone with the key can spend your money, so it must stay private.

An environment variable is a named value that your terminal session or operating system holds and programs can read. Python reads one with os.environ. In Windows PowerShell you set one for the current session with $env:NAME = "value". Hard-coding a secret means writing it directly into a source file, which is what you must not do.

Tokens, context windows and cost

A token is a piece of a word, often a few characters. The model reads input tokens and writes output tokens. Providers charge per token, so the cost of one call is the number of tokens multiplied by the published price. A context window is the most text the model can take in one request.

Temperature, timeouts, retries and exceptions

Temperature is a setting that controls randomness. A low value makes the model pick its most likely words. A timeout is the longest time your program waits for a reply. A retry is a second attempt after a failure. An exception is an error raised while code runs. try and except let your code run something and handle the error instead of crashing.

Regular expressions, assert, pytest and Git

A regular expression (regex) is a pattern that matches text, such as "four digits, a dash, two digits". Section 7 teaches them properly.

assert condition stops the program with an error when the condition is False. pytest is a tool that runs test functions. A test function has a name starting with test_ and uses assert to check results.

Git records changes to files. A file named .gitignore lists files Git must never store, such as .env, which holds secrets.

The tools

LLMs and tokens

What it is. A large language model predicts the next token, given all the text so far. It repeats this until it stops. You reach it over HTTPS with an API key.

Why CityPulse uses it. BBMP (the municipal body that runs Bengaluru's civic services) wants plain-language bulletins that residents can read. Writing those sentences from scratch is text generation, which an LLM does well. The slides compare three alternatives. A template-only bulletin is deterministic and free, but it reads mechanically, so the course keeps it as the fallback. A self-hosted open model keeps data on your own servers but needs GPUs (graphics processors) and tuning. A fine-tuned model needs training data and extra cost. The course rules them out for this spike.

How it works. The provider converts your prompt into tokens. It then generates output tokens one at a time, choosing each with the temperature setting. Generation stops at a natural end or when it reaches max_tokens, the cap on output length. The reply reports how many input and output tokens were used. You multiply those counts by the published price to get the cost of each call.

The flow below shows one bulletin request. The number checker in the last step is explained later in this chapter.

After the flow, here is the call-wrapper from the slides, genai/llm.py. The slides split long lines; the code below has them rejoined.

import os
import anthropic
client = anthropic.Anthropic(api_key=os.environ["LLM_API_KEY"], timeout=15.0, max_retries=2)
def call_llm(system: str, user: str) -> tuple[str, dict]:
    msg = client.messages.create(
        model=os.environ["LLM_MODEL"],   # trainer-approved model id
        max_tokens=400,
        temperature=0.2,
        system=system,
        messages=[{"role": "user", "content": user}],
    )
    usage = {"input_tokens": msg.usage.input_tokens,
             "output_tokens": msg.usage.output_tokens}
    return msg.content[0].text, usage

Line by line:

  • import os loads the standard module for reading environment variables. import anthropic loads the SDK.
  • client = anthropic.Anthropic(...) creates a client object. It is built once and reused. api_key= takes the key from the environment variable LLM_API_KEY. The square brackets read the variable, and a missing variable raises an error straight away.
  • timeout=15.0 gives up after 15 seconds. max_retries=2 lets the SDK retry twice on failures before raising an error.
  • def call_llm(system: str, user: str) -> tuple[str, dict]: defines the function. system: str says the first input is text. -> tuple[str, dict] says it returns a pair: the reply text and a dictionary of usage counts.
  • client.messages.create( sends the request. model= takes the model id from LLM_MODEL, so the model can change without editing code. The comment after # is ignored by Python.
  • max_tokens=400 caps the reply at 400 output tokens. temperature=0.2 keeps the wording steady.
  • system=system passes the instructions. messages=[...] passes the user's part in a list of messages, each with a role and content.
  • usage = {...} copies the two token counts from the reply into a dictionary.
  • return msg.content[0].text, usage returns the text of the first content block, plus the counts. Expect the function to return something like ("Air quality is ...", {"input_tokens": 48, "output_tokens": 28}).

Now a real run from the course workbook. The command is typed at the prompt, and the lines below it are the output.

The first line is the advisory text. The second line is a comment added in the sheet, showing 24 input and 31 output tokens. Your counts will differ, because the prompt and reply differ each time.

Trap: Hard-coding the key

Writing client = Anthropic(api_key="sk-ant-...") in a file or notebook means the key is in your Git history the moment you commit. Read it from the environment, as the code above does, and keep .env in .gitignore.

Trap: No timeout or retry limit

Without a timeout, a hung call blocks your service. The slides set 15 seconds and at most 2 retries. Setting those values is the only protection you have in this code.

Trap: Estimating cost from characters

Characters are not tokens. Use the usage counts from each reply and the provider's published price for the model.

Prompt patterns and JSON output

What it is. A prompt pattern is a reusable prompt structure. It has a role, the data inside clear delimiters, explicit rules, one example and the required output format. JSON output means you ask the model to reply in a fixed shape, such as {"headline": ..., "body": ...}, so your code can read the fields.

Why CityPulse uses it. Three reasons, from the slides. Putting the stats inside <stats> delimiters separates data from instructions, which makes the rule "only use these numbers" enforceable. A JSON shape lets /v1/bulletin return fields and lets the checker read them reliably. A version name such as PROMPT_VERSION='bulletin_v1' becomes part of the cache key, so changing the prompt never serves stale bulletins.

The alternatives are free-form prompts written in code, which are untracked and cannot be tested, provider features for structured output, which are stronger but tied to one provider, and prompt frameworks such as LangChain, which are heavy for one template. The course keeps a portable parse, retry and fallback instead.

How it works. The template is a file with a system part and a user part, split by the line ---USER---. The stats are inserted as JSON. The reply is cleaned of code fences, parsed, and if parsing fails the code retries once with a stricter instruction. If the retry also fails, a template bulletin is returned.

The code below is genai/bulletin.py from the slides.

import json, re
from genai.llm import call_llm
PROMPT_VERSION = "bulletin_v1"
SYSTEM, USER_TMPL = open("genai/prompts/bulletin_v1.txt").read().split("---USER---")
def bulletin(stats: dict) -> dict:
    user = USER_TMPL.replace("{stats}", json.dumps(stats))
    for extra in ("", "\nReturn valid JSON only."):
        text, usage = call_llm(SYSTEM, user + extra)
        try:
            out = json.loads(re.sub(r"^```(?:json)?|```$", "", text.strip(), flags=re.M))
            return {"headline": out["headline"], "body": out["body"], "source": "llm", "usage": usage}
        except (json.JSONDecodeError, KeyError, TypeError):
            continue
    return {"headline": "Bengaluru air quality update", "body": f"City mean PM2.5: {stats['city_pm25_mean']} ug/m3.", "source": "template"}

Line by line:

  • import json, re loads the JSON module and the regex module in one line. from genai.llm import call_llm brings in the function from the previous block.
  • PROMPT_VERSION = "bulletin_v1" records the version. You change this name when you change the prompt.
  • SYSTEM, USER_TMPL = open(...).read().split("---USER---") opens the template file, reads all of it, and cuts it in two at the marker line. The two parts are stored in two variables. open(...) returns a file handle; .read() returns its text as one string.
  • user = USER_TMPL.replace("{stats}", json.dumps(stats)) replaces the placeholder {stats} with the JSON text of the stats dictionary. json.dumps turns a Python dictionary into JSON text.
  • for extra in ("", "\nReturn valid JSON only."): runs the loop twice. The first time the extra text is empty. The second time it adds the stricter instruction. \n is a new line.
  • text, usage = call_llm(SYSTEM, user + extra) makes the call and unpacks the pair it returns.
  • json.loads(...) turns text into a Python dictionary. It raises json.JSONDecodeError if the text is not valid JSON.
  • re.sub(r"^```(?:json)?|```$", "", text.strip(), flags=re.M) removes Markdown code fences. The pattern matches an opening fence with an optional json label, or a closing fence at the end of a line. re.M makes ^ and $ match at each line, not only the start and end of the whole text. text.strip() first removes spaces and new lines at both ends.
  • out["headline"] and out["body"] read two keys. A missing key raises KeyError.
  • The return line sends back a dictionary with "source": "llm", so later code knows the text came from the model.
  • except (json.JSONDecodeError, KeyError, TypeError): continue catches parse and shape errors and moves to the next attempt.
  • The last return is the template fallback. It is deterministic, so the endpoint always answers.
Trap: The API error is not caught here

In the code as printed, call_llm sits outside the try block, so an exception from the API, such as a timeout, is not caught by the except in bulletin. The slides' live demo expects source='template' after a simulated timeout, so the fallback must also cover errors from the call. Move the call inside the try, or catch the API's error class around it. Do not assume the code does this just because the slides say it does.

Trap: Editing bulletin_v1.txt in place

If you change the wording of the template but keep the name, old cached bulletins and saved samples no longer match the prompt that made them. Create bulletin_v2.txt and change PROMPT_VERSION to match.

Trap: Passing user text into the prompt

/v1/bulletin accepts only a validated day and ward. Free text from a user would let the user write instructions into the prompt. Section 6 returns to this.

Here is the same pattern used in the workbook's simpler advisory. Read the sample and notice that the output is not checked yet. Step 5 of the lab adds that check.

Grounding and hallucination

What it is. Grounding means the model may state only facts that appear in the input. A hallucination is fluent text that the input does not support, such as an invented AQI value. An automated checker compares every number in the output with the numbers that were allowed.

Why CityPulse uses it. BBMP staff will share bulletins without checking every sentence, and one invented figure damages trust. The slides also cite a court ruling in which an airline was held responsible for what its chatbot said. The course treats the organisation as accountable for its output, so the rule is to verify, not to hope. The checker runs as a pytest test on saved fixtures, so continuous integration (automatic testing on every change) checks grounding without calling the network or needing an API key.

The alternatives are manual review, which does not scale to daily bulletins for every ward, an LLM-as-judge, which is itself unverified and costs another call, and retrieval-augmented generation (RAG), covered in section 6. Code checks numbers better than another model does.

How it works. The checker builds the set of allowed numbers from the stats and the date. It extracts every number from the headline and body, ignoring pollutant names such as PM2.5. Any number outside the set makes the bulletin ungrounded, and the API serves the template.

Before the code, here is how the checker processes a small input. This animation runs the same idea on dates.

The checker in the slides is genai/check.py:

import json, re
NUM = re.compile(r"\d+(?:\.\d+)?")
def check(bulletin: dict, stats: dict, day: str) -> tuple[str, list[str]]:
    """PASS only if every number in the bulletin appears in stats or the date."""
    allowed = {float(n) for n in NUM.findall(json.dumps(stats) + " " + day)}
    text = re.sub(r"PM\s?(2\.5|10)", "PM", f"{bulletin['headline']} {bulletin['body']}")
    bad = [n for n in NUM.findall(text) if float(n) not in allowed]
    return ("PASS" if not bad else "FAIL"), bad
def test_invented_aqi_is_caught():
    stats = {"city_pm25_mean": 61.2, "pct_change_vs_prev_day": -12.5}
    status, bad = check({"headline": "PM2.5 averaged 61.2", "body": "AQI reached 180."}, stats, "2026-03-02")
    assert status == "FAIL" and bad == ["180"]

Line by line:

  • NUM = re.compile(r"\d+(?:\.\d+)?") builds a pattern once. \d+ is one or more digits. (?:\.\d+)? is an optional part: a dot followed by more digits. So 61.2 and 180 both match. (?:...) groups without capturing, and ? makes the group optional.
  • allowed = {float(n) for n in NUM.findall(...)} is a set comprehension. findall returns every match as a string, and float turns each into a number. A set keeps only unique values. The text joined is the JSON of the stats and the date. The date 2026-03-02 contributes 2026, 3 and 2.
  • text = re.sub(r"PM\s?(2\.5|10)", "PM", ...) removes the digits in names such as PM2.5 and PM10. \s? allows an optional space. (2\.5|10) is one of two alternatives. The f"..." string puts the headline and body together with a space.
  • bad = [n for n in NUM.findall(text) if float(n) not in allowed] keeps every number from the text that is not in the allowed set. The result is a list of strings.
  • return ("PASS" if not bad else "FAIL"), bad returns a status and the list of bad numbers.
  • def test_invented_aqi_is_caught(): is a test. pytest runs it because the name starts with test_.
  • The assert checks two things. The status must be "FAIL", and the bad list must be exactly ["180"]. Expect this test to pass with no output, and a failed assert would show the values.
Trap: Rounding mismatch

If the stats say 61.24 and the bulletin says 61.2, the check fails, because 61.2 is not in the allowed set. Round the stats to one decimal place before you put them into the prompt, so both sides match.

Trap: Calling the real LLM in tests

Continuous integration should not call the model. Use saved fixtures, and replace call_llm with a stub using pytest's monkeypatch, which swaps a function for the length of one test.

Trap: Low temperature prevents hallucination

A low temperature reduces randomness. It does not stop invention. Only a check in code proves that the numbers are grounded.

Responsible-use policy

What it is. A responsible-use policy is a short, written agreement on how the team uses generative AI. It states what data may and may not be sent to an external model, how outputs are verified, how keys are handled, and how AI coding assistants may be used. It turns good intentions into rules you can check.

Why CityPulse uses it. The slides give an example. Samsung staff pasted confidential code into a public chatbot in 2023. A written policy names data that never leaves CityPulse. A second reason is that BBMP must know bulletins are generated, checked, and not health advice. A third is the rule that you must be able to explain any code you commit, which protects code quality and the viva.

The alternatives are no written policy, which means nobody can audit anything, a complete ban, which removes a client-requested feature, and a generic corporate policy, which is too long and not specific to CityPulse.

How it works. The policy starts from data. Only aggregated public air-quality statistics may go to an external model. It then covers key storage, automated checks on every output, cost limits and the rule for AI coding assistants. The squad agrees a three-line summary that every member can recite. The slides record that summary as: only public aggregates go to the LLM; every number is checked; we own what it says.

Here are the course's key points from docs/genai-policy.md, condensed:

  • Allowed to send: aggregated, public air-quality stats from stats_for(day).
  • Never send: DATABASE_URL, API keys, raw logs, personal data, client documents, source code.
  • Keys: LLM_API_KEY only in .env, which is gitignored, and in the cloud secret manager.
  • Outputs: every bulletin passes genai/check.py. Failures return the template, with source=template.
  • Disclaimer: auto-generated from CityPulse data; not medical or health advice.
  • Cost: max_tokens 400, BULLETIN_DAILY_CAP=50, cached per (day, ward, prompt_version).
  • Input: no free-text user prompts; only validated day and ward parameters.
Trap: A policy nobody reads

Keep the policy to one page, and be ready to recite the three-line summary. An examiner will ask you to.

Trap: Forgetting the spend cap

Keys stay live for about two weeks after the course's demo period, so a loop that keeps calling the model can run up cost. Enforce BULLETIN_DAILY_CAP. The sources do not say whether the cap counts calls or money, so confirm that with your trainer before you rely on it.

Trap: Leaving out the disclaimer

Every /v1/bulletin payload must include the disclaimer, not only the human-facing page.

The worked example

Goal. Send one number, PM2.5 at 82 micrograms per cubic metre, to the model and get a one-line advisory for residents. The number is in the prompt, and the model writes the sentence. This is the simplest version of the bulletin.

Code. The file is advisory.py:

import os
from anthropic import Anthropic

client = Anthropic(api_key=os.environ["ANTHROPIC_API_KEY"])  # key from env
prompt = "PM2.5 is 82 ug/m3. One-line advisory for residents."
msg = client.messages.create(model="claude-opus-5", max_tokens=120,
                             messages=[{"role": "user", "content": prompt}])
print(msg.content[0].text)

Explanation. Line by line:

  • import os and from anthropic import Anthropic load the environment reader and the SDK client class.
  • client = Anthropic(...) creates the client. os.environ["ANTHROPIC_API_KEY"] reads the key from the environment, so the key is not in the file.
  • # key from env is a comment. Python ignores it. It is there for the reader.
  • prompt = "..." stores the whole prompt in one variable. The string contains the number and the instruction.
  • client.messages.create(...) sends the request. model="claude-opus-5" names the model, and max_tokens=120 limits the reply. messages=[{"role": "user", "content": prompt}] is the single message in the conversation.
  • print(msg.content[0].text) prints the first part of the reply.

Note that this workbook version sets the model name in the code and does not set a temperature. The slides' version reads the model from LLM_MODEL and sets temperature 0.2. Use the model your trainer approves.

Output. Running python advisory.py should print a single advisory line. The sheet shows this sample:

Air quality is unhealthy for sensitive groups (PM2.5 82). Limit prolonged outdoor exertion; keep windows closed.

The reply cites PM2.5 82, which is the number you gave it. This is what grounding looks like at the first level. The reply is still unchecked, so a model could have written a different number. Lab step 5 adds the check.

These calls are how you will build the tickets Y2-T47 and Y2-T48. T47 records token cost per call and sets up the prompt and checker. T48 ships the /v1/bulletin endpoint with validation, caching and a daily cap.

The hands-on lab, step by step

Before you start, create a folder for the lab and a file called readings.json in it. The code in steps 1 and 2 reads this file. Create it with Notepad or VS Code, and paste the text below exactly:

{
  "date": "2026-07-14",
  "city": "Riverside",
  "readings": [
    {"pollutant": "PM2.5", "value": 82, "unit": "ug/m3"},
    {"pollutant": "PM10", "value": 61, "unit": "ug/m3"},
    {"pollutant": "NO2", "value": 38, "unit": "ug/m3"},
    {"pollutant": "O3", "value": 44, "unit": "ug/m3"}
  ]
}

Each step below has a file to save and a command to type. Use the folder as your working directory. In PowerShell, cd followed by the folder path moves there.

Step 1. Load today's readings and pick the headline

What you do. Save this as readings.py. It loads the file, finds the highest PM2.5 value, and finds the worst reading of any pollutant.

import json
d = json.load(open("readings.json"))
pm = max(r["value"] for r in d["readings"] if r["pollutant"] == "PM2.5")
worst = max(d["readings"], key=lambda r: r["value"])
print("date:", d["date"], "city:", d["city"])
print("PM2.5:", pm, "ug/m3 | worst:", worst["pollutant"], worst["value"])

Line by line: json.load(open(...)) opens the file and turns the JSON into a dictionary. The first max takes the largest PM2.5 value from the list of readings, using a generator expression (a short loop inside brackets). max(..., key=lambda ...) picks the whole reading with the largest value. lambda r: r["value"] is a tiny unnamed function that returns the value of a reading. The two print lines show the results.

Type this. python3 readings.py

You should see.

date: 2026-07-14 city: Riverside
PM2.5: 82 ug/m3 | worst: PM2.5 82

How you know it worked. The PM2.5 value is 82 and it is also the worst reading. If you see an error such as KeyError, check the spelling of the keys in the JSON file.

Step 2. Prepare grounded input

What you do. Save this as build_prompt.py. It turns every reading into text and adds one instruction.

import json
d = json.load(open("readings.json"))
nums = "; ".join(f"{r['pollutant']} {r['value']} {r['unit']}" for r in d["readings"])
prompt = (f"Air-quality readings for {d['city']} on {d['date']}: {nums}. "
          "Write a one-line advisory for residents in plain language.")
print(prompt)

Line by line: "; ".join(...) joins the list of strings with a semicolon and a space. The f-string inside builds one piece for each reading. The prompt is two strings joined by Python's implicit joining, which places the numbers first and the instruction last.

Step 5. Validate before you show it

What you do. Save this as validate.py. It checks the length of the reply, requires it to cite the reading, and rejects unsafe text.

def validate(text, pollutant, value):
    t = text.strip()
    assert 0 < len(t) <= 240, "length out of range"
    assert str(value) in t or pollutant in t, "must cite reading"
    banned = ("http://", "<script", "ignore previous")
    assert not any(b in t.lower() for b in banned), "unsafe"
    return t

resp = ("Air quality is unhealthy for sensitive groups "
        "(PM2.5 82). Limit prolonged outdoor exertion; "
        "keep windows closed.")
print("validated:", bool(validate(resp, "PM2.5", 82)))
print("chars:", len(resp))

Line by line: t = text.strip() removes spaces at both ends. Each assert checks one rule and shows its message if it fails. 0 < len(t) <= 240 checks that the reply is not empty and not longer than 240 characters. str(value) in t checks that the number appears in the text. banned lists three phrases that should never reach a resident, and t.lower() makes the check case-insensitive. not any(...) is True only if none of them appears. bool(...) turns the returned text into True.

How you know it worked. validated: True means every rule passed. If you change the sample so that it no longer mentions 82, the assert fails with "must cite reading".

or pollutant in t means a reply that mentions PM2.5 but a wrong number still passes. Think about why the check is written that way, and say what it would miss.

Step 6. Handle timeouts and errors

What you do. Save this as safe_call.py. It wraps the call in try and except, and falls back to a safe message.

except APIError as e:
    print("LLM call failed:", e.__class__.__name__)
    text = "Advisory unavailable; check local readings."
print(text)

Line by line: from anthropic import Anthropic, APIError loads the client and the base error class. The code inside try: runs first. The fallback text is then assigned to text.

Keeping the API key secret

What it is. An API key is a secret string that proves to a provider who you are. The provider uses it to decide whom to bill, and anyone who holds it can spend your money. A secret must stay out of source files, notebooks, logs and Git. Python can read a value that your terminal session holds, called an environment variable, with os.environ:

import os
key = os.environ.get("LLM_API_KEY")
print("key set:", key is not None)

If the variable is set in your session, the output is key set: True. If it is not set, the output is key set: False, and the program can stop with a message. The code never contains the key itself.

Git keeps a full history of every commit. A key committed once stays in that history even after a later commit deletes it. A file named .env holds local values such as the key, and .gitignore tells Git to skip it. Logs are copies too, so print only a length or a short masked prefix.

How it shows up in a case study. The bulletin job runs on a laptop for testing and on a cloud server every morning. On the laptop, the key sits in a .env file that Git ignores. On the server, the cloud secret manager gives the same variable name to the job when it starts. A teammate suggests pasting the key into a settings file so the job runs with no setup. The right decision is to keep the key out of that file. The same code then works in both places, because only the source of the value changes, and the repository never holds the secret.

Trap: Deleting the line later is enough

Once a key has been committed, removing it in a later commit does not remove it from history. Treat the key as exposed, and replace it with a new one at the provider.

Getting structured JSON back from the model

What it is. Structured output means the model replies in a fixed shape that your code can read. The usual shape is JSON (JavaScript Object Notation), a text format for dictionaries, lists, strings and numbers. Your code turns JSON text into a Python dictionary with json.loads:

import json
reply = '{"headline": "Clean air", "body": "PM2.5 is 18."}'
data = json.loads(reply)
print(data["headline"])

The output is Clean air. If the text is not valid JSON, json.loads raises json.JSONDecodeError. If a key is missing, data["body"] raises KeyError. Models sometimes wrap JSON in a Markdown code fence, which is a line of three backticks before and after the text. Your code must remove the fence before it parses the text.

How it shows up in a case study. The bulletin endpoint asks the model for JSON with two keys. In a test run, the reply arrives inside a fence, and the body key is missing. The page must still show something safe. The right design removes the fence, parses the text, checks the keys, retries once with a stricter instruction, and then returns a template bulletin if the retry also fails. The page never receives raw text, and the endpoint still answers. The response records which source was used, so the caller can see that the fallback was served.

Trap: Passing raw text to the page

Raw text skips parsing and the checks, so the page can break or show unverified content. Stopping the service on a parse error is the other trap, because it takes the endpoint down for every resident.

Hallucination and grounding

What it is. Grounding means the model may state only facts that appear in the input you gave it. A hallucination is fluent text that the input does not support, such as an invented number. The only reliable way to catch one is a check in code that compares each number in the output with the set of allowed numbers. Here is the same idea on words, so you can see the mechanism without any numbers:

allowed = {"Riverside", "Monday"}
claimed = ["Riverside", "Tuesday"]
print([word for word in claimed if word not in allowed])

The output is ['Tuesday']. The set holds what the input allows. The list comprehension keeps every claim that is not in the set. An empty result means nothing was invented. A set is the right tool here, because the test asks only whether a value is present.

How it shows up in a case study. The model writes that a ward reached a value that nobody recorded. The stats sheet has a PM2.5 mean and no AQI at all. A reviewer reads the bulletin and says it sounds right. The correct decision is that the bulletin is not grounded. The checker finds a number outside the allowed set, so the endpoint serves the template instead. The bulletin reads well, but reading well is not a test of truth, and the team does not ship it on that basis.

Trap: It reads well, so it is grounded

Fluent text can contain invented numbers. Only a check that compares every number with the facts proves that the text is grounded.

Temperature and randomness

What it is. Temperature is a setting that controls how much the model varies its word choice. For this API it is usually a number from 0 to 1. A low value makes the most likely next word more likely, so replies repeat and read the same way. A high value lets less likely words through, so replies vary more. The table shows the same request at three settings:

Temperature What you see across repeated calls
0.0 Nearly the same wording each time
0.2 Steady wording, with small variation
1.0 Wide variation, and more surprising word choices

Temperature is set in the request, next to max_tokens. It changes the random choice of each word. It does not change what the model knows, and it does not decide whether a number is true. A low temperature is useful for steady wording, which residents and staff value, but it is not a safety control.

How it shows up in a case study. A teammate wants the bulletins to read the same from one day to the next, so that staff can compare them. The teammate sets the temperature to 0 and believes the bulletins can no longer contain invented numbers. The right decision keeps the low temperature for steady wording, and keeps the number checker, because only the checker can show that a number came from the stats. The course's value of 0.2 gives steady wording, and the checker handles grounding.

Trap: Temperature as a safety switch

A low temperature reduces randomness, but it does not stop the model from inventing a number. A check in code is the only proof.

Retrieval-augmented generation (RAG)

What it is. Retrieval-augmented generation, or RAG, is a pattern where your program first searches a collection of documents for passages that fit the question, then adds those passages to the prompt. The model answers from the passages rather than from memory alone. Here is retrieval in its simplest form, a keyword search in plain Python:

notes = ["Parking closed on Monday.", "Air quality alert on Tuesday.", "Library open late."]
question = "air"
hits = [note for note in notes if question.lower() in note.lower()]
print(hits)

The output is ['Air quality alert on Tuesday.']. Real systems use better search, often based on embeddings, which are numeric representations of meaning. The steps are the same: search, select the best passages, add them to the prompt, then ask. RAG adds moving parts, namely an index to build and keep up to date, a search that can miss the right passage, and text splitting decisions. Each one is a place where a failure can hide.

How it shows up in a case study. CityPulse would need RAG if it answered resident questions about hundreds of council documents, which are long and change often. The bulletin is different. Its input is a stats dictionary of a few dozen numbers, computed each day in pandas. The whole input fits in one prompt, so retrieval would add failure points without giving the model anything it does not already have. The right decision is to pass the stats directly and check the numbers in the output.

Trap: RAG makes the answer true

Retrieval improves the chance that the model sees the right source. The model can still misread a passage or invent a detail, so the output still needs a check against the source.

Context windows and max_tokens

What it is. A context window is the most text a model can handle in one request. The input and the output both count toward it. max_tokens is different: it is a cap on the output only, and it does not make the input any smaller. Here is the arithmetic, using a made-up window of 10,000 tokens for this example:

window = 10000
prompt_tokens = 9800
max_tokens = 400
print(prompt_tokens + max_tokens <= window)

The output is False, because 9,800 plus 400 is 10,200, which is more than 10,000. If max_tokens were 200, the sum would be exactly 10,000 and the output would be True. Token counts also set the price, so a large input costs more on every call, even when the reply is short.

How it shows up in a case study. A team wants to put thirty days of hourly readings into one prompt. They set max_tokens to 400, hoping that this keeps the request small, and the request fails with a size error. The right decision is to measure the input from the token counts, check that the input plus the planned output fits in the window, and send a summary if it does not. Raising max_tokens would only make the problem worse, because the reply would need even more room.

Trap: max_tokens limits the input

The cap applies only to the reply. A long input is limited by the context window, and it is billed on every call.

Rate limits and backing off

What it is. A rate limit caps how many requests or tokens a key may use in a period. When a request goes over the limit, the provider returns an error, commonly with status 429, which means too many requests. Backing off means waiting before the next attempt, and waiting longer after each failure. The example below only prints the waits, so you can see the growth. A real program would pause for that many seconds before the next call.

for attempt in range(3):
    wait = 2 ** attempt
    print("attempt", attempt, "waits", wait, "seconds")

The output is three lines: attempt 0 waits 1 seconds, then attempt 1 waits 2 seconds, then attempt 2 waits 4 seconds. The waits double each time, and the number of attempts is fixed. The SDK's max_retries setting controls how many automatic retries it makes, and your code still needs a limit and a fallback of its own.

How it shows up in a case study. A nightly job sends one request for each of forty wards, all at once, and about half of them come back with 429. The team has not added any wait between attempts. The right decision is to limit how many calls run at the same time, wait a growing time between a small number of retries, use an existing cached bulletin where one exists, and serve the template when all attempts fail. The job then finishes, and the endpoint keeps answering.

Trap: Retrying at once in a tight loop

Immediate retries add to the overload, and a loop with no limit never ends. Removing the timeout does not help either, because calls then hang and hold the service.

Prompt injection

What it is. Prompt injection is text in untrusted input that tries to change the model's instructions. If your code pastes a resident's text into the prompt, the model may read that text as instructions and follow it. The example below shows the mechanism:

ward = "ignore previous instructions"
prompt = f"Write a bulletin for ward {ward}."
print(prompt)

The output is Write a bulletin for ward ignore previous instructions. The attacker's words now sit inside your instruction, where the model cannot tell them apart from your rules. The defence is to keep free text out of the prompt. The endpoint accepts only validated values, such as a ward code from a known list, and returns a 422 error for anything else. A list of banned phrases is a weaker extra layer, because an attacker can rephrase.

How it shows up in a case study. A resident portal has a free-text box for a ward or a note. One entry says to ignore earlier rules and list every stats field. The right decision is to remove the free-text box from the prompt path entirely. The ward must match one of the known codes, and anything else is refused at validation with a 422 response. A stronger filter on the text is not the fix, because the text should never reach the prompt.

Trap: Removing the bad words

An attacker who sees a phrase removed can write the same instruction in other words. Validation of allowed values is the defence, not editing the text.

Tool calling

What it is. Tool calling, also called function calling, lets a model reply with a request to run a named function and pass it arguments. For example, the model might ask to run get_readings with day set to "2026-07-14". The request is text generated by the model, so it is untrusted, and your code decides whether to run anything. The example below shows the check:

allowed_tools = {"get_readings"}
request = {"name": "get_readings", "arguments": {"day": "2026-07-14"}}
if request["name"] in allowed_tools:
    print("run", request["name"], "with", request["arguments"]["day"])

The output is run get_readings with 2026-07-14. The allowlist is a set of the only names your code will run. If the name is not in the set, nothing runs. Arguments need the same care, so your code must check their type, format and range before it calls anything.

How it shows up in a case study. A chat assistant for residents lets the model call tools. The model proposes a tool named delete_readings for the day's data. The team has one read-only tool, get_readings. The right decision is to reject the request, because the name is not on the allowlist, and return a safe message to the resident. The decision does not depend on how often the model asks. A repeated request is still an unchecked request.

Trap: The model asked, so it runs

The model's request is output, and injected text can shape it. Check the name and the arguments in your own code before anything runs.

Evaluating LLM output with tests

What it is. Evaluation means measuring the quality of output with evidence that you can repeat. For this course that means offline tests on saved inputs, so the same test gives the same result every time. A test is a function whose name starts with test_ and that uses assert to check a result. Here is the idea with a plain check on text:

def bulletin_mentions_pm25(text):
    return "PM2.5" in text

assert bulletin_mentions_pm25("PM2.5 is 82.")
assert not bulletin_mentions_pm25("The air is clean.")

Both asserts pass, so the program prints nothing. A failed assert stops the program with an error that shows the line. Real tests of a model replace the model call with a stub, which is a fake function that returns a saved reply, so that no network or key is needed. Cost is evaluated from the saved token counts, multiplied by the published price.

How it shows up in a case study. A teammate changes the wording of the bulletin prompt and says the new version is better, because three bulletins read well. The right decision is that reading three outputs is not repeatable evidence. The team runs offline pytest tests on saved fixtures that check the JSON shape, the numbers and the banned phrases, with the model call replaced by a stub. Continuous integration then runs the same tests on every change, without an API key.

Trap: Asking a second model to grade the first

A judge model is itself unverified and costs another call. Use code checks where you can, and test the judge on cases with known answers before you trust it.

The graded lab

The task in plain words

The scenario. A CityPulse assistant answers air-quality questions by asking a language model for a reply. Before a reply reaches a resident, your code must flag any number the model invented, and it must remove personal details from the text. You write four functions in one file, using only the standard library. The starter file already names them, so keep the names exactly as they are and fill in the bodies.

Each function, with its rules, is below.

  • extract_numbers(text: str) -> list[float] takes a text and returns every integer or decimal in it, as floats, in the order they appear.
  • Each number is returned as a float, so the integer 95 becomes 95.0.
  • A number that appears twice is returned twice. The statement asks for every number in order, not for unique values.
  • A full stop at the end of a sentence is not a decimal point. In the statement's example, "station 7." ends the sentence, so the number is 7.0.
  • The statement does not mention minus signs. Do not add special handling for them unless a visible test shows that you must.
  • unsupported_numbers(answer: str, allowed: list) -> list[float] returns the numbers in answer that are not in allowed, which is the list of facts the model was given.
  • The result is sorted from smallest to largest.
  • Each value appears once, even if it appears several times in the answer.
  • The values are floats.
  • The statement's example is unsupported_numbers("The AQI was 95 at station 7.", [42, 7]), which returns [95.0]. The 7 is allowed, so it is not reported.
  • is_grounded(answer: str, allowed: list) -> bool returns True if unsupported_numbers finds nothing, and False otherwise. It returns a bool, not a list.
  • redact_pii(text: str) -> str returns the text with two kinds of change.
  • Every email address is replaced with [EMAIL].
  • Every phone number in the form ddd-ddd-dddd is replaced with [PHONE]. The separator between the groups may be a dash, a dot, or nothing at all.
  • Emails are redacted before phones.
  • The statement's example is redact_pii("contact me at jo@airteam.io or 555-123-4567"), which returns 'contact me at [EMAIL] or [PHONE]'.

Limits. Each run may take 30 seconds and use 128 MB. A regular-expression solution is far inside both limits, so they matter only if your code does something very slow.

Visible test Points
Every number is grounded in the facts 15
95 is not in the allowed facts (hallucinated) 20
Grounded answer 10
Ungrounded answer 10
Redact an email and a dashed phone 20

The hidden tests are three automated checks worth 25 points together. You cannot see their inputs. They try cases the visible tests do not cover, such as empty text, repeated numbers, an email that contains digits, or a phone number written without separators. What each function needs

Each idea below is taught with a small example that has nothing to do with the lab's data. Work out the lab's functions yourself from the rules.

  • Finding every match. re.findall returns every match of a pattern as a list of strings. re.findall(r"[a-z]+", "tea, milk and 2 eggs") returns ['tea', 'milk', 'and', 'eggs']. The pattern [a-z]+ means one or more lowercase letters, so the 2 is skipped.
  • Matching a real dot. In a pattern, a plain dot matches any character. To match a real dot, write \.. re.findall(r"\d\.\d", "3.5 and 3x5") returns ['3.5'], because the x is not a dot.
  • Converting to float. float("4") returns 4.0, and float("0.5") returns 0.5. The result is always a float, even for a whole number.
  • Unique and sorted. set keeps one copy of each value, and sorted puts a list in order. sorted(set(["pear", "fig", "pear"])) returns ['fig', 'pear']. Numbers sort by size, so sorted([2.5, -1.0, 2.5]) returns [-1.0, 2.5, 2.5].
  • Membership across types. 2 in [1, 2.0] returns True, because 2 and 2.0 are equal in Python. "2" in [1, 2.0] returns False, because text is never equal to a number.
  • Booleans and integers. isinstance(3, int) returns True. isinstance(True, int) also returns True, because bool is a subclass of int, so True counts as 1 in arithmetic. This matters only if you check types, and the statement does not ask for that. Use it as background, not as a rule.
  • Returning a bool. A comparison already gives a bool. len([]) == 0 returns True, so a function can return the comparison directly instead of using an if.
  • Replacing matches. re.sub replaces every match with a new string. re.sub(r"[aeiou]", "*", "tea") returns t**.
  • Order of replacements. The order of two replacements can change the result. re.sub(r"b", "c", re.sub(r"a", "bb", "a")) returns 'cc', because the first replacement creates new b letters that the second one changes. Swapping the order gives 'bb'.
  • Empty input. re.findall(r"\d+", "") returns [], and "".split() returns []. Empty text should give an empty result, not an error.

The rules people miss

Each row below is a rule taken from the statement. The last column is an assert line you can write yourself. It checks the rule against the statement's own wording, so the answer is clear.

A method that works for every graded lab

  1. Read the starter file. Note the four function names, their signatures, and any helper code you are told to keep.
  2. Write the statement's examples as assert lines before you write any solution code. Use the examples in the statement, including the two shown above. At this point they will fail, which is expected.
  3. Add your own assert lines for every row of the rules table. Make each one check a single rule, so that a failure tells you which rule broke.
  4. Implement one function at a time. After each function, run only the asserts that belong to it. Do not start the next function while one of its asserts fails.
  5. Check the types last. Numbers must be floats, is_grounded must return a bool, and redact_pii must return a string.
  6. Run the visible tests. Read any failure as a rule you have not met yet, not as bad luck.
  7. Submit once, when every assert and every visible test passes. Do not use submissions to test guesses, because the score comes from what you submit.

Worked twin problem

The problem below is a different domain, a library loan desk, but it needs the same skills: finding patterns in text, sets, a sorted unique result, a bool, and replacing matches.

Scenario. A library prints an overdue notice that lists book barcodes and fines. Before the notice is printed, the desk must find the barcodes the notice names that are not on the loan list, and hide the fine amounts from the printed copy.

Implement four module-level functions, using only the standard library.

  • barcodes_in(text: str) -> list[str] returns every barcode in the text, in order of appearance. A barcode is the letters LIB followed by exactly six digits, as a whole word. A repeated barcode is returned each time it appears.
  • missing_barcodes(notice: str, loans: list) -> list[str] returns the sorted unique barcodes that appear in the notice and are not in loans.
  • all_on_loan(notice: str, loans: list) -> bool returns True if missing_barcodes gives an empty list, and False otherwise.
  • mask_fines(text: str) -> str replaces every dollar amount, such as $3 or $12.50, with [AMOUNT]. A dollar amount is a dollar sign, one or more digits, and optionally a dot followed by exactly two digits.

Example: barcodes_in("Items LIB004521 and LIB000007.") returns ['LIB004521', 'LIB000007'], and mask_fines("Fine $12.50 for one day.") returns 'Fine [AMOUNT] for one day.'

The solution and its checks:

import re

BARCODE_RE = re.compile(r"\bLIB\d{6}\b")
AMOUNT_RE = re.compile(r"\$\d+(?:\.\d{2})?")


def barcodes_in(text):
    return BARCODE_RE.findall(text)


def missing_barcodes(notice, loans):
    on_loan = set(loans)
    found = set(barcodes_in(notice))
    return sorted(code for code in found if code not in on_loan)


def all_on_loan(notice, loans):
    return missing_barcodes(notice, loans) == []


def mask_fines(text):
    return AMOUNT_RE.sub("[AMOUNT]", text)


assert barcodes_in("Items LIB004521 and LIB000007.") == ["LIB004521", "LIB000007"]
assert barcodes_in("LIB004521 then LIB004521") == ["LIB004521", "LIB004521"]
assert barcodes_in("LIB12345 is too short") == []
assert barcodes_in("LIB0045210 is too long") == []
assert barcodes_in("") == []
assert missing_barcodes("LIB900001 LIB100002 LIB900001", ["LIB100002"]) == ["LIB900001"]
assert missing_barcodes("LIB900001 LIB100002", []) == ["LIB100002", "LIB900001"]
assert missing_barcodes("no codes", []) == []
loans = ["LIB000007"]
missing_barcodes("LIB000007 LIB000008", loans)
assert loans == ["LIB000007"]
assert all_on_loan("LIB000007 is due", ["LIB000007"]) is True
assert all_on_loan("LIB000007 is due", []) is False
assert all_on_loan("no codes here", []) is True
assert mask_fines("Fine $12.50 and $3 today.") == "Fine [AMOUNT] and [AMOUNT] today."
assert mask_fines("no money") == "no money"
assert mask_fines("$100.00") == "[AMOUNT]"

Line by line:

  • import re loads the regular-expression module. It is the only module the solution uses.
  • BARCODE_RE = re.compile(r"\bLIB\d{6}\b") builds the pattern once. LIB matches those letters. \d{6} matches exactly six digits. The \b on each side is a word boundary, so the match cannot start or end inside a longer run of letters or digits. That is why LIB0045210 is rejected.
  • AMOUNT_RE = re.compile(r"\$\d+(?:\.\d{2})?") matches a dollar sign, one or more digits, and an optional dot with exactly two digits. The backslash makes the dollar sign a literal character, because a bare $ means the end of the text in a pattern.
  • barcodes_in returns BARCODE_RE.findall(text). The result is a list of strings, in order, with repeats kept. Empty text gives an empty list.
  • missing_barcodes first builds on_loan as a set, so each membership test is quick. found holds the barcodes from the notice with repeats removed. The return line keeps the codes not on loan and sorts them. Strings sort character by character, which is why LIB100002 comes before LIB900001. The loans list is only read, never changed.
  • all_on_loan compares the missing list with an empty list. The comparison already gives True or False, so the function returns a bool.
  • mask_fines calls AMOUNT_RE.sub, which replaces each match with [AMOUNT]. Text with no dollar amount comes back unchanged.
  • The assert lines are the tests. Each one checks a single rule. They pass silently when the code is correct.

The trickiest function is missing_barcodes, because it combines a set, a filter and a sort. The trace below follows the same idea on a short list. It uses split() to keep the example small, while the real function uses barcodes_in.

Your turn

Scenario. A bakery's till totals each order and lists its cheapest items. This is a new problem, so write the two functions yourself.

  • order_total(prices: list) -> float returns the sum of the prices, rounded to two decimal places at the end. An empty list gives 0.0.
  • cheapest(menu: dict, n: int) -> list[str] returns the names of the n cheapest items, cheapest first. Items with the same price are listed in alphabetical order. If n is larger than the menu, return every name. The menu must not change.

Make these asserts pass:

assert order_total([]) == 0.0
assert order_total([1.10, 2.20]) == 3.3
assert order_total([0.1, 0.2]) == 0.3
assert cheapest({"bun": 2.0, "tart": 1.5, "cake": 1.5}, 2) == ["cake", "tart"]
assert cheapest({"bun": 2.0}, 5) == ["bun"]
assert cheapest({"bun": 2.0, "tart": 1.5}, 0) == []
menu = {"bun": 2.0}
cheapest(menu, 1)
assert menu == {"bun": 2.0}
Show a solution

The solution sums first and rounds once, at the end. It sorts the names by a key that holds the price and then the name, so ties fall back to alphabetical order. Slicing with [:n] gives the first n names, and a slice larger than the list returns all of them.

def order_total(prices):
    return round(float(sum(prices)), 2)


def cheapest(menu, n):
    names = sorted(menu, key=lambda name: (menu[name], name))
    return names[:n]


assert order_total([]) == 0.0
assert order_total([1.10, 2.20]) == 3.3
assert order_total([0.1, 0.2]) == 0.3
assert cheapest({"bun": 2.0, "tart": 1.5, "cake": 1.5}, 2) == ["cake", "tart"]
assert cheapest({"bun": 2.0}, 5) == ["bun"]
assert cheapest({"bun": 2.0, "tart": 1.5}, 0) == []
menu = {"bun": 2.0}
cheapest(menu, 1)
assert menu == {"bun": 2.0}

Before you press Submit

  • Each of the four names is spelled exactly as in the starter file, and no name is renamed or moved.
  • Every function returns the type the statement asks for: a list of floats, a bool, or a string.
  • extract_numbers keeps repeated numbers and returns them in the order they appear.
  • unsupported_numbers returns sorted values, each once, and compares numbers rather than text.
  • is_grounded returns True or False, never a list and never 0 or 1.
  • redact_pii replaces emails before it replaces phone numbers, and it leaves other text alone.

  • Every assert you wrote from the rules table passes.
  • Run the visible tests one more time.

Say it out loud

Interviewers and viva examiners ask these questions to see whether you understand the design, not just the code. Answer in your own words.

Why is the API key read from the environment?

Model answer

The key is a secret that grants access and spending. If it is written in code, it enters Git history the moment you commit, and anyone with the repository can use it. Reading it from an environment variable keeps it out of the repository, and the cloud secret manager supplies it at run time. The code also refuses to start without it, and prints only a masked prefix.

What happens if the model returns invalid JSON?

Model answer

The code strips any Markdown code fences and tries to parse the text. If parsing fails, or a key is missing, it retries once with a stricter instruction to return valid JSON only. If the retry also fails, the endpoint returns a template bulletin built from the stats, with source set to template. The service never breaks, and the caller can see that the fallback was used.

How do you know a bulletin is grounded?

Model answer

Grounding is proved by code, not by reading the text or by the temperature setting. The stats are calculated in pandas and passed in, so the model is not asked to compute anything. A checker builds the set of allowed numbers from the stats and the date, extracts every number from the bulletin, and fails it if any number is not in the set. A failed bulletin is replaced by the template. The checker runs as an offline test, so the same check runs in continuous integration.

How do you defend against prompt injection?

Model answer

Prompt injection is text that tries to change the model's instructions. The defence is to keep untrusted text out of the prompt. The endpoint accepts only a validated day and ward, and returns 422 for anything else. The model's output is also checked before display, and a short list of banned phrases adds a second layer. I would not rely on the blocklist alone, because an attacker can rephrase.

Why did the team not use retrieval-augmented generation?

Model answer

RAG fetches relevant documents and gives them to the model, which helps when the answer depends on a large body of text. Here the input is a small stats dictionary that is already computed and structured. Retrieval would add a search step, an index and more ways to fail, without making the numbers any more correct. The number checker is what provides grounding, and it works on the stats directly.
