The idea in one minute

Renting a cloud server is like booking a lab bench by the hour. You choose the building (a region), you pay for the time you use, and you can give the bench back when you finish. IAM is the lab's key-card system. Every person and every program gets a card, and each card opens only the doors its job needs.

Today you lock down a new AWS account. You set up a safe admin identity, create a restricted identity for the CityPulse pipeline, prove that it can write to two folders and nothing else, and set a spending alarm so a forgotten resource does not become a surprise bill.

Starting from zero

Computer and server. A computer is a machine that runs programs. A server is a computer that waits for requests from other programs and answers them. CityPulse will eventually have a server that receives air-quality readings.

Cloud. "The cloud" means computers that belong to a provider, kept in data centres, which you rent over the internet. You pay for the hours or the storage you use, and you can start or stop them.

Terminal and command. The terminal is a text window. You type a command and press Enter, and the program prints its reply. In aws sts get-caller-identity, the program is aws. The words after it, sts and get-caller-identity, are arguments that say which service and which question.

Flag. A flag is an option that changes how a command behaves. Flags start with one dash (-r) or two (--output). A flag often takes a value: --output text means "print plain text".

Variable and export. A variable stores a value under a name. NAME=asha stores the text asha under the name NAME, and $NAME reads it back. Putting export in front makes the variable visible to programs started from the same terminal. That is how the aws program learns which profile to use.

File, folder and path. A file holds data. A folder (directory) holds files and other folders. A path names a location. infra/iam/asha/pipeline-policy.json is the file pipeline-policy.json inside asha, inside iam, inside infra.

JSON. JSON is a text format for structured data. Curly braces { } hold named values, square brackets [ ] hold lists, and each name is followed by a colon. For example, {"Effect": "Allow"} says that Effect has the value Allow. AWS policies and most CLI output use JSON.

API, SDK and CLI. An API is a defined way for one program to ask another to do something. Each AWS action, such as storing a file, is an API call. The CLI (command-line interface) is the aws program, which makes those calls for you when you type commands. An SDK is a library that makes the same calls from code. boto3 is the AWS SDK for Python.

Identity. An identity is who is making a call. A user is a long-lived identity for a person or a script. A role is an identity that someone or something borrows for a while.

Policy, permission, action and resource. A policy is a JSON document that lists permissions. A permission says that one identity may perform one action on one resource. An action is an operation written as a service and a name, such as s3:PutObject (put a file into S3). A resource is the thing acted on.

ARN. An ARN (Amazon Resource Name) is the unique address of an AWS resource. arn:aws:s3:::citypulse-asha-7k2q names a bucket. The empty fields between the colons are the region and account, which bucket ARNs leave blank.

Region and availability zone. A region is a geographic area with its own data centres, such as ap-south-1 (Mumbai). An availability zone (AZ) is an isolated data centre inside a region, so a fault in one should not take down the others. A resource lives in one region, and the console shows only the region you have selected.

Bucket, object and prefix. S3 is AWS file storage. A bucket is a container with a globally unique name. An object is a stored file. An object's key is its full name inside the bucket, such as raw/readings.csv. The raw/ part is a prefix. S3 has no real folders, so a prefix only looks like one.

Access key. An access key is a pair of strings, an ID and a secret. It lets a script or the CLI sign its calls. It works like a username and password for programs, so the secret must never be shared or committed to Git.

MFA. Multi-factor authentication asks for a second proof when you sign in, usually a six-digit code from an authenticator app on your phone. It protects an account even if the password leaks.

Budget. A budget is a spending limit you set. It sends emails when spending passes a percentage of the limit. It does not stop anything by itself.

The tools

Cloud models and regions

What it is. Cloud computing rents compute, storage and services over the internet. The service models differ in how much you manage. With IaaS (infrastructure as a service) you manage virtual machines, which is EC2 in this course. With PaaS or serverless you manage only your code, which is Lambda later in the module. With SaaS you just use finished software. A useful picture: IaaS is renting an empty flat, PaaS a furnished flat, and SaaS a hotel room.

Why CityPulse uses it. CityPulse must keep running when interns' laptops are switched off. The lab machines cannot guarantee that. AWS region ap-south-1 is the closest to Bengaluru, which gives lower latency and keeps the data in India. Azure and Google Cloud are allowed only with trainer sign-off for this cohort. An on-premises server gives full control, but it has a high upfront cost, no elastic scaling, and someone must maintain the hardware.

How it works. Under the shared responsibility model, AWS secures the physical infrastructure, and you secure your identities, data and settings. On EC2 you patch the operating system yourself. On Lambda, AWS does.

Set up your admin CLI profile and look at the regions:

NAME=asha
aws configure --profile "$NAME-admin"
export AWS_PROFILE="$NAME-admin" AWS_REGION=ap-south-1
aws sts get-caller-identity --query Arn --output text
aws ec2 describe-regions --query 'Regions[].RegionName' --output text
  • NAME=asha stores your first name in a variable. Use lowercase, because the bucket names must be lowercase too.
  • aws configure --profile "$NAME-admin" asks you four questions: an access key ID, a secret access key, a default region and an output format. It saves the answers under a named profile called asha-admin. The double quotes make sure $NAME expands before the name is built.
  • export AWS_PROFILE=... AWS_REGION=... sets two variables for this terminal only. Every aws command you run afterwards uses the asha-admin profile and the ap-south-1 region.
  • aws sts get-caller-identity asks AWS who you are. --query Arn returns only the field named Arn, and --output text prints it without JSON. The expected result ends in :user/asha-admin. If it ends in :root, stop, because you are using the root account.
  • aws ec2 describe-regions lists the regions your account can use. --query 'Regions[].RegionName' keeps only the names. The output is a single line of names separated by spaces, and ap-south-1 appears among them.
Trap: Creating resources in the wrong region

The CLI and console default to other regions if you do not set one. Set AWS_REGION=ap-south-1 in every new terminal before you create anything. A resource made in us-east-1 will not appear when you look in ap-south-1.

Trap: Assuming the cloud is secure by default

AWS gives you the tools, not the protection. You must set up access rules, encryption and network settings yourself. A new account with no rules still needs a careful owner.

Trap: Leaving resources running

A forgotten virtual machine or a public storage bucket costs money every hour. Check the budget at the end of each lab and stop or delete what you no longer need.

AWS IAM (users, roles and policies)

What it is. AWS Identity and Access Management controls access to every AWS API call. A user is a long-lived identity for a person or a script. A role is an identity that is assumed temporarily, and it hands out short-lived credentials. A policy is a JSON document that allows or denies actions on resources. Every call is denied unless a policy allows it.

Why CityPulse uses it. The pipeline must run as citypulse-pipeline, not as an admin, because the client's security reviewer requires it. CloudTrail records every call by identity, so you can later find your own PutObject or AccessDenied event. The alternatives are weaker. Sharing the admin user's keys means that one leak exposes the whole account. The managed policy AmazonS3FullAccess grants every bucket and every delete, so it fails the no-wildcard rule the course uses.

How it works. A policy does nothing until it is attached to a user or a role. When that identity makes a call, IAM checks every attached policy. An explicit Deny wins. Otherwise an explicit Allow is needed. If nothing matches, the answer is Deny.

If no Allow matches, IAM answers at the second arrow with AccessDenied, and the bucket never receives the request.

Check which identity your terminal is using:

The command prints three fields. UserId is an internal ID. Account is the 12-digit account number, which is the billing and isolation boundary. Arn says that the caller is the user asha-admin in that account. Check this before every IAM change, because the wrong identity is the most common cause of confusing results.

The policy that lets the pipeline write and read two prefixes looks like this. Replace the bucket name with yours.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListOnlyPipelinePrefixes",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::citypulse-asha-7k2q",
      "Condition": {"StringLike": {"s3:prefix": ["raw/*", "clean/*"]}}
    },
    {
      "Sid": "ReadWritePipelineObjects",
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject"],
      "Resource": [
        "arn:aws:s3:::citypulse-asha-7k2q/raw/*",
        "arn:aws:s3:::citypulse-asha-7k2q/clean/*"
      ]
    }
  ]
}
  • "Version": "2012-10-17" is the fixed version string of the policy language. Copy it exactly. It is not a date you choose.
  • "Statement": [ ... ] is a list of rules. IAM reads all of them.
  • "Sid" is a label you choose, so that a reader and the error messages can name the statement. It has no effect on the decision.
  • "Effect": "Allow" says that the statement grants permission. The other possible value is Deny.
  • "Action": "s3:ListBucket" is one operation: listing the names of objects in a bucket. The first statement has one action, so it is a plain string rather than a list.
  • "Resource": "arn:aws:s3:::citypulse-asha-7k2q" is the bucket itself, with no slash and no object name. ListBucket must name the bucket, not the objects inside it.
  • "Condition" narrows the statement. StringLike means "matches a pattern with *", and s3:prefix is the prefix the caller asked to list. So the listing is allowed only for raw/... or clean/....
  • "Action": ["s3:PutObject", "s3:GetObject"] is a list of two actions. The second statement uses a list because it covers two actions on the same resources.
  • The two Resource entries end in /raw/* and /clean/*. Object actions take the bucket, then a slash, then a prefix pattern, so /* means "any object under this prefix".

The expected output of a successful check is ListBucket accepted for raw/, and a file uploaded under raw/ appearing in the listing.

Trap: ListBucket on the object pattern

Writing arn:aws:s3:::citypulse-asha-7k2q/* for s3:ListBucket never matches. ListBucket takes the bucket ARN. Object actions take the bucket ARN followed by /prefix/*.

Trap: Wildcards that are too broad

s3:* or "Resource": "*" fails the course gate. Name each action and scope each ARN.

Trap: Keys in code

Never put access keys in a Python file, a .env file or a Git commit. Keep them only in aws configure --profile.

Least privilege and MFA

What it is. Least privilege means each identity gets only the permissions its job needs. A leaked credential then has a small blast radius. Multi-factor authentication adds a second proof, an authenticator code, to sign-in. It protects the root user and human admins even if a password leaks.

Why CityPulse uses it. If the citypulse-pipeline key leaks, the attacker can only read and write two prefixes in one bucket. Root can close the account and change billing, so Y2-T16 requires root MFA and no root access keys at any time. A tested deny matrix also proves that the policy denies what it should, which the client's reviewer asked for. The alternatives are weaker. A broad policy that you plan to tighten later usually stays broad. SMS codes are better than nothing, but a SIM swap can capture them. An authenticator app is preferred.

How it works. A policy is proven only when the expected denials return AccessDenied. The course script infra/iam/test_access.sh runs six real commands as the pipeline user. Two must be allowed and four must be denied.

#!/usr/bin/env bash
set -uo pipefail
B=$1; export AWS_PROFILE=citypulse-pipeline AWS_REGION=ap-south-1
check() {
  local want=$1 out got
  shift
  if out=$("$@" 2>&1); then
    got=allow
  elif grep -qE 'AccessDenied|not authorized' <<<"$out"; then
    got=deny
  else
    got=error
  fi
  if [ "$got" = "$want" ]; then echo "PASS $want: $*"; else echo "FAIL want=$want got=$got: $*"; fi
}
echo probe > /tmp/probe.txt
check allow aws s3 cp /tmp/probe.txt "s3://$B/raw/probe.txt"
check allow aws s3 ls "s3://$B/raw/"
check deny  aws s3 cp /tmp/probe.txt "s3://$B/secret/probe.txt"
check deny  aws s3api delete-object --bucket "$B" --key raw/probe.txt
check deny  aws s3 ls
check deny  aws iam list-users
  • #!/usr/bin/env bash is the first line. It tells the system to run the file with Bash.
  • set -uo pipefail changes how Bash behaves. -u stops on an unset variable, which catches typos. -o pipefail makes a pipeline fail if any part fails. The script deliberately does not use -e, because a failing command is exactly what it wants to test.
  • B=$1 stores the first argument, the bucket name, in B. export AWS_PROFILE=citypulse-pipeline makes the script test as the pipeline user, whatever your terminal was set to.
  • check() { ... } defines a function. Everything inside the braces runs when you call check.
  • local want=$1 out got declares three variables that exist only inside the function. want is the expected result, out is the output, got is the actual result.
  • shift removes the first argument, so "$@" now holds only the command to run.
  • if out=$("$@" 2>&1); then runs the command. $(...) captures its output into out. 2>&1 sends error text into the same capture, so the error message can be read. The then branch runs if the command exited successfully.
  • grep -qE 'AccessDenied|not authorized' <<<"$out" searches the captured text for either message. -q prints nothing and sets the exit code, and -E allows the | alternative.
  • else got=error covers everything else: a typo, a missing file, a network problem. The script does not call those a deny.
  • echo "PASS $want: $*" prints the expected result and the command, which is the line you will read as evidence.
  • Each check line passes the wanted result, then the command. The first is check allow aws s3 cp ..., which uploads probe.txt under raw/.

Expected output, one line per check:

PASS allow: aws s3 cp /tmp/probe.txt s3://citypulse-asha-7k2q/raw/probe.txt
PASS allow: aws s3 ls s3://citypulse-asha-7k2q/raw/
PASS deny: aws s3 cp /tmp/probe.txt s3://citypulse-asha-7k2q/secret/probe.txt
PASS deny: aws s3api delete-object --bucket citypulse-asha-7k2q --key raw/probe.txt
PASS deny: aws s3 ls
PASS deny: aws iam list-users
Trap: Counting every error as a deny

If the script treated any failure as a deny, a typo in the bucket name would show as a PASS. The grep for AccessDenied is what keeps the matrix honest. Keep it.

Trap: Running the tests as admin

With the admin profile, every case passes, and the result proves nothing. Run aws sts get-caller-identity first. It must show user/citypulse-pipeline.

Tip: Explain the deny lines out loud

In a viva, examiners ask why a deny case matters. The answer: a policy that only shows its allows has not been tested for what it blocks.

Budgets

What it is. AWS Budgets tracks actual and forecast spending against a limit you set. It sends email alerts at thresholds you choose. It does not stop resources.

Why CityPulse uses it. Interns run virtual machines and storage on personal accounts, and a forgotten t3.micro or public traffic costs real money. Y2-T16 makes a US$5 budget, with 80% and 100% alerts, a precondition: no alarm, no cloud lab. The alternatives are less suitable. A CloudWatch billing alarm works, but it uses an older approach based on estimated charges in us-east-1. Checking Cost Explorer by hand works only if someone remembers to look.

How it works. The budget compares month-to-date spend with the limit. Billing data updates a few times a day, so the alert is a safety net, not a live meter.

ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
N80='{"NotificationType":"ACTUAL","ComparisonOperator":"GREATER_THAN","Threshold":80,"ThresholdType":"PERCENTAGE"}'
N100='{"NotificationType":"ACTUAL","ComparisonOperator":"GREATER_THAN","Threshold":100,"ThresholdType":"PERCENTAGE"}'
SUB='[{"SubscriptionType":"EMAIL","Address":"'"$ALERT_EMAIL"'"}]'
aws budgets create-budget --account-id "$ACCOUNT_ID" \
  --budget '{"BudgetName":"citypulse-monthly","BudgetLimit":{"Amount":"5","Unit":"USD"},"TimeUnit":"MONTHLY","BudgetType":"COST"}' \
  --notifications-with-subscribers "[{\"Notification\":$N80,\"Subscribers\":$SUB},{\"Notification\":$N100,\"Subscribers\":$SUB}]"
aws budgets describe-budgets --account-id "$ACCOUNT_ID" --query 'Budgets[].[BudgetName,BudgetLimit.Amount]' --output text

Before you run it, set ALERT_EMAIL to an address you read every day, for example ALERT_EMAIL=you@example.com.

  • ACCOUNT_ID=$(...) runs the command in brackets and stores its output, your 12-digit account number, in a variable.
  • N80= and N100= store JSON for two alerts. Each says: fire when the actual spend is greater than 80 per cent, or 100 per cent, of the limit.
  • SUB= stores a JSON list with one subscriber, an email address. The "'"$ALERT_EMAIL"'" pattern closes the single quotes, inserts the variable, and reopens them.
  • aws budgets create-budget creates the budget. --account-id says which account.
  • --budget is the budget definition. It names the budget citypulse-monthly, sets the limit to 5 US dollars, repeats monthly, and tracks cost.
  • --notifications-with-subscribers attaches the two alerts and their email subscriber. The backslashes at line ends continue the command on the next line. The \" sequences put literal double quotes inside the double-quoted string.
  • aws budgets describe-budgets lists the budgets. --query keeps the name and the limit, and --output text prints them on one line.

Expected output of the last line: citypulse-monthly followed by 5.0.

Trap: Believing a budget stops spending

A budget only alerts. You must stop or delete resources yourself.

Trap: The admin user cannot see billing

An IAM admin cannot see billing data until the root user turns on IAM access to billing in the account settings. If the budget page is empty for asha-admin, check that setting.

Trap: Alerts sent to an unread inbox

An alert that nobody reads is useless. Use an address you check daily, and look for any confirmation message AWS sends to it.

The worked example

The workbook builds a small role for an ingest server. The server should be able to write sensor readings into one bucket and nothing else. The sample account and names in the workbook are examples, so use your own values in the lab.

Step 1: Confirm the identity. The workbook starts with aws sts get-caller-identity, which prints a user ARN and an account number. The output confirms that the CLI acts as a user in the account where you want to build. Nothing is created yet.

Step 2: Write the trust policy. A role has two policies. The trust policy says who may assume the role. The permissions policy says what the role may do. This is the trust policy, saved as trust.json:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "ec2.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}
  • "Principal": {"Service": "ec2.amazonaws.com"} names the caller allowed to assume the role. Here it is the EC2 service, which runs the ingest job. No human and no key is named.
  • "Action": "sts:AssumeRole" is the one action the trust policy grants: borrowing the role's temporary credentials.
  • The rest is the same structure you met in the policy above: a version, a list of statements, and an effect.

Step 3: Create the role. The workbook creates the role with the trust policy:

aws iam create-role --role-name citypulse-ingest --assume-role-policy-document file://trust.json
  • aws iam create-role creates a role. --role-name gives it a name.
  • --assume-role-policy-document file://trust.json reads the trust policy from the file. The file:// prefix tells the CLI to read the value from a file rather than treat the text as the policy itself.

The output is JSON with "Arn": "arn:aws:iam::<account>:role/citypulse-ingest". The role exists but has no permissions yet. That is intentional. You add permissions deliberately in the next step, instead of starting broad and trimming later.

Step 4: Write the scoped policy. The permissions policy, saved as citypulse-ingest-policy.json, allows exactly one action on one bucket:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:PutObject"],
    "Resource": "arn:aws:s3:::citypulse-readings/*"
  }]
}
  • The action is a list with one entry, s3:PutObject, which writes an object. Reading and deleting are not granted.
  • The resource is the bucket citypulse-readings, followed by /*, which means every object in it. This is an object action, so the pattern has the /* suffix.

The workbook checks the file with a short Python script, validate_policy.py. It asserts that the action list is exactly ["s3:PutObject"] and that there is no * in it. Its output looks like this:

Each line prints one part of the statement. effect : Allow confirms the statement grants access. The action line shows exactly one action. The resource line shows the bucket and object pattern. The last line appears only when every assert in the script passed. If an assert fails, Python stops with an error message naming the failed check.

Step 5: Attach and read back. The policy is attached to the role as an inline policy, which means it belongs only to this role:

aws iam put-role-policy --role-name citypulse-ingest --policy-name write-readings --policy-document file://citypulse-ingest-policy.json
aws iam get-role-policy --role-name citypulse-ingest --policy-name write-readings --query PolicyDocument.Statement[0].Action
  • put-role-policy attaches the policy. --policy-name write-readings names it inside the role.
  • get-role-policy reads it back. --query PolicyDocument.Statement[0].Action returns the action of the first statement, so you can confirm what was saved.

The workbook prints the action in its listing as ["s3:PutObject"]. The workbook writes -query with one dash. Use two dashes, --query, as in every other command.

Step 6: Simulate the decisions. The simulator tests what a role could do without touching real data:

aws iam simulate-principal-policy --policy-source-arn arn:aws:iam::<account>:role/citypulse-ingest --action-names s3:PutObject s3:DeleteObject --resource-arns arn:aws:s3:::citypulse-readings/jan.csv --query 'EvaluationResults[].[EvalActionName,EvalDecision]'
  • --policy-source-arn names the role to test.
  • --action-names lists the actions to test. --resource-arns names the object they would act on.
  • --query prints each action with its decision.

The expected output is s3:PutObject with allowed, and s3:DeleteObject with implicitDeny. implicitDeny means that no statement allows the action, so the default applies. The role can write readings but cannot delete them.

Step 7: Get the ARN for the server. Finally, the workbook reads the role ARN:

aws iam get-role --role-name citypulse-ingest --query Role.Arn --output text

The output is the ARN alone, arn:aws:iam::<account>:role/citypulse-ingest. An EC2 server does not take a role directly. You wrap the role in an instance profile, and the server then receives temporary credentials at boot. No access key is stored on disk.

Trap: Attaching the role to a server directly

A role is not attached to an EC2 instance as it is. It goes into an instance profile, which is a container for the role. Look up instance profiles in the EC2 course material before you set one up.

The hands-on lab, step by step

This lab builds the citypulse-pipeline identity. It uses a group, which is how teams normally share permissions. Your bucket is citypulse-asha-7k2q in the examples. Replace asha and the random suffix with your own values, and use the same name everywhere.

Step 1: Confirm your identity and region

What you do. Set your profile and region, then ask AWS who you are.

NAME=asha
export AWS_PROFILE="$NAME-admin" AWS_REGION=ap-south-1
aws sts get-caller-identity --query Arn --output text
aws configure get region

What you should see. The first line ends in :user/asha-admin. The second line prints ap-south-1.

How you know it worked. The ARN is your admin user, not :root. Nothing else in this lab should run with root.

Step 2: Create a group to hold the permissions

What you do. Create the group. Permissions go to the group, and users join it later.

aws iam create-group --group-name citypulse-pipeline-group

IAM roles

What it is. A role is an identity with no password and no permanent key of its own. Another identity, or an AWS service, assumes the role, which means it asks AWS for temporary credentials that expire after a set time. The response contains an access key ID, a secret, a session token and an expiry time. A role has two policies. The trust policy says who may assume it. The permissions policy says what the role may do once it has been assumed. The difference is easiest to see in a trust policy:

{"Effect": "Allow", "Principal": {"Service": "ec2.amazonaws.com"}, "Action": "sts:AssumeRole"}

This statement lets the EC2 service borrow the role. It says nothing about S3. A separate permissions policy, such as one allowing s3:PutObject on one bucket, decides what the borrowed credentials can do. If the trust statement were removed, nobody could assume the role, even though its permissions would still exist.

How it shows up in a case study. CityPulse's ingest job runs on a server in ap-south-1 and writes sensor readings to the citypulse-readings bucket. A student first stored an access key in a file on the server. A reviewer asks for that file to go. The right design is a role whose trust policy names the EC2 service and whose permissions policy allows only s3:PutObject on the readings bucket. The role is attached to the server through an instance profile, so the server receives temporary credentials at boot and no key sits on disk. Both designs can write readings, so the question is which one leaves no long-lived secret that could leak. Only the role design removes that secret.

Trap: Rotating a key instead of using a role

Rotating a long-lived key every month still leaves a secret on the server for the whole month. A role removes the stored secret altogether.

Least privilege

What it is. Least privilege means that each identity gets only the actions and resources its job calls, and nothing wider. You start from the real calls the job makes, grant exactly those, and then test that other calls are denied. A policy that works but is broad still counts as a failure. The table compares two ways of letting a job read summaries.

Policy                                        What a leaked key can do
s3:GetObject on citypulse-raw/summaries/*     Read the summaries, nothing else
s3:* on *                                     Read, change and delete anything in every bucket

Both policies let the job read its summaries, so both look correct on a normal day. Least privilege is judged by what a leaked credential could do. The second policy fails that test, which is why reviewers look for wildcards in actions and resources before they approve anything.

How it shows up in a case study. A CityPulse reporting service reads daily summaries from the summaries/ folder of the citypulse-raw bucket. During development, a teammate attaches the managed policy AmazonS3FullAccess so that nothing blocks the work. The project's rule is that the policy must name each action and scope each resource, and that the denied cases must be tested. The right fix is a policy with s3:GetObject on the summaries prefix, followed by a test that a write is denied. Development is not an exception. A key used in development can leak too, and the broad policy usually stays in place after the demo ends.

Trap: Keeping the broad policy for the demo

A broad policy that is meant to be tightened later usually stays broad. Write the narrow policy first and test it.

Root account security

What it is. The root user is the identity created together with the AWS account. It has unrestricted access to everything in the account, including billing and closing the account itself. IAM policies cannot limit it. The protections are a multi-factor authentication (MFA) device on the root user, no root access keys, and daily work done by an IAM admin user instead. MFA asks for a code from an authenticator app as a second proof when you sign in. An access key is a long-lived secret that a script can use without any password prompt, so a root access key is the most dangerous kind of key, because nothing can restrict it. The IAM credential report lists every identity, including root, with its MFA and access key status. Checking that report is a quick way to confirm the protections are in place.

How it shows up in a case study. A new CityPulse account owner wants a deployment script to run without any prompt. A teammate suggests creating a root access key for the script, because it is the quickest option. The safe design is different. Root keeps MFA and has no access keys. The script runs as an IAM admin user with MFA for setup work, and the pipeline uses a role or a scoped user whose policy names only the calls it needs. The reasoning is that a leaked root key cannot be restricted or contained by any policy, so it must never exist, however convenient it looks on the day it is created.

Trap: Creating a root key and limiting it with a policy

IAM policies do not apply to the root user, so a policy cannot limit a root key. Do not create one.

Regions and availability zones

What it is. A region is a geographic area with its own AWS data centres, such as ap-south-1 in Mumbai. An availability zone (AZ) is an isolated data centre inside one region, with a letter after the region name, such as ap-south-1a. Most resources, such as virtual servers and storage volumes, are created in one region and are listed only when that region is selected in the console or the CLI. IAM is different. Users and roles are global and are not tied to a region. You can list the zones of a region with this command:

aws ec2 describe-availability-zones --region ap-south-1 --query 'AvailabilityZones[].ZoneName' --output text

The output is one line of zone names, such as ap-south-1a. The command shows where a region's zones are. It does not show where your resources are, which is why the region selector matters.

How it shows up in a case study. A team's shared test server was created in ap-south-1. A teammate has the console set to a different region and reports that the server has disappeared. The server has not been deleted, because the console lists only the resources of the selected region. The teammate should first check the region selector and then look at the list in ap-south-1. Changing the availability zone does not help, because an AZ is a place inside one region and cannot reveal a server created in another. A design decision follows from the same fact. If the team wants the data to stay in India, it must create the resources in ap-south-1 and confirm the region before every create.

Trap: Blaming the availability zone

An AZ is one data centre inside a region. A missing resource is almost always a region selector problem, not an AZ problem.

Execution roles

What it is. An execution role is the role a service assumes so that it can act on your behalf when your code runs. A Lambda function, for example, runs with an execution role. Its trust policy names the service, and its permissions policy lists what the function needs, such as writing logs and reading one object. The trust statement for a Lambda function looks like this:

{"Effect": "Allow", "Principal": {"Service": "lambda.amazonaws.com"}, "Action": "sts:AssumeRole"}

The function borrows the role each time it runs. The person who deployed the function does not pass their own rights to it. Giving the role the deployer's admin rights is the easiest fix when a permission error appears, and it is also the widest permission on offer. Each new error should be answered by adding the one action and the one resource that the function really calls.

How it shows up in a case study. A Lambda function writes logs and reads one object from citypulse-raw. Its execution role was created with the deployer's admin rights, because that removed every error during testing. A reviewer points out that the function can now delete any bucket in the account. The fix is to replace the admin rights with a policy that names the log actions and the one object's ARN. The function is then tested with a denied case, such as a delete. The reasoning is that the function's identity is the role, so the policy on the role is the only thing that decides what the function can do.

Trap: Giving the execution role the deployer's rights

The function then inherits everything the deployer can do. The execution role should hold only what the function calls.

Policy evaluation

What it is. When an identity makes a request, IAM collects every policy attached to that identity and applies three rules in order. First, an explicit Deny that matches wins at once. Second, an explicit Allow that matches is needed. Third, if neither exists, the request is denied by default. The order of the statements inside the policies does not matter, and neither does how specific a statement looks. The table shows three requests against the same policy.

Attached statement                               Request                              Result
Allow s3:GetObject on reports/*                  s3:GetObject reports/q1.csv          Allowed
Allow s3:GetObject on reports/*                  s3:GetObject reports/secret/a.csv    Allowed
Deny s3:GetObject on reports/secret/*            s3:GetObject reports/secret/a.csv    Denied, the Deny wins
Allow s3:GetObject on reports/* only             s3:PutObject reports/q1.csv          Denied by default

The last row is the default. Nothing forbids the write, but nothing allows it either, so IAM answers Deny.

How it shows up in a case study. A CityPulse user has an Allow for s3:DeleteObject on the reports bucket, which was added by one team. A second policy, attached by the security team, has an explicit Deny for s3:DeleteObject on reports/archive/*. The user deletes an archive file and is refused. A student might blame the order of the policies or say that the more specific rule was ignored. Neither is the reason. The explicit Deny matches, and an explicit Deny wins over any Allow. The fix is a policy change that the security team agrees, not a change to the order of the statements.

Trap: Reading the first matching statement as the answer

IAM does not stop at the first match. It checks every attached policy for a matching Deny before it looks for an Allow.

Cross-account access

What it is. Cross-account access lets an identity in one AWS account use resources in another. The owning account creates a role whose trust policy names the other account, and the role carries the permissions the outsider needs. The other account then gives its own identity permission to call sts:AssumeRole on that role. Both sides must agree. The caller assumes the role, receives temporary credentials, and uses them to reach the resource. The trust statement in the owning account looks like this:

{"Effect": "Allow", "Principal": {"AWS": "arn:aws:iam::111122223333:root"}, "Action": "sts:AssumeRole"}

Here :root means the whole account 111122223333, which is the trusted account, not its root user. The trusted account still has to allow its own identity to make the call. Without that second step, the caller is refused even though the trust statement is correct.

How it shows up in a case study. A partner's application in account C must read a report bucket owned by CityPulse in account A. The owner creates a role in account A that trusts account C and can read the bucket. The partner's application still gets AccessDenied when it tries to assume the role. The reviewer checks the trust policy first and finds it correct. The missing step is on the caller side, where the identity in account C needs an Allow for sts:AssumeRole on that role's ARN. The reasoning is that each account controls only its own side, so a correct trust policy cannot compensate for a missing caller permission.

Trap: Configuring only one side

A correct trust policy alone does nothing if the caller has no permission to assume the role. Both accounts must be set.

IAM groups

What it is. A group is a collection of users that holds policies. Each member inherits every policy attached to the group. You attach a read-only policy to the group once, and when a person joins or changes team, you add or remove them from the group. A group is not an identity. It cannot sign in, make calls or be assumed, so it cannot appear as the principal in a trust policy. These commands show the usual pattern:

aws iam add-user-to-group --group-name analysts --user-name asha
aws iam list-groups-for-user --user-name asha --query 'Groups[].GroupName' --output text

The second command prints analysts, which confirms the membership. A policy attached directly to the user is a separate thing, and it stays in place when the user leaves the group.

How it shows up in a case study. Six analysts need the same read-only access to a bucket. The team first attaches the policy to each analyst separately, which works but means six edits for every change. Next quarter, two analysts move teams and one new analyst joins, so the policy must be checked for three people. A group solves this: one policy on the group, and membership changes only. A later problem appears when a user is removed from the group and can still read the bucket. The cause is a policy attached directly to the user, which removing group membership does not change.

Trap: Attaching the policy to each user

It works on the day you set it up, but every future change must be repeated for each person. Attach it to a group instead.

Policy conditions

What it is. A Condition block narrows an Allow, or a Deny, using a context key. A context key is a fact about the request, such as the prefix a listing asks for, the IP address of the caller or the region a request targets. An operator compares the key with a value. StringLike compares text and allows * in the value. If a key is missing from the request, a positive operator such as StringLike does not match, so an Allow with that condition does not apply. Here is a statement that allows listing only under logs/:

{"Effect": "Allow", "Action": "s3:ListBucket", "Resource": "arn:aws:s3:::citypulse-raw", "Condition": {"StringLike": {"s3:prefix": "logs/*"}}}

A listing request with a prefix of logs/2026/ is allowed, because that prefix matches logs/*. A listing request with no prefix at all is not allowed, because there is no prefix to compare.

How it shows up in a case study. A monitoring tool lists the whole citypulse-raw bucket with no prefix and is refused. The team had written a StringLike condition on s3:prefix for logs/*, and they assumed the condition was generous. The reasoning is that the condition checks a value the request did not supply. The tool must send a prefix, such as logs/, and the team should decide whether listing the bucket root is allowed at all. With a positive operator such as StringLike, a condition whose key is missing does not become a match.

Trap: Expecting a missing key to match

A listing with no prefix has no s3:prefix value. The condition does not match, so the Allow does not apply.

Permissions boundaries

What it is. A permissions boundary is a managed policy attached to a user or role as its maximum. The effective permissions are the overlap between the identity's own policies and the boundary. A boundary grants nothing by itself, and it can only reduce what an identity can do. The overlap works like this:

Identity policy allows:   s3:GetObject, s3:PutObject
Boundary allows:          s3:GetObject
Effective permissions:    s3:GetObject

The identity can read but not write, even though its own policy names the write. Developers use boundaries to delegate safely. A team lead lets a developer create roles, and a boundary limits every role the developer creates, so a later broad policy cannot widen them past the boundary.

How it shows up in a case study. A developer is allowed to create roles for the pipeline, but the team lead wants each role to stay within S3 actions. A tempting plan is to add an explicit Allow for s3:* to each new role, which is the opposite of what the team needs. The team sets a permissions boundary that allows only S3 actions and applies it to the roles the developer creates. The reasoning is that the boundary sets a ceiling. A policy attached later cannot exceed that ceiling, because the effective permissions are the overlap.

Trap: Thinking a boundary opens access

A boundary never adds a permission. If an identity has no identity policy, the boundary alone leaves it with nothing.

The task in plain words

The scenario. The CityPulse data-lake team protects the citypulse-raw S3 bucket with IAM-style policies. For each API request, your code must decide whether the request is permitted. A request has an action, such as s3:PutObject, and a resource, such as the ARN of one object. A policy is a list of statements. Each statement has an effect, which is either "Allow" or "Deny", an action pattern and a resource pattern.

Your task. You write three module-level functions. The starter file already contains their names, and it imports fnmatch above them. Keep the names and the parameters exactly as they are.

  • _match(pattern, value) returns bool. It returns True when the wildcard pattern matches value. Use fnmatch.fnmatch, as the statement says, so that * matches any run of characters and a prefix wildcard such as s3:Get* matches s3:GetObject.
  • statement_matches(statement, request) returns bool. It returns True when the statement's action pattern and its resource pattern both match the request's action and resource.
  • evaluate_policy(statements, request) returns the string "Allow" or the string "Deny". It applies the AWS precedence rules, which are listed below.

Every rule in the statement, in plain English:

  • _match returns True when the pattern matches the value, and False otherwise.
  • A statement matches a request only when its action pattern matches the request's action and its resource pattern matches the request's resource. Both must match. A matching action with a non-matching resource does not match.
  • An explicit Deny that matches always wins. If any matching statement has the effect "Deny", the answer is "Deny", whatever the other statements say and wherever they sit in the list.
  • If no matching Deny exists, the answer is "Allow" only when at least one matching Allow exists.
  • If neither exists, the answer is the implicit "Deny". This includes the case where the list of statements is empty.
  • The answer is exactly one of the two strings, "Allow" or "Deny".
  • The statement's example shows action and resource as single pattern strings. It does not say whether a real statement may hold a list of patterns, so the lab probably does not use lists. If you are unsure, ask your trainer. Also, fnmatch treats ? (one character) and [abc] (one of these characters) as special, as well as *. The statement only shows *, but fnmatch.fnmatch handles all of them for you, so do not write your own matcher.
  • The statement gives one example. It has an Allow for s3:* on * and a Deny for s3:DeleteObject on *. A delete request on an object in citypulse-raw returns "Deny", because the Deny matches and wins.

What each function needs

Each idea below is taught with a small example that has nothing to do with the lab's data. Work out how each one maps to the three functions, but do not assemble these examples into the lab's functions.

Wildcard matching with fnmatch.fnmatch. The fnmatch module compares a name with a pattern in which * means any run of characters, including none.

import fnmatch

print(fnmatch.fnmatch("photos/cat.jpg", "photos/*"))
print(fnmatch.fnmatch("photos/cat.png", "photos/*.jpg"))

The first line prints True, because photos/cat.jpg starts with photos/. The second prints False, because the file ends in .png. The function also treats case the way the operating system does. On Windows it ignores case, so fnmatch.fnmatch("Cat.JPG", "*.jpg") returns True there. On most Linux systems the same call returns False. Test the case you care about, and do not assume either behaviour.

A real bool from a comparison. A bool has two values, True and False. In Python, bool is a subclass of int, so True also counts as the integer 1 in some checks.

print(3 > 2)
print(isinstance(True, int))
print(isinstance(2, bool))
print((3 > 2) is True)

The output is True, True, False and True. The first line returns a real bool from a comparison. The second line is True because bool is a kind of int. The third is False, because the integer 2 is not a bool. The fourth needs its brackets: without them, 3 > 2 is True is read as a chained comparison and prints False. Use is True and is False in your own checks, so that a value such as 1 cannot pass as True by accident.

Reading a dictionary safely. A dictionary maps keys to values. Square brackets raise KeyError when a key is missing, while get returns a default instead.

ticket = {"zone": "north"}
print(ticket.get("zone", "unknown"))
print(ticket.get("seat", "unknown"))
print(ticket["zone"])

The output is north, unknown and north. The second line does not crash, because get supplies the default. If you wrote ticket["seat"] instead, Python would stop with a KeyError. Use get whenever a key might be absent, and use brackets when a missing key is a real error.

Using and and or on booleans. and gives True only when both sides are True. or gives True when at least one side is.

room_open = True
has_key = False
print(room_open and has_key)
print(room_open or has_key)

The output is False, then True. A rule that needs two conditions to hold uses and. A rule that needs either one uses or.

Checking a list with a loop and any. A loop visits each item. any returns True when at least one item in a sequence is true, and it stops as soon as it finds one.

readings = [4, 9, 12, 7]
print(any(value > 10 for value in readings))

for value in readings:
    if value > 10:
        print("first large reading:", value)
        break

The first line prints True. The loop prints first large reading: 12, then break leaves the loop at once, so the 7 after it is never looked at. A return inside a function does the same thing for the whole function, which lets you stop as soon as the answer is known.

Exact string comparison and picking a string. Python compares strings letter by letter, and case matters. A conditional expression chooses one of two values.

level = "Warn"
print(level == "warn")
print("Alert" if 90 > 80 else "Calm")

The output is False, because "Warn" and "warn" differ, and then Alert. A result that must be exactly one of two words should be built with an expression like the second line, so that its spelling is fixed.

How the ideas map to the lab. _match needs the first two ideas, because it must return a real bool from a wildcard test. statement_matches needs dictionary reading and and, because both the action and the resource must match. evaluate_policy needs a loop with an early return, exact string results, and a default. Check each idea against the statement's rules before you combine them.

The problem below is a twin. It is set in a library, not in AWS, and it uses a different precedence rule, so it is not a copy of the lab. It still needs wildcard matching, dictionary access, a loop with an early return and whole-number arithmetic.

Library loan periods. A library lends each book category for a set number of days. You receive rules, a list of dictionaries. Each dictionary has a match key, which is a wildcard pattern for the category, and a days key, which is the loan length. The rules are checked in list order, and the first rule whose pattern matches the category decides the loan. If no rule matches, the loan lasts 14 days. Write loan_days(rules, category), which returns an int.

The library also charges a late fee. Write late_fee(days_late, pence_per_day), which returns the fee as a whole number of pence. A book that is not late has a fee of 0, including a negative number of days. Otherwise the fee is the number of late days multiplied by the daily rate.

import fnmatch


def loan_days(rules, category):
    for rule in rules:
        if fnmatch.fnmatch(category, rule["match"]):
            return rule["days"]
    return 14


def late_fee(days_late, pence_per_day):
    if days_late <= 0:
        return 0
    return days_late * pence_per_day


rules = [
    {"match": "reference/*", "days": 3},
    {"match": "fiction/*", "days": 21},
    {"match": "fiction/crime", "days": 7},
]
assert loan_days(rules, "reference/atlas") == 3
assert loan_days(rules, "fiction/crime") == 21
assert loan_days(rules, "music") == 14
assert loan_days([], "music") == 14
assert loan_days([{"match": "fiction/crime", "days": 7}], "fiction/crime") == 7
assert late_fee(4, 20) == 80
assert late_fee(0, 20) == 0
assert late_fee(-3, 20) == 0
assert type(late_fee(4, 20)) is int
print("all checks passed")

  • import fnmatch loads the standard-library module that compares a name with a wildcard pattern.
  • def loan_days(rules, category): defines the function with two inputs.

  • return 14 runs only when the loop finishes without a return. That means no rule matched, so the default applies.
  • def late_fee(days_late, pence_per_day): defines the second function.
  • if days_late <= 0: and return 0 cover a book that is not late, including negative input. The fee is 0 in both cases.
  • return days_late * pence_per_day multiplies two whole numbers, so the result is a whole number of pence.

  • The last print runs only when every assert has passed. Its expected output is all checks passed.

import statistics
from collections import Counter


def trip_summary(trips):
    if not trips:
        return {"count": 0, "total_km": 0.0, "median_minutes": None}
    total = sum(trip["km"] for trip in trips)
    minutes = [trip["minutes"] for trip in trips]
    return {
        "count": len(trips),
        "total_km": round(total, 1),
        "median_minutes": statistics.median(minutes),
    }


def busiest_bikes(trips, n):
    counts = Counter(trip["bike"] for trip in trips)
    ranked = sorted(counts, key=lambda bike: (-counts[bike], bike))
    return ranked[:n]

What is the difference between a user, a group and a role?

A user is a long-lived identity for a person or a script, with its own credentials. A group is a container for users, and it holds policies that its members inherit. A role is an identity that is assumed for a time, and it hands out temporary credentials. The difference matters because a role does not carry a permanent secret.
