How the board works:

  • A ticket moves Backlog, To Do, In Progress, Review, Done. Only a trainer can move it to Done, after running its test cases, and gives it a gate score from 0 to 3.
  • Every ticket is judged from commit evidence: your commits, pull requests and reviews in the squad repository. Work done on someone else's laptop does not count for you.
  • Each ticket has a points value (the "pts" column). Defence tickets (marked D01, D02 and so on) are where you present and answer questions.
  • Your viva scores acceptance criteria met, technical depth, contribution and ownership, and understanding, each 0 to 5. The final capstone grade shown on the platform is 60% your own contribution and 40% your team's.

Y2-T13 · Design star schema and idempotent load.py; solve 15 SQL challenges

Session 13 · phase E4 · 8 points

The ticket in plain words

CityPulse collects Bengaluru city data, such as air quality readings. Y2-T12 cleaned them into data/clean/readings.parquet, a compressed table file. Parquet is good for pipelines, but a dashboard, an API or an analyst needs a database to ask questions and get guaranteed answers. A database stores tables and enforces rules on them.

This ticket designs those tables, then writes a loader, the program that copies the cleaned file into the database. The loader must be safe to run twice, because a scheduled job may rerun after a failure, and the data must not double.

The description cites Healthcare.gov, a government health website that failed at the joins between its separate parts. The seam between two components needs deliberate design. Here the seam is the clean-to-load step. You will design it, get it reviewed, and prove it with test cases. You will also solve 15 SQL challenges on your own squad database.

Before you start

Assume Y2-T10, Y2-T11 and Y2-T12 are merged on main. Y2-T12 gives you src/citypulse/clean.py, data/clean/readings.parquet and docs/data-dictionary.md.

You need Git, GitHub access to the squad repository, Python 3, pandas and pyarrow, the sqlite3 module (built into Python), and the sqlite3 command-line shell. On Windows, run commands in Git Bash, not PowerShell. The trainer runs the same commands on the lab Linux machine.

How your trainer checks it

The trainer starts from a clean state on the lab Linux machine and runs five test cases, in order.

Acceptance criterion How it is checked
Two runs of the loader give the same fact count TC1
sql/schema.sql has keys, foreign keys, NOT NULL, UNIQUE and CHECK TC2, and the schema self-check below
A negative pm2_5 is rejected by a CHECK constraint TC3
The orphan query returns 0 rows TC4
The ERD in docs/ matches the table and column names Self-check below
Your practice file scores at least 11 of 15 TC5

The ERD self-check is grep -oE 'CREATE TABLE IF NOT EXISTS [a-z_0-9]+' sql/schema.sql. It prints each table name in your schema, and every name must match your ERD exactly. Then compare columns: sqlite3 /tmp/t.db "PRAGMA table_info(dim_location)" lists the column names of one table, and you repeat it for each table. Every column name must match the ERD too.

TC1: the loader gives the same count twice

Steps: rm -f /tmp/t.db; SQLITE_PATH=/tmp/t.db python -m citypulse.load; sqlite3 /tmp/t.db 'SELECT COUNT(*) FROM fact_air_quality', then the same load and count again.

The parts: rm -f deletes the old file, so the database starts empty. SQLITE_PATH=/tmp/t.db sets a variable for this command, which your loader reads. python -m citypulse.load runs the module by name. sqlite3 runs the quoted count query.

Passing output looks like this. The 1392 is an example, so your number will differ, but both counts must match and be above 0.

Failing output and the usual cause:

  • 0 on both lines: nothing was inserted. Check the Parquet path and the inserts.
  • Error: no such table: fact_air_quality: the loader never ran the schema.
  • Two different counts: the upsert or the UNIQUE key is missing.
  • ModuleNotFoundError: No module named 'citypulse': wrong folder, or src/ is not on the path. Run from the repository root, and ask your trainer which setup the course uses.

Windows note: if native Python cannot read /tmp/, use a file in the repository root, such as t.db, in every command, and add it to .gitignore first. Tell your trainer.

TC2: the schema has the constraints

Steps: sqlite3 /tmp/t.db ".schema" | grep -cE 'PRIMARY KEY|REFERENCES|CHECK|UNIQUE'. The dot command .schema prints the stored CREATE statements. | passes them to grep, which counts lines containing any of the four words. -E makes the | mean "or", and -c prints a count.

Expected: at least 4 matching lines, across at least 3 tables. Failing output is a lower count, usually from a constraint left out of a table.

TC3: the database rejects pm2_5 = -5

Steps: sqlite3 /tmp/t.db "PRAGMA foreign_keys=ON; INSERT INTO fact_air_quality(ts_utc,location_id,source_id,pm2_5) VALUES('2026-12-05T00:00:00Z',1,1,-5)". The PRAGMA turns on foreign-key checks for this connection. The INSERT names four columns and gives the negative pm2_5. The double quotes keep the single quotes inside the statement intact.

Passing output: an error containing CHECK constraint failed. The ticket shows Error: CHECK constraint failed, and newer shells print a longer line with the same words. No output at all means the row was stored, so the CHECK is missing. no such column means a column name differs from the schema. NOT NULL constraint failed means another column of your fact table is required, so the CHECK never ran; make the other columns nullable. FOREIGN KEY constraint failed means dimension rows 1 and 1 do not exist, so run the loader first.

TC4: no orphan facts

Steps: sqlite3 /tmp/t.db 'SELECT COUNT(*) FROM fact_air_quality f LEFT JOIN dim_location l USING(location_id) WHERE l.location_id IS NULL'. The LEFT JOIN keeps every fact row, and USING(location_id) matches on that column. WHERE ... IS NULL keeps only the rows with no match, which are the orphans, and COUNT(*) counts them.

Expected: 0. Any higher number usually means a fact row points at a location that was never seeded, so check the name-to-id map.

TC5: the practice file runs and scores 11 of 15

Steps: sqlite3 /tmp/t.db < sql/practice/<name>.sql, then the trainer compares your results with the answer key.

The < feeds your file to the shell, which runs its statements in order. Replace <name> with the file name your trainer tells you to use.

Passing output: no error text. The trainer scores your results against the answer key, which you cannot see. Failing output such as Parse error near line N usually means a missing semicolon.

Do it, step by step

Y2-T13.1: write the grain sentence and the ERD

Goal: a written design that the trainer approves before any SQL. The grain decides which columns must be unique.

Stage 1: write the grain on paper as "One row per , per , per ___." Your CityPulse grain is yours to decide, and your trainer signs it off.

Stage 2: list each table, its key, and the columns that point to other tables.

Stage 3: draw the ERD in docs/erd.md as a mermaid block, which GitHub renders from text. Each table lists its columns, marked PK or FK, and each parent links to its children with a line labelled by the key. Look up the erDiagram syntax in the Mermaid documentation.

Stage 4: ask the trainer for sign-off. Commit the ERD only after sign-off, and do not write schema.sql before it.

Test this stage: every foreign key has an arrow from the child table to the parent, and every name matches the names you will type in the schema.

Y2-T13.2: write sql/schema.sql in stages

Goal: a file that creates three tables and one index, and is safe to run twice.

New technique: CREATE TABLE, which names the table, its typed columns and its rules. IF NOT EXISTS makes it do nothing if the table exists. Practise in a throwaway database:

rm -f /tmp/scratch.db
sqlite3 /tmp/scratch.db

Stage 1: a dimension table. This example describes bikes, not CityPulse.

CREATE TABLE IF NOT EXISTS dim_bike (
  bike_id INTEGER PRIMARY KEY,
  code    TEXT NOT NULL UNIQUE
);

Line by line: bike_id INTEGER PRIMARY KEY makes the id the key, and SQLite fills it in if you do not supply one. code TEXT NOT NULL UNIQUE refuses an empty code and a repeated code. Nothing is printed when it works. Check it with .schema dim_bike.

Stage 2: the fact table, with a foreign key, a CHECK and a natural key.

CREATE TABLE IF NOT EXISTS fact_trip (
  trip_id     INTEGER PRIMARY KEY,
  bike_id     INTEGER NOT NULL REFERENCES dim_bike(bike_id),
  started_utc TEXT NOT NULL,
  minutes     REAL CHECK (minutes >= 0),
  UNIQUE (bike_id, started_utc)
);

Line by line: REFERENCES dim_bike(bike_id) is the foreign key. CHECK (minutes >= 0) refuses a negative duration. UNIQUE (bike_id, started_utc) is the natural key: one trip per bike per start time.

Stage 3: an index, a lookup structure. Column order matters: this one suits filters on bike, then time.

CREATE INDEX IF NOT EXISTS ix_trip_bike_time ON fact_trip (bike_id, started_utc);

Stage 4: translate the pattern into CityPulse, using the names in your approved ERD. The tests need location_id and source_id keys, a pm2_5 CHECK, and a UNIQUE key on (location_id, source_id, ts_utc). Add the other columns yourself, and keep them nullable or give them defaults, because TC3 inserts only four columns. Also add the index the subtask asks for, on (location_id, ts_utc), in the same style as Stage 3.

Stage 5: apply the file twice to an empty database and check that nothing breaks:

rm -f /tmp/schema-test.db
sqlite3 /tmp/schema-test.db ".read sql/schema.sql"
sqlite3 /tmp/schema-test.db ".read sql/schema.sql"
sqlite3 /tmp/schema-test.db ".tables"

.read runs a SQL file. Run from the repository root, so that sql/schema.sql is found. The first two runs print nothing. .tables prints dim_location dim_source fact_air_quality, in alphabetical order.

Test this stage: run grep -oE 'CREATE TABLE IF NOT EXISTS [a-z_0-9]+' sql/schema.sql. It must print every table in your ERD. Trap: IF NOT EXISTS does not change a table that already exists. After you edit a column, delete the test database and apply the file again.

Y2-T13.3: write src/citypulse/load.py in stages

Goal: a module that reads the Parquet file, creates the schema, seeds the dimensions, and inserts the facts in one transaction, so a second run changes nothing.

New technique: if __name__ == "__main__":. Code under it runs when you start the file with python -m citypulse.load, but not when another file imports it.

Stage 1: paths and settings. Building paths from the file keeps the loader independent of the current folder.

from pathlib import Path
import os
import sqlite3

import pandas as pd

ROOT = Path(__file__).resolve().parents[2]  # src/citypulse/load.py -> repo root
SCHEMA = ROOT / "sql" / "schema.sql"
READINGS = ROOT / "data" / "clean" / "readings.parquet"
DB_PATH = os.environ.get("SQLITE_PATH", "citypulse.db")

Line by line: Path(__file__) is this file. .parents[2] climbs from load.py to citypulse, then src, then the repository root. os.environ.get reads SQLITE_PATH and falls back to a default name.

Stage 2: inspect the input before you use it. Run this from the repository root:

python -c "import pandas as pd; df = pd.read_parquet('data/clean/readings.parquet'); print(df.dtypes); print(len(df))"

pd.read_parquet loads a DataFrame, an in-memory table. df.dtypes lists each column's type, and len(df) counts rows. Note the column names, which must match your data dictionary.

Stage 3: connect and create the schema.

def connect():
    con = sqlite3.connect(DB_PATH)
    con.execute("PRAGMA foreign_keys = ON")  # per connection, before any transaction
    con.executescript(SCHEMA.read_text(encoding="utf-8"))
    return con

Line by line: sqlite3.connect opens the file and creates it if missing. The PRAGMA applies to this connection only, and it does nothing inside a transaction, so it comes first. executescript runs the whole schema file, and it is safe to repeat.

Stage 4: seed the dimensions. A dimension row must exist before a fact row can point to it.

def seed(con, table, id_col, names):
    for name in names:
        con.execute(
            f"INSERT INTO {table} (name) VALUES (?) ON CONFLICT (name) DO NOTHING",
            (name,),
        )
    return dict(con.execute(f"SELECT name, {id_col} FROM {table}").fetchall())

The f-string puts names from your code, not from the data, into the SQL, which is safe. The values still use ?. ON CONFLICT (name) DO NOTHING keeps existing ids stable. The return value maps each name to its id, such as {"Hebbal": 1}.

Stage 5: convert the values. Missing numbers must become NULL, and timestamps must become ISO text.

def nn(x):
    return None if pd.isna(x) else float(x)

def iso_z(ts):
    return ts.strftime("%Y-%m-%dT%H:%M:%SZ")

pd.isna is true for NaN, which becomes None (SQL NULL). strftime writes the same UTC text every run, which keeps the keys stable. If your timestamps are not UTC, convert them first.

Stage 6: the upsert, then one transaction. The ON CONFLICT columns must match your UNIQUE key.

UPSERT = """
INSERT INTO fact_air_quality (location_id, source_id, ts_utc, <your value columns>)
VALUES (?, ?, ?, ?)
ON CONFLICT (location_id, source_id, ts_utc)
DO UPDATE SET <column> = excluded.<column>
"""

Each ? takes one value from a tuple. excluded.<column> is the incoming value. Replace each <...> with your own names, with one placeholder per column.

Now build the rows and write everything in one transaction:

def load(con, df):
    with con:  # one transaction: seeds and facts commit together, or not at all
        loc = seed(con, "dim_location", "location_id", df["<location column>"].unique())
        src = seed(con, "dim_source", "source_id", df["<source column>"].unique())
        rows = [
            (loc[r.<location column>], src[r.<source column>], iso_z(r.<time column>), nn(r.<value>))
            for r in df.itertuples()
        ]
        con.executemany(UPSERT, rows)

itertuples() yields each row, with column names as attributes. executemany runs the upsert once per tuple.

Stage 7: the entry point, then a check.

def main():
    con = connect()
    load(con, pd.read_parquet(READINGS))
    con.close()

if __name__ == "__main__":
    main()

Test with the TC1 command. If the count is 0, print len(rows) temporarily.

Trap: a PRAGMA foreign_keys inside the transaction has no effect, so keep it in connect.

Y2-T13.6: solve the SQL challenges and save them

Goal: write queries from scratch on your own squad database, and save each answer with its result as comments.

First, learn the skills on a made-up database. Run this setup in a scratch file:

CREATE TABLE dim_bike (bike_id INTEGER PRIMARY KEY, code TEXT NOT NULL UNIQUE);
CREATE TABLE fact_trip (trip_id INTEGER PRIMARY KEY, bike_id INTEGER NOT NULL REFERENCES dim_bike(bike_id), started_utc TEXT NOT NULL, minutes REAL CHECK (minutes >= 0));
INSERT INTO dim_bike VALUES (1,'B-01'), (2,'B-02'), (3,'B-03');
INSERT INTO fact_trip VALUES (1,1,'2026-01-02T08:00:00Z',12.0), (2,1,'2026-01-02T09:00:00Z',30.0), (3,2,'2026-01-03T10:00:00Z',5.5), (4,2,'2026-01-03T11:00:00Z',0.0);

A worked query totals minutes per bike. JOIN attaches each trip to its bike, GROUP BY makes one group per bike, and SUM and COUNT work on each group.

SELECT b.code, SUM(t.minutes) AS total_min, COUNT(*) AS trips
FROM fact_trip t JOIN dim_bike b ON b.bike_id = t.bike_id
GROUP BY b.code
ORDER BY total_min DESC;

Expected output:

code  total_min  trips
----  ---------  -----
B-01  42.0       2
B-02  5.5        2

A second query finds bikes with no trips, using LEFT JOIN and IS NULL. Expected: B-03.

SELECT b.code
FROM dim_bike b LEFT JOIN fact_trip t ON t.bike_id = b.bike_id
WHERE t.trip_id IS NULL;

Practise these four tasks on the made-up database, writing your own queries.

  • Count trips per calendar day. Hint: the first 10 characters of an ISO timestamp are the date, and substr takes them.
  • List trips longer than 20 minutes, longest first.
  • List bikes with more than one trip. Hint: filter groups with HAVING, not WHERE.
  • Find the average minutes of trips longer than zero, rounded to one decimal place.

For each of the 15 challenges your trainer sets, write one query in sql/practice/<name>.sql, with its result pasted below as -- comments, which SQL ignores. Check the file with:

sqlite3 -header -column /tmp/t.db < sql/practice/<name>.sql

-header prints column names, and -column lines the output up. Fix any error before you commit under your own identity. Do not commit the database file.

Y2-T13.7: stretch with window functions

Goal: two queries that compare each row with its group.

A window function works over related rows and keeps every row. PARTITION BY splits rows into groups, and ORDER BY sets the order inside each group. Window functions need SQLite 3.25 or later.

SELECT trip_id, bike_id, minutes,
       ROW_NUMBER() OVER (PARTITION BY bike_id ORDER BY started_utc) AS nth_trip,
       LAG(minutes) OVER (PARTITION BY bike_id ORDER BY started_utc) AS prev_minutes
FROM fact_trip;

Why did the design come before the DDL?

Model answer

The grain decides the natural key, and the natural key decides what counts as a duplicate. Tables written first could carry a UNIQUE rule that does not match the real measurement, so the loader would be built on that mistake.

What is the trade-off of a star schema compared with one wide table?

Model answer

A wide table repeats the place name on every row, so a rename means many updates. A star schema stores each place once and points to it by id. The cost is joins at query time, which is worth paying when reads far outnumber writes.

What did you personally do on this ticket?

Why ON CONFLICT DO UPDATE rather than INSERT OR IGNORE?

Model answer

INSERT OR IGNORE keeps the old row, so a corrected reading is silently lost. ON CONFLICT DO UPDATE applies the new value. Both are repeatable, but only the upsert stays correct when values change.

Defend it in the viva

1. Why write views rather than leave the queries in a notebook?

Model answer

A view is stored in the database, so every reader gets the same definition, and the dashboard can call it by name. A notebook query runs only when someone runs it, and an edited copy can give a different number.

2. What is the trade-off between a view and a summary table?

Model answer

A view always reflects current data, but its work repeats on every read, so a slow view on a large table is slow to read. A summary table is fast to read but must be refreshed, and it goes stale if nobody refreshes it. SQLite has no materialised views, so a summary table is the only stored form.

3. Which view did you write, and how did you check its row count?

4. Why state the IST rule explicitly?

Model answer

Readings are stored in UTC, but the client's day and hour are in IST, which is UTC plus five and a half hours. Grouping by the UTC hour moves the "worst hour" by five and a half hours, so the answer is wrong even though the arithmetic is right.

5. When would you add an index to a view, and when would you leave it alone?

Model answer

I add an index only when the plan shows a full SCAN on a large table with a selective filter. Otherwise it adds write cost and no benefit.

Y2-T15.1 Add the two window views

Goal. sql/views.sql has two new views. Each returns rows with the gap-exposing columns, and the views work on a fresh database.

Technique first: window functions. A normal GROUP BY collapses rows into one result per group. A window function keeps every row and adds a calculated column that looks at nearby rows. OVER says which rows to look at. Here is a small example in a scratch file, not in the project. It uses Python's built-in sqlite3 module, so you need no packages:

import sqlite3
con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE t (ts TEXT, pm25 REAL)")
con.executemany("INSERT INTO t VALUES (?, ?)", [
    ("2026-03-01T08:00Z", 40.0),
    ("2026-03-01T10:00Z", 50.0),
    ("2026-03-02T09:00Z", 30.0),
])
q = """
SELECT ts, pm25,
       COUNT(*) OVER w AS n_in_window,
       AVG(pm25) OVER w AS avg_24h
FROM t
WINDOW w AS (ORDER BY julianday(ts) RANGE BETWEEN 1 PRECEDING AND CURRENT ROW)
"""
for row in con.execute(q):
    print(row)

Line by line: the first three lines create an in-memory database and a table t with a text timestamp and a number. The executemany line inserts three rows. q is a multi-line string holding the query. WINDOW w AS (...) names a window so you can reuse it. ORDER BY julianday(ts) sorts the rows by time, measured in days. RANGE BETWEEN 1 PRECEDING AND CURRENT ROW means: all rows whose time is between one day before the current row and the current row. The last loop prints each result row.

Expected output:

('2026-03-01T08:00Z', 40.0, 1, 40.0)
('2026-03-01T10:00Z', 50.0, 2, 45.0)
('2026-03-02T09:00Z', 30.0, 2, 40.0)

The second row counts two readings because the 08:00 reading is within 24 hours of 10:00. The third row (09:00 next day) excludes the 08:00 reading, which is 25 hours earlier, but includes the 10:00 reading, which is 23 hours earlier, so its window holds two readings. n_in_window is the count, and it shows you when a window is thin.

Trap: ROWS is not the same as a time window

ROWS BETWEEN 23 PRECEDING AND CURRENT ROW takes the previous 23 rows, whatever their times are. If one hour is missing, that window quietly covers more than 24 hours. A RANGE on time keeps the window to 24 hours, and n_in_window shows how many readings really fell inside it.

Stage 1: write the rolling view. Open sql/views.sql and add a view that follows the pattern above, but uses the real table and column names from sql/schema.sql, and the PM2.5 column in your schema. Partition by station if your data has one station per row group. A partition (PARTITION BY station_id inside the OVER part) splits the rows into separate groups so that stations do not average together. Keep the column name n_in_window.

Stage 2: write the day-over-day view. First build one row per day, then compare each day with the previous one. The LAG function returns the value from the row before, in the order you set. Here is the pattern, using a daily summary called daily that you write as a subquery or a CTE (a named temporary query, written with WITH):

SELECT day,
       daily_avg,
       daily_avg - LAG(daily_avg) OVER (ORDER BY day) AS change_vs_prev,
       julianday(day) - julianday(LAG(day) OVER (ORDER BY day)) AS days_since_prev
FROM daily;

Line by line: day and daily_avg come from your daily summary. LAG(daily_avg) OVER (ORDER BY day) takes the previous day's average, and the subtraction gives the change. The days_since_prev column subtracts two day numbers. The first row has no previous day, so both LAG results are NULL, which is correct. A value of 2 or more in days_since_prev means a day is missing, and that is the gap the column exposes.

Stage 3: re-apply the views on a fresh database. Build a scratch database from the schema, then apply the views:

rm -f scratch.db
sqlite3 scratch.db ".read sql/schema.sql"
sqlite3 scratch.db ".read sql/views.sql"
sqlite3 scratch.db ".tables"

Each part: rm -f deletes the scratch file if it exists. The first sqlite3 line builds the tables. The second builds the views. The last line lists the tables and views. Expected output: the view names appear in the list, and no error is printed. If you see already exists, the views file creates the views without first dropping them. Change it to DROP VIEW IF EXISTS before each CREATE VIEW, or use CREATE VIEW IF NOT EXISTS, and run it again.

Test. Run sqlite3 -header citypulse.db 'SELECT * FROM v_pm25_rolling_24h LIMIT 3;' on the lab database. You should see n_in_window in the header and three rows. Then delete scratch.db so that you do not commit it.

Y2-T15.2 Write your DQ check

Goal. src/citypulse/dq_checks.py holds one check from your squad's assigned dimension, with a threshold, a blocking flag and a one-line reason. Your commit shows your name on it.

Technique first: a check is data plus a rule. Each check needs five things: a name, a dimension, an SQL query that returns one number, a rule that judges the number, and a blocking flag. Keep them together in one entry, so that one line shows everything about the check.

Stage 1: measure before you choose a threshold. A threshold that is too strict fails every day, and one that is too loose never fails. Measure normal values first. For example, for a completeness check on the last 24 hours, count the rows per day for the last week:

sqlite3 -header citypulse.db "SELECT substr(<time_column>,1,10) AS day, COUNT(*) AS n FROM <fact_table> GROUP BY day ORDER BY day DESC LIMIT 7;"

Each part: substr(..., 1, 10) takes the first ten characters of the timestamp, which is the date. GROUP BY day collapses rows per date. COUNT(*) counts them. ORDER BY day DESC LIMIT 7 shows the latest seven days. Replace <time_column> and <fact_table> with the names in sql/schema.sql. Expected output: a header and up to seven rows with a date and a count. Choose your threshold below the normal count, and write the reason in the comment.

Stage 2: write the entry. Add one tuple to a list called CHECKS. The placeholders below are yours to fill in with your dimension, name and numbers:

## One check per entry: name, dimension, SQL returning one number,
## pass rule, blocking flag. Reason: <one line on why this threshold>.
CHECKS = [
    (
        "<your_check_name>",            # shown in the output
        "<your_dimension>",             # completeness, validity, uniqueness or freshness
        "<SQL that returns one number>",
        lambda v: <your_rule>,          # True means the check passes
        True,                           # True: a failure stops the pipeline
    ),
]

Line by line: CHECKS is a list of entries. Each entry is a tuple, written in round brackets, with five items in a fixed order. The comment above explains the reason. The lambda is a small unnamed function that takes the number and returns True or False. For example, a rule v >= 40 passes when the number is 40 or more. The last item True makes the check blocking.

If your dimension is freshness, handle an empty table. MAX(...) returns NULL on an empty table, which Python reads as None, and comparing None with a number raises an error. Write the rule as v is not None and v <= <limit>.

Test. Check that the list loads and has your entry:

python -c "from citypulse.dq_checks import CHECKS; print(len(CHECKS), CHECKS[-1][0])"

Expected output: the number of checks and your check's name, such as 1 <your_check_name>. If you see ImportError, the file has a syntax error. Run python -m py_compile src/citypulse/dq_checks.py to see the line.

Commit. Commit only your entry and its comment, under your identity: git add src/citypulse/dq_checks.py and then git commit -m "<your own words>". Check the author with git log -1 --format=%an, which must show your name.

Key fact: Blocking is for data you must not publish

Make a check blocking only when a failure means the data would be wrong for the client. Use a warning for something that is only unusual. Every check needs a reason in its comment, because the viva will ask for it.

Y2-T15.3 Make main() print the summary and return the exit code

Goal. Running python -m citypulse.dq_checks prints one line per check, then DQ: X passed, Y failed, Z warnings. It returns 1 when a blocking check fails, and 0 otherwise.

Technique first: exit codes. A Python program returns its number to the shell with sys.exit(...). The shell stores that number in $?. The pipeline only needs the number, not the text, to know whether to stop. Also, a main() that prints FAIL but has no return gives back None, and the process exits with 0. That is a silent failure, so return the number explicitly.

Stage 1: run every check. Inside main(), open the database and run each check:

def run_all(con):
    results = []
    for name, dimension, sql, rule, blocking in CHECKS:
        value = con.execute(sql).fetchone()[0]
        results.append((name, blocking, rule(value)))
    return results

Line by line: run_all takes an open database connection. for name, dimension, sql, rule, blocking in CHECKS unpacks each tuple into five names. con.execute(sql) runs the query, fetchone() returns one row as a tuple, and [0] takes its first item, which is the number. rule(value) applies your rule, and the result is a list of (name, blocking, passed) tuples. Expected: nothing is printed yet.

Stage 2: print each line and the summary.

for name, blocking, passed in results:
    label = "PASS" if passed else ("FAIL" if blocking else "WARN")
    print(label, name)
failed = sum(1 for _, b, ok in results if b and not ok)
warned = sum(1 for _, b, ok in results if not b and not ok)
passed_count = len(results) - failed - warned
print(f"DQ: {passed_count} passed, {failed} failed, {warned} warnings")

Line by line: the loop gives each check one label. The nested if picks PASS if the check passed, FAIL if it failed and is blocking, and WARN otherwise. failed counts blocking checks that did not pass, and warned counts the other failures. The last line uses an f-string, which puts the numbers inside the text. Expected output for one passing check: PASS <your_check_name> and DQ: 1 passed, 0 failed, 0 warnings.

Stage 3: return the code and stop with it.

    return 1 if failed else 0

if __name__ == "__main__":
    sys.exit(main())

Line by line: return 1 if failed else 0 is a one-line choice. If any blocking check failed, the function returns 1. The if __name__ == "__main__": line means the code below runs only when you start this file directly, not when another file imports it. sys.exit(main()) passes the returned number to the shell as the exit code.

Also read the database path. The script sources .env, which may set SQLITE_PATH. Use os.environ.get("SQLITE_PATH", "citypulse.db") so that a run without .env still finds the default file.

Test both outcomes without touching the real database. Copy the database, then point the check at the copy:

cp citypulse.db scratch_pass.db
SQLITE_PATH=scratch_pass.db python -m citypulse.dq_checks; echo $?

Each part: cp copies the file. SQLITE_PATH=scratch_pass.db sets the variable for this one command only, so the check reads the copy. echo $? prints the exit code. Expected: 0 on the lab data.

For the failure path, make a copy and delete its recent rows with the DELETE statement from subtask T15.5, then run the same command with scratch_fail.db. Expected: at least one FAIL line and 1. Delete both scratch files afterwards.

Trap: set -e changes what a failing command does

In the pipeline script, a bare python -m citypulse.dq_checks that returns 1 stops the whole script at that line. That is what you want in the pipeline. In the sabotage script you need the failure, so wrap it in if, as subtask T15.5 shows.

Y2-T15.4 Write scripts/run_pipeline.sh

Goal. scripts/run_pipeline.sh runs fetch, clean, load, views and dq in order. Each stage logs START and END. It exits 0 when everything passes, and it works from any folder.

Technique first: strict mode and a runner function. set -euo pipefail makes Bash stop at the first failing command, stop on unset variables, and fail a pipeline when any part fails. A function is a named block of commands, written with name() { ...; }, and you call it by name.

Build the file in stages. Each stage adds a few lines, and you test before you add the next.

Stage 1: the header and the repository root. Create scripts/run_pipeline.sh with these lines:

#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."

Line by line: the first line is the shebang. The second line is strict mode. The third line moves to the repository root. $0 is the path the script was started with, such as scripts/run_pipeline.sh. dirname gives its folder, scripts. .. goes up one level, to the repository root. The $( ... ) form runs the command and puts its output in place. The quotes keep folder names with spaces working.

Test it from another folder: run bash /full/path/to/scripts/run_pipeline.sh after adding the line pwd below the cd. The printed folder should be the repository root.

Stage 2: load your settings. Add:

if [ -f .env ]; then set -a; . ./.env; set +a; fi
DB="${SQLITE_PATH:-citypulse.db}"

Line by line: [ -f .env ] is true if the file exists. set -a marks each variable created next as exported, so child programs see it. . ./.env reads the file. set +a switches that behaviour off again. The second line sets DB to SQLITE_PATH if it is set and not empty, and to citypulse.db otherwise. The :- form is the "use this default" form.

Test: no stages exist yet, so running bash scripts/run_pipeline.sh should print nothing and exit 0. The point of this stage is only that the file has no syntax errors. Check it with bash -n scripts/run_pipeline.sh, which reads the file and reports syntax errors without running it. No output means no errors.

Stage 3: the logging and runner functions.

log() { echo "$(date -u +%FT%TZ) [pipeline] $*"; }
run() { local name=$1; shift; log "START $name"; "$@"; log "END $name"; }

Line by line: log prints a UTC timestamp, the tag, and its arguments. date -u gives UTC time, and +%FT%TZ formats it like 2026-11-17T09:00:00Z. Git Bash on Windows also supports this format. run takes a stage name and then the command. local name=$1 stores the first argument. shift removes it, so "$@" now holds only the command. "$@" runs that command. Because set -e is on, a failing command stops the script before the END line prints.

Stage 4: the first two stages. Add:

run fetch python -m citypulse.fetch
run clean python -m citypulse.clean

Line by line: each line calls run with a stage name, then the module that does the work. The module names come from your earlier tickets. Expected output when run: a START fetch line, the module's own output, an END fetch line, and the same for clean. Test with bash scripts/run_pipeline.sh; echo exit=$?.

Stage 5: the rest of the stages and the final line. Add:

run load python -m citypulse.load
run views sqlite3 "$DB" ".read sql/views.sql"
run dq python -m citypulse.dq_checks
log "pipeline OK"

Line by line: load writes the data. views runs your saved views file against the database. The quoted ".read sql/views.sql" is a SQLite command that runs the file. dq runs your checks, and its exit code 1 stops the script. The last line runs only if every stage passed.

Stage 6: the virtual environment. Under cron, or when the shell's python is not your environment, the module import fails. Make the script use the project's environment when one exists. Add this line directly after the cd line:

if [ -f .venv/bin/activate ]; then . .venv/bin/activate; fi

Line by line: if the activate script exists, it runs and puts that environment's python first. On Windows Git Bash the file is .venv/Scripts/activate, so the check fails there and the line does nothing. Your laptop's python must then already be the right one, or add a second check for Scripts.

Test from both places. Run from the repository root, then from /tmp with the full path:

scripts/run_pipeline.sh; echo exit=$?
cd /tmp && /full/path/to/your/clone/scripts/run_pipeline.sh; echo exit=$?

Expected: every stage prints START and END, and each run ends with pipeline OK and exit=0. If the second run fails with a missing file, the cd line is wrong.

Trap: pipefail and tee

If you add | tee run.log to a stage to save its output, the stage's exit code is replaced by the exit code of tee, which is 0. set -o pipefail makes the pipeline fail if the stage fails. Your set -euo pipefail line already does this.

Y2-T15.5 Write scripts/dq_sabotage.sh

Goal. The script deletes the last 24 hours of facts, expects the dq stage to fail, reloads the data, and expects the dq stage to pass. It exits 0 only if both expectations hold.

Technique first: an expected failure. A normal failing command stops a script under set -e. To say "this failure is expected", put the command inside an if. The if tests the exit code and does not stop the script.

Stage 1: the header and the database path. Create scripts/dq_sabotage.sh:

#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."
if [ -f .env ]; then set -a; . ./.env; set +a; fi
DB="${SQLITE_PATH:-citypulse.db}"

Line by line: this is the same header as the pipeline script in T15.4. Copying the setup lines keeps both scripts reading the same database.

Stage 2: delete the last 24 hours. First look at how timestamps are stored, because the delete compares text. Run:

sqlite3 "$DB" "SELECT MAX(<time_column>) FROM <fact_table>;"

The value should look like 2026-11-17T08:00:00Z. Now add the delete, with the same format:

sqlite3 "$DB" "DELETE FROM <fact_table> WHERE <time_column> >= strftime('%Y-%m-%dT%H:%M:%SZ','now','-1 day');"
echo "sabotage: deleted last 24h of facts"

Line by line: DELETE FROM removes rows. WHERE ... >= selects rows at or after the cut-off. strftime with 'now' and '-1 day' builds the timestamp for 24 hours ago in UTC, in the same format as the stored values. Text comparison works only when both sides use the same format, so a mismatch deletes too many rows, or none. Check the count afterwards with a SELECT COUNT(*).

Test: run scripts/dq_sabotage.sh up to this point and check the count before and after with SELECT COUNT(*) FROM <fact_table> WHERE <time_column> >= ..., using the same cut-off. After the delete, the count for that window should be 0.

Stage 3: the first dq run, which must fail.

if python -m citypulse.dq_checks; then
  echo "UNEXPECTED: dq passed after sabotage"; exit 1
fi
echo "OK: dq failed with non-zero exit as expected"

Line by line: if runs the dq module and branches on its exit code. A 0 takes the then branch, and that would be the wrong result here. exit 1 stops the script with failure, because the sabotage did not break anything. fi closes the if. The last line prints when the dq run failed, which is the expected result. Expected output: FAIL lines, the summary, then the OK line.

Trap: A bare failing command stops the script

Without the if, python -m citypulse.dq_checks returning 1 would end the script under set -e, and the reload would never run. Wrapping it in if tells Bash the failure is expected.

Stage 4: reload and the second dq run, which must pass.

python -m citypulse.load
python -m citypulse.dq_checks
echo "OK: dq passed after reload"

Line by line: load restores the rows. The second dq run is not wrapped in if, so under set -e a failure stops the script with a non-zero exit, which is what you want. The final line prints only when dq passed. Expected: all PASS lines, the summary with 0 failed, and the OK line.

If the second run still fails, load.py does not restore the deleted window. That is a fault in the load from Y2-T13, which must be idempotent. Fix it there, and do not work around it in the sabotage script.

Test. Run scripts/dq_sabotage.sh; echo exit=$?. Expected: a failing first run, a passing second run, and exit=0. Take the two screenshots the ticket asks for: one of the first run's FAIL lines and exit, and one of the second run's PASS lines.

Defend it in the viva

The viva examiner asks about your reasoning, not your memory of the commands. Answer in full sentences.

Why does the dq stage run after load and views, rather than before the load?

Model answer

The dq checks read the data that the pipeline has put in the database, including the views the client sees. A check run before the load would test a copy that is not the one the client uses. In this pipeline the load is idempotent, so a failed run can be repeated, and the checks test the final state. If you moved dq before the load, a failure would no longer prove what the client receives. The trade-off is that bad rows are already in the database when a check fails. That is why the views and the dashboard must read only after dq passes, and why the ticket's sabotage shows the reload restoring a good state.

What is the trade-off between a blocking check and a warning, and how did you decide for your check?

Model answer

A blocking check protects the client from data that must not be published, but a false alarm stops the whole pipeline. A warning keeps the pipeline running and leaves the decision to a person. I would make a check blocking when the data would be wrong for the client, such as a value that cannot be negative. I would make it a warning when the data is only unusual. Your answer should name your own check, its threshold, the number you measured to set it, and the reason in your comment. Explain why you chose blocking or warning for that check.

Walk me through the DQ check you wrote. What dimension is it, what is its threshold, and how did you choose the threshold?

Model answer

This is a structure for your own answer, not a script to memorise. Name the check and its dimension, and explain what it counts or measures. Then give the threshold, and say how you measured normal values before you chose it, for example with a daily count over the last week. State whether it is blocking and why. Finish with the commit that added it. A strong answer shows you can explain the number, not only read it. Write your answer from what you actually measured.

Why does the rolling view use a time range rather than a fixed number of rows?

Model answer

A fixed number of rows, such as the previous 23 rows, covers a different length of time whenever a reading is missing. A range on time always covers 24 hours, however many readings it holds. The cost is that the window can hold fewer readings, which is why the view exposes n_in_window. A small count tells the reader that the average rests on a gap in the data, so the number is not treated as a complete day.

How did you prove the failure path works, and what would happen if the pipeline ignored the dq exit code?

Model answer

The sabotage script deletes the last 24 hours, runs the dq stage, and checks that it returned 1. Then it reloads and checks that the dq stage returns 0. Together, these show the checks fail when data is bad and pass when it is good. If the pipeline ignored the exit code, the script would keep going after a failed check, and the load and views would run on data the checks had rejected. The client would see bad numbers with a green message. The exit code is the only signal the pipeline needs, which is why main() must return it.

TC2: sabotage fails, then reload passes

Y2-T16.1: Check the fresh clone and the sabotage run

Goal. Before 09:00, you know that main is green, and that both scripts work from a clean copy. You are not the trainer, but you rehearse exactly what the trainer runs.

Technique first: exit codes. Every command returns a number when it ends. Try these in Git Bash.

true; echo "exit=$?"
false; echo "exit=$?"

The first line prints exit=0, because true succeeds. The second prints exit=1, because false fails. A script decides what to do from these numbers, not from the words printed on screen. Stage 3 uses this.

Stage 1: check that main is green. Run this on your laptop:

gh run list --branch main --limit 3

gh run list shows recent CI runs. --branch main limits the list to main. --limit 3 shows the last three. Expected output: three lines, the newest with a completed status and success. If the newest says failure, fix that first, because the trainer will see it. The exact layout of the output can differ a little between a terminal and a pipe, so read the status and result words, not the column positions.

Stage 2: a small idempotency example. A load is idempotent when running it twice leaves the same rows. The trick is a key: each row has an identity, and a second load replaces the row instead of adding one. This test uses only the standard library and an in-memory database, so it needs no files.

import sqlite3

def load_once(conn, rows):
    conn.execute("CREATE TABLE IF NOT EXISTS fact (station TEXT, day TEXT, pm25 REAL, PRIMARY KEY (station, day))")
    conn.executemany("INSERT OR REPLACE INTO fact VALUES (?, ?, ?)", rows)
    conn.commit()

def count(conn):
    return conn.execute("SELECT COUNT(*) FROM fact").fetchone()[0]

conn = sqlite3.connect(":memory:")
batch = [("S1", "2026-01-01", 12.5), ("S2", "2026-01-01", 9.0)]
load_once(conn, batch)
first = count(conn)
load_once(conn, batch)
second = count(conn)
assert first == 2
assert second == 2
assert first == second

Line by line: PRIMARY KEY (station, day) makes each pair unique. INSERT OR REPLACE writes a row, and if the key already exists it replaces the old row. executemany runs the insert once per row. conn.commit() saves the change. count returns the number of rows. The batch goes in twice, and the count stays at 2. The three assert lines check that the count is 2, twice, and that the two counts match. If the insert were a plain INSERT, the second load would fail on the key, and if there were no key at all, the count would become 4.

Run the check on your own loader, not on this example. The point is the pattern: the key, and INSERT OR REPLACE or an equivalent delete-then-insert for the same period.

Y2-T16.4: Review comments, CHANGELOG, tag and release

Goal. Every review comment from the trainer becomes an Issue. Each fix goes through a PR. The CHANGELOG has a [0.3.0] section. The tag v0.3.0 points at the merged commit, and a GitHub release uses the same notes.

Technique first: annotated tags and awk. A tag names one commit. An annotated tag also stores a message, who made it and when. Make a practice tag in a throwaway repository, not in your squad's, if you want to try it. The real command is:

git tag -a v0.3.0 -m 'D02: data ingestion & SQL pipeline'

-a creates an annotated tag. v0.3.0 is the name. -m gives the message in quotes, so the & is safe. Check it with git show --no-patch v0.3.0. Expected output: the tagger, the date and the message. Do not run it yet, because the tag must point at the merged commit.

awk reads text line by line and can print the lines between two markers. Test it on a small example before you use it on the CHANGELOG:

printf 'a\n## [0.2.0]\nx\n## [0.3.0]\ny\n' | awk '/^## \[0\.3\.0\]/{f=1;next} /^## \[/{f=0} f'

Expected output: y. The first rule turns printing on at the 0.3.0 heading and skips that heading. The second rule turns it off at any other ## heading. The last f prints each line while printing is on.

Stage 1: turn each review comment into an Issue. For each comment, run this on your laptop:

gh issue create --repo citypulse-y2/citypulse-<squad> --title "Trainer review: <short name>" --body "<what is wrong, where, and how to check it>"

The parts: gh issue create makes an Issue. --repo names the repository. --title and --body are the text, in quotes. Expected output: the link to the new Issue. Write the body so that someone else can check the fix without asking you.

Stage 2: fix each Issue in a PR. Create a branch, make the fix and open the PR:

git switch -c y2-t16-<your-name>-d02-fixes
git add <the files you changed>
git commit -m "fix(pipeline): exit non-zero when a blocking check fails"
git push -u origin y2-t16-<your-name>-d02-fixes
gh pr create --fill

git switch -c makes a new branch. git add stages named files, so you do not commit by accident. git commit -m saves with a message. git push -u sends the branch to GitHub. gh pr create --fill opens a PR, using the commit message as the title. Expected output: the PR link. A squad-mate must approve it before the merge, and you must not merge your own PR.

Stage 3: write the CHANGELOG entry. Find the existing heading format first:

grep -n "0.3.0" CHANGELOG.md

Expected output: the heading line, such as 12:## [0.3.0] - <date>. Use the same heading style for your entry. Write the notes in your own words. Each line should say what changed and why, and link to the Issue or PR where it helps.

Stage 4: tag the merged commit. When main holds the final fixes and the CHANGELOG, switch to main and pull it. Then create and push the tag:

git switch main
git pull
git tag -a v0.3.0 -m 'D02: data ingestion & SQL pipeline'
git push origin v0.3.0

git pull brings the merged code into your copy. git push origin v0.3.0 sends the tag to GitHub. Expected output: a line showing the tag was pushed to origin.

Stage 5: create the release with the CHANGELOG notes. Keep the notes file outside the repository, so it is never committed. Save it one folder up, then create the release:

awk '/^## \[0\.3\.0\]/{f=1;next} /^## \[/{f=0} f' CHANGELOG.md > ../notes-0.3.0.md
gh release create v0.3.0 --repo citypulse-y2/citypulse-<squad> --title "v0.3.0" --notes-file ../notes-0.3.0.md

--notes-file takes the release text from a file. Expected output: the release link. Test it with TC3 in section 4. If the notes file is empty, the awk pattern does not match the heading, so check Stage 3 again.

Open ../notes-0.3.0.md before you publish. If your CHANGELOG ends with link lines such as [0.3.0]: https://..., awk copies them into the notes too, so delete those lines from the notes file.

Defend it in the viva

The trainer asks five questions. Each model answer gives the reasoning. Your own answer must use your own commits and your own checks.

1. Why must the second run leave the count unchanged? This is the "why" question.

Model answer

A pipeline that runs on a schedule, or is run again after a failure, must not double the data. If the load is idempotent, the second run replaces the same rows, so the count stays the same. Without that, every retry inflates the facts, and the reports give wrong numbers. The trainer tests this by running the pipeline twice from a fresh clone and comparing the counts.

2. Why does the pipeline stop on a blocking DQ failure, instead of loading the rows with a warning? This is the trade-off question.

Model answer

Stopping protects the reports. Bad rows that reach the fact table can change every query that reads them, and it is hard to remove them later. The cost of stopping is delay: the data arrives late until someone fixes the cause. A warning keeps the data flowing, but the people reading it may not notice the warning. The course chooses blocking for the checks that protect the client's answers, and a squad can discuss which checks should block.

3. What did you personally build or check in this ticket, and where can I see it in Git? This is the "what you did" question. Replace the model answer with your own facts.

Model answer

Answer with one named fix, one commit, one check you ran and the output you saw. For example: "I changed the DQ entry point so a failure returns 1. The commit is on my branch, and I ran the sabotage script before and after. The shell showed exit 1, then exit 0 after the reload." Name the file, the commit and the output. Do not describe work you did not do. If a teammate did a part, say so, and say what you checked in it.

4. Why use an IAM admin user for daily work, and not the root account? This is the "why" question about cloud security.

Model answer

The root account can do anything in the account, and it cannot be restricted by policy. If its password or key leaks, the whole account is exposed. An IAM admin user has broad permissions, but it can be given MFA, disabled or limited, and its actions are recorded under its own name. Daily work on the user, with root kept for the rare tasks that need it, follows least privilege and leaves a clearer audit trail.

5. What is the difference between a tag and a release, and why do you create the tag first? This is the explanation question.

Model answer

A tag is a fixed name for one commit in Git. A release is a GitHub page built on a tag, with notes and optional files. The tag must come first, because the release is attached to it, and the tag fixes which commit is the version. Creating the release first would attach it to a tag that does not exist yet, so the commit would be chosen by accident. An annotated tag also records who made it and why, which helps in the viva.
