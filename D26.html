Day 26 — CI/CD and cloud deployment

The idea in one minute

Today you make a computer do the checking and shipping that you would otherwise do by hand. Each time you send a change to GitHub, a fresh machine in the cloud runs your tests. If they pass, the same machine packages CityPulse into a container image, labels the image with the exact code commit it came from, and stores it in a registry. When you mark a release with a tag, a second pipeline deploys that same image to a public web address, checks that it answers correctly, and can send users back to the previous version within minutes.

The analogy is a factory line. A part moves on to painting only after inspection passes, and every finished part gets a serial number. Tests are the inspection, the image is the part, and the commit SHA is the serial number.

Starting from zero

This section defines every word the day depends on. Read it once now and come back to it when a later section uses a word you are unsure of.

Terminal. A text window where you type instructions for the computer and read its replies. Each instruction is a command, such as git status. The computer runs it and prints output below it.

File and folder. A file holds text or data, such as a Python program. A folder (also called a directory) holds files and other folders. A path such as .github/workflows/ci.yml is the address of a file: start at the top folder, go into .github, then workflows, then open ci.yml. The dot at the start of .github means the folder name begins with a dot, which marks it as a hidden or settings folder.

Variable. A name that holds a value. In the line version = "1.4.2", the name version holds the text "1.4.2". In a terminal script, a variable is read with a dollar sign, so $SHA means "the value stored in SHA".

Function. A named block of Python code that takes inputs, does some work and gives back a result. You define it with def and call it by writing its name with brackets, such as next_version("1.4.2", []).

Server. A program that waits for requests and sends answers. A web API is a server that answers requests sent to web addresses. CityPulse exposes an address called /v1/health that reports whether the app is alive.

Git, commit, SHA. Git records snapshots of your project called commits. Every commit has a long identifier called a SHA (a 40-character code made of letters a to f and digits). The short SHA is the first seven characters, such as e610ea4. A SHA never changes and always points to the same code.

Branch and tag. A branch is a named line of commits. main is the main line. A tag is a permanent name attached to one commit, such as v1.4.2. Tags do not move when you add new commits.

Push. Sending your local commits or tags to the copy on GitHub with git push.

YAML. A plain-text format for settings. Indentation (spaces at the start of a line) shows which lines belong together. key: value sets one thing, and a line starting with - is an item in a list.

Workflow, job, step, runner. A workflow is one YAML file in .github/workflows that describes automation. A job is a group of steps. A step is one action or one shell command. A runner is the fresh virtual machine that GitHub gives a job to run on. Each job gets a new runner, so nothing from one job exists in the next unless you pass it on.

Exit code. Every program finishes with a number. Zero means success. Any other number means failure. Automation relies on this: a failed command stops the step, and a failed step fails the job.

Container, image, registry. A container is a program packaged with the libraries it needs, so it runs the same way on any machine. An image is the stored template that a container starts from. A registry is a storage service for images, such as GitHub Container Registry (GHCR) or Amazon Elastic Container Registry (ECR).

Secret and token. A secret is a sensitive value, such as a password. A token is a long string that proves who you are to a service. Secrets should never be written into files that are stored in Git.

Environment variable. A named value handed to a program when it starts. Apps read settings such as DATABASE_URL this way.

Semantic version. A version number written as MAJOR.MINOR.PATCH, such as 1.4.2. A major change can break users, a minor change adds features without breaking anything, and a patch fixes bugs.

Smoke test. A quick check that a deployed app starts and gives a basic correct answer. It is not a full test suite. It answers one question: is the thing that went live working at all?

The tools

GitHub Actions

What it is. GitHub Actions runs workflows defined in YAML files on GitHub-hosted machines when events happen, such as a push or a pull_request. An event is something that happened in the repository. A push to main is one event; opening a pull request (a request to merge one branch into another, reviewed before merging) is another.

Why CityPulse uses it. The course repositories, branch protection and GHCR already live on GitHub, so one tool covers code, tests and images. The alternatives in the slides each have a cost. GitLab CI is equally capable, but it would mean moving the repositories. Jenkins is flexible, but someone must run and maintain its server. Cloud Build and CodeBuild sit close to the cloud platform, but they split the pipeline across two systems and need extra permission wiring.

How it works. Jobs run on separate fresh runners. The needs: keyword makes one job wait for another, and the job waits only if the earlier one succeeded. An if: condition decides whether a job runs at all. The diagram below shows one merge to main.

The test job. This is the gate, the first job every later job depends on. The slides' version of the file is shown below, with the indentation restored.

name: ci
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt && pytest -q

Line by line:

  • name: ci sets the name shown in the GitHub Actions tab.
  • on: [push] says this workflow starts on every push. The square brackets make a list with one item.
  • jobs: starts the list of jobs. Each job name is indented under it.
  • test: names the job. The name is used by needs: elsewhere.
  • runs-on: ubuntu-latest asks for a fresh Linux machine using the latest Ubuntu image GitHub provides.
  • steps: starts the list of steps for this job.
  • - uses: actions/checkout@v4 copies your repository onto the runner. uses: runs a reusable action, and @v4 pins the version.
  • - run: pip install -r requirements.txt && pytest -q runs two commands in order. pip install -r requirements.txt installs the libraries listed in that file. && runs the second command only if the first succeeded. pytest -q runs the tests, and -q (quiet) prints less detail. Expected output is a line such as 3 passed.

The build-push job. This job builds the image and pushes it to the registry. It runs only for pushes to main. The slides' version is restored below.

  build-push:
    needs: test
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions: {contents: read, packages: write}
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with: {registry: ghcr.io, username: "${{ github.actor }}", password: "${{ secrets.GITHUB_TOKEN }}"}
      - id: meta
        uses: docker/metadata-action@v5
        with: {images: "ghcr.io/${{ github.repository }}", tags: "type=sha,format=long,prefix=\ntype=sha,prefix="}
      - uses: docker/build-push-action@v6
        with: {context: ., push: true, tags: "${{ steps.meta.outputs.tags }}", cache-from: "type=gha", cache-to: "type=gha,mode=max", build-args: "GIT_SHA=${{ github.sha }}"}

Line by line:

  • build-push: is the job name, indented to sit beside test: under jobs:.
  • needs: test means this job waits for the test job and is skipped if that job fails.
  • if: github.event_name == 'push' && github.ref == 'refs/heads/main' is a condition. github.event_name is the event type, and github.ref is the branch or tag. == means "equals" and && means "and". On a pull request the condition is false, so the job is skipped.
  • permissions: {contents: read, packages: write} gives this job only the rights it needs. contents: read lets it read code, and packages: write lets it push images.
  • docker/setup-buildx-action@v3 prepares Docker's newer build tool, which supports the cache options used below.
  • docker/login-action@v3 logs in to ghcr.io, the GitHub container registry. username is the person who triggered the run, from github.actor. password is secrets.GITHUB_TOKEN, a short-lived token that GitHub creates for each run. You never type it.
  • id: meta gives this step a name, so later steps can read its outputs.
  • docker/metadata-action@v5 creates the tag names. The value type=sha,format=long,prefix= makes the full 40-character SHA. The second line type=sha,prefix= makes the short form. Without prefix= the action would add sha- in front of each tag, and the deploy step could not find the image by the plain SHA. The \n between them is a newline, which separates the two rules.
  • docker/build-push-action@v6 builds and pushes. context: . means "use the current folder". push: true sends the image to the registry after building.
  • tags: "${{ steps.meta.outputs.tags }}" uses the tag names created in the meta step.
  • cache-from and cache-to with type=gha keep build layers in GitHub's cache, so the next build can reuse them. Warm builds are faster than cold ones.
  • build-args: "GIT_SHA=${{ github.sha }}" passes the commit SHA into the Dockerfile as a build argument. The app reads it and reports it at /v1/health.

Expected result: on a push to main, both jobs appear in the Actions tab with green ticks. On a pull request, build-push shows as skipped.

Trap: Granting write permission to everything

Put packages: write at the top level and every job can push images, including the test job. Keep contents: read globally and add write only on build-push.

Trap: Pasting a token into the YAML

A personal access token typed into the file is stored in Git history forever. Use secrets.GITHUB_TOKEN for GHCR. If a token has already leaked, revoke it, because deleting the line does not remove it from history.

Trap: Mixed-case repository names

Registry image paths must be lowercase. ghcr.io/MyTeam/CityPulse fails. Use lowercase names.

Container registries and SHA tags

What it is. A container registry stores images so that servers can download them. Common registries are GHCR, Amazon ECR and Google Artifact Registry. Each image has a tag, which is a label such as latest or e610ea4. Tags are names, not copies.

Why SHA tags. A tag made from the full commit SHA is immutable in practice: it always points to the same code. The tag latest changes every time someone pushes a new image. If a server runs latest, you cannot tell which code it is running, and you cannot reproduce it. The alternative of using only semantic version tags needs manual bumps, so CityPulse uses v* Git tags to trigger deployments and SHA tags to identify images.

How it works. The script below builds one image and tags it with the short commit SHA. Run it inside the project folder, where a Dockerfile (a text file describing how to build the image) sits.

SHA=$(git rev-parse --short HEAD)
docker build -t citypulse:$SHA .
echo "built citypulse:$SHA"

Line by line:

  • SHA=$(git rev-parse --short HEAD) runs a command inside $( ) and stores its output in the variable SHA. git rev-parse translates a name into a SHA. --short asks for the seven-character form. HEAD means "the commit you currently have checked out".
  • docker build -t citypulse:$SHA . builds the image. -t (tag) names it citypulse with the tag from $SHA. The final . is the build context, the folder whose files the build may use.
  • echo "built citypulse:$SHA" prints a confirmation line.

Run it in the terminal and you see:

The first line is the command you type. The second line is the output the script prints. The tag e610ea4 is the commit you built from, so you can match the running image to the code later.

The CI version goes one step further. The metadata step creates two tags for the same image digest. A digest is a fingerprint of the image's content. The full SHA and the short SHA point to the same digest. To check that the registry is consistent, you can pull the image, compare its digest, and read the git_sha value from /v1/health. All three must match the commit.

Trap: Deploying by latest

If the deploy step says image: citypulse:latest, the next push silently changes what is deployed and rollback has no fixed target. Always deploy an explicit SHA.

Trap: Declaring the build argument in the wrong stage

A multi-stage Dockerfile has separate stages. An ARG (build argument) declared in the builder stage does not exist in the runtime stage. Declare ARG and ENV again in the runtime stage, or the app will report an empty git_sha.

Trap: Pushing from pull requests

An image built from an unreviewed branch can become deployable. The if: condition on build-push prevents this.

Deploy on tag, smoke tests and rollback

What it is. Continuous deployment here means that pushing a v* tag, such as v0.9.0-rc1, starts a workflow. That workflow tells a managed container service to run the image already built for that commit. Managed means the cloud provider runs the servers, patches them and restarts them. The slides use Google Cloud Run as the default service. Cloud Run keeps a list of revisions, which are saved versions of your service, and can send traffic to any one of them.

Why a managed service. CityPulse needs a public HTTPS address that updates without someone typing commands on one laptop. The alternatives are a manual deploy from a laptop (depends on one person's credentials and is not repeatable), EC2 with SSH (virtual servers you manage yourself, including patches and TLS), and Kubernetes (powerful, but heavy for one small API).

How it works. The deploy workflow below runs when a tag is pushed. It does not rebuild the image. It deploys the one CI already tested.

on:
  push:
    tags: ["v*"]
permissions: {contents: read, id-token: write}
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: google-github-actions/auth@v2
        with: {workload_identity_provider: "${{ vars.WIF_PROVIDER }}", service_account: "${{ vars.DEPLOY_SA }}"}
      - uses: google-github-actions/setup-gcloud@v2
      - run: gcloud run deploy citypulse-api --image "${{ vars.IMAGE }}:${{ github.sha }}" --region asia-south1 --quiet
      - run: ./scripts/smoke.sh "${{ vars.BASE_URL }}" "${{ github.sha }}"

Line by line:

  • on: push: tags: ["v*"] starts the workflow only when a pushed tag begins with v. The * is a wildcard that matches any ending, so v0.9.0-rc1 matches.
  • permissions: {contents: read, id-token: write} lets the job read the code and ask GitHub for an identity token. id-token: write is what makes the keyless login below possible.
  • google-github-actions/auth@v2 logs the job in to Google Cloud. workload_identity_provider names a trust relationship that someone set up in advance in Google Cloud. service_account names the identity the job will act as. Both values come from repository variables (vars.), which are not secret, so the workflow contains no key file.
  • The login works through OIDC (OpenID Connect, a standard way to prove identity without a password). GitHub gives the job a short-lived token that says which repository and tag it came from. Google checks that token against the trust set up in advance and issues short-lived credentials. No long-lived key is stored anywhere.
  • google-github-actions/setup-gcloud@v2 installs the gcloud command-line tool.
  • gcloud run deploy citypulse-api tells Cloud Run to create a new revision of the service named citypulse-api. --image "${{ vars.IMAGE }}:${{ github.sha }}" names the exact image: the image name followed by the tag equal to the commit SHA the tag points to. --region asia-south1 picks the Google Cloud region. --quiet stops the command asking questions, which would hang the runner.
  • ./scripts/smoke.sh "${{ vars.BASE_URL }}" "${{ github.sha }}" runs the smoke test against the live URL. It must exit with zero, or the job fails. The script checks that /v1/health returns the expected git_sha and that one real prediction request succeeds.

Rollback works by moving traffic, not by rebuilding. The example below is the rollback script from the slides.

The first line is the command you type. The later lines are what the script prints: it names the previous SHA, redeploys that image, and reports the result. In the lab you do the Cloud Run version of this with gcloud run services update-traffic citypulse-api --to-revisions=<previous>=100, which sends 100% of traffic to the previous revision.

Trap: Rebuilding in deploy.yml

If deploy.yml runs docker build again, you deploy code that CI never tested. Deploy the SHA CI already tested.

Trap: Putting DATABASE_URL in plain text

A database address with a password in it must be stored in the platform's secret manager and referenced by the service. A plain environment variable in the YAML file is visible to anyone who can read the repository.

Trap: No limit on instances

Without a maximum number of instances and a budget alert, a loop in the code can start many servers and spend credits. The slides suggest a maximum of two instances and a budget.

The worked example

Goal. Build a pipeline where a broken test blocks the deploy. You will use the test_app.py file from the course and a deploy job that waits for test.

Step 1: the tests. The file below is the gate. It is the same test file the course gives you, with indentation restored.

from app import aqi_band

def test_good():
    assert aqi_band(8) == "Good"

def test_moderate():
    assert aqi_band(30) == "Moderate"

def test_unhealthy():
    assert aqi_band(120) == "Unhealthy"

Line by line:

  • from app import aqi_band loads the function aqi_band from the file app.py. from ... import ... picks one name out of a module (a Python file).
  • def test_good(): defines a function. Pytest runs every function whose name starts with test_.
  • assert aqi_band(8) == "Good" calls aqi_band with the number 8 and checks that the answer is the text "Good". If the check is false, assert raises an error and the test fails.
  • The next two blocks follow the same pattern with other inputs. Thirty should give "Moderate", and 120 should give "Unhealthy".

Run it locally:

pytest finds the tests, runs them, and prints the summary. Three dots mean three passes.

Step 2: the tag script. The tag.sh script from the previous section gives the image its commit SHA. CI does the same thing with the metadata action.

Step 3: the workflow with dependencies. The workflow in the course has a test job and a deploy job. The deploy job uses needs: test, so GitHub starts it only after the test job passes.

name: ci
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt && pytest -q
  deploy:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - run: docker build -t citypulse:${GITHUB_SHA::7} .
      - run: docker push citypulse:${GITHUB_SHA::7}
      - run: ./deploy.sh citypulse:${GITHUB_SHA::7}

Line by line:

  • The test job is the same as before.
  • deploy: is a second job, at the same indentation as test:.
  • needs: test is the dependency. It makes deploy wait for test.
  • ${GITHUB_SHA::7} is a bash expression that takes the first seven characters of the commit SHA GitHub stores in GITHUB_SHA. The result is the same short SHA as git rev-parse --short HEAD.
  • The three run: lines build, push and deploy the image tagged with that short SHA.

Check the dependency from the terminal. This command needs the PyYAML library (pip install pyyaml):

The python3 -c runs the code in quotes. It loads the YAML file, reads the list of job names and the needs value of deploy, and prints them. The output shows that deploy needs test.

Step 4: a failing test. If you change aqi_band(8) so it returns "Poor", the test job fails, GitHub marks deploy as skipped, and no image is pushed. The result is one red run and no deployed change. That is the point of the gate.

Explanation. The tests are the inspection, needs is the rule that the next part waits for the inspection, and the SHA is the serial number that follows the part through every step.

The hands-on lab, step by step

The lab uses Amazon ECR, the AWS container registry, where the slides use GHCR. The job shape stays the same: test first, then build and push a full-SHA tag. Only the registry and the login change. Where a command uses a value from your lab sheet, replace the placeholder in angle brackets such as <region>.

Step 1: Create the ECR repository

What you do. Create a place in ECR where the CityPulse images will be stored. ECR stands for Elastic Container Registry, and aws is the AWS command-line tool, which must already be set up with the credentials on your lab sheet.

What you type.

aws ecr create-repository --repository-name citypulse-api --region <region>

aws ecr create-repository asks AWS to make a new repository. --repository-name citypulse-api names it. --region chooses the AWS region where it lives.

What you should see. A block of JSON text that includes a repositoryUri field ending in /citypulse-api.

How you know it worked. Run aws ecr describe-repositories --repository-names citypulse-api --region <region>. It prints the same repository. If it says the repository does not exist, the first command failed; read its error message.

Step 2: Add repository secrets

What you do. Store the sensitive values the lab names in GitHub's secret store, so the workflow can read them at run time.

What you type. The pattern from the course is shown below. Use the names and values from your lab sheet.

gh secret set REG_TOKEN --body "$REGISTRY_TOKEN"
gh secret list

gh is the GitHub command-line tool. gh secret set REG_TOKEN stores the value under the name REG_TOKEN. --body gives the value. "$REGISTRY_TOKEN" reads it from an environment variable on your machine, so the value is never typed into the command history. gh secret list shows the names that exist.

What you should see. A table with REG_TOKEN in the name column and a note such as "less than a minute ago" in the updated column. The value itself is never shown.

How you know it worked. The name appears in the list. Then check that no secret leaked into the repository with this search, which must print nothing:

grep -rnE '(ghp_|github_pat_|AKIA|password:|token:)' .github/

grep searches text for a pattern. -r searches all files in the folder, -n prints line numbers, and -E allows the pattern's | (which means "or"). The pattern lists the prefixes that common tokens start with and the words password: and token:. An empty output means nothing matched. If a line appears, remove it and revoke the token.

Step 3: Scaffold the workflow

What you do. Create the folder and file that GitHub reads for the workflow.

What you type.

mkdir -p .github/workflows
touch .github/workflows/ci.yml

mkdir -p creates the folder and any missing parent folders, and does not fail if the folder already exists. touch creates an empty file if it does not exist. Then open ci.yml in an editor and paste the start of the file: name: ci, on: [push] and jobs:.

What you should see. Running ls .github/workflows prints ci.yml.

How you know it worked. The file is in the right place, and git status lists it as a new file. If it is in the wrong folder, GitHub will not run it.

Step 4: The test job (the gate)

What you do. Add the test job so every push runs the tests first.

What you type. Add this under jobs: and keep the indentation:

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -r requirements.txt && pytest -q

test: is the job name. runs-on picks a fresh Ubuntu machine. The first step copies the repository, and the second installs the requirements and runs the tests, as explained in the GitHub Actions section.

What you should see. Locally, pytest -q prints 3 passed (or the number of tests your project has, all passing).

How you know it worked. Push the branch, then run gh run list. The newest run has a green tick next to test.

Step 5: The build-and-push job

What you do. Add a build-push job that depends on test and runs only on pushes to main.

What you type. Add the build-push block from the GitHub Actions section under jobs:, at the same indentation as test:. Then check the dependency:

python3 -c "import yaml;d=yaml.safe_load(open('.github/workflows/ci.yml'));print(list(d['jobs']),'| build-push needs',d['jobs']['build-push']['needs'])"

What you should see.

['test', 'build-push'] | build-push needs test

How you know it worked. The job names are listed, and build-push needs test. The if: line stays in the file, so pull requests will skip the job. On your next push to a branch, the Actions tab shows build-push as skipped.

Step 6: Understand the ECR login

What you do. Learn how CI logs in to ECR. You do not type this in the workflow. Your lab workflow runs the same logic as this command, and you run it once yourself to see it work.

What you type.

aws ecr get-login-password --region <region> | docker login --username AWS --password-stdin <account-id>.dkr.ecr.<region>.amazonaws.com

aws ecr get-login-password prints a temporary password for the registry. The vertical bar | is a pipe: it sends the output of the left command into the input of the right command. docker login reads the password from standard input because of --password-stdin, so the password never appears in your command history. --username AWS is a fixed username ECR expects. The last part is the address of the registry in your account.

What you should see.

Login Succeeded

How you know it worked. The message Login Succeeded appears. The password is temporary, so it stops working after a set period, which is why CI logs in fresh on every run.

Step 7: Trigger and verify

What you do. Send your commit to main, watch the run, and check that the image in the registry has the commit's SHA as its tag.

What you type.

git push origin main
gh run watch
git rev-parse origin/main
aws ecr describe-images --repository-name citypulse-api --image-ids imageTag=<full-sha> --region <region>

git push origin main sends your commits to the main branch on GitHub. gh run watch follows the latest run live. git rev-parse origin/main prints the full SHA of the commit on GitHub. The last command asks ECR for the image with that tag. Replace <full-sha> with the output of the third command.

What you should see. gh run watch shows test and then build-push ending with a green tick. The describe-images command prints JSON with an imageDigest field and the tag you asked for.

How you know it worked. The tag in the output equals the SHA printed by git rev-parse. That chain (commit, tag, image) is what makes a rollback safe later. If you also deploy with a tag, run curl -s <your-url>/v1/health | jq .git_sha and compare the result with the SHA. jq is a tool that reads JSON and prints one field; .git_sha selects that field, and -s (silent) hides the progress meter of curl, which is a tool for fetching web addresses.

Triggers and job conditions

What it is. A workflow starts when an event happens to the repository. An event is a named action, such as push, which sends new commits to a branch, or pull_request, which asks for one branch to be merged into another. The workflow lists its events under on:. Each job can also have an if: line, a condition that GitHub checks before the job starts. Two values are common in conditions. github.event_name holds the name of the event, such as push. github.ref holds the full name of the branch or tag, such as refs/heads/main. When the condition is false, GitHub skips the job.

on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: echo "running tests"
  publish:
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - run: echo "publishing"

on: [push, pull_request] starts the workflow for both events. test has no if:, so it runs every time. publish runs only when both halves of its condition are true. == means "equals" and && means "and". On a pull request the condition is false, so the Actions tab shows test with a green tick and publish as skipped. A skipped job is not a failure.

How it shows up in a case study. A CityPulse teammate pushes a branch called feature/bus-map. The Actions tab shows test in green and publish in grey. A new team member thinks the workflow has broken. The reasoning is short: the branch is not main, so the condition is false, and the skip is the rule working as designed. The branch is still tested, but nothing is published from it. The team would change the condition only if it decided that feature branches should publish.

Trap: Assuming every change publishes

The tempting answer is that every push, or every pull request, builds and pushes an image. The condition says otherwise: only a push to main passes it. Feature-branch pushes run the tests and stop there, and pull requests never reach the publish job.

Grouping jobs with needs

What it is. needs: names one or more jobs that must finish successfully before this job starts. It sets the order, and it also depends on the result. A job with needs: is skipped if any job it names did not succeed. Here is a small example with two jobs.

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - run: echo "lint passed"
  test:
    needs: lint
    runs-on: ubuntu-latest
    steps:
      - run: echo "tests passed"

lint has no needs:, so it starts at once. test waits until lint finishes. If lint fails, test is skipped. Expected output in the Actions tab: lint shows a green tick first, then test shows a green tick. needs also accepts a list, written as needs: [lint, test], which waits for every named job. A job never retries a failed job on its own. Each job starts on a fresh runner, so a file made in one job does not exist in the next unless you pass it on.

How it shows up in a case study. A CityPulse pipeline has lint, unit-tests and build, and build has needs: [lint, unit-tests]. On a push to main, lint passes and unit-tests shows a red cross because one test fails. The Actions tab shows build as skipped. Someone asks why the image was not built, and whether the build should be retried. The reasoning is that build starts only when every job it names succeeded. The fix is in the failing test, not in the needs: line. Once the test passes, the next push runs the build.

Trap: Thinking needs only sets the order

The tempting answer is that needs: controls order and ignores results. It does not. A failed job in the list stops every job that depends on it, and nothing is retried, so no broken image is pushed.

Secrets and tokens

What it is. A secret is a sensitive value, such as a password, an API key or a token. A token is a long string that proves who you are to a service. Secrets belong in the platform's secret store, not in files you commit to Git. A workflow reads a stored secret as secrets.NAME, and GitHub gives the value to the run only while it runs. GitHub hides secret values in the logs, so a printed secret appears as ***. GitHub also creates secrets.GITHUB_TOKEN for each run. It is short-lived and ends when the run ends. Here is a step that passes a secret to a script through an environment variable.

steps:
  - run: ./publish.sh
    env:
      API_KEY: ${{ secrets.API_KEY }}

The env: block sets the variable API_KEY for this step only. The script reads it as $API_KEY. The value is never written in the YAML file, so the file is safe to commit.

How it shows up in a case study. A CityPulse engineer needs a registry password in a workflow. To make the build pass quickly, they paste the password into ci.yml and commit it. A colleague says the repository is private, so it is fine. The reasoning is that the password is now in Git history, which every collaborator and every clone keeps, even after the line is deleted. The password must be revoked and replaced. The correct place for it is the secret store, read as secrets.REG_TOKEN.

Trap: Deleting the line and calling it fixed

The tempting answer is that removing the token from the file in a new commit solves the problem. The old commit still holds the value, so the token must be revoked, and a new one stored as a secret.

Image tagging with commit SHAs

What it is. A tag is a name attached to an image, such as latest, v0.9.0 or e610ea4. Tags are labels, and a label can be moved to a different image. A commit SHA is the identifier of a commit, a 40-character code. The short form is the first seven characters. If an image is tagged with the commit SHA, the tag names the code of that commit, and it does not move. A digest is a fingerprint of the image's contents, and two tags can point to the same digest. The example below tags an image with the short SHA of the commit that is checked out.

SHA=$(git rev-parse --short HEAD)
docker build -t citypulse:$SHA .
echo "built citypulse:$SHA"

git rev-parse --short HEAD prints the short SHA of the current commit, for example e610ea4. The docker build line names the image citypulse:e610ea4. If the team later pushes another image under latest, the old latest name points to the new build. The commit SHA tag does not move.

How it shows up in a case study. A city dashboard server runs the image citypulse:latest. A user reports a wrong band for one reading. Two engineers disagree about which code is live. The registry shows that latest has been moved twice since the release. The reasoning is that a moving label cannot tell you the code. The team checks the git_sha value from /v1/health on the running server. That value is a commit SHA, so it names the code exactly. From now on the server runs an explicit SHA tag, so the rollback target is clear.

Trap: Treating latest as a version number

The tempting answer is that latest is the newest release. It is only the last image pushed under that name, which may be a broken build. Name an exact SHA when you deploy or roll back.

Canary releases

What it is. A canary release sends a small share of real traffic, such as 5% of requests, to the new version. The old version serves the rest. The team watches the error rate and the response time. If the numbers are healthy, the share rises step by step, for example to 25%, 50% and 100%. If they are not, the new version's share goes back to 0%, and the old version serves everyone again. The steps might look like this, where each line is a decision.

Step 1: 5% of requests to version 2 for 10 minutes. Error rate 0.1%. Continue.
Step 2: 25% of requests to version 2 for 20 minutes. Error rate 0.1%. Continue.
Step 3: 100% of requests to version 2. Release complete.

The team does not move to the next line until the measures on the current line are acceptable. A canary needs a platform or a router that can split traffic by percentage.

How it shows up in a case study. The CityPulse API handles about 800 requests a minute. A new version changes how the air-quality band is rounded. The team sends 5% of traffic to it. After ten minutes the error rate is unchanged, but the response time for the new version is twice as high. The reasoning is that the change works but is slower, so the team holds the share at 5% and investigates. They do not raise the share to 100%, because more users would see the slowdown. If the slowdown continues, they set the share back to 0%.

Trap: Confusing canary with blue-green

Blue-green moves all traffic at once. A canary moves a share of traffic in steps, and it can stop at any step. The tempting answer is that both methods switch everyone at the same moment.

Blue-green deployments

What it is. A blue-green deployment keeps two identical environments. Blue is live and serves all users. Green is idle. The new version is deployed to green and tested there. Then the router is switched so that all traffic goes to green. Blue keeps running the previous version, so switching back to blue is the rollback. The table shows the state at three points in a release.

Stage Blue Green Live traffic goes to
Before Version 1, live Empty Blue
Deployed Version 1, live Version 2, tested Blue
Switched Version 1, idle Version 2, live Green

The cost is the second environment, which doubles the servers while both run. The benefit is speed: a switch changes a router setting rather than rebuilding or redeploying anything. A switch does not reverse changes made to shared data. If version 2 changed the database, the old version must still be able to read it.

How it shows up in a case study. A school's exam-results portal runs blue. On Friday the team deploys version 2 to green and runs the smoke test against green's private address. It passes, so they switch the load balancer. Two minutes later the error rate jumps. They switch the balancer back to blue, which still runs version 1. The reasoning is that the old version was never removed, so the rollback is one setting change. The team then checks whether version 2 changed anything in the database before it tries again.

Trap: Rebuilding the old image for rollback

The tempting answer is to rebuild version 1 when something goes wrong. With blue-green the old version is still running, so switching the router back is the rollback. Rebuilding is slower and may produce a different image.

Parallel jobs and runners

What it is. A job with no needs: line has no ordering rule. GitHub can start it at the same time as other jobs with no ordering rule, and each job runs on its own fresh runner. The order of the jobs in the file does not decide this. Because every runner starts clean, parallel jobs do not share a file system. A file written in one job is absent from another unless it is passed on as an artifact. An artifact is a file or folder that one job uploads and a later job downloads. The example below has two jobs with no ordering rule, so they can run together.

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - run: echo "lint"
  test:
    runs-on: ubuntu-latest
    steps:
      - run: echo "test"

Both jobs can start at once, and the Actions tab may show them running side by side. Neither can see a file that the other creates. To pass a report from lint to a later job, lint uploads it with actions/upload-artifact, and the later job downloads it with actions/download-artifact. A needs: line makes a job wait, but it does not copy files between runners.

How it shows up in a case study. The CityPulse workflow has lint, test and security-scan, and none of them has needs:. The lint job writes report.txt. The security-scan job reads the same file and fails with "No such file". The reasoning is that the two jobs run on different fresh runners, so the file never reached the scan job. The fix is to upload the report as an artifact in lint and download it in security-scan, and to add needs: lint if the scan must wait for it.

Trap: Sharing files between parallel jobs

The tempting answer is that all jobs in one run share one disk, or that jobs in the file run one after another. Neither is true. Jobs get separate runners, and only artifacts or outputs carry data between them.

Delivery versus deployment

What it is. Continuous integration means changes are merged often and checked automatically. Continuous delivery means every change produces a tested artifact, such as a container image, that is ready to ship. A person or a rule then decides when to ship it. Continuous deployment means a change that passes the checks goes into the live service automatically. The difference is the last step. Delivery stops at a stored, deployable artifact. Deployment puts that artifact into service. The table shows the two side by side.

Term What is produced Who or what decides to ship
Continuous delivery A tested image in the registry A person or a rule
Continuous deployment A new version in the live service The pipeline itself

In CityPulse, the build-and-push job runs on every merge to main, so each merge produces a tested image. Pushing a v* tag starts the deploy workflow, so the tag push is the decision to ship. Building an image is delivery. Running that image in the live service is deployment.

How it shows up in a case study. A CityPulse team merges a change to main. The pipeline builds and pushes a tested image, and the product manager says the release is finished. Nothing has changed for users yet. The reasoning is that the merge produced a deployable artifact, which is delivery. The release is finished only when someone pushes a version tag and the deploy workflow puts that exact image into the live service.

Trap: Calling the build deployment

The tempting answer is that pushing an image means the software is deployed. The image is only stored. Deployment starts when the image is run in a live service.

Expand-and-contract database migrations

What it is. A database migration is a change to the structure of a database, such as adding, renaming or removing a column. During a rolling update, the old version and the new version of the code run together for a while. A change that works for only one version breaks the other. Expand-and-contract keeps both versions working. First, expand: add the new column and let the new code write to both columns. Second, backfill: copy the old values into the new column. Third, switch reads to the new column. Fourth, contract: remove the old column in a later release, once no running version uses it. The first step looks like this.

ALTER TABLE readings ADD COLUMN pm25_ug REAL;

This statement adds a new empty column called pm25_ug to the table readings. The old column is untouched, so the old code keeps working. Rolling back the code does not undo a change to the schema. That is why the old column stays in place until the contract step.

How it shows up in a case study. The CityPulse team plans to rename the column pm25 to pm2_5_ug. The release rolls out over an hour, and during that hour old and new instances run together. A one-step rename would break the old instances, which still read pm25. The reasoning is that the team must expand first, let both versions work with both columns, and remove pm25 only in a later release. If a release has to be rolled back, the old code still finds its column.

Trap: Believing rollback also reverts the database

The tempting answer is that rolling back the code also undoes the schema change. It does not. Rollback changes the code only. A renamed or dropped column stays changed, so the old version must be able to work with the new schema.

Reproducible builds

What it is. A build is reproducible when the same inputs always give the same result. The inputs are the source code, the exact versions of the libraries, and the base image that the container starts from. If a library version is not pinned, the installer may choose a newer version next time, and the build changes without any change in your repository. Pinning means writing the exact version. In a requirements file, example-lib==1.4.2 pins one library. In a Dockerfile, FROM python:3.11-slim names a tag that the image maintainers update over time. A tag with the full version, such as python:3.11.9-slim, changes far less often.

## requirements.txt
example-lib==1.4.2

## Dockerfile
FROM python:3.11.9-slim

The == means the installer must use exactly that version. Two builds of the same commit with these files install the same library and start from the same base.

How it shows up in a case study. A CityPulse build passed on Monday. On Tuesday the same commit is rebuilt by a different engineer, and the container crashes at start-up. The base image tag python:3.11-slim has moved to a newer build, and one library behaves differently on it. The reasoning is that nothing in the repository changed, so an unpinned input changed. The fix is to pin the base image to a full version and pin every library, then rebuild and test.

Trap: Using latest or an unpinned requirements file

The tempting answer is that the newest version is the safe choice. It is safe only when you control the test. A build that depends on latest or on an unpinned library can change without any change in your repository.

The graded lab

The graded lab is a Python problem with visible and hidden tests. You write a small set of functions. The visible tests run as you work, and the hidden tests run when you submit. This section explains the real task in plain words and teaches the Python you need. It then sets a twin problem: a different task with the same kinds of rules. You will not be given a solution to the real lab, and the examples below do not solve it.

The task in plain words

The scenario. The CityPulse pipeline may release the API only when every stage is green. Each release also gets a semantic version bump. A semantic version has three numbers, MAJOR.MINOR.PATCH, such as 1.4.9. A bump raises one of the numbers and resets the ones to its right to zero. Your starter file contains three functions. Keep their names and parameters exactly as the starter file gives them.

should_deploy(stages) takes a list of stages. Each stage is a dictionary with a name (text) and a status (text).

  • It returns True only when the list is not empty and every stage has a status equal to the text "pass".
  • It returns False in every other case, including an empty list and any list with one stage that is not "pass".
  • It returns the bool value itself, True or False, not a count or a truthy value.

bump_version(current, level) takes a version text such as "1.4.9" and a level text.

  • The level is "major", "minor" or "patch".
  • "major" adds one to the major number and sets the minor and patch numbers to zero. For example, bump_version("1.4.9", "major") should give "2.0.0".
  • "minor" adds one to the minor number and sets the patch number to zero. For example, bump_version("1.4.9", "minor") should give "1.5.0".
  • "patch" adds one to the patch number and changes nothing else. For example, bump_version("2.0.0", "patch") should give "2.0.1".
  • It returns the new version as text in the same MAJOR.MINOR.PATCH form.

pipeline_result(stages, current, level) combines the two.

  • If should_deploy is true for the stages, it returns the result of bump_version for the current version and the level.
  • Otherwise it returns the exact text "BLOCKED".

The statement gives two examples. bump_version("1.4.9", "minor") gives '1.5.0'. pipeline_result([{"name": "build", "status": "pass"}], "2.0.0", "patch") gives '2.0.1'.

Limits. Each run may take up to 30 seconds and use up to 128 MB of memory. A solution that does ordinary list and string work is far inside both limits.

Two hidden tests are worth 15 points together, so the full mark is 100. A hidden test is a check whose inputs are not shown to you. What each function needs

The real lab uses a few Python ideas. Each one is taught below with a small example about something unrelated to the lab, so the example does not solve the task. Try each one in a scratch file before you use it.

Dictionaries and get. A dictionary maps keys to values. dict[key] raises an error if the key is missing. dict.get(key, default) returns the default instead.

stock = {"apples": 3, "plums": 0}
print(stock.get("apples", 0))
print(stock.get("pears", 0))

Output: 3, then 0. The second key is missing, so get returns the default.

all over a list. all(...) returns True only when every item it checks is true. The important edge is an empty input: all over nothing is True. Any check that treats an empty list as a success needs a separate test for emptiness.

readings = [12, 18, 9]
print(all(r < 15 for r in readings))
print(all(r < 15 for r in []))

Output: False, then True. The first list has one reading that is not below 15. The empty list is True because nothing fails the check.

Text, split and int. split cuts text at a separator and returns a list of pieces, which are still text. int turns digit text into a number. isdigit tells you whether the text is made only of digits.

parts = "red,green,blue".split(",")
print(parts)
print("42".isdigit(), "4a".isdigit(), "".isdigit())
print(int("42") + 1)

Output: ['red', 'green', 'blue'], then True False False, then 43. An empty string is not digits, so "".isdigit() is False.

Building text with f-strings and join. An f-string puts values into text. join puts a list of text pieces together with a separator.

name, count = "bridges", 4
print(f"{count} {name} checked")
print("-".join(["north", "east"]))

Output: 4 bridges checked, then north-east. Inside an f-string, {count} is replaced by the value of count.

isinstance and the bool trap. isinstance(value, int) checks the type. A bool is a subclass of int, so True also passes an int check.

print(isinstance(True, int))
print(isinstance(7, int))
print(isinstance("7", int))
print(isinstance(True, bool))

Output: True, True, False, True. To reject booleans when you want a whole number, check for bool as well.

Rounding. round(number, digits) rounds to a set number of decimal places. round(number) with no digits gives a whole number. Python rounds exact halves to the nearest even whole number.

print(round(2.5))
print(round(3.14159, 2))
print(round(7 / 2))

Output: 2, then 3.14, then 4. Notice that round(2.5) is 2. Round once, at the end of a calculation, not in the middle.

Returning versus printing. A function sends its answer back with return. A function that only prints gives back None, which is Python's word for nothing. A test receives the return value, so a printed answer does not count.

def double(n):
    print(n * 2)

result = double(4)
print(result)

Output: 8, then None. The function printed 8 and returned nothing, so result is None. Use return for every answer the tests check.

A method that works for every graded lab

  1. Read the starter file. Note the three function names, their parameters and their order. Do not rename anything.
  2. Write the examples from the statement as assert lines first. They are the first tests you will run.
  3. Add your own assert lines for every row of the rules table above. Write them before you write the code they test.
  4. Implement one function at a time. After each function, run all the assert lines. Fix the function before you start the next one.
  5. Check types and rounding last. Confirm that the return values are the right type: True or False for the gate, text for the version and "BLOCKED" for the blocked result.
  6. Run the visible tests. Read every failure message, because each one names the rule it broke.
  7. Submit once, when every assert you wrote passes and the visible tests pass.

Worked twin problem

The twin task. A library lends books, and a late return costs a fine. Each loan is a dictionary with a title (text) and a due day (a whole number). The library counts days as whole numbers. Write four functions.

  • days_overdue(due, today) returns the number of days a loan is late. If the book is not late, it returns 0. Both inputs must be whole numbers, and a boolean is not accepted. Otherwise it raises ValueError.
  • fine_for(days, rate) returns the fine for a number of late days at a rate per day. A zero or negative number of days gives 0. The fine never goes above 300.
  • ranked_fines(loans, today, rate) returns a list of (title, fine) pairs for every loan with a fine above zero. The list is sorted by fine, largest first. Loans with equal fines are sorted by title, A to Z.
  • average_fine(loans, today, rate) returns the average fine over every loan, including loans with no fine. It is rounded to two decimal places, and an empty list gives 0.0.

The solution. The code below is the full answer for the twin task. Read it, then try to write your own version before you check.

def days_overdue(due, today):
    for value in (due, today):
        if not isinstance(value, int) or isinstance(value, bool):
            raise ValueError("days must be whole numbers")
    if today <= due:
        return 0
    return today - due

def fine_for(days, rate):
    if days <= 0:
        return 0
    return min(days * rate, 300)

def ranked_fines(loans, today, rate):
    found = []
    for loan in loans:
        days = days_overdue(loan["due"], today)
        amount = fine_for(days, rate)
        if amount > 0:
            found.append((loan["title"], amount))
    found.sort(key=lambda pair: (-pair[1], pair[0]))
    return found

def average_fine(loans, today, rate):
    if not loans:
        return 0.0
    total = 0
    for loan in loans:
        total += fine_for(days_overdue(loan["due"], today), rate)
    return round(total / len(loans), 2)

Explanation, function by function.

  • days_overdue first checks both inputs. The loop runs over the pair (due, today), so one check covers both. isinstance(value, int) accepts whole numbers, and isinstance(value, bool) rejects True and False, because a boolean is also an int. If today is not after due, the book is not late, and the function returns 0. Otherwise the difference is the number of late days. The first assert lines check the boundary: a book due on day 10 and returned on day 10 is not late.
  • fine_for returns 0 for zero or negative days. For a positive number of days, days * rate is the fine, and min(..., 300) stops the fine at the cap. fine_for(100, 5) would be 500, so the cap gives 300.
  • ranked_fines builds the list one loan at a time. A loan with no fine is left out by the if amount > 0 check. The sort call uses a key, which is a tuple. The first part, -pair[1], is the negated fine, so the largest fine sorts first. The second part, pair[0], is the title, which breaks ties in A to Z order. The assert on ties checks this with two loans that have the same fine. The assert on loans[0] checks that the function does not change the input list.
  • average_fine returns 0.0 for an empty list before any division, which avoids a division by zero. It adds up the fines over all loans, including zeros, then divides by the number of loans. The rounding happens once, at the end. For the short list, the total fine is 5, and 5 / 3 is 1.666..., which rounds to 1.67.

Say it out loud

Why must the build job wait for the tests?

Because a build that starts before the tests finish can push an image that fails them. The needs: test line makes GitHub skip the build when the tests fail, so a broken change never reaches the registry. This is the gate the course describes: a red suite stops everything. In a viva you can add that the same rule means a failing change simply does not produce a deployable image.

Why tag images with the commit SHA and not latest?

A SHA always points to one commit, so you can say exactly which code is running. The tag latest moves every time someone pushes, so two servers may be running different code under the same name. A SHA also makes rollback precise: you deploy the previous SHA, not a guess. I would tell the examiner that the SHA is the serial number of the part from the factory picture.

How does a secret reach the workflow without being in the repository?

The value is stored in the platform's secret store, and GitHub injects it into the run when the workflow asks for it with secrets.NAME. The value is hidden from logs, and it is not written into the repository, so it does not appear in Git history. For the deployment, the cloud login uses OIDC, which gives a short-lived token and no stored key at all. The rule I follow is that a secret should never be typed into a file I commit.

What does a rollback actually do, and what does it not do?

A rollback moves traffic back to the previous revision, which is still stored by the platform, so no image is rebuilt. It does not undo changes to the database, and it does not undo data written by the new version. That is why a schema change must be backward compatible before a release that might be rolled back. I would say the rollback restores the code path, and the database has to be designed to support both versions.

What is the difference between continuous delivery and continuous deployment in CityPulse?

Continuous delivery means every change produces a tested image that is ready to ship. In CityPulse, every merge to main does that, because the build-push job runs on each push. Continuous deployment means the change goes live automatically. Here, pushing a v* tag is the decision to deploy, so the deploy workflow starts from that tag. I would add that the deployed image is the one CI already tested, never a new build.
