What you are building

You are building a small air-quality monitor for four sensor stations, ST-01 to ST-04. A person opens a web page in a browser and sees a table of each station's average PM2.5 reading. PM2.5 means very fine particles in the air, measured in micrograms per cubic metre (µg/m³). The person can also pick an hour of the day, type in the last reading, press a button and get a predicted value with a label such as Unhealthy.

Two programs produce this. The first is an API (application programming interface), a program that answers requests from other programs over a network. The second is the dashboard, which is the web page itself. Each program runs in a container, a sealed package that holds the program and everything it needs, so it behaves the same on any machine. Every API request is written to a log as one line of structured data, and a health page at /metrics counts requests and errors. When you push code to the main branch of your Git repository, a robot run by GitHub Actions tests the code, builds the containers and deploys them. Nobody runs those steps by hand.

Read the flow below as a story. Data and a trained model are read once when the API starts. The dashboard then asks the API for numbers, and the API replies in JSON, which is plain text in a structured layout that programs can read.

Starting from zero

Python is the programming language used for everything in this project. A program is a text file of instructions, and Python runs those instructions line by line from top to bottom. You will write the code in editors and run it from a terminal, which is a window where you type commands. The Day chapter on Python for engineers covers the language in depth.

pandas is a library for tables of data. A library is code written by someone else that you can import and call. In pandas, a table is a DataFrame, with named columns and numbered rows. Steps 2 to 5 use it to read the CSV file, filter rows and group them. The earlier Day chapter on pandas covers it in depth.

scikit-learn is a library of standard machine-learning methods. Machine learning means fitting a model to examples so that it can predict something for new inputs. This project uses a LinearRegression, which draws the straight line through the examples that fits them best. The model is small, fast and free to run. The Day chapter on scikit-learn covers the method in depth.

matplotlib draws charts. You use it in step 6 to save a PNG image. It is set to the "Agg" mode, which draws to a file rather than a window, so it works on a server with no screen.

joblib saves a Python object, such as a trained model, to a file and loads it back later. The file model.joblib is the link between training and serving. The API never trains a model, it only loads this file.

FastAPI is a framework for building APIs in Python. A framework is a set of ready-made parts that you fill in. In FastAPI, you write a Python function and decorate it with a route such as @app.get("/health"). The decorator tells FastAPI which web address calls the function. Pydantic is the library FastAPI uses to check incoming data against types and limits, such as "hour must be a whole number from 0 to 23". The FastAPI chapter covers routes and Pydantic in depth.

JSON is a text format for structured data, built from key and value pairs in braces, for example {"status": "ok"}. Programs exchange JSON, and logs written as JSON can be searched by machines. In step 12 each log entry is one JSON object on one line.

Streamlit turns a Python script into a web page. You call functions such as st.title and st.dataframe, and Streamlit draws the page. You do not write any HTML. The page reruns from the top every time a user changes a control.

transformers, torch and Qwen2.5 are the libraries and the model used for the advisory in step 14. The transformers library downloads a language model and runs it. torch is the engine that does the arithmetic. Qwen2.5-0.5B-Instruct is a small language model, with about half a billion parameters, that can run on a normal CPU, which is the main processor of a computer. It is free and needs no API key.

Docker packages a program and its environment into an image. An image is a read-only template. When you start an image, Docker creates a running container from it. A Dockerfile is a text file of instructions that builds an image, and docker-compose is a tool that starts several containers from one file called docker-compose.yml. The Docker chapters cover both in depth.

pytest runs tests. A test is a function that calls your code and checks a result with assert, which stops the test with an error when a statement is false. pytest reports how many tests passed. You will meet it in step 17.

GitHub Actions runs a list of commands on a fresh machine every time something happens in your repository, such as a push. The list is written in a YAML file, a text format that uses indentation to show structure. Each list of commands is a job.

curl sends a web request from the terminal, and jq formats and filters JSON text. You use them to check the API without a browser. The pipe symbol | sends the output of one command into the next.

Step 2 — Ingest the raw readings

What you are doing: generating a week of hourly PM2.5 readings for four stations, with three deliberately bad rows so that the cleaner has something to catch.

STATIONS = {"ST-01":42,"ST-02":55,
            "ST-03":38,"ST-04":61}   # baselines
for h in range(168):                 # 7 days, hourly
    rush = 1.3 if h%24 in RUSH else 0.8
    for s,base in STATIONS.items():
        val = base + 8*gauss(1,.2)*rush + gauss(0,4)
        rows.append([s, ts, "pm25", round(val,1)])
rows += [["ST-02",...,-3.0], ["ST-09",...],
         ["ST-01","bad-ts",...]]   # 3 planted faults

The extract omits some lines: the imports, the definition of RUSH (the set of rush-hour hours), the creation of the rows list, and the line that builds ts. The ... marks parts the extract leaves out. The full file is in the course workbook, so copy the missing lines from there rather than guessing them.

STATIONS is a dictionary, a set of key and value pairs. Each key is a station id and each value is that station's typical reading, its baseline. range(168) gives the numbers 0 to 167, which is 7 days times 24 hours. h%24 is the remainder when h is divided by 24, so it gives the hour of the day. gauss(1, .2) draws a random number from a bell-shaped distribution with mean 1 and spread 0.2, from Python's standard random module. Each reading is the baseline, plus 8 times a random factor and the rush-hour multiplier, plus a small random noise. rows.append adds one row to the list. round(val,1) keeps one decimal place. The last line adds three faults on purpose: a negative value, a station that does not exist (ST-09), and a timestamp that is not a date.

Expected output: wrote data/readings.csv: 675 rows.

What it proves: 4 stations times 168 hours gives 672 good rows, and 672 plus 3 faults gives 675. The file has exactly the rows you planned.

Step 3 — Clean and validate

What you are doing: loading the CSV, turning the timestamps into real dates, and removing unknown stations, impossible values and duplicates.

def load(path="data/readings.csv"):
    df = pd.read_csv(path)
    df["ts"] = pd.to_datetime(df["ts"],
                              errors="coerce")
    df = df[df.station_id.isin(STATIONS)]
    df = df[df.value.between(0, 500)]
    df = (df.dropna(subset=["ts"])
            .drop_duplicates(["station_id","ts"]))
    print(f"clean: {before} -> {len(df)} rows")
    return df

The extract omits one line. The print statement uses before, which must be set straight after the CSV is read, as before = len(df), so that the message shows the row count before cleaning. The line is needed for the output shown below.

def load(path=...) defines a function called load. A function is a named block of code you can call with inputs and that gives back a result. The path has a default value, so you can call load() with no argument. pd.read_csv(path) reads the file into a DataFrame. pd.to_datetime(..., errors="coerce") turns text into dates, and any value it cannot read becomes NaT, pandas' "not a time", instead of crashing. df.station_id.isin(STATIONS) gives True for rows whose station is in the dictionary, and df[...] keeps only those rows. df.value.between(0, 500) keeps values from 0 to 500 inclusive. dropna(subset=["ts"]) removes rows whose timestamp is NaT. drop_duplicates(["station_id","ts"]) keeps the first row for each station and time pair. The brackets around the two lines let you split one chain across lines. The f-string in print puts variable values into the text inside braces.

Expected output: clean: 675 -> 672 rows (3 dropped).

What it proves: exactly the three planted faults are removed. This is the function the model, the API and the dashboard all depend on.

This is the step to watch slowly. The trace below shows the same filtering logic on a short list, so that you can see the variables change. It uses a plain Python list instead of a DataFrame, so each reading is visible.

Trap: Checking the wrong list

A common error is to test value >= 0 but forget the upper limit of 500. The extract checks both ends with between(0, 500). Keep both, because an impossible value above 500 is as wrong as a negative one.

Step 4 — Guard it with a data-quality gate

What you are doing: writing assertions that stop the run when the data breaks an assumption.

df = load()
assert df.value.min() >= 0,   "negative reading"
assert df.value.max() <= 500, "out of range"
assert df.groupby(["station_id","ts"]) \
         .size().max() == 1,  "duplicate"
print("data-quality checks: 3 passed")

df = load() runs the cleaner from step 3. Each assert line has a condition and a message after the comma. If the condition is False, Python stops with an AssertionError and shows the message. df.value.min() finds the smallest value in the column. The backslash at the end of the third line joins it to the next line, so the statement continues. groupby(...).size() counts rows per station and time pair, and .max() == 1 checks that no pair appears twice.

Expected output: the cleaner message, then data-quality checks: 3 passed.

What it proves: the assumptions are now code. If a future feed contains a negative value, the script fails with the message "negative reading", and the bad data never reaches the model.

Step 5 — Aggregate per station

What you are doing: summarising the clean readings into one row per station, which is the shape the API will serve.

def per_station(df):
    return (df.groupby("station_id")["value"]
              .agg(["count", "mean", "max"])
              .round(1))

groupby("station_id") splits the rows into one group per station. ["value"] selects the value column inside each group. .agg(["count", "mean", "max"]) computes three summaries for each group: the number of rows, the average and the highest value. .round(1) rounds all results to one decimal place for display.

Expected output:

            count  mean   max
station_id
ST-01         168  50.3  62.9
ST-02         168  63.2  74.9
ST-03         168  46.4  61.3
ST-04         168  68.8  82.0

What it proves: each station has 168 readings, one per hour for a week. ST-04 has the highest mean, 68.8 µg/m³, so it is the dirtiest station in this data.

Step 6 — Chart the trends

What you are doing: drawing a three-hour rolling average for each station and saving it as trend.png.

import matplotlib; matplotlib.use("Agg")

df = load().set_index("ts")
fig, ax = plt.subplots(figsize=(7.2, 3.1))

matplotlib.use("Agg") must run before pyplot is imported, and it chooses the drawing mode that writes to a file. set_index("ts") makes the timestamp the row label, which pandas needs for time-based resampling. plt.subplots creates a figure, the whole picture, and one axes, the area with the axis lines. The loop draws one line per station. resample("3h").mean() groups the hourly values into three-hour blocks and averages each block. label=sid names the line for the legend. ax.legend(ncol=4) places the legend in four columns. savefig writes the picture; dpi=110 sets the resolution in dots per inch.

Expected output: wrote trend.png, and a file of about 77 KB.

What it proves: the rush-hour peaks are visible in the picture, and the image is saved without any screen.

Step 7 — Engineer features

What you are doing: adding two columns the model can learn from: the hour of the day and the previous reading at the same station.

def features(df):
    df = df.sort_values(["station_id","ts"]).copy()
    df["hour"] = df.ts.dt.hour
    df["prev"] = (df.groupby("station_id")
                    .value.shift(1))   # lag-1
    return df.dropna(subset=["prev"])

A feature is an input column the model uses. sort_values puts each station's rows in time order, which matters because the lag depends on order. .copy() makes a new table, so the original is not changed. df.ts.dt.hour reads the hour from each timestamp. shift(1) moves each value down one row inside its group, so each row gets the previous reading. The group is needed so that the first reading of one station does not take the last reading of another. dropna(subset=["prev"]) removes the first row of each station, which has no previous reading.

$ python -c "from train import *; print(features(load()).head())"

python -c runs a line of Python typed on the command line. from train import * imports everything from train.py. head() prints the first five rows.

Expected output: a table with columns station_id, hour, prev and value, with rows such as ST-01 at hour 1 with prev 50.1 and value 50.7.

What it proves: each row now carries an hour and the previous reading, which are the two inputs of the model.

Step 8 — Train, evaluate and persist

What you are doing: fitting a linear model, testing it on rows it has not seen, and saving it.

X, y = df[["hour","prev"]], df["value"]
Xtr,Xte,ytr,yte = train_test_split(
    X, y, test_size=.2, random_state=42)
m = LinearRegression().fit(Xtr, ytr)
pred = m.predict(Xte)
print(f"MAE {mean_absolute_error(yte,pred):.2f}"
      f"   R2 {r2_score(yte,pred):.3f}")
joblib.dump(m, "model.joblib")

X holds the inputs and y holds the answer the model should predict. train_test_split shuffles the rows and sets 20 percent aside as the test set, so test_size=.2. random_state=42 fixes the shuffle, so the same split happens every run. fit learns the best straight-line relation from the training rows. predict produces values for the test rows. MAE is the mean absolute error, the average size of the miss in µg/m³. R2 is the coefficient of determination, a score where 1 is perfect and 0 means no better than guessing the average. joblib.dump writes the fitted model to model.joblib.

The imports at the top of train.py are needed: train_test_split comes from sklearn.model_selection, LinearRegression from sklearn.linear_model, and the two metrics from sklearn.metrics. The extract does not show them.

Expected output:

$ python train.py
clean: 675 -> 672 rows (3 dropped)
MAE 4.89 µg/m³   R2 0.653
saved model.joblib

What it proves: the average error is 4.89 µg/m³, which the course treats as a useful baseline. The saved file, about 857 bytes, is the contract between training and serving.

Step 9 — Reload and predict

What you are doing: checking that the saved file works on its own, outside the app.

import joblib, pandas as pd
model = joblib.load("model.joblib")
x = pd.DataFrame([{"hour": 8, "prev": 55.0}])
print(round(float(model.predict(x)[0]), 1),

joblib.load reads the file back into a working model. pd.DataFrame([{...}]) builds a one-row table with the same column names the model was trained on, and the names must match exactly. model.predict(x) returns an array with one value, [0] takes that value, and float turns it into an ordinary number. round(..., 1) rounds it.

Expected output: reloaded model.joblib; followed by predict(hour=8, prev=55) -> 55.2 ug/m3.

What it proves: the API in part C can use the same file in the same way.

Part C — Serve it, observably

Step 10 — API skeleton and station stats

What you are doing: wrapping the pipeline and the model in FastAPI, and serving a health check and the station table.

app = FastAPI(title="CityPulse", version="2.0")
_df = load()
_model = joblib.load("model.joblib")
@app.get("/health")
def health():
    return {"status": "ok", "version": app.version}
@app.get("/stations")

app = FastAPI(...) creates the application object. _df = load() and _model = joblib.load(...) run once, when the module is imported at startup. Every request then reuses them, so no request waits for training or file reading. The leading underscore is a convention meaning "private to this file". @app.get("/health") registers the function below it for GET requests to that address. A GET request asks for data, and a POST request, used later, sends data. reset_index() turns the station name from a row label into an ordinary column. to_dict("records") turns the table into a list of dictionaries, one per station, which FastAPI converts to JSON.

$ curl -s localhost:8000/stations | jq '.[0]'

curl -s fetches the address and -s hides the progress meter. The pipe passes the JSON to jq, and '.[0]' selects the first item of the list.

Expected output: a JSON object with station_id "ST-01", count 168, mean 50.3 and max 62.9.

What it proves: the service is running, and /stations returns the aggregate in a form the dashboard can render.

Step 11 — Predict, with validation

What you are doing: accepting an hour and the last reading, returning a prediction and a category, and rejecting impossible input.

class PredictIn(BaseModel):
    hour: int   = Field(ge=0, le=23)
    prev: float = Field(ge=0, le=500)
@app.post("/predict")
def predict(p: PredictIn):
    X = pd.DataFrame([{"hour":p.hour,"prev":p.prev}])
    pm25 = round(float(_model.predict(X)[0]), 1)
    return {"pm25": pm25, "category": category(pm25)}

class PredictIn(BaseModel) defines the shape of an incoming request. hour: int means the value must be a whole number. Field(ge=0, le=23) adds the limits: "greater than or equal to 0" and "less than or equal to 23". If a request breaks these rules, FastAPI replies with status 422 and an explanation, before your function runs. @app.post handles POST requests, which carry data in the body. The parameter p: PredictIn tells FastAPI to parse and check the body against the class.

The function category is used but the extract does not show it. It turns a number into a label such as Unhealthy. The course file defines its bands. Copy them from the course material rather than inventing your own, because the expected output below depends on them.

$ curl -s -XPOST localhost:8000/predict -H "Content-Type: application/json" -d '{"hour":19,"prev":70}'

-XPOST sets the request method to POST. -H adds a header that tells the server the body is JSON, which FastAPI needs. -d sends the text that follows as the body.

Expected output: {"pm25": 67.3, "category": "Unhealthy"}. With hour set to 99, the reply is status 422 and the message "Input should be less than or equal to 23".

What it proves: the endpoint returns a checked prediction, and bad input gets a clear error.

Step 12 — Structured JSON logging

What you are doing: replacing print statements with JSON log lines, and adding one middleware that logs every request.

class JsonFormatter(logging.Formatter):
    def format(self, r):
        return json.dumps({"level": r.levelname,
          "msg": r.getMessage(), **vars(r).get(
          "extra", {})})
@app.middleware("http")
async def observe(req, call_next):
    t0 = time.time(); resp = await call_next(req)
    ms = (time.time()-t0)*1000
    log.info("request", extra={"extra":{"path":
      req.url.path,"status":resp.status_code,
      "ms":round(ms,1)}})
    return resp

A formatter controls how a log record becomes text. class JsonFormatter(logging.Formatter) creates a formatter that inherits from Python's built-in one, and format replaces its output. json.dumps turns a dictionary into a JSON string. **vars(r).get("extra", {}) copies in any extra fields attached to the log record, using **, which unpacks a dictionary into the surrounding one.

A middleware is code that runs around every request. @app.middleware("http") registers it. t0 = time.time() records the start time. await call_next(req) passes the request on to the route and waits for the response, which is why the keyword await appears. ms is the elapsed time in milliseconds. log.info(...) writes one log record, with the path, status code and latency in its extra field.

The extract does not show how log is created or how JsonFormatter is attached to a handler. Standard practice is log = logging.getLogger(__name__) plus a handler that uses JsonFormatter. If your output is plain text rather than JSON, the handler is not using this formatter.

{"level":"INFO","msg":"request","path":"/predict","status":422,"ms":0.4}

Step 13 — A /metrics health view

What you are doing: counting requests, errors and latency inside the process, and exposing the counts at /metrics.

class Metrics:
    def observe(self, path, status, ms):
        self.requests[path] += 1
        if status >= 400: self.errors[path] += 1
        self.latency_ms.append(ms)
    def snapshot(self):
        lat = sorted(self.latency_ms) or [0]
        return {"uptime_s": ..., "requests_total":
          sum(self.requests.values()),
          "errors_total": sum(self.errors.values()),
          "p50_ms": lat[len(lat)//2]}

A class groups data and the functions that work on it. self refers to the object itself. self.requests[path] += 1 adds one to a counter for that path. For this to work without errors, self.requests must start as a counter that gives 0 for a new key, such as collections.Counter or defaultdict(int). status >= 400 treats 4xx and 5xx responses as errors. append adds a latency value to a list. In snapshot, sorted puts the latencies in order, and or [0] supplies a default when the list is empty. lat[len(lat)//2] picks the middle value, which is the median, also called p50. The // operator divides and drops the remainder.

The extract shows "uptime_s": ... without its calculation, and the example output includes a by_path field that the snapshot code does not build. Work out both from the course file, and make sure your snapshot returns every field the example shows.

Part D — Plain-English advice

Step 14 — Advisory from a free CPU model

What you are doing: asking a small language model for one sentence of health advice about a station's reading.

M = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(M)
llm = AutoModelForCausalLM.from_pretrained(M)
def advisory(station, pm25, category):
    msgs = [{"role":"system","content":
             "Answer in ONE short sentence."},
            {"role":"user","content":f"PM2.5 at "
             f"{station} is {pm25} ({category})."}]
    ids = tok(tok.apply_chat_template(msgs,
      tokenize=False, add_generation_prompt=True),
      return_tensors="pt")
    out = llm.generate(**ids, max_new_tokens=50)
    return tok.decode(out[0][ids.input_ids
      .shape[1]:], skip_special_tokens=True)

M is the name of the model on the Hugging Face model hub, a public library of models. AutoTokenizer converts text into the numbers the model reads, and AutoModelForCausalLM loads a model that writes text one token at a time. A token is a word or a piece of a word. The msgs list is a chat: a system message sets the rule, and a user message holds the question. apply_chat_template wraps the chat in the layout this model was trained to expect. return_tensors="pt" asks for PyTorch arrays. generate writes new tokens, and max_new_tokens=50 caps the reply at 50 tokens. The last line keeps only the new tokens, by skipping the length of the prompt, and turns them back into text.

The model is not in the Dockerfile, so the first call downloads it from the hub. The container needs network access the first time it runs advisory().

Challenge 1 — Persist the metrics (easy, data)

Challenge 2 — Alert on model drift (medium, model)

What is asked. In train.py, write the test MAE to a file called model_card.json. Add a check that fails the run with exit code 1 when MAE is above 6.0, so a bad retrain cannot be saved.

Ideas you need. A JSON file is written with the json module. sys.exit(1) stops a script with a failure code. Exit codes are how a program tells the shell or CI that it failed. Order of steps matters: a save must come after a check.

Plan of attack. 1. Compute the test MAE as in step 8, and write it to model_card.json. 2. Move the joblib.dump line so that it runs only after the check passes. 3. Challenge 3 — Readiness versus liveness (medium, API)

What is asked. Split /health into /livez, which always returns 200, and /readyz, which returns 200 only once the model is loaded. Point the compose healthcheck at /readyz.

Done when: "The UI starts only after /readyz returns 200; /livez answers during startup."

Ideas you need. Liveness means the process is running. Readiness means it can serve real requests. A healthcheck decides when a container counts as healthy. HTTP status codes, where 200 means success and 503 is the usual code for "not ready yet".

Plan of attack. 1. Write /livez to return a success status unconditionally. 2. Write /readyz to check that _model and _df exist and are usable, then return 200. Otherwise return 503. 3. Keep /health working, or make it an alias, so that existing tests still pass. 4. Change the compose healthcheck to call /readyz with the full URL. 5. Start the stack with docker compose up and watch the order of the containers. 6. Call /livez while the api is still starting, to confirm it answers.

Mistakes that fail the test. Making /readyz always return 200, which defeats the point. Loading the model lazily inside a request, which hides the not-ready state. Leaving the healthcheck on /health, so the UI starts before the model is loaded.

Challenge 4 — Cache the LLM advisory (hard, LLM)

What is asked. Add GET /advisory/{station} that returns the Qwen2.5 advisory for the station's latest reading. Memoise the result per (station, category), so repeat calls skip generation and log a cache hit.

Done when: "A second call to /advisory/ST-04 logs cache_hit=true and returns instantly."

Ideas you need. A path parameter, written in braces in the route, is read into the function's argument. Memoising means remembering a result for a given input. A dictionary keyed by a tuple, such as (station, category), works well. The model is slow, so a cache hit should skip generate().

Plan of attack. 1. Find the latest reading for the station in _df, and compute its category with the same function the predict endpoint uses. 2. Build the cache key from the station and the category, as a tuple. 3. If the key is in the cache, log cache_hit=true with the structured logger and return the stored text. 4. Mistakes that fail the test. Using only the station as the key, which returns stale advice when the category changes. Using print instead of the structured logger, so the log line is not JSON. Challenge 5 — Zero-downtime rollout (hard, CI/CD)

What is asked. Extend the deploy job so that it starts the new image, polls /readyz until it is healthy, switches traffic and stops the old container. If /readyz never passes, roll back automatically.

Done when: "A push with a failing /readyz leaves the previous version serving and the run is marked failed."

Ideas you need. A rollout starts the new version alongside the old one, so users are not left without a service. A poll is a loop that checks a condition until it passes or a timeout runs out. A shell step that exits non-zero marks the Actions run as failed.

Plan of attack. 1. Start the new container on a different host port, while the old one keeps serving on 8000. 2. Write a loop that calls /readyz on the new port every few seconds, with a total timeout. 3. If the loop sees 200, switch traffic: stop the old container and make the new one answer on port 8000. 4. If the timeout runs out, stop the new container, leave the old one running and exit with code 1. 5. Test the failure path by making /readyz fail on purpose in a branch, and check that the old version still answers.

Mistakes that fail the test. Stopping the old container before the new one is ready, which causes downtime. A loop with no timeout, which hangs the job forever. Polling /health instead of /readyz. Rolling back without failing the run, so the workflow looks green while the new version never went live.

Practise the eight questions below out loud. Each answer is a model. Use your own words, but keep the facts.

Q1. Walk me through what happens from a git push to a live service.

Model spoken answer

A push to main starts the GitHub Actions workflow. The test job checks out the code, installs the libraries from requirements.txt, rebuilds the data and model, and runs pytest. If any step fails, the job stops. If the tests pass, the deploy job starts, logs in to ghcr.io with the temporary GITHUB_TOKEN, builds the image tagged with the commit id, and pushes it. The rollout then starts both services from that image, and the UI waits until the API healthcheck passes.

Q2. Why does the API load model.joblib at startup rather than training when a request arrives?

Model spoken answer

Training takes time and needs the full data, but serving needs an answer in milliseconds. Loading the saved file once, at startup, makes every request fast. It also means the model that serves is exactly the file that was tested, so training and serving stay in sync. The file is the contract between the two halves.

Q3. How does the data-quality gate fail a run, and why use assertions rather than printed warnings?

Model spoken answer

Each assert checks a rule, such as no negative values or no duplicate station and time pairs. When a condition is False, Python raises an AssertionError, which stops the script with a non-zero exit code. A printed warning would let the pipeline continue, and the bad numbers would reach the model and the dashboard. The failure stops the pipeline before it can ship a wrong number.

Q4. What does depends_on with service_healthy guarantee, and what does it not guarantee?

Model spoken answer

It guarantees that Compose starts the ui service only after the api healthcheck reports healthy. It does not guarantee that the API will stay healthy afterwards, and it does not check anything beyond what the healthcheck tests. If the healthcheck only tests that the process is up, the UI can still start before the model is ready. That is why readiness is a separate check.

Q5. Why does the UI use the address http://api:8000 rather than localhost?

Model spoken answer

Each container has its own network namespace, so localhost inside the UI container means the UI container itself. Compose puts both services on a shared network and gives each service a name that resolves to its address. api is the name of the API service, so the UI reaches it by that name. The API_URL environment variable sets this address, so the same code works locally and in compose.

Q6. What does /metrics measure, and what are its limits?

Model spoken answer

It counts requests and errors in the running process, and it reports the median latency from the stored times. Its limits are that the counters are kept in memory, so they reset when the process restarts, and that they cover only this one process. A real monitor would export them to a time-series store and keep history. The /metrics/history challenge is a first step towards keeping history.

Q7. Why does the deploy job depend on the test job, and what is GITHUB_TOKEN for?

Model spoken answer

The deploy job uses needs: test, so it runs only after the tests have passed. Without needs, jobs run in parallel and a broken build could be pushed. GITHUB_TOKEN is a short-lived token that GitHub creates for each run, with the permissions the job asks for. It lets the job push to the package registry without a stored password in the code.

Q8. What would you change before this ran in production with real users?

Model spoken answer

I would pin every dependency to an exact version, add readiness and liveness checks, and store metrics outside the process. I would also make the rollout zero-downtime and add a rollback. I would move the model download out of the first request and check the model's error against a threshold before saving it. Each change maps to one of the five challenges.
