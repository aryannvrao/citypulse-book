How to use these ticket guides

These chapters walk through the real tickets on your squad's capstone board, in the order the board schedules them. The ticket text (story, acceptance criteria, test cases, subtasks and definition of done) comes from the course site. The guides teach you how to do each ticket yourself and how your trainer will check it.

How the board works:

  • A ticket moves Backlog, To Do, In Progress, Review, Done. Only a trainer can move it to Done, after running its test cases, and gives it a gate score from 0 to 3.
  • Every ticket is judged from commit evidence: your commits, pull requests and reviews in the squad repository. Work done on someone else's laptop does not count for you.
  • Each ticket has a points value (the "pts" column). Defence tickets (marked D01, D02 and so on) are where you present and answer questions.
  • Your viva scores acceptance criteria met, technical depth, contribution and ownership, and understanding, each 0 to 5. The final capstone grade shown on the platform is 60% your own contribution and 40% your team's.

Y2-T17 · Create least-privilege IAM identity for citypulse-pipeline

Session 17 · phase M4 · 3 points

The ticket in plain words

CityPulse is the Bengaluru city-data platform your squad is building. It already runs from start to finish on the lab machine, and it passed the defence in Y2-T16. Before any of its data leaves the lab, the client's security reviewer sets one condition: the pipeline must never run as an admin.

The reason is a well-known breach. In 2019 an attacker used cloud credentials that had far more power than the application needed, and reached data well beyond that application's job. The lesson is simple: a stolen key is only as dangerous as the things it is allowed to do.

So this ticket asks you to create a separate identity called citypulse-pipeline. An identity is who a request claims to be. It may read and write its own folders (prefixes) inside one storage bucket, and nothing else. A test script then tries six actions: two must succeed and four must be refused.

Later labs reuse this identity, so a loose policy spreads its risk everywhere.

Before you start

The earlier tickets must be merged or completed first (Y2-T14 to Y2-T16). Y2-T15 gives you a pipeline that runs fetch, clean, load and data-quality stages. Y2-T16 gives you the defence, the tag v0.3.0, and a cloud account with root MFA, a budget alarm, an IAM admin user and a CLI admin profile. The squad repository needs a protected main branch and a shellcheck CI check. Without the Y2-T16 gate you may not start.

You need Git for Windows (Git Bash), AWS CLI version 2, gitleaks, shellcheck and Python 3. Run commands in Git Bash from the squad repository root. On Windows, Python is often called python, not python3. Check each tool:

The ARN must end in :user/ and your admin user name. If it ends in :root, stop, because you are using the root account.

How your trainer checks it

The trainer checks six acceptance criteria and five test cases. Know each one before the session.

  • AC1, no wildcards. Checked by TC1.
  • AC2, six-case matrix. Checked by TC2.
  • AC3, explain the policy. The trainer points at any line, and you say what it permits and what breaks without it.
  • AC4, no secrets. Checked by TC4, and no string matches AKIA[0-9A-Z]{16}.
  • AC5, README rows. One row per Action in the policy, each with a reason.
  • AC6, evidence. docs/evidence/<name>/ holds one allowed and one AccessDenied screenshot, each with the command and a timestamp.

TC1: no wildcards. The trainer runs grep -rnE '"(\*|s3:\*)"' infra/iam/ in the squad repository.

  • grep prints the lines that match a pattern.
  • -r searches folders recursively, -n shows line numbers, and -E makes | mean "or".
  • '"(\*|s3:\*)"' matches a double quote, then * or s3:*, then a double quote. The backslash makes the star literal.

Passing output is nothing at all. grep exits with code 1 when it finds no match. Check it with echo $? straight after:

A failing output looks like infra/iam/asha/pipeline-policy.json:14: "Action": "s3:*",. The cause is a wildcard action or a "Resource": "*" line. Replace it with named actions and an exact ARN. Note that the README is searched too, so do not write "*" in quotes in your README.

TC2: the six-case matrix. On screen the trainer runs two commands. The first is aws sts get-caller-identity --profile citypulse-pipeline --query Arn --output text. It must print an ARN ending in :user/citypulse-pipeline. The second is bash infra/iam/test_access.sh citypulse-<name>-<rand4>.

  • bash runs the script. The argument is your bucket name.
  • Passing output is six lines, all starting PASS. The two allow lines are the upload to raw/ and the listing of raw/. The four deny lines are the upload to secret/, the delete-object, the aws s3 ls with no bucket, and iam list-users.
  • A failing line looks like FAIL want=allow got=deny: aws s3 cp ..., usually a missing statement or a wrong ARN. got=error means a typo in the bucket name, not a policy problem.
  • If every line passes but the ARN ends in :user/asha-admin, the test proves nothing. Your terminal was still using the admin profile.

TC3: a denied upload. The trainer runs aws s3 cp README.md s3://<bucket>/secret/x.txt --profile citypulse-pipeline.

  • aws s3 cp copies a file. README.md is the local source.
  • s3://<bucket>/secret/x.txt is the destination: a bucket, then a key under secret/.
  • --profile citypulse-pipeline makes the call as the pipeline user.
  • Expected: An error occurred (AccessDenied) when calling the PutObject operation.
  • If the copy succeeds, your policy allows secret/. Remove that resource. If you see NoSuchBucket, the bucket name is wrong.

TC4: no secrets in history. The trainer runs gitleaks detect --source . --log-opts=--all -v.

  • gitleaks detect scans for secrets.
  • --source . scans the current folder, which is the repository.
  • --log-opts=--all passes --all to git log, so every branch and commit is scanned.
  • -v prints extra detail.
  • Passing output ends with no leaks found.
  • A failing output reports leaks found. Deleting the file is not enough, because Git history keeps it. Deactivate the key first, then tell your trainer.

TC5: explain a resource. The trainer asks why ListBucket uses the bucket ARN but PutObject uses bucket/raw/*. See the viva section below.

Do it, step by step

Y2-T17.1: create your bucket

Goal: one bucket, named after you, in ap-south-1. Bucket names are lowercase, use letters, digits and hyphens, are 3 to 63 characters long, and are unique across all of AWS.

Stage 1. Set your name and suffix. Choose four random lowercase letters or digits yourself.

NAME=asha
SUFFIX=3m9x
BUCKET="citypulse-$NAME-$SUFFIX"
echo "$BUCKET"

NAME=asha and SUFFIX=3m9x store values in variables. BUCKET="..." builds the name by inserting both variables. echo prints it. Expect citypulse-asha-3m9x. Use the same value in every later step.

Stage 2. Create the bucket with the admin profile.

export AWS_PROFILE=asha-admin AWS_DEFAULT_REGION=ap-south-1
aws s3 mb "s3://$BUCKET" --region ap-south-1
mkdir -p "docs/evidence/$NAME"
echo "$BUCKET" > "docs/evidence/$NAME/bucket.txt"

aws s3 mb makes a bucket (mb means make bucket). > writes the name into a file. Expect make_bucket: citypulse-asha-3m9x.

Test: aws s3 ls | grep "$BUCKET" prints the bucket name.

Y2-T17.2: write the scoped policy

Goal: a JSON file, infra/iam/<name>/pipeline-policy.json, that names your bucket only. Build it in stages.

Stage 1. Create the folder, then the file with this outer shape. Leave the list empty for now.

mkdir -p "infra/iam/$NAME"

{
  "Version": "2012-10-17",
  "Statement": []
}

"Version": "2012-10-17" is the fixed version string of the policy language. Copy it exactly. "Statement" is the list of rules. Each rule is one object in that list, and objects are separated by commas.

Stage 2. Add the listing statement inside the square brackets. Replace BUCKET with your bucket name.

{
  "Sid": "ListRawPrefix",
  "Effect": "Allow",
  "Action": "s3:ListBucket",
  "Resource": "arn:aws:s3:::BUCKET",
  "Condition": {"StringLike": {"s3:prefix": ["raw/*"]}}
}

Sid is a label you choose. Action lists names in the bucket. Resource is the bucket itself, with no slash. Condition allows the listing only when the prefix matches raw/*. That asterisk is a pattern for the prefix value, not a wildcard action.

Stage 3. Add the object statement. Add a comma after the first statement, then this object.

{
  "Sid": "WriteReadRawObjects",
  "Effect": "Allow",
  "Action": ["s3:PutObject", "s3:GetObject"],
  "Resource": "arn:aws:s3:::BUCKET/raw/*"
}

PutObject uploads a file and GetObject reads one. Both act on objects, so the resource is the bucket, then /raw/, then /*.

Stage 4. Validate the JSON, then check for forbidden text.

python3 -m json.tool "infra/iam/$NAME/pipeline-policy.json" > /dev/null && echo "JSON OK"
grep -nE '"\*"|s3:\*' "infra/iam/$NAME/pipeline-policy.json"

json.tool stops with an error if the JSON is broken. && echo prints JSON OK only when it passed. Use python on Windows if needed. The grep must print nothing.

Y2-T17.3: create the policy, the user and the access key

Goal: the pipeline user has your policy and one access key, stored only in its profile.

Stage 1. Create the policy from the file. Run this from the repository root, so the relative file:// path works in Git Bash. Use the admin profile: run export AWS_PROFILE=asha-admin first if this is a new terminal, because the pipeline user cannot create policies.

ACCT=$(aws sts get-caller-identity --query Account --output text)
aws iam create-policy --policy-name citypulse-pipeline-s3 \
  --policy-document "file://infra/iam/$NAME/pipeline-policy.json" \
  --query Policy.Arn --output text

ACCT=$(...) stores your account number. --policy-document file://... reads your file. The output is the policy ARN. If you see EntityAlreadyExists, the name is taken: reuse that ARN and ask your trainer before you delete anything.

Stage 2. Create the user and attach the policy.

aws iam create-user --user-name citypulse-pipeline
aws iam attach-user-policy --user-name citypulse-pipeline \
  --policy-arn "arn:aws:iam::$ACCT:policy/citypulse-pipeline-s3"

create-user makes the user. attach-user-policy connects the policy to it. The attach command prints nothing when it succeeds.

Stage 3. Create the access key and store it. Copy the AccessKeyId and SecretAccessKey straight into the prompts. Do not save the output to a file.

aws iam create-access-key --user-name citypulse-pipeline
aws configure --profile citypulse-pipeline
aws sts get-caller-identity --profile citypulse-pipeline --query Arn --output text

The secret is shown only once. aws configure --profile stores keys outside the repository. Set the region to ap-south-1. The final line must end in :user/citypulse-pipeline.

Trap: Keys in the repository

Never write the access key into a file, a README, a screenshot or a commit. gitleaks will find it, and the ticket fails.

Y2-T17.4: run the six-case test

Goal: six lines of PASS, plus two screenshots.

Stage 1. The script starts with three lines.

#!/usr/bin/env bash
set -uo pipefail
B=$1; export AWS_PROFILE=citypulse-pipeline AWS_DEFAULT_REGION=ap-south-1

The first line tells the system to use Bash. set -uo pipefail makes Bash stop on unset variables (-u) and on failures inside a pipeline (pipefail). Do not add -e, because a failing command is exactly what the test expects. B=$1 stores the bucket name passed as the first argument. export makes the profile apply to every aws call in the script.

Stage 2. Add a checking function. This is the technique: run one command, capture its output, and decide the result.

check() {
  local want=$1 out got
  shift
  if out=$("$@" 2>&1); then got=allow
  elif grep -qE 'AccessDenied|not authorized' <<<"$out"; then got=deny
  else got=error
  fi
  if [ "$got" = "$want" ]; then echo "PASS $want: $*"; else echo "FAIL want=$want got=$got: $*"; fi
}

local keeps variables private to the function. shift removes the first argument, so "$@" holds only the command. $(...) captures the output, and 2>&1 adds error text to it. Only an AccessDenied message counts as deny, so a typo cannot pass as a denial.

Stage 3. Add the first two checks. Write echo probe > /tmp/probe.txt once before them.

echo probe > /tmp/probe.txt
check allow aws s3 cp /tmp/probe.txt "s3://$B/raw/probe.txt"
check allow aws s3 ls "s3://$B/raw/"

Each line gives the wanted result first. Write the four deny lines yourself, with deny first:

  • an upload to secret/ with aws s3 cp
  • a delete-object with aws s3api delete-object --bucket "$B" --key raw/probe.txt
  • a listing with aws s3 ls and no bucket name
  • aws iam list-users

Save the file as infra/iam/test_access.sh, then run shellcheck infra/iam/test_access.sh. It must print nothing, because CI runs the same check.

Stage 4. Run it. date prints a timestamp for your screenshots.

date
bash infra/iam/test_access.sh "$BUCKET"

Expect six lines starting PASS. Screenshot one allowed and one AccessDenied line, with the command and timestamp visible.

Trap: Testing as admin

If AWS_PROFILE is still set to asha-admin, every case passes and the result means nothing. Run the get-caller-identity check from Y2-T17.3 before the test.

Y2-T17.5: find the event in CloudTrail

Goal: one screenshot of a call made by your pipeline user.

CloudTrail records API calls with the identity that made them. Run this with the admin profile:

aws cloudtrail lookup-events --lookup-attributes AttributeKey=Username,AttributeValue=citypulse-pipeline \
  --max-results 10 --query 'Events[].[EventTime,EventName]' --output table

AttributeKey=Username filters by user name. Events can take several minutes to appear. Object uploads (PutObject) are data events, which event history often does not show. If yours is missing, note that and screenshot a management event instead, such as the denied ListUsers call. The ticket allows this.

Y2-T17.6: write the README table and the reference policy

Goal: infra/iam/README.md with one row per action, and a reference copy of the policy.

Write a table with three columns: the action, the resource, and one sentence on why the pipeline needs it. The header is:

| Action | Resource | Why the pipeline needs it |

Add exactly one row per Action in your policy. Your policy has three actions, so the table has three rows. Write each reason in your own words. Do not write "*" in quotes anywhere in this file.

Then copy the reviewed policy as the reference version:

cp "infra/iam/$NAME/pipeline-policy.json" infra/iam/pipeline-policy.json

cp copies your file to the squad reference path.

Y2-T17.7: run the team checks and update .gitignore

Goal: both checks print nothing, and the ignore rules cover credential files.

grep -rn '"\*"' infra/iam/
gitleaks detect --source . --log-opts=--all
printf '%s\n' '*.csv' '.aws/' >> .gitignore
git ls-files | grep -E '\.csv$|\.aws/'

gitleaks detect scans the history. printf '%s\n' prints each argument on its own line, and >> appends them to .gitignore. The final git ls-files must print nothing, because .gitignore does not hide files Git already tracks.

Y2-T17.8: review and merge

Goal: a reviewed PR with one approval and green CI. Push your branch and open the PR. A squad-mate picks one line and asks, "why does it need this action?" Nobody merges their own PR. gh pr checks shows whether CI passed.

Prove it before review

Run TC1 to TC4 yourself, in order, from a clean terminal, and save each output into docs/evidence/<name>/. Never save the access key.

Write the PR description with these headings, in your own words:

  • What: the policy and the test script.
  • Why: the reviewer's condition.
  • How to test: the exact commands, in order.
  • Evidence: the six PASS lines, the grep and gitleaks output, and your two screenshots.
  • Checklist: the definition of done below, ticked.

  • [ ] infra/iam/<name>/pipeline-policy.json, infra/iam/pipeline-policy.json, infra/iam/README.md and infra/iam/test_access.sh are merged to main through a reviewed PR. You know it when git log --oneline main shows the merge and the PR shows one approval.

Defend it in the viva

Each model answer below explains the reasoning. Give your answers in your own words, using your own policy lines.

Question 1 (why): Why must the pipeline run as its own user and not as the admin?

Model answer

A leaked admin key gives an attacker the whole account. A separate user with one bucket limits the damage to that bucket.

Question 2 (trade-off): Your policy allows GetObject as well as PutObject. What do you gain and what do you risk?

Model answer

The pipeline reads its own raw files back, so it can check what it uploaded. The risk is that a leaked key can also read everything under the granted prefixes. The trade-off is acceptable here only because the prefixes are limited to the pipeline's own data.

Question 3 (technique): Why does ListBucket use the bucket ARN but PutObject uses bucket/raw/*?

Model answer

ListBucket acts on the bucket itself, so its resource has no slash. PutObject and GetObject act on objects inside it, so their resource names the object path and ends in /*.

Question 4 (what you did): Walk me through one statement you wrote. What breaks if you remove it?

Model answer

Name the statement, its actions and its resource, then say what fails without it. Removing the listing statement makes aws s3 ls s3://bucket/raw/ return AccessDenied. Match your answer to your own file.

Question 5 (why a deny test): Why is a denied case as important as an allowed case?

Model answer

A policy that shows only its allows has not been tested for what it blocks. The deny cases prove that an upload to secret/ is refused.

Y2-T18 · Upload clean parquet to date-partitioned private bucket

Session 18 · phase M4 · 3 points

The ticket in plain words

CityPulse is the course's Bengaluru city-data platform. Its clean air-quality data sits only on the lab disk. This ticket moves it into cloud object storage, where you store whole files under names and read them over the internet. The course uses Amazon S3 for this.

Cloud storage can leak. A public bucket is a container that anyone on the internet can open. Leaks in the news usually come from someone who left a bucket open and never checked. This ticket asks for the opposite: a private bucket that refuses anonymous readers, encryption on every file, and versioning, which keeps an older copy when a file is overwritten, so a bad upload can be undone.

Each file goes under a key that contains its date, such as clean/aqi/date=2026-12-17/aq_clean.parquet. A dashboard can then read one day without reading the rest.

Finally, two roles stay separate. An admin profile sets the bucket's safety settings. Your upload script uses the citypulse-pipeline identity from T17, which can write files but cannot change the bucket. The script must never contain a key or a profile name.

T18.1 Bucket settings (admin profile)

Goal. Turn on the three safety settings and save proof of each.

export AWS_PROFILE=<admin-profile> AWS_DEFAULT_REGION=ap-south-1

T18.2 Write upload.py in four stages

Goal. Build src/citypulse/upload.py in stages. Test each stage before the next.

Stage 1: the pure function. Practise the pattern with a twin file outside the repository.

import datetime

def report_key(source, day, filename):
    return f"raw/{source}/date={day.isoformat()}/{filename}"

The f-string fills each {...} slot. isoformat() turns a date into 2026-01-05. Running it prints raw/sensors/date=2026-01-05/t.csv. This layout is not the one you need.

try:

T18.5 Apply the lifecycle rules (admin profile)

Goal. Write infra/storage/lifecycle.json, apply it, and save what S3 reports back.

Stage 1: the file. A lifecycle file is JSON with a Rules list. This example is for a different prefix, so choose your own prefix and number of days:

{"Rules": [{"ID": "expire-old-exports", "Status": "Enabled", "Filter": {"Prefix": "exports/"}, "NoncurrentVersionExpiration": {"NoncurrentDays": 90}}]}

Filter picks which keys the rule covers, and NoncurrentVersionExpiration deletes old versions (not the current one) after that many days. Pick a rule that limits the cost of versioning on your data, and be ready to explain it.

Defend it in the viva

Question 1 (why): Why use Block Public Access rather than careful object permissions?

Model answer

Object permissions can be changed one object at a time, and one mistake can expose data. Block Public Access is a bucket-level switch that overrides any ACL or policy that would make data public. One get-public-access-block call shows all four flags, so the setting is easy to check.

Question 2 (trade-off): What does versioning cost, and how is the cost controlled?

Model answer

Every overwrite keeps an old copy, so storage grows. Lifecycle rules limit that growth by expiring old versions after a set number of days. Versioning also is not a full backup, because it protects only inside the same bucket.

Question 3 (what you did): Which code did you write, and how do you know it works?

Model answer

Name the function you wrote, the commit that holds it, and the test and output you saw. Use your own commit and output, because the trainer checks your answer against your commits.

Question 4 (why): Why can the object_key test run without AWS?

Model answer

object_key is a pure function. It makes no network call and reads no file, so the test checks the string directly, with no credentials. A layout error is caught quickly, and an upload error is caught separately in main.

Question 5 (understanding): Why does a 403 prove privacy, but a 404 proves nothing?

Model answer

A 403 means the object exists and the bucket refused an anonymous request. A 404 says only that the key was not found.

The ticket in plain words

The CityPulse pipeline is the script that fetches city data, cleans it and uploads the result to a bucket, which is a storage container in Amazon S3. Right now it runs on the lab machine and your laptop. A laptop sleeps, changes networks and gets switched off, so the data stops flowing. This ticket moves the pipeline onto a cloud virtual machine (VM): a computer rented from Amazon Web Services (AWS) that stays on and runs the job on a timetable.

The client sets two rules. First, the server holds no long-lived access keys. AWS gives it temporary permission through an instance role, so no secret file sits on the disk. Second, the server is hard to break into. Its SSH port, the remote-login door numbered 22, opens only to your own address, and only your own key can log in.

The ticket also tells a story. In October 2021 a bad network change at Facebook locked out the engineers who ran the system, because they had no tested way back in. So you also write a runbook, a document of exact commands for launching, connecting, deploying, stopping and recovering the server. Finally, every VM must be stopped at the end of the day, because a running VM is billed every hour.

Y2-T19.1: Launch and connect

Goal. A running VM tagged with your name that accepts your key.

Stage 1 (laptop): find the Ubuntu image. Run:

AMI=$(MSYS_NO_PATHCONV=1 aws ssm get-parameter --name /aws/service/canonical/ubuntu/server/24.04/stable/current/amd64/hvm/ebs-gp3/ami-id --query Parameter.Value --output text)

AMI=$(...) stores the output of the command in AMI. In Git Bash, MSYS_NO_PATHCONV=1 stops Git Bash rewriting the parameter name that starts with / into a Windows path; on Linux it does no harm. The parameter holds the official Ubuntu 24.04 image ID, so you avoid a stranger's image. echo "$AMI" prints an ID starting ami-.

Stage 2 (laptop): look up your firewall. Run SG_ID=$(aws ec2 describe-security-groups --group-names "citypulse-ssh-$NAME" --query 'SecurityGroups[0].GroupId' --output text). Check with echo "$SG_ID".

Stage 3 (laptop): launch.

ID=$(aws ec2 run-instances --image-id "$AMI" --instance-type t3.micro \
  --key-name "citypulse-$NAME" --security-group-ids "$SG_ID" \
  --metadata-options HttpTokens=required,HttpEndpoint=enabled \
  --tag-specifications "ResourceType=instance,Tags=[{Key=Owner,Value=$NAME}]" \
  --query 'Instances[0].InstanceId' --output text)

The backslashes continue the command. --key-name installs your public key. --metadata-options HttpTokens=required requires IMDSv2. --tag-specifications adds the Owner tag that TC5 searches for. The output is an ID starting i-. Add --iam-instance-profile Name=citypulse-pipeline only if that profile already exists. Otherwise attach it in T19.3.

Stage 4 (laptop): wait and read the address.

aws ec2 wait instance-running --instance-ids "$ID"
IP=$(aws ec2 describe-instances --instance-ids "$ID" --query 'Reservations[0].Instances[0].PublicIpAddress' --output text)

wait pauses until the VM runs, and prints nothing. Run echo "$IP" to read the address. Look it up again after every start, because it changes.

Stage 5 (Git Bash): connect. Run ssh -i ~/.ssh/citypulse-$NAME ubuntu@"$IP". Type yes the first time. whoami on the VM prints ubuntu.

Trap: Key permissions

If ssh refuses the key as unprotected, run chmod 600 ~/.ssh/citypulse-$NAME and try again.

Y2-T19.2: Harden SSH

Goal. Password and root logins refused, with a working session kept open.

Stage 1 (VM): write the drop-in. Keep this session open.

sudo tee /etc/ssh/sshd_config.d/99-citypulse.conf >/dev/null <<'EOF'
PasswordAuthentication no
PermitRootLogin no
KbdInteractiveAuthentication no
EOF

tee writes the text into the file, and >/dev/null hides its copy. <<'EOF' begins a block that ends at the next EOF line. The quotes stop $ from being changed. Expect no output.

Stage 2 (VM): check, then reload. Run sudo sshd -t && sudo systemctl reload ssh. The reload runs only if the check passes. Expect no output.

Stage 3 (VM): see the winning values. Run ls /etc/ssh/sshd_config.d/ and sudo sshd -T | grep -Ei 'passwordauthentication|permitrootlogin|kbdinteractive'. sshd uses the first value it finds, so an earlier file can win. Expect three no lines. If an earlier file sets yes, ask your trainer before you change it.

Stage 4 (laptop, second terminal): test. Run ssh -o PreferredAuthentications=password ubuntu@"$IP". Expect Permission denied (publickey).

Trap: Closing your only session

Keep the first session open until a new session has logged in with your key. A broken config with no open session can lock you out.

Y2-T19.3: Role, not keys

Goal. The VM uses the citypulse-pipeline role, with no stored keys.

Stage 1 (laptop): create the role. The trust policy names EC2 as the service allowed to take the role.

ACCT=$(aws sts get-caller-identity --query Account --output text)
aws iam create-role --role-name citypulse-pipeline \
  --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ec2.amazonaws.com"},"Action":"sts:AssumeRole"}]}'
aws iam attach-role-policy --role-name citypulse-pipeline --policy-arn "arn:aws:iam::$ACCT:policy/citypulse-pipeline-s3"

ACCT holds your account number. attach-role-policy attaches the T17 policy to the role, not to a user.

Stage 2 (laptop): build the profile and attach it.

aws iam create-instance-profile --instance-profile-name citypulse-pipeline
aws iam add-role-to-instance-profile --instance-profile-name citypulse-pipeline --role-name citypulse-pipeline
aws ec2 associate-iam-instance-profile --instance-id "$ID" --iam-instance-profile Name=citypulse-pipeline
aws ec2 modify-instance-metadata-options --instance-id "$ID" --http-tokens required --http-endpoint enabled

The profile carries the role onto the VM. The last command makes IMDSv2 required.

Stage 3 (VM): install the AWS CLI, then prove it. A fresh Ubuntu image has no aws program. Run sudo snap install aws-cli --classic, then aws --version, which should start with aws-cli/. Now run ls -la ~/.aws 2>/dev/null || echo "no ~/.aws", then aws sts get-caller-identity --query Arn --output text. The folder should be missing and the ARN should contain assumed-role/citypulse-pipeline/.

Trap: Waiting for the profile

A new profile can take a few seconds to appear. Wait, then retry.

Y2-T19.4: The bootstrap script, in stages

Goal. infra/vm/bootstrap.sh that prepares the VM and refuses stored keys. Test it by hand before cron uses it.

Technique: strict mode. Begin the script with #!/usr/bin/env bash and set -euo pipefail. -e stops at the first failing command, -u makes unset variables an error, and pipefail makes a pipeline fail if any part fails.

Stage 1 (VM): refuse stored keys.

if [ -e "$HOME/.aws/credentials" ]; then
  echo "stored AWS keys found; remove them first" >&2
  exit 1
fi

[ -e path ] is true when the file exists. >&2 sends the message to the error stream.

Stage 2 (VM): check the role. Add aws sts get-caller-identity >/dev/null || { echo "no role credentials" >&2; exit 1; }. The braces group two commands.

Stage 3 (VM): clone over HTTPS. Use git clone https://github.com/<org>/<repo>.git "$HOME/citypulse". For a private repository, ask your trainer how to authenticate. Never place a token in the script.

Stage 4 (VM): install packages. On Ubuntu 24.04, run sudo apt-get install -y python3-venv once. Then python3 -m venv "$HOME/citypulse-venv" and "$HOME/citypulse-venv/bin/pip" install -r "$HOME/citypulse/requirements.txt". Calling pip by full path uses the venv's copy.

Stage 5 (VM): run once by hand. Read the header of scripts/run_pipeline.sh to learn what it expects, then run it. Check with aws s3 ls s3://citypulse-<name>-<rand4>/clean/aqi/date=$(date +%F)/. date +%F prints a date like 2026-11-17. Expect one new object. The VM clock is UTC, not IST, so date +%F can differ from your local date near midnight, and the crontab hours are in UTC too. Convert your times before you write the schedule. Rerunning git clone into an existing folder fails, so delete the folder or test for it first.

Test. Run shellcheck infra/vm/bootstrap.sh on the VM. No output means no warnings.

Y2-T19.5: Cron and evidence

Goal. Two scheduled runs at least 30 minutes apart, each with a log line and a bucket object.

Technique: a cron line. The five fields are minute, hour, day of month, month and day of week. This line is a different example, a backup at 06:30 on weekdays:

30 6 * * 1-5 /usr/bin/tar -czf /home/ubuntu/backup.tgz /home/ubuntu/notes

30 is the minute, 6 the hour, * means every day or month, and 1-5 means Monday to Friday. Write your own schedule, giving runs at least 30 minutes apart. Cron has a short PATH and no terminal, so use full paths. In a crontab, % means newline, so escape it as \%.

Trap: The missing log folder

Cron does not create folders. Run mkdir -p /home/ubuntu/logs first, or the redirect fails silently.

Stage 1 (VM): find full paths. Run command -v aws, and note the path it prints.

Stage 2 (laptop): write your line. In infra/vm/crontab.txt, use the full path to aws, the full path to run_pipeline.sh, and a redirect: >> /home/ubuntu/logs/pipeline.log 2>&1. >> appends each run, and 2>&1 sends errors to the same file. The VM has no default region, so put AWS_DEFAULT_REGION=ap-south-1 on its own line at the top of the crontab (a NAME=value line before the schedule lines), or the upload may fail with a region error.

Stage 3 (VM): install. Run crontab -l to save the current list, then crontab /home/ubuntu/citypulse/infra/vm/crontab.txt, then crontab -l again. Installing replaces the whole list, so keep any entries you need.

Stage 4 (VM): check cron. Run systemctl status cron --no-pager and journalctl -u cron -n 20 --no-pager. Expect active (running).

Stage 5 (wait). Wait at least 30 minutes after the first run, and write the runbook meanwhile.

Stage 6 (laptop): save evidence.

ssh -i ~/.ssh/citypulse-$NAME ubuntu@"$IP" 'tail -n 40 ~/logs/pipeline.log' > docs/evidence/$NAME/T19-cron-log.txt
aws s3 ls s3://citypulse-$NAME-<rand4>/clean/aqi/ --recursive > docs/evidence/$NAME/T19-bucket.txt

The > writes the output to a file on your laptop. Open both files before you commit.

Defend it in the viva

1. Why an instance role, not an access key?

Model answer

An access key on the VM never expires and can leak through a disk snapshot. An instance role gives temporary credentials that AWS replaces automatically, so no permanent secret sits on the disk. The role carries the same scoped policy, so the access is no broader than before.

2. What is the trade-off of allowing SSH only from a /32?

Model answer

The rule is strict, so scanners cannot see the port. The cost is that when your IP changes, you lose access until you update the rule. That is why the runbook has a recovery section. Session Manager avoids an inbound port, but it needs an agent and extra IAM setup.

3. Why run sshd -t and sshd -T before closing your session?

Model answer

sshd -t catches syntax errors before the reload. sshd -T shows the values that really apply, because the first value read wins and an earlier drop-in can override mine. I kept my first session open until a new login with the key worked.

4. What did you personally do in this ticket?

Model answer

Name your own subtasks, commits and owned section, and point to the commit hashes and your review. Keep it to what the commit history shows.

5. How do you know the pipeline ran twice without you touching it?

Model answer

The log shows two runs at least 30 minutes apart, and each run has a bucket object with a matching time. Cron wrote the log. If a run left no object, I would read the log tail to find out why.
