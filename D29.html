The idea in one minute

Building a project and delivering it are different jobs. Delivery means that someone who did not write the code can run it, explain it and keep it alive after you leave. Today you practise the four steps that make that possible. You sort your to-do list into what must ship and what waits. You translate your model's error into minutes or rupees that a client can act on. You name the release with a version tag, and you write a handover document that a stranger can follow.

Think of a cook opening a restaurant. The menu needs an order and prices, the owner needs to know what each dish costs in rupees rather than grams, the kitchen needs a recipe card for each dish, and the restaurant needs a way to go back to last week's menu if tonight's goes wrong.

Starting from zero

Project, client and stakeholder. A project is a piece of work with a goal and an end date. The client is the person or organisation the work is for. A stakeholder is anyone with a stake in the result, such as the client, the mentor who marks the work, or the people who will run it after you.

Backlog, sprint and story point. A backlog is a list of work items, often called tickets. A sprint is a fixed period, usually one or two weeks, in which the team commits to some of those items. A story point is a number the team agrees on to compare the effort of two items. It is not an hour count.

File, folder, terminal and command. A file is a named piece of stored text or data. A folder (also called a directory) holds files and other folders. The terminal is a text window where you type commands, which are instructions the computer runs when you press Enter. A flag is an option that changes what a command does. In git log --oneline, the word --oneline is a flag.

Git vocabulary. Git records the history of a folder of files. A repository (repo) is a folder that Git tracks. A commit is a saved snapshot with a message. A tag is a permanent name attached to one commit. A remote is a copy of the repository on another machine, and origin is the usual name for the main one. To clone is to copy a remote repository to your machine.

Code vocabulary. A variable is a name that holds a value, such as remaining = 3. A function is a named block of code that you call with inputs, such as advise(12.0). A server is a program that waits for requests and sends replies. A port is a numbered door on a machine, such as 8000, where a server listens. An endpoint is one address a server answers, such as /predict. HTTP is the request-and-reply protocol the web uses. A status code is the number in the reply: 200 means success and 422 means the input was rejected. JSON is a text format for structured data, written with braces and square brackets.

Docker vocabulary. An image is a packaged copy of an app with everything it needs to run. A container is one running copy of an image. A registry is a shared store where images are kept so that other people can pull them.

Model vocabulary. A model is a program that has learned patterns from data. A baseline is the simple rule you compare against, such as "use the median wait time of past patients". MAE (mean absolute error) is the average size of the model's mistake, in the same units as the thing predicted. A holdout is data kept aside during training and used only for testing. Data leakage happens when the model learns from information it would not have at prediction time.

Bus factor. The number of people who would have to leave a project before it could no longer be maintained. A bus factor of 1 means one person holds the knowledge.

The tools

MoSCoW prioritisation

MoSCoW sorts every backlog item into one of four buckets: Must have, Should have, Could have, and Won't have (this time). The name is an acronym made from the first letter of each bucket and the vowels added for pronunciation.

CityPulse uses it because the course gives you a fixed deadline and no usage data. The slides compare three alternatives. RICE scoring gives numeric scores for reach, impact, confidence and effort, but it needs data you will not have in a three-week project. The Kano model is useful for customer delight, but it is heavier than a fixed deadline needs. An unordered to-do list has no overhead, but everything looks equally urgent, so the core chain of work slips. MoSCoW forces an explicit decision about what the product cannot ship without, and it records what you left out, so that scope creep can be seen.

The rule is simple. For each candidate item, ask: does the product fail without it? Only the items where the answer is yes become Musts, and the course caps them at five. Each Must gets an owner, a one-line acceptance test and a ticket number. Each Won't gets a written reason, so that you can point to it when someone asks again.

Musts come first, so the sprint is filled with the core work before anything else. The following trace shows the selection loop in a small form. You will write a version of it in the graded lab skill section.

The loop does not stop at the first item that does not fit. It keeps going, so a small item later in the list can still be chosen. This is the behaviour that lets a sprint use its capacity fully.

Trap: Six or more Musts

If everything is a Must, nothing is. The slides say that a list of six or more Musts means the list has not been sorted. Move the extras to Should, and keep the Musts to five or fewer.

Trap: Vague acceptance lines

"Works well" cannot be checked, so it cannot be a Must's acceptance line. Write a command or a number that someone else can run. The slides use curl -d @tests/sample.json returns 200.

Business metrics from ML metrics

An ML metric such as MAE, recall or precision describes how wrong the model is. A client does not decide in those units. A client decides in minutes, cases caught or rupees. Translating the metric means stating the improvement over the current way of working, in those units, with the assumption that connects them.

The course uses a hospital outpatient (OPD) brief as the example. The model predicts how long a patient will wait. The current rule is the median wait of past patients, which is the baseline. The model's MAE is 12.1 minutes and the baseline's error is 18.4 minutes, so the model is about 6.3 minutes closer per patient on the holdout. That is the sentence the client needs, and the slides want it in the README.

The slides also require a sensitivity check. You multiply the MAE by 1.10, which models a production model that is 10% worse than the test result. If the worse number still beats the baseline, the claim survives a bad day.

The code below writes the numbers to metrics.json, so that every slide and report can copy them from one place.

import json, joblib, pandas as pd, yaml
from sklearn.metrics import mean_absolute_error
cfg = yaml.safe_load(open("config.yaml")); base = json.load(open("reports/baseline.json"))
df = pd.read_parquet("data/clean/dataset.parquet")
test = df[df[cfg["data"]["date_col"]] >= cfg["split"]["holdout_from"]]
model, target = joblib.load("models/model.joblib"), cfg["data"]["target"]
mae = mean_absolute_error(test[target], model.predict(test.drop(columns=[target])))
sens = mae * 1.10                                   # what if production is 10% worse?
metrics = {"model": {"mae": round(mae, 2)}, "baseline": base,
           "improvement_pct": round((base["value"] - mae) / base["value"] * 100, 1),
           "sensitivity_10pct": {"mae": round(sens, 2), "beats_baseline": bool(sens < base["value"])},
           "segments_worse_than_baseline": []}      # fill from the per-department loop
json.dump(metrics, open("metrics.json", "w"), indent=2)
print(f"Wait-time estimates are off by {mae:.1f} min per patient, versus {base['value']:.1f} min today.")

Line by line:

  • import json, joblib, pandas as pd, yaml loads four libraries. json reads and writes JSON, joblib loads a saved model, pandas handles tables and yaml reads configuration files. as pd gives pandas the short name pd.
  • from sklearn.metrics import mean_absolute_error loads one function from the scikit-learn library, the function that computes MAE.
  • cfg = yaml.safe_load(open("config.yaml")) opens the configuration file and turns it into a dictionary, a named collection of values. base = json.load(...) does the same for the baseline's result.
  • df = pd.read_parquet(...) reads the cleaned dataset into a table called a data frame.
  • test = df[...] keeps only the rows whose date is on or after the start of the holdout. The condition inside the square brackets is a true-or-false test for each row.
  • model, target = joblib.load(...), cfg[...] loads the saved model and reads the name of the column to predict.
  • mae = mean_absolute_error(...) asks the model for predictions on the test rows, with the target column removed (drop), and compares them with the true values.
  • sens = mae * 1.10 is the 10% worse scenario. The comment after # is ignored by Python.
  • improvement_pct is the gain as a percentage of the baseline. round(..., 1) keeps one decimal place. With the slide numbers, (18.4 − 12.1) / 18.4 × 100 gives 34.2.
  • beats_baseline is True when the worse scenario is still lower than the baseline. bool(...) turns the result into true or false for the JSON file.
  • segments_worse_than_baseline is an empty list here. You must fill it with the departments where the model loses.
  • json.dump(..., indent=2) writes the dictionary to metrics.json with two spaces of indentation, which makes the file easy to read.
  • The last print line uses an f-string, a text with {} slots filled by variables. {mae:.1f} shows the MAE with one decimal place.

With the slide values, the output is Wait-time estimates are off by 12.1 min per patient, versus 18.4 min today.

Trap: Claiming minutes saved

The model reduces estimate error. It does not save anyone minutes by itself. Write exactly what changes: "wait estimates are closer by 6.3 minutes per patient". Do not write "the hospital saves six hours a day" unless you have measured that.

Trap: Improvement over 40 per cent

A large gain is a warning sign. Check for leakage first, such as a feature that is only known after the outcome. The slides ask you to re-check before you celebrate.

Trap: Hiding the segments where the model loses

If the model is worse than the baseline for one department, list it in segments_worse_than_baseline and in the Known limits section. Leaving it out is an overclaim, and the slides treat that as a failure.

HANDOVER.md and bus factor

A HANDOVER.md file gives a newcomer the architecture, a runbook of exact commands, the known issues and the next steps. It is the document that lets a project continue without its original authors. The slides list three alternatives: a README alone is fine for users but does not hold the runbook or the ownership a maintainer needs; a wiki drifts from the code and is not reviewed in pull requests; a recorded video cannot be searched or copied, and commands must be text.

Bus factor is measured from git history. The question is not "how many commits did each person make?" but "how many distinct people have changed this module?" A module with one author has a bus factor of 1, and the course asks you to assign a non-author as a second owner.

The following term block shows the basic count for one folder. The command lines start with $. The line below the command is what the terminal prints.

The output means that only one distinct author name appears in the history of api/. The loop below repeats this check for each module and writes a table to a file.

for m in src/ingest src/train.py api ui tests; do
  n=$(git log --format='%an' -- "$m" | sort -u | wc -l)
  flag=$([ "$n" -lt 2 ] && echo "BUS FACTOR 1: assign second owner")
  echo "| $m | $n authors | $flag |"
done | tee -a docs/module-owners.md
git shortlog -sn --no-merges                 # commits per person
git log --author="Asha" --oneline -- api/    # verify a contribution statement
gh pr list --state merged --author @me --json number,title   # PR links for your statement

Line by line:

  • for m in src/ingest src/train.py api ui tests; do starts a loop. The variable m takes each module path in turn, and the loop ends at done.
  • n=$(...) runs the commands inside the brackets and stores their output in n. $(...) is command substitution.
  • Inside the brackets, git log --format='%an' -- "$m" prints the author name of every commit that touched the path. --format='%an' prints only the author name. The -- tells git that what follows is a path, not an option.
  • sort -u sorts the names and removes duplicates. wc -l counts the lines that remain. The result is the number of distinct authors.
  • flag=$([ "$n" -lt 2 ] && echo "...") tests whether n is less than 2 with -lt. If the test is true, echo prints the warning. If it is false, the flag stays empty.
  • echo "| $m | $n authors | $flag |" prints one table row in Markdown format.
  • done | tee -a docs/module-owners.md sends the output of the loop into tee, which shows it on the screen and appends it to the file. -a means append, so an earlier table is not overwritten.
  • git shortlog -sn --no-merges prints commit counts per person. -s shows only the counts, -n sorts them from largest to smallest, and --no-merges leaves out merge commits.
  • git log --author="Asha" --oneline -- api/ lists Asha's commits to api/, one per line. Use it to check a claim before you write it down.
  • gh pr list --state merged --author @me --json number,title asks GitHub's command-line tool for your merged pull requests and prints their number and title as JSON. @me means the account you are logged in with.
Trap: Commit count is not bus factor

A person with 200 commits and a second person with one commit can still leave a bus factor of 1, if the second person cannot explain or run the module. What counts is whether a second person can explain and run the module. The slides say the test is a second person who can explain and run it.

Trap: Runbook commands that were never run

Each command in the runbook must be run on a clean clone before the document is merged. A command that has never been run is a guess.

Trap: Contribution statements that overclaim

Every pull request you list must exist, and it must be yours or one you reviewed. The trainers check statements against git log.

Git tags and semantic versions

A tag is a permanent name for one commit. An annotated tag, made with git tag -a, also stores who made it, when, and a message. The course uses annotated tags with names like v1.0.0. The number follows the semantic versioning pattern of MAJOR.MINOR.PATCH, where a larger number means a bigger change. A tag makes a deploy or a rollback precise. "Deploy the latest" is vague. "Deploy v1.0.0" names one commit that anyone can check out again.

The flow below shows how the release leaves your laptop. Two things travel: the tag, which goes to GitHub, and the image, which goes to the registry.

The tagging commands from the slides are these.

git tag -a v1.0.0 -m "CityPulse v1.0.0: ingest, validate, advise"
git show v1.0.0 --no-patch
git describe --tags

Line by line:

  • git tag -a v1.0.0 creates an annotated tag called v1.0.0 on the current commit. -a makes it annotated.
  • -m "..." gives the tag its message in double quotes. The message is required for an annotated tag, so the tag records why it was made.
  • git show v1.0.0 --no-patch displays the tag and the commit it points to. --no-patch hides the list of file changes, so you see only the summary.
  • git describe --tags prints the nearest tag name for the current commit. Right after tagging, it prints v1.0.0.

The slide output for the first command shows the tag's tagger, date and message, followed by the commit hash a01db2c..., which is the exact commit the tag pins. Pushing the tag is a separate step. Until you run git push origin v1.0.0, the tag exists only on your machine.

Trap: Forgetting to push the tag

A tag created on your laptop is invisible to the team. Check that the tag is on GitHub, not only on your machine, before you announce the release.

Trap: Rolling back with a detached HEAD

git checkout v1.0.0 shows the old code, but git will say you are in a "detached HEAD" state. Do not commit there unless you create a branch first. To run the old version, rebuild or pull the old image tag instead.

Docker images for a release

Docker packages the service and its pinned dependencies into an image. A dependency is a library your code uses, such as a web framework. Pinned means you fix the exact version, so the same image is produced on every machine. The course gives the reason: handing over an image, not a "works on my machine" setup, removes environment drift, and the receiving team runs the exact bytes you tested.

The alternative to Docker that the course mentions indirectly is a README that asks the receiver to install everything. That works until one library version differs, and then the service behaves differently. An image does not depend on what is installed on the receiver's machine.

The Dockerfile is the recipe for the image. Each line adds a step.

FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "service:app", "--host", "0.0.0.0", "--port", "8000"]

Line by line:

  • FROM python:3.11-slim starts from a ready-made base image that has Python 3.11 installed. The slim version is a smaller build.
  • WORKDIR /app sets /app as the folder that later commands run in. It is created if it does not exist.
  • COPY requirements.txt . copies the dependency list from your computer into the image's /app folder. The . on the end means "the current folder".
  • RUN pip install --no-cache-dir -r requirements.txt runs a command while the image is built. pip installs Python packages, -r reads the list from the file, and --no-cache-dir stops pip from keeping a download cache inside the image, which keeps the image smaller.
  • COPY . . copies the rest of your project into the image. The dependency step comes before this line on purpose. Docker reuses saved steps when nothing above them has changed, so changing only your code does not reinstall every package.
  • EXPOSE 8000 documents that the service listens on port 8000. It does not open the port on its own.
  • CMD [...] is the command that starts when a container runs. uvicorn is a web server for Python. --host 0.0.0.0 makes it listen on all network interfaces inside the container, and --port 8000 sets the port.

Line by line: docker build creates an image from the Dockerfile in the current folder, which is the final .. -t citypulse:1.0.0 gives the image a name, citypulse, and a tag, 1.0.0. Trap: Dockerfile and file list do not match

The slide's Dockerfile starts the server with service:app, which means a file called service.py. The file list in the Step 3 commit example does not include service.py. Before you build, check that the file the CMD line names exists in your repository. This is the kind of mismatch that a stranger finds in the first minute.

Trap: Pushing a tag before the image builds

In the release script shown in the worked example, the tag is pushed before the Docker build runs. If the build then fails, the tag is already on GitHub. Decide the order before you run the script for real.

GitHub Pages portfolios

GitHub Pages publishes static files (HTML pages, CSS styling and media) from a GitHub repository as a free website over HTTPS. The course's portfolio uses the repository named <username>.github.io, and the site is published from its main branch. A portfolio must show who you are, what you built, proof that it works, and how to contact you, in a page that a hiring manager can scan in 30 seconds.

The slides compare the alternatives. Netlify and Vercel offer similar free hosting with previews, but they need another account, and Pages is enough for one page. A LinkedIn profile must be consistent with the portfolio, but it cannot embed demo media or structure case studies well. Drag-and-drop website builders charge for HTTPS on custom domains, and they keep no Git history.

The publishing commands are below. They create the repository, copy the starter files, compress a demo video, and push.

GH_USER=$(gh api user --jq .login)
gh repo create "$GH_USER.github.io" --public --clone && cd "$GH_USER.github.io"
cp -r ../portfolio-starter/. .
mkdir -p assets
ffmpeg -i ~/Videos/citypulse-demo.mov -t 45 -vf "scale=720:-2" -c:v libx264 -crf 28 -an -movflags +faststart assets/citypulse-demo.mp4
ls -lh assets/citypulse-demo.mp4
git add . && git commit -m "Portfolio: hero, CityPulse case study, demo" && git push -u origin main
sleep 60 && curl -sI "https://$GH_USER.github.io" | head -1

Line by line:

  • GH_USER=$(gh api user --jq .login) stores your GitHub username in a variable. gh api user fetches your profile from GitHub, and --jq .login picks out only the login field.
  • gh repo create "$GH_USER.github.io" --public --clone creates a public repository with that name and copies it to your machine. --public makes it visible to everyone, which Pages needs.
  • && cd "$GH_USER.github.io" runs only if the first command succeeded, and then moves into the new folder. cd means change directory.
  • cp -r ../portfolio-starter/. . copies everything from the starter folder into the current folder. -r copies folders as well as files.
  • mkdir -p assets creates the assets folder. -p means "create it, and do not fail if it already exists".
  • ffmpeg -i ~/Videos/citypulse-demo.mov reads the input video. ~ means your home folder.
  • -t 45 keeps only the first 45 seconds.
  • -vf "scale=720:-2" is a video filter. It sets the width to 720 pixels and calculates the height to keep the shape, and the -2 makes the height an even number, which video codecs need.
  • -c:v libx264 chooses the H.264 video codec, which plays on almost every phone.
  • -crf 28 sets the quality. A higher number gives a smaller, lower-quality file.
  • -an removes the audio track.
  • -movflags +faststart moves the file's index to the front, so the video can start playing before it has fully downloaded.
  • assets/citypulse-demo.mp4 is the output file.
  • ls -lh lists the file with a human-readable size. The slides require it to be under 5 MB. The output is a line such as -rw-r--r-- ... 3.1M ... assets/citypulse-demo.mp4, and the size is the figure you check.
  • git add . && git commit -m "..." && git push -u origin main stages every file, commits it and pushes to GitHub. -u links your local main branch to the remote one, so later pushes need no extra words.
  • sleep 60 waits a minute, because Pages takes a short time to build the site after a push.
  • curl -sI "https://..." | head -1 asks for the headers only (-I), silently (-s), and shows the first line. The expected first line is HTTP/2 200.
Trap: Wrong repository name

The site is published only from a repository named exactly <username>.github.io. A repository with any other name gives a site at a different address.

Trap: Video that stalls on a phone

Recruiters often open links on phones. Keep the demo under 5 MB and test it on a phone before you publish. A video that is fine on your laptop can stall on mobile data.

Trap: Numbers that differ across documents

The résumé, LinkedIn profile and portfolio must show the same numbers. Copy them from metrics.json and keep all three the same.

The worked example

The workbook's example is the release of CityPulse v1.0.0. The goal is that a stranger can clone the repository, build the image and run the service, with a tag that names the exact tested commit. The full release script is below, with the line breaks that the slide extraction split put back together.

pytest -q || exit 1
git tag -a v1.0.0 -m "CityPulse v1.0.0"
git push origin v1.0.0
docker build -t citypulse:1.0.0 .
docker push registry.example.com/citypulse:1.0.0
echo "Release v1.0.0 published"

Line by line:

  • pytest -q runs the tests in quiet mode. pytest is a Python testing tool that runs every test function in files whose names start with test_.
  • || exit 1 means "if the command before this failed, stop the script with an error code of 1". The double bar || is the "or" that runs only when the left side fails. If a test fails, no tag or image is created.
  • git tag -a v1.0.0 -m "..." creates the annotated tag, as explained above.
  • git push origin v1.0.0 sends the tag to the remote called origin.
  • docker build -t citypulse:1.0.0 . builds the image from the Dockerfile.
  • docker push registry.example.com/citypulse:1.0.0 uploads the image to a registry. registry.example.com is a placeholder from the slides. Replace it with the registry your course gives you.
  • echo "..." prints a final message, so you know the script reached the end.

The slide's test file is the first thing that runs. It checks the advisory bands that the service returns for pm2.5 readings. pm2.5 is a measure of fine particles in air, and the bands are the public-health categories built from it.

from advisory import advise
def test_bands():
    assert advise(12.0) == "good"
    assert advise(49.7) == "moderate"
    assert advise(75.0) == "unhealthy"
    assert advise(140.0) == "hazardous"

Line by line, with the indentation restored: from advisory import advise loads the function advise from the file advisory.py. def test_bands(): defines a test function, and pytest finds it because its name starts with test_. Each assert line states something that must be true. If one is false, pytest reports a failure. The four readings 12.0, 49.7, 75.0 and 140.0 are the test values. Only those four results are shown in the slides. The slides do not show advisory.py itself, so the thresholds are not given here.

Running pytest -q . in the project folder prints 1 passed in 0.00s, which means the single test function passed. The . tells pytest to search the current folder.

The demo script is the last check, and it shows the service doing its job.

from advisory import advise
for pm25 in [12.0, 49.7, 75.0, 140.0]:
    print(f"pm2.5={pm25:>6} -> {advise(pm25)}")

Line by line: the first line imports the same function. for pm25 in [...]: repeats the body once for each number in the list, and pm25 holds the current number. The print line builds a sentence. {pm25:>6} right-aligns the number in a field six characters wide, which makes the arrows line up. {advise(pm25)} calls the function and inserts its answer. The slide extraction lost the spaces, but with this formatting the output is pm2.5= 12.0 -> good, then pm2.5= 49.7 -> moderate, then pm2.5= 75.0 -> unhealthy, then pm2.5= 140.0 -> hazardous. Run python3 demo.py in the project folder to see it for yourself.

Requirements prioritisation

What it is. A requirement is something the product must do or must have, such as "show the latest reading" or "export a report". Prioritising requirements means putting them in order, so that the team builds the most important ones first and can say clearly what waits. The method the course uses is MoSCoW. Must means the product fails without the item. Should means the item is important, but the product still works without it. Could means a useful extra that is built only if there is time. Won't (this time) means the team has decided not to build the item in this project, and it has written down why.

The test for each item is one question: does the product fail without it? Here is a small example from a dashboard for air-quality readings.

Requirement Bucket Reason
Show the latest reading Must Without it, the dashboard has no content
Colour each reading by its advisory band Should Useful, but the readings can still be read without colour
Export a PDF of last week Could Build only if time remains
Dark mode Won't (this time) Not needed for this project, and the reason is written down

After sorting, the team can point to one bucket for every row, and each bucket has a reason. That is what prioritisation produces: a decision that someone else can read and check.

How it shows up in a case study. The CityPulse squad has nine candidate items and three weeks. A stakeholder asks for four of them to be Musts because they matter to him. The squad asks the test question for each one. The dashboard cannot show a prediction without the prediction endpoint, so that item is a Must. The four requested items are useful, but the product still runs without them, so they become Should or Could. The team keeps the Musts to five or fewer and writes a reason for each Won't. The reasoning rests on the failure test, not on who asked loudest.

Trap: Everything is a Must

Marking every item as a Must because one senior person asked for all of them looks thorough, but it protects nothing. A list with six or more Musts has not been sorted. Move the least essential ones to Should, and keep the Musts to five or fewer.

Managing scope

What it is. Scope is the set of work that a project will deliver. Managing scope means deciding what is in and what is out, and recording each decision so that it can be checked later. Scope creep is the slow growth of work that happens when new requests are accepted without anything being removed. In a sprint, the team has a fixed capacity, measured in story points. Every addition uses some of that capacity, so an addition must displace something or wait for the next sprint.

Suppose the team has committed 10 story points, which is its whole capacity. A new request is estimated at 3 points. The team has two honest options: name a committed item that moves out to make room, or put the request in the next sprint. A third option, quietly working longer hours, hides the cost rather than managing it.

How it shows up in a case study. Midway through a CityPulse sprint, a client's manager sends a message: "Can you add a CSV download? It should be quick." The squad has no spare capacity. The correct first move is to write the request down, estimate it, and ask the product owner which committed item it would displace or whether it waits for the next sprint. Only then does the team answer the client. Whether the download is quick is a claim nobody has checked, so the estimate comes before any promise. The decision is recorded, so the team can explain it at the review.

Trap: The quick favour

"It should be quick" sounds harmless, and accepting it feels like good service. But capacity is fixed, so a quick favour is still work, and it pushes out something the team already promised. Estimate first, and make the trade-off visible.

Incremental delivery

What it is. Incremental delivery means building and shipping small pieces that work from one end to the other, one after another. A layered plan does the opposite: it finishes the whole database, then the whole model, then the whole interface. A thin slice is a narrow path through every layer that works. It takes one input, passes it through each part and returns a visible result. Here is a tiny example of a slice written in Python.

def ingest(reading):
    return {"pm25": reading}

def predict(row):
    return "good" if row["pm25"] < 50 else "moderate"

print(predict(ingest(12.0)))

The function ingest wraps the reading in a dictionary, and predict returns a band. The last line passes one value through both. The output is good, because 12.0 is below 50. The slice is small, but it proves that the path from input to answer works. Later, the team widens each part: real storage replaces the dictionary, and a real model replaces the rule. Each step keeps a working path.

How it shows up in a case study. A CityPulse team spends its first three weeks building the database layer, with no endpoint and no model. In week four it discovers that the stored format does not match what the model expects. A thin slice in week one would have shown that mismatch while there was still time to change the design. The mentor's advice is to make the first slice run from one reading in to one prediction out, and then widen it each week, checking the end-to-end path after each change.

Trap: Integrate at the end

"We will connect the layers in the last week" sounds like a plan, but it hides every integration problem until the time when fixing them is most expensive. Each layer may look finished alone and still fail when it meets the next one.

Managing risk

What it is. A risk is an event that may happen and would hurt the project if it did. Risk management means recording each risk, judging how likely it is and how much damage it would do, naming an owner, and writing down what will be done about it. A list of these entries is called a risk register. Each entry needs a date on which someone reviews it, because a risk that nobody reviews is simply forgotten.

Risk Likelihood Impact Owner Response Review
The data agreement may not arrive Medium High Asha Switch to the public air-quality dataset if no agreement by 10 April Friday stand-up

The row is useful because someone can act on it. It names the event, the size of the damage, a person, a fallback and a date. A risk with only a description is a worry, not a plan.

How it shows up in a case study. The CityPulse squad's register says only "data may be late". The mentor asks the team to make the entry complete. The squad adds an owner who will chase the agreement, a likelihood and impact rating, a fallback dataset, and a date on which the fallback is switched on if the agreement has not arrived. The entry is now something the team can act on. The reasoning is that a fallback you have not triggered is still a plan, but only once it has a trigger and an owner.

Trap: The register with no owner

A register that lists risks with no owner, no response and no review date looks careful, because it is long. It cannot change anything, because nobody is responsible for acting on it.

Agile ceremonies

What it is. A ceremony is a regular meeting with a fixed purpose in an agile team. The four that matter here are sprint planning, the daily stand-up, the sprint review and the retrospective. Each one answers a different question. Sprint planning asks what the team will commit to in the next sprint. The daily stand-up asks whether anything is blocking the work today. The sprint review asks whether the product works and whether stakeholders want to change it. The retrospective asks how the team worked and what it will change.

Ceremony When Question it answers Main audience
Sprint planning Start of the sprint What will we commit to, and what is the goal? The team
Daily stand-up Every day, about 15 minutes What is blocking us today? The team
Sprint review End of the sprint Does the product work, and is it what stakeholders need? The team and stakeholders
Retrospective End of the sprint, after the review How did we work, and what will we change? The team

How it shows up in a case study. A CityPulse squad reaches the end of its sprint. The client's manager attends the demo and gives feedback on the dashboard. A teammate then wants to use the same meeting to discuss how the sprint was run. The mentor separates the two. The feedback on the product belongs to the sprint review, and the discussion of the team's process belongs to the retrospective, which should be held after the review and be blameless. Keeping them apart stops the client from sitting through an internal debate, and it stops the team's process from being judged by a stakeholder.

Trap: Review and retrospective are the same meeting

Both happen at the end of a sprint, so they are easy to confuse. The review is about the product and includes stakeholders. The retrospective is about the team's process and is internal. Mixing them means that neither is done properly.

Acceptance criteria

What it is. An acceptance criterion is a condition that must be true before a piece of work counts as done. A good criterion is testable: someone who did not write the work can check it with a command or a number and get a clear yes or no. Here are two examples.

Vague Testable
The API works curl -d @tests/sample.json to /predict returns HTTP 200
Predictions are fast 95 per cent of requests on the test laptop finish in under 500 ms

The vague version cannot fail, so it cannot be checked. Two people can read "works" and disagree about whether it is met. The testable version names the command or measure, so the result is either a 200 status or it is not, and either under 500 ms or not.

How it shows up in a case study. The CityPulse team writes a card for the prediction endpoint that says "the endpoint is reliable". A tester asks how she will know it is done. The mentor asks the team to rewrite the criterion so that it names a sample request, the expected status code and the field the reply must contain. The rewrite also says where the test runs. The reasoning is that a criterion is only as good as the check someone can run from it.

Trap: Criteria that cannot fail

"The dashboard is user-friendly" and "the code is clean" are common acceptance lines. They describe a quality, but they give no test and no number, so the work can be called done whatever happens.

Handover runbooks

What it is. A runbook is a document of exact steps for running and looking after a system. Each step gives a command, the output a reader should expect, what to do if the output is different, and how to roll back. A handover runbook is written so that a stranger can keep the system running after the original authors have left. It sits alongside the README and the HANDOVER.md file, and it holds the parts that a README usually leaves out, such as known issues.

Step Command Expected output
1 pytest -q . 1 passed in 0.00s
2 docker compose up -d --build One line per service, each started or running
3 curl -i -X POST -d @tests/sample.json ... First line HTTP/1.1 200 OK

The table is a runbook in miniature. A newcomer can see the command, the result that means success, and the result that means something has gone wrong.

How it shows up in a case study. The CityPulse project is handed to a client's engineer. On the first run, Step 3 fails with "file not found", although the file exists on the original author's laptop. The runbook was written from memory, and the file is listed in .gitignore, so it never reached the repository. The fix is to run every command on a clean clone of the tagged version before the handover is merged, and to record the expected output beside each command. The new owner then sees the failure in the runbook's own test, not in the first minute of their own work.

Trap: Commands that were never run

A runbook command that has never been run from a clean copy is a guess. The first real run then fails in front of the new owner, which is the worst time to find out.

Roles and RACI

What it is. A RACI chart lists each task and says who plays which role in it. R means Responsible, the person who does the work. A means Accountable, the person who signs off the result. C means Consulted, people who give input before the decision. I means Informed, people who hear the outcome afterwards. Each task must have exactly one A. Two As mean that nobody clearly owns the outcome, and no A means that nobody signs it off. Here is a small chart for three tasks.

Task Asha Ravi Neha Client
Ingest the readings R C I I
Train the model C A R I
Sign off the release A R C I

Read down a column to see a person's roles, and read across a row to check that a task has exactly one A. The client is marked I because they hear about the release but do not approve it.

How it shows up in a case study. The CityPulse squad fills in a RACI chart for the release of the OPD model. Two people are marked A for the release, and the client is also marked A because it owns the product. The mentor says the chart is invalid. The fix is to keep exactly one A, on the person who signs the release off, and to give the other roles to the people who do the work, consult or inform. The client moves to I, since it hears about the release and does not approve it.

Trap: Two Accountables, or none

A chart with two As looks shared, but it means nobody owns the result. A chart with no A looks neutral, but it means nobody can sign off. Both break the rule.

Retrospectives

What it is. A retrospective is a short meeting at the end of a sprint. The team asks three questions: what went well, what did not go well, and what it will change next time. Each change needs an owner and a date for the next sprint, or it will not happen. The meeting should be blameless, which means it examines the process rather than looking for the person who made a mistake. A useful retrospective produces a few specific changes, not a list of complaints.

Went well Did not go well Change Owner Check
The stand-ups were short The demo data was loaded on the morning of the review Load and check the demo data the day before each review Asha Next sprint retrospective

The row shows the three parts of a good output: what happened, what will change, and who will check it by when.

How it shows up in a case study. At the end of a CityPulse sprint, the sprint review failed because the demo data was not loaded in time. At the retrospective, someone suggests that one teammate should be more careful. The mentor asks the team to turn the problem into a process change: check and load the demo data the day before, give the job to one named owner, and review the result at the next retrospective. The reasoning is that blaming a person does not stop the next failure, but a changed process can.

Trap: A list of complaints

A retrospective that ends with a long list of complaints and no actions feels honest, but nothing changes. Each complaint should become a change with an owner and a date, and the team should pick the few that matter most.

The project charter

What it is. A project charter is a short document that starts a project. It states the purpose, which is why the project exists. It names the sponsor, who authorises the work. It lists the success measures, which show when the project has succeeded. It records the main constraints, such as the deadline or the data available, and the main risks. The charter changes rarely. A sprint plan is different. It lists the work for the next few weeks in detail, and it changes at each sprint.

Charter field Example for CityPulse
Purpose Tell hospital operations staff how long each outpatient wait is likely to be
Sponsor The client's operations manager, who approves the project
Success measures The model beats the current median rule on the holdout data
Constraints Three weeks, the data available by 10 April, no paid hosting
Main risks The data agreement may not arrive

The field list answers why the project exists and how it will be judged. A day-by-day task list does not belong in it, because that list will be out of date within a week.

Its document is a list of tasks for each of the next three weeks, with names and hours beside each task. The mentor asks for the charter to be rebuilt. The purpose, the sponsor, the success measures and the constraints must come first, and the task list moves to the sprint plan where it can change. The reasoning is that a charter tells the reader why the work matters and who decided it, while a plan tells them what the team will do this week.

Trap: A plan called a charter

A day-by-day plan looks like a serious document, so it is easy to mistake it for a charter. But it leaves out why the project exists and who approved it, and those are the two things a charter must answer.

The graded lab

The graded lab is a short Python task with a time limit of 30 seconds and a memory limit of 128 MB. It is marked by visible tests, which you can run yourself, and by hidden tests, which you cannot see. The visible tests are worth 85 points and the hidden tests are worth 15 points. Hidden tests check the edge cases and rules that the visible tests do not cover, so they decide whether you reach full marks. This section restates the task, explains the Python ideas it needs, lists the rules that careless solutions break, gives a method, and works through a different problem that uses the same skills.

The task in plain words

The scenario. The CityPulse team has a fixed sprint capacity. It must decide which backlog items to commit to, using each item's value, its effort and whether it is a Must. Your job is to write three functions that make those decisions for the backlog.

Each backlog item is a dictionary with four keys: id, which is text; value, which is a whole number; effort, which is a whole number; and must, which is True or False. A dictionary is a collection of named values, written in braces. The starter file gives you a module-level dictionary called RANK and three functions. The rules for each function are these.

  • moscow_bucket(item) -> str takes one item and returns one of four text values: "Must", "Should", "Could" or "Wont".
  • If item["must"] is truthy, return "Must". In Python, a value is truthy if it counts as True in an if test. Most values are truthy, but 0, False, None and the empty string are not.
  • Otherwise, compute the ratio value / effort. If the ratio is 3 or more, return "Should". If it is 1.5 or more, return "Could". Otherwise return "Wont". "3 or more" includes exactly 3, and "1.5 or more" includes exactly 1.5.
  • prioritise(items) -> list[str] takes a list of items and returns the list of their ids, in priority order.
  • Sort by three things, in this order: the bucket rank, where Must comes before Should, Should before Could, and Could before Wont; then the ratio value / effort, highest first; then the id, A to Z, to break any tie.
  • The bucket rank is looked up in RANK, which maps each bucket name to a number from 0 to 3.
  • fit_capacity(items, capacity) -> list[str] walks the items in the priority order that prioritise gives. For each item, it keeps the item if its effort still fits in the capacity that remains, and then takes that effort off the remaining capacity. It returns the chosen ids in the order they were taken. It does not stop when an item does not fit.

The statement gives one worked example. An item with value 10 and effort 2 has a ratio of 5, and its bucket is "Should" if it is not a Must. With a backlog of A (10 over 2), E (8 over 2), D (a Must), B (3 over 2) and C (1 over 2), and a capacity of 8, prioritise returns D, A, E, B, C, and fit_capacity returns D, A, E.

What each function needs

Each idea below is taught with a small example that uses different data, such as exam marks or a shopping list. Do not use these examples as parts of your solution. Their job is to show you the idea, so that you can apply it to the lab's data yourself.

Truthiness and if. An if statement runs its block when the test after it is truthy. Python treats 0, False, None, "" and an empty list as false, and most other values as true.

for answer in [0, "no", ""]:
    print(repr(answer), bool(answer))

The output is 0 False, then 'no' True, then '' False. The string "no" is not empty, so it is truthy, even though its meaning is negative. If the statement says "truthy", test the value with if, not with == True.

Comparisons at a boundary. A comparison with >= includes the boundary, and a comparison with > excludes it. Use the one the statement names.

def grade(mark):
    if mark >= 70:
        return "Distinction"
    if mark >= 50:
        return "Pass"
    return "Fail"

print(grade(70), grade(69.9), grade(50))

The output is Distinction Pass Pass. A mark of exactly 70 is a Distinction, because the test includes 70. A mark of 69.9 is not, so it falls to the next test.

Division and rounding. In Python 3, / gives a decimal result, and // drops the decimal part. Round only once, at the end of a calculation, and only if the task asks for it.

print(7 / 2, 7 // 2, round(10 / 3, 2))

The output is 3.5 3 3.33. The // operator gives 3, which would be wrong for any comparison that needs the decimal part. Rounding 10 / 3 early to a whole number would also change the answer that a boundary test sees.

Numbers and bool. A bool is a special kind of integer. True counts as 1 and False as 0, so isinstance(True, int) is True. This matters when a check must distinguish a flag from a number.

print(isinstance(True, int), isinstance(True, bool), type(5).__name__)

The output is True True int. If a check must reject flags but accept numbers, test for bool first, because a plain int test accepts True as well.

Reading dictionary values. d["key"] returns the value for key, and fails with a KeyError if the key is missing. d.get("key", default) returns the default instead.

member = {"name": "Mira", "paid": True}
print(member["name"], member.get("discount", 0))

The output is Mira 0. Use [] for keys that must exist, and .get only for keys that are optional.

Sorting with a key. sorted(items, key=f) returns a new list in the order of the value f gives for each item. The original list is left unchanged. A key can be a tuple, and tuples compare one position at a time from the left.

words = ["pear", "fig", "apple", "kiwi"]
print(sorted(words, key=lambda w: (-len(w), w)))

The output is ['apple', 'kiwi', 'pear', 'fig']. The number of letters is negated, so longer words come first. Words of the same length are then ordered A to Z. Sorting text places capital letters before lower-case ones, so sorted(["b", "A", "a"]) gives ['A', 'a', 'b'].

Reversing only one part of a key. reverse=True flips the whole ordering, including any part of the key you wanted to keep ascending. To make one part descending and another ascending, negate the number that should be descending, and leave the text part alone.

Dictionary lookup for a rank. A dictionary can map a name to a rank, and sorting by that rank puts the groups in the order you want.

ORDER = {"low": 0, "medium": 1, "high": 2}
levels = ["high", "low", "medium"]
print(sorted(levels, key=lambda lv: ORDER[lv]))

The output is ['low', 'medium', 'high']. The lookup ORDER[lv] fails with a KeyError if a name is missing from the dictionary, which is a useful signal that the data is wrong.

The greedy loop with continue. A greedy loop takes the best available option at each step and does not look back. The continue statement skips the rest of the current pass through a loop and moves to the next item. A loop that uses continue for a skipped item keeps checking the items after it.

budget = 5
picked = []
for cost in [4, 2, 1]:
    if cost > budget:
        continue
    picked.append(cost)
    budget -= cost
print(picked, budget)

The output is [4, 1] 0. The cost 2 is skipped because it is more than the 1 that is left, and the loop still checks the cost 1 after it. A break in that place would have stopped the loop and given [4].

Returning a list. A function returns a value with return, and a test can compare that value. Build the list in the loop with .append, and return it at the end. Do not print the result, because the tests check returned values.

Worked twin problem

This problem is about a food bank that loads a van. It uses the same skills as the lab: classifying items with thresholds, sorting by several keys, and a greedy loop that skips items that do not fit. The rules are different, so you must read them.

Each donation is a dictionary with name (text), days_left (a whole number), kg (a whole number) and an optional urgent flag, which is False if it is missing. Implement three functions.

  • band(donation) -> str returns "Now" if urgent is truthy. Otherwise it returns "Soon" if days_left is 2 or less, "Later" if days_left is 7 or less, and "Hold" for anything else.
  • load_order(donations) -> list[str] returns the names sorted by band, in the order Now, Soon, Later, Hold; then by weight, heaviest first; then by name, A to Z.
  • pack_van(donations, max_kg) -> list[str] walks through the donations in load order, skips every "Hold", keeps each donation whose kg fits in the space left, and returns the names in the order they were kept. A negative max_kg raises ValueError.

A load that exactly fills the remaining space counts as fitting. Work through the example below before you read the solution.

donations = [{"name": "Milk", "days_left": 1, "kg": 5}, {"name": "Rice", "days_left": 10, "kg": 20}]
print(band(donations[0]), band(donations[1]))

The output is Soon Hold. Milk has two days or fewer left, and Rice has more than seven.

The solution is in the block below. It is run by the build, so every assert must pass.

NOW, SOON, LATER, HOLD = "Now", "Soon", "Later", "Hold"
BAND_RANK = {NOW: 0, SOON: 1, LATER: 2, HOLD: 3}


def band(donation):
    if donation.get("urgent", False):
        return NOW
    if donation["days_left"] <= 2:
        return SOON
    if donation["days_left"] <= 7:
        return LATER
    return HOLD


def load_key(donation):
    return (BAND_RANK[band(donation)], -donation["kg"], donation["name"])


def load_order(donations):
    return [d["name"] for d in sorted(donations, key=load_key)]


def pack_van(donations, max_kg):
    if max_kg < 0:
        raise ValueError("max_kg cannot be negative")
    remaining = max_kg
    taken = []
    for d in sorted(donations, key=load_key):
        if band(d) == HOLD:
            continue
        if d["kg"] <= remaining:
            taken.append(d["name"])
            remaining -= d["kg"]
    return taken

    {"name": "Rice", "days_left": 10, "kg": 20, "urgent": False},
    {"name": "Lentils", "days_left": 6, "kg": 8, "urgent": False},

Line by line, the important parts are these.

  • NOW, SOON, LATER, HOLD = ... gives each band name a variable. A typo in a variable name raises an error, while a typo in a plain string silently makes a different band.
  • BAND_RANK maps each band to its place in the order, so Now is 0 and Hold is 3. Sorting by these numbers puts the bands in the required order.
  • In band, the urgent test comes first, so an urgent donation is Now whatever its days. donation.get("urgent", False) returns False when the key is missing, which is the behaviour you want for an optional field.
  • The two if tests with <= include the boundaries. Two days is Soon, and seven days is Later.
  • load_key returns a tuple of three parts. The first is the band rank. The second is -donation["kg"], so heavier items come first. The third is the name, which breaks any tie in weight. Because the name is last, Flour comes before Lentils when both weigh 8 kg.
  • load_order builds the names in the order that load_key gives. The list comprehension is a short form of a loop that appends each name to a new list.
  • pack_van raises ValueError before it does any work when the limit is negative. The variable remaining starts at the limit and goes down each time an item is kept.
  • The continue line skips every Hold, and the if line keeps an item only when its weight fits in what is left. The loop never stops early, so a small item later in the order can still be kept after a large one is skipped.
  • sorted(...) returns a new list, so the donations list keeps its original order. The check on before confirms that.
  • The try block expects ValueError. If no error were raised, the raise SystemExit line would stop the program with a message, and the test would fail. When the error is raised, the except catches it and the test passes.

When the block runs, it prints nothing if every assert passes.

def courier_fee(parcel):
    weight = parcel["weight_g"]
    if weight <= 500:
        fee = 40
    elif weight <= 2000:
        fee = 70
    else:
        fee = 120
    if parcel.get("express", False):
        fee = fee * 1.25
    return round(fee, 2)


def cheapest_first(parcels):
    return [p["id"] for p in sorted(parcels, key=lambda p: (courier_fee(p), p["id"]))]

Model answer

Bus factor is the number of people who would have to leave before a module could no longer be maintained. We measured it from git history by counting the distinct authors of each module, not the number of commits. Any module with only one author was given a second owner, who is a person who did not write the code. That person drafted the runbook section, and the original author reviewed it before it was merged into HANDOVER.md.
