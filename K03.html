How to use these ticket guides

These chapters walk through the real tickets on your squad's capstone board, in the order the board schedules them. The ticket text (story, acceptance criteria, test cases, subtasks and definition of done) comes from the course site. The guides teach you how to do each ticket yourself and how your trainer will check it.

How the board works:

  • A ticket moves Backlog, To Do, In Progress, Review, Done. Only a trainer can move it to Done, after running its test cases, and gives it a gate score from 0 to 3.
  • Every ticket is judged from commit evidence: your commits, pull requests and reviews in the squad repository. Work done on someone else's laptop does not count for you.
  • Each ticket has a points value (the "pts" column). Defence tickets (marked D01, D02 and so on) are where you present and answer questions.
  • Your viva scores acceptance criteria met, technical depth, contribution and ownership, and understanding, each 0 to 5. The final capstone grade shown on the platform is 60% your own contribution and 40% your team's.

Read the guide the evening before the session that ticket is scheduled for. Do the work yourself, in your squad's repository, and run every test case in "How it is checked" before you ask the trainer to review it.

Y2-T08 · First real PR per student, 2 peer reviews, protect main

Session 8 · phase E2 · 3 points

The ticket in plain words

CityPulse now runs on its own. A script fetches city data on a timer, and five students change the same code. Until now, anyone could push a change straight onto main, the shared main line of the repository. One careless push can break the data for the whole squad.

This ticket moves the squad to GitHub flow, the way most software teams work. Each student takes one small task card, called an Issue, and works on a feature branch, a separate line of work. When the change is ready, the student opens a pull request (PR), which asks for that branch to be merged into main. Two squad-mates read the change, run it and comment. The author answers with new commits, and only then does the change merge.

The Tech Lead also turns on branch protection, a GitHub rule that refuses direct pushes to main and requires an approval first. GitHub enforces it, so nobody can skip it under deadline pressure.

A comment that says only "LGTM" (short for "looks good to me") scores zero. A useful review says what you ran, what input you used and what you saw.

Before you start

The spec says Y2-T07 must be complete: the tag v0.1-p1 exists, fetch.sh, healthcheck.sh and merge.sh are on main, the Project board holds at least ten Issues, and the trainer has recorded the baseline, the commit hash of main at the end of Y2-T07.

You need a GitHub account with write access to the squad repository, Git and the GitHub command-line tool gh on your laptop, and your squad-mates' usernames. Run the commands in Git Bash, not PowerShell, because the quoting rules differ. Run these checks inside your clone of the squad repository.

Key fact: Why the baseline matters

The last two test cases look only at commits after the baseline hash. Earlier commits, from earlier tickets, are out of scope.

How your trainer checks it

The trainer checks five acceptance criteria with five test cases. Replace <squad> with your squad name and <n> with a PR number.

  • Criterion 1: five merged PRs, one per student, each with Closes #<n> and the template sections. TC1 checks the count, the authors and Closes #. The trainer reads the template sections by eye.
  • Criterion 2: at least two review comments per PR, and every thread resolved. TC2 counts the comments.
  • Criterion 3: each student reviewed two PRs, with a comment that is not just "LGTM". Check with the reviews command in Y2-T08.5.
  • Criterion 4: a direct push to main is rejected. TC5 tests this.
  • Criterion 5: every commit after the baseline references a PR. TC4 tests this.

TC1: merged PRs with the closing keyword

gh pr list --state merged --search 'merged:>=2026-11-24' --json number,author,body --jq '.[] | [.number,.author.login,(.body|test("Closes #"))] | @tsv'
  • gh pr list lists pull requests in the repository you are standing in.
  • --state merged keeps only merged PRs.
  • --search 'merged:>=2026-11-24' uses GitHub search syntax to keep PRs merged on or after the date in the ticket.
  • --json number,author,body asks for three fields, as JSON.
  • --jq '...' filters the JSON with a jq program. Single quotes stop the shell changing it.
  • .[] takes each PR in turn. [...] builds a list of the number, the author's login and one true or false value.
  • .body|test("Closes #") checks the body for the exact text Closes #. It is case sensitive, so closes # in lower case gives false.
  • | @tsv prints each list as one tab-separated line.

Passing output has at least five rows, five distinct authors, and true on every row:

A failing false on a row means that PR's body lacks Closes #. Fix the PR description, and the trainer reads the new text. Write Closes # with a capital C, because the trainer's jq test is case sensitive.

TC2: at least two review comments per PR

gh api repos/citypulse-y2/citypulse-<squad>/pulls/<n>/comments --jq 'length'
  • repos/citypulse-y2/citypulse-<squad> is the squad repository.
  • pulls/<n>/comments lists the review comments on PR n, which are the comments attached to lines of the diff.
  • --jq 'length' counts the items returned.

Passing output is 2 or more. A failing 0 or 1 usually means the reviewer wrote in the conversation box or in a review summary, and those are not counted.

TC2 does not check that threads are resolved, but criterion 2 does. Check it yourself on the PR page, where each thread shows a Resolved label, or run this and expect only true lines:

gh api graphql -f query='query { repository(owner:"citypulse-y2", name:"citypulse-<squad>") { pullRequest(number: <n>) { reviewThreads(first: 50) { nodes { isResolved } } } } }' --jq '.data.repository.pullRequest.reviewThreads.nodes[].isResolved'

TC3: one approval required on main

gh api repos/citypulse-y2/citypulse-<squad>/branches/main/protection --jq '.required_pull_request_reviews.required_approving_review_count'
  • repos/.../branches/main/protection is the protection rule for main.
  • .required_pull_request_reviews picks the review section of the JSON.
  • .required_approving_review_count picks the number of approvals required.

Passing output is 1 (or more). Failing output is null or 0, which means the rule does not require reviews. A not-found error that says the branch is not protected means no rule exists yet.

TC4: every commit after the baseline references a PR

git fetch origin
git log --first-parent --format='%h %s' <baseline>..origin/main
  • git fetch origin downloads new commits without changing your files.
  • --first-parent follows only the line that main follows, so each merged PR appears as one line.
  • --format='%h %s' prints the short hash, a space and the subject line.

Passing output has every subject ending in (#<n>) or containing Merge pull request #<n>. A failing line has no PR reference, such as a1b2c3d Fix typo in healthcheck.sh. The usual cause is a commit pushed straight to main. Tell the Tech Lead at once, and do not rewrite main to hide it.

TC5: direct push rejected

git commit --allow-empty -m test && git push origin main
  • git commit --allow-empty creates a commit that changes no files, and && runs the push only if it worked.

Passing output is a refusal that contains the words protected branch hook declined. The exact wording depends on GitHub. A failing run says the push succeeded, which means the rule is missing or administrators are not covered. That also leaves a commit with no PR on main, which then fails TC4, so tell the Tech Lead at once. Run this only in a throwaway clone, never in your working clone.

Do it, step by step

Y2-T08.1: Add the pull request template (Tech Lead)

Goal. Put a file at .github/PULL_REQUEST_TEMPLATE.md. GitHub reads this exact path and fills every new PR description with it.

Stage 1: branch from main.

git switch main
git pull --ff-only
git switch -c chore/pr-template

git pull --ff-only refuses if it cannot move your main forward in a straight line, for example when your main has commits of its own that origin lacks. You should see Switched to a new branch 'chore/pr-template'.

Stage 2: create the folder and the file.

mkdir -p .github

-p creates missing parent folders, and it does nothing with no error if the folder already exists. Create the file in your editor, with these headings in this order, and a short prompt under each in your own words:

## What
## Why
## How to test
## Evidence
## Checklist

The Checklist should remind the author to write Closes #<n>, with a capital C.

Stage 3: commit, push and open the PR.

git add .github/PULL_REQUEST_TEMPLATE.md
git commit -m "Add pull request template"
git push -u origin chore/pr-template
gh pr create --fill --reviewer <name>

git push -u uploads the branch and links it to origin. gh pr create --fill builds the title and body from the commit message, and prints the PR URL.

Stage 4: merge after one review.

gh pr merge <n> --squash --delete-branch

--squash makes one commit on main, and --delete-branch removes the branch.

How to test. Run gh api repos/<owner>/<repo>/contents/.github/PULL_REQUEST_TEMPLATE.md --jq .name. It should print PULL_REQUEST_TEMPLATE.md.

Trap: Protecting main before the template is merged

The ticket orders the template first. Merge it, then protect main. If you protect first, the template PR still needs an approval, and a mistake in your first rule is harder to fix while every merge waits on a review.

Y2-T08.2: Turn on branch protection (Tech Lead)

Goal. Make GitHub refuse direct pushes to main and require one approval.

Stage 1: check the current state.

gh api repos/<owner>/<repo>/branches/main/protection

Before any rule exists, this prints an error containing Branch not protected (HTTP 404). You need admin rights on the repository for this call.

Stage 2: set the rule. On the website, open Settings, then Branches, and add a classic branch protection rule for main (TC3 reads this kind of rule, not a newer "ruleset"). Tick the options to require a pull request before merging, to require one approval, and to include administrators. GitHub's newer wording for the last one is "Do not allow bypassing the above settings". Take a screenshot for the LMS.

Stage 3: test. Run TC3. It should print 1.

Key fact: What include administrators means

Without enforce_admins, administrators could still push straight to main. TC5 checks this setting.

Y2-T08.3: Take an Issue and branch

Goal. Have one Issue that is yours, on a branch that starts from the latest main.

Stage 1: choose the Issue. On GitHub, open an Issue from the board and assign yourself. Move its card to In progress in the browser.

Stage 2: update main and create the branch.

git status
git switch main
git pull --ff-only
git switch -c feat/<n>-<slug>
git branch --show-current

git switch -c creates the branch from the commit you are on, which is now the latest main. git branch --show-current prints the branch name so you can confirm it.

Trap: Branching from a stale main

A new branch starts at the commit you are on. If you skip the pull, your PR will include other people's old work.

Y2-T08.4: Implement, commit, push and open the PR

Goal. Make small commits, push the branch and open a PR the reviewers can run.

Stage 1: stage only your change.

git add -p <file>

-p shows each changed block and asks whether to stage it. Type y or n for each block.

Stage 2: commit and check.

git commit -m "Add usage message when an option gets no value"
git show --stat HEAD

git show --stat HEAD lists the files in the latest commit. If an unexpected file appears, run git reset --soft HEAD~1, which undoes the commit but keeps your edits, and stage again.

Stage 3: test on the lab machine. Run the change exactly as the Issue describes, on the lab Linux machine where the scripts run. Save the command and its output for your PR evidence.

Stage 4: push.

git push -u origin feat/<n>-<slug>

Stage 5: open the PR. Write the PR body in a file first, which avoids quoting problems in Git Bash. Fill in the template in your own words, with Closes #<n>. Then run:

gh pr create --base main --title "<your title>" --body-file <file> --reviewer <name1>,<name2>

--body-file reads the description from your file. --reviewer takes two names with a comma and no spaces.

Stage 6: check the body.

gh pr view --json body --jq .body | grep -c "Closes #"

The output should be 1.

Trap: Opening a second PR for a fix

A PR follows its branch. Push fixes to the same branch, or the review history splits.

Y2-T08.5: Review two PRs by running them

Goal. Give two PRs a substantive review, each with a verdict.

Stage 1: find the PRs.

gh pr list --search 'review-requested:@me'

Stage 2: check out and run.

gh pr checkout <n>

This downloads the branch and switches your clone to it. Run the PR's "How to test" steps, save the output, and return with git switch to your own branch.

Stage 3: write the comment. A useful comment states what you ran, the input, what you saw and what you suggest:

I ran <command> with <input>. It printed <what you saw>. I suggest <change>, because <reason>.

Stage 3b: attach it to a line. TC2 counts only comments on lines of the diff. In the browser, open the PR's Files changed tab, click the + beside the line you tested, write your comment and choose Start a review. Add a second line comment if you can. The next stage then submits the review.

Stage 4: post the verdict. The --body text becomes the review summary, which TC2 does not count, so the line comments from stage 3b matter.

gh pr review <n> --comment --body "<your comment>"
gh pr review <n> --request-changes --body "<your comment>"
gh pr review <n> --approve --body "<your comment>"

Choose the verdict that matches what you found.

How to test.

gh api repos/<owner>/<repo>/pulls/<n>/reviews --jq '.[] | select(.user.login=="<your-login>") | .state'

select(...) keeps only your reviews, and .state prints each verdict: APPROVED, CHANGES_REQUESTED or COMMENTED.

Trap: Writing LGTM and nothing else

"LGTM" on its own earns no credit. Say what you ran, with what input, and what you saw.

Y2-T08.6: Address comments, resolve, merge and clean up

Goal. Answer every comment, push fixes, resolve each thread and merge.

Stage 1: fix and push.

git add <file>
git commit -m "Address review: <short description>"
git push

Stage 2: reply, resolve and re-request. Reply on each thread, mark it resolved, and ask the reviewer to look again. A reviewer who requested changes must approve again.

Stage 3: merge and clean up.

gh pr merge <n> --squash --delete-branch
git switch main
git pull --ff-only

How to test.

git fetch origin
git log --oneline -1 origin/main

The subject should end with (#<n>), the form TC4 checks.

Trap: Deleting the branch before the merge

Deleting a branch closes its PR without merging it. Merge first, then delete.

Y2-T08.7: Confirm the Issues and the evidence (Scrum/Docs)

Goal. Every Issue is closed and every card is in Done.

For each Issue number, run:

gh issue view <n> --json state --jq .state

The answer should be CLOSED. Then move each card to Done on the board, and post the PR links and the protection screenshot to the LMS.

Prove it before review

Run every test case yourself, in this order, and keep each output: TC1, then TC2 for each of your PRs, then TC3, then TC4 after git fetch origin. Run TC5 last, in a throwaway clone made with git clone in a separate folder, and delete that folder afterwards.

Then write the PR description with five headings: What, Why, How to test, Evidence and Checklist. Write each in your own words. Evidence means pasted real output, log excerpts or screenshots, with tokens and personal details removed first. The Checklist holds - [ ] items and the line Closes #<n>.

Definition of done

  • [ ] PULL_REQUEST_TEMPLATE.md is on main. You know it is true when the Y2-T08.1 check prints the file name.
  • [ ] Branch protection is on, and the screenshot is on the LMS. You know it is true when TC3 prints 1 and the screenshot shows administrators included.
  • [ ] Your PR is merged with the template, an Issue link and at least two review comments you addressed. You know it is true when TC1 shows your row as true and every thread is resolved.
  • [ ] You reviewed two PRs substantively. You know it is true when the reviews check shows your verdicts, and each comment names what you ran.
  • [ ] Your Issue is closed and its card is in Done. You know it is true when gh issue view prints CLOSED.
  • [ ] No direct pushes to main after the baseline. You know it is true when TC4 shows only PR references.

What goes wrong

Symptom Cause Fix
TC1 shows false for your PR. The body says closes # in lower case, or the line is missing. Edit the PR description to use Closes #<n>.
TC1 shows four distinct authors, not five. One student merged two PRs and another merged none. Agree who merges next.
TC2 shows 0 or 1. The comments are in the conversation box, not on diff lines. Ask the reviewer to comment on specific lines.
TC3 shows null. The rule does not require reviews, or no rule exists. Ask the Tech Lead to check Y2-T08.2.
TC4 shows a commit with no (#n). A commit was pushed straight to main. Tell the Tech Lead at once. Do not rewrite main.
TC5 push succeeds. enforce_admins is off. Ask the Tech Lead to turn it on, then run TC5 again.

Defend it in the viva

1. Why must branch protection include administrators?

Model answer

The rule exists so that nobody skips the review. Without enforce_admins, the Tech Lead could push straight to main under deadline pressure. The setting applies the same rule to everyone, and TC5 proves it by refusing a direct push.

2. What is the trade-off between a squash merge and a normal merge commit?

Model answer

A squash merge gives main one commit per PR, which keeps history short. The cost is that the branch's individual commits are no longer on main, so the detail lives on the PR page.

3. Walk me through one review you gave. What did you run, and why did you write what you wrote?

Model answer

Name the PR, the exact command you ran after gh pr checkout, the input you used and what the output showed. Explain your verdict. A comment needs evidence, because "LGTM" alone earns nothing. Describe only a review you really gave.

4. A required approval slows every merge. Why is it still worth it?

Model answer

The wait is short, and a second person reads the diff and runs the code before the change reaches the shared line. An error caught there is far cheaper than a broken fetch that nobody notices for a day.

5. What does git log --first-parent show, and why does TC4 use it?

Model answer

It follows only the line of commits that main itself follows, so each merged PR appears as one line. TC4 can then check that each line references a PR number. Without the flag, commits inside merged branches would appear too, and some would have no PR reference.

Check yourself

Y2-T09 · Add shellcheck CI gate on PRs; resolve and log one conflict each

Session 9 · phase E2 · 3 points

The ticket in plain words

Five students in your squad edit the same shell scripts. A shell script is a text file of terminal commands that the computer runs from top to bottom. When two people change the same lines on different branches, Git cannot decide which version to keep. It stops and reports a merge conflict. This ticket teaches two habits.

The first habit is to resolve a conflict on purpose. You read both sides, write the version that keeps what both people intended, test the script, and record what you did. The second habit is to let a robot judge each change. Every pull request will run ShellCheck, a tool that reads shell scripts and reports risky lines. "It works on my machine" is not evidence. A green check on the pull request is.

CityPulse needs this because its fetch job runs unattended on a schedule. A script with a missing pair of quotes can break on a file name that contains a space, and nobody is watching. The ticket makes sure a broken script cannot reach main.

Before you start

These must already be merged, from Y2-T08: PULL_REQUEST_TEMPLATE.md on main, branch protection on main that requires one approving review, and one merged pull request from you. The trainer must also have created the branches conflict-a and conflict-b.

Check each tool before you begin. Run the commands in Git Bash on Windows or on the lab Linux machine.

  • Git. Run git --version. Ready when it prints git version and a number.
  • GitHub CLI, gh. Run gh auth status. Ready when it says you are logged in to github.com.
  • ShellCheck. Run shellcheck --version. Ready when it prints a version: line. On the lab machine, install it with sudo apt install shellcheck if missing. On Git Bash, use the Docker route in step 3.
  • Clean repository on main. Run git switch main and then git status. Ready when it prints nothing to commit, working tree clean.
  • Conflict branches. Run git fetch origin and then git branch -r. Ready when the list includes origin/conflict-a and origin/conflict-b.

In this guide, <name> means your own name in lower case, with no spaces, as your squad agreed.

1. Resolve the planned conflict (T09.1)

The goal. Merge two branches that changed the same lines, resolve the conflict by hand, test it, and push.

Practise on a scratch repository first. Git marks a conflict with three marker lines. Make a throwaway repository and cause one:

mkdir conflict-practice && cd conflict-practice
git init -q
printf 'LIMIT=10\n' > config.sh
git add config.sh && git commit -qm "start"
git switch -q -c left && printf 'LIMIT=20\n' > config.sh && git commit -qam "left"
git switch -q - && printf 'LIMIT=30\n' > config.sh && git commit -qam "right"
git merge left
  • git switch -q -c left creates a branch called left and moves onto it. -c means create.
  • git switch -q - returns to the previous branch.
  • The last command changes the same line on both branches, so the merge stops.

Run cat config.sh. You see:

<<<<<<< HEAD
LIMIT=30
=======
LIMIT=20
>>>>>>> left

The lines between <<<<<<< HEAD and ======= are your version. The lines between ======= and >>>>>>> left are the other version. To resolve it, edit the file to hold the final value, delete all three marker lines, then run git add config.sh and git commit -m "Resolve LIMIT: keep 30". The git add marks the conflict resolved, and the commit completes the merge. If you get stuck, git merge --abort returns you to the state before the merge.

The real conflict. In your squad repository:

git fetch origin
git switch -c resolve-<name> origin/conflict-a
git merge origin/conflict-b
git status --short
  • git switch -c resolve-<name> origin/conflict-a creates your branch from the trainer's conflict-a.
  • git merge origin/conflict-b stops with a conflict in scripts/fetch_once.sh. The ticket says the trainer or your pair prepared both branches on the same lines of that file. If your merge reports a different file, or no conflict, ask your trainer which branches and file to use.
  • UU in front of a file in git status --short means it has an unresolved conflict.

Open scripts/fetch_once.sh, read both sides, and write the version that keeps both intentions. Then check it:

grep -nE '^(<<<<<<<|=======|>>>>>>>)' scripts/fetch_once.sh || echo "no markers left"
bash -n scripts/fetch_once.sh && echo "syntax ok"
  • grep -nE prints the line number of any line that starts with a marker. The ^ anchors the match to the start of the line.
  • || echo runs only if grep found nothing. Expected output: no markers left.
  • bash -n checks the syntax without running the script. Expected output: syntax ok.

Run the script the way Y2-T06 taught you, and confirm it exits with 0. Then commit and push:

git commit -m "Merge conflict-b: keep both sides' changes in fetch_once.sh"
git push -u origin resolve-<name>

  • -u links the local branch to the remote one.
  • --draft marks the pull request as not ready to merge. You close it after the trainer has seen it, with gh pr close <number>.

Defend it in the viva

1. Why does the check gate the merge button instead of only reporting a result?

Model answer

A report that people can ignore protects nothing. A required check blocks the merge until it passes, so a broken script cannot reach the scheduled job. The gate is the whole point of the check.

2. Why use merge for the conflict branches rather than rebase?

Model answer

Merge keeps the history exactly as it happened and adds one commit that joins the branches. The cost is a messier graph. Rebase gives a straight line, but it rewrites commits, and on a branch others have pulled that makes their copies disagree with yours. The trade-off is clean history against safety on shared work, and this squad chooses safety.

3. Which piece did you own, and how do you show it works?

Model answer

Name the piece you owned, the command that proves it, and where the evidence is posted. For example, a student who owned the workflow file would say which job and step they wrote, and that the run history shows a failure followed by a success. Write your answer from your own commits, because the trainer checks the history against what you say.

4. Why is an unquoted variable dangerous in a script that runs unattended?

Model answer

The shell splits an unquoted value at spaces and expands wildcards into file names. A value with a space becomes two words, so the command may act on the wrong files or fail. Nobody is watching a 3 a.m. run, so the damage can go unnoticed. Double quotes keep the value as one word, which is why ShellCheck reports SC2086.

5. What happens if someone renames the job shellcheck?

Model answer

The check gets a new name, but the required check still waits for the old one. Every pull request then waits forever for a check that never reports. The fix is to restore the job id, or to change the rule and the job name in one step.

The command has four parts, and each one matters:

  • ls lists files. Given two paths, it lists each one. A file is printed by name, and a folder is printed with its contents.

If ls works but grep prints nothing, the heading is missing or written differently, such as ## [v0.2.0] or ### [0.2.0]. Make the heading match the pattern exactly.

TC3. GitHub Release. The trainer runs:

  • gh release view v0.2.0 shows the release that uses tag v0.2.0.
  • --repo citypulse-y2/citypulse-<squad> names the repository, so the command works from any folder. Replace <squad> with your squad's name.
  • --json tagName,body asks for two fields only, the tag name and the notes text, and prints them as JSON.

TC4. Issues on the peer repository. The trainer runs:

  • --repo names the peer repository, which is the one you audited.
  • --author keeps only Issues opened by one login. It takes a single value, so if several of you filed Issues, run the command once per login. Use real GitHub logins.

Passing output has one row per High or Medium finding in your audit file, with the Issue number and title. Failing output is no issues match your search. The usual causes are a wrong login in --author, Issues filed in your own squad repository by mistake, or a missing --state all if you have closed some Issues.

Y2-T10.2 Add CODEOWNERS and issue forms

Goal. Changes to each folder need the right reviewer, and people who report problems use a form.

Stage 1. Create the folders. Start from up-to-date main on a new branch:

git switch main && git pull --ff-only
git switch -c docs/codeowners-issue-forms
mkdir -p .github/ISSUE_TEMPLATE
  • git switch -c creates the branch from the commit you are on, which is now the latest main.
  • mkdir -p creates a folder and any missing parents. -p stops it from failing if the folder exists.

Stage 2. Write CODEOWNERS. CODEOWNERS is a text file at .github/CODEOWNERS. Each line is a path pattern and then one or more owners. GitHub uses the last matching line, so put the general default first and the specific folders after it. One line has this shape:

docs/   @your-login
  • docs/ is the path pattern. A trailing slash matches the folder and everything in it.
  • @your-login is the owner. Use a real GitHub login. The owner must be a member of the organisation or a collaborator.

Add the other lines yourself, in the order the ticket gives: * for the Tech Lead, scripts/ for QA/DevOps and docs/ for Scrum/Docs. Put * first.

Test. Open the file and check that each owner is a real login. After you push the branch, GitHub shows the owners on the file page. Later, a pull request that changes scripts/ lists the QA owner as a required reviewer.

Stage 3. Write one issue form. An issue form is a YAML file in .github/ISSUE_TEMPLATE/. The file has three top-level keys. The skeleton below has placeholders, and you write the rest:

name: <name shown in the New issue menu>
description: <one line about when to use this form>
body:
  - type: textarea
    attributes:
      label: <question the reporter answers>
  • name: and description: set what people see in the New issue menu.
  • body: is a list. Each item is one field on the form. The - type: line starts an item, and the lines indented under it describe it.
  • attributes: holds the settings for the field, such as its label:.

Write at least two forms, for example a bug report and a feature request, as the ticket asks for three files in total.

Test. After you push, open the repository on GitHub, choose Issues, then New issue. Each form should appear in the list. If it does not, the file is in the wrong folder or its YAML is broken. Check the indentation first. YAML uses spaces, not tabs.

Stage 4. Commit and open the pull request.

git add .github/
git commit -m "Add CODEOWNERS and issue forms" -m "Owners per folder and forms for bugs and features."
git push -u origin docs/codeowners-issue-forms
gh pr create --base main --title "Add CODEOWNERS and issue forms" --fill
  • git add .github/ stages every change in that folder, and nothing outside it.
  • The two -m flags make a title and a body paragraph.
  • git push -u origin uploads the branch and links it to origin.
  • gh pr create --fill builds the body from your commit messages. The pull request is created at once, so open it on GitHub afterwards and check the text.

Test. Run git show --stat HEAD. It should list only files under .github/.

Y2-T10.3 Add labels, a milestone and the CHANGELOG section

Goal. Issues can be sorted, the next milestone exists, and the changelog says what P2 delivered.

Stage 1. See the existing labels.

gh label list

gh label list prints the labels already in the repository. Use this list to avoid duplicates. You need eight to twelve labels in total, so create the missing ones.

Stage 2. Create a label.

gh label create "data-quality" --color "B60205" --description "Problems with the data itself"
  • gh label create makes one label. The name is in quotes because it is one argument.
  • --color takes six hexadecimal digits without a #. B60205 is a dark red.
  • --description shows under the label name.

Repeat the command for each label your squad agrees, changing the name, colour and description each time.

Stage 3. Create the milestone. GitHub's command-line tool has no milestone command, so you call the API directly. An API is the set of web addresses a service offers for reading or changing data.

gh api -X POST repos/{owner}/{repo}/milestones -f title='P3 Data pipeline' -f due_on='2026-12-12T23:59:59Z'
  • gh api sends a request to GitHub.
  • -X POST sets the request method to POST, which creates something.
  • repos/{owner}/{repo}/milestones is the address for milestones. gh fills {owner} and {repo} from the folder you are in.
  • -f title=... and -f due_on=... add two text fields. due_on is a timestamp in ISO format, with a T between the date and the time.

Test. List the milestones:

gh api repos/{owner}/{repo}/milestones --jq '.[].title'

--jq picks the value out of the JSON response. You should see P3 Data pipeline.

Stage 4. Write the CHANGELOG section. Open CHANGELOG.md. A Keep a Changelog file starts with a title and an ## [Unreleased] section, followed by one section per version, newest first. The version heading has a fixed shape:

## [0.2.0] - <date>
### Added
- <one line per merged piece of work, with its PR number>
  • ## [0.2.0] must match exactly, because TC2 searches for it.
  • - <date> is the date of the release, in YYYY-MM-DD form.
  • ### Added, ### Changed, ### Fixed and the other Keep a Changelog headings group the lines.

Write one line for each merged piece of work from P2, with its pull request number. Do not paste whole commit messages.

Test. List the headings and check the order:

grep -n '^## ' CHANGELOG.md

The [0.2.0] heading should appear, with the newest version above the older ones.

Y2-T10.4 Tag v0.2.0 and publish the release

Goal. A permanent tag marks the exact commit that closes P2, and the GitHub Release shows its notes.

This subtask belongs to the Tech Lead. Everyone should still read it, because the notes check in TC3 depends on it.

Stage 1. Tag the latest main.

git switch main && git pull --ff-only
git tag -a v0.2.0 -m 'P2: team workflow'
git show --no-patch v0.2.0
  • git pull --ff-only makes sure you tag the latest main, not an old copy.
  • git tag -a v0.2.0 creates an annotated tag. -a stores the author, date and message.
  • git show --no-patch v0.2.0 prints the tag details without the file diff, so you can see that it is annotated and names the right commit.

Stage 2. Push the tag.

git push origin v0.2.0
git ls-remote --tags origin v0.2.0

git push does not send tags unless you name them, so the tag name is required. git ls-remote --tags origin v0.2.0 asks origin for the tag and prints its ID. If it prints nothing, the push did not arrive.

Stage 3. Extract the notes and publish. The release notes should match the changelog section, so take the text from the file:

awk '/^## \[0.2.0\]/{f=1; next} /^## \[/{f=0} f' CHANGELOG.md > /tmp/notes-0.2.0.md
gh release create v0.2.0 --title "v0.2.0" --notes-file /tmp/notes-0.2.0.md
  • awk reads the file line by line. The first rule switches a flag on at the [0.2.0] heading and skips that line. The second rule switches it off at the next heading. The last part prints lines while the flag is on.
  • > /tmp/notes-0.2.0.md writes the result to a file. On Git Bash, /tmp points to a temporary folder, which works for this purpose.
  • gh release create v0.2.0 makes the release for the tag. --notes-file fills its notes from the file you made.

The ticket also allows --notes-from-tag. That option reads the tag's own message, which here is only P2: team workflow, so the notes would not match the changelog. Use the file.

Test. Run gh release view v0.2.0 and check that the notes match your changelog section. TC3 checks the same thing.

Y2-T10.7 Start fetch.py

Goal. A short Python script that fetches one endpoint and writes a CSV with the same header and column order as fetch_once.sh.

Read fetch_once.sh first, because you need the column order. Do not copy another student's code.

Stage 1. Make a branch and a virtual environment. A virtual environment keeps the libraries for this project in one folder:

git switch main && git pull --ff-only
git switch -c feat/<name>-fetch-py
python -m venv .venv
source .venv/Scripts/activate
pip install requests
pip freeze > requirements.txt
  • python -m venv .venv creates the folder .venv with its own Python.
  • source .venv/Scripts/activate turns the environment on in Git Bash on Windows. On the Linux lab machine, use source .venv/bin/activate instead. Your prompt shows (.venv) when it is on.
  • pip install requests installs the requests library into the environment.
  • pip freeze > requirements.txt writes every installed library with its exact version, and the > sends the output to the file. This is the pin.

Check that .venv/ is ignored by Git, so it does not get committed:

grep -n 'venv' .gitignore

Check the library works:

python -c "import requests; print(requests.__version__)"

The output is a version number. If you see ModuleNotFoundError, the environment is not active.

Stage 2. Read the reference output. Look at the first line of the reference file:

head -1 data/raw/<date>.csv

Write the column names down in this order. This is your target. Do not reorder them to suit your code.

Stage 3. Learn to write a CSV with a fixed order. Try this small example in a scratch folder, not in the repository:

import csv

columns = ["station", "value"]
with open("demo.csv", "w", newline="") as f:
    writer = csv.writer(f, lineterminator="\n")
    writer.writerow(columns)
    writer.writerow(["S1", 42])
  • import csv loads the standard CSV library.
  • columns = [...] is the header, in the order you need.
  • open("demo.csv", "w", newline="") opens the file for writing. newline="" stops Python from translating line endings on Windows, which would otherwise give blank lines or doubled carriage returns.
  • csv.writer(f, lineterminator="\n") makes a writer for that file. Without lineterminator, the csv module ends every line with CRLF, which is the cause of the ^M problem in the checks below. "\n" gives plain LF, like a file made by a Bash script.
  • writer.writerow(...) writes one line, with commas between the values.

Save the code as demo.py in the scratch folder and run python demo.py. You should get demo.csv with two lines. Delete the demo file with rm demo.csv afterwards.

This trace shows why the column order must be set by you, not by the dictionary a record happens to arrive in:

Stage 4. Make one request. In src/citypulse/fetch.py, the first version should make one request to one endpoint. Choose the endpoint from your squad's data source. Here is the request part alone, with the address left for you to fill in:

import requests

URL = "<your endpoint>"
response = requests.get(URL, timeout=10)
response.raise_for_status()
  • import requests loads the library you installed.
  • URL = "..." holds the address. Put your own endpoint there.
  • requests.get(URL, timeout=10) sends a GET request, which asks for data. timeout=10 stops the program waiting for more than 10 seconds.
  • response.raise_for_status() raises an error if the server replied with a failure code, such as 404. Without it, a failed request could write an empty file without any error.

Test. Run the file and check the status:

python -c "import requests; r = requests.get('<your endpoint>', timeout=10); print(r.status_code)"

The output should be 200. Replace the placeholder with your endpoint and keep the single quotes.

Stage 5. Write the rows. Turn the reply into records, then write them in your column order. The parsing depends on your data source, so this skeleton leaves the field names to you:

rows = response.json()
for item in rows:
    # list the fields in the order from the reference header
    writer.writerow([...])
  • response.json() turns a JSON reply into Python lists and dictionaries. Check the shape of the reply first, because some endpoints wrap the records in another object.
  • for item in rows: runs the next line once per record.
  • writer.writerow([...]) writes one line. Fill the list with the fields in the order from Stage 2.

Write the header with writer.writerow(columns) before the loop, as in the Stage 3 example.

Stage 6. Name the output file. Use the same folder and date pattern as fetch_once.sh, which is data/raw/<date>.csv. Get today's date in the same form with datetime.date.today().isoformat(). Do not change the date logic now. Making it UTC belongs to Y2-T11.

Test. Run the script, then compare the headers:

python src/citypulse/fetch.py && diff <(head -1 <output csv>) <(head -1 data/raw/<date>.csv) && echo "headers match"
  • diff compares two inputs and prints the lines that differ. Nothing printed means no difference.
  • <(...) is process substitution. It gives diff the output of a command as if it were a file. It works in Git Bash and Linux bash, but not in plain sh.
  • echo "headers match" runs only when diff succeeded, so the message is an honest pass.

Once it passes, commit requirements.txt and fetch.py, push, and open the pull request. Use the exact title from the ticket:

git commit -m "Add fetch.py v0 that fetches one endpoint" -m "Writes the same header and column order as fetch_once.sh."

1. Why does the release note have to match the CHANGELOG section, and not a one-line tag message?

Model answer

The changelog is the record that a reader of the release can check. A tag message is a single line that marks a commit, so it cannot tell a reader what changed. If the release notes come from the changelog section, anyone can compare the two and see the same list of changes. The notes are extracted from the file with awk, then passed to gh release create with --notes-file. That keeps one source of truth, so the two cannot drift apart.

2. What is the trade-off in pinning requirements with pip freeze, compared with always installing the newest version?

Model answer

Pinning gives you repeatable runs. Your script behaves the same on your laptop, on the lab machine and in a month's time. The cost is that you must update the pins on purpose, and an old pinned version may miss a security fix. Always installing the newest version gets fixes automatically, but a library can change under you, and a run that worked yesterday can fail today. For a data pipeline that the team must trust, repeatable runs matter more, so you pin and update on purpose.

4. Why compare your header with the output of fetch_once.sh, rather than trusting your own column list?

Model answer

The reference output is the agreed contract. Later steps, and your trainer's TC5, may read the file by column position, so a column in the wrong place can break them without an error message. Your list is a guess until it matches the reference. Comparing with diff gives an objective result: either the two header lines are identical or they are not. It also catches small differences such as line endings, which a visual check would miss.

5. How do you prove that main is protected, and what does the required check add to the review rule?

Model answer

Query the protection rule with gh api and read the fields. The review count shows how many approvals a pull request needs. The required status check shows which automated job, here shellcheck, must pass before a merge. The review rule depends on people, and the check depends on code, so they catch different problems. A protection that refuses a direct push is the strongest proof, because the server enforces it.
