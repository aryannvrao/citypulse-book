The idea in one minute

Every change to CityPulse code should be checked before a person reviews it, and the check should run the same way every time. Today you hand that job to a robot. GitHub starts a fresh computer in the cloud for each change, copies your code onto it, runs your tests and reports the result on the pull request as a green tick or a red cross. Think of it as a robot reviewer who checks every change in exactly the same way and never forgets a step.

By the end of the day you will be able to write the workflow file, run the same checks on your own laptop first, and find the broken line when a run goes red.

Starting from zero

Every term below is used in this chapter. Skim the ones you already know.

Terminal. A text window where you type commands and read the replies. Everything in this chapter is typed into a terminal.

Command. One line you type that asks the computer to do something. ls is a command that lists the files in the current folder. A command can take arguments, which are extra words that change what it does. In pytest -q, pytest is the command and -q is an argument.

Flag. An argument that starts with a dash, such as -q. Flags change how a command behaves. -q asks for quiet output.

File and folder. A file holds text or data. A folder (also called a directory) holds files and other folders. A folder whose name starts with a dot, such as .github, is hidden in many file browsers but still exists.

Variable. A name that holds a value. In Python, total = 5 stores 5 under the name total. In a shell script, OUT="report.csv" stores the text report.csv under the name OUT.

Function. A named block of code that you can run by name with brackets, such as normalise("pm2.5"). The text inside the brackets is the argument passed to the function. The function may send back a return value, which is the answer it produces.

Script. A file of commands or code that the computer runs from top to bottom. A Python script ends in .py. A shell script ends in .sh and holds terminal commands.

Shell and Bash. The shell is the program that reads your terminal commands. Bash is the most common shell, and most course scripts use it.

Exit code. Every program finishes with a number. 0 means success. Any other number means something failed. After running a command in Bash, echo "exit=$?" prints the exit code of that command. The $? is the Bash way of asking for the last exit code.

Server. A computer that runs programs for other people, all day. GitHub runs your repository on servers, and it also runs your workflows on servers.

Repository (repo). A project folder that Git is tracking. The CityPulse project is one repository.

Git. A tool that records the history of changes to files. Each saved set of changes is a commit.

Branch. A separate line of work inside a repository. Your work goes on a branch, such as feature/clean-readings, and the main line is called main.

Push. Sending your local commits to GitHub, where other people can see them. git push does this.

Pull request (PR). A request on GitHub to merge the commits from one branch into another, usually into main. Other people review it there, and checks such as tests appear on it.

Merge. Combining the changes from one branch into another. A merge conflict happens when two branches changed the same lines and Git cannot decide which version to keep.

YAML. Short for YAML Ain't Markup Language. It is a text format for settings, where indentation shows structure. Use spaces for indentation, never tabs. GitHub Actions workflows are written in YAML.

Test. A small piece of code that calls another piece of code and checks that the answer is right. A test passes or fails.

pytest. A Python tool that finds test functions in files and runs them. The lab uses it. A test function uses the word assert, which checks a condition and stops the test with an error if the condition is false.

pip and requirements.txt. pip is the Python package installer. A package is a library of code someone else wrote, such as pytest. A file named requirements.txt lists the packages a project needs, and pip install -r requirements.txt installs everything listed in it. The -r flag means "read the list from this file".

Linter. A tool that reads code without running it and reports likely bugs or risky patterns.

Continuous integration (CI). Running checks such as tests and linters automatically on every change, rather than when someone remembers.

Runner. The computer that runs a GitHub Actions job. GitHub provides them, and each job gets a fresh one.

Virtual machine (VM). A computer that exists as software inside another computer. Runners are virtual machines, and they are thrown away after each job.

GitHub Actions workflows

What it is. GitHub Actions runs workflows. A workflow is a YAML file in the folder .github/workflows/ of your repository. The file says when the workflow starts (its triggers) and what it does (its jobs). Each job runs its steps on a fresh runner, and the result of the job appears on the pull request as a status check.

Why CityPulse uses it. Every change to fetch.sh and the cleaning code is checked before review. You do not have to remember to run the checks, and a status check can make the merge button unavailable while the check is red. The slides list three alternatives:

Alternative When you would pick it Why CityPulse did not
Jenkins Very flexible, and you run your own servers It needs a server to run and maintain.
GitLab CI Similar YAML model Our repositories and branch protection live on GitHub.
Local pre-commit hooks Fast feedback on your own machine Each developer can skip them. CI cannot be skipped.

How it works. When a pull request is opened, or a commit is pushed to it, GitHub looks at every workflow whose on: block matches the event. Each job starts a clean runner, checks out the code and runs its steps in order. If any step exits with a non-zero code, the job fails, and so does the check. The animation below shows one run.

The slide code, line by line. This is .github/workflows/lint.yml from the slides, with the indentation restored:

name: lint
on:
  pull_request:
  push:
    branches: [main]
jobs:
  shellcheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: ShellCheck scripts/
        run: |
          ls scripts/*.sh
          shellcheck scripts/*.sh
  • name: lint gives the workflow a name. It is the label shown in the Actions tab.
  • on: starts the trigger list. Each key under it is an event.
  • pull_request: runs the workflow when a pull request is opened or updated. The colon with nothing after it means "use the default settings".
  • push: runs the workflow when someone pushes commits.
  • branches: [main] limits the push trigger to the main branch. The square brackets make a list, so you could add more branch names separated by commas.
  • jobs: starts the list of jobs. Each job has an id, and here the id is shellcheck.
  • runs-on: ubuntu-latest asks for a runner using the latest Ubuntu Linux image. ShellCheck is already installed on that image, so the workflow needs no install step.
  • steps: starts the ordered list of steps. Each step starts with a dash.
  • - uses: actions/checkout@v4 runs a ready-made action called checkout, version 4. It copies your repository onto the runner. The @v4 pins the version.
  • - name: ShellCheck scripts/ gives this step a readable label.
  • run: | starts a block of shell commands. The vertical bar means "the lines below, as one block".
  • ls scripts/*.sh lists every shell script in scripts/. The * is a wildcard that matches any name. The line proves the glob found files. If it finds none, ls reports an error and the step stops, so the log shows it.
  • shellcheck scripts/*.sh runs ShellCheck on every .sh file. If ShellCheck finds a problem, it exits non-zero and the step fails.
Trap: Wrong folder, wrong extension

A workflow must be a .yml or .yaml file inside .github/workflows/, at the top of the repository. A file in scripts/workflows/ or workflows/ is ignored, and nothing runs. Nothing warns you.

Trap: Tabs in YAML

YAML does not accept tab characters for indentation. A tab causes a parse error, and the Actions page shows the error line. Indent with spaces, and keep each level consistent.

Trap: Renaming the job

The job id, here shellcheck, is the name that branch protection uses for the required check. If you rename it, the required check name changes too, and pull requests then wait forever for a check with the old name.

The pytest workflow, line by line. The lab uses this ci.yml file, which you will type in the lab:

name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - run: pytest -q
  • on: [push, pull_request] is the same triggers written in short form. The square brackets list both events, with no branch filter. A push to a branch that has an open pull request starts the workflow twice, once for each event.
  • test: is the job id. The check on the pull request is named after the workflow and the job, which is why the Technology in Action page shows CI / test (pull_request).
  • - uses: actions/setup-python@v5 installs a Python version on the runner.
  • with: gives the action its settings. Here it has one, python-version.
  • "3.11" is the Python version. The quotes are needed (see the trap below).
  • - run: pip install -r requirements.txt installs the packages listed in the file.
  • - run: pytest -q runs the tests. -q makes the output short. The step passes only if pytest exits with 0.
Trap: Unquoted version numbers

In YAML, python-version: 3.10 without quotes is read as the number 3.1, because the trailing zero disappears in a number. The runner then installs the wrong Python. Always write the version in quotes, such as "3.10".

Trap: The word on

Some YAML readers, including the PyYAML library used in Python, read a bare word on as the value True. Scripts that check the file may then not find the on key. GitHub itself reads the key correctly. If your own checking script cannot find on, this is the likely reason.

What pytest does. The Technology in Action page runs pytest -q and shows the result below. Each dot means one test passed. The last line gives the total and the time.

The animation below shows how one test drives a small function. The function normalise is in the file clean.py, and the test calls it with the text "pm2.5".

Trap: A passing test is not proof

Tests check only the cases you wrote. If there is no test for a rule, the rule can break and CI stays green. Each rule in the cleaning code should have at least one test that would fail if the rule broke.

ShellCheck linting

What it is. ShellCheck reads a shell script without running it. It reports bugs and risky patterns, each with a line number and a code such as SC2086. It exits with a non-zero code when it finds problems, which makes it a usable gate in CI.

Why CityPulse uses it. The scripts fetch.sh and healthcheck.sh run unattended, so a path bug fails at 3 a.m. with nobody watching. SC2086, the unquoted variable, is the most common bug in student scripts such as fetch_once.sh. Each ShellCheck finding links to a wiki page explaining the fix, so you learn the rule instead of guessing. The alternatives are bash -n, which checks syntax only and misses quoting problems, and manual review, which wastes reviewer time on mechanical issues.

How it works. ShellCheck parses each script, looks for patterns it knows are risky, and prints the line and the code. You fix the code, usually by adding quotes around a variable. Alternatively you add a disable comment with a reason. Then you run it again until it exits with 0, and that is what turns the CI check green.

The animation below is a typed session. The command runs ShellCheck and then prints its exit code. The message text is the one from the slides. Your output layout may differ slightly, depending on the ShellCheck version, but the code and the message are the same.

The mistake and the fix. Suppose someone appends a line to fetch_once.sh:

echo 'wc -l $OUT' >> scripts/fetch_once.sh
  • echo prints its text. Here it prints into the file, not the screen.
  • The single quotes stop the shell from changing $OUT at the time you run echo, so the file gets the literal text $OUT.
  • >> appends the output to the end of scripts/fetch_once.sh. A single > would overwrite the file, which is much worse.

When the script runs later, the shell replaces $OUT with the value of the variable. The line that ShellCheck flags is wc -l $OUT. The fix is to put double quotes around the variable:

wc -l "$OUT"

The quotes keep the value as one word. Without them, a value that contains a space or a wildcard character such as * is split into several words, or it is expanded to match file names. A path with a space in it then breaks the command.

The slides fix the line with sed, a tool that edits text in a stream or file:

sed -i 's/wc -l \$OUT/wc -l "$OUT"/' scripts/fetch_once.sh
  • sed runs the editor. -i edits the file in place, so the result is written back to the same file.
  • s/.../.../ means "substitute the text between the first pair of slashes with the text between the second pair".
  • wc -l \$OUT is the text to find. The single quotes already stop the shell from expanding $OUT, and the backslash tells sed to match a literal dollar sign.
  • wc -l "$OUT" is the replacement text.

You can also open the file in an editor and make the change by hand. The result must be the same.

Trap: Disabling a warning to get green

Do not add a disable comment just to turn the check green. Fix the code. A disable comment is allowed only when you can explain in a comment why the warning does not apply. ShellCheck reads a comment such as # shellcheck disable=SC2086 placed on the line above.

Trap: Sourcing a file

When a script uses source .env, ShellCheck reports SC1091 because it cannot read the file. Put # shellcheck source=/dev/null on the line above the source command to tell it that you know the file is not checked. Use this only when the file is not part of the check.

Trap: An empty wildcard

If scripts/*.sh matches nothing, the command receives the literal text scripts/*.sh, and no real file is checked. The ls scripts/*.sh line in the workflow prints the file list in the log, so you can prove which files were checked.

Merge-conflict resolution

What it is. A merge conflict happens when two branches changed the same lines, and Git cannot choose one. Git stops the merge, marks the file, and waits for you. Git marks the conflicting part like this:

<<<<<<< HEAD
the lines from your branch
=======
the lines from the other branch
>>>>>>> origin/conflict-b

The three marker lines start with <<<<<<<, ======= and >>>>>>>. You edit the file so that it contains the correct final lines, delete all three marker lines, test the script, and commit.

Why CityPulse uses it. Several students edit scripts/fetch_once.sh, so conflicts on the same lines will happen. The planned conflict-a and conflict-b branches let you practise the resolution safely before a real deadline. The file docs/git-log/<name>.md records the cause, the resolution and the verification as evidence for marking. The alternatives are the GitHub web conflict editor, which is fine for small text conflicts but does not let you run the script before committing, and git checkout --theirs, which throws away one side silently.

How it works. The commands in the slides, with a short explanation of each:

git fetch origin
git switch -c resolve-asha origin/conflict-a
git merge origin/conflict-b
git status --short
git diff
  • git fetch origin downloads the latest branches from GitHub without changing your files.
  • git switch -c resolve-asha origin/conflict-a creates a new branch called resolve-asha that starts at the remote branch origin/conflict-a. -c means "create". Replace asha with your own name.
  • git merge origin/conflict-b tries to combine conflict-b into your branch. It stops and reports a conflict in scripts/fetch_once.sh.
  • git status --short lists changed files, one per line. UU in front of a file name means that the file has an unresolved conflict.
  • git diff shows the differences, including the marker blocks, so you can read both sides.

Then you edit the file, keep the correct lines, and delete the three marker lines. Check that none are left, check the syntax, and run the script:

grep -nE '^(<<<<<<<|=======|>>>>>>>)' scripts/fetch_once.sh || echo "no markers left"
bash -n scripts/fetch_once.sh && ./scripts/fetch_once.sh
  • grep searches for text. -n prints the line number of each match, and -E turns on extended patterns.
  • The pattern ^(<<<<<<<|=======|>>>>>>>) matches a line that starts (^) with any of the three markers.
  • || echo "no markers left" runs the echo only if grep found nothing. || means "or, if the first command failed".
  • bash -n reads the script and checks its syntax without running it.
  • && runs the second command only if the first succeeded. So the script runs only after the syntax check passes.
  • ./scripts/fetch_once.sh runs the script. The ./ says "in this folder".

Finally, stage the file, commit the merge and push:

git add scripts/fetch_once.sh
git commit -m "Merge conflict-b: keep env-driven LOC and pm10 column"
git push -u origin resolve-asha

git add marks the file as resolved for Git. git commit -m completes the merge with the message in quotes. -u on the push links the local branch to the remote branch, so later pushes need no extra words.

Trap: Committing leftover markers

If a line ======= remains in the file, the script breaks, and the commit records the broken file. Always run the grep line before git add.

Trap: Keeping one side by habit

Choosing one side without reading it loses a teammate's work. Read both sides first, then write the version that has both intentions.

Trap: Rebase on shared branches

Rebase rewrites commits, so it changes history that other people may already have. On a branch that others share, a rebase forces them to repair their own copies. Use merge on shared branches, as the slides do.

The worked example

Goal. Prove that the test suite protects the cleaning code. You will break normalise on purpose, watch the suite fail, and then restore it. This is the same demonstration as step 6 on the Technology in Action page.

The code. The cleaning code is clean.py, with the indentation restored:

## clean.py - CityPulse reading cleaning
VALID = {"PM25", "PM10", "NO2", "O3"}
ALIASES = {"pm2.5": "PM25", "no2": "NO2"}

def normalise(code):
    c = code.strip().lower()
    return ALIASES.get(c, code.strip().upper())

def clean(rows):
    out = []
    for r in rows:
        code = normalise(r["pollutant"])
        if code not in VALID:
            continue  # drop unknown
        if r["value"] is None or r["value"] < 0:
            continue  # drop bad value
        out.append({**r, "pollutant": code})
    return out
  • VALID is a set, written in braces, of the pollutant codes the project accepts. A set holds each item once, and checking in a set is fast.
  • ALIASES is a dictionary, written in braces with key: value pairs. It maps spelling variants to canonical codes. "pm2.5" maps to "PM25".
  • def normalise(code): defines a function that takes one argument, called code.
  • c = code.strip().lower() makes a new value, c. strip() removes spaces at both ends, and lower() makes every letter lowercase.
  • return ALIASES.get(c, code.strip().upper()) looks up c in the dictionary. get returns the value for the key, or the second argument if the key is missing. If there is no alias, the function returns the text in capitals.
  • def clean(rows): takes a list of readings. Each reading is a dictionary with the keys station_id, pollutant and value.
  • out = [] creates an empty list. The loop adds good rows to it.
  • for r in rows: takes one reading at a time.
  • if code not in VALID: and continue skip the rest of the loop body for this reading. continue means "go to the next reading".
  • if r["value"] is None or r["value"] < 0: drops a reading with no value or a negative value.
  • out.append({**r, "pollutant": code}) adds a copy of the reading with the cleaned pollutant code. {**r, ...} copies every key from r and then replaces pollutant.
  • return out returns the list after the loop finishes.

The tests. The test file is test_clean.py. It contains five test functions:

## test_clean.py
from clean import normalise, clean

def test_normalise_alias():
    assert normalise("pm2.5") == "PM25"

def test_normalise_upper():
    assert normalise(" no2 ") == "NO2"

def test_clean_drops_unknown_pollutant():
    assert clean([{"station_id": "S1", "pollutant": "XYZ", "value": 5}]) == []

def test_clean_drops_negative_value():
    assert clean([{"station_id": "S1", "pollutant": "PM25", "value": -1}]) == []

def test_clean_keeps_good_row():
    r = [{"station_id": "S1", "pollutant": "pm2.5", "value": 40}]
    assert clean(r)[0]["pollutant"] == "PM25"
  • from clean import normalise, clean loads the two functions from the file clean.py. The file name without .py is the module name.
  • Each function whose name starts with test_ is found and run by pytest.
  • Each assert line checks one expected result. If the two sides are not equal, pytest reports a failure.
  • == [] checks that the result is an empty list.

Step 1: run the suite. Run pytest -q in the folder that contains both files:

Five dots and 5 passed means the five tests passed.

Step 2: break the code on purpose. Empty the alias table, so that pm2.5 no longer maps to PM25:

ALIASES = {}   # was {"pm2.5": "PM25", "no2": "NO2"}

With the table empty, normalise("pm2.5") returns PM2.5, because the fallback is only the text in capitals. The dot stays in the text.

Step 3: run the suite again.

  • The summary names each failing test and the file it is in.
  • AssertionError is the error an assert raises when its condition is false.
  • The text after it shows the two sides of the failed comparison: the value the code produced, then the value the test expected. In the second failure, clean dropped the row because PM2.5 is not in VALID, so clean(r)[0] raises IndexError on an empty list.
  • 2 failed, 3 passed is the total count. The tests about upper-casing and about dropping bad rows still pass, because they do not depend on the alias table.

Step 4: restore the table and run again. Put back ALIASES = {"pm2.5": "PM25", "no2": "NO2"}, then run pytest -q. The output returns to 5 passed.

What this proves. On the pull request, the same run would show CI / test (pull_request) failed, and a required check would block the merge. The bug never reaches main. The steps you just followed are the same ones the robot follows, only on a clean runner in the cloud.

Key fact: Reading a failure

A failed test prints the name of the test, the file, the expected value and the actual value. Start from the first FAILED line. The line number of the failure, if shown, tells you where the assert was.

The hands-on lab, step by step

Run the commands in a terminal that understands Bash syntax. The course examples use Bash. On Windows, Git Bash is the usual choice. Before the lab, check that Git is installed with git --version, and that the GitHub command line tool gh is installed and logged in with gh auth status. gh is a program that talks to GitHub from the terminal.

Work inside a folder that is a Git repository, for example your CityPulse project. Use a new branch for all of the lab, so that main is never changed directly.

1. Add a test the CI will run

What you do. Create the cleaning code and the tests from the worked example. Create the branch first, with git switch -c feature/clean-readings. The -c flag creates the branch and switches to it.

What you type. Create clean.py and test_clean.py with the code from the worked example, with the alias table restored to {"pm2.5": "PM25", "no2": "NO2"}.

What you should see. Running pytest -q shows five dots and 5 passed.

How you know it worked. The count is five, and no test has the word FAILED next to it.

2. Pin dependencies

What you do. Create requirements.txt in the same folder. Pinning a version means writing the exact version you tested with. A fresh runner has no packages installed, so this file tells it what to install.

What you type. Create requirements.txt with one line:

pytest==9.1.1

The == means "exactly this version". A line with just pytest would install whatever the newest release is, and a green run today could turn red next month for reasons that have nothing to do with your code.

Then run the install and the tests together:

pip install -r requirements.txt && pytest -q
  • pip install -r requirements.txt installs the packages listed in the file.
  • && runs pytest -q only if the install succeeded.

What you should see. The line Requirement already satisfied: pytest==9.1.1 if pytest is already installed, then 5 passed.

How you know it worked. The pytest==9.1.1 version is in the output, and the test count is still five.

3. Create the workflow file

What you do. Create the folder .github/workflows and the file ci.yml inside it.

What you type. Run this in the repository root:

mkdir -p .github/workflows
  • mkdir makes a folder.
  • -p creates the parent folder .github too if it is missing, and does not complain if the folder already exists.

Then create .github/workflows/ci.yml in your editor with the content from the section above, the pytest workflow. Read the earlier section for what each line means.

What you should see. The file appears at .github/workflows/ci.yml, and the folder is hidden in some file browsers.

How you know it worked. Run ls .github/workflows. The output is ci.yml. To check that the YAML is readable, run this Python command, which reads the file and prints a summary:

python3 -c "import yaml;d=yaml.safe_load(open('.github/workflows/ci.yml'));print(d['name'],'/',list(d['jobs']),'/',len(d['jobs']['test']['steps']),'steps')"
  • python3 -c runs a line of Python typed after -c.
  • import yaml loads the YAML library. It must be installed. If it is not, install it with pip install pyyaml.
  • yaml.safe_load(open(...)) opens the file and turns it into Python data.
  • d['jobs'] looks up the jobs key, and list(...) turns its keys into a list.
  • len(d['jobs']['test']['steps']) counts the steps in the test job.

Expected output: CI / ['test'] / 4 steps. If the file has a tab or a missing colon, this command stops with an error that names the line.

4. Declare the triggers

What you do. Check that the on: block runs the workflow on pushes and on pull requests.

What you type. The top of ci.yml must have:

name: CI
on: [push, pull_request]

This runs the workflow when anyone pushes commits to any branch, and when a pull request is opened or updated. The block form is also valid, for example to run on pushes to main only:

on:
  pull_request:
  push:
    branches: [main]

What you should see. Nothing is printed on your machine. The effect is seen on GitHub after the push in step 7.

How you know it worked. The Actions tab shows a run whose event is push or pull_request after you push. If no run appears, the file is probably in the wrong folder.

5. Define the job and steps

What you do. Check that the test job has the four steps in the correct order: checkout, set up Python, install, test.

What you type. The jobs: part of ci.yml:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -r requirements.txt
      - run: pytest -q

Each line has a job in it with a purpose:

  • runs-on: ubuntu-latest chooses the operating system of the runner.
  • actions/checkout@v4 copies your repository. Without it, the runner has an empty folder and pytest finds no files.
  • actions/setup-python@v5 installs Python 3.11, in quotes as required.
  • pip install -r requirements.txt installs the pinned packages on the fresh runner.
  • pytest -q runs the tests, and the job passes only if pytest exits with 0.

Order matters. The install step needs the code checked out first, because the file it reads is in the repository.

What you should see. The YAML check in step 3 prints CI / ['test'] / 4 steps.

How you know it worked. The four steps appear in the order above on the job page after the run in step 7. Each one has a green tick when it passes.

6. Run the suite locally first

What you do. Replay on your own machine exactly what the runner will do. The suite must be green here before the cloud sees it. A test author who cannot make the suite pass locally would only be outsourcing the debugging to a slower machine.

What you type. Run the two commands in the same folder:

pip install -r requirements.txt
pytest -q

The Technology in Action page also shows a file called run_ci_locally.sh that contains these two commands. It is optional. Two commands typed by hand are enough.

What you should see. 5 passed in ... at the end.

How you know it worked. The exit code is 0. Check with pytest -q; echo "exit=$?", which prints exit=0 after the test output.

7. Commit, push and watch CI

What you do. Save your work as a commit, send the branch to GitHub, and watch the run.

What you type. Run these commands in the repository:

git add .
git commit -m "Add clean.py tests and CI workflow"
git push origin feature/clean-readings
gh run watch
  • git add . stages every changed file in the current folder and below. The dot means "here".
  • git commit -m "..." saves the staged files as one commit with the message in quotes.
  • git push origin feature/clean-readings sends the branch to the remote named origin.
  • gh run watch follows the latest workflow run and prints each step as it finishes.

The output shows each step, then the result:

Where a workflow file must live

What it is. A GitHub Actions workflow is a YAML file. It must have the extension .yml or .yaml, and it must sit in the folder .github/workflows/ at the top of the repository. GitHub reads only that folder, and it does not search the rest of the project. A file in any other place is ignored. GitHub gives no error and no warning, so the Actions tab simply stays empty.

For example, the repository layout below runs a workflow. The second layout runs nothing, even though the file content is identical.

citypulse/
  .github/workflows/ci.yml     <- read by GitHub
  scripts/ci.yml               <- ignored

The output you see on the Actions page is the first workflow, named by its name: line. The second file produces no output at all, because no run is ever created from it.

How it shows up in a case study. A teammate writes a correct workflow and saves it as scripts/workflows/lint.yml. The pull request shows no checks. The reasoning is short: GitHub looks for workflows only under .github/workflows/, so the path is the first thing to check. The fix is to move the file, not to rewrite its content, and the next pull request then shows the check.

Trap: Right folder name, wrong place

A folder called workflows is not enough. The path must be exactly .github/workflows/, starting at the repository root. Nothing warns you when the path is wrong.

Choosing when a workflow runs

What it is. The on: block lists the events that start a workflow. An event is something that happens in the repository, such as a push of commits or the opening of a pull request. pull_request starts the workflow for a pull request. push starts it for a push of commits. Adding branches: [main] under push limits that trigger to pushes to the branch main.

For example, the block below runs on every pull request, and on pushes to main only.

on:
  pull_request:
  push:
    branches: [main]

A direct push to feature/login does not match the push trigger, because the branch filter excludes it. Nothing runs for that push. A pull request from feature/login into main does start the workflow, because the pull_request trigger is listed.

How it shows up in a case study. A workflow contains only on: pull_request. A developer pushes a commit straight to main without opening a pull request. Nothing starts, because the trigger is about pull request events, and a direct push creates none. The reasoning is to match the event in the scenario against the event in the on: block, one line at a time.

Trap: Two events, two runs

A workflow with on: [push, pull_request] and no branch filter runs twice when a branch with an open pull request receives a commit: once for the push and once for the pull request. Count the events, not the commits.

Copying your code with checkout

What it is. Every job starts on a fresh runner, which is a clean virtual machine. Before a job starts its steps, the runner's working folder is empty. The step actions/checkout@v4 copies the repository onto the runner, so the later steps can read your files. The @v4 at the end pins the version of the action.

For example, a job that runs pytest -q without a checkout step looks like this:

steps:
  - run: pytest -q

The output on the runner is an error such as "no tests ran" or "file not found", because there are no files to read. Adding - uses: actions/checkout@v4 as the first step makes the same pytest -q line find test_clean.py.

How it shows up in a case study. A job runs pytest -q, and the log says it collected no tests, even though the repository holds test_clean.py. The reasoning starts with the runner. A fresh runner does not remember the repository, so the first question is whether the job copied the code. The missing step is the checkout, and it must come before any step that reads a file.

Trap: Checkout after the test

Moving checkout to the last step does not help. Steps run in the order written, so pytest runs on the empty folder before checkout copies anything.

Installing a Python version

What it is. The step actions/setup-python@v5 installs the Python version you name in its with: block. The with: keyword passes settings to an action. The version is text, so it must be in quotes. YAML reads an unquoted number such as 3.10 as the number 3.1, because a trailing zero in a number disappears. The action then asks for the wrong version, and the step usually fails with a "version not found" message.

For example:

- uses: actions/setup-python@v5
  with:
    python-version: "3.10"

With the quotes, the text 3.10 reaches the action unchanged, and the runner installs Python 3.10. Without them, the value becomes 3.1, which is a different version.

How it shows up in a case study. A team's workflow asks for Python 3.10, but the log shows that version 3.1 was requested, and the setup step fails. The reasoning goes back to the file. The value in the file is unquoted, so YAML changed it before the action saw it. Quoting the version fixes the cause, and the team does not need to change the runner or the packages.

Trap: Quotes that look optional

Quotes around a version look like decoration, but here they change the meaning. The unquoted value is a number, and the quoted value is text. Always quote every version.

Keeping tokens out of the code (secrets)

What it is. A secret is a value stored in the repository settings, such as an API token or a deploy key. It is kept out of the workflow file, so it never enters the history of a commit. A step reads it with the expression ${{ secrets.NAME }}. GitHub hides the value in the log, so a printed secret shows as ***. An expression in double curly braces is GitHub's way of inserting a value into the workflow at run time.

For example, this step gives the token to a deploy script without writing it into the file:

- run: ./deploy.sh
  env:
    API_TOKEN: ${{ secrets.DEPLOY_TOKEN }}

The file itself contains only the name DEPLOY_TOKEN. The real value stays in the repository settings.

How it shows up in a case study. A student wants to save time and pastes the token into the workflow file, so that it is easy to find. The reasoning follows the history. Every commit that holds the file keeps the token, even after a later edit removes it, so the token must be treated as leaked and replaced. The correct design uses a secret, and the token is then changed only in the settings.

Trap: A private repository is still a shared history

Making the repository private does not protect a token written into a file. Anyone with access, and every clone, keeps the old commits with the token in them.

Running one job for many versions (matrix)

What it is. A strategy: matrix: block runs the same job once for each combination of values in its lists. The keyword matrix names the lists, and ${{ matrix.python-version }} reads the value that the current job uses. Each combination is one job. Each job runs all of its steps, and by default the jobs run in parallel on separate runners.

For example:

strategy:
  matrix:
    python-version: ["3.10", "3.11", "3.12"]

This block starts three jobs, one for each version. A second list, such as an os: list with two values, would multiply the count: two operating systems and three versions give six jobs.

How it shows up in a case study. A team wants the tests to run on three Python versions. They write one job with a loop in its shell script, and the run is slow and hides which version failed. The reasoning favours the matrix. One job per version gives a separate result for each version on the pull request, and a failure names the version that broke.

Trap: Counting the wrong thing

A matrix does not loop inside one job. Count the combinations: each combination is one job, and the number of jobs is the product of the list lengths.

Making one job wait for another (needs)

What it is. The needs: keyword makes a job wait for one or more other jobs. If a job named in needs does not succeed, the job that depends on it is skipped, not run. Jobs with no needs: start at the same time, as soon as a runner is free.

For example:

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - run: echo "linting"
  test:
    needs: lint
    runs-on: ubuntu-latest
    steps:
      - run: echo "testing"

If lint fails, the job test is shown as skipped. If lint passes, test starts. Without the needs: line, both jobs would start together.

How it shows up in a case study. A workflow has a lint job, a test job that needs lint, and a deploy job that needs test. Lint fails. The reasoning follows the chain of needs. test is skipped because lint failed, and deploy is skipped because test did not run successfully. The reader must not expect deploy to run on its own, because the chain carries the skip forward.

Trap: Skipped is not passed

A skipped job is not a green job. If the release depends on a skipped job, the release is skipped too. Do not read a skipped job as a passing check.

Keeping files after a run (upload-artifact)

What it is. A runner is removed when its job ends, so any file left on it is lost. The action actions/upload-artifact@v4 saves chosen files with the run, so that you can download them from the run page afterwards. A later job can fetch the same files with actions/download-artifact, because each job gets its own runner. The path: value is a pattern, such as reports/*.html, that names the files to save.

For example:

- uses: actions/upload-artifact@v4
  with:
    name: coverage
    path: coverage.xml

The file coverage.xml appears in the run's artifacts list. Without this step, the file is gone when the job finishes.

How it shows up in a case study. A test job writes a coverage report, and a reviewer cannot find it after the run. The reasoning starts from the runner's life. The runner is deleted at the end of the job, so the file must be uploaded during the job. The fix is to add the upload step after the file exists, and to check that the pattern matches it.

Trap: A pattern that matches nothing

If path: matches no file, the default behaviour is to warn and carry on. The job can then pass with no artifact at all. Read the log of the upload step to confirm that a file was found.

Speeding up installs with a cache

What it is. A cache keeps downloaded files between runs, so a later run can reuse them instead of downloading again. The actions/setup-python@v5 step can cache pip downloads with the line cache: pip. A cache is found by its key. If a run finds a cache with the same key, it restores the saved files. The key must change when the dependencies change. A hash is a short fingerprint of a file's content, and it changes whenever the content changes, so a key built from the hash of requirements.txt is a good key.

For example, cache: pip in the setup step uses a key derived from requirements.txt for you. Without that setting, a fixed key such as pip-v1 never changes, so the old packages keep coming back.

How it shows up in a case study. A team upgrades pytest in requirements.txt, but the run still uses the old version. The reasoning goes to the key. The key is fixed, so the run restores the cache from before the upgrade and installs nothing new. The fix is to make the key depend on the file content, so a change in the file gives a new key.

Trap: Speed that hides the truth

A cache makes runs faster, but a stale cache can make a green run test the wrong packages. A faster run is useful only when the key changes with the dependencies.

Required checks and re-running a job

What it is. A required status check is a rule in the branch protection settings for main. It names a check, and the pull request cannot merge until that check reports success. The name must match the check the workflow reports, which is the job's name (its name: line, or the job id if there is none). A check that never runs leaves the pull request waiting. To run a failed job again on the same commit, use the Re-run failed jobs button on the run page. Re-running uses the same commit, so it cannot fix a bug in the code. A bug needs a new commit.

For example, a job with the id shellcheck and no name: line reports a check called shellcheck, and that is the name the branch rule must use.

How it shows up in a case study. A pull request waits forever for a check called shellcheck, but the workflow job is named lint-shell. The reasoning starts with the name. The rule and the job name do not match, so the check never appears and the merge stays blocked. The fix is to rename the job id to match the rule, or to update the rule, and then push a new commit to see the check run.

Trap: Turning the gate off

Removing the required check makes the waiting stop, but it also removes the protection. Fix the name or the code instead.

Quick self-test

Ten mixed questions, one per topic, in the same order as the topics above. They are harder than the ones in each topic.

The graded lab

The graded lab is a Python problem with a fixed statement. You write three functions, the platform runs visible tests, and then it runs hidden tests that you cannot see. This section explains the task in plain words, teaches the Python ideas you need for it with small examples that have nothing to do with the lab's data, lists the rules that careless solutions break, and then works through a different problem from start to finish. The worked problem is for practice only. It does not solve the graded lab.

The task in plain words

The scenario. A CityPulse GitHub Actions workflow connects its jobs with needs:. Before a run starts, the scheduler must put the jobs in a valid order, and it must refuse a workflow whose needs form a loop. A workflow is modelled as a dictionary. Each key is a job name, and each value is the list of jobs that the key needs. For example, {'lint': [], 'test': ['lint'], 'build': ['lint'], 'deploy': ['test', 'build']} says that test and build both need lint, and deploy needs both test and build.

The three functions and their rules.

  • run_order(jobs) takes the dictionary and returns a list of job names. It must return a deterministic topological order, using Kahn's algorithm.
  • A job is ready when every job it needs is already in the order. When several jobs are ready at the same time, take them in alphabetical order.
  • If the graph has a cycle, run_order returns an empty list.
  • If any name in a needs list is not a defined job, run_order returns an empty list.
  • has_cycle(jobs) returns True if a non-empty workflow cannot be fully ordered, and False otherwise. The statement's wording makes an empty workflow not a cycle. The statement does not say what has_cycle should return when a needs name is not defined (only run_order is told to return [] there), so this is unclear in the course itself. Ask your trainer which answer the hidden tests expect, and do not guess silently.
  • ready_jobs(jobs, completed) takes the dictionary and a list of finished job names. It returns a sorted list of the jobs whose every dependency is in completed, and which are not themselves in completed.
  • The statement gives an example. run_order on the dictionary above returns ['lint', 'build', 'test', 'deploy'], and ready_jobs with ['lint'] as completed returns ['build', 'test'].

The limits. The program may use 30 seconds of run time and 128 MB of memory. The platform checks your functions only; you do not need to read files or print anything.

The scoring. There are four visible tests worth 62 points in total. They are: topological order with the alphabetical tie-break (20 points), a valid graph has no cycle (12 points), A to B to C back to A is a cycle (14 points), and with lint done, test and build become ready (16 points). There are also 3 hidden tests worth 38 points in total.

What hidden tests are and why they decide the top marks. A hidden test is a check you cannot read. It runs your functions on inputs that the platform has chosen, and it reports only pass or fail. The visible tests use a few cases that are easy to guess. The hidden tests use the cases that careless solutions get wrong, such as an empty workflow, a missing job name, a tie between two jobs, or a graph in which the loop is not the whole graph. A solution that passes only the visible tests can reach 62 points. The 38 hidden points are what separate a correct solution from a fragile one, so you must check the edge cases yourself before you submit.

What each function needs

Each idea below is taught with a small example. The examples use fruit, numbers and words, not the lab's job names, so you can see the idea without copying a solution.

Dictionary lookups with a default. dict.get(key, default) returns the value for the key, or the default if the key is missing. Here, stock = {"apple": 3} and stock.get("pear", 0) returns 0, and stock.get("apple", 0) returns 3. Use this form when a name may not be a key, so that a missing key does not stop the program with an error.

Building a dictionary from a list. A dictionary comprehension builds one in a line. {fruit: 0 for fruit in ["fig", "plum"]} returns {'fig': 0, 'plum': 0}. This pattern gives every name a starting count, which you can then change as you go.

Sorting with a key. sorted(words, key=len) returns the words ordered by length, and sorted(words) orders them by letters. For ["banana", "fig", "kiwi"], sorted(words, key=len) returns ['fig', 'kiwi', 'banana']. The original list is not changed; sorted returns a new list.

A smallest-first queue. The module heapq keeps a list in heap order, so the smallest item comes out first. heapq.heapify(words) arranges a list of ["sun", "moon", "star"] into heap order, and heapq.heappop(words) returns 'moon', because m comes before s. heapq.heappush(words, "ash") adds a new item and keeps the order. This is how you take the alphabetically first ready job each time.

Membership in a set. A set holds each item once, and in checks membership quickly. done = {"tea", "milk"} and "tea" in done returns True. Use a set for the list of finished names, so each check is fast and a repeated name does not matter.

The all function. all(items) returns True only when every item is true. all(x > 0 for x in [2, 5]) returns True, and all(x > 0 for x in []) also returns True, because nothing is false. A job with no needs therefore passes the check that every need is done.

Comparing with is and ==. Use == to compare values and is to ask whether two names refer to the same object. [] == [] is True, but [] is [] is False, because each [] makes a new list. For the answer to None or to a boolean, use is, as in result is None.

Returning booleans. has_cycle must return True or False. A comparison such as len(order) < total already gives a boolean, so you can return it directly rather than writing if ... return True.

Checking the length of an answer. len(order) counts the items in a list. If a topological order has fewer items than the number of jobs, some jobs were never added, and that tells you a loop exists. This is the idea behind Kahn's check.

Kahn's algorithm in words. Repeat this: find every item whose needs are all already placed, pick one by your tie-break rule, place it, and look again. When nothing is ready, stop. If every item was placed, the order is complete. If some items are left, each of them waits for another item that is also left, so they form a loop or depend on one. Work out how to code this yourself, using the tools above.

Worked twin problem

This problem is a different domain: a spreadsheet, where each cell holds a formula that refers to other cells. It needs the same skills of ordering, loop detection and the ready set, but its output is a list of rounds rather than one flat order, so it is a different task.

The task. A spreadsheet is a dictionary. Each key is a cell name, and each value is the list of cells that the formula in that cell refers to. Write three functions.

  • calc_layers(cells) returns a list of lists. The first list holds every cell with no references. Each later list holds every cell whose references are all in the earlier lists. Each list is sorted alphabetically. Return [] for an empty dictionary. Return None if any reference names a cell that is not defined, or if the cells contain a loop.
  • is_circular(cells) returns True if some defined cell can never be calculated, because it is in a loop or depends on one. References to undefined cells are ignored by this function. Return False for an empty dictionary.
  • missing_refs(cells) returns a sorted list of the names that are referred to but not defined, each name once.

Examples: {"A1": [], "B1": ["A1"], "C1": ["A1", "B1"]} gives [["A1"], ["B1"], ["C1"]] from calc_layers. The dictionary {"Z": ["Q"]} gives None from calc_layers, and ["Q"] from missing_refs.

def _layers(cells):
    placed = set()
    layers = []
    remaining = set(cells)
    while True:
        ready = sorted(
            c for c in remaining
            if all(d in placed or d not in cells for d in cells[c])
        )
        if not ready:
            break
        layers.append(ready)
        placed.update(ready)
        remaining -= set(ready)
    return layers, remaining


def missing_refs(cells):
    names = set()
    for deps in cells.values():
        names.update(deps)
    return sorted(n for n in names if n not in cells)


def calc_layers(cells):
    if missing_refs(cells):
        return None
    layers, remaining = _layers(cells)
    if remaining:
        return None
    return layers


def is_circular(cells):
    _, remaining = _layers(cells)
    return len(remaining) > 0

Line by line. The code has four functions. Read _layers first, because the other two depend on it.

  • _layers(cells) builds the rounds. placed is the set of cells already in an earlier round. layers is the list of rounds. remaining starts as every cell name, and it shrinks as cells are placed.
  • while True: repeats one round at a time. The loop ends with break when no cell is ready.
  • The ready line is the core of the function. A cell is ready when every name it refers to is either placed already, or is not a defined cell at all. The second condition is what lets is_circular ignore undefined names. sorted(...) makes each round alphabetical.
  • if not ready: break stops the loop when a round finds nothing. An empty list is false in Python, so not ready is True.
  • layers.append(ready) saves the round. placed.update(ready) marks its cells as placed. remaining -= set(ready) removes them from the waiting set.
  • return layers, remaining gives back both the rounds and the cells that could not be placed. The leftover set is the key to the cycle check.
  • missing_refs collects every name that appears in any list into one set, which removes duplicates. It keeps only the names that are not keys, and returns them sorted.
  • calc_layers first checks for undefined names, and returns None if there are any. It then calls _layers, and returns None if anything was left over. Otherwise it returns the rounds. For an empty dictionary the rounds are empty, so the result is [].
  • is_circular ignores the rounds and returns True only if the leftover set is not empty. The len(remaining) > 0 form gives a boolean directly.

class _Loop(Exception):
    pass


def longest_chain(plan):
    depth = {}
    busy = set()

    def visit(task):
        if task in depth:
            return depth[task]
        if task in busy:
            raise _Loop()
        busy.add(task)
        best = 0
        for dep in plan.get(task, []):
            best = max(best, visit(dep))
        busy.discard(task)
        depth[task] = best + 1
        return depth[task]

    try:
        return max((visit(t) for t in plan), default=0)
    except _Loop:
        return -1

assert longest_chain({"X": [], "A": ["B"], "B": []}) == 2
assert longest_chain({"P": ["Q", "Q"], "Q": ["R"], "R": [], "S": []}) == 3
assert longest_chain({"A": ["B"], "B": ["A"]}) == -1
assert longest_chain({"A": ["A"]}) == -1

The function visit works out the depth of one task, and remembers it in depth. It asks the depth of each task it needs first, then adds one for itself. A busy set holds the tasks on the current path. If a task is met again while it is still busy, the path has looped back, so the code raises _Loop and the outer call returns -1. The class _Loop is a small error type made for this purpose. The max(..., default=0) line returns 0 for an empty plan, because an empty sequence has no largest value. The try and except lines catch the loop error, so that a loop gives -1 instead of a crash. Note that busy.discard(task) removes the task from the path before the depth is stored, so later paths can use it again.

Say it out loud

1. What is continuous integration, and why does it run on a fresh machine?

Model spoken answer

Continuous integration runs checks such as tests and linters automatically on every change. It runs on a fresh runner because a fresh machine has nothing installed and no leftover files from earlier work. A pass therefore means the code works from the repository alone, not only on a developer's machine. This removes the excuse that the code worked on my laptop.

2. Why do you pin versions in requirements.txt and quote the Python version?

Model spoken answer

Pinning makes a green run mean the same thing next month as it does today. Without a pin, the runner installs the newest release, which can change behaviour without any change to your code. Quoting the Python version stops YAML from reading 3.10 as the number 3.1. Both steps protect against a failure that has nothing to do with your code.

3. What does a required status check change about merging?

Model spoken answer

A required status check is a rule in the branch protection settings for main. It stops a pull request from merging until the named check reports success. The name must match the check the workflow reports, so a renamed job breaks the rule. Approvals are a separate requirement, and the course asks for both: the check and one approval.

4. A CI run failed. How do you find out why?

Model spoken answer

Open the run in the Actions tab, and find the first failing step. Read the log of that step from the first line marked as failing, not from the bottom. For a test, the summary names the test and the expected and actual values. For ShellCheck, the output names the line and the code, such as SC2086, and the code tells you the fix.

5. How do you resolve a merge conflict, and what do you check before committing?

Model spoken answer

Git marks the conflicting lines with three marker lines. You edit the file so that the correct final lines remain, and you delete all three markers. Before committing, you search for leftover markers with grep, check the syntax with bash -n, and run the script. Only then do you run git add and commit, which completes the merge.
