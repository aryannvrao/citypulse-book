The idea in one minute

Today you turn a trained model into a web service. A service is a program that sits and waits for requests, then answers them. Think of a hospital pharmacy counter: the pharmacist does not walk to every ward. Staff send a written request through the window, and the answer comes back in a standard form. Your dashboard will not import the model. It will send a request to a URL such as /v1/predict and read a JSON answer back.

By the end you will be able to choose the right status code for each outcome, write FastAPI endpoints, run them with Uvicorn, read the generated docs, and load a model once at startup so each prediction is fast.

Starting from zero

This section defines every word the day depends on. Read it before the tools.

Terminal. A text window where you type instructions to the computer instead of clicking. Each instruction is a command. The line starts with a prompt, shown in this book as $. You type after the prompt, and you do not type the $ itself.

File and folder. A file holds data or code. A folder (also called a directory) holds files and other folders. A path such as api/main.py names a file from the folder you are in. Here api is a folder and main.py is a file inside it.

Program and script. A program is a set of instructions the computer runs. A script is a program kept in a file, usually short. In this course the programs are written in Python, and their file names end in .py.

Variable. A name that holds a value, such as hours = 8. Later lines can use hours and get the 8 back.

Function. A named block of code you can run by name. def health(): creates a function called health. Its indented lines run when something calls health().

Module and import. A module is one Python file that other code can use. import os loads Python's built-in os module so your code can read settings from the computer.

Dictionary. A collection of key-value pairs written inside braces, such as {"status": "ok"}. The key "status" gives you the value "ok". Dictionaries are the Python form of JSON, which you will meet shortly.

Type hint. A note after a name that says what kind of value it should hold. In hour: int, the : int says "a whole number". Python does not enforce this by itself. FastAPI reads these hints and enforces them for web requests.

Server. A program that listens for requests on a network. Port is the numbered door it listens on. Your own computer is called localhost (or 127.0.0.1), so http://localhost:8000 means "port 8000 on this machine".

Client. Whatever sends the request. A browser, a dashboard or curl can all be clients.

HTTP request and response. HTTP is the protocol the web uses. A client sends a request with a method (such as GET to read, POST to send data, DELETE to remove) and a path. The server sends back a response with a status code (a three-digit number) and often a body.

Status code. The first thing a client reads. 200 means success, 404 means the thing does not exist, 422 means the request content is wrong, 503 means the service is temporarily unavailable, and 500 means the server crashed.

JSON. JavaScript Object Notation, a text format for structured data, such as {"pm25": 51.8}. APIs usually send and receive JSON.

Database and SQL. A database stores data in tables. SQL (Structured Query Language) is the language you use to ask it questions. SELECT 1 is the smallest possible SQL question: it asks the database to answer with the number 1. It is a cheap way to check the database is alive. PostgreSQL (often shortened to Postgres) is the database CityPulse uses.

Environment variable and .env file. A setting kept outside the code, such as the address of the database. A file named .env holds these settings. It must never be committed to Git, which is why the course says it is "gitignored", meaning Git is told to ignore it.

Container. A packaged, isolated copy of a program and its surroundings, run by a tool called Docker. The course runs the database in a container named citypulse-db.

Model and joblib. A trained model is a saved set of learned numbers and steps. joblib is a Python library that writes such objects to a file and reads them back.

The tools

REST design and status codes

REST is a style for HTTP APIs. URLs name things (resources such as stations, readings and stats), and the HTTP method says what to do with them. The status code is the first thing the client reads, so it must be honest. A 200 means the body really contains the requested data. A 4xx code means the client must change its request. A 5xx code means the server failed, and the client may try again later.

CityPulse uses REST for three reasons. The Bengaluru ward dashboard team integrates without reading our code, so the URLs and status codes are the contract. A missing station must return 404, and a dead database must return 503, so the dashboard can show "no data" and "service down" as two different messages. And versioning with /v1 lets us change responses later as /v2 without breaking the dashboard already in use.

The alternatives were GraphQL (flexible, but one endpoint hides status meaning), gRPC (fast, but browsers and curl cannot call it directly) and direct database access (couples clients to our schema and exposes credentials).

The course checks each status path with curl -i. The -i flag makes curl print the status line and headers as well as the body:

Read each line like this. BASE=http://localhost:8000 stores the address in a variable called BASE, so you do not retype it. $BASE later in the line is replaced by that address. -X DELETE sets the method to DELETE. The 405 appears because /v1/stats exists, but has no DELETE handler.

Trap: Returning 200 for a missing station

Returning 200 with an empty list when the station is unknown tells the dashboard that the station exists and has no readings. Raise HTTPException(status_code=404) instead.

Trap: Letting a database error become a 500

A 500 with a traceback tells the client nothing useful. Catch psycopg.OperationalError and return 503.

Trap: Verbs in URLs

/getStats puts the action in the URL. Use a noun, /v1/stats, and let the method carry the action.

FastAPI

FastAPI is a Python framework for building HTTP APIs. You write ordinary functions with type-hinted parameters. FastAPI turns each function into a route, checks the inputs before your code runs, converts the return value to JSON and builds documentation automatically.

CityPulse uses FastAPI for three reasons. First, type hints such as hours: int = Query(ge=1, le=168) give the 422 behaviour the ticket requires, with no hand-written checks. Second, it is Python, so it can reuse src/predict.py and the scikit-learn model from the ML phase without changing language. Third, the automatic /docs page gives the dashboard team a live contract that matches docs/api.md.

The alternatives were Flask (simple, but validation and documentation need extra libraries), Django REST Framework (heavy for a small read-only API over existing Postgres views) and Express (would split the project across two languages).

Before the code, watch one request travel through the parts. The dashboard never touches Postgres directly:

The health check is the part where the database is reached, so watch its code run line by line. The variable db is a stand-in for the database state, and the lesson does not use it in code.

Here is the health endpoint from the lesson, with indentation restored:

import os
import psycopg
from fastapi import APIRouter, FastAPI, HTTPException
from psycopg.rows import dict_row

router = APIRouter(prefix="/v1")

def q(sql: str, params: tuple = ()) -> list[dict]:
    with psycopg.connect(os.environ["DATABASE_URL"],
                         connect_timeout=3, row_factory=dict_row) as conn:
        return conn.execute(sql, params).fetchall()

@router.get("/health", summary="Liveness and database check")
def health():
    try:
        q("SELECT 1")
    except psycopg.OperationalError:
        raise HTTPException(status_code=503, detail="database unavailable")
    return {"status": "ok"}

app = FastAPI(title="CityPulse API", version="0.1.0")
app.include_router(router)

Line by line:

  • import os loads the module that reads environment variables.
  • import psycopg loads the PostgreSQL driver. A driver is the library that speaks the database's protocol.
  • from fastapi import APIRouter, FastAPI, HTTPException takes three names from FastAPI. APIRouter groups routes, FastAPI creates the app, and HTTPException is the error you raise to choose a status code.
  • from psycopg.rows import dict_row makes query results come back as dictionaries, so you can write row["status"] rather than counting positions.
  • router = APIRouter(prefix="/v1") creates a group of routes. Every route added to it starts with /v1.
  • def q(sql: str, params: tuple = ()) -> list[dict]: defines a helper called q. sql is text, params is a tuple of values (default empty), and the arrow says it returns a list of dictionaries.
  • os.environ["DATABASE_URL"] reads the database address from the environment. If the variable is missing, Python raises an error, which is what you want.
  • connect_timeout=3 gives up after three seconds if the database does not answer. Without it, a dead database can hang a request for a long time.
  • with ... as conn: opens the connection and closes it when the indented block ends.
  • conn.execute(sql, params).fetchall() runs the query and returns every row.
  • @router.get("/health", summary=...) is a decorator. The @ line attaches the function below it to the URL /v1/health for GET requests. summary is the label shown in /docs.
  • try: and except psycopg.OperationalError: run the query and catch only connection-type database errors.
  • raise HTTPException(status_code=503, detail="database unavailable") stops the function and makes FastAPI send a 503 with that message.
  • return {"status": "ok"} is the normal answer. FastAPI turns this dictionary into JSON.
  • app = FastAPI(title=..., version=...) creates the application. The title and version appear in the docs.
  • app.include_router(router) adds the /v1 routes to the application.

When you run curl -i /v1/health with the database up, you should see 200 and {"status":"ok"}. With the database stopped, you should see 503.

Trap: Building SQL with f-strings

Writing f"SELECT * FROM stations WHERE id = '{station_id}'" lets a user type SQL into your query. Always pass values as %s placeholders and a tuple, such as q("... WHERE id = %s", (station_id,)).

Trap: Hard-coding the database URL

Writing the postgresql:// address into api/main.py puts a secret into Git. Read DATABASE_URL from the environment and keep .env gitignored.

Trap: async def with blocking code

psycopg waits for the database, and that waiting blocks everything else if your handler is async def. Use a plain def. FastAPI runs plain def handlers in a thread pool, so they do not block other requests.

Uvicorn and OpenAPI docs

Uvicorn is an ASGI server. It is the program that listens on a port, accepts connections and hands each request to your FastAPI app. ASGI (Asynchronous Server Gateway Interface) is the standard that lets servers and Python web apps talk to each other. FastAPI also publishes an OpenAPI description of every route at /openapi.json, and renders it as interactive pages at /docs and /redoc. OpenAPI is a standard format for describing web APIs.

CityPulse uses Uvicorn for three reasons. uvicorn api.main:app --reload gives a fast edit-and-retry loop. The same command becomes the container's start command later, so the local and deployed runs match. And the /docs page is the evidence screenshot for the T38 pull request, and lets peers call the API from their own laptops.

The alternatives were Gunicorn with Uvicorn workers (several processes for production, unnecessary on one laptop), Hypercorn (HTTP/2, not needed here) and hand-written docs (drift from the code silently).

The lesson's run commands, with their meaning:

set -a; source .env; set +a
uvicorn api.main:app --reload --port 8000 &
sleep 2
curl -s localhost:8000/openapi.json | jq '.paths | keys'

Line by line:

  • set -a tells the shell to export every variable it sets from now on, which means child programs can see them.
  • source .env runs the lines of .env in the current shell, so DATABASE_URL gets set.
  • set +a turns the automatic export off again.
  • uvicorn api.main:app means: load the file api/main.py as a module called api.main, and use the object called app inside it.
  • --reload restarts the server when a source file changes. Use it only on your laptop.
  • --port 8000 chooses the port. This is the default, so the flag is only for clarity.
  • The final & runs the server in the background, so the terminal is free again.
  • sleep 2 waits two seconds so the server has started before the next command.
  • curl -s fetches silently, without the progress meter. jq then reads the JSON. The filter .paths | keys means "take the paths field, then list its keys". You should see a list of your route paths such as "/v1/health".

To share the API with a peer on the same Wi-Fi, start it with uvicorn api.main:app --host 0.0.0.0 --port 8000. The default host is 127.0.0.1, which only your own machine can reach. 0.0.0.0 means "accept connections on every network address this machine has".

Trap: Running uvicorn from inside api/

Inside api/, the import api.main fails. Run the command from the repository root, the folder that contains api/.

Trap: --reload in production

--reload watches files and wastes CPU. Containers and production runs leave it out.

Trap: Peers cannot reach 127.0.0.1

A friend's laptop cannot use your 127.0.0.1, because that address means "this machine" for each computer. Bind with --host 0.0.0.0 when another laptop must call your API.

Tip: Show the contract, not just the code

In the viva, open /docs and point at the parameter types and the summary text. The examiner can see the contract without reading your code.

Model serving with joblib

Serving a model means keeping it loaded in the running service and calling it for each request. The fitted pipeline is saved to a file, models/model_v1.joblib, during training. The service loads that file once when it starts. Each request then builds a small table with one row and calls the loaded pipeline. The response includes the model version from models/metrics_v1.json, so every answer can be traced to one saved model.

CityPulse serves the model this way for three reasons. Ticket Y2-T39 requires the second /v1/predict call to take under 50 ms, which is only possible if the model is not reloaded per request. Returning model_version in every response lets us trace each forecast to one artefact and notice drift later. And the lifespan handler fails fast at startup if the model file is missing, instead of returning 500 errors to the dashboard.

The alternatives were pickle (same idea, but joblib is more efficient for large NumPy arrays and is the scikit-learn convention), MLflow serving (useful at scale in Year III, heavy for one model) and ONNX Runtime (adds conversion risk with no latency need at our traffic).

Here is the lesson's model-serving code, with the lines rejoined:

import json, time, joblib
from contextlib import asynccontextmanager
from fastapi import FastAPI
from api.schemas import PredictRequest
from src.predict import predict

@asynccontextmanager
async def lifespan(app: FastAPI):  # raises at startup if either file is missing
    app.state.model, app.state.metrics = (
        joblib.load("models/model_v1.joblib"),
        json.load(open("models/metrics_v1.json")),
    )
    yield

app = FastAPI(title="CityPulse API", lifespan=lifespan)

@app.post("/v1/predict")
def predict_v1(body: PredictRequest):
    t0 = time.perf_counter()
    y = predict(app.state.model, body.model_dump())
    return {
        "prediction": y,
        "model_version": app.state.metrics["version"],
        "latency_ms": round((time.perf_counter() - t0) * 1000, 1),
    }

Line by line:

  • import json, time, joblib loads three modules: json reads the metrics file, time measures elapsed time, and joblib loads the model.
  • from contextlib import asynccontextmanager provides a decorator for writing startup and shutdown code.
  • from api.schemas import PredictRequest takes the request class you define in lab step 1.
  • from src.predict import predict takes the function from the ML phase. The lesson does not print its body, so treat it as a black box that takes a model and a dictionary of features.
  • @asynccontextmanager turns the function below into something FastAPI can use as a lifespan.
  • async def lifespan(app: FastAPI): is the startup and shutdown function. The function is passed to FastAPI through the lifespan= argument.
  • # raises at startup... is a comment. Python ignores it, and it tells the reader the design intent.
  • app.state.model, app.state.metrics = (...) stores two values on app.state, a container that lives as long as the app. The parentheses make the two-value assignment easy to read across lines.
  • json.load(open(...)) reads the metrics file. The lesson leaves the file open. A tidier version uses with open(...) as f:, which closes it straight away.
  • yield marks the point where startup ends and the server starts accepting requests. Anything after yield runs at shutdown.
  • app = FastAPI(..., lifespan=lifespan) tells the app to run lifespan at start.
  • @app.post("/v1/predict") attaches the function to POST requests on that path. POST is used because the features travel in the request body, not the URL.
  • def predict_v1(body: PredictRequest): says the body must match PredictRequest. FastAPI parses and checks it before this function runs.
  • t0 = time.perf_counter() records a high-precision start time.
  • y = predict(app.state.model, body.model_dump()) calls the loaded model. model_dump() turns the validated request object into a plain dictionary.
  • The return builds the response. latency_ms is the time taken, rounded to one decimal place.

Start the service and call it. Expect a number in JSON, such as {"pm25":51.8} in the workbook run. The first run of the TIA workbook shows 52.4 on one page and 51.8 on a later page. The exact value depends on the model you trained, so do not worry about the difference.

Trap: Calling joblib.load in the route

Loading inside the route reads the file on every request, and latency explodes. Load once in lifespan and read from app.state.

Trap: A different scikit-learn version

Serving with a different scikit-learn version from training can load a model that gives different answers, or fails. Pin the version in requirements.txt to the one recorded in metrics_v1.json.

Trap: NumPy values in JSON

A NumPy float may not convert to JSON directly. Wrap the value in float(), as the lesson's TIA code does with round(float(model.predict(X)[0]), 1).

The worked example

Goal. Serve a saved CityPulse PM2.5 model over HTTP, with a health check and a prediction endpoint, and show that it runs.

Code. The workbook builds this file across seven pages. The final main.py is shown below. It is the workbook's version, which uses GET and query parameters. The course slides later move prediction to POST with a JSON body. Both teach the same ideas.

from fastapi import FastAPI
import joblib, pandas as pd

app = FastAPI(title="CityPulse PM2.5 API")

model = joblib.load("model.pkl")  # loaded once

@app.get("/health")
def health():
    return {"status": "ok"}

@app.get("/predict")
def predict(hour: int, temp: float, humidity: float):
    X = pd.DataFrame([{"hour": hour, "temp": temp, "humidity": humidity}])
    pm25 = round(float(model.predict(X)[0]), 1)
    return {"pm25": pm25}

Explanation. FastAPI(...) creates the app. joblib.load("model.pkl") runs once when Python imports this file, so the model stays in memory. @app.get("/health") returns a fixed answer, which proves the server is alive. predict declares three typed query parameters. FastAPI turns the URL values into int and float, and rejects bad values. The function puts the three values into a one-row table with pd.DataFrame, because scikit-learn expects a table. model.predict(X)[0] takes the first prediction. float(...) converts it to a plain number, and round(..., 1) keeps one decimal place. The dictionary returned becomes JSON.

Run and output.

Read the first line as: run the app object called app inside main.py, and watch for changes. The Application startup complete. line means joblib.load succeeded. The curl line sends three values in the URL after the ?. Each pair is name=value, and pairs are joined with &.

Validation. Send a bad value to see FastAPI reject it:

-o /dev/null throws away the body, and -w "%{http_code}\n" prints only the status code. The second command pipes the body into jq, and .detail[].msg prints each message. The output names both problems: hour is not an integer, and humidity is missing. Your function never ran.

The hands-on lab, step by step

The lab builds the service in CityPulse's api/ folder. Work from the repository root. Each step lists what you do, what you type, what you should see and how you know it worked.

Step 1: Define the request schema

What you do. Create api/schemas.py with a class that describes the JSON body /v1/predict accepts. The lesson imports the class as PredictRequest. The workbook's features are hour, temp and humidity. If your training code used other column names, use those.

from pydantic import BaseModel

class PredictRequest(BaseModel):
    hour: int
    temp: float
    humidity: float

Line by line: from pydantic import BaseModel loads the validation library FastAPI uses. class PredictRequest(BaseModel): defines a class, which is a blueprint for a kind of object, and says it inherits validation from BaseModel. Each indented line declares one field and its type.

What you should see. Running python -c "from api.schemas import PredictRequest; print(PredictRequest(hour=8, temp=19, humidity=60))" prints the object with the three values. No error means the file is correct.

Step 2: Define the response schema

What you do. In the same file, add a class for the answer. The lesson returns these three keys, and the schema must match them.

class PredictResponse(BaseModel):
    prediction: float
    model_version: str
    latency_ms: float

What you should see. The same import check works with PredictResponse. Later, /docs shows this shape under the response for /v1/predict, once you add response_model (see the section on response models below).

Step 3: Load the model at startup

What you do. Add the lifespan function and the app = FastAPI(..., lifespan=lifespan) line from the joblib section to api/main.py. Make sure models/model_v1.joblib and models/metrics_v1.json exist, relative to the repository root.

What you should see. Starting uvicorn api.main:app prints Application startup complete. with no traceback.

How you know it works. Rename models/model_v1.joblib, restart the server, and watch it fail during startup with a file-not-found error. A failure at startup is the goal: it is better than the dashboard receiving 500 errors. Rename the file back afterwards.

Step 4: Add a health endpoint

What you do. Add the q helper and the /v1/health route from the FastAPI section, with a router created by APIRouter(prefix="/v1"). Set DATABASE_URL in .env, and load it with set -a; source .env; set +a.

What you should see. curl -i localhost:8000/v1/health prints HTTP/1.1 200 OK and {"status":"ok"}.

How you know it works. Run docker stop citypulse-db, call the health endpoint again, and expect HTTP/1.1 503 Service Unavailable. Then run docker start citypulse-db. A 503 with the database stopped, and a 200 once it is running, proves the check is real.

Step 5: Add the prediction endpoint

What you do. Add the @app.post("/v1/predict") function from the joblib section. It takes body: PredictRequest and returns the three response keys. Keep predict imported from src/predict.py.

What you should see. /docs now lists POST /v1/predict, with the request body fields hour, temp and humidity.

How you know it works. Send a valid body and get a JSON answer with prediction, model_version and latency_ms. Send hour as a string such as "morning" and get a 422 that names the field.

Step 6: Run and explore the docs

What you do. Start the server with uvicorn api.main:app --reload --port 8000. Open http://localhost:8000/docs in a browser.

What you should see. A page titled CityPulse API, with one section per route. Each route has a "Try it out" button that sends a real request.

How you know it works. Press "Try it out" on /v1/health and check that the response code is 200. The page is generated from the code, so if a route is missing here, it is missing from the app.

Step 7: Call it from the terminal

What you do. Send a POST request with a JSON body:

curl -i -X POST http://localhost:8000/v1/predict \
  -H "Content-Type: application/json" \
  -d '{"hour": 8, "temp": 19, "humidity": 60}'

Line by line: curl -i prints the status line and headers. -X POST sets the method. -H "Content-Type: application/json" tells the server the body is JSON. -d '...' supplies the body, and the single quotes stop the shell from touching the braces. The backslash at the end of the first line joins the two lines into one command.

What you should see. HTTP/1.1 200 OK, then a JSON body with prediction, model_version and latency_ms. Send the request twice and compare the latency_ms values, as the course asks.

How you know it works. Remove -d and send the request again. The status is 422, because the body is missing. That is the same validation you saw with the query parameters.

Routes and routers

What it is. A route is a function linked to one HTTP method and one path. When a request arrives with that method and path, FastAPI calls the function. You create a route with a decorator, which is the line beginning with @ above a function. For example, @app.get("/health") links the function below it to GET /health.

A router is a group of routes. In CityPulse the group is created with router = APIRouter(prefix="/v1"). Every path in the group starts with /v1, so a route written as @router.get("/health") answers at /v1/health. FastAPI adds the prefix for you, so you do not type it twice.

A router takes effect only when the app includes it with app.include_router(router). If you create a router and forget to include it, none of its routes exist in the running app, and every path in the group returns 404 Not Found.

router = APIRouter(prefix="/v1")

@router.get("/stations")
def list_stations():
    return {"stations": []}

app.include_router(router)

A request to GET /v1/stations returns 200 with {"stations": []}. A request to GET /stations returns 404, because the route is registered only under /v1.

How it shows up in a case study. The ward dashboard team reports that the station list page is empty, and their browser shows 404 for /stations. A developer opens api/main.py and sees a router with the prefix /v1. The route itself was written in a new file, api/stations.py, but nobody added app.include_router(...) to main.py. The reasoning has two steps. The prefix explains why the decorator says /stations but the real URL is /v1/stations. The missing include explains why even that URL does not answer. The fix is to include the router in the app, then check GET /v1/stations with curl -i and expect 200.

Trap: Reading only the decorator

@router.get("/stations") looks as if the URL is /stations. The prefix from APIRouter(prefix="/v1") is added to it, so the full path is /v1/stations.

Values inside the path

What it is. A path parameter is a value written inside the URL path, between braces. In the path /v1/wards/{ward_id}/readings, the part in braces is a placeholder. A client that calls /v1/wards/42/readings sends the text 42 in that position. FastAPI passes the value to the function argument with the same name.

The type hint on that argument tells FastAPI how to read the text. With ward_id: int, FastAPI converts "42" to the number 42. If the text cannot be converted, such as north, FastAPI returns 422 Unprocessable Entity before your code runs.

@router.get("/wards/{ward_id}/readings")
def ward_readings(ward_id: int):
    return {"ward": ward_id}

A call to /v1/wards/42/readings returns {"ward": 42}. A call to /v1/wards/north/readings returns 422, and the function never runs.

How it shows up in a case study. A ward team has a route that takes the ward number from the path. An analyst reports that one URL returns 422 and another returns 200 with an empty list. The team asks which of the two is the correct design. The reasoning separates two kinds of problem. A value such as north cannot be read as an integer, so FastAPI rejects it, and that is a request-content error. A valid integer that no ward has is a different case: the value is acceptable, but the record is missing, so the function must return 404. The route must check the database and raise an error when no row comes back.

Trap: Treating a missing record as a valid empty answer

A valid integer such as 999 that matches no ward is a missing resource. Returning 200 with an empty list tells the dashboard that the ward exists and has no readings. Raise HTTPException(status_code=404) instead.

Reading a JSON request body

What it is. A request body is data sent along with a request, usually in JSON. Clients send bodies with POST, PUT or PATCH. JSON is text in the form {"hour": 8, "temp": 19.0}. You declare a body in a route by giving a parameter a Pydantic model type, such as body: PredictRequest.

FastAPI reads the JSON, checks it against the model, and passes a typed object into your function. If a required field is missing or has the wrong type, FastAPI returns 422 and names the field in the detail list. The function does not run in that case.

@app.post("/v1/predict")
def predict_v1(body: PredictRequest):
    return {"hour": body.hour}

The body parameter is the only input that comes from the request content. Path and query values come from the URL, so they are not part of the body.

How it shows up in a case study. A dashboard developer sends a JSON body with hour and temp but leaves out humidity. They expect a 400 Bad Request and wonder why the response is 422. The team's question is which status the client should see and where the message is. The reasoning is that FastAPI uses 422 for body validation, and it names the missing field under detail. The developer should read the field name from the response and fix the client, not change the server to return 400.

Trap: Expecting 400 from FastAPI for a bad body

Many APIs use 400 for bad input, but FastAPI uses 422 for body validation. The detail list tells the client which field failed.

Query parameters and range limits

What it is. A query parameter is a name=value pair after the ? in a URL. Pairs are joined by &. In /v1/stations/BLR_SILKBOARD/readings?hours=24&limit=10, the names are hours and limit. A function argument that is not part of the path becomes a query parameter automatically.

You add rules with Query. In hours: int = Query(ge=1, le=168), ge means greater than or equal to, and le means less than or equal to. A value outside that range returns 422. FastAPI rejects the request. It does not change the value to fit the range.

A default value makes a query parameter optional. With station: str | None = None, a request without station gives the function None, and the request still succeeds.

@router.get("/readings")
def readings(hours: int = Query(ge=1, le=168)):
    return {"hours": hours}

A call to /v1/readings?hours=24 returns {"hours": 24}. A call to /v1/readings?hours=500 returns 422.

How it shows up in a case study. The Bengaluru ward team wants the readings endpoint to accept up to a week of history, which is 168 hours. A support engineer reports that a user asked for 500 hours and got a response with data for 168 hours. The team wonders whether the server caps large values, or whether it should. The ticket asks for an honest answer, so the reasoning is that capping hides the mistake from the client. A request for 500 hours should fail with 422, and the dashboard should show a clear message. The engineer should check the response code with curl -i, not look at the data alone.

Trap: Expecting FastAPI to cap the value

Query(le=168) does not reduce 500 to 168. It rejects the request with 422, and the function never sees the value.

Validating data with Pydantic

What it is. Pydantic is a library that checks and converts data against a class definition. A class that inherits from BaseModel lists each field with a type. When Pydantic builds an object from input, it converts values when it safely can, and it raises an error when it cannot. A numeric string such as "8" becomes the number 8 for an int field. The text "morning" raises an error.

from pydantic import BaseModel, Field

class Reading(BaseModel):
    hour: int
    humidity: float = Field(ge=0, le=100)

r = Reading(hour="8", humidity=60)
print(r.hour, r.humidity)

This prints 8 60.0. The string "8" became the integer 8, and the value 60 became the float 60.0. If you change humidity to 120, Pydantic raises a ValidationError, because 120 is above the limit of 100.

FastAPI uses Pydantic for request bodies and response models. The check runs before your function is called, so the function receives only valid, typed data.

How it shows up in a case study. A developer wants to keep a PredictRequest model with three fields, but they also write if not 0 <= body.humidity <= 100 inside the route. A reviewer points out that the range can be declared on the model with Field. The reasoning is that the model is the request contract. If the range sits on the model, FastAPI returns 422 with a message that names the field, and the route never runs. The hand-written check would run only after the function had started, and it would return whatever message the developer chose. The team should move the rule into the model and delete the duplicate check.

Trap: Thinking validation only checks types

Pydantic also checks ranges, such as Field(ge=0, le=100). A value of 120 is rejected even though it is a valid number.

Sending honest error codes

What it is. An HTTP status code is the first thing a client reads. You choose it in your code by raising HTTPException(status_code=..., detail=...). Raising the exception stops the function, and FastAPI sends the status code with a JSON body. The detail text appears under the key detail.

If an error is not caught and not raised as an HTTPException, FastAPI sends 500 Internal Server Error. A 500 response tells the client that the server failed, with no useful message and no hint about whether to retry.

For database problems, CityPulse catches the specific error psycopg.OperationalError. This error means the connection to Postgres failed. The code then raises an HTTPException with 503, which tells the client that the service is temporarily unavailable.

try:
    q("SELECT 1")
except psycopg.OperationalError:
    raise HTTPException(status_code=503, detail="database unavailable")

The except line catches only that error type. Other unexpected errors still surface, so the team can see them in the logs.

How it shows up in a case study. When Postgres is stopped on the staging server, the dashboard shows a generic failure message, and the API log shows a long traceback. The team wants the dashboard to show "service down" instead. The reasoning is that the failure is a connection problem, which the client cannot fix, so the right status is 503. The route should catch the connection error, not every exception. Catching everything would hide bugs in the code, and a bug should still appear as a 500 in the logs.

Trap: Catching every exception

Catching Exception and returning 503 hides real bugs as "service down". Catch the specific database error, and let other errors reach the logs.

Loading things once at startup

What it is. The lifespan function is a startup and shutdown hook. You write it with @asynccontextmanager, and you give it to the app with FastAPI(lifespan=lifespan). Code before the yield line runs when the server starts, before it accepts requests. Code after yield runs when the server is stopping.

Shared objects, such as a loaded model, are stored on app.state. This is a container that lives as long as the app does. A route reads the object from there, instead of reading the file again.

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.model = joblib.load("models/model_v1.joblib")
    yield

app = FastAPI(lifespan=lifespan)

If models/model_v1.joblib is missing, joblib.load raises an error during startup. Uvicorn then stops, and no request is ever answered with a 500 error about the missing file.

How it shows up in a case study. The team's /v1/predict route loads the model file on every request. A load test shows the second call takes about 400 milliseconds, and the ticket requires less than 50 milliseconds. A teammate suggests making the route async def. The reasoning is that the speed problem comes from reading the file again on each request, not from how the function is declared. Loading the model once in the lifespan handler, and reading it from app.state inside the route, removes that cost. The file also gets checked at startup, so a missing model shows up when the team starts the server.

Trap: Loading the model inside the route

Reading the model file in every route call repeats the expensive work for each request. Load it once in lifespan and store it on app.state.

Shaping the response with response_model

What it is. A response model is a Pydantic class that you name in the decorator with response_model=. FastAPI takes the value your function returns, checks it against that class, and sends only the fields the class declares. Any extra key in the returned dictionary is removed. The response model also appears in /docs, so the client can see the shape of the answer.

class PredictResponse(BaseModel):
    prediction: float
    model_version: str

@app.post("/v1/predict", response_model=PredictResponse)
def predict_v1(body: PredictRequest):
    return {"prediction": 51.8, "model_version": "v1", "debug": "internal"}

The client receives {"prediction": 51.8, "model_version": "v1"}. The debug key is removed, because PredictResponse does not declare it.

If a value cannot be converted to the declared type, FastAPI reports a server error, because the function returned data that does not match the contract. A whole number such as 52 in a float field is converted to 52.0.

How it shows up in a case study. The dashboard team asks why /docs shows no response shape for /v1/predict. The developer adds a debug dictionary to the return value, and the team then notices that internal query text reaches the client. The reasoning has two parts. Adding response_model=PredictResponse documents the contract and also removes undeclared fields, so internal data stays on the server. The team should change the decorator and keep the debug information in the log.

Trap: Trusting that extra keys reach the client

A handler can return a dictionary with extra keys, but a response model sends only its declared fields. The extra key does not reach the client.

Dependencies with Depends

What it is. A dependency is a function that FastAPI calls before the route body runs. A route receives the result by declaring a parameter with a default of Depends(function_name). FastAPI calls the function for each request that uses it, and passes the returned value into the route.

def get_settings():
    return {"db_url": os.environ["DATABASE_URL"]}

@router.get("/health")
def health(settings = Depends(get_settings)):
    return {"status": "ok", "has_db": "db_url" in settings}

Each request to /v1/health calls get_settings() once. The result is passed into health as settings. Within a single request, FastAPI caches a dependency by default, so two parameters that use the same dependency share one call.

Dependencies keep setup code out of each route. They are also a common way to check a shared requirement, such as a login token, before the route runs.

How it shows up in a case study. A team has five routes, and each one opens a database connection at the top of the function. A reviewer suggests moving that step into a dependency. The reasoning is that the dependency gives one definition of the setup, and each route declares what it needs. Because FastAPI calls the dependency per request, each request still gets its own connection, and the route body stays short. The team should not assume the dependency runs once at startup. A startup value belongs in lifespan, which is a different tool.

Trap: Thinking a dependency runs once for the whole app

Depends runs the dependency for each request that uses it. It does not run once at startup. Startup work belongs in lifespan.

Work after the response

What it is. A background task is a function that runs after the response has been sent to the client. A route declares a parameter of type BackgroundTasks and calls background.add_task(function, argument). The route returns its answer straight away, and the task runs afterwards.

from fastapi import BackgroundTasks

@router.post("/predict")
def predict_v1(body: PredictRequest, background: BackgroundTasks):
    background.add_task(write_log_line, body.model_dump())
    return {"prediction": 51.8}

The client gets {"prediction": 51.8} without waiting for write_log_line. The task runs after the response has gone out. If the task fails, the response is already sent, so the client's answer does not change.

Use background tasks for short work that the client does not need to see, such as writing a log line or sending a notification. Do not use them for work that the response must contain.

How it shows up in a case study. CityPulse wants each prediction to be logged, and the dashboard must receive the prediction quickly. A developer puts the logging call inside the route, before the return line, and the dashboard reports slow responses on busy days. The reasoning is that a log write does not need to finish before the answer goes back. A background task moves that work after the response. The prediction calculation must still happen before the return, because the answer depends on it.

Trap: Expecting the task to finish before the response

The call to add_task sits above the return line in the code, but the task still runs after the response is sent. Its position in the file does not control when it runs.

The graded lab

The task in plain words

The scenario. The CityPulse /predict endpoint must reject bad payloads cleanly. The validation and the response logic live in two pure functions. A pure function takes its inputs, returns a result, and changes nothing else. That makes it possible to test the logic without starting a server.

The starter file contains these two functions, and you fill in their bodies:

  • validate_request(payload) takes one argument, payload, which is a dictionary. It returns the text "OK" when the payload is valid. Otherwise it returns one failure code, as described below.
  • handle_predict(payload) takes the same kind of dictionary. It returns a new dictionary that describes the response.

The rules for validate_request. A payload is valid when all three of these hold:

  • It has a station_id that is a non-empty string.
  • It has a pollutant that is exactly one of PM25, PM10, NO2 or O3. Spelling and capitals must match.
  • It has a value that is numeric and not negative.

When a payload is invalid, return the first failing code, checking in this order:

  1. MISSING_FIELD. A required field is absent, or station_id is empty or is not a string.
  2. BAD_POLLUTANT. The pollutant is not one of the four allowed names.
  3. BAD_VALUE. The value is not numeric, or it is negative.

The order matters. A payload with a bad pollutant and a negative value must return BAD_POLLUTANT, because that check comes first.

The rules for handle_predict.

  • If the payload is invalid, return a dictionary with two keys: status set to 400, and error set to the code that validate_request returned.
  • If the payload is valid, return a dictionary with three keys: status set to 200, pollutant set to the pollutant name, and prediction set to round(value * 1.05 + offset, 2).
  • The offset depends on the pollutant: PM25 adds 2.0, PM10 adds 1.5, NO2 adds 1.0, and O3 adds 0.5.
  • The statement's example is handle_predict({"station_id": "A", "pollutant": "PM25", "value": 40.0}), which returns a status of 200, the pollutant PM25, and a prediction of 44.0.

Limits. Your file must finish within 30 seconds and 128 MB of memory. The tests are small, so this is unlikely to be a problem unless you do something unusual, such as an endless loop.

What each function needs

The ideas below are taught with examples about fruit, shop prices and temperatures. The examples are not parts of the lab, and you should not copy them into your functions. Use them to learn the idea, then apply it to the lab's own names.

Checking whether a key is present. "name" in d returns True only when the key exists. d.get("name") returns the value, or None when the key is missing. The two are different when the stored value is None.

stock = {"apple": 3, "plum": None}
print("apple" in stock)        # True
print("pear" in stock)         # False
print(stock.get("pear"))       # None
print("plum" in stock)         # True, even though the value is None

A missing key and a key holding None need different handling when the rules say a field is required.

Telling types apart with isinstance. isinstance(x, int) checks the type. A tuple of types checks for either type. A bool is a subclass of int, so a number check must treat booleans separately.

print(isinstance(7, int))              # True
print(isinstance(2.5, (int, float)))   # True
print(isinstance("7", (int, float)))   # False, a string is not a number
print(isinstance(True, int))           # True, because bool is a subclass of int
print(isinstance(True, bool))          # True

To reject booleans and keep numbers, test for bool first. The check isinstance(x, bool) or not isinstance(x, (int, float)) is True for any value that should be rejected.

Order of checks with and and or. Python evaluates and and or from left to right and stops as soon as the answer is known. This lets a later test assume that an earlier test passed.

items = []
print(len(items) > 0 and items[0] == "tea")   # False, and items[0] is never read

Put the test that protects an operation before the operation. This is why an earlier check can make a later check safe.

Membership in a fixed set. x in {"red", "green"} checks whether x is one of the members. Comparison is exact, so "Red" is not in that set.

colours = {"red", "green", "blue"}
print("red" in colours)    # True
print("Red" in colours)    # False

If a rule says the spelling must match exactly, do not change the text with upper() or lower() before the check.

Boundaries. >= includes the boundary value and > does not. A rule such as "zero is allowed" needs >=, and a rule such as "must be above zero" needs >.

print(0 >= 0)      # True
print(0 > 0)       # False
print(-0.5 < 0)    # True

Looking up a value in a dictionary. prices["tea"] returns the value, but it raises KeyError when the key is missing. Check membership first, or use .get with a default, when the key may be absent.

prices = {"tea": 1.5, "coffee": 2.0}
print(prices["tea"])          # 1.5
print(prices.get("juice", 0)) # 0, because the default is used

Rounding at the end. round(x, 2) rounds a number to two decimal places. Round once, after the whole calculation, so that the rounding does not change the result.

print(round(10 / 3, 2))       # 3.33
print(round(7.0 * 1.1, 2))    # 7.7, because 7.0 * 1.1 is 7.700000000000001

Building a result dictionary. A dictionary literal lists its keys and values in braces. The returned dictionary must have exactly the keys the statement names, no more and no fewer.

def make_report(city, count):
    return {"city": city, "count": count}

print(make_report("Pune", 4))   # {'city': 'Pune', 'count': 4}

Worked twin problem

The twin problem below is in a different domain, a bike-share app, and uses different data. It needs the same skills: checking required fields, checking allowed values, checking numbers, checking the order of tests, and returning a result in a fixed shape.

Task. A bike-share app receives a list of trip records. Each trip is a dictionary with three keys: rider, minutes and zone.

  • check_trip(trip) returns one code. It returns "OK" when the trip is valid, or the first failing code, checked in this order: 1. MISSING_FIELD. One of the three keys is absent, or rider is an empty string or not a string. 2. BAD_MINUTES. minutes is not a number, is a boolean, is negative, or is more than 240. Zero and 240 are allowed. 3. BAD_ZONE. zone is not one of "North", "South" or "East". The spelling must match exactly.
  • summarise_trips(trips) takes a list of trip dictionaries and returns a dictionary with four keys:
  • valid, the number of valid trips.
  • rejected, the number of trips that failed check_trip.
  • average_minutes, the mean minutes of the valid trips, rounded to one decimal place. It is 0.0 when there are no valid trips.
  • zones, a list of (zone, count) pairs for the valid trips, sorted by count from largest to smallest. Zones with the same count are sorted alphabetically.
  • summarise_trips must not change the list or the dictionaries in it.

Solution. Read the code first, and try to predict each assert before you run it.

ZONES = ("North", "South", "East")

def check_trip(trip):
    if "rider" not in trip or "minutes" not in trip or "zone" not in trip:
        return "MISSING_FIELD"
    rider = trip["rider"]
    if not isinstance(rider, str) or rider == "":
        return "MISSING_FIELD"
    minutes = trip["minutes"]
    if isinstance(minutes, bool) or not isinstance(minutes, (int, float)):
        return "BAD_MINUTES"
    if minutes < 0 or minutes > 240:
        return "BAD_MINUTES"
    if trip["zone"] not in ZONES:
        return "BAD_ZONE"
    return "OK"

def summarise_trips(trips):
    valid = []
    rejected = 0
    for trip in trips:
        if check_trip(trip) == "OK":
            valid.append(trip)
        else:
            rejected += 1
    if valid:
        average = round(sum(t["minutes"] for t in valid) / len(valid), 1)
    else:
        average = 0.0
    counts = {}
    for t in valid:
        counts[t["zone"]] = counts.get(t["zone"], 0) + 1
    zones = sorted(counts.items(), key=lambda kv: (-kv[1], kv[0]))
    return {"valid": len(valid), "rejected": rejected,
            "average_minutes": average, "zones": zones}

Line by line: check_trip.

  • ZONES = ("North", "South", "East") stores the allowed zones in a tuple. A tuple is a fixed list, and in checks it by exact comparison.
  • if "rider" not in trip or ... checks that all three keys exist. The or means one missing key is enough to stop.
  • rider = trip["rider"] reads the value once, so the next lines can use a short name.
  • if not isinstance(rider, str) or rider == "": rejects a value that is not text, and rejects the empty text. The or means either test is enough to fail.
  • minutes = trip["minutes"] reads the value once. It runs after the rider check, because the statement puts MISSING_FIELD first.
  • isinstance(minutes, bool) or not isinstance(minutes, (int, float)) rejects booleans first, then anything that is not a number. The bool test comes first because True would otherwise pass as an int.
  • if minutes < 0 or minutes > 240: rejects negative values and values above 240. Zero and 240 pass, because both ends are inclusive. The isinstance test above makes this comparison safe, because a string would raise TypeError here.
  • if trip["zone"] not in ZONES: checks the zone spelling last, because the statement puts BAD_ZONE after BAD_MINUTES.
  • return "OK" is reached only when every earlier check passed.

Line by line: summarise_trips.

  • valid = [] and rejected = 0 start the two collections.
  • The loop calls check_trip once for each trip. A valid trip is added to valid, and any other result increases rejected.
  • if valid: protects the division. Dividing by len(valid) when the list is empty would raise ZeroDivisionError.
  • round(..., 1) rounds once, after the whole sum is divided. This is the rounding rule the lab also uses.
  • counts.get(t["zone"], 0) + 1 counts the trips per zone. The get default of 0 handles a zone seen for the first time.
  • sorted(counts.items(), key=lambda kv: (-kv[1], kv[0])) sorts the pairs. The key is a tuple. The first part, -kv[1], sorts by count from largest to smallest, because the minus sign reverses the order. The second part, kv[0], breaks ties alphabetically.
  • The dictionary returned has exactly the four keys the task names.
  • The function reads each trip and never assigns to it, so the input list and its dictionaries stay the same. The before check proves this.

    if isinstance(servings, bool) or not isinstance(servings, int) or servings < 1:

    name = recipe.get("name")

    items = recipe.get("ingredients")
    if not isinstance(name, str) or name == "":
        return {"ok": False, "error": "BAD_RECIPE"}
    if isinstance(serves, bool) or not isinstance(serves, int) or serves < 1:
        return {"ok": False, "error": "BAD_RECIPE"}
    if not isinstance(items, dict):
        return {"ok": False, "error": "BAD_RECIPE"}

Say it out loud

Q1. Why does an unknown station return 404 and not 200 with an empty list?

Model spoken answer

A 404 tells the caller that the resource does not exist, which is a different fact from having no readings. An empty list with 200 says the station exists and has no data, so the dashboard would show a misleading "no readings" message. The status code is the first thing a client reads, so it has to be accurate. We raise HTTPException with status 404, and the dashboard can then separate "no such station" from "service down".

Q2. Why is the model loaded in the lifespan handler and not inside the route?

Model spoken answer

Loading the model reads a file from disk, which takes time. If the route loaded it, every request would pay that cost, and the 50 ms target in the ticket would be impossible. The lifespan handler runs once before the server accepts traffic, and stores the model on app.state, which the route reads. If the file is missing, the server fails at startup, which is better than returning 500 errors to users.

Q3. What does the /v1 prefix protect, and when do you create /v2?

Model spoken answer

The /v1 prefix lets us change responses later without breaking clients that already use /v1. A breaking change is one that removes or renames a field, changes a type, or changes the meaning of a status code. We document what counts as breaking in docs/api.md. Adding an optional field is usually safe and does not need a new version. A breaking change creates /v2, while /v1 stays available for the dashboard already in use.

Q4. Why use a plain def for a handler that calls psycopg, and not async def?

Model spoken answer

psycopg waits for the database to reply, and that wait is blocking work. In an async def handler, a blocking call stops the event loop, so other requests wait too. A plain def handler is run by FastAPI in a thread pool, so the wait happens in a separate thread and other requests can continue. This is why the course says to use plain def with blocking drivers.

Q5. What happens when a request has a bad body, and why does the function not need to check it?

Model spoken answer

FastAPI reads the JSON and checks it against the Pydantic model before the function is called. If a field is missing or the wrong type, FastAPI returns 422 and names each bad field. The function only runs with a valid, typed object, so it does not need its own checks for type or presence. This keeps the handler short and makes the contract visible in the generated docs.
