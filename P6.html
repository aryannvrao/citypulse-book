What you are building

Picture an air-quality team in a city office. Their sensors record fine particles in the air. The particles are called PM2.5, and the level is measured in micrograms per cubic metre (written µg/m³). The team wants one web page that shows what is happening.

Open the dashboard in your browser and you see a table with four monitoring stations, ST-01 to ST-04. Each row shows how many readings the station has, its average PM2.5 and its highest reading. A bar chart shows the averages, so the dirtiest station stands out at once.

Below the table is a question box. Type "Why is ST-01 high?" and press Ask. The platform searches the team's operations notes, uses a small language model to write one sentence, and tells you which notes it used.

A second part of the page takes three inputs: the hour of the day, the last reading and the recent average. It returns a predicted PM2.5 and a category such as Unhealthy. Behind the page, a monitoring address reports how long the service has been running and how many requests it has handled. Every push of new code runs the tests, builds a package called a container image and deploys it. If the new version fails its health check, the previous version is put back.

Each ticket has a user story, acceptance criteria written as Given/When/Then, test cases your trainer runs, a definition of done and a points value. Only a trainer can move a ticket to Done, and each ticket gets a gate score from 0 to 3.

Starting from zero

Python is the language the whole project is written in. A Python program is a plain text file ending in .py. You run it by typing python followed by the file name. A library is a set of ready-made code that you import into your own file. pip is the tool that downloads libraries from the Python package index, and pip install -r requirements.txt installs every library listed in a file. The terminal is the text window where you type these commands.

pandas holds tables in memory. Its main object is the DataFrame, a table with named columns (such as station_id, ts and value) and numbered rows. You can filter rows, group them and calculate totals in a few lines. The day chapter that covers pandas in depth is the earlier one on pandas, and it is the place to go if a call in this chapter feels unfamiliar.

scikit-learn is a library of machine-learning tools. Machine learning means the program learns a rule from examples instead of you writing the rule by hand. GradientBoostingRegressor builds many small decision trees one after another. Each new tree tries to correct the errors that the earlier trees made. A regressor predicts a number, here the PM2.5 value. You covered a simpler model, the linear baseline, on Day 5. The capstone compares the two.

TF-IDF (term frequency times inverse document frequency) turns each note into a list of word weights. A word counts for more if it appears often in one note and rarely in the others. Cosine similarity compares two of these lists. It measures the angle between them, so two notes that use the same words in similar amounts score close to 1, and unrelated notes score close to 0.

Qwen2.5-0.5B-Instruct is a small language model. It is a program that predicts text, and it has been trained to follow instructions. The 0.5 means about half a billion learned numbers, which is small enough to run on an ordinary computer processor (the CPU) with no paid service. The library transformers loads the model, and torch does the arithmetic underneath. RAG stands for retrieval-augmented generation. The program first retrieves relevant text, then gives that text to the model with the question, so the answer is grounded in your own notes.

FastAPI is a web framework. A framework is a library that gives you the standard structure, so you only write the parts specific to your project. An API (application programming interface) is a set of addresses a program can call to ask for data or an action. Each address is an endpoint. Pydantic checks that incoming data has the right type and range. uvicorn is the server program that listens for requests and passes them to FastAPI. HTTP is the protocol browsers and programs use to send requests, and JSON is the plain text format used for the replies.

Streamlit turns a Python script into a web page. You write normal Python, and the library draws widgets such as tables, charts, text boxes and buttons. matplotlib draws charts. The Agg setting draws to a file without opening a window, which is why it works on a server.

pytest runs functions whose names start with test_ and reports which assertions failed. An assertion is a line that says a condition must be true, such as assert r.status_code == 422. TestClient lets a test send a request to the API in memory, so no server has to be running.

Docker packages an application with everything it needs into a container image. A container is a running copy of an image. docker-compose starts several containers together from one file. Git records changes to files, and git push sends your commits to the shared copy on GitHub. GitHub Actions runs a list of commands on GitHub's own machines whenever a trigger happens, such as a push. The list is written in a YAML file, which uses indentation to show structure. curl is a command-line tool that sends an HTTP request and prints the reply. Its -s flag hides the progress meter, and -X sets the method, such as POST.

Step 2: Make the raw readings. The goal is a reproducible week of hourly PM2.5 data for four stations, with a few deliberately bad rows.

STATIONS = {"ST-01":42,"ST-02":55,"ST-03":38,"ST-04":61}   # baselines
for h in range(168):                       # 7 days, hourly
    rush = 1.3 if (6<=h%24<=10 or 17<=h%24<=21) else 0.8
    for s,base in STATIONS.items():
        val = base + 8*gauss(1,.2)*rush + gauss(0,4)
        rows.append([s, ts, "pm25", round(val,1)])
rows += [["ST-02",...,-3.0], ["ST-09",...], ["ST-01","bad-ts",...]]

STATIONS maps each station id to a baseline level. The for h in range(168) loop runs 168 times, one for each hour in seven days. h%24 is the hour of the day, because % gives the remainder after dividing by 24. The rush line uses a higher multiplier of 1.3 during the morning and evening peaks, and 0.8 otherwise. That creates the rush-hour pattern. The inner loop makes one reading per station for each hour. gauss draws a random number from a bell curve, so each value is near the baseline with some noise. The last line adds three planted faults: a negative value, an unknown station ST-09 and a broken timestamp bad-ts. The ... marks are elisions in the course extract. Take the missing timestamp and the rest of each row from the course file and do not fill them from guesses.

Four stations times 168 hours gives 672 good rows. Adding the three planted faults gives 675. The count proves the generator worked and that you know exactly what the cleaner must remove next.

Step 3: Clean and validate. The goal is to load the CSV, parse the timestamps and drop anything that is not trustworthy.

def load(path="data/readings.csv"):
    df = pd.read_csv(path)
    df["ts"] = pd.to_datetime(df["ts"], errors="coerce")
    df = df[df.station_id.isin(STATIONS)]
    df = df[df.value.between(0, 500)]
    df = df.dropna(subset=["ts"]) \
           .drop_duplicates(["station_id","ts","pollutant"])
    print(f"clean: {before} -> {len(df)} rows")
    return df

def load(path=...) defines a function named load. It has one parameter, path, with a default value, so calling load() reads the standard file. pd.read_csv reads the file into a DataFrame, and df is the variable that holds it. pd.to_datetime(..., errors="coerce") converts the text in ts into real timestamps. Text that is not a date becomes NaT, which means "not a time". df.station_id.isin(STATIONS) keeps only rows whose station is in the list. df.value.between(0, 500) keeps values from 0 to 500, both included. dropna(subset=["ts"]) removes rows whose timestamp is NaT. The backslash at the end of a line tells Python that the statement continues on the next line, and drop_duplicates removes repeated station and time pairs for the same pollutant. The print line reports the result in an f-string, where {...} puts a value inside the text. The course extract uses before in that line but does not show where it is set. Add before = len(df) straight after read_csv, so the message can report the starting count.

The count goes from 675 to 672, so exactly the three planted faults are gone. This proves each filter removed the right rows and no good rows.

The animation below shows the same idea on four toy readings, so you can watch each test run. The real data has 675 rows, but the logic is identical.

Trap: Forgetting to set before

The printed line fails with a NameError if before is not defined. Count the rows straight after reading the file, or the message will not match the rows you actually kept.

Step 4: Guard it with a data-quality gate. The goal is to turn the assumptions about the data into assertions, so a bad feed stops the pipeline instead of quietly ruining the model.

df = load()
assert df.value.min() >= 0,            "negative reading"
assert df.value.max() <= 500,          "out-of-range value"
assert df.groupby(["station_id","ts"]).size().max()==1, "dup"
assert set(df.station_id.unique()) == STATIONS
print("data-quality checks: 4 passed")

df = load() reuses the cleaner from Step 3. Each assert line checks one rule and stops with the message after the comma if the rule is false. df.value.min() is the smallest value, so the first rule says nothing is negative. The second rule checks the largest value. The third groups the rows by station and timestamp, counts the rows in each group, and checks that the largest count is 1. That means there are no duplicates. The fourth rule compares the set of station ids in the data with STATIONS. The course extract does not show the import line. You need from pipeline import load, STATIONS at the top of the file.

The first line is printed by load(). The second line appears only if all four assertions pass. If one fails, Python stops with AssertionError and the message. That is the behaviour CI relies on in Part E.

Step 5: Aggregate per station. The goal is one summary row per station, which is the shape the API serves.

def per_station(df):
    return (df.groupby("station_id")["value"]
              .agg(["count", "mean", "max"]).round(1))

groupby("station_id") splits the rows into one group per station. ["value"] picks the column to summarise. .agg(["count", "mean", "max"]) calculates three numbers for each group: how many readings, their average and their highest value. .round(1) rounds to one decimal place. The brackets and the line break inside the outer parentheses let the chain run over several lines.

python -c runs one line of Python typed on the command line. from pipeline import * brings in everything from the file. The output has one row per station, and each count is 168, which matches seven days of hourly readings. ST-04 has the highest mean at 68.8, so it is the dirtiest station. The number proves the aggregation is correct and the data is clean.

Part B: Model, RAG and a free LLM

Step 6: Chart the trends. The goal is a PNG of the 3-hour average for each station, drawn without a screen.

import matplotlib; matplotlib.use("Agg")   # headless
import matplotlib.pyplot as plt
df = load().set_index("ts")
fig, ax = plt.subplots(figsize=(7.2, 3.1))
for sid, g in df.groupby("station_id"):
    ax.plot(g.value.resample("3h").mean(), label=sid)
ax.set_ylabel("µg/m³"); ax.legend(ncol=4)
fig.savefig("trend.png", dpi=110)

matplotlib.use("Agg") chooses the drawing mode that writes to a file and opens no window. The import ... as plt line gives the plotting module a short name. set_index("ts") makes the timestamp the row label, which lets pandas resample by time. plt.subplots creates a figure and one set of axes, with a width of 7.2 and height of 3.1 inches. The loop draws one line per station. resample("3h").mean() groups the readings into 3-hour blocks and averages each block. ax.set_ylabel labels the vertical axis, and legend(ncol=4) puts the station names in four columns. savefig writes the image at 110 dots per inch.

The file trend.png appears in the folder, at about 78 KB. The rush-hour peaks should show as regular bumps. The chart proves the data and the plotting work without any display on the machine.

Step 7: Engineer features. The goal is to turn each reading into a row that carries its hour, the previous value and a recent average.

def features(df):
    df = df.sort_values(["station_id","ts"]).copy()
    df["hour"] = df.ts.dt.hour
    g = df.groupby("station_id").value
    df["prev"]  = g.shift(1)               # lag-1
    df["roll3"] = g.shift(1).rolling(3).mean()
    return df.dropna(subset=["hour","prev","roll3"])

sort_values puts each station's readings in time order. .copy() makes a separate table, so the original is not changed. df.ts.dt.hour reads the hour from each timestamp. g.shift(1) moves each value down one row within its station, so each row sees the reading before it. That is the lag. rolling(3).mean() averages each set of three rows. Applied to the shifted values, it averages the three readings before the current one. The current value is never used as its own input. Groupby shifting leaves an empty value at the start of each station, and that empty value stops the rolling window reaching into the previous station. The final line drops the rows at the very start where the lag or the average does not exist yet.

The command loads the features, keeps five columns, rounds to one decimal place and shows the first five rows. Look at the prev column. In the row for hour 4, prev is 50.4, which is the value in the row for hour 3. That proves the lag is correct. Every row now carries the hour, the previous reading and a three-reading average, which are the three inputs the model uses.

Step 8: Train and evaluate the model. The goal is a fitted GradientBoosting model with a measured error, saved to disk.

X, y = df[FEATS], df["value"]
Xtr,Xte,ytr,yte = train_test_split(X, y, test_size=.2, random_state=42)
model = GradientBoostingRegressor(random_state=42).fit(Xtr, ytr)
pred = model.predict(Xte)
print(f"MAE {mean_absolute_error(yte,pred):.2f}  R2 {r2_score(yte,pred):.3f}")
joblib.dump(model, "model.joblib")

X holds the input columns and y holds the target, the reading to predict. FEATS is the list of input column names, which is hour, prev and roll3. The course extract uses it without showing its definition, so define it once in train.py and reuse it everywhere. train_test_split sets aside 20 per cent of the rows for testing (test_size=.2). random_state=42 fixes the random choice, so you get the same split every run. fit trains the model on the training rows. predict produces guesses for the test rows. mean_absolute_error is the average size of the miss, in the same units as the reading. r2_score measures how much of the variation in the readings the model explains, where 1.0 is perfect. joblib.dump saves the trained model to a file, so the API can load it later without retraining.

The model is off by 4.25 µg/m³ on average and explains 74 per cent of the variation. The day 5 linear baseline scored an error of 4.89, so the boosted model is measurably better. The file model.joblib is about 137 KB. That proves the model is worth shipping and is ready for the API.

Step 9: Build a tiny RAG index. The goal is a searchable index of the operations notes, with no database.

_notes = pd.read_csv("data/notes.csv")
_vec = TfidfVectorizer(stop_words="english")
_mat = _vec.fit_transform(_notes.text)
def retrieve(question, k=2):
    sims = cosine_similarity(_vec.transform([question]), _mat)[0]
    top = sims.argsort()[::-1][:k]
    return _notes.iloc[top], sims[top]

The first line reads the notes into a table. The second creates a TF-IDF converter. stop_words="english" ignores common English words such as "the" and "is", which carry no meaning for search. fit_transform learns the vocabulary and the weights from all notes and turns every note into a vector. retrieve takes a question and turns it into a vector with the same vocabulary, using transform. cosine_similarity compares it with every note and returns one list of scores. [0] takes the first row of that result. argsort() gives the indexes of the scores in ascending order, [::-1] reverses the order to descending, and [:k] keeps the top k. The function returns those notes and their scores. Because the code runs at import time, the index is built once when the file is loaded.

The question is turned into a vector, compared with every note, and the best note comes back. The output is the note id N1 and its score of 0.367. The right note surfacing proves retrieval works, and the score tells you how confident the match is.

Step 10: Answer with the free LLM. The goal is a one-sentence answer built only from the retrieved notes.

def ask(question, k=2):
    hits, scores = retrieve(question, k)
    context = "\n".join(f"- {t}" for t in hits.text)
    prompt = (f"Use ONLY these ops notes to answer in one "
              f"sentence.\n{context}\n\nQuestion: {question}")
    return {"answer": generate(prompt),
            "sources": hits.note_id.tolist()}

retrieve finds the top notes. The context line builds a bulleted list, with one dash and a space before each note's text. \n is a new line. The prompt is the text the model reads. It starts with an instruction to use only the notes, then the notes, then the question. The function returns a dictionary, which is a set of named values. The answer comes from generate, a shared function that runs the language model. The course extract calls generate but does not show it, so you will need the version from the earlier step that loads Qwen. The sources list holds the note ids, so the answer can be checked.

The answer is taken from notes N6 and N8, and the top score is 0.611. The model's words depend on the notes it was given, which is the point of RAG. The output proves the answer is grounded and cited.

Step 11: Plain-English advisory. The goal is to reuse the same model to turn a number into advice for residents.

def advisory(station, pm25, category):
    return generate(
      f"PM2.5 at {station} is {pm25} ug/m3 "
      f"({category}). Advise residents.",
      system="You are an air-quality assistant. "
             "Answer in ONE short sentence.")

The function takes a station id, a PM2.5 value and a category label. The f-string puts those values into the prompt. The system= argument is a separate instruction that sets the model's role and the answer length. The function returns whatever generate produces.

Each line shows the station, its value and category, then the advice. The advice differs with the category, and it is one sentence each time. That proves one model serves two jobs without extra cost. The model's wording is not fixed, so check that it is sensible before you show it.

Part C: Serve it with FastAPI

Step 12: The API skeleton. The goal is a running web service with a health check and a stations endpoint.

app = FastAPI(title="CityPulse Capstone", version="6.0")
_df = load(); _model = joblib.load("model.joblib")
class PredictIn(BaseModel):
    hour: int = Field(ge=0, le=23)
    prev: float = Field(ge=0, le=500)
    roll3: float = Field(ge=0, le=500)
@app.get("/health")
def health(): return {"status": "ok"}
@app.get("/stations")
def stations(): return per_station(_df).reset_index().to_dict("records")

app = FastAPI(...) creates the service and gives it a title and version. load() and joblib.load run once at startup, so each request does not reload the data or the model. class PredictIn(BaseModel) defines the shape of a prediction request. hour: int must be an integer, and Field(ge=0, le=23) says it must be between 0 and 23 inclusive. ge means greater than or equal to, and le means less than or equal to. The @app.get("/health") line is a decorator. It tells FastAPI that the function below answers GET requests to /health. reset_index() turns the station id back into an ordinary column, and to_dict("records") turns the table into a list of dictionaries, which FastAPI sends as JSON. The extract does not show _m (the request counters) or _t0 (the start time). Create them at the top, for example _m = {"requests": 0, "predictions": 0, "asks": 0} and _t0 = time.time(), and import time, joblib, category and FEATS.

uvicorn starts the server. main:app means "the variable named app inside the file main.py". --reload restarts the server when you save a change, which is useful while you learn. The address 127.0.0.1 is your own computer, and 8000 is the port. The last line is a request to /health that returned status 200, which means success. That proves the service starts, loads its data and answers.

Step 13: Predict, with validation. The goal is a POST endpoint that returns a prediction and rejects impossible input.

@app.post("/predict")
def predict(p: PredictIn):
    X = pd.DataFrame([{"hour":p.hour,"prev":p.prev,
                       "roll3":p.roll3}])
    pm25 = round(float(_model.predict(X[FEATS])[0]), 1)
    cat = category(pm25)
    return {"pm25": pm25, "category": cat}

@app.post means the function answers POST requests, which are used to send data. p: PredictIn tells FastAPI to check the body of the request against the PredictIn rules before the function runs. The function builds a one-row table with the three values. _model.predict returns an array of guesses, and [0] takes the first. float converts it to a normal number, and round(..., 1) keeps one decimal place. category(pm25) turns the number into a label. The function returns a dictionary, which becomes JSON. Note that the course code does not add to the predictions counter, although the metrics output shows one. Add _m["predictions"] += 1 before the return line.

curl -s sends the request quietly. -XPOST sets the method to POST. -H adds a header that tells the server the body is JSON. The -d value is the JSON body. The reply gives a prediction of 66.8 and the label Unhealthy. The second block is a note that a request with hour 99 is rejected with status 422, which means the data was understood but breaks a rule. The message names the rule, so the caller knows what to fix. That proves validation runs before the model sees the input.

Step 15: Expose /metrics for monitoring. The goal is a heartbeat endpoint that a monitor can check.

@app.middleware("http")
async def count(req, nxt):
    _m["requests"] += 1
    return await nxt(req)
@app.get("/metrics")
def metrics():
    return {"uptime_s": round(time.time()-_t0,1),
            "rows": len(_df), "model": "GradientBoosting",
            **_m}

@app.middleware("http") registers a function that runs on every request, before the endpoint. async def means the function can pause while it waits, which lets the server handle other requests in the meantime. await nxt(req) passes the request on to the endpoint and waits for its reply. The middleware counts every request first. metrics calculates the uptime by subtracting the start time from the current time. len(_df) counts the rows. The **_m part adds all the counters from the dictionary into the reply. Two stars unpack a dictionary into the surrounding one.

The reply shows 672 rows, the model name, four requests so far, one prediction and no questions. These are the numbers a monitor needs. The count of 4 proves the middleware sees every request. Because the predictions counter is one, the code in Step 13 must have incremented it.

Step 19: CI, test, build and push. The goal is an automatic job that installs, rebuilds the data and model, runs the gate and the tests, and builds the image on every push.

      - uses: actions/checkout@v4

jobs: lists the work to do, and test is one job. runs-on: ubuntu-latest picks a Linux machine that GitHub provides. Each item under steps: starts with a dash and runs in order. uses: actions/checkout@v4 downloads your code into the machine. @v4 names the version of the action. setup-python installs Python 3.11, which is set in the with block. Each run: line executes a shell command. The && between two commands means the second runs only if the first succeeded. The last line runs the gate and the tests. The course extract does not show the on: trigger that starts the workflow. The callout on the course page says it runs on push to main.

Step 20: CD, deploy, monitor and roll back. The goal is a deploy job that runs only after the tests pass, checks the new release, and rolls back if the check fails.

  deploy:
    needs: test
    steps:
      - run: docker push ghcr.io/$REPO:$SHA
      - run: ./deploy.sh ghcr.io/$REPO:$SHA
      - run: curl -f $URL/metrics || ./deploy.sh $PREV_TAG
        # health-check; roll back to last good on failure

needs: test means the deploy job waits for the test job, and does not start if the tests failed. $REPO, $SHA, $URL and $PREV_TAG are variables. Each one holds a value such as the image path, the commit id, the service address or the last good tag. docker push uploads the image to the registry at ghcr.io. ./deploy.sh runs the rollout script with the new image. The third line calls curl -f on the /metrics address. The -f flag makes curl return an error for an HTTP failure such as 500. The || means "or, if the left side failed", so the rollback runs only when the check fails. The course extract does not show where PREV_TAG is set. You must store the tag of the last good release somewhere CI can read it.

The push starts the pipeline. The image tag 9f2e1d is the new release, and 7a3c0b is the previous one kept for rollback. The line "/metrics 200" shows the health check passed. This proves the release went out only after tests passed, and that a rollback target was ready.

The Part G challenges

The five challenges are the assessed work. Each one below states what is asked, quotes the acceptance test exactly, names the ideas it needs, gives a plan and lists the mistakes that fail the test. The plans are steps to follow, not finished code. Write the code yourself.

Challenge 1: Carry a second pollutant (easy, data)

What is asked. Extend make_data.py and pipeline.py to carry NO2 as well as PM2.5, and make /stations aggregate per station and pollutant through the quality gate.

Done when: "GET /stations returns both pm25 and no2 rows for every station and dq_check still passes."

Ideas it needs. The data generator must write rows with the pollutant name no2. per_station must group by two columns, not one. The gate's duplicate check in Step 4 groups by station and time only, so once NO2 rows exist, two rows share the same station and timestamp and the check fails.

Plan of attack. 1. Read make_data.py and decide how NO2 rows look. Keep the same four columns as the PM2.5 rows. 2. Generate the NO2 rows with their own baselines, and re-run make_data.py. 3. Re-run the cleaner and check the row count is what you expect. 4. Change the duplicate check in dq_check.py so the group key includes the pollutant. 5. Change per_station to group by station and pollutant. 6. Check the dashboard. Its bar chart indexes by station_id, which will repeat once each station has two rows, so decide what it should plot. 7. Call /stations and check that both pollutants appear for each station.

Mistakes that fail the test. Leaving the duplicate check unchanged, so dq_check fails. Grouping by station only, which averages PM2.5 and NO2 together into a meaningless number. Changing the response shape and forgetting that the dashboard expects one row per station.

Challenge 2: Add a note to the RAG index (medium, LLM and RAG)

What is asked. Append a new ops note to data/notes.csv about winter inversions, and confirm that /ask retrieves and cites it for a relevant question.

Done when: "POST /ask a winter-inversion question returns an answer whose sources include the new note id."

Ideas it needs. The index is built from the CSV when rag.py is imported (Step 9), so a change to the file has no effect until the server restarts. TF-IDF weights depend on the whole set of notes, so a new note shifts the scores of the others. A question with few words in common with your note will lose to older notes.

Plan of attack. 1. Open data/notes.csv and check the column names, note_id and text. 2. Choose a note_id that is not used. Write a short note with distinctive words that a question would also use, such as winter, inversion and cold air. 3. Save the file and restart the server. 4. Test retrieval directly with retrieve, using a question that uses the same words. Check that your note is in the top results. 5. Send the same question to /ask and read the sources list.

Mistakes that fail the test. Reusing an existing note id, so one note overwrites or confuses the other. Forgetting to restart, so the index is stale. Writing a note that shares almost no meaningful words with the question. Trusting the answer text without checking that your note id is in sources.

Challenge 3: Latest-reading forecast endpoint (medium, API)

What is asked. Add GET /forecast/{station} that computes the features from the station's latest readings and returns the model's next-hour prediction.

Done when: "curl /forecast/ST-04 returns a pm25 and category with no manual feature input."

Ideas it needs. The features must match the training definitions in Step 7 exactly. prev is the latest value, and roll3 is the average of the three latest readings including the latest. The hour is the hour of the reading being predicted, which is one hour after the latest timestamp. The {station} in the path is a parameter, and the endpoint should handle a station that does not exist.

Plan of attack. 1. Write down, for a station with readings up to time T, the values of prev, roll3 and hour you want for the reading at T plus one hour. Compare them with the definitions in features(). 2. Pick the station's rows from the cleaned data and sort them by time. 3. Compute the three inputs from those rows. 4. Send them through the same model call that /predict uses, so the two endpoints agree. 5. Return the same shape of reply as /predict. 6. Test with the course station and one unknown station.

Mistakes that fail the test. Using the hour of the latest reading instead of the predicted hour. Averaging only the two latest readings, or including a reading that the training definition would not use. Forgetting that the rows must be sorted by time, which gives a wrong latest reading. Returning a server error for an unknown station instead of a clear error.

Challenge 4: Interactive dashboard (medium, UI)

What is asked. Add a station selector and a 24-hour line chart to the Streamlit app, plus a live /metrics panel that refreshes on each run.

Done when: "Picking a station redraws its last-24h PM2.5 trend and the metrics panel updates."

Ideas it needs. Streamlit runs the whole script again from the top each time a widget changes. The current API returns only per-station summaries, so the 24-hour trend needs data the API does not yet give. You will need a new endpoint, or another way to fetch the readings. The chart needs a real time axis.

Plan of attack. 1. Decide where the 24-hour data comes from, and add an endpoint if the current API cannot provide it. 2. Get the list of station ids from /stations and show them in a selector. 3. Request the readings for the selected station and keep only the last 24 hours. 4. Draw a line chart with the timestamps on the horizontal axis. 5. Request /metrics on each run and show its values in a panel. 6. Check that changing the station redraws the chart.

Mistakes that fail the test. Hardcoding one station. Drawing the chart against the row number instead of the timestamp, so the time gaps disappear. Caching the metrics for too long, so the panel does not refresh. Requesting a whole week and calling it 24 hours.

Challenge 5: Block a bad model in CI and prove rollback (hard, CI/CD)

What is asked. Add a CI check that fails the build when test MAE exceeds 5.0, and make the deploy job redeploy the previous tag when the post-deploy /metrics health check fails.

Done when: "A deliberately-bad model fails the Actions run; a broken deploy is detected by /metrics and rolled back to the last good tag automatically."

Ideas it needs. A CI step fails only when its command exits with a non-zero code. Printing an error does not fail a step. The MAE is printed by train.py in Step 8, so the check must read or receive that number. The rollback needs the previous image tag, which must be stored by the last successful deploy. A health check right after a rollout may need a short retry before you judge it.

Plan of attack. 1. Make the MAE available to the check, either by having train.py write it to a file or by having the check recompute it. 2. Write a small check that compares the MAE with 5.0 and exits with a non-zero code when it is larger. 3. Add that check to the test job after training and before the tests. 4. Prove it: make a deliberately weak model on a branch, push it, and confirm the Actions run fails. 5. Store the tag of each successful deploy, so the next deploy knows the last good tag. 6. Keep the /metrics check after the rollout, and make a failed check call the redeploy of that stored tag. 7. Prove the rollback by making the health check fail on purpose, and confirm the service returns to the last good tag.

Mistakes that fail the test. Printing the MAE without failing the step. Measuring the error on the training rows, which hides overfitting, instead of the test rows. Rolling back to the new tag instead of the previous one. Storing the previous tag only in a shell variable that disappears when the job ends. Judging the health check before the new version has started, which causes a false rollback.

Viva preparation

The capstone viva scores four things from 0 to 5: acceptance criteria met, technical depth, contribution and ownership, and understanding. Acceptance criteria means you can show that the Done when tests pass. Technical depth means you can explain the mechanisms, such as how a lag or a cosine score works. Contribution and ownership means you can say which parts you wrote and changed yourself. Understanding means you can reason about what fails and why. The eight questions below cover all four. Practise saying each answer aloud in your own words.

1. Walk me through what happens from a git push to a live service.

Model answer

A push to main starts the GitHub Actions workflow on a fresh Linux machine. The test job installs the requirements, rebuilds the data and model, runs the data-quality gate and then the pytest suite. Only if the tests pass does the deploy job start, because it declares needs: test. The deploy job pushes the image, runs the rollout script, and then checks /metrics, and it rolls back to the previous tag if that check fails.

2. Why does the pipeline have a data-quality gate, and what does it stop?

Model answer

The gate turns assumptions about the data into assertions that stop the run when they are false. It checks for negative values, values above 500, duplicate station and time pairs, and unknown stations. Without it, a bad feed would train the model and fill the dashboard with wrong numbers, and nobody would notice. Because the same gate runs in CI, a broken feed stops the release before it ships.

3. Why GradientBoosting, and how do you know the model is good enough to ship?

Model answer

GradientBoosting builds many small trees, each correcting the errors of the earlier ones, which suits a small table with three numeric inputs. I measured it on a held-out 20 per cent of the rows, not on the rows it trained on. The result was a mean absolute error of 4.25 µg/m³ and an R² of 0.740, compared with 4.89 for the day 5 linear baseline. That gives a measured improvement, although a single split is a limited test.

4. Why TF-IDF and cosine similarity for retrieval instead of a vector database?

Model answer

The notes are a small set of short texts, so TF-IDF with cosine similarity is accurate enough, fast, and needs no extra service or cost. A vector database makes sense at a much larger scale or when you need semantic matching beyond shared words. The trade-off is that TF-IDF only matches words, so a question with different wording can miss a note. I would say so openly in a viva.

5. How does the RAG answer stay grounded, and what does the language model actually see?

Model answer

The retrieval step selects the top notes by score, and the prompt contains only those notes and the question, with an instruction to use only them. The model never sees the whole notes file. The reply also returns the note ids, so a person can check the source. The grounding is only as good as the retrieval, so a wrong top note produces a confident but wrong answer.

6. Why validate input with Pydantic, and what does a 422 tell the caller?

Model answer

Pydantic checks each field's type and range before the endpoint runs, so the model never receives an impossible hour or a question that is too short. When the check fails, FastAPI returns status 422 with a message that names the rule, such as "Input should be less than or equal to 23". The caller can fix the request from that message. A 500 would mean the server itself broke, which is a different problem.

7. How does the rollback decide to act, and what could go wrong with it?

Model answer

The deploy step calls curl -f on the /metrics address after rollout. The -f flag makes curl fail on an HTTP error, and the || then runs the redeploy of the previous tag. What can go wrong is a check that runs before the new version is ready, which causes a false rollback. Another risk is a missing or empty previous tag, so the rollback has nothing to deploy. A short retry and a stored last-good tag address both problems.

8. What would you monitor in production, and what does /metrics not tell you?

Model answer

I would watch the request count, error rate and latency of each endpoint, plus the uptime and the model's error on recent data. /metrics gives uptime, row count and request counters, so it shows that the service is alive and busy. It does not show whether the predictions are accurate, how slow the answers are, or whether the data feed is fresh. Those need additional measurements, which is a useful point to raise in a viva.
