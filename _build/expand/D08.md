## What the quiz tests

The Day Quiz has ten multiple-choice case-study questions, one for each topic in this section, asked in the order shown. Each question describes a small CityPulse situation, such as a loader that fails or a report with a wrong count, and asks what to do next. The pass mark is 70%, so you need at least seven correct. Only your first attempt counts towards your skill score, so treat every attempt as the real thing.

Use the same method on every question. Start with the last line, because it tells you what is being asked: the first step, the most likely cause or the best fix. Then reread the scenario and underline the facts that matter, such as the type of a column, the key that identifies a row, or how many stations appear. Those facts decide the answer, and the fact you ignore is often the one that makes a tempting option wrong.

Next, eliminate options. Many wrong options are true in general, for example "pandas can group rows", but they do not fix the problem in the scenario. Ask whether the option solves the situation described, not whether it is a correct statement about pandas.

Watch three words. "Most" means one option is better than the others, not that the others are false. "First" means the earliest step, which is often a check rather than a fix. "Best" means the option that meets every constraint, including the quiet ones, such as keeping a count or not losing data.

Each topic below starts with what the idea is, from zero, then a case study, then the trap, then three practice questions. Read the WHY line even when you answer correctly, because it explains the wrong options too.

### Column types in pandas (dtypes)

A dtype is the type that pandas stores in a column. It decides which operations work on that column. A column of numbers stored as `float64` can be averaged. A column of text is stored as `object` in most pandas versions (newer versions may show `str`), and text can be compared and joined but not averaged. Dates have their own dtype, `datetime64`, and a timezone-aware date shows its zone in the dtype, as in `datetime64[ns, UTC]`. A `category` dtype stores a fixed set of labels efficiently.

pandas guesses a dtype when it reads a file. If every cell in a column is a number, the column becomes a number type. If one cell is text, such as `NA*`, the whole column becomes `object`. You can remove the guessing by stating the type yourself, or by converting the column afterwards:

```python
import pandas as pd

raw = pd.Series(["12.5", "7", "NA*"])
print(raw.dtype)
numbers = pd.to_numeric(raw, errors="coerce")
print(numbers.tolist())
print(numbers.dtype)
```

The output is `object`, then `[12.5, 7.0, nan]`, then `float64`. The cell `NA*` cannot be read as a number, so `errors="coerce"` turns it into `NaN`, which is pandas' marker for a missing number. The other two cells keep their values. The word `nan` in the list output is the same marker.

#### How it shows up in a case study

A team at a city air-quality desk loads a week of sensor CSV files. The daily mean of PM2.5 fails, and the `value` column reports dtype `object`. The team finds that one sensor wrote `NA*` into a cell, so the whole column is text, and text cannot be averaged. The right decision is to convert with `pd.to_numeric(..., errors="coerce")`, count how many cells became `NaN`, and report that count, so the faulty sensor is visible. Changing the loader to hide the problem, or deleting the column, would stop the error message without explaining the cause.

:::trap astype looks like the same fix
`df["value"].astype(float)` stops at the first text cell with a `ValueError`, and the run ends. It does not count the bad cells. When some cells may be bad, use `pd.to_numeric(..., errors="coerce")` and count the `NaN` results.
:::

```quiz

WHY: pd.to_numeric with errors="coerce" converts each cell and writes NaN where it cannot. Converting to category keeps labels rather than numbers, so the mean still fails. str.len() counts characters, and sorting changes no type.
```

### Grouping rows with groupby

A group-by splits the rows into groups by one or more columns, then runs an aggregation such as `mean`, `sum`, `count` or `size` on each group. The result has one row per group. Pass a list to group by several columns at once, as in `groupby(["station", "pollutant"])`.

```python
import pandas as pd

df = pd.DataFrame({"station": ["ST-02", "ST-02", "ST-03"],
                   "value": [36.4, None, 49.3]})
print(df.groupby("station")["value"].size())
print(df.groupby("station")["value"].count())
```

The first print shows ST-02 with 2 and ST-03 with 1, because `size()` counts every row. The second shows ST-02 with 1 and ST-03 with 1, because `count()` counts only values that are present. The blank cell for ST-02 is in the first count and not in the second. When a group column is a category, pass `observed=True`, so that unused categories do not create empty groups.

#### How it shows up in a case study

A team is about to publish a monthly PM2.5 average for each station. Station ST-07 has five rows, one of them blank. The average is only as trustworthy as the number of readings behind it. The decision is to report `count()` next to the mean, so a reader sees that ST-07 rests on four readings. Using `size()` would show five and overstate the evidence. Stations with very few valid readings should be flagged rather than averaged silently.

:::trap size() is not count()
`size()` counts every row in each group, including rows whose value is missing. If the question asks how many readings carry a value, the answer is `count()`.
:::

```quiz
Q: Station ST-07 has five rows in the table, and one of them has a blank value. The analyst needs the number of readings that actually carry a value for each station, so that the monthly mean is not overstated. Which expression gives that count?

* df.groupby("station")["value"].count()
- df.groupby("station")["value"].mean()
- df.groupby("station")["value"].sum()
WHY: count() counts non-missing values, so ST-07 gives 4. size() counts all five rows and overstates the evidence. mean() and sum() return a value, not a count.

Q: A table has a station column stored as a category with five defined stations, but only three appear in this month's data. You group by station and take the mean of value, and the result contains two extra rows full of NaN. Which argument stops pandas from creating rows for the unused categories?

- as_index=False
* observed=True
- sort=False
WHY: observed=True tells pandas to use only the categories that appear in the data. dropna controls missing group keys, as_index controls whether the group labels become the index, and sort controls the order of the rows.

Q: A monthly report groups readings by station and pollutant, then takes the mean of value. Two groups contain only blank values. The lead asks what those groups show in the result. Which answer is right?

WHY: a group with no valid values gives a NaN mean. It is neither zero nor an error. The tempting answer 0.0 treats a missing reading as a measured zero, which hides the gap.
```

### Removing repeated rows with drop_duplicates

`drop_duplicates(subset=..., keep=...)` removes rows that repeat a key. The `subset` names the columns that identify one reading, which is the key. The `keep` argument decides which copy survives. `keep="first"` keeps the first copy in the current row order, `keep="last"` keeps the last copy, and `keep=False` removes every copy of a repeated key.

```python
import pandas as pd

df = pd.DataFrame({"station": ["ST-02", "ST-02", "ST-03"],
                   "ts": ["07:00", "07:00", "07:00"],
                   "value": [36.4, 38.1, 49.3]})
print(df.drop_duplicates(subset=["station", "ts"], keep="first")["value"].tolist())
print(df.drop_duplicates(subset=["station", "ts"], keep="last")["value"].tolist())
```

The first line prints `[36.4, 49.3]`, because the first ST-02 row survives. The second prints `[38.1, 49.3]`, because the second ST-02 row survives. Nothing in the rule looks at time. It looks only at row order, so the copy that wins is the one that happens to come first or last in the table.

#### How it shows up in a case study

Two feeds from one sensor overlap for three hours, so each station-hour appears twice. The first feed sent a blank for one of the duplicated rows. The team wants one row per reading and the valid value kept. The decision has three parts: fix the key as station, timestamp and pollutant, drop the blank rows first so that a valid copy is the only copy left for its key, and then remove duplicates. The team also writes down each count, so the effect of each rule can be checked.

:::trap Dropping blanks after deduplicating
Suppose a blank and a valid reading share the same key, and the blank comes first. `keep="first"` keeps the blank and discards the valid reading. Dropping blanks afterwards then removes the only remaining row, and the reading is lost. Drop the blanks first, so that only valid copies are left to compete.
:::

```quiz
Q: Two feeds send a reading for ST-04 at 08:00 for PM2.5. The first row in the file has a blank value, and the second has 41.2. You run drop_duplicates(subset=["station_id", "ts", "pollutant"], keep="first"), and then dropna on value. What remains for that key?
- The 41.2 row, because dropna runs first
- Both rows, because the keys look the same but are different objects
* Nothing, because the valid 41.2 row was removed as a duplicate
- The blank row, which is kept because it came first in a list
WHY: keep="first" keeps the blank row and removes the 41.2 row. dropna then removes the blank, leaving nothing for that key. Dropping the blanks before deduplicating would leave the 41.2 row as the only copy.

Q: A cleaning script removes repeated readings with keep="first". After a re-fetch, the newest copy of each reading sits at the bottom of the file. A teammate asks which copy survives. What is the accurate answer?
- The newest, because pandas always keeps the most recent row
- The one with the largest value, because duplicates are ranked by value
- Both, because keep="first" keeps every copy
* The first copy in the current row order, which is the oldest unless the rows were sorted by fetch time first
WHY: keep="first" depends only on the current row order, not on time. To keep the newest copy, sort by fetch time so that the newest comes last, and then use keep="last".

Q: The analyst wants every copy of a repeated key removed, with none kept, because the sensor's repeats cannot be trusted. Which argument does this?
- keep="first"
* keep=False
- keep="last"
- subset=None
WHY: keep=False marks every copy of a repeated key for removal. keep="first" and keep="last" each keep one copy. subset=None compares whole rows, not the key.
```

### Parquet: typed columns in one file

Parquet is an open file format that stores a table column by column. Each column is compressed, and the file holds a schema, which records the name and type of every column. CSV stores only text. After a CSV round trip, a timestamp comes back as plain text. Parquet keeps the UTC datetime, the floats and the categories as they were written.

```python
import pandas as pd

df = pd.DataFrame({
    "ts": pd.to_datetime(["2026-03-01 07:00", "2026-03-01 08:00"], utc=True),
    "value": [36.4, 38.1],
})
df.to_csv("demo.csv", index=False)
df.to_parquet("demo.parquet", index=False)
print(pd.read_csv("demo.csv").dtypes)
print(pd.read_parquet("demo.parquet").dtypes)
```

The CSV reload shows `ts` as `object`, which means text, and `value` as `float64`. The Parquet reload shows `ts` as `datetime64[ns, UTC]` and `value` as `float64`. The two files hold the same numbers. The difference is the schema, which only the Parquet file stores. Writing Parquet needs the pyarrow library to be installed.

#### How it shows up in a case study

A pipeline writes cleaned readings to a file, and the analysis notebook reads them the next morning. The notebook shows timestamps as text, so the hourly grouping fails. The file itself is correct. The team decides that the cleaned table should be stored as Parquet, because Parquet keeps the UTC datetime type, while CSV loses it. They also record the schema in the handover note, so the next reader knows which types to expect without guessing.

:::trap Compression is not the main reason
Parquet is smaller partly because it compresses each column. The main reason for the format is the typed, self-describing columns. When a question asks why the types survive a round trip, the answer is that the file stores a schema, not that it is compressed.
:::

```quiz
Q: A notebook reads a CSV of cleaned readings, and the ts column comes back as text, so the hourly grouping fails. The file is correct. Which file format keeps the UTC timestamp type when the table is written and read again?
* Parquet
- Plain text with comma separators
- A text file saved from Notepad with the same rows
- A CSV file with an extra header row
WHY: CSV keeps no types, so every reader must parse the text again. Parquet stores the schema, so timestamps come back as timestamps. The other three options are all CSV or CSV-like, and they lose the types in the same way.

Q: A teammate says Parquet is smaller than CSV only because it is columnar, so any column-based format would be just as small. Which response is most accurate?
- Parquet is smaller only because it drops the header row.
- Any file that stores columns separately is equally small, because size depends only on the disk.
* Column layout helps compression, but the main purpose of the format is its stored types and schema, and size is a side benefit.
- Parquet is always larger than CSV for numbers.
WHY: the layout helps compression, and Parquet also compresses each column, but the claim that any column-based format is equally small is not established. The format exists to keep typed, self-describing columns. Size is a useful side effect, not the whole story.

Q: A teammate wants to check the values of a Parquet file by opening it in a text editor before loading it. What is the most accurate advice?

- Rename it to .csv first, and the editor will show the rows.
- Open it in a text editor set to UTF-8, which displays the rows.
* Read it with pandas or pyarrow, because Parquet is binary and an editor shows unreadable bytes.
WHY: Parquet is a binary format, so a text editor shows bytes, not rows. Renaming the file does not change its contents. Use pandas, pyarrow or a Parquet viewer to read it.
```

### Partitioned Parquet folders

A partitioned Parquet dataset is a folder with one subfolder for each value of a chosen column. You ask for it with `partition_cols`. The subfolders are named in the form `station_id=ST-02`, and the rows for that station are stored inside. The partition column is not repeated inside the files, because its value is already in the folder name. A reader that filters on that column can skip the other folders entirely.

```python
import pandas as pd

df = pd.DataFrame({"station_id": ["ST-02", "ST-02", "ST-03"],
                   "value": [36.4, 38.1, 49.3]})
df.to_parquet("out/readings", index=False, partition_cols=["station_id"])
```

On disk, `out/readings` now contains a subfolder called `station_id=ST-02` and another called `station_id=ST-03`, each with a Parquet file inside. Reading the dataset back with `pd.read_parquet("out/readings", filters=[("station_id", "==", "ST-02")])` opens only the matching folder. Partitioning saves reads, not storage. It can even make the total size larger when it creates many small files.

#### How it shows up in a case study

A team stores a year of hourly readings for twelve stations. The dashboard always asks for one station at a time. The team proposes partitioning by station, which has twelve values. The reasoning is that the queries filter on station, so the reader can skip eleven of the twelve folders. Partitioning by the full timestamp would create a folder and a file for almost every reading, and every query would open thousands of small files. The decision is to partition by station, and never by a column with one value per reading.

:::trap Partitioning by a column with one value per reading
Partitioning by `ts` creates one folder for each reading. The folders multiply, the files become tiny, and every read has to open thousands of them. Choose a column with a few values, such as station, region or month.
:::

```quiz
Q: A team stores readings for forty stations, and most queries ask for one station at a time. They write the data with partition_cols=["station_id"]. Which result should they expect on disk?
- One file called readings.parquet, with station_id repeated in every row
* A folder with one subfolder per station, and the rows for each station stored inside its subfolder
- Forty complete copies of the whole table
- One CSV file for each station
WHY: partition_cols creates a subfolder for each value, named like station_id=ST-02. The station column is not repeated inside the files. The tempting answer is one file with repeated station values, which is what you get without partitioning.

Q: A dataset is partitioned by ts, the full timestamp of each reading, and it holds 500,000 rows. A teammate asks what this will cost. Which answer is correct?
* Each reading gets its own folder, so the dataset holds a huge number of tiny files and reads slow down.
- The files shrink, so the total storage falls.
- Nothing changes, because timestamps are never used for partitions.
- The timestamp column is compressed to a single value.
WHY: partitioning creates a folder for each distinct value, so a column with one value per reading creates one folder per reading. Each folder holds a small file, and queries open all of them. The total storage does not fall, because the files add overhead.

Q: A query filters station_id == "ST-02" on a partitioned dataset and runs much faster than before. Which explanation fits best?

- The filter converts the station column to text first.
WHY: the reader compares the filter with the folder names and reads only the matching folders. Compression does not depend on the station, and caching is not the cause. Partitioning changes which files are read, not how well they compress.
```

### Reshaping with pivot, pivot_table and melt

Reshaping changes the layout of a table without changing the values, although some functions also aggregate. `pivot` turns labels in one column into column headers, and it needs each combination of index and column to appear only once. `pivot_table` does the same job, but it aggregates duplicate combinations, with the mean by default. `melt` does the reverse, turning columns back into rows.

```python
import pandas as pd

long = pd.DataFrame({
    "day": ["03-01", "03-01", "03-02"],
    "pollutant": ["PM2.5", "O3", "PM2.5"],
    "value": [36.4, 21.5, 33.0],
})
wide = long.pivot_table(index="day", columns="pollutant", values="value", aggfunc="mean")
print(wide)
```

The table has one row per day and one column per pollutant. The day 03-02 has no O3 reading, so its cell shows `NaN`. That is expected: a pivot places `NaN` wherever no row exists for an index and column pair. Calling `melt` on the wide table turns the columns back into rows, and it keeps the `NaN` row unless you drop it afterwards.

#### How it shows up in a case study

A report needs one row per day and one column per pollutant. The raw export is long, with one row per reading, and several stations report on the same day. The report wants one number per day per pollutant, so an aggregation is needed. `pivot` would fail on the duplicates, and picking one reading at random would be wrong. The decision is `pivot_table` with `aggfunc="mean"`, and the report says that the figure is a daily mean across stations.

:::trap pivot_table hides duplicates
`pivot` raises an error when the same index and column pair occurs twice, which is a useful warning. `pivot_table` averages the duplicates without any message. If the average is not what you want, check for duplicates first.
:::

```quiz
Q: A table has one row per station and pollutant, with the values in a single column, and each pair appears exactly once. You want one row per station and one column per pollutant, with no aggregation. Which function fits?
- melt
- concat
- drop_duplicates
* pivot
WHY: pivot moves the pollutant labels into column headers. Because each pair appears once, nothing needs averaging. melt does the reverse, concat stacks tables, and drop_duplicates removes rows.

Q: A long table holds two PM2.5 readings for ST-02 on 03-01, and you call pivot with the same index and columns. What happens?

* pandas raises a ValueError because the index contains duplicate entries.
- The two values are added together.
- pandas creates a second column named PM2.5_2.
WHY: pivot requires each index and column pair to be unique, and it stops with an error when a pair repeats. The pivot_table function would average or aggregate the values instead.

Q: A wide table has one column each for O3, PM2.5 and NO2, with one row per day. The analyst wants one row for each day, pollutant and value, which is the long shape. Which function does this?
* melt
- pivot_table
- merge
- groupby
WHY: melt turns columns into rows. pivot and pivot_table do the reverse. merge joins two tables on keys, and groupby computes aggregates without changing the layout.
```

### Joining tables with merge

`pd.merge` joins two tables on one or more key columns. The `how` argument decides which rows are kept. `how="left"` keeps every row of the left table. `how="inner"` keeps only rows with a match on both sides. `how="outer"` keeps the rows of both tables. If the right table has a key more than once, each matching left row is copied once for each match, so the result can have more rows than the left table.

```python
import pandas as pd

readings = pd.DataFrame({"station_id": ["ST-02", "ST-03"], "value": [36.4, 49.3]})
stations = pd.DataFrame({"station_id": ["ST-02", "ST-02"], "zone": ["North", "North-east"]})
merged = readings.merge(stations, on="station_id", how="left")
print(len(readings), len(merged))
```

The output is `2 3`. ST-02 appears twice on the right, so its reading is copied twice. ST-03 has no match, so it keeps one row with a missing zone. No error is raised. The row count grew, and that growth is the thing to watch for. The `validate=` argument makes pandas check the relationship, and it stops the run when the check fails.

#### How it shows up in a case study

A team joins 5,000 readings to a station table to add a zone name. After the join the row count is 5,400, and the averages have moved. The station table has two rows for some stations, probably from an edited copy. The left join is doing what it was told, which is to copy each reading once per match. The decision is to add `validate="many_to_one"`, which stops the run on the duplicate station. Then the team removes the duplicate from the station table, and counts the rows again to confirm that they match the readings.

:::trap A join that does not warn
`merge` with the default settings does not raise an error when the right table has duplicate keys. The output just has more rows. Count the rows before and after the join, or pass `validate=`.
:::

```quiz
Q: A table of 100 readings is joined to a station table with how="left". Each reading should appear exactly once in the result. Which property of the station table must hold?
- It must have more columns than the readings table.
- It must be sorted by value.
* Its key column must be unique, so each reading matches at most one station row.
- It must have no missing zone names.
WHY: duplicate keys on the right copy the left row. Column count and sort order do not change the number of rows, and a missing zone name is a value, not a duplicate.

Q: An analyst merges readings onto a station list with how="inner". The result has fewer rows than the readings table. Which explanation is most likely?
- An inner join always doubles the rows.
- The merge raised an error and kept the readings.
- pandas sorted the rows and dropped the ones at the end.
* Some readings have a station_id with no match in the station list, and an inner join drops them.
WHY: an inner join keeps only the rows that match on both sides. A left join would keep every reading and leave the zone blank for the unmatched ones.

Q: You run readings.merge(stations, on="station_id", how="left", validate="many_to_one"), and the station table has two rows for ST-02. What happens?

- The ST-02 readings are dropped from the result.
```

### Timestamps, time zones and daily groups

A timestamp with a timezone is one instant. The clock time you see depends on the zone. `tz_convert` changes the zone shown without changing the instant, while `tz_localize` attaches a zone to a time that has none. The `.dt` accessor gives the date and time parts of a column. The `resample("D")` method groups time-stamped rows by calendar day, using the zone of the index.

```python
import pandas as pd

ts = pd.Series([40.0, 20.0],
               index=pd.to_datetime(["2026-03-01 20:00", "2026-03-02 07:00"], utc=True))
ist = ts.tz_convert("Asia/Kolkata")
print(ist.index[0])
print(ist.index[0].date())
print(ts.resample("D").mean())
```

The first print shows `2026-03-02 01:30:00+05:30`, because 20:00 UTC is 01:30 the next morning in India. The date is therefore `2026-03-02`. The `resample` line groups by UTC days, so the reading at 20:00 UTC falls on 2026-03-01, and the reading at 07:00 falls on 2026-03-02. Grouping by the IST date would move the first reading to the next day, which changes the daily mean.

#### How it shows up in a case study

A team computes a daily mean of PM2.5 for an Indian city report. A reading taken at 20:00 UTC on 1 March is filed under 1 March, because the grouping used UTC dates. The report is about local days in IST, and 20:00 UTC is already 01:30 on 2 March in IST. The decision is to convert the index to IST before taking the date, and to state the zone in the report heading. The stored values stay in UTC, so the instant is never changed.

:::trap Naive timestamps have no zone
A timestamp with no timezone is only a clock reading. If you call `tz_convert` on it, pandas raises an error, because it does not know which instant it is. Parse with `utc=True` on load, or use `tz_localize("UTC")` when you know the source is UTC.
:::

```quiz
- 2026-03-01, because the date does not change when the zone changes
- 2026-02-28, because IST is behind UTC
```

### Reading only the columns you need from Parquet

Column pruning means reading only the columns you name. Because Parquet stores each column in its own chunks, the reader can skip the chunks it does not need. You request the columns with the `columns=` argument of `read_parquet`. The file footer holds the schema and the position of each chunk, and the reader uses that information to skip the rest.

```python
import pandas as pd

wide = pd.read_parquet("data/clean/readings.parquet", columns=["ts_utc", "pm2_5"])
print(wide.columns.tolist())
```

The output is `['ts_utc', 'pm2_5']`. The other columns are never loaded into memory, and on disk their chunks are skipped. A CSV file has no equivalent saving. `read_csv` has a `usecols` argument, but it still has to scan the whole text file line by line, so the saving is much smaller.

#### How it shows up in a case study

A dashboard shows PM2.5 over time, and the clean file has sixty columns. Every page load takes several seconds. The chart needs only two columns, so the reader should load only those two. The other fifty-eight columns waste disk reads and memory. The decision is to pass `columns=` to `read_parquet`, check the column names printed by the code, and keep the column list in one place, so that the loader and the chart cannot drift apart.

:::trap Selecting after loading
`pd.read_parquet(path)[["ts_utc", "pm2_5"]]` reads all sixty columns first, and only then keeps two. The saving is lost. Pass `columns=` so the other chunks are never read.
:::


### Selecting rows with loc, iloc and masks

`loc` selects by label, which is the value in the index. `iloc` selects by integer position, counting from zero. A boolean mask, such as `df[df["value"] > 40]`, keeps the rows where the test is true, and it keeps their original labels. To change values, write through `loc`, as in `df.loc[mask, "value"] = 0`.

```python
import pandas as pd

df = pd.DataFrame({"value": [10, 44, 50, 60, 30, 70]}, index=[0, 1, 2, 5, 6, 7])
print(df.loc[0:2])
print(df.iloc[0:2])
print(df[df["value"] > 40])
```

`df.loc[0:2]` returns the rows with labels 0, 1 and 2, so three rows. A label slice includes both ends. `df.iloc[0:2]` returns the rows at positions 0 and 1, so two rows, because a position slice excludes its end. The mask keeps the rows whose value is above 40, which are labels 1, 2, 5 and 7, so four rows. The row with label 6 is dropped because its value is 30.

#### How it shows up in a case study

A script removes two blank rows, and the index labels become 0, 1, 2, 5, 6, 7, 8 and 9. It then takes the first five readings with `loc[0:4]` and gets only three. The reason is that `loc` uses labels, and labels 3 and 4 no longer exist. The request was for the first five rows by position, which is `iloc[:5]`. The decision is to use `iloc` when the meaning is a position, and `loc` when it is a label or a condition. After any slice, the team checks the row count against what it expects.

:::trap Chained assignment
`df[df["value"] > 40]["value"] = 0` may write to a temporary copy, so `df` stays unchanged. Use one indexing step: `df.loc[df["value"] > 40, "value"] = 0`.
:::

### What each function needs

Each function needs a few Python ideas. The examples below use fruit, books and numbers, so you can learn each idea without reading the lab's own data. Build the lab's functions yourself from these ideas.

**Dictionary counters with `get`.** The method `dict.get(key, default)` returns the stored value, or the default when the key is not there. This is how you keep a running total for each group.

```python
stock = {}
stock["apples"] = stock.get("apples", 0) + 3
stock["apples"] = stock.get("apples", 0) + 2
print(stock)
```

The output is `{'apples': 5}`. The first `get` returns `0` because the key is new. The second `get` returns `3`.

**Sorting with a key.** `sorted(items)` returns a new sorted list, and the original list is left alone. `key=` says what to compare. Sorting by pollutant or by date is the same idea.

```python
words = ["kiwi", "fig", "banana"]
print(sorted(words, key=len))
print(words)
```

The output is `['fig', 'kiwi', 'banana']`, then the original `['kiwi', 'fig', 'banana']`. The `sorted` function did not change `words`. The method `words.sort()` does change the list in place, and that matters later.

**Rounding.** `round(number, 2)` rounds to two decimal places. A decimal number gives a decimal result, and a whole number gives a whole number.

```python
print(round(7.126, 2))
print(round(7, 2))
print(round(7.0, 2))
```

The output is `7.13`, then `7`, then `7.0`. The middle line is an integer, which compares equal to `7.0` but has a different type. Round once, at the end, because rounding a running total early can change the last digit of the answer.

**Types and bool.** `isinstance(value, float)` tests the type of a value. A surprise is that `bool` is a subclass of `int`. Checking `isinstance(True, int)` returns `True`. If a function must treat booleans differently from numbers, test for `bool` before `int`.

```python
print(isinstance(True, int))
print(isinstance(True, bool))
print(isinstance(2.5, int))
```

The output is `True`, `True` and `False`. A value of `True` is also an integer, with the value 1.

**Slicing text.** `text[:7]` returns the first seven characters. Slices count from zero, and the end is excluded. This is how you take a date out of a longer timestamp.

```python
code = "BK-2024-XYZ"
print(code[:7])
print(code[3:7])
```

The output is `BK-2024`, then `2024`. The first slice keeps positions 0 to 6. The second keeps positions 3 to 6, so the last character is at position 6.

**The median.** `statistics.median(values)` returns the middle value of a sorted list. For an odd count it returns the middle item. For an even count it returns the average of the two middle items. It raises `StatisticsError` for an empty list.

```python
import statistics
print(statistics.median([10, 30, 20]))
print(statistics.median([5, 1, 9, 3]))
```

The output is `20`, then `4.0`. The second list sorted is `[1, 3, 5, 9]`, and the two middle items are 3 and 5, whose average is 4.0. Check the empty case in your own code, because a grader may call your function with no matching readings.

**Copying a list before changing it.** `list.sort()` changes the list it is called on, which is a problem if the caller still needs the original. `sorted(list)` returns a new list and leaves the original alone. A pattern that is safe for both is to build a new list and never change the input.

```python
letters = ["c", "a", "b"]
ordered = sorted(letters)
print(letters)
print(ordered)
```

The output is `['c', 'a', 'b']`, then `['a', 'b', 'c']`. The input is unchanged.

**Tuples.** A tuple is written in round brackets, such as `("pear", 3)`. Tuples and lists are not equal, even when they hold the same items. The comparison `("pear", 3) == ["pear", 3]` is `False`. Check the type of each result with the statement in mind.

**Dictionary to list of pairs.** `d.items()` gives key and value pairs. A list of those pairs can be sorted with `sorted`, and each pair can be written as a tuple.

```python
prices = {"pear": 3, "fig": 5}
pairs = [(name, cost) for name, cost in prices.items()]
print(sorted(pairs))
```

The output is `[('fig', 5), ('pear', 3)]`. The sort compares the names first, because they come first in each tuple.
