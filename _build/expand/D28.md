Every question describes a CityPulse team with a symptom or a constraint. Use the same routine on each one.

### Keeping the API key secret

**What it is.** An API key is a secret string that proves to a provider who you are. The provider uses it to decide whom to bill, and anyone who holds it can spend your money. A secret must stay out of source files, notebooks, logs and Git. Python can read a value that your terminal session holds, called an environment variable, with `os.environ`:

```python
import os
key = os.environ.get("LLM_API_KEY")
print("key set:", key is not None)
```

If the variable is set in your session, the output is `key set: True`. If it is not set, the output is `key set: False`, and the program can stop with a message. The code never contains the key itself.

Git keeps a full history of every commit. A key committed once stays in that history even after a later commit deletes it. A file named `.env` holds local values such as the key, and `.gitignore` tells Git to skip it. Logs are copies too, so print only a length or a short masked prefix.

**How it shows up in a case study.** The bulletin job runs on a laptop for testing and on a cloud server every morning. On the laptop, the key sits in a `.env` file that Git ignores. On the server, the cloud secret manager gives the same variable name to the job when it starts. A teammate suggests pasting the key into a settings file so the job runs with no setup. The right decision is to keep the key out of that file. The same code then works in both places, because only the source of the value changes, and the repository never holds the secret.

:::trap Deleting the line later is enough
Once a key has been committed, removing it in a later commit does not remove it from history. Treat the key as exposed, and replace it with a new one at the provider.
:::

### Getting structured JSON back from the model

**What it is.** Structured output means the model replies in a fixed shape that your code can read. The usual shape is JSON (JavaScript Object Notation), a text format for dictionaries, lists, strings and numbers. Your code turns JSON text into a Python dictionary with `json.loads`:

```python
import json
reply = '{"headline": "Clean air", "body": "PM2.5 is 18."}'
data = json.loads(reply)
print(data["headline"])
```

The output is `Clean air`. If the text is not valid JSON, `json.loads` raises `json.JSONDecodeError`. If a key is missing, `data["body"]` raises `KeyError`. Models sometimes wrap JSON in a Markdown code fence, which is a line of three backticks before and after the text. Your code must remove the fence before it parses the text.

**How it shows up in a case study.** The bulletin endpoint asks the model for JSON with two keys. In a test run, the reply arrives inside a fence, and the body key is missing. The page must still show something safe. The right design removes the fence, parses the text, checks the keys, retries once with a stricter instruction, and then returns a template bulletin if the retry also fails. The page never receives raw text, and the endpoint still answers. The response records which source was used, so the caller can see that the fallback was served.

:::trap Passing raw text to the page
Raw text skips parsing and the checks, so the page can break or show unverified content. Stopping the service on a parse error is the other trap, because it takes the endpoint down for every resident.
:::

```quiz

- The JSON is invalid, so the parser must be replaced
- The model is too random, so the temperature should go down
* The reply does not match the agreed key names, so the shape check should fail and move the code to the retry or template path
- The page should read headLine instead
WHY: The text parses, so the failure is in the shape check, which is the check that exists for this case. Lowering the temperature does not guarantee a key name. The tempting wrong answer is the last, because it hides a broken contract instead of catching it.

- Accept any text and show it to residents

```

### Hallucination and grounding

**What it is.** Grounding means the model may state only facts that appear in the input you gave it. A hallucination is fluent text that the input does not support, such as an invented number. The only reliable way to catch one is a check in code that compares each number in the output with the set of allowed numbers. Here is the same idea on words, so you can see the mechanism without any numbers:

```python
allowed = {"Riverside", "Monday"}
claimed = ["Riverside", "Tuesday"]
print([word for word in claimed if word not in allowed])
```

The output is `['Tuesday']`. The set holds what the input allows. The list comprehension keeps every claim that is not in the set. An empty result means nothing was invented. A set is the right tool here, because the test asks only whether a value is present.

**How it shows up in a case study.** The model writes that a ward reached a value that nobody recorded. The stats sheet has a PM2.5 mean and no AQI at all. A reviewer reads the bulletin and says it sounds right. The correct decision is that the bulletin is not grounded. The checker finds a number outside the allowed set, so the endpoint serves the template instead. The bulletin reads well, but reading well is not a test of truth, and the team does not ship it on that basis.

:::trap It reads well, so it is grounded
Fluent text can contain invented numbers. Only a check that compares every number with the facts proves that the text is grounded.
:::

```quiz
Q: The stats sheet has a PM2.5 mean of 61.2 and no AQI value. A bulletin says the mean was 61.2 and that AQI reached 180. The checker rejects the bulletin, and a manager says the checker is too strict because the bulletin reads well. What is the right answer?
* The checker is right to reject it, because 180 is not in the allowed facts, and fluent wording does not make a number true

- The checker should accept it, because only one number is wrong

WHY: Grounding applies to every number, not only the correct ones. The tempting wrong answer is the third, which accepts a bulletin with an invented number because part of it is right.

* A code check that compares every number in the bulletin with the allowed set, run on saved samples

WHY: A prompt is a request, not a proof. Only code that checks the numbers shows that they match. The tempting wrong answer is the second, which is an unverified judge that costs another call.

Q: A bulletin passes the number check, but its body says the air is clean in a ward that has no reading at all. Every number in the bulletin is allowed. What does this show?

```

### Temperature and randomness

**What it is.** Temperature is a setting that controls how much the model varies its word choice. For this API it is usually a number from 0 to 1. A low value makes the most likely next word more likely, so replies repeat and read the same way. A high value lets less likely words through, so replies vary more. The table shows the same request at three settings:

| Temperature | What you see across repeated calls |
|---|---|
| 0.0 | Nearly the same wording each time |
| 0.2 | Steady wording, with small variation |
| 1.0 | Wide variation, and more surprising word choices |

Temperature is set in the request, next to `max_tokens`. It changes the random choice of each word. It does not change what the model knows, and it does not decide whether a number is true. A low temperature is useful for steady wording, which residents and staff value, but it is not a safety control.

**How it shows up in a case study.** A teammate wants the bulletins to read the same from one day to the next, so that staff can compare them. The teammate sets the temperature to 0 and believes the bulletins can no longer contain invented numbers. The right decision keeps the low temperature for steady wording, and keeps the number checker, because only the checker can show that a number came from the stats. The course's value of 0.2 gives steady wording, and the checker handles grounding.

:::trap Temperature as a safety switch
A low temperature reduces randomness, but it does not stop the model from inventing a number. A check in code is the only proof.
:::

```quiz
Q: A team wants the bulletin wording to stay almost the same from one day to the next, so that staff can compare them. Which setting most directly serves that goal?
- A maximum output of one token
- A longer system prompt with more rules
- A larger context window
* A low temperature such as 0.2
WHY: Temperature controls how much word choice varies between calls. The tempting wrong answer is the second, because extra rules shape content, not how much the wording varies. A context window is a limit on input size, and it does not control variation.

* No, temperature changes randomness in word choice, so a number check in code is still required
- Yes, because the model stops guessing at temperature 0
- Yes, as long as the prompt also says to be accurate
- Only if the model is open source
WHY: Temperature affects how varied the wording is, not whether a fact is true. The tempting wrong answer is the second, which confuses less randomness with accuracy.

Q: Two bulletins were produced at temperature 0.2 from the same prompt. Their wording differs. One is accepted by the checker and one is rejected, because it contains a number that is not in the allowed set. What explains the result?

- The checker reads word order, and the word order changed
* The checker looks at numbers, and the rejected bulletin contains a number outside the allowed set, whatever the temperature
- The cache returned an old bulletin by mistake
WHY: The checker compares numbers. Different wording does not change its result unless a new number appears. The tempting wrong answer is the first, which treats a deterministic check as if it were random.
```

### Retrieval-augmented generation (RAG)

**What it is.** Retrieval-augmented generation, or RAG, is a pattern where your program first searches a collection of documents for passages that fit the question, then adds those passages to the prompt. The model answers from the passages rather than from memory alone. Here is retrieval in its simplest form, a keyword search in plain Python:

```python
notes = ["Parking closed on Monday.", "Air quality alert on Tuesday.", "Library open late."]
question = "air"
hits = [note for note in notes if question.lower() in note.lower()]
print(hits)
```

The output is `['Air quality alert on Tuesday.']`. Real systems use better search, often based on embeddings, which are numeric representations of meaning. The steps are the same: search, select the best passages, add them to the prompt, then ask. RAG adds moving parts, namely an index to build and keep up to date, a search that can miss the right passage, and text splitting decisions. Each one is a place where a failure can hide.

**How it shows up in a case study.** CityPulse would need RAG if it answered resident questions about hundreds of council documents, which are long and change often. The bulletin is different. Its input is a stats dictionary of a few dozen numbers, computed each day in pandas. The whole input fits in one prompt, so retrieval would add failure points without giving the model anything it does not already have. The right decision is to pass the stats directly and check the numbers in the output.

:::trap RAG makes the answer true
Retrieval improves the chance that the model sees the right source. The model can still misread a passage or invent a detail, so the output still needs a check against the source.
:::

```quiz
Q: CityPulse must answer resident questions about a 300-page council noise policy, and each answer must point to the section it came from. Which approach fits best?
- Send the whole policy with every request, without any search step
* Retrieve the most relevant sections for each question, add them to the prompt, and ask the model to answer from them
- Rely on the model's memory of council policy
- Use the daily stats dictionary as the only source
WHY: RAG suits answers that depend on a large body of text, and retrieval keeps each prompt small. The tempting wrong answer is the first, because a 300-page prompt on every request is slow and costly, and it may not fit the context window at all.

Q: The bulletin uses a stats dictionary of about thirty numbers that pandas computes each day. A teammate proposes a vector index so the model can search for the right numbers. Which reason best rejects the proposal?

- Vector indexes are not allowed by the policy

* The stats are already small, structured and computed in code, so retrieval adds failure points without adding grounding
WHY: The dictionary fits in one prompt, and the checker, not retrieval, provides grounding. The tempting wrong answer is the third, which is true but weaker, because the real problem is the added failure points.

Q: A RAG answer cites a passage about noise limits, but the answer gives a limit that does not appear in that passage. What is the correct conclusion?

- RAG has failed completely, so the feature must be switched off

WHY: A citation is a source, not a guarantee that the claim matches the source. The tempting wrong answer is the third, which assumes that a cited passage proves the claim.
```

### Context windows and max_tokens

**What it is.** A context window is the most text a model can handle in one request. The input and the output both count toward it. `max_tokens` is different: it is a cap on the output only, and it does not make the input any smaller. Here is the arithmetic, using a made-up window of 10,000 tokens for this example:

```python
window = 10000
prompt_tokens = 9800
max_tokens = 400
print(prompt_tokens + max_tokens <= window)
```

The output is `False`, because 9,800 plus 400 is 10,200, which is more than 10,000. If `max_tokens` were 200, the sum would be exactly 10,000 and the output would be `True`. Token counts also set the price, so a large input costs more on every call, even when the reply is short.

**How it shows up in a case study.** A team wants to put thirty days of hourly readings into one prompt. They set `max_tokens` to 400, hoping that this keeps the request small, and the request fails with a size error. The right decision is to measure the input from the token counts, check that the input plus the planned output fits in the window, and send a summary if it does not. Raising `max_tokens` would only make the problem worse, because the reply would need even more room.

:::trap max_tokens limits the input
The cap applies only to the reply. A long input is limited by the context window, and it is billed on every call.
:::

```quiz
Q: A developer puts a year of hourly readings into one prompt and sets max_tokens to 400 to keep the reply short. The request fails with a size error. Which statement explains the failure?
- max_tokens of 400 is too small for the input, so it should be raised to 4000

* The input plus the output must fit in the context window, and max_tokens does not shrink the input
- The API key lacks permission for large prompts
WHY: The window holds the input and the output together, and max_tokens only caps the output. The tempting wrong answer is the first, because raising the cap makes the sum larger, not smaller.

WHY: The window is a limit on tokens, so the size check comes first. The tempting wrong answer is the third, because a higher temperature changes word choice and does not make more room.

Q: A team computes the cost of each bulletin from the number of characters in the prompt, and the total is far from the provider's invoice. The replies include token counts. What is the best correction?
```

### Rate limits and backing off

**What it is.** A rate limit caps how many requests or tokens a key may use in a period. When a request goes over the limit, the provider returns an error, commonly with status 429, which means too many requests. Backing off means waiting before the next attempt, and waiting longer after each failure. The example below only prints the waits, so you can see the growth. A real program would pause for that many seconds before the next call.

```python
for attempt in range(3):
    wait = 2 ** attempt
    print("attempt", attempt, "waits", wait, "seconds")
```

The output is three lines: `attempt 0 waits 1 seconds`, then `attempt 1 waits 2 seconds`, then `attempt 2 waits 4 seconds`. The waits double each time, and the number of attempts is fixed. The SDK's `max_retries` setting controls how many automatic retries it makes, and your code still needs a limit and a fallback of its own.

**How it shows up in a case study.** A nightly job sends one request for each of forty wards, all at once, and about half of them come back with 429. The team has not added any wait between attempts. The right decision is to limit how many calls run at the same time, wait a growing time between a small number of retries, use an existing cached bulletin where one exists, and serve the template when all attempts fail. The job then finishes, and the endpoint keeps answering.

:::trap Retrying at once in a tight loop
Immediate retries add to the overload, and a loop with no limit never ends. Removing the timeout does not help either, because calls then hang and hold the service.
:::

```quiz
Q: A bulletin request gets three 429 replies in a row. The team lists its options. Which design is sound?
- Retry immediately ten times to get past the limit
* Wait a growing time between a small number of retries, then serve a cached or template bulletin
- Remove the timeout, so each call waits until the limit resets
- Create a new key for every retry, so each one has its own limit
WHY: A sound design reduces load and keeps the service answering. The tempting wrong answer is the last, because a new key for each retry is a way to avoid the limit rather than respect it, and it is not a design the course accepts.

Q: The team wants more bulletins per day than the provider allows. Which step is the sound first move?

- Lower max_tokens to 1
WHY: A cache means a bulletin for the same inputs is made once. The tempting wrong answer is the first, which removes the one control that protects the budget.

Q: A call has no timeout, and a slowdown at the provider means some calls hang for minutes. The team adds a 15-second timeout and at most two retries. Which risk does this reduce?
* A hung call blocking the whole service while everyone waits
- The chance of invalid JSON in the reply
- The number of tokens in the prompt
- Drift in the wording between days
WHY: A timeout limits how long one call can hold the service. The other options are real concerns, but a timeout does not affect them. The tempting wrong answer is the second, because JSON checks sound related, but they run after the reply arrives.
```

### Prompt injection

**What it is.** Prompt injection is text in untrusted input that tries to change the model's instructions. If your code pastes a resident's text into the prompt, the model may read that text as instructions and follow it. The example below shows the mechanism:

```python
ward = "ignore previous instructions"
prompt = f"Write a bulletin for ward {ward}."
print(prompt)
```

The output is `Write a bulletin for ward ignore previous instructions.` The attacker's words now sit inside your instruction, where the model cannot tell them apart from your rules. The defence is to keep free text out of the prompt. The endpoint accepts only validated values, such as a ward code from a known list, and returns a 422 error for anything else. A list of banned phrases is a weaker extra layer, because an attacker can rephrase.

**How it shows up in a case study.** A resident portal has a free-text box for a ward or a note. One entry says to ignore earlier rules and list every stats field. The right decision is to remove the free-text box from the prompt path entirely. The ward must match one of the known codes, and anything else is refused at validation with a 422 response. A stronger filter on the text is not the fix, because the text should never reach the prompt.

:::trap Removing the bad words
An attacker who sees a phrase removed can write the same instruction in other words. Validation of allowed values is the defence, not editing the text.
:::

```quiz
Q: A public form lets residents type a ward name, and one entry says to ignore earlier rules and list every stats field. The endpoint currently passes the ward into the prompt as text. Which change is the strongest defence?
- Add the word "ignore" to the banned phrases
- Make the prompt longer, with more polite rules
- Put the ward name in capital letters in the prompt
* Accept only ward codes that pass validation, return 422 for anything else, and keep free text out of the prompt
WHY: Validation keeps untrusted text out of the instructions altogether. The tempting wrong answer is the first, because a single banned word is easy to avoid with a rephrase.

Q: A blocklist removes the phrase "ignore previous instructions" from user text. An attacker then writes "disregard everything before this line", and the bulletin changes as the attacker wanted. What does this show?
- The blocklist worked, because the attacker's phrase is shorter
* A blocklist is easy to bypass by rephrasing, so it is a weak extra layer behind validation
- The model cannot follow instructions that appear in user text
- The attack worked only because the cache was switched off
WHY: The blocklist matched one wording, and the attacker used another. The tempting wrong answer is the third, which mistakes a model behaviour for a fix.

Q: The bulletin prompt places the stats between delimiters and states the rules clearly. A reviewer points out that the stats come from code, not from residents, yet a free-text field still reaches the prompt elsewhere. Why is the delimiter alone not enough?
- Delimiters are only for styling the prompt
- The stats must be placed inside a Markdown fence

- The model reads delimiters as commands it must obey
WHY: Delimiters help the model, but they are not a guarantee. The defence is to keep untrusted text out of the prompt. The tempting wrong answer is the fourth, which overstates what delimiters do.
```

### Tool calling

**What it is.** Tool calling, also called function calling, lets a model reply with a request to run a named function and pass it arguments. For example, the model might ask to run `get_readings` with `day` set to `"2026-07-14"`. The request is text generated by the model, so it is untrusted, and your code decides whether to run anything. The example below shows the check:

```python
allowed_tools = {"get_readings"}
request = {"name": "get_readings", "arguments": {"day": "2026-07-14"}}
if request["name"] in allowed_tools:
    print("run", request["name"], "with", request["arguments"]["day"])
```

The output is `run get_readings with 2026-07-14`. The allowlist is a set of the only names your code will run. If the name is not in the set, nothing runs. Arguments need the same care, so your code must check their type, format and range before it calls anything.

**How it shows up in a case study.** A chat assistant for residents lets the model call tools. The model proposes a tool named delete_readings for the day's data. The team has one read-only tool, get_readings. The right decision is to reject the request, because the name is not on the allowlist, and return a safe message to the resident. The decision does not depend on how often the model asks. A repeated request is still an unchecked request.

:::trap The model asked, so it runs
The model's request is output, and injected text can shape it. Check the name and the arguments in your own code before anything runs.
:::

```quiz
Q: A resident chat assistant lets the model call tools. The model asks to run delete_readings for 2026-07-14. The only tool the team allows is get_readings. What should the code do?
* Reject the request, because the name is not on the allowlist, and return a safe message to the resident
- Run it, because the model is trusted to choose tools
- Run it only if the same request appears twice
- Pass it to the bulletin page so that staff can see it
WHY: The allowlist decides what may run, and the model's request does not change that. The tempting wrong answer is the third, which treats repetition as if it were validation.

* Check the arguments in code, including the date format and that the date really exists, before the call runs

Q: A developer proposes that the model chooses which tool to run, and that the code runs the choice without checks, because the functions are in the team's own codebase. Which statement is correct?

```

### Evaluating LLM output with tests

**What it is.** Evaluation means measuring the quality of output with evidence that you can repeat. For this course that means offline tests on saved inputs, so the same test gives the same result every time. A test is a function whose name starts with `test_` and that uses `assert` to check a result. Here is the idea with a plain check on text:

```python
def bulletin_mentions_pm25(text):
    return "PM2.5" in text

assert bulletin_mentions_pm25("PM2.5 is 82.")
assert not bulletin_mentions_pm25("The air is clean.")
```

Both asserts pass, so the program prints nothing. A failed assert stops the program with an error that shows the line. Real tests of a model replace the model call with a stub, which is a fake function that returns a saved reply, so that no network or key is needed. Cost is evaluated from the saved token counts, multiplied by the published price.

**How it shows up in a case study.** A teammate changes the wording of the bulletin prompt and says the new version is better, because three bulletins read well. The right decision is that reading three outputs is not repeatable evidence. The team runs offline pytest tests on saved fixtures that check the JSON shape, the numbers and the banned phrases, with the model call replaced by a stub. Continuous integration then runs the same tests on every change, without an API key.

:::trap Asking a second model to grade the first
A judge model is itself unverified and costs another call. Use code checks where you can, and test the judge on cases with known answers before you trust it.
:::

## The graded lab

### The task in plain words

**The scenario.** A CityPulse assistant answers air-quality questions by asking a language model for a reply. Before a reply reaches a resident, your code must flag any number the model invented, and it must remove personal details from the text. You write four functions in one file, using only the standard library. The starter file already names them, so keep the names exactly as they are and fill in the bodies.

Each function, with its rules, is below.

- `extract_numbers(text: str) -> list[float]` takes a text and returns every integer or decimal in it, as floats, in the order they appear.
  - Each number is returned as a float, so the integer 95 becomes 95.0.
  - A number that appears twice is returned twice. The statement asks for every number in order, not for unique values.
  - A full stop at the end of a sentence is not a decimal point. In the statement's example, "station 7." ends the sentence, so the number is 7.0.
  - The statement does not mention minus signs. Do not add special handling for them unless a visible test shows that you must.
- `unsupported_numbers(answer: str, allowed: list) -> list[float]` returns the numbers in `answer` that are not in `allowed`, which is the list of facts the model was given.
  - The result is sorted from smallest to largest.
  - Each value appears once, even if it appears several times in the answer.
  - The values are floats.
  - The statement's example is `unsupported_numbers("The AQI was 95 at station 7.", [42, 7])`, which returns `[95.0]`. The 7 is allowed, so it is not reported.
- `is_grounded(answer: str, allowed: list) -> bool` returns True if `unsupported_numbers` finds nothing, and False otherwise. It returns a bool, not a list.
- `redact_pii(text: str) -> str` returns the text with two kinds of change.
  - Every email address is replaced with `[EMAIL]`.
  - Every phone number in the form ddd-ddd-dddd is replaced with `[PHONE]`. The separator between the groups may be a dash, a dot, or nothing at all.
  - Emails are redacted before phones.
  - The statement's example is `redact_pii("contact me at jo@airteam.io or 555-123-4567")`, which returns `'contact me at [EMAIL] or [PHONE]'`.

**Limits.** Each run may take 30 seconds and use 128 MB. A regular-expression solution is far inside both limits, so they matter only if your code does something very slow.

**Scoring.** The visible tests are five checks, worth a total of 75 points.

| Visible test | Points |
|---|---|
| Every number is grounded in the facts | 15 |
| 95 is not in the allowed facts (hallucinated) | 20 |
| Grounded answer | 10 |
| Ungrounded answer | 10 |
| Redact an email and a dashed phone | 20 |

The hidden tests are three automated checks worth 25 points together. You cannot see their inputs. They try cases the visible tests do not cover, such as empty text, repeated numbers, an email that contains digits, or a phone number written without separators. Hidden tests decide the top marks because a solution that only fits the visible examples can score 75 and no more. Read the rules in the list above as the specification for those hidden cases.

### What each function needs

Each idea below is taught with a small example that has nothing to do with the lab's data. Work out the lab's functions yourself from the rules.

- **Finding every match.** `re.findall` returns every match of a pattern as a list of strings. `re.findall(r"[a-z]+", "tea, milk and 2 eggs")` returns `['tea', 'milk', 'and', 'eggs']`. The pattern `[a-z]+` means one or more lowercase letters, so the 2 is skipped.
- **Matching a real dot.** In a pattern, a plain dot matches any character. To match a real dot, write `\.`. `re.findall(r"\d\.\d", "3.5 and 3x5")` returns `['3.5']`, because the x is not a dot.
- **Converting to float.** `float("4")` returns `4.0`, and `float("0.5")` returns `0.5`. The result is always a float, even for a whole number.
- **Unique and sorted.** `set` keeps one copy of each value, and `sorted` puts a list in order. `sorted(set(["pear", "fig", "pear"]))` returns `['fig', 'pear']`. Numbers sort by size, so `sorted([2.5, -1.0, 2.5])` returns `[-1.0, 2.5, 2.5]`.
- **Membership across types.** `2 in [1, 2.0]` returns `True`, because 2 and 2.0 are equal in Python. `"2" in [1, 2.0]` returns `False`, because text is never equal to a number.
- **Booleans and integers.** `isinstance(3, int)` returns `True`. `isinstance(True, int)` also returns `True`, because `bool` is a subclass of `int`, so True counts as 1 in arithmetic. This matters only if you check types, and the statement does not ask for that. Use it as background, not as a rule.
- **Returning a bool.** A comparison already gives a bool. `len([]) == 0` returns `True`, so a function can return the comparison directly instead of using an if.
- **Replacing matches.** `re.sub` replaces every match with a new string. `re.sub(r"[aeiou]", "*", "tea")` returns `t**`.
- **Order of replacements.** The order of two replacements can change the result. `re.sub(r"b", "c", re.sub(r"a", "bb", "a"))` returns `'cc'`, because the first replacement creates new b letters that the second one changes. Swapping the order gives `'bb'`.
- **Empty input.** `re.findall(r"\d+", "")` returns `[]`, and `"".split()` returns `[]`. Empty text should give an empty result, not an error.

### The rules people miss

Each row below is a rule taken from the statement. The last column is an assert line you can write yourself. It checks the rule against the statement's own wording, so the answer is clear.

| Rule in the statement | What a careless solution does | How to check yours |

### Worked twin problem

The problem below is a different domain, a library loan desk, but it needs the same skills: finding patterns in text, sets, a sorted unique result, a bool, and replacing matches.

**Scenario.** A library prints an overdue notice that lists book barcodes and fines. Before the notice is printed, the desk must find the barcodes the notice names that are not on the loan list, and hide the fine amounts from the printed copy.

Implement four module-level functions, using only the standard library.

- `barcodes_in(text: str) -> list[str]` returns every barcode in the text, in order of appearance. A barcode is the letters LIB followed by exactly six digits, as a whole word. A repeated barcode is returned each time it appears.
- `missing_barcodes(notice: str, loans: list) -> list[str]` returns the sorted unique barcodes that appear in the notice and are not in `loans`.
- `all_on_loan(notice: str, loans: list) -> bool` returns True if `missing_barcodes` gives an empty list, and False otherwise.
- `mask_fines(text: str) -> str` replaces every dollar amount, such as `$3` or `$12.50`, with `[AMOUNT]`. A dollar amount is a dollar sign, one or more digits, and optionally a dot followed by exactly two digits.

Example: `barcodes_in("Items LIB004521 and LIB000007.")` returns `['LIB004521', 'LIB000007']`, and `mask_fines("Fine $12.50 for one day.")` returns `'Fine [AMOUNT] for one day.'`

The solution and its checks:

```python test
import re

BARCODE_RE = re.compile(r"\bLIB\d{6}\b")
AMOUNT_RE = re.compile(r"\$\d+(?:\.\d{2})?")


def barcodes_in(text):
    return BARCODE_RE.findall(text)


def missing_barcodes(notice, loans):
    on_loan = set(loans)
    found = set(barcodes_in(notice))
    return sorted(code for code in found if code not in on_loan)


def all_on_loan(notice, loans):
    return missing_barcodes(notice, loans) == []


def mask_fines(text):
    return AMOUNT_RE.sub("[AMOUNT]", text)


assert barcodes_in("Items LIB004521 and LIB000007.") == ["LIB004521", "LIB000007"]
assert barcodes_in("LIB004521 then LIB004521") == ["LIB004521", "LIB004521"]
assert barcodes_in("LIB12345 is too short") == []
assert barcodes_in("LIB0045210 is too long") == []
assert barcodes_in("") == []
assert missing_barcodes("LIB900001 LIB100002 LIB900001", ["LIB100002"]) == ["LIB900001"]
assert missing_barcodes("LIB900001 LIB100002", []) == ["LIB100002", "LIB900001"]
assert missing_barcodes("no codes", []) == []
loans = ["LIB000007"]
missing_barcodes("LIB000007 LIB000008", loans)
assert loans == ["LIB000007"]
assert all_on_loan("LIB000007 is due", ["LIB000007"]) is True
assert all_on_loan("LIB000007 is due", []) is False
assert all_on_loan("no codes here", []) is True
assert mask_fines("Fine $12.50 and $3 today.") == "Fine [AMOUNT] and [AMOUNT] today."
assert mask_fines("no money") == "no money"
assert mask_fines("$100.00") == "[AMOUNT]"
```

Line by line:

- `import re` loads the regular-expression module. It is the only module the solution uses.
- `BARCODE_RE = re.compile(r"\bLIB\d{6}\b")` builds the pattern once. `LIB` matches those letters. `\d{6}` matches exactly six digits. The `\b` on each side is a word boundary, so the match cannot start or end inside a longer run of letters or digits. That is why `LIB0045210` is rejected.
- `AMOUNT_RE = re.compile(r"\$\d+(?:\.\d{2})?")` matches a dollar sign, one or more digits, and an optional dot with exactly two digits. The backslash makes the dollar sign a literal character, because a bare `$` means the end of the text in a pattern.
- `barcodes_in` returns `BARCODE_RE.findall(text)`. The result is a list of strings, in order, with repeats kept. Empty text gives an empty list.
- `missing_barcodes` first builds `on_loan` as a set, so each membership test is quick. `found` holds the barcodes from the notice with repeats removed. The return line keeps the codes not on loan and sorts them. Strings sort character by character, which is why `LIB100002` comes before `LIB900001`. The `loans` list is only read, never changed.
- `all_on_loan` compares the missing list with an empty list. The comparison already gives True or False, so the function returns a bool.
- `mask_fines` calls `AMOUNT_RE.sub`, which replaces each match with `[AMOUNT]`. Text with no dollar amount comes back unchanged.
- The `assert` lines are the tests. Each one checks a single rule. They pass silently when the code is correct.

The trickiest function is `missing_barcodes`, because it combines a set, a filter and a sort. The trace below follows the same idea on a short list. It uses `split()` to keep the example small, while the real function uses `barcodes_in`.


### Your turn

**Scenario.** A bakery's till totals each order and lists its cheapest items. This is a new problem, so write the two functions yourself.

- `order_total(prices: list) -> float` returns the sum of the prices, rounded to two decimal places at the end. An empty list gives 0.0.
- `cheapest(menu: dict, n: int) -> list[str]` returns the names of the n cheapest items, cheapest first. Items with the same price are listed in alphabetical order. If n is larger than the menu, return every name. The menu must not change.

Make these asserts pass:

```python

assert order_total([0.1, 0.2]) == 0.3
```

:::answer Show a solution
The solution sums first and rounds once, at the end. It sorts the names by a key that holds the price and then the name, so ties fall back to alphabetical order. Slicing with `[:n]` gives the first n names, and a slice larger than the list returns all of them.

```python test
def order_total(prices):
    return round(float(sum(prices)), 2)


def cheapest(menu, n):
    names = sorted(menu, key=lambda name: (menu[name], name))
    return names[:n]


assert order_total([]) == 0.0
assert order_total([1.10, 2.20]) == 3.3
assert order_total([0.1, 0.2]) == 0.3
assert cheapest({"bun": 2.0, "tart": 1.5, "cake": 1.5}, 2) == ["cake", "tart"]
assert cheapest({"bun": 2.0}, 5) == ["bun"]
assert cheapest({"bun": 2.0, "tart": 1.5}, 0) == []
menu = {"bun": 2.0}
cheapest(menu, 1)
assert menu == {"bun": 2.0}
```
:::
