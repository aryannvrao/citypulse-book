## What the quiz tests

The Day Quiz has ten case-study multiple-choice questions on today's topics, with one question on each topic. Each question gives you a short scenario about a CityPulse team, a dataset or a model, then asks one question about it. The pass mark is 70 per cent. Only your first attempt is kept for your skill score, so read every question slowly the first time you see it.

Use the same method for every case-study question.

1. Read the last line first. It tells you what is being asked: a decision, a number, a verdict or a cause. Knowing this before you read the scenario stops you answering a different question.
2. Read the scenario again and underline the facts that matter. Look for the split method, the dates, the metric, the baseline, the features and the size of each data set. Ignore decoration.
3. Eliminate options that are true in general but do not fix this scenario. "Accuracy can be misleading" is a true sentence, but it may not explain why this team's model failed.
4. Watch three words. "Most" means the option that covers the largest share of cases, not every case. "First" means the earliest step in a process. "Best" means the best option given the constraints in this scenario.
5. Choose, then check the scenario once more against your choice.

The rest of this section takes the nine topics in order. Each one explains the idea from zero, shows how it appears in a case study, names the trap an examiner sets, and gives practice questions. Read the WHY line after every answer, even when you were right, because the wrong options are the ones you will meet in the real paper.

### Splitting rows into training and test sets

**What it is**

A machine learning model learns from some rows and is then checked on rows it has not seen. The rows used for learning are the **training set**. The rows held back for the final check are the **test set**. Many projects also keep a **validation set**, which helps you choose settings such as the depth of a tree.

Why hold rows back at all? A model scored on the rows it learned from looks better than it really is, because it has partly memorised them. The test set stands in for the future: data the model could not have seen when it was built.

Splitting by position is the simplest split. The code below holds eight daily readings, oldest first, and keeps the newest two for testing.

```
temps = [12, 15, 14, 18, 21, 19, 17, 16]
test_size = int(len(temps) * 0.25)   # 2
cut = len(temps) - test_size         # 6
train, test = temps[:cut], temps[cut:]
print(train)
print(test)
```

Output:

```
[12, 15, 14, 18, 21, 19]
[17, 16]
```

Line by line. `len(temps)` counts the eight readings. Multiplying by 0.25 gives 2.0, and `int` drops the decimal part, so `test_size` is 2. `cut` is the position where the test rows start, counting from 0. `temps[:cut]` keeps positions 0 to 5, and `temps[cut:]` keeps the last two. Slicing never changes the order, so the test rows are the newest readings. The line `train, test = ...` stores both slices at once. The two `print` lines show the results.

**How it shows up in a case study**

A ward team builds a model that forecasts tomorrow's noise level from a year of hourly readings. Their notebook shuffles the rows, splits them 80/20 and reports a very good test score. The analyst's reasoning is that shuffling mixes January with December, so the model has learned from days that come after many of the test rows. In use, the model will only ever see the past. The split must therefore follow the calendar: train on the earlier months, test on the later ones, and leave a gap day at the boundary. The good score is a warning, not a result.

:::trap Blaming the randomness
A random split is not wrong because it is random. It is wrong for time-ordered data, because it lets the training rows sit on both sides of the test rows. In your answer, say that the test set must be the newest rows, not "a random 20 per cent".
:::

```quiz
Q: A sensor team has two weeks of readings every ten minutes. Their script keeps every fifth row for testing and uses the rest for training. Which concern matters most when the goal is to forecast the next hour?
- The test set is too small to be useful
- Ten-minute readings should not be used for regression
* Every fifth row is spread across the whole fortnight, so training rows include readings from after many test rows
- The model needs a larger random seed
WHY: Taking every fifth row is a disguised random split across time, so the model trains on readings that come later than some tested ones. The size of the test set is not the main problem, and the random seed only makes the choice repeatable. It does not make the choice correct.

Q: A team splits daily rainfall records by year. Training is 2019 to 2023 and testing is 2024. There is no gap at the boundary. Which risk is most relevant?
* The last training target can be the first test day's value, so a value from the test period leaks into training at the boundary
- Five years of training data always causes overfitting
- Years cannot be used to split data, only months can
- The test year must be chosen at random or the metric is invalid
WHY: With daily data, the target for 31 December 2023 is the value for 1 January 2024, which belongs to the test period. A gap day at the boundary stops that. The overfitting option is false, since more years of data does not cause overfitting by itself. The random-test option is the trap that this topic is built around.

Q: A student writes this rule: training rows are dated before 1 March, and test rows are dated 1 March or later. A reviewer asks for one change to protect against a boundary leak. Which change does that most directly?
- Shuffle the rows inside each part
- Raise the test fraction to 30 per cent
- Set the random seed to 0 for both parts
* Drop one boundary day, such as 29 February, so that the last training target cannot be the first test input
WHY: The gap day is the fix named for this problem. Shuffling makes the leak worse, not better. Changing the test fraction or the seed does not change which days sit on each side of the boundary.
```

### Beating a baseline

**What it is**

A **baseline** is the simplest reasonable prediction. You compute it on the same rows as your model and score it with the same metric. If your model cannot beat the baseline, it has shown no skill, however small its error looks.

For air quality, the common baseline is **persistence**: tomorrow's value is predicted to equal today's value. The table below uses four days. Each row's guess is the value from the row above it.

| Day | Today | Tomorrow (actual) | Persistence guess | Gap |
|---|---|---|---|---|
| 1 | 30 | 32 | 30 | 2 |
| 2 | 32 | 35 | 32 | 3 |
| 3 | 35 | 33 | 35 | 2 |
| 4 | 33 | 36 | 33 | 3 |

The gaps are 2, 3, 2 and 3. Their average is 2.5, so persistence has an average gap of 2.5 on these four days. Any model you build for the same four days must average a smaller gap to be worth using. A second baseline, **seasonal-naive**, predicts tomorrow as the value one week earlier, on the same weekday.

**How it shows up in a case study**

A team reports that its model has an average error of 4.1 units on the test rows. The lead asks whether that is good. The analyst computes persistence on the same rows and gets 3.9. Her reasoning is that skill is the comparison, not the raw error. On these rows, copying today's value does slightly better, so the model has no demonstrated skill here. She reports that result plainly, with both numbers and the row count.

:::trap A small number with no comparison
An error of 4 sounds good until you learn that yesterday's value gives 3.9. A small error is only evidence of skill when the baseline's error on the same rows is larger.
:::

```quiz
Q: A model has R-squared 0.45 on the test rows. Its average error is 5.8 and the seasonal-naive baseline's average error is 6.2 on the same rows. The team says the model is clearly better. What is the most accurate verdict?
- The model is clearly better, because its R-squared is positive
* The model is better by a small margin on these rows, and the report must show that margin next to the baseline
- The baseline is better, because seasonal values are always more accurate
- The comparison cannot be made, because the baseline has no features
WHY: Both scores come from the same rows, so the comparison is fair. The gap of 0.4 is small, and the report should say so. A positive R-squared does not show that the model beats a baseline. The tempting wrong answer treats any positive score as a win.

Q: A flood-warning team computes a persistence baseline on the training rows and places it next to the model's test score. Which correction is needed?
- Use a higher fraction of rows for the baseline
- Compute persistence on the validation rows only
- Report only the model's score, to keep the report short
* Compute the baseline on the same test rows as the model and score both with the same metric
WHY: A baseline is comparable only when both are scored on identical rows with the same metric. A different fraction or a different subset of rows breaks that comparison, and hiding the baseline is the failure the lesson warns against.

Q: A student's model has a test error of 2.0. A naive model that always predicts the training mean has a test error of 2.4 on the same rows. Her supervisor calls the model "not impressive". What is the correct statement?
* The model beat the naive mean on these rows by 0.4, and before claiming skill she should also check a stronger baseline
- The model is useless, because 2.0 is not zero
- The naive model is better, because it is simpler
- Two errors on different scales can never be compared
WHY: The naive mean is a valid baseline on the same rows, so the model is better than it by 0.4. Claiming skill still needs a stronger baseline such as persistence, which is the check the supervisor is missing. The tempting wrong answer treats zero as the only good error, which is not a fair test.
```

### Choosing a regression metric

**What it is**

A **regression** model predicts a number, such as tomorrow's pollution level. A **metric** turns a list of errors into one number. Each metric answers a different question, so the choice matters.

The table below shows three days of forecasts.

| Day | Actual | Forecast | Error |
|---|---|---|---|
| Mon | 40 | 38 | 2 |
| Tue | 42 | 47 | 5 |
| Wed | 39 | 39 | 0 |

The **mean absolute error** averages the sizes of the errors, ignoring the sign. Here it is (2 + 5 + 0) divided by 3, which is 2.33 in the target's own units. It is the easiest metric to explain. The **root mean squared error** squares each error, averages the squares and then takes the square root. Large misses count for more. Here the squares are 4, 25 and 0, their mean is 9.67, and its square root is 3.11. The **R-squared** compares the model's squared errors with the squared spread of the actual values around their mean. It has no units, and it is covered in its own topic below.

The metric must be chosen, and written down, before the test rows are scored. Changing it afterwards is the error that examiners look for.

**How it shows up in a case study**

A council wants next-day pollution forecasts that officers can explain. A team proposes the mean absolute error as the headline, because it is in the same units as the readings. They also note that one very large miss could hide a dangerous day, so they add the root mean squared error beside it. They commit both metrics in the project log before the test rows are scored. The reasoning is that the metric should match the harm, and the decision should be made before the result is known.

:::trap Comparing numbers with different units
A mean absolute error of 8 in µg/m³ and an error of 8 in degrees cannot be compared, even though both are "8". Compare metrics only for the same target, with the same units, on the same rows.
:::

```quiz
Q: A team predicts daily PM2.5 for a ward office. Officers want one headline number they can explain, in the same unit as the readings. Which metric suits that headline best?
- R-squared, because it always lies between 0 and 1
- Precision, because it measures how many alarms were real
- Recall, because it measures how many events were caught
* The mean absolute error in µg/m³, because it is in the readings' own unit and is easy to explain
WHY: The mean absolute error is an average error in the target's own unit, so an officer can read it directly. R-squared has no unit, and precision and recall are classification measures. The tempting wrong answer is R-squared, which is common in textbooks but harder for officers to use.

Q: Two forecasters have the same mean absolute error of 3.0 on the same test days. Officers worry about occasional very large misses that could hide a dangerous day. Which additional measure should be reported?
- Recall, because it counts missed events
* The root mean squared error, because squaring gives large misses more weight, so it shows whether one forecaster makes occasional big misses
- Accuracy, because it counts the days that were right
- Nothing, because equal averages mean equal models
WHY: Equal averages can hide one large miss, and the root mean squared error reveals it. Recall and accuracy are classification measures and do not apply to a numeric forecast. The tempting wrong answer assumes equal averages mean equal models.

Q: A team scored its model's root mean squared error on the test rows. After seeing the value, they prefer R-squared and want to report that instead. What should happen?
- Report R-squared, because a metric chosen after results is acceptable
- Drop the test rows and report the training score
* Report the change openly, label the result as exploratory, and commit one metric in the log before any further test scoring
- Switch to the mean absolute error, because it is the default metric
WHY: Choosing a metric after seeing the test result makes the test score optimistic, so the change must be disclosed and the test result labelled. Dropping rows or switching to a different default still hides the problem.
```

### Scoring rare events

**What it is**

A **rare event** is one that happens on few days, such as a flood. When the rare class is very small, **accuracy** misleads. A model that never predicts the rare event can still be right on almost every day.

Three counts make this clear. A **true alarm** is a predicted event that really happens. A **false alarm** is a predicted event that does not happen. A **missed event** is a real event the model did not predict. The two measures use these counts:

- **Precision** is the share of alarms that were real: true alarms divided by all alarms.
- **Recall** is the share of real events that were caught: true alarms divided by all real events.

Take a year with 1,000 days, 3 of them flood days, and a model that never raises an alarm. It is right on 997 days, so its accuracy is 99.7 per cent. Its recall for floods is 0 out of 3, which is zero. Its precision cannot be computed, because it made no alarms at all. Accuracy looked excellent and the model is useless for warnings.

**How it shows up in a case study**

A flood-warning pilot reports that its model is "very accurate". The team lead asks what it misses. The analyst reasons that the flood class is rare, so accuracy is the wrong headline. She reports recall for flood days, which shows the missed floods, and precision, which shows the false alarms. She writes both counts and both measures in the log, so that officers can judge the cost of each kind of error.

:::trap Accuracy as the headline
A high accuracy on a rare-event problem can mean the model catches nothing. Always check recall for the rare class before trusting a high accuracy.
:::

```quiz
Q: A river gauge records a flood on 4 days out of 365. A model predicts "no flood" on every day. The team's slide says the model is 98.9 per cent accurate. What is the best response?
* Accuracy hides that every flood was missed, so recall for flood days is zero and the model is useless for warnings
- The slide is correct, because 98.9 per cent is an excellent score
- The model should be scored with the mean absolute error instead
- Precision shows the model is perfect, because it never raised a false alarm
WHY: The model is right on 361 of 365 days, but it caught none of the 4 floods, so recall is zero. A model that never raises an alarm has no false alarms, which is not the same as being good. The tempting wrong answer treats high accuracy as the right headline.

Q: A model raises 10 flood alarms in a month. Four of them are real floods. The month had 6 real floods in total. Which pair of numbers is correct?
- Precision 40 per cent, recall 40 per cent
- Precision 60 per cent, recall 60 per cent
- Precision 4 per cent, recall 6 per cent
* Precision 40 per cent, recall about 67 per cent
WHY: Precision is the 4 real alarms out of 10 alarms, which is 40 per cent. Recall is the 4 caught floods out of 6 real floods, which is about 67 per cent. The two denominators differ, so the two values differ. The tempting wrong answer assumes the two measures must match.

Q: Rule 1 misses 1 real flood in 10 but raises 50 false alarms a month. Rule 2 misses 3 real floods but raises 5 false alarms. The ward manager says missed floods are dangerous and false alarms waste officer time. What is the most defensible starting point?
- Choose rule 1, because it has fewer misses, and ignore the false alarms
* Write down both costs first, then choose the rule whose misses and false alarms the ward can accept, and report recall and precision for each
- Choose rule 2, because it has fewer false alarms, so accuracy must be higher
- Pick whichever rule has more true alarms
WHY: Both rules trade misses against false alarms, so the decision needs the costs, which the lesson asks you to write down before choosing. Ignoring false alarms is the tempting wrong answer, because they have a real cost in officer time.
```

### Root mean squared error

**What it is**

The **root mean squared error** is the square root of the average squared error. It is worked out in three steps: square each error, average the squares, then take the square root at the end.

Squaring makes large errors count for much more than small ones. Take the errors 3 and 4. Their squares are 9 and 16. Their average is 12.5. The square root of 12.5 is about 3.54. The answer is in the same unit as the target, because the root undoes the squaring. If you forgot the final root, the result would be in squared units, which is not a unit anyone can read off a chart.

Two models can have the same average error and different root mean squared errors. Errors of 2, 2, 2 and 2 give a root mean squared error of 2. Errors of 1, 1, 1 and 5 give an average of 2 too, but a larger root mean squared error, because the single error of 5 dominates the squares. The root mean squared error tells you whether a model makes occasional large misses.

**How it shows up in a case study**

A team's new model has the same average error as the old rule, but its root mean squared error is higher. Officers ask why. The analyst reasons that the new model must have a few very large misses, which the average hides. She checks the largest errors on the test rows and finds one day with a very large miss. She reports the average and the root mean squared error together, and recommends the old rule for alerts until the large misses are explained.

:::trap Forgetting the final root, or rooting too early
Taking the square root of each error before averaging, or averaging the squares and forgetting the final root, both give numbers in the wrong unit. The root goes last.
:::

```quiz
Q: Errors on four test days are 2, 2, 2 and 10. A colleague says the root mean squared error is about 2, because the typical error is 2. What is the correct response?
- The colleague is right, because the typical error is the most common value
- The colleague is right if the errors are rounded first
* The colleague ignores the large miss: the squares are 4, 4, 4 and 100, and the root of their mean is about 5.3, well above 2
- The root mean squared error cannot be computed when one error is much larger than the others
WHY: The squares add up to 112, their mean is 28, and the square root of 28 is about 5.3. A typical error is not the same as the root mean squared error, which is pulled up by the single large miss. The tempting wrong answer confuses the most common error with the metric.

Q: A student computes the root mean squared error by squaring each error, averaging the squares and reporting that average, with no root. The report then shows squared units. Which correction is needed?
* Take the square root of the mean of the squared errors, so the result is back in the target's unit
- Divide the total by the count twice
- Take the absolute value of each error before squaring it
- Round each squared error to a whole number first
WHY: The square root restores the unit. Taking absolute values before squaring is unnecessary, because squaring already removes the sign. Rounding the squares early adds error and does not fix the unit.

Q: Two models both have an average absolute error of 4.0 on the same five test days. Model P's errors are all 4. Model Q's errors are 12, 2, 2, 2 and 2. Which model has the higher root mean squared error, and why?
- Model P, because its errors are equal
- Both are equal, because their averages match
- Neither can be compared, because the metric is different
* Model Q, because its squared error of 144 pulls the mean of the squares up, so its root is larger
WHY: Model P's squares are all 16, so its root is 4.0. Model Q's squares are 144, 4, 4, 4 and 4, with a mean of 32, so its root is about 5.7. The equal averages hide the single large miss. The tempting wrong answer treats equal averages as equal models.
```

### Temporal leakage

**What it is**

**Leakage** happens when a model learns from information that will not be available when it makes a real prediction. The model then looks excellent in testing and fails in use. In time series, leakage usually comes from one of three places: a feature that reads future rows, a random split, or preprocessing that was fitted on all the data, including the test rows.

The simplest check is the **availability time**: the moment when each feature's value becomes known. For a prediction made at the end of today, a feature may use today and earlier days. It may not use tomorrow.

The table below uses four days of temperatures, 20, 22, 25 and 21, and two features for day 2.

| Feature for day 2 | Rows it reads | Known at end of day 2? | Value |
|---|---|---|---|
| Average of days 1 and 2 | Days 1 and 2 | Yes | 21.0 |
| Average of days 1 and 3 | Days 1 and 3 | No, day 3 is in the future | 22.5 |

The second feature is leaky because it reads day 3, which is the value the model is trying to predict. The SQL below shows how such a feature is written by mistake.

```sql
SELECT day,
       AVG(temp) OVER (ORDER BY day ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING) AS leaky
FROM readings;
```

The frame reads one row back and one row forward, so each output row averages tomorrow's value into today's feature. A frame that ends at `CURRENT ROW` is safe for features.

**How it shows up in a case study**

A team adds a feature called "average PM2.5 over the three days centred on today". Their test score improves far beyond the baseline, and an officer doubts it. The analyst reasons that a centred window reads tomorrow's value, which does not exist at prediction time. The large jump is a warning sign, not a success. She removes the forward-reading part of the window and checks the score again.

:::trap A reasonable-sounding name
A feature called "average of today and the next day" sounds harmless. Its name says nothing about when its values become known. Always check the rows it reads.
:::

```quiz
Q: A team predicts tomorrow's PM2.5 using the feature "average PM2.5 over the three days centred on today", which covers yesterday, today and tomorrow. The test score is far better than the baseline, and officers doubt it. What is the most likely cause?
- The team used too few trees in the model
* The feature reads tomorrow's value, which is unknown at prediction time, so it leaks the target
- The baseline is wrong, so the model must be correct
- The test set is too large to be reliable
WHY: The centred window includes tomorrow, which is the target's own day, so the feature leaks the answer. The number of trees and the size of the test set do not create a leak. The tempting wrong answer treats a big jump in score as proof of a good model.

Q: Which feature is safe for predicting tomorrow's value, made at the end of today?
- The wind speed recorded tomorrow
- The average of today and the next two days
- The target column, copied into the feature table
* The sensor reading taken at 18:00 today, which exists before the prediction is made
WHY: The safe feature uses only rows available at the prediction time. The other options each read tomorrow or later, or copy the answer itself. The tempting wrong answer is the wind speed, because it sounds like a useful weather input.

Q: A team adds the feature "number of flood alerts issued during the following week". They argue it is useful because warnings cluster in time. Which statement is correct?
* It is leakage, because the alerts issued during the following week are not known when the prediction is made
- It is safe, because alerts are a category, and categories cannot leak
- It is safe, because a week is longer than a day
- It is leakage only if the model is a decision tree
WHY: The following week's alerts are in the future, so the feature is not available at prediction time. The type of feature and the type of model do not decide leakage. Availability time does.
```

### Cross-validation on time-ordered data

**What it is**

**Cross-validation** repeats the train-and-score step on several folds, so that the score does not depend on one lucky split. For independent rows, the usual design is a shuffled K-fold. For time series, each fold must train on the past and test on the future, which is what a time-ordered split does.

The table below shows six months of data split into three time-ordered folds. Each fold trains on earlier months and tests on the next month.

| Fold | Training months | Test month |
|---|---|---|
| 1 | January, February | March |
| 2 | January to March | April |
| 3 | January to April | May |

The mean of the three fold scores shows the typical result. The spread shows how much to trust it. A wide spread means the model is unstable across periods, even if the mean looks good.

**How it shows up in a case study**

A team reports a score of 0.82 from five shuffled folds on two years of daily data. A second team, using time-ordered folds on the same data, reports 0.61. The analyst reasons that shuffling lets each training fold contain later days than some test days, which makes the first score too optimistic for forecasting. She recommends the time-ordered result, reports the mean and spread, and notes which period had the weakest fold.

:::trap Shuffling time-ordered folds
Shuffled cross-validation repeats the leak of a random split several times over. It is not a stronger check, only a more optimistic one.
:::

```quiz
Q: A team reports the mean of five shuffled folds on two years of daily data as its forecast accuracy. Which phrase best describes the problem?
- The five folds are too few to average
- Cross-validation cannot be applied to regression
- Each fold is too large to be useful
* Shuffled folds train on some later days and test on some earlier days, so the estimate can be too optimistic for forecasting
WHY: The problem is the order of the folds, not their number or size. Shuffling lets training rows lie after test rows, which a real forecast never has. The tempting wrong answer blames the number of folds.

Q: A student uses folds that each train on earlier months and test on the next month. The fold scores are 0.55, 0.61 and 0.12. What should she report?
- Only the mean, because the spread is just noise
- The highest fold, because it shows the model's potential
* The mean and the spread, together with the weak fold, because a drop in one period says the model is unstable there
- Nothing, because time-ordered folds cannot give a number
WHY: The mean of the three scores is 0.43, but the 0.12 fold shows that the model fails in one period. Reporting only the mean hides that. The tempting wrong answer chooses the best fold, which is cherry-picking.

Q: A team wants a stable validation estimate for a forecasting model. Which design fits the way the model will be used?
- Random 5-fold, because it uses all rows
* Folds that always train on the past and test on a later period, with a gap at each boundary
- Leave-one-row-out, because it uses the most rows for training
- Train on all rows and test on all rows, so nothing is held back
WHY: The design should match how the model will be used, which means predicting the future from the past. Leave-one-row-out and random folds mix the time order. Training and testing on the same rows measures memorising.
```

### Diagnosing overfitting

**What it is**

**Overfitting** is when a model learns the noise in its training rows. Its error on the training rows keeps falling, while its error on validation rows stops falling and then rises. The diagnosis is to compare the two errors as the model gets more complex.

The table below shows a decision tree at four depths. Depth controls how many questions the tree may ask in a row.

| Depth | Training error | Validation error |
|---|---|---|
| 2 | 9.1 | 10.4 |
| 4 | 6.2 | 8.0 |
| 6 | 3.1 | 8.6 |
| 8 | 0.8 | 9.9 |

The training error falls at every depth, so it cannot tell you which depth to choose. The validation error is lowest at depth 4. Beyond that point, the tree is fitting the noise, which is the sign of overfitting. You choose the setting from the validation column, and you score the test rows only once, for the chosen setting.

**How it shows up in a case study**

A team picks the deepest tree because it has the lowest training error. On the test rows, its error is much worse than a shallow tree's. The analyst reasons that the training error measured memorising, not learning. She reports the validation table, names the depth with the lowest validation error, and shows that the test score for that depth is close to its validation score.

:::trap Choosing by training error
The deepest tree always has the lowest training error. That is why training error cannot choose the depth. Choose with the validation error.
:::

```quiz
Q: Using the depth table above, a team wants the model that will generalise best. Which depth should they choose, reading the validation column?
* Depth 4, because it has the lowest validation error, and beyond it the validation error rises while training error keeps falling
- Depth 8, because it has the lowest training error
- Depth 2, because it is the simplest model
- Depth 6, because it sits in the middle of the table
WHY: Depth 4 has the lowest validation error, 8.0. Depth 8 has the lowest training error, which is the trap. Depth 2 is simple, but its validation error of 10.4 is worse than depth 4's. The middle value has no special meaning.

Q: A deep tree has training error 1.2 and validation error 12.8. A shallow tree has training error 6.0 and validation error 7.1. Which statement is right?
- The deep tree is better, because its training error is lower
- The two trees cannot be compared, because they have different depths
* The deep tree is overfitting: it fits the training rows closely but does worse on validation rows, so the shallow tree generalises better
- The validation error must be wrong, because the training error is correct
WHY: A large gap between training and validation error is the signature of overfitting. The shallow tree is better on the rows that matter for choosing. The tempting wrong answer trusts the training error, which always favours complexity.

Q: A student tunes the tree depth by testing many depths on the test rows and keeps the depth with the best test score. What is the problem?
- The test rows are too few for any tuning
- Depth should never be tuned at all
- The model will be slower to run in production
* The test rows have been used for choosing, so the reported test score is optimistic and no longer an honest final check
WHY: The test set must be scored once, after the settings are chosen on validation rows. Choosing on the test rows turns it into a second validation set. Speed in production is not the issue here.
```

### R-squared

**What it is**

**R-squared** compares the model's squared errors with the squared errors of always predicting the mean of the actual values. A value of 1 means the predictions are perfect. A value of 0 means the model is no better than the mean. A negative value means the model is worse than the mean.

The table below uses three actual values, 10, 12 and 14, with a mean of 12. The total variation around the mean is (10 minus 12) squared, plus (12 minus 12) squared, plus (14 minus 12) squared. That is 4 + 0 + 4 = 8.

| Prediction for each day | Squared errors | Sum of squared errors | R-squared |
|---|---|---|---|
| 11, 12, 13 | 1, 0, 1 | 2 | 1 minus 2/8 = 0.75 |
| 12, 12, 12 (the mean) | 4, 0, 4 | 8 | 1 minus 8/8 = 0 |
| 14, 14, 14 | 16, 4, 0 | 20 | 1 minus 20/8 = -1.5 |

The middle row shows that predicting the mean gives R-squared 0. The last row shows that a bad model gives a negative value. R-squared is not a percentage of correct predictions, and it is not an error in the target's unit.

**How it shows up in a case study**

A test set gives an R-squared of 0.61 for next-day PM2.5. A councillor asks what that means for the public. The analyst reasons that R-squared is the share of the variation in the test values that the model explains. It is not the share of days predicted correctly, and it does not say how large a typical error is. She pairs it with the average error in µg/m³, which is the number officers can act on.

:::trap Reading R-squared as accuracy
R-squared is neither a percentage of right answers nor an error size. It can also be negative, which many people wrongly believe is impossible.
:::

```quiz
Q: A test set gives an R-squared of 0.61 for next-day PM2.5. A councillor says, "The model is correct 61 per cent of the time." What is the best reply?
- Correct, because R-squared is a percentage of right predictions
- Correct only if the readings are in µg/m³
* Incorrect: R-squared is the share of the variation in the test values that the model explains, not the share of correct predictions, and it is not an error size
- Incorrect, because a good R-squared must be above 0.9
WHY: R-squared measures explained variation, so the councillor has misread it. The unit of the readings does not change that. The threshold of 0.9 is an invented rule, and the right reply is about what the number means.

Q: The actual values on five test days are all 20. A team wants to report R-squared. What happens?
- R-squared is 1, because the predictions are perfect
- R-squared is 0, because there is no variation
- R-squared is negative, because a constant cannot be matched
* R-squared is undefined, because the total variation around the mean is zero and the division fails
WHY: When every actual value is the same, the denominator is zero, so no ratio can be formed. The team must report that the measure does not apply. The tempting wrong answer is 1, because the predictions may look perfect.
```

### What each function needs

Each idea below is taught with a small example that has nothing to do with the lab's data. Try each example in a Python shell before you use the idea in your solution.

**Integer division and `int`.** The `/` operator divides and keeps the decimal part. The `//` operator divides and drops it. The `int` function also drops the decimal part, so it rounds towards zero, not to the nearest whole number.

```python
print(7 / 2)       # 3.5
print(7 // 2)      # 3
print(int(2.9))    # 2
print(int(7 * 0.5))  # 3
```

Expected output: `3.5`, `3`, `2` and `3`. The last line shows that multiplying by a fraction and then calling `int` is how you turn a share into a whole count of items, as the statement asks.

**Slicing.** A slice takes a range of positions. `word[:3]` takes positions 0, 1 and 2, and it stops before position 3. `word[3:]` takes position 3 to the end. Slicing never reorders anything.

```python
word = "crumble"
print(word[:4])   # crum
print(word[4:])   # ble
print(word[-2:])  # le
```

A negative start counts from the end, so `word[-2:]` is the last two characters. Be careful with `word[-0:]`, which is the same as `word[0:]` and gives the whole word. A count of zero needs its own check, which is a rule you will meet again in the twin problem below.

**Averages.** The mean of a list is its sum divided by its count. Use `/` for the division.

```python
rainfall = [3, 5, 10]
print(sum(rainfall) / len(rainfall))   # 6.0
```

Expected output: `6.0`. The result is a float, even though the inputs are whole numbers, because `/` always gives a float in Python 3.

**Absolute value and powers.** `abs(-4)` is 4, and `abs(4)` is also 4. `**` raises a number to a power, so `3 ** 2` is 9. `math.sqrt` needs `import math` first.

```python
import math
print(abs(-4))         # 4
print(3 ** 2)          # 9
print(math.sqrt(16))   # 4.0
```

The three results are `4`, `9` and `4.0`. Note that `math.sqrt` returns a float even for a perfect square.

**Pairing two lists.** `zip` walks two lists together, one position at a time. It stops at the end of the shorter list.

```python
names = ["x", "y", "z"]
scores = [10, 20]
print(list(zip(names, scores)))   # [('x', 10), ('y', 20)]
```

The output shows two pairs. The third name has no partner, so it is dropped. Your functions will get two lists of equal length, but a rule about unequal lengths may still apply, and the next section covers it.

**Rounding.** `round(x, 2)` rounds to two decimal places. `round(2.5)` gives 2, because Python rounds halves to the nearest even digit. Round once, at the end of a calculation, because rounding in the middle passes an error into the rest of the calculation.

```python
print(round(3.14159, 2))  # 3.14
print(round(2.5))         # 2
print(round(3.456, 1))    # 3.5
```

Expected output: `3.14`, `2` and `3.5`.

**Copies and mutation.** A list is changed in place by methods such as `append` and `sort`. If two names point to the same list, a change through one name shows through the other. `list(original)` makes an independent copy.

```python
a = [1, 2]
b = a
b.append(3)
print(a)   # [1, 2, 3]
c = list(a)
c.append(4)
print(a)   # [1, 2, 3]
```

The first `print` shows that `a` changed, because `b` is the same list. The second `print` shows that `a` did not change after `c` was appended to, because `c` is a copy. The statement does not ask you to avoid changing inputs, but keeping the inputs unchanged is a safe habit.

**Booleans and numbers.** In Python, `True` counts as 1 and `False` as 0. A boolean is a kind of `int`, so `isinstance(True, int)` is `True`. If your function checks types, remember this subclass relationship. The lab statement does not mention booleans, so only check for them if you have a reason.

```python
print(isinstance(True, int))   # True
print(True + True)             # 2
```

### The rules people miss

The table lists the rules a hidden test could check. Each row takes its rule from the statement. Where the statement says nothing about a case, the row says so, so you do not invent a rule.

| Rule in the statement | What a careless solution does | How to check yours |
|---|---|---|
| `test_size = int(len(data) * test_fraction)` | Rounds the product instead, so 3.5 becomes 4 rather than 3. | With 7 rows and fraction 0.5, `int(3.5)` is 3, so the test set has 3 rows. |
| The last `test_size` rows form the test set | Takes the first rows as the test set, or takes the middle. | With `[10, 20, 30, 40, 50]` and 0.4, the test set must be `[40, 50]`. |

### Worked twin problem

**Scenario.** An estate agent keeps house sale prices in date order, oldest first. Before she predicts the next price, she needs a fair test set and a simple guess to beat. She asks you for five functions, using the standard library only.

- `three_way_split(prices, val_share, test_share)` returns `(train, val, test)`. The test set is the last `int(len(prices) * test_share)` prices. The validation set is the `int(len(prices) * val_share)` prices just before them. The training set is everything earlier. All three keep date order. Raise `ValueError` if either share is not strictly between 0 and 1, if the two shares add up to 1 or more, if `prices` is empty, or if the validation or test set would be empty.
- `median_guess(train, n)` returns a list of `n` copies of the median of the training prices. Raise `ValueError` if the training list is empty.
- `worst_miss(actual, guess)` returns the largest absolute error, unrounded.
- `mean_signed_error(actual, guess)` returns the mean of `guess - actual`, unrounded. A negative value means the guesses are too low on average.
- `r2_manual(actual, guess)` returns `1 - ss_res / ss_tot`, where `ss_res` is the sum of squared errors and `ss_tot` is the sum of squared differences from the mean of the actual values. Raise `ValueError` if the two lists are empty, have different lengths, or if all actual values are equal.

The domain, the data and the functions differ from the real lab's, but the skills (slicing by position, a median, averages, error handling) are the same, so the method above applies directly. The worked solution is below. Read it only after you have tried the scenario yourself.

```python test
import statistics


def three_way_split(prices, val_share, test_share):
    if not (0 < val_share < 1 and 0 < test_share < 1):
        raise ValueError("each share must be between 0 and 1")
    if val_share + test_share >= 1:
        raise ValueError("shares must add up to less than 1")
    if len(prices) == 0:
        raise ValueError("prices must not be empty")
    n_test = int(len(prices) * test_share + 1e-9)
    n_val = int(len(prices) * val_share + 1e-9)
    if n_test == 0 or n_val == 0:
        raise ValueError("validation or test set would be empty")
    test_start = len(prices) - n_test
    val_start = test_start - n_val
    return (list(prices[:val_start]),
            list(prices[val_start:test_start]),
            list(prices[test_start:]))


def median_guess(train, n):
    if len(train) == 0:
        raise ValueError("training set is empty")
    return [statistics.median(train)] * n


def _check(actual, guess):
    if len(actual) == 0:
        raise ValueError("nothing to score")
    if len(actual) != len(guess):
        raise ValueError("lengths differ")


def worst_miss(actual, guess):
    _check(actual, guess)
    return max(abs(a - g) for a, g in zip(actual, guess))


def mean_signed_error(actual, guess):
    _check(actual, guess)
    return sum(g - a for a, g in zip(actual, guess)) / len(actual)


def r2_manual(actual, guess):
    _check(actual, guess)
    mean_actual = sum(actual) / len(actual)
    ss_tot = sum((a - mean_actual) ** 2 for a in actual)
    if ss_tot == 0:
        raise ValueError("all actual values are equal")
    ss_res = sum((a - g) ** 2 for a, g in zip(actual, guess))
    return 1 - ss_res / ss_tot


def expect_error(error_type, func, *args):
    try:
        func(*args)
    except error_type:
        return True
    return False


prices = [200, 220, 240, 260, 280, 300, 320, 340, 360, 380]
train, val, test = three_way_split(prices, 0.2, 0.3)
assert train == [200, 220, 240, 260, 280]
assert val == [300, 320]
assert test == [340, 360, 380]
guess = median_guess(train, len(test))
assert guess == [240, 240, 240]
assert worst_miss(test, guess) == 140
assert mean_signed_error(test, guess) == -120
assert r2_manual(test, guess) == -54

assert median_guess([1, 2, 3, 4], 2) == [2.5, 2.5]
assert median_guess([5, 1, 9], 1) == [5]
assert worst_miss([3, 4], [3, 4]) == 0
assert worst_miss([10, 20], [13, 15]) == 5
assert mean_signed_error([10, 20], [13, 15]) == -1
assert r2_manual([3, 4], [3, 4]) == 1
assert r2_manual([1, 2, 3], [1, 2, 4]) == 0.5

train2, val2, test2 = three_way_split(list(range(100)), 0.1, 0.29)
assert len(test2) == 29 and len(val2) == 10 and len(train2) == 61
train3, val3, test3 = three_way_split(list(range(10)), 0.2, 0.2)
assert train3 == [0, 1, 2, 3, 4, 5] and val3 == [6, 7] and test3 == [8, 9]

assert expect_error(ValueError, three_way_split, [], 0.2, 0.2)
assert expect_error(ValueError, three_way_split, prices, 0, 0.2)
assert expect_error(ValueError, three_way_split, prices, 0.2, 1)
assert expect_error(ValueError, three_way_split, prices, 0.5, 0.5)
assert expect_error(ValueError, three_way_split, [1, 2, 3], 0.1, 0.2)
assert expect_error(ValueError, median_guess, [], 2)
assert expect_error(ValueError, worst_miss, [], [])
assert expect_error(ValueError, worst_miss, [1, 2], [1])
assert expect_error(ValueError, r2_manual, [4, 4, 4], [1, 2, 3])
```

**Line by line.**

- `import statistics` brings in the median from the standard library. Nothing needs installing.
- `three_way_split` checks the shares first. `0 < val_share < 1` is a chained comparison, true only inside the open range from 0 to 1. The sum check makes sure some rows are left for training. The checks run before any arithmetic, so bad input fails clearly.

Explanation, line by line. `last_share` refuses empty input and a share outside the range from 0 to 1. The line `count = int(len(delays) * share)` finds how many items to keep. The check `if count == 0` is the important one. The slice `delays[-count:]` with a count of 0 is `delays[-0:]`, which is the same as `delays[0:]`, so it returns the whole list. Without the check, a share of 0 would return every delay, which is the opposite of what the rule asks. The `list(...)` call returns a new list, so the caller cannot change the original by accident.

`mean_delay` sums the delays and divides by the count with `/`. `round(..., 2)` rounds once, at the end. The sum is 58 and the count is 10, so the mean is 5.8.

`count_over` uses a generator expression. `sum(1 for d in delays if d > limit)` adds 1 for each delay that passes the test. The comparison `>` is strict, so a delay equal to the limit does not count. The delays above 6 are 7, 12, 9 and 15, which makes 4.
