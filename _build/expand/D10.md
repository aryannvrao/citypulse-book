## What the quiz tests

The quiz has ten multiple-choice questions. Each one is a short case study about a CityPulse team, and each one tests one topic from this section, in the order listed below. You need 70% to pass. Your first attempt is the one your skill score keeps, so read each question carefully before you choose.

Read the last line of a question first. It tells you what is asked: a number, the sign of a change, a query that will run, or the reason a query fails. Then read the scenario again and underline the facts that matter, such as the partition, the sort order, the size of the frame, a tie or a missing value. Many scenarios also contain details that are true but irrelevant, such as the name of a city or the date of a report. Ignore those.

Eliminate options that are true in general but do not fix this scenario. A correct SQL fact can still be the wrong answer if it does not answer the question. For example, "PARTITION BY splits the rows into groups" is always true, but it does not tell you how many rows a frame holds.

Watch for three words. "Most" means one option is better than the others, not that the others are false. "First" usually points to the first row of a partition, or to the first step SQL performs. "Best" means the option that meets every condition in the question, not the one that works most of the time.

Choose your answer before you read the WHY line. The WHY line explains the right answer and why the most tempting wrong option fails. Read it after you choose, so that a wrong choice teaches you something.

### Window frames

**What it is.** A window function calculates a value using a set of rows around the current row. That set is called the frame. The frame is written inside `OVER (...)`, after the `ORDER BY`. Here is a small example:

```sql
SELECT ts, value,
       AVG(value) OVER (ORDER BY ts ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS ma3
FROM reading;
```

`ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` means the current row and the two rows before it. The count is by position in the order, not by clock time. Suppose the values in time order are 10, 20, 30 and 40. The first row has only itself, so `ma3` is 10.0. The second row averages 10 and 20 to give 15.0. The third row averages 10, 20 and 30 to give 20.0. The fourth row averages 20, 30 and 40 to give 30.0. The output column therefore reads 10.0, 15.0, 20.0 and 30.0.

SQLite does not stop the calculation at the start of the series. It averages the rows that exist. That is why the early values in a rolling column rest on fewer readings than the later ones.

The frame is separate from the partition. `PARTITION BY` decides which groups of rows exist, so that one station never mixes with another. The frame decides how many neighbours each row sees inside its group. If you change the frame, every rolling number changes, even though the query still runs without an error.

**How it shows up in a case study.** The CityPulse team at a city council is checking a dashboard for station S3. The dashboard shows a "three-hour smoothed" PM2.5 value. Four hourly readings are 42, 47, 51 and 49. The query uses `ROWS BETWEEN 3 PRECEDING AND CURRENT ROW`. The team reads this as a three-hour window, but the frame holds four rows: the current row and three before it. The fourth row therefore averages all four values to give 47.25, not the three-hour average of 49.0. The decision is to change the frame to `2 PRECEDING`, which holds exactly three rows. The reasoning is to count the current row first and then count back. The number after PRECEDING is one less than the number of rows you want.

:::trap Frame and partition are different jobs
Writing `PARTITION BY station_id` and expecting it to limit the window to three rows is a common mistake. The partition only separates the stations. Without a frame, a window with an ORDER BY uses the default frame, which runs from the first row up to the current row, so the window keeps growing. Keep the two ideas apart: the partition chooses the group, and the frame chooses the neighbours.
:::

```quiz
Q: A station has PM2.5 readings of 30, 36, 42, 48 and 54 in time order. The dashboard query is AVG(value) OVER (PARTITION BY station_id ORDER BY ts ROWS BETWEEN 3 PRECEDING AND CURRENT ROW), and the health officer wants a three-hour smoothed value. What does the query return on the fifth row, whose value is 54?
- 42.0
- 48.0
* 45.0
- 39.0
WHY: 3 PRECEDING means three rows before the current one, so the frame holds four rows: 36, 42, 48 and 54. Their average is 45.0. The tempting 48.0 comes from reading the frame as three rows in total, which is what 2 PRECEDING would give. The query runs either way, so the mistake shows only in the numbers.

* Add station_id to the PARTITION BY clause
- Change ROWS to RANGE so that the frame counts hours
- Increase the frame to 3 PRECEDING

WHY: The partition is by pollutant only, so both stations share one window and their readings mix together. Adding station_id gives each station its own partition. RANGE counts by the ordering value rather than by readings, and removing the ORDER BY would leave the time sequence undefined.

The tempting first option is the centred average, which looks smoother, but it uses one reading from the future.
```

### Ranking functions

**What it is.** Three window functions number the rows inside a partition: `ROW_NUMBER()`, `RANK()` and `DENSE_RANK()`. They differ only when two rows tie, which means their ORDER BY values are equal. Take three rows ordered by value, highest first, with values 80, 80 and 60:

```text
value  row_number  rank  dense_rank
80     1           1     1
80     2           1     1
60     3           3     2
```

`ROW_NUMBER()` gives every row its own number. When values tie, the numbers 1 and 2 go to the tied rows in an order SQLite chooses, unless the ORDER BY has a tie-breaker. `RANK()` gives tied rows the same number and then skips the next number, so the 60 is third. `DENSE_RANK()` gives tied rows the same number and does not skip, so the 60 is second. All three keep every row, which is what makes them window functions.

To choose between them, ask one question: do you need unique numbers, a league where a tie shares a place and the next place is numbered with a gap, or a league with no gaps at all?

**How it shows up in a case study.** A city publishes a league table of stations by their daily peak PM2.5. Two stations tie at 92, and a third station has 85. The printed sheet needs a unique line number for every station, so the team uses `ROW_NUMBER()` and breaks the tie by station name. The public league must say that the 85 station is in second place after the tie, not third. The team uses `DENSE_RANK()` for that column. The reasoning is to ask what the number means to a reader: a line on a sheet, or a place in a league.

:::trap Reading RANK as a row count
`RANK()` skips numbers after a tie, so a result of 1, 1, 3 can look as if a row is missing. No row is missing. `DENSE_RANK()` would give 1, 1, 2. Choose the function by the meaning the question asks for, not by which output looks tidier.
:::

```quiz
Q: Three stations report daily PM2.5 averages of 55, 55 and 40. The city wants a league table in which tied stations share a place, and the next place follows without a gap. Which number does the 40 station receive, and from which function?
- 3 from RANK()
* 2 from DENSE_RANK()
- 1 from ROW_NUMBER()
- 3 from ROW_NUMBER()
WHY: DENSE_RANK() gives the tied 55s the place 1 and gives the 40 the next place, which is 2. RANK() would give 3, which is the tempting answer, because it skips 2 after the tie. ROW_NUMBER() gives the 40 the number 3, because it numbers rows rather than places.

Q: A health report needs exactly one row per station for its peak reading, even when two readings tie for the highest value. Which window expression guarantees exactly one row per station after the filter rn = 1?
- RANK() OVER (PARTITION BY station_id ORDER BY value DESC)
- DENSE_RANK() OVER (PARTITION BY station_id ORDER BY value DESC)

* ROW_NUMBER() OVER (PARTITION BY station_id ORDER BY value DESC, ts ASC)
WHY: ROW_NUMBER() never repeats a number inside a partition, and the ts tie-breaker makes the choice repeatable. RANK() and DENSE_RANK() both give two rows the number 1 when the peak is tied, so the filter would keep two rows for that station. The AVG option is not a ranking and does not filter anything.

Q: One station's readings for a day are 88, 88 and 80, ordered highest first. The analyst numbers them with RANK(). Which number does the reading of 80 receive?
* 3
- 2
- 1
- 4
WHY: RANK() gives both 88s the number 1, then skips 2, so the 80 receives 3. The tempting 2 is the DENSE_RANK() answer, which does not skip. The number 4 would need a fourth row, and there are only three readings.
```

### LAG and LEAD

**What it is.** `LAG(value)` returns the value from the previous row in the same partition. `LEAD(value)` returns the value from the next row. The simplest use is one row back or one row forward, and both can take an optional offset and default. Here is a change calculation:

```sql
SELECT ts, value,
       value - LAG(value) OVER (ORDER BY ts) AS change
FROM reading;
```

Suppose the values in time order are 30, 36 and 33. The first row has no earlier row, so `LAG` returns NULL and the change is NULL. The second row gives 36 minus 30, which is 6. The third row gives 33 minus 36, which is -3. The output column reads NULL, 6 and -3.

Two points matter. The first row of each partition has no previous row, so its result is NULL, which SQLite prints as an empty cell. The sign of a change depends on the order of the subtraction. `value - LAG(value)` is the current value minus the earlier one, which is the usual change over time. `LAG(value) - value` has the same size with the opposite sign. `LEAD` looks forward, so it answers the question "what comes next?", and it is the wrong tool for a change from the previous period.

**How it shows up in a case study.** A health officer receives daily averages for station S7: 40.0 on Monday, 46.0 on Tuesday and 43.0 on Wednesday. The officer asks whether conditions got worse on Wednesday. The right expression reads the previous day, which is Tuesday's 46.0. The change is 43.0 minus 46.0, which is -3.0, so the air improved. A query that uses `LEAD` would look at Thursday, which is not in the data, and returns NULL. The reasoning is to ask which row comes before the current one, then subtract in the order that matches the question: current minus previous.

:::trap Reversing the subtraction
`LAG(value) - value` gives the right size of change with the wrong sign, so a fall in pollution looks like a rise. `LEAD` answers a different question, because it looks forward. Check the sign with a row you can work out by hand before you trust the column.
:::

```quiz
Q: A station's daily averages are 22.0 on Monday, 25.0 on Tuesday and 19.0 on Wednesday. The report needs the change from the previous day for each row. Which expression gives the change for Wednesday?
* value - LAG(value) OVER (ORDER BY day_ist), which is -6.0
- LAG(value) OVER (ORDER BY day_ist) - value, which is 6.0
- value - LEAD(value) OVER (ORDER BY day_ist), which is NULL
- AVG(value) OVER (ORDER BY day_ist ROWS BETWEEN 1 PRECEDING AND CURRENT ROW), which is 22.0
WHY: LAG reads Tuesday's 25.0, so 19.0 minus 25.0 is -6.0. The reversed subtraction is the tempting option, because it gives the right size with the wrong sign. LEAD looks forward, finds no day after Wednesday, and returns NULL. The AVG option is a rolling mean, not a change.

Q: A team wants an alert when a station's reading rises by more than 10 since that station's previous reading. The table holds readings from five stations in one table with the columns station_id, ts and value. Which expression should the alert use?
- value - LEAD(value) OVER (PARTITION BY station_id ORDER BY ts)
- LAG(value) OVER (PARTITION BY station_id ORDER BY ts) - value
* value - LAG(value) OVER (PARTITION BY station_id ORDER BY ts)
- value - LAG(value) OVER (ORDER BY ts)
WHY: The PARTITION BY keeps each station's previous reading, and LAG looks backward, so each reading is compared with the one before it at the same station. LEAD looks forward and answers a different question. Without PARTITION BY, the first reading of one station is compared with the last reading of another, which is the tempting option. The second option reverses the subtraction, so a rise appears as a fall.

Q: A dashboard shows each reading's change from the previous reading at the same station. The first reading of every station has no previous reading, and the developer wants that first change to show 0 rather than an empty cell. Which change does this?
- Replace LAG(value) with LEAD(value, 0)
* Use LAG(value, 1, 0) OVER (PARTITION BY station_id ORDER BY ts)
- Add a frame of ROWS BETWEEN 0 PRECEDING AND CURRENT ROW to the same window
- Add HAVING value > 0 at the end of the query
WHY: The third argument of LAG is the default, which is used when no earlier row exists, so LAG(value, 1, 0) gives 0 on the first row of each station. LEAD(value, 0) returns the current row, not the previous one. A frame does not change what LAG reads. HAVING needs a grouped query and would remove the readings instead of filling them in.
```

### Window functions versus GROUP BY

**What it is.** `GROUP BY` collapses the rows that share a value into one row per group. A window function keeps every row and adds a column calculated from related rows. Compare two queries on the same table, which holds two readings for S1 and one reading for S2:

```sql
SELECT station_id, AVG(value) AS station_avg
FROM reading
GROUP BY station_id;

SELECT station_id, value,
       AVG(value) OVER (PARTITION BY station_id) AS station_avg
FROM reading;
```

If S1's readings are 40 and 60, and S2's reading is 30, the first query returns two rows: 50.0 for S1 and 30.0 for S2. The second query returns all three rows, with S1's average repeated beside each S1 reading: 40 with 50.0, 60 with 50.0, and 30 with 30.0. The readings are still there.

The window version puts an aggregate such as AVG, COUNT or MAX inside `OVER`. It does not need a GROUP BY. Because the window works row by row, you can show the reading and its group's summary side by side.

**How it shows up in a case study.** A city analyst is asked to show each reading beside its station's average, so that a reader can see which readings sit above the usual level. She writes `GROUP BY station_id` first, and the query returns three rows, one per station, so the individual readings have gone. The fix is the window version, which keeps every reading. The reasoning is to ask whether the question needs the individual readings or only a summary. If it needs the readings, the answer is a window function.

:::trap Bare columns after GROUP BY
If you write `GROUP BY station_id` and then list `value` without an aggregate, SQLite does not stop you. It returns the value of one arbitrary reading in each group, so the output looks valid and is wrong. Use a window function when you need every reading.
:::

```quiz
Q: A health officer wants every reading of station S1 listed, with S1's average beside each reading, and all twelve readings must remain in the answer. Which query meets both conditions?
- SELECT station_id, AVG(value) FROM reading WHERE station_id = 'S1' GROUP BY station_id
- SELECT station_id, value FROM reading GROUP BY station_id, value
- SELECT DISTINCT station_id, AVG(value) FROM reading
* SELECT station_id, value, AVG(value) OVER (PARTITION BY station_id) FROM reading WHERE station_id = 'S1'
WHY: The window version keeps all twelve rows and repeats S1's average on each one. The first option returns a single row, and the second returns no average at all. The tempting first option gives the correct average, but it collapses the readings into one row.

Q: A city analyst wants to know by how much each reading differs from its own station's average, with one answer per reading. Which expression does this in a query over the reading table?
- value - AVG(value) with GROUP BY station_id, which hides each reading
* value - AVG(value) OVER (PARTITION BY station_id)
- value - AVG(value) OVER (ORDER BY ts)
- value - (SELECT AVG(value) FROM reading)
WHY: PARTITION BY station_id gives each reading its own station's average, and the subtraction runs on every row. The subquery option subtracts the average of all stations together, which is the tempting error. The ORDER BY option builds a running average through time rather than a station average. The GROUP BY option returns one row per station.

Q: A developer writes GROUP BY station_id, then adds a window column that refers to the readings. The query returns one row per station, although the developer expected one row per reading. What is the cause?
- The window needs a DISTINCT on station_id
- The window cannot read a column that is not in the GROUP BY
* The GROUP BY collapses the rows before the window runs, so the window sees one row per station
- The ORDER BY inside the window is missing
WHY: Windows run after GROUP BY, so by then the readings are already collapsed. The fix is to remove the GROUP BY and let the window keep every row. The missing ORDER BY is tempting, but an average over a whole partition needs no ORDER BY, and adding one would not change the number of rows. The second option describes an error that SQLite does not report here.
```

### Top N per group

**What it is.** A top-N-per-group query keeps the best N rows inside each group, not the best N rows overall. The standard method has two steps. An inner query numbers the rows in each group with `ROW_NUMBER()`. An outer query keeps the rows whose number is at most N. Here is the shape, using a table of charging sessions:

```sql
SELECT zone, point, sessions
FROM (
  SELECT zone, point, sessions,
         ROW_NUMBER() OVER (PARTITION BY zone ORDER BY sessions DESC, point ASC) AS rn
  FROM charge
)
WHERE rn <= 2
ORDER BY zone, rn;
```

Suppose zone North has point A with 30 sessions, point B with 45 and point C with 20. The inner query numbers B as 1, A as 2 and C as 3. The outer query keeps B and A. The other zones are numbered in the same way, from their own rows, so the output has at most two rows per zone.

The tie-breaker `point ASC` makes the result repeatable. Without it, two points with the same number of sessions can swap places from one run to the next.

**How it shows up in a case study.** The city wants the two busiest charging points in each of four zones for a monthly report. An engineer proposes `ORDER BY sessions DESC` with `LIMIT 8`, reasoning that eight is two times four. The team checks the table and finds that one zone holds most of the busy points, so all eight rows come from that zone. The correct design numbers the points inside each zone and keeps two per zone. The reasoning is that the number of rows per group must come from a partition, not from a total you guess.

:::trap LIMIT on the whole table
`ORDER BY ... LIMIT 8` returns the eight highest rows across all zones. It does not return two per zone, and the answer changes whenever the busy zone changes. Numbering the rows per group in a subquery is the fix.
:::

```quiz
Q: The city wants the two busiest charging points in each of four zones. An engineer writes SELECT zone, point, sessions FROM charge ORDER BY sessions DESC LIMIT 8, arguing that eight is two times four. Why is the result wrong?
- The query is invalid, because ORDER BY and LIMIT cannot be used together
* It returns the eight busiest rows across all zones, so one busy zone can take most of the places
- It cannot sort the sessions column because it is a number
- It counts charging points instead of sessions
WHY: LIMIT counts rows in the whole result, not rows in each zone. One busy zone can fill all eight places, so another zone may get none. The fix is ROW_NUMBER() per zone in a subquery, then rn <= 2. The tempting argument is the multiplication, which holds only if every zone has exactly the same pattern of busy points, and nothing in the data guarantees that.

Q: A shop's report needs its single best-selling item for each shop, with exactly one row per shop even when two items tie on sales. Which structure is correct?
* A subquery with ROW_NUMBER() PARTITION BY shop ORDER BY sales DESC, item ASC, then WHERE rn = 1 in the outer query
- RANK() OVER (PARTITION BY shop ORDER BY sales DESC) in the same query, with WHERE rnk = 1
- SELECT shop, item, MAX(sales) FROM sale GROUP BY shop
- ORDER BY sales DESC LIMIT 1, repeated once for each shop
WHY: ROW_NUMBER() with an item tie-breaker gives exactly one row per shop, and the outer filter uses rn, which the subquery created. The RANK option fails because WHERE runs before the window, so rnk does not exist yet. The GROUP BY option is tempting, but item is not inside an aggregate, so SQLite returns an arbitrary item among the ties. A LIMIT cannot be repeated for each shop inside one statement.

Q: A branch has five books that arrived on the same day, and the team wants exactly three books per branch in a result that is the same every time the query runs. Which ORDER BY inside ROW_NUMBER() gives that?
- ORDER BY arrival_day DESC only
- ORDER BY RANDOM()
- ORDER BY COUNT(*) DESC
* ORDER BY arrival_day DESC, title ASC
WHY: A second sort key breaks the ties, so the three kept books are the same on every run. Without one, rows with the same day can be numbered in any order, and the kept books can change. RANDOM() is never repeatable. COUNT(*) is not a tie-breaker for individual books, and it needs a grouped query.
```

### The default frame

**What it is.** A window with an ORDER BY and no frame clause uses a default frame. In SQLite that default is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. Read it as "from the first row of the partition up to the current row, and include every row that ties with the current row on the ORDER BY value". Rows that tie in this way are called peers.

```sql
SELECT ts, value,
       SUM(value) OVER (ORDER BY ts) AS running_total
FROM reading;
```

Suppose two readings share the timestamp 08:00 with values 10 and 20, and a third reading at 09:00 has the value 30. The two 08:00 rows are peers, so each one includes both values and shows 30. The 09:00 row includes everything above it and shows 60. The output column reads 30, 30 and 60, not 10, 30 and 60.

This matters whenever you want one line per reading with its own running total. If the order of tied rows should decide the result, you must ask for it explicitly with `ROWS` and add a tie-breaker to the ORDER BY.

**How it shows up in a case study.** A dashboard shows a cumulative count of PM2.5 alerts for each station. Two sensors at one station report at the same minute, and the count jumps by two on that line. The team first thinks the data is wrong. It is not: the default frame treats the two tied rows as peers. If the team wants a count that rises by one per reading, it must write `ROWS` with a tie-breaker. The reasoning is to ask whether the number should be shared by tied rows or separate for each row.

:::trap Peers share one running value
With the default RANGE frame, tied rows share one running total, so a running total can jump by two at a single timestamp. This is correct SQL behaviour, not a fault in the data. If you want a true row-by-row total, write ROWS and add a tie-breaker to ORDER BY.
:::

```quiz
Q: Two readings from one station share the timestamp 08:00 and have values 10 and 25. A third reading at 09:00 has the value 5. The team runs SUM(value) OVER (ORDER BY ts) with no frame and expects a separate running total on each 08:00 row. What does the first 08:00 row show?
- 10
- 25
* 35
- 40
WHY: The default RANGE frame makes both 08:00 rows peers, so each shows the total of 10 plus 25, which is 35. The tempting 10 is what a true row-by-row running total would show, and that needs ROWS. The 40 is the total at 09:00, which is not part of either 08:00 row.

Q: A health team wants a strict running count of readings, one line per reading, even when two readings share a timestamp. The lines must come in a repeatable order. Which window clause should they write?
- RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, with ORDER BY ts only
- ORDER BY ts ROWS BETWEEN 1 FOLLOWING AND CURRENT ROW
- ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING, with ORDER BY ts only
* ORDER BY ts, reading_no ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
WHY: ROWS counts each row by its position, so each reading adds once, and the reading_no tie-breaker makes the positions repeatable. The first option is the default RANGE frame, which still treats tied timestamps as peers. The second option is not a valid frame in SQLite, and the third looks forward, which is the opposite of a running total.

Q: A query over readings with repeated timestamps shows a running count that rises by two at one timestamp. The team expected a rise of one for each row. Which explanation is correct?
* Tied rows are peers under the default RANGE frame, so they receive the same running value
- SQLite skipped one row, because COUNT ignores duplicates
- The ORDER BY is on the wrong column, so the rows are out of order
- The frame is ROWS, which counts clock times rather than rows
WHY: Peers share one running value, so both tied rows move the count together, in one step. The second option is false, because COUNT does not drop duplicate rows. The third is a plausible guess, but the question does not show a wrong column. The fourth is backwards: ROWS counts rows rather than clock times, and this query uses the default RANGE frame.
```

### Percentiles

**What it is.** Two window functions turn a row's position into a value between 0 and 1. `PERCENT_RANK()` gives (rank minus 1) divided by (the number of rows minus 1). `CUME_DIST()` gives the number of rows at or below the current row, divided by the number of rows. Here are four values in order: 10, 20, 30 and 40.

```sql
SELECT value,
       ROUND(PERCENT_RANK() OVER (ORDER BY value), 2) AS pr,
       ROUND(CUME_DIST() OVER (ORDER BY value), 2) AS cd
FROM reading;
```

The output is:

```text
value  pr    cd
10     0.00  0.25
20     0.33  0.50
30     0.67  0.75
40     1.00  1.00
```

For `PERCENT_RANK`, the lowest row gets 0 and the highest gets 1. For `CUME_DIST`, the lowest row gets one quarter, because one of four rows is at or below it, and the highest gets 1. Both are measures on a 0 to 1 scale, but they answer different questions. `PERCENT_RANK` is a position between the two ends. `CUME_DIST` is a share of all the rows.

**How it shows up in a case study.** A city has fifty stations. The officer wants a public figure for each station that answers the question "what share of stations are at or below this station's PM2.5?" The lowest station should show 0.02, because one of fifty stations is at or below it. `CUME_DIST` gives that result. `PERCENT_RANK` would show 0.0 for the lowest station, which is a position and not the share the report asks for. The reasoning is to read the question as a share of rows, not as a place between the ends.

:::trap Confusing the two measures
`PERCENT_RANK` gives the lowest row 0.0, while `CUME_DIST` gives it one divided by the number of rows. The two differ by one row at the bottom of the scale, which is enough to change a public figure. Name the measure your report needs before you choose the function.
:::

```quiz
Q: A city has fifty stations, and the officer wants the lowest station to show 0.02, meaning that one of fifty stations is at or below it. Which function gives that result when the stations are ordered by PM2.5?
* CUME_DIST() OVER (ORDER BY pm25)
- PERCENT_RANK() OVER (ORDER BY pm25)
- RANK() OVER (ORDER BY pm25)
- NTILE(50) OVER (ORDER BY pm25)
WHY: CUME_DIST counts the rows at or below the current row, so the lowest of fifty gets 1 out of 50, which is 0.02. PERCENT_RANK gives the lowest station 0.0, which is the tempting answer for a bottom percentile. RANK gives a place from 1 to 50, not a share, and NTILE gives a bucket number.

Q: An analyst computes PERCENT_RANK() OVER (ORDER BY pm25) for five stations with values 12, 18, 25, 31 and 40. Which value does the station with 25 receive?
- 0.4
* 0.5
- 0.6
- 0.75
WHY: PERCENT_RANK is (rank minus 1) divided by (rows minus 1). The 25 is third, so (3 minus 1) divided by (5 minus 1) is 0.5. The 0.6 option is CUME_DIST, which counts the 25 and the two values below it as 3 out of 5. The 0.4 option divides by the number of rows rather than the number of rows minus one.

Q: A dashboard shows the lowest of a station's one hundred readings as 0.01 on a share scale. The analyst asks which measure gives the lowest reading that value. Which one does?
- PERCENT_RANK() OVER (ORDER BY value), which gives 0.0 at the bottom
- RANK() OVER (ORDER BY value), which gives 1 at the bottom
- DENSE_RANK() OVER (ORDER BY value), which gives 1 at the bottom
* CUME_DIST() OVER (ORDER BY value)
WHY: CUME_DIST gives the share of rows at or below the current one, which is 1 out of 100, or 0.01, for the lowest reading. PERCENT_RANK gives 0.0 for the lowest reading, which is the tempting answer for a bottom share. RANK and DENSE_RANK both give 1, which is a place rather than a share.
```

### RANGE and INTERVAL frames

**What it is.** A `RANGE` frame defines the window by the value in the ORDER BY column, not by the number of rows. In SQLite the ORDER BY column must be a single number, such as Unix epoch seconds, and the offset is a plain number in the same unit. `RANGE BETWEEN 3600 PRECEDING AND CURRENT ROW` means every reading whose time is no more than 3600 seconds before the current reading, plus the current reading itself.

```sql
SELECT ts, value,
       AVG(value) OVER (ORDER BY ts RANGE BETWEEN 3600 PRECEDING AND CURRENT ROW) AS hour_avg
FROM reading;
```

Suppose three readings have times 0, 1800 and 5400 seconds, with values 10, 20 and 30. The first reading's frame holds only itself, so `hour_avg` is 10.0. The second reading's frame reaches back to 1800 seconds before its time, which is -1800, and holds both the first and second readings, so the average is 15.0. The third reading's frame starts at 5400 minus 3600, which is 1800, so it holds the second and third readings, and the average is 25.0. The output reads 10.0, 15.0 and 25.0.

A `ROWS` frame counts rows and ignores the gaps between them. A `RANGE` frame counts time, so a missing reading does not stretch the window. SQLite does not accept the INTERVAL keyword in a frame, so the time must be stored as a number.

**How it shows up in a case study.** A sensor at one station reports irregularly, sometimes after two hours and sometimes after ten minutes. The team wants a rolling one-hour average. A `ROWS` frame of four readings would cover different spans of time depending on the gaps. A `RANGE` frame over epoch seconds covers exactly one hour each time. The reasoning is to ask whether the window should be measured in readings or in time. The course uses `ROWS` for its reference, but when the window must be an exact span of time, `RANGE` with a number is the right tool.

:::trap Copying an INTERVAL frame
A frame such as `RANGE BETWEEN INTERVAL '1 hour' PRECEDING AND CURRENT ROW` comes from other databases. SQLite does not accept it, so the statement fails. Store time as a number, such as epoch seconds, and use 3600 for one hour.
:::


### NTILE buckets

**What it is.** `NTILE(n)` divides the rows of a partition into `n` buckets and returns the bucket number, from 1 to `n`, for each row. The rows are taken in the order of the ORDER BY. If the rows do not divide evenly, the first buckets each receive one extra row. Here are seven values in order.

```sql
SELECT value,
       NTILE(3) OVER (ORDER BY value) AS bucket
FROM reading;
```

With the values 4, 5, 6, 8, 9, 11 and 12, the output is:

```text
value  bucket
4      1
5      1
6      1
8      2
9      2
11     3
12     3
```

Seven rows over three buckets gives a base size of two with one row left over. The first bucket takes the extra row, so the sizes are three, two and two. The bucket number is a label for the group, not a measurement that you can average. To compare the groups, count the rows in each bucket with GROUP BY on the bucket number.

**How it shows up in a case study.** A city ranks its ten stations into four bands by average PM2.5 for a league report. The report says each band holds two or three stations, so the team checks the bucket sizes. Ten over four gives a base of two with two left over, so the sizes are three, three, two and two. The reasoning is that buckets are as equal as whole rows allow, not that every bucket holds the same count. Band 1 holds the cleanest stations only if the ORDER BY is ascending.

:::trap Assuming equal buckets
NTILE does not make every bucket the same size. Ten rows in four buckets gives 3, 3, 2 and 2, so the first buckets are the larger ones. The bucket number is also a label for the group, not a value that you can average.
:::


### Clause evaluation order

**What it is.** SQL works through a query in a fixed order, which is not the order in which you write the clauses. In a typical query, the database first reads the tables named in FROM and JOIN, then applies WHERE, then GROUP BY, then HAVING. Window functions in the SELECT list are calculated after those steps. ORDER BY comes after the windows, and LIMIT comes last. A small query shows the effect:

```sql
SELECT station_id, value,
       ROW_NUMBER() OVER (ORDER BY value DESC) AS rn
FROM reading
WHERE pollutant = 'pm25';
```

The WHERE clause removes the NO2 rows before ROW_NUMBER is calculated, so the numbers run over PM2.5 readings only. If you moved the pollutant filter into an outer query, the window would number both pollutants first. The outer filter would then remove the NO2 rows from a numbering that already counted them, and the PM2.5 numbers would be wrong.

Because the windows come after WHERE, you cannot use a window alias such as `rn` in the WHERE clause of the same query.

**How it shows up in a case study.** An analyst wants a rolling three-reading average of PM2.5 only. She writes the window in a subquery with no pollutant filter, then adds `WHERE pollutant = 'pm25'` in the outer query. The averages near the NO2 readings are now wrong, because those readings were part of each frame. The fix is to filter inside the same SELECT that holds the window. The reasoning is to ask at which step a row disappears, and to make sure that step comes before the window is calculated.

:::trap Filtering a window result in the same WHERE
`WHERE rnk = 1` beside the `RANK()` that defines `rnk` fails, because WHERE runs before the window exists. Put the window in a subquery or CTE, then filter in the outer query.
:::

```quiz
Q: An analyst wants a rolling three-reading average of PM2.5 for each station. She computes the window in a subquery over all readings, and adds WHERE pollutant = 'pm25' in the outer query. The averages on the PM2.5 rows look wrong. What is the fix?
- Move the ORDER BY into the outer query
* Put the pollutant filter in the same SELECT as the window, so that the NO2 rows are removed before the window runs
- Add LIMIT 3 to the outer query
- Replace AVG with SUM
WHY: WHERE runs before window functions in the same SELECT, so a filter there removes the NO2 rows before any frame is built. In the subquery, the frames already contained NO2 values, and the outer filter cannot take them back out of the averages. Moving the ORDER BY or adding a LIMIT does not change which rows enter a frame, and SUM would give totals, not averages.

Q: A developer writes SELECT station_id, value, RANK() OVER (ORDER BY value DESC) AS rnk FROM reading WHERE rnk = 1, and the query fails. What is the cause?
- SQLite does not support RANK
- The ORDER BY is in the wrong place
- The rnk column needs a GROUP BY
* WHERE runs before the window is calculated, so rnk does not exist yet
WHY: The evaluation order puts WHERE before the window functions, so the alias rnk does not exist when the filter runs. The fix is to wrap the ranked query in a subquery or CTE and filter rnk in the outer query. The GROUP BY option is tempting, but GROUP BY does not create a rank, and this query has no aggregate to group.

Q: A query has a window function in the SELECT list, an ORDER BY and a LIMIT. Which step runs last?
* LIMIT
- The window function
- The WHERE clause
- The GROUP BY clause
WHY: LIMIT is applied last, after ORDER BY has sorted the rows, so it cuts the sorted list. The window function is calculated before ORDER BY and LIMIT. WHERE is one of the earliest steps, so it cannot be last. The GROUP BY option is tempting, but it runs before the window, so it is not last either.
```

## The graded lab

The graded lab is a Python problem with visible tests and hidden tests. You run the visible tests yourself before you submit. The platform runs the hidden tests when you submit, and you cannot see them. This section explains the task, the ideas each function needs, the mistakes people make, and a method you can use on any lab of this kind. It then works through a different problem in full and sets one for you to solve.

### The task in plain words

**Scenario.** The CityPulse analytics team wants the worst spikes per station and a smoothed trend line. Both must be calculated in SQL, using window functions, rather than with Python loops. You write two functions. Each one runs SQL against an in-memory SQLite database and returns a plain Python list of tuples.

You use the standard library module `sqlite3` and SQL window functions. The starter file already contains `import sqlite3` and a list named `READINGS` with sample rows. Keep both. Before you write any code, read the rows of `READINGS` and note the order of the fields in each row.

The first function is `top_n_per_station(readings, n)`.

- It takes `readings`, which is the list of readings, and `n`, which is a whole number.
- For each station, it returns the top `n` readings by `value`, highest first.
- Each result is a tuple `(station_id, ts, value)`.
- The whole list is ordered by `station_id` ascending, then by `value` descending, then by `ts` ascending.
- The statement asks you to number the readings inside each station with `ROW_NUMBER() OVER (PARTITION BY station_id ...)`.
- Each `value` is rounded to 2 decimal places.
- Example: for the sample `READINGS`, `top_n_per_station(READINGS, 2)` returns `[('S1', '2026-01-01T10:00:00', 60.0), ('S1', '2026-01-01T11:00:00', 40.0), ('S2', '2026-01-01T09:00:00', 35.0), ('S2', '2026-01-01T10:00:00', 15.0)]`.

The second function is `rolling_avg(readings, station_id, pollutant, window)`.

- It takes the same list of readings, a station id, a pollutant name and a whole number `window`.
- It keeps only the rows for that station and that pollutant.
- It orders those rows by `ts` ascending.
- For each row, it finds the average of `value` over the current row and the `window - 1` rows before it. The statement gives the pattern `AVG(value) OVER (ORDER BY ts ROWS BETWEEN ... PRECEDING AND CURRENT ROW)`.
- It returns a list of `(ts, avg)` tuples in `ts` order, with `avg` rounded to 2 decimal places.
- The first rows have fewer than `window` rows behind them. Their average uses only the rows that exist.

| Visible test | Points |

| Single peak per station | 14 |
| 3-point moving average for S1 | 20 |

The visible tests are worth 54 points in total. Limits are 30 seconds of run time and 128 MB of memory. A correct SQL solution on this data uses far less than either limit.

### What each function needs

Each idea below comes with a small example that uses different data: cafe sales, sports scores, a step counter, a visit log. Do not copy these examples into the lab. Read each one, run it in your own editor and compare the output with what the text says.

**1. Sorting a list of tuples with a key.** `sorted` takes a `key` function that says what to compare. Here the list is sorted by score highest first, and by name for ties.

```python
players = [("Ana", 14), ("Ben", 9), ("Cy", 14)]
ranked = sorted(players, key=lambda p: (-p[1], p[0]))
print(ranked)
```

The output is `[('Ana', 14), ('Cy', 14), ('Ben', 9)]`. The key `(-p[1], p[0])` is a tuple. Python compares the first item, the negated score, so the largest score comes first. It compares the second item, the name, only when two scores are equal. The minus sign works for numbers only.

**2. Rounding.** `round(x, 2)` rounds to two decimal places, but the result can surprise you.

```python
print(round(2.675, 2))
print(round(0.125, 2))
print(round(2.5))
```

The output is `2.67`, then `0.12`, then `2`. The number 2.675 is stored in binary as a little less than 2.675, so it rounds down. The number 0.125 sits exactly halfway, and Python rounds halfway cases to the even digit. The rule for the lab is to round once, at the end, because rounding an intermediate average changes the later results.

**3. Booleans are integers.** In Python, `bool` is a subclass of `int`, so `True` behaves as the number 1.

```python
print(isinstance(True, int))
print(isinstance(True, bool))
print(isinstance(5, bool))
```

The output is `True`, `True` and `False`. If a function must reject booleans while accepting whole numbers, check `isinstance(x, bool)` before you check for `int`.

**4. Slicing.** A slice `start:stop:step` takes part of a sequence. The stop index is not included.

```python
word = "espresso"
print(word[:3])
print(word[-2:])
print(word[1:6:2])
```

The output is `esp`, `so` and `srs`. Index 0 is the first letter, and a negative index counts from the end. The step of 2 takes every second letter in the range.

**5. Running SQL with placeholders.** A `?` in the SQL is replaced by a value from a tuple, which keeps quotes and user input out of the SQL text.

```python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE sale (cafe TEXT, cups INTEGER)")
conn.executemany("INSERT INTO sale VALUES (?, ?)",
                 [("Market", 12), ("Harbour", 7), ("Market", 9)])
rows = conn.execute("SELECT cups FROM sale WHERE cafe = ? ORDER BY cups",
                    ("Market",)).fetchall()
print(rows)
conn.close()
```

The output is `[(9,), (12,)]`. `executemany` runs the same INSERT once for each tuple. Even with one value, the placeholder values must be in a tuple, which is why `("Market",)` has a trailing comma. `fetchall()` returns a list of tuples, one tuple per row, even when the query asks for one column.

**6. A window that numbers all rows.** Without `PARTITION BY`, the whole result is one group.

```python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE match_score (player TEXT, points INTEGER)")
conn.executemany("INSERT INTO match_score VALUES (?, ?)",
                 [("Asha", 30), ("Ravi", 45), ("Meena", 30)])
sql = """
    SELECT player, points,
           ROW_NUMBER() OVER (ORDER BY points DESC, player ASC) AS place
    FROM match_score
"""
print(conn.execute(sql).fetchall())
conn.close()
```

The output is `[('Ravi', 45, 1), ('Asha', 30, 2), ('Meena', 30, 3)]`. Every row gets a number, and the ORDER BY decides which row is first. The second key, `player ASC`, breaks the tie between the two 30s. Adding `PARTITION BY` would restart the numbering inside each group.

**7. A moving average with a frame.** A frame gives each row its own set of neighbours. This example uses a step counter, not the lab's data.

```python
import sqlite3

conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE steps (day INTEGER, count INTEGER)")
conn.executemany("INSERT INTO steps VALUES (?, ?)", [(1, 100), (2, 300), (3, 200)])
sql = """
    SELECT day,
           ROUND(AVG(count) OVER (
               ORDER BY day
               ROWS BETWEEN 1 PRECEDING AND CURRENT ROW
           ), 2) AS avg_2
    FROM steps
    ORDER BY day
"""
print(conn.execute(sql).fetchall())
conn.close()
```

The output is `[(1, 100.0), (2, 200.0), (3, 250.0)]`. Day 1 has no earlier row, so its average is its own count. Day 2 averages 100 and 300. Day 3 averages 300 and 200. The first row is not dropped, because the frame simply holds fewer rows at the start.

**How the ideas map to the two functions.** `top_n_per_station` needs items 1, 2, 5 and 6: a sort with several keys, a rounding step at the end, a placeholder if you filter, and a window numbered within each group. `rolling_avg` needs items 2, 5 and 7: a filter with a placeholder, a frame over ordered rows, and rounding at the end.

### The rules people miss

Each row below is a rule from the statement, or a case the statement's rules imply. The last column is a check you can run on your own output.

| Rule in the statement | What a careless solution does | How to check yours |
|---|---|---|
| Top `n` readings for each station | Takes the top `n` across all stations, so one busy station fills the list | Count the rows for each station in your output. No station should have more than `n` rows. |
| A station with fewer than `n` readings | Pads the list, repeats a row, or raises an error | Use a station with one reading and `n` set to 2. The function should return that one reading. |
| A station or pollutant with no rows | Raises an error, or returns `None` instead of an empty list | Call `rolling_avg` with a station that does not exist. The result must be `[]`. |
| Ordered by `value` descending | Sorts ascending, or sorts the values as text | The first row of each station must be that station's highest value. |
| Ties on `value` | Gives the tied readings in an order you did not choose | Put two equal readings in one station. The earlier `ts` must come first. |
| Output ordered by `station_id`, then `value` descending, then `ts` ascending | Relies on the order in which SQL happened to return the rows | Print the result and read the three sort keys in the order listed. |

### Worked twin problem

This problem is set in a different domain, with different data. It needs the same skills: a top-N per group, a frame over ordered rows, and a filter that keeps only full windows.

**Scenario.** A city bike scheme records how many bikes leave each dock in each hour. The planning team wants the busiest hours for each dock, and a trailing total that shows how many bikes left over a few hours in a row. Compute both in SQL with window functions, using the standard library `sqlite3` module.

Write two functions.

- `busiest_hours(trips, n)` takes `trips`, a list of `(dock, hour, bikes)` tuples, where `hour` and `bikes` are whole numbers. For each dock, it returns the top `n` hours by `bikes`, highest first. Ties on `bikes` go to the earlier hour. The result is a list of `(dock, hour, bikes)` tuples, ordered by `dock` ascending, then `bikes` descending, then `hour` ascending. Use `ROW_NUMBER()` inside a subquery.
- `trailing_sum(trips, dock, window)` takes the same list, a dock name and a whole number `window`. For that dock only, it returns `(hour, total)` tuples in hour order, where `total` is the sum of `bikes` over the current hour and the `window - 1` hours before it. Only full windows count, so the first `window - 1` hours produce no tuple. An unknown dock, or a dock with too few hours, returns `[]`.

```python test
import sqlite3


def make_db(trips):
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE trip (dock TEXT, hour INTEGER, bikes INTEGER)")
    conn.executemany("INSERT INTO trip VALUES (?, ?, ?)", trips)
    return conn


def busiest_hours(trips, n):
    conn = make_db(trips)
    sql = """
        SELECT dock, hour, bikes
        FROM (
            SELECT dock, hour, bikes,
                   ROW_NUMBER() OVER (
                       PARTITION BY dock
                       ORDER BY bikes DESC, hour ASC
                   ) AS rn
            FROM trip
        )
        WHERE rn <= ?
        ORDER BY dock ASC, bikes DESC, hour ASC
    """
    result = conn.execute(sql, (n,)).fetchall()
    conn.close()
    return result


def trailing_sum(trips, dock, window):
    conn = make_db(trips)
    sql = f"""
        SELECT hour, total
        FROM (
            SELECT hour,
                   SUM(bikes) OVER (
                       ORDER BY hour
                       ROWS BETWEEN {window - 1} PRECEDING AND CURRENT ROW
                   ) AS total,
                   COUNT(*) OVER (
                       ORDER BY hour
                       ROWS BETWEEN {window - 1} PRECEDING AND CURRENT ROW
                   ) AS n_in_window
            FROM trip
            WHERE dock = ?
        )
        WHERE n_in_window = ?
        ORDER BY hour
    """
    result = conn.execute(sql, (dock, window)).fetchall()
    conn.close()
    return result


trips = [
    ("Dock A", 7, 5), ("Dock A", 8, 9), ("Dock A", 9, 9), ("Dock A", 10, 4),
    ("Dock B", 7, 3), ("Dock B", 8, 6),
]

assert busiest_hours(trips, 2) == [
    ("Dock A", 8, 9), ("Dock A", 9, 9), ("Dock B", 8, 6), ("Dock B", 7, 3),
]
assert busiest_hours(trips, 1) == [("Dock A", 8, 9), ("Dock B", 8, 6)]
assert busiest_hours([], 2) == []

assert trailing_sum(trips, "Dock A", 1) == [(7, 5), (8, 9), (9, 9), (10, 4)]
assert trailing_sum(trips, "Dock B", 2) == [(8, 9)]
assert trailing_sum(trips, "Dock B", 3) == []
assert trailing_sum(trips, "Nowhere", 2) == []
assert trailing_sum([], "Dock A", 2) == []
```

**Explanation, line by line.**

- `import sqlite3` loads the standard library module. No installation is needed.
- `make_db` opens a new in-memory database for each call, so the tests never share data. It creates the table `trip` with three columns, then loads every tuple with `executemany`. Each `?` takes one value from the tuple.
- In `busiest_hours`, the inner query numbers the rows of each dock. `PARTITION BY dock` restarts the numbering for each dock. `ORDER BY bikes DESC, hour ASC` puts the busiest hour first and gives the earlier hour the lower number when two hours tie. For Dock A, hours 8 and 9 both have 9 bikes, so hour 8 gets number 1 and hour 9 gets number 2.
- `WHERE rn <= ?` keeps the top `n` rows. The tuple `(n,)` supplies the value for the placeholder.
- The outer `ORDER BY` gives the output order the statement asks for. Running `busiest_hours(trips, 2)` returns four tuples, two for each dock.
- In `trailing_sum`, the frame size depends on `window`, so an f-string places `window - 1` into the SQL text. This is safe here because `window` is a whole number that the caller controls. The dock name never goes into the text. It is passed through a `?` placeholder.
- `SUM` and `COUNT` use the same frame. `COUNT(*)` counts the rows in each frame. For Dock A with `window` 3, hour 7 has one row in its frame, hour 8 has two, and hours 9 and 10 have three.
- `WHERE n_in_window = ?` keeps only the rows whose frame is full. Dock A at hour 9 has the frame 5, 9 and 9, which sums to 23. Dock A at hour 10 has the frame 9, 9 and 4, which sums to 22. Those are the two values in the first assert.
- The last asserts check the edge cases: an empty list, a window of 1, a dock with too few hours, and a dock that is not in the data.

Running the file prints nothing when every assert passes. If an assert fails, Python shows the line number of the failing check.

```python test
import sqlite3


def longest_loan_per_shelf(loans):
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE loan (shelf TEXT, title TEXT, days INTEGER)")
    conn.executemany("INSERT INTO loan VALUES (?, ?, ?)", loans)
    sql = """
        SELECT shelf, title, days
        FROM (
            SELECT shelf, title, days,
                   ROW_NUMBER() OVER (
                       PARTITION BY shelf
                       ORDER BY days DESC, title ASC
                   ) AS rn
            FROM loan
        )
        WHERE rn = 1
        ORDER BY shelf
    """
    result = conn.execute(sql).fetchall()
    conn.close()
    return result


def gap_days(log, member):
    conn = sqlite3.connect(":memory:")
    conn.execute("CREATE TABLE visit (member TEXT, day INTEGER)")
    conn.executemany("INSERT INTO visit VALUES (?, ?)", log)
    sql = """
        SELECT day - LAG(day) OVER (ORDER BY day) AS gap
        FROM visit
        WHERE member = ?
        ORDER BY day
    """
    gaps = [row[0] for row in conn.execute(sql, (member,)) if row[0] is not None]
    conn.close()
    return gaps


loans = [
    ("Fiction", "Dune", 14), ("Fiction", "Emma", 14), ("Fiction", "Beloved", 9),
    ("History", "Spqr", 21), ("History", "Ulysses", 7),
]
log = [("ana", 3), ("ana", 10), ("ben", 4), ("ana", 15), ("ana", 16)]

assert longest_loan_per_shelf(loans) == [("Fiction", "Dune", 14), ("History", "Spqr", 21)]
assert longest_loan_per_shelf([]) == []
assert gap_days(log, "ana") == [7, 5, 1]
assert gap_days(log, "ben") == []
assert gap_days(log, "cy") == []
assert gap_days([], "ana") == []
assert gap_days(list(reversed(log)), "ana") == [7, 5, 1]
```

**Why it works.** `ROW_NUMBER` with `title ASC` as the second key picks one loan per shelf, and the tie on 14 days goes to Dune. In `gap_days`, `WHERE` runs before the window, so `LAG` only sees one member's visits. The first visit has no previous row, so its gap is NULL, and the list comprehension drops it. The `ORDER BY` inside `OVER` makes the result independent of the order of the input.
