## What the quiz tests

The Day Quiz has ten case-study multiple-choice questions. There is one question for each topic in this section, asked in the same order. Each question gives you a short scenario about a team running CityPulse, and then asks what the team should conclude or do next. The pass mark is 70%, which means seven correct answers out of ten. Your skill score is kept from your first attempt.

Each question is built around a decision, not a definition. Use the same routine on every question:

1. Read the last line first. It tells you what is asked: a cause, a number, a next step or the best description.
2. Reread the scenario and underline the facts that matter, such as the status codes, the window length, the target, the latency limit and the counts.
3. Eliminate options that are true in general but do not fix this scenario. A correct definition can still be the wrong answer.
4. Watch the qualifier words. "Most" asks for the likeliest cause, "first" asks for the earliest step and "best" asks you to choose between two reasonable answers.
5. Check the numbers. If a question gives counts or percentages, work the arithmetic on paper before you choose.

### Structured logging

**What it is.** A log is a record that a program writes about what it did, usually one line for each event. A structured log line is a JSON object: a set of named fields inside curly braces, such as `{"path": "/v1/predict", "status": 200, "latency_ms": 48.1}`. Each name is a key, and a log tool treats each key as a column, in the same way that a spreadsheet treats the heading of a column.

The same event can be written as plain text or as structured data. Both of the lines below describe one failed request.

```text
Plain text: request to /v1/predict failed with status 503 after 812 ms
Structured: {"path": "/v1/predict", "status": 503, "latency_ms": 812}
```

A tool can filter the structured line with a test such as `status >= 500`, because `status` is a field that holds a number. The plain text line has no such field. Cloud Logging stores each JSON line under `jsonPayload` and each plain text line under `textPayload`, so a filter on a named field only finds the JSON lines.

**How it shows up in a case study.** The CityPulse squad keeps a saved query that counts server errors: `jsonPayload.status>=500` over the last 24 hours. On Tuesday the query shows 14 errors. The BBMP dashboard team reports 31 failed requests for the same day, and someone suggests that the query is broken. The squad searches the logs and finds 17 lines that begin with the word `ERROR` and are not JSON. A `print()` statement in an error handler wrote them. The right decision is to change the handler so that it writes a JSON line with a status field, and to keep the query as it is.

:::trap Blaming the query
A filter cannot find lines that are not in the field it reads. The tempting wrong answer is to rewrite the query with a different operator, which changes nothing. Fix the lines the program writes, and keep the query.
:::

```quiz
Q: The squad's saved filter jsonPayload.status>=500 shows 14 server errors for Tuesday, but the load balancer reports 31 failed requests. A review finds 17 error lines that begin with ERROR and are not JSON. What most likely explains the gap?
- The load balancer counts requests that clients cancelled, which the service never logs.
* The 17 plain text lines are stored in textPayload, so the jsonPayload filter never matches them.
- Cloud Logging keeps only the first 14 errors of each day.
- The status field is stored as text, so the greater-than-or-equal comparison cannot match it.
WHY: Plain text lines land in textPayload, not jsonPayload, so a filter on a JSON field cannot see them. The cancelled-request idea is tempting, but it does not explain 17 error lines that the service did write. Retention is about age, not format, and the JSON status fields are numbers.

Q: A developer wants a chart of successful uploads each day. Some log lines are written as JSON with a status field, and others are written as a sentence such as upload ok with status 201. Which change makes the chart reliable?
* Write every request line as JSON with the same keys, so the chart can filter on the status field.
- Add the word ok to the sentence lines, so a text search can find them.
- Make the sentence lines longer, so that each line is unique in the log.
- Chart the textPayload field, because it holds more detail than jsonPayload.
WHY: Consistent JSON keys turn status into a column that the chart can filter on every time. Adding words to sentence lines still gives the tool nothing reliable to parse. The textPayload option is the trap, because the sentence is there, but without a named status field it cannot be counted precisely.

Q: A log entry reads Request handled in 48 ms and nothing else. An engineer wants to find all slow requests over 500 ms next week with one filter. What should the log line contain?
- A longer description of what the handler did with the request.
* A field named latency_ms with a number, written as part of a JSON object.
- The word slow, whenever a request takes more than half a second.
- A copy of the request body, so that the duration can be checked later.
WHY: A filter needs a named numeric field to compare, so latency_ms as a number inside JSON is what makes the threshold testable. A sentence containing the word slow is still text, and a request body adds data without a duration. The tempting answer is the longer description, which reads well for people but gives the tool nothing to compare.
```

### Correlation id

**What it is.** A correlation id is a value that the program attaches to every log line written while it handles one request. In CityPulse this is the `request_id` field. Each part of the system writes its own lines, and the shared `request_id` collects them. The id is created once and passed along with the request.

Here is what three lines with the same id might look like after a filter on that id:

```text
{"request_id": "7f3a", "service": "api", "path": "/v1/upload", "status": 202}
{"request_id": "7f3a", "service": "queue", "event": "job enqueued", "latency_ms": 12}
{"request_id": "7f3a", "service": "worker", "event": "job done", "latency_ms": 940}
```

A correlation id is not a count, a rate or a percentile. It is a label that connects lines, which is why it is the first thing to search when one user reports one failure.

**How it shows up in a case study.** A user reports that a prediction took nine seconds, and the request id is `c81e`. The squad filters the logs on that id and finds three lines, one each from the API, the feature service and the model service. The model service line shows 8,700 ms, while the other two show about 30 ms each. The decision is to investigate the model service for that request, and to check whether other requests with a long model step share the same cause.

:::trap Reading one id as a user
A `request_id` groups the lines of one request, not all requests from one user. The tempting wrong answer is to assume that the id shows a user's whole history, which it does not.
:::

```quiz
Q: A checkout passes through three services, and each writes a log line with the same request_id. A user reports a nine-second wait. Which question can the team answer with that shared field?
- How many users used the checkout feature this week.
- What the 99th percentile latency was across all checkouts.
* Which step of that one request spent the nine seconds.
- Whether the payment provider's fraud model has become less accurate.
WHY: A shared request_id ties together the lines of one request, so the team can see where the time went. Counts and percentiles need many requests, and model accuracy is not written into a request log. The percentile is the tempting option, but it describes all requests rather than the one the user reported.

Q: A junior engineer proposes setting request_id to the customer's account number, so that all requests from one customer can be found together. Which statement is correct?
* A request_id should be unique to each request and copied to every line of that request, so that it groups one request, not one customer.
- A request_id should be the same for every request a customer makes, so the customer's history can be found.
- A request_id should be the account number, because that keeps the logs private.
- A request_id should change each time a line is written, so that no two lines look alike.
WHY: The id is created once per request and copied to each line that the request produces. Setting it to the account number would merge every request from that customer, which is the trap in the second option. It would also put a personal identifier into logs that many people can read.

Q: A support engineer searches for request_id 7f3a. The search returns six lines from three different services, all within 200 ms of each other. The engineer asks why one request appears in several services. Which answer is best?
- The id was reused by another user, so the lines belong to several people.
- The services copied the status code into the id by mistake.
- The request was retried five times, so the logs hold five copies of the same line.
* The request passed through three services, and each one wrote its lines with the id it received.
WHY: The id travels with the request from service to service, so every service that handles the request writes the same value. Reuse by another user would be a design fault, not the normal case. The retry option is tempting, but retries do not explain lines from three different services, and a status code cannot be an id.
```

### SLO definition

**What it is.** A service level objective, or SLO, is a numeric target for a measured ratio, such as the share of good requests. A complete SLO has three parts. It names the measure, gives the number that must be reached, and states the time window over which the number is judged. For example, 99% of `/v1/predict` requests are not 5xx and finish under 500 ms, over a rolling 7 days. The SLO is a promise that someone can check, so it should also name the query that measures it.

The SLO is the promise, and the SLI is what the service achieved.

**How it shows up in a case study.** A CityPulse engineer writes this target in the design document: the prediction endpoint should be reliable most of the time. The dashboard team cannot check that sentence, and the squad cannot decide what to do when it is broken. A reviewer asks the squad to rewrite it with a measure, a number, a window and the query. The rewritten SLO says 99% of prediction requests are not 5xx and finish under 500 ms over seven days, and the query is stored in `docs/queries`.

:::trap A target of always
Writing always or 100% sounds strong, but no real service meets it, and it leaves no budget for any change. A good SLO is strict and achievable.
:::

```quiz
Q: The design document says the prediction endpoint should be reliable most of the time. Which change turns this into a proper SLO?
* State a measure, a number and a window, such as 99% of /v1/predict requests not 5xx over 7 days, and name the query that measures it.
- Replace most of the time with always, so that the promise is stronger.
- Add a sentence saying that the team will try hard to meet it.
- Move the target to the CPU dashboard, so that the team sees it every day.
WHY: A proper SLO has a measured ratio, a number, a window and the query that measures it, so anyone can reproduce the result. Always is a 100% target, which cannot be met, and it is the tempting wrong answer. Trying hard and moving the target to another dashboard do not make the promise checkable.

Q: A team sets its SLO for a booking service at 100% of requests not 5xx over 30 days, so that customers are never let down. Which criticism is most accurate?
- It is too easy to meet, so customers will see many errors.
- It measures the wrong endpoint, so it should move to the health check.
* No real service can meet it, and it leaves no budget for deploys, so the first failure breaks the promise and the team has nothing left to spend.
- It uses a window that is too long, so the team cannot see changes quickly.
WHY: A 100% target allows zero failures, so the first failure breaks the promise, and there is no budget left for planned change. The too-easy option is backwards, because 100% is the hardest possible target. A 30-day window is a reasonable length for most services.

Q: An SLO says 99.5% of requests over 30 days are good. Which item is still needed before someone can check the number next Friday?
- A bigger dashboard with more colours, so that the number is easier to read.
- A longer window, such as one year, so that short spikes do not matter.
* The exact query that counts good and valid requests over the window, with today's measured value written beside the target.
- A promise that the team will tell customers about every failure.
WHY: A target without its query cannot be reproduced, so nobody can check it on Friday. A dashboard, a longer window or a customer message does not make the number checkable. The longer window is the tempting answer, but the length of the window does not make a target measurable.
```

### SLI definition

**What it is.** A service level indicator, or SLI, is a measured ratio. It counts good events and divides them by valid events, and it is usually shown as a percentage. The course defines the SLI for `/v1/predict` as the share of valid requests that are not 5xx and finish under 500 ms. Valid requests are the prediction requests that are not client errors, and the health check is excluded from the count entirely. The ratio is what makes an SLI useful, because it shows how many events went well, not just how fast the average event was.

An SLI must name its events, and the definition must be written down with the number.

**How it shows up in a case study.** An uploads team measures its SLI as the average response time over the last hour. The average is 42 ms, and the team says the service is healthy. A squad member points out that the average is not a ratio of good events, so it does not count requests at all. The right decision is to replace the average with a ratio, such as the share of uploads that are not 5xx and finish under the limit, and to write the valid events beside it.

:::trap Counting the health check
The health check is fast and always succeeds, so counting it inflates the SLI. Exclude it from the valid events before you compute the ratio.
:::

```quiz
Q: An engineer defines the SLI for the uploads endpoint as the average response time over the last hour. Which problem matters most?
- The average is reported in seconds, while the target is in milliseconds.
- The average cannot be computed from logs at all.
- The average includes the health check, which is the only problem.
* The average is not a ratio of good events over valid events, so it does not count requests and can hide a slow tail.
WHY: An SLI is a ratio of good events to valid events. The average does not count events, and a small number of very slow requests can leave it looking healthy. The unit and the log source are not the main problem. The health check is a separate issue, and it would not fix an average either.

Q: Valid requests exclude client errors and the health check. In one hour there are 1,200 requests to /v1/predict. Of these, 40 return 422 and 6 return 503, and the rest return 200 within 500 ms. Using the course definition, what is the SLI?
- 96.17%
* 99.48%
- 99.50%
- 99.99%
WHY: Removing the 40 client errors leaves 1,160 valid requests. Six of those are 503s, so 1,154 are good, and 1,154 divided by 1,160 is 99.48%. The tempting option 96.17% divides by all 1,200 requests, which keeps the client errors in the denominator. The option 99.50% counts the client errors as good, which breaks the definition the other way.

Q: A dashboard shows the /v1/predict SLI at 99.99%, but users complain about slow answers. The query includes the /v1/health endpoint, which takes 2 ms and never fails. What should the team do?
- Keep the query, since more events make the SLI more accurate.
- Lower the target to 99.9%, so that the dashboard matches what users say.
* Exclude /v1/health from the valid events and recalculate the SLI.
- Replace the SLI with the average latency of both endpoints.
WHY: The health check is fast and always succeeds, so it inflates the ratio and hides the slow answers that users see. Excluding it changes the valid events, which is the real fix. Lowering the target hides the problem, and an average does not count events.
```

### Error budget

**What it is.** The error budget is the number of failures that an SLO allows. It equals `(100 - SLO)` percent of the valid requests in the window. For a 99.5% SLO over 5,000 valid requests, the allowed share is 0.5%, which is 25 requests. The budget is a count, not a percentage, even though it is worked out from one. Each failure that happens in the window is subtracted from the budget. What remains tells the team whether it can ship features or must spend its time on reliability.

The budget is useful only when the team agrees in advance what happens at each level.

**How it shows up in a case study.** A CityPulse SLO of 99.9% covers 40,000 valid requests in a 30-day window. The budget is therefore 0.1% of 40,000, which is 40 failures. Halfway through the window the squad has 15 failures. The budget left is 25 failures, so about 62% of it remains. The decision is to keep shipping and watch the burn.

:::trap A budget read as a percentage
A 99.5% SLO over 5,000 requests allows 0.5% of 5,000, which is 25 failures. It does not allow 0.5 failures. Always convert the percentage into a count.
:::

```quiz
Q: An SLO of 99.9% covers 40,000 valid requests in a 30-day window, and 15 failures have happened so far. How many failed requests does the budget still allow?
* 25
- 40
- 15
- 400
WHY: The budget is 0.1% of 40,000, which is 40 failures, and 15 have been spent, so 25 remain. The total budget is 40, not what is left. The option 400 uses 1% instead of 0.1%, which is a common scaling error.

Q: A team's monthly budget is 60 failed requests, and it has already had 75. The squad has agreed a rule in advance for this situation. What should the squad do?
- Keep shipping, because an overspend is only a number and reliability work can wait until next month.
- Lower the SLO, so that the budget becomes positive again.
* Stop new features and put reliability work first, because the budget is overspent.
- Ask the dashboard team to remove the failures from the logs.
WHY: When the budget is spent, the agreed rule is to stop features and fix reliability. Hiding the overspend by lowering the SLO changes the promise rather than the service, and removing logs destroys the evidence. The keep-shipping option is tempting because the number looks small, but the rule was agreed to prevent exactly that.

Q: An engineer reads the budget for a 99.5% SLO as 0.5 failed requests instead of a count. The window has 2,000 valid requests. What is the budget in requests?
- 0.5
* 10
- 2
- 200
WHY: The budget is 0.5% of 2,000, which is 10 requests. The number 0.5 is the percentage, not the count. The number 2 is 0.1% of 2,000, and 200 is 10% of the window, so both are the wrong share.
```

### Latency percentiles

**What it is.** A percentile is the value below which a given share of sorted values falls. The 95th percentile, or p95, is the value that 95 out of 100 requests beat. The p99 is the value that 99 out of 100 requests beat, and it shows the slow tail that a small number of users feel. To find the nearest-rank percentile, you sort the values from smallest to largest, compute the rank as `ceil(p × n / 100)`, and take the value at that position, counting from 1. The `ceil` function rounds up to the next whole number, so a rank of 8.55 becomes 9.

Alerts and SLOs use tail percentiles because averages hide the tail.

**How it shows up in a case study.** Nine valid requests in one hour took 40, 45, 48, 52, 55, 60, 61, 70 and 900 ms. The squad asks what the p95 is, because the alert is set on p95. The rank is `ceil(0.95 × 9)`, which is `ceil(8.55)`, so the rank is 9 and the answer is 900 ms. The decision is to report 900 ms, and to look at the single slow request.

:::trap Truncating instead of rounding up
Using `int(0.95 × 9)` gives 8 and picks the value 70 ms. Nearest rank needs `ceil`, which gives 9. The mistake is common when the sample is small.
:::

```quiz
Q: Nine valid requests in an hour took 40, 45, 48, 52, 55, 60, 61, 70 and 900 ms. Using the nearest-rank method, what is the p95?
- 70
- 61
- 55
* 900
WHY: The rank is ceil(95 × 9 / 100), which is ceil(8.55), so the rank is 9 and the answer is the largest value, 900. Truncating 8.55 to 8 gives the eighth value, 70, which is the tempting wrong answer. Nearest rank always rounds the rank up.

Q: A service has 20 requests, with latencies of 1, 2 and so on up to 20 ms, one of each. What is the nearest-rank p95?
* 19
- 20
- 18
- 10
WHY: The rank is ceil(0.95 × 20), which is 19, and the 19th smallest value is 19 ms. The maximum, 20, is the tempting answer for anyone who rounds the percentile up to the largest value. The value 18 is one rank short, which happens when the rank is not rounded up.

Q: A dashboard shows an average latency of 48 ms and a p99 of 900 ms for the same hour. A product manager asks which figure should drive the alert. Which answer is best?
- The average, because it is smaller and fewer alerts will fire.
* The p99, because it shows the slow tail that users feel, while the average can look healthy even when some requests are very slow.
- Neither, because percentiles cannot be used in alerts.
- The maximum only, because the maximum is always the same as the p99.
WHY: The p99 shows the slow tail, and an average can hide it. Alerts and SLOs are commonly set on tail percentiles, so the third option is wrong. The maximum equals the p99 only when the sample is tiny, so the fourth option is not a rule. The average is the tempting choice because it is smaller and easy to read.
```

### Alerting and burn rate

**What it is.** Burn rate is how fast the error budget is being spent, compared with the steady pace that would use exactly the whole budget by the end of the window. If the window is 30 days and the budget is 600 failures, the steady pace is 20 failures a day. A burn rate of 1 means the budget runs out exactly at the end of the window. A burn rate of 10 means the budget would run out in a tenth of the time. A burn rate of 0.5 means the budget would last twice as long.

Burn-rate alerts warn early when the budget is spent too quickly.

**How it shows up in a case study.** An SLO has a 30-day window and 600 allowed failures. In the last six hours the team has had 150 failures. The steady pace is 600 divided by 720 hours, which is about 0.83 failures an hour. The actual pace is 25 failures an hour, so the burn rate is 25 divided by 0.83, which is about 30. The decision is to page the squad now, because at this rate the whole monthly budget would be spent in a single day.

:::trap Reading the rate as a share used
A burn rate describes a pace, not the total spent so far. Half the budget may be gone while the burn rate is low, and a high burn rate may still leave most of the budget intact.
:::

```quiz
Q: An SLO has a 30-day window and allows 600 failures. In the last six hours the team has had 150 failures. Roughly what is the burn rate?
- 5
- 15
* 30
- 0.25
WHY: The steady pace is 600 over 720 hours, about 0.83 failures an hour. The actual pace is 25 an hour, and 25 divided by 0.83 is about 30. The option 0.25 is the share of the budget used, which is not the same as a rate against the steady pace. The option 5 is the steady-pace amount for six hours, not a rate.

Q: An alert fires when a single five-minute window shows a 1% error rate. Overnight traffic is low, and a handful of failed requests can push the rate over 1%. What is the best change?
- Alert on every failed request, so that nothing is missed.
- Alert only when the whole monthly budget is gone.
- Remove the alert and check the dashboard each morning.
* Alert on a burn rate measured over a longer window, with a short check to confirm that the problem is still happening.
WHY: A longer window smooths out noise from low traffic, and the short check confirms that the burn is current. Alerting on every failure creates noise, and waiting for the monthly budget to run out is too late. Removing the alert leaves the team unaware until the morning.

Q: A team's 30-day SLO has a burn rate of 0.5. What does that mean?
- The budget will run out in 15 days.
- The team has already used half of its budget.
* At this pace, only half of the budget is used by the end of the 30 days.
- The budget will run out in 10 days.
WHY: A burn rate of 1 uses the budget exactly over the window, so 0.5 uses half of it by the end. The tempting answer reads the rate as a share already spent, but the rate describes a future pace, not the total so far. The 15-day and 10-day options wrongly say the budget runs out inside the window, which would need a burn rate above 1.
```

### Observability pillars

**What it is.** Observability is the ability to work out what a running system is doing from the records it leaves behind. The three commonly named pillars are logs, metrics and traces. Logs record individual events, one record for each thing that happened. Metrics are numbers summed or averaged over time, such as a count of requests per minute, and they are cheap to store and chart over long periods. Traces follow one request across several services and record the time each step took. 

The course uses logs and metrics, and adds an outside uptime check.

**How it shows up in a case study.** A monthly review asks how the number of failed checkouts has changed over the past six months. The engineer wants a chart. The right tool is a metric, because the question is a trend of a count over time, and a metric is cheap to query over a long period. Logs could answer the question, but they would need to be scanned event by event. A later question asks why one checkout took twelve seconds and which downstream call caused it. That needs a trace, because only a trace follows one request across the services and shows where its time went.

:::trap Using logs for trends
Logs are the right tool for one event, and a poor tool for a long trend. The tempting answer is to scan logs for the trend, which is slower and more expensive than a metric.
:::

```quiz
Q: A team wants to show how the number of checkout failures has changed over the last six months in a monthly review. Which pillar is the best tool?
* Metrics, because they are numbers summed over time and are cheap to chart over long periods.
- Logs, because every event can be read one by one for six months.
- Traces, because they follow each checkout across the services.
- Health checks, because they run every minute and show the trend.
WHY: Metrics aggregate numbers over time and are cheap to chart across months. Logs can answer the question but are slower and costlier for a trend. Traces follow single requests, and health checks say whether a service answers now, not how a count has changed.

Q: A customer says one checkout took twelve seconds. The checkout calls a pricing service and then a payments service, and the squad needs to know which call was slow for that request. Which pillar answers this?
- Metrics, because a counter of checkouts shows which call was slow.
- Health checks, because they report the speed of each downstream call.
* Traces, because a trace follows one request across the services and records the time each step took.
- A monthly SLO report, because it lists every checkout with its time.
WHY: A trace follows one request through each service and records how long each step took. Metrics show totals and rates across requests, and a health check says only whether a service works. The metrics option is tempting, because it shows that checkouts were slow overall, but it cannot say which call was slow for this one request.

Q: An engineer uses logs to draw a chart of CPU usage every five seconds for the past year. Which change is most sensible?
- Keep using logs, because logs are always the cheapest option.
- Read the CPU usage from a single log line each year.
- Replace the chart with a list of every request the server handled.
* Record CPU usage as a metric and chart the metric.
WHY: CPU usage is a number sampled over time, which is exactly what a metric is for. Logs are expensive to scan over a year, so the first option is wrong. A list of requests does not show CPU use at all, and one log line a year cannot make a trend.
```

### Health checks

**What it is.** A health check is an endpoint that an outside checker calls to test whether the service works. In CityPulse this is `/v1/health`. The checker sends a request on a schedule, and it passes only if the answer is correct. A status code alone is not always enough, because an error page can arrive with status 200. The course check therefore also requires the body to contain the word `ok`. A health check is useful only when it tests something real. If it always answers ok without touching anything the service depends on, the check passes while users fail.

**How it shows up in a case study.** A health endpoint returns 200 and the body `ok`, but it never calls the database. One afternoon the database connection breaks, and every prediction request fails. The uptime checker still reports UP, because the endpoint does not depend on the database. The squad decides to make the check exercise the dependency, for example by running a small read with a short timeout.

:::trap The check that never checks
An endpoint that always returns ok without testing its dependencies lets the check pass while users fail. The tempting fix is to change the timeout or the frequency, which does not touch the real gap.
:::

```quiz
Q: A health endpoint returns 200 and the body ok, but it never touches the database. The database connection breaks, and users see errors while the uptime checker keeps reporting UP. What is the flaw?
- The check runs too often, so it hides the database failure.
* The endpoint tests nothing the service depends on, so the check passes while users fail.
- The check has a timeout, so slow database calls are cut off.
- The body should be JSON, not plain text.
WHY: A health check is useful only when it tests what users need. The frequency and timeout are settings, and they are not the cause of a check that never reaches the database. The JSON question is a separate design choice. The timeout is the tempting answer, but a generous timeout would not help an endpoint that never calls the database.

Q: The uptime check requires only status 200 and never reads the body. A bad deploy makes the service return a 200 error page whose body says Service unavailable. What is the right fix?
- Remove the timeout, so the checker waits longer for a reply.
- Alert after ten failures instead of two.
- Check the checker's own address on each run.
* Also require the body to contain the expected text, such as ok, and fail the check otherwise.
WHY: A status-only check passes on a 200 error page, so matching the body catches the wrong answer. Waiting longer or raising the failure count makes the alert slower and still does not catch a wrong answer. The checker's address is irrelevant to what the response says.

Q: The squad wants a health check that tells a load balancer when to stop sending traffic to one container. Which design is most suitable?
* A check that answers quickly with ok only when the container can handle requests, which tests its required dependencies within a short timeout.
- A check that writes a long report of every log line from the past hour.
- A check that waits until the monthly error budget is spent before it answers.
- A check that always returns 200, so that no container is ever removed.
WHY: A health check should report, quickly and correctly, whether this instance can serve requests. A long report, a budget check or an always-200 check each fails that purpose. The always-200 check is the trap, because it hides broken containers from the load balancer.
```

### Counter versus gauge

**What it is.** A counter is a metric that only goes up. The total number of requests is a counter. It resets to zero when the process restarts, so you read it as a rate of change, such as requests per minute, rather than as a level. A gauge is a metric that can go up and down, such as the number of jobs waiting in a queue or the number of open connections. You read a gauge as its current value at each moment.

**How it shows up in a case study.** A worker exposes a metric called `jobs_processed_total`. After each deploy the metric drops to zero, and a colleague says the metric is broken. The squad recognises the metric as a counter, which resets when the process restarts. The right decision is to read the rate of increase, and to ignore the drop at the deploy. A second metric, `jobs_waiting`, rises and falls with the queue. The squad should read that as a gauge, showing the current queue length.

:::trap The reset is not a fault
A counter that drops to zero after a restart is normal. The tempting error is to call such a metric a gauge, or to report the drop as a failure.
:::

## The graded lab

The graded lab is a Python problem with visible and hidden tests. You are given a starter file with three functions, and you must write their bodies so that the tests pass. This section explains the task in plain words, teaches the Python you need with examples unrelated to the lab, lists the rules people miss, and gives you a method. It also works through a twin problem in a different domain. A twin problem uses the same skills with different data, so you can practise without the answer to the real task.

Read the first two parts before you open the starter file.

### The task in plain words

**Scenario.** The CityPulse API publishes an SLO dashboard. You are given a list of request records, and from them you compute three numbers: availability, the error budget that is left, and the p95 latency. Each record is a dictionary with two keys. `status` is an integer HTTP status code, and `latency_ms` is a number of milliseconds. The statement shows this shape for every record, so assume both keys are present unless a visible test shows otherwise.

**The functions.** The starter file defines these three names, and you write their bodies.

- `availability(records)` returns a float. It is the percentage of records whose `status` is below 500, rounded to two decimal places with `round(..., 2)`.
 - Every record counts in the total.
 - A record counts as available when its status is below 500.
 - A 4xx status is below 500, so a 4xx record counts as available.
 - Empty input returns `0.0`.
- `error_budget_remaining(records, slo)` returns a float. `slo` is the target availability as a percentage, such as `99.0`.
 - The allowed error budget is `100 - slo`.
 - The actual error rate is `100 - availability`, as the statement defines it. The statement does not say whether `availability` here is the rounded value that the function returns or the unrounded percentage, and the two can differ in the last decimal. This is unclear in the course: ask your trainer which one the reference uses, and check the visible tests.
 - The result is the percentage of the budget that is still remaining, written as `round((allowed - error_rate) / allowed * 100, 2)`.
 - The result may be negative when the budget is overspent.
 - If `allowed` is zero or less, return `0.0`.
- `p95_latency(records)` returns a float. It is the 95th percentile of `latency_ms` over all the records, by the nearest-rank method.
 - Sort the latency values in ascending order.
 - Take the item at index `ceil(0.95 * n) - 1`, where `n` is the number of records.
 - Round the result to two decimal places.
 - Empty input returns `0.0`.

The statement gives one example. Two records, one with status 200 and one with status 503, give an availability of 50.0. Their p95 latency is 20.0, because the index is `ceil(1.9) - 1`, which is 1.

**Limits.** Your code may run for 30 seconds and use up to 128 MB of memory. Neither limit should matter for this task, unless your code does something very wasteful.

**Scoring.** The visible tests are worth 75 points in total. The statement gives them as follows.

| Test | Points |
|---|---|
| 19 of 20 OK gives 95.0% | 20 |
| All OK gives 100.0% | 10 |
| One 5xx of two gives 50.0% | 10 |
| Nearest-rank p95 of 4 samples | 20 |

**Hidden tests.** There are three hidden tests, worth 25 points in total. A hidden test is a check that the platform runs after you submit, and its inputs are not shown to you. The visible tests give you 75 points, so a solution that passes only the visible tests scores at most 75 out of 100. ### What each function needs

Each idea below is taught with a small example that has nothing to do with CityPulse. Use these examples to understand the idea, and then write the lab's functions yourself.

**Counting matches with a generator.** `sum(1 for x in items if test)` adds 1 for each item that passes the test. For example, `temps = [18, 25, 30]` and `sum(1 for t in temps if t > 20)` gives 2, because 25 and 30 pass. The `sum` adds only the 1s, so the result is a count.

**Empty input.** `len(items)` is 0 for an empty list, and dividing by it raises a `ZeroDivisionError`. Check for emptiness first with `if not items:` and return the value the statement asks for. The check `if not items` is True for an empty list and False otherwise.

**Percentages and rounding.** `2 / 3 * 100` is about 66.666..., and `round(2 / 3 * 100, 2)` gives 66.67. Round only when you return the answer, not partway through a calculation. Rounding early can change the second decimal place of the final result.

**Dictionary keys and get.** Given `pets = {"cat": 2}`, the expression `pets["cat"]` gives 2, and `pets.get("dog", 0)` gives 0 because the key is missing. A plain key lookup raises a `KeyError` when the key is absent, and `get` returns a default instead. The statement shows both keys in every record, so plain lookups are probably safe for this lab.

**Sorting with and without a key.** `sorted(["pear", "fig", "banana"], key=len)` gives `['fig', 'pear', 'banana']`, because the words are ordered by length. `sorted` returns a new list, and the original is unchanged. For example, if `scores = [3, 1, 2]`, then `ordered = sorted(scores)` gives `[1, 2, 3]`, and `scores` still reads `[3, 1, 2]`.

**Integer ceiling.** `import math` gives you `math.ceil`. For example, `math.ceil(7 / 3)` is 3, and `math.ceil(0.5)` is 1. The same answer without floats is `(7 + 3 - 1) // 3`, which is also 3. The integer version adds the divisor minus one before the floor division. Floating-point products such as `0.95 * n` may be a hair above or below a whole number, so a ceiling of them can jump by one. Test this with a list whose length makes the product whole.

**Floating-point tolerance.** Computer decimals are approximate. `0.1 + 0.2 == 0.3` gives `False`, but `round(0.1 + 0.2, 2) == 0.3` gives `True`. Compare floats with a tolerance when you test them, such as `abs(a - b) < 1e-9`, which means "closer than a billionth".

**Types: int, bool and float.** `isinstance(5, int)` is `True`. `isinstance(True, int)` is also `True`, because `bool` is a subclass of `int`. So a check for `int` cannot tell `True` from `1`. The check `type(True) is int` gives `False`. A function that is meant to return a float should return `float(x)` rather than `x`, because `round(20, 2)` returns the integer 20.

**Slicing.** `"parking"[2:5]` gives `'rki'`. The slice starts at index 2 and stops before index 5, so the item at index 5 is not included. Slices never change the original string or list.

**The median.** `statistics.median([5, 1, 3])` gives 3. For an even count, `statistics.median([1, 2, 3, 4])` gives 2.5, which is the mean of the two middle values. The lab uses a percentile rather than the median, but the idea of picking a value at a position in sorted data is the same.

**Returning None.** `None` means that there is no value. `result = None` followed by `result is None` gives `True`. Use `is None` to test for `None`, and not `== None`. The lab does not ask for `None`, so return the numbers the statement gives, such as `0.0`.

### The rules people miss

Each row is a rule from the statement, or a habit that protects you when the statement says nothing about it. Rows marked *(habit)* are not in the statement. Check every row with an `assert` before you submit.

| Rule in the statement | What a careless solution does | How to check yours |

### Worked twin problem

The twin problem uses a payments API instead of the CityPulse API. It needs the same skills: filtering, a ratio, a budget and a nearest-rank percentile. It is different in three places. It excludes client errors, it uses a different target, and it asks for the p99.

**Scenario.** A payments API writes one record for each request. Each record is a dictionary with `status`, an integer HTTP status code, and `latency_ms`, a number of milliseconds. Both keys are present in every record. A valid request is any request whose status is not 4xx. Write three functions.

- `success_percent(records)` returns a float: the percentage of valid requests whose status is below 500, rounded to two decimal places. If there are no valid requests, return `0.0`.
- `budget_spent_fraction(records, target=99.5)` returns a float: the number of failed valid requests divided by the number of failures that the target allows. The allowed failures are the number of valid requests times `(100 - target) / 100`. Round the result to four decimal places. If there are no valid requests, or the target is 100, return `0.0`.
- `p99_nearest_rank(records)` returns a float: the nearest-rank 99th percentile of `latency_ms` over the valid requests. Sort the values, take the rank `ceil(0.99 * n)`, and return the value at that rank counting from 1. If there are no valid requests, return `0.0`.

The test block below is the solution, with the helper `valid_payments` added. Try the problem yourself before you read on.

```python test
def valid_payments(records):
    """Requests that count against the service: everything except 4xx responses."""
    return [r for r in records if not 400 <= r["status"] <= 499]


def success_percent(records):
    valid = valid_payments(records)
    if not valid:
        return 0.0
    good = sum(1 for r in valid if r["status"] < 500)
    return round(good * 100 / len(valid), 2)


def budget_spent_fraction(records, target=99.5):
    valid = valid_payments(records)
    allowed_share = 100 - target
    if not valid or allowed_share <= 0:
        return 0.0
    bad = sum(1 for r in valid if r["status"] >= 500)
    allowed = len(valid) * allowed_share / 100
    return round(bad / allowed, 4)


def p99_nearest_rank(records):
    valid = valid_payments(records)
    if not valid:
        return 0.0
    ordered = sorted(r["latency_ms"] for r in valid)
    rank = (len(ordered) * 99 + 99) // 100
    return float(ordered[rank - 1])
```

**Line by line.** When every assert passes, the file prints nothing. An `AssertionError` names the first assert that fails.

- `valid_payments` builds a new list. The condition `400 <= r["status"] <= 499` is a chained comparison, and `not` flips it, so the list keeps every status outside the 4xx range. The docstring in triple quotes documents the function and does nothing when the code runs.
- `success_percent` returns `0.0` when there are no valid requests. `good` counts the valid requests below 500. `good * 100 / len(valid)` multiplies before it divides, which avoids an extra rounding step. `round` is applied only at the return.
- `budget_spent_fraction` has the same empty check, and it also returns `0.0` when the target is 100, because `allowed_share` is then zero. `allowed` is the number of failures the target permits. `bad` counts the valid requests that are 5xx, and `bad / allowed` is the fraction of the budget spent.
- `p99_nearest_rank` sorts the valid latencies. The rank `(len(ordered) * 99 + 99) // 100` is the ceiling of `0.99 * n`, written with integers, so no float can push it off a whole number. `ordered[rank - 1]` turns the 1-based rank into a 0-based index. `float(...)` makes the return type float.
- `EXAMPLE` is the ten-request log, and `valid_payments(EXAMPLE)` keeps nine. The first group of asserts checks the success percentage of 800 out of 9, the budget spent of 1 failure against 0.045 allowed failures, and the p99 of 900 ms.
- The empty and all-4xx asserts check the `0.0` results. The clean-log asserts check zero failures, and the target of 100.
- The `edge` asserts check the boundaries. Status 399 is valid and good, status 499 is a client error and is excluded, and status 500 is a failure.
- The `hundred` and `hundred_one` asserts check exact multiples. For 100 values the rank is 99, and for 101 values the rank is 100.
- The `three` asserts check that unsorted input is sorted before the rank is taken. The single-record assert checks that one value is its own p99.
- The `slow_client` assert checks that a 4xx latency cannot change the result.

```python test
def closed_share_percent(tickets):
    if not tickets:
        return 0.0
    closed = sum(1 for t in tickets if t["state"] == "closed")
    return round(closed * 100 / len(tickets), 1)


def median_close_time(tickets):
    times = sorted(t["minutes"] for t in tickets if t["state"] == "closed")
    if not times:
        return None
    mid = len(times) // 2
    if len(times) % 2 == 1:
        return float(times[mid])
    return (times[mid - 1] + times[mid]) / 2


tickets = [
    {"state": "closed", "minutes": 10},
    {"state": "open", "minutes": 500},
    {"state": "closed", "minutes": 30},
    {"state": "closed", "minutes": 20},
]
assert closed_share_percent(tickets) == 75.0
```

**Line by line.** `closed_share_percent` counts the closed tickets with a generator and divides by the total. It multiplies by 100 before the division, and rounds only at the return. `median_close_time` sorts the closed minutes into a new list. For an odd count, `len(times) // 2` is the middle index, and `float` makes the return type float. For an even count, the two middle values are added and divided by 2. For `[10, 20, 30, 40]` the middle indexes are 1 and 2, so the answer is `(20 + 30) / 2`, which is 25.0. When every assert passes, the file prints nothing.
