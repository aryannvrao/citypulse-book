### Chaining steps with Pipeline

**What it is.** A `Pipeline` is a list of named steps that acts like one model. Every step except the last must provide `transform`, which changes the data. The last step is the estimator, and it must provide `predict`. When you call `fit` on the whole Pipeline, each step learns from the training data in order, and passes its output to the next step. When you call `predict`, the same steps run again, using what they learned during `fit`. Nothing is learned again at that point.

A short example shows the names a Pipeline keeps:

```python
from sklearn.linear_model import LinearRegression
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler

pipe = make_pipeline(StandardScaler(), LinearRegression())
print([name for name, step in pipe.steps])
```

The first two lines load the model and the helper that builds a pipeline. The third loads the scaler. The last two lines build the pipeline and print the name of each step. `make_pipeline` names each step with the lowercase version of its class name, so the output is `['standardscaler', 'linearregression']`.

**How it shows up in a case study.** A CityPulse analyst cleans readings in a notebook with pandas, and the API team later rewrites the same steps by hand for the live service. Three months on, the API gives different numbers from the notebook for the same reading. The symptom is a mismatch between training and serving. The right decision is one Pipeline object that both training and the API load, so there is only one version of the steps.

:::trap Predict refits the scaler
It is tempting to think that `predict` should refit the scaler on the new rows, so that the model adapts. It does not. Refitting changes the scale the model learned from, so one reading would get different numbers on different days.
:::

```quiz

WHY: predict reuses the fitted steps and never refits them. Refitting on the new rows is the tempting wrong answer, because it sounds adaptive, but it changes the scale the model learned from.

```

### Sending columns to separate branches with ColumnTransformer

**What it is.** A `ColumnTransformer` sends named groups of columns to separate branches, then joins the results side by side. Each branch is a tuple of three things: a name, a transformer and a list of columns. Any column that is not listed in a branch is dropped by default, because the `remainder` argument defaults to `"drop"`. If you want unlisted columns to pass through unchanged, you set `remainder="passthrough"`.

A short example shows the default at work:

```python
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import OneHotEncoder

df = pd.DataFrame({"station": ["S1", "S2"], "hour": [8, 9], "ts": ["2027-02-01", "2027-02-02"]})
ct = ColumnTransformer([("cat", OneHotEncoder(), ["station"])])
print(ct.fit_transform(df).shape)
```

Only `station` is listed, so `hour` and `ts` are dropped without an error. The output is `(2, 2)`: two rows, and one column for each station.

**How it shows up in a case study.** A CityPulse team adds a timestamp column called `ts` to the table, for a later feature. The model's results do not change, and nobody sees an error. The symptom is silence. The reasoning is that the transformer only uses the columns it is told about, so `ts` was dropped at every fit and every predict. The fix is to list the column in a branch, or to set `remainder="passthrough"` if it should be kept unchanged.

:::trap Expecting an error for a missing column
It will not raise an error, because the default is to drop it quietly. An error appears only when a branch names a missing column.
:::

```quiz
Q: A table has columns station, hour, temp and ts. A ColumnTransformer lists station in a one-hot branch and hour and temp in a scaling branch. No remainder argument is given. Which statement about ts is correct?

- fit raises an error, because ts is not in any branch.
* ts is dropped from the output, because the default remainder is "drop".
- ts is one-hot encoded with station, because the two columns share a table.
WHY: unlisted columns are dropped by default, so ts never reaches the model. The error is the tempting wrong answer, but an error only appears when a branch names a column that is missing.

- Nothing, because a ColumnTransformer always reads every column in the table.
* Add "wind_gust" to the list of numeric columns in the branch that does the scaling.

Q: Which argument makes a ColumnTransformer pass unlisted columns through unchanged, instead of dropping them?

- unlisted="keep"

WHY: the remainder argument controls columns that no branch lists. "passthrough" keeps them, and "drop" removes them, which is the default. The other three names are not arguments of ColumnTransformer.
```

### One-hot encoding categories

**What it is.** One-hot encoding turns a category, such as a station code, into a row of 0s and 1s. The encoder learns the list of known categories during `fit`, and it makes one column for each one. A row gets a 1 in the column of its own category and 0 everywhere else. With `handle_unknown="ignore"`, a category the encoder has not seen gets 0 in every column, so the model can still predict. The default setting raises an error instead.

A short example shows the output:

```python
import numpy as np
from sklearn.preprocessing import OneHotEncoder

enc = OneHotEncoder(handle_unknown="ignore")
enc.fit([["S1"], ["S2"], ["S3"]])
print(enc.transform([["S2"], ["S9"]]).toarray())
```

The row for S2 has a 1 in the second column. The row for the unseen S9 gets zeros. The output is `[[0. 1. 0.]` on the first line and `[0. 0. 0.]]` on the second.

**How it shows up in a case study.** A new sensor goes live at a fifth station. The API uses the default encoder, so every prediction request for the new station fails. The symptom is a crash on the day the sensor starts. The right decision is `handle_unknown="ignore"`, so the new station gets zeros in its encoded columns and the model still predicts. The choice is recorded in the code, so a reviewer can see it.

:::trap Thinking an unseen station is treated as the most common one
It does not assign the most frequent station. Every encoded column for that row is 0.
:::

```quiz
Q: An encoder was fitted on station codes S1, S2 and S3 with handle_unknown set to "ignore". At predict time a row arrives with station S7. What does the encoded part of that row look like?
* Every encoded column is 0 for that row.
- The row takes the encoding of the most frequent station, which is S1 or S2.
- The encoder refits itself on S7 and adds a fourth column.
- predict stops with an error and returns nothing.
WHY: an unknown category sets all of its columns to zero, so the model can still predict. Giving the row the most frequent station is the tempting wrong answer, because it sounds like a sensible guess.

Q: A OneHotEncoder with default settings is fitted on a column that contains four distinct station codes in the training rows. How many encoded columns does it produce?
- 3
- 5
* 4
- 1
WHY: the default encoder makes one column for each category, so four categories give four columns. Dropping one column is a separate option, and it is not the default. Choosing 3 is the tempting wrong answer, because it looks like the number of gaps between categories.

Q: A linear model with an intercept is trained on a one-hot encoded station column that has one column for every category. Which setting removes one redundant column?
- handle_unknown="ignore"
* drop="first"
- sparse_output=False
- categories="auto"
WHY: drop="first" removes the first category's column, because the other columns already carry that information. handle_unknown changes what happens to unseen rows, not how many columns exist, so it is the tempting wrong answer.
```

### Filling missing values with SimpleImputer

**What it is.** A missing value is a gap, and in scikit-learn it is written as `NaN`, which means "not a number". `SimpleImputer` fills each gap with a statistic. With `strategy="median"`, it fills gaps with the median of the column. The median is the middle value after sorting. `SimpleImputer` learns the median during `fit`, from the values that are present, and it reuses that same number during `transform`.
A short example shows the learned value:

```python
import numpy as np
from sklearn.impute import SimpleImputer

imp = SimpleImputer(strategy="median")
imp.fit(np.array([[1.0], [2.0], [np.nan], [10.0]]))
print(imp.transform(np.array([[np.nan]])))
```

The known values are 1, 2 and 10, so the median is 2.0. The gap in the last line is filled with 2.0, and the output is `[[2.]]`.

**How it shows up in a case study.** A colleague proposes the mean to fill gaps in wait times, but a sensor fault has sent a few huge spikes. The symptom is that the filled values are pulled upwards, so the model learns a higher typical level than the real one. The reasoning points to the median, because one extreme value barely moves it. The imputer must also sit inside the Pipeline, so it learns the median from training rows only.

:::trap Computing the median on the whole table first
It is tempting to fill the gaps once, using the median of the full table, and then split the data. The validation and test rows then influence the values that the training rows receive. The imputer should be fitted on the training rows only, inside the Pipeline.
:::

```quiz
Q: A column of wait times has a few missing values and a few very large outliers from a faulty sensor. You want to fill the gaps with a typical value that the outliers do not pull away from the middle. Which strategy do you choose?
- strategy="mean"
- strategy="constant", with a fill value of 0
- strategy="most_frequent"
* strategy="median"
WHY: the median is the middle value, so one extreme reading barely moves it. The mean is pulled towards the outliers. most_frequent is meant for categories, and constant fills every gap with one number you choose yourself.

Q: A SimpleImputer with strategy="median" sits inside a Pipeline. The Pipeline is fitted on the training rows of one cross-validation fold. Which rows are used to learn the median?
* The training rows of the current fold only.
- All rows in the table, including the test rows, so that the median is stable.
- The validation rows of each fold, because they show the true spread of the data.
- The last row of the table, because it is the most recent.
WHY: fit learns only from the rows it is given, which must be the training part of the fold. Using all rows is the tempting wrong answer, because it looks like more data.

Q: You have a training table and a separate test table, both with some missing values. Which order of operations is leakage-free for a median imputer?
- Compute the median on the full table, then split the rows into training and test.
- Fit the imputer on the test rows, because they are the newest values.
* Split the rows first, fit the imputer on the training rows only, then transform the test rows with that fitted imputer.
- Fill the test gaps with the median of the test rows, then fit the imputer on the training rows.
WHY: the test rows must never influence what the imputer learns. The fitted imputer then fills the test gaps with the training median. Computing the median on the full table is the tempting wrong answer, because it is one line of code and it looks harmless.
```

### Avoiding leakage in cross-validation

**What it is.** Leakage means that information from the validation or test rows reaches the training step. It makes scores look better than the model really is, because the model has seen part of the exam. When you put the scaler and the model in one Pipeline and pass the Pipeline to `cross_val_score`, scikit-learn clones the Pipeline for each fold and fits the clone on that fold's training part only.

A short example shows what the scaler learns:

```python
import numpy as np
from sklearn.preprocessing import StandardScaler

train = np.array([[1.0], [2.0], [3.0]])
sc = StandardScaler().fit(train)
print(sc.mean_)
```

The scaler learns its mean from the three training values, which is 2.0. The output is `[2.]`.

**How it shows up in a case study.** A student scales 1,000 readings, then runs five-fold cross-validation on the scaled table. The mean fold score is 0.82, but the test window scores 0.64. The symptom is a large gap between the two. The reasoning is that the scaler used the whole table, so validation rows helped to shape the training features. The fix is to put the scaler inside the Pipeline, so it is refitted in every fold.

:::trap Scaling first because the code still runs
Scaling the whole table before cross-validation looks reasonable, and the code runs without any error. The score is what changes, and it is biased upwards.
:::

```quiz
Q: A team standardises all 1,000 rows, then runs cross-validation on the scaled table. Each fold score is better than the final test score. What is the most likely cause?
- The folds are too small to give a reliable score.
* The scaler learned its mean and standard deviation from rows that later served as validation rows, which is leakage.
- The model has too few trees to fit the data.
- The test score uses a different metric from the folds.
WHY: scaling the table first lets the validation rows shape the scaling of the training rows. The small-folds explanation is the tempting wrong answer, because small folds do add noise, but they do not bias the score upwards.

Q: Which setup gives an honest cross-validation score for a pipeline that scales its features?
- Scale the test rows with their own mean and standard deviation before scoring.
- Report the test score as the cross-validation score, because it is the most honest number.
- Scale the whole table first, then pass the scaled table to cross_val_score.
* Put the scaler and the model in one Pipeline, then pass the Pipeline to cross_val_score.
WHY: a Pipeline refits the scaler inside each fold, so the validation rows never influence the scaling. Scaling the whole table first is the common mistake, and the test score is not a cross-validation score at all.

Q: You run GridSearchCV on a Pipeline that contains an imputer. Which statement about the imputer is correct?
* It is refitted on the training part of every fold, so the validation rows never influence it.
- It is fitted once on the full table before the search starts, and then reused for every fold.
- It is fitted only on the final test rows, after the search has finished.
- It is never fitted, because the search only tunes the model.
WHY: the search clones the whole Pipeline for each fold and fits it on that fold's training rows. Fitting the imputer once before the search is the tempting wrong answer, because it looks faster and it looks the same.
```

### Searching a grid with GridSearchCV

**What it is.** `GridSearchCV` tries every combination of values in a grid. The number of candidates is the product of the list lengths. Each candidate is scored with cross-validation, so each candidate is fitted once per fold. The search keeps the best candidate. With `refit=True`, which is the default, the best setting is then fitted once more on all the training rows.

A short example counts the candidates:

```python
from sklearn.model_selection import ParameterGrid

grid = {"a": [1, 2, 3], "b": [4, 5]}
print(len(ParameterGrid(grid)))
```

The grid has three values for `a` and two for `b`, so it has 3 times 2 combinations. The output is `6`. Each of the six candidates is then fitted once per fold, so the number of fits inside the search is six times the number of folds.

**How it shows up in a case study.** A student plans a grid with two regularisation values and five tree counts, using five folds, and expects ten fits. Her tutor asks her to count again. Ten is the number of candidates, not the number of fits. Each candidate is fitted once per fold, so the loop runs fifty fits, and the final refit comes on top.

:::trap Counting candidates and forgetting folds
With one fold, the fits equal the candidates. With `cv=5`, every candidate is fitted five times.
:::

```quiz
Q: A grid search has one parameter with two values and another with five values. You use cv=4. How many fits happen inside the cross-validation loop, not counting the final refit?
- 14
- 20
* 40
- 10
WHY: there are 2 times 5, which is 10 candidates, and each candidate is fitted once per fold, so 10 times 4 gives 40. The tempting wrong answer is 10, which forgets the folds.

Q: A grid search runs with refit=True. Which statement about the refit is correct?
- Each candidate is refitted on the test rows to check its score.
* The best setting is refitted once on all training rows after the search has finished.
- The refit is skipped, so you must fit the model yourself afterwards.
- A refit happens once per fold, inside the search loop.
WHY: the final refit happens once, after the search, and it uses all the training rows with the winning setting. The per-fold fits are the search itself, not a refit. Choosing "once per fold" is the tempting wrong answer.

Q: Your grid has four values for one parameter. You change cv from 5 to 10 and leave the grid unchanged. How does the number of fits inside the loop change?
- It stays the same, because the grid did not change.
- It falls by half, because each fold is bigger.
- It changes by five, because five more folds are added.
* It doubles, from 20 fits to 40 fits.
WHY: fits equal candidates times folds. Four candidates times five folds is 20, and four times ten folds is 40. Saying that it changes by five is the tempting wrong answer, because it adds the difference in folds rather than multiplying.
```

### Naming parameters inside a pipeline

**What it is.** A Pipeline step is addressed with a key made from three parts: the step name, two underscores and the parameter name. For example, `model__alpha` means the `alpha` parameter of the step called `model`. The step name is the one you gave in `Pipeline`, or the lowercase class name if you used `make_pipeline`. Nested steps add more double underscores.
A short example shows the key in use:

```python
from sklearn.linear_model import Ridge
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler

pipe = make_pipeline(StandardScaler(), Ridge(alpha=1.0))
pipe.set_params(ridge__alpha=10.0)
print(pipe.named_steps["ridge"].alpha)
```

`make_pipeline` names the Ridge step `ridge`, so the key is `ridge__alpha`. The call sets alpha to 10.0 inside the pipeline. The output is `10.0`. The key uses the lowercase name, not the class name `Ridge`.

**How it shows up in a case study.** One student writes the key `Ridge__alpha` and another writes `model.alpha`. Both get an invalid parameter error. The reasoning is that the key is built from the step name, so with `make_pipeline` the step is `ridge` and the key is `ridge__alpha`. The first student used a capital letter, and the second used a dot.

:::trap Using the class name or a dot
The class name and a dot both fail. The key is the step name, two underscores, then the parameter name.
:::

```quiz
Q: A pipeline is built with make_pipeline(StandardScaler(), Lasso()). Which key sets the alpha of the Lasso step inside a grid?
* lasso__alpha
- Lasso__alpha
- lasso.alpha
- alpha
WHY: make_pipeline uses the lowercase class name as the step name, so the key starts with lasso, then two underscores, then alpha. Writing the capital letter is the tempting wrong answer, because it matches the class name.

Q: A pipeline has a step named scaler, which is a StandardScaler. Which key sets its with_mean setting?
- StandardScaler__with_mean
- scaler.with_mean
* scaler__with_mean
- with_mean
WHY: the step is named scaler, so the key begins with scaler, then two underscores, then the parameter name with_mean. A bare with_mean does not name the step, so the search cannot find it.

Q: Your grid uses the key model__max_depth, and the search reports an invalid parameter error. The pipeline has a step named model that holds a Ridge estimator. What is the most likely cause?
- The grid is too large for the search to run.
* The estimator in the step named model has no parameter called max_depth, because Ridge does not have one.
- Double underscores are not allowed inside keys.
- The key must be written in capital letters.
WHY: the key format is correct, so the problem is the parameter name. Ridge has alpha and similar settings, but no max_depth. The grid size is the tempting wrong answer, because a big grid feels like the more likely reason for an error.
```

### Sampling settings with RandomizedSearchCV

**What it is.** `RandomizedSearchCV` does not try every combination. You pass a dictionary of distributions or lists, and an `n_iter` count. The search samples that many candidates at random, and scores each one with cross-validation. Set `random_state` to make the same candidates come out on every run.
A short example shows the count:

```python
from sklearn.linear_model import Ridge
from sklearn.model_selection import RandomizedSearchCV

search = RandomizedSearchCV(Ridge(), {"alpha": [0.1, 1.0, 10.0, 100.0]},
                            n_iter=2, cv=3, random_state=0)
search.fit(X, y)
print(len(search.cv_results_["params"]))
```

This assumes `X` and `y` already hold the training data. The list has four values, but `n_iter=2` samples two candidates, so the output is `2`.

**How it shows up in a case study.** A team sets `n_iter=20` over 500 combinations, and its report says the search checked every combination. The symptom is a claim that the search is exhaustive. The reasoning is that twenty samples leave most combinations untried. The honest report states how many candidates were sampled and the `random_state`, so the search can be repeated.

:::trap Believing the random search covers the space
Twenty random tries do not cover the whole space. A random search is a sample, and its best candidate can be worse than a full grid's.
:::

```quiz
Q: A RandomizedSearchCV has 500 possible combinations and n_iter=20. Which description is correct?
- It tries all 500 combinations, but only uses 20 folds.
- It tries the first 20 combinations in the list, in order.
- It tries 20 folds, and each fold runs all 500 combinations.
* It samples 20 candidate settings at random, and scores each one with cross-validation.
WHY: n_iter sets how many candidates are sampled, and each sampled candidate is scored with cross-validation. The folds are set by cv, not by n_iter. Assuming that all 500 combinations are tried is the tempting wrong answer.

Q: You run the same RandomizedSearchCV twice on the same data, with the same distributions and the same random_state. What do you expect?
* The same candidates are drawn in both runs, so the results match.
- The results differ every time, because random sampling is always different.
- The second run uses the test rows to choose better candidates.
- scikit-learn skips the second run, because the first run already happened.
WHY: random_state fixes the draws, so the same candidates come out on each run. Saying that the results always differ is the tempting wrong answer, because it treats randomness as uncontrolled.

Q: A space has three parameters with ten values each, which is 1,000 combinations. You compare a grid search with a randomized search that has n_iter=50. Which statement is correct?
- A grid search always gives a better result than a randomized search.
- A randomized search always tries all 1,000 combinations.
* The randomized search tries 50 candidates and may miss the best one, while the grid tries all 1,000.
- A grid search with cv=5 tries only 200 candidates.
WHY: the randomized search is a sample of 50 from 1,000, so it can miss the best setting. Whether it is better depends on the space and the budget, not on a rule. Saying that the grid always wins is the tempting wrong answer.
```

### Engineering features with lags and rolling means

**What it is.** A lag feature is a value moved down by a fixed number of rows. `shift(1)` gives each row the value from one row earlier. With several stations in one table, you must group by station first, so that the shift does not cross from one station into the next. A rolling mean averages a window of rows. `rolling(3).mean()` gives each row the average of itself and the two rows before it. The first rows of each group are NaN, because there is no earlier data to use.

A short example shows the grouping:

```python
import pandas as pd

df = pd.DataFrame({"station": ["A", "A", "B", "B"], "v": [1, 2, 10, 20]})
df["lag1"] = df.groupby("station")["v"].shift(1)
print(df["lag1"].tolist())
```

Each station's first row has no earlier value, so it gets NaN. The second row of station A gets 1, and the second row of station B gets 10. The output is `[nan, 1.0, nan, 10.0]`. Without `groupby`, the third row, which is the first of station B, would have received the value 2 from station A.

**How it shows up in a case study.** A team adds previous-hour PM2.5 values with a plain `shift(1)` to a table of three stations. Training error looks better than test error. The symptom is a feature that seems too good. The reasoning is that the first row of each station received a value from another station. The fix is to group by station before the shift. Every feature must also be known at prediction time.

:::trap Trusting a lag with no groupby
It is tempting to write `df["pm25"].shift(1)` and assume pandas knows where each station starts. It does not. The shift moves values across station boundaries, and the mistake is silent.
:::

```quiz
Q: A table holds readings from three stations, one row per station per hour, sorted by station and then by time. You add a column with df["pm25"].shift(1) and no groupby. What is the defect?
- The whole column is NaN.
* The first row of each station receives the last value of the station above it.
- pandas refuses to shift a column unless it is grouped.
- Nothing is wrong, because shift always stays within each station.
WHY: without groupby, shift moves values across the boundary between stations. The tempting wrong answer is that shift detects stations by itself, which it does not.

Q: A feature for predicting PM2.5 at 14:00 is built from the PM2.5 value recorded at 14:00 in the same row. Why is this a problem?
- It is fine, because a lag is only a copy of the target column.
- It is fine, because the model is trained on the same row it predicts.
- It only makes training slower, so the result is still valid.
* The value is not known at prediction time, so the feature leaks the target into the model.
WHY: at 14:00 the team cannot know the reading at 14:00 before it is recorded. Calling it a harmless copy is the tempting wrong answer, because the copy looks like an innocent shift.

Q: An ablation removes one feature and the MAE changes by 0.004. The seed-to-seed noise floor is 0.02. What should the ablation table say about that feature?
* There is no evidence that the feature helps.
- The feature is a clear win and should be kept.
- The feature harms the model, so it should be removed.
- Retrain with new seeds until the change becomes larger.
WHY: a delta smaller than the noise floor cannot be told apart from chance. Calling it a win is the tempting wrong answer, because the number is positive and it looks like progress.
```

### Reading the results of a search

**What it is.** After `GridSearchCV` finishes, several attributes hold different things. `best_params_` is a dictionary of the winning settings. `best_score_` is the mean cross-validation score of the winning setting. `cv_results_` is a table of every candidate and its scores. `best_estimator_` is the model refitted on all training rows with the winning settings, and it is the only one of these that can predict.
A short example shows the attributes:


## The graded lab

This section explains the techniques the graded lab needs, then gives you a twin problem to practise on. The real lab asks for four functions. ### The task in plain words

**Scenario.** CityPulse models need numeric features, so raw readings pass through a scale-then-encode pipeline. It is the same idea as a scikit-learn `Pipeline`, but you build it from plain functions, with no library.

You write four functions in the starter file. Keep their names and parameters exactly as the starter file shows them.

- `fit_scaler(values)` takes a list of numbers. It returns a tuple `(min, max)`, the smallest and largest value in the list. These two numbers are the learned min-max parameters.
- `scale(values, scaler)` takes a list of numbers and a scaler tuple `(min, max)`. For each value, it computes `(v - min) / (max - min)` and rounds the result to 2 decimals. It returns the list of results.
- If `max` equals `min`, every output is `0.0`.
- `one_hot(value, vocab)` returns one entry for each item in `sorted(vocab)`. The entry is 1 at the position of `value` and 0 everywhere else.
- If `value` is not in the vocabulary, every entry is 0.
- `build_features(readings, vocab)` returns one feature row for each reading. Each row is `[scaled_value, *one_hot(pollutant)]`. The scaled value is min-max scaled, and the scaler is fitted on the values of all the readings in the list, not on one reading at a time.

The statement gives one example for each of two functions:

```python
scale([10.0, 20.0, 30.0], (10.0, 30.0))   # [0.0, 0.5, 1.0]
one_hot("NO2", ["PM25", "NO2", "O3"])      # [1, 0, 0], because the sorted vocab is NO2, O3, PM25
```

The starter file defines four module-level names, one for each function. The run limits are 30 seconds and 128 MB of memory, so you do not need a fast solution. You need a correct one.

### What each function needs

Each idea below is taught with a small example that has nothing to do with the lab's data. Try each one in a fresh file before you use it in the lab.

**Tuples and the order of min and max.** `min` and `max` return the smallest and largest value of a list. A tuple is written in round brackets, and a tuple is not equal to a list with the same items.

```python
sizes = [38, 42, 40]
low, high = min(sizes), max(sizes)
print((low, high))
print((low, high) == [38, 42])
```

The first line prints `(38, 42)`. The second prints `False`, because a tuple and a list are different types even when their items match. The statement asks for a tuple, so you must return one.

**Division, rounding and the zero guard.** The `/` operator keeps decimals, while `//` throws away the fraction. Python's `round` rounds half values to the nearest even digit, so it does not always round the way you expect. Division by zero raises an error, so any division by a range must be guarded first.

```python
print(7 / 2)
print(7 // 2)
print(round(2.5))
print(round(0.125, 2))
print(1 / 0)
```

The output is `3.5`, then `3`, then `2`, then `0.12`. The last line stops the program with `ZeroDivisionError`. The statement rounds each result to 2 decimals, so round the final result once and never the minimum or the maximum.

**Sorting without changing the original.** `sorted` returns a new list and leaves the original alone. `list.sort` changes the list it is called on. The statement says "over `sorted(vocab)`", so the vocabulary you were given must not be changed.

```python
transport = ["train", "bus", "tram"]
print(sorted(transport))
print(transport)
for position, name in enumerate(sorted(transport)):
    print(position, name)
```

The first line prints `['bus', 'train', 'tram']`. The second prints the original list, `['train', 'bus', 'tram']`, unchanged. The loop prints the position and the name, so `enumerate` gives you the index of each item while you walk through a list.

**Building rows with a fixed column order.** The star in `[first, *rest]` spreads the items of a list into the new list. A row must keep the same column order every time, so the scaled value comes first.

```python
row = [0.5, *[1, 0]]
print(row)
print(len(row))
```

The output is `[0.5, 1, 0]` and then `3`. The star unpacks the list `[1, 0]` into the row, so the one-hot entries follow the scaled value without needing a loop.

**Booleans are a kind of integer.** In Python, `bool` is a subclass of `int`. `True` equals 1 and `False` equals 0, so a comparison can pass even when the type is wrong. `isinstance` also accepts a subclass, so it cannot tell a bool from an int.

```python
print(isinstance(True, int))
print(type(True) is int)
print(True == 1)
```

The output is `True`, then `False`, then `True`. The statement's example shows the one-hot entries as the integers `1` and `0`. Returning `True` and `False` would pass a comparison with `==` but would fail a check that uses `type(x) is int`, so write the integers.

### Worked twin problem

The twin problem is about bike-share trips. It has a different domain and different data, but it needs the same skills: learning a value from a list, filling gaps, one-hot encoding over a sorted list, and building fixed-order rows.

**Bike-share trips.** A bike-share company records how long each trip took, in minutes. Some trips have no recorded duration, which is stored as `None`. You build the feature rows for a duration model with four functions.

- `learn_median(minutes)` takes a list of durations, where some entries may be `None`. It ignores the `None` values and returns the median of the rest, using `statistics.median`. If no known durations are left, it raises `ValueError`.
- `fill_missing(minutes, fill)` returns a new list in which every `None` is replaced by `fill`. It does not change the list it was given.
- `encode_type(bike_type, types)` encodes the type over `sorted(types)` but leaves out the first sorted type, which is the baseline and has no column of its own. Each remaining entry is `1` if it matches `bike_type` and `0` otherwise, so the baseline type and any unknown type both give all zeros.
- `build_trip_rows(history, trips, types)` learns the median from `history` only. It returns one row for each trip, in the form `[minutes, *encode_type(bike, types)]`. A trip with no duration gets the learned median. An empty list of trips returns an empty list.

Each trip is a dictionary with the keys `"minutes"` and `"bike"`.

Here is the solution, with its tests:

```python test
import statistics

def learn_median(minutes):
    known = [m for m in minutes if m is not None]
    if len(known) == 0:
        raise ValueError("no known durations to learn from")
    return statistics.median(known)

def fill_missing(minutes, fill):
    return [fill if m is None else m for m in minutes]

def encode_type(bike_type, types):
    return [1 if bike_type == t else 0 for t in sorted(types)[1:]]

def build_trip_rows(history, trips, types):
    fill = learn_median(history)
    minutes = fill_missing([t["minutes"] for t in trips], fill)
    rows = []
    for m, trip in zip(minutes, trips):
        rows.append([m, *encode_type(trip["bike"], types)])
    return rows

# learn_median ignores missing values
assert learn_median([10, None, 20, 40]) == 20
assert learn_median([5, None]) == 5
assert learn_median([1, 2, 3, 4]) == 2.5
try:
    learn_median([None, None])
except ValueError:
    pass
else:
    raise AssertionError("expected ValueError for no known durations")

# fill_missing returns a new list and leaves the input alone
original = [7, None, 9]
assert fill_missing(original, 8) == [7, 8, 9]
assert original == [7, None, 9]
assert fill_missing([], 8) == []

# encode_type works over the sorted types, minus the baseline "cargo"
types = ["electric", "classic", "cargo"]
assert encode_type("classic", types) == [1, 0]
assert encode_type("electric", types) == [0, 1]
assert encode_type("cargo", types) == [0, 0]
assert encode_type("tandem", types) == [0, 0]
assert types == ["electric", "classic", "cargo"]

# build_trip_rows
history = [10, None, 20, 40]
trips = [
    {"minutes": 12, "bike": "classic"},
    {"minutes": None, "bike": "electric"},
    {"minutes": 30, "bike": "tandem"},
]
assert build_trip_rows(history, trips, types) == [
    [12, 1, 0],
    [20, 0, 1],
    [30, 0, 0],
]
assert build_trip_rows(history, [], types) == []
assert build_trip_rows([3, 3], [{"minutes": None, "bike": "electric"}], types) == [[3, 0, 1]]
print("all tests passed")
```

Line by line:

- `import statistics` loads the standard library module that provides `median`.
- `learn_median` builds `known` with a list comprehension. It keeps every value that is not `None`, so the gap is skipped.
- The `if` line raises `ValueError` when nothing is left. The message explains why.
- `statistics.median(known)` sorts the known values and returns the middle one. For an even count it returns the average of the two middle values, which is why `[1, 2, 3, 4]` gives `2.5`.
- `fill_missing` returns a new list. The comprehension uses `fill` wherever the value is `None` and keeps every other value. The input list is never assigned to, so it is not changed.
- `encode_type` sorts the types with `sorted`, which returns a new list, and the slice `[1:]` drops the first sorted type, the baseline. For each remaining type, `1 if bike_type == t else 0` gives an integer 1 or 0. The baseline and an unknown type both match nothing, so all entries are 0.
- In `build_trip_rows`, the median is learned from `history` alone. The durations of the trips are collected into a list, and `fill_missing` replaces the gaps with the learned median.
- The loop pairs each filled duration with its trip, using `zip`, and builds the row. The star in `[m, *encode_type(...)]` puts the one-hot entries after the duration, in a fixed order.
- The asserts check each rule, including the empty and unknown cases. The `try` block forces a failure if `learn_median` does not raise an error.

Expected output: the program prints `all tests passed`. If an assert fails, Python stops with an `AssertionError` that points to the failing line.

```python test
def summarise(parcels):
    if len(parcels) == 0:
        return {"count": 0, "couriers": {}, "heaviest": None, "avg_kg": 0.0}
    couriers = {}
    for p in parcels:
        couriers[p["courier"]] = couriers.get(p["courier"], 0) + 1
    ranked = sorted(parcels, key=lambda p: (-p["weight_kg"], p["id"]))
    total = sum(p["weight_kg"] for p in parcels)
    return {
        "count": len(parcels),
        "couriers": couriers,
        "heaviest": ranked[0]["id"],
        "avg_kg": round(total / len(parcels), 2),
    }
```
