## What the quiz tests

The Day Quiz has ten case-study questions, one for each topic below, in this order. Each question gives you a short scenario from the CityPulse project and asks what the team should do, or what the code will do. The pass mark is 70%. Your first attempt is the one your skill score keeps, so read every question fully the first time.

Read a case-study question in this order:

1. Read the last line first. It tells you what is asked, such as "which change" or "what is the result".
2. Read the scenario again and underline the facts that matter: the type of the data, the error that appeared, how often something runs, and whether something is shared between calls.
3. Eliminate options that are true in general but do not fix this scenario. An option can be correct about Python and still be the wrong answer here.
4. Watch for three words. "Most" asks for the best of several good options. "First" asks for the first step, not the final fix. "Best" asks you to weigh trade-offs, and the simplest correct option usually wins.

Each topic below explains the idea from zero, gives a small example, shows a CityPulse case, names the trap, and ends with three questions. The self-test at the end mixes all ten topics and is harder than the questions above it.

### Converting types with int, float and str

**What it is.** Python tracks the type of every value. `int` is a whole number, `float` is a decimal number and `str` is text. A value read from a CSV file is always text, even when it looks like a number. Three built-in functions change the type. `int()` gives a whole number, `float()` gives a decimal number and `str()` gives text. Each one accepts only the text it can read. `float("36.6")` works, but `int("36.6")` raises `ValueError`.

```python
raw = "36.6"
print(type(raw).__name__)
print(float(raw) > 50)
print(int(float(raw)))
```

Output:

```text
str
False
36
```

The first line shows that `raw` is text. The second line converts it to a float and compares it with 50. The third line converts to a float and then to an int. `int()` cuts off the decimal part without rounding, so 36.6 becomes 36, not 37.

**How it shows up in a case study.** A CityPulse loader sends the `value` column straight into a check for readings above 50. The job fails with `TypeError` on the first row, although the file is fine. The check compares text with a number. The right decision is to convert the value once, with `float()`, at the point where each row is read. The rest of the program then works with numbers. The team does not need a different file format or a higher threshold.

:::trap Calling int on a decimal
The tempting wrong answer is that `int("52.1")` gives 52, so the check still works. In fact it raises `ValueError`, and the row is never read. Use `float()` for sensor values.
:::

```quiz

- Python compares text as strings, so the check is always false.

- The file uses the wrong encoding, so the number cannot be read.
- The comparison needs == instead of >, because > works only on whole numbers.
WHY: Python 3 refuses to order text against 50. Converting once with float() where the row is read fixes it. The tempting wrong answer is that Python converts text in comparisons, which it does not do.
```

### Lists, dictionaries, sets and tuples

**What it is.** A collection holds several values in one variable. A list is ordered, can hold repeats and is written in square brackets. A dictionary holds key-value pairs in curly braces and finds a value by its key. A set holds unique items with no fixed order. A tuple is ordered and cannot be changed after it is made. Reading a dictionary with `d[key]` raises `KeyError` when the key is missing, while `d.get(key, default)` returns the default instead.

```python
readings = ["S1", "S2", "S1"]
print(len(readings), readings.count("S1"))
print(sorted({"S1", "S2", "S1"}))
limits = {"pm25": 50, "no2": 200}
print(limits["pm25"], limits.get("o3", "none"))
```

Output:

```text
3 2
['S1', 'S2']
50 none
```

`len` counts all three items, and `count` counts the S1 items. The set literal keeps each id once, and `sorted` returns a list in order. The square-bracket read finds the value for `pm25`. The `get` call looks for `o3`, which is not a key, so it returns the default text `none`.

**How it shows up in a case study.** A dashboard keeps the latest reading for each station in a dictionary. A station that has not reported yet has no key. The page reads `latest["S9"]`, crashes, and takes the rest of the page down with it. The right decision is to read with `get`, and to show a missing station as "no data yet", not as zero. A list would not help, because it has no keys. A set would not store the values at all.

:::trap Expecting a dictionary to create missing keys on read
The tempting wrong answer is that reading `latest["S9"]` creates the key. A normal dictionary raises `KeyError`. Only a `defaultdict` creates a missing key on read, and you must choose it on purpose.
:::

```quiz
Q: A dashboard stores the latest value per station in a dictionary. The page reads latest["S9"] for a station that has not reported yet, and the page crashes. Which change stops the crash and keeps the gap visible?
- Store the readings in a list, because lists never raise an error for a missing item.
- Set latest["S9"] = 0 before every read, so the key always exists.
* Read with latest.get("S9") and show None as no data yet.
- Convert latest to a set, so the station names are checked for duplicates.
WHY: Square brackets raise KeyError for a missing key. get returns None, so the page shows a gap instead of a fake zero. The tempting wrong answer is storing 0, which hides the missing station.

Q: A team needs the unique station ids from a long list that contains repeats. The order does not matter. Which collection fits best?
* A set, because it keeps each item once and has no fixed order.
- A list, because it removes repeats whenever you call len on it.
- A tuple, because a tuple cannot contain repeated items.
- A dictionary with the ids as keys, because keys are the only way to remove duplicates.
WHY: A set is the simplest collection for unique items. A list and a tuple both keep repeats, and a dictionary works but carries values you do not need.

Q: A developer uses the list [77.59, 12.97] as the key of a dictionary of station locations. Python raises TypeError: unhashable type: 'list'. Which change fixes it?
- Use a set for the coordinates, because a set can be a dictionary key.
- Sort the list first, because sorted lists become hashable.
- Store the list in a second dictionary, which Python then uses as the key.
* Convert the coordinates to a tuple, which cannot change and can therefore be a key.
WHY: Keys must be hashable, and a list can change, so it has no hash. A tuple of the same numbers is hashable. Sets cannot be keys, and sorting does not change the type.
```

### Closing files with with open

**What it is.** A context manager is an object that prepares something before an indented block and cleans it up afterwards. You use one with the `with` keyword. The most common example is a file. `with open(path) as f:` opens the file and names it `f`. When the block ends, Python closes the file, even when an error happened inside the block. Your code does not need to remember a `close()` call.

```python
with open("notes.txt", "w", encoding="utf-8") as f:
    f.write("pm25 ok\n")
print(f.closed)
```

Output:

```text
True
```

The first line opens `notes.txt` for writing, which creates it if it is missing. The second line writes one line into it. When the indented block ends, Python closes the file. The last line prints `True`, which shows that `f` is closed. The name `f` still exists after the block, but the file it points to is closed.

**How it shows up in a case study.** A scheduled job reads a large readings file and writes a summary. Row 300 is malformed and raises an error. The team's version opens the file with a plain `open` call and closes it at the bottom. The bottom line is never reached, so the file stays open and the summary is left half written. The right decision is to use `with` for every file the job opens. A longer timeout or a sleep does not close the file.

:::trap Using the file after the block
The tempting wrong answer is that `f` can still be read after the block. The file is closed, so `f.read()` raises `ValueError: I/O operation on closed file`. Read and write only inside the block.
:::

```quiz
Q: A scheduled job opens readings.csv with f = open("readings.csv") and processes rows. Row 300 is malformed, the job crashes, and the close() call at the bottom never runs. Which change closes the file even when the job crashes?
- Open the file a second time for each row, so each handle is short-lived.
- Put the processing in a try block with no except, which stops the crash.
- Call f.flush() after each row, which closes the file as it goes.
* Open the file with with open("readings.csv") as f:, so the block closes it even after an error.
WHY: A with block runs its cleanup on exit, including exit by an error. flush saves data but does not close the file.

Q: A function reads the first line of a file inside with open(path) as f: and returns f, so the caller can read more. The caller then calls f.readline(). What happens?
- It returns the first line again, because Python reopens the file automatically.
* It raises ValueError: I/O operation on closed file, because the block closed the file when it ended.
- It returns an empty string, because the file pointer moved to the end.
- It raises FileNotFoundError, because the path is no longer valid.
WHY: The block ends when the function returns, so the file is closed before the caller reads it. The empty string is tempting, but it is what an open file at its end gives.

Q: A class with __enter__ and __exit__ methods prints closing in __exit__. A with block that uses it raises ZeroDivisionError. What is printed, and what happens to the error?
- Nothing is printed, because errors skip __exit__ entirely.
- closing is printed twice, once for the error and once for the block.
* closing is printed, __exit__ runs even though the block failed, and the error continues upward.
- closing is printed, and the error is silently removed.
WHY: __exit__ always runs. It does not return a true value, so the error is not suppressed and still appears in the traceback.
```

### Defining functions with def, parameters and return

**What it is.** A function is a named block of code. `def` starts the definition, the names in brackets are parameters, and the indented body does the work. `return` sends a value back to the caller. A function with no `return` line gives back `None`, which means no value. `print` shows text on the screen, but it does not give the value to the caller.

```python
def show_average(values):
    print(sum(values) / len(values))

def average(values):
    return sum(values) / len(values)

result = show_average([30, 60])
print(result)
print(average([30, 60]))
```

Output:

```text
45.0
None
45.0
```

`show_average` computes the mean and prints it, but it has no return line. The assignment stores `None` in `result`, so the second line prints `None`. `average` returns 45.0, and the last line prints it. Both functions do the same arithmetic. Only the one with `return` gives the caller a value to use.

**How it shows up in a case study.** A CityPulse analyst writes a function that works out the average pm25 value and prints it for the morning standup. Later, the weekly report calls the same function, stores the result and multiplies it by a factor. The job crashes with `TypeError`. The function works on screen, but it never sends the average back. The right decision is to return the number and let the caller decide how to display it.

:::trap Printing instead of returning
The tempting wrong answer is that a printed result is a returned result. The caller receives `None`, so every later step that uses the number fails.
:::

```quiz
Q: A function avg_pm25(rows) computes the average pm25 value and prints it, with no return line. A later step writes m = avg_pm25(rows) and then m * 2, which raises TypeError. Why?
* m is None, because a function with no return statement gives back None.
- m holds the list of rows, because the function reads them and keeps them.
- m is a string, because print always returns text to its caller.
- The function must be called without assignment, so m has no value.
WHY: Assignment stores only the value that return sends back. The tempting wrong answer is that the rows are kept, but the function never hands them over.

Q: A student writes a helper for the CityPulse report, and the file does not start. The line is def check(limit=50.0, values):. What is the reason?
- Python accepts the line, but limit is ignored because it has a default.
- Python runs the file, but values must be passed as a keyword every time.
* Python raises SyntaxError when it reads the def line, because a parameter without a default cannot follow one with a default.
- Python runs the file only if check is called before it is defined.
WHY: Parameters without defaults must come first. The first option is tempting, but Python refuses the line before any call happens.

Q: A rule for counting exceedances is copied into three places in a report script. The limit changes next month, and only two copies are updated. What is the best change?
- Make the limit a global variable and keep the three copies, so they all read it.
* Move the rule into one function that takes the limit as a parameter, and call it from all three places.
- Rename the three copies so that each one has a unique name.
- Add a print statement to each copy, so any difference shows up in the output.
WHY: One function with one job is changed in one place and tested once. A global variable still leaves three copies of the logic in place.
```

### Handling errors with try, except, else and finally

**What it is.** Some code can fail, for example when text is not a number or a file is missing. The `try` block holds that code. An `except` block runs only when the named error happens inside the try block, so you name the error type you expect. An `else` block runs only when nothing went wrong. A `finally` block runs in every case, including when the function reaches a `return`. An error you do not catch stops the program and shows a traceback.

```python
def to_float(text):
    try:
        value = float(text)
    except ValueError:
        print("not a number:", text)
        return None
    else:
        print("converted")
        return value
    finally:
        print("checked")

print(to_float("36.6"))
print(to_float("n/a"))
```

Output:

```text
converted
checked
36.6
not a number: n/a
checked
None
```

The first call succeeds, so `except` is skipped and `else` prints `converted` and returns the value. `finally` runs before the function hands the value back, so `checked` prints next. The second call raises `ValueError` inside `float`. The `except` block prints the message and returns `None`, and `finally` still runs.

**How it shows up in a case study.** A CityPulse fetch step calls a web service while the network is down. A developer wrote `except:` with `pass` so that the scheduled job does not crash. The job ends with an empty report and no error in the log. The right decision is to catch only the error the call can raise, log the reason, and raise a clear error that stops the run. The problem is not that errors happen, but that they disappear.

:::trap A silent except
The tempting wrong answer is that a silent handler is safer. The empty report then looks like valid data. A bare `except:` also catches `KeyboardInterrupt`, which stops the user from cancelling the program.
:::

```quiz
Q: A fetch step wraps a network call in try and has except: pass. The network is down and the report shows no rows, with no error in the log. What is the root problem?
- The report needs an else block, which would show the rows when the call fails.
* The bare except hides the real error, so an empty result looks like valid data.
- The finally block is missing, so the connection cannot be closed.
- Fetch steps should not use try, because Python never recovers from network errors.
WHY: The error is removed before anyone sees it. Catching the expected type and logging the reason keeps the failure visible. Adding finally still hides the error.

Q: A script wraps float(row["value"]) in try with except ValueError: and logs the row. A row arrives with no value column at all, and the script stops with KeyError. Why?
- ValueError also covers KeyError, so the handler should have caught it.
- KeyError is only a warning, and Python prints it and carries on.
- The except clause runs only when the file is empty.
* KeyError is a different error type, so except ValueError does not catch it. Catch KeyError too, or check the header.
WHY: Each except names one error type. The tempting wrong answer is that ValueError covers any bad row, which it does not.

Q: A job must release a lock on a shared file whether it succeeded or failed. Which block runs in both cases?
* finally, which runs after try, except and else, in every case.
- else, which runs only when the try block finished with no error.
- except Exception, which runs only when an error happened, so it skips success.
- raise, which runs the cleanup code at the end of the function.
WHY: finally is the only block that runs in both cases. The tempting wrong answer is else, which skips every failure.
```

### Producing values lazily with yield

**What it is.** A generator is a function that uses `yield` instead of `return` to hand back values one at a time. Calling the function does not run its body. It returns a generator object, and each value is produced only when the caller asks for the next one. A generator can be used only once, because it is empty after it has produced everything. Generators save memory on large data, because the whole list is never built.

```python
def high_values(values, limit):
    for v in values:
        if v > limit:
            yield v

gen = high_values([40, 55, 61], 50)
print(sum(gen))
print(list(gen))
```

Output:

```text
116
[]
```

The function yields each value above the limit, one at a time. `gen` holds the generator, and its body has not run yet. `sum(gen)` pulls 55 and 61 from it and gives 116. After that the generator is empty, so `list(gen)` returns `[]`. To use the values again, you must call `high_values` again.

**How it shows up in a case study.** A team reads a year of readings from a very large file. The first step builds a list of every row in memory, and the shared server runs out of memory. A second step computes the total with `sum` and the count with `len(list(...))` from the same generator, and the count is zero. The right decision has two parts. Use a generator so each row is handled as it arrives. When two results need the same data, build one list once, or call the generator function again.

:::trap Reusing a generator
The tempting wrong answer is that `list(gen)` after `sum(gen)` still gives the values. It gives `[]` with no error, so the mistake is easy to miss.
:::

```quiz
Q: A script reads readings through a generator and needs both the total and the count. It writes total = sum(gen) and then count = len(list(gen)). The count is zero. Why?
- len cannot count the items of a generator, so it always returns zero.
- The sum step closed the file, so the second step has nothing to read.
* sum used up the generator, so the second use has no values left to produce.
- A generator must use return instead of yield to give back its values twice.
WHY: A generator produces each value once. The file-closing answer mixes up the file with the generator, and the file is still open.

Q: A job reads about two gigabytes of readings and must not keep every row in memory at once. Which feature fits best?
* A generator function with yield, which produces one row at a time as the loop asks for it.
- A dictionary keyed by row number, which stores every row for later lookup.
- A tuple of all rows, which is faster to build than a list and uses less memory.
- A global variable that holds the latest row, which every function can see.
WHY: yield gives one row at a time, so memory stays small. The tuple is tempting, but a tuple still holds every row at once.

Q: A student calls high_values(readings, 50) and prints the result. The output starts with <generator object. What must the student do to see the values?
- Call print on the function name, without the brackets.
- Change yield to return inside the function.
- Import the generator module first, because the function is in another file.
* Loop over the result, or pass it to list() or sum(), to pull the values out.
WHY: Calling a generator function returns a generator object, and the body runs only when values are requested. Changing yield to return removes the lazy behaviour the job needs.
```

### Writing small record classes with @dataclass

**What it is.** A class is a blueprint for a kind of object. A dataclass is a class in which you list the fields with type hints, and the `@dataclass` line above the class writes the usual set-up code for you. That code includes `__init__`, which stores the fields when you create an object, `__repr__`, which prints the object clearly, and `__eq__`, which compares two objects field by field.

```python
from dataclasses import dataclass

@dataclass
class Reading:
    station_id: str
    value: float

a = Reading("S1", 36.6)
b = Reading("S1", 36.6)
print(a)
print(a == b)
```

Output:

```text
Reading(station_id='S1', value=36.6)
True
```

`@dataclass` changes the class below it. The two fields are the only code you wrote. `Reading("S1", 36.6)` creates an object, matching the values to the fields in order. `print(a)` shows the generated text form. `a == b` is `True`, because every field is equal, even though `a` and `b` are two separate objects.

**How it shows up in a case study.** A team stores each parsed sensor row as a plain dictionary. A typo such as `"stn_id"` silently creates a new key, and the report counts the wrong station. The right decision is a dataclass with fixed field names. A misspelled attribute such as `reading.stn_id` fails at once with `AttributeError`, instead of quietly producing a wrong count. The dataclass is not a database, and it is not faster, so those answers are wrong here.

:::trap Mutable default lists
The tempting wrong answer is that `items: list = []` gives each object its own list. Python raises `ValueError` when the class is defined, so the module does not even import.
:::

```quiz
Q: A developer creates two Reading objects with the same station_id and value, then checks a == b in a test. Which result is correct for a dataclass?
- False, because each object has its own memory address.
- An error, because dataclasses cannot be compared with ==.
- False, because only the first field is compared.
* True, because the generated __eq__ compares every field.
WHY: The memory-address answer describes a plain class, where == compares identity. A dataclass generates __eq__ that compares fields.

Q: A team needs each Station object to start with its own empty list of tags. Which field line does this?
- tags: list = [], which is safe because each object gets a fresh list.
* tags: list = field(default_factory=list), which calls list() for each new object.
- tags: list = field(default=list), which gives each object a new list.
- tags: list = None, which is safe because None cannot be shared.
WHY: default_factory is called for every new object. The first option is rejected when the class is defined, and default=list sets the type itself as the default.

Q: A developer wants a Reading object that cannot be changed after it is created, so no later step alters a value by mistake. Which decorator argument does this?
- eq=False, which stops two objects from being compared.
- repr=False, which hides the object from print.
* frozen=True, which makes an assignment to a field raise an error.
- init=False, which stops the constructor from running.
WHY: frozen=True makes field assignment fail. The other arguments change comparison, printing or construction, not mutability.
```

### Default arguments that are lists or dicts

**What it is.** A default argument is a value used when the caller does not pass one, written as `def f(x=5)`. Python evaluates the default once, when `def` runs, not on each call. If the default is a list or a dictionary, every call that uses it shares the same object. Changes made in one call are visible in the next. The usual fix is a `None` default, with a new list created inside the function.

```python
def add_tag(tag, tags=[]):
    tags.append(tag)
    return tags

print(add_tag("pm25"))
print(add_tag("no2"))
```

Output:

```text
['pm25']
['pm25', 'no2']
```

The fixed version is this:

```python
def add_tag(tag, tags=None):
    if tags is None:
        tags = []
    tags.append(tag)
    return tags
```

With the fixed version, both calls print a one-item list: `['pm25']` and then `['no2']`. The default `tags=[]` creates one list when the function is defined, so the first call adds `pm25` to it, and the second call finds it still holding `pm25`. In the fixed version, `None` is the default, so `if tags is None` creates a new list for each call that does not pass one.

**How it shows up in a case study.** A CityPulse alert function keeps a history of alerts for the dashboard. Tests run one after another in the same process, and the second test sees alerts left over from the first. The team's first idea is to clear the history at the end of each run, but that breaks callers who pass their own list. The better decision is to change the default to `None` and create the list inside the function. No caller has to remember to clean up.

:::trap Thinking defaults reset on each call
The tempting wrong answer is that Python rebuilds `[]` for every call. It does not. The same list object is reused, so check what a second call sees.
:::

```quiz
Q: A function record_alert(value, history=[]) appends each value to history and returns it. In one run, the code calls record_alert(60) and then record_alert(70) without passing history. What does the second call return?
* [60, 70], because the default list is created once and reused by every call.
- [70], because each call starts with a new empty list.
- An error, because a default argument cannot be a list.
- [60], because the second call ignores the list from the first.
WHY: The default is created once, when def runs. The new-list answer is the most tempting, and it describes the fixed version, not this one.

Q: A developer wants a call that does not pass history to start with an empty list. Which definition does this correctly?
- def record_alert(value, history=list()): , which creates a new list for each call.
- def record_alert(value, history=[]): with history.clear() on its first line.
* def record_alert(value, history=None): with if history is None: history = [] inside the function.
- def record_alert(value, history=()): because a tuple is always empty.
WHY: list() in a default is evaluated once, like []. Clearing a shared list also clears the caller's own list. A tuple has no append method.

Q: A function count_hit(station, counts={}) increments counts[station] and returns counts. Two calls are made with no counts argument. What is true?
- Each call gets a new dictionary, so the counts never carry over.
* Both calls use the same dictionary, so counts from the first call remain in the second.
- The second call raises TypeError, because the default was already used.
- The second call receives None, because the default is cleared after one use.
WHY: The default dictionary is shared across calls. The fresh-dictionary answer is tempting, but it describes the None pattern.
```

### Importing modules and the __name__ check

**What it is.** A module is one `.py` file. `import name` loads the whole module, and you use its names with a dot, such as `statistics.mean`. `from name import thing` loads one name, so you can write `mean` alone. Python searches the folder of the running script first, then the standard library and installed packages. The check `if __name__ == "__main__":` is true only when the file is run directly. When another file imports it, `__name__` holds the module name, so the code under the check does not run.

```python
# helpers.py
def double(x):
    return x * 2

if __name__ == "__main__":
    print("running helpers directly")
```

```python
# main.py
from helpers import double
print(double(4))
```

Running `python main.py` prints `8`. Running `python helpers.py` prints `running helpers directly`.

`main.py` loads only `double`. Importing runs the top of `helpers.py`, which defines `double`, but it skips the body of the check, because `__name__` is `helpers` during the import. ### Caching results with functools.lru_cache

**What it is.** `functools.lru_cache` is a decorator, a line beginning with `@` that wraps a function. The wrapper keeps a table from arguments to results. When the function is called again with the same arguments, the stored result is returned at once, and the body does not run. The table lives in memory for one run of the program. Every argument must be hashable, which means Python can compute a stable key from it. Numbers, text and tuples are hashable. Lists and dictionaries are not, so calling a cached function with them raises `TypeError`.

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def square(n):
    print("computing", n)
    return n * n

print(square(3))
print(square(3))
```

Output:

```text
computing 3
9
9
```

The first call with 3 finds no stored result, so the body runs, prints `computing 3` and returns 9. The second call finds the stored 9 and returns it without printing. `maxsize=None` means the table has no size limit.

**How it shows up in a case study.** A CityPulse function `station_total(path)` reads a CSV file and sums its values. A developer adds `lru_cache` to speed up a dashboard. At 09:00 the total is correct. At 10:00 the file has new rows, but the dashboard still shows the 09:00 total. The function reads the file, which is not one of its arguments, so the cache cannot see the change. The right decision is to remove the cache from any function that reads files, the clock or other changing data. A bigger cache size does not help.

:::trap Caching a function that reads a file or the clock
The tempting wrong answer is that a bigger cache fixes stale results. The cache returns the old result for the same argument, even when the file has changed. Cache only pure functions, whose result depends only on their inputs.
:::

```quiz

- The cache is too small, so the old result was never removed.
- lru_cache works only with whole-number arguments, so it cannot read files.
* The function depends on the file, which is not an argument, so the 09:00 result is returned for the same path.
- lru_cache writes its results to the file, so the file cannot change.
WHY: The cache key is the argument, here the path. The file changes outside the key, so the cached answer is stale.

Q: A function total_for(station_ids) is decorated with lru_cache. A call with the list ['S1', 'S2'] raises TypeError: unhashable type: 'list'. Which change makes the call work and keeps the cache?
* Pass tuple(['S1', 'S2']) instead, because a tuple of text is hashable.
- Set maxsize=0, so the cache stores lists without hashing them.
- Remove the decorator, because the function is too simple to need a cache.
- Put the call inside a try block, which skips the unhashable argument.
WHY: A tuple with hashable items can be a key, and it keeps the caching. Removing the decorator also works, but it gives up the speed the question asks you to keep.

Q: A developer asks what lru_cache does with a pure function square(n) that is called many times in one program run. Which statement is true?

WHY: The cache is in memory and keyed by arguments. It does not check purity, and it never returns a result for different arguments.
```

### Worked twin problem

This problem has a different domain and different rules from the lab, but it needs the same skills. Read it as a lab task.

A library records each loan as a dictionary with three keys: `member` (text), `genre` (text) and `days` (a whole number of days the book was kept). Write three functions.

- `loans_per_genre(loans)` returns a list of `(genre, count)` tuples, sorted by count from highest to lowest. Genres with the same count are sorted by name, A to Z. An empty list gives `[]`.
- `average_days(loans, genre)` returns the average `days` of the loans for that genre, rounded to one decimal place. It returns `None` if no loan has that genre.
- `top_member(loans)` returns the member with the most loans. On a tie, it returns the member who appears first in the list. It returns `None` for an empty list.

The solution and its tests are below. The block runs when the book is built.

```python test
def loans_per_genre(loans):
    counts = {}
    for loan in loans:
        genre = loan["genre"]
        counts[genre] = counts.get(genre, 0) + 1
    return sorted(counts.items(), key=lambda pair: (-pair[1], pair[0]))


def average_days(loans, genre):
    days = [loan["days"] for loan in loans if loan["genre"] == genre]
    if not days:
        return None
    return round(sum(days) / len(days), 1)


def top_member(loans):
    counts = {}
    for loan in loans:
        member = loan["member"]
        counts[member] = counts.get(member, 0) + 1
    if not counts:
        return None
    return max(counts, key=counts.get)


loans = [
    {"member": "Ana", "genre": "science", "days": 14},
    {"member": "Ben", "genre": "fiction", "days": 7},
    {"member": "Ana", "genre": "fiction", "days": 10},
    {"member": "Ben", "genre": "science", "days": 21},
]

assert average_days(loans, "science") == 17.5
assert average_days(loans, "fiction") == 8.5
assert average_days(loans, "poetry") is None
assert average_days([], "science") is None
thirds = [{"member": "x", "genre": "g", "days": d} for d in (1, 2, 2)]

assert top_member(loans) == "Ana"
assert top_member([]) is None
assert top_member([
    {"member": "Zed", "genre": "g", "days": 1},
    {"member": "Amy", "genre": "g", "days": 1},
]) == "Zed"
assert top_member(loans + [{"member": "Ben", "genre": "g", "days": 1}]) == "Ben"
print("all checks passed")
```

Line by line, starting with `loans_per_genre`:

- `counts = {}` starts an empty dictionary for the counts.
- The loop reads the genre of each loan and stores the count plus one, using `get` with a default of 0, so a new genre starts at 1.
- `sorted(counts.items(), key=...)` turns the dictionary into `(genre, count)` tuples and sorts them. The key `(-pair[1], pair[0])` sorts the count from highest to lowest, because the minus sign reverses it, and the genre name from A to Z for equal counts.
- An empty list never enters the loop, so `counts` stays empty and `sorted` returns `[]`.

For `average_days`, the list comprehension keeps the days for one genre. An empty list returns `None` before any division. Otherwise the sum divided by the length is rounded to one decimal place. The third assert, `thirds`, gives 5 divided by 3, which is 1.6666, and that rounds to 1.7.

For `top_member`, the counting is the same. `max(counts, key=counts.get)` returns the member with the largest count. Python's `max` returns the first maximal item it meets, and dictionaries keep the order in which keys were first added. So on a tie, the member who appeared first in the list wins. The `top_member(loans)` assert (Ana and Ben tied, Ana first) and the Zed and Amy assert test that rule, and the final assert checks that Ben wins when he has the most loans.
