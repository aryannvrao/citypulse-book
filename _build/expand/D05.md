## What the quiz tests

The Day quiz has ten case-study multiple-choice questions. There is one question for each topic below, in the same order. You need 70% to pass, so seven correct answers is the minimum. The first attempt is the one your skill score keeps, so take your time on the first try and do not treat it as practice.

Each case study is a short scenario with a team, a symptom and a constraint. Work through it in a fixed order. Read the last line first, because it tells you what is being asked. Then go back to the scenario and underline the facts that matter: which branch is involved, whether anyone else has pulled it, and whether main has moved since the branch was made. Next, go through the options and eliminate any that are true in general but do not fix this scenario. Many wrong answers are sensible Git advice that answers a different question.

Watch three words. "Most" asks for the strongest answer when several are reasonable. "First" asks what to do before anything else, so a good step that comes later is wrong. "Best" asks for the option that fits every constraint in the scenario, not just any correct statement. If an option would destroy work or rewrite history that a teammate depends on, it is almost never the answer.

### Creating a branch

**What it is.** A branch is a movable name that points at a commit. When you run `git switch -c feat/21-export`, Git creates the name at the commit you are on at that moment and switches your files to it. The new branch starts from that point and from nothing else. Creating a branch does not change main, and it changes nothing on GitHub until you push. You can check where you are with these commands:

```term
$ git switch main
Switched to branch 'main'
$ git pull --ff-only
Already up to date.
$ git switch -c feat/21-export
Switched to a new branch 'feat/21-export'
$ git log --oneline -1
6400cdb Drop duplicate station readings
```

The last command shows the commit the branch starts from. The name `feat/21-export` says nothing about that point, so check the commit before you write any code.

**How it shows up in a case study.** Mina has finished her export code for Issue #21. Her local main is three days old because she has not pulled, and she runs `git switch -c feat/21-export` straight away. When she opens the pull request, the diff shows old ingest code as new, and Git reports conflicts that a teammate has already solved on main. The reasoning is that the starting point decides what the diff contains. The fix is to switch to main, run `git pull --ff-only`, create the branch again, and re-apply her edits on top. Nothing needs to be deleted on GitHub, and the name of the branch can stay the same.

:::trap Thinking a branch name is the starting point
The name `feat/21-export` looks as if it starts from a known point, but it does not. Only the commit you are on when you create the branch decides where it begins.
:::

```quiz
Q: Yusuf has a finished change for Issue #18. His local main is a week old because he has not pulled, and he creates feat/18-alerts with git switch -c right away. What is the main risk of this order?
- Git deletes the remote main branch on GitHub.
* The branch starts from the old main, so his diff mixes his change with old code and conflicts become likely.
- The Issue moves to the Done column on the project board.
- Main becomes read-only until he pushes the branch.
WHY: A new branch starts at the commit you are on, so a stale main gives a stale starting point. git switch -c never touches the remote. The tempting answer about deleting remote main is wrong because no branch command does that.

Q: Lena made the branch feat/9-units from an old commit and has not shared it. Main has moved on, and she wants her commits to sit on the latest main without losing any of them. Which step comes first?
- Delete feat/9-units and create it again, which keeps her commits.
- Run git push --force to reset the remote branch to match her laptop.

- Commit an empty change so that Git treats the branch as new.
WHY: A rebase moves the starting point of her commits without losing them, and the fetch makes sure origin/main is current. Deleting the branch throws the commits away. The force push does not change where the branch starts, and an empty commit changes nothing about the base.

* git switch -c feat/30-filters
- git branch --delete feat/30-filters
- git push origin feat/30-filters

WHY: git switch -c creates a branch at the current commit and switches to it. git branch --delete removes a branch. git push uploads a branch that already exists, and git tag -a creates a tag rather than a branch.
```

### Why a pull request exists

**What it is.** A pull request is GitHub's page for asking that one branch be merged into another, usually main. It holds the diff, the discussion and the results of any checks in one place. Opening a pull request does not change main. Nothing is merged until someone merges it, and in CityPulse that happens only after a teammate has reviewed the change. The author writes a description that says what changed, why, and how it was tested. The words `Closes #12` in the description link the pull request to Issue #12, so GitHub closes the Issue when the pull request merges. Here is what the command looks like from the terminal:

```term
$ gh pr create --base main --title "Add --loc flag" --body "Closes #12. How tested: one row appended."
https://github.com/you/citypulse/pull/14
```

The printed address is the page where reviewers read the diff and leave comments.

**How it shows up in a case study.** Ravi tells the squad that they do not need pull requests, because he can merge his branch into main himself. He has tested the change on his laptop and is confident it is correct. The squad's gate counts substantive reviews, and the team wants the Issue to close on its own when the work lands. The reasoning is that a pull request is the control point where a teammate reads and runs the change before it reaches main. Ravi's own test is useful evidence, but it is not a review. The pull request is also where `Closes #n` takes effect, so the right reply explains the review and the link as the purpose of the pull request.

:::trap Treating the PR as a backup
A pull request is not a backup. The branch on origin already holds the commits. The pull request is the proposal to merge them.
:::

```quiz

* It puts the diff, the discussion and the checks in one place, so a teammate can review and run the change before it reaches main.

WHY: The review is the control the squad is scored on, and the pull request is where that review happens. The backup answer is tempting, but the branch on origin already holds the commits, so the pull request adds no backup.

- Ask one reviewer to approve without reading, because the title is clear.
- Delete the branch, since the pull request has no description.
WHY: A description that says what, why and how lets reviewers act on it, and Closes #21 links the Issue. Merging directly skips the review that the course rules require. Deleting the branch would throw away the work.

```

### Resolving a merge conflict

**What it is.** A merge or a rebase stops with a conflict when two lines of history changed the same lines of one file, and Git cannot choose between the two versions. Git writes both versions into the file between marker lines, so that a person can decide. A conflict looks like this in the terminal:

```term
$ git merge origin/main
Auto-merging clean.py
CONFLICT (content): Merge conflict in clean.py
Automatic merge failed; fix conflicts and then commit the result.
```

Inside `clean.py`, the conflicting part is marked like this:

```text
<<<<<<< HEAD
rows = [r for r in rows if float(r["value"]) > 0]
=======
rows = [r for r in rows if float(r["value"]) >= 0]
>>>>>>> origin/main
```

In a merge, the line `<<<<<<< HEAD` starts your version (in a rebase the two sides are swapped: HEAD is the branch you are rebasing onto). The line of equals signs separates the two versions, and the line ending in `>>>>>>>` closes the other side. To resolve the conflict, you edit the lines to keep the correct code, delete the three marker lines, run `git add` on the file, and then finish the merge or rebase. A conflict is a request for a human decision, not a failure that needs a force push.

**How it shows up in a case study.** Dana's merge of origin/main into her branch stops in clean.py. Her branch removes zero-value readings, and main has changed the same line in another way. Git cannot know which rule CityPulse wants, because that depends on the data and the team's decision. Dana must read both versions, choose or combine them, delete the markers, run the tests, and only then stage and commit. She must not force push, because that would overwrite the teammate's change on origin.

:::trap Force-pushing to get rid of a conflict
A force push does not resolve a conflict. It replaces the remote version with yours and can erase a teammate's work.
:::

```quiz
Q: Dana runs git merge origin/main and sees CONFLICT (content) in clean.py. Her branch and main both changed the same line. Which action resolves the conflict correctly?
* Edit clean.py to keep the right code, delete the three marker lines, run git add clean.py, then finish the merge with a commit.
- Run git merge --abort, then git push --force so that the remote matches her branch.
- Delete clean.py from the branch and commit the deletion.
- Run git commit --allow-empty to clear the conflict markers.
WHY: The markers show two versions, and a person must choose between them. Once the file is edited and staged, Git can finish the merge. The force-push answer is tempting because it looks quick, but it overwrites a teammate's work on origin.

Q: Kofi is rebasing feat/15-zones onto origin/main, and the rebase stops with a conflict in zones.py. The file shows a line of equals signs between two blocks of code. What does that line mark?

- The end of the file, where Git stops reading.
* The boundary between the two versions of the conflicting lines, with the first version above it and the second below.
- The line that tells Git the conflict is already resolved.
WHY: The equals line separates the two versions. The start marker opens the first version and the end marker closes the second. The answer about "already resolved" is tempting, but only deleting the markers, running git add and continuing the rebase finishes the job.

Q: Meera's merge stopped with a conflict. She has edited the file, deleted the markers and run the tests, and they pass. What is the next step, and what must she avoid?
* Run git add on the file, then complete the merge with a commit, and avoid git push --force to make the remote match her local copy.
- Run git push --force and skip git add, since the tests pass.
- Delete the markers, then create a new branch from the old commit.
- Open a second pull request, because every conflict needs its own pull request.
WHY: git add records the resolved file, and the commit finishes the merge. A force push would overwrite the remote version and could erase a teammate's work. The second pull request is wrong because a conflict belongs to the same branch.
```

### Updating a pull request with new commits

**What it is.** A pull request follows its branch. The pull request records the branch name, and it shows whatever commits are on that branch. When you push a new commit to the same branch, GitHub adds the commit to the pull request, and the diff updates by itself. You do not open a second pull request. Review threads stay attached to the lines they were written about, so you answer each thread, and then resolve it. The push output shows the branch moving from one commit to another:

```term
$ git add scripts/fetch.sh
$ git commit -m "Add usage check for --loc without a value"
$ git push
   a1b2c3d..e4f5a6b  feat/12-loc-flag -> feat/12-loc-flag
```

The arrow shows that the branch on origin now points at the new commit, and the pull request shows it too.

**How it shows up in a case study.** Ines's reviewer has requested changes on PR #14 because the script has no usage check. Ines creates a new pull request with the fix, and the first pull request stays open with its review history. Now two reviewers must read the same change twice, and the approval is split. The reasoning is that the pull request is the branch, so the fix belongs on feat/12-loc-flag as a new commit. Ines pushes the commit, replies in the thread, resolves it, and asks the reviewer to re-run the code and approve.

:::trap Opening a second PR for the fix
A second pull request splits the review history and leaves the first one stuck. Push the fix to the same branch instead.
:::

```quiz
Q: Tomas has pushed a fix commit to feat/12-loc-flag after a request for changes on PR #14. The reviewer asks where the new code is. Which statement is correct?
- The reviewer must open a new pull request, because the old one shows a fixed snapshot.
- The fix exists only on Tomas's laptop until he opens a second pull request.
- The pull request must be closed and reopened before the new commit can appear.
* The pull request follows its branch, so the new commit appears on PR #14 by itself and the reviewer can check it there.
WHY: A pull request is a live view of its branch, not a snapshot. The second pull request is tempting, but it splits the review history and is not needed.

Q: Hana's reviewer left a thread about a missing usage check. Hana has fixed the code, pushed the commit and replied in the thread. What must happen before the pull request merges?
* The reviewer re-runs the branch and approves, and every thread is either answered or resolved.
- Hana merges at once, because she has replied to the thread.
- The reviewer deletes the thread so that the pull request can merge.
- Hana rebases main onto the branch so that the thread disappears.
WHY: A reply does not replace the reviewer's check. The course rule is to answer or resolve each thread, and the approval comes after the re-run. Rebasing does not remove comments from a pull request.

Q: Jun pushed a new commit to his branch on Tuesday. On Wednesday a reviewer says the pull request still shows the old diff. What is the most likely explanation, and what should Jun check first?
- The pull request is a fixed copy, so Jun must recreate it with the same title.
- GitHub keeps the first diff for a week, so Jun should wait and see.
* Jun may have pushed to a different branch from the one the pull request follows, so he should check the branch name on the pull request and push there.
- Git does not send commits to GitHub unless the commit has a tag.
WHY: A pull request follows the branch it was opened from. If the push went to another branch, the pull request cannot see it. The tag answer is wrong, because push sends commits and tags are separate.
```

### Branch protection rules

**What it is.** Branch protection is a GitHub rule that applies to a branch such as main. It blocks direct pushes and can require conditions before a merge, such as a pull request with approvals or passing checks. GitHub enforces the rule on the server, so it still applies when someone pushes from a terminal. In CityPulse, the rule requires one approving review, and it covers administrators through the setting `enforce_admins`. A direct push that is refused looks like this:

```term
$ git push origin main
! [remote rejected] main -> main (protected branch hook declined)
error: failed to push some refs to 'origin'
```

The setting `enforce_admins` decides whether the rule binds administrators. If it is missing or false, the rule applies to everyone except repository administrators, and those people can push directly. The required approval count is a number. A value of 1 means one approving review is needed before a merge.

**How it shows up in a case study.** The Tech Lead of a squad pushes a small fix straight to main during a deadline, and the push succeeds. The squad's rule says main needs one approval, so the protection exists on paper, but administrators were not included. The reasoning is that the rule is not enforced for administrators at all. The fix is to set `enforce_admins` to true, then prove the rule works by trying a direct push that GitHub must refuse. A promise from the Tech Lead is not enforcement, and neither is a team agreement written in a document.

:::trap Forgetting administrators
A rule that does not include administrators is not enforced for the Tech Lead. The setting `enforce_admins` must be true.
:::

```quiz
Q: The squad has a rule that main needs one approval. The Tech Lead, who is a repository administrator, pushes a fix to main during a deadline, and the push succeeds. Which setting most likely explains this?
* enforce_admins is missing or false, so the rule does not apply to repository administrators.
- The required approval count is zero, so the rule has no effect at all.
- main has no commits, so GitHub has nothing to compare the push with.
- The branch name does not start with feat, so the protection ignores it.
WHY: enforce_admins decides whether administrators are covered. A count of zero would also explain the result, but the case says the rule requires one approval, so the missing setting is the most likely cause. The naming answer is wrong because the rule is set on main itself.

Q: The squad has turned on branch protection for main. Which test best proves that the rule works for everyone, including the Tech Lead?
- Read the rule on the GitHub settings page and confirm that it is switched on.
- Run git status on main and check that it says there is nothing to commit.
- Create a new branch and open a pull request from it.
* Create an empty commit, try to push it straight to main as the Tech Lead, and keep the rejection message as evidence.
WHY: A direct push is exactly what the rule must refuse, so the refusal is the proof. Reading the settings page shows what was intended, not what is enforced. Git status shows local files only, and a new branch does not test the protection on main.

Q: Ellen has enabled branch protection on main and requires one approval. A teammate asks whether the rule also stops a direct push from an administrator. What is the correct answer?
* Only if enforce_admins is set to true, because otherwise administrators are not bound by the rule.
- Yes, always, because administrators can never push directly under any protection.
- No, because a rule can only block people who are not in the team.
- Yes, because the approval count applies to administrators' own commits by default.
WHY: enforce_admins brings administrators under the rule. Without it, the required approval does not bind them. The "always" answer is tempting, but it assumes a setting that the question does not confirm.
```

### Rebasing onto main

**What it is.** A rebase takes your commits and replays them on top of a newer base, usually origin/main. Git creates new copies of the commits with new IDs, so the history looks as if you started from the newer main. The old commits stay in Git's reflog for a while, but they are no longer on the branch. Because the history has changed, a normal push is refused afterwards. The usual sequence is shown below:

```term
$ git fetch origin
$ git rebase origin/main
Successfully rebased and updated refs/heads/feat/15-zones.
$ git push --force-with-lease
```

The `--force-with-lease` option replaces the remote branch, but only if the remote is the same as the copy your last fetch saw. If someone else has pushed since then, the push is refused, and nobody's work is overwritten silently.

**How it shows up in a case study.** Ben's branch feat/22-alerts has been pulled by Carla, who has added her own commit on top. Main has moved on, and Ben wants a clean history, so he plans to rebase and force-push. The reasoning is that Carla's copy still holds the old commits, so after the rebase her next pull would produce a tangle of duplicate history. Ben should merge origin/main into the branch instead and push normally. The merge keeps every commit that Carla already has, and it adds one new commit that records the join.

:::trap Rebasing a shared branch
The usual mistake is to rebase a branch that a teammate has already pulled. Their next pull then produces duplicate or tangled history.
:::

```quiz
Q: Carla has pulled Ben's branch feat/22-alerts and added a commit. Main has moved on, and Ben wants the new main work in without making a tangle. Which action is correct?
- Rebase onto origin/main and force-push, so that the branch has one clean line.
- Delete the branch on GitHub and push a new copy from Ben's laptop.
* Merge origin/main into the branch and push normally, because Carla already has the old commits.
- Run git commit --allow-empty and push, so that main's work is marked as seen.
WHY: A rebase gives the commits new IDs, so Carla's copy no longer matches the branch. A merge keeps the old commits and adds one new commit. The force-push answer is tempting, but it would leave Carla with a tangle the next time she pulls.

Q: Priya is the only person using feat/15-zones, and she has already pushed it. Main has moved on, and she wants her history to sit on the latest main. Which sequence is both readable and safe?
* git fetch origin, then git rebase origin/main, then git push --force-with-lease.
- git rebase origin/main, then git push --force.
- git merge main, then git push --force-with-lease.
- git rebase main, then git push.
WHY: Only Priya uses the branch, so rebasing is safe. Fetching first makes origin/main current, and --force-with-lease refuses if someone has pushed since her fetch. Plain --force skips that check. The answer with git rebase main uses her local main, which may be out of date.

Q: Sam rebased his branch onto origin/main and then ran a normal git push. Git refused the push. What is the best explanation?
- GitHub does not accept branches that have been rebased.
- The branch name is too long for the remote to store.
- Main is protected, so no branch can be pushed to it.
* The rebase rewrote the commits, so the remote branch and the local branch now have different histories, and a normal push is refused.
WHY: A push is refused when the remote would lose commits that the local branch does not contain. The answer is --force-with-lease, provided that only Sam uses the branch. The protected-main answer is tempting, but this push targets his own branch.
```

### Writing a useful review

**What it is.** A code review is a teammate reading a change, running it, and then commenting, requesting changes or approving. A useful review comment says three things: what you ran, what input you used, and what you saw. The course rule is that a bare "LGTM" earns no credit under the T08 rules, and general praise earns nothing either. An approval needs evidence in the same way. A review of a script might look like this in the terminal:

```term
$ gh pr checkout 14
$ ./scripts/fetch.sh --loc
```

The first command downloads the pull request's branch to your computer, so you can run it. The second command runs the script with the flag but no value, which is the case the author may have missed. The review comment then reports what happened when the script ran, using the exact input.

**How it shows up in a case study.** Dev's pull request changes a script that reads location names. The reviewer, Ana, writes "Looks good, nice work" and approves. Later the script fails when a location name contains a space. The reasoning is that general praise and an approval without a run give the author nothing to act on. A comment that states the run, the input and the result would have caught the problem: "I ran the branch with a location name that has a space. It failed on the variable, so please quote it." A stranger could act on that without asking any question.

:::trap Approving without running
An approval that does not mention a run is not evidence. A reviewer who only read the diff can miss runtime errors.
:::

```quiz
Q: Which review comment earns credit under the course rules for a change to fetch.sh?
* I ran the branch with a location name that has a space. The script failed with an error on the variable, so please quote it.
- LGTM.
- Nice work, the code is clean and tidy.
- Approved after reading the diff carefully.
WHY: The right comment says what was run, what input was used, what happened and what to change. The other three contain no evidence. The answer about reading the diff is tempting, but reading is not running.

Q: Kiran wants to approve PR #14, which adds a usage check for the flag. Which approval comment is most useful to the author?
- Approved, ship it.
- Good work on this one, team.
* Re-ran the branch with --loc and no value. It printed the usage message and exited with an error, so the fix works.
- Approved, I trust you.
WHY: The approval states the run and the result, so the author knows what was checked. The first three comments give no evidence. "I trust you" is a feeling, not a check.

Q: A reviewer has run the branch and found a real bug. Which comment is most useful, and why does its form matter?
- Please look at it again, something seems wrong.
* Blocking: with a space in the location name the script stops with an error at the line that uses the variable. Quote the variable and re-run with that input.
- It is a problem, so maybe fix it sometime.
- It would be better if it were done in a different way in general.
WHY: A comment that a stranger could act on names the problem, the input, the place and the change. A vague comment forces the author to ask questions before fixing anything. The first answer is tempting, but it is vague.
```

### Squash merging

**What it is.** A squash merge takes all the commits of a pull request and combines their changes into one new commit on main. The branch keeps its own commits, but main gets one commit that carries the pull request's title. The command is run by the person who merges the approved pull request:

```term
$ gh pr merge 14 --squash --delete-branch
```

The flag `--delete-branch` removes the branch after the merge. A normal merge with a merge commit keeps every commit from the branch, plus the merge itself, so main gets all of them. A squash keeps main to one commit per pull request, which makes its history short and easy to read. Neither choice changes the commits that are already on main.

**How it shows up in a case study.** The squad wants main to show one commit per pull request, with no work-in-progress commits such as "fix typo" or "try again". Kiran's pull request has seven commits of that kind. The reasoning is that a squash merge keeps main readable, while the branch keeps the detailed history for anyone who needs it. The team should choose a squash for pull requests where the detail is noise, and a merge where the separate commits matter. A squash does not rewrite main's old history. It adds one new commit.

:::trap Assuming squash rewrites main's old history
A squash merge does not change the commits that are already on main. It adds one new commit for the pull request.
:::

```quiz
Q: The squad wants main to get one commit per pull request, with no work-in-progress commits such as "try again". Which command does this once the pull request is approved?
- git merge --no-ff feat/21-export, which keeps every commit.
- git push --force origin main, which rewrites main to match the branch.
- git rebase main on the feature branch, then push the branch.
* gh pr merge 21 --squash --delete-branch
WHY: The squash merge combines the pull request's commits into one commit on main. The no-fast-forward merge keeps every commit, which is the opposite of the goal. Rebasing changes only the branch, and force-pushing main breaks the protection rule.

Q: Mina squash-merged PR #21, and now main has one new commit. The individual commits from her branch do not appear on main. Which statement describes this correctly?
* A squash merge copies the net change into one new commit on main, so the separate branch commits are summarised by that commit.
- The squash merge deleted the branch commits from the repository.
- The squash merge rewrote all of main's old commits into one commit.
- The squash merge is only valid when the branch has exactly one commit.
WHY: The net change is kept, but the separate commits are not on main. The rewrite answer is the tempting one, but a squash leaves main's older history alone.

Q: After a squash merge, git branch -d feat/22-alerts refuses to delete the local branch. What is the reason, and what should the developer do?
- Git refuses because the branch name starts with feat, which is reserved.
- Git refuses because main is protected, so it cannot check the branch.
* Git cannot find the branch's original commits on main, so it treats the branch as unmerged. Check with git log main..feat/22-alerts, and use -D only if the squash was correct.
- Git refuses because the branch still exists on GitHub, so it must be deleted there first.
WHY: After a squash, main holds one new commit, so the branch's own commits are not in main's history. The -d option checks for that and refuses. The -D option forces the deletion, so you should check the commits first. Note that git log main..feat/22-alerts lists every branch commit after a squash, so it shows what would be lost; confirm on GitHub that the pull request was merged.
```

### The fork concept

**What it is.** A fork is a copy of someone else's repository that GitHub makes under your own account. You have full rights in your fork, but you have no push rights in the original unless the owner gives you write access. To contribute, you push a branch to your fork and open a pull request from that fork into the original repository. A clone is different. It is a download of a repository to your computer. Your clone usually points at a remote called `origin`, and that remote can be your fork or the original. A typical clone looks like this:

```term
$ git clone https://github.com/you/citypulse.git
Cloning into 'citypulse'...
```

The address contains your account name, which shows that the copy belongs to you. A fork is the GitHub copy. A clone is what you download onto your machine.

**How it shows up in a case study.** A student who is not on the CityPulse team wants to add a feature, but has only read access to the repository. The student forks the repository, pushes feat/31-units to the fork, and opens a pull request from the fork into the original. The reasoning is that the fork is the only place where this student has rights. The original repository receives the proposal, and the Tech Lead reviews it there. A direct push to the original would be refused, and a download of the code would not let the student propose a merge.

:::trap Confusing a fork with a clone
A clone is a download to your own machine. A fork is a copy on GitHub that belongs to your account.
:::

```quiz
Q: A student has only read access to the CityPulse repository and wants to propose a change. What is the correct route?
* Fork the repository, push a branch to the fork, then open a pull request from the fork into the original.
```

### Comparing branches with diff

**What it is.** `git diff` compares two versions of the files and prints the changed lines. Two dots, as in `main..feat/22-alerts`, compare the tip of main with the tip of the branch. Three dots, as in `main...feat/22-alerts`, compare the branch with the point where it split from main. If main has moved on since the split, the two-dot form also shows main's newer work, but as removed lines, as if the branch had deleted it. The three-dot form shows only what the branch adds. The `--stat` option summarises the result by file:

```term
$ git diff --stat main...feat/22-alerts
 alerts.py | 14 ++++++++++++--
 1 file changed, 12 insertions(+), 2 deletions(-)
```

The last line gives the totals, so you can see at a glance how large the change is before you read the lines themselves.

**How it shows up in a case study.** Shreya's branch was made a week ago, and main has merged two pull requests since then. She wants to check that her pull request contains only her own change before she asks for a review. Her two-dot diff shows lines from the other pull requests as removed, which looks alarming. The reasoning is that the three-dot form compares against the split point, so only her own change appears. She should run the three-dot `--stat` command to check the summary, then read the lines of the file she changed.

:::trap Using two dots when main has moved
Two dots show main's newer work as removed. Use three dots to see only what the branch adds.
:::


## The graded lab

The graded lab is a Python problem with three functions in a starter file. The platform runs automatic tests on your functions after you submit. Some tests use cases that the examples do not show, so you have to think about the edge cases yourself. This part explains the task, the Python ideas it needs, the rules that careless solutions break, and a method you can use for any graded lab. It also works through a twin problem from another domain, so that you can practise the same skills on different data.

### The task in plain words

**The scenario.** The CityPulse team has a bot that runs as part of its pull request gate. The bot summarises the diff, reads the review states and decides whether a pull request may merge. Your job is to write the three functions that do these three jobs. You do not need files, network access or input from the keyboard.

**The functions and their rules.** Each function is listed with its name, its input and every rule in the statement.

- `summarize(changes)`: `changes` is a list of dictionaries. Each dictionary has the keys `path`, `additions` and `deletions`.
  - Return a tuple of three integers, in this order: the number of files changed, the total of the additions, and the total of the deletions.
  - Each dictionary is one changed file, so the file count is the number of dictionaries.
  - An empty list has no changes, so the result is `(0, 0, 0)`.
  - The statement's example is one file with 40 additions and 5 deletions, which gives `(1, 40, 5)`.
- `review_decision(reviews)`: `reviews` is a list of review states. Each state is one of the strings `'approve'`, `'request_changes'` or `'comment'`.
  - Return `'blocked'` if any reviewer requested changes, even when other reviewers approved.
  - Otherwise return `'approved'` if at least one reviewer approved.
  - Otherwise return `'pending'`. This includes an empty list and a list that contains only comments.
  - The statement's example is `["approve", "request_changes"]`, which gives `'blocked'`.
- `is_mergeable(pr)`: `pr` is a dictionary with the keys `draft`, `conflicts`, `ci_passed`, `changes_requested`, `approvals` and `required_approvals`.
  - Return `True` only if the pull request is not a draft, has no conflicts, has passing CI, has no outstanding change requests, and has `approvals` at least equal to `required_approvals`.
  - In every other case the result is `False`.

**The scoring.** The five visible tests are worth 68 points in total. The table below gives each one.

| Visible test | Points |
|---|---|
| Totals files, additions and deletions | 18 |
| No changes gives (0, 0, 0) | 10 |
| Approvals with no blocks gives approved | 14 |
| Any request_changes gives blocked | 14 |
| All rules satisfied gives mergeable | 12 |

The limits are 30 seconds of running time and 128 MB of memory. Your solution is far inside both limits, so speed is not the issue.

**Hidden tests.** There are three hidden tests, worth 32 points together. You do not see their inputs. They run only after you submit, and they check cases that the visible tests do not show. Because they are worth 32 of the 100 points, a solution that passes only the visible tests can reach at most 68. The top marks depend on the hidden tests, so you must read the rules as closely as a tester would. The rules table later in this section lists the checks that they are most likely to make.

### What each function needs

Each idea below is taught with a small example that has nothing to do with the lab's data. Work out the output yourself before you check it.

**Adding up a field in a list of dictionaries.** Use `sum` with a generator, or a loop with a counter. Each item of the list is one record, and you pick out the field you want.

```python
sales = [{"item": "bun", "count": 3}, {"item": "cake", "count": 1}]
total = sum(s["count"] for s in sales)
print(total)
```

The output is `4`. The `for s in sales` part runs once for each dictionary, and `s["count"]` reads one field from it. An empty list gives `sum` the value `0`, which is the correct total for no records.

**Returning several values as a tuple, and reading them back.** A tuple is a fixed group of values in round brackets. A function can return one, and the caller can unpack it into names.

```python
pair = (2, 7, 1)
first, second, third = pair
print(second)
```

The output is `7`. The three names take the three values in order, so the order you return the values in matters to the caller. The number of values must also match the number of names, or Python raises an error.

**Counting items and checking their number.** `len` returns the number of items in a list or a tuple. An empty list has length `0`.

```python
print(len(["red", "green"]), len([]))
```

The output is `2 0`. Counting entries is the simplest way to report how many records there were.

**Matching text exactly.** The `==` operator compares two strings letter by letter, and capital letters count as different letters.

```python
print("Yes" == "yes", "yes" in ["no", "yes"])
```

The output is `False True`. A review state written as `'Approve'` would not match `'approve'`, so the rules that name exact strings must be followed exactly.

**Checking whether any or all items match.** `any` returns `True` when at least one item is true. `all` returns `True` only when every item is true. Both behave in a surprising way for an empty list.

```python
print(any([]), all([]), any([0, 3]), all([0, 3]))
```

The output is `False True True False`. An empty list has no item that is true, so `any` gives `False`. It also has no item that is false, so `all` gives `True`. Remember this when a rule says "every" or "at least one" and the input may be empty.

**Choosing a result with an ordered series of checks.** When several rules can apply, test them in priority order and return at the first match. The order of the `if` lines is the priority.

```python
def weather_advice(rain, cold):
    if rain:
        return "take an umbrella"
    if cold:
        return "wear a coat"
    return "go out"

print(weather_advice(True, True))
```

The output is `take an umbrella`. Both conditions are true here, but the first one wins, because the function returns as soon as it reaches a `return`. If the rules are in the wrong order, a case that should be blocked can be reported under a weaker message.

**Booleans, comparisons and the boundary.** A comparison gives `True` or `False`. The `>=` operator includes the boundary value, and `>` does not.

```python
print(3 >= 3, 3 > 3, 2 >= 3)
```

The output is `True False False`. The rule "at least" uses `>=`, and the rule "more than" uses `>`. A bool is also a kind of integer in Python, so `isinstance(True, int)` gives `True`, but `type(True) is int` gives `False`. When a value must be a real bool, a comparison or a literal `True` is the safest way to return it.

**Reading a dictionary with a default.** `dict.get(key, default)` returns the value for the key, or the default when the key is missing. A plain `dict[key]` raises an error for a missing key.

```python
stock = {"bun": 3}
print(stock.get("bun", 0), stock.get("cake", 0))
```

The output is `3 0`. A missing optional field can be read safely with `get`, and a required field should be read with square brackets so that a missing key is noticed.

**Sorting by more than one field.** `sorted` with a `key` function builds a new list in the order the key gives. A tuple key sorts by the first item, then by the second item for ties. A minus sign reverses the order of a number.

```python
snacks = [("tea", 2), ("jam", 5), ("bun", 2)]
print(sorted(snacks, key=lambda p: (-p[1], p[0])))
```

The output is `[('jam', 5), ('bun', 2), ('tea', 2)]`. The largest count comes first because of the minus sign, and the two items with count 2 are in name order because the name is the second part of the key.

**Not changing the input.** `sorted` returns a new list and leaves the original alone. The method `list.sort()` changes the list in place and returns `None`. Choose the first when the caller's data must stay the same.

```python
nums = [3, 1]
new = sorted(nums)
print(nums, new)
```

The output is `[3, 1] [1, 3]`. The original list is unchanged. Changing the input by accident is one of the most common reasons a hidden test fails, because a later check uses the changed data.

**Rounding.** Python's `round` uses round-half-to-even for exact halves, and it can show a float that is slightly off.

```python
print(round(2.5), round(3.5), round(2.675, 2))
```

The output is `2 4 2.67`. The float 2.675 is stored as a value a little below 2.675, so it rounds down. Round only at the end of a calculation, and never round a count. A count of whole things is already an exact integer.

Each row is a rule from the statement, the mistake a careless solution makes, and a check you can run yourself. Write the checks as `assert` lines before you submit.

| Rule in the statement | What a careless solution does | How to check yours |

### Worked twin problem

The problem below is a bike-share task with the same skills as the lab: totals over a list of dictionaries, a decision that depends on several conditions, and a boolean with a strict boundary. It is a different domain with different data, so it is not the lab.

**The scenario.** BikeHop runs a bike-share app. Its back office checks trips, fares and accounts with three functions.

- `trip_totals(trips)`: `trips` is a list of dictionaries with the keys `km` and `minutes`, both whole numbers. Return a tuple of three whole numbers: the number of trips, the total of `km`, and the total of `minutes`. An empty list gives `(0, 0, 0)`.
- `fare_state(fares)`: `fares` is a list of dictionaries with the key `status`, which is `'paid'`, `'waived'` or `'due'`. Return `'overdue'` if any fare is `'due'`. Otherwise return `'clear'`. An empty list gives `'clear'`.
- `can_rent(account)`: `account` is a dictionary with the keys `suspended` (`True` or `False`), `active_rentals` and `limit`, both whole numbers. Return `True` only when the account is not suspended and `active_rentals` is less than `limit`. Otherwise return `False`.

**The solution and its tests.** Read the code and the asserts. The solution is shown in full here because this is a worked example. You will write your own solution to the second twin problem below.

```python test
def trip_totals(trips):
    count = len(trips)
    total_km = sum(t["km"] for t in trips)
    total_minutes = sum(t["minutes"] for t in trips)
    return (count, total_km, total_minutes)

def fare_state(fares):
    for f in fares:
        if f["status"] == "due":
            return "overdue"
    return "clear"

def can_rent(account):
    if account["suspended"]:
        return False
    return account["active_rentals"] < account["limit"]

assert trip_totals([]) == (0, 0, 0)
assert trip_totals([{"km": 4, "minutes": 15}]) == (1, 4, 15)
assert trip_totals([{"km": 4, "minutes": 15}, {"km": 0, "minutes": 3}]) == (2, 4, 18)
assert fare_state([]) == "clear"
assert fare_state([{"status": "paid"}, {"status": "waived"}]) == "clear"
assert fare_state([{"status": "paid"}, {"status": "due"}]) == "overdue"
assert can_rent({"suspended": False, "active_rentals": 1, "limit": 2}) is True
assert can_rent({"suspended": False, "active_rentals": 2, "limit": 2}) is False
assert can_rent({"suspended": True, "active_rentals": 0, "limit": 2}) is False
assert can_rent({"suspended": False, "active_rentals": 0, "limit": 0}) is False
```

**Explanation, line by line.**

- `count = len(trips)` counts the dictionaries. An empty list gives `0`.
- `total_km = sum(t["km"] for t in trips)` adds the `km` field of each trip. For an empty list, `sum` returns `0`.
- `total_minutes = sum(t["minutes"] for t in trips)` does the same for the `minutes` field.
- `return (count, total_km, total_minutes)` returns the three numbers in the order the statement gives. All three are whole numbers, so no rounding is needed.
- `def fare_state(fares):` starts the second function. The loop checks each fare in turn.
- `if f["status"] == "due":` compares the text exactly. A fare with status `'Due'` would not match, which is why the rule uses the exact lower-case word.
- `return "overdue"` leaves the function at once, so the first overdue fare decides the answer. The loop does not need to look at the rest.
- `return "clear"` is reached only when the loop finished without a return. This covers the empty list and the case with only paid or waived fares.
- `if account["suspended"]:` returns `False` straight away for a suspended account. The later checks are not needed, so the order matters.
- `return account["active_rentals"] < account["limit"]` returns the result of a comparison, which is a real bool. The strict `<` means that an account with exactly `limit` rentals cannot rent another bike.

The asserts show the expected output. When the file runs, nothing is printed, and each assert passes silently. If one fails, Python stops and names the line.
