### Two-sum with a hash set

**What it is.** The two-sum problem asks whether any two numbers in a list add up to a target. The slow way compares every pair with two nested loops, which costs O(n squared). A set gives a faster way. For each number x, check whether target minus x is already in the set. Then add x to the set. A set lookup takes O(1) on average, so one pass costs O(n).

```python
seen = set()
target = 10
for x in [3, 7, 4]:
    if target - x in seen:
        print("pair found:", target - x, x)
    seen.add(x)
```

Running this prints `pair found: 3 7`. When x is 7, the number 3 is already in the set, and 3 plus 7 makes 10. The number 4 finds nothing, because 6 has not appeared. The set does not keep the positions of the numbers, so it can tell you that a pair exists, but not where the pair sits in the list. If the question asks for positions, store a dictionary from value to index instead.

**How it shows up in a case study.** A calibration team has 50,000 readings from a sensor array. A fault code is raised when two different readings add up to a fixed correction value. A junior engineer writes a loop that compares each new reading with every earlier reading. On a laptop the first thousand rows finish quickly, but the full file takes many minutes. The team asks why the time grows so fast. The answer is the nested comparison: every new row causes a scan of all earlier rows. Replacing the scan with a set lookup makes each row a single check, so the work grows with n rather than n squared. The correct decision is to change the data structure, not to buy a faster machine.

:::trap Pairing an element with itself
If you add x to the set before checking, then a target of twice x finds x itself. Check first, then add.
:::

### Sliding windows with a running sum

**What it is.** A sliding window is a run of neighbouring items of fixed size k. A running sum keeps the total of the window. Each step adds the item that enters on the right and subtracts the item that leaves on the left. Every item is added once and removed once, so the whole pass is O(n). Recomputing the sum from scratch at each position costs O(n times k) instead.

```python
data = [2, 5, 1, 6]
k = 2
window = sum(data[:k])
sums = [window]
for i in range(k, len(data)):
    window += data[i] - data[i - k]
    sums.append(window)
print(sums)
```

The first window is 2 plus 5, which is 7. At i equal to 2, the code adds 1 and removes 2, so the total becomes 6. At i equal to 3, it adds 6 and removes 5, so the total becomes 7. The output is `[7, 6, 7]`. The loop starts at k because that is the first index that has an item k places back to remove.

**How it shows up in a case study.** A noise monitor sends one value every minute, and the dashboard shows the 30-minute average at every minute. The team's script calls `sum` on a 30-item slice each minute. It works for an hour of data, but the nightly job over two days runs too long. The problem is not the average itself. Each minute repeats 30 additions that the previous minute already made, and the windows overlap almost completely. Keeping a running total turns the repeated work into one addition and one subtraction per minute. The right decision is to update the total, not to rebuild it.

:::trap Recomputing the window
If the loop calls `sum(values[i - k:i])` at every step, the cost stays at O(n times k). The total has to be updated, not rebuilt.
:::

### Counting with a dictionary

**What it is.** A dictionary can count items in one pass. The code `counts[key] = counts.get(key, 0) + 1` reads the current count, which is 0 if the key is new, adds one, and stores the result. The `Counter` class from the `collections` module does the same job and adds a method called `most_common`. Each update costs O(1) on average. The space needed is O(d), where d is the number of distinct keys, not the number of rows.

```python
from collections import Counter

fruits = ["fig", "apple", "fig", "kiwi", "fig"]
counts = {}
for f in fruits:
    counts[f] = counts.get(f, 0) + 1
print(counts)
print(Counter(fruits).most_common(1))
```

The first print shows `{'fig': 3, 'apple': 1, 'kiwi': 1}`. Dictionaries keep the order in which keys first appeared. The second print shows `[('fig', 3)]`, the single most frequent item. `most_common(k)` gives the k most frequent items, which is quicker than sorting the whole table when k is small.

**How it shows up in a case study.** A monitoring team wants to know which station and pollutant pairs raise the most alerts. Their first report counts alerts by station only, so the PM25 and NO2 alerts from the same station are added together, and the totals look wrong. The fix is to change the key. The question asks for totals per pair, so the key must contain both fields, as a tuple. Once the key is correct, the same single loop gives the right totals. A common mistake is to change the loop, when the real fault is in the key.

:::trap Using the wrong key
Counting by station when the question asks for station and pollutant together gives totals that look plausible and are wrong. Read the question for the exact grouping.
:::

### Matching pairs with a stack

**What it is.** A stack adds and removes items at one end only. The last item pushed is the first item popped, which is called last in, first out. Matching nested pairs such as brackets needs this order. Each opening symbol is pushed. Each closing symbol must match the item on top of the stack, and that item is popped. At the end the stack must be empty.

```python
pairs = {")": "(", "]": "["}
stack = []
for ch in "([)]":
    if ch in "([":
        stack.append(ch)
    elif not stack or stack.pop() != pairs[ch]:
        print("mismatch at", ch)
        break
else:
    print("ok" if not stack else "unclosed")
```

The loop pushes the opening bracket `(` and then `[`. When it meets `)`, the top of the stack is `[`, which does not match `(`. The program prints `mismatch at )` and stops. The `else` block of the `for` loop runs only when the loop finishes without a `break`, which is how the program reports a valid line.

**How it shows up in a case study.** A calibration tool writes a log in which blocks can sit inside other blocks. Each block opens with `(` and closes with `)`. The checker reports an error when a block closes before the blocks inside it. The team thinks the problem is a missing line in the log. The real fault is that the checker treats the blocks as a queue, so it pairs the oldest open block with the new close. Nested blocks need the most recent open block to close first, which is the stack rule. Once the checker uses a stack, the same log passes.

:::trap Forgetting the empty check
A closing symbol with an empty stack has nothing to match. Check that the stack is not empty before you pop, or the code raises an error.
:::

Quiz:

```quiz
Q: A calibration log opens and closes blocks with brackets, and blocks can nest inside other blocks. Which structure checks that the most recently opened block closes first?
- A set of the opening brackets
- A queue that adds at the back and removes at the front
- A sorted list of bracket positions
* A stack that pushes each opening bracket and pops on each closing bracket
WHY: Nesting needs last in, first out. A queue would match the oldest opening bracket, which breaks nesting. A set has no order, so it cannot say which bracket is the most recent. A sorted list does not remove items when they are matched.

```

### Variable-size windows

**What it is.** A variable-size window changes its length while the program runs. The right end moves forward to add an item. The left end moves forward to remove items while a condition is true. This works when all values are zero or positive, because adding a value can only raise the total and removing a value can only lower it. Each index moves forward at most once, so the whole pass is O(n).

```python
nums = [2, 1, 5, 2, 3, 2]
target = 7
left = 0
total = 0
best = None
for right, x in enumerate(nums):
    total += x
    while total >= target:
        size = right - left + 1
        best = size if best is None else min(best, size)
        total -= nums[left]
        left += 1
print(best)
```

The program prints `2`. The shortest run with a total of at least 7 is the pair 5 and 2, which sums to 7. The loop records the length of each run that meets the target, then removes the leftmost value so the search can look for a shorter run. The check `while total >= target` is what allows the left end to move.

**How it shows up in a case study.** A health team wants the shortest stretch of consecutive hours in which the total dose of a pollutant reaches a safety limit. Doses are never negative, because the sensors only record exposure. An analyst tries every start hour and every end hour and sums each stretch from scratch. For a month of hourly data the run takes too long. The window method fits the question: grow the stretch at the right, and shrink it at the left while the total is still at the limit. Each hour is passed once by each end, so the cost is O(n). The key fact that makes this safe is that no dose is negative.

:::trap Negative values
The shrink-while-true rule assumes that removing a value lowers the total. A negative value breaks that assumption, so read the question for this condition before you pick the window method.
:::

```quiz
WHY: Growing raises the total and shrinking lowers it, so each index moves forward once. Trying every pair costs O(n squared) or worse. Sorting ignores the consecutive order the question needs. A set of totals cannot tell you which run is shortest.

Q: A correction entry can make a dose negative. Why can the shrink-while-true rule now give wrong answers?
```

### Prefix sums for range totals

**What it is.** A prefix array stores the running total up to each position. The usual layout is P[0] equal to 0, and P[i] equal to the sum of the first i values. The total of the values from index l to index r inclusive is then P[r + 1] minus P[l]. Building the array costs O(n) once. Each range total after that costs O(1).

```python
values = [3, 1, 4, 1, 5]
P = [0]
for v in values:
    P.append(P[-1] + v)
print(P)
l, r = 1, 3
print(P[r + 1] - P[l])
```

The first print shows `[0, 3, 4, 8, 9, 14]`. The second print shows `6`. The values from index 1 to index 3 are 1, 4 and 1, which add up to 6. The formula P[4] minus P[1] gives 9 minus 3, which is also 6. The line `P.append(P[-1] + v)` uses the last item of the array, so each new total is built from the one before it.

**How it shows up in a case study.** A city dashboard answers many questions about the total pollution between two hours, such as "from hour 2 to hour 5". The analysts ask about 500 different ranges each day. The first version adds the values again for every question. It is slow because the same readings are added over and over. A prefix array does the work once. After one pass to build it, each question is a subtraction. The decision is to precompute the running totals, because the same data is queried many times.

:::trap The off-by-one index
With P[0] equal to 0, the total from index l to index r inclusive is P[r + 1] minus P[l]. Subtracting P[r] drops the last value of the range.
:::

### Next greater with a monotonic stack

**What it is.** A monotonic stack is a stack that keeps its items in a sorted order by removing the items that can no longer matter. For a question such as "what is the next higher reading?", the stack holds the indexes of readings that are still waiting for a higher value. When a new reading arrives, every waiting index whose reading is smaller is answered and popped. Then the new index is pushed. Each index is pushed once and popped at most once, so the total cost is O(n).

```python
temps = [3, 1, 4, 2]
answer = [-1] * len(temps)
stack = []
for i, t in enumerate(temps):
    while stack and temps[stack[-1]] < t:
        answer[stack.pop()] = t
    stack.append(i)
print(answer)
```

The output is `[4, 4, -1, -1]`. The reading 3 waits, then 1 waits above it. The reading 4 arrives and answers both waiting readings, so both get the answer 4. The readings 4 and 2 have no later higher value, so they keep the value -1. The answer list uses the position of each waiting reading, which is why the stack stores indexes and not values.

**How it shows up in a case study.** A monitoring team wants, for every day in a month, the next day that has a higher reading. A junior writes a nested loop that checks each later day. On a month of data, the first day may be compared with up to 29 later days, the second with up to 28, and so on, so the total grows with the square of the number of days. The stack method handles the same question in one pass. Each day waits on the stack until a higher day arrives, then it is answered and removed. The total number of pushes and pops is about twice the number of days, so the cost is O(n).

:::trap Storing values, not positions
If the stack stores readings instead of indexes, the answer cannot be written to the right position in the result list, because the stack no longer says where each reading sits.
:::

### Removing duplicates with a set

**What it is.** A set stores unique keys. Checking whether a key is already present, and adding it, each cost O(1) on average. To remove duplicates, build a key from the fields that define a duplicate, check the key against the set, and keep the row only when the key is new. The key must be hashable, which means Python can compute a stable hash for it. A tuple is hashable. A list is not.

```python
rows = [("A", 1), ("B", 1), ("A", 1), ("A", 2)]
seen = set()
kept = []
for row in rows:
    if row in seen:
        continue
    seen.add(row)
    kept.append(row)
print(kept)
```

The output is `[('A', 1), ('B', 1), ('A', 2)]`. The third row is dropped because its tuple is already in the set. The fourth row is kept, because ('A', 2) is different from ('A', 1). The list `kept` keeps the rows in the order they first appeared, while the set does the checking.

**How it shows up in a case study.** A city alarm feed sometimes sends the same event twice. The support team wants a rule that counts each real event once. The first draft uses only the alarm code as the key, so two different alarms with the same code, raised in different minutes, are removed as duplicates. The cause is a key that is too coarse. The question defines a duplicate as the same source, code and minute together, so the key must hold all three fields. A tuple of those three fields goes into the set, and the events that differ in any field are kept.

:::trap A key that is too coarse
Using only the alarm code merges events from different minutes. The key must contain every field the question names.
:::

Quiz:

```quiz
WHY: A tuple is hashable and matches the definition of a duplicate. The code alone merges events from different sources and minutes. The minute alone does the same. A list cannot be stored in a set, because it is not hashable.
```

### Window extremes with a monotonic deque

**What it is.** A deque, short for double-ended queue, adds and removes items at both ends in O(1). Python provides it as `collections.deque`. A monotonic deque stores indexes in an order chosen by their values, and removes the items that can no longer win. For a window maximum, the values decrease from front to back. The front is always the largest value in the current window. The front is removed when its index is too old to be in the window. Each index enters and leaves the deque at most once.

```python
from collections import deque

dq = deque([5, 6, 7])
dq.append(8)
dq.popleft()
print(dq)
```

The output is `deque([6, 7, 8])`. The method `append` adds 8 at the back. The method `popleft` removes 5 from the front in O(1). The method name pop with a left is the one to remember. A list's `pop(0)` also removes the front, but it shifts every other item and costs O(n).

**How it shows up in a case study.** A dashboard raises an alert when the highest PM2.5 reading in the last six hours passes a limit. The first version calls `max` on the six-hour slice at every hour. It is correct, but it repeats the same comparisons for overlapping slices and slows as the stream grows. A deque of indexes gives the answer more efficiently. The team must also store indexes rather than readings, so the code can tell when the front has left the window. Read the question for whether it asks for the maximum or the minimum, because the order inside the deque changes.

:::trap Expiry with the wrong comparison
The front expires when its index is at most i minus k. A strict less-than test keeps it one step too long, and the window becomes one item too big.
:::

Quiz:

```quiz
Q: A monotonic deque is used for a window of size 4. At step i equal to 9, the front of the deque holds index 5. Should the front be removed, and by which test?
```

### Amortised analysis

**What it is.** Amortised analysis averages the cost of operations over a whole sequence of steps. A single step can be expensive, but the total cost across all steps is what sets the bound. In a stack or a monotonic deque, one new item may pop many waiting items, so one step may cost O(n). Because each item is pushed once and popped at most once, the total number of pops over n steps is at most n. The average cost per step is therefore constant, and the whole run is O(n) amortised.

```python
stack = []
pushes = 0
pops = 0
for x in [5, 6, 1, 7]:
    while stack and stack[-1] < x:
        stack.pop()
        pops += 1
    stack.append(x)
    pushes += 1
print(pushes, pops, len(stack))
```

The program prints `4 3 1`. The value 6 pops one item, and the value 7 then pops two items (the 1 and the 6) in one step, which is the expensive step. Across all four steps, though, the pops total 3, and there were 4 pushes. The total work is bounded by a small multiple of the number of steps, which is the point of the analysis.

**How it shows up in a case study.** A monitoring tool processes a long stream of readings. One reading occasionally flushes a large batch of waiting items, and an engineer reports that the tool is quadratic because one step takes a long time. The claim is wrong. The flush removes items that were added earlier, and each item is removed once. Counting the total work across the run shows that the cost is linear. The correct wording for a report is that the whole run is O(n) amortised, while a single step may take O(n).

:::trap Confusing one expensive step with the total
"A step can take O(n)" does not mean the algorithm is O(n squared). Count the total operations across all steps.
:::

Quiz:

## The graded lab

The graded lab is one Python problem, marked by visible tests and hidden tests. The visible tests are shown to you and give part of the marks. The hidden tests check cases you do not see, and they give the rest. Most marks in a lab like this are lost on edge cases, not on the main idea. This section explains the problem in plain words, teaches the Python ideas each function needs, lists the rules people miss, and gives a method to follow. Two twin problems let you practise the same skills on different data. Neither twin is the real lab, and neither contains a solution to it.

### The task in plain words

**The scenario.** The CityPulse pipeline receives noisy sensor readings. Two steps must be written for the dashboard. The first removes repeated readings from the same station and pollutant, keeping only the latest one. The second computes a rolling peak, which is the largest value in each window of neighbouring readings.

**The data.** Each reading is a dictionary with four keys: `station_id`, `ts`, `pollutant` and `value`. The key `station_id` names the sensor site. The key `ts` is the time stamp of the reading. The key `pollutant` names the substance measured. The key `value` is the measurement.

**Function 1: `dedup_latest(readings)`, which returns a list.** It takes a list of reading dictionaries and returns a list. Its rules are:

- For each pair of `station_id` and `pollutant`, keep only one reading: the one with the largest `ts`.
- Each kept reading becomes a tuple of three items, in this order: `station_id`, `pollutant`, `value`.
- The returned list must be sorted. Each tuple is compared in order, so the list is sorted by station first, then by pollutant, then by value.
- Only the three fields above appear in the tuple. The time stamp `ts` is used to choose the reading but is not returned.
- The statement's example: two readings for station S1 and pollutant pm25, at ts 1 (value 10) and ts 3 (value 22), give the single result `[("S1", "pm25", 22)]`.

**Function 2: `rolling_max(values, k)`, which returns a list.** It takes a list of numbers and a window size `k`, and returns a list. Its rules are:

- A window is a run of `k` neighbouring values. Windows slide one place to the right at a time.
- The function returns the maximum of each window, from left to right, so the first result is for the first window.
- The method must use a monotonic deque, and the whole function must run in O(n) time. This is a requirement of the statement, not only a suggestion.
- The statement's example uses the list 5, 3, 8, 2, 7, 1 with a window of 3, and the expected result is 8, 8, 8, 7.

**Limits.** The program may run for at most 30 seconds, and it may use at most 128 megabytes of memory.

**The starter file.** The file imports `deque` from `collections`, and it defines the two functions with empty bodies. Keep the imports and the function names exactly as given. The tests call the names, so a renamed function fails every test.

**Scoring.** The visible tests are worth 60 points in total, shared across four tests:

| Test | Points |
|---|---|
| Keep the latest reading per station and pollutant | 18 |
| Window maxima for k equal to 3 | 18 |
| k equal to 1 returns the values unchanged | 12 |
| A single reading passes through | 12 |

The hidden tests are three tests worth 40 points in total. You are not shown what they check. Hidden tests exist so that a program cannot pass by fitting only the visible examples. They usually check the cases the statement mentions but the examples do not show, such as ties, empty input, a window the same size as the list, and large inputs that would be too slow if the method were wrong. Because the hidden tests are worth more than the visible ones, a solution that passes every visible test but fails a hidden one loses marks that matter. Treat every rule in the statement as something a hidden test may check.

### What each function needs

Each function uses a few Python ideas. Each idea is taught below with a small example that has nothing to do with the lab's data. Try each example in a Python shell before you use the idea in the lab.

**Overwriting a dictionary value.** Assigning to a key that already exists replaces its value and keeps the key where it was:

```python
prices = {}
prices["apple"] = 3
prices["apple"] = 5
prices["pear"] = 2
print(prices)
```

The output is `{'apple': 5, 'pear': 2}`. The apple key appears once, and its value is the last one assigned. A dictionary keeps keys in the order they were first added. This is useful when you want one record per key, and the newer record replaces the older one only when a rule says so.

**Comparing tuples.** Python compares two tuples item by item, from left to right. The first items decide the order unless they are equal, and only then are the second items compared:

```python
print(("apple", 1) < ("apple", 9))
print(("apple", 9) < ("pear", 2))
print(sorted([("pear", 2), ("apple", 9), ("apple", 1)]))
```

The output is `True`, then `True`, then `[('apple', 1), ('apple', 9), ('pear', 2)]`. The first comparison is decided by the second item, because the first items are equal. The second comparison is decided by the first item alone. The `sorted` function returns a new list in this order and leaves the original list unchanged.

**Sorting with a key.** The `sorted` function accepts a `key` argument that tells it what to compare. This does not change the items, only the order:

```python
words = ["banana", "fig", "cherry"]
print(sorted(words, key=len))
print(sorted(words))
```

The output is `['fig', 'banana', 'cherry']`, then `['banana', 'cherry', 'fig']`. Sorting by length puts fig first because it is shortest. Sorting without a key compares the words alphabetically. Use a key only when the order you need is not the default one.

**Turning a dictionary into a list.** The method `values()` gives the values of a dictionary, in insertion order, and `list()` turns that view into a list:

```python
scores = {"a": 10, "b": 4}
scores["c"] = 7
print(list(scores.values()))
```

The output is `[10, 4, 7]`. The list follows the order in which the keys were first added. If you want a different order, you must sort the list yourself.

**Using a deque as a queue.** A deque adds and removes items at both ends in O(1). The methods `append` and `popleft` work at the two ends, and `pop` removes from the right end:

```python
from collections import deque

queue = deque(["a", "b"])
queue.append("c")
first = queue.popleft()
print(first, queue)
print(queue[0], queue[-1])
```

The output is `a deque(['b', 'c'])`, then `b c`. The method `popleft` removes the leftmost item, and `queue[0]` reads the front without removing it. The index `queue[-1]` reads the back. A deque can also hold numbers, such as the index positions your method may need to store.

**Enumerating with positions.** The function `enumerate` gives a position and an item for each step of a loop. Its positions start at 0 unless you change them:

```python
letters = "xyz"
for pos, ch in enumerate(letters):
    print(pos, ch)
```

The output is `0 x`, `1 y`, `2 z`, one line each. The loop variables are assigned in pairs, so the position and the item are available together. This is the usual way to know where you are in a list while you read its items.

**Counting windows.** A list of n items has n minus k plus 1 windows of size k, as long as k is at least 1 and no larger than n. Slicing takes a run of items from a list, with the start included and the end excluded:

```python
items = [4, 9, 2, 7, 5]
print(items[1:4])
print(len(items) - 3 + 1)
```

The output is `[9, 2, 7]`, then `3`. The slice `items[1:4]` has three items, positions 1, 2 and 3. A list of five items has three windows of size three. Use this counting rule to check the length of your output, because a wrong length fails a test even when the values are right.

**Checking for an empty collection.** An empty list is false in a condition, and a non-empty list is true. This lets a loop or a test stop early without a separate length check:

```python
for item in []:
    print("never printed")
print("empty loops do nothing")
```

The output is only `empty loops do nothing`. A loop over an empty list does not run at all. Code that reads an item by position, such as `items[0]`, does fail on an empty list, so check for emptiness before you read the first item.

### A method that works for every graded lab

2. **Write the examples from the statement as `assert` lines first.** Copy each example from the statement into an `assert` line, with the expected output. Do not run them yet. This turns the statement into checks before you write any logic.
3. **Add your own `assert` lines for every row of the rules table.** For each row, write one assert that would fail if the careless solution were used. For example, for the tie rule, write an input with two readings of the same time, and assert the result you decided on.
4. **Implement one function at a time.** Start with `dedup_latest`, because its tests are simpler. Run the asserts for that function after each change. Do not start the second function until the first one passes every assert you wrote for it.
5. **Implement the second function.** Use the deque, and store indexes rather than values. Test it with k equal to 1, with a window the same size as the list, and with a window larger than the list.

### Worked twin problem

This twin uses a different domain. The data are stock ticks, not sensor readings. The skills are the same: keeping one record per key by a rule, and computing a rolling minimum with a monotonic deque. The twin is not the lab. Its rules differ on purpose, so solve it by understanding the rules, not by renaming the code from the lab.

**The statement.** A tick is a tuple `(ticker, time, price)`. A ticker is a short name for a stock. Write two functions.

1. `last_price_per_ticker(ticks)` returns a dictionary. Each key is a ticker, and each value is the price of that ticker's latest tick, meaning the tick with the largest time. If two ticks for the same ticker have the same time, the one that comes later in the input wins.
2. `rolling_min(prices, k)` returns a list with the minimum of each full window of k consecutive prices, from left to right. A window must have exactly k prices. Use a monotonic deque. If k is less than 1, raise a `ValueError`.

The example is `ticks = [("ACME", 1, 10.0), ("BOLT", 1, 5.0), ("ACME", 3, 11.0), ("BOLT", 2, 6.0), ("ACME", 2, 99.0)]`. The result of `last_price_per_ticker(ticks)` is `{"ACME": 11.0, "BOLT": 6.0}`. The result of `rolling_min([5, 3, 8, 1, 4, 2], 3)` is `[3, 1, 1, 1]`.

```python test
from collections import deque


def last_price_per_ticker(ticks):
    latest = {}
    for ticker, time, price in ticks:
        if ticker not in latest or time >= latest[ticker][0]:
            latest[ticker] = (time, price)
    return {ticker: price for ticker, (time, price) in latest.items()}


def rolling_min(prices, k):
    if k < 1:
        raise ValueError("k must be at least 1")
    dq = deque()
    out = []
    for i, price in enumerate(prices):
        while dq and prices[dq[-1]] >= price:
            dq.pop()
        dq.append(i)
        if dq[0] <= i - k:
            dq.popleft()
        if i >= k - 1:
            out.append(prices[dq[0]])
    return out


ticks = [("ACME", 1, 10.0), ("BOLT", 1, 5.0), ("ACME", 3, 11.0),
         ("BOLT", 2, 6.0), ("ACME", 2, 99.0)]
assert last_price_per_ticker(ticks) == {"ACME": 11.0, "BOLT": 6.0}
assert last_price_per_ticker([]) == {}
assert last_price_per_ticker([("X", 4, 1.0), ("X", 4, 2.0)]) == {"X": 2.0}
assert last_price_per_ticker([("X", 4, 1.0), ("X", 4, 2.0), ("X", 3, 9.0)]) == {"X": 2.0}

assert rolling_min([5, 3, 8, 1, 4, 2], 3) == [3, 1, 1, 1]
assert rolling_min([7, 7, 7], 1) == [7, 7, 7]
assert rolling_min([3, 1, 2], 3) == [1]
assert rolling_min([1, 2], 5) == []
assert rolling_min([], 3) == []
try:
    rolling_min([1, 2], 0)
except ValueError:
    pass
else:
    raise AssertionError("k=0 should raise ValueError")
```

**Explanation of `last_price_per_ticker`, line by line.**

- `latest = {}` creates an empty dictionary. Its keys are tickers, and each value is a pair of the time and the price of the best tick so far.
- `for ticker, time, price in ticks:` unpacks each tick into three names.
- `if ticker not in latest or time >= latest[ticker][0]:` is true for a ticker not seen before, or when the new tick's time is at least as late as the stored one. The `>=` makes the later row win a tie. The index `[0]` reads the stored time.
- `latest[ticker] = (time, price)` stores the new pair. For a ticker that already exists, this replaces the value and keeps the key where it was.
- The `return` line builds the final dictionary. The loop `for ticker, (time, price) in latest.items()` unpacks each key and each stored pair, and keeps only the price. Expect `{"ACME": 11.0, "BOLT": 6.0}` for the example.

**Explanation of `rolling_min`, line by line.**

- `if k < 1: raise ValueError(...)` stops the function for an invalid window, with a message that explains why.
- `dq = deque()` creates the deque of indexes. The prices at those indexes increase from front to back, so the front holds the minimum.
- `while dq and prices[dq[-1]] >= price:` removes the back indexes whose prices are no smaller than the new price. They can never be the minimum again, because the new price is no larger and stays in any window at least as long.
- `dq.append(i)` adds the new index at the back.
- `if dq[0] <= i - k: dq.popleft()` removes the front when its index has left the window. An index at or below `i - k` is outside a window of size k.
- `if i >= k - 1:` records a result only when the window is full. This is the rule that skips the partial windows at the start.
- `out.append(prices[dq[0]])` adds the minimum of the current window.
