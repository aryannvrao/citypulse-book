## What the quiz tests

The real Day Quiz has ten case-study multiple-choice questions, one for each topic below, in the same order. The pass mark is 70 per cent, which means seven correct answers out of ten. Your skill score keeps only your first attempt, so use the practice questions here to find your gaps before the real quiz.

Each topic has an explanation, a worked scenario, a trap and three practice questions. Read the WHY line of every question, even the ones you answered correctly, because it explains why the most tempting wrong option fails.

**How to answer a case-study question.** Use four habits.

1. Read the last line first. It says what you must find: the best fix, the first step, or the result that will happen. Knowing this tells you which facts to look for in the scenario.
2. Underline the facts that matter. These are the field name, the value that was sent, the constraint the team has and the symptom they report. Case studies include details that do not change the answer, so ignore them.
3. Eliminate options that are true in general but do not fix this scenario. Many wrong options are correct statements about a library. They answer a different question from the one asked.
4. Watch for three words. "Most" means one option is the strongest, not merely true. "First" means the order of steps matters. "Best" means one option fits the team's constraint better than the others, even when two would work.

### Type coercion in Pydantic

**What it is.** Pydantic checks each value against the type you declared. Before it checks, it tries to convert the value, provided the conversion does not change its meaning. This conversion is called coercion. In its default mode, the text `"12"` becomes the integer 12 for an `int` field, and the text `"42.5"` becomes the float 42.5 for a `float` field. A conversion that would lose information is refused. The text `"4.5"` is refused for an `int` field, because the `.5` would be lost, and `"abc"` is refused for any number.

```python
from pydantic import BaseModel

class Pet(BaseModel):
    age: int
    weight: float

print(Pet(age="12", weight="42.5"))
```

The output is `Pet(age=12, weight=42.5)`. The text has become real numbers. If you change `age="12"` to `age="4.5"`, the same line raises a `ValidationError` that names the field `age`. A `float` field also accepts `nan` and infinity unless you forbid them with `Field(allow_inf_nan=False)`. Coercion only changes the value. The field's other rules still apply to the converted value afterwards.

**How it shows up in a case study.** A canteen runs a feedback tablet. Every value arrives as text, and the model declares `rating: int = Field(ge=1, le=5)`. The payload sends `"rating": "4"`. A junior engineer asks whether the database will store the text `"4"` or the number 4, and whether the field should become a `str`. Pydantic converts `"4"` to the integer 4 in its default mode, then checks the range. The field stays an `int`, so the dashboard can average it. The team should not switch to `str`, because that removes the type check. If the tablet ever sends `"4.5"`, the model refuses it, which is the behaviour the team wants.

:::trap Coercion is not validation
Coercion changes the value only. A value can convert correctly and still fail a rule. The text `"7"` becomes 7, and then `le=5` refuses it. The tempting wrong idea is that a value which converts is therefore allowed.
:::

```quiz

WHY: In its default lax mode Pydantic converts numeric text to the declared type when the conversion is exact. Rejection is the tempting wrong answer, but it happens only in strict mode.

Q: A feedback form sends "rating": "4.5" for a field declared rating: int. What is the result?
```

### Limiting a field to fixed values

**What it is.** Two tools restrict a field to a fixed set of values. A `Literal` lists the allowed values as text, such as `Literal["bronze", "silver", "gold"]`. An `Enum` is a class whose members are the allowed values, and your code can refer to them by name, such as `Tier.GOLD`. Both compare values exactly. A `Literal` does not change letter case, so a `Literal` that lists `"gold"` refuses `"GOLD"`. The error message lists the allowed values, which tells the sender what to send.

```python
from typing import Literal
from pydantic import BaseModel

class Membership(BaseModel):
    tier: Literal["bronze", "silver", "gold"]

print(Membership(tier="gold").tier)
Membership(tier="GOLD")
```

The first line prints `gold`. The second line raises a `ValidationError`, whose message reads `Input should be 'bronze', 'silver' or 'gold'`. If a business rule says that `"GOLD"` must be accepted, you must normalise the text yourself. Put a validator in `mode="before"` that lower-cases the text. A before validator runs before the set check, so the `Literal` then sees the cleaned text.

**How it shows up in a case study.** A loyalty app has an old version that sends the plan name as `"Premium"`, with a capital P. The new model says `plan: Literal["basic", "premium"]`, and the old app's requests fail with a literal error. The team asks whether the model is broken. It is not. The `Literal` compares exact text, so the decision depends on the rule the team agrees. If the team wants every capitalisation accepted, the right fix is a before validator that lower-cases the text, with the `Literal` kept strict. The wrong fix is to change the field to a plain `str`, which removes the check entirely.

:::trap Literal ignores case
A `Literal` does not ignore case. Listing `"gold"` does not accept `"GOLD"`. You must normalise the text in a before validator if you want that behaviour.
:::

```quiz
Q: A model has status: Literal["open", "closed"]. The team wants "Open", "OPEN" and "open" all accepted, and the Literal kept strict. Which change does this?
- Add ignore_case=True to the Literal
- Add "Open" and "OPEN" to the list of allowed values
* Add a before validator that lower-cases the text, and keep the Literal
- Change the field type to str
WHY: A before validator runs first and turns every capitalisation into one form, so the strict Literal can then check the result. The tempting wrong answer is ignore_case, which Literal does not offer. Changing the type to str removes the check entirely.

Q: An Enum class Tier has the members BRONZE = "bronze" and GOLD = "gold". A payload sends "gold". What happens?

* It is accepted and becomes Tier.GOLD
- It is accepted and stored as the text "gold" without conversion
- It is refused, because Enum fields cannot be sent as JSON
WHY: Pydantic matches an Enum field by the value of its members, here "gold", and returns the member itself. The tempting wrong answer is that the member name must be typed in upper case, but the name is not what Pydantic compares.

Q: A field allows only "ok" and "failed". Each new client sends a different capitalisation, such as "FAILED" or "Ok". Which design is best?

WHY: A before validator fixes the capitalisation for every client in one place, and the Literal keeps the set strict. Adding variants one at a time never ends, and removing the check lets unknown values into storage.
```

### Checks across two fields with a model validator

**What it is.** A `field_validator` looks at one field. A `model_validator` runs after the whole object has been built, so it can compare two fields. Use `@model_validator(mode="after")`. The method receives the built object as `self`, and it must return `self`. A rule such as "the end must be later than the start" belongs in a model validator.

```python
from datetime import datetime
from pydantic import BaseModel, model_validator

class Booking(BaseModel):
    start: datetime
    end: datetime

    @model_validator(mode="after")
    def end_after_start(self):
        if self.end <= self.start:
            raise ValueError("end must be later than start")
        return self

Booking(start="2026-01-05T09:00", end="2026-01-05T08:00")
```

The last line raises a `ValidationError`. Its message contains `Value error, end must be later than start`. The `raise` inside the method is turned into a validation error. The `return self` line hands the checked object back to Pydantic. If the method finishes without that line, the method returns `None`, so the validated model becomes `None` or Pydantic raises an error, depending on the version. Either way the result is wrong.

**How it shows up in a case study.** A maintenance log stores `opened_on` and `closed_on` for each job. The rule is that a job cannot close before it opens. A teammate writes the check in a field validator on `closed_on`. That validator is built around one field and can reach other fields only through awkward extra access, so the comparison is fragile and in the wrong place, and the team finds that rules for other dates are missing. The right decision is to move the comparison into a model validator in `mode="after"`. The validator then sees both values, returns the object, and the error names the job record. The wrong decision is to add a `Field` constraint to `closed_on`, because a constraint on one field cannot compare it with another.

:::trap Two-field rules on one field
A rule that compares two fields placed on one field's validator is either missing data or fragile. Put it on the model. Forgetting `return self` in an after validator is a second common mistake.
:::

```quiz
Q: A Trip model has depart and arrive datetimes. The rule is that arrive must be later than depart. Which tool checks this rule?
* A model validator in mode "after" that compares the two fields
- A field validator attached to arrive only
- A Field(ge=0) constraint on arrive
- A Literal type on arrive
WHY: Only a model validator sees both fields once the object is built. A field validator is written for one field, and a Field constraint cannot compare two fields. The tempting wrong answer is a field validator on arrive, which cannot compare the two values cleanly.

Q: A model validator in mode "after" checks that low is not greater than high, but the method ends without a return statement. What goes wrong?
- Pydantic ignores the check, because the validator must be in mode "before"
- Pydantic reports the same error twice
* The validator returns None instead of the model, so Pydantic has no object to hand back
- Pydantic needs a Config subclass before it will run the check
WHY: An after validator must return self. The tempting wrong answer is switching to mode "before", but a before validator runs on the raw input, before the object exists, so it does not solve the missing return.

Q: A Booking has start and end. Which placement is best for the rule that a booking may last no more than 8 hours?

- A Field(le=8) constraint on end
* A model validator in mode "after" that subtracts start from end
- A Literal type on the duration
WHY: The duration needs two fields and a subtraction, so only a model validator in after mode can compute it. A Field(le=8) on end compares a timestamp with a plain number, which is not the rule the team wants.
```

### Sharing setup with fixtures

**What it is.** A fixture is a function marked with `@pytest.fixture`. It returns the setup that a test needs. A test asks for the fixture by naming a parameter with the same name, and pytest runs the fixture and passes its result in. The scope decides how often the fixture runs. The default scope is `function`, which runs the fixture again for each test. The scope `session` runs it once for the whole test run.

```python
import pytest

@pytest.fixture
def basket():
    return {"items": ["apple"], "total": 2.5}

def test_basket_has_one_item(basket):
    assert len(basket["items"]) == 1

def test_add_item(basket):
    basket["items"].append("pear")
    assert len(basket["items"]) == 2
```

pytest reports both tests as passed. Each test receives a new dictionary, because the scope is `function`. The first test can change its copy without affecting the second test. If the scope were `session`, the append in the second test would change the same dictionary that a later test reads, and the order of the tests would start to matter.

**How it shows up in a case study.** A test suite has two costs. Starting the web application with its startup code takes ten seconds, and the application is read-only once started. Each test also needs a payload dictionary that some tests edit. A teammate sets the application fixture to `function` scope, so the start-up runs for every test, and the suite becomes slow. Another teammate keeps the payload at `session` scope, and tests begin to fail only when they run together. The right decision is `session` scope for the read-only application, and `function` scope for the mutable payload, so that each test gets a fresh copy of the data.

:::trap Wide scope on mutable data
A session-scoped dictionary is shared by every test in the run. One test that changes it changes the input for the next test, so the failure moves to a different test each time the order changes.
:::

```quiz
Q: A fixture payload returns a dictionary. Two tests each add a key to it. Which scope is the safest choice for payload?
- session, so that the dictionary is built only once
- module, so that every test in one file shares it
- class, so that the tests in one class share it
* function, so that each test receives a new dictionary
WHY: Function scope is the default and gives each test a fresh copy. The tempting wrong answer is session, which saves set-up time but lets one test's edits reach the next test.

Q: A fixture client starts a web application that takes ten seconds to start, and the application's data is read-only. Which scope suits it?
* session, so that the application is built once for the whole run
- function, so that each test starts from a clean state
- class, so that each test class gets its own copy
- module, so that the fixture is rebuilt for each file in the run
WHY: Read-only and expensive set-up is the case for session scope. The tempting wrong answer is function scope, which would repeat the ten-second start for every single test.

Q: A test asks for a fixture called order, but no fixture with that name exists in the test file or in conftest.py. What happens?
- The test runs with order set to None
- The test is skipped with a warning and is not counted
* pytest reports an error that the fixture 'order' was not found
- The test is rewritten so that pytest creates order from the test's name
WHY: pytest matches parameter names to fixtures, and it reports an error when a name has no matching fixture. The tempting wrong answer is that the parameter silently becomes None.
```

### Checking that an error is raised

**What it is.** `with pytest.raises(ValueError):` is a block. The test passes when the code inside the block raises the named exception, and fails when nothing is raised. Adding `match="text"` also checks that the error message contains the text, using a pattern search. Adding `as info` stores the exception, so that you can read `info.value`.

```python
import pytest

def copies_from(text):
    count = int(text)
    if count < 1:
        raise ValueError("copies must be at least 1")
    return count

def test_zero_copies_is_refused():
    with pytest.raises(ValueError, match="at least 1"):
        copies_from("0")
```

`int("0")` gives 0, the check fails, and `ValueError` is raised with the message `copies must be at least 1`. The test passes. If `copies_from` returned 0 instead of raising, pytest would report `DID NOT RAISE`, and the test would fail. The `match` text is searched inside the message, so `"at least 1"` is enough.

**How it shows up in a case study.** A library team has a function that refuses zero copies of a book. One teammate writes `copies_from("0")` on a line above the `with` block, so the exception is raised outside the block and fails the test with an error. Another teammate writes `pytest.raises(Exception)`, and the test passes when a typing mistake inside the function raises a `TypeError`. The right decision is to put the call inside the block, and to name `ValueError`, which is the exact promise the rule makes. Adding `match` then proves that the message is the one the team intended.

:::trap Catching Exception
`pytest.raises(Exception)` passes for almost any error, including a bug such as a `TypeError` from a typo. Name the exact class that the rule promises.
:::

```quiz
Q: A test should show that copies_from refuses "0". The developer writes result = copies_from("0") on a line above a with pytest.raises(ValueError): block whose body is just pass. What is wrong?
- Nothing, because the test checks the error after the call
* The call is outside the with block, so its exception ends the test before the block is ever reached
- The test should name Exception instead of ValueError
- The test must return the result to pytest before it can check it
WHY: The call that should raise must sit inside the with block. Otherwise the exception is raised outside pytest.raises, so it ends the test with an error and the block never catches it. The tempting wrong answer is that checking after the call is fine.

Q: A test uses with pytest.raises(Exception): around a call that should refuse a bad value. A typo inside the function raises a TypeError, and the test still passes. What is the problem?
- Nothing, because Exception is the base of all errors
- The test should use assert True instead of a with block
- The test needs a fixture to catch the typo
* The class is too broad, so the test hides a different bug
WHY: pytest.raises passes for the named class and for any subclass of it. Exception covers TypeError as well, so the test cannot tell the intended refusal from a bug. Name ValueError.

Q: A test must check that a Pydantic model refuses a bad input, and that the error is about the value field. Which code does this?
* with pytest.raises(ValidationError) as info:, around the model call, followed by an assert on info.value.errors()
- try: Model(...) followed by except: pass
- assert Model(...) raises ValidationError
- with pytest.raises(Exception): Model(...) with nothing else in the test
WHY: The as info part stores the exception, and errors() returns a list of dictionaries with the keys loc, msg and type. A bare except passes even when no error is raised, and a plain Exception check says nothing about the field.
```

### Running one test on many inputs

**What it is.** `@pytest.mark.parametrize("name", [values])` runs one test function once for each value. Each run is reported on its own line, so a failing run names its input. With several names, write them as one comma-separated string, and give each row as a tuple in the same order.

```python
import pytest

@pytest.mark.parametrize("text, expected", [("1", 1), ("  7 ", 7), ("0", 0)])
def test_text_becomes_int(text, expected):
    assert int(text) == expected
```

pytest runs the test three times, once per row. The first run uses `text="1"` and `expected=1`. The second run uses the text with spaces around it, and `int` accepts those spaces. The report shows `3 passed`. If the second row had a wrong expected value, the report would name that row, and the other two rows would still be reported as passed.

**How it shows up in a case study.** A courier team must check that a shipping function refuses a weight of 0, a negative weight, the text `"abc"` and `None`. One engineer writes a `for` loop inside a single test. The first failing value stops the test, so the team cannot see which other values also fail. The right decision is to parametrize the four values, so that each one is reported on its own line. The team should also add the boundary value and an awkward case such as an empty string, because those are where the bugs usually are.

:::trap A loop hides later failures
A `for` loop inside one test stops at the first failure. Each value needs its own run, which parametrize gives you.
:::

```quiz
Q: A test must refuse four bad codes: an empty string, a code in lower case, a code with a space in it, and a code of the wrong length. Which structure is cleanest?
- Four copies of the same test, each with one value
- One test with a for loop over the four values
* One test marked with parametrize that lists the four values
- One test that reads the four values from a file on each run
WHY: parametrize gives each value its own report line without copying code. Four copies are harder to maintain, a loop hides later failures, and a file adds a dependency that the test does not need.

Q: A parametrize decorator lists the rows (0, False), (5, True) and (-1, False) for a function allowed(n) with the names n and expected. How many tests does pytest run, and what does the second element of a row mean?
- One test, and the second element is ignored
* Three tests, and the second element is passed in as expected
- Two tests, because the first row is a header
- Three tests, and the second element is the type the function returns
WHY: Each row becomes one run, and the values are matched to the names in order. Rows are not headers, and the second element is a value to compare with, not a type.

Q: A test is parametrized with the values 1 to 5, and the run for value 3 fails. Which report helps most?
- A single line that says the test failed somewhere
- A line that gives the number of failed loops
- A report that shows only the first failing value
* A separate report line for the run with value 3, which names its input, while the other runs still show their results
WHY: Each row is reported separately, so the failure names its input and the other results remain visible. The tempting wrong answer is a report that shows only the first failure, which is what a loop gives you.
```

### Replacing a dependency with a mock

**What it is.** A mock is a stand-in object that records how it was called and returns a value that you choose. `unittest.mock.patch` replaces a name for the length of a `with` block, and the original is restored afterwards. The `pytest-mock` plugin offers the same idea as a `mocker` fixture, and its `mocker.patch` is undone automatically at the end of the test. Use a mock for things a test should not really do, such as a network call or a clock. Patch the name where the code uses it, not where the name is defined.

```python
# weather.py
def fetch_temperature(city):
    ...  # a real network call would go here

def describe(city):
    temp = fetch_temperature(city)
    return f"{city}: {temp} C"
```

```python
# test_weather.py
from unittest import mock
import weather

def test_describe_uses_fake_temperature():
    with mock.patch("weather.fetch_temperature", return_value=24) as fake:
        assert weather.describe("Pune") == "Pune: 24 C"
    fake.assert_called_once_with("Pune")
```

The test passes without any network call. The patch replaces `weather.fetch_temperature` with a stand-in that returns 24. The `describe` function calls the stand-in, builds the sentence, and the test checks it. The last line checks that the stand-in was called exactly once, with the city name `"Pune"`.

**How it shows up in a case study.** A report generator calls a weather function, and its tests fail whenever the network is down. The team wants the tests to run offline, and to check that the city name is passed on correctly. A teammate proposes mocking `describe` itself, which is the function under test. The right decision is to mock only the outside call, `fetch_temperature`, in the module where the report code uses it, and to assert on the result of the real `describe`. This keeps the code under test real, and the network out of the test.

:::trap Mocking the code under test
If you mock the function you are testing, the test checks the stand-in and proves nothing about your code. Mock only the outside dependency.
:::

```quiz
Q: A test must run offline. The function describe calls fetch_temperature, which makes a network call. What does a mock do here?
* It replaces the network call with a stand-in that records calls and returns a value the test chooses
- It starts a second copy of the weather service for the length of the test
- It removes describe from the program for the length of the test
- It turns off pytest's assert checks
WHY: A mock is a stand-in for one dependency during one test. Starting a real service is the tempting wrong answer, because it makes the test slow and dependent on the network.

Q: A test patches weather.fetch_temperature, but report.py contains from weather import fetch_temperature at the top. The patch seems to have no effect. Why?
- Mocks cannot replace functions, only classes
- The patch is correct, and the test is wrong to expect a change
* The patch must target report.fetch_temperature, because that is where the code looks the name up
- The test needs the pytest-cov plugin before a patch can be seen
WHY: A from-import copies the name into report.py. Patching the original module does not change report's copy, so you patch the name where it is used. The tempting wrong answer is that the patch itself is at fault.

Q: A test mocks describe itself, and then asserts that the mock returns the value it was given. What is the flaw?
- The test is correct, because mocks should always replace the function under test
- The test needs a session fixture before it can run
* The test checks the stand-in, not the code, so it proves nothing about describe
- The test should call assert_called_with on the network instead
WHY: A test must exercise the real code and mock only the outside dependency. A mock of the function under test only confirms that the stand-in returns what it was told to return.
```

### Nested models and error paths

**What it is.** A field can have another model as its type. Pydantic validates the inner dictionary as well, and each error has a `loc` value. The `loc` is a tuple that gives the path from the top level to the bad field. A list of models adds a position number to the path, counting from 0.

```python
from pydantic import BaseModel, ValidationError

class Address(BaseModel):
    city: str
    postcode: str

class Customer(BaseModel):
    name: str
    address: Address

try:
    Customer(name="Meera", address={"city": "Pune"})
except ValidationError as e:
    print(e.errors()[0]["loc"])
```

The output is `('address', 'postcode')`. The path starts at the top-level field `address`, goes into the nested model, and ends at the missing field `postcode`. If `Customer` had a field `orders: list[Address]`, a bad item in the third position would have a `loc` that includes the index `2`, so the path would look like `('orders', 2, 'postcode')`.

**How it shows up in a case study.** A retail team receives customer records with nested addresses, and the error log shows a `loc` of `("address", "postcode")`. A developer reads only the last part of the path, and looks for a top-level field called `postcode` in the customer model. The field does not exist there, so the developer changes the wrong code. The right decision is to read the whole path from left to right, go into `address`, and then fix the nested field in the sender's payload. For a list, the number in the path tells you which item to look at.

:::trap Reading only the last part of loc
The last element names the field, but the earlier elements tell you where that field lives. An error at ("address", "postcode") is inside address, not at the top level.
:::

```quiz
Q: A Customer contains address: Address. The payload leaves out postcode inside address. Which loc does the error report?
- ("postcode",)
- ("customer", "postcode")
- ("address",) alone
* ("address", "postcode")
WHY: The loc tuple records the whole path from the top level to the missing field. The tempting wrong answer is ("postcode",), which reads only the last part of the path.

Q: A Cart has items: list[Item], and the second item has a bad qty value. What does the loc look like?
* ("items", 1, "qty"), with the position of the bad item in the path
- ("items", "qty"), with no position number
- ("qty",), because lists are flattened in the error
- ("items",), because the list is the field that failed
WHY: List positions are numbers counted from 0, so the second item is at position 1. Leaving out the position loses the place of the error, and the field name alone does not identify which item was wrong.

Q: A log shows loc values such as ("location", "lat"). Which reading is correct?
- The bad field is lat at the top level of the payload
- The error belongs to the parent, and it can be ignored
* The lat field inside the nested location object is the bad one
- The location object was not sent at all
WHY: Reading the path from left to right takes you into location first and then to lat. The tempting wrong answer is to treat lat as a top-level field, which the path does not say.
```

### Constraints and serialisation

**What it is.** `model_dump()` returns a dictionary of the model's values. `model_dump_json()` returns a JSON string. `model_dump(mode="json")` returns a dictionary in which values such as dates have become text. Constraints such as `ge=1` are checked when the object is created. Dumping the object does not check them again. The options `exclude_none=True` and `exclude_unset=True` leave keys out of the output, and they do different things. The first removes fields whose value is `None`. The second removes fields that the input did not supply at all.

```python
from datetime import date
from pydantic import BaseModel, Field

class Book(BaseModel):
    title: str
    pages: int = Field(ge=1)
    published: date

b = Book(title="Dune", pages=412, published="1965-08-01")
print(b.model_dump())
print(b.model_dump_json())
```

The first line prints a dictionary whose `published` value is a `date` object, shown as `datetime.date(1965, 8, 1)`. The second line prints the compact JSON string `{"title":"Dune","pages":412,"published":"1965-08-01"}`. A plain `json.dumps(b)` would raise a `TypeError`, because a model is not a dictionary and the date is not JSON-ready.

**How it shows up in a case study.** A books API must return each record as JSON, with the publication date written as text. A developer writes `json.dumps(book)` and gets a `TypeError`. A second developer changes `pages` on an existing object to 0, dumps it, and is surprised that no error appears. The right decision is to use `model_dump_json()` for the response, because it produces the text in one step. The second case needs a clear rule: dumping never runs the constraints again, so a value that breaks a rule must be stopped when the object is created, or by re-creating the model with the new values.

:::trap Believing model_dump checks ge=1
`model_dump()` only reads the values. A constraint such as `ge=1` runs at creation, and a later change does not trigger it unless the model is set up to validate assignments.
:::

### Missing values and optional fields

**What it is.** In Pydantic version 2, a field with no default is required, even when its type allows `None`. The declaration `city: str | None` means that the key must be present, and its value may be `None`. The declaration `nickname: str | None = None` has a default, so the key may be absent. `model_fields_set` is a set of the field names that the input actually supplied. An empty string is a value, and it is not the same thing as an absent key.

```python
from pydantic import BaseModel

class Profile(BaseModel):
    name: str
    city: str | None
    nickname: str | None = None

p = Profile(name="Ana", city=None)
print(p.model_fields_set)
Profile(name="Ana")
```

The first print shows the set `{'name', 'city'}`, in no particular order. The `nickname` field is missing from the set, because the input did not supply it. The second line raises a `ValidationError` with the message `Field required` for `city`, because `city` has no default, even though `None` is an allowed value for it.

**How it shows up in a case study.** A sign-up form sends `"middle_name": ""` for some users and leaves the key out for others. The team must decide what each case means. A blank string is a value the user typed, so it is stored as an empty string and the key counts as supplied. An absent key is not a value, so the field should use a default. A second problem is a field such as `delivery_note: str | None` with no default. The API rejects every request that leaves the key out, even though the team thinks the note is optional. The right decision is to give truly optional fields a default of `None`, and to treat an empty string as the value it is.

:::trap Allowing None is not the same as optional
The type `str | None` allows the value None. It does not make the field optional. Only a default makes a field optional, and an empty string is a value, not a missing one.
:::

```quiz

WHY: A field with no default is required, even though its type allows None. The tempting wrong answer is that a type which allows None is therefore optional.
```

## The graded lab

The graded lab is a short Python task with visible tests and hidden tests. The visible tests show you four cases. The hidden tests check cases that you cannot see, so the habit that matters most is thinking about edge cases before you write code. You need six techniques: string cleaning, type checks, numeric text, whole numbers, booleans, and copying dictionaries.

### The task in plain words

**The scenario.** CityPulse ingests raw sensor payloads from the field. Before a reading reaches the database, it must be validated and coerced the way a Pydantic model would enforce it. A reading is a dictionary with the keys `station_id`, `ts`, `pollutant` and `value`.

**What you write.** The starter file already contains a tuple named `ALLOWED`, which holds the six allowed pollutant names. It also contains two empty function headers. You fill in the two functions.

- **`validate_reading(raw: dict) -> list[str]`** takes one reading and returns a sorted list of error codes. An empty list means the reading is valid. Each code is added when its rule fails:
  - `station_id_missing`: the key `station_id` is absent, or its value is blank.
  - `ts_missing`: the key `ts` is absent, or its value is blank.
  - `pollutant_unknown`: the value of `pollutant` is not one of the names in `ALLOWED`. The check ignores letter case, so `NO2` and `no2` are the same.
  - `value_not_number`: the value of `value` cannot be converted to a float.
  - `value_negative`: the value converts to a number below 0.
- **`normalize_reading(raw: dict) -> dict`** works on a valid reading. It returns a new dictionary with four keys: `station_id` as a string with the spaces removed at both ends, `ts` as a string with the spaces removed at both ends, `pollutant` in lower case, and `value` as a float rounded to 2 decimal places. If the reading is invalid, it returns an empty dictionary, `{}`.

A value is blank when nothing is left after you remove the spaces at both ends. The statement gives one example for each function. Copy both examples into `assert` lines before you start, as the method section explains.

**Limits.** Your code may run for 30 seconds and use 128 MB of memory. Neither limit should matter for this task. If your code is slow, look for a loop that is doing work it does not need to do.

**Scoring.** The table shows the visible tests and their points.

### What each function needs

The examples below use fruit, pets and colours, not sensor data. Each one teaches a Python idea that you need. None of them is part of the lab's solution.

**For `validate_reading`:**

- **Reading a key that may be missing.** `dict.get(key)` returns the value, or `None` if the key is absent. Using `dict[key]` instead raises `KeyError`.

```python
pets = {"cat": 2}
print(pets.get("dog"))
print(pets.get("dog", 0))
```

The output is `None`, then `0`. The second argument to `get` is the default that is returned when the key is missing.

- **Cleaning text and checking membership.** `.strip()` removes the spaces at both ends, `.lower()` makes the letters lower case, and `in` checks whether a value is one of the items in a tuple.

```python
colours = ("red", "green", "blue")
word = "  RED ".strip().lower()
print(word in colours)
```

The output is `True`, because the cleaned text is `red`.

- **Converting text safely.** `float()` converts text such as `"2.5"` to a number. When the text is not a number, it raises `ValueError`, so you wrap the call in `try` and `except`. A value that is not text or a number at all, such as `None`, raises `TypeError` instead.

```python
for text in ["2.5", "two"]:
    try:
        print(float(text))
    except ValueError:
        print("not a number:", text)
```

The output is `2.5`, then `not a number: two`. The loop does not stop at the bad value, because the `except` block handles it.

- **Sorting a list.** `sorted(items)` returns a new list in order. The list's own `.sort()` method changes the list it is called on.

```python
fruit = ["pear", "apple", "fig"]
print(sorted(fruit))
print(fruit)
```

The output is `['apple', 'fig', 'pear']`, then `['pear', 'apple', 'fig']`. The first line sorts a copy, so the original list is unchanged.

**For `normalize_reading`:**

- **Rounding to 2 decimal places.** `round(x, 2)` rounds a number to 2 decimal places. Python rounds an exact half to the nearest even digit, so `round(2.5)` gives 2, not 3.

```python
print(round(3.14159, 2))
print(round(2.5), round(3.5))
```

The output is `3.14`, then `2 4`. The second line shows the even-digit rule with two halves.

- **Building a new dictionary.** `{**old, "key": new}` makes a copy of `old` with one key changed. The original dictionary is not touched.

```python
item = {"colour": "blue", "size": 2}
changed = {**item, "colour": "red"}
print(item["colour"], changed["colour"])
```

The output is `blue red`. Your functions must behave in the same way toward the input they receive.

- **Type checks and the bool trap.** `isinstance(value, int)` is True for `True`, because `bool` is a subclass of `int`. When you need to tell a boolean apart from a number, check for `bool` first.

```python
print(isinstance(True, int), isinstance(True, bool))
```

The output is `True True`. Both checks are true for the same value, which is why the order of your checks matters.

### The rules people miss

Each row is a rule from the statement, or a rule that follows directly from it. The third column tells you how to check your own function.

| Rule in the statement | What a careless solution does | How to check yours |
|---|---|---|

### Worked twin problem

The lab's skills apply to other problems. This twin problem is about a sign-up form rather than sensors. Read it as if it were a lab task.

Write a function `normalise_profile(raw)` for a sign-up form. The input `raw` is a dictionary with the keys `username`, `email`, `age` and `country`.

- `username` is required. Remove the spaces at both ends and make it lower case. It must then be 3 to 20 characters long.
- `email` is required. Remove the spaces at both ends and make it lower case. It must contain one `@`, with at least one character before it, and a dot somewhere after it.
- `age` is required. It may be a number or text. Numeric text is converted. The value must be a whole number from 13 to 120 inclusive, and the result is an `int`.
- `country` is optional. If it is missing, `None`, or only spaces, the result is `"IN"`. Otherwise it must be exactly two ASCII letters, returned in upper case.
- If any rule fails, return a list of messages, one per failed field, in the order username, email, age, country. Use exactly these messages: `username: is required`, `username: must be 3 to 20 characters`, `email: must contain @`, `email: is not a valid address`, `age: must be a whole number`, `age: must be between 13 and 120`, and `country: must be a 2-letter code`.
- If every rule passes, return a dictionary with the keys `username`, `email`, `age` and `country`.

The solution is in one block below. It uses only the standard library, and the `assert` lines check normal cases and every edge case in the checklist above.

```python test
import math


def to_number(value):
    """Return the value as a finite float, or None."""
    if isinstance(value, bool):
        return None
    if isinstance(value, str):
        try:
            value = float(value.strip())
        except ValueError:
            return None
    if not isinstance(value, (int, float)):
        return None
    if not math.isfinite(value):
        return None
    return float(value)


def normalise_profile(raw):
    """Return a clean dict, or a list of error messages."""
    errors = []
    clean = {}

    username = raw.get("username")
    if not isinstance(username, str) or username.strip() == "":
        errors.append("username: is required")
    elif not 3 <= len(username.strip()) <= 20:
        errors.append("username: must be 3 to 20 characters")
    else:
        clean["username"] = username.strip().lower()

    email = raw.get("email")
    if not isinstance(email, str) or "@" not in email:
        errors.append("email: must contain @")
    else:
        address = email.strip().lower()
        local, _, domain = address.partition("@")
        if local and "." in domain and "@" not in domain:
            clean["email"] = address
        else:
            errors.append("email: is not a valid address")

    age = to_number(raw.get("age"))
    if age is None or age != int(age):
        errors.append("age: must be a whole number")
    elif not 13 <= age <= 120:
        errors.append("age: must be between 13 and 120")
    else:
        clean["age"] = int(age)

    country = raw.get("country")
    if country is None or (isinstance(country, str) and country.strip() == ""):
        clean["country"] = "IN"
    elif (isinstance(country, str) and len(country.strip()) == 2
          and country.strip().isascii() and country.strip().isalpha()):
        clean["country"] = country.strip().upper()
    else:
        errors.append("country: must be a 2-letter code")

    if errors:
        return errors
    return clean


GOOD = {"username": "  Asha_Rao ", "age": " 34 ", "email": "Asha@Example.com", "country": "in"}
```

- `import math` loads the standard maths module, which provides `math.isfinite`.

```python test
import math


def as_number(value):
    """Return the value as a finite float, or None."""
    if isinstance(value, bool):
        return None
    if isinstance(value, str):
        try:
            value = float(value.strip())
        except ValueError:
            return None
    if not isinstance(value, (int, float)):
        return None
    if not math.isfinite(value):
        return None
    return float(value)


def hire_cost(days, rate):
    """Return days * rate rounded to 2 dp, or None if an input is invalid."""
    days = as_number(days)
    rate = as_number(rate)
    if days is None or rate is None:
        return None
    if days != int(days) or not 1 <= days <= 30:
        return None
    if rate < 0:
        return None
    return round(days * rate, 2)


assert hire_cost(3, 10) == 30.0

assert hire_cost(2, -1) is None
```
