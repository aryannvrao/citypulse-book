## What the quiz tests

The Day Quiz has ten case-study multiple-choice questions. Each question sits on one of today's topics, and the ten are asked in the order given below, one question per topic. The pass mark is 70%. Your first attempt is the one your skill score keeps, so a second attempt does not replace it. Read each question as a short story about a team, a symptom or a design, then choose the option that fixes that story.

Case-study questions reward a method more than memory. Use this order every time:

1. Read the last line of the question first. It tells you what is being asked, such as the best fix, the first thing to check or the most likely cause.
2. Go back to the scenario and underline the facts that matter: the database, the table, the symptom, the constraint and any word that limits the answer, such as "retry", "crash" or "nightly".
3. Eliminate options that are true in general but do not fix this scenario. Many wrong options are correct statements about databases. The question is whether they solve the problem described.
4. Watch for three words. "Most" means several options help, and you must pick the strongest. "First" means there is an order, and the step that must come first is the answer. "Best" means you must compare two good answers and choose the one that fits the stated goal.

Each topic below explains the idea from zero, shows a small example, then shows how the idea appears in a CityPulse-style case. Read the topic, try its three questions, and only then read the WHY lines. The WHY line explains the right answer and why the most tempting wrong option fails. The trap box at the end of each topic names the mistake examiners rely on most.

### Primary keys

**What it is.** A primary key is the column, or the combination of columns, that identifies one row in a table. Two rows cannot have the same primary key, and the key cannot be empty. A key can be built from facts that already exist in the real world, such as a station id plus a timestamp plus a pollutant name. That kind of key is called a natural key. A key can also be a number the database creates for you, which is called a surrogate key.

Here is a small table of library members, with a single-column key:

```sql
CREATE TABLE member (
  member_id INTEGER PRIMARY KEY,
  name TEXT NOT NULL
);
INSERT INTO member VALUES (1, 'Asha');
INSERT INTO member VALUES (1, 'Ravi');
```

The first insert works. The second fails with `UNIQUE constraint failed: member.member_id`, because the number 1 is already taken, so Ravi is not stored. In SQLite, an `INTEGER PRIMARY KEY` column is filled with the next free number when you leave it out of an insert.

When the rule is about a combination, the key must be the combination. A loan is one member borrowing one book on one day. Any single one of those columns repeats too often to identify a loan, so the primary key is the three columns together. The database then refuses a second copy of the same loan, but still accepts the same member borrowing a different book on the same day.

**How it shows up in a case study.** A sensor loader writes readings into a table. After a network problem, the sensor resends a batch, and the row count doubles. The team's first idea is to make the timestamp the key, because every reading has a time. That fails at once: all four stations report at 09:00, so the second station's reading clashes with the first and is refused. The right key is the combination that defines one measurement: the station, the time and the pollutant. Now a resent reading clashes with the stored one and is refused, while readings from other stations and other pollutants at the same time are kept.

:::trap Choosing a column that looks unique
A timestamp can look unique in a small sample, and so can a station name. The key must match the real rule, which here is one measurement per station, time and pollutant. A key on one column refuses valid rows as well as duplicates.
:::

```quiz
Q: A library table records each loan with member_id, book_id and borrowed_on. A member may borrow the same book again on a later day, but the system must refuse the same member borrowing the same book twice on the same day. Which set of columns should be the primary key?
- borrowed_on alone
* (member_id, book_id, borrowed_on)
- book_id alone
- member_id alone
WHY: Only the three columns together express the rule. book_id alone would let each book be lent only once, ever, and member_id alone would allow only one loan per member for all time.

Q: A sensor loader inserts a reading after a network retry. The table has PRIMARY KEY (station_id, ts, pollutant), and the same reading arrives twice with identical values. What should the database do with the second copy?
- Store both, because a retry is a separate measurement
- Replace the first row silently, because keys always overwrite
* Refuse the second row with a constraint error, so the table keeps one row
- Rebuild the table before the second insert can run
WHY: The combination is the identity of the measurement, so a second copy clashes with the first and is refused. A plain INSERT does not overwrite, and a table does not need rebuilding to refuse a duplicate.

Q: A table has an INTEGER PRIMARY KEY column called parcel_id. A courier inserts a parcel row and leaves parcel_id out of the statement, and the insert succeeds. What is the best explanation?
- The primary key is optional when the table is small
- SQLite stores the row with a NULL key, which it always allows
- The insert must fail, because a primary key can never be left out
* SQLite gives the row the next free number, because an INTEGER PRIMARY KEY is filled automatically when no value is given
WHY: SQLite treats an INTEGER PRIMARY KEY as the row's own number, so it chooses one for you. The NULL option is the tempting trap, because a text key can hold NULL in SQLite unless you add NOT NULL, but an integer primary key does not store NULL like that.
```

### Foreign keys

**What it is.** A foreign key is a column whose value must already exist in a key of another table. The table that holds the foreign key is the child, and the table it points to is the parent. If a child row names a parent that does not exist, the database refuses the child row. A child row with no parent is called an orphan.

```sql
CREATE TABLE member (member_id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE loan (
  loan_id INTEGER PRIMARY KEY,
  member_id INTEGER NOT NULL REFERENCES member(member_id)
);
INSERT INTO loan (member_id) VALUES (99);
```

With foreign-key checks active, the last insert fails with `FOREIGN KEY constraint failed`, because member 99 does not exist. In SQLite, the checks run only after `PRAGMA foreign_keys = ON` has been run on that connection, and the setting is off by default. In Postgres, the check applies as soon as the constraint exists, unless the constraint was declared DEFERRABLE and the check is postponed to the end of the transaction.

To find orphans after the fact, use a LEFT JOIN. A LEFT JOIN keeps every child row. Where no parent matches, the parent's columns are NULL, so a filter for `IS NULL` on the parent's key keeps only the orphans. An INNER JOIN would drop the orphans and hide the problem.

**How it shows up in a case study.** A dashboard lists readings for each station, but one station's readings never appear on the map. The readings exist in the database and point to a station id that is missing from the station table. The loader ran for weeks on a connection that never switched foreign-key checks on. The fix has two parts. The loader must run the pragma on every connection, and the team must find and repair the existing orphans with a LEFT JOIN and an `IS NULL` filter before the foreign key can be trusted.

:::trap Assuming a foreign key is always enforced in SQLite
A foreign key written in the schema is only a promise until the connection enables checks. Two connections to the same file can behave differently, because the setting belongs to the connection, not to the file.
:::

```quiz
Q: A reading for station CP-777 is stored, but CP-777 is not in the station table. The loader runs on SQLite, and the schema declares a foreign key from reading to station. What must you check first?
- Whether the value column has a CHECK constraint
- Whether the station table has a UNIQUE name column
* Whether PRAGMA foreign_keys = ON ran on the connection that did the insert
- Whether the station column is stored as REAL
WHY: SQLite leaves foreign-key checks off for each connection until the pragma turns them on. A CHECK constraint, a UNIQUE name or a numeric type cannot stop an orphan that a foreign key would have refused.

Q: An analyst needs every reading whose station does not exist in the station table. Which query finds exactly these rows?
- SELECT * FROM reading WHERE station_id IN (SELECT station_id FROM station)
* SELECT r.* FROM reading r LEFT JOIN station s ON s.station_id = r.station_id WHERE s.station_id IS NULL
- SELECT * FROM reading INNER JOIN station ON station.station_id = reading.station_id
- SELECT COUNT(*) FROM reading GROUP BY station_id
WHY: The LEFT JOIN keeps all readings, and the IS NULL filter keeps those with no matching station. The IN query returns the matching rows, which is the opposite of what is needed, and the INNER JOIN hides the orphans it was meant to find.

Q: A batch loads a child table before its parent table in Postgres, and the foreign key is not deferred. What happens to the child rows?
- They are stored, because Postgres checks foreign keys only at the end of the day
- They are stored, because COPY turns off the foreign key during the load
- They are stored without any checks, because bulk loads skip constraints
* They are refused when the parent key is missing at the moment each child row is inserted, so the load must put parents first
WHY: Postgres checks each child row when it is inserted unless the constraint was declared DEFERRABLE. Bulk loads such as COPY still enforce constraints, so the claim that they skip checks is the trap.
```

### Postgres column types

**What it is.** A column type sets which values a column can hold and how the database stores, compares and adds them. The choice matters even when the query is right. Four types matter for this lesson. TEXT holds characters. REAL holds a four-byte floating-point number. NUMERIC holds exact decimal digits. TIMESTAMPTZ holds a point in time, and Postgres converts the input to UTC for storage. A plain TIMESTAMP holds a wall-clock date and time with no zone attached.

The difference between a floating-point type and an exact type shows up at once:

```sql
SELECT 0.1::double precision + 0.2::double precision = 0.3::double precision;
-- false
SELECT 0.1::numeric + 0.2::numeric = 0.3::numeric;
-- true
```

Binary floating-point types cannot store 0.1 exactly, so the sum is slightly off and the equality fails. NUMERIC stores the decimal digits themselves, so the sum is exact. This is why money uses NUMERIC, and why sensor values are usually stored as REAL when small errors do not matter.

**How it shows up in a case study.** A team loads readings from two cities. The sensors send local times without a zone, and the team stores them in a TIMESTAMP column. A chart then puts a morning reading from one city after an evening reading from another, because the stored values carry no zone. The fix is to store the instant as TIMESTAMPTZ, with each source's time converted to UTC on the way in. The database can then compare the two cities correctly, and the displayed time can still be shown in the local zone.

:::trap Choosing TIMESTAMP because it looks shorter
TIMESTAMP looks simpler, but it cannot tell two cities apart. TIMESTAMPTZ is the type that keeps an instant that can be compared across sources.
:::

```quiz
Q: Sensors in two cities send readings in UTC, and the team must compare the times later in one table. Which Postgres type keeps the exact instant safely?
* TIMESTAMPTZ
- TIMESTAMP
- DATE
- INTEGER
WHY: TIMESTAMPTZ stores the instant in UTC, so the readings line up. TIMESTAMP stores a wall-clock time with no zone, and DATE drops the time of day. INTEGER stores a number that has no time meaning unless you add one.

Q: A table stores money amounts, such as 0.10 and 0.20, and the team needs sums that are exactly right. Which type fits best in Postgres?
- REAL
- DOUBLE PRECISION
- TEXT
* NUMERIC
WHY: NUMERIC stores exact decimal digits, so 0.10 plus 0.20 is exactly 0.30. REAL and DOUBLE PRECISION are binary floating-point types, so sums can be slightly off. TEXT cannot be added without a cast.

Q: A sensor reports particle values to one decimal place. The team wants a compact type that suits measurements and does not need exact decimal sums. Which type should the column use?
- NUMERIC with no precision
* REAL
- TIMESTAMP
- BOOLEAN
WHY: REAL is compact and fits measurements. NUMERIC is exact and takes more space and time than the job needs. BOOLEAN holds only true or false, and TIMESTAMP holds a date and time.
```

### Bulk loading

**What it is.** Bulk loading sends a whole file of rows into a table in one operation, rather than running one INSERT statement for each row. Each row still goes through the same checks, but the database avoids a separate statement, a separate round trip and a separate parse for every row. In Postgres, the `COPY` command reads a file on the server. The `\copy` command in `psql` reads a file on your own computer and streams it to the server.

```sql
\copy station from 'stations.csv' csv header
```

The `csv` option says the file is comma-separated. The `header` option says the first line holds column names and must be skipped. A successful run prints `COPY 4` when four rows were stored. The number is the count of rows stored, not the count of lines in the file.

The same idea appears in Python. A loop that calls `execute` once per row sends one statement for each row. A call to `executemany` with a list of tuples runs one prepared statement for all rows in one go, which is much faster for a large batch.

**How it shows up in a case study.** A team loads 1,392 readings with a Python loop, and the load takes several minutes. They switch to a bulk load, and it finishes in a fraction of a second. The next run fails with a foreign-key error on the readings, because the readings file was loaded before the stations file. The decision is to load the parent table first, so every reading's station exists when its row is checked. The speed does not change the rules, and the order does.

:::trap Skipping constraints to load faster
A bulk load is fast because of how rows are sent, not because it turns checks off. Keys, NOT NULL, CHECK and foreign keys still apply to every row. A load that is fast but wrong is a worse result than a slower correct one.
:::

```quiz
Q: A loader must add 1,392 readings. One version runs an INSERT inside a Python loop for each row. Another version sends the file as one bulk command. What is the main reason the bulk version is faster?
- It skips every constraint, so there are fewer checks to run
- It stores each row as text, which is smaller on disk
- It writes to a second database first and copies the result later
* It reads the file once and streams the rows, avoiding a separate statement and round trip for every row
WHY: The speed comes from avoiding per-row overhead, and the constraints still run. Skipping constraints is the tempting wrong answer, and it is false for both COPY and \copy.

Q: A CSV file starts with a header line of column names. A bulk load into a table with a numeric column fails with a type error on the first line of data. What is the most likely cause?
* The header line was not skipped, so the column names were read as values for a numeric column
- The table has too many primary keys
- The file has more rows than the table can hold
- The file was saved with the wrong extension
WHY: A header is text that names the columns, and a loader that does not skip it tries to store those names as data. Too many keys, the row limit or the extension would not produce this particular type error.

Q: A stations file and a readings file must be loaded in one run, and every reading refers to a station that is only added by the stations file. Which order is correct?
- Load readings first, so the foreign key can point forward to stations that come later
- Load both files in parallel, because the order does not matter with a foreign key
* Load stations first, so each reading's parent row exists when the reading is inserted
- Load readings only, and let the database create the stations automatically
WHY: Each child row is checked when it is inserted, so the parent must be there first. A parallel load can race, and a foreign key never creates a missing parent row on its own.
```

### Normalisation

**What it is.** Normalisation is the process of arranging tables so that each fact is stored in one place. A table is in first normal form when each cell holds a single value and there are no repeating groups of columns. It is in third normal form when every non-key column depends on the key itself, and not on some other non-key column. Here is a table that breaks the third rule:

```text
reading_id  station_id  station_name  value
1           CP-001      Hebbal        51.3
2           CP-001      Hebbal        52.0
```

The station name depends on the station, not on the reading. If the station is renamed, both rows must change. If a later update changes only one row, the table now gives two names for one station. Moving the name into a station table, and keeping only `station_id` in the reading table, removes the repeated fact.

Normalisation is not a rule that more tables are always better. Each extra table means more joins when you read the data. A transactional app with many small updates usually benefits from full normalisation. An analytics store that mostly reads large amounts of data can accept some repetition for speed and simplicity. CityPulse uses a star schema for that reason.

**How it shows up in a case study.** A reporting team stores the station name and the city on every reading. A station is renamed, and an update changes most of its rows but misses a batch that came from a second loader. Now one station appears under two names in the report. The team's question is which design stops this. The answer is a station table with a station key, and a reading table that holds only the station id. A rename then touches one row, and the reports join to the new name.

:::trap Thinking normalisation means more tables is always better
Normalisation removes repeated facts. It does not reward the number of tables. A star schema with repeated text can be the right design when the workload is read-heavy analytics.
:::

```quiz
Q: A reading table stores the station name on every row. A station is renamed, and a loader misses one batch of rows. What is the main problem?
- The reading values become NULL after the rename
- The primary key on the reading table is deleted
* Some rows keep the old name, so one station now appears under two names
- Postgres refuses to store a name longer than the old one
WHY: The problem is a repeated fact that can disagree with itself. Storing the station id and joining to a station table keeps one copy of the name. The length of the name is a red herring.

Q: A table stores the city and the region name and region code on every reading. Which rule does this design break most directly?
- Every table must have exactly one row
- Every column must be a number
- A table must never contain a foreign key
* Non-key columns must depend on the key, not on another non-key column, which is the third normal form rule
WHY: The region code depends on the region, not on the reading key, so it is a transitive dependency. The other options describe rules that do not exist in normalisation.

Q: A colleague says that normalisation means more tables are always better for CityPulse. Which reply is most accurate?
* Normalisation removes repeated facts, and CityPulse keeps a star schema because its reads are analytics and some repetition is accepted
- Normalisation applies only to Postgres and never to SQLite
- More tables always make queries faster, so the colleague is right
- Normalisation means every value should be stored as text
WHY: The goal is one place for each fact, judged against the workload. More tables add joins, so they can slow reads. The text option confuses normalisation with the choice of data type.
```

### Upserts and idempotency

**What it is.** An upsert is a single statement that inserts a row when its key is new and updates the existing row when the key is already present. In SQLite and Postgres, the syntax is `INSERT ... ON CONFLICT (key columns) DO UPDATE SET ...`. An operation is idempotent when running it again leaves the same result as running it once. A load becomes idempotent when its rows are keyed by a UNIQUE constraint and the load uses an upsert.

```sql
INSERT INTO member_fee (member_id, fee) VALUES (1, 500)
ON CONFLICT (member_id) DO UPDATE SET fee = excluded.fee;
```

The word `excluded` refers to the row that you tried to insert. If you run this statement twice, the table still has one row for member 1, and its fee is the value from the latest run. The first run inserts the row. The second run hits the conflict and updates the fee to the same value. The row count does not change.

The conflict target, here `(member_id)`, must match a UNIQUE or PRIMARY KEY constraint with exactly those columns. If it does not, the database raises an error rather than guessing.

**How it shows up in a case study.** A nightly job loads the same file every night. One night, the source corrects the fee for a member, and the job must store the corrected value. A plain INSERT fails on the second run because the key already exists. An INSERT OR IGNORE keeps the old fee, so the correction is lost. A DELETE followed by an INSERT works if both steps run inside one transaction, but without one, a crash in the middle leaves an empty table. The upsert with a transaction is the only option that is repeatable and applies the correction.

:::trap INSERT OR IGNORE for a value that can change
INSERT OR IGNORE is repeatable, but it keeps the first value it saw. A corrected reading for an existing key is silently discarded, and no error tells you so.
:::

```quiz
Q: A nightly job reloads a file. One reading arrives with a corrected value for a key that is already in the table. The table must hold the corrected value and no duplicate rows. Which statement does this?
- INSERT OR IGNORE on the same key
- DELETE FROM reading, then INSERT, with no transaction
* An INSERT with ON CONFLICT on the key, using DO UPDATE to set the new value
- A plain INSERT with no conflict clause
WHY: Only the upsert both applies the new value and avoids a duplicate. INSERT OR IGNORE keeps the old value, a DELETE with no transaction can leave the table empty after a crash, and a plain INSERT fails on the second run.

Q: A team runs the same load twice and counts the rows before and after the second run. The two counts are equal, and the values are the same. Which property has been shown?
- Atomicity only
* Idempotency
- Normalisation
- Partitioning
WHY: Idempotency means running the operation again leaves the same result. Atomicity is about all-or-nothing changes, which matters for a crash but is not what two equal counts prove.

Q: An upsert is written as ON CONFLICT (station_id, ts, pollutant). What must be true of the table for this statement to work?
- The table must have a CHECK constraint on value
- The table must have an index on value alone
* The table must have a UNIQUE or PRIMARY KEY constraint on exactly station_id, ts and pollutant
- The file must be sorted by value before the load
WHY: The conflict target must match a unique key exactly, or the database rejects the statement. A CHECK and an index on value do not define a conflict, and the sort order of the file does not matter.
```

### Indexing strategy

**What it is.** An index is a separate structure that lets the database find rows without reading the whole table. It works like the index at the back of a book, which lists each term with its pages. A UNIQUE constraint and a PRIMARY KEY both create an index automatically. An index on several columns is sorted by the first column, then the second, and so on.

```sql
CREATE INDEX ix_loan_member_date ON loan (member_id, borrowed_on);
SELECT * FROM loan
WHERE member_id = 7 AND borrowed_on BETWEEN '2026-01-01' AND '2026-01-31';
```

The index first narrows the search to member 7, because that is the first column. Within those rows, it finds the January dates, because the second column is sorted inside each member. A query that filters only on `borrowed_on` cannot use this index well, because the index is not sorted by date first. The column order is therefore part of the design. Put the column that you compare with equals first, and the column you compare with a range second.

Indexes are not free. Each index must be updated whenever a row is inserted, changed or deleted, and each one takes disk space.

**How it shows up in a case study.** An analyst asks for one station's readings across one week, and the query takes several seconds. The table has a UNIQUE key on location, source and time, but the time column is last, so the source column sits between them and the key helps little for a query that filters by location and then by time. The team adds an index on the location and then the time. The query now reads only the rows it needs. The team also decides not to index the value column, because nobody filters by it, and the inserts would slow down for no gain.

:::trap Indexing every column
An index on every column makes each insert slower and uses space, and most of those indexes are never used. Add an index for a query you actually run, and choose the column order to match that query.
:::

```quiz
Q: An analyst often asks for one station's readings across a single week, and this happens many times a day. The table has an index on (location_id, ts_utc). Why does this index help?
* It starts with the station and then the time, so it finds the station's rows and then the time range quickly
- It stores every timestamp as a number, which makes comparisons faster
- It removes the need for the primary key on the table
- It makes inserts faster because it sorts the rows as they arrive
WHY: The equality column comes first, and the range column comes second, which is what the query needs. Storing timestamps as numbers is a different choice, not what an index does. Indexes usually make inserts slower, not faster.

Q: A table has a UNIQUE key on (location_id, source_id, ts_utc). A query filters only on source_id. Which statement is most accurate?
- The unique key is useless for every query on the table
- The database always uses the unique key for a filter on source_id alone
* The key helps much less for source_id alone, because source_id is not its leading column
- source_id cannot be indexed unless it is a primary key
WHY: An index is most useful for filters on its leading columns. Saying it is always used is too strong, because the planner chooses by cost, and saying it is useless for every query is also too strong.

Q: A team adds an index to every column of a table, to make every query faster. What cost should they expect?
- Queries on every column will now return wrong answers
- Primary keys stop working until the indexes are dropped
- The table stores fewer rows than before
* Inserts and updates get slower, and the indexes take extra disk space
WHY: Every index is maintained on each change to the table, which costs time and space. Indexes do not change query answers, and they do not reduce the number of rows.
```

### Constraints

**What it is.** A constraint is a rule the database checks on every insert and update, so bad data is refused rather than stored. The common types are NOT NULL, which refuses a missing value, UNIQUE, which refuses a repeated value, CHECK, which refuses a row when an expression is false, and FOREIGN KEY, which refuses a value with no parent. A PRIMARY KEY is a combination of NOT NULL and UNIQUE on one set of columns.

```sql
CREATE TABLE hire (days INTEGER NOT NULL CHECK (days > 0));
INSERT INTO hire VALUES (5);
INSERT INTO hire VALUES (0);
INSERT INTO hire VALUES (NULL);
```

The first insert is stored. The second fails with `CHECK constraint failed`, because zero is not greater than zero. The third fails with `NOT NULL constraint failed: hire.days`, because the value is missing. A constraint error is the database saying that the data breaks a rule, and nothing from that statement is stored.

A CHECK fails only when its expression is false. When the value is NULL, the comparison is unknown, so the CHECK passes. The NOT NULL constraint is the rule that forbids the missing value.

**How it shows up in a case study.** A team validates readings in its Python code, and a bug in the code lets a negative particle value through. The bad value reaches the table, and a chart shows a dip below zero. The team's question is where the rule should live. The answer is in the database, as a CHECK constraint, because every program that writes to the table then obeys it. The team also notices that a few rows have a missing value, and that the CHECK does not catch them. They add NOT NULL to the column, because their documented rule says a reading must be present.

:::trap Believing a CHECK refuses NULL
CHECK (pm2_5 >= 0) accepts a missing value, because the comparison is unknown and only a false result fails. If the value must be present, add NOT NULL as well.
:::

```quiz
Q: A reading has pm2_5 set to NULL. The column has CHECK (pm2_5 >= 0) and no NOT NULL constraint. What happens when the row is inserted?
- The row is refused, because NULL is treated as zero and zero fails
- The row is refused, because NULL is treated as a negative number
- The row is stored only if a default value is set for the column
* The row is stored, because the check is unknown for NULL and only a false result is refused
WHY: A CHECK refuses a row only when its expression is false, and a comparison with NULL is unknown. Calling NULL zero is the common mistake, and adding NOT NULL is the fix when missing values are not allowed.

Q: A rule says that every reading must name a station. Which constraint enforces that the station id is present on every row?
* NOT NULL on the station id column
- UNIQUE on the station id column
- An index on the station id column
- A DEFAULT of zero on the station id column
WHY: NOT NULL refuses a missing value. UNIQUE refuses repeats, an index only speeds up lookups, and a DEFAULT of zero stores a made-up station, which is worse than refusing the row.

Q: A rule says that each combination of station id, timestamp and pollutant may appear only once. Which constraint should the schema use?
- NOT NULL on each of the three columns
- CHECK on the value column
- A foreign key from the reading to the station table
* UNIQUE or PRIMARY KEY on the three columns together
WHY: A composite UNIQUE or PRIMARY KEY is the constraint that refuses a repeated combination. NOT NULL does not stop repeats, a CHECK tests one row's values, and a foreign key points to a parent table.
```

### Transactions

**What it is.** A transaction is a group of changes that the database treats as one unit. The changes either commit together, which saves all of them, or roll back together, which undoes all of them. A change that is not yet committed is visible only to the connection that made it. If a program stops before the commit, the database undoes the uncommitted changes.

```python
import sqlite3

con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE tally (n INTEGER)")
try:
    with con:
        con.execute("INSERT INTO tally VALUES (1)")
        raise RuntimeError("stop")
except RuntimeError:
    pass
print(con.execute("SELECT COUNT(*) FROM tally").fetchone()[0])
```

The output is `0`. The INSERT ran inside the `with con:` block, then the error left the block, so Python's sqlite3 module rolled the change back. Had the block ended normally, the insert would have been committed. The connection is still open after the rollback, so it can be used again.

**How it shows up in a case study.** A loader writes 5,000 rows, one commit for each row. The process stops at row 3,000. When the team looks at the table, it holds exactly 3,000 rows, which is a partial load that looks complete. A re-run then adds the rest, but only because the key stops the duplicates. The fix is to wrap the whole batch in one transaction. A stop in the middle then leaves the table as it was before the load, so the table is either complete or untouched.

:::trap Committing row by row
A commit after every row is slow, and it leaves a partial load if the program stops. Wrap the whole batch in one transaction, so the load is all or nothing.
:::

```quiz

* Nothing from this load, because the transaction was never committed and the database undoes it
- Half of the rows, chosen at random
- All 1,392 rows, because most of the rows were inserted before the crash
WHY: One transaction is all or nothing. The changes are undone when the commit does not happen. The first-699 answer describes per-row commits, which is the trap.

Q: A developer commits after each row in a loop of 1,392 inserts. Compared with one transaction for the whole load, which two things does this lose?

- Indexes and the table name, because each commit rebuilds the table
- Upserts and CHECK constraints, because each commit skips them

WHY: Per-row commits allow a partial load and add a cost to every row. Keys, foreign keys, CHECK constraints and upserts still apply to every row in both designs, so those options are false.
```

### Partitioning

**What it is.** Partitioning splits one large logical table into smaller physical parts, usually by a range of values such as a month or a year. Each part is stored separately, and the rows are routed to the right part when you insert them. A query that filters on the partition key can skip the parts that cannot match. Postgres supports this as declarative partitioning. SQLite has no built-in partitioning.

```sql
CREATE TABLE reading_log (
  ts TIMESTAMPTZ NOT NULL,
  value REAL
) PARTITION BY RANGE (ts);

CREATE TABLE reading_2026 PARTITION OF reading_log
  FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
```

Rows with a timestamp in 2026 go to `reading_2026`. A query with a filter such as `WHERE ts >= '2026-03-01' AND ts < '2026-04-01'` can skip the other parts when the planner knows their ranges do not match. Partitioning changes how the data is stored and read. It does not change the rules. Keys, constraints and foreign keys still apply to every row.

**How it shows up in a case study.** A team keeps ten years of hourly readings in one table, and most reports cover one year. Those reports have become slow, and the table is still growing. The team considers removing the primary key to make inserts faster. That would allow duplicate readings, which is the wrong fix. The better change is to partition the table by year, so a one-year report reads only one part. The key stays, so duplicates are still refused.

:::trap Using partitioning to replace keys
Partitioning is for speed and manageability. It does not make wrong data correct, and it does not stop duplicates unless the key does that job. Keep the keys and constraints in place when you partition.
:::

```quiz
Q: A fact table holds ten years of hourly readings, and most queries cover one year. Which change best helps those queries?
- Remove the primary key, so that inserts are faster
- Store every number as TEXT, so that it is smaller
- Add a CHECK constraint on every column
* Partition the table by year, so a query for one year can skip the other years
WHY: Partitioning lets the planner skip the parts that cannot match the filter. Removing the key allows duplicates, storing numbers as text slows comparisons, and extra CHECK constraints add cost without helping the date filter.

Q: A colleague says that because the table is partitioned, duplicate readings can no longer happen. What is the correct reply?
- Yes, every partition is unique by default
* No, partitioning splits the storage for speed, and the keys and constraints still refuse duplicates
- Yes, but only when the database is SQLite
- Only when each partition is split by station
WHY: Keys and constraints do the rule-checking, and partitioning does not replace them. The claims that partitions are unique by default, or that this is a SQLite feature, are both false.

Q: Which database in the Day 9 course supports declarative partitioning of a table?
- SQLite, which partitions every table automatically
- Python's sqlite3 module, which partitions files on disk
- A CSV file, which is split into parts when it is loaded
* PostgreSQL
WHY: Postgres supports declarative partitioning. SQLite has no built-in partitioning, and a CSV file and a Python module are not databases. The Day 9 sources do not use partitioning, so treat it as an idea to explain in an interview.
```

### What each function needs

Each Python idea below is taught with a small example that is not about the lab's data. The examples use a fruit stall, so you can learn the tool without being given the lab's solution. Do not copy these examples into your functions as they are. Use the idea, then write your own code for the real task.

**Opening an in-memory connection and creating a table.** `sqlite3.connect(":memory:")` opens a database that lives only in memory. It disappears when the connection closes, which suits tests because nothing is written to disk. A table is created with `CREATE TABLE`, and a UNIQUE constraint is written as a clause in the table definition.

```python
import sqlite3

stall = sqlite3.connect(":memory:")
stall.execute("CREATE TABLE fruit (name TEXT NOT NULL, kg REAL, UNIQUE (name))")
```

Nothing is printed. If you ran the `CREATE TABLE` statement a second time, it would fail with an error, because the table already exists. Adding `IF NOT EXISTS` makes the statement safe to repeat.

**Inserting one row with placeholders.** A `?` in an SQL statement is a placeholder. Python fills each `?` from a tuple, in order, so values are never pasted into the SQL text. `INSERT OR IGNORE` skips a row that breaks a UNIQUE constraint, and keeps the row that was stored first. It also skips a row that breaks a NOT NULL or CHECK rule, with no error, so use it only when skipping every bad row is what you want.

```python
stall.execute("INSERT OR IGNORE INTO fruit (name, kg) VALUES (?, ?)", ("mango", 1.5))
stall.execute("INSERT OR IGNORE INTO fruit (name, kg) VALUES (?, ?)", ("mango", 9.0))
```

The second statement is skipped without an error, because `mango` is already there. The table still holds `1.5` for mango. `executemany` runs the same statement once for each tuple in a list, which is the tool to use when you have many rows.

**Counting rows and reading one value.** `COUNT(*)` counts the rows that a query returns. `fetchone()` returns the first row as a tuple, and the `[0]` picks the first item of that tuple, which is the number itself.

```python
count = stall.execute("SELECT COUNT(*) FROM fruit").fetchone()[0]
print(count)  # 1
```

The result is an `int`. The `fetchone()` call returns `(1,)`, a one-item tuple, and the index turns it into the plain number.

**Distinct values in sorted order.** `DISTINCT` removes repeated values from a result. `ORDER BY` sorts the result. `fetchall()` returns every row as a list of tuples, so a list comprehension turns the one-item tuples into plain values.

```python
names = [row[0] for row in stall.execute("SELECT DISTINCT name FROM fruit ORDER BY name")]
print(names)  # ['mango']
```

**Grouping, summing and rounding.** `GROUP BY` makes one group for each distinct value. `SUM` adds up a column inside each group. `ROUND(x, 2)` rounds a number to two decimal places. Floating-point arithmetic can leave small errors, so a sum such as 0.1 plus 0.2 may come out as 0.30000000000000004, and rounding removes that noise.

```python
stall.execute("CREATE TABLE weigh (name TEXT, kg REAL)")
stall.execute("INSERT INTO weigh VALUES ('fig', 0.1)")
stall.execute("INSERT INTO weigh VALUES ('fig', 0.2)")
rows = stall.execute(
    "SELECT name, ROUND(SUM(kg), 2) FROM weigh GROUP BY name ORDER BY name"
).fetchall()
print(rows)  # [('fig', 0.3)]
```

Python's own `round` works the same way for a single number: `round(1.236, 2)` gives `1.24`. Round once, at the end of the calculation, so that the error from earlier steps does not build up.

**Checking the type of a result.** `isinstance(x, int)` is true for an `int`, and it is also true for a `bool`, because `bool` is a subclass of `int`. `type(x) is int` is true only for a true `int`. This matters when a function must return an integer and a `True` or `False` value would be wrong.

```python
print(isinstance(True, int))   # True
print(type(True) is int)       # False
print(type(3) is int)          # True
```

**Sorting with a key.** `sorted` returns a new list and leaves the original unchanged. Its `key` argument decides what is compared. Python's sort is stable, so items that compare equal keep their original order.

```python
words = ["pear", "fig", "kiwi"]
print(sorted(words, key=len))  # ['fig', 'pear', 'kiwi']
print(words)                   # ['pear', 'fig', 'kiwi'], unchanged
```

**Never changing an input.** A function that receives a list should not alter it, because the caller may use the list again. Use `sorted(items)` to get a new sorted list, rather than `items.sort()`, which changes the list in place. The same care applies to any list you were given as a parameter.

### Worked twin problem

The twin problem below is about library loans, not about readings. It needs the same skills: a table with a composite UNIQUE rule, a load that refuses repeated keys, a count of stored rows, and a grouped average rounded to one decimal place. It adds a rule the real lab does not have, a CHECK constraint, so that you practise a second kind of refusal.

**The task.** Write `load_loans(records)`. It receives a list of `(member, book, borrowed_on, days)` tuples. It creates an in-memory database with a table called `loans`, with the columns `member`, `book`, `borrowed_on` and `days`. The table has a composite primary key on member, book and borrowed_on, and the `days` column must be greater than zero. Each record is inserted. A record that the database refuses is not stored, and the function counts it. The function returns a tuple of the open connection and the number of refused records.

Write `loan_count(conn)`, which returns the number of stored loans as an `int`. Write `average_days_by_book(conn)`, which returns a list of `(book, average_days)` tuples, grouped by book, sorted by book ascending, with each average rounded to one decimal place.

Here is the full solution, with the asserts that check normal cases and every edge case.

```python test
import sqlite3

INSERT_SQL = "INSERT INTO loans (member, book, borrowed_on, days) VALUES (?, ?, ?, ?)"

def load_loans(records):
    conn = sqlite3.connect(":memory:")
    conn.execute(
        "CREATE TABLE loans ("
        " member TEXT NOT NULL,"
        " book TEXT NOT NULL,"
        " borrowed_on TEXT NOT NULL,"
        " days INTEGER NOT NULL CHECK (days > 0),"
        " PRIMARY KEY (member, book, borrowed_on))"
    )
    refused = 0
    for record in records:
        try:
            conn.execute(INSERT_SQL, record)
        except sqlite3.IntegrityError:
            refused += 1
    conn.commit()
    return conn, refused

def loan_count(conn):
    return conn.execute("SELECT COUNT(*) FROM loans").fetchone()[0]

def average_days_by_book(conn):
    return conn.execute(
        "SELECT book, ROUND(AVG(days), 1) FROM loans GROUP BY book ORDER BY book ASC"
    ).fetchall()

RECORDS = [
    ("Asha", "Dune", "2026-01-05", 14),
    ("Ravi", "Dune", "2026-01-09", 7),
    ("Asha", "Emma", "2026-01-12", 21),
    ("Asha", "Dune", "2026-01-05", 14),
    ("Mei", "Emma", "2026-02-01", 0),
    ("Mei", "Emma", "2026-02-01", 10),
    ("Ravi", "Ulysses", "2026-03-01", 1),
    ("Mei", "Ulysses", "2026-03-02", 1),
    ("Asha", "Ulysses", "2026-03-03", 2),
]

conn, refused = load_loans(RECORDS)
assert loan_count(conn) == 7
assert refused == 2
assert average_days_by_book(conn) == [("Dune", 10.5), ("Emma", 15.5), ("Ulysses", 1.3)]

empty_conn, empty_refused = load_loans([])
assert loan_count(empty_conn) == 0
assert empty_refused == 0
assert average_days_by_book(empty_conn) == []

one_conn, one_refused = load_loans([("Mei", "Emma", "2026-02-01", 5)])
assert loan_count(one_conn) == 1 and one_refused == 0
```

**Explanation, line by line.**

- `import sqlite3` loads the standard library module. No installation is needed.
- `INSERT_SQL` holds the insert statement once, with four `?` placeholders. Each tuple in the list supplies the four values in order.
- `def load_loans(records):` defines the loader. It takes the list of tuples and gives nothing else.
- `conn = sqlite3.connect(":memory:")` opens a fresh in-memory database for each call, so one call cannot see another call's loans.
- The `CREATE TABLE` statement has three parts that matter here. `NOT NULL` refuses a missing text value. `CHECK (days > 0)` refuses a loan of zero or fewer days. `PRIMARY KEY (member, book, borrowed_on)` refuses a second copy of the same loan.
- `refused = 0` starts the counter of refused records.
- The `for` loop takes one record at a time. The `try` block runs the insert, and the `except` block catches the error that the database raises when a rule is broken.
- `refused += 1` adds one to the counter. The refused record is simply not stored, and the loop carries on with the next record.
- `conn.commit()` saves the inserted rows. Without it, the changes would still be visible on this connection, but they would not be committed.
- `return conn, refused` returns both values as one tuple. The connection is left open for the caller.
- `loan_count` counts the rows in the table and returns the number as an `int`.
- `average_days_by_book` groups the rows by book, averages the days in each group, rounds the average to one decimal place, and sorts by the book's name.

Now the asserts. The first block uses the nine records. Record 4 repeats record 1, so the database refuses it because the key already exists. Record 5 has zero days, so the CHECK refuses it. That gives 9 minus 2 equals 7 stored loans, and a refused count of 2. The averages are Dune with 14 and 7, which is 10.5, Emma with 21 and 10, which is 15.5, and Ulysses with 1, 1 and 2, which is 4 divided by 3, or 1.333, rounded to 1.3. The second block checks that an empty list gives zero loans and an empty result. The third block checks a single valid record.

Notice that the ROUND happens in the query, after the average is worked out. The average of the three Ulysses loans is rounded once, from the exact value. Rounding early, before the final average, is the habit to avoid.

```python test
import sqlite3

def load_scans(rows):
    conn = sqlite3.connect(":memory:")
    conn.execute(
        "CREATE TABLE scans ("
        " scan_id INTEGER PRIMARY KEY,"
        " courier TEXT NOT NULL,"
        " kg REAL NOT NULL CHECK (kg >= 0))"
    )
    conn.executemany(
        "INSERT OR IGNORE INTO scans (scan_id, courier, kg) VALUES (?, ?, ?)", rows
    )
    return conn

def scan_count(conn):
    return conn.execute("SELECT COUNT(*) FROM scans").fetchone()[0]

def heaviest_by_courier(conn):
    return conn.execute(
        "SELECT courier, ROUND(MAX(kg), 1) FROM scans GROUP BY courier ORDER BY courier ASC"
    ).fetchall()

rows = [(1, "Zed", 2.04), (2, "Ace", 0.5), (3, "Zed", 3.26), (1, "Zed", 9.9), (4, "Ace", 1.0)]
conn = load_scans(rows)
assert scan_count(conn) == 4
assert heaviest_by_courier(conn) == [("Ace", 1.0), ("Zed", 3.3)]
assert scan_count(load_scans([])) == 0
assert heaviest_by_courier(load_scans([])) == []
assert heaviest_by_courier(load_scans([(9, "Ace", 0.0)])) == [("Ace", 0.0)]
assert heaviest_by_courier(load_scans([(1, "A", 1.0), (1, "A", 2.0)])) == [("A", 1.0)]
```

The first scan with id 1 is stored with 2.04. The later scan with id 1 and 9.9 is ignored, so Zed's heaviest value is 3.26 from scan 3, which rounds to 3.3. The `executemany` call runs the insert once per tuple, and `INSERT OR IGNORE` skips the repeat. The `MAX` function picks the largest value in each group, and `ROUND` rounds it once at the end. An empty input creates the table and returns nothing from the grouped query, which is why the last assert on the empty load is an empty list.
