## What the quiz tests

The Day Quiz has ten case-study multiple-choice questions, one for each topic in this section, in the same order. Each gives a short scenario about a team, a symptom or a limit, and asks for the best action or explanation. The pass mark is 70%. Your skill score keeps the result of your first attempt, so use a second attempt to learn, not to change the score. Read the topics as a study guide, then try the self-test at the end.

Answer every case-study question with the same four steps.

1. Read the last line first. It says what is asked: a cause, the cheapest option, a first step or a fix.
2. Underline the facts that change the decision: the numbers, the service names, the limits and the symptom.
3. Eliminate options that are true in general but do not fix this scenario. Many wrong options are correct statements about Lambda. Ask whether the option solves the problem described.
4. Watch the key words. "Most" means one option is better than the rest. "First" means order matters. "Best" means a trade-off, so pick the option that fits the scenario's constraint.

Each topic ends with a trap box that names the tempting wrong answer.

### Starting Lambda from an S3 upload

**What it is.** Amazon S3 can send a notification when something happens in a bucket, such as `s3:ObjectCreated` when a new object is written. The notification sends an event to a Lambda function, so the function starts on the upload and nothing has to poll the bucket. Two parts are needed. The function's resource policy must allow S3 to call it, which you add with `aws lambda add-permission`. The bucket notification then names the function and the event type.

The event is a dictionary. Its `Records` list holds one entry per object, with the bucket name, the key and the size:

```python
event = {"Records": [{"s3": {"bucket": {"name": "readings"},
                             "object": {"key": "raw/a.json", "size": 210}}}]}
rec = event["Records"][0]["s3"]
print(rec["object"]["key"], rec["object"]["size"])
```

The output is `raw/a.json 210`. The file contents are not in the event, so a handler that needs them must read the object with a separate call.

**How it shows up in a case study.** A CityPulse team receives an hourly sensor file in a bucket. A teammate proposes a cron job that lists the bucket every minute. The team wants the lowest cost and a delay of only a few seconds. The listing would run every minute whether or not a file had arrived, and the server would sit idle most of the day. The event notification runs the function only when a file lands. The reasoning starts from the constraints: idle time costs money, and polling adds delay.

:::trap Polling because it feels familiar
A listing loop looks simple, but it pays for idle time, adds up to a minute of delay and needs extra code to avoid handling a file twice.
:::

```quiz
Q: A CityPulse team stores hourly readings in a bucket. They want the lowest cost and a delay of only a few seconds. Which design fits?
- A cron job on a server that lists the bucket every minute
* An S3 event notification that invokes the function on each object-created event
- A loop inside the function that sleeps for five minutes, then lists the bucket
- A daily job that copies the whole bucket to a second bucket
WHY: The event starts the function as each object arrives, so nothing runs between uploads. The cron job pays for idle time and can be a minute late.

Q: A bucket notification has a prefix filter of raw/. Uploads to landing/ never start the function, although its code and permissions are correct. What is the most likely explanation?
- The function needs a cron schedule to pick up landing/ files
- The execution role needs write access to landing/
* The notification only matches keys that start with raw/, so landing/ objects never trigger it
- The function's timeout is too short for landing/ files
WHY: A prefix filter limits which keys send an event. If no event is sent, the function never starts, whatever its role or timeout.

Q: A handler reads event["Records"][0]["s3"]["object"]["key"] for each upload. Which statement about the event is correct?
* It gives the key and size of the object, but not the file contents
- It gives the full file contents, so the handler never calls S3
- It gives only the function's own name and memory size
- It gives a list of every object in the bucket
WHY: The event carries metadata. The tempting wrong answer, that it includes the contents, would make a separate read unnecessary.
```

### Pricing Lambda in GB-seconds and requests

**What it is.** Lambda bills compute in GB-seconds, which is memory in gigabytes multiplied by billed time in seconds. Each invocation also has a request charge. The console shows memory in megabytes, and a gigabyte is 1,024 megabytes, so divide by 1,024 first. A setting of 512 MB is 0.5 GB, so a 2-second run at 512 MB uses 1 GB-second:

```python
memory_mb = 512
seconds = 2
print(memory_mb / 1024 * seconds)
```

The output is `1.0`. The REPORT line rounds billed time up to the next whole millisecond. For a month, multiply the GB-seconds of one run by the number of runs, then add the request charge as a separate amount.

**How it shows up in a case study.** A finance analyst at CityPulse estimates the monthly compute of a fetch function. It runs 1,440 times a month, takes 1.5 seconds per run and is set to 1,024 MB. The first draft used 1,024 as gigabytes and came out 1,024 times too large. Converting first gives 1 GB, so the answer is 1,440 times 1.5 times 1, which is 2,160 GB-seconds. The request charge is added separately.

:::trap Forgetting the megabyte conversion
Using the megabyte figure as gigabytes inflates the answer by 1,024. At 1,024 MB, one second of run time is exactly one GB-second.
:::

```quiz
Q: A function runs 2,000 times a month, takes 0.5 seconds per run and is set to 256 MB. What is the monthly compute usage in GB-seconds?
- 1,000
- 2,000
* 250
- 128,000
WHY: 2,000 times 0.5 is 1,000 seconds, and 256 MB is 0.25 GB, so the answer is 250. The answer 1,000 leaves out the memory.

Q: Memory rises from 512 MB to 1,024 MB, and billed time falls from 800 ms to 500 ms. Prices and request counts do not change. What happens to compute cost per run?
* It rises, from 0.4 to 0.5 GB-seconds, even though each run is faster
- It falls, because the run is faster
- It is unchanged, because the request count is the same
- Memory is not part of the GB-second charge
WHY: 0.5 GB times 0.8 s is 0.4. 1 GB times 0.5 s is 0.5. The speed gain does not cancel the higher memory price.

Q: Team A adds the request charge to the compute charge. Team B uses only compute. For very short runs with many invocations, which statement is correct?
- Team B is right, because compute always dwarfs requests
- Both teams get the same answer for any workload
- Team A double-counts, because compute already includes requests
* Team B can underestimate the bill, because the request charge is added on top of compute
WHY: Requests and compute are separate charges. With many short runs, the request part can be a large share of the bill.
```

### Tuning memory against cost

**What it is.** Memory changes two things at once: the price per millisecond and the CPU share. A run that needs CPU may finish faster at a higher setting, so the total cost can fall, stay the same or rise. You cannot tell from the setting alone. Measure the same workload at two or more sizes, read the billed time from each REPORT line, and work out the GB-seconds:

```python
runs = [(128, 2000), (512, 500)]
for memory_mb, billed_ms in runs:
    gb_s = (memory_mb / 1024) * (billed_ms / 1000)
    print(memory_mb, round(gb_s, 3))
```

The output is `128 0.25` and `512 0.25`. Both settings cost the same here, so the memory size alone does not decide. Only the measured times, multiplied by memory, show the true cost.

**How it shows up in a case study.** A validation function is set to 128 MB and takes 900 ms. A manager proposes 1,024 MB, because bigger must be cheaper. An engineer measures 256 MB and finds 400 ms. At 128 MB the compute is 0.125 times 0.9, which is 0.1125 GB-seconds. At 256 MB it is 0.25 times 0.4, which is 0.1 GB-seconds. The middle setting is cheaper. Measurement, not the largest setting, gives the answer.

:::trap Assuming the largest setting is cheapest
A bigger setting pays off only when the run gets faster by more than the price rises. If 1,024 MB still takes 400 ms, it costs four times as much per run as 256 MB.
:::

```quiz
Q: A function runs in 1,200 ms at 128 MB and in 250 ms at 512 MB. A manager says 512 MB must cost more, because its price per millisecond is higher. What is the best reply?
- The manager is right, because the rate is higher, so the total is higher
* At 512 MB the cost is lower, 0.125 GB-seconds against 0.15, because the run finishes much sooner
- Both settings cost the same, because billing ignores memory
- The result depends only on the timeout
WHY: 0.125 times 1.2 is 0.15, and 0.5 times 0.25 is 0.125. The manager judges by the rate and ignores the time.

Q: A workload takes 400 ms at both 1,024 MB and 1,536 MB. Which action best reduces cost?
- Raise the memory to 2,048 MB to see whether the duration changes
- Remove the timeout so a run cannot be stopped
- Switch the function to a cron job to reduce the cost per run
* Keep 1,024 MB, because 1,536 MB costs more and did not shorten the run
WHY: With equal durations, cost rises with memory, so the lower setting wins. Raising memory further adds cost before any benefit is shown.

Q: A CPU-heavy job is measured at 256 MB and at 512 MB. At 512 MB the billed time falls by more than half. Which conclusion is best supported?
* At 512 MB the run is likely cheaper, because the time fell by more than the price doubled, but the REPORT lines should confirm it
- The 256 MB setting is always cheaper, because its memory price is lower
- The 512 MB setting is cheaper only with a longer timeout
- Memory has no effect on a CPU-heavy job
WHY: Doubling memory doubles the rate, but a time below half of its old value makes the product smaller. Durations still vary, so confirm with measurements.
```

### Lambda's time and memory limits

**What it is.** Some Lambda limits cannot be changed. One run lasts at most 15 minutes, which is 900 seconds, and the timeout you set must be at or below that. Memory can be set from 128 MB up to 10,240 MB. More memory gives more CPU, but it does not extend the time limit. A run that passes its timeout is stopped and reported as a failure. Work that needs longer must move to another service, such as a container task on ECS Fargate, or be split into smaller runs. A quick check makes the point:

```python
MAX_TIMEOUT_S = 15 * 60
job_seconds = 40 * 60
print(job_seconds <= MAX_TIMEOUT_S)
```

The output is `False`. A 40-minute job does not fit in one run, however much memory you give it.

**How it shows up in a case study.** A CityPulse team must process an export that takes about 40 minutes. A teammate suggests a 40-minute timeout and the maximum memory. The timeout cannot exceed 900 seconds, and memory does not change that. The job would fail at 15 minutes. The team can move the export to a container task, which is not bound by the 15-minute cap, or split it into monthly chunks that each finish well inside the limit.

:::trap Raising memory to fix a slow run
More memory may shorten a slow run, but the 15-minute ceiling stays. A 40-minute job still fails at 15.
:::

```quiz
Q: A nightly aggregation needs 35 minutes. The team sets the timeout to 15 minutes and the memory to 10,240 MB, but the run still stops at 15 minutes. What is the root cause?
- The memory is too high, so the CPU is throttled
- The timeout is in milliseconds, so 15 means 15 ms
* The job needs longer than the 15-minute maximum that one Lambda run can have
- The schedule fires too often and cuts runs short
WHY: The 15-minute limit applies to every run, and memory does not change it. High memory gives more CPU, not less.

Q: A tiny validator peaks at about 40 MB and finishes in 80 ms. The team wants the lowest memory setting that Lambda allows. Which should it use?
- 32 MB
* 128 MB
- 40 MB
- 64 MB
WHY: The lowest allowed setting is 128 MB, so smaller values cannot be chosen. 40 MB is above the peak but still below the minimum.

Q: A weekly report takes 14 minutes, but on slow days it takes 16 and the function fails. Which action fits Lambda's limits?
* Split the report into smaller parts that each finish well within 15 minutes, or move the whole job to a container task
- Raise the memory to 10,240 MB so the slow days finish
- Set the timeout to 20 minutes in the console
- Retry automatically until one attempt finishes
WHY: The limit is fixed, so the work must change or move. A 20-minute timeout is refused, and retries repeat the same failing work.
```

### Idempotent retries

**What it is.** An operation is idempotent when running it again leaves the same result as running it once. Retries make this important. Lambda may retry a failed asynchronous invocation, and an event source may deliver the same event twice. A simple way to make a write idempotent is to build the key from a value that stays the same for every attempt, such as the reading's own time. Here a dictionary stands in for a bucket:

```python
store = {}
def save(key, body):
    store[key] = body
save("raw/2027-01-12/fetch_0900.json", "reading A")
save("raw/2027-01-12/fetch_0900.json", "reading A")
print(len(store))
```

The output is `1`. The second save used the same key, so it replaced the object. With a random key, the output would be `2`.

**How it shows up in a case study.** A fetch function sometimes times out after writing an object, and Lambda retries it. The team asks whether the bucket will hold duplicates. If the key comes from the reading's fixed time, a retry in the same minute writes the same key and the bucket keeps one copy. A retry in a later minute writes a new key, so duplicates can still appear across minutes. Adding a random suffix would make every attempt a new object.

:::trap A random key for every attempt
A key with a random ID, or with the current second, turns every retry into a new object. Nothing in S3 flags the copies as duplicates.
:::

```quiz
Q: A function writes each reading under a key with a random ID. The first attempt wrote an object and then failed, and the retry wrote a second. What does the bucket hold, and what fixes it?
- One object, because S3 merges identical bodies
- Zero objects, because retries are never written
- One object, because Lambda deletes the earlier attempt
* Two objects for one reading, so the key should come from the reading's own time
WHY: A new random key makes a new object each time. A key from the reading's time gives the same name on each attempt, so a retry overwrites.

Q: A function builds its key from the date and the minute. A retry starts two minutes after the original run. What is the most accurate result?
- The retry overwrites the first object, because the key matches
* The retry writes a second object under a different key, so duplicates can appear across minutes
- The bucket refuses the retry, because the object already exists
- Lambda ignores the retry because it is late
WHY: A minute-based key changes every minute. S3 allows overwrites by default, so refusal is wrong. Use the reading's own timestamp or a deduplication step.

Q: A reviewer says a handler is idempotent. Which test best supports that claim?
- The handler finishes in under three seconds on its first run
- The logs show a single START line for each run
* Running the handler twice with the same event leaves the bucket as running it once would
- The handler creates its boto3 client at module level
WHY: Idempotency is about the final state after repeated runs. Speed and logs say nothing about repeat safety.
```

### The execution role and temporary credentials

**What it is.** An execution role is an IAM role that Lambda assumes when it runs your function. Lambda gives the code temporary credentials for that role, and they expire on their own. The role's trust policy names `lambda.amazonaws.com` as the service allowed to assume it. Its permissions policy lists what the function may do. The code needs no access key, and none is stored in the environment. A least-privilege statement for the fetch function might look like this:

```json
{
  "Effect": "Allow",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::citypulse-pipeline-s3/raw/openmeteo-aq/*"
}
```

It allows writes under `raw/openmeteo-aq/` in one bucket and nothing else. Writing logs needs a separate permission, which the standard basic execution policy provides.

**How it shows up in a case study.** A new team member wants quick results, so they create an access key for an administrator user and paste it into the environment variables. The key is long-lived, it can leak through a log or a commit, and it grants far more than the function needs. The better design is the execution role. If the function later gets an access denied error, the fix is to add the missing action to the role's policy.

:::trap Full access for convenience
Full access stops failures, but it removes least privilege. A bug can then delete or overwrite data the function never needed to touch.
:::

```quiz
Q: A function fails with access denied when it calls put_object. A colleague proposes an access key in the environment variables. What is the better fix?
* Add only the s3:PutObject permission for the needed prefix to the execution role's policy
- Store the key in the handler code and add the file to .gitignore
- Give the execution role full administrator access
- Turn off the bucket's encryption
WHY: A missing action belongs in the role's policy, kept as narrow as the job allows. Keys in code or environment variables can leak, and administrator access is far too broad.

Q: How does the running function get its AWS permissions?
- It reads an access key from a file uploaded with the code
- It uses the deploying user's credentials, stored permanently in the function
- It has no permissions, because permissions come only from the bucket
* Lambda assumes the execution role and gives the function temporary credentials for it
WHY: The execution role is assumed by Lambda, and its credentials are temporary. The deploying user's credentials are not used by the running code.

Q: A reviewer finds the fetch role allows all S3 actions on every bucket. Which change best follows least privilege?
- Keep the policy, and rotate the access key every month
* Replace it with s3:PutObject on the raw/openmeteo-aq/ prefix of the one bucket, plus log permissions
- Add a second role with the same access as a backup
- Attach the administrator policy so future features do not fail
WHY: Least privilege means the needed action on the needed resource. The role uses temporary credentials, so there is no key to rotate.
```

### Cold starts and warm starts

**What it is.** A cold start happens when Lambda has no ready environment for a request. It creates one, loads the code, starts the runtime and runs the module-level code, such as creating the boto3 client. A warm start reuses an environment that has already run, so module-level code does not run again. The first call pays the set-up time, which appears on the REPORT line as `Init Duration`. Keep slow set-up at module level and out of the handler:

```python
CONFIG = {"bucket": "citypulse-readings"}  # runs once per cold start
def handler(event, context):
    return CONFIG["bucket"]                # runs on every call
```

The first call in a new environment runs both lines. Later calls run only the handler body.

**How it shows up in a case study.** A team sees the first run of the morning take 1.8 seconds, and later runs take 0.3 seconds. A teammate suspects the bucket policy. The slow run follows a quiet period, and the gap matches the time to create a new environment. The REPORT line on that run shows an Init Duration, which confirms a cold start. A bucket policy would slow every call, not only the first one.

:::trap Blaming the cold start for every slow call
A slow call is a cold start only when the REPORT line shows an Init Duration or the timing matches a new environment. A slow handler is slow on every call.
:::

```quiz
Q: A function's slow runs take about 1.2 seconds longer, and they follow long idle periods. Their REPORT lines show an Init Duration. What is the most likely cause?
- A bucket policy that delays every upload
- The memory was set too high
- The timeout was reached on each slow run
* A cold start, because Lambda created a new environment and ran the module-level code
WHY: An Init Duration appears when Lambda creates a new environment. A bucket policy would slow every call, and a timeout would stop the run, not delay it.

Q: A team moves its S3 client creation from the handler to module level. What should it expect?
- Every call creates a new client, so calls become slower
* The client is created once per environment, so warm calls skip that set-up
- Memory usage drops to zero
- Cold starts are removed completely
WHY: Module-level code runs once per environment and is reused. Cold starts still happen, because each new environment pays the set-up time.

Q: A function is slow only on the first call of the day. Which change lowers the effect most safely?
- Set the timeout to 900 seconds so the first call can finish
- Increase memory to the maximum without measuring
* Trim the start-up work: import only what is needed and create clients once at module level, so the cold start is short
- Remove the logging so the first call is quicker
WHY: Start-up time shrinks when the set-up code is small and runs once per environment. A longer timeout changes the limit, not the speed.
```

### Limiting concurrency

**What it is.** Concurrency is the number of copies of a function running at the same moment. When every copy is busy, Lambda starts another, up to account and regional limits. Reserved concurrency caps one function at a fixed number of copies and sets that many aside from the account's pool. Calls beyond the cap are throttled. A synchronous caller gets an error. An asynchronous event, such as an S3 notification, is retried for a period and may be dropped if it keeps failing. For a burst:

```python
burst_events = 500
reserved = 50
print(min(burst_events, reserved), "copies run at once")
print(burst_events - reserved, "events are throttled and must wait or be retried")
```

The output shows 50 copies at once and 450 events waiting or retrying.

**How it shows up in a case study.** A CityPulse function calls a city API that fails under load. A burst of 500 uploads arrives in one second, and the team wants no more than 50 copies at once. The cap on parallel copies is reserved concurrency, set on the function. Memory and timeout change how long each run takes and what it costs, but they do not change how many copies start. The team also checks how the throttled events are retried.

:::trap Tuning memory to limit parallel runs
Memory changes run speed and cost, not the number of copies. It does nothing to protect a downstream API from a burst.
:::

```quiz
Q: A city API accepts only 10 requests at the same time. A sensor-alert function calls it. Which setting protects the API?
* Reserved concurrency of 10 on the function
- A memory size of 10 GB
- A timeout of 10 minutes
- An S3 lifecycle rule that expires objects after 10 days
WHY: Reserved concurrency caps how many copies of one function run at once. Memory and timeout change speed and cost, not the number of copies.

Q: A burst of 2,000 uploads arrives. Reserved concurrency is 100, and each run takes 3 seconds. Ignoring start-up, roughly how long does the burst take?
- 3 seconds
- 20 seconds
* 60 seconds
- 2,000 seconds
WHY: 2,000 runs in rounds of 100 is 20 rounds of 3 seconds, which is 60 seconds. The 3-second answer assumes everything runs at once.

Q: A function's reserved concurrency is set to 0. What happens to a new S3 upload that triggers it?
- The upload is processed, but more slowly
* The function is throttled, so the event does not run until the limit is raised, and retries may end in failure
- The function uses the full account capacity
- The bucket deletes the object
WHY: A reserved concurrency of 0 stops the function from running. Treating throttling as a delay is the tempting wrong answer.
```

### Batching records per invocation

**What it is.** Batching handles many items in one invocation instead of one invocation per item. Each invocation has a request charge and fixed overhead, such as start-up and connection time. Batches cut the invocation count, but a batch waits to fill, so items arrive later. For queues and streams, an event source mapping sets a batch size and a batching window, the longest wait before Lambda invokes with a partial batch. For a steady stream:

```python
readings_per_minute = 10000
batch_size = 100
print(readings_per_minute // batch_size)
```

The output is `100`. One invocation per reading would need 10,000. The batch must also finish within its time and memory limits.

**How it shows up in a case study.** A queue receives about 10,000 small readings a minute, and the first design runs once per reading. A cost review finds that request charges and overhead dominate. The team proposes batches of 100 with a window of a few seconds. Batching cuts the invocations by 100 times, and a short window keeps data fresh. Before choosing the size, the team measures how long a batch of 100 takes, because it must finish well inside its timeout.

:::trap Batching so far that data goes stale
A large batch with a long wait saves money but delivers readings late. A batch that reaches the timeout is retried whole.
:::

```quiz
Q: A source sends 6,000 small readings a minute, and each reading has its own run. Which change most reduces invocations while keeping data fresh?
- Keep one run per reading and raise the memory
- Process the readings once a day
* Batch the readings in groups of about 50, with a short batching window
- Disable the trigger and read the queue by hand
WHY: Groups of about 50 cut 6,000 invocations a minute to about 120. Daily processing is cheap but the data is up to a day old.

Q: Team A batches 1,000 readings per run, and each run takes 14 minutes against a 15-minute limit. What is its main risk?
- Lambda stops charging for runs longer than 10 minutes
* A slow day can push a run over 15 minutes, and then the whole batch is retried
- Batches cannot contain more than 10 readings
- Batching stops the REPORT line from being written
WHY: A batch needs headroom under its timeout. One slow day can multiply the work through retries. The other options are not Lambda behaviour.

Q: A reviewer says batching always saves money. Which statement is most accurate?
- Batching always saves money, because compute is free for batched runs
- Batching removes the need for a timeout
- Batching only matters for S3 events
* Batching usually reduces request charges, but larger batches add waiting and can reach the timeout, so the size must be measured
WHY: Fewer invocations usually cut request charges. The word "always" is the tempting wrong answer, because oversized batches cost more in delay and retries.
```

### Reading logs, REPORT lines and alarms

**What it is.** Lambda writes logs to CloudWatch Logs, in a log group named `/aws/lambda/` followed by the function name. Each run writes START, any `print` output, END and a REPORT line. The REPORT line gives Duration, Billed Duration, Memory Size and Max Memory Used. Billed Duration is the figure you pay for, rounded up to the next whole millisecond. Metrics such as `Errors` and `Throttles` are published per function, and an alarm watches a metric against a threshold:

```text
REPORT RequestId: 4a1b Duration: 311.50 ms Billed Duration: 312 ms Memory Size: 256 MB Max Memory Used: 88 MB
```

Here 311.50 ms of work is billed as 312 ms. The 88 MB used against a 256 MB setting hints that less memory might do, but measure before you change it.

**How it shows up in a case study.** A team's function has a few errors on Monday, but the team reads only the print output and sees nothing wrong. The monthly bill also looks high. Print output shows what the code did, not whether the run failed or what it cost. The REPORT lines show billed time and memory, and an alarm on Errors would have flagged the failures. The team adds that alarm and checks the billed time against its estimate.

:::trap Reading only the print output
Print lines show what the code did, not what it cost. Billed Duration appears only on the REPORT line, and a failed run may print nothing useful.
:::

```quiz
Q: A team wants the billed duration of each run. Which log line holds it?
- The START line with the request ID
- The END line with the request ID
- The line printed by the handler's print call
* The REPORT line, which shows Billed Duration
WHY: REPORT is the only line with billing figures. START and END mark run boundaries, and print output shows what the code did.

Q: An alarm watches Errors, with a threshold of one error in one five-minute period. Overnight a run fails and a retry succeeds. What is the best reading?
- The alarm cannot fire, because the retry succeeded
* The alarm fires, because the failed attempt is counted in the Errors metric for that period
- The alarm fires only when the schedule is stopped
- The alarm measures billed duration
WHY: Errors counts failed invocations, including the failed attempt before a successful retry. A successful retry does not erase the error.

Q: Which metric best signals that calls are being held back by the concurrency cap?
- Duration
- Errors
* Throttles
- ConcurrentExecutions
WHY: Throttles counts calls refused because a limit was reached. ConcurrentExecutions shows how many copies run, not the refused calls.
```

### What each function needs

This section teaches the Python ideas that the three functions use. Each idea comes with a small example that uses different data from the lab. Work through the examples yourself before you write the functions. Do not copy any of them into the lab's functions.

**Division, units and floats.** Dividing with `/` always gives a float, even when the result is a whole number. Floats are binary approximations, so some decimal values cannot be stored exactly:

```python
grams = 1500
kilograms = grams / 1000
print(kilograms)     # 1.5
print(0.1 + 0.2)     # 0.30000000000000004
```

The statement's `gb_seconds` is a raw value, not a rounded one, so do not round it. The rounding comes only in `lambda_cost`. If you compare floats in your own asserts, check for a small difference rather than exact equality, unless the value is a clean number such as 1.0.

**Constants and round.** Module-level names, such as `REQUEST_PRICE`, can be read from inside any function. Use the name, not a retyped copy of the number, so that the value stays the same as the starter file. The built-in `round` takes an optional number of places:

```python
RATE = 0.5                 # a module-level constant
hours = 3
print(hours * RATE)        # 1.5
print(round(4.125, 2))     # 4.12, because ties go to the even digit
print(round(2.675, 2))     # 2.67, because 2.675 is stored slightly below the half
```

`round` uses round-half-to-even on the stored binary value. The statement says `round(total, 2)`, so you use the built-in `round` on the final total, as the statement requires.

**Round once, at the end.** Rounding parts before you add them can change the total. This example uses an unrelated price of 1.005 twice:

```python
a = 1.005
b = 1.005
print(round(a, 2) + round(b, 2))   # 2.0
print(round(a + b, 2))             # 2.01
```

The first line rounds each part and gets 2.0. The second adds first and rounds once, and gets 2.01. The statement rounds only the total, so only the second pattern is correct for `lambda_cost`.

**Lists of dictionaries and dict.get.** `configs` is a list of dictionaries. Reading a key with square brackets fails loudly if the key is missing, which is useful when a key must exist. The `get` method returns a default instead of failing:

```python
book = {"title": "Atlas", "pages": 320}
print(book["pages"])           # 320
print(book.get("price", 0))    # 0, because the key is missing
```

For the lab, the statement's configuration keys are always present, so square brackets are the natural choice.

**Tuples and tie-breaks.** A tuple is compared item by item from the left. `min` over a list of tuples returns the smallest tuple, so a tie on the first item is settled by the second item:

```python
scores = [(72, "Ravi"), (85, "Asha"), (85, "Bilal")]
print(min(scores))                  # (72, 'Ravi')
print(min([(85, "Bilal"), (85, "Asha")]))   # (85, 'Asha')
```

This is how a tie-break can be written in one comparison. Put the value you want to minimise first, and the tie-break value second. Think about which item must be smaller when two values are equal, and make sure the tuple puts that item in the right place.

**Returning the right type.** `isinstance` checks the type of a value. `bool` is a subclass of `int`, so a boolean passes an integer check, and that can surprise you:

```python
print(isinstance(7, int))        # True
print(isinstance(True, int))     # True, because bool is a subclass of int
print(isinstance(7.0, int))      # False
print(7.0 == 7)                  # True, but the two types differ
```

The last line matters for `cheapest_memory`. The value `7.0` equals `7`, but it is a float. If the statement asks for an int, return the value as it was given, and do not convert it to a float along the way.

**Slicing and not changing the input.** A slice makes a new list. The `sort` method changes a list in place, while `sorted` returns a new one:

```python
letters = ["a", "b", "c", "d"]
print(letters[1:3])            # ['b', 'c']
copy = list(letters)
copy.sort(reverse=True)
print(letters)                 # ['a', 'b', 'c', 'd'], unchanged
```

The statement does not require the input list to stay the same. It is still good practice, and it is easy to check with your own assert.

### The rules people miss

The table below lists the rules from the statement, the mistake a careless solution makes, and how to check your own. Each row can become one assert in your own test file.

| Rule in the statement | What a careless solution does | How to check yours |
|---|---|---|
| gb_seconds uses memory_mb / 1024 | Uses the megabyte value as if it were gigabytes, so the answer is 1,024 times too large | One invocation at 1,024 MB for 1,000 ms must give exactly 1.0 |
| gb_seconds uses duration_ms / 1000 | Forgets the division, or divides by 1,000 twice | The same case gives 1.0, not 1000.0 or 0.001 |
| gb_seconds scales with invocations | Returns the value for one run instead of all of them | Double the invocations and check that the result doubles |
| lambda_cost adds the request cost and the compute cost | Returns only the compute part, or only the request part | Compare the total with a sum you work out on paper |
| Use REQUEST_PRICE and GBS_PRICE | Retypes the prices with fewer digits, which can change the last cent | Read the prices from the module names, and check that changing a constant changes the result |
| round(total, 2) is applied to the total | Rounds the GB-seconds or each part first, which can move the total by a cent | Compare the rounded result with a version that rounds only the total |
| cheapest_memory compares the lowest lambda_cost | Compares unrounded totals, or compares durations or memory sizes instead | Print each configuration's cost next to its memory and find the lowest by eye |

| The names and signatures in the starter file | Renames a parameter or moves a constant into the function | Keep the starter file's names and order exactly as they are |

These are not rules in the statement, so do not invent a behaviour for them. Your own asserts can still check that the input list is unchanged, because that is good practice, but you should not treat any of these cases as a graded rule. ### Worked twin problem

The twin problem is a different domain that needs the same skills: integer and decimal arithmetic, rounding at the end, a tie-break and a function that chooses the best option from a list.

**The twin problem.** A bike-share company bills each trip in 15-minute blocks. A block that has started counts in full. So 1 minute and 15 minutes are each one block, and 16 minutes is two blocks. Every trip also pays a base fee. The fare is the base fee plus the number of blocks times the block price, rounded half up to the nearest cent at the end. Write three functions.

- `billable_blocks(minutes)` returns the number of blocks as an int.
- `trip_fare(minutes, base_fee, block_price)` returns the fare as a float with two decimal places.
- `cheapest_plan(minutes, plans)` takes a list of dictionaries with the keys `name`, `base_fee` and `block_price`. It returns the name of the plan with the lowest fare. On a tie, it returns the name that comes first alphabetically. If `plans` is empty, it raises `ValueError`. It must not change the list.

Here is the full solution with its tests. The block runs when the book is built, and it must pass.

```python test
from decimal import Decimal, ROUND_HALF_UP


def billable_blocks(minutes):
    return (minutes + 14) // 15


def trip_fare(minutes, base_fee, block_price):
    blocks = billable_blocks(minutes)
    total = Decimal(str(base_fee)) + blocks * Decimal(str(block_price))
    return float(total.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP))


def cheapest_plan(minutes, plans):
    if not plans:
        raise ValueError("no plans given")
    best = None
    for plan in plans:
        fare = trip_fare(minutes, plan["base_fee"], plan["block_price"])
        candidate = (fare, plan["name"])
        if best is None or candidate < best:
            best = candidate
    return best[1]


plans = [
    {"name": "Basic", "base_fee": 0.50, "block_price": 0.30},
    {"name": "Plus", "base_fee": 0.00, "block_price": 0.40},
    {"name": "Ride", "base_fee": 1.00, "block_price": 0.10},
]
snapshot = [dict(p) for p in plans]

# billable_blocks: a started block counts in full
assert billable_blocks(0) == 0
assert billable_blocks(1) == 1
assert billable_blocks(15) == 1
assert billable_blocks(16) == 2
assert billable_blocks(40) == 3

# trip_fare: base fee plus blocks, rounded half up at the end
assert trip_fare(40, 0.50, 0.30) == 1.40
assert trip_fare(0, 0.50, 0.30) == 0.50
assert trip_fare(1, 0.00, 0.005) == 0.01
assert isinstance(trip_fare(40, 0.50, 0.30), float)

# cheapest_plan: the lowest fare wins
assert cheapest_plan(40, plans) == "Plus"
assert cheapest_plan(0, plans) == "Plus"
assert cheapest_plan(15, plans) == "Plus"

# the order of the list does not change the answer
assert cheapest_plan(40, plans[::-1]) == "Plus"

# a tie on fare goes to the name that comes first alphabetically
assert cheapest_plan(40, [
    {"name": "Zed", "base_fee": 0.00, "block_price": 0.40},
    {"name": "Ann", "base_fee": 0.00, "block_price": 0.40},
]) == "Ann"

# an empty list raises ValueError
try:
    cheapest_plan(40, [])
except ValueError:
    pass
else:
    raise AssertionError("expected ValueError for an empty list")

# the input list is not changed
assert plans == snapshot
```

The block prints nothing when it passes. A failed assert stops the build with an error that names the line.

Explanation, line by line:

- `from decimal import Decimal, ROUND_HALF_UP` brings in the exact decimal type and the rounding mode for money.
- In `billable_blocks`, `(minutes + 14) // 15` uses integer division, which always rounds down. Adding 14 means any remainder from 1 to 14 pushes the result up by one. Zero minutes give 0, 1 minute gives 1, 15 minutes gives 29 // 15, which is 1, and 16 minutes gives 30 // 15, which is 2.
- In `trip_fare`, `Decimal(str(base_fee))` converts the value through its text form, so 0.50 stays exactly 0.50. Multiplying an int by a `Decimal` works, so `blocks * Decimal(...)` is the block charge.
- `total.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)` rounds once, at the end, to two places, with halves going up. The `float(...)` call converts the result back for the return value.
- In `cheapest_plan`, the empty-list check comes first, so the function never looks for a minimum of nothing. `best` starts as `None`.
- Each plan gives a `candidate` tuple, with the fare first and the name second. The `if` line takes the first candidate, and then any candidate that is smaller. Tuples compare the fare first, and they compare names only when the fares are equal.
- `return best[1]` returns the name from the best tuple.
- The asserts check each rule in turn: the block counts, the fare and its rounding, the lowest fare, the order of the list, the alphabetical tie-break, the empty list, and the unchanged input.
- The `try` and `except` block checks that the error is raised. If no error is raised, the `else` branch fails the build on purpose.

```python test
def fine_pence(days_late, rate_pence, cap_pence):
    if days_late <= 0:
        return 0
    return min(days_late * rate_pence, cap_pence)


def total_fines(loans, rate_pence, cap_pence):
    total = 0
    for loan in loans:
        total += fine_pence(loan["days_late"], rate_pence, cap_pence)
    return total


def most_overdue(loans):
    if not loans:
        raise ValueError("no loans given")
    best = None
    for loan in loans:
        key = (-loan["days_late"], loan["title"])
        if best is None or key < best:
            best = key
    return best[1]


loans = [
    {"title": "Dune", "days_late": 3},
    {"title": "Emma", "days_late": 0},
    {"title": "Ajax", "days_late": 12},
    {"title": "Zoo", "days_late": 12},
]
snapshot = [dict(x) for x in loans]

assert fine_pence(3, 25, 500) == 75
```
