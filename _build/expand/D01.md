## What the quiz tests

The Day Quiz has ten case-study multiple-choice questions, one for each topic listed in this section, in the same order. Each question gives you a short scenario from a CityPulse squad and then asks what the team should do, or what a command will show. The pass mark is 70%. Your skill score keeps the result of your first attempt, so a second attempt helps you learn but does not change the score that counts.

Use the same method on every case-study question. First, read the last line of the question, because it tells you what is being asked: the cause, the next command, the safest action or the reason. Second, underline the facts in the scenario that matter, such as whether a file is tracked, whether a secret has reached GitHub, or whether a teammate has already pulled. Third, eliminate options that are true in general but do not fix this scenario. Many wrong options are correct statements about Git that answer a different question. Fourth, watch the words "most", "first" and "best". "First" often means that one step must come before the others, such as revoking a secret before you clean history. "Best" means the option that solves the stated problem with the least damage.

Each topic below has a trap box. The trap is the tempting wrong answer, and it is usually a plausible sentence about Git. Once you can say why the trap fails, the real question becomes much easier to answer.

### Reading the status codes

**What it is.** `git status --short` prints one line for each file that differs from the last commit, or that Git cannot yet track. Each line starts with two characters, then a space, then the path. The first character describes the staging area, which Git also calls the index. The second character describes the working tree, which is the set of files you can see and edit. A space means that nothing has changed in that place.

```text
$ git status --short
 M src/app.py
M  data/readings.csv
MM ingest.py
?? notes.txt
!! debug.log
```

Read each line as a pair. ` M` means the file is modified in the working tree and not staged. `M ` means a change is staged and the file has not been edited since. `MM` means a change was staged, and then the file was edited again, so the next commit holds the staged version and the working tree holds a newer one. `??` means Git can see the file but does not track it. `!!` means an ignore rule matches the file. The `!!` code appears only when you add `--ignored`.

**How it shows up in a case study.** Ravi ran `git add src/parser.py`, kept editing, and then ran `git commit -m "Add readings parser"`. He now says his last edits are missing from the commit, and he remembers that his status showed `MM src/parser.py` just before committing. The first letter was a staged change, so the commit holds the version from the moment `git add` ran. The second letter showed the later edit. The right decision is to check `git status`, stage the newer edit with `git add src/parser.py` and commit again. Forcing a push does not help, because the commit never contained the newer lines.

:::trap Reading ?? as added
`??` means untracked. A file that has been added with `git add` shows `A` in the first column. A file that never reached `git add` still shows `??`.
:::

```quiz
Q: Your teammate shows you git status --short with the line MM ingest.py. She is sure she changed the parser, but the commit she made an hour ago does not contain the newest lines. Which statement explains the two letters?
- The first M means the file is untracked, and the second M means it is ignored
* The first M is a change staged for the next commit, and the second M is a newer edit that is not staged
- Both letters mean the file was pushed and then edited on GitHub
- The file is staged twice, so the commit will include both copies
WHY: The first column describes the staging area and the second describes the working tree. The commit holds the staged version, so the newer edit is missing. The tempting wrong answer treats MM as a double stage, which Git does not do.

Q: A new file report.txt was created today, and nobody has run any Git command on it yet. The squad lead runs git status --short and wants to know which line the file should show before anyone adds it. Which line is correct?
- A report.txt
- !! report.txt
- M report.txt
* ?? report.txt
WHY: ?? means Git can see the file but is not tracking it. A would appear only after git add, and !! would require an ignore rule that matches the file.

Q: The squad adds *.log to .gitignore and then runs git status --ignored --short. A file debug.log in the project root was never committed. Which line should appear for it?
* !! debug.log
- ?? debug.log
- A  debug.log
- M  debug.log
WHY: !! marks a file that an ignore rule matches. Without --ignored the file would be hidden entirely. The tempting wrong answer is ??, but an ignored file is not an untracked file that Git is waiting to add.
```

### Untracking a file that is already committed

**What it is.** A `.gitignore` rule only affects files that Git does not yet track. Git starts tracking a file when you add it and commit it. If you later add the file's name to `.gitignore`, Git keeps tracking it, and every change to it still shows as `M`. To stop tracking, you remove the file from the index with `git rm --cached`. That command keeps the file on your disk. You then commit the removal so that the change reaches the repository.

```bash
git rm --cached .env
git commit -m "Stop tracking .env"
git status --ignored --short
```

The first command prints `rm '.env'` and leaves the file on your disk. The commit records the removal. The status command then shows `!! .env`, because the file exists and the rule now ignores it. Without `--cached`, `git rm` would also delete the file from your disk. Past commits still hold the old content, so removing the file from the latest version does not remove it from history.

**How it shows up in a case study.** Priya's team committed `config/local.env` by mistake two days ago. On Tuesday someone added the same name to `.gitignore`, but every edit to the file still appears as `M` in `git status`. The team reads the symptom and sees that the rule was added after the file was already tracked. The correct sequence is `git rm --cached config/local.env`, a commit and a push. The disk copy stays, so nobody loses local settings. The team also checks whether the stored value was a real secret, because the old commits still hold it.

:::trap Believing the ignore rule erased history
Adding a rule does not touch past commits or files that are already tracked. Only `git rm --cached` followed by a commit stops the tracking. A plain `git rm` also deletes the file from disk.
:::

```quiz
Q: A squad member added .env to .gitignore last week, but git status --short still shows M .env after each edit. Which explanation is correct?
- The ignore rule is broken and must be reinstalled
- GitHub holds a copy of .env that overrides the local rule
* The file was already tracked when the rule was added, so the rule does not apply to it
- Ignore rules only take effect after the next git push
WHY: An ignore rule never applies to a file that is already tracked. The tempting wrong answer blames the rule itself, but the rule is working as designed for untracked files.

Q: The team wants to stop tracking secrets/api.key, but the file must stay on each laptop. Which command removes it from the index and keeps it on disk?
- git rm secrets/api.key
* git rm --cached secrets/api.key
- git clean -f secrets/api.key
- git reset --hard secrets/api.key
WHY: The --cached flag removes the file from the index and leaves the disk copy alone. git rm alone deletes the disk copy too, and git clean and git reset --hard both discard local content.

Q: After git rm --cached .env and a commit, a new teammate clones the repository. Which statement describes what the teammate can see?
- .env in the latest files, because the ignore rule restores it automatically
- .env in the latest files, because the removal rewrote every older commit
- .env in the latest files and in every older commit, because the commit kept it
* No .env in the latest files, but older commits still contain the old content
WHY: Removing a file in a new commit changes only the latest snapshot. Older commits still hold the value, which is why a real secret needs revoking as well.
```

### Recording a commit

**What it is.** A commit records the contents of the staging area as one snapshot. It stores the author name and email from your Git settings, a timestamp, a message and a hash. `git commit -m "message"` gives the message on the command line, so Git does not open an editor. A commit exists only on your computer until you push it. The flag `-a` stages changes to files that Git already tracks before it commits. It never adds a new file.

```term
$ git config user.name
Asha Rao
$ git add ingest.py
$ git commit -m "Drop negative readings"
[main 9c01e4d] Drop negative readings
 1 file changed, 2 insertions(+)
```

The first command prints the name that Git will stamp on your commits. The `git add` line stages `ingest.py`. The commit line prints the branch and the short hash. Nothing has reached GitHub at this point, because no push has run.

**How it shows up in a case study.** Ana's squad lead says the sprint's work is safe, because "everyone committed". The lead looks at the history on her own laptop and sees the commits, but the team's GitHub page shows none of them. The commits are local until someone runs `git push`. Before pushing, the team checks `git log --format='%h %an %s' -3`, to make sure that the author names are correct, since the names are stamped at commit time and a push does not change them.

:::trap Committing means sending
A commit is saved on your computer. Your teammates see it only after `git push`. A commit made with the wrong identity keeps the wrong name even after you push, so check `git config user.name` before you commit.
:::

```quiz
Q: Your squad believes the feature is saved for the whole team, because you ran git commit -m "Add export" an hour ago. The lead can see nothing on GitHub. Which explanation fits the evidence?
* The commit is local, and it reaches GitHub only after git push
- The commit was pushed automatically when the message was written
- The commit is on GitHub but hidden until the next pull
- The commit reached GitHub, but the lead is looking at an old cached page
WHY: git commit saves the snapshot on your machine only. The tempting wrong answer assumes that committing and sending are one step, but they are two separate commands.

Q: You created a brand-new file parser.py that you never added, and then you ran git commit -am "Add parser" with changes to a tracked file. Which files are in the commit?
- parser.py and all the other changes in the working tree
- Only the new file parser.py
* The changes to files Git already tracks, but not parser.py
- Nothing, because git commit -am always fails when a file is new
WHY: The -a flag stages changes to tracked files only. A new file needs git add before it can be committed. The tempting wrong answer assumes that -a covers every file in the folder.

Q: Which command records a commit with the message "Add export" without opening an editor?
- git commit --edit
* git commit -m "Add export"
- git commit --amend only
- git commit -S
WHY: -m supplies the message on the command line, so no editor opens. --edit forces an editor, --amend rewrites the last commit, and -S signs the commit but says nothing about the message.
```

### Proving who you are with SSH keys

**What it is.** SSH authentication uses two files. The private key stays on your computer and must never be shared. The public key ends in `.pub` and can be given to GitHub. When you push over SSH, GitHub sends a challenge, and your computer answers it using the private key. GitHub checks the answer against the public key on your account. Your password is never sent in this exchange.

```term
$ ssh-keygen -t ed25519 -C "you@example.com"
$ cat ~/.ssh/id_ed25519.pub
ssh-ed25519 AAAAC3...example you@example.com
$ ssh -T git@github.com
Hi your-username! You've successfully authenticated, but GitHub does not provide shell access.
```

The `-t ed25519` flag chooses the algorithm. The `cat` command prints the public key, which is the only line you copy into GitHub. The last command tests the connection. The address in a push that starts with `git@github.com:` is an SSH address, so Git uses the key. A message from GitHub that includes your username shows that the key works.

**How it shows up in a case study.** Joel has a new laptop. He copies his teammate's `id_ed25519` file "to save time", and then his push fails with `Permission denied (publickey)`. The team sees two problems. The key on Joel's laptop is his teammate's private key, so the teammate's identity is now in two places. The public key on GitHub belongs to the teammate's account, so it cannot prove Joel's identity. The right fix is a new key pair on Joel's laptop, with only its `.pub` line added to Joel's own GitHub account.

:::trap Uploading the private key
GitHub needs only the `.pub` file. A private key file, without `.pub`, is the secret that proves your identity. Anyone who holds it can push as you.
:::

```quiz
Q: A developer sends the file id_ed25519, which has no .pub ending, to a shared chat channel so that a teammate can "check the key". Which risk is the most serious?
- The chat stores the account password in plain text
- Only the repository name is exposed to the teammate
- GitHub asks the developer to change the username
* Anyone who gets that file can act as the developer, so the key must be replaced
WHY: The file without .pub is the private key. Possession of it is the proof of identity, so the key must be replaced. The tempting wrong answer is about the password, but SSH never sends the password.

Q: You run git push over SSH and it succeeds without a password prompt. Which fact does GitHub's check establish?
* That your computer holds the private key that matches a public key on your account
- That your password is correct
- That the repository is private
- That two-factor authentication is switched on
WHY: The challenge proves possession of the private key. It says nothing about the password, the repository's visibility or 2FA. The tempting wrong answer is the password.

Q: A teammate says, "SSH is set up, so my password does not matter when I push." Which statement is accurate?
- Pushes fall back to the password whenever the key is wrong
- The password is checked as well, but a wrong password only slows the push
* Pushes over SSH do not send the password, so the password is not what GitHub checks
- SSH keys are used only for downloads, and pushing always needs the password
WHY: Over SSH, the proof is the key, and the password is not part of that exchange. The tempting wrong answer assumes a password fallback that does not exist for SSH pushes.
```

### Signed commits

**What it is.** The author name on a commit is a label. Anyone can set it with `git config user.name`, so a name alone does not prove who made a commit. A signature is extra data that proves the commit was made by someone who holds a particular private key. You sign a commit with `git commit -S` once a signing key is configured in Git. GitHub shows a "Verified" badge when the signature matches a key registered on the account. A signature proves who signed the commit. It does not prove that the code works or that the message is accurate.

```term
$ git commit -S -m "Add station filter"
[main 7d3b210] Add station filter
$ git log --show-signature -1
```

The `-S` flag asks Git to sign the new commit. The `--show-signature` flag on `git log` prints the signature check for the latest commit, so you can see whether the signature is valid.

**How it shows up in a case study.** The course's CHARTER check counts distinct authors with `git log`. Sam has set `user.name` to "Ravi Kumar" on his own laptop, and his commits now show Ravi's name. The team notices that Ravi's commits carry a Verified badge on GitHub, while Sam's do not. The correct conclusion is that the name alone is not evidence. The team asks Sam to correct his identity, to sign future commits and to check his own signature line in the CHARTER.

:::trap A verified commit is a correct commit
"Verified" means the signature matches a registered key. A verified commit can still contain a bug, a leaked password or a wrong message.
:::

```quiz
Q: The CHARTER check counts authors with git log. One commit shows the name Ravi Kumar, but the commit is not signed, and the commit's author email is not Ravi's. What can you conclude?
- The commit must have been made by Ravi, because the name is correct
* The name is only a label, so the commit could have been made by anyone who set that name
- Git has already checked the name against GitHub and found it correct
- The commit is not valid until someone signs it
WHY: An author name is set on the local machine and is not checked. The tempting wrong answer assumes Git verifies the name, which it does not.

Q: A commit shows a Verified badge on GitHub. A reviewer asks whether the feature works. Which answer is best?
- Yes, because the signature proves that the tests passed
- Yes, because GitHub runs every test on verified commits
- Only if the commit message says that the tests passed
* The signature shows who made the commit, not whether the code is correct, so tests and review still decide
WHY: A signature answers a question about authorship. Tests and review answer questions about correctness. The tempting wrong answer mixes the two.

Q: Which statement describes what git commit -S adds to a commit?
* A signature made with a configured signing key, so the commit can be checked against that key
- A second copy of the commit stored on GitHub
- A check that the commit message is written in English
- A rule that stops anyone else from pushing to the branch
WHY: The -S flag adds a signature. It does not copy the commit, check the message or change branch permissions. The tempting wrong answer confuses signing with protection.
```

### Responding to a leaked secret

**What it is.** A secret is any value that proves identity or grants access: a password, an API key, a token or a private key. Once a secret reaches a repository, treat it as known. Automated scanners search public code for keys, and any clone or fork already holds a copy of the value. The response has a fixed order. First, revoke or rotate the secret in the service that issued it, so the old value stops working. Second, remove the file from the project and stop tracking it, as in the untracking topic above. Third, decide with your team whether to rewrite the history, which needs a force push and affects everyone who has cloned the repository.

```text
1. Revoke or rotate the key in the service that issued it.
2. Remove the file with git rm --cached, add it to .gitignore and commit.
3. Ask the team whether to rewrite history.
```

**How it shows up in a case study.** Amal pushes a commit that contains `API_KEY=...` in `config.py`. Ten minutes later the squad lead wants to run a history rewrite and force push, because the commit looks untidy. You are asked for the first step. The secret is already in the repository, and copies may exist, so the first action is to revoke the key in the provider's dashboard and issue a new one. The history rewrite can follow once the team agrees. It does not make the old key stop working, and it does not reach copies that were already made.

:::trap Cleaning history first
Rewriting history leaves the secret valid. Anyone who already cloned or forked the repository still has the value. Revoke it first.
:::

```quiz
Q: A developer's push included a cloud access key 15 minutes ago. The repository is private, but three teammates have already cloned it. What should the developer do first?
- Force-push a rewritten history that removes the key
- Delete the repository and create a new one with the same name
* Revoke the key in the issuing service and create a replacement
- Add the file to .gitignore and wait for the next push
WHY: Revoking stops misuse at once, even though copies exist. The tempting wrong answer starts with the history, which does not reach the clones that already hold the key.

Q: After the key is revoked, the team asks whether they still need to remove the file from the project. Which answer is correct?
- No, revoking the key also removes the file from history
* Yes, remove the file from the current project so it is not committed again, and decide about history as a separate question
- No, the ignore rule removes the file from every commit
- Yes, but the only way is to delete the whole repository
WHY: Revoking makes the value useless, and removing the file stops it being committed again. Neither step rewrites history by itself. The tempting wrong answer treats the ignore rule as a history cleaner.

Q: Which step must the team decide together, rather than the developer deciding alone?
- Revoking the leaked key
- Adding the file to .gitignore
- Running git rm --cached on the file
* Rewriting history with a force push that affects every clone
WHY: A force push changes the shared history, so everyone who cloned must update. That is a team decision. The other three steps are local and safe to take at once.
```

### Pulling changes from GitHub

**What it is.** `git pull` fetches commits from the remote and then combines them with your current branch. By default it merges them. If you have configured it to rebase, it places your commits on top instead. The fetch step downloads new commits and updates the remote-tracking name, such as `origin/main`. A conflict happens when the same lines were changed in two different ways. Git stops and marks the file, and you must edit it, stage it and commit before the work can continue.

```term
$ git pull
remote: Enumerating objects: 5, done.
Updating 2a661c5..d4e8f10
Fast-forward
 src/ingest.py | 3 ++-
```

`git pull` never sends your own commits. That is the job of `git push`, which runs in the opposite direction.

**How it shows up in a case study.** Two squad members edit `src/ingest.py` on the same afternoon. Lina pushes first. Omar runs `git pull` and sees a conflict in the same function, because both of them changed the same line. The team asks whether Omar's pull uploaded his changes. It did not. The pull brought Lina's commits down and then stopped at the conflict. Omar edits the file, keeps the correct lines, runs `git add src/ingest.py` and commits. Only then does `git push` send the result to GitHub.

:::trap Pull as an upload
`git pull` brings commits down and `git push` sends them up. A pull that stops with a conflict sends nothing until the merge is committed and pushed.
:::

```quiz
Q: A teammate asks you to "pull your work up to GitHub" before the deadline. Which command actually uploads your commits to the remote?
* git push
- git pull
- git fetch
- git clone
WHY: Only git push sends commits to the remote. git pull and git fetch bring commits down, and git clone makes a new copy on your computer. The tempting wrong answer is git pull, because both commands talk to GitHub.

Q: You run git pull and it stops with a conflict in notes.md. Which statement is accurate?
- The pull has already uploaded your changes to GitHub
- Git has deleted your local changes and replaced them with the remote copy
* The two versions of the same lines must be resolved, then the file added and committed, before you push
- The conflict means the remote repository is broken and must be recreated
WHY: A conflict is a merge that needs a human decision. Nothing is uploaded until the merge is complete. The tempting wrong answer says the pull has already sent your work.

Q: What two steps does git pull combine by default?
- A push followed by a tag
* A fetch of remote commits followed by a merge into your current branch
- A clone followed by a checkout
- A stash followed by a reset
WHY: By default, git pull is a fetch followed by a merge. Stash, reset, clone and tag are different commands with different jobs.
```

### Tagging a release

**What it is.** A tag is a name attached to one commit. A tag does not move when new commits arrive, so it marks a fixed point such as a release. An annotated tag, created with `git tag -a`, stores a message and the name of the person who made it. A lightweight tag stores only the name. Git does not push tags with a normal `git push`, so you send one tag with a command that names it.

```term
$ git tag -a v1.0 -m "First release"
$ git push origin v1.0
 * [new tag]         v1.0 -> v1.0
```

The `-a` flag makes the tag annotated, and `-m` supplies its message. The push command sends that one tag to `origin`. Later commits on `main` leave `v1.0` pointing at the commit that you tagged.

**How it shows up in a case study.** The squad wants the Week 6 version of the ingest pipeline to be easy to find for the trainer. Chidi suggests creating a branch named `release-w6` and leaving it alone. Two days later the branch shows three commits from the next sprint, because people kept working on it. The team replaces the branch with an annotated tag, `v0.6`, on the correct commit. The tag stays on that commit, so the trainer can check out exactly what was released.

:::trap A branch as a release marker
A branch moves whenever someone commits to it. A tag stays on one commit, so use a tag to mark a release.
:::

```quiz
Q: Which command creates an annotated tag named v0.6 with a message for the current commit?
- git branch v0.6 -m "Release"
- git commit --tag v0.6
- git stash v0.6
* git tag -a v0.6 -m "Release"
WHY: git tag -a creates an annotated tag with a message. The other three commands either create a branch, try to commit with a tag option that does not exist, or stash changes.

Q: A squad keeps a release marker as a branch named release-w6. A week later, the branch has three new commits that were not part of the release. What is the explanation?
* A branch moves when new commits are made on it, so it does not mark a fixed point
- Branches are locked automatically after a release
- The commits were copied into the branch by git tag
- The branch was deleted and recreated by GitHub
WHY: A branch is a pointer that moves with each new commit. The tempting wrong answer is that a branch is locked after a release, which Git never does by itself.

Q: Which statement about tags is true?
- Tags are pushed automatically with every git push
- An annotated tag stores only the commit hash and nothing else
* A tag names one commit, and it stays on that commit when new commits arrive
- A tag can be moved by git commit
WHY: A tag names one commit and stays put. Tags are not pushed by default, and git commit never moves them. The tempting wrong answer says that tags are pushed automatically.
```

### What the staging area holds

**What it is.** The staging area, also called the index, holds a copy of each file's content at the moment you run `git add`. It is not a link to the file on disk. When you edit the file again, the working tree changes, but the staging area keeps the older copy until you run `git add` again. `git commit` records exactly what is in the staging area. `git diff` compares the working tree with the staging area, and `git diff --staged` compares the staging area with the last commit.

```term
$ echo "v1" > report.txt
$ git add report.txt
$ echo "v2" >> report.txt
$ git status --short
AM report.txt
$ git commit -m "Add report"
```

The first `echo` writes `v1` into the file, and `git add` copies that content into the staging area. The second `echo` appends `v2` to the file on disk. The status shows `AM`, because the file is new in the staging area (`A`) and the working copy now differs from the staged copy (`M`). For a file that was already tracked, the same steps would show `MM`. The commit records only the staged copy, which holds `v1`.

**How it shows up in a case study.** Priya fixes a bug in `parser.py`, runs `git add parser.py`, and then corrects a typo in a comment. Her teammate asks why the commit would lack the typo fix. Before committing, the status shows `MM`. The answer is that the commit would hold the version staged before the typo fix. Priya runs `git add parser.py` again, which updates the staging area, and then commits. She does not need to revert anything.

:::trap Expecting the newest edit in the commit
Editing a file after `git add` does not update the staging area. The commit holds the staged copy until you add the file again.
:::

```quiz
Q: You ran git add config.yaml, then changed one value in config.yaml, and then ran git commit -m "Update config". Which version of the file does the commit record?
- The edited version with the new value
* The version as it was when git add ran, without the later change
- Both versions, as two separate commits
- Neither, because the file is no longer staged after an edit
WHY: The staging area keeps the content from the moment of git add. The tempting wrong answer is the newest version, which stays in the working tree until you add it again.

Q: Your git status --short shows MM for tests/test_ingest.py. Which command shows the content that the next commit will record?
- git diff
- git log --stat
- git status --ignored
* git diff --staged
WHY: git diff --staged compares the staging area with the last commit, which is exactly what the next commit records. Plain git diff compares the working tree with the staging area, so it shows the later edit instead.

Q: A squad member says, "I added the file an hour ago, so my latest edits are safe in the commit." Which statement corrects this?
* The commit holds the content from the last git add, so the latest edits need another git add
- The staging area updates each time the file is saved on disk
- Commits automatically include every edit made to tracked files
- The later edits are merged into the commit by git push
WHY: Only git add updates what the next commit will hold. Saving a file does not update the staging area, and pushing sends commits without changing them.
```

### Two-factor authentication on GitHub

**What it is.** Two-factor authentication (2FA) asks for a second proof at login, in addition to your password. The usual second proof is a six-digit code from an authenticator app on your phone. The app creates a new code every 30 seconds, and it does not connect to GitHub. You read the code and type it into the login page. Recovery codes are one-time backup codes that you download when you turn 2FA on, so that you can sign in if you lose the phone. Codes sent by text message are a weaker second factor than an app.

```term
$ gh api user --jq '.two_factor_authentication'
true
```

The value `true` means that 2FA is switched on for the account. If the value is `false`, go back to your security settings before you continue.

**How it shows up in a case study.** A trainer checks the organisation and finds one member with 2FA disabled. Hadi's password appeared in a website breach last week. The team asks whether an attacker can now push to the squad repository. With 2FA on, the attacker still needs the current code from Hadi's phone, so the login stops at the second step. The trainer asks Hadi to enable an authenticator app, save his recovery codes and change his password.

:::trap Treating SMS and an app as equal
A text-message code is easier to intercept than a code from an app. The course asks you to use an authenticator app, and to download recovery codes before you log out.
:::

```quiz
Q: A member's password has leaked, and the organisation enforces 2FA. The member's phone is still in their hand. What must an attacker still have to log in?
- The organisation's invitation link
- The member's SSH public key only
* The current code from the member's authenticator app
- A copy of the repository's history
WHY: 2FA asks for a second proof that the password does not supply. The tempting wrong answer is the public key, which is not secret and is not a login code.
```

## The graded lab

The graded lab asks you to write three small Python functions and then runs hidden tests against them. This section restates the task, explains the ideas you need, and shows a method. It does not give you a solution to the real task. The worked example and the practice problem use a different domain, so that you can practise the same skills on data you have not seen.

### The task in plain words

The scenario is that you are tidying the CityPulse `citypulse` repository. You must audit its commit history and confirm that secrets never get committed. You do that by writing three module-level functions in the starter file. The starter already imports `fnmatch`, the standard module that matches glob patterns.

The three functions are these:

- `parse_oneline(text)` takes the raw text of `git log --oneline`. It returns a list of `(short_hash, subject)` tuples, in the order the lines appear in the text.
- `is_ignored(patterns, path)` takes a list of `.gitignore`-style patterns and one path. It returns `True` if the path is covered by any pattern, and `False` otherwise.
- `count_covered(patterns, paths)` takes the same kind of pattern list and a list of paths. It returns one integer: how many entries of `paths` are ignored.

The rules for `parse_oneline` are these:

- Each line is the short hash, then a single space, then the commit subject.
- The subject is everything after that one space, and it may contain more spaces.
- Blank lines are skipped.
- The output keeps the order of the input.
- An empty string gives an empty list.

The rules for `is_ignored` are these:

- A pattern can be an exact name or a full path. A path it matches is covered.
- A pattern with `*` or `?` is a glob. It is matched against the file's basename, which is the last part of the path. The pattern `*.env` covers `ingest/.env`, because the basename is `.env`.
- A pattern that ends in `/`, such as `__pycache__/`, covers any file whose path contains that directory.
- A line that is blank, or that starts with `#`, is not a pattern and is ignored.
- The function returns `True` when at least one pattern covers the path.

The rules for `count_covered` are these:

- It returns an integer, not a list.
- The integer is the number of entries in `paths` that `is_ignored` reports as covered.

The limits are 30 seconds and 128 MB for each run.

### What each function needs

Each idea below is taught with a small example that has nothing to do with the lab's data. Try each one in a Python shell before you use it in the lab.

**Splitting text into lines.** `str.splitlines` cuts a string at each line break and returns a list of lines. A line that is empty or only spaces is blank.

```python
poem = "red\n\nblue"
print(poem.splitlines())
print(" ".join(["  ", ""]).strip() == "")
```

The first line prints `['red', '', 'blue']`. The empty string in the middle is a blank line. The second line prints `True`, because `strip()` removes spaces at both ends, and an empty result means the line had nothing in it. The test `if not line.strip():` uses the same idea. An empty string is false in Python, so `not` turns it into `True`.

**Splitting once.** `str.split(sep, 1)` cuts a string at most once. The result has at most two pieces, which is useful when the second piece may contain the separator.

```python
drink = "Tea with milk"
first, rest = drink.split(" ", 1)
print(first, "|", rest)
```

The output is `Tea | with milk`. Without the `1`, the same line would split into three pieces and the two-name unpacking would fail. The number is the maximum number of cuts, not the number of pieces you get back.

**Building a list of tuples.** A tuple is a fixed group of values in round brackets. You can append tuples to a list in order.

```python
pairs = []
pairs.append(("Tea", "hot"))
pairs.append(("Juice", "cold"))
print(pairs)
```

The output is `[('Tea', 'hot'), ('Juice', 'cold')]`. The list keeps the order in which you appended the tuples, which is the order the statement requires.

**Checking the start, the end or the inside of a string.** `startswith` and `endswith` test the beginning and the end. The `in` operator tests whether one string appears anywhere inside another.

```python
note = "# keep this line"
print(note.startswith("#"))
print("chapter-3.md".endswith(".md"))
print("rock" in "rockabilly/song.mp3")
```

The output is `True`, `True` and `True`. The last line shows a trap. The text `rock` appears inside `rockabilly`, so `in` says yes even though `rock` is not a folder. To test whole folder names, split the path on `/` first, and leave out the last part, which is the file name.

```python
parts = "rockabilly/song.mp3".split("/")
print(parts)
print("rock" in parts[:-1])
```

The output is `['rockabilly', 'song.mp3']` and then `False`. The slice `parts[:-1]` means every part except the last one. Now `rock` is compared with whole folder names only.

**Getting the last part of a path.** `rsplit` cuts from the right. With `"/"` and a limit of `1`, it separates the final part from everything before it.

```python
path = "music/rock/song.mp3"
print(path.rsplit("/", 1)[-1])
print("notes.txt".rsplit("/", 1)[-1])
```

The first line prints `song.mp3`. The second prints `notes.txt`, because a name with no slash is its own last part. The index `[-1]` means the last item of a list.

**Glob matching with fnmatch.** `fnmatch.fnmatchcase(name, pattern)` returns `True` when the name matches the pattern. `*` matches any run of characters, and `?` matches exactly one character. The `case` version is case-sensitive, which is what you want for predictable results.

```python
import fnmatch

print(fnmatch.fnmatchcase("photo.jpg", "*.jpg"))
print(fnmatch.fnmatchcase("a1.txt", "a?.txt"))
print(fnmatch.fnmatchcase("a10.txt", "a?.txt"))
```

The output is `True`, `True` and `False`. The third line is `False` because `?` matches only one character, and `10` is two characters. Note that `*` also matches a slash, so `fnmatch` does not understand folders on its own.

**Counting, and why `True` is a number.** In Python, `bool` is a subclass of `int`. That means `True` behaves as `1` and `False` behaves as `0` in arithmetic, and `isinstance(True, int)` is `True`. You can use this to count.

```python
votes = [True, False, True]
print(sum(votes))
print(isinstance(True, int))
print(sum(1 for n in [4, 9, 12] if n > 5))
```

The output is `2`, then `True`, then `2`. The first line works because `sum` adds `True` as `1`. The third line is the clearer way to count matches, because it adds `1` only for each item that passes the test. Use it for `count_covered`, and remember that the result must be an `int`, not a list.

### Worked twin problem

This is a different domain that needs the same skills: splitting text into lines, building tuples, glob matching and counting.

**Bike-share station report.** A city bike-share team stores a report as text, with one line for each station. Each line holds the station name, one space, and the number of free bikes. Write three functions. `parse_report(text)` returns a list of `(name, count)` tuples, in order, where `count` is an integer. Blank lines are skipped, and an empty string gives an empty list. `is_flagged(rules, name)` returns `True` if the station name matches any rule. A rule is a glob matched against the whole name with `fnmatchcase`, so matching is case-sensitive. A rule that is blank, or that starts with `#`, is ignored. `count_flagged(rules, report)` returns the number of `(name, count)` entries whose name is flagged. Each entry is counted once.

The solution is written as a test block. It runs when the book is built, so it must pass.

```python test
import fnmatch


def parse_report(text):
    rows = []
    for line in text.splitlines():
        if not line.strip():
            continue
        parts = line.split()
        rows.append((parts[0], int(parts[1])))
    return rows


def is_flagged(rules, name):
    for rule in rules:
        if not rule.strip() or rule.startswith("#"):
            continue
        if fnmatch.fnmatchcase(name, rule):
            return True
    return False


def count_flagged(rules, report):
    total = 0
    for name, count in report:
        if is_flagged(rules, name):
            total += 1
    return total


text = "Indiranagar-2 14\n\nKoramangala-1 0\nJayanagar 7\n"
report = parse_report(text)
assert report == [("Indiranagar-2", 14), ("Koramangala-1", 0), ("Jayanagar", 7)]
assert parse_report("") == []
assert parse_report("\n  \n") == []
assert isinstance(report[0][1], int)
assert is_flagged(["Indiranagar*"], "Indiranagar-2") is True
assert is_flagged(["*-1"], "Koramangala-1") is True
assert is_flagged(["*-1"], "Koramangala-10") is False
assert is_flagged(["# note", "  "], "Jayanagar") is False
assert is_flagged(["jayanagar"], "Jayanagar") is False
assert count_flagged(["Indiranagar*", "*-1"], report) == 2
assert count_flagged([], report) == 0
assert count_flagged(["Jayanagar"], []) == 0
print("all checks passed")
```

The first line imports `fnmatch`, which provides the glob matching. `parse_report` starts with an empty list. The loop reads each line from `text.splitlines()`. The `if not line.strip()` check skips blank lines, including lines that hold only spaces. `line.split()` with no arguments cuts the line at any run of spaces, so `parts[0]` is the name and `parts[1]` is the count. `int(parts[1])` turns the text `"14"` into the number `14`, and the tuple is added to `rows`.

`is_flagged` loops over the rules. A rule that is blank, or that starts with `#`, is skipped by the `continue` line. `fnmatch.fnmatchcase(name, rule)` returns `True` when the name matches. The function returns `True` as soon as one rule matches, and `False` after the loop ends with no match. `count_flagged` starts `total` at zero, then adds one for each entry whose name is flagged. The function returns the total, which is an integer.

The asserts check the normal case, the blank input, the `#` rule, the case sensitivity and the counting. `"Koramangala-10"` does not match `"*-1"`, because the name must end in `-1`. The final `print` only shows that the file ran to the end. A failed assert stops the build, and the hidden tests in the real lab stop your code in the same way.
