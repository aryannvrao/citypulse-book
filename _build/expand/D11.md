## What the quiz tests

The Day Quiz for this chapter has ten case-study multiple-choice questions. Each question is about one of today's topics, and there is one question per topic, in the order used below. The pass mark is 70%, so you need seven correct answers out of ten. Your first attempt is the one your skill score keeps, so read this section before you attempt the quiz, not after.

Each question gives a short scenario about a team that runs a data pipeline, then asks you what is happening, what is wrong, or what to do next. The facts in the scenario are there for a reason, so treat each one as evidence. Use this method for every question:

1. Read the last line of the question first. It tells you what is asked: a name for something, a cause, or the best next step.
2. Reread the scenario and underline the facts that matter: what failed, when, how often, what the team needs, and what they must not do.
3. Read all four options before you choose. Eliminate any option that is true in general but does not fix this scenario. A correct statement about pipelines can still be the wrong answer.
4. Watch three words. "Most" means several options are sensible, but one is the strongest. "First" means there is an order, and the earlier step wins. "Best" means the answer must fit every fact in the scenario, not just one of them.
5. Ask which single fact would change your answer. If the scenario says the job runs twice, idempotency matters. If it says the source is busy for one minute, a retry may be right.

Each topic below explains the idea from zero, shows the kind of case study it appears in, names the trap, and gives you three practice questions. The quick self-test at the end mixes all ten topics and is harder than the individual questions.

### Pipelines as a directed acyclic graph

A pipeline is a set of steps, and some steps need the output of other steps. You can draw this as a graph. Each step is a node, which is a box, and each arrow says that one step needs the output of another. The graph is called a DAG, which stands for directed acyclic graph. "Directed" means each arrow has a direction. "Acyclic" means there is no cycle, which is a route that starts at one step and comes back to it.

A small pipeline can be written as a Python dictionary. Each key is a step, and its value lists the steps it depends on:

```python
deps = {"extract": [], "validate": ["extract"], "load": ["validate"]}
print(deps["load"])
```

The output is `['validate']`. Load can run only after validate, and validate only after extract. There is no cycle, so the run has a clear start, which is extract, and a clear end, which is load.

A straight line of steps is still a DAG, and it is the simplest kind. Branches matter when two steps do not depend on each other. Those two steps can run in parallel, or in either order, as long as both finish before any step that needs them. A cycle is a real problem because no step can go first: each one waits for another one to finish.

**How it shows up in a case study.** A team's nightly job has four stages: fetch readings, clean them, load them, and rebuild the dashboard views. Someone adds an arrow from the views back to fetch, so that empty views can ask for a fresh download. The job now runs for hours and never finishes. The question asks what the new arrow has created. The reasoning is that the arrow closes a loop, so there is no first step and no defined end. The fix is to remove the arrow and let a separate check decide whether a new fetch is needed. You find cycles by reading the arrows, not only the boxes.

:::trap A loop is harmless because it eventually stops
A cycle has no start, so the run cannot be ordered, retried or reasoned about. Nothing guarantees that it stops at all. A pipeline that is a single line is also a DAG, so you do not need extra complexity to make one.
:::

```quiz
Q: A nightly job has three steps: fetch, clean and load. Clean needs the output of fetch, and load needs the output of clean. Which description of this pipeline is most accurate?
- A cycle, because load could send the job back to fetch
* A directed acyclic graph with a single path from fetch to load
- Three independent jobs that can run in any order
- A graph with two start points that merge at load
WHY: Every arrow points one way and nothing loops back, so the run has one start and one end. Independent jobs would have no arrows between them, but the scenario says clean needs fetch.

Q: A developer wants a failed publish step to retry the whole job from fetch, so they add an arrow from publish back to fetch. The first run of the job now never finishes. Which structural problem does the new arrow create?
- Two steps now run in parallel
- The fetch step now stores fewer rows
- The publish step has too many inputs
* The arrows form a cycle, so no step can be called the first
WHY: A cycle means each step waits on another, so there is no first step and no defined end. The other options describe effects that an extra arrow does not cause. Retries belong outside the graph.

Q: Two steps, read_station_list and read_readings, read different raw files. Neither needs the other's output, and both feed the step load. Which statement about this graph is most accurate?
* They are separate nodes with no arrow between them, so either can run first, as long as both finish before load
- They must be merged into one node before the graph is valid
- They form a cycle with load, because both feed it
- Load must run before either of them, because it is the last step
WHY: Two nodes with no arrow between them have no fixed order, and both arrows into load mean load waits for both. Merging is not required, and load cannot run before the steps that feed it.
```

### Idempotent loads

An operation is idempotent if running it twice leaves the same result as running it once. For a load, this means a rerun must not double the rows. The idea is simple, but it is the reason a crashed job can be restarted safely.

Compare two ways of writing the same day's readings into a store:

```python
table = {}
table["2026-03-01"] = [42.1, 38.7]
table["2026-03-01"] = [42.1, 38.7]
print(len(table["2026-03-01"]))

log = []
log.extend([42.1, 38.7])
log.extend([42.1, 38.7])
print(len(log))
```

The first form replaces the rows for the key on each run, so the output is `2`. The second form appends, so the output is `4`. The first form is idempotent and the second is not. In the course's pipeline project (not today's graded lab), `to_sql` with `if_exists="replace"` drops the table and writes it again, so a second run gives the same row count. That replace method is not fully atomic, which you will meet later in this section.

**How it shows up in a case study.** CityPulse's daily job appends readings to a fact table. After a power cut, the scheduler reruns the job, and the dashboard now shows double the readings for that day. The team wants a rerun to be harmless. The reasoning is that the second run must find the day's rows and replace them, or delete them before it inserts, so the final table is the same either way. A job that succeeds once and then doubles data on a rerun is not safe to restart.

:::trap Rerunning after a success is the only test that matters
A load that works once can still double data on a rerun, and a rerun after a crash is exactly the case that matters. Logging the run, adding pauses or making the job faster does not change what the table holds afterwards. Only the way the second run treats existing rows does.
:::

```quiz
Q: A scheduler restarted a load job after a crash. The job appends rows, and the dashboard now counts each reading twice for that day. Which change makes a rerun harmless?
- Log the start time of every run
- Increase the batch size so the job finishes sooner
* Delete or replace the day's rows before inserting them, so a second run leaves the same table
- Add a short pause before each insert
WHY: Idempotent means a second run gives the same result as the first. Logging, speed and pauses do not change what the table holds after a rerun, but replacing the day's rows does.

Q: A sensor feed is loaded once an hour with a plain append. An engineer runs the same hour twice by mistake. Which property is the job missing?
* Idempotency, because a second run changes the table
- Completeness, because the feed sometimes has gaps
- Uniqueness, because two keys are the same
- Atomicity, because the rows arrive one at a time
WHY: The problem is that the second run changes the result. Atomicity is about whether readers see a half-finished load, but here the table is complete and simply doubled. A uniqueness check would detect the duplicates, but it would not stop the job from creating them.

Q: A team deletes all rows for the day before inserting them. The job then runs three times in one afternoon, and the row count is the same after each run. A colleague asks whether the job is idempotent for that day. What is the right answer?
- No, because it deletes data before inserting it
- No, because running a job three times is always wrong
- Only if the job also uses a transaction
* Yes, because each run leaves the same final state as the first
WHY: Idempotency concerns the final state after each run, not whether rows were deleted along the way. Delete-then-insert of the same data gives the same table every time. A transaction protects against partial writes, which is a separate property.
```

### The four data-quality dimensions

A data-quality dimension is the kind of problem a check looks for. The course uses four: completeness, validity, uniqueness and freshness. Each check you write should belong to one of them, and the course requires at least five checks across at least three of the four.

| Question the check asks | Dimension | Example rule |
|---|---|---|
| Did enough data arrive? | Completeness | At least 40 rows in the last 24 hours |
| Do the values follow the rules? | Validity | PM2.5 is at least 0 |
| Does a key appear only once? | Uniqueness | No repeated station, time and pollutant |
| Is the newest data recent? | Freshness | Newest reading is at most 3 hours old |

The difference between completeness and freshness causes most mistakes. Completeness counts how much data there is in a window, and freshness measures how old the newest item is. A count of rows in the last 24 hours tests coverage, so it is completeness even though it uses a time window. Freshness is the age of the latest row, measured in hours.

**How it shows up in a case study.** A dashboard shows an average PM2.5 for each station. The team has two checks: one fails when fewer than 40 rows arrived in the last day, and one fails when a reading is negative. A reviewer asks which dimensions the two checks cover. The reasoning is that the first asks whether enough data arrived, which is completeness, and the second asks whether values follow the rules, which is validity. Neither check measures how old the data is, so neither is freshness.

:::trap Filing every time-based check under freshness
Any check that mentions time is not automatically freshness. Ask what the number measures. The age of the newest row is freshness. The number of rows in a window is completeness.
:::

```quiz
Q: A dashboard shows average PM2.5 for each station. One check counts rows in the last 24 hours and fails below 40, and another checks that every value is at least zero. Which pair of dimensions fits these checks, in that order?
- Freshness and uniqueness
- Uniqueness and validity
- Validity and freshness
* Completeness and validity
WHY: Counting recent rows tests whether enough data arrived, which is completeness. The non-negative rule tests whether values follow the rules, which is validity. Freshness is about the age of the newest reading.

Q: A check fails when the same station, timestamp and pollutant appear on two rows, and the team wants such a batch blocked. Which dimension does this check belong to?
* Uniqueness
- Completeness
- Freshness
- Validity
WHY: The check looks for a key that must appear only once, which is uniqueness. Validity asks whether each value is allowed, and a duplicated row can contain perfectly valid values.

Q: A sensor feed stops at night. One check reports that the newest reading is 9 hours old and fails above 3 hours. Another reports that only 12 rows arrived in the last 24 hours, against a threshold of 40. Which dimensions do these two checks test?
- Both are validity checks, because the readings are out of range
- Both are freshness checks, because both involve time
* Freshness for the age of the newest reading, and completeness for the row count
- Uniqueness for the newest reading, and validity for the row count
WHY: The age of the newest reading is freshness. The row count tests whether enough data arrived, which is completeness. Filing both under freshness is the trap, because the count does not measure how old the data is.
```

### Range validation with inclusive bounds

Range validation checks that a value lies between a lower bound and an upper bound. A bound is inclusive if the boundary value itself is allowed. The rule `value >= 0` accepts zero, while `value > 0` rejects it. Both choices are valid rules, but they are different rules, so you must choose on purpose.

```python
readings = [0.0, -0.1, 1000.0, 1000.5]
accepted = [v for v in readings if 0 <= v <= 1000]
print(accepted)
```

The output is `[0.0, 1000.0]`. The chained comparison `0 <= v <= 1000` means both parts must be true, so both bounds are inclusive. The value -0.1 fails the lower bound and 1000.5 fails the upper bound.

There is one trap in this topic that the pandas course warns about. A comparison with a missing value is False. In Python, `float("nan")` behaves the same way, so `0 <= float("nan") <= 1000` gives `False`. A rule written as "reject if below zero or above 1000" does not fire for a missing value, so the missing value passes. A rule written as "accept only if inside the range" rejects it. Check for missing values with a separate completeness rule as well.

**How it shows up in a case study.** A cold-store logger must accept temperatures from 0 to 100 degrees, including both ends. A developer writes the rule as `value > 0 and value < 100`, and a reading of exactly 0.0 is rejected. The team then asks why a valid reading is missing. The reasoning is that the bounds are inclusive, so the rule must use `>=` and `<=`. The bounds should come from what the data means, and the reason should be written next to them.

:::trap Rejecting with the wrong comparison
A rule of "reject if below 0 or above 100" lets a missing value through, because a NaN fails both comparisons. A rule of "accept only if between 0 and 100" rejects it. Two rules that look like opposites can give different answers for the same input.
:::

```quiz
Q: A cold-store logger must accept temperatures from 0 to 100 degrees, including both ends. Which pass rule does this?
* 0 <= value <= 100
- 0 < value < 100
- value >= 0 only
- value != 100
WHY: Both bounds are inclusive, so 0 and 100 must pass. The strict form rejects both ends, and a rule with only a lower bound would accept 500 degrees.

Q: A pipeline rejects a reading when `value < 0 or value > 1000`. A sensor sends a missing value that arrives as NaN, which means not a number. What does this rule do with that reading?
- It rejects the reading as out of range
- It stops the pipeline with a type error
* It accepts the reading, because both comparisons are False for NaN
- It counts the reading as a duplicate
WHY: Any comparison involving NaN is False, so neither part of the rule fires and the reading passes. Writing the rule as "accept only if 0 <= value <= 1000" would reject the same reading correctly.

Q: A team writes a range rule as `value >= 0 and value <= 1000`. A reading of exactly 1000.0 arrives. What happens?
- It is rejected, because the upper bound is exclusive
* It is accepted, because the upper bound is inclusive
- It is accepted only if the station is known
- It is rejected, because a float cannot equal an integer
WHY: The bound 1000 is inclusive, so 1000.0 passes. Python compares floats and integers as numbers, so 1000.0 equals 1000. Station checks are a separate rule and do not apply here.
```

### Quarantining rejected rows

A rejected record should be kept, not thrown away. A quarantine, which is also called a dead-letter store, holds rejected rows together with the reason each one was rejected. The good rows go on to the next stage. The reason is what makes the quarantine useful, because it lets someone find the faulty sensor later.

```python
rows = [{"id": 1, "value": 4.0}, {"id": 2, "value": -3.0}]
good = [r for r in rows if r["value"] >= 0]
quarantine = [{"row": r, "reason": "negative_value"} for r in rows if r["value"] < 0]
print(len(good), len(quarantine), quarantine[0]["reason"])
```

The output is `1 1 negative_value`. The good list keeps the accepted row, and the quarantine keeps the rejected row with its reason. Nothing was deleted, so the evidence is still there.

This design has two parts, and both matter. Keeping the rows gives you evidence. Keeping the reason gives you a way to group the evidence. A quarantine with rows but no reasons can show that something is wrong, but it cannot show what.

**How it shows up in a case study.** A regional manager asks why one station has no readings for a week. The cleaning step filtered out negative values with a plain filter and wrote nothing else. The reasoning is that the rejected rows were dropped with no record, so there is no way to see which rule removed them or whether the sensor is faulty. The fix is to write the rejected rows to a quarantine table with the reason for each, while the good rows continue to the load.

:::trap Deleting rejects, or quarantining without reasons
Deleting rejected rows removes the evidence. Quarantining rows with no reason keeps the rows but makes them hard to diagnose. Both are mistakes, and the first is the more serious.
:::

```quiz
Q: A feed of 2,000 hourly readings has 12 rows that fail the range rule. The team wants to find which sensor produces them next week. Which handling best supports that investigation?
- Delete the 12 rows and record only the number rejected
* Write the 12 rows to a quarantine table with the reason, and load the other 1,988
- Load all 2,000 rows and mark the 12 in the dashboard
- Discard the whole feed so no bad data is kept
WHY: The quarantine keeps the evidence and the reason, and the good rows still flow through. Deleting the rows loses the evidence, loading everything publishes bad data, and discarding the feed throws away good data.

Q: A cleaning step filters out rows with a negative value using a plain filter and writes nothing else. A manager later asks why one station is missing readings. What is the gap in the design?
- The threshold should have been higher
- The filter should run after the load instead of before it
- The filter should have skipped the header line
* The rejected rows were dropped with no record, so nobody can see why they went missing
WHY: Dropping rows without a record removes the evidence. Changing the threshold or the order does not give the manager the rejected rows or their reasons. The design needs a quarantine.

Q: A quarantine table holds rejected rows, but the reason column is empty for every row. An analyst tries to find which rule rejects the most rows. What is wrong with the design?
* The rows are kept but not the reason, so the table cannot answer the question
- The quarantine should hold only accepted rows
- The rows should be stored on a separate database server
- The quarantine should be emptied after one day
WHY: A quarantine is useful because each rejected row keeps its reason. Without a reason, the rows exist but cannot be grouped for diagnosis, which is the whole point of the store.
```

### Incremental loading and the high-water mark

Incremental loading loads only the records that are new since the last run, instead of loading everything again. To do this, the job stores a high-water mark. This is the largest event timestamp it has already loaded safely. On the next run it takes only the rows above that value.

```python
events = [("2026-03-01T08:00", 1), ("2026-03-01T09:00", 2), ("2026-03-01T10:00", 3)]
mark = "2026-03-01T08:30"
new = [e for e in events if e[0] > mark]
print(new)
```

The output is `[('2026-03-01T09:00', 2), ('2026-03-01T10:00', 3)]`. ISO timestamps written in the same format compare correctly as text, so the comparison works here. After a successful load, the job stores the largest timestamp it loaded, which is `2026-03-01T10:00`, as the new mark.

Incremental loading is worth its complexity only when the data is too large to reload in each run. For a small table, a full reload is simpler and cannot miss rows. Note that a full reload must still be idempotent, so the table is replaced rather than appended.

**How it shows up in a case study.** A job takes the time at which it last ran as its mark. A feed sometimes delivers readings several hours late. A reading recorded at 14:00 arrives at 16:00, after a 15:00 run. The reasoning is that the mark is 15:00, and 14:00 is not later than 15:00, so the row is never selected. It is skipped for ever. The fix is to use the event timestamp of the data as the mark, not the time the job ran.

:::trap Using the job's run time as the mark
Late records have older timestamps than the run that should have picked them up. A mark based on run time skips them silently, and the dashboard looks complete while it is not.
:::

```quiz
Q: A job loads readings from a feed that sometimes delivers late. It stores the time at which it last ran, and each run loads rows with a timestamp later than that stored time. A reading recorded at 14:00 arrives at 16:00, after a 15:00 run. What happens to it?
- It is loaded on the next run, because it is newer than the last load
- It is loaded twice, once in each run
* It is skipped for ever, because its timestamp is earlier than the stored run time
- It makes the job fail with an error
WHY: The mark is 15:00, and 14:00 is not later than 15:00, so no later run selects the row. The fix is a high-water mark based on the event timestamps of the data.

Q: A team wants to load only new readings each hour. Their feed is small, about 3,000 rows a day, so reloading everything each hour is cheap. Which approach is the simplest correct choice for this team?
* A full reload, replacing the table each run, because the table is small and nothing can be missed
- An incremental load with the mark set to the job's start time
- An incremental load with the mark kept only in memory
- No load at all, because incremental loading is always faster
WHY: Incremental loading is for data too large to reload. For a small table, a full reload is simpler and cannot miss late rows. A mark kept only in memory is lost when the job restarts.

Q: A job stores a high-water mark of 2026-11-16T22:00 in a file. It loads a batch of rows, then crashes before it writes the new mark. What happens on the next run?
- The rows are lost, because the mark was not written
- The job skips every row after 22:00
- The job reloads only the rows after the time of the crash
* The job reads from the old mark again, so rows already loaded may be loaded twice, which is why the load must be idempotent
WHY: The mark is written only after success, so a crash leaves the old mark in place and the same rows are selected again. Idempotent loading makes that safe. The other options misdescribe what the stored mark does.
```

### Schema validation before row checks

Schema validation checks the structure of the data before any row is checked. It asks whether the required column names are present, and where needed whether each column has the right type. It runs first because a renamed or missing column makes every row check crash or report misleading results.

```python
required = {"station_id", "ts", "pollutant", "value"}
incoming = {"station_id", "ts", "pollutant_code", "value"}
print(sorted(required - incoming))
```

The output is `['pollutant']`. The set difference lists the required names that the incoming file does not have. This is the kind of message a schema check should give: it names the exact column that is missing, instead of a `KeyError` in the middle of a value check.

Schema validation also covers types. If a numeric column arrives as text, every number is a string. A range check that compares strings to numbers then fails in confusing ways, so the structure check should catch this first.

**How it shows up in a case study.** A supplier's export renames `station_id` to `station`. The row checks start to run, and the first error the team sees is a `KeyError` deep inside a value check. The reasoning is that a schema check, run before the row checks, would have compared the column names and reported the missing `station_id` directly. The row checks were not wrong. They were given a file that did not have the structure they expect.

:::trap Checking values and assuming the columns are right
If you check the values first, a renamed column appears as a confusing crash deep in a row check. Confirm the structure before you trust any value test.
:::

```quiz
Q: A supplier's export renames station_id to station. The row checks run, and the first error the team sees is a KeyError inside a value check. Which check should have caught the problem earlier and more clearly?
- A range check on the value column
- A uniqueness check on the timestamps
- A freshness check on the newest row
* A schema check that the required column names are present before any row is checked
WHY: A schema check compares column names before row checks run, so it reports the rename directly. The row checks were given a file they could not read, so the failure appeared in the wrong place.

Q: A file has all four required columns, but the value column is stored as text, so every number is a string. Which check is the right first line of defence?
* A schema check on column types, because the values are not numbers
- A uniqueness check on each row
- A drift check on the average
- A freshness check on the file date
WHY: Schema validation covers types as well as names. A text column breaks range checks, which compare numbers. A uniqueness check, a drift check and a freshness check answer other questions and do not look at column types.

Q: A schema check passes because every required column is present. A row check then finds that the ts value is missing for one row. Which statement is accurate?
- The schema check should have caught the missing timestamp value
- The row check is wrong to flag it, because the column exists
* The schema check confirms names and types, and a missing value in a present column is a row-level completeness problem
- The whole file must be rejected, because one row has a missing value
WHY: Schema validation works on the structure of the file. A missing value in a column that exists is a data problem, which row checks handle, usually by quarantining that row. Rejecting the whole file is too strong for one row.
```

### Drift detection against a baseline

Drift is a change in the pattern of the data over time. A batch can pass every rule and still be unusual. For example, its average PM2.5 can be three times last month's average while every single value is valid. A drift check compares a statistic from the new batch with a baseline, which is a reference value taken from earlier data, and it fires when the difference is too large.

```python
baseline = [20.0, 22.0, 21.0, 19.0]
today = [60.0, 66.0, 63.0, 61.0]
print(sum(baseline) / len(baseline), sum(today) / len(today))
print(round((sum(today) / len(today)) / (sum(baseline) / len(baseline)), 2))
```

The output is `20.5 62.5` on the first line and `3.05` on the second. Every value in today's batch is a plausible reading, so a range check would pass it. The drift check compares the two averages and finds that today's average is about three times the baseline.

Drift checks are usually warnings rather than blocking checks. A drift is a reason to look, not always a reason to stop the pipeline. Each drift threshold needs a written reason, because a threshold picked at random either fires every day or never fires.

**How it shows up in a case study.** A batch passes the range, uniqueness and completeness checks. The team's average temperature is 5.5 degrees above the baseline, and the drift check warns. The reasoning is that the rules judge single rows, but drift compares a statistic with a baseline. The right first step is to review the warning and confirm whether the change is real, such as a heatwave or a sensor fault, before anyone changes the threshold.

:::trap Passing the rules means the data is normal
Rule checks cannot see a change in the overall pattern. A batch of valid values can still be the wrong batch. Drift checks exist for exactly that gap.
:::

```quiz
Q: Tonight's batch passes every range, uniqueness and completeness check. Its average PM2.5 is about three times the average of the past month, and no station is missing. What is the right name for this finding?
* Drift, a change in the data's pattern against a baseline
- A duplicate key
- A schema error
- A null value
WHY: Rules judge single rows, while drift compares a statistic with a baseline. The duplicate, schema and null checks all passed, so none of them describes this change.

Q: A drift check compares this week's average temperature with a baseline of 18.0 and warns when the difference is more than 4 degrees. This week's average is 23.5. What should the team do first?
- Stop the pipeline, because the value is out of range
- Delete the week's rows, because they must be wrong
* Review the warning and confirm whether the change is real before touching the threshold
- Ignore it, because drift checks never matter
WHY: The difference is 5.5 degrees, so the warning fires as designed. Drift checks are warnings, and the first step is to find the cause. Changing the threshold to hide the warning would remove the check's purpose.

Q: A team sets a drift threshold of twice the baseline, with no written reason. Six months later nobody remembers why. Which practice does the course require instead?
- Set the threshold to zero, so every change is reported
* Write the reason for each threshold beside it, so the check can be judged later
- Use only blocking checks for drift, so they cannot be missed
- Remove the threshold and compare each day with the day before
WHY: The course requires each threshold to have a one-line justification. Without one, nobody can tell whether the number is sensible, and the check quietly becomes useless.
```

### Retry with backoff for transient failures

A transient failure is a temporary problem, such as a network timeout or a busy database, that may succeed if you try again. Retry with backoff means waiting longer after each failed attempt, for example 1 second, then 2, then 4. A maximum number of attempts stops the retries from going on for ever.

```python
delays = [2 ** n for n in range(3)]
print(delays)
```

The output is `[1, 2, 4]`. The expression `2 ** n` doubles the wait each time. Some systems add a small random amount to each wait, called jitter, so that many clients do not retry at the same moment and overload the service again.

Retries are for transient failures only. A validation failure, such as a negative reading, fails the same way every time. Retrying it wastes time and hides the real problem. The rule is to retry a failure that might clear by itself, and to fail a data-quality failure straight away.

**How it shows up in a case study.** A sensor API sometimes returns a timeout, and a batch sometimes fails the negative-value check. The team wants one retry rule for both. The reasoning is that the timeout is transient, so a bounded retry with growing waits is right. The negative value is a data problem that will fail again, so it must not be retried. The two failures need different handling, and the case study tests whether you separate them.

:::trap Retrying data-quality failures, or retrying without a limit
Retrying a failed check repeats the same failure and delays the stop. A retry with no maximum can run for ever and load the service that is already struggling.
:::

```quiz
Q: A sensor API sometimes returns a connection timeout. Some batches also fail because they contain a negative value. Which retry plan is correct for both?
- Retry every failure every second, without a limit
* Retry the timeouts with growing waits and a fixed maximum, and do not retry the batch that fails the check
- Retry both kinds of failure once, then delete the batch
- Never retry, because retries always hide bugs
WHY: A timeout is transient, so bounded backoff gives it a chance to clear. A negative value fails the same way on every attempt, so retrying it only wastes time.
```

### Atomic publish: all or nothing for readers

An atomic publish means that readers see either the complete old version or the complete new version of a table, and never a half-written state. A common way to achieve this is to load into a new table, or to write inside a transaction. A transaction is a group of database changes that either all succeed together or all roll back together. The new version is then made visible in one step.

```python
import sqlite3
con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE readings (v REAL)")
con.execute("INSERT INTO readings VALUES (1.0)")
con.commit()
con.execute("INSERT INTO readings VALUES (2.0)")
con.rollback()
print(con.execute("SELECT COUNT(*) FROM readings").fetchone()[0])
```

The output is `1`. The first insert is committed, so it is kept. The second insert is part of an open transaction, and `rollback` undoes it, so the table looks as if the second insert never happened. This is the all-or-nothing behaviour that a reader depends on.

The course's pipeline project uses `to_sql` with `if_exists="replace"`. That is idempotent, because a rerun gives the same table. It is not guaranteed to be atomic: depending on the database, a crash in the middle of writing can leave the table partly written. The pattern that avoids this is to build the new table under another name and then switch readers to it in one step.

**How it shows up in a case study.** A dashboard reads the readings table while the pipeline loads 50,000 rows into it. Users sometimes see a chart with about half of the day's data. The reasoning is that the loader writes into the live table, so every partial state is visible to readers. Loading more slowly, or showing a warning banner, does not remove the partial state. The fix is to load into a new table or inside one transaction, and then switch readers to the complete version.

:::trap Writing straight into the live table
Writing row by row into the table that readers use exposes every partial state. A banner or a slower load only hides the problem for a while.
:::


### What each function needs

The lab needs a small set of Python ideas. Each one is taught below with an example that has nothing to do with the lab's data. Work out how each idea applies to the lab yourself.

**Returning a tuple.** A tuple is a fixed group of values in round brackets. A function returns two values by separating them with a comma. The caller can unpack them into two names.

```python
def split_total(total):
    return total // 2, total - total // 2

halves, rest = split_total(7)
print(halves, rest)
```

The output is `3 4`. The expression `total // 2` is integer division, which drops the remainder. The caller's line `halves, rest = ...` unpacks the tuple into two names.

**Dictionary lookups with a default.** `d[key]` raises a `KeyError` if the key is missing. `d.get(key)` returns `None` in that case, and `d.get(key, default)` returns your default instead.

```python
stock = {"apple": 3}
print(stock.get("apple"), stock.get("pear"), stock.get("kiwi", 0))
```

The output is `3 None 0`. Use `get` when a key may be absent, and then test the result yourself.

**Counting with a dictionary.** To count items, start with an empty dictionary. For each item, read the current count with `get` and store one more.

```python
counts = {}
for colour in ["red", "blue", "red"]:
    counts[colour] = counts.get(colour, 0) + 1
print(counts)
```

The output is `{'red': 2, 'blue': 1}`. The first time a colour appears, `get` returns `0`, so the count starts at one.

**Counter from collections.** `Counter` does the same job as the loop above. Its `items()` method gives pairs, and `sorted` puts them in order.

```python
from collections import Counter
c = Counter(["red", "blue", "red"])
print(sorted(c.items()))
```

The output is `[('blue', 1), ('red', 2)]`. `sorted` on a list of tuples compares the first item of each tuple, then the second if the first ties.

**Sorting with a key.** `sorted(items)` returns a new list in ascending order, and it leaves the original list unchanged. `sorted(items, key=len)` compares the lengths instead of the items themselves.

```python
words = ["pear", "fig", "banana"]
print(sorted(words))
print(sorted(words, key=len))
print(words)
```

The output is `['banana', 'fig', 'pear']`, then `['fig', 'pear', 'banana']`, then `['pear', 'fig', 'banana']`. The last line shows that `sorted` did not change the original list.

**Types and booleans.** `isinstance(x, int)` is True for integers, and `isinstance(x, float)` is True for floats. A boolean is a subclass of int in Python, so `isinstance(True, int)` is True. When a boolean must be rejected, test for it first.

```python
for x in [5, 2.5, True, "7"]:
    if isinstance(x, bool) or not isinstance(x, (int, float)):
        print(repr(x), "rejected")
    else:
        print(repr(x), "accepted")
```

The output is `5 accepted`, `2.5 accepted`, `True rejected` and `'7' rejected`. The `repr` function shows the value with its quotes, so the text `'7'` is visibly a string.

**Membership in a set.** `x in {"a", "b"}` is True if `x` is one of the set's items. Membership in a set is fast, and it reads more clearly than a long chain of `or` tests.

```python
flavours = {"sweet", "sour"}
print("sour" in flavours, "salty" in flavours)
```

The output is `True False`. The comparison is case sensitive, so `"Sour"` would not be found.

**Chained comparisons.** Python lets you write `0 <= x <= 10`, which means the same as `0 <= x and x <= 10`. Both ends are included in this form. To exclude an end, use `<` instead of `<=`.

```python
for x in [0, 5, 10, 11]:
    print(x, 0 <= x <= 10)
```

The output is `0 True`, `5 True`, `10 True` and `11 False`. The test is inclusive at both ends.

**Regular expressions.** The module `re` matches text against a pattern. `re.fullmatch(pattern, text)` returns a match only if the whole text fits the pattern. `re.match` and `re.search` do not require that. There is a trap with the `$` symbol: in Python, `$` also matches just before a newline at the end of the text.

```python
import re
print(bool(re.match(r"^[a-z]+$", "abc\n")))
print(bool(re.fullmatch(r"[a-z]+", "abc\n")))
```

The output is `True`, then `False`. The `$` matched before the trailing newline in the first line. `fullmatch` requires the whole text, including the newline, to fit the pattern, so it fails.

**Not changing the input.** A function that returns a new value should not change the list or dictionary it was given. Build a new list for the result. Calling `.sort()` on a list changes that list in place, while `sorted(...)` returns a new one.

```python
data = [3, 1, 2]
ordered = sorted(data)
print(data, ordered)
```

The output is `[3, 1, 2] [1, 2, 3]`. The original list is unchanged, and the test harness may reuse the same input list in several tests.

### Worked twin problem

The twin problem below has a different domain, different data and a different rule order, so it does not give you the lab's answer. It uses the same skills: rules checked in order, the first failing rule wins, a count per reason, and an accepted and quarantined total. The domain is a sign-up form for a community library app.

A sign-up record is a dictionary with four keys: `email`, `age`, `country` and `joined`. Write two functions.

- `triage_signups(records)` returns a tuple `(accepted_count, quarantined_count)`.
- `quarantine_counts(records)` returns a dictionary that maps each reason to the number of quarantined records with that reason.

A record is quarantined for the first failing rule, checked in this order:

- `joined` is not a string matching the pattern `YYYY-MM-DD` (digits only). The reason is `"bad_joined"`. The pattern is the only test: you do not check the calendar.
- `age` is not an `int`, and booleans are invalid. Floats such as `21.0` are also invalid here. The reason is `"bad_age"`.
- `age` is less than 16 or greater than 120. The reason is `"age_range"`.
- `country` is not one of `"IN"`, `"US"`, `"GB"` or `"DE"` (exact, capital letters). The reason is `"bad_country"`.
- `email` is missing, is not a string, or does not contain exactly one `@`. The reason is `"bad_email"`.

Here is the solution:

```python test
import copy
import re

JOINED_RE = re.compile(r"\d{4}-\d{2}-\d{2}")
COUNTRIES = {"IN", "US", "GB", "DE"}


def signup_problem(record):
    joined = record.get("joined")
    if not isinstance(joined, str) or JOINED_RE.fullmatch(joined) is None:
        return "bad_joined"
    age = record.get("age")
    if isinstance(age, bool) or not isinstance(age, int):
        return "bad_age"
    if age < 16 or age > 120:
        return "age_range"
    if record.get("country") not in COUNTRIES:
        return "bad_country"
    email = record.get("email")
    if not isinstance(email, str) or email.count("@") != 1:
        return "bad_email"
    return None


def triage_signups(records):
    accepted = 0
    quarantined = 0
    for record in records:
        if signup_problem(record) is None:
            accepted += 1
        else:
            quarantined += 1
    return accepted, quarantined


def quarantine_counts(records):
    counts = {}
    for record in records:
        reason = signup_problem(record)
        if reason is not None:
            counts[reason] = counts.get(reason, 0) + 1
    return counts


GOOD = {"email": "asha@example.com", "age": 21, "country": "IN", "joined": "2026-02-14"}
NO_EMAIL = {k: v for k, v in GOOD.items() if k != "email"}
RECORDS = [
    GOOD,
    {**GOOD, "joined": "14/02/2026"},
    {**GOOD, "joined": None, "age": True},
    {**GOOD, "age": 21.0},
    {**GOOD, "age": True},
    {**GOOD, "age": 15},
    {**GOOD, "age": 16},
    {**GOOD, "age": 120},
    {**GOOD, "age": 121},
    {**GOOD, "country": "in"},
    {**GOOD, "email": "asha.example.com"},
    NO_EMAIL,
    {**GOOD, "email": "a@@b.com"},
]
snapshot = copy.deepcopy(RECORDS)

assert triage_signups(RECORDS) == (3, 10)
assert quarantine_counts(RECORDS) == {
    "bad_joined": 2, "bad_age": 2, "age_range": 2, "bad_country": 1, "bad_email": 3,
}
assert triage_signups([]) == (0, 0)
assert quarantine_counts([]) == {}
assert signup_problem({**GOOD, "joined": "2026-02-14 ", "age": 5}) == "bad_joined"
assert signup_problem({**GOOD, "joined": "2026-13-45"}) is None
assert signup_problem({**GOOD, "age": "21"}) == "bad_age"
assert signup_problem({**GOOD, "age": 5, "country": "XX"}) == "age_range"
assert signup_problem({**GOOD, "country": "XX", "email": ""}) == "bad_country"
assert RECORDS == snapshot
```

The first lines import `copy` and `re`, then create a compiled pattern and a set of allowed countries. `JOINED_RE` is compiled once, so the pattern is not rebuilt for every record. `COUNTRIES` is a set, so the membership test is quick and clear.

`signup_problem` runs the rules in the order given. Each `if` returns a reason as soon as the record breaks that rule, so the first failing rule is the one reported. The `.get` calls read the fields without crashing when a key is missing. The `isinstance(joined, str)` test comes before `fullmatch`, because `fullmatch` on `None` raises a `TypeError`. When every rule passes, the last line returns `None`.

The boolean test comes before the number test. `isinstance(True, int)` is True, so without the first check a boolean age would be accepted as the number 1. In this twin a float age such as `21.0` is also invalid, because only `int` is allowed. That is a choice made by this twin's statement, so always read your own statement to see which types it allows.

The age rule uses `age < 16 or age > 120`. An age of exactly 16 or exactly 120 is accepted, because both bounds are inclusive, and 15 and 121 are quarantined. Because the age-range rule comes before the country rule, a record with age 5 and country `"XX"` is reported as `age_range` only.

```python test
START_RE = re.compile(r"\d{2}:\d{2}")


def trip_reason(trip):
    start = trip.get("start")
```
