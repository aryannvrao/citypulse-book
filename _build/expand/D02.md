## What the quiz tests

The Day 2 quiz has ten case-study multiple-choice questions, one for each topic below, in the same order. The pass mark is 70%, which means seven correct answers. Only your first attempt counts, because the skill score keeps that first attempt and a second try does not replace it. The questions in this section are practice questions of your own, written for these topics. They are not the platform questions, so do not expect the same wording.

Every case-study question describes a short CityPulse situation: a team, a symptom or a limit. Use the same method each time.

1. Read the last line first. It tells you what is being asked, such as the command to run, the likely cause or the safest choice.
2. Underline the facts in the scenario that matter. A file name, a permission, a line count or a process that ignores a signal is often the whole answer.
3. Eliminate options that are true in general but do not fix this scenario. Many wrong options are good commands used in the wrong place.
4. Watch three words. "Most" asks for the strongest answer among several sensible ones. "First" asks for the step that comes before the others. "Best" asks for the option that is safest or simplest, not just one that works.

Each topic below explains the tool from zero, shows it in a scenario, warns you about one trap and then gives you three practice questions. Read the explanation before you try the questions. The section ends with a harder self-test that mixes all ten topics.

### Listing files with ls and wildcards

**What it is.** `ls` lists the names in a directory. A wildcard is a symbol that stands for other characters. `*` matches any run of characters, including none. `?` matches exactly one character, and `[ab]` matches one character from the list. The shell does the matching before the command runs. It replaces the pattern with the matching names in the current directory, and then `ls` receives those names. Wildcards look only at the current directory, not at subdirectories. Names that start with a dot are not matched by `*`.

```bash
ls -lh *.csv
```

If the folder holds `jan.csv` and `feb.csv`, the shell turns the command into `ls -lh feb.csv jan.csv` (the names come in alphabetical order), and you see one long line per file, with sizes in K or M. If no file matches, the shell passes the pattern through unchanged, and `ls` reports that it cannot access it.

**How it shows up in a case study.** A data team keeps raw drops in `/data/readings`. The folder holds `jan.csv`, `feb.csv`, a `.env` file with API keys and `notes.txt`. A new engineer wants a quick size check of the drops only. A pattern selects names by their shape, not by their contents, so `*.csv` picks the drops and leaves the secrets and the notes out. One line, `ls -lh *.csv`, does the job and opens no file.

:::trap Leaving the pattern unquoted in find
Writing `find /data -name *.csv` without quotes lets the shell expand the pattern in the current folder first. `find` then receives a list of file names, not a pattern to search for. Quote it: `find /data -name '*.csv'`.
:::

```quiz
Q: The raw drop folder holds jan.csv, feb.csv, a .env file and notes.txt. Your lead wants the sizes of the CSV drops only, in human units, from the current folder. Which command does this?
- ls -lh csv
* ls -lh *.csv
- ls -lh .env
- cat *.csv
WHY: The shell replaces *.csv with the matching names before ls runs, so only jan.csv and feb.csv are listed. The tempting wrong answer is cat *.csv, which prints the contents of the files instead of listing their names and sizes.

Q: A folder holds app.log and web.log. A teammate types find /srv/hunt -name *.log and gets an error saying that paths must precede the expression. What is the cause and the fix?
- find cannot use -name with a wildcard, so use -iname instead
- find must be started from /srv/hunt, so run cd first
* The shell expanded *.log into app.log and web.log before find ran, so quote the pattern as '*.log'
- The error means the log files are empty, so find has nothing to read
WHY: With two matches the shell passes find two names, and find treats web.log as a second starting path after the test, which it rejects. Quotes stop the expansion. The tempting wrong answer is -iname, which changes only the letter case and leaves the expansion problem in place.

Q: In a folder with no .txt files, ls *.txt prints "cannot access '*.txt': No such file or directory". Which statement explains this?
- ls cannot read hidden files, and every .txt file is hidden
- The folder is locked, so the shell refuses to list it
- The shell searches every subfolder for .txt files and finds none
* When a wildcard matches nothing, the shell passes the pattern through unchanged, so ls looks for a file literally named *.txt
WHY: The message names the pattern itself, which shows that the shell found no match and handed the text over unchanged. The tempting wrong answer is that the folder is locked, but the problem is the missing match, not a permission.
```

### Reading the start and end of a file

**What it is.** `head -n N` prints the first N lines of a file, and `tail -n N` prints the last N lines. `tail -n +N` is different. The plus sign means "start at line N and print to the end". In a CSV file, `tail -n +2` skips the header in line 1. If you ask for more lines than the file holds, `head` and `tail` print the whole file and report no error.

```bash
head -n 2 readings.csv
tail -n 1 readings.csv
tail -n +2 readings.csv | head -n 1
```

Assume the file has four lines: a header, then three readings. The output is:

```text
station_id,ts,pollutant,value
ST-01,2025-01-01T00:00:00,PM2.5,53.3
ST-03,2025-01-01T02:00:00,PM2.5,47.9
ST-01,2025-01-01T00:00:00,PM2.5,53.3
```

The first command shows the header and the first reading. The second shows the last line. The third starts at line 2 and keeps only the first row of what follows.

**How it shows up in a case study.** An on-call engineer wants a sample of the newest rows from `readings.csv`, which is 10,000 lines long. The ingest job appends to the end of the file, so the newest rows are at the bottom. The newest rows are at the end, so the right tool is `tail`, and the number after `-n` is how many rows you want. `head` would show the oldest rows, which were written first.

:::trap Reading tail -n 2 as "skip the first two lines"
Typing `tail -n 2` to skip a header is a mistake. It prints the last two lines of the file, so almost every reading is missing. `tail -n +2` is the form that starts at line 2.
:::

```quiz
Q: The ingest job appends to readings.csv, which is 10,000 lines long. The on-call engineer needs the five most recent rows to check the ingest. Which command prints them?
- head -n 5 readings.csv
* tail -n 5 readings.csv
- tail -n +5 readings.csv
- wc -l readings.csv
WHY: tail -n 5 prints the last five lines, which are the newest rows. head prints the oldest rows. tail -n +5 prints from line 5 to the end, which is nearly the whole file.

Q: A teammate needs every row of feb.csv except the header, to pass into a sort. Which command does this?
- tail -n 1 feb.csv
- head -n 2 feb.csv
* tail -n +2 feb.csv
- tail -n 2 feb.csv
WHY: tail -n +2 starts at line 2 and prints to the end. The tempting wrong answer is tail -n 2, which prints only the last two lines, not the rows after the header.

Q: A file has 12 lines, and somebody runs head -n 20 on it. What does the command print?
- An error, because 20 is larger than the number of lines
- Only the first 10 lines, because head always prints ten
- Nothing, because the count must match the length of the file
* All 12 lines, because head stops at the end of the file without reporting an error
WHY: head stops when it reaches the end of the file, and a larger count is not an error. The tempting wrong answer is that head always prints ten lines, which is true only when you leave out -n.
```

### Counting lines with wc

**What it is.** `wc` stands for "word count". With `-l` it counts lines. It counts the newline characters, the invisible marks that end each line, so a last line that has no newline is not counted. Without a flag, `wc` prints lines, words and bytes together.

```bash
wc -l jan.csv
tail -n +2 jan.csv | wc -l
```

The output is:

```text
4033 jan.csv
4032
```

The first count includes the header. The second skips it, so it is the number of readings.

**How it shows up in a case study.** A teammate counted the readings for one station by running `wc -l` on an export that has a header line. The summary sheet shows one more row than the station really has. The header is a line of text, not a reading, so one line must come off the count. The check is simple: count with `tail -n +2`, or subtract one.

:::trap Reporting the raw wc figure as the reading count
Writing 4,033 as the number of readings because `wc -l` printed it. The header is one of those 4,033 lines. The right figure is 4,032.
:::

```quiz
Q: A station file holds a header line and 2,500 readings, one reading per line. A teammate reports 2,501 readings from wc -l. Which statement is correct?
* 2,500 readings, because the header is one of the 2,501 lines counted by wc -l
- 2,501 readings, because wc -l counts only the readings
- 2,502 readings, because wc adds one for the header
- 5,002 readings, because each reading takes two lines
WHY: wc -l counts every line, and the header is one of them, so it must come off the count. The tempting wrong answer is 2,501, which assumes wc -l skips the header.

Q: A pipeline counts rows with wc -l, but the last reading of the file is not followed by a newline character. Compared with the number of lines a person sees on screen, what does wc -l report?
- One more than the visible lines, because wc counts the end of the file
- The same number in every case, because wc counts characters
* One fewer than the visible lines, because wc -l counts newline characters and the last line has none
- Zero, because wc -l needs a blank line at the end
WHY: wc -l counts newline characters, so an unfinished last line is missed. The tempting wrong answer is one more, which assumes that the end of the file counts as a line.

Q: A team runs grep ',PM2.5,' jan.csv | wc -l and gets 1008 for a file that has a header. Which statement is correct?
- The header is counted, so there are 1007 PM2.5 readings
* The header is not counted, because its text does not contain ,PM2.5, so 1008 is the number of matching rows
- The count includes NO2 rows, because wc does not filter
- The result is a size in bytes, because wc -l always counts bytes
WHY: grep filters the rows before wc counts them, so the header never reaches wc. The tempting wrong answer is the first option, which assumes the header is always included.
```

### Searching text with grep

**What it is.** `grep` prints every line that contains the text you give it. `-r` searches all subfolders, `-n` shows line numbers, `-i` ignores letter case, `-l` prints only the names of files that match, and `-c` counts matching lines. The pattern is a regular expression, and in a regular expression a dot matches any single character. So `PM2.5` also matches `PM205`. Put the pattern in single quotes so the shell does not change it.

```bash
grep -rin 'pm2_5' /srv/hunt
grep -c ',PM2.5,' jan.csv
```

A match looks like `/srv/hunt/site3/notes.txt:12:PM2_5 sensor offline`. The text before the first colon is the file, the number is the line, and the rest is the line itself. The second command prints one number, the count of matching rows, which might be 1008 for a month of data.

**How it shows up in a case study.** An engineer must find every note under `/srv/hunt` that mentions a sensor fault, however the words are capitalised. The notes sit in several folders, so one file is not enough. Recursion is needed to reach every folder, and ignoring case matches `PM2_5`, `pm2_5` and `Pm2_5` in one search. The reasoning picks the flags first and the pattern second.

:::trap Expecting grep to search a whole folder by default
Running `grep 'pm2_5' /srv/hunt` without `-r` prints `grep: /srv/hunt: Is a directory` and searches nothing. Without `-r`, grep reads one file at a time.
:::

```quiz
Q: An engineer must find every line under /srv/hunt that mentions PM2.5 in any capitalisation, with its line number. Her first try, grep -n 'PM2.5' /srv/hunt, prints an error and no matches. Which command does the job?
- grep -n 'PM2.5' /srv/hunt, which searches only one file
- grep -rn 'PM2.5' /srv/hunt, which searches folders but keeps case
* grep -rin 'PM2.5' /srv/hunt, which searches folders, ignores case and shows line numbers
- find /srv/hunt -i 'PM2.5', which lists file names only
WHY: -r, -i and -n together cover all three needs. The tempting wrong answer is grep -rn, which searches folders but is case-sensitive, so it misses pm2.5 written in lower case.

Q: A search for 'PM2.5' returns a line that reads "PM205 sensor offline", which nobody expected. Which explanation fits best?
- The pattern is read as PM25, so the dot is removed before the search
* In a regular expression the dot matches any single character, so PM2.5 also matches PM205
- The line is in lower case, and grep ignores case by default
- grep counts characters, so it printed the wrong line
WHY: The dot is a wildcard for one character, so the 0 in PM205 satisfies it. The tempting wrong answer is the case explanation, but grep is case-sensitive by default, so case does not explain a match.

Q: A teammate runs grep -n 'pm2_5' /srv/hunt and sees "grep: /srv/hunt: Is a directory". What should they do?
- Use cat /srv/hunt, which prints the contents of the directory
- Use ls -lh /srv/hunt and read the names by eye
- Use sudo, because the directory must be locked
* Add -r, so grep descends into the directory tree and searches the files inside it
WHY: -r tells grep to search the files inside folders. The tempting wrong answer is sudo, but the message is not a permission error.
```

### Redirecting input and output

**What it is.** Every program has three streams. Standard input (0) is where it reads, standard output (1) is where normal results go, and standard error (2) is where error messages go. `>` sends standard output to a file and replaces the file. `>>` adds to the end of the file. `<` feeds a file in as input. `2>` sends standard error to a file, and `|` sends standard output to the next program. A stream you do not redirect still appears on the screen.

```bash
grep ',NO2,' jan.csv > no2.csv
grep ',NO2,' jan.csv >> all_pollutants.csv
sort < no2.csv | head -n 1
ls /no/such/folder 2> errors.txt
```

The first two commands print nothing to the screen. The third prints the first line in sort order. The fourth prints nothing, because its error message goes into `errors.txt`.

**How it shows up in a case study.** A nightly job writes one summary line to `report.txt`, and the team wants each run to add a line and keep the older ones. Another job should save its error messages for later. The reasoning is that `>` replaces, so the job must use `>>` to keep its history. Error messages are a separate stream, so they need `2>`.

:::trap Expecting > to capture error messages
Writing `ls /missing > listing.txt` and expecting the error to land in `listing.txt`. Only standard output is redirected. The error still appears on screen, and `listing.txt` is created empty. Use `2>` for errors.
:::

```quiz
Q: A nightly job writes one summary line per run into report.txt, which already holds the earlier runs. The job uses > report.txt. What happens to the earlier lines?
* They are lost, because > replaces the file, so the job should use >> instead
- They are kept, because > always adds to the end of a file
- They move to standard error, because > sends old content there
- They are sorted, because > runs sort on the file first
WHY: > empties the file before writing. The tempting wrong answer is that the old lines are kept, which assumes > behaves like >>.

Q: A script runs ls /data/missing > listing.txt. The folder does not exist, and the team expects the error to be saved in listing.txt for later. What actually happens?
- The error is saved in listing.txt, because > captures everything the command prints
- The command runs silently, because the shell hides errors from redirected commands
* The error appears on screen, and listing.txt is created empty, because > redirects only standard output
- The shell refuses to run the command, because it cannot write its error to a file
WHY: Only standard output goes to the file, so the error stays on screen, and the file is created empty before ls runs. The tempting wrong answer is the first option, which treats > as a catch-all.

Q: Which pipeline prints the number of PM2.5 rows on screen and saves any error messages from grep in errors.log?
- grep ',PM2.5,' jan.csv | wc -l > errors.log
- grep ',PM2.5,' jan.csv > errors.log | wc -l
- grep ',PM2.5,' jan.csv 2>&1 | wc -l
* grep ',PM2.5,' jan.csv 2> errors.log | wc -l
WHY: 2> sends grep's error messages to the file, and the pipe still carries its normal output to wc. Option two sends the rows into the file, so wc counts nothing. Option one sends the count into the file instead of the screen, and option three counts the error messages as lines.
```

### Setting permissions with chmod

**What it is.** Every file has permissions for three groups of users: the owner, the group and everyone else. Each group has three bits: `r` for read (value 4), `w` for write (value 2) and `x` for execute (value 1). A permission string such as `-rw-r-----` has ten characters: the file type, then the three groups. `chmod` changes the bits. A three-digit number sets all three groups at once, and each digit is the sum of its bits. `+x` adds the execute bit and leaves the others alone.

```bash
ls -l .env
chmod 600 .env
ls -l .env
```

The output is:

```text
-rw-r--r-- 1 city city 22 Nov 11 09:14 .env
-rw------- 1 city city 22 Nov 11 09:14 .env
```

Only the permission string changes. The owner keeps read and write, and the group and others lose everything.

**How it shows up in a case study.** A new script, `fetch_once.sh`, fails with "Permission denied" when run as `./fetch_once.sh`. The same team keeps an API key in `.env`, which must stay private. The script needs the execute bit, which `+x` adds and nothing else. The key needs the smallest access, which is `600`. Opening access to everyone is never the fix.

:::trap Using chmod 777 to make an error go away
`chmod 777` makes a file readable, writable and executable by every user on the server, including a file that holds secrets. It stops the error, but it gives away far more access than the fix needs.
:::

```quiz
Q: A teammate's script fails with "Permission denied" when run as ./fetch_once.sh, and its permissions are -rw-r--r--. Which change fixes the problem with the least access?
- chmod 777 fetch_once.sh
- chmod 600 fetch_once.sh
* chmod +x fetch_once.sh
- chmod -w fetch_once.sh
WHY: +x adds execute and keeps the other bits. The tempting wrong answer is 777, which works but gives every user write access to the script. chmod 600 would remove the read bit for the group and others, and it would still not add execute.

Q: The team stores the CityPulse API key in .env, and only the owner should use it. Which mode is most appropriate?
- 777
- 644
- 666
* 600
WHY: 600 gives the owner read and write and nothing to anyone else. The tempting wrong answer is 644, which lets every user on the server read the key.

Q: ls -l shows -rwxr-x--- for deploy.sh. Who can run it?
* The owner and the members of the group, but not other users
- The owner only, because the group has no execute bit
- Everyone, because others can read the file
- Nobody, because a group cannot execute a file
WHY: The owner has rwx and the group has r-x, so both can run the script. The tempting wrong answer is that only the owner can run it, which ignores the group's execute bit.
```

### Grouping with cut, sort and uniq

**What it is.** `cut -d, -f1` keeps field 1 of each comma-separated line. `sort` puts lines in order. `sort -n` compares numbers by value, `sort -r` reverses the order, `sort -k2` sorts on the second field and `sort -rn` combines reverse and numeric. `uniq -c` collapses runs of identical neighbouring lines into one line and writes the count in front. Together, `cut | sort | uniq -c` counts how often each value appears.

```bash
printf 'b,1\na,2\nb,3\n' | cut -d, -f1 | sort | uniq -c
```

The output is:

```text
      1 a
      2 b
```

`printf` writes three lines. `cut` keeps the letters, `sort` brings the two `b` lines together, and `uniq -c` counts each group.

**How it shows up in a case study.** A team wants the readings per station from a day's file, and then the three busiest stations. They count with `cut | sort | uniq -c`, which puts the count first on each line. The busiest stations need a reverse numeric sort, because a text sort would rank `9` above `672`. The reasoning is that `sort -rn` compares the counts as numbers, and `head -n 3` keeps the top of the list.

:::trap Dropping -c from uniq
Without `-c`, `uniq` prints each distinct station once and gives no count, so the tally is lost. Keep `-c`, and keep the `sort` before `uniq` so that identical ids sit next to each other.
:::

```quiz
Q: A teammate ran cut -d, -f1 jan.csv | uniq -c on an unsorted file and sees ST-01 on several lines, each with a small count. Which change gives one count per station?
- Replace cut with head
* Put sort between cut and uniq, so that identical ids sit next to each other
- Add -n to uniq, so that it sorts the counts
- Replace uniq -c with wc -l
WHY: uniq merges only neighbouring duplicates, so the rows must be grouped before it runs. The tempting wrong answer is adding -n to uniq, but uniq has no option that sorts, so the identical ids stay apart.

Q: You need the five stations with the most readings, highest first, from lines such as "672 ST-03" that an earlier count produced. Which command comes closest?
- sort | head -n 5
- sort -k2 | tail -n 5
* sort -rn | head -n 5
- uniq -c | wc -l
WHY: -n compares the counts as numbers, -r puts the largest first, and head keeps five. The tempting wrong answer is sort | head -n 5, which sorts the text and returns the first five lines in text order, not the largest counts.

Q: Which pipeline gives one line per pollutant, with its count, from a file where the pollutant is the third comma-separated field?
- cut -d, -f2 jan.csv | sort | uniq -c
- cut -f3 jan.csv | uniq -c
- sort -d, -f3 jan.csv | uniq -c
* cut -d, -f3 jan.csv | sort | uniq -c
WHY: -d, sets the comma as the delimiter and -f3 selects the third field. The tempting wrong answer is -f2, which is the timestamp. cut -f3 without -d splits on tabs, so it returns whole lines.
```

### Checking disk space with df

**What it is.** `df` stands for "disk free". It reports each filesystem, which is a disk or partition with a set of folders on it. `df -h` shows sizes in K, M, G and T. Its columns are Size, Used, Avail (the space you can still write to), Use% (how full the disk is) and Mounted on (the folder where that filesystem appears). `du` answers a different question. `du -h` adds up the size of the files under a folder. Use `df` to ask whether a disk is full and `du` to find which folder is large.

```bash
df -h /data
du -sh /data/readings
```

The output looks like this, with your own sizes:

```text
Filesystem      Size  Used Avail Use% Mounted on
/dev/sdb1       200G  184G   16G  92% /data
140K    /data/readings
```

**How it shows up in a case study.** The ingest job fails with "No space left on device" while it writes to `/data`. The team must decide whether to clear old drops or ask for more disk. The first question is how much space is free on the filesystem that holds `/data`, which is `df`. Only then does `du` help, to find the folders that take the most room.

:::trap Using du to find free space
`du -h /data` adds up the files in `/data`, so it says nothing about the space left on the disk. Use `df -h /data` for the free space.
:::

```quiz
Q: The /data disk is full, and the ingest job fails with "No space left on device". Which command shows the free space on the filesystem that holds /data, in human units?
- free -h
* df -h /data
- du -h /data
- ps aux
WHY: df -h /data shows Avail and Use% for the disk. free -h reports memory (RAM), and du -h /data measures the size of the folder without giving the free space on the disk.

Q: The team wants the folders under /data/readings sorted from the largest to the smallest, with sizes in human units. Which command is best?
- df -h /data/readings
- ls -l /data/readings | wc -l
- which du
* du -sh /data/readings/* | sort -rh
WHY: du -sh prints one total per folder, and sort -rh understands K, M and G and puts the largest first. The tempting wrong answer is df -h, which reports the whole disk, not the folders on it.

Q: Which statement about df and du is correct?
* df reports whole filesystems, including the free space, while du adds up the size of the files under one path
- df measures the size of folders, and du reports the free space on the disk
- They report the same numbers, so either one answers any disk question
- du is the memory counter, and df counts running processes
WHY: The tempting wrong answer is the second option, which swaps the two tools. Each one answers a different question.
```

### Finding your location with pwd

**What it is.** `pwd` stands for "print working directory". It prints the absolute path of the directory you are in, which starts at the root `/`. `cd` changes that directory for the current shell only. A relative path such as `raw/jan.csv` is measured from the working directory, so the same command can find different files from different folders.

```bash
cd /data/readings
pwd
cd ..
pwd
```

The output is:

```text
/data/readings
/data
```

`cd ..` moves one level up to the parent directory, so the second `pwd` shows `/data`.

**How it shows up in a case study.** A job runs `ingest.sh raw/jan.csv` from `/home/city`, and it fails with "No such file or directory". The data is in `/data/readings/raw`. A relative path is measured from the place where the command starts, and that place is `/home/city`. The check is `pwd`, and the fix is either an absolute path or a `cd` before the run.

:::trap Thinking a script resolves paths from its own folder
A relative path inside a script is measured from the folder where the command was started, not from the folder that holds the script. A script started from another folder reads relative paths from there.
:::

```quiz
Q: Your teammate runs head -n 2 jan.csv from /home/city and gets "No such file or directory". The file is in /data/readings. Which first step and fix are right?
- echo $PATH, then add /data/readings to PATH
- which jan.csv, then copy the file into /home/city
* pwd, then cd /data/readings before running the command, or pass the full path to jan.csv
- ls -la /home/city, then move jan.csv into /home/city
WHY: pwd shows where the shell is. PATH lists folders for finding programs, not data files, so changing it would not help a data file path. The tempting wrong answer is adding /data/readings to PATH.

Q: A script runs find . -name '*.csv' and finds nothing, although CSV files are visible in /data/readings. What is the most likely cause?
- find needs -r before it can see files in a folder
- The CSV files start with a dot, so find hides them
- The quotes around *.csv stop find from seeing any files
* The dot in find . means the folder where the script was started, which is not /data/readings
WHY: The dot is a relative path measured from where the command runs. The tempting wrong answer is the quotes, but quoting the pattern is correct here.

Q: Which statement about cd and the working directory is correct?
* cd changes the working directory of the current shell, and a script you run starts in the folder you ran it from
- cd changes the working directory of every program on the server
- cd must be typed before each command, or the command fails
- pwd changes the directory to the one it prints
WHY: The tempting wrong answer is that cd affects every program on the server. It affects only the shell where you typed it.
```

### Stopping processes with kill

**What it is.** A process is a running program, and it has a number called its PID. Adding `&` to the end of a command starts it in the background, so the prompt comes back at once. `jobs` lists the background jobs of this shell, and `kill %1` sends a signal to job number 1. `ps aux` lists every process on the machine. `kill PID` sends the TERM signal, which asks a program to stop and run its cleanup. `kill -9` sends KILL, which the program cannot catch, so it stops without cleanup.

```bash
sleep 300 &
jobs
```

**How it shows up in a case study.** An ingest job started in the background is halfway through writing a file, and it must stop. The team wants the program to finish the step it is on and remove its temporary file. TERM lets the program run that cleanup, and KILL does not. The reasoning is to send the plain `kill` first, check after a short wait, and use `-9` only if the process is still running.

:::trap Reaching for kill -9 first
`kill -9` stops a process, but it skips cleanup and can leave files half-written. Send the plain `kill` first, and use `-9` only when the process ignores it.
:::

## The graded lab

The graded lab is a Python problem. You write small functions, the platform runs the visible tests, and then it runs hidden tests that check the cases the visible tests leave out. This part of the chapter restates the task, teaches the Python ideas you need with examples that have nothing to do with the sensor data, and then gives you a method and a twin problem to practise on.

### The task in plain words

The scenario is the one you met in the cut, sort and uniq section. On a CityPulse ingest box, you pull station counts out of raw sensor lines with a shell pipeline. The pipeline is `grep ',pm25,' | cut -d, -f1 | sort | uniq -c`. In this lab you rebuild the same logic in Python, so that each step can be unit-tested.

Each line is CSV with four fields: `station_id,ts,pollutant,value`. For example, `ST3,2026-01-01T00:00,pm25,42.0` is a reading from station ST3 for pm25 with the value 42.0. Counting starts at zero, so field 0 is the station, field 1 is the timestamp, field 2 is the pollutant and field 3 is the value.

You must write four functions with these exact names. Keep the names and the order of the arguments as they are in the starter file.

- `grep(lines, pollutant)` takes a list of lines and a pollutant name. It returns the list of lines whose pollutant field, which is index 2, equals the pollutant you pass. The lines keep their original order. The match is exact: the field must equal the pollutant, not merely contain it.
- `cut(lines, idx)` takes a list of lines and an index. For each comma-delimited line, it returns the field at the 0-based index `idx`. It works like `cut -d, -f` with a number one higher, because `cut` counts fields from 1 and this function counts from 0.
- `count_sorted(items)` takes a list of items, such as the station ids that `cut` returns. It returns a list of `(item, count)` tuples, one for each distinct item, sorted by the item in ascending order. This is `sort | uniq -c`, except that the order is by item and not by count.
- `station_counts(lines, pollutant)` chains the other three. It greps the pollutant, cuts the station id from field 0, and passes the result to `count_sorted`.

The statement gives one example. Given the lines `ST3,t,pm25,42.0`, `ST1,t,pm10,30.0` and `ST3,t,pm25,51.0`, the call `station_counts(lines, "pm25")` returns `[('ST3', 2)]`. The station ST1 is absent because its only reading is for pm10.

The limits are 30 seconds of run time and 128 MB of memory for each run. Neither limit should matter for a solution of this size, so you do not need to optimise.

The scoring has two parts. The visible tests are worth 62 points:

| Test | Points |
|---|---|
| grep keeps only pm25 rows | 14 |
| cut extracts the station_id column | 14 |
| sort and uniq -c as sorted (item, count) tuples | 14 |
| Full pipeline for pm25 | 20 |

The hidden tests are three tests worth 38 points together. The platform does not show you their inputs. A hidden test is a fixed case that checks behaviour you have not seen, such as an empty input, a pollutant that no line contains, or a line where the pollutant text appears in another column. The hidden tests decide the top marks because they are worth more than a third of the total, and a solution can pass every visible test and still fail them. Treat the visible tests as a first check, not as the finish.

### What each function needs

Each idea below is shown with a small example about fruit, colours or temperatures. Do not try to assemble these examples into the lab's functions. Use them to understand the tools, then build the lab functions yourself.

**Looping and keeping items in order.** A `for` loop visits each item in turn, and `append` adds an item to the end of a list. Looping and appending keeps the original order, which `grep` needs.

```python
fruits = ["fig", "kiwi", "fig", "pear"]
figs = []
for fruit in fruits:
    if fruit == "fig":
        figs.append(fruit)
print(figs)  # ['fig', 'fig']
```

The `if` line keeps only the figs, and the list comes out in the same order it went in.

**Splitting text at a delimiter.** `text.split(",")` cuts a string at every comma and returns a list of pieces. Each piece is a string, and you pick one with its index.

```python
row = "red,large,12"
parts = row.split(",")
print(parts)     # ['red', 'large', '12']
print(parts[1])  # large
```

Indexes start at 0, so `parts[1]` is the second piece. The pieces are still text, even the `'12'`.

**Indexes past the end.** Asking for an index that does not exist raises an error. `len(parts)` tells you how many pieces there are, so you can check before you ask for one.

```python
parts = ["red", "large"]
print(len(parts))  # 2
print(parts[0])    # red
```

Asking for `parts[2]` would stop the program with an `IndexError`. A check such as `if index < len(parts)` prevents it.

**Counting with a dictionary.** A dictionary stores key and value pairs. `tally.get(key, 0)` returns the stored value, or 0 if the key is new. Adding one to that value counts an item the first time and every time after.

```python
colours = ["red", "blue", "red"]
tally = {}
for colour in colours:
    tally[colour] = tally.get(colour, 0) + 1
print(tally)  # {'red': 2, 'blue': 1}
```

**Turning a dictionary into pairs and sorting them.** `tally.items()` gives the key and value pairs, and `list(...)` turns them into a list of tuples. `.sort(key=...)` changes the list in place, and the key function decides what to compare.

```python
tally = {"red": 2, "blue": 1}
pairs = list(tally.items())
print(pairs)  # [('red', 2), ('blue', 1)]
pairs.sort(key=lambda pair: pair[1])
print(pairs)  # [('blue', 1), ('red', 2)]
```

The `lambda` is a short unnamed function. Here it returns the second item of each pair, so the list is sorted by the count.

**Sorting by two rules at once.** A tuple compares its items one at a time, from the left. A minus sign reverses a number, so a key of `(-count, name)` puts the largest count first and then sorts names in ascending order.

```python
pairs = [("fig", 1), ("kiwi", 3), ("apple", 3)]
pairs.sort(key=lambda pair: (-pair[1], pair[0]))
print(pairs)  # [('apple', 3), ('kiwi', 3), ('fig', 1)]
```

**Text order is not number order.** Strings compare character by character, so `"10"` comes before `"9"`. `sorted` returns a new list in text order.

```python
print(sorted(["10", "9", "2"]))  # ['10', '2', '9']
print(("apple", 2) < ("apple", 5))  # True
```

**Sorting without changing the original.** `sorted(items)` returns a new list and leaves `items` alone. `items.sort()` changes `items` itself and returns nothing.

```python
numbers = [3, 1, 2]
new_list = sorted(numbers)
print(numbers)   # [3, 1, 2]
print(new_list)  # [1, 2, 3]
```

Use `sorted` when the caller gave you a list and you should not change it.

### The rules people miss

The table lists the rules from the statement and what a careless solution does with each. The last column gives you a way to check your own code. The statement says nothing about lines with too few fields or about blank lines, so do not invent a rule that changes the output for normal lines.

| Rule in the statement | What a careless solution does | How to check yours |
|---|---|---|
| grep: match the pollutant field, index 2 | Tests whether the pollutant text appears anywhere in the line, so a line with pm25 in the station id or value also matches | Make a line where the pollutant text sits in another field, and check that grep drops it |

A solution that sorts by count and then breaks ties would give the wrong order, because the statement sorts by item. Boundaries and rounding do not arise in this statement, because the answers are whole counts.

### Worked twin problem

This twin problem uses web-server log lines, not sensor readings, but it needs the same skills. Read it as a lab task first.

Each line of a web-server log is CSV with four fields: `ip,timestamp,path,status`. For example, `10.0.0.2,2025-01-01T00:00:00,/home,200` is a request from `10.0.0.2` for `/home` that returned status 200. Write these five functions.

- `filter_by_status(lines, status)` returns the lines whose fourth field, index 3, equals the status. The status may be given as a number or as text, and the lines keep their order.
- `extract_column(lines, index)` returns the field at the 0-based index from each line, in order. It skips blank lines.
- `count_items(items)` returns a list of `(item, count)` tuples, one for each distinct item. The list is sorted by count from highest to lowest, and for equal counts by item in ascending text order.
- `top_pairs(pairs, n)` returns the first `n` pairs. If `n` is zero or negative, it returns an empty list.
- `top_ips_for_status(lines, status, n)` chains the four functions above and returns the top `n` `(ip, count)` pairs for that status.

This is the same job as `grep ',200,' | cut -d, -f1 | sort | uniq -c | sort -rn | head -n 2`, written as small functions that you can test one at a time.

The solution below is complete. Read the task first and try it yourself before you read the code.

```python test
def filter_by_status(lines, status):
    """Keep the lines whose fourth field equals status, in their original order."""
    kept = []
    for line in lines:
        fields = line.split(",")
        if len(fields) == 4 and fields[3] == str(status):
            kept.append(line)
    return kept


def extract_column(lines, index):
    """Return the field at index from each non-blank line."""
    values = []
    for line in lines:
        if not line.strip():
            continue
        fields = line.split(",")
        if index < len(fields):
            values.append(fields[index])
    return values


def count_items(items):
    """Return (item, count) pairs, highest count first, then item in ascending order."""
    counts = {}
    for item in items:
        counts[item] = counts.get(item, 0) + 1
    pairs = list(counts.items())
    pairs.sort(key=lambda pair: (-pair[1], pair[0]))
    return pairs


def top_pairs(pairs, n):
    """Return the first n pairs, or an empty list when n is zero or negative."""
    if n <= 0:
        return []
    return pairs[:n]


def top_ips_for_status(lines, status, n):
    """Filter by status, take the ip column, count the ips, then keep the top n."""
    kept = filter_by_status(lines, status)
    ips = extract_column(kept, 0)
    return top_pairs(count_items(ips), n)


lines = [
    "10.0.0.2,2025-01-01T00:00:00,/home,200",
    "10.0.0.1,2025-01-01T00:00:01,/home,404",
    "10.0.0.2,2025-01-01T00:00:02,/api,200",
    "10.0.0.3,2025-01-01T00:00:03,/api,200",
    "10.0.0.1,2025-01-01T00:00:04,/home,200",
    "10.0.0.3,2025-01-01T00:00:05,/api,200",
    "",
    "bad line",
]

# filter_by_status
assert len(filter_by_status(lines, "200")) == 5
assert len(filter_by_status(lines, 200)) == 5
assert filter_by_status(lines, "500") == []
assert filter_by_status([], "200") == []
assert filter_by_status(["1.1.1.1,t,/x"], "200") == []

# extract_column
assert extract_column(["a,b,c", "", "d,e,f"], 1) == ["b", "e"]
assert extract_column(["a,b"], 5) == []
assert extract_column([], 0) == []

# count_items
assert count_items(["x", "y", "x"]) == [("x", 2), ("y", 1)]
assert count_items([]) == []
assert count_items(["10.0.0.2", "10.0.0.10"]) == [("10.0.0.10", 1), ("10.0.0.2", 1)]
assert count_items(["b", "a", "b", "a"]) == [("a", 2), ("b", 2)]

# top_pairs
assert top_pairs([("a", 3), ("b", 1)], 0) == []
assert top_pairs([("a", 3), ("b", 1)], -2) == []
assert top_pairs([("a", 3), ("b", 1)], 5) == [("a", 3), ("b", 1)]

# the full pipeline
assert top_ips_for_status(lines, "200", 2) == [("10.0.0.2", 2), ("10.0.0.3", 2)]
assert top_ips_for_status(lines, "200", 3) == [("10.0.0.2", 2), ("10.0.0.3", 2), ("10.0.0.1", 1)]
assert top_ips_for_status(lines, "404", 5) == [("10.0.0.1", 1)]
assert top_ips_for_status([], "200", 3) == []
assert top_ips_for_status(lines, "200", 0) == []

# the input list must not change
original = list(lines)
top_ips_for_status(lines, "200", 2)
assert lines == original
```

**Explanation, line by line.**

- `filter_by_status` builds the `kept` list and then loops over the lines. `line.split(",")` makes a list of fields. The test `len(fields) == 4` skips blank lines and malformed lines, because a blank line gives one empty field and `"bad line"` gives one field. `fields[3] == str(status)` compares the status as text, so the number `200` and the text `"200"` both work. The whole original line is appended, so the output has the same format as the input.
- `extract_column` skips blank lines with `line.strip()`, which is empty for a blank line. The check `index < len(fields)` prevents an `IndexError` when a line is too short. For the input `["a,b,c", "", "d,e,f"]` with index 1, the function returns `["b", "e"]`.
- `count_items` counts with a dictionary. `counts.get(item, 0) + 1` starts a new item at 1 and adds one each time the item comes back. `list(counts.items())` gives the pairs.
- The sort key `(-pair[1], pair[0])` is the important line. The minus sign on the count makes larger counts sort first. Equal counts are then compared by the item in ascending text order. For `["b", "a", "b", "a"]` both items have count 2, so `"a"` comes first.
- `top_pairs` returns nothing for zero or a negative `n`. Otherwise `pairs[:n]` takes at most `n` pairs. If `n` is larger than the list, the slice simply returns every pair.
- `top_ips_for_status` is the pipeline. It filters, extracts, counts and cuts, in the same order as the shell pipeline, and each step hands its result to the next.
- The last three lines check that the function does not change its input. The copy `original` is made first, the function runs, and then the two lists are compared.

Write one function, `total_minutes(rows)`. It takes a list of such lines and returns a list of `(dock, total)` tuples. Each dock appears once, with the sum of its minutes.
```python test
def total_minutes(rows):
    totals = {}
    for row in rows:
        if not row.strip():
            continue
        dock, minutes = row.split(",")
        totals[dock] = totals.get(dock, 0) + int(minutes)
    pairs = list(totals.items())
    pairs.sort(key=lambda pair: (-pair[1], pair[0]))
    return pairs
```
