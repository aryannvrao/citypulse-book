## What the quiz tests

The Day Quiz has 10 case-study multiple-choice questions. Each one is about a single topic from today, so you get one question per topic, in the order this section follows. The pass mark is 70%. Your first attempt is the one your skill score keeps, so read the topics carefully before you start.

Every case-study question describes a team, a symptom and a constraint, then asks for one decision. Use this method on each one:

1. Read the last line first. It tells you what is being asked: the cause, the fix or the best next step.
2. Underline the facts in the scenario that matter. A port number, a password, a file name or a version usually matters. The story around them usually does not.
3. Eliminate options that are true in general but do not fix this scenario. A statement about Docker can be correct and still be the wrong answer.
4. Watch the words "most", "first" and "best". They mean that more than one option is partly right, and you must choose the one that fits this scenario most closely.
### Choosing the base image with FROM

**What it is.** A Dockerfile is a text recipe. `FROM` is the instruction that names the base image every later line builds on. A base image is a ready-made image with an operating system and a language runtime already installed, so you do not start from an empty machine.

An image name can carry a tag after a colon. The tag selects a version:

```dockerfile
FROM python:latest
FROM python:3.11.9-slim
```

The first line means "whatever Python release is newest today". The second pins Python 3.11.9, and `slim` leaves out many extra packages and build tools. The tag `latest` can point to a different image next month, so the same Dockerfile can produce a different result without anyone editing it.
A second `FROM` starts a new build stage.

**How it shows up in a case study.** A CityPulse API builds on Monday and fails on Friday with a library error, although nobody changed the Dockerfile. The first line reads `FROM python:latest`, so the base image moved overnight. The recipe did not change, but its input did. The right decision is to pin `python:3.11.9-slim` and rebuild, then move to a newer Python later as a tested change.

:::trap Choosing latest because it is newest
`latest` looks safe because it always has the newest release. The question is about reproducibility, though. A build that changes without any code change is the defect, so the fix is to pin the tag.
:::

```quiz
Q: A CityPulse Dockerfile begins with FROM python:latest. On Monday the image builds and the API starts. On Friday the build fails with a library error, and no line of the Dockerfile has changed. Which change stops this happening again?
- Add a RUN line that upgrades pip before the install
- Move the COPY of the code above the pip install
* Change the base line to a pinned tag such as python:3.11.9-slim
- Add --no-cache to the docker build command
WHY: The base image moved under an unchanged recipe, so pinning the tag fixes the input. The cache flag is tempting, but the failure is about which base is used.

Q: A colleague writes FROM python:slim for a service whose model was trained on Python 3.11. Both of you build the image on different days. What is the most likely problem with this line?
* It leaves the Python version unpinned, so the image can change under the same recipe
- The slim variant has no pip, so every pip install fails
- It starts a second build stage, which copies the wrong files
- It is only valid after an ARG line, so the build ignores it
WHY: A tag without a version moves as the image is updated, so the model may run on a different Python. The other options describe things Docker does not do.

Q: A reviewer asks what the second FROM does in a Dockerfile that has two FROM lines. Which answer is correct?
- It repeats the first stage, so the build runs twice and keeps the first image
- It is ignored, because only the first FROM is read
- It merges the two images into one layer by layer
* It starts a new build stage, and only the last stage becomes the final image
WHY: Each FROM starts a stage. The last stage is what Docker outputs unless you choose another target. The option that says only the first FROM is read is tempting, because the first line is usually the base, but a second FROM is read and begins a new stage.
```

### Publishing a port with -p

**What it is.** A container has its own network, so the API's port 8000 is unreachable from your laptop until you publish it. The flag is `-p host:container`:

```bash
docker run -p 8000:8000 citypulse-api:p8
```

In a second terminal, `curl -i localhost:8000/v1/health` should print `HTTP/1.1 200 OK`. The host port comes first. With `-p 9000:8000`, the API is reached at `localhost:9000`, while the process still listens on 8000 inside the container.

`EXPOSE 8000` in a Dockerfile only records which port the app uses. It publishes nothing. Also, the server must listen on all addresses inside the container. `--host 0.0.0.0` does that. If the server listens only on `127.0.0.1` inside the container, a published port still refuses connections.

**How it shows up in a case study.** A reviewer runs your image. The log says uvicorn listens on port 8000, but the browser cannot reach `localhost:8000`. The Dockerfile has `EXPOSE 8000`, and the run command has no `-p`. The server is fine, and the missing step is the publish. The right decision is to add `-p 8000:8000`, not to change EXPOSE or rebuild.

:::trap EXPOSE publishes the port
Seeing `EXPOSE 8000` looks as if the port is open. It is documentation only. Changing it to another number, or rebuilding, does not make the port reachable from the host.
:::

```quiz
Q: A CityPulse container logs that it listens on port 8000. The Dockerfile contains EXPOSE 8000, and the run command is docker run citypulse-api:p8. Your browser cannot reach localhost:8000. What is the most direct fix?
- Rebuild the image with --no-cache so the port is registered
* Add -p 8000:8000 to the docker run command
- Change EXPOSE to 8080 in the Dockerfile
- Set the environment variable PORT=8000 with -e
WHY: The server is running, so only the publish step is missing, and -p supplies it. Rebuilding does not publish a port, and neither EXPOSE nor an environment variable does. The PORT option is tempting, but nothing in the run command reads it.

Q: A teammate runs docker run -p 9000:8000 citypulse-api:p8 on a laptop. Another colleague says the API should be opened at localhost:8000 on this laptop. Which statement is correct?
- Use localhost:8000, because the container port is always the one you browse
- Use localhost:8000 only if the image has EXPOSE 9000
- Use localhost:8000, because uvicorn moves itself to the host port
* Use localhost:9000, because the host port is the left-hand number in -p
WHY: In -p host:container the left number is the host port, so the browser uses 9000. The first option swaps the two sides.

Q: The server in a container binds to 127.0.0.1:8000 inside the container. The run command publishes -p 8000:8000, but the host gets connection refused. Which change most likely fixes it?
* Change the server's bind address to 0.0.0.0, for example with --host 0.0.0.0 in CMD
- Change -p to 8000:9000
- Add EXPOSE 127.0.0.1 to the Dockerfile
- Remove the -d flag from docker run
WHY: Traffic from the host arrives on the container's external address, which a server bound only to 127.0.0.1 refuses. 0.0.0.0 accepts it.
```

### Keeping data in volumes

**What it is.** A container's filesystem belongs to that container. When the container is removed, its changes go with it. A volume is storage that Docker keeps outside the container, so data survives removal. Two kinds appear in CityPulse. A named volume has a name, and Docker decides where it lives:

```yaml
volumes: ["pgdata:/var/lib/postgresql/data"]
```

This keeps the Postgres database files in a volume called `pgdata`. A bind mount maps a file from your project into the container:

```yaml
volumes: ["./sql/init.sql:/docker-entrypoint-initdb.d/init.sql:ro"]
```

`:ro` makes it read-only inside the container. The Postgres image runs the scripts in `/docker-entrypoint-initdb.d` only on the first start, when the data folder is empty. If `pgdata` already holds a database, editing `init.sql` changes nothing. Removing the volume with `docker compose down -v` empties it, and that also deletes the data.

**How it shows up in a case study.** A developer adds a table to `sql/init.sql` and runs `docker compose up`, but the table is missing. The database volume already holds data from an earlier start, so the init step is skipped. If it is only test data, `docker compose down -v` resets it. If the data matters, apply the change to the existing database instead.

:::trap Editing init.sql and expecting a rerun
The script is not rerun on each start. Editing the file has no effect on a volume that already holds data. Deleting the volume fixes the symptom, but it also deletes every row.
:::

```quiz
Q: A developer edits sql/init.sql to add a table and runs docker compose up. The table is missing, and the pgdata volume holds test data from last week. What is the correct explanation and action?
- Compose caches the old file, so run docker compose build --no-cache
- The API must be restarted, because the database reads init.sql on each request
* The init script only runs on an empty data folder, so run docker compose down -v to empty the volume
- The new table must be declared with EXPOSE so Postgres sees it
WHY: Postgres skips init scripts when its data folder already holds data. Removing the volume empties it, which is acceptable only because the data is test data. The no-cache option is tempting, but the file is not cached; the volume is the issue.

Q: A team wants the new schema in init.sql applied to a production database that already holds customer data in the pgdata volume. Which statement is correct?
- Running docker compose down -v applies the schema and keeps the data
* Running docker compose down -v would delete the production data, so the change must be applied in a reviewed way instead
- Adding init.sql to .dockerignore makes Postgres apply it on the next start
- Renaming the volume to pgdata2 runs the script and keeps the old rows
WHY: Deleting the volume deletes the data. Ignoring the file has no effect on Postgres, and a new volume name creates an empty database rather than changing the existing one.

Q: A Compose file maps ./sql/init.sql into the container with :ro and keeps the database in pgdata. A reviewer asks what :ro does and whether the database survives docker compose down. Which answer is correct?
- :ro makes the file writable only by root, and down deletes pgdata
- :ro hides the file from the container, and down deletes pgdata
- :ro makes the file read-only, and down deletes pgdata
* :ro makes the mapped file read-only inside the container, and pgdata survives down because only down -v removes volumes
WHY: :ro sets read-only access for that one mapping. docker compose down stops and removes containers and networks but keeps named volumes. Only down -v also removes volumes.
```

### Reusing layers with the build cache

**What it is.** Each Dockerfile instruction creates a layer. During a build, Docker looks at each instruction and the files it reads. If nothing has changed since an earlier build, Docker reuses the stored layer and prints `CACHED`. If something changed, Docker runs that instruction again, and every instruction below it runs again too.
Take this order:

```dockerfile
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY api/ api/
```

Change one line in `api/main.py` and rebuild. The first COPY sees the same requirements file, so it is cached. The install depends on the layer above it, which did not change, so it is cached too. Only the last COPY runs again. Now put `COPY . .` above the install. Every code edit changes the copied files, so the copy reruns, and then the install reruns because the layer above it changed.
**How it shows up in a case study.** A rebuild takes four minutes after every small change, and the log shows the pip install running each time. The Dockerfile copies the whole project before the install, so any file change, even a README edit, invalidates the install layer. The right decision is to copy `requirements.txt` first, install, and copy the code afterwards.

:::trap Each line is cached on its own
Because the install line did not change, a candidate expects it to stay cached. Caching is a chain. A change high in the file invalidates every later line, even if those lines are unchanged.
:::

```quiz
Q: A Dockerfile copies the full project with COPY . . and then runs pip install. After a one-line change to api/main.py, the build reinstalls every package and takes four minutes. Which change gives the fastest rebuilds for code-only edits?
* Copy requirements.txt, run pip install, and then copy the project
- Add RUN pip cache purge before the COPY line
- Use the latest tag so the cache refreshes
- Add --no-cache to every build command
WHY: Reordering moves the install into a layer that does not depend on the code. --no-cache forces a full rebuild every time, which is slower. Purging the cache inside the build does not stop the copy layer from changing first.

Q: A developer edits only a README file. The build log shows COPY . . running again, and then RUN pip install also running again. Which answer explains the second run?
- Docker always runs pip install, because RUN lines are never cached
- The README edit changed requirements.txt, so the install must run
- The build cache was deleted by docker build
* COPY . . copies the README, which changed the layer above the install, so every later layer reruns
WHY: The README is part of the copied files, so the copy layer changes. Docker reuses a layer only when the layer above it is also reused. RUN lines are cached normally.

Q: A team wants fast CI builds. Developers change code many times a day but change dependencies rarely. Which Dockerfile order is best?
- COPY . . first, then WORKDIR, then requirements, then pip install
* WORKDIR, then COPY requirements.txt, then pip install, then COPY the code
- pip install first, then COPY requirements.txt, then the code
- COPY the code first, and put pip install at the end of the file
WHY: Stable inputs go at the top, so their layers stay cached. Installing before the requirements file is copied cannot work.
```

### Multi-stage builds

**What it is.** A multi-stage build has more than one `FROM` line, and each `FROM` starts a stage. A stage can be named with `AS`, and a later stage can copy files from it with `COPY --from=name`. Only the final stage becomes the image unless you choose another target. Here is the course pattern in short form:

```dockerfile
FROM python:3.11.9-slim AS builder
COPY requirements.txt .
RUN python -m venv /opt/venv && /opt/venv/bin/pip install --no-cache-dir -r requirements.txt

FROM python:3.11.9-slim
COPY --from=builder /opt/venv /opt/venv
```

The builder stage creates a virtual environment and installs the packages into it. The final stage starts clean and copies only `/opt/venv`, so the pip cache and any compiler stay behind in the builder. The venv must be copied to the same path it was created in, because its scripts contain that path.

**How it shows up in a case study.** A CityPulse image is over a gigabyte, and a scan reports hundreds of packages, many of them build tools that nothing uses at run time. The team installs in a builder stage and copies only the virtual environment and the code into the final stage. The problem is what was left over from installing, not what the app needs. The right decision is to split the stages, not to delete files in a later RUN line.

:::trap Every stage ends up in the image
A candidate thinks that because the builder stage ran, its tools are in the final image. Only the final stage becomes the image. Anything not copied with `COPY --from` is discarded with the builder.
:::

```quiz
Q: A builder stage installs a C compiler and a pip cache. The final stage runs COPY --from=builder /opt/venv /opt/venv, and a security scan then runs on the final image. What will the scan find?
- The compiler, because every stage is shipped in the image
- The pip cache, because COPY --from copies whole stages
- Nothing from the venv, because it is removed when the build ends
* The packages in /opt/venv and the base packages of the final stage, but not the compiler or the pip cache
WHY: COPY --from copies only the named path. The builder stage is discarded, so its compiler and cache are not in the image. The third option is tempting, but the copied venv stays in the image.

Q: A teammate copies /opt/venv from the builder to /home/app/venv in the final stage. When the container starts, uvicorn cannot be found. Which change most likely fixes it?
- Add EXPOSE for the venv folder in the final stage
- Use COPY --chown on the venv folder and nothing else
* Copy the venv to /opt/venv, the path it was created at, and put /opt/venv/bin first on PATH
- Use the latest base image so that the venv is rebuilt
WHY: The scripts in a venv refer to the path it was created at, so moving it breaks them. Keeping the original path and putting its bin folder on PATH makes the tools findable. Changing ownership does not solve a missing path.

Q: A reviewer asks you to prove that the final image does not include build tools. Which check is most direct?
* Run docker history on the final image to list its layers, and run a scan on the image
- Run docker build with --target builder and count the lines of output
- Count the FROM lines in the Dockerfile
- Run docker ps to see which tools the container is running
WHY: docker history lists each layer and its size, and a scan lists the packages present in the image. Counting lines describes the intent of the Dockerfile, not the image. docker ps lists running containers and does not show installed tools.
```

### CMD, ENTRYPOINT and arguments

**What it is.** `CMD` sets the default command that runs when a container starts. It can be written in JSON form or shell form:

```dockerfile
CMD ["uvicorn", "api.main:app", "--host", "0.0.0.0", "--port", "8000"]
CMD uvicorn api.main:app --host 0.0.0.0 --port 8000
```

The JSON form runs the program directly. The shell form runs it through `/bin/sh`. The shell can then be the process that receives a stop signal, so the server may not shut down cleanly. If you add arguments after the image name, they replace the whole CMD:

```bash
docker run citypulse-api:p8 --port 9000
```

Docker then tries to run `--port` as a program and fails. `ENTRYPOINT` is a fixed program that always runs. CMD then supplies its default arguments, so arguments given to `docker run` replace only the CMD part.

**How it shows up in a case study.** An operator wants the API on port 9000, so they add `--port 9000` after the image name. The container exits at once with an executable error, because the arguments replace CMD and Docker tries to run `--port`. The right decision is to publish with `-p 9000:8000`, which keeps the server on 8000 inside the container.

:::trap Arguments are added to CMD
A candidate expects the extra arguments to be appended to the existing list. They replace it. The uvicorn command never runs, so its settings never matter.
:::

```quiz
Q: An image has CMD ["uvicorn", "api.main:app", "--port", "8000"]. An operator runs docker run citypulse-api:p8 --port 9000, and the container exits at once with an executable-not-found error. What is the cause?
- Port 9000 is not allowed, so Docker blocks the container
* The extra arguments replace the whole CMD, so Docker tries to run --port as a program
- The image has no EXPOSE line, so the start fails
- Uvicorn cannot bind to port 9000 inside a container
WHY: Without an ENTRYPOINT, arguments after the image name replace CMD, so Docker looks for a program named --port. Uvicorn never starts, so it never tries to bind a port. The last option is tempting, but the failure happens earlier.

Q: A team uses CMD uvicorn api.main:app --host 0.0.0.0 in shell form. When they stop the container, the server takes the full timeout and is then killed. Which change best addresses the cause?
* Change CMD to the JSON form, so uvicorn runs as the main process and receives the stop signal
- Add EXPOSE 8000 so Docker knows the port
- Change the port in the health check
- Add -p 8000:8000 to the stop command
WHY: In shell form, /bin/sh is the main process, and the stop signal may not reach uvicorn. JSON form runs uvicorn directly. The port options do not affect how the process stops.

Q: A team wants one image that runs the API, or runs a one-off migration script, by changing only the arguments. They set ENTRYPOINT ["python"] and CMD ["-m", "api"]. Which statement is correct?
- ENTRYPOINT is replaced by CMD, so python never runs
- Any arguments after the image name always replace ENTRYPOINT
- The image cannot run a migration, because ENTRYPOINT and CMD cannot both be set
* python always runs, and arguments given after the image name replace only the CMD defaults
WHY: The entrypoint stays fixed, so python always starts. Arguments given to docker run replace CMD, so running the image with migrate.py runs python migrate.py. ENTRYPOINT and CMD are designed to be used together.
```

### Setting environment variables at run time

**What it is.** An environment variable is a named value that a program reads when it starts. `ENV` in a Dockerfile sets one inside the image:

```dockerfile
ENV PYTHONUNBUFFERED=1
```

Every container started from that image gets the value. The `-e` flag sets a value for one container when you run it:

```bash
docker run -e DATABASE_URL="$DATABASE_URL" citypulse-api:p8
```

A value given with `-e` overrides the value in the image, for that container only. Because `ENV` values are stored in the image, anyone who has the image can read them with `docker inspect`. A password written with `ENV` is therefore a leaked password.
**How it shows up in a case study.** A developer writes a database password into the Dockerfile with `ENV`, and the image is pushed to a shared registry. A reviewer runs `docker inspect` and reads the password. The value belongs to the image, not to the run. The right decision is to remove the line, pass `DATABASE_URL` with `-e` at run time, and change the password, which is already exposed.

:::trap ENV is safe because the container is private
A candidate assumes that a container's settings stay private. They are stored in the image, and anyone with the image can read them.
:::

```quiz
Q: A Dockerfile contains ENV DATABASE_URL=postgresql://app:realpass@db:5432/citypulse, and the image is pushed to a shared registry. Which fix keeps the password out of the image while the container still connects?
- Keep the ENV line and delete the image from the registry
- Change ENV to ARG, which is hidden from docker inspect
* Remove the password from the Dockerfile, pass DATABASE_URL with -e at run time, and change the password
- Add the password to .dockerignore so it is not copied
WHY: Deleting the image from the registry does not remove copies others pulled. An ARG value still shows in the build history. The password must be changed, because it was exposed.

Q: Your laptop has a local Postgres, and a teammate's container needs a different database. Which statement about ENV and -e is correct?
- A value set with ENV cannot be changed when the container starts
- A value set with -e is saved into the image for the next build
- ENV and -e cannot set the same name, so the build fails
* A value set with -e overrides the image's ENV value for that one container only
WHY: The -e value applies when the container starts, and it overrides the image value without changing the image. ENV values can be replaced at run time, so the first option is wrong.

Q: An API container connects to localhost:5432 and gets connection refused, although Postgres runs on the laptop. What is the cause and the fix?
- Port 5432 is not published, so add -p 5432:5432 to the API container
* Inside a container, localhost means the container itself, so set DATABASE_URL to a host name the container can reach, such as host.docker.internal on Docker Desktop
- The ENV line is ignored, so add the value to CMD
- Postgres must be installed inside the image, so add an apt install line
WHY: The API connects from inside its own container, so localhost points at the API container. Publishing port 5432 would let the laptop reach a container, but it does not change the address the API uses. Installing Postgres in the image is not needed.
```

### Running services with Compose

**What it is.** Docker Compose starts several containers from one file, `docker-compose.yml`. Each entry under `services` is one container. Compose creates a private network for them, and each service can be reached by its service name, which acts as a hostname:

```yaml
services:
  db:
    image: postgres:16-alpine
  api:
    build: .
    depends_on:
      db:
        condition: service_healthy
```

The sketch omits the healthcheck on `db`, which the course file includes. `depends_on` with `condition: service_healthy` makes `api` wait until `db` reports healthy. Without the condition, `depends_on` only sets the start order, so it cannot know when Postgres accepts connections. Inside the API container, the host in `DATABASE_URL` is `db`, not `localhost`. Run the stack with `docker compose up --build -d` and check it with `docker compose ps`, which shows `(healthy)` next to `db`.

**How it shows up in a case study.** A team's API crashes with connection refused for Postgres, then works on a restart. Adding a plain `depends_on` makes the crash rarer but not gone, because it controls start order only. The right decision is a `pg_isready` healthcheck on `db`, and `condition: service_healthy` on `api`.

:::trap depends_on means the database is ready
A list-style `depends_on` or one without a condition looks like a guarantee. It controls only the start order. The database process can still be starting when the API connects.
:::

```quiz
Q: A team's API crashes on start because Postgres is still starting. The Compose file has depends_on: [db]. What change makes the API wait until Postgres accepts connections?
* Add a pg_isready healthcheck to db, and set depends_on with condition: service_healthy on api
- Add ports: 5432:5432 to the api service
- Add more service names to the depends_on list
- Add restart: always to the db service only
WHY: A list form sets the start order only, and the condition needs a healthcheck to evaluate. Publishing ports and restart policies do not make the API wait for readiness.

Q: A developer's API has DATABASE_URL pointing at localhost:5432 and fails, although docker compose ps shows db as healthy. Which change fixes it?
- Make db publish port 5432 on localhost
- Add depends_on with no condition to the api service
* Change the host in DATABASE_URL to db, the service name on the Compose network
- Remove the healthcheck from the db service
WHY: Inside the API container, localhost is the API container itself, so the connection never reaches db. The service name works across the Compose network, and publishing a port is not needed for containers to reach each other.

Q: A team runs docker compose stop and then docker compose up. Which statement about the database data is correct?
- docker compose stop deletes the pgdata volume
- up creates a new empty pgdata volume each time it runs
- The data is saved only inside the API image, so it is lost on stop
* docker compose stop keeps the containers and volumes, so up starts them again with the data intact
WHY: stop halts the containers but keeps them and their volumes. The first option is tempting, because people confuse stop with down -v.
```

### Keeping files out with .dockerignore

**What it is.** When you run `docker build`, Docker sends the build context to the builder first. The build context is the folder named at the end of the command, here the dot, and it is everything `COPY . .` can reach. A file named `.dockerignore` lists paths that are left out of that context. Left-out files cannot be copied into the image:

```text
.git
.venv
.env
data/raw
```

With these lines, the build does not send `.git`, the local virtual environment, `.env` or the raw data folder, so the image is smaller and the secrets stay out. It does not delete anything from your disk, and it does not change Git. An image built earlier still contains whatever it copied, until you rebuild.

**How it shows up in a case study.** A team's image is two gigabytes and contains a `.git` folder, a large virtual environment and a `.env` file, because `COPY . .` takes everything in the context. The right decision is a `.dockerignore` file and a rebuild. The team also checks that `.env` was never committed to Git.

:::trap Adding a file to .dockerignore removes it from Git
A candidate adds `.env` to `.dockerignore` after a secret was committed, and believes the secret is gone. The file stays in Git history and in any image built before the change.
:::

```quiz
Q: A CityPulse image is two gigabytes. The build context holds .git, a local .venv and a .env with secrets, and the Dockerfile uses COPY . . Which change is the cleanest fix?
- Add RUN rm -rf .git .venv .env after the copy
* Add .git, .venv and .env to .dockerignore, then rebuild
- Add EXPOSE lines for the three paths
- Add the three paths to requirements.txt
WHY: .dockerignore keeps the files out of the build context, so they never reach the image. A RUN line that deletes them leaves them in the layer created by the copy, and that layer still counts towards the image size.

Q: A developer committed .env with a database password to Git. The next day they added .env to .dockerignore and pushed. A reviewer asks whether the password is still exposed. Which answer is correct?
- No, because .dockerignore removes the file from Git
- No, because the password is removed from new images and the commit is cleared
- Only the first commit exposes it, so the next commit fixes it
* Yes, the password stays in Git history and in any image built earlier, so it must be rotated
WHY: .dockerignore changes only what a build sends, so the old commit still holds the password. Rotating the secret is the real fix.

Q: The team's Dockerfile copies the project with COPY . ., and the context includes a three-gigabyte data/raw folder that the image does not need. Which action helps most directly?
- Add data/raw to requirements.txt
- Add a USER line before the COPY line
* Add data/raw to .dockerignore, so it is not sent in the build context
- Run docker build with --no-cache, so the context is skipped
WHY: The context is sent before the build starts, so excluding the folder saves transfer time and keeps it out of the image. --no-cache changes layer reuse, not the context.
```

### Running as a non-root user

**What it is.** By default, container processes run as `root`, the user with the most power. A normal user has fewer powers, so an attacker gets less. The `USER` instruction changes that:

```dockerfile
COPY --chown=10001:10001 api/ api/
USER 10001
```

`USER 10001` runs the later build steps and the container's processes as user number 10001, even when the image has no user with that name. Files copied into the image are owned by root unless you add `--chown`, which sets the owner as the file is copied. To check the result, run `docker exec cp-api id -u`, which should print `10001`. If it prints `0`, the process is root.

**How it shows up in a case study.** A team adds `USER 10001` for a security review. The API starts, but the first request that writes a cache file fails with a permission error, because the copied folders are owned by root. The right decision is `--chown=10001:10001` on the COPY lines, not root rights.

:::trap USER alone is enough
Adding `USER 10001` without `--chown` looks complete. The process runs as the new user, but the files it writes to may still belong to root.
:::

## The graded lab

The graded lab is a Python task. You read a Dockerfile as plain text and write two functions that check it. You do not build or run any Docker image, and you do not need Docker installed to pass.

### The task in plain words

**The scenario.** Before a CityPulse service image ships, a pre-commit check scans its Dockerfile for common security and reproducibility problems. A Dockerfile is a text file of instructions, one per line. Each instruction starts with a keyword such as `FROM`, `USER` or `ENV`, followed by its argument. Your job is to read that text and report the problems.

You write two module-level functions. The names and the parameters are fixed, and the platform calls them by name.

- `parse_instructions(text: str) -> list[tuple]` returns a list with one `(INSTRUCTION, argument)` tuple for each line. The rules are:
  - Blank lines are skipped.
  - Comment lines, which begin with `#`, are skipped. Treating an indented `#` line as a comment (after stripping its leading spaces) is the natural reading, but the statement does not say so. Ask your trainer if unsure, and strip each line before you test for `#`.
  - The keyword is uppercased, so `from` becomes `FROM`.
  - The argument is the rest of the line with the spaces at both ends removed.
  - If a line has no argument, the argument is the empty string `""`, not `None`.
  - Example: `parse_instructions("# base image\nFROM python:3.11\nUSER app\n")` returns `[('FROM', 'python:3.11'), ('USER', 'app')]`.
- `lint_dockerfile(text: str) -> list[str]` returns a sorted list of anti-pattern codes. There are four codes, and each one means:
  - `unpinned_base`: a `FROM` image whose tag is missing or is `latest`.
  - `runs_as_root`: there is no `USER` instruction, or the last `USER` instruction names `root`.
  - `no_healthcheck`: there is no `HEALTHCHECK` instruction anywhere in the file.
  - `secret_in_env`: an `ENV` instruction whose key contains `KEY`, `SECRET`, `TOKEN` or `PASSWORD`, in any letter case.
  - Example: `lint_dockerfile("FROM python:latest\nENV API_KEY=abc123\nRUN pip install flask\nCOPY . /app")` returns `['no_healthcheck', 'runs_as_root', 'secret_in_env', 'unpinned_base']`.

| Test | Points |
|---|---|

| All four anti-patterns present | 25 |

**Hidden tests.** The platform also runs three hidden tests, worth 30 points together. A hidden test is an input you cannot see. ### What each function needs

Each idea below is taught with a small example that does not use the lab's data. Try each one in a shell before you use it.

- **Splitting lines.** `splitlines()` cuts text into lines, and `strip()` removes spaces at both ends. The two differ on empty text: `"".splitlines()` returns `[]`, while `"".split("\n")` returns `['']`. Your function should give `[]` for empty input.
- **Splitting off the first word.** `split(None, 1)` splits on any run of spaces and stops after one cut. `"brew  hot  tea".split(None, 1)` returns `['brew', 'hot  tea']`, and `"brew".split(None, 1)` returns `['brew']`. The second case has no argument, so you must supply `""` yourself.
- **Splitting on a separator that may be missing.** `partition(":")` returns three parts, always. `"cake:chocolate".partition(":")` returns `('cake', ':', 'chocolate')`, and `"cake".partition(":")` returns `('cake', '', '')`. You can tell whether the separator was present by checking the middle part.
- **Changing case for comparison.** `upper()` and `lower()` return a new string. `"Tea".upper()` returns `'TEA'`. The original string is unchanged. Compare the uppercased form when a rule ignores case.
- **Substring tests.** `in` on strings checks whether one string sits inside another. `"ch" in "chocolate"` returns `True`. Note that this is a substring test: `"ant" in "elephant"` is also `True`.
- **Testing several words at once.** `any()` returns `True` if at least one item in an iterable is true. `any(c in "GREEN TEA".upper() for c in ("TEA", "MILK"))` returns `True`, because one item matches.
- **Sorting a list.** `sorted()` returns a new sorted list and leaves the original alone. `sorted(["pear", "apple", "fig"])` returns `['apple', 'fig', 'pear']`.
- **Remembering the last match.** Set a variable to `None` before a loop, and overwrite it inside the loop each time you see a match. After the loop, the variable holds the last match. A list `[7, 3, 9]` with `last = None` and `if x > 5: last = x` ends with `last == 9`.
- **Building tuples.** A tuple is a fixed group of values in parentheses. `[(word, len(word)) for word in ["ann", "bo"]]` returns `[('ann', 3), ('bo', 2)]`.
- **Empty text.** `if not text:` is true for `""` and for an empty list. Test empty input first, because many hidden tests use it.

### Worked twin problem

The real lab checks a Dockerfile. This twin checks a Procfile, the file that tells a hosting platform which processes to start. It needs the same skills: splitting lines, uppercasing or normalising a keyword, returning tuples, collecting findings and returning them sorted.

**Task.** A Procfile has one process per line in the form `name: command`. Write two module-level functions.

- `parse_procfile(text: str) -> list[tuple]` returns one `(name, command)` tuple for each line. Blank lines and comment lines starting with `#` are skipped. Both the name and the command are stripped of spaces. A line with no colon gives a name equal to the whole line and the command `""`.
- `lint_procfile(text: str) -> list[str]` returns a sorted list of codes:
  - `no_web`: no process is named `web`.
  - `unknown_process`: a name is not one of `web`, `worker` or `release`. Names are case-sensitive, so `Web` is unknown.
  - `duplicate_process`: a name appears more than once.
  - `empty_command`: a command is empty after the spaces are removed.

Examples: `parse_procfile("# app\nweb: gunicorn app:app\n\nworker: python jobs.py\n")` returns `[('web', 'gunicorn app:app'), ('worker', 'python jobs.py')]`. `lint_procfile("Web: a\n")` returns `['no_web', 'unknown_process']`.

Try to write `lint_procfile` yourself from the rules above before you read the solution. Then compare your result with the solution, and run both against the asserts.

**Solution.**

```python test
KNOWN = {"web", "worker", "release"}


def parse_procfile(text):
    entries = []
    for raw in text.splitlines():
        line = raw.strip()
        if not line or line.startswith("#"):
            continue
        name, _, command = line.partition(":")
        entries.append((name.strip(), command.strip()))
    return entries


def lint_procfile(text):
    entries = parse_procfile(text)
    codes = set()
    names = [name for name, _ in entries]
    if "web" not in names:
        codes.add("no_web")
    seen = set()
    for name, command in entries:
        if name not in KNOWN:
            codes.add("unknown_process")
        if name in seen:
            codes.add("duplicate_process")
        seen.add(name)
        if command == "":
            codes.add("empty_command")
    return sorted(codes)


assert parse_procfile("") == []
assert parse_procfile("# app\nweb: gunicorn app:app\n\nworker: python jobs.py\n") == [
    ("web", "gunicorn app:app"),
    ("worker", "python jobs.py"),
]
assert parse_procfile("release:\n") == [("release", "")]
assert parse_procfile("worker\n") == [("worker", "")]
assert lint_procfile("web: gunicorn app:app\nworker: python jobs.py\n") == []
assert lint_procfile("") == ["no_web"]
assert lint_procfile("worker: run\n") == ["no_web"]
assert lint_procfile("web: a\nweb: b\n") == ["duplicate_process"]
assert lint_procfile("web: a\ncron: b\n") == ["unknown_process"]
assert lint_procfile("web:\nrelease: x\n") == ["empty_command"]
assert lint_procfile("Web: a\n") == ["no_web", "unknown_process"]
assert lint_procfile("web: a\nweb: \n") == ["duplicate_process", "empty_command"]
```

**Line by line.**

- `KNOWN` is a set of the three allowed names. A set answers "is this name allowed?" quickly, and it keeps the list in one place.
- `parse_procfile` builds an empty list and walks the lines. `text.splitlines()` cuts the text into lines, and `raw.strip()` removes the spaces at both ends.
- The `if` line skips a blank line, and a line that starts with `#`. A blank line is empty after stripping, so `not line` is true for it.
- `line.partition(":")` splits the line at the first colon into three parts. The middle part is the colon itself, which is not needed, so the code assigns it to `_`. A line with no colon gives the whole line as `name` and an empty `command`.
- `name.strip()` and `command.strip()` remove the spaces around each part, so `web: gunicorn app:app` gives the command `gunicorn app:app`.
- `lint_procfile` calls `parse_procfile`, so both functions agree about what a line means.
- `codes = set()` collects findings. A set stores each code once, so a repeated finding does not appear twice.
- `names = [name for name, _ in entries]` builds a list of names. The `_` ignores the command. The `no_web` check is `"web" not in names`, which is a membership test on a list.
- `seen` records the names already met. For each entry, `name in seen` is true only for a repeat, which is how `duplicate_process` is found. Then `seen.add(name)` records the name for later lines.
- `command == ""` checks for an empty command. The parser has already removed the spaces, so this comparison is enough.
- `sorted(codes)` turns the set into a sorted list of strings. Sorting works on strings alphabetically.

Running the block prints nothing. Every `assert` passes, so the program ends without an error. An assert that fails stops the run and shows a message, which is how the build checks the solution.

def summarise_gauges(text):
    totals = {}
    for raw in text.splitlines():
        line = raw.strip()
        if not line or line.startswith("#"):

        parts = line.split()
        if len(parts) != 2:
            continue

        try:

        except ValueError:

        values = totals[station]
        result.append((station, round(sum(values) / len(values), 1)))
    return result
