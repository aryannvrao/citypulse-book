## What the quiz tests

The Day Quiz has ten case-study multiple-choice questions, one for each topic in this section, in the order given here. You need 70% to pass, which means seven correct answers. Your skill score keeps the result of your first attempt. A second attempt helps you learn, but it does not change the score. Every question describes a team, a symptom or a constraint, and then asks for a decision.

Answer each case-study question in this order. First, read the last line of the question to find what is being asked. Many students read the scenario first and lose track of the task, so know the task before you sort the facts. Second, underline the facts in the scenario that matter: the schedule, the path, the error message, the constraint. Third, eliminate options that are true in general but do not fix this scenario. A correct fact can still be the wrong answer. Fourth, watch for three words. "Most" asks for the strongest answer among several sensible ones. "First" asks what to do before anything else. "Best" asks for the option with the fewest downsides for this team.

Each topic below follows the same pattern. You get a plain explanation with a small example and its output, a short CityPulse scenario, a trap box that shows the tempting wrong answer, and three practice questions. Each section ends with a self-test of ten mixed questions. Read the explanation before you try the questions. Every WHY line explains the right answer and why the most tempting wrong option fails.

### The shebang line

**What it is.** The shebang is the first line of a script. It starts with the two characters `#!` and is followed by the path of the program that should run the file. For a Bash script the line is `#!/usr/bin/env bash`. When you type `./pull.sh`, the system reads those first two characters, starts the named program and gives it the file. The line must be the very first thing in the file. A blank line, a space or a comment above it means the system does not see a shebang at all. `/usr/bin/env` searches PATH for `bash`, so the line works on machines where Bash lives in a different folder.

```bash
#!/usr/bin/env bash
echo "pulled readings"
```

Running `./pull.sh` prints `pulled readings`. Running `bash pull.sh` prints the same line, but there the shebang is ignored, because you have named Bash yourself. Bash also treats the shebang as a comment, since it starts with `#`.

**How it shows up in a case study.** The CityPulse squad keeps `fetch.sh` in Git. Ruth's laptop has Bash installed in a folder other than `/bin`, and the lab server has it in `/bin`. Ruth pastes the script into a chat message, and her editor adds a blank first line. On the lab server, Mohan runs `./fetch.sh` and the file does not start with Bash through its first line, although `bash fetch.sh` still works. The right decision is to delete the blank line, so that `#!/usr/bin/env bash` is the first line again. Keep `env`, because it lets both machines find Bash.

:::trap A blank line above the shebang
It is tempting to think that Bash skips whitespace, so a blank line does no harm. For the shebang it does. The system reads the first two bytes of the file, so `#!` must be there and nothing else can come first.
:::

```quiz
- Bash reads only shebangs that name /bin/bash.
* The shebang must be the first two characters of the file, so on line 2 it is only a comment.

WHY: The system reads the shebang only when #! are the first two characters. The tempting answer is that blank lines are skipped, but no such exception exists.

WHY: env searches PATH for bash, so the line works wherever Bash is installed. A hard-coded /bin/bash does not point at the Bash in /opt/homebrew/bin, and a bare name without a path is not looked up in PATH, so it does not work reliably.
```

### Positional arguments

**What it is.** Arguments are the values typed after a script name. Inside the script they are numbered. `$0` holds the script name, `$1` the first argument, `$2` the second, and so on. `$#` holds the number of arguments. `"$@"` holds all the arguments, each kept as its own word even when it contains a space. Positions above nine need braces, so the tenth argument is `${10}`.

```bash
#!/usr/bin/env bash
echo "script: $0"
echo "station: $1"
echo "count: $#"
```

Running `./show.sh CP-001 pm25` prints `script: ./show.sh`, then `station: CP-001`, then `count: 2`. The script name is not counted in `$#`. The command `shift` drops `$1` and moves every later argument down by one place, so the old `$2` becomes `$1`.

**How it shows up in a case study.** The squad's `backfill.sh` takes a station id in `$1` and a start date in `$2`. Priya runs `./backfill.sh CP-004` and forgets the date. Because the script runs with `set -u`, it stops with an error about an unbound variable at the point where `$2` is used. The right decision is to check `$#` at the top of the script, print a usage line that shows both arguments, and exit with status 1 before the script touches the network or the data folder.

:::trap Writing $10 for the tenth argument
`$10` means the first argument followed by a zero, so the script receives the value of `$1` with a 0 added. Write `${10}` when you need the tenth argument.
:::

```quiz
Q: Ben starts a script as ./import.sh data/cp.csv 2026-11-03 strict. Inside the script he writes echo "$3". What is printed?
- data/cp.csv
* strict
- 2026-11-03
- 3
WHY: $3 is the third argument after the script name. $1 is the file and $2 is the date. The tempting answer 3 confuses the position with the value stored there.

Q: A script receives twelve arguments, and its author writes echo "$10" to print the tenth one. What happens?
- It prints the tenth argument, as intended.
- It prints an error, because positions above nine are not allowed.
- It prints nothing, because numbers above nine are ignored.
* It prints the first argument followed by a zero.
WHY: Bash reads $10 as $1 followed by the text 0. The tenth argument needs braces, written ${10}. The tempting answer assumes the number is read as a whole.

Q: A script is run as ./copy.sh "north dock" south. It loops with for f in "$@" and echoes each item. How many lines are printed, and what is the first?
* Two lines, the first being north dock.
- Three lines, the first being north.
- Two lines, the first being "north.
- One line, containing north dock south.
WHY: "$@" keeps each argument as one word, so the quoted name stays together. The tempting answer splits it at the space, which is what an unquoted $@ would do.
```

### Strict mode with set -euo pipefail

**What it is.** `set -e` stops the script when a command returns a non-zero exit code. `set -u` stops it when a variable that was never set is used. `set -o pipefail` makes a pipeline fail when any command in it fails, not only the last one. Strict mode has one important exception: a failure inside the condition of an `if` is handled by the `if`, so `-e` does not stop the script there.

```bash
#!/usr/bin/env bash
set -euo pipefail
false | true
echo "still running"
```

This script prints nothing. The pipeline `false | true` fails because of `pipefail`, so `-e` stops the script on line 3 and the second `echo` never runs. Without `pipefail`, the pipeline would report the status of `true`, which is 0, and the script would print `still running`.

**How it shows up in a case study.** The nightly job runs `curl -sS --fail "$URL" | jq '.readings' > data/today.json`. The API returns a 404. `curl` fails, and `jq` receives nothing and exits with 0, so without `pipefail` the file is written as empty and the job reports success. The team needs the job to stop. With `set -euo pipefail` the pipeline fails as a whole, and `-e` stops the script at that line, so the empty file is never trusted.

:::trap Assuming -e stops for every failure
`-e` does not stop the script for a failing command used as an `if` test, and it does not see a failure inside the first command of a pipeline unless `pipefail` is on. The tempting belief is that strict mode catches everything. Check each case.
:::

```quiz
Q: A script runs cat missing.txt | sort > out.txt under set -euo pipefail. The file is missing, so cat fails, but sort succeeds and writes an empty out.txt. What happens next?
- The script carries on, because sort succeeded and only the last command counts.
- The script carries on, because -e never applies to pipelines.
* The script stops, because pipefail makes the pipeline fail when cat failed.
- The script stops, because -u stops on any missing file.
WHY: pipefail makes the status of a pipeline the rightmost non-zero status, so the failed cat stops the script. -u is about variables that were never set, not about files. The tempting answer is what Bash does without pipefail.

Q: A script sets NAME="" on purpose and later uses "$NAME". It runs under set -u. What happens?
* The script carries on, because the variable is set, even though its value is empty.
- The script stops at the assignment, because empty values are not allowed.
- The script stops at the use, because the variable is empty.
- The script stops only if NAME is used inside an if test.
WHY: -u checks whether a variable has been set, not whether it holds text. An empty string is a value. The tempting answer confuses empty with unset.

Q: A script under set -e runs if grep -q ERROR logs/fetch.log; then echo found; fi. There are no ERROR lines, so grep returns 1. Does set -e stop the script at this line?
- Yes, because grep returned 1, which is a failure.
- Yes, because -e stops on any non-zero status.
- Only if pipefail is also active.
* No, because a command used as the test of an if is handled by the if.
WHY: The condition of an if is designed to handle failure, so set -e ignores it. The tempting answer is that -e stops on every non-zero status.
```

### Looping over a list with for

**What it is.** A `for` loop runs its body once for each word in a list. `for id in CP-001 CP-002; do echo "$id"; done` prints two lines. The list can also be a pattern such as `data/readings/*.json`. Bash replaces an unquoted pattern with the names of the matching files before the loop starts, and each name becomes one word. The loop variable keeps its last value after the loop has finished.

```bash
for f in data/readings/*.json; do
  echo "$f"
done
```

If the folder holds `2026-11-01.json` and `2026-11-02.json`, the output is two lines, one per file, in sorted order. If you add a third file, the loop runs three times without any change to the script.

**How it shows up in a case study.** The squad counts readings for each station file in one folder. Sam writes `for f in "data/readings/*.json"` with quotes. The quotes stop the expansion, so the loop receives one word, the text with the star in it. It runs once and reports zero readings for a file that does not exist. The right decision is to remove the quotes around the pattern. Quote the variable inside the loop, as in `"$f"`, to keep names with spaces intact.

:::trap Quoting the pattern
Quotes around a pattern stop the shell from expanding it. The loop then runs once with the literal text, not once per file. Remove the quotes around the pattern and keep quotes around the variable.
:::

```quiz
Q: The folder data/readings holds 2026-11-01.json, 2026-11-02.json and 2026-11-03.json. A script contains for f in data/readings/*.json; do echo "$f"; done. How many lines does it print?
* Three, one for each file name.
- One, showing the text data/readings/*.json.
- Zero, because an unquoted pattern is never expanded.
- Three, but each line shows only the date part of the name.
WHY: The shell expands an unquoted pattern into the matching file names before the loop starts. The quoted version would give one literal word, which is the tempting answer.

Q: A script sets count=0 and then runs for id in CP-001 CP-002 CP-003; do count=$((count + 1)); done. What are count and id after the loop?
- count is 3 and id is empty.
- count is 0, because the loop variable is local to the loop.
* count is 3 and id is CP-003.
- count is 2, because the last item is skipped.
WHY: The loop runs three times and the variable id keeps its last value. The tempting answer assumes the loop variable is cleared at the end.

Q: A teammate writes for id in "CP-001 CP-002"; do echo "$id"; done and expects two lines. What does the script print?
- CP-001 and CP-002 on two lines.
* CP-001 CP-002 on one line.
- Nothing, because the quotes stop the loop.
- An error, because a loop needs a list without quotes.
WHY: The quotes make the whole text one word, so the loop runs once and prints the text with a space in it. The tempting answer is two lines, which needs the list to be unquoted.
```

### Reading a cron schedule

**What it is.** A crontab line has five schedule fields and then a command. The fields are minute (0 to 59), hour (0 to 23), day of month (1 to 31), month (1 to 12) and day of week (0 to 6, where 0 is Sunday). An asterisk means every value. `*/n` means every n units, counted from zero, so `*/15` in the minute field fires at 0, 15, 30 and 45. A comma makes a list, and a hyphen makes an inclusive range that includes both ends.

```bash
*/30 9-17 * * 1-5 bash scripts/fetch.sh
```

This line runs the script at minutes 0 and 30 of hours 9 to 17, on Monday to Friday. That is 18 runs a day, from 09:00 to 17:30, and none at weekends.

**How it shows up in a case study.** The sponsor wants the ingest to run every 30 minutes from 08:00 to 17:30 on working days, and nothing outside those hours. Lee writes `*/30 8-17 * * 1-5`. The minute field handles the 30-minute rhythm, the hour field holds the window, and the weekday field limits the job to Monday to Friday. The other two fields stay as stars, because the sponsor did not mention a day of the month or a month. The decision is to keep the five fields in order and to use the step only in the minute field.

:::trap A step in the wrong field
The line `0 */30 * * *` looks like a half-hourly job, but the step is in the hour field. Hours only run from 0 to 23, so `*/30` matches hour 0 alone, and the job runs once a day at midnight.
:::

```quiz
Q: A crontab line reads 0 */6 * * * bash fetch.sh. At which times does the job run?
- Every six minutes, at all hours.
- Once a day at 06:00.
- Every hour, on the sixth minute.
* At minute 0 of hours 0, 6, 12 and 18.
WHY: The first field is the minute and the second is the hour. The hour step */6 matches 0, 6, 12 and 18, and the minute 0 fixes the time. The tempting answer assumes the step belongs to the minute field because it appears first.

Q: A job must run at 09:00 and 17:00 every Monday to Friday. Which five fields are right?
- 9,17 0 * * 1-5
* 0 9,17 * * 1-5
- 0 9-17 * * 0-5
- 0 9 17 * * 1-5
WHY: The order is minute, hour, day of month, month, day of week. Minute 0 with the hour list 9,17 is right. 9-17 would run every hour in the range, 0-5 includes Sunday, and 17 in the day-of-month field would run the job only on the 17th.

Q: A job must run every 15 minutes, but only during the hour from 02:00 to 02:45. Which five fields are right?
- */15 * 2 * *
- 15 2 * * *
* */15 2 * * *
- 0,15,30,45 * 2 * *
WHY: The minute field is */15 and the hour field is 2. The tempting answer */15 * 2 * * puts the hour in the day-of-month field, so it runs on the second of every month. The answer 15 2 * * * runs only once.
```

### The cron environment

**What it is.** cron starts each job in a minimal environment. The PATH is short, there is usually no terminal, settings in your `.bashrc` are not loaded, and the working directory is your home folder. A command that works when you type it may not be found under cron. A crontab line such as `*/30 * * * * jq --version >> logs/cron.out 2>&1` can write `command not found` to the log when `jq` is installed in a folder that cron's PATH does not search (on some systems `jq` is in `/usr/bin`, which cron does search, so the example depends on where your machine installs it). Three fixes are common: give the full path to the program, set PATH at the top of the script, or load settings from a file such as `.env` inside the script.

```bash
#!/usr/bin/env bash
export PATH="/usr/local/bin:/usr/bin:/bin"
command -v jq
```

`command -v jq` prints the path of `jq` when it can find it, and prints nothing with a failing status when it cannot. Put the PATH line before any command that needs a program, and cron finds the program in the same way your terminal does.

**How it shows up in a case study.** Dev's script `render.sh` uses the program `convert`, which the laptop installs in `/usr/local/bin`. The same script runs by hand on the laptop, but under cron the log says `convert: command not found`. The program is installed and works by hand, so the problem is cron's short PATH, not a missing program. The best decision is to set PATH in the script, or give the full path to `convert`, which needs no change to the crontab. Running cron as root is not needed and would not be safe.

:::trap Running cron as root
Running the job as root would let cron find more programs, but it is unnecessary and unsafe. The fix is a full path or a PATH line in the script, which works for any user.
:::

```quiz
Q: Mira's script runs convert on a PNG file. It works in her terminal, but the cron log says convert: command not found. Which fix is right?
* Give the full path to convert in the script, or set PATH at the top of the script.
- Run the job as the root user so that it can see every program.
- Change the schedule to */2 so that it retries more often.
- Add set -x so that the log shows more detail.
WHY: cron starts with a short PATH, so the shell cannot find convert. The full path or a PATH line fixes it. Root is the tempting but unsafe answer, and set -x adds detail without changing where Bash looks.

Q: A script loads its settings from .env, which holds API_URL. Under cron the script reports that API_URL is unset, although it is set in Ana's terminal. Which change is correct?
- Copy the .env file into /etc so that cron can read it.
- Ask cron to start a terminal session, so that the shell reads .bashrc.
* Load .env inside the script, after changing to the repository folder.
- Remove set -u, so that unset variables are ignored.
WHY: cron does not read your .bashrc or start a terminal, so settings exported in your shell are missing. Loading the file inside the script works under any caller. Removing set -u hides the problem instead of fixing it.

Q: Eli's crontab line is */30 * * * * bash scripts/fetch.sh with no cd. By hand, the same command works from the repository. Under cron the log says bash: scripts/fetch.sh: No such file or directory. Why?

* cron starts in the home folder, so the relative path is looked up there.
- The script has no shebang, so cron refuses to run it.

WHY: A relative path is resolved from the working directory, and cron normally starts in your home folder. The tempting answer blames the crontab, but the path is valid; it is simply resolved from a different place.
```

### Conditional operators in tests

**What it is.** A test written inside `[ ]` is a command that returns 0 when the condition is true and 1 when it is false. For numbers, the operators are `-eq`, `-ne`, `-lt`, `-le`, `-gt` and `-ge`. For text, use `=` and `!=`. `&&` runs the second command only if the first succeeded, and `||` runs the second command only if the first failed.

```bash
attempt=3
if [ "$attempt" -ge 3 ]; then echo "give up"; fi
```

The output is `give up`, because 3 is greater than or equal to 3. Changing `-ge` to `-gt` would print nothing, because `-gt` is false for 3.

**How it shows up in a case study.** The healthcheck computes the age of the last successful fetch in minutes. The rule is that an age of 120 minutes or more is critical. Kofi writes `[ "$age" -gt 120 ]`, and the team is surprised when an age of exactly 120 is reported as a warning. The decision is to use `-ge`, which includes the boundary value. The quotes around `"$age"` also protect the test if the variable is empty.

:::trap Using > inside brackets
`>` inside `[ ]` is not a comparison. Bash reads it as a redirection and writes the output of the test to a file named after the word on the right. Use `-gt` for numbers.
:::

```quiz
Q: A script must exit when count is below 5 and carry on when it is 5 or more. Which test should guard the exit?
- [ "$count" -le 5 ]
- [ "$count" -gt 5 ]
* [ "$count" -lt 5 ]
- [ "$count" = 5 ]
WHY: -lt is true when count is less than 5, so the exit runs only for values below 5. -le includes 5, which would exit at the wrong value. The tempting answer -gt is true for 6 and above, the opposite of what is needed.

Q: A script contains if [ $size > 100 ]; then ... fi. What is the main problem?
* Bash treats > as a redirection and writes to a file named 100, so the comparison never happens.
- Bash compares the two values as text, which is always correct for numbers.
- The test works, but it runs slowly on large files.
- Nothing, because > and -gt mean the same inside brackets.
WHY: Inside single brackets > is a redirection, which creates a file, so the test does not compare sizes. The fix is -gt. The tempting answer assumes > behaves like -gt.

Q: A script runs grep -q ERROR logs/fetch.log && echo "errors found" || echo "clean". grep finds no match and returns 1. What is printed?
- errors found
* clean
- errors found, then clean
- Nothing, because grep stops the script.
WHY: && runs the next command only when the previous one succeeded, and || runs its command only when the previous one failed. grep returns 1 when there is no match, so the second echo runs. The tempting answer is errors found, because that text comes first in the line.
```

### Redirecting cron output

**What it is.** Redirection changes where a command sends its streams. Standard output is stream 1 and standard error is stream 2. `>` writes to a file and replaces what was there. `>>` appends to the end of the file. `2>&1` sends stream 2 to wherever stream 1 is going at that point. Redirections are read from left to right, so the order matters.

```bash
echo "fetched" >> logs/cron.out 2>&1
ls /missing >> logs/cron.out 2>&1
```

After both lines, `logs/cron.out` contains `fetched` and the error from `ls`, which reads `ls: cannot access '/missing': No such file or directory`. Both streams reached the file. Had the second line been written as `2>&1 >> logs/cron.out`, the error would have gone to the place where standard output pointed before the redirection, and the file would have held only standard output.

**How it shows up in a case study.** The cron job runs `bash scripts/fetch.sh >> logs/cron.out`. A fetch fails and prints an ERROR line on standard error. The log file has nothing new, so the team concludes that no run happened. The decision is to append standard error to the same file by writing `>> logs/cron.out 2>&1`. The team then reads the file and finds the error line that explains the failure.

:::trap Writing 2>1
`2>1` does not mean "send errors to standard output". It writes standard error to a file named `1`. To join the streams, write `2>&1`.
:::

```quiz
Q: A crontab line reads */30 * * * * bash fetch.sh 2>&1 >> logs/cron.out. An ERROR line is written to standard error. Where does it go?
- Into logs/cron.out.
- Into a file named 1.
* To wherever standard output pointed before the redirection, not to the file.
- Nowhere, because 2>&1 hides it.
WHY: Redirections are read left to right. When 2>&1 is read, standard output still points to the old place, so stream 2 is copied there, before the file redirection takes effect. The tempting answer is that the line sends everything to the file.

Q: A job runs every 30 minutes and ends with > logs/cron.out 2>&1. Each run deletes the previous run's output. Which change keeps the history?
- Change > to 2>, so that errors are kept.
* Change > to >>, so that each run appends to the file.
- Add set -x to the script, so that the log grows.
- Send the output to /dev/null instead of the file.
WHY: > replaces the file and >> appends to it. The tempting answer 2> keeps only errors, and it would drop the normal output the team needs.

Q: A crontab writes with >> logs/cron.out 2>log/errors.out. The team wants both streams in cron.out. What is wrong?
* Standard error goes to a separate file, so the errors are not in cron.out. Use 2>&1 instead.
- Nothing is wrong, because 2>log/errors.out is the same as 2>&1.
- The file names must be in quotes, or cron rejects the line.
- Redirections are read right to left, so errors reach cron.out anyway.
WHY: 2> with a file name sends standard error to that file, not to cron.out. 2>&1 joins it to the same place as standard output. The tempting answer equates the two forms, but only 2>&1 joins the streams.
```

### Command substitution

**What it is.** `$(command)` runs the command and puts its output in place of the substitution. Trailing newlines are removed. You can store the result in a variable or put it inside a line of text. Single quotes stop the substitution, so `'$(date)'` is only the text. Substitution also carries the exit code of the command, which matters when the script uses `set -e`.

```bash
today=$(date +%F)
echo "Report for $today"
```

On 3 November 2026 the output is `Report for 2026-11-03`. The `%F` format prints the date as year, month and day. The command inside the brackets runs first, and its output replaces it before `echo` runs.

**How it shows up in a case study.** A script counts the readings in a file with `rows=$(wc -l data/readings.csv)`. The report reads `rows: 12 data/readings.csv` instead of `rows: 12`. The problem is that `wc` prints the file name when the file is passed as an argument, but not when the file is given through input redirection. The decision is to write `rows=$(wc -l < data/readings.csv)`, which gives the count alone, and to keep the substitution in a plain assignment, so `set -e` sees its exit code.

:::trap local hides the exit code
`local status=$(curl -sf "$URL")` looks like one step, but `local` succeeds whatever the command returns. Under `set -e` the failure is hidden. Declare the variable with `local status` on one line, then assign it with `status=$(...)` on the next.
:::

```quiz
Q: In a function, a teammate writes local status=$(curl -sf "$URL") under set -e. curl fails with exit code 22, and the script keeps going. Why?
* local always succeeds, so the failure of the substitution is hidden from set -e.
- The substitution is in quotes, so curl never runs.
- set -e ignores every command inside a function.
- curl returns 0 whenever -f is used.
WHY: local is a command that returns 0, so the status of the substitution is lost. Declaring the variable on one line and assigning it on the next keeps the status. The tempting answer blames the function, but the cause is the single line.

Q: A script contains echo 'Today is $(date +%F)'. What does it print?
- Today is 2026-11-03
- Today is date +%F
* Today is $(date +%F)
- Nothing, because single quotes are not allowed around substitutions.
WHY: Single quotes stop expansion, so the text is printed exactly as typed. The tempting answer is the date, which appears only when the substitution is outside single quotes.

Q: A script runs mode="$(grep -o 'mode=[a-z]*' config.txt)" with no local keyword, under set -e. config.txt has no matching line, so grep returns 1 and prints nothing. What happens?
- The script carries on, with mode set to the word none.
- The script carries on, because -e ignores assignments.
- The script stops, because set -u sees an unset variable.
* The script stops, because the assignment takes the failing status of grep.
WHY: A plain assignment takes the exit status of its command substitution, so set -e stops the script. The variable is set to an empty value, so -u does not fire. The tempting answer is that the assignment is harmless.
```

### File test conditions

**What it is.** A file test asks a question about a path and returns true or false. `-e` is true when the path exists, in any form. `-f` is true for a regular file. `-d` is true for a directory. `-s` is true for a file that is not empty. `-x` is true for a file with the execute permission. `-n` tests whether a string is not empty.

```bash
if [ -f ops/STOP ]; then echo "stopped"; fi
```

If `ops/STOP` exists as a regular file, the output is `stopped`. If it does not exist, nothing is printed. A directory named `ops/STOP` would not match `-f`, which is what you want for a kill switch that is meant to be a file.

**How it shows up in a case study.** The ingest must skip the run when the kill switch is on, and it must refuse to append to a daily file that is empty, because an empty file would hide the outage. Ines writes `[ -e results/day1.csv ]` for the empty-file check, and the test passes for an empty file. The correct decision is `-s`, which is false for an empty file. For the kill switch, the team uses `-f`, not `-e`, so a folder with the same name does not stop the job.

:::trap -n on a file path
`-n` tests whether a string is non-empty. A file path is always a non-empty string, so `[ -n ops/STOP ]` is always true. Use `-f` or `-s` to test the file itself.
:::

```quiz
Q: A script must append to results/day1.csv only if the file exists and holds some data. Which test does this?
- [ -e results/day1.csv ]
- [ -d results/day1.csv ]
* [ -s results/day1.csv ]
- [ -n results/day1.csv ]
WHY: -s is true only when the file has a size above zero. -e accepts an empty file, and -n is always true for a non-empty path. The tempting answer -e checks existence but says nothing about the content.

Q: A script contains if [ -n logs/fetch.log ]; then ... fi. It is meant to skip work when the log is missing. Why does it misbehave?
* -n tests a non-empty string, and the path is always non-empty, so the test is always true.
- -n tests whether the file is missing, so the logic is inverted.
- -n works only on directories, not on files.
- -n is the same as -f, so the test is correct.
WHY: The path is text, and text is always non-empty whether the file exists or not. The fix is -f, which tests the file itself. The tempting answer assumes -n checks the file.

Q: A script should run the helper scripts/fetch.sh only when it has the execute permission. Which test does this?
- [ -f scripts/fetch.sh ]
- [ -d scripts/fetch.sh ]
- [ -s scripts/fetch.sh ]
* [ -x scripts/fetch.sh ]
WHY: -x checks the execute permission. -f accepts a file that has no execute bit, and running it directly would then fail. -s checks for content, and -d checks for a folder.
```

### What each function needs

This section teaches the Python ideas each function uses. Every example is small and uses data that has nothing to do with the lab. Try each one in a Python file or an interpreter before you move on.

**Splitting text with `str.split`.** Called with no argument, `split` breaks text at any run of spaces and ignores leading and trailing spaces.

```python
print("  red   green  blue ".split())  # ['red', 'green', 'blue']
```

Called with a second argument, `split` stops after that many splits. The rest of the text stays in the last piece, with its inner spaces intact.

```python
print("red green blue black".split(None, 2))  # ['red', 'green', 'blue black']
```

**Slicing a list.** `items[:2]` takes the items before position 2, and `items[2:]` takes the items from position 2 to the end. Positions start at 0.

```python
colours = ["red", "green", "blue", "black"]
print(colours[:2])  # ['red', 'green']
print(colours[2:])  # ['blue', 'black']
```

**Returning several values.** A function can return a tuple. The caller can unpack it into names in one line.

```python
def shop_totals():
    return 3, 12
apples, pears = shop_totals()
print(apples, pears)  # 3 12
```

**Converting text to a number with `int`.** `int("7")` gives the number 7. Text that is not a whole number raises a `ValueError`, which is an error that Python raises when a value has the right type but a wrong content.

```python
print(int("7") + 1)  # 8
# int("x") raises ValueError
```

**Remainders with `%`.** `%` gives the remainder after division. A remainder of 0 means the first number is an exact multiple of the second.

```python
print(12 % 4)  # 0, so 12 is a multiple of 4
print(13 % 4)  # 1, so 13 is not
```

**Splitting once with `partition`.** `text.partition("/")` returns three pieces: the part before the first slash, the slash itself, and the part after. If there is no slash, the second and third pieces are empty text.

```python
print("a-b/3".partition("/"))  # ('a-b', '/', '3')
print("a-b".partition("/"))    # ('a-b', '', '')
```

**Sets and `sorted`.** `set.update` adds many items at once, repeats are dropped, and `sorted` turns a set into an ordered list.

```python
seen = set()
seen.update([3, 1, 3])
print(sorted(seen))  # [1, 3]
```

**Ranges that include both ends.** `range(3, 6)` gives 3, 4 and 5, because the end is excluded. Include the end by adding one to it.

```python
print(list(range(3, 7)))  # [3, 4, 5, 6]
print(list(range(0, 10, 4)))  # [0, 4, 8], a third argument is the step
print(6 in range(3, 7))  # True
print(7 in range(3, 7))  # False
```

**Checking any item in a list.** `any` returns `True` when at least one item in a list is true. An empty list gives `False`.

```python
print(any([False, True, False]))  # True
print(any([]))  # False
```

**Reading a dictionary with `get`.** `d[key]` raises a `KeyError` when the key is missing. `d.get(key)` returns `None` instead, and `d.get(key, default)` returns the default.

```python
stock = {"apples": 3}
print(stock.get("pears"))     # None
print(stock.get("pears", 0))  # 0
print("apples" in stock)      # True
```

**Checking a type with `isinstance`.** `isinstance(value, int)` is `True` for a whole number. A boolean is also an `int` in Python, because `bool` is a subclass of `int`, which means it is a special kind of integer. So `isinstance(True, int)` is `True`, and you must check for `bool` separately when a boolean should not count.

```python
print(isinstance(True, int))           # True
print(isinstance(True, bool))          # True
print(isinstance(2.5, (int, float)))   # True
```

**Matching a whole pattern with `re.fullmatch`.** `re.compile` prepares a pattern once. `fullmatch` returns a match object only when the pattern matches the entire text, and `None` otherwise.

```python
word = re.compile(r"[a-z]{3}")
print(word.fullmatch("cat") is not None)   # True
print(word.fullmatch("cats") is not None)  # False
```

**Checking membership in a set.** A set is written in braces and holds unique values. `in` checks membership quickly.

```python
print("tea" in {"tea", "coffee"})  # True
print("juice" in {"tea", "coffee"})  # False
```

### Worked twin problem

**The twin problem.** A small company runs a nightly backup scheduler. Each job is one line made of a minute field, an hour field, a weekday field and a command, for example `*/20 22 1-5 rsync -a /data /backup`. Minutes run from 0 to 59, hours from 0 to 23 and weekdays from 0 to 6, where 0 is Sunday. Blank lines and lines that start with `#` are comments. This is a backup tool, not the CityPulse cron check, but it needs the same skills.

- `split_job(line)` returns `None` for a blank line or a comment. Otherwise it returns a dictionary with the keys `minute`, `hour`, `weekday` and `command`. The first three fields are separated by spaces, and the command is everything after them, with its inner spaces kept. A line with fewer than four parts raises `ValueError`.
- `expand_field(spec, low, high)` turns one field into the sorted list of the numbers it allows, without repeats. The forms are `*` (every number from `low` to `high`), a plain number, a range `a-b` that includes both ends, `*/n` and `a-b/n` (every n-th number, counted from the start of the range), and comma lists of these. A step of zero or less, a number outside `low` to `high`, a range whose start is above its end, a step on a plain number and text that is not a number all raise `ValueError`.
- `runs_at(line, minute, hour, weekday)` returns `True` when all three numbers are allowed by the job's fields. A comment or blank line never runs.
- `valid_log(record)` returns `True` only when `record` is a dictionary and all of these hold. Its `time` is text in the form `YYYY-MM-DDTHH:MM:SS` with a real month (1 to 12), a day from 1 to 31, an hour up to 23, and a minute and second up to 59. Its `level` is one of `INFO`, `WARN` or `ERROR`. Its `message` is text that is not empty once spaces are removed. If the record has a `size_kb` key, it must be a whole number of zero or more and not a boolean.

**The solution.** Read the code once, then read the explanation. Run it, and check that the message `all tests passed` appears.

```python test
import re

LEVELS = {"INFO", "WARN", "ERROR"}
STAMP = re.compile(r"[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}")


def split_job(line):
    text = line.strip()
    if text == "" or text.startswith("#"):
        return None
    parts = text.split(None, 3)
    if len(parts) < 4:
        raise ValueError("a job needs minute, hour, weekday and a command")
    return {"minute": parts[0], "hour": parts[1], "weekday": parts[2], "command": parts[3]}


def expand_field(spec, low, high):
    allowed = set()
    for item in spec.split(","):
        body, slash, step_text = item.partition("/")
        step = 1
        if slash:
            step = int(step_text)
            if step <= 0:
                raise ValueError("step must be positive")
        if body == "*":
            start, end = low, high
        elif "-" in body:
            first, last = body.split("-", 1)
            start, end = int(first), int(last)
        else:
            if slash:
                raise ValueError("a step needs * or a range")
            start = end = int(body)
        if start < low or end > high or start > end:
            raise ValueError("number outside the allowed range")
        allowed.update(range(start, end + 1, step))
    return sorted(allowed)


def runs_at(line, minute, hour, weekday):
    job = split_job(line)
    if job is None:
        return False
    minutes = expand_field(job["minute"], 0, 59)
    hours = expand_field(job["hour"], 0, 23)
    days = expand_field(job["weekday"], 0, 6)
    return minute in minutes and hour in hours and weekday in days


def valid_log(record):
    if not isinstance(record, dict):
        return False
    stamp = record.get("time")
    if not isinstance(stamp, str) or STAMP.fullmatch(stamp) is None:
        return False
    month, day = int(stamp[5:7]), int(stamp[8:10])
    hour, minute, second = int(stamp[11:13]), int(stamp[14:16]), int(stamp[17:19])
    if not (1 <= month <= 12 and 1 <= day <= 31):
        return False
    if hour > 23 or minute > 59 or second > 59:
        return False
    level = record.get("level")
    if not isinstance(level, str) or level not in LEVELS:
        return False
    message = record.get("message")
    if not isinstance(message, str) or message.strip() == "":
        return False
    if "size_kb" in record:
        size = record["size_kb"]
        if isinstance(size, bool) or not isinstance(size, int) or size < 0:
            return False
    return True


def raises_value_error(function, *args):
    try:
        function(*args)
    except ValueError:
        return True
    return False


job = "*/20 22 1-5 rsync -a  /data /backup"
assert split_job("# nightly") is None
assert split_job("   ") is None
assert split_job(job) == {"minute": "*/20", "hour": "22", "weekday": "1-5", "command": "rsync -a  /data /backup"}
assert raises_value_error(split_job, "0 3 *")

assert expand_field("*", 0, 6) == [0, 1, 2, 3, 4, 5, 6]
assert expand_field("5", 0, 59) == [5]
assert expand_field("*/20", 0, 59) == [0, 20, 40]
assert expand_field("10-12", 0, 59) == [10, 11, 12]
assert expand_field("10-30/10", 0, 59) == [10, 20, 30]
assert expand_field("1,3-4,3", 0, 6) == [1, 3, 4]
for bad in ["*/0", "*/x", "7", "5-2", "x", "5/10"]:
    assert raises_value_error(expand_field, bad, 0, 6), bad

assert runs_at(job, 40, 22, 3)
assert runs_at(job, 0, 22, 5)
assert not runs_at(job, 30, 22, 3)
assert not runs_at(job, 40, 21, 3)
assert not runs_at(job, 40, 22, 0)
assert not runs_at("# " + job, 40, 22, 3)

good = {"time": "2026-11-03T22:40:05", "level": "INFO", "message": "backup done"}
assert valid_log(good)
assert valid_log({**good, "size_kb": 0})
assert not valid_log({**good, "size_kb": True})
assert not valid_log({**good, "size_kb": -1})
assert not valid_log({**good, "size_kb": "5"})
assert not valid_log({**good, "time": "2026-11-03 22:40:05"})
assert not valid_log({**good, "time": "2026-13-03T22:40:05"})
assert not valid_log({**good, "time": "2026-11-03T24:40:05"})
assert not valid_log({**good, "time": "2026-11-03T22:40:05\n"})
assert not valid_log({**good, "level": "info"})
assert not valid_log({**good, "level": ["INFO"]})
assert not valid_log({**good, "message": "   "})

```

**Explanation.**

- `LEVELS` is a set, so membership checks are quick. `STAMP` is compiled once. It checks only the shape of the time text, which is digits in the right places. The ranges of the numbers are checked separately, because a pattern cannot easily say "01 to 12".
- `split_job` removes outer spaces with `strip`. A blank line becomes the empty text, and a comment starts with `#`, so both return `None`. Otherwise `split(None, 3)` gives at most four parts, and the fourth keeps its inner spaces. Fewer than four parts raises `ValueError`. The result is a dictionary, so the later code can say `job["hour"]` instead of remembering positions.
- `expand_field` builds a set called `allowed`, which removes repeats on its own. For each comma-separated item, `partition("/")` gives the part before the slash, the slash itself and the part after it. When there is no slash, `slash` is the empty text, so the step stays 1. When there is one, `int` turns the step into a number, and a step of zero or less raises `ValueError`.
- The body then picks the start and the end. A star means the whole range `low` to `high`. A hyphen means the two numbers around it. A plain number means start and end are the same number, but a step on a plain number is rejected.
- The test `start < low or end > high or start > end` rejects numbers outside the bounds and ranges written backwards. `range(start, end + 1, step)` includes the end, because `range` stops before its second argument. `sorted` turns the set into an ordered list.
- `runs_at` returns `False` for a comment. It expands all three fields before it compares, so a bad field raises an error even when the minute does not match. The final line uses `and`, so all three must allow their number.
- `valid_log` checks the rules in order. It rejects a record that is not a dictionary, then checks that the time is text and has the right shape. It cuts the numbers out of the text by position, because the pattern guarantees where they are. Month, day, hour, minute and second are checked against their limits. The level must be text before the set lookup, so a list cannot crash it. The message must be text with something other than spaces in it. The `size_kb` key is optional, but when it is there it must be a whole number of zero or more, and a boolean is rejected.
- `raises_value_error` is a small helper used only by the asserts. It returns `True` when the call raises `ValueError`, which keeps the test lines short.

```python test
def average_wait(minutes):
    if len(minutes) == 0:
        raise ValueError("no waits")
    for minute in minutes:

    return round(sum(minutes) / len(minutes), 1)
```
