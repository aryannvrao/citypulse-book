## What the quiz tests

The Day Quiz has ten case-study multiple-choice questions, one for each topic in this section and in the same order. Each question describes a CityPulse team with a model, a symptom or a constraint, and asks for the right next step or the right reading of a result. The pass mark is 70%. Your first attempt is the one the skill score keeps, so a second try does not replace a weak first score.

Every question has four options and only one is correct. The wrong options are often true statements in general that do not fix the problem in the scenario. Four habits help. Read the last line first, so you know what is being asked. Note the facts in the scenario that matter, such as the number of rows, the group size, the split and the time zone. Eliminate options that are true but do not answer this scenario. Watch for three words: "most" asks for the strongest of several true answers, "first" asks for the step that comes before the others, and "best" asks for the option that fits the constraint in the scenario, not the most sophisticated one.

### Random forests

**What it is.** A random forest is a group of decision trees whose answers are averaged. A decision tree predicts by asking a chain of yes/no questions about the inputs, such as "is the hour after 17?", and stops at a leaf that holds a value. One tree is unstable: change a few training rows and its questions change. A random forest trains many trees, each on a **bootstrap sample**. A bootstrap sample is drawn with replacement from the training rows, so each tree sees a different mix, with some rows repeated and others left out. For a regression forest, the prediction is the average of the trees' predictions.

Here is the averaging step for three trees that predict 12, 15 and 9 minutes for the same row:

```python
tree_predictions = [12, 15, 9]
print(sum(tree_predictions) / len(tree_predictions))
```

The output is `12.0`. Averaging reduces variance, which means the answer swings less when the training rows change. Two settings matter most. `n_estimators` sets how many trees are trained. `min_samples_leaf` sets the smallest number of rows a leaf may hold, so a larger value gives smaller trees.

**How it shows up in a case study.** A CityPulse team's forest predicts the 30-minute rise in PM2.5 more accurately than a single tree. But the saved file is 400 MB and takes minutes to load, which breaks the API's start-up time. The forest's averaging already keeps variance low, so adding trees is not the fix. The leaves are the problem: a tree with one row per leaf stores far too much. Setting `min_samples_leaf` to 5 or more shrinks each tree, and the team keeps the tree count where cross-validation stops improving.

:::trap A forest is not boosting
Trees in a forest are trained independently, each on its own bootstrap sample, so no tree corrects another tree's mistakes. An option that says each new tree fixes the one before describes gradient boosting, not a forest.
:::

```quiz
Q: A random forest for regression averages 300 trees, each trained on a bootstrap sample. The team wants fewer wild swings in the prediction when the training rows change. Which explanation fits?
- Each tree is trained on the full data, so all the trees agree
- The forest keeps the single best tree and discards the rest
* Averaging trees whose errors differ lowers the variance of the forest
- Each new tree is fitted to the errors of the trees before it
WHY: Averaging trees trained on different bootstrap samples reduces variance. The boosting option is the tempting wrong one, because it also uses many trees, but those trees are not independent.

Q: A forest model file is very large and slow to load, and its leaves hold one row each. Which setting most directly reduces the file size?
- learning_rate=0.05
* min_samples_leaf=5 or more
- random_state=42
- n_jobs=-1
WHY: min_samples_leaf stops a tree splitting until each leaf holds at least that many rows, so the trees stay small. n_jobs only changes training speed, and learning_rate belongs to boosting.

Q: A colleague reports a forest's MAE as 2.0 on the training rows and 6.5 on the held-out rows. What does this gap most likely show?
- The forest is the best model available for every station
- The bootstrap sampling has a bug and should be removed
- The held-out rows contain wrong values in the target column
* The forest has memorised its training rows more than it generalises
WHY: A large gap between training and held-out error is a sign of overfitting. The tempting wrong answer blames the bootstrap, but the sampling is the mechanism that makes the forest generalise.
```

### Gradient boosting

**What it is.** Gradient boosting builds its trees in order. The first tree makes a rough prediction. The second tree is fitted to what the first got wrong, which are the residuals. The third is fitted to what the first two still get wrong, and so on. Each tree is shallow and weak alone. The final answer is a start value plus a small share of each tree's correction, and that share is the `learning_rate`. A smaller learning rate usually needs more stages. `HistGradientBoostingRegressor` groups each numeric feature into bins (buckets) before fitting, which makes it fast on large tables.

```python
prediction = 20.0                       # a simple starting guess
for correction in [4.0, 1.0, -0.5]:     # corrections from three stages
    prediction += 0.5 * correction      # learning_rate is 0.5
print(prediction)
```

The output is `22.25`. The first stage adds 2.0, the second adds 0.5 and the third takes off 0.25. Each stage moves the answer only part of the way, which is why the rate matters.

**How it shows up in a case study.** A team adds a boosting model after its forest. Its training MAE falls at every stage, but its held-out MAE starts rising after about 400 stages. The model is now following noise in the training rows. The right step is to choose a stage count from cross-validated error on the same folds, and to stop adding stages just because training error still falls.

:::trap Boosting is not averaging
Boosting trees depend on each other, so too many stages can overfit. Adding trees to a random forest rarely hurts. Choosing the largest stage count because training error keeps falling is the wrong reason.
:::

```quiz
Q: A boosting model's training MAE falls at every stage, but its held-out MAE rises after stage 250. Which action is best supported by this?
* Choose a stage count near the point where held-out error stops improving
- Add more stages, because training error is still falling
- Set the learning rate to zero so every stage has equal weight
- Use one deep tree that memorises the rows
WHY: Held-out error is the honest signal, and its rise after stage 250 is overfitting. Falling training error is the tempting wrong reason to add stages.

Q: A team says its gradient boosting model is the same as its forest, because both use many trees. Which statement corrects them?
- Both train each tree on a bootstrap sample of the same size, so they are identical
- Both average independent trees, so their settings can be swapped
* In boosting each tree is fitted to the errors left by earlier trees, so the trees depend on each other
- Boosting trees are always deeper than forest trees
WHY: The trees in boosting are sequential and dependent, and that is the key contrast. The tempting wrong answer relies on the surface similarity of "many trees", and the depth claim is not true in general.

Q: A boosting model with learning_rate 0.5 reaches its best held-out MAE at 40 stages. The team lowers the learning rate to 0.05. What should they expect?
- The best count stays at 40, because the learning rate does not matter
* The best count usually rises, because each stage moves the prediction less
- The model stops working, because the rate must be above 1
- The model turns into a random forest
WHY: A smaller learning rate shrinks each stage, so more stages are usually needed to reach the same fit. The claim that the rate does not matter is the tempting wrong answer.
```

### Feature importance

**What it is.** A feature is an input column. Feature importance is a number that says how much a model relies on a column. Tree models have a built-in value, `feature_importances_`, computed from the training data: it adds up how much each column's splits reduced error. A column with many distinct values gets more chances to be split on, so it tends to score high. **Permutation importance** works on held-out rows instead. It shuffles one column, which breaks that column's link to each row, and measures how much the error rises. A column the model relies on causes a large rise.

| Row | pm10 (original) | pm10 (shuffled) |
|---|---|---|
| 1 | 40 | 70 |
| 2 | 55 | 40 |
| 3 | 70 | 55 |

If the MAE rises from 5.2 to 9.8 after this shuffle, the rise of 4.6 is the importance of pm10 for this run. Repeating the shuffle gives a mean and a standard deviation.

**How it shows up in a case study.** A reviewer asks which input drives a CityPulse forecast. The built-in ranking puts a `timestamp_id` column first, and that column has hundreds of distinct values. The team should check permutation importance on the held-out test rows, because the built-in measure is computed on training data and favours columns with many distinct values. Only the held-out measure shows how much the error rises when a column is broken.

:::trap High importance is not cause
Importance shows how much the model relies on a column. It does not show that the column causes the outcome in the real world. A station or an id can rank high because it separates training rows, not because it changes air quality.
:::

```quiz
Q: A forest's built-in importance ranks a `timestamp_id` column first, and that column has 900 distinct values. On held-out rows, permutation importance ranks it fifth. What is the best explanation?
- The held-out rows are wrong and should be dropped
- The timestamp causes most of the pollution in the city
- Permutation importance is always wrong for tree models
* The built-in measure favours columns with many distinct values, so its top rank is partly an artefact
WHY: The built-in measure is computed on training data and favours high-cardinality columns. The causal reading is the tempting wrong option, because importance is a reliance measure and not a cause.

Q: A permutation table shows that shuffling `o3` raises the MAE by 0.02, and shuffling `pm10` raises it by 4.1. Which claim does the table support?
* The model's held-out error depends much more on pm10 than on o3
- Lowering pm10 by 4 units lowers the pollution by 4 units
- The o3 column has no effect on air quality at any station
- The model uses pm10 and no other column
WHY: The table reports how much error rises when a column is shuffled, so it describes reliance. The causal claim is the tempting wrong option, and the claim that pm10 is the only column misreads a ranking.

Q: A team wants to show which input matters most in the saved model to a reviewer who does not know machine learning. Which measure should it use, and where?
- Built-in feature_importances_ on the training rows, because it is free
- The coefficient of each column in a straight-line model, because a tree has none
* Permutation importance on held-out test rows, reported as a mean and a standard deviation over repeats
- The number of times each column appears in the training file
WHY: Permutation importance on held-out rows avoids the bias toward training data, and the repeats give a spread. The free built-in value is the tempting wrong option, because it is computed on training data.
```

### Residuals and bias

**What it is.** A residual is the gap between the actual value and the prediction for one row: residual = actual minus predicted. A positive residual means the model under-predicted, and a negative one means it over-predicted. In this chapter, bias is the mean of the residuals. A bias near zero means positive and negative errors cancel out. MAE is the mean of the absolute residuals, so it measures size and ignores direction. The two can tell different stories:

```python
actual = [10, 20, 30]
predicted = [14, 18, 27]
gaps = [a - p for a, p in zip(actual, predicted)]
print(gaps)
```

The output is `[-4, 2, 3]`. The bias is (-4 + 2 + 3) / 3, which is about 0.33. The MAE is (4 + 2 + 3) / 3, which is 3.0. The bias is small only because the errors cancel. The MAE shows that the typical miss is three units.

**How it shows up in a case study.** A CityPulse team reports a bias of 0.1 and calls the model unbiased. An officer asks about one row during a dust storm, where the forecast was 21 units below the actual value. The mean hides that miss. The report should add the worst absolute residual and the standard deviation of the residuals, and it should check which rows produced the large misses.

:::trap A small mean is not accuracy
A bias near zero does not mean the model is accurate. Large errors of opposite sign can cancel. Reporting only the mean residual hides both the worst miss and the spread.
:::

```quiz
Q: On the test rows, the mean residual is +0.05 and the MAE is 8.4. A colleague says the model is accurate to within 0.05. What is the best reply?
- Agreed, the mean residual is the accuracy
* The mean cancels errors of both signs, so the MAE of 8.4 is the size of a typical miss
- The MAE must be wrong, because it is larger than the bias
- The residual should be predicted minus actual, so 8.4 is the answer
WHY: Bias is an average of signed errors, which can cancel. MAE measures the typical size of a miss. Treating the bias as accuracy is the tempting wrong answer.

Q: A residual is actual minus predicted. One row has actual 52 and predicted 61. What is the residual, and what does it mean?
- 9, the model under-predicted by 9
- -9, the model under-predicted by 9
- 113, the model over-predicted by 113
* -9, the model over-predicted by 9
WHY: 52 minus 61 is -9, and a negative residual means over-prediction. The tempting wrong answer is the positive 9 with under-prediction, because the size is right but the direction is wrong.

Q: A card reports a mean residual of 0.17, a residual standard deviation of 6.5 and a worst absolute residual of 21.8. Which statement is correct?
* The mean shows little systematic skew, but single rows can still miss by a large amount
- The model is unsafe to publish because its worst miss is above 20
- The worst residual means the model is wrong on 21.8 percent of rows
- A mean of 0.17 proves that no row was badly predicted
WHY: Bias measures systematic skew, while the spread and the worst miss measure single-row errors. The claim that the model is unsafe goes beyond what these numbers establish, so it is the tempting wrong answer.
```

### Slicing errors by group

**What it is.** Slicing splits the test rows into groups and computes the same error for each group. A slice might be one station or one IST hour. Each group gets a count, an MAE and often a bias. The example below uses six rows with a station and an absolute error:

```python
import pandas as pd
table = pd.DataFrame({"station": ["ST-01", "ST-01", "ST-04", "ST-04", "ST-04", "ST-02"],
                      "abs_err": [4.0, 6.0, 9.0, 7.0, 8.0, 3.0]})
summary = table.groupby("station")["abs_err"].agg(n="size", mae="mean")
print(summary)
```

The output has one row per station, sorted by name:

```text
         n  mae
station
ST-01    2  5.0
ST-02    1  3.0
ST-04    3  8.0
```

The counts add up to 6, the number of rows. The count matters as much as the MAE, because a group with one row can look bad by chance.

**How it shows up in a case study.** The overall test MAE is 5.2, which the team thinks is acceptable. A slice table shows ST-04 at an MAE of 8.1 from 340 rows, and the 18 to 21 IST band at an MAE of 11.8 from only 18 rows. The reviewer asks what to write. ST-04 becomes a finding with its count. The 18-row band is flagged as insufficient evidence, but it is still named as a risk. Neither group is removed, and the model is not retrained on those rows.

:::trap Slicing without the count
A slice with few rows can look terrible by chance. Flag it with its count rather than hiding it. Also convert timestamps to IST before grouping by hour, because a UTC hour puts an evening spike in the wrong band.
:::

```quiz
Q: A team groups test errors by IST hour. The 19:00 band has an MAE of 14.2 from 9 rows, and the overall MAE is 5.5. What should the write-up do with this band?
- Remove it, because it is noise
- Report only the overall MAE, which is the honest summary
* Report the band with its count, flag it as insufficient evidence, and name it as a possible risk
- Retrain the model on the rows in that band so the MAE drops
WHY: A slice with 9 rows is thin evidence, so its count and flag must be shown, and the band still counts as a risk. Removing it or retraining on the test rows hides evidence, which is the tempting wrong answer.

Q: The slice script takes the hour from a raw timestamp stored in UTC. A spike at 18:00 IST appears in the 12:30 UTC row. What problem does this cause?
- The MAE is computed on the wrong number of rows
* The spike is attributed to an hour band that does not match officers' clocks, so the finding points at the wrong time
- The model is retrained on IST rows automatically
- The bias flips sign for every hour
WHY: 18:00 IST is 12:30 UTC, so grouping in UTC puts the spike in the wrong band. The row count is unaffected, which is why the count-based option is the tempting wrong one.

Q: A model card's slice table is being prepared for the next release. Which rule must hold for the slice findings to be honest?
- Use the training rows, because they are the largest group
- Use cross-validation predictions, because they are the most stable
- Slice the training and test predictions together, so the table has more rows
* Slice only held-out test-window predictions, and show the count for each group
WHY: Training predictions are too optimistic, and cross-validation predictions are not the final test window that the card reports, so slices on them can hide the real weak spots. Pooling them with the test rows is the tempting wrong option, because it enlarges the groups.
```

### Ensemble diversity

**What it is.** Diversity means the models in an ensemble make different errors. Averaging helps only when the errors point in different directions or fall on different rows. If two models make the same error on every row, averaging them returns that error unchanged. Diversity can come from different algorithms, different training samples or different input columns.

```python
model_a_errors = [5, -3, 4]
model_b_errors = [5, -3, 4]
avg_errors = [(a + b) / 2 for a, b in zip(model_a_errors, model_b_errors)]
print(avg_errors)
```

The output is `[5.0, -3.0, 4.0]`. The average is the same as either model, so the second model adds nothing. If the second model's errors were `[1, -6, 7]` instead, the average would be different, and it would be worth checking on held-out rows.

**How it shows up in a case study.** A team has three forests trained on the same rows and inputs, differing only by random seed. Their test errors are almost identical on every row. The team proposes adding two more forests to the average to improve the card. The reply is that the extra forests add little, because they repeat the same mistakes. More diversity would come from different inputs or algorithms, and the cost of each extra model should be weighed against the gain.

:::trap More models is not better
Copies of a good model average to nearly the same error. Averaging can also hurt when one member is much weaker than the others. Adding members is only worth it when they make different mistakes.
:::

```quiz
Q: Two gradient boosting models use the same rows and inputs and differ only in their random seed. Their predictions agree to within 0.01 on every row. Which statement about averaging them is correct?
* Averaging them gives almost no gain, because their errors are nearly the same
- Averaging them will halve the MAE
- Averaging them is impossible, because seeds cannot be combined
- Averaging them always adds the seed difference to the error
WHY: Nearly identical predictions have nearly identical errors, so averaging cancels very little. The claim that the MAE halves is the tempting wrong answer, because halving needs errors that cancel.

Q: An ensemble averages a strong model with MAE 5.0 and a weak model with MAE 12.0. Their errors differ on most rows. What is the most sensible expectation?
- The average's MAE is exactly 8.5, the mean of the two MAEs
- The average is always better than 5.0, whatever the errors
* The average may beat 5.0, but the weak model can drag it back, so it must be checked on held-out rows
- The average is always worse than the strong model
WHY: The MAE of an average is not the average of the MAEs, so the exact 8.5 claim is wrong. The result depends on how the errors line up, which is why held-out rows decide it.

Q: A team has three models with nearly identical errors and wants more diversity. Which change is most likely to add real diversity?
- Train three copies of the same tree with three different seeds
* Train models on different algorithms or input sets, then check the average on held-out rows
- Add a fourth copy of the best model to the average
- Average the three models' training errors instead of their predictions
WHY: Different algorithms or inputs make different mistakes, and that is what averaging needs. Adding a copy of the best model is the tempting wrong answer, because it looks like more work for the same result.
```

### Intended use

**What it is.** A model card has an intended-use section that names the users, the decision, the inputs and the time scale. Its out-of-scope section names uses the model was not built or tested for. Both must be specific enough for a reviewer to test. A vague phrase such as "for air quality" cannot be tested. A specific phrase can be checked against the data.

```text
Intended use: ward officers use the next-hour PM2.5 estimate to decide on same-day advisories.
Inputs: station, hour, no2, o3, pm10.
Out of scope: individual medical advice, enforcement against one factory, forecasts beyond six hours.
```

Each line can be checked. A reviewer can ask whether the team tested an hourly forecast, whether officers were the users, and whether six hours was the horizon in the test.

**How it shows up in a case study.** A draft card says its intended use is "air quality monitoring across India". A reviewer asks for the decision it supports and the rows it was tested on. The test covered one station for one week. The team narrows the intended use to the decision, the station and the period it was tested on, and lists out-of-scope uses such as other cities and monsoon months.

:::trap Vague is not broader
Writing "for everyone" or "for air quality" feels safe, but it gives a reviewer nothing to check. A vague claim is not a wider claim. It is an untestable one.
:::

```quiz
Q: A card for a PM2.5 model says only: "Intended use: air quality." Which edit makes the statement testable?
- Add "and related health topics" to widen the audience
- Shorten it to "air"
- Replace it with the model's file size
* Name the users, the decision, the inputs and the time horizon, for example ward officers, a same-day advisory, five input columns and the next hour
WHY: A testable intended use names users, decision, inputs and horizon. Widening the audience is the tempting wrong option, because it adds claims without making any of them checkable.

Q: A card is written for an hourly PM2.5 forecast. Which item belongs in its out-of-scope section?
- The station codes used as inputs
* Using the forecast as the only basis for a clinical treatment decision
- The date range of the training rows
- The model's learning rate
WHY: Out-of-scope lists uses the model was not built or tested for. Listing the inputs describes the model, not a misuse, so it is the tempting wrong answer.

Q: A reviewer asks why the card names ward officers as users and not the general public. What is the best reply?
* The officers' decision and the tested inputs were checked, while public use was never tested and would need its own evaluation
- The public is less important than officers
- The card must name the largest possible audience
- Naming the public is only needed when the model is a web app
WHY: A card names only the uses it was built and tested for. Naming the largest possible audience is the tempting wrong answer, because breadth is not evidence.
```

### Disaggregated metrics

**What it is.** Disaggregated metrics report the same metric for each important group, with the count for each group. An overall MAE is one number for the whole test set. A disaggregated table shows the MAE and the count for each station or each IST band. A large group can dominate the overall figure, so a weak small group can stay hidden.

```text
Group        n     MAE
ST-01      140     4.9
ST-04      120     8.1
Overall    400     5.2   (all six stations)
```

Only two of the six stations are shown in this extract. The overall row is the figure for every station together, which is why it can look fine while one station is much worse.

**How it shows up in a case study.** A card reports only the overall MAE of 5.2 and calls the model fair across stations. A reviewer asks for the breakdown. The team computes the per-station MAE and finds ST-04 at 8.1 from 120 rows. The card must add the table, state the gap and drop the word "fair" unless the evidence supports it.

:::trap Fair needs evidence
Reporting only the overall metric and calling the model fair is a common mistake. Fairness needs evidence for each group, and the overall figure cannot supply it.
:::

```quiz
Q: A card reports an overall MAE of 5.2 across six stations. Station ST-04 has an MAE of 8.1 from 120 of the 400 test rows. Which statement is supported?
- The model is fair because the overall MAE is under 6
- ST-04 is noise, since it is only 30 percent of the rows
* The overall figure hides a group that is much worse, so the card must show the per-station figures
- The overall MAE must be recomputed without ST-04
WHY: A large group can keep the overall figure low while one group is much worse. Calling ST-04 noise because it is 30 percent of the rows is the tempting wrong answer, since 120 rows is not a tiny group.

Q: A card says the model works well everywhere. Which addition turns that claim into evidence a reviewer can check?
- A longer description of the features
- The model file size in megabytes
- The Python version used in training
* A table of MAE and n for each station and each IST hour band
WHY: A per-group MAE with its count can be checked against the data. A longer feature description is the tempting wrong answer, because it describes the model without saying how well it performs.

Q: A slice has 18 rows and an MAE of 11.8, while the overall MAE is 6.0. What should the disaggregated table show for it?
- Hide the row so the table looks clean
* The row with its n of 18, flagged as insufficient evidence
- The row merged into another band without saying so
- Only the overall figure, because small groups are unreliable
WHY: The row and its count must be shown, with a flag. Hiding or merging it is the tempting wrong answer, because it removes evidence the reviewer needs.
```

### Choosing the number of trees

**What it is.** The number of trees is a setting. A forest uses `n_estimators`, and `HistGradientBoostingRegressor` uses `max_iter` for its stages. More trees in a random forest reduce variance, but the gain flattens out, and each extra tree costs fit time and file size. The rule this chapter uses is cross-validation on the same folds. Pick the smallest count after which the mean MAE improves by no more than the fold standard deviation.

```text
trees   CV MAE (mean)   fold std   fit time per fold
100     5.60            0.40       2.1 s
300     5.12            0.40       6.3 s
1000    5.10            0.40       20.8 s
```

Going from 100 to 300 trees improves the MAE by 0.48, which is more than the fold standard deviation of 0.40, so 300 is needed. Going from 300 to 1000 improves it by only 0.02, which is inside the standard deviation, so 300 is the choice.

**How it shows up in a case study.** A team trains a forest with 1000 trees. Each fold takes 20 seconds, and the model file is 480 MB. The MAE is only 0.02 better than with 300 trees, which is smaller than the fold standard deviation. The API must load the file quickly. The team picks 300 and writes the rule in its notes, so a reviewer can see why.

:::trap The best score on one split
Choosing the largest count because it scores best on one split is the usual mistake. One split is a noisy estimate, and the gain may be inside the noise. The extra trees still cost fit time and file size.
:::

```quiz
Q: A forest with 300 trees has a CV MAE of 5.12 ± 0.40. With 1000 trees it is 5.10 ± 0.41, and the file is three times larger. Which choice is best?
* Keep 300, because the 0.02 gain is inside the fold standard deviation
- Choose 1000, because the lower mean is always better
- Choose 1000, because file size does not matter for the API
- Choose the count with the slowest fit time
WHY: A difference smaller than the fold standard deviation is a tie, so the cheaper model wins. Choosing 1000 for the lower mean is the tempting wrong answer.

Q: Which statement about the number of stages in boosting is correct?
- More stages always help, so the largest count should be picked
- The stage count does not affect boosting performance
- The stage count is irrelevant once the learning rate is set
* Too many stages can overfit, so the count is tuned on held-out folds like any other setting
WHY: Boosting can overfit with too many stages, so the count is a tuned setting. The claim that more stages always help is the tempting wrong answer.

Q: A team picks 2000 trees for a forest because that setting had the best score on one split. What is the main weakness of that choice?
- The forest cannot use more than 500 trees
- The choice makes the bootstrap samples too small
* One split is a single noisy estimate, and the extra trees cost time and size for little measured gain
- The forest stops averaging once it has more than 1000 trees
WHY: One split can be noisy, and 2000 trees add cost. The claim that a forest cannot use more than 500 trees is false, which makes it a tempting but wrong answer.
```

### Training data and limits

**What it is.** The training-data section of a model card says where the rows came from, the date range, how many rows there were, which columns were features, how the train and test split was made, and what the data does not cover. The limits follow from the coverage. If the data covers one week in January, the card must say the model has not seen other seasons, and that its accuracy there is unknown. A limit states what was not covered. It does not claim that the model is accurate everywhere.

```text
Training data: CityPulse readings, one week of January, 1,600 training rows and 400 test rows.
Features: station, hour, no2, o3, pm10. Split: 80/20 with random seed 42.
Limits: no monsoon-season rows; ST-04 has the highest error; no per-prediction uncertainty.
```

**How it shows up in a case study.** A card reports an excellent MAE and says the model is ready for the whole year. The training data covers one week in January. A reviewer asks for the training-data section. The team states the date range and the row counts. It adds the limit that there are no monsoon rows, so accuracy in those months is unknown, and it recommends retraining with monsoon data before the claim is extended.

:::trap Facts without limits
Describing the data without the limits that follow from it is the usual mistake. A card that gives the rows but not the gaps lets a reader assume coverage the model never had.
:::


### The task in plain words

**Scenario.** A CityPulse model card must show more than one error number. It has to show where the model is weak. So the team averages several models into one ensemble, then slices the errors by station and by hour. You write three small functions that do the averaging, the subtraction and the grouping.

**Limits.** Each run may use 30 seconds and 128 MB of memory.

**The three functions.** The starter file has these names, with the parameters in this order:

- `ensemble_mean(predictions)`
  - `predictions` is a list with one inner list per model. All the inner lists have the same length.
  - Return one list. Position 0 of the result is the mean of position 0 across all the models, and so on for each position.
  - Round each value in the result to 2 decimals.
  - The statement's example: three models giving `[40.0, 50.0]`, `[44.0, 46.0]` and `[46.0, 54.0]` produce `[43.33, 50.0]`.

  - Round each value to 2 decimals.

  - `groups[i]` is the label of row `i`, such as a station id or an hour.
  - Return a dictionary from each label to the mean absolute error of the rows that carry that label.
  - Round each MAE to 2 decimals.
  - The keys of the dictionary must be in sorted order.

The visible tests add up to 75 points.

### What each function needs

Each idea below is shown on data that has nothing to do with CityPulse. Run each example in a Python shell, then try the same idea on the lab's data yourself.

**Pairing lists with `zip`.** `zip` pairs item 0 of one list with item 0 of the next, then item 1 with item 1, and it stops at the shorter list.

```python
for a, b in zip("abc", "xyz"):
    print(a + b)
```

The output is `ax`, `by` and `cz` on three lines. `zip(*lists)` takes a list of lists apart into separate arguments, so `list(zip(*[["a", "b"], ["c", "d"], ["e", "f"]]))` gives `[('a', 'c', 'e'), ('b', 'd', 'f')]`. The star is what makes the outer list separate.

**Averaging with `sum` and `len`.** The mean of a group of numbers is their sum divided by how many there are.

```python
takings = (120, 80, 100)
print(sum(takings) / len(takings))
```

The output is `100.0`. The `/` operator always returns a float, even when the division is exact. An empty list has a length of 0, and dividing by 0 raises `ZeroDivisionError`, so a function must deal with empty input before it divides.

**Rounding with `round`.** `round` takes a number and the count of decimal places.

```python
print(round(10 / 3, 2))   # 3.33
print(round(2.675, 2))    # 2.67
print(round(7, 2))        # 7
```

The second line gives 2.67, not 2.68, because 2.675 is stored as a value slightly below 2.675. The third line gives the integer 7, not 7.0. Round once, at the end of a calculation, rather than on every step.

**Sorting with `sorted` and a key.** `sorted` returns a new sorted list and leaves the original alone. The `key` argument says what to compare.

```python
print(sorted(["pear", "fig", "apple"], key=len))
print(sorted({"kiwi": 1, "date": 2}))
```

The output is `['fig', 'pear', 'apple']` and then `['date', 'kiwi']`. With `key=len`, the words are compared by length. Sorting a dictionary gives its keys in order, which is how you produce sorted keys.

**Reading a dictionary with `get`.** `get` returns the stored value, or a default when the key is missing. It does not add the key.

```python
stock = {"tea": 3}
print(stock.get("tea", 0))    # 3
print(stock.get("milk", 0))   # 0
print("milk" in stock)        # False
```

**Absolute value.** `abs` removes the sign of a number. A mean absolute error takes `abs` of each error before it averages them.

```python
print(abs(-4.5), abs(4.5))
```

The output is `4.5 4.5`.

### The rules people miss

The table covers the rules that the statement states. The statement does not mention empty input, ties or boundaries, so it gives no rule for them. If the starter file's docstring adds a rule, treat it as a statement rule and add a row.

| Rule in the statement | What a careless solution does | How to check yours |
|---|---|---|
| `ensemble_mean` takes the mean across models, position by position | Averages each model's list, or returns only the first model's list | Give three one-value models, such as `[[1.0], [2.0], [6.0]]`, and work out the answer by hand before you run it |
| Each ensemble value is rounded to 2 decimals | Rounds each model's prediction before averaging, or returns strings | Compare with the rounded version of your own unrounded mean; the values must be numbers |
| The predictions are equal-length lists, one per model | Uses only the first list's length and misses positions that the other models have | Use a three-model input and check that the result has as many values as each inner list |
| `residuals` is actual minus predicted | Takes predicted minus actual, which flips every sign | Take one row by hand and compute its residual on paper before you run the code |
| The residuals are signed | Takes absolute values, so the direction of the error is lost | Find a row where the model over-predicts; its residual must be negative |
| `mae_by_group` returns the mean absolute error | Returns the mean of the signed errors, which is the bias, so errors of +3 and -3 cancel to 0 | Use errors of +3 and -3 in one group; the MAE must be 3.0 |
| `groups[i]` labels row `i` | Pairs the lists in the wrong order, or sorts the rows before pairing them | Check the statement's example: it must give A of 3.0 and B of 3.0 with the groups in the order given |
| The keys are in sorted order | Returns the keys in the order they first appeared | Check that `list(result)` equals `sorted(result)` |
| The MAE is rounded to 2 decimals | Rounds every row's error before taking the mean, which changes the result | Compute the exact mean first, then round once at the end |
| A single-point ensemble (a visible test) | Divides by a fixed number of models instead of counting the models it was given | Give one model and expect its own values back, rounded to 2 decimals |

### A method that works for every graded lab

1. **Read the starter file.** Note the three names, their parameter order and any docstring. Do not rename anything.
2. **Write the statement's examples as assert lines first.** Each example gives an input and an expected output, so each assert is a copy of the example with the expected value. Run the file now. The asserts fail, because nothing is written yet. That is expected.
3. **Add your own asserts for every row of the rules table.** Use small inputs that you can work out by hand. Write the expected answer on paper before you run anything.
4. **Implement one function at a time.** Start with the simplest. After each function, run the asserts. Do not move on while one of them fails.
5. **Check types and rounding last.** Every number should be a float rounded to 2 decimals, and the keys of the dictionary should be in sorted order.
6. **Run the visible tests.** Read each failure message. A wrong value and a wrong type need different fixes.
7. **Submit once.** Submit when your own asserts and the visible tests all pass, not before.

### Worked twin problem

This twin problem uses a different domain: pH readings from lakes. It needs the same skills as the lab: a loop that builds totals, a dictionary of results, sorting with a key, rounding at the end, and skipping invalid values. pH measures how acid or alkaline water is, on a scale from 0 to 14, where 7 is neutral.

**Statement.** A reading is a dictionary with a `lake` name and a `ph` value.

- `clean_readings(rows)` keeps only the rows whose `ph` is a real number (an int or a float, but not a boolean and not a string) from 0 to 14 inclusive. A missing `ph` does not count as a number. Return the kept rows in their original order.
- `average_by_lake(rows)` returns a dictionary from each lake name to the mean `ph` of its rows, rounded to 1 decimal. The keys are in sorted order. A lake with no rows does not appear.
- `top_lakes(averages, k)` returns the names of the `k` lakes with the highest averages. Ties are ordered alphabetically by name. If there are fewer than `k` lakes, return all of them.

```python test
def clean_readings(rows):
    """Keep rows whose ph is a real number from 0 to 14 inclusive."""
    kept = []
    for row in rows:
        ph = row.get("ph")
        if isinstance(ph, bool) or not isinstance(ph, (int, float)):
            continue
        if 0 <= ph <= 14:
            kept.append(row)
    return kept


def average_by_lake(rows):
    """Mean pH per lake, rounded to 1 decimal, keys in sorted order."""
    totals = {}
    for row in rows:
        lake = row["lake"]
        total, count = totals.get(lake, (0.0, 0))
        totals[lake] = (total + row["ph"], count + 1)
    return {lake: round(total / count, 1) for lake, (total, count) in sorted(totals.items())}


def top_lakes(averages, k):
    """Names of the k highest averages, ties broken alphabetically."""
    ranked = sorted(averages.items(), key=lambda item: (-item[1], item[0]))
    return [name for name, _ in ranked[:k]]


# clean_readings
assert clean_readings([{"lake": "A", "ph": 7.0}, {"lake": "B", "ph": "7.2"}, {"lake": "C", "ph": True}, {"lake": "D", "ph": 15}, {"lake": "E", "ph": 0}]) == [{"lake": "A", "ph": 7.0}, {"lake": "E", "ph": 0}]
assert clean_readings([]) == []
assert clean_readings([{"lake": "X", "ph": 14}]) == [{"lake": "X", "ph": 14}]
assert clean_readings([{"lake": "Y", "ph": None}]) == []

# average_by_lake
assert average_by_lake([{"lake": "Bhimtal", "ph": 7.0}, {"lake": "Nainital", "ph": 8.0}, {"lake": "Bhimtal", "ph": 6.6}]) == {"Bhimtal": 6.8, "Nainital": 8.0}
assert list(average_by_lake([{"lake": "Nainital", "ph": 8.0}, {"lake": "Bhimtal", "ph": 6.6}]).keys()) == ["Bhimtal", "Nainital"]
assert average_by_lake([]) == {}

# top_lakes
assert top_lakes({"Bhimtal": 6.8, "Nainital": 8.0, "Sukhna": 8.0}, 2) == ["Nainital", "Sukhna"]
assert top_lakes({"A": 1.0}, 5) == ["A"]
assert top_lakes({}, 3) == []
assert top_lakes({"B": 2.0, "A": 2.0, "C": 1.0}, 1) == ["A"]

print("all checks passed")
```

Run the file. If every assert passes, it prints `all checks passed` and nothing else.

**Line by line, for `clean_readings`.**

- `row.get("ph")` reads the value, and gives `None` when the key is missing. A missing value then fails the type test instead of crashing the function.
- `isinstance(ph, bool)` is checked first, because `bool` is a subclass of `int`. `isinstance(True, int)` is `True`. Without this check, `True` would count as the number 1.
- `not isinstance(ph, (int, float))` skips strings such as `"7.2"`. They look like numbers, but they are text.
- `0 <= ph <= 14` keeps both ends of the range, because the statement says inclusive.
- `kept.append(row)` keeps the original dictionary, so the output has the same rows in the same order.

**Line by line, for `average_by_lake`.**

- `totals` stores a pair of (sum, count) for each lake.
- `totals.get(lake, (0.0, 0))` returns a pair of zeros for a lake that is new, which is the same idea as a running total that starts at zero.
- The loop adds the reading to the sum and adds one to the count.
- The dictionary comprehension goes over `sorted(totals.items())`, so the lakes come out in alphabetical order. For each lake it divides the sum by the count, and it rounds once, at the end.

**Line by line, for `top_lakes`.**

- `key=lambda item: (-item[1], item[0])` sorts by the average, largest first, because the average is negated. Ties are then sorted by name.
- `ranked[:k]` takes the first `k` items. If there are fewer than `k` items, the slice gives all of them.
- The list comprehension keeps only the name. The `_` is the usual name for a value you do not need.
