## What the quiz tests

The real Day Quiz has ten case-study multiple-choice questions, one on each topic below, in the same order. The pass mark is 70%. Only your first attempt is kept for your skill score, so treat the first attempt as the real test. Read each topic once, try the quiz block that follows it, and only then read the WHY lines.

Each question gives a short scenario, such as a team, a symptom or a constraint, and then one question. Answer it in this order.

1. Read the last line first. It tells you what is asked: the cause, the safest step, the cheapest option or the first thing to do.
2. Underline the facts in the scenario that matter. A port that is open to everyone, a key file with the wrong permissions or a stopped instance often decide the answer.
3. Eliminate options that are true in general but do not fix this scenario. Many wrong options are correct statements about a different problem.
4. Watch for three words. "Most" means several options are sensible and you must choose the strongest. "First" means the order of steps matters. "Best" means the answer must meet every constraint in the scenario, not just one of them.

The quiz blocks use the same format as the real quiz. Each WHY line explains the right answer and why the most tempting wrong option fails.

### SSH keys

**What it is.** SSH is a login that uses two linked files instead of a password. You make both files on your laptop with `ssh-keygen`. The private file has no extension and stays on your laptop. The public file ends in `.pub` and can be shared. The server keeps the public half. When you connect, SSH proves that you hold the private half without sending it across the network, so no password is typed.

```term
$ ssh-keygen -t ed25519 -f ~/.ssh/citypulse-asha -C "asha@citypulse"
Your identification has been saved in /home/asha/.ssh/citypulse-asha
Your public key has been saved in /home/asha/.ssh/citypulse-asha.pub
```

The `-t ed25519` option chooses a modern key type. The `-f` option sets the file name, and `-C` adds a label to the public key. In AWS there are two ways to get a key pair. `create-key-pair` makes both halves inside AWS and returns the private key once, in the command output. `import-key-pair` uploads a public key that you made yourself, so the private half never leaves your laptop. If you lose a private key that AWS created, AWS cannot give it back.

**How it shows up in a case study.** A CityPulse engineer's laptop is stolen. She had imported her public key into AWS, and her team lead asks whether AWS can re-send the private key so she can log in from a new laptop. The reasoning is simple. AWS never held the private key, so there is nothing to re-send. The fix is a new key pair made on the new laptop. Its public half is then added to the VM while an existing session is still open, and the new login is tested before the old key is retired.

:::trap Believing AWS keeps a copy of your private key
AWS keeps only the public half. A lost private key cannot be downloaded again. Keep the private file safe, and never commit it to Git.
:::

```quiz
Q: A CityPulse engineer's laptop is stolen. She made her key with ssh-keygen and imported the public half into AWS. Her colleague says AWS can send the private key to her again from the console. What is correct?
- AWS can send the private key to her from the console at any time.
* The private key existed only on the laptop, so she must make a new key pair and import its public half.
- AWS keeps the private key on the VM, so the VM can send it back to her.
- The public key contains the private key, so she can rebuild the private file from it.
WHY: AWS holds only the public half, so there is nothing to recover. The tempting wrong answer says the VM keeps a copy, but the private key never leaves the laptop it was made on.

Q: A team lead wants a key for a new VM. Nobody should ever need a copy of a private key that AWS created. Which approach meets this?
- Run aws ec2 create-key-pair and share the output file with the whole team.
- Run aws ec2 delete-key-pair and then reuse the old private file.
- Run ssh-add on the VM so that it holds the private key.
* Run ssh-keygen on your laptop, then run aws ec2 import-key-pair with the .pub file.
WHY: import-key-pair uploads only the public half, so the private key stays on your laptop. The tempting wrong answer is create-key-pair, which returns the private key once, so sharing its output spreads the secret.

Q: A script on your laptop fails with "Permission denied (publickey)". You find that the -i option points at the .pub file, not the private file. What is the correct fix?
* Point -i at the private file, which has no .pub ending.
- Add the .pub file to the VM with chmod 644 so that it can be read.
- Ask AWS to create a new private key, because the current one is damaged.
- Turn on password logins so that the script can continue without a key.
WHY: The -i option needs the private key, and the public file cannot prove that you own it. The tempting wrong answer, turning on passwords, weakens the server and removes the protection the key gives.
```

### Key file permissions

**What it is.** Every file has permissions that say who may read, write or run it. On Linux they appear in `ls -l`. The three groups are the owner, the group and everyone else. A number such as 600 is a short form. Each digit adds up the rights: 4 is read, 2 is write and 1 is run. So 6 means read and write, 4 means read only, and 0 means nothing. OpenSSH checks the private key before it uses it, and refuses a key that the group or other users can read.

```term
$ ls -l ~/.ssh/citypulse-asha
-rw------- 1 asha asha 411 citypulse-asha
$ chmod 644 ~/.ssh/citypulse-asha
$ ssh -i ~/.ssh/citypulse-asha ubuntu@203.0.113.7
@ WARNING: UNPROTECTED PRIVATE KEY FILE! @
```

The `chmod` command changes the mode. `chmod 600` gives the owner read and write, and removes everyone else's access. `chmod 400` gives the owner read only. Both are accepted. A mode of 644 lets everyone read the file, so SSH refuses it. Renaming or moving a file does not change its mode.

**How it shows up in a case study.** A student copies her key from a shared lab PC to her own laptop, then renames it to end in `.pem`. SSH now refuses the key with a warning about unprotected permissions. Her teaching assistant tells her that the rename caused the problem. The reasoning is that the rename did not change the mode. The mode was already too open when the file was copied. The fix is `chmod 600` on the renamed file, and then `ls -l` to confirm that the group and others have no access.

:::trap Choosing 777 or 644 because the command runs
A `chmod` command that runs is not the same as a correct one. 777 gives everyone write and run access. 644 still lets everyone read a private key. Only 600 or 400 is correct for a private key.
:::

```quiz
Q: A teammate sees that SSH refuses a key with mode 0640, which lets the group read it. He proposes chmod 777 and says the problem is solved because everyone can now use the key. What is the best reply?
- Agree, because a mode of 777 gives full access and SSH accepts any mode with full access.
- Agree only if the file is renamed to end in .pem first.
* Reject it. 777 lets everyone write and run the key. Use 600 or 400 so that only the owner has access.
- Reject it, because the group must be able to read a private key for it to work.
WHY: SSH needs the private key to be private, and 777 is the opposite of that. The tempting wrong answer treats "everyone can use it" as success, when the key is then open to any user on the machine.

Q: A key was copied from a shared PC and now has mode 644. SSH refuses it. You want the smallest correct change that keeps the key private to you. Which command?
* chmod 600 on the private key file, then run ssh again.
- chmod 666 on the private key file, because the owner needs to write to it.
- chmod 644 on the .pub file, because the server checks the public key first.
- Rename the private key file to a .txt extension and then run ssh.
WHY: chmod 600 removes group and other access and changes nothing else. The tempting wrong answer changes the .pub file, which is not the file SSH is refusing.

Q: You rename a private key from citypulse-asha to citypulse-asha.pem and move it into a new folder with mv. Its mode was 644 before the change. SSH now refuses it. Which explanation and fix are correct?
- The rename changed the mode to 644, so rename the file back to fix it.
- SSH refuses every .pem file, so convert the key to a .txt file.
- The move removed the owner's read permission, so the key must be created again on AWS.
* The rename and move do not change the mode, which was already 644. Run chmod 600 on the file.
WHY: A rename or a move keeps the mode, so the problem existed before the change. The tempting wrong answer blames the rename, which is a common but mistaken belief.
```

### Security groups

**What it is.** A security group is a stateful firewall attached to an EC2 instance. Each inbound rule names a protocol, a port or range of ports, and a source written as a CIDR range. A new security group has no inbound rules, so all inbound traffic is blocked until you add one. "Stateful" means that when a rule lets a connection in, the reply traffic is allowed back out automatically. A CIDR range such as `203.0.113.47/32` means exactly one address, and `10.0.0.0/16` means every address from 10.0.0.0 to 10.0.255.255.

```term
$ aws ec2 authorize-security-group-ingress --group-id sg-0cp42 --protocol tcp --port 22 --cidr 203.0.113.47/32
{
    "Return": true,
    ...
}
```

The command prints JSON. The `Return` field is `true` when the rule was added. A rule for port 22 with a source of `/32` admits one machine. The same port with a source of `10.0.0.0/16` admits every machine inside that private network.

**How it shows up in a case study.** The CityPulse ingest VM and a database VM share a VPC. A junior engineer adds the rule TCP 22 from the VPC range, so that the database VM can also reach the ingest VM. The team asks whether this is acceptable. The reasoning is that the range includes every machine in the VPC, not only the one that needs access. Any compromised machine in the network could then try SSH. The correct rule names one source only, such as the bastion's own `/32` address, and the team checks the rule set after each change.

:::trap Using a private range because it looks safe
A private range such as 10.0.0.0/16 is not private to a single machine. Read the range out as a list of addresses before you accept it.
:::

```quiz
Q: The operator's laptop has the address 198.51.100.20. A teammate proposes the inbound rule TCP 22 from 198.51.100.0/24, which is wider, "in case the laptop's address changes". What is the best response?
- Accept it, because a /24 range is narrower than the whole internet and therefore safe.
* Reject it. A /24 covers 256 addresses. Use 198.51.100.20/32, and update that one rule when the address changes.
- Accept it, because the group also needs port 22 open for the replies.
- Reject it, because security groups cannot use a /24 range at all.
WHY: A /24 includes 256 addresses, so it admits machines the team did not mean to allow. The tempting wrong answer compares it with the whole internet, which is a different question from who should reach port 22.

Q: A security group was created an hour ago and has no rules added. A developer says that the VM is in the team's VPC, so SSH from the office should already work. Which statement is correct?
- The VPC opens port 22 automatically from its own range, so SSH should work.
- Outbound traffic is blocked, so the replies to SSH cannot leave the VM.
- A new group allows inbound SSH from the operator's address by default.
* A new group has no inbound rules, so all inbound traffic is blocked until a rule is added.
WHY: A new security group blocks all inbound traffic until a rule is added. The tempting wrong answer assumes the VPC opens port 22 for you, which it does not.

Q: A security group allows TCP 22 from the operator's /32. The operator asks whether an outbound rule is also needed for the server's replies to reach the laptop. Which answer is correct?
- Yes, add an outbound rule for TCP 22 to the operator's /32, or the replies will be dropped.
- Yes, add an outbound rule for all ports to 0.0.0.0/0, or the session will hang.
* No. The security group is stateful, so replies to an allowed connection are allowed back automatically.
- No, because replies to SSH always use a different port, which is open by default.
WHY: The security group tracks the connection, so the replies need no separate rule. The tempting wrong answer is the first one, which treats the security group as if it were stateless and needed a matching outbound rule.
```

### Hardening sshd

**What it is.** sshd is the SSH server program. Its main settings live in `/etc/ssh/sshd_config`. Ubuntu also reads small drop-in files from `/etc/ssh/sshd_config.d/`. Three settings matter for CityPulse. `PasswordAuthentication no` turns off password logins. `PermitRootLogin no` stops anyone from logging in directly as the root user. `KbdInteractiveAuthentication no` turns off another way of typing a password. After you change a setting, `sudo sshd -t` checks the syntax and prints nothing when the file is valid. `sudo sshd -T` prints the settings that sshd will really use.

```term
$ sudo sshd -T | grep -Ei 'passwordauthentication|permitrootlogin'
passwordauthentication no
permitrootlogin no
```

sshd uses the first value it finds for each setting. Files in the drop-in folder are read in name order, so a file called `10-defaults.conf` is read before `99-citypulse.conf`. A later file with the same setting has no effect.

**How it shows up in a case study.** An engineer adds `99-citypulse.conf` with `PasswordAuthentication no`, runs `sshd -t`, and reloads the service. A reviewer agrees the change is done. A second engineer runs `sshd -T` and sees `passwordauthentication yes`. The reasoning points to an earlier drop-in that sets the value first. The correct next step is to find that line, make the two files agree, reload, and check the effective value again with `sshd -T`.

:::trap Trusting your own file instead of sshd -T
Your file may not be the setting that wins. Confirm the effective value with `sshd -T` before you claim the hardening works.
:::

```quiz
Q: An engineer adds 99-citypulse.conf with PasswordAuthentication no. The syntax check prints nothing, and the service is reloaded. A second engineer runs sshd -T and sees passwordauthentication yes. What is the most likely cause, and what should be done next?
* An earlier drop-in, such as 10-defaults.conf, sets the value first. Find it, make the files agree, reload, and check again with sshd -T.
- The reload did not run, so restart the VM, which always rereads the drop-in files.
- The file must end in .txt for sshd to read it, so rename it and reload.
- The syntax check is not a valid test, so ignore it and trust the reviewer.
WHY: sshd uses the first value it reads, and files are read in name order, so an earlier file wins. The tempting wrong answer is restarting the VM, which does not change which file sets the value first.

Q: You need to change the SSH settings on a VM that only you can reach. Which order is safest?
- Reload ssh, then look at the file for typos, then close your session.
- Restart the VM, then check the file for typos, then log in again.
* Make the change, run sshd -t, keep your current session open, reload, and open a new session that logs in with your key.
- Delete the existing sshd_config so that only your drop-in is read, then reload ssh.
WHY: The syntax check comes first, and the open session is your way back in if the new settings lock you out. The tempting wrong answer, closing the session after the reload, removes that way back in.

Q: A VM must refuse passwords but still accept your key. Which setting, and which check, confirm this?
- PermitRootLogin yes, checked with sshd -t, because a passing test means the setting is active.
- PasswordAuthentication yes, checked with sshd -T, because a yes value makes key login stricter.
- PubkeyAuthentication no, checked with systemctl status ssh, because the status shows the login method.
* PasswordAuthentication no, checked with sshd -T, which prints the effective value.
WHY: The effective value shown by sshd -T is the proof. The tempting wrong answer is sshd -t, which checks only the syntax and does not show which value is in force.
```

### EC2 pricing

**What it is.** EC2 charges for an instance while it runs, billed by the second. It also charges for the storage that the instance's disk uses. A stopped instance has no compute charge, but its disk still exists, so the storage charge continues. Terminating the instance deletes the instance and, by default, its root disk, so both charges stop (an extra volume that you attached yourself may survive, so check for one). Some other charges, such as those for public IP addresses, may continue after a stop, so check the current AWS pricing pages before you rely on an exact figure.

| Action | Compute charge | Disk (storage) charge |
|---|---|---|
| Instance running | Yes, by the second | Yes |
| Instance stopped | No | Yes, the disk is kept |
| Instance terminated | No | No, the disk is deleted |

Here is a simple way to estimate running hours. A VM that runs all day, every day, for 30 days runs 24 times 30, which is 720 hours. A VM stopped at 15:30 each day runs far fewer hours, but only if somebody remembers to stop it.

**How it shows up in a case study.** A lab team stops its CityPulse VM at 15:30 each day, but the bill still shows storage charges. Their manager asks whether the VM is free while it is stopped. The reasoning is that a stop removes the compute charge only. To remove the storage charge too, the team must terminate the VM, and that deletes the disk. The team therefore keeps the VM stopped during the course, and terminates it only when the lab is finished and the data has been copied elsewhere.

:::trap Assuming a stopped instance is free
A stopped instance keeps its disk, and the disk is still charged. Only termination removes the disk.
:::

```quiz
Q: A VM was stopped at 15:30 yesterday and started again this morning. A teammate says the VM cost nothing overnight because it was off. Which statement is correct?
- The VM was free overnight, because stopping an instance removes all of its charges.
- The VM was billed for every hour overnight at the full running rate.
- The VM was free overnight, but its disk was deleted, so the data is gone.
* Compute charges stopped overnight, but the disk attached to the VM was still charged.
WHY: Stopping halts the compute charge while the disk remains. The tempting wrong answer says the VM was free, which ignores the storage that the stop does not remove.

Q: A lab is finished, and the team wants to end all charges for it. Nothing needs to be kept on the VM. Which action should they take?
- Stop the instance and leave it for next week, when the lab may be resumed.
* Terminate the instance, which deletes the instance and its disk so that the charges stop.
- Change the instance to the smallest size, so that the compute charge is lower.
- Remove the security group, so that the instance cannot be billed while it runs.
WHY: Only termination deletes the disk, which removes the storage charge. The tempting wrong answer is stopping, which keeps the disk and its charge.

Q: A monthly bill for a CityPulse lab is larger than expected. The VM ran all day, every day, for a 30-day month because nobody stopped it. Which estimate of its running hours is right, and why?
* About 720 hours, because 24 hours a day times 30 days is 720.
- About 30 hours, because a VM is billed once a day.
- About 240 hours, because a VM runs only during the working day.
- About 72 hours, because billing stops after the first three days.
WHY: 24 times 30 is 720. The tempting wrong answer, 240, assumes the VM ran only during working hours, but nobody stopped it, so it ran all day.
```

### Instance hardening

**What it is.** Hardening means removing what you do not need, so that an attacker has fewer ways in. The attack surface is the set of all those ways: every open port, every enabled login method, every running service and every unpatched package. For a single VM, hardening means closing ports that are not needed, turning off logins that are not needed, stopping services that are not used, and installing security updates. The `ss` command shows what is listening.

```term
$ sudo ss -tlnp
LISTEN 0 128 0.0.0.0:22 0.0.0.0:* users:(("sshd",pid=812))
LISTEN 0 511 0.0.0.0:8000 0.0.0.0:* users:(("python3",pid=1507))
```

The second line shows a service listening on port 8000. Its output is shortened here for clarity. If nothing in the pipeline uses that service, it is attack surface, even if nobody has tried to reach it yet. Hardening is also not a one-time task. New security bugs are found all the time, so updates must be applied regularly, for example with `sudo apt-get upgrade`.

**How it shows up in a case study.** A demo of a CityPulse dashboard needs port 8000 open. The team opens it to 0.0.0.0/0 and says it will close later. A month later the port is still open, and the dashboard service is still running. The reasoning is that a temporary rule is one that is forgotten. The better approach is to open the port only from the audience's network range, and to close the rule and stop the service as soon as the demo ends. The change is recorded in the runbook so that anyone can see it.

:::trap Opening everything for convenience and calling it temporary
Temporary rules are the ones that get forgotten. Close the rule as part of the task, and write the closing step in the runbook.
:::

```quiz
Q: A CityPulse VM is configured correctly for its job, but the team has not installed any updates for four months. A manager says the VM is hardened, so no more work is needed. What is the best reply?
- The manager is right, because hardening is a one-off step that cannot be repeated.
- The manager is right, because updates only add features and never change security.
* The manager is wrong. Hardening includes keeping software patched, because new security bugs are found all the time.
- The manager is right, because a VM with no open ports cannot be attacked.
WHY: Patching closes known bugs in the software that is already installed. The tempting wrong answer says that no open ports means no attack, but an attacker can use unpatched software through a port that is open.

Q: Which change best reduces the attack surface of the ingest VM, without changing what the pipeline needs?
* Stop a service that the pipeline does not use, and close the port that nothing connects to.
- Open port 22 to 0.0.0.0/0 so that the monitoring tool can connect from anywhere.
- Install a second database server on the same VM so that the first one has a backup.
- Turn on password logins as a backup in case the key is lost.
WHY: Removing an unused service and an unused port reduces the ways in. The tempting wrong answer, turning on passwords, adds a login method that scanners try first.

Q: A demo needs port 8080 reachable by an audience on the office network, which is a /24 range. A teammate suggests opening 8080 to 0.0.0.0/0 and closing it later. What is the best approach?
- Open 8080 to 0.0.0.0/0 and write the closing date in a comment in the security group.
* Open 8080 only from the office /24 range, then remove the rule and stop the service when the demo ends, recording the steps in the runbook.
- Open all ports to 0.0.0.0/0, so that nothing is blocked during the demo.
- Leave the rule in place and rely on the instance stopping at 15:30.
WHY: The narrow range meets the demo's need, and the removal step makes the rule temporary in practice. The tempting wrong answer records a date but leaves the whole internet able to reach the port.
```

### User data bootstrap

**What it is.** User data is a script or piece of text that you give to AWS when you launch an instance. On the first boot, a service called cloud-init runs it, with administrator rights. This is useful for setting up packages and folders, so that each new VM starts in the same state. You pass the script with `--user-data`:

```bash
aws ec2 run-instances --image-id "$AMI" --instance-type t3.micro --user-data file://bootstrap.sh
```

A simple script might install a package and create a folder. User data is not private. Anyone who has permission to read the instance's attributes can read its user data, so it must never hold a password, a token or a private key. The script also runs only once, at the first boot. Editing it in the repository later changes nothing on a running VM.

**How it shows up in a case study.** A new engineer proposes putting the database password in the user-data script, so that the VM can connect as soon as it boots. The team reviews the idea. The reasoning is that anyone who can describe the instance could read the password, and the password would stay in the instance's record. The better approach is an instance role for AWS access, and a secret store or a prompt for anything else. The team also notes that the script runs only once, so a change to it needs a new instance or a manual run.

:::trap Putting a password or key in user data
User data can be read by anyone with permission to describe the instance. A secret placed there must be treated as exposed.
:::

```quiz
Q: A developer wants the VM to connect to the database on its first boot. The developer proposes writing the database password into the user-data script. What is the correct reply?
- Good plan, because user data is deleted after the first boot.
- Good plan, because only the root user can read user data.
- Good plan, if the script is stored in a private Git repository.
* Bad plan. Anyone who can describe the instance can read its user data, so the password would be exposed. Use an instance role or a secret store instead.
WHY: User data is readable through the instance's attributes, so it is not a safe place for secrets. The tempting wrong answer is the private repository, which protects the copy in Git but not the copy stored with the instance.

Q: A VM was launched with a user-data script that creates a folder. The team later edits the script in the repository and expects the running VM to pick up the change. What happens?
- The running VM reruns the new script at once.
* Nothing happens to the running VM, because the script runs once on the first boot. A new instance or a manual run is needed.
- The VM reruns the script every hour, so the change arrives within the hour.
- The VM reruns the script every time it is stopped and started.
WHY: User data is an instance-level script that runs once at first boot. The tempting wrong answer assumes it runs on every stop and start, which it does not by default.

Q: A team lead wants every new CityPulse VM to install the same packages during its first boot, with as little manual work as possible. Which setup meets the request?
- Store the package list in a database that the VM reads at login.
- Copy the packages from your laptop to the VM every morning.
* Pass a script with the install commands as user data at launch, so that the first boot runs them.
- Put the install commands in your ~/.aws folder, which the VM reads at boot.
WHY: Passing the script as user data makes the first boot install the packages without anyone typing them. The tempting wrong answer, copying packages by hand each morning, is manual work that the request was meant to remove.
```

### Private subnet egress

**What it is.** A subnet is a range of addresses inside a VPC. A private subnet has no route from the internet, and its machines have no public IP address, so nothing outside can start a connection to them. A NAT gateway sits in a public subnet and lets machines in the private subnet start outbound connections, for example to download updates. The replies come back through the gateway, but no one outside can start a new connection inward. This is why the private subnet is considered protected.

```term
$ aws ec2 describe-route-tables --route-table-ids rtb-0priv --query 'RouteTables[0].Routes[*].[DestinationCidrBlock,NatGatewayId]' --output text
10.0.0.0/16 None
0.0.0.0/0 nat-0a1b2c3d4e5f6a7b8
```

The first line is the local route, which covers traffic inside the VPC (it has no NAT gateway, so the query prints `None`). The second line shows that the default route for the private subnet points to a NAT gateway, not to an internet gateway. The route table is the part that makes a subnet private or public. If you need a shell on a private machine without opening any inbound port, AWS Systems Manager Session Manager is the alternative.

**How it shows up in a case study.** An ingest VM in a private subnet cannot download operating system updates. A teammate proposes giving the VM a public IP and opening port 80 to 0.0.0.0/0, so that the updates can arrive. The reasoning is that the VM needs outbound access only. A NAT gateway in a public subnet provides that, and it leaves inbound connections closed. The team changes the route table, and checks the update command again.

:::trap Giving a private machine a public IP to fix an update problem
A public IP and an open port remove the protection the private subnet gives. Fix outbound access with a NAT gateway instead.
:::

```quiz
Q: A VM in a private subnet cannot download operating system updates. The team wants the smallest change that allows downloads and allows no new connections from the internet. Which change should it make?
* Point the subnet's default route at a NAT gateway in a public subnet.
- Give the VM a public IP and open inbound port 80 from 0.0.0.0/0.
- Move the VM into a public subnet and open every port, so that the updates can arrive.
- Attach a second security group that allows all inbound traffic.
WHY: A NAT gateway forwards outbound traffic, and replies return through it. The tempting wrong answer, a public IP with an open port, makes the machine reachable from the whole internet.

Q: An engineer needs a shell on a VM in a private subnet. She plans to open port 22 from her office /32. A colleague says there is an option with no inbound port at all. Which option is it?
- Open port 22 to the VPC range, so that the connection stays inside the network.
- Attach an Elastic IP address to the VM, so that port 22 is reachable from the office.
- Use the NAT gateway, which accepts SSH connections from the office.
* Use AWS Systems Manager Session Manager, which needs the SSM agent and IAM permissions but no inbound port.
WHY: Session Manager opens a connection from the instance outward to AWS, so no inbound port is needed. The tempting wrong answer, an Elastic IP, makes the machine reachable from the internet, which the private subnet was designed to prevent.

Q: A team asks which device carries the outbound update traffic from a private VM to the internet. Which answer is correct?
- The VM's own public IP, because the VM must have one to send any traffic.
* The NAT gateway in a public subnet, which forwards the VM's outbound traffic.
- The internet gateway directly, because the private subnet is attached to it.
- The inbound rules of the security group, because those rules control all traffic.
WHY: The private subnet's default route points at the NAT gateway, which forwards the traffic. The tempting wrong answer is the internet gateway, which the private subnet does not route to.
```

### Access management

**What it is.** Access management decides who or what may perform which actions on which AWS resources. The principle of least privilege says to grant only the permissions that a job needs. An IAM user has long-lived access keys. An IAM role has no permanent keys. A service, such as an EC2 instance, takes the role and receives temporary credentials, which AWS rotates automatically. The identity that a VM uses appears in the output of a simple command:

```term
$ aws sts get-caller-identity --query Arn --output text
arn:aws:sts::123456789012:assumed-role/citypulse-pipeline/i-0a1b2c3d4e5f6a7b8
```

The word `assumed-role` shows that the VM is using a role. If the output says `user/`, the VM is using a person's keys, which is the wrong setup for a server.

**How it shows up in a case study.** A script on the ingest VM fails with AccessDenied when it writes to the bucket. The team attached the policy to the IAM user `citypulse-pipeline`, so the VM's role still lacks the permission. A teammate proposes copying the operator's access keys onto the VM as a quick fix. The reasoning is that those keys never expire and leak with any disk snapshot. The correct fix is to attach the policy to the role with `attach-role-policy`, and to check the identity output again.

:::trap Copying a user's access keys onto the VM
Keys copied to a VM never expire, and they leak through disk snapshots and backups. Use an instance role instead.
:::

```quiz
Q: A CityPulse script on a VM fails with AccessDenied when it writes to the S3 bucket. The team attached the policy citypulse-pipeline-s3 to the IAM user citypulse-pipeline. What is the correct step?
- Copy the user's access keys onto the VM and keep them there.
- Give the user the AdministratorAccess policy, so that every request passes.
* Attach the policy to the role citypulse-pipeline with attach-role-policy, because the VM uses the role, not the user.
- Remove the instance profile, so that the script uses the laptop's credentials.
WHY: The VM takes the role, so the permission must be on the role. The tempting wrong answer is to copy the user's keys, which is unsafe because a copied key can be leaked and never expires.

Q: A VM only needs to read one folder in an S3 bucket. Which permission setup follows least privilege?
- Attach AdministratorAccess to the role, so that future needs are covered.
* Attach a policy that allows only the read actions on that one folder of the bucket.
- Attach a policy that allows all S3 actions on all buckets, to be safe.
- Give the role the same policy as the root account, because it is the simplest option.
WHY: Least privilege grants the minimum the job needs, which is reading one folder. The tempting wrong answer is the broad policy, which is simpler to write but grants far more than the job requires.

Q: Why does an instance role avoid the risk of leaked keys in a disk snapshot?
- The snapshot encrypts the role's keys with the operator's password.
- Roles store their keys in a locked file that snapshots skip.
- The role can be used only from the operator's /32 address.
* The VM holds no permanent keys. It holds temporary credentials that expire and rotate, so a snapshot contains nothing that stays valid.
WHY: The credentials are short-lived and are fetched from the metadata service, so there is no long-lived secret to copy. The tempting wrong answer, the locked file, describes a storage method that does not exist for roles.
```

### Config drift

**What it is.** Config drift is the gap between the settings that a server should have, as recorded in its runbook or code, and the settings it really has. It happens when someone edits a file on the server by hand, changes a setting in the console, or skips a step. Drift is dangerous because the next rebuild, made from the recorded version, loses the change or repeats the old mistake. You can detect drift by checking the effective settings on the server. The `sshd -T` command is the example used in this course.

```term
$ sudo sshd -T | grep -i ^passwordauthentication
passwordauthentication yes
```

If the runbook says `PasswordAuthentication no`, this output shows drift. The fix is to find where the value is set, make the recorded version match the intended setting, and check the live value again.

**How it shows up in a case study.** An engineer rebuilds the CityPulse VM from the runbook. Afterwards, a password login succeeds. The team checks `sshd -T` and finds that password logins are on. The reasoning is that someone had edited the old VM's configuration during an incident and never recorded it. The rebuild followed the runbook, so it did not include the change. The team records the intended setting in the runbook and the drop-in file, then runs the check again.

:::trap Assuming a console change is documented
A change made by hand is not documented until someone writes it into the runbook or the code.
:::

```quiz
Q: The runbook says PasswordAuthentication no. On a rebuilt VM, sshd -T shows passwordauthentication yes. A teammate says the runbook must be wrong because the VM was rebuilt correctly. What is the best next step?
* Treat it as config drift. Find where the yes value comes from, make the code and runbook state the intended setting, then check again with sshd -T.
- Trust the teammate and delete the runbook section, because the server is the real truth.
- Restart the VM, so that the setting returns to the runbook value.
- Change the runbook to say yes, so that the two documents match.
WHY: The runbook records the intended setting, so the live value is the one to correct. The tempting wrong answer, changing the runbook to match the server, records the mistake as the plan.

Q: Someone changed the SSH settings on a VM by hand last month and did not record the change. The VM is still running, and the next rebuild from the runbook will not contain the change. Which statement is correct?
- The change is safe, because the VM runs the new setting, so the drift is already fixed.
- The change is safe if the VM is stopped for a day, because stopping resets the drift.
* This is config drift. The live server differs from the recorded setting, so the change must be written into the runbook or the code and the live settings checked.
- This is key rotation, so the fix is to generate a new key pair and leave the configuration alone.
WHY: Drift means the record and the running server disagree. The tempting wrong answer says the change is safe because the server works, but the next rebuild will lose it.

Q: Which practice is most likely to prevent config drift on a CityPulse VM over the next year?
```

## The graded lab

The graded lab is a Python problem. You write four functions in a starter file. The platform runs your functions against visible tests, which you can see, and then against hidden tests, which you cannot see. This section explains the task, the Python ideas it needs, the rules that careless solutions miss, a method you can repeat, and a worked twin problem. A twin problem has a different domain and different data, but it uses the same skills. You will not find a solution to the real task here, so you must write that yourself.

### The task in plain words

**The scenario.** The CityPulse ingest server runs on EC2. Before it goes live, you must audit the inbound rules of its security group. Each rule is a dictionary with three keys: `from_port` and `to_port`, which are whole numbers, and `cidr`, which is text. For example, `{"from_port": 22, "to_port": 22, "cidr": "0.0.0.0/0"}` is one rule.

You must write four functions in the starter file. The starter file defines their names already, so keep them exactly as given.

- `_in_range(rule, port)` returns `True` or `False`. It returns `True` when `port` is within the rule's range from `from_port` to `to_port`, including both ends.
- `port_allowed(rules, port, source_cidr)` returns `True` or `False`. It returns `True` when some rule covers `port` **and** its `cidr` is either `"0.0.0.0/0"` or exactly equal to `source_cidr`. Otherwise it returns `False`.
- `world_open_ports(rules)` returns a list. The list holds the distinct ports that are exposed to `"0.0.0.0/0"`, sorted in ascending order.
- `has_open_ssh(rules)` returns `True` or `False`. It returns `True` when port 22 can be reached from `"0.0.0.0/0"`.

The statement's example is this. With the single rule that opens port 22 to `"0.0.0.0/0"`, `port_allowed` for port 22 and the source `"203.0.113.7/32"` returns `True`, because the world rule allows any source. `world_open_ports` returns `[22]`, and `has_open_ssh` returns `True`, which is a red flag for hardening.

**The rules, one by one.**

- A rule covers every port from `from_port` up to `to_port`, including both of those ports. A rule from 80 to 82 covers 80, 81 and 82.
- A rule where `from_port` and `to_port` are equal covers exactly one port.
- A `cidr` of `"0.0.0.0/0"` allows any source. This includes the source you pass in.
- Any other `cidr` must match `source_cidr` exactly, as text. The address `203.0.113.7/32` is not the same as `203.0.113.70/32`, and it is not the same as `203.0.113.7`.
- `port_allowed` needs both conditions on the same rule. A world rule on another port does not help, and a rule on the right port with a different source does not help.
- `world_open_ports` counts only rules whose `cidr` is `"0.0.0.0/0"`. A rule with a private range or a single address is ignored, even if it covers the same ports.
- Each port appears once in the output of `world_open_ports`, even if two or more rules expose it.
- The output of `world_open_ports` is sorted in ascending order.
- `has_open_ssh` looks at port 22 only, and only at rules whose `cidr` is `"0.0.0.0/0"`. A rule whose range covers port 22 counts, even if 22 is not its first port.
- `_in_range`, `port_allowed` and `has_open_ssh` return `bool`. `world_open_ports` returns a `list`.

**Limits and scoring.** Each run is limited to 30 seconds and 128 MB of memory. The visible tests are worth 76 points in total. The hidden tests are two tests worth 24 points together. Together they make up the 100 points of the lab.

| Visible test | Points |
|---|---|

| 0.0.0.0/0 allows any source | 14 |
| Port not covered by any rule is blocked | 14 |

| Flag SSH (22) open to the world | 16 |

**What hidden tests are.** A hidden test is a test whose inputs and expected outputs are not shown to you. The platform runs it after you submit. You see only whether it passed or failed. Hidden tests exist to check the rules that the visible examples do not show, such as overlapping ranges, boundary ports, empty lists and near-miss addresses. ### What each function needs

This section teaches the Python ideas that the four functions use. Each example uses different data from the lab, so it is safe to try. Do not combine these examples into a solution. Write the functions yourself, and use the examples only to check how an idea behaves.

**Chained comparisons.** Python lets you write a range check as one expression. Both ends are included when you use `<=`.

```python
temperature = 21
print(18 <= temperature <= 24)   # True
print(18 <= 24 <= 24)            # True, the upper end is included
print(18 <= 25 <= 24)            # False
```

**Reading a dictionary value.** Use square brackets to read a key that you know is there. Use `get` with a default when the key may be missing.

```python
basket = {"pears": 4, "plums": 0}
print(basket["pears"])           # 4
print(basket.get("kiwis", 0))    # 0, because the key is missing
```

**Combining conditions.** `and` gives `True` only when both sides are `True`. `or` gives `True` when either side is. Python stops early when the answer is already known, so the second side is not evaluated in some cases.

```python
is_weekend = True
is_holiday = False
print(is_weekend and not is_holiday)   # True
print(is_weekend or is_holiday)        # True
```

**Testing whether any item matches.** `any` returns `True` as soon as one item in an iterable is true. It returns `False` when none is.

```python
scores = [72, 95, 60]
print(any(score > 90 for score in scores))   # True, because 95 is above 90
print(any(score > 99 for score in scores))   # False
```

**Exact text comparison.** `==` compares text character by character, and it is case-sensitive.

```python
fruit = "Apple"
print(fruit == "Apple")     # True
print(fruit == "apple")     # False, the capital A differs
```

**Collecting distinct values in a set.** A set keeps each value once, and it has no order. `set` turns an iterable into a set.

```python
letters = set("banana")
print(sorted(letters))      # ['a', 'b', 'n'], each letter once
print(len(letters))         # 3
```

**Sorting and filtering a list.** `sorted` returns a new list in ascending order, and the original list is not changed. A list comprehension builds a list from a loop with an optional `if`.

```python
words = ["pear", "apple", "fig", "kiwi"]
long_words = [w for w in words if len(w) > 3]
print(sorted(long_words))   # ['apple', 'kiwi', 'pear']
print(words)                # the original order is unchanged
```

**Sorting distinct values together.** Combining `set` and `sorted` gives a sorted list with no duplicates. Note that `sorted` always returns a list, even when its input is a set.

```python
numbers = [5, 2, 5, 9, 2]
print(sorted(set(numbers)))  # [2, 5, 9]
```

**Membership tests.** `in` returns `True` when a value is inside a list, a set or a string.

```python
colours = ["red", "green"]
print("green" in colours)    # True
print("blue" in colours)     # False
```

**Booleans are numbers too.** `True` and `False` belong to the `bool` type, which is a subclass of `int`. So `isinstance(True, int)` is `True`, and `True == 1` is also `True`. The comparison `is True` checks the identity of the value, which is stricter.

```python
flag = True
print(isinstance(flag, int))   # True, because bool is a subclass of int
print(type(flag) is int)       # False, the type is bool
print(flag == 1)               # True
print(flag is True)            # True
```

**Calling one function from another.** A function can call another function you wrote. This keeps each function short and easy to test.

```python
def is_even(n):
    return n % 2 == 0

def count_evens(numbers):
    return sum(1 for n in numbers if is_even(n))

print(count_evens([1, 2, 4, 7]))   # 2
```

### Worked twin problem

**The task.** A study-room desk in a library keeps a list of bookings. Each booking is a dictionary with `room` (a whole number), `start_hour` (a whole number), `end_hour` (a whole number), and `booked_by` (text). A booking covers the hours from `start_hour` up to but not including `end_hour`. So a booking from 9 to 11 covers hours 9 and 10, and hour 11 is free again. Write these four functions.

- `is_booked_at(booking, hour)` returns `True` when the booking covers `hour`, and `False` otherwise.
- `room_free(bookings, room, hour)` returns `True` when no booking for `room` covers `hour`.
- `busy_rooms(bookings, hour)` returns a sorted list of the distinct room numbers that are booked at `hour`. It returns `[]` when none are.
- `hours_booked(bookings, room)` returns the number of hours the room is booked in total. An hour that is booked twice counts once.

The solution below is complete and has been checked by hand.

```python test
def is_booked_at(booking, hour):
    return booking["start_hour"] <= hour < booking["end_hour"]


def room_free(bookings, room, hour):
    for b in bookings:
        if b["room"] == room and is_booked_at(b, hour):
            return False
    return True


def busy_rooms(bookings, hour):
    rooms = {b["room"] for b in bookings if is_booked_at(b, hour)}
    return sorted(rooms)


def hours_booked(bookings, room):
    hours = set()
    for b in bookings:
        if b["room"] == room:
            hours.update(range(b["start_hour"], b["end_hour"]))
    return len(hours)


bookings = [
    {"room": 1, "start_hour": 9, "end_hour": 11, "booked_by": "Asha"},
    {"room": 2, "start_hour": 10, "end_hour": 12, "booked_by": "Ben"},
    {"room": 1, "start_hour": 10, "end_hour": 13, "booked_by": "Chen"},
]

assert is_booked_at(bookings[0], 9) is True
assert is_booked_at(bookings[0], 10) is True
assert is_booked_at(bookings[0], 11) is False
assert is_booked_at(bookings[0], 8) is False

assert room_free(bookings, 1, 11) is False
assert room_free(bookings, 1, 13) is True
assert room_free(bookings, 3, 10) is True

assert busy_rooms(bookings, 10) == [1, 2]
assert busy_rooms(bookings, 12) == [1]
assert busy_rooms(bookings, 8) == []
assert busy_rooms([], 10) == []

assert hours_booked(bookings, 1) == 4
assert hours_booked(bookings, 2) == 2
assert hours_booked(bookings, 7) == 0

zero = [{"room": 5, "start_hour": 14, "end_hour": 14, "booked_by": "Dee"}]
assert hours_booked(zero, 5) == 0
assert is_booked_at(zero[0], 14) is False
```

```python test
def is_low(item, threshold):
    return item["qty"] < threshold


def low_items(items, threshold):
    names = [item["name"] for item in items if is_low(item, threshold)]
    return sorted(names)


def average_qty(items):
    if not items:
        return 0.0
    total = sum(item["qty"] for item in items)
    return round(total / len(items), 2)
```
