## What the quiz tests

The Day Quiz has ten case-study multiple-choice questions, one for each topic in this section, in the order given here. The pass mark is 70 per cent, so you need at least seven correct. Your skill score keeps your first attempt only, so take the quiz once with care. The practice questions below prepare you for the kind of reasoning the real questions need. They are not copies of the real questions, which you have not seen.

A case-study question gives you a short scenario about a team, then asks one question about it. Use the same method every time:

1. Read the last line first. It tells you what is being asked: the first step, the best reason, the most likely cause or the right owner.
2. Go back to the scenario and underline the facts that matter: the deadline, the number of items, who has which role, what is already done and what is still missing.
3. Eliminate options that are true in general but do not fix this scenario. "Testing is important" may be true, and still be the wrong answer to a question about the next step.
4. Watch the signal words. "Most" asks for the strongest answer among several sensible ones. "First" asks for the step that comes before the others. "Best" asks you to compare each option with the facts you underlined.

Each topic below has the same parts: what it is, how it shows up in a CityPulse case study, a box that names the most tempting mistake, and three practice questions with a reason for each answer. The section ends with a quick self-test of ten harder questions.

### Requirements prioritisation

**What it is.** A requirement is something the product must do or must have, such as "show the latest reading" or "export a report". Prioritising requirements means putting them in order, so that the team builds the most important ones first and can say clearly what waits. The method the course uses is MoSCoW. Must means the product fails without the item. Should means the item is important, but the product still works without it. Could means a useful extra that is built only if there is time. Won't (this time) means the team has decided not to build the item in this project, and it has written down why.

The test for each item is one question: does the product fail without it? Here is a small example from a dashboard for air-quality readings.

| Requirement | Bucket | Reason |
|---|---|---|
| Show the latest reading | Must | Without it, the dashboard has no content |
| Colour each reading by its advisory band | Should | Useful, but the readings can still be read without colour |
| Export a PDF of last week | Could | Build only if time remains |
| Dark mode | Won't (this time) | Not needed for this project, and the reason is written down |

After sorting, the team can point to one bucket for every row, and each bucket has a reason. That is what prioritisation produces: a decision that someone else can read and check.

**How it shows up in a case study.** The CityPulse squad has nine candidate items and three weeks. A stakeholder asks for four of them to be Musts because they matter to him. The squad asks the test question for each one. The dashboard cannot show a prediction without the prediction endpoint, so that item is a Must. The four requested items are useful, but the product still runs without them, so they become Should or Could. The team keeps the Musts to five or fewer and writes a reason for each Won't. The reasoning rests on the failure test, not on who asked loudest.

:::trap Everything is a Must
Marking every item as a Must because one senior person asked for all of them looks thorough, but it protects nothing. A list with six or more Musts has not been sorted. Move the least essential ones to Should, and keep the Musts to five or fewer.
:::

```quiz
Q: The CityPulse squad has nine candidate items for a three-week project. A mentor asks the team to mark every item the client requested as a Must. Which decision best fits the MoSCoW method?
- Mark all nine as Must, so that nothing is dropped
- Mark the three items the client asked for first as Must and the rest as Won't
* Mark an item as Must only where the product fails without it, and keep the Musts to five or fewer
- Mark everything as Should, so that the decision can wait
WHY: A Must is an item the product fails without, and the course caps Musts at five. Asking for an item does not make it essential. Nine Musts protects nothing, and marking everything Should avoids the decision rather than making it.

Q: After a sprint review the Must list has six items, and two of them depend on a data agreement that has not arrived. The lead asks what to do first. Which action is correct?
* Move the least essential extra Must to Should, keep five or fewer Musts, and record the data dependency as a risk
- Keep six Musts and ask the mentor to extend the deadline
- Move the data-dependent items to Won't without writing a reason
- Delete the data-dependent items from the backlog so the list looks clean
WHY: Six Musts breaks the cap of five, so one item must move. Moving an item without a reason removes the record, and a Won't needs a written reason. Deleting the items loses the record entirely, and a deadline extension is not the team's decision to make.

Q: Three weeks into the project, the Won't list is empty. A stakeholder keeps asking for a live link to the hospital database, which the team has no agreement to use. Which action gives the team a defensible answer?
- Keep answering the request until the stakeholder stops asking
- Add the database link to the Must list, because it is asked for often
- Delete the Won't list, since a short project does not need one
* Write the database link on the Won't list with its reason, such as no data agreement, so that the team can point to the decision
WHY: A Won't with a reason gives the team a documented answer that it can point to. Adding the link to the Musts would commit the team to work it cannot finish without an agreement. Deleting the list removes the record that the request was considered.
```

### Managing scope

**What it is.** Scope is the set of work that a project will deliver. Managing scope means deciding what is in and what is out, and recording each decision so that it can be checked later. Scope creep is the slow growth of work that happens when new requests are accepted without anything being removed. In a sprint, the team has a fixed capacity, measured in story points. Every addition uses some of that capacity, so an addition must displace something or wait for the next sprint.

Suppose the team has committed 10 story points, which is its whole capacity. A new request is estimated at 3 points. The team has two honest options: name a committed item that moves out to make room, or put the request in the next sprint. A third option, quietly working longer hours, hides the cost rather than managing it.

**How it shows up in a case study.** Midway through a CityPulse sprint, a client's manager sends a message: "Can you add a CSV download? It should be quick." The squad has no spare capacity. The correct first move is to write the request down, estimate it, and ask the product owner which committed item it would displace or whether it waits for the next sprint. Only then does the team answer the client. Whether the download is quick is a claim nobody has checked, so the estimate comes before any promise. The decision is recorded, so the team can explain it at the review.

:::trap The quick favour
"It should be quick" sounds harmless, and accepting it feels like good service. But capacity is fixed, so a quick favour is still work, and it pushes out something the team already promised. Estimate first, and make the trade-off visible.
:::

```quiz
Q: Midway through a sprint, a client's manager messages the squad: "Can you add a CSV download? It should be quick." The sprint has 10 story points committed and the team has no spare capacity. What should the squad do first?
- Build the CSV download in the evening, so the sprint still ends on time
* Estimate the CSV download, record it in the backlog, and agree with the product owner which committed item it would displace
- Tell the manager it is quick and add it to the sprint without a check
- Ignore the message, since the sprint is already committed
WHY: Fixed capacity means any addition displaces something, and the trade-off must be agreed and recorded. Evening work hides the cost. Ignoring the message leaves no record of the request. "Quick" is an unchecked estimate, so it cannot be promised.

Q: The scope document for a project lists a dashboard, a prediction API and a HANDOVER.md file. A teammate has built a map view that nobody approved, and the mentor asks how to keep scope honest. Which answer is best?
- Let teammates add anything useful, as long as they finish it before the deadline
- Remove the scope document, so that nobody can argue about it
- Accept the map view, because finished work is proof that it was needed
* Record the map view as a change request with its effort and a decision, and keep it out of the committed work until the team agrees
WHY: Scope control means that each change is written down and its cost is visible. Finished work does not show that the work was planned or agreed. Removing the document removes the thing that makes scope checkable, and accepting finished work by default rewards unapproved additions.

Q: A project's Won't list has four entries, each with a reason. Two months later a new team member proposes one of them again. What does the scope record allow the team to do?
* Point to the recorded reason, then decide with the product owner whether that reason still holds before reopening the item
- Accept the proposal at once, because the new member is enthusiastic
- Hide the old entry, so that the proposal looks new
- Refuse the proposal without discussion and without writing anything down
WHY: The reason in the Won't entry is the evidence for the earlier decision. A reason can stop being true, so reopening is possible, but only through a discussion that checks the reason. Accepting at once ignores the decision, and hiding or silently refusing the proposal loses the record.
```

### Incremental delivery

**What it is.** Incremental delivery means building and shipping small pieces that work from one end to the other, one after another. A layered plan does the opposite: it finishes the whole database, then the whole model, then the whole interface. A thin slice is a narrow path through every layer that works. It takes one input, passes it through each part and returns a visible result. Here is a tiny example of a slice written in Python.

```python
def ingest(reading):
    return {"pm25": reading}

def predict(row):
    return "good" if row["pm25"] < 50 else "moderate"

print(predict(ingest(12.0)))
```

The function `ingest` wraps the reading in a dictionary, and `predict` returns a band. The last line passes one value through both. The output is `good`, because 12.0 is below 50. The slice is small, but it proves that the path from input to answer works. Later, the team widens each part: real storage replaces the dictionary, and a real model replaces the rule. Each step keeps a working path.

**How it shows up in a case study.** A CityPulse team spends its first three weeks building the database layer, with no endpoint and no model. In week four it discovers that the stored format does not match what the model expects. A thin slice in week one would have shown that mismatch while there was still time to change the design. The mentor's advice is to make the first slice run from one reading in to one prediction out, and then widen it each week, checking the end-to-end path after each change.

:::trap Integrate at the end
"We will connect the layers in the last week" sounds like a plan, but it hides every integration problem until the time when fixing them is most expensive. Each layer may look finished alone and still fail when it meets the next one.
:::

```quiz
Q: A squad plans to build the database schema in weeks one and two, the model in weeks three and four and the web page in week five. Integration is planned for week six. A mentor asks what risk this plan carries. Which answer is best?
- It has no risk, because each layer is finished before the next one begins
* The layers may not fit together until week six, so integration problems appear late, when they are most costly to fix
- The schema will be too large to test properly
- The web page should be built first, because users see it first
WHY: Building one layer at a time hides integration problems until the end. Finishing a layer does not show that it works with the next one. The schema size and the order of the web page are not the risk the plan creates.

Q: A team must show a demo at the end of week one, and the data agreement is still pending. Which item is the best thing to show?
* One sample reading going through ingest, a simple advisory rule and a returned answer
- The full model with twelve features, trained on the complete dataset
- A complete design document with every table drawn
- A set of unit tests for code that has not yet been written
WHY: A thin slice runs from input to a visible output, so it is shown early and proves the path works. The full model needs data the team does not yet have. A design document and tests for code that does not exist prove nothing that runs.

Q: After its first thin slice works, the team must widen it. Which order keeps a working version at every step?
- Add all the remaining endpoints in one commit, then test everything
- Replace the database with a new one before testing the path
- Turn off the tests while the slice is widened
* Widen one step at a time, for example more readings and then real storage, and run the end-to-end check after each step
WHY: Widening in small steps with an end-to-end check after each one keeps a working version at all times, and it shows which change caused a failure. One large commit hides that cause, and turning off the tests removes the check that would catch the failure.
```

### Managing risk

**What it is.** A risk is an event that may happen and would hurt the project if it did. Risk management means recording each risk, judging how likely it is and how much damage it would do, naming an owner, and writing down what will be done about it. A list of these entries is called a risk register. Each entry needs a date on which someone reviews it, because a risk that nobody reviews is simply forgotten.

| Risk | Likelihood | Impact | Owner | Response | Review |
|---|---|---|---|---|---|
| The data agreement may not arrive | Medium | High | Asha | Switch to the public air-quality dataset if no agreement by 10 April | Friday stand-up |

The row is useful because someone can act on it. It names the event, the size of the damage, a person, a fallback and a date. A risk with only a description is a worry, not a plan.

**How it shows up in a case study.** The CityPulse squad's register says only "data may be late". The mentor asks the team to make the entry complete. The squad adds an owner who will chase the agreement, a likelihood and impact rating, a fallback dataset, and a date on which the fallback is switched on if the agreement has not arrived. The entry is now something the team can act on. The reasoning is that a fallback you have not triggered is still a plan, but only once it has a trigger and an owner.

:::trap The register with no owner
A register that lists risks with no owner, no response and no review date looks careful, because it is long. It cannot change anything, because nobody is responsible for acting on it.
:::

```quiz
Q: The risk register says "the server may be slow", with no owner, no rating and no date. The mentor reviews it on Friday. Which change most improves the entry?
* Add an owner, a likelihood and impact rating, a response such as caching the advice, and a review date
- Add the word critical to the title, so that people notice it
- Delete the risk, because a slow server is normal
- Move the risk to the Won't list
WHY: A complete risk has an owner, a rating, a response and a review date. A word like critical adds no information. Deleting the risk removes a real concern, and the Won't list records scope decisions, not risks.

Q: A risk is rated high impact and medium likelihood. The team has a fallback dataset ready but has not decided when to use it. Which is the most useful next step?
- Treat the risk as closed, because a fallback exists
- Wait until the deadline and see what happens
- Lower the impact rating, because the team is confident in the rest of the plan
* Set a decision date and name the person who will switch to the fallback if the agreement is late
WHY: A fallback that has no trigger and no owner is not yet a response. Waiting leaves no time to act, and lowering the rating without evidence hides the risk rather than managing it. Closing the risk is premature while the decision is still open.

Q: A squad writes the risk "the client may change their mind". Which rewrite turns it into a useful risk entry?
- The client may be difficult to work with
- The client is unpredictable, so the team cannot plan anything
* If the client changes the success measure after week two, the sprint may need re-planning, so the product owner agrees a change process and reviews scope at each sprint review
WHY: A useful risk names a specific event, its effect and a response. Difficult and unpredictable are labels that nobody can assess, and they suggest no response. The correct option names the trigger, the consequence and the action.
```

### Agile ceremonies

**What it is.** A ceremony is a regular meeting with a fixed purpose in an agile team. The four that matter here are sprint planning, the daily stand-up, the sprint review and the retrospective. Each one answers a different question. Sprint planning asks what the team will commit to in the next sprint. The daily stand-up asks whether anything is blocking the work today. The sprint review asks whether the product works and whether stakeholders want to change it. The retrospective asks how the team worked and what it will change.

| Ceremony | When | Question it answers | Main audience |
|---|---|---|---|
| Sprint planning | Start of the sprint | What will we commit to, and what is the goal? | The team |
| Daily stand-up | Every day, about 15 minutes | What is blocking us today? | The team |
| Sprint review | End of the sprint | Does the product work, and is it what stakeholders need? | The team and stakeholders |
| Retrospective | End of the sprint, after the review | How did we work, and what will we change? | The team |

**How it shows up in a case study.** A CityPulse squad reaches the end of its sprint. The client's manager attends the demo and gives feedback on the dashboard. A teammate then wants to use the same meeting to discuss how the sprint was run. The mentor separates the two. The feedback on the product belongs to the sprint review, and the discussion of the team's process belongs to the retrospective, which should be held after the review and be blameless. Keeping them apart stops the client from sitting through an internal debate, and it stops the team's process from being judged by a stakeholder.

:::trap Review and retrospective are the same meeting
Both happen at the end of a sprint, so they are easy to confuse. The review is about the product and includes stakeholders. The retrospective is about the team's process and is internal. Mixing them means that neither is done properly.
:::

```quiz
Q: At the start of a sprint, the squad decides which backlog items it will commit to, and writes down a sprint goal. Which ceremony is this?
- The daily stand-up
* Sprint planning
- The retrospective
- The sprint review
WHY: Sprint planning chooses the committed work and states the goal. The stand-up is a short daily check, the review shows the product to stakeholders at the end, and the retrospective examines how the team worked.

Q: A squad's daily stand-up has grown to forty minutes, with people solving problems during the meeting. The scrum master wants it back to its purpose. Which change fits?
- Add a second stand-up each day for the same purpose
- Stop the stand-ups and send a weekly email instead
- Have the product owner give a full status report to the client each day
* Keep it short, with each person saying what they did, what they will do and what blocks them, and take problem-solving to a separate conversation afterwards
WHY: The stand-up is a short status check, so problems are taken after it, with only the people involved. A second meeting doubles the cost without fixing the cause. A weekly email loses the daily coordination, and a client report is not the purpose of the meeting.

Q: A sprint review ends with the team discussing that the stand-ups were too long and that planning took two hours. Which ceremony should have covered this discussion?
* The retrospective, because it looks at how the team worked
- The sprint review, because it shows the product to stakeholders
- The daily stand-up, because it is a short status check
- Sprint planning, because it chooses the next work
WHY: The retrospective examines the team's process, including meeting length and planning time. The review is about the product, and it is the wrong place for an internal discussion. The stand-up and planning are the meetings whose length is being judged, and they do not review themselves.
```

### Acceptance criteria

**What it is.** An acceptance criterion is a condition that must be true before a piece of work counts as done. A good criterion is testable: someone who did not write the work can check it with a command or a number and get a clear yes or no. Here are two examples.

| Vague | Testable |
|---|---|
| The API works | `curl -d @tests/sample.json` to `/predict` returns HTTP 200 |
| Predictions are fast | 95 per cent of requests on the test laptop finish in under 500 ms |

The vague version cannot fail, so it cannot be checked. Two people can read "works" and disagree about whether it is met. The testable version names the command or measure, so the result is either a 200 status or it is not, and either under 500 ms or not.

**How it shows up in a case study.** The CityPulse team writes a card for the prediction endpoint that says "the endpoint is reliable". A tester asks how she will know it is done. The mentor asks the team to rewrite the criterion so that it names a sample request, the expected status code and the field the reply must contain. The rewrite also says where the test runs. The reasoning is that a criterion is only as good as the check someone can run from it.

:::trap Criteria that cannot fail
"The dashboard is user-friendly" and "the code is clean" are common acceptance lines. They describe a quality, but they give no test and no number, so the work can be called done whatever happens.
:::

```quiz
Q: A squad's card for the prediction endpoint says "the endpoint is reliable". A tester asks how she will know the card is done. Which acceptance criterion is testable?
- The endpoint is reliable for most users
- The team is confident that the endpoint is reliable
- A senior developer has reviewed the endpoint
* A sample request with a valid body returns HTTP 200, and the reply contains a field named wait_minutes
WHY: A testable criterion gives a command or number and a clear yes or no. Reliable for most users, confidence and review are judgements, and two people could disagree about each one. Only the sample request with its expected status and field can be checked by anyone.

Q: A criterion reads "the report loads quickly on a phone". Which rewrite is the most testable?
* The report page loads in under three seconds on a mid-range phone over a 4G connection, measured in the browser's network panel
- The report page loads faster than the old version
- The report page looks modern on phones
- The report page is quick for most users
WHY: The correct rewrite names a number, the conditions and a way to measure. "Faster than the old version" has no number, and "modern" and "quick for most users" are opinions. The tester would still have to ask the author what each one means.

Q: A tester is told that the acceptance line for the ingest step is "ingest works". She runs it and loads zero rows. Why did the criterion fail to protect the team?
- The tester ran it on the wrong laptop
- The criterion was too long to read easily
- The team did not write a test file for the ingest step
* The criterion did not name a count or a check, so a run that loaded zero rows could still be called a success
WHY: Without a number, "works" can be claimed when the output is empty. A criterion such as "the logged row count matches the number of readings in the file" would fail at zero. The other options do not explain why the criterion allowed a failure to pass.
```

### Handover runbooks

**What it is.** A runbook is a document of exact steps for running and looking after a system. Each step gives a command, the output a reader should expect, what to do if the output is different, and how to roll back. A handover runbook is written so that a stranger can keep the system running after the original authors have left. It sits alongside the README and the HANDOVER.md file, and it holds the parts that a README usually leaves out, such as known issues.

| Step | Command | Expected output |
|---|---|---|
| 1 | `pytest -q .` | `1 passed in 0.00s` |
| 2 | `docker compose up -d --build` | One line per service, each started or running |
| 3 | `curl -i -X POST -d @tests/sample.json ...` | First line `HTTP/1.1 200 OK` |

The table is a runbook in miniature. A newcomer can see the command, the result that means success, and the result that means something has gone wrong.

**How it shows up in a case study.** The CityPulse project is handed to a client's engineer. On the first run, Step 3 fails with "file not found", although the file exists on the original author's laptop. The runbook was written from memory, and the file is listed in `.gitignore`, so it never reached the repository. The fix is to run every command on a clean clone of the tagged version before the handover is merged, and to record the expected output beside each command. The new owner then sees the failure in the runbook's own test, not in the first minute of their own work.

:::trap Commands that were never run
A runbook command that has never been run from a clean copy is a guess. The first real run then fails in front of the new owner, which is the worst time to find out.
:::

```quiz
Q: A new owner follows the handover runbook. Step 3 fails with "file not found", although the file is in the author's folder. Which change to the runbook prevents this next time?
- Add a longer introduction about the history of the project
* Run every command on a clean clone of the tagged version before merging, and write the expected output beside each command
- Replace the runbook with a recorded video
- Delete Step 3, since the loader is optional
WHY: A runbook fails when its commands were never run from the state a newcomer starts in. A clean clone and recorded output catch that. A longer history, a video or removing a step does not address the cause, which is an untested assumption about which files exist.

Q: A runbook has an accurate list of commands, but it does not say what to do when the service answers the sample request with 422. Which section is missing?
- The architecture diagram
- The list of owners in the README
- The changelog
* The known issues and troubleshooting section, with the meaning and the fix for each documented failure
WHY: Known issues and troubleshooting tell the newcomer what a failure means and what to do about it. A 422 means the input was rejected, so the fix is in the request, not in the service. A diagram, an owner list and a changelog do not explain a status code.

Q: A handover includes the rollback step "go back to the old version". Which rewrite makes the step precise?
- Go back to the previous version of the code
- Use whichever version worked last time
* Check out the tag v1.0.0 for the code, start the image citypulse:1.0.0 for the running service, and do this when the smoke test fails after deploy
- Contact the original author for help
WHY: A rollback is precise when it names the tag, the image and the trigger. "The previous version" and "whichever worked last time" are vague. Asking the original author defeats the purpose of a handover, because the new owner must be able to act without them.
```

### Roles and RACI

**What it is.** A RACI chart lists each task and says who plays which role in it. R means Responsible, the person who does the work. A means Accountable, the person who signs off the result. C means Consulted, people who give input before the decision. I means Informed, people who hear the outcome afterwards. Each task must have exactly one A. Two As mean that nobody clearly owns the outcome, and no A means that nobody signs it off. Here is a small chart for three tasks.

| Task | Asha | Ravi | Neha | Client |
|---|---|---|---|---|
| Ingest the readings | R | C | I | I |
| Train the model | C | A | R | I |
| Sign off the release | A | R | C | I |

Read down a column to see a person's roles, and read across a row to check that a task has exactly one A. The client is marked I because they hear about the release but do not approve it.

**How it shows up in a case study.** The CityPulse squad fills in a RACI chart for the release of the OPD model. Two people are marked A for the release, and the client is also marked A because it owns the product. The mentor says the chart is invalid. The fix is to keep exactly one A, on the person who signs the release off, and to give the other roles to the people who do the work, consult or inform. The client moves to I, since it hears about the release and does not approve it.

:::trap Two Accountables, or none
A chart with two As looks shared, but it means nobody owns the result. A chart with no A looks neutral, but it means nobody can sign off. Both break the rule.
:::

```quiz
Q: For the release task, the squad has marked two people as A, one of them also as R. Which correction makes the chart valid under RACI?
- Put the A on the client, because the client is the final user
- Mark both people as C, so that neither signs off
- Remove the A from both and mark the team as a whole as A
* Keep exactly one A, on the person who signs off the release, and give the other person the role that fits their work, R, C or I
WHY: Each task needs exactly one Accountable person. Two As leave the outcome unowned. Marking both as C removes the sign-off altogether, and a team or client cannot be accountable in the RACI sense. The correction is one A and roles that match the work.

Q: A roles chart for the handover has no A on the task "write the runbook section for api/". The original author will review and sign off the section, and a non-author will draft it. Which change is correct?
* Assign the single A to the original author, who signs off the section, and keep the non-author as R
- Remove the R from the non-author, so that only one person works on it
- Add a second A, so that both people are accountable
- Mark the original author as I, so that they only hear about it
WHY: The reviewer who signs off the section is Accountable, so the A belongs to the original author. The drafter remains Responsible. Two As or marking the sign-off person as I breaks the rule. Removing the drafter leaves the section with nobody doing the work.

Q: A client receives a note about the release and attends the review, but does not approve the release. Which RACI letter fits the client?
- R
- A
- C
* I
WHY: Informed means the person hears the outcome and takes no part in the decision. Consulted means the person gives input before the decision, which the client did not do here. Responsible and Accountable both imply doing the work or signing it off, and the client does neither in this case.
```

### Retrospectives

**What it is.** A retrospective is a short meeting at the end of a sprint. The team asks three questions: what went well, what did not go well, and what it will change next time. Each change needs an owner and a date for the next sprint, or it will not happen. The meeting should be blameless, which means it examines the process rather than looking for the person who made a mistake. A useful retrospective produces a few specific changes, not a list of complaints.

| Went well | Did not go well | Change | Owner | Check |
|---|---|---|---|---|
| The stand-ups were short | The demo data was loaded on the morning of the review | Load and check the demo data the day before each review | Asha | Next sprint retrospective |

The row shows the three parts of a good output: what happened, what will change, and who will check it by when.

**How it shows up in a case study.** At the end of a CityPulse sprint, the sprint review failed because the demo data was not loaded in time. At the retrospective, someone suggests that one teammate should be more careful. The mentor asks the team to turn the problem into a process change: check and load the demo data the day before, give the job to one named owner, and review the result at the next retrospective. The reasoning is that blaming a person does not stop the next failure, but a changed process can.

:::trap A list of complaints
A retrospective that ends with a long list of complaints and no actions feels honest, but nothing changes. Each complaint should become a change with an owner and a date, and the team should pick the few that matter most.
:::


### The project charter

**What it is.** A project charter is a short document that starts a project. It states the purpose, which is why the project exists. It names the sponsor, who authorises the work. It lists the success measures, which show when the project has succeeded. It records the main constraints, such as the deadline or the data available, and the main risks. The charter changes rarely. A sprint plan is different. It lists the work for the next few weeks in detail, and it changes at each sprint.

| Charter field | Example for CityPulse |
|---|---|
| Purpose | Tell hospital operations staff how long each outpatient wait is likely to be |
| Sponsor | The client's operations manager, who approves the project |
| Success measures | The model beats the current median rule on the holdout data |
| Constraints | Three weeks, the data available by 10 April, no paid hosting |
| Main risks | The data agreement may not arrive |

The field list answers why the project exists and how it will be judged. A day-by-day task list does not belong in it, because that list will be out of date within a week.

**How it shows up in a case study.** A CityPulse squad is asked for its charter before the work starts. Its document is a list of tasks for each of the next three weeks, with names and hours beside each task. The mentor asks for the charter to be rebuilt. The purpose, the sponsor, the success measures and the constraints must come first, and the task list moves to the sprint plan where it can change. The reasoning is that a charter tells the reader why the work matters and who decided it, while a plan tells them what the team will do this week.

:::trap A plan called a charter
A day-by-day plan looks like a serious document, so it is easy to mistake it for a charter. But it leaves out why the project exists and who approved it, and those are the two things a charter must answer.
:::

```quiz

WHY: A charter states why the project exists, who authorised it, how success is measured and what limits it. Sprint review dates and task lists belong in the sprint plan, and retrospective notes and pull request lists are outputs that come later.
```

## The graded lab

The graded lab is a short Python task with a time limit of 30 seconds and a memory limit of 128 MB. It is marked by visible tests, which you can run yourself, and by hidden tests, which you cannot see. The visible tests are worth 85 points and the hidden tests are worth 15 points. Hidden tests check the edge cases and rules that the visible tests do not cover, so they decide whether you reach full marks. This section restates the task, explains the Python ideas it needs, lists the rules that careless solutions break, gives a method, and works through a different problem that uses the same skills.

### The task in plain words

**The scenario.** The CityPulse team has a fixed sprint capacity. It must decide which backlog items to commit to, using each item's value, its effort and whether it is a Must. Your job is to write three functions that make those decisions for the backlog.

Each backlog item is a dictionary with four keys: `id`, which is text; `value`, which is a whole number; `effort`, which is a whole number; and `must`, which is True or False. A dictionary is a collection of named values, written in braces. The starter file gives you a module-level dictionary called `RANK` and three functions. The rules for each function are these.

- `moscow_bucket(item) -> str` takes one item and returns one of four text values: "Must", "Should", "Could" or "Wont".
  - If `item["must"]` is truthy, return "Must". In Python, a value is truthy if it counts as True in an `if` test. Most values are truthy, but 0, False, None and the empty string are not.
  - Otherwise, compute the ratio `value / effort`. If the ratio is 3 or more, return "Should". If it is 1.5 or more, return "Could". Otherwise return "Wont". "3 or more" includes exactly 3, and "1.5 or more" includes exactly 1.5.
- `prioritise(items) -> list[str]` takes a list of items and returns the list of their ids, in priority order.
  - Sort by three things, in this order: the bucket rank, where Must comes before Should, Should before Could, and Could before Wont; then the ratio `value / effort`, highest first; then the `id`, A to Z, to break any tie.
  - The bucket rank is looked up in `RANK`, which maps each bucket name to a number from 0 to 3.
- `fit_capacity(items, capacity) -> list[str]` walks the items in the priority order that `prioritise` gives. For each item, it keeps the item if its effort still fits in the capacity that remains, and then takes that effort off the remaining capacity. It returns the chosen ids in the order they were taken. It does not stop when an item does not fit.

The statement gives one worked example. An item with value 10 and effort 2 has a ratio of 5, and its bucket is "Should" if it is not a Must. With a backlog of A (10 over 2), E (8 over 2), D (a Must), B (3 over 2) and C (1 over 2), and a capacity of 8, `prioritise` returns D, A, E, B, C, and `fit_capacity` returns D, A, E.

**The scoring table.** Each visible test is worth the points shown below. The total is 85.

| Visible test | Points |
|---|---|
| Must-have flag wins regardless of ratio | 10 |
| Ratio 5 gives Should | 10 |
| Ratio 1.5 gives Could | 10 |
| Ratio 0.5 gives Wont | 10 |
| Must first, then by value/effort descending | 25 |
| Greedy fit within capacity 8 | 20 |

**The hidden tests.** There are two hidden tests, worth 15 points between them. You cannot see them, and they are not described one by one. They are the reason you must test your own edge cases. A solution that passes every visible test can still lose the 15 points if it gets an edge case wrong, such as a ratio exactly on a boundary, a tie in the sort, an empty list or an input that has been changed.

### What each function needs

Each idea below is taught with a small example that uses different data, such as exam marks or a shopping list. Do not use these examples as parts of your solution. Their job is to show you the idea, so that you can apply it to the lab's data yourself.

**Truthiness and `if`.** An `if` statement runs its block when the test after it is truthy. Python treats `0`, `False`, `None`, `""` and an empty list as false, and most other values as true.

```python
for answer in [0, "no", ""]:
    print(repr(answer), bool(answer))
```

The output is `0 False`, then `'no' True`, then `'' False`. The string "no" is not empty, so it is truthy, even though its meaning is negative. If the statement says "truthy", test the value with `if`, not with `== True`.

**Comparisons at a boundary.** A comparison with `>=` includes the boundary, and a comparison with `>` excludes it. Use the one the statement names.

```python
def grade(mark):
    if mark >= 70:
        return "Distinction"
    if mark >= 50:
        return "Pass"
    return "Fail"

print(grade(70), grade(69.9), grade(50))
```

The output is `Distinction Pass Pass`. A mark of exactly 70 is a Distinction, because the test includes 70. A mark of 69.9 is not, so it falls to the next test.

**Division and rounding.** In Python 3, `/` gives a decimal result, and `//` drops the decimal part. Round only once, at the end of a calculation, and only if the task asks for it.

```python
print(7 / 2, 7 // 2, round(10 / 3, 2))
```

The output is `3.5 3 3.33`. The `//` operator gives 3, which would be wrong for any comparison that needs the decimal part. Rounding `10 / 3` early to a whole number would also change the answer that a boundary test sees.

**Numbers and `bool`.** A `bool` is a special kind of integer. `True` counts as 1 and `False` as 0, so `isinstance(True, int)` is True. This matters when a check must distinguish a flag from a number.

```python
print(isinstance(True, int), isinstance(True, bool), type(5).__name__)
```

The output is `True True int`. If a check must reject flags but accept numbers, test for `bool` first, because a plain `int` test accepts True as well.

**Reading dictionary values.** `d["key"]` returns the value for `key`, and fails with a `KeyError` if the key is missing. `d.get("key", default)` returns the default instead.

```python
member = {"name": "Mira", "paid": True}
print(member["name"], member.get("discount", 0))
```

The output is `Mira 0`. Use `[]` for keys that must exist, and `.get` only for keys that are optional.

**Sorting with a key.** `sorted(items, key=f)` returns a new list in the order of the value `f` gives for each item. The original list is left unchanged. A key can be a tuple, and tuples compare one position at a time from the left.

```python
words = ["pear", "fig", "apple", "kiwi"]
print(sorted(words, key=lambda w: (-len(w), w)))
```

The output is `['apple', 'kiwi', 'pear', 'fig']`. The number of letters is negated, so longer words come first. Words of the same length are then ordered A to Z. Sorting text places capital letters before lower-case ones, so `sorted(["b", "A", "a"])` gives `['A', 'a', 'b']`.

**Reversing only one part of a key.** `reverse=True` flips the whole ordering, including any part of the key you wanted to keep ascending. To make one part descending and another ascending, negate the number that should be descending, and leave the text part alone.

**Dictionary lookup for a rank.** A dictionary can map a name to a rank, and sorting by that rank puts the groups in the order you want.

```python
ORDER = {"low": 0, "medium": 1, "high": 2}
levels = ["high", "low", "medium"]
print(sorted(levels, key=lambda lv: ORDER[lv]))
```

The output is `['low', 'medium', 'high']`. The lookup `ORDER[lv]` fails with a `KeyError` if a name is missing from the dictionary, which is a useful signal that the data is wrong.

**The greedy loop with `continue`.** A greedy loop takes the best available option at each step and does not look back. The `continue` statement skips the rest of the current pass through a loop and moves to the next item. A loop that uses `continue` for a skipped item keeps checking the items after it.

```python
budget = 5
picked = []
for cost in [4, 2, 1]:
    if cost > budget:
        continue
    picked.append(cost)
    budget -= cost
print(picked, budget)
```

The output is `[4, 1] 0`. The cost 2 is skipped because it is more than the 1 that is left, and the loop still checks the cost 1 after it. A `break` in that place would have stopped the loop and given `[4]`.

**Returning a list.** A function returns a value with `return`, and a test can compare that value. Build the list in the loop with `.append`, and return it at the end. Do not `print` the result, because the tests check returned values.

### The rules people miss

The table below lists the rules from the statement that a careless solution is most likely to break. Each row says what the wrong version does, and how you can check your own version.

| Rule in the statement | What a careless solution does | How to check yours |
|---|---|---|
| Must if `must` is truthy | Tests `item["must"] is True`, so a truthy value such as 1 is not treated as a Must | Call `moscow_bucket` with `"must": 1` and an effort that gives a ratio of 0.5, and expect "Must" |
| The Must rule comes first | Calculates the ratio first and ignores `must` when the ratio is low | A Must with a ratio of 0.5 returns "Must" |
| Ratio 3 or more gives Should | Uses `>` instead of `>=` | An item with value 3 and effort 1 returns "Should" |
| Ratio 1.5 or more gives Could | Uses `>` instead of `>=` | An item with value 3 and effort 2 returns "Could" |
| The ratio is `value / effort` | Uses `//`, so 3 over 2 becomes 1 and falls into Wont | Value 3 and effort 2 returns "Could", not "Wont" |
| Below 1.5 gives Wont | Uses a threshold that is too low or too high | Value 1 and effort 2 returns "Wont" |
| The statement asks for no rounding | Rounds the ratio, so 8 over 3 becomes 3 and wrongly reaches Should | Compare the exact ratio with the thresholds, and do not round it anywhere |
| Bucket rank comes before ratio | Sorts by ratio alone, so a Should with a high ratio comes before a Must | A Must with ratio 0.5 comes before a Should with ratio 5 |
| Within a bucket, ratio is highest first | Sorts by value, or by ratio ascending | Two Should items with ratios 4 and 5 are listed with the 5 first |
| Ties are broken by id, A to Z | Uses the input order, or sorts ids descending | Two items with equal ratio and ids "B" and "A", listed B first, give A first |
| `prioritise` returns ids | Returns the items, or the whole dictionaries | Every element of the result is a text value |
| The loop does not stop at an item that does not fit | Breaks out of the loop at the first item that does not fit | Capacity 1, then an item of effort 3, then an item of effort 1 still selects the second item |
| `fit_capacity` returns ids in the order taken | Sorts the chosen ids alphabetically before returning them | The result matches the order in which you took the items |
| An item fits when its effort fits the capacity left | Is unsure what to do when an effort exactly equals what is left | The statement does not say whether equality fits, so it is unclear in the course itself. Most people read "still fits" as "effort <= remaining", but ask your trainer, then write one assert for your choice |
| Empty input is possible | Crashes on an empty list, for example when it calls `max` on nothing | `prioritise([])` returns an empty list, and `fit_capacity([], 8)` returns an empty list |
| Inputs are not changed | Calls `.sort()` on the caller's list, or edits the dictionaries | After each call, the input list is in its original order and every dictionary is unchanged |
| Types: `value` and `effort` are whole numbers, and the ratio is a decimal | Mixes integer division with the ratio, which is the same error as `//` above | Print the ratio for value 3 and effort 2 in your test, and check it is 1.5 |

### A method that works for every graded lab

1. Read the starter file first. Note the names of the functions, their parameters and the `RANK` dictionary, and do not rename anything.
2. Write the examples from the statement as `assert` lines before you write any logic. For example, `assert moscow_bucket({"id": "A", "value": 10, "effort": 2, "must": False}) == "Should"` describes what the function must do, before you know how.
3. Add your own `assert` lines for every row of the rules table above. Each row is a possible hidden test, so each row should have an assert that would fail for the careless version.
4. Implement one function at a time. After each one, run the asserts. Do not start the next function until the current one passes.
5. Check the types and the boundaries last. Confirm that a ratio on a boundary is compared with `>=`, that no rounding has crept in, and that the returned values are lists of text.
6. Run the visible tests. Read any failure message closely, because it usually names the input that went wrong.
7. Check that your code does not print anything and does not change its inputs.
8. Submit once, after the visible tests pass and your own asserts pass.

### Worked twin problem

This problem is about a food bank that loads a van. It uses the same skills as the lab: classifying items with thresholds, sorting by several keys, and a greedy loop that skips items that do not fit. The rules are different, so you must read them.

Each donation is a dictionary with `name` (text), `days_left` (a whole number), `kg` (a whole number) and an optional `urgent` flag, which is False if it is missing. Implement three functions.

- `band(donation) -> str` returns "Now" if `urgent` is truthy. Otherwise it returns "Soon" if `days_left` is 2 or less, "Later" if `days_left` is 7 or less, and "Hold" for anything else.
- `load_order(donations) -> list[str]` returns the names sorted by band, in the order Now, Soon, Later, Hold; then by weight, heaviest first; then by name, A to Z.
- `pack_van(donations, max_kg) -> list[str]` walks through the donations in load order, skips every "Hold", keeps each donation whose `kg` fits in the space left, and returns the names in the order they were kept. A negative `max_kg` raises `ValueError`.

A load that exactly fills the remaining space counts as fitting. Work through the example below before you read the solution.

```python
donations = [{"name": "Milk", "days_left": 1, "kg": 5}, {"name": "Rice", "days_left": 10, "kg": 20}]
print(band(donations[0]), band(donations[1]))
```

The output is `Soon Hold`. Milk has two days or fewer left, and Rice has more than seven.

The solution is in the block below. It is run by the build, so every assert must pass.

```python test
NOW, SOON, LATER, HOLD = "Now", "Soon", "Later", "Hold"
BAND_RANK = {NOW: 0, SOON: 1, LATER: 2, HOLD: 3}


def band(donation):
    if donation.get("urgent", False):
        return NOW
    if donation["days_left"] <= 2:
        return SOON
    if donation["days_left"] <= 7:
        return LATER
    return HOLD


def load_key(donation):
    return (BAND_RANK[band(donation)], -donation["kg"], donation["name"])


def load_order(donations):
    return [d["name"] for d in sorted(donations, key=load_key)]


def pack_van(donations, max_kg):
    if max_kg < 0:
        raise ValueError("max_kg cannot be negative")
    remaining = max_kg
    taken = []
    for d in sorted(donations, key=load_key):
        if band(d) == HOLD:
            continue
        if d["kg"] <= remaining:
            taken.append(d["name"])
            remaining -= d["kg"]
    return taken


donations = [
    {"name": "Rice", "days_left": 10, "kg": 20, "urgent": False},
    {"name": "Lentils", "days_left": 6, "kg": 8, "urgent": False},
    {"name": "Milk", "days_left": 1, "kg": 5, "urgent": False},
    {"name": "Bread", "days_left": 9, "kg": 3, "urgent": True},
    {"name": "Eggs", "days_left": 2, "kg": 6, "urgent": False},
    {"name": "Flour", "days_left": 4, "kg": 8, "urgent": False},
    {"name": "Oats", "days_left": 3, "kg": 4, "urgent": False},
]

assert band(donations[0]) == HOLD
assert band(donations[1]) == LATER
assert band(donations[3]) == NOW
assert band(donations[4]) == SOON
assert band({"name": "Z", "days_left": 7, "kg": 1}) == LATER
assert band({"name": "Z", "days_left": 8, "kg": 1}) == HOLD
assert band({"name": "Z", "days_left": 30, "kg": 1, "urgent": True}) == NOW

assert load_order(donations) == ["Bread", "Eggs", "Milk", "Flour", "Lentils", "Oats", "Rice"]
assert pack_van(donations, 20) == ["Bread", "Eggs", "Milk", "Oats"]
assert pack_van(donations, 10) == ["Bread", "Eggs"]
assert pack_van(donations, 1000) == ["Bread", "Eggs", "Milk", "Flour", "Lentils", "Oats"]
assert pack_van(donations, 0) == []
assert pack_van([], 5) == []
assert pack_van([{"name": "X", "days_left": 1, "kg": 3}], 3) == ["X"]

before = [d["name"] for d in donations]
pack_van(donations, 20)
assert [d["name"] for d in donations] == before
assert before == ["Rice", "Lentils", "Milk", "Bread", "Eggs", "Flour", "Oats"]

try:
    pack_van(donations, -1)
    raise SystemExit("expected ValueError")
except ValueError:
    pass
```

Line by line, the important parts are these.
