### The ticket in plain words

So far CityPulse runs only on your laptops, so nobody outside your team can use it. The client's ward dashboard team needs a public address they can call over HTTPS. HTTPS is the secure form of a web address, where traffic between their computer and yours is encrypted.

This ticket asks for three things. First, the API must run on a cloud platform with a public address. Second, pushing a version tag such as `v0.9.0-rc1` must deploy the image CI already built and tested, and a smoke test (a quick check that the live app answers correctly) must pass before the job turns green. Third, the squad must be able to return to the previous version within minutes.

The third point comes from a famous failure. In July 2024 a faulty update to security software from CrowdStrike crashed many Windows computers worldwide, and fixing each machine took hours. The lesson is that a bad release must be easy to undo.

Secrets matter too. The database address `DATABASE_URL` contains a password, so it lives in the platform's secret manager, never in the image, the workflow file or a plain setting. Costs must be bounded: the service may scale to zero (stop when idle) and must never run more than two servers at once.

### How your trainer checks it

The trainer checks six acceptance criteria and runs five test cases.

**Criterion 1: the live URL.** The README 'Live' URL answers `curl -i https://<url>/v1/health` with HTTP 200, and `git_sha` equals the deployed commit. TC1 and TC2 prove this.

**Criterion 2: deploy on tag.** A `v*` tag on a `main` commit deploys that SHA without rebuilding, and the smoke step passes. A failing smoke test must fail the job. TC3 and TC4 prove this.

**Criterion 3: secrets.** `DATABASE_URL` comes from the secret manager and appears in neither `deploy.yml`, the image, nor a plain environment listing. The checks are in T45.3 and T45.5.

**Criterion 4: runbook.** `docs/cloud-runbook.md` records at least one completed rollback, with exact commands, start and end timestamps, duration, and the command that lists previous revisions. TC5 proves this.

**Criterion 5: limits.** Maximum instances are 2 or fewer, and a budget alert or spending limit exists.

**Criterion 6: contribution.** Your handle appears on a rollback drill entry as driver or navigator.

**TC1: the health code.** The command is `curl -s -o /dev/null -w '%{http_code}' https://<url>/v1/health`.

- `curl` sends the request.
- `-s` runs silently, hiding the progress meter.
- `-o /dev/null` discards the body, because only the code matters.
- `-w '%{http_code}'` prints the status code after the request.

Passing output is `200`. `000` means curl could not connect, usually a wrong URL or no deployment. `403` means the service is not public. `500` or `503` means the app failed to start, often because it cannot read its secret. The Cloud Run logs in the console show why.

```term
$ curl -s -o /dev/null -w '%{http_code}' https://<url>/v1/health
200
```

**TC2: the commit match.** The command is `curl -s https://<url>/v1/health | jq -r .git_sha`, compared with `git rev-parse <latest v* tag>^{commit}`.

- `|` is a pipe. It sends the JSON reply into `jq`.
- `jq -r .git_sha` prints the `git_sha` field without quotes.
- `git tag --sort=-v:refname | head -n 1` finds the latest `v*` tag. The sort puts the highest version first. Once a final tag such as `v0.9.0` exists next to `v0.9.0-rc1`, git ranks the `-rc1` tag higher by default, so check the result by eye.
- `^{commit}` resolves the tag to the commit it points at.

Passing output is the same 40-character SHA printed twice. A different SHA means an older revision still serves traffic. An empty line means the build argument did not reach the runtime stage of the Dockerfile.

**TC3: the workflow run.** The command is `gh run list --workflow deploy.yml --limit 1 --json conclusion,event,headBranch`. `--workflow` picks the deploy workflow, `--limit 1` keeps the newest run, and `--json` prints the three named fields. Passing output looks like `[{"conclusion":"success","event":"push","headBranch":"v0.9.0-rc1"}]`. An empty list means the tag did not match `v*`, for example `0.9.0` without the `v`.

**TC4: the smoke script.** The command is `BASE_URL=https://<url> bash scripts/smoke.sh https://<url> <sha>`. The first argument becomes `$1` in the script and the SHA becomes `$2`. Passing output ends with `smoke OK`, and `echo $?` straight after prints `0`. Failing output ends with a `FAIL:` line and exit code `1`.

**TC5: the rollback.** The trainer runs the `Rollback` commands in your runbook word for word. Passing means the previous revision serves within the recorded time and the smoke test passes. Failing usually means a placeholder was not replaced or a name was copied wrongly.

### Do it, step by step

**How the pieces fit.** Cloud Run runs an image as a revision, and older revisions stay stored. The workflow builds nothing. It tells Cloud Run which image to run.

```flow
TITLE: One tag push, from laptop to live service
NODES: Your laptop | GitHub Actions | Cloud Run
STEPS:
1>2 :: git push origin v0.9.0-rc1 :: The tag travels to GitHub, which matches v* and starts deploy.yml.
2>3 :: deploy image by SHA :: The job asks for a new revision that runs the image stored under the commit SHA.
3>2 :: revision live :: Cloud Run reports the new revision as serving traffic.
2>3 :: run smoke.sh :: The job calls the public URL and checks git_sha and a prediction.
3>2 :: smoke result :: Exit zero keeps the job green. Any failure turns it red.
```

#### Y2-T45.1: Make the image pullable and create the service identity

**Stage 1. Check the SHA-tagged image exists.**

```bash
docker manifest inspect ghcr.io/ORG/citypulse-squadnn:$(git rev-parse origin/main)
```

`docker manifest inspect` reads the image description from the registry without downloading the image. `git rev-parse origin/main` prints the full SHA of GitHub's newest `main` commit, and `$( )` places it in the tag. Replace `ORG` and the image name with your squad's values. Expected output is JSON with a `mediaType` line. An "unknown manifest" error means CI did not push that tag.

**Stage 2. Copy the image to a registry Cloud Run can read.** Cloud Run reads Google's Artifact Registry, not GHCR, so create a repository and copy the image:

```bash
gcloud artifacts repositories create citypulse --repository-format=docker --location=asia-south1
gcloud auth configure-docker asia-south1-docker.pkg.dev
docker pull ghcr.io/ORG/citypulse-squadnn:<sha>
docker tag ghcr.io/ORG/citypulse-squadnn:<sha> asia-south1-docker.pkg.dev/<project>/citypulse/citypulse-api:<sha>
docker push asia-south1-docker.pkg.dev/<project>/citypulse/citypulse-api:<sha>
```

`repositories create` makes a Docker repository in the `asia-south1` region. `configure-docker` lets Docker log in through your Google account. `pull` downloads from GHCR, `tag` gives the image the registry address, and `push` uploads it. The last command ends with a confirmation line.

**Stage 3. Create the service identity.**

```bash
gcloud iam service-accounts create citypulse-api-sa --display-name="CityPulse API"
```

It prints `Created service account [citypulse-api-sa].` Grant roles only when a step needs them, so a misused identity does limited damage.

**Two things to plan.** First, the copy in Stage 2 must exist for every SHA that a tag can point at, not just one. Either extend your CI push step so it also pushes to Artifact Registry, or add a copy step (pull, tag, push, no rebuild) at the start of `deploy.yml`. Second, the identity that `deploy.yml` logs in as (the `DEPLOY_SA` variable in T45.5) is a different account from `citypulse-api-sa`. It needs permission to deploy Cloud Run services (for example `roles/run.admin`) and to act as `citypulse-api-sa` (`roles/iam.serviceAccountUser` on that account). Agree both with your Tech Lead.

**How to test.** `gcloud artifacts docker images list asia-south1-docker.pkg.dev/<project>/citypulse` lists your SHA tag. `gcloud iam service-accounts describe citypulse-api-sa@<project>.iam.gserviceaccount.com --format="value(email)"` prints the email when the identity exists.

#### Y2-T45.2: Store DATABASE_URL in the secret manager

**Stage 1. Create the secret.**

```bash
gcloud secrets create database-url --replication-policy=automatic
```

It prints `Created secret [database-url].`

**Stage 2. Add the value without typing it into history.** Your `DATABASE_URL` is already in an environment variable:

```bash
printf '%s' "$DATABASE_URL" | gcloud secrets versions add database-url --data-file=-
```

`printf '%s'` prints the text exactly, with no added newline. `--data-file=-` tells `gcloud` to read standard input. The value never appears in the command you type. Expected output reports `Created version [1]`.

**Stage 3. Grant read access on this secret only.**

```bash
gcloud secrets add-iam-policy-binding database-url --member="serviceAccount:citypulse-api-sa@<project>.iam.gserviceaccount.com" --role="roles/secretmanager.secretAccessor"
```

Binding the role to the secret, not the project, means the identity can read this secret and no others.

**How to test.** `gcloud secrets get-iam-policy database-url` lists your service account under `secretAccessor`. Do not run `gcloud secrets versions access` in a shared terminal, because it prints the password.

:::trap Printing the secret to test it
Reading a secret to check it prints the password into your terminal and your history. Check the access policy instead.
:::

#### Y2-T45.3: Manual deploy and checks

**Stage 1. Deploy with explicit flags.** Your Tech Lead agrees the values with the squad.

```bash
gcloud run deploy citypulse-api --image asia-south1-docker.pkg.dev/<project>/citypulse/citypulse-api:<sha> --region asia-south1 --port 8000 --service-account citypulse-api-sa@<project>.iam.gserviceaccount.com --allow-unauthenticated --min-instances 0 --max-instances 2 --set-secrets DATABASE_URL=database-url:latest
```

`--port 8000` names the container door that receives requests. `--service-account` sets the identity from T45.1. `--allow-unauthenticated` makes the service public. `--min-instances 0` allows scale to zero, and `--max-instances 2` caps it. `--set-secrets DATABASE_URL=database-url:latest` makes the variable read the latest secret version.

**Stage 2. Check the answers over HTTPS.** `curl -s https://<url>/v1/health` prints JSON containing `git_sha`. For the prediction, send a POST with `curl -s -X POST https://<url>/v1/predict -H "Content-Type: application/json" -d '<body from your API spec>'`. `-X POST` sets the method, `-H` declares a JSON body, and `-d` carries it.

**Stage 3. Confirm the secret is not plain text.**

```bash
gcloud run services describe citypulse-api --region asia-south1 --format="yaml(spec.template.spec.containers[0].env)"
```

For `DATABASE_URL` you should see a secret reference naming `database-url`, and no `value:` line holding the address. If the address is visible, redeploy with `--set-secrets` and remove the plain setting.

**Stage 4.** Add the HTTPS address under 'Live' in the README. Get it with `gcloud run services describe citypulse-api --region asia-south1 --format="value(status.url)"`.

#### Y2-T45.4: Write scripts/smoke.sh

**Technique first: exit codes.** A script ends with `exit 1` to report failure, and the calling workflow then fails. Put these lines at the top:

```bash
#!/usr/bin/env bash
set -euo pipefail
```

`set -e` stops at the first failing command. `set -u` treats an unset variable as an error. `set -o pipefail` makes a pipeline fail if any part fails, so `curl | jq` cannot hide a curl error.

**Stage 1. Read the arguments.**

```bash
BASE_URL="${1:?usage: smoke.sh BASE_URL EXPECTED_SHA}"
EXPECTED_SHA="${2:?usage: smoke.sh BASE_URL EXPECTED_SHA}"
```

`${1:?message}` stops with the message if an argument is missing, so a forgotten argument cannot pass silently.

**Stage 2. Check health with retries.**

```bash
check_health() {
  local body
  body=$(curl -sf --max-time 10 "$BASE_URL/v1/health") || return 1
  echo "$body" | jq -e --arg sha "$EXPECTED_SHA" '.git_sha == $sha' > /dev/null
}

for attempt in 1 2 3 4 5; do
  if check_health; then
    echo "health ok on attempt $attempt"
    break
  fi
  echo "health not ready (attempt $attempt of 5)"
  if [ "$attempt" -eq 5 ]; then
    echo "FAIL: health never returned the expected git_sha" >&2
    exit 1
  fi
  sleep 5
done
```

`curl -sf` fails on 4xx and 5xx replies. `jq -e` sets its exit code from the comparison, so a wrong SHA counts as failure. `--arg` passes the SHA into jq safely. The loop waits five seconds between attempts, because a new service can take a moment to start. The message goes to standard error (`>&2`).

**Stage 3. Check one numeric prediction.**

```bash
PREDICT_BODY='<request body from your API spec>'
predict=$(curl -sf --max-time 10 -H "Content-Type: application/json" -d "$PREDICT_BODY" "$BASE_URL/v1/predict") || { echo "FAIL: predict request failed" >&2; exit 1; }
echo "$predict" | jq -e '.prediction | type == "number"' > /dev/null || { echo "FAIL: no numeric prediction" >&2; exit 1; }
echo "smoke OK"
```

`.prediction` is an example field name. Use the one your API returns. Each `||` runs its block only when the command before failed.

**How to test.** Run the script with a SHA that cannot match. You should see five `health not ready` lines, then `FAIL: health never returned the expected git_sha` and `exit 1`. Then run it with the real SHA and expect `smoke OK` and exit 0.

:::tip Test the failure first
A smoke script that always exits 0 is the most dangerous bug in this ticket, because it lets broken releases go green.
:::

#### Y2-T45.5: Write deploy.yml

**Goal.** A workflow that starts only on `v*` tags, deploys that commit's image, runs the smoke script, and never builds.

**Stage 1. Trigger on version tags.** Start the file with:

```yaml
name: deploy
on:
  push:
    tags: ["v*"]
```

The `*` matches any ending, so `v0.9.0-rc1` matches and `0.9.0` does not.

**Stage 2. Set permissions and log in without a key.** Add a job:

```yaml
permissions: {contents: read, id-token: write}
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: google-github-actions/auth@v2
        with: {workload_identity_provider: "${{ vars.WIF_PROVIDER }}", service_account: "${{ vars.DEPLOY_SA }}"}
```

`id-token: write` lets the job request a short-lived token from GitHub, which the `auth` action exchanges for Google credentials. Your Tech Lead sets up the trust in advance, so no key file exists.

**Stage 3. Deploy the SHA, not a rebuild.**

```yaml
      - uses: google-github-actions/setup-gcloud@v2
      - run: gcloud run deploy citypulse-api --image "${{ vars.IMAGE }}:${{ github.sha }}" --region asia-south1 --quiet
```

`github.sha` is the commit the tag points at, so the deployed image is the one CI tested. `--quiet` stops the command waiting for an answer, which would hang the runner.

**Stage 4. Smoke test as the last step.**

```yaml
      - run: ./scripts/smoke.sh "${{ vars.BASE_URL }}" "${{ github.sha }}"
```

A step whose command exits non-zero fails, and a failed step fails the job. Make the script executable in Git with `git update-index --chmod=+x scripts/smoke.sh`.

**Stage 5. Check the rules with grep.**

```bash
grep -n "docker build" .github/workflows/deploy.yml
grep -n "DATABASE_URL" .github/workflows/deploy.yml
```

`grep -n` prints matching lines with their numbers. Both must print nothing. A `docker build` line means the workflow rebuilds code CI never tested.

**Stage 6. Push a release candidate tag.**

```bash
git fetch origin main
git tag v0.9.0-rc1 origin/main
git push origin v0.9.0-rc1
gh run watch
```

The tag must sit on a `main` commit, or the image will not exist. A normal `git push` does not send tags, so the last push is needed. `gh run watch` follows the run live and should end with green ticks.

**How to test.** `gh run list --workflow deploy.yml --limit 1` shows the run as green. The failing path is proved by the wrong-SHA run of `smoke.sh` in T45.4: the script exits 1, so the step and the job fail.

:::trap Tag created but not pushed
A tag that exists only on your laptop starts nothing. Run `git push origin <tag>` and check `gh run list`.
:::

#### Y2-T45.6: The rollback drill

**Stage 1. Record the start time in UTC.**

```bash
date -u +%Y-%m-%dT%H:%M:%SZ
```

`date -u` prints UTC, the same clock for everyone. Copy the output into the runbook.

**Stage 2. List the revisions.**

```bash
gcloud run revisions list --service citypulse-api --region asia-south1
```

The table lists revisions newest first. To see which one serves traffic, run `gcloud run services describe citypulse-api --region asia-south1 --format="yaml(status.traffic)"`, which shows the revision name and its percentage. Write the serving revision's name down. That is the revision you will roll back to.

**Stage 3. Deploy a visible change.** Change the health message in a pull request, merge after review, wait for CI, then tag as in T45.5 with `v0.9.1-rc1`. Afterwards the health endpoint shows the new message and SHA.

**Stage 4. Roll back.**

```bash
gcloud run services update-traffic citypulse-api --region asia-south1 --to-revisions=<previous-revision-name>=100
```

`--to-revisions=NAME=100` sends 100% of traffic to the named revision. Copy the name from stage 2.

**Stage 5. Verify.** `curl -s https://<url>/v1/health | jq -r .git_sha` should print the previous SHA, and `bash scripts/smoke.sh https://<url> <previous-sha>` should print `smoke OK` and exit 0.

**Stage 6. Record the end time and duration.** Run `date -u +%Y-%m-%dT%H:%M:%SZ` again as soon as the smoke test passes and note it as the end time. Then work out the duration:

```bash
echo $(( $(date -u -d "2026-11-17T10:21:30Z" +%s) - $(date -u -d "2026-11-17T10:15:00Z" +%s) ))
```

`date -d` reads a time, and `+%s` prints it as seconds since 1970. Subtracting the start from the end gives the duration in seconds. Replace the example times with yours. The example prints `390`.

**How to test.** The runbook entry has start, end, duration, both revision names and your handle, and the health check shows the previous SHA.

### Defend it in the viva

**1. Why does deploy.yml deploy the SHA instead of building again?**

:::answer Model answer
The image CI built is the only artifact that passed the gate. A rebuild creates an image no test saw, so the deployed code might differ from the tested code. Deploying the SHA also lets the health check compare the running `git_sha` with the tagged commit, which proves the match.
:::

**2. What is the trade-off of scale to zero with a maximum of two instances?**

:::answer Model answer
Scale to zero saves money while idle, but the first request after a quiet period waits for a cold start. A maximum of two caps spending, but it also caps how many requests run at once, so a spike can queue or fail. The budget alert is the safety net for cost.
:::

**3. What did you personally do in this ticket, and how do you show it?**

:::answer Model answer
Name the subtask you owned, the commits you made in that area, the test that proved the piece worked, and one change you made after review. Your commits and review comments must support every claim.
:::

**4. Why must DATABASE_URL never appear in deploy.yml or a plain environment listing?**

:::answer Model answer
The address holds a password, and Git keeps committed values in history even after the line is deleted. A plain environment listing can be read by anyone with access to the service. The secret manager stores the value once and lets only the named identity read it, and the workflow refers to it by name only.
:::

**5. How do you know a rollback worked, and what does it not fix?**

:::answer Model answer
I check three things: the traffic split names the previous revision at 100%, the health endpoint returns the previous SHA, and the smoke script exits 0 against that SHA. A rollback moves traffic only, so it does not undo database changes the newer version made. A schema change must work for both versions before a release that might be rolled back.
:::
