### The ticket in plain words

CityPulse is a platform that shows Bengaluru city data, and each squad builds one product on top of it. The squad needs one place that says what it builds and how success is judged. That place is a GitHub repository named `citypulse-<squad>`.

The repository holds a README, which states the problem, the user, the data source and one success metric. It also holds a charter, a short agreement that all five members sign, with rules that prevent a repeat of the GitLab accident of 2017. In that case a production database was deleted by mistake while an engineer was fixing a database replication problem, and the backups had not been working. A good charter names rules that would have caught a failure like that early.

The ticket also builds the backlog: at least ten labelled issues on a project board, each with acceptance criteria (the checks that show an issue is finished). Every student also proves basic Linux skill on the shared server, because every pipeline from T05 runs in a terminal.

### How your trainer checks it

Criterion 1 is TC1, criterion 2 is TC4, criterion 3 is TC2, criterion 4 is TC3 plus a look at the board, and criterion 6 is TC5. Criterion 5, the hunt score, is read from the trainer's sheet.

#### TC1: the files and folders exist

```bash
gh repo clone citypulse-y2/citypulse-<squad> && cd citypulse-<squad> && ls -a && ls src data docs tests
```

- `gh repo clone OWNER/REPO` copies the repository into a folder with its name.
- `&&` runs the next command only if the last one succeeded.
- `ls -a` lists every name, including hidden ones such as `.gitignore`.
- `ls src data docs tests` prints a heading per folder. The folders hold only `.gitkeep`, which is hidden, so the lines under each heading are empty. That is correct.

Passing output shows `.git`, `.gitignore`, `CHARTER.md`, `LICENSE`, `README.md`, `data`, `docs`, `src` and `tests`, then four headings with no error. `cannot access 'tests'` means the folder is missing on main.

#### TC2: five distinct authors signed the charter

```bash
git log --format='%an <%ae>' -- CHARTER.md | sort -u | wc -l
```

- `--format='%an <%ae>'` prints each commit's author name and email.
- `-- CHARTER.md` keeps only commits that changed that file. The `--` separates options from the file name.
- `sort -u` keeps one copy of each line, and `wc -l` counts the lines.

On a finished squad the result looks like this:

```term
$ git log --format='%an <%ae>' -- CHARTER.md | sort -u | wc -l
5
```

Passing output is `5`. A `1` means everyone committed from one identity. A `4` means one signature is missing or committed from another identity. A count of 6 or more means one student has two identities, such as a work and a personal email.

#### TC3: at least ten labelled issues

```bash
gh issue list --repo citypulse-y2/citypulse-<squad> --state all --limit 50 --json number,labels | jq 'length, [.[] | select(.labels|length==0)] | length'
```

- `--state all` includes closed issues. `--json number,labels` prints each issue's number and labels as JSON.
- In the `jq` program, `length` counts the issues. The comma prints a second answer.
- `[.[] | select(.labels|length==0)]` keeps issues with no labels, and the final `length` counts them.

Passing output is two lines: a total of at least 10, then 0. No output at all, with an error message from `gh`, usually means a wrong repository name or no access. (The `jq` program works because `|` has the lowest priority: both answers before it are passed through the final `length`.) A second number above 0 means an issue has no label; fix it with `gh issue edit <number> --add-label docs`. The test checks only that labels exist, so read the names yourself: each must be one of the four agreed labels.

#### TC4: the metric line has a number, a unit and a date

```bash
grep -iE 'metric' -A2 CHARTER.md
```

- `grep` prints lines that match a pattern. `-i` ignores case, and `-E` selects the extended pattern language.
- `-A2` prints two lines after each match, so the value appears with its heading.

Passing output shows a line with a number, a unit and a date in `YYYY-MM-DD` form, such as `≥95% of hourly PM2.5 readings captured per week by 2026-12-12`. No output means the word `metric` is missing, or you are in the wrong folder (check with `pwd`).

#### TC5: each student's Linux record has the student as author

```bash
git log --format='%an' -- docs/linux/<name>.txt | sort -u
```

Passing output is the student's own name only. Empty output means the file was not pushed, or has a different name. A teammate's name means the file was committed from a shared laptop.

### Do it, step by step

Use your squad's name in place of `<squad>`. Test each stage before moving on.

#### Y2-T03.1 Create the first commit (Tech Lead)

Goal: main holds the four folders, `.gitignore` and `LICENSE`.

Stage 1, clone and check identity, in Git Bash on your laptop:

```bash
gh repo clone citypulse-y2/citypulse-<squad>
cd citypulse-<squad>
git config user.name
git config user.email
```

`gh repo clone` copies the repository and `cd` enters it. The two `git config` lines print your name and email. The email must match your GitHub account, because the course counts authors from these values.

Stage 2, make folders. Git ignores empty folders, so each gets a `.gitkeep` file:

```bash
mkdir -p src data docs tests
touch src/.gitkeep data/.gitkeep docs/.gitkeep tests/.gitkeep
ls -a src
```

`mkdir -p` creates folders and ignores ones that exist. `touch` creates an empty file. `ls -a src` should show `.gitkeep`.

Stage 3, write `.gitignore` in VS Code. Use `data/*` with `!data/.gitkeep`, then add rules for `.env` and `__pycache__/`. Never write `data/` alone, because that hides `data/.gitkeep`.

Stage 4, add `LICENSE` with the licence your trainer approves. The ticket does not say which licence that is, so ask your trainer before you choose one.

Stage 5, commit and push:

```bash
git add .
git status --short
git commit -m "Add folder layout, .gitignore and LICENSE"
git push origin main
git log --format='%h %an %s' -1
```

`git add .` stages every file that is not ignored. The last command prints the hash, your name and the message. Cloning an empty repository prints a warning that you cloned an empty repository; that is normal. If `git branch --show-current` does not print `main`, run `git branch -M main` before pushing. If the push is refused because main is protected, open a pull request instead.

:::trap git commit -am and new files
`-a` stages only files Git already tracks, so new files need `git add`. See [Day 1 — Git, GitHub and secure accounts](D01.html).
:::

#### Y2-T03.2 Co-write CHARTER.md (Squad)

Goal: the charter has a metric with a number, a unit and a date, and at least three process controls drawn from the 2017 case.

Stage 1, read the case and write three failures it shows. As a starting point, the public account says an engineer deleted the data folder on the wrong server late at night, and the team then found that several backup methods had been failing without anyone noticing, so failure alerts did not reach them. Read the account yourselves and find more. For each, ask which simple rule, checked by a second person, would have caught it. A process control is a rule someone can check. "Be careful with deletes" is not one. "A second member confirms the exact path before any delete on shared data" is.

Stage 2, write the metric as one sentence. The check needs three parts: a target number, a unit and a date. Name the measured thing (and a time window if it repeats) so the number means something. A fictional example about a library shows the shape:

`At least 90% of returned library books checked in within 1 day, by 2027-03-31.`

:::trap A line starting with a greater-than sign
In Markdown, a line that starts with `>` becomes a quotation. Write ≥ or "At least" instead.
:::

Stage 3, lay out the file with headings and checklist boxes. This is the shape only:

```text
# CityPulse <squad> Charter
## Success metric
<your metric sentence>
## Process controls
- [ ] <control one, in your own words>
- [ ] <control two>
- [ ] <control three>
## Signatures
```

Stage 4, preview with Ctrl+Shift+V in VS Code, then open a pull request. Each member adds their own control in their own commit.

Test: TC4 prints the metric line with all three parts.

#### Y2-T03.3 Add your signature (every student)

Goal: your signature sits in a commit with your name as author.

Stage 1, get the latest main and branch:

```bash
git switch main
git pull
git switch -c feat/y2-t03-<your-name>
```

`git switch -c` creates a branch and moves onto it.

Stage 2, add your line under Signatures, in the form `Signed: <full name> (@<login>), <date>`, with the date as `YYYY-MM-DD`. Then commit and push:

```bash
git add CHARTER.md
git commit -m "Add my signature to CHARTER.md"
git push -u origin feat/y2-t03-<your-name>
```

`gh pr create --fill` opens the pull request and uses the commit message as its title. A squad-mate approves it. You never merge your own pull request.

Here is how your commit reaches the trainer's check:

```flow
TITLE: From your commit to the trainer's count
NODES: Your laptop | GitHub | Trainer's check
STEPS:
1>2 :: git push :: Your signature commit travels to GitHub under your own identity.
2>3 :: merged to main :: After approval, the commit reaches main.
```

#### Y2-T03.5 Create 10 labelled issues (Data and Backend)

Goal: ten issues, each with exactly one label from feature, data, bug or docs, and each with an acceptance-criteria section.

Stage 1, check labels, and create any that are missing:

```bash
gh label list --repo citypulse-y2/citypulse-<squad>
gh label create data --repo citypulse-y2/citypulse-<squad> --color 0E8A16 --description "Data work"
```

A new repository usually has `bug` and `documentation` but not `docs`, `feature` or `data`, so create each of the four names you use. `gh label create` takes a name, a six-digit hex colour and a description. Without the label, `gh issue create` fails with a "label not found" message.

Stage 2, write each body in a file, with a `## Acceptance criteria` heading and `- [ ]` items. A fictional example for another project shows the layout:

```text
## Acceptance criteria
- [ ] The import script runs on a sample file
```

Stage 3, create one issue, then repeat for the others:

```bash
gh issue create --repo citypulse-y2/citypulse-<squad> --title "Check the source URL returns JSON" --label data --body-file issue1.txt
```

`--title` names the issue, `--label` attaches one label, and `--body-file` reads the body from a file. `gh` prints the new issue's URL.

#### Y2-T03.7 Complete the Linux hunt (every student)

Goal: your answers are in `~/hunt/answers.txt` on the lab machine. The hunt is individual, so do not copy a teammate's file. You need at least 16 of the 20 correct. The Linux skills behind it are in [Day 2 — Linux and the command line](D02.html).

Learn redirection on a practice file first:

```bash
echo "first line" > ~/practice.txt
echo "second line" >> ~/practice.txt
cat ~/practice.txt
```

`>` writes and replaces. `>>` appends. `cat` prints the file. Expected output: two lines.

Create your answers file with `mkdir -p ~/hunt`, and add each answer with `>>` so none is lost.

Commands you type are saved in your history. Never type a password or token into a command. If one slips in, follow the secret response in [Day 1](D01.html): revoke the secret first, then tell your trainer.

#### Y2-T03.8 Save your history and push it (every student)

Goal: `docs/linux/<name>.txt` holds your history, committed under your identity.

Stage 1, save the history. `history` prints numbered commands, so redirect it to a file in `/tmp`, a shared temporary folder:

```bash
history > /tmp/<name>.txt
wc -l /tmp/<name>.txt
```

`wc -l` counts lines. A count of 0 means this shell has no history, so run the commands in the same session. Files in `/tmp` can be removed on restart, so copy promptly.

Stage 2, bring the file from the lab machine into your clone on your laptop, using the method your trainer set up, such as `scp` (run on the laptop, inside your clone):

```bash
mkdir -p docs/linux
scp <lab-user>@<lab-host>:/tmp/<name>.txt docs/linux/<name>.txt
git status --short
```

`<lab-user>` and `<lab-host>` are the login details your trainer gave you. `git status --short` should show `?? docs/linux/` as untracked.

Search it for `token`, `key` and `password`, and remove any secret before you commit.

Stage 3, commit on your own branch and open a pull request:

```bash
git switch -c feat/y2-t03-<your-name>-history
git add docs/linux/<name>.txt
git commit -m "Add Linux history record for <your-name>"
git push -u origin feat/y2-t03-<your-name>-history
gh pr create --fill
```

Test: `git log --format='%an' -- docs/linux/<name>.txt | sort -u` prints your name.

### Defend it in the viva

Why does the metric need a number, a unit and a target date?

:::answer Model answer
The number sets the size of the goal, the unit says what is measured, and the date makes the goal testable. Without a date, a metric can never be marked as missed, which is why TC4 checks all three.
:::

Why sign the charter with Git commits instead of a Word file with a signature image?

:::answer Model answer
This is a trade-off. Word gives richer formatting, but its file cannot be compared line by line in a pull request. A commit records who signed and when, and TC2 counts those authors. The cost is plainer formatting.
:::

What did you personally contribute, and how can the trainer check it?

:::answer Model answer
Name the control you wrote, the pull request that reviewed it and the commit hash. Then point to the evidence: TC2 and `git log` on the file show your name against that commit. Use your own words, and claim only work you did.
:::

Why does the ticket require process controls, and what does each one cost?

:::answer Model answer
The 2017 case shows that one mistake can destroy data when no second person checks the action and the backups are untested. A control is a checkable rule. Each one adds a small step, so choose the failures the team could realistically have.
:::

Why might TC2 give a wrong answer, and how would you spot it?

:::answer Model answer
The command counts each name and email pair, so one person with two emails is counted twice. Run it without `sort -u` and `wc -l` to read the full list, and ask your trainer before changing old history.
:::

### Check yourself

```quiz
Q: Which command prints the number of distinct people who committed to CHARTER.md?
- ls -a CHARTER.md
* git log --format='%an <%ae>' -- CHARTER.md | sort -u | wc -l
- git status --short
- grep -c CHARTER.md
WHY: git log lists the authors of commits that touched the file, sort -u keeps one copy of each, and wc -l counts them. The other options do not list authors.

Q: The trainer's check needs a number, a unit and a date. Your metric line reads: Reach 90 by 2027-03-31. Which required part is missing?
- A target date
- A number
- A time window
* A unit
WHY: The rule needs a number, a unit and a date. 90 is a number and 2027-03-31 is a date, but nothing says what 90 is counted in, such as a percentage. The time window is tempting, but it is not one of the three required parts.

Q: Why does the trainer check that each issue has a label from a fixed set?
* So the backlog can be sorted into the four agreed types
- So GitHub emails the squad when an issue opens
- So the commit author becomes the issue owner
- So the issue closes when its branch is merged
WHY: Labels from one agreed set sort the backlog. The other options are not what labels do.
```
