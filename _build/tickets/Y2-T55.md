### The ticket in plain words

Ticket Y2-T55 asks you to find your weakest skill, measure it, practise it with feedback, measure again, and log both numbers with links anyone can open. The idea behind it comes from the research the ticket cites by Ericsson: you improve fastest by working on your weaknesses with feedback, not by doing more of what you already do well.

CityPulse needs this for CRI checkpoint 2 on Demo Day 2 (24 Apr), which targets 68 or more. The trainer needs a fair "before" and "after" number for every student, taken the same way under the same time limit.

You produce a gap-log entry in the LMS with seven fields, a mistake log (a notes file of each error and the rule that fixes it), and a booked check-in with your accountability partner. Your trainer will click your links and ask what changed.

### Before you start

These tickets must already be merged in your squad repository: Y2-T52, Y2-T53 and Y2-T54. T54's scores help you pick your weakness.

You need Git Bash (a Linux-style command line that comes with Git for Windows; every command here runs in it unless stated), Python 3, a GitHub account with access to `dsa-<name>` and `citypulse-<squad>`, and your LMS login.

### How your trainer checks it

The ticket has four acceptance criteria (what must be true) and three test cases (what the trainer does to check it).

**Acceptance criterion 1: the gap log has all the fields.** The log must hold the dimension, your CRI 1 score, a specific goal, the before measure, the after measure and the evidence links.

**Acceptance criterion 2: comparable measures.** The before and after measures must use twin sets A and B, or the same scoring card, under the same time limit.

**Acceptance criterion 3: evidence links open.** Each link opens a platform attempt, a recording or a pull request.

**Acceptance criterion 4: check-in booked.** A check-in date before Saturday 17 April is recorded.

**Test case TC1.** The trainer opens the LMS gap-log export, filtered by squad. The expected result is five entries with every field filled in by 20:30. You can rehearse this with your own checker script. The command below runs in Git Bash, in the folder that holds `check_gap_log.py` and your exported `gap_log.csv`:

```term
$ python check_gap_log.py gap_log.csv
5 rows read
OK
```

`python` starts Python. `check_gap_log.py` is the script you write in Y2-T55.5. `gap_log.csv` is the export it reads. The first line is the row count, and `OK` appears only when no field is empty.

If the output looks like this instead, the check has failed:

```term
$ python check_gap_log.py gap_log.csv
5 rows read
row 3 empty after_measure
```

The usual cause is a blank LMS field, or an export that includes another squad's rows.

**Test case TC2.** The trainer clicks the before and after links for three random students. Both must open, the set IDs must differ (A against B), and the difficulty tags must match. Open your own links in a fresh private window. A link to the course list, or a login page, fails.

**Test case TC3.** The trainer asks: "What changed between before and after, and what is next?" A passing answer names a measured change and the next item from your mistake log. "I practised more" fails, because it has no numbers.

### Do it, step by step

#### Y2-T55.1 State your weakest dimension and CRI 1 score

Goal: one dimension, one CRI 1 score, and one written goal in the LMS gap log.

Stage 1. Find your numbers in your CRI 1 report and T54 scores. Pick the lowest dimension. If two tie, pick the one your mentor flagged. You are choosing a weakness to practise, not a score to defend.

Stage 2. Write the goal. A good goal has a number, a pattern and a time limit, such as the ticket's "4/5 sliding-window, each under 20 min". Write it in the LMS goal field.

Stage 3. Create your notes folder. Run these commands in Git Bash:

```
$ cd ~/dsa-yourname
$ mkdir -p notes
$ ls notes
```

`cd` moves into your personal repository. In Git Bash, `~` means your Windows home folder, so replace `yourname` with your repository folder name. `mkdir -p notes` creates a folder called `notes`. The `-p` flag means "create it if needed, and do not fail if it already exists". `ls notes` lists the folder. It prints nothing, which is correct for an empty folder.

Stage 4. Create the mistake log file. Name it after your pattern, using the ticket's pattern name if it is yours:

```
$ touch notes/sliding-window.md
$ ls notes
sliding-window.md
```

`touch` creates an empty file. If the file exists, `touch` only updates its timestamp, so it is safe to run twice.

Test this stage: read your goal aloud in under ten seconds. It must have a number, a pattern and a time limit.

#### Y2-T55.2 Take the before measure

Goal: one scored, timed attempt, with its score and time written in the log, before you practise anything.

First, the timing technique, with a small example. Type these lines in Git Bash:

```
$ start=$(date +%s)
$ sleep 3
$ end=$(date +%s)
$ echo "$((end - start)) seconds"
3 seconds
```

`start=$(date +%s)` stores the current time in seconds. `sleep 3` stands in for your work. The second `date` call stores the end time, and `$((end - start))` does the subtraction. Use the LMS timer if your set has one.

Now the measure itself. Pick one option and use the same one after practice:

- Timed set A on the LMS, scored by the platform.
- Three answers you record, scored with a scoring card.
- An old pull request or README, scored against a checklist.

A scoring card is a fixed list of one-point checks, applied the same way each time. Write down the score and the maximum, for example `3/5`.

Stage. Start the timer, do set A, stop the timer. Record the score, the maximum, the time limit you used and the seconds taken in the gap-log before field. Keep the attempt link from the LMS for the evidence.

Test this stage: the entry has a score, a maximum, a time limit, the seconds taken and an attempt link.

#### Y2-T55.3 Practise 30 minutes with feedback

Goal: 30 minutes of practice where every wrong answer is checked, written in the mistake log and fixed.

Feedback means you learn the result of each attempt straight away, from the LMS tests, a reference answer, a pair or a trainer hint.

Start your practice timer:

```
$ start=$(date +%s)
```

After each wrong item, add one line to the mistake log. Here is how appending works, using a fictional item:

```
$ printf '%s\n' "- Item A3: window end off by one. Rule: stop when end is the last index." >> notes/sliding-window.md
$ cat notes/sliding-window.md
- Item A3: window end off by one. Rule: stop when end is the last index.
```

`printf '%s\n' "..."` prints the text and adds a newline. `>>` appends the output to the file, instead of replacing it (a single `>` would overwrite the file). `cat` prints the file so you can check it.

To understand the technique, here is a small worked example of a sliding window. It is a teaching example, not one of your practice items, so do not copy it into your answers:

```python
def max_window_sum(nums, k):
    window = sum(nums[:k])
    best = window
    for end in range(k, len(nums)):
        window += nums[end] - nums[end - k]
        best = max(best, window)
    return best

print(max_window_sum([4, 0, 3, 7, 1], 2))
```

Line by line: `window` holds the sum of the first `k` values, and `best` the largest sum seen. Each loop step moves the window one place right, adding the new value and removing the one that fell off the left. The `print` line should show `10`, the window `3, 7`.

Check the time when you stop practising:

```
$ echo "$(( ($(date +%s) - start) / 60 )) minutes"
30 minutes
```

`/ 60` converts seconds into minutes. Bash arithmetic drops the remainder, so 1187 seconds shows as 19 minutes. You need at least 30 minutes on the timer.

Test this stage: your mistake log has one line for every wrong item, and the timer shows 30 or more minutes.

#### Y2-T55.4 Redo failed items, then take the after measure

Goal: redo the items you got wrong without notes, then measure again under the same conditions.

Stage 1. Redo without notes. Close your mistake log and reference, redo each failed item from memory, and time yourself. Write down what stopped you on any item you cannot solve.

Stage 2. Build the twin set. Set B must match set A in pattern, size, time limit and difficulty tag. Only the values change. If set A has eight numbers and a window of three, set B also has eight numbers and a window of three. If you are unsure whether set B is comparable, ask your trainer.

Stage 3. Take the after measure on set B. Use the same scoring card or platform score, the same time limit and the same timer method as the before measure. Record the score, the maximum, the time limit, the seconds taken and the attempt link in the after field.

Test this stage: compare the two entries. The maximum, time limit and difficulty tag must match.

#### Y2-T55.5 Log the numbers, the evidence and the check-in

Goal: a complete gap-log entry, evidence links that open, a mistake log committed to your repository and a booked check-in.

Stage 1. Fill every field, using the names your LMS shows: dimension, CRI 1 score, goal, before measure, after measure, and the before and after evidence links.

Stage 2. Download the gap-log export as a CSV file and save it as `gap_log.csv`. If the LMS gives another format, ask your trainer before converting it.

Stage 3. Write the checker, a small Python script that reads the export. Save this first part as `check_gap_log.py`:

```python
import csv
import sys

with open(sys.argv[1], newline="", encoding="utf-8") as f:
    rows = list(csv.DictReader(f))

print(len(rows), "rows read")
```

`csv` and `sys` are standard-library tools. `sys.argv[1]` is the file name you type after the script. `csv.DictReader` gives each row as a dictionary keyed by column header. Run it:

```
$ python check_gap_log.py gap_log.csv
5 rows read
```

Stage 4. Find empty fields. Step through this worked example of two invented rows, then add the same loop to your script:

```trace
TITLE: Finding empty gap-log fields
CODE:
rows = [{"dimension": "sliding-window", "before": "3/5"}, {"dimension": "", "before": "4/5"}]
for number, row in enumerate(rows, start=1):
    for field, value in row.items():
        if not value.strip():
            print("row", number, "empty", field)
STEPS:
1 :: rows=2 dicts :: Build a list with two rows. Each row is a dictionary keyed by column name.
2 :: number=1; row={"dimension": "sliding-window", "before": "3/5"} :: enumerate pairs each row with a number that starts at 1.
3 :: number=1; field="dimension"; value="sliding-window" :: The inner loop visits each field of row 1. Filled fields print nothing.
2 :: number=2; row={"dimension": "", "before": "4/5"} :: Move on to row 2.
3 :: number=2; field="dimension"; value="" :: The first field of row 2 is empty.
4 :: number=2; field="dimension"; value="" :: The test is true for an empty value.
5 :: number=2; field="dimension"; value="" :: print shows the row number and the empty field.
```

`value.strip()` removes spaces at both ends, so a cell with only spaces counts as empty. Add `bad = 0` before the loop, and `bad += 1` after the `print` inside the `if`, at the same indentation as the `print`. Then, after the loop, add:

```python
if bad == 0:
    print("OK")
```

Stage 5. Run the check on your export. If it reports empty fields, fix them in the LMS and re-export. Do not edit the CSV by hand, because the trainer checks the LMS export.

Stage 6. Open each evidence link in a fresh private window. The before link must show set A, the after link set B.

Stage 7. Commit the mistake log and checker on your branch, in Git Bash:

```
$ cd ~/dsa-yourname
$ git checkout -b y2-t55-gap-log-yourname
$ git add notes check_gap_log.py
$ git status
$ git commit -m "Add mistake log for sliding-window practice"
$ git push -u origin y2-t55-gap-log-yourname
```

`git checkout -b` creates and switches to a new branch. `git add` stages files, and `git status` shows what is staged (expect `new file:` lines for `notes/sliding-window.md` and `check_gap_log.py`). `git commit -m` saves a snapshot with a message. `git push -u origin` sends the branch to GitHub. If Git asks for your name and email, set them to match your GitHub account.

Stage 8. Book the check-in before Saturday 17 April. Confirm the weekday with `date -d "2027-04-17" +%A`, which should print `Saturday` if 2027 is your course year. Agree the date with your partner, then write it in your mistake log and the LMS. Commit and push the mistake log again (`git add notes`, `git commit -m "Add check-in date to the mistake log"`, `git push`) so the date is on your branch.

Open a pull request from your branch in your personal repository, and ask one squad-mate to approve it. Do not merge your own pull request.

Test this stage: the check prints `OK`, every evidence link opens to your attempt, the pull request exists and the check-in date is written down.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| Checker prints `row 3 empty after_measure` | You saved the entry before filling the after measure | Fill the field in the LMS, re-export, and run the checker again |
| Set IDs for before and after are the same | You repeated set A as the after measure | Use set B, built with the same pattern, size, limit and tag |
| Evidence link shows a login page or the course list | The link is not to your attempt | Copy the link from your attempt page, then test it in a fresh private window |
| Before and after times differ by a lot and the scores are not comparable | You changed the time limit or the card between measures | Use the same limit and the same scoring card for both |
| `date +%s` gives an error in PowerShell or Command Prompt | You ran the command outside Git Bash | Open Git Bash and run the timing commands there |
| `git push` is rejected or `git commit` says nothing to commit | You are on the wrong branch, or the file is not in `notes/` | Run `git status` and `git branch`, then move the file and commit again |
| Trainer asks what is next and you have no answer | Your mistake log has no next item | Add the next practice item to the log at the end of every session |

### Defend it in the viva

**1. Why did you choose this dimension and not your highest one?**

:::answer Model answer
The ticket's logic is that focused practice on a weakness gives more improvement than more practice on a strength. My CRI 1 and T54 scores both pointed to this dimension, so the choice rests on evidence. The goal has a number, a pattern and a time limit, so I can measure whether the practice worked.
:::

**2. Why did you use a twin set instead of retaking the same set?**

:::answer Model answer
This is a trade-off. Retaking set A is quicker, but it measures memory of the answers, not skill. A twin set costs time to check comparability, and that cost buys a fair comparison.
:::

**3. Walk me through what you personally did in this ticket.**

:::answer Model answer
Walk through your steps in order, and name the file or commit that shows each one. Your answer must match your own `git log`, so practise it against that before the viva.
:::

**4. How do you know the improvement is real, and not because set B was easier?**

:::answer Model answer
I checked comparability first: same pattern, size, limit, tag and scoring card. One pair of measures is still a small sample, so I would repeat the measure before a strong claim.
:::

**5. What is your next practice item, and where did it come from?**

:::answer Model answer
The next item comes from the mistake log, not from memory. I name the error I made most often, the rule that fixes it, and the item I will use to check it next.
:::

### Check yourself

```quiz
Q1: Which command creates a folder called notes, and does not fail if the folder already exists?
- mkdir notes
* mkdir -p notes
- touch notes
- ls -p notes
WHY: -p means create the folder if needed and do not fail if it exists. Plain mkdir fails on an existing folder, and touch makes a file.

Q2: Your timer shows 1187 seconds. Using Bash arithmetic with / 60, how many whole minutes does it show?
- 1187
- 20
- 0
* 19
WHY: Bash integer division drops the remainder: 1187 divided by 60 is 19, remainder 47. Rounding up to 20 is the tempting mistake.

Q3: What makes a before and after comparison fair under the ticket's rules?
* The two sets share the same pattern, size, time limit and difficulty tag, but the values differ
- The second set is easier, so the score is higher
- You use a different scoring card for the after measure to show new skills
- You repeat set A exactly, so the score can be compared word for word
WHY: Twin sets must be comparable, meaning the same pattern, size, limit and difficulty tag, with different values. Repeating set A measures memory of the answers, and a deliberately easier set makes the comparison meaningless.
```
