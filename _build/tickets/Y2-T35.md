### The ticket in plain words

Demo Day 1 is on 13 February. The panel will ask how your model was tuned. Tuning means trying several settings, such as how strongly a model is penalised for large coefficients, and keeping the setting that scores best.

There are two ways to fool yourself while tuning. The first is to pick settings by looking at the test rows, which are the rows you hold back as an honest exam. The second is to shuffle hourly rows into random folds. A shuffled fold can train on hour 10 and then test on hour 11, and those two readings are almost the same, so the score looks better than the model really is. A model tuned either way gives numbers that collapse once it runs on new data.

CityPulse needs honest, time-ordered cross-validation on training rows only. The test window is opened exactly once, at the end.

Live demos fail as well. A Wi-Fi drop or a projector fault can wipe out a squad's slot. So every squad records a backup video of at most 3 minutes, and rehearses a timed talk in which every member speaks. Your squad's README must link to the backup, and the trainer must be able to play it without signing in.

### Words you need

| Term | Plain meaning |
|---|---|
| Training rows | The rows the model is allowed to learn from. |
| Test window | The most recent rows, kept back until the final, single check. |
| Cross-validation | Splitting training rows into parts, training on some and scoring on the rest, then repeating so every part is scored. |
| Fold | One split from cross-validation: one training part and one validation part. |
| Time-ordered split | A split where training rows always come before validation rows in time. |
| `TimeSeriesSplit` | The scikit-learn class that makes time-ordered folds. |
| `gap` | Rows left out between the end of a training part and the start of its validation part. |
| `KFold` and `shuffle=True` | Ordinary folds, and a flag that shuffles rows before splitting. Both are banned here. |
| `GridSearchCV` | Tries every combination in a list of settings, scores each with cross-validation, and keeps the best. |
| `RandomizedSearchCV` | Tries a fixed number of random combinations from the settings you give. |
| `n_iter` | How many random combinations `RandomizedSearchCV` tries. |
| `random_state` | A seed for random choices. The same seed gives the same choices. |
| Pipeline | A scikit-learn object that chains preprocessing and a model into one object. |
| `model__alpha` | The `alpha` setting of the step named `model` inside a Pipeline. Two underscores join step and setting. |
| Ridge regression | A linear model with a penalty `alpha` on large coefficients. |
| Tree model | A model built from decision trees, such as a random forest. |
| `neg_mean_absolute_error` | A score that is the negative of the MAE. scikit-learn maximises scores, so errors are negated. |
| MAE | Mean absolute error: the average size of the prediction error, in the same unit as the target. |
| Standard deviation (std) | How widely the fold scores spread around their mean. |
| `cv_results_` | The table of every candidate that a search tried. |
| `rank_test_score` | The rank of a candidate. Rank 1 is the best. |
| `best_estimator_` | The model refitted on all training rows with the winning settings. |
| `joblib` | A library that saves a fitted model to a file and loads it again. |
| Pre-registration | Writing the search space and the decision rule down before you run anything. |
| Leakage | Information from validation or test rows reaching training, which makes scores look better than they are. |
| Commit | A saved snapshot of your changes in Git, with a message. |
| Branch | A separate line of work in Git, so changes can be reviewed before they join the main code. |
| Pull request (PR) | A request to merge your branch, which squad-mates review before it is merged. |
| SHA | The unique code of a commit. `git rev-parse --short HEAD` prints the short form of the current one. |
| Grep | A command that prints lines of text matching a pattern. |
| Run sheet | A timed plan that says who speaks in each minute of the rehearsal and demo. |
| Unlisted video | A video that anyone with the link can open, but that does not appear in search results. |
| Logged out | Viewing a page without signing in, which shows what an outside visitor sees. |

#### Y2-T35.1 Sort the training rows and build time-ordered folds

**Goal.** Build five folds where each validation part comes after its training part, and record their date ranges.

**Technique first: `TimeSeriesSplit`.** This class gives you index positions, not rows. For each fold it returns two lists of positions: the training positions and the validation positions. Here is a small example on ten numbers:

```python
from sklearn.model_selection import TimeSeriesSplit
import numpy as np

X = np.arange(10).reshape(-1, 1)
cv = TimeSeriesSplit(n_splits=3)
for train_pos, val_pos in cv.split(X):
    print("train", train_pos, "validate", val_pos)
```

Line by line:

- `X = np.arange(10).reshape(-1, 1)` makes ten rows, numbered 0 to 9.
- `cv = TimeSeriesSplit(n_splits=3)` asks for three folds. The validation part always comes after the training part.
- `for train_pos, val_pos in cv.split(X):` loops over the folds. Each fold gives two arrays of positions.
- The `print` line shows the positions for each fold.

Expected output is three lines. The first fold trains on positions 0 to 3 and validates on positions 4 and 5, and the last validates on positions 8 and 9. Training positions grow with each fold, and no validation position appears in its own training part.

**Stage 1: load the config and sort.** Your data path and key names come from your own `config.yaml`. The lines below use the same key names as the course chapter, so replace them if your file differs.

```python
import pandas as pd
import yaml

cfg = yaml.safe_load(open("config.yaml"))
df = pd.read_parquet(cfg["data"]["path"]).sort_values(["ts", "station"])
```

Line by line:

- `yaml.safe_load` reads the config file as plain data and returns a dictionary.
- `pd.read_parquet` reads the Parquet data file, which is a compact table format.
- `.sort_values(["ts", "station"])` orders rows by time, then by station. Sorting is the first thing the ticket asks for.

Test it: `python3 -c "import pandas as pd; print('ok')"` should print `ok`, and then run the file. It prints nothing, which is correct.

**Stage 2: keep the training rows only.** The test window must never reach tuning code.

```python
train = df[df["ts"] < pd.Timestamp(cfg["split"]["test_start"], tz="Asia/Kolkata")]
print(train.shape, train["ts"].min(), train["ts"].max())
```

The filter keeps rows before the test start date. The `print` shows how many rows you kept and the date range. If comparing `ts` with the timestamp raises a timezone error, your `ts` column has a different timezone. Match the two, and do not drop the time filter.

Expected output looks like `(1234, 6) 2025-... 2026-...` with your own numbers. The last date must be before your test start.

**Stage 3: make the folds and paste their ranges.** The ticket asks for `gap=24`.

```python
from sklearn.model_selection import TimeSeriesSplit

cv = TimeSeriesSplit(n_splits=5, gap=24)
ts = train["ts"].reset_index(drop=True)
for k, (tr, va) in enumerate(cv.split(train)):
    print(k, ts.iloc[tr].min(), ts.iloc[tr].max(), ts.iloc[va].min(), ts.iloc[va].max())
```

Line by line:

- `TimeSeriesSplit(n_splits=5, gap=24)` builds five folds with 24 rows left out between training and validation.
- `ts = train["ts"].reset_index(drop=True)` makes a copy of the timestamps with row numbers from 0. This matters because `cv.split` returns positions from 0, and `iloc` also uses positions.
- The loop reads each fold's training positions `tr` and validation positions `va`.
- The `print` shows the fold number and the first and last timestamp of the training part and the validation part.

Expected output is five lines, one per fold, with the validation dates after the training dates.

:::trap Gap is counted in rows, not hours
The ticket says `gap=24`. The chapter notes that `gap` counts rows. With two or more stations, one hour is several rows, so 24 rows can be less than 24 hours. Decide with your Data and Tech Lead which value you mean, write the reasoning in the ml-log, and be ready to defend it in the viva.

#### Y2-T35.3 Write `tune.py` with two searches

**Goal.** One script that runs a grid search for the Ridge pipeline and a randomised search for a tree pipeline, both on training rows only, and prints the top five rows.

**Technique first: `GridSearchCV` and `RandomizedSearchCV`.** A grid search fits every combination. A randomised search fits `n_iter` combinations drawn at random. Both score each candidate with cross-validation and keep the best. Here is a small example with a Pipeline and a grid:

```python
from sklearn.linear_model import Ridge
from sklearn.model_selection import GridSearchCV
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
import numpy as np

X = np.arange(20, dtype=float).reshape(-1, 1)
y = 3.0 * X[:, 0] + 1.0
grid = GridSearchCV(make_pipeline(StandardScaler(), Ridge()),
                    {"ridge__alpha": [0.1, 1.0, 10.0]}, cv=4,
                    scoring="neg_mean_absolute_error")
grid.fit(X, y)
print(grid.best_params_)
```

Line by line:

- `make_pipeline(StandardScaler(), Ridge())` chains a scaler and the model. The step name for Ridge is `ridge`, the lowercase class name.
- `{"ridge__alpha": [0.1, 1.0, 10.0]}` is the grid. The key is the step name, two underscores, then the setting.
- `scoring="neg_mean_absolute_error"` makes the search score by negative MAE, so the best score is the closest to zero.
- `grid.fit(X, y)` runs the search. It fits 3 candidates on 4 folds, then refits the winner on all rows.
- `print(grid.best_params_)` shows the winning setting.

Expected output is a dictionary such as `{'ridge__alpha': 0.1}`. Any winning value is acceptable here, because this is only practice.

**Stage 1: the Ridge grid in `tune.py`.** Use the grid you pre-registered, not the example values. Build the Pipeline with your `build_pipeline` from `src/pipeline.py`, which the Features v2 PR already provides.

```python
from sklearn.model_selection import GridSearchCV, TimeSeriesSplit
from src.pipeline import build_pipeline

cv = TimeSeriesSplit(n_splits=5, gap=24)
ridge_search = GridSearchCV(build_pipeline(cfg), {"model__alpha": [0.1, 1.0, 10.0, 100.0]},
                            cv=cv, scoring="neg_mean_absolute_error")
```

Line by line:

- The import brings in the two search tools and the Pipeline builder.
- `cv = TimeSeriesSplit(n_splits=5, gap=24)` uses the same folds you checked in T35.1.
- `build_pipeline(cfg)` returns the Ridge Pipeline. The key `model__alpha` addresses the Ridge step, which the chapter names `model`.
- `cv=cv` passes the time-ordered folds. The grid search must never use `KFold`.
- Nothing runs yet. This line only builds the search object.

**Stage 2: the tree search.** Turn the Ridge Pipeline into a tree Pipeline by replacing the model step. `clone` copies the Pipeline without any fitted state, and `set_params` swaps the `model` step.

```python
from sklearn.base import clone
from sklearn.ensemble import RandomForestRegressor
from sklearn.model_selection import RandomizedSearchCV

seed = cfg["seed"]  # use your config's seed key; add one if it is missing and note it
tree_pipe = clone(build_pipeline(cfg)).set_params(model=RandomForestRegressor(random_state=seed))
tree_search = RandomizedSearchCV(tree_pipe,
                                 {"model__n_estimators": [100, 200, 400],
                                  "model__max_depth": [4, 8, None],
                                  "model__min_samples_leaf": [1, 5, 10]},
                                 n_iter=20, random_state=seed, cv=cv,
                                 scoring="neg_mean_absolute_error")
```

Line by line:

- `clone(...)` makes an unfitted copy of the Pipeline.
- `.set_params(model=RandomForestRegressor(...))` replaces the step named `model` with a random forest. The Pipeline keeps the same preprocessing steps.
- The distributions list the values each setting may take. `None` for `max_depth` means no depth limit.
- `n_iter=20` asks for 20 random candidates out of the 27 possible combinations.
- `random_state=seed` makes the random draws repeatable.

**Stage 3: fit and print the top five.** The ml-log needs the MAE, not the negative score, so flip the sign.

```python
ridge_search.fit(train, train[cfg["target"]])
table = pd.DataFrame(ridge_search.cv_results_).nsmallest(5, "rank_test_score")
table["mae_mean"] = -table["mean_test_score"]
table["mae_std"] = table["std_test_score"]
print(table[["params", "mae_mean", "mae_std"]].to_string(index=False))
```

Line by line:

- `ridge_search.fit(train, train[cfg["target"]])` runs the search on training rows only. The test rows are not in `train`.
- `pd.DataFrame(ridge_search.cv_results_)` turns the results into a table with one row per candidate.
- `.nsmallest(5, "rank_test_score")` keeps the five best rows, where rank 1 is the best.
- `-table["mean_test_score"]` flips the negative MAE to a positive MAE.
- The last line prints the five settings with their mean and standard deviation.

Expected output: one row per candidate, up to five, each with a settings dictionary such as `{'model__alpha': 10.0}`, a positive `mae_mean` and a positive `mae_std`. A grid of four alpha values gives only four rows, because `nsmallest(5, ...)` cannot invent a fifth; add a value to your pre-registered grid if you want five. Run the tree search in the same way, with `tree_search.fit(...)`, and print its top five.

#### Y2-T35.4 Choose the simplest config within one std

**Goal.** Apply the pre-registered rule to the top five and save the chosen candidate with its metrics.

**Technique first: the decision rule as a trace.** The rule has three steps. Find the best mean MAE, add its standard deviation to get a limit, then keep the simplest candidate under that limit. Here is the rule written as a tiny program, with each candidate as `(complexity, mean MAE, std)`:

```trace
TITLE: Simplest config within one std
CODE:
rows = [(1, 12.5, 0.4), (2, 12.2, 0.3), (3, 12.0, 0.5)]
best = min(rows, key=lambda r: r[1])
limit = best[1] + best[2]
eligible = [r for r in rows if r[1] <= limit]
choice = min(eligible, key=lambda r: r[0])
print(choice)
STEPS:
1 :: rows=[(1, 12.5, 0.4), (2, 12.2, 0.3), (3, 12.0, 0.5)] :: Three candidates, each stored as (complexity, mean MAE, std).
2 :: rows=[(1, 12.5, 0.4), (2, 12.2, 0.3), (3, 12.0, 0.5)]; best=(3, 12.0, 0.5) :: min picks the row with the smallest mean MAE.
3 :: rows=[(1, 12.5, 0.4), (2, 12.2, 0.3), (3, 12.0, 0.5)]; best=(3, 12.0, 0.5); limit=12.5 :: The limit is the best mean plus its standard deviation.
4 :: rows=[(1, 12.5, 0.4), (2, 12.2, 0.3), (3, 12.0, 0.5)]; best=(3, 12.0, 0.5); limit=12.5; eligible=[(1, 12.5, 0.4), (2, 12.2, 0.3), (3, 12.0, 0.5)] :: Every candidate at or under the limit stays in the list.
5 :: choice=(1, 12.5, 0.4) :: Among the eligible rows, the smallest complexity number wins.
6 :: choice=(1, 12.5, 0.4) :: The chosen row is printed, so you can copy it into the ml-log.
```

The trace uses the number 1 as the simplest complexity. Your squad must define complexity in the pre-registration. For Ridge, a larger `alpha` gives simpler coefficients. For a forest, fewer trees or a shallower depth is simpler. Write your definition down before you read the table.

**Stage 1: find the chosen row.** Put the top-five table into the same form as the trace, with the complexity column you defined. Then apply the rule with the function below. It is the same four lines as the trace, which you should type yourself.

```python test
def simplest_within_one_std(rows):
    # each row is (complexity, mean_mae, std_mae); a lower complexity means simpler
    best = min(rows, key=lambda r: r[1])
    limit = best[1] + best[2]
    eligible = [r for r in rows if r[1] <= limit]
    return min(eligible, key=lambda r: r[0])

assert simplest_within_one_std([(1, 12.5, 0.4), (2, 12.2, 0.3), (3, 12.0, 0.5)]) == (1, 12.5, 0.4)
assert simplest_within_one_std([(1, 15.0, 0.5), (2, 12.0, 0.25)]) == (2, 12.0, 0.25)
assert simplest_within_one_std([(5, 9.0, 0.0)]) == (5, 9.0, 0.0)
print("rule ok")
```

Explanation of the test: the first assert shows that a candidate within the limit beats the best one when it is simpler. The second shows that a single close candidate wins when nothing else is under the limit. The third shows the trivial case. Running it prints `rule ok`. Your own `tune.py` must follow the same rule on your real table.

**Stage 2: save the candidate with its metrics.** If the chosen row is not the best one, refit it on the training rows. `set_params` takes the winning settings as keyword arguments.

```python

from sklearn.base import clone

h = subprocess.check_output(["git", "rev-parse", "--short", "HEAD"], text=True).strip()
chosen_search = ridge_search  # or tree_search, whichever search produced the chosen row
chosen = clone(chosen_search.estimator).set_params(**chosen_params)
chosen.fit(train, train[cfg["target"]])
joblib.dump(chosen, f"models/candidate_{h}.joblib")
with open(f"models/candidate_{h}.json", "w") as f:
    json.dump({"params": chosen_params, "mae_mean": chosen_mae, "mae_std": chosen_std}, f, indent=2)
```

Line by line:

- `subprocess.check_output([...], text=True)` runs `git rev-parse --short HEAD` from Python and returns the short SHA. It works the same on Linux and in Git Bash.
- `chosen_search` must be the search the chosen row came from, because the Ridge pipeline and the tree pipeline accept different settings. `clone(...).set_params(**chosen_params)` makes an unfitted copy with the winning settings. `**` unpacks the dictionary into keyword arguments.
- `chosen.fit(train, ...)` refits it on training rows only.
- `joblib.dump(...)` writes the fitted model to a file. The name uses the SHA, so the file is traceable.
- `json.dump(...)` writes the metrics beside it.

Create the folder first with `mkdir -p models`. Expected output: two files appear in `models/`. The `.joblib` file may be large for a forest, which is normal. `chosen_params`, `chosen_mae` and `chosen_std` are the values you read from your table in the previous stage.

### Defend it in the viva

Each answer shows the reasoning you should give out loud. Use your own work in your own words, and name the commit or file you changed.

**1. Why did you use `TimeSeriesSplit` and not `KFold` with shuffling?**

:::answer Model answer
Hourly readings sit close to their neighbours in time, so a shuffled split can train on hour 10 and validate on hour 11. The score then looks better than the model is on future data. `TimeSeriesSplit` trains only on earlier rows and validates on the period after them, which matches how the model will be used. The grep in TC1 proves the shuffled version is absent.
:::

**2. What is the trade-off in your gap setting?**

:::answer Model answer
A larger gap keeps lag features in the validation part from reaching into the training part, so the validation score is more honest. It also removes more rows from each fold. The ticket sets `gap=24`, but the splitter counts rows, not hours. With several stations, 24 rows covers less than a day. I would state which value I used, why, and what it would change, rather than hide it.
:::

**3. What did you personally do, and how can we see it?**

:::answer Model answer
A good answer names the subtask you owned, the file you changed and the commit message that shows it. It describes one decision you made, such as the grid values, the complexity definition or the run sheet timing, and why. The trainer checks this against your commits, so name only what your commits show.
:::

**4. Why did you open the test window only once?**

:::answer Model answer
Each time the test score changes a choice, the test rows act as a training set, and the reported score becomes too optimistic. The honest number is the first and only look. I logged that single result with its timestamp and git SHA, so anyone can check it did not change.
:::

**5. Why does the rule choose the simplest config within one standard deviation rather than the best one?**

:::answer Model answer
The best mean MAE is partly luck of the folds. Two settings within one standard deviation of each other cannot be told apart reliably. The simpler setting usually generalises at least as well and is easier to explain, so I choose it. Because I wrote the rule before running anything, the choice is not a judgement made after seeing the result.
:::
