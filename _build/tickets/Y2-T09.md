### The ticket in plain words

Five students in your squad edit the same shell scripts. A shell script is a text file of terminal commands that the computer runs from top to bottom. When two people change the same lines on different branches, Git cannot decide which version to keep. It stops and reports a **merge conflict**. This ticket teaches two habits.

The first habit is to resolve a conflict on purpose. You read both sides, write the version that keeps what both people intended, test the script, and record what you did. The second habit is to let a robot judge each change. Every pull request will run ShellCheck, a tool that reads shell scripts and reports risky lines. "It works on my machine" is not evidence. A green check on the pull request is.

CityPulse needs this because its fetch job runs unattended on a schedule. A script with a missing pair of quotes can break on a file name that contains a space, and nobody is watching. The ticket makes sure a broken script cannot reach `main`.

Check each tool before you begin. Run the commands in Git Bash on Windows or on the lab Linux machine.

### How your trainer checks it

The five acceptance criteria are covered as follows. Criteria 1 and 2 are shown by TC1 and TC2. Criterion 3 is TC3. Criterion 4 is TC4. Criterion 5 is answered in the cold-call (Y2-T09.7). TC5 tests criterion 1 again, by trying to merge bad code.

**TC1: the workflow file.** Run from the root of the squad repository:

```term
$ cat .github/workflows/lint.yml
on:
  pull_request:
...
        run: |
          ls scripts/*.sh
          shellcheck scripts/*.sh
```

- `cat` prints a file. The path must be exactly `.github/workflows/lint.yml`.
- Passing means there is a `pull_request` trigger and a step that runs `shellcheck scripts/*.sh`.
- Failing usually means the file is in the wrong folder. `cat` then prints `No such file or directory`.

**TC2: the checks history.** The trainer runs two commands. The first lists the checks on your red-green pull request:

```bash
gh pr checks <red-green PR number>
```

- `gh pr checks` lists the checks on one pull request. Replace the placeholder, including the angle brackets, with the number `gh` printed when you opened it.
- Passing means the `shellcheck` line shows `pass`.

The second lists the workflow runs on the branch:

```bash
gh run list --workflow lint.yml --branch ci/red-green-demo --json conclusion --jq '.[].conclusion'
```

- `gh run list` lists runs, newest first.
- `--workflow lint.yml` and `--branch ci/red-green-demo` filter the runs.
- `--json conclusion` asks for each run's result. `--jq '.[].conclusion'` prints that field, one per line.

Passing output has a `failure` and a `success`:

```term
$ gh run list --workflow lint.yml --branch ci/red-green-demo --json conclusion --jq '.[].conclusion'
success
failure
```

Failing output has only `success`, meaning you never made the check go red, or only `failure`, meaning the fix was never pushed. The `success` must come from a later commit than the `failure`.

**TC3: branch protection.** The trainer runs:

```bash
gh api repos/citypulse-y2/citypulse-<squad>/branches/main/protection --jq '.required_status_checks.contexts, .required_pull_request_reviews.required_approving_review_count'
```

- `gh api` calls the GitHub address that follows, which holds the protection rules for `main`.
- The two jq fields are separated by a comma, so each prints as its own output: first the list, such as `["shellcheck"]`, then the number.
- Passing shows `shellcheck` in the list, then a number of `1` or more.
- Failing shows `Branch not protected`, meaning no rule exists, or an empty list, meaning the status check is missing. Reading this address may need admin rights.

**TC4: the five git-log files.** The trainer runs:

```bash
ls docs/git-log/ && git log --format=%an -- docs/git-log/<name>.md | sort -u
```

- `ls` lists the folder. `&&` runs the second command only if the first succeeds.
- `git log --format=%an -- <file>` prints the author of each commit that changed the file. `--` separates options from the path.
- `sort -u` sorts the names and removes repeats.
- Passing lists five files, each authored by its student. The name must match what `git config user.name` prints on your machine, so set it before you commit.

**TC5: the blocked merge.** The trainer opens a throwaway pull request that adds `echo $UNQUOTED` to a script. Passing means the `shellcheck` check fails and the merge button is blocked.

**The cold-call (criterion 5).** Each student must say that rebase rewrites commits and must not be used on a shared branch.

### Do it, step by step

#### 1. Resolve the planned conflict (T09.1)

**The goal.** Merge two branches that changed the same lines, resolve the conflict by hand, test it, and push.

**Practise on a scratch repository first.** Git marks a conflict with three marker lines. Make a throwaway repository and cause one:

```bash
mkdir conflict-practice && cd conflict-practice
git init -q
printf 'LIMIT=10\n' > config.sh
git add config.sh && git commit -qm "start"
git switch -q -c left && printf 'LIMIT=20\n' > config.sh && git commit -qam "left"
git switch -q - && printf 'LIMIT=30\n' > config.sh && git commit -qam "right"
git merge left
```

- `git switch -q -c left` creates a branch called `left` and moves onto it. `-c` means create.
- `git switch -q -` returns to the previous branch.
- The last command changes the same line on both branches, so the merge stops.

Run `cat config.sh`. You see:

```text
<<<<<<< HEAD
LIMIT=30
=======
LIMIT=20
>>>>>>> left
```

The lines between `<<<<<<< HEAD` and `=======` are your version. The lines between `=======` and `>>>>>>> left` are the other version. To resolve it, edit the file to hold the final value, delete all three marker lines, then run `git add config.sh` and `git commit -m "Resolve LIMIT: keep 30"`. The `git add` marks the conflict resolved, and the commit completes the merge. If you get stuck, `git merge --abort` returns you to the state before the merge.

**The real conflict.** In your squad repository:

```bash
git fetch origin
git switch -c resolve-<name> origin/conflict-a
git merge origin/conflict-b
git status --short
```

- `git switch -c resolve-<name> origin/conflict-a` creates your branch from the trainer's `conflict-a`.
- `git merge origin/conflict-b` stops with a conflict in `scripts/fetch_once.sh`. The ticket says the trainer or your pair prepared both branches on the same lines of that file. If your merge reports a different file, or no conflict, ask your trainer which branches and file to use.
- `UU` in front of a file in `git status --short` means it has an unresolved conflict.

Open `scripts/fetch_once.sh`, read both sides, and write the version that keeps both intentions. Then check it:

```bash
grep -nE '^(<<<<<<<|=======|>>>>>>>)' scripts/fetch_once.sh || echo "no markers left"
bash -n scripts/fetch_once.sh && echo "syntax ok"
```

- `grep -nE` prints the line number of any line that starts with a marker. The `^` anchors the match to the start of the line.
- `|| echo` runs only if `grep` found nothing. Expected output: `no markers left`.
- `bash -n` checks the syntax without running the script. Expected output: `syntax ok`.

Run the script the way Y2-T06 taught you, and confirm it exits with 0. Then commit and push:

```bash
git add scripts/fetch_once.sh
git commit -m "Merge conflict-b: keep both sides' changes in fetch_once.sh"
git push -u origin resolve-<name>
gh pr create --draft --base main --head resolve-<name> --title "Evidence: resolve conflict-b (<name>)" --body "Evidence only. Closed after review."
```

- `-u` links the local branch to the remote one.
- `--draft` marks the pull request as not ready to merge. You close it after the trainer has seen it, with `gh pr close <number>`.

**Test this stage.** `no markers left`, then `syntax ok`, then exit code 0.

#### 2. Write your conflict log (T09.2)

**The goal.** Write `docs/git-log/<name>.md` with five headings, and merge it through a pull request.

```markdown
## Files and lines in conflict
## Cause
## Resolution and why
## Verification
## Rebase or merge
```

- **Files and lines in conflict.** The files and line numbers that Git marked.
- **Cause.** Why the two branches changed the same lines.
- **Resolution and why.** What the final version keeps from each side.
- **Verification.** The exact command you ran and the result it printed.
- **Rebase or merge.** One sentence in your own words.

A fictional example, about a different project, to show the style only: a recipe app had two branches that both changed a serving count. The writer kept the larger value, because the other branch added a test that expected it. Verified with `npm test`, which printed `12 passed`.

```bash
mkdir -p docs/git-log
git switch main && git pull
git switch -c docs/git-log-<name>
```

- `mkdir -p` creates the folder and does not fail if it exists.
- `git pull` brings `main` up to date before you branch.

Create the file, then commit, push and open a pull request with `gh pr create --base main --fill`. `--fill` takes the title and body from your commit. A squad-mate must approve it before you merge.

**Test this stage.** `grep -c '^## ' docs/git-log/<name>.md` prints `5`.

#### 3. Add the ShellCheck workflow on `ci/lint` (T09.3)

**The goal.** Fix every ShellCheck finding, then add a workflow that runs ShellCheck on each pull request.

**A small example first.** Run ShellCheck on your scripts:

```bash
shellcheck scripts/*.sh; echo "exit=$?"
```

- `scripts/*.sh` is expanded by the shell to every `.sh` file before ShellCheck starts.
- `; echo "exit=$?"` prints the exit code. `1` means a problem was found.

A finding looks like this. The layout varies by version and the line shown is only an example, but the code and line number are reported the same way:

```term
$ shellcheck scripts/*.sh; echo "exit=$?"
In scripts/fetch_once.sh line 12:
wc -l $OUT
       ^--^ SC2086 (info): Double quote to prevent globbing and word splitting.
exit=1
```

The fix is double quotes around the variable. Without them, a value with a space is split into two words. If ShellCheck is missing on Git Bash, run it in Docker: `docker run --rm -v "$PWD:/mnt" koalaman/shellcheck scripts/*.sh`. The `-v` option shares your folder with the container.

**Fix the findings.** Create the branch, then fix each flagged line, for example `wc -l "$OUT"`. Run ShellCheck again until the last line is `exit=0`. Do not add a disable comment just to turn it green. A disable comment needs a written reason.

```bash
git switch main && git pull
git switch -c ci/lint
```

**Stage A: the file and trigger.** Run `mkdir -p .github/workflows`, then create `.github/workflows/lint.yml` with these first lines:

```yaml
name: lint
on:
  pull_request:
```

- `name: lint` is the label in the Actions tab.
- `on:` starts the list of triggers. `pull_request:` runs the workflow for each pull request.

**Stage B: the job.** Add under the trigger lines:

```yaml
jobs:
  shellcheck:
    runs-on: ubuntu-latest
    steps:
```

- `shellcheck:` is the job id. Branch protection uses it as the check name, so do not rename it later.
- `runs-on: ubuntu-latest` gives a fresh Ubuntu runner, which already has ShellCheck.

**Stage C: the steps.** Add under `steps:`, with the dash indented six spaces:

```yaml
      - uses: actions/checkout@v4
      - name: ShellCheck scripts/
        run: |
          ls scripts/*.sh
          shellcheck scripts/*.sh
```

- `actions/checkout@v4` copies your repository onto the empty runner.
- `ls scripts/*.sh` prints the files checked, so the log proves coverage.
- `shellcheck scripts/*.sh` fails the step if it finds a problem.

**Stage D: check the YAML.**

```bash
python3 -c "import yaml;d=yaml.safe_load(open('.github/workflows/lint.yml'));print(list(d['jobs']))"
```

This needs Python with the PyYAML package; if `import yaml` fails, skip this check and read the file for tabs and indentation instead. Expected output: `['shellcheck']`. A parse error usually means a tab. Replace it with spaces.

Commit, push and open the pull request:

```bash
git add scripts .github/workflows/lint.yml
git commit -m "Add shellcheck workflow lint.yml with job shellcheck"
git push -u origin ci/lint
gh pr create --base main --fill
```

Once a squad-mate approves and the pull request merges, the check is in place on `main`.

**Test this stage.** The local ShellCheck run ends with `exit=0`, and the YAML check prints `['shellcheck']`.

The animation below shows what happens once the workflow file is on a pull request.

```flow
TITLE: One pull request, one ShellCheck run
NODES: Your laptop | GitHub | Fresh runner
STEPS:
1>2 :: gh pr create :: Your branch and its commits reach GitHub.
2>3 :: start job shellcheck :: GitHub reads lint.yml and gives the job to a fresh runner.
```

#### 4. Make the check go red, then green (T09.4)

**The goal.** Show a failing run, then a passing run on a later commit, on the same branch.

Start from `ci/lint`, which holds the workflow, and create a new branch:

```bash
git switch ci/lint
git switch -c ci/red-green-demo
```

Create `scripts/red_green_demo.sh`:

```bash
#!/bin/bash
OUT="report.csv"
echo $OUT
```

The unquoted `$OUT` on the last line is the SC2086 mistake. CI only reads this script, it never runs it.

```bash
git add scripts/red_green_demo.sh
git commit -m "Add red-green demo script with an unquoted variable"
git push -u origin ci/red-green-demo
gh pr create --base main --head ci/red-green-demo --title "Red-green demo: SC2086" --body "Demo pull request. Do not merge."
gh pr checks --watch
RUN_ID=$(gh run list --branch ci/red-green-demo --limit 1 --json databaseId --jq '.[0].databaseId')
gh run view "$RUN_ID" --log-failed | grep SC2086
```

- `gh pr checks --watch` waits for the run to finish. If it says no checks are reported yet, wait a few seconds and run it again.
- `gh run list ... --limit 1` finds the newest run on the branch, and `--jq '.[0].databaseId'` keeps only its id.
- `gh run view "$RUN_ID" --log-failed` prints only the failed steps. `grep SC2086` keeps the line with the code.

Now fix it. Change the line to `echo "$OUT"`, then:

```bash
git add scripts/red_green_demo.sh
git commit -m "Quote \$OUT in the red-green demo so ShellCheck passes"
git push
gh pr checks --watch
```

The second run is on a later commit and should pass. Check the history with the TC2 command. The output is `success`, then `failure`, newest first. Leave the pull request open until the trainer has seen it.

**Test this stage.** The history contains both words, and the newest run is `success`.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| No `shellcheck` check appears on the pull request. | The workflow is in the wrong folder, or its name does not end in `.yml`. | Move it to `.github/workflows/lint.yml` at the top of the repository. |

### Defend it in the viva

**1. Why does the check gate the merge button instead of only reporting a result?**

:::answer Model answer
A report that people can ignore protects nothing. A required check blocks the merge until it passes, so a broken script cannot reach the scheduled job. The gate is the whole point of the check.
:::

**2. Why use merge for the conflict branches rather than rebase?**

:::answer Model answer
Merge keeps the history exactly as it happened and adds one commit that joins the branches. The cost is a messier graph. Rebase gives a straight line, but it rewrites commits, and on a branch others have pulled that makes their copies disagree with yours. The trade-off is clean history against safety on shared work, and this squad chooses safety.
:::

**3. Which piece did you own, and how do you show it works?**

:::answer Model answer
Name the piece you owned, the command that proves it, and where the evidence is posted. For example, a student who owned the workflow file would say which job and step they wrote, and that the run history shows a failure followed by a success. Write your answer from your own commits, because the trainer checks the history against what you say.
:::

**4. Why is an unquoted variable dangerous in a script that runs unattended?**

:::answer Model answer
The shell splits an unquoted value at spaces and expands wildcards into file names. A value with a space becomes two words, so the command may act on the wrong files or fail. Nobody is watching a 3 a.m. run, so the damage can go unnoticed. Double quotes keep the value as one word, which is why ShellCheck reports SC2086.
:::

**5. What happens if someone renames the job `shellcheck`?**

:::answer Model answer
The check gets a new name, but the required check still waits for the old one. Every pull request then waits forever for a check that never reports. The fix is to restore the job id, or to change the rule and the job name in one step.
:::

### Check yourself

```quiz
Q: Your ShellCheck run prints SC2086 on the line echo $OUT. What is the correct fix?
- Add a comment that disables SC2086 at the top of the file.
- Delete the echo line, because the variable is not needed.
* Put double quotes around the variable, so the line reads echo "$OUT".
- Rename the variable to a name with no letters in it.
WHY: Double quotes keep the value as one word. A disable comment hides the warning without fixing the code, and the course allows it only with a written reason. The most tempting wrong option is the disable comment, because it turns the check green quickly.

Q: A workflow's job is named shellcheck, but branch protection requires a check named lint-shellcheck. What happens to pull requests?
- They merge as normal, because the rule is only a suggestion.
- The check runs twice, once under each name.
```
