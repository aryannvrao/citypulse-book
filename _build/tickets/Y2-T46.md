### The ticket in plain words

CityPulse is now public, and the ward dashboard team is building on it. If the service stops overnight, the first person to find out is an angry client. This ticket makes the squad find out first.

Three things change. An outside checker calls the API's health address every minute. If it fails twice in a row, an alert goes to a shared channel, and a recovery notice follows when the service works again. This is uptime monitoring.

The API's request logs also become structured: each request writes one JSON line with named fields, so you can ask "how many server errors today?" and save the question as a query.

Finally, the team writes a service level objective (SLO), a promise such as "99% of requests succeed over seven days". The measured value is the service level indicator (SLI). The error budget is the failure that promise still allows. When the budget is spent, the team stops new features and fixes reliability.

### Words you need

| Term | Plain meaning |
|---|---|
| Uptime check | A probe that calls a URL on a schedule from outside the service and records pass or fail. |
| Health endpoint | A URL, here `/v1/health`, that reports whether the service works. |
| Alert policy | A rule that turns repeated failures into a notification. |
| Notification channel | A destination for alerts, such as a shared alias or the squad chat channel. |
| Runbook | A document that says what to do when an alert fires. |
| Structured log | A log line in a fixed format, here one JSON object per request. |
| Standard output (stdout) | The text stream a program prints to, which the platform collects. |
| `PYTHONUNBUFFERED` | An environment variable that makes Python send each log line at once. |
| Environment variable | A named value a program reads when it starts, such as `GIT_SHA`. |
| Git SHA | The short id of a commit, printed by `git rev-parse --short HEAD`. |
| Logs Explorer | The Google Cloud console page that searches logs with a query. |
| `jsonPayload` | The Cloud Logging field that holds the parsed JSON fields of a log line. |
| 4xx and 5xx | Status code families: 4xx means the caller erred, 5xx means the server failed. |
| SLI | Service level indicator: a measured ratio of good events to valid events. |
| SLO | Service level objective: a target for an SLI over a stated window. |
| Error budget | The failures an SLO allows: 100 minus the target, applied to the window. |
| Cloud Run | The Google service that runs your container when requests arrive. |
| Public invoker | The permission (`allUsers`, role `roles/run.invoker`) that lets anyone call a Cloud Run service. |
| `gcloud` | The Google Cloud command-line tool. |

### How your trainer checks it

The trainer checks five acceptance criteria: an alert within 5 minutes with a screenshot showing both timestamps; a shared target and a recovery notice; a complete SLO in `docs/slo.md`; two saved queries that run; and a latency SLI that excludes `/v1/health`. Four test cases follow.

**TC1: the alert fires and recovers.** The trainer stops the service and notes the time, for example with `gcloud run services update <svc> --max-instances=0`.

- `gcloud run services update` changes a Cloud Run service. `run` is the product and `services update` is the action.
- `<svc>` is your service name.
- `--max-instances=0` allows no running copies, so requests fail.
- If your gcloud version rejects `0`, ask the trainer which method they use. Removing the public invoker (the `allUsers` invoker role) also makes the service unreachable.

Passing: the alert arrives within 5 minutes of the stop, and a recovery notice arrives after the restore. Failing: no alert, or one after 5 minutes. The usual causes are an unsaved check, a policy pointing at another check, or a threshold of more than 2 failures.

```term
$ curl -fsS -m 10 "$URL/v1/health" | grep -q '"ok"' && echo UP
UP
$ echo "restored: $(date -Iseconds)" | tee -a docs/alert-test.md
restored: 2026-11-17T10:24:12+05:30
```

Line by line. `curl -fsS -m 10` fetches the health URL and gives up after 10 seconds. The pipe sends the body to `grep -q`, which exits with 0 only if `"ok"` is present, and `&& echo UP` prints `UP` only then. The second line prints the restore time and appends it to a file, in the format `date -Iseconds` prints.

**TC2: the 5xx query runs.** The trainer pastes `docs/queries/errors_5xx.txt` into Logs Explorer for the last 24 hours. Passing: it runs with no syntax error and returns a count, and 0 is acceptable. Failing: a red syntax error, usually from a stray quote or a comment line the console rejects.

**TC3: the SLO query matches.** The trainer runs the query in `docs/slo.md`. Passing: the number is close to the written current value. Failing: a large gap, usually from a different window or from counting `/v1/health`.

**TC4: the uptime check config.** Passing: a 1-minute interval, target `/v1/health` on the README host, and a 2-failure threshold. The threshold lives in the alert policy condition, so check there too. Failing: a 5-minute interval, a wrong path, or an old host.

### Do it, step by step

Commands run in Git Bash on Windows or on the lab Linux machine, and behave the same unless a note says otherwise.

#### Y2-T46.1: JSON request logs with the required fields

The goal is for each request line to carry `path`, `status`, `latency_ms`, `request_id`, `git_sha` and `model_version`, with no buffering.

**Stage 1: look at what the platform stores.** In Logs Explorer, filter on the service:

```text
resource.type="cloud_run_revision"
resource.labels.service_name="citypulse-api"
```

Your JSON lines should show their keys under `jsonPayload`. A line under `textPayload` is plain text and cannot be filtered by field.

**Stage 2: read the two new values from the environment.** The container receives these when it starts:

```python
import os
git_sha = os.environ.get("GIT_SHA", "unknown")
```

`os.environ.get(name, default)` returns the variable's value, or the default if it is missing, so a missing value logs as `unknown` instead of crashing the request. Add `git_sha` and `model_version` to the dictionary the middleware logs. The field names must match the ticket exactly. The variable names are your squad's choice.

**Stage 3: set the values at build time.** `git rev-parse --short HEAD` prints the commit SHA. Pass it into the image through your deploy workflow, and add the buffering setting to the Dockerfile:

```dockerfile
ENV PYTHONUNBUFFERED=1
```

`ENV` sets an environment variable inside the image. This value stops Python holding log lines in memory, so they survive a crash.

**Stage 4: redeploy by tag.** The deploy workflow runs on tags starting with `v`. Run `git tag v1.0.1` then `git push origin v1.0.1`, with a name of your choice.

Test: make a few requests and check that the new fields appear under `jsonPayload` and that nothing appears under `textPayload`.

#### Y2-T46.2: the uptime check

**Stage 1: fill in the form.** In the console, go to Monitoring, then Uptime checks, then Create uptime check. Set the protocol to HTTPS, the host to your README host without `https://`, the path to `/v1/health`, the interval to 1 minute and the timeout to 10 seconds. The host and path form the URL the checker calls. The timeout is how long it waits before it counts a failure.

**Stage 2: add the response check.** Expect status 200, and add a content matcher that requires the body to contain `ok`. A status code alone is not enough, because an error page can come back as 200.

**Stage 3: save and run.** Use the run or test option if the form offers one. Expect a pass, and note the check's name for T46.3.

#### Y2-T46.3: the alert policy

**Stage 1: the condition.** Go to Alerting, then Create policy. Choose your uptime check and set the condition to fire after failures in 2 consecutive checks. Two checks in a row avoid alarms from a single network blip.

**Stage 2: the notifications.** Add the shared email alias and the squad channel. Do not use one person's inbox, because an alert there is lost when that person is ill.

**Stage 3: the runbook link and recovery.** Put the full GitHub link to `docs/cloud-runbook.md` in the policy's documentation field. Turn on the option that notifies when the incident closes.

**Stage 4: test notification.** Send a test notification and check that it reaches the alias and the channel.

#### Y2-T46.4: the fire test

Run this with the squad, because the trainer watches the alert arrive.

```flow
TITLE: One fire test, from stop to recovery
NODES: You | Cloud Run service | Uptime checker | Squad channel
STEPS:
1>2 :: remove invoker :: You take away public access, so outside calls are refused.
3>2 :: GET /v1/health :: The checker calls every minute and is refused.
2>3 :: refused :: The second failure in a row triggers the alert.
3>4 :: alert with runbook link :: The squad channel receives the alert.
1>2 :: add invoker :: You restore public access.
3>4 :: recovery notice :: The next passing check sends the recovery notice.
```

Run the commands in order, keeping `docs/alert-test.md`:

```bash
echo "stop: $(date -Iseconds)" | tee -a docs/alert-test.md
gcloud run services remove-iam-policy-binding citypulse-api --region <your-region> --member=allUsers --role=roles/run.invoker
echo "alert: <time from the notification>" >> docs/alert-test.md
gcloud run services add-iam-policy-binding citypulse-api --region <your-region> --member=allUsers --role=roles/run.invoker
echo "restored: $(date -Iseconds)" | tee -a docs/alert-test.md
```

Line by line. `date -Iseconds` prints the time with its offset, and `tee -a` shows and appends it. `remove-iam-policy-binding` takes `allUsers` off the invoker role, so the public can no longer call the service. `--region` is the Cloud Run region from your README. `>>` appends a line, and you type the alert time from the notification. The add command gives the permission back. Successful removal and restore commands print nothing. Test: the curl check from TC1 must print `UP` after the restore.

#### Y2-T46.5: two saved queries

**Stage 1: the common lines.** Every query starts with the same two filters, which join with AND:

```text
resource.type="cloud_run_revision"
resource.labels.service_name="citypulse-api"
```

**Stage 2: the 5xx query.** Add `jsonPayload.status>=500`. The `>=` means greater than or equal to. Paste the three lines into Logs Explorer, set the range to the last 24 hours, and run it. To see the count by path, open the Log fields panel and read the counts for `jsonPayload.path`. Save it in the console and in `docs/queries/errors_5xx.txt`.

**Stage 3: the slow prediction query.** Replace the status line with two lines. Text values need quotes, and numbers do not:

```text
jsonPayload.path="/v1/predict"
jsonPayload.latency_ms>500
```

Save it as `docs/queries/slow_predict.txt`.

**Stage 4: test the file.** Comments in the Logging query language start with `--`, not `#`. If the console rejects a comment line, delete it and put the description in the runbook. You can test the same idea locally:

```bash
jq -c 'select(.status>=500)' access.log | wc -l
```

`jq -c` prints each matching object on one line, and `select` keeps objects with status 500 or more. `wc -l` counts the lines. Test: each query runs in Logs Explorer without an error.

#### Y2-T46.6: one section of docs/slo.md

The examples use an invented bike-share API called BikeHop. Your squad chooses its own endpoint, target and window.

**Stage 1: the definitions.** The SLI is good events divided by valid events. A good event is not 5xx and finishes under the latency limit. A valid event is not 4xx and is not `/v1/health`. The D27 chapter gives the course definitions.

**Stage 2: count a small window.** This trace counts four invented requests:

```trace
TITLE: Counting valid and good requests
CODE:
seen = [("/health", 200, 5), ("/trips", 200, 120), ("/trips", 404, 30), ("/trips", 503, 900)]
valid = [s for s in seen if s[0] == "/trips" and not 400 <= s[1] <= 499]
good = [s for s in valid if s[1] < 500 and s[2] < 300]
sli = len(good) / len(valid)
STEPS:
1 :: seen has 4 rows of (path, status, latency_ms) :: Each row is one request, and the health row is still in the list.
2 :: valid=[("/trips", 200, 120), ("/trips", 503, 900)] :: The health row fails the path test and the 404 is a client error, so both are dropped.
3 :: valid=[("/trips", 200, 120), ("/trips", 503, 900)]; good=[("/trips", 200, 120)] :: The 200 is fast enough. The 503 is a server error, so it is not good.
4 :: good has 1 row; sli=0.5 :: One good request out of two valid ones.
```

Line 2 keeps rows with the right path and no 4xx status. The `not 400 <= s[1] <= 499` test is a chained comparison, flipped by `not`. Line 4 divides good by valid.

**Stage 3: the budget.** With a 99% target over 7 days, BikeHop with 40,000 valid requests has a budget of 1% of 40,000, which is 400 failed requests. In minutes, 7 days is 10,080 minutes, and 1% of that is 100.8 minutes. Write both, and say which one the policy uses.

**Stage 4: the measurement query.** Export the window, then count with the rules from stage 2:

```bash
gcloud logging read 'resource.labels.service_name="citypulse-api" AND jsonPayload.path="/v1/predict"' --freshness=7d --format=json > logs/predict_7d.json
```

`--freshness=7d` keeps the last seven days, and `--format=json` prints a JSON list. The `>` writes the file, so `logs` must exist. Write a short Python script that applies the same rules to that file.

**Stage 5: the current value and the policy.** Compute the value for the last 24 hours (use `--freshness=1d` in the export, or filter the file by timestamp), and write it with the date and your initials or handle. Then write one sentence on what the team does at each budget level. A number without its command does not count.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| No alert after 5 minutes | The policy points at another check, or was not saved | Open the policy, confirm it uses your check, and run the fire test again |
| Alert arrives late | Interval longer than 1 minute, or threshold above 2 | Set 1 minute and 2 consecutive failures |
| Check stays green while the service is down | Old host, or no `ok` content matcher | Copy the host from the README and add the matcher |
| Query shows a syntax error | A `#` comment line (comments start with `--`) or a stray quote | Remove the comment and check each quote |
| Query returns no rows | Range too short, or logs under `textPayload` | Widen the range and check the logs are JSON with `PYTHONUNBUFFERED=1` |

### Defend it in the viva

Each answer explains the reasoning. Your own answer must describe the work you did.

**Why does the alert wait for two failed checks?**

:::answer Model answer
One failed check can come from a network blip outside the service. Requiring two in a row filters most false alarms, so the team trusts the alert. The check still runs every minute, so a real outage is reported well inside the 5-minute target.
:::

**What is the trade-off of an outside checker compared with logs inside the service?**

:::answer Model answer
An outside checker sees what a real client sees, including DNS and encryption problems. A service that stops writing logs cannot report its own failure. The cost is that the check tests one URL, so it does not say which feature broke. Logs give that detail once the alarm has sounded.
:::

**What did you personally do in this ticket?**

:::answer Model answer
Name the subtask you owned and the commits you made from the list. Then explain one decision in it, such as the host you chose or how you checked the query. A good answer names a file, a command and a result that a trainer can find in Git.
:::

**Why is the error budget a count and not only a percentage?**

:::answer Model answer
The budget is the number of failures the team can still spend. A 99% target over 40,000 valid requests allows 400 failures, a count the team can watch run down. A percentage alone does not show how close the team is to the limit when traffic changes.
:::

**Why is `/v1/health` excluded from the latency SLI?**

:::answer Model answer
The health check is fast and always succeeds. Counting it adds many easy good events and makes the SLI look better than users experience it. The SLI should measure the requests users make, such as `/v1/predict`.
:::

### Check yourself

```quiz
Q: The alert policy fires after two consecutive failed checks. What is the main reason for requiring two rather than one?
- It makes the alert arrive at the same time as the outage.
- It removes the need for a recovery notice.
* It filters out one-off network blips so the team trusts the alert.
- It stops the check from running every minute.
WHY: One failed check can come from a network problem unrelated to the service. Two in a row give fewer false alarms. The tempting wrong option is about timing, but waiting for two checks takes longer, not less time.

Q: An SLO of 99% over 7 days is measured on 20,000 valid requests. How many failed requests does the error budget allow?
* 200
- 20
- 2,000
- 99
WHY: 1% of 20,000 is 200. The 20 option uses 0.1%, and 2,000 uses 10%. Reading 99 as a count mixes the target with the budget.

Q: Which filter line keeps the latency SLI from counting the health check?
- jsonPayload.path="/v1/health"
- jsonPayload.status>=500
- resource.type="cloud_run_revision"
* jsonPayload.path="/v1/predict"
WHY: Keeping only the prediction path leaves out /v1/health entirely. The first option keeps only the health check, the opposite of what you need. The status and resource lines do not change which path is counted.
```
