### The ticket in plain words

CityPulse will soon have a public web address, and the client will send requests to `/v1/predict`, the endpoint that returns a prediction. So far the team has checked that endpoint by hand with `curl`, a command that sends one request and prints the reply. Nobody repeats hand checks on every change. A small edit to a validation rule can quietly break the contract, which is the set of promises the API makes about inputs, errors and model version.

In T40, peer fuzzing found real bugs. Fuzzing means sending many odd or invalid inputs on purpose to see what breaks. Each bug it found must stay fixed.

This ticket asks for an automatic test suite. A test is a short piece of code that sends a request, then checks the reply. The suite runs in GitHub Actions, a service that starts a fresh machine on every push. A coverage floor of 60 per cent requires that at least 60 per cent of the API's lines run during the tests. Branch protection on `main` then disables the merge button while a check is red.

### How your trainer checks it

The trainer checks six acceptance criteria and four test cases. Work through all of them yourself before you ask for review.

**Acceptance criteria, and how you prove each one:**

1. At least 10 tests are collected: `pytest --collect-only -q` ends with `N tests collected`.
2. The suite has the required kinds of test. Read the names in `pytest --collect-only -q tests/test_api.py`.
3. The CI test job is green and reports coverage of at least 60 per cent. Check the Actions tab.
4. A failing test job blocks the merge. Your evidence is the gate-check screenshot.
5. Every student authored two or more test functions, one an error case. Check with TC4.
6. No credentials are needed. `grep -n secrets .github/workflows/ci.yml` prints nothing.

**TC1: the clean install and test run.**

The steps are `git clone ... && pip install ... && pytest`. Read it in parts:

- `git clone ...` copies the repository into a new folder. `...` is the repository address.
- `&&` runs the next command only if the previous one succeeded.
- `pip install -r ...` installs the packages listed in each named requirements file.
- `pytest` runs the suite with the options in `pyproject.toml`.

The passing output looks like this:

```term
$ pytest
...........                              [100%]
Required test coverage of 60% reached. Total coverage: 74.00%
11 passed in 1.84s
```

The numbers are a sample. What matters is `Required test coverage of 60% reached` and the pass count. Failing output and its usual cause:

- `FAIL Required test coverage of 60% not reached`: too few lines ran. Read the Missing column and add tests for those lines.
- `ModuleNotFoundError: No module named 'api'`: `pythonpath = ["."]` is missing from `pyproject.toml`.
- `RuntimeError: The starlette.testclient module requires the httpx package to be installed` (or a `ModuleNotFoundError` for `pytest_cov` or another package): a package is missing from `requirements-dev.txt`.

**TC2: branch protection lists the test check.**

Run `gh api repos/ORG/citypulse-<squad>/branches/main/protection --jq '.required_status_checks.contexts'`. Read it in parts:

- `gh api` calls one GitHub REST address. `repos/ORG/citypulse-<squad>/branches/main/protection` is that address; `ORG` and `<squad>` are replaced by real names.
- `--jq '.required_status_checks.contexts'` keeps only the list of required check names from the JSON reply.

The expected output is a list such as `["test"]`. It must include the name of your CI job. A `[]` means no check is required. An error saying the branch is not protected means branch protection is not set up.

**TC3: a failing PR is blocked.**

Run `gh pr view <gate-check PR> --json statusCheckRollup,mergeStateStatus`. Read it in parts:

- `gh pr view <gate-check PR>` shows one PR. Replace the placeholder with its number.
- `--json statusCheckRollup,mergeStateStatus` picks two fields. `statusCheckRollup` lists each check and its result. `mergeStateStatus` says whether GitHub allows the merge.

The expected result is a check with conclusion `FAILURE` and `mergeStateStatus` `BLOCKED`. If it says `CLEAN`, the test job is not required, so return to TC2.

**TC4: every student wrote tests.**

Run `git blame -w tests/test_api.py | grep 'def test_' | awk '{print $2}' | sort | uniq -c`. Read it in parts:

- `git blame -w` lists every line with its author. `-w` ignores whitespace changes, so a reformat does not take ownership of lines.
- `grep 'def test_'` keeps only the lines that start a test function.
- `awk '{print $2}'` prints the second field. In default blame output that is the first name with a bracket, such as `(Ada`.
- `sort | uniq -c` counts how many test functions each author started.

Every squad member should appear with a count of at least 2. If two squad-mates share a first name, their counts merge, so count those by hand from the blame output.

#### Y2-T41.1: pin the dev tools and set the coverage floor

**Goal:** a file that installs the same test tools for everyone, and a pytest setting that fails the run below 60 per cent.

First install the three tools, then read the exact versions.

```bash
pip install pytest pytest-cov httpx
pip show pytest pytest-cov httpx | grep -E "^(Name|Version)"
```

`pip install` downloads each package and its dependencies. `pip show` prints details, and `grep -E "^(Name|Version)"` keeps only the name and version lines.

Create `requirements-dev.txt` in the repository root. Write one line per package with `==` and the version you just read:

```text
pytest==<version from pip show>
pytest-cov==<version from pip show>
httpx==<version from pip show>
```

`==` pins the version. Without it, a future release could change how the tests behave. 
Now open `pyproject.toml` and add a `[tool.pytest.ini_options]` section. The ticket gives the exact `addopts` value, so copy it:

```text
[tool.pytest.ini_options]
pythonpath = ["."]
addopts = "--cov=api --cov-report=term-missing --cov-fail-under=60"
```

`pythonpath = ["."]` lets `from api.main import app` work on any machine. `addopts` adds these options to every run. `--cov=api` measures the package only, and `--cov-fail-under=60` fails the run below 60 per cent.

Test this stage. Install from both files in a fresh virtual environment (`python -m venv .venv`, activate it, then `pip install -r requirements.txt -r requirements-dev.txt`), then run:

```bash
pytest --collect-only -q
```

With no tests yet, pytest prints `no tests collected` and exits with code 5. That is expected at this stage. Check the exit code with `echo $?`.

#### Y2-T41.2: build the fixtures in conftest.py

**Goal:** a shared `client` and a shared `valid_payload` that every test receives.

A fixture is a function marked with `@pytest.fixture`. A test asks for it by naming a parameter with the same name. Here is a fictional example about a bike-share app, which is not your project:

```python
import pytest

@pytest.fixture
def basket():
    return {"items": 2, "total": 9.5}

def test_basket_total(basket):
    assert basket["total"] == 9.5
```

Line by line: `@pytest.fixture` marks `basket` as shared setup, and the test's parameter `basket` makes pytest pass its result in.

Now create `tests/conftest.py` with the `client` fixture. The `scope="session"` setting means pytest builds the client once for the whole run.

```python
import pytest
from fastapi.testclient import TestClient
from api.main import app

@pytest.fixture(scope="session")
def client():
    with TestClient(app) as c:
        yield c
```

`with TestClient(app) as c:` starts the app's lifespan, so the model loads. `yield c` hands the client to the tests, and the `with` block closes it afterwards. Without `with`, the model is never loaded.

Write `valid_payload` yourself. Open `api/schemas.py`, find `PredictRequest`, and return a dictionary with every required field, inside its limits. The default `function` scope gives each test a fresh copy.

Test this stage:

```bash
python -c "from api.main import app; print(type(app).__name__)"
```

The output must be `FastAPI`. An `ImportError` here means `pythonpath` or the package folder is wrong.

#### Y2-T41.3: write your own error-case tests

**Goal:** at least two test functions, one checking an error, each named after the behaviour it checks.

A test sends a request and asserts on the reply. Here is the pattern with a fictional ride-fare endpoint:

```python
def test_ride_rejects_negative_minutes_with_422(client, valid_ride):
    r = client.post("/v1/rides/fare", json={**valid_ride, "minutes": -1})
    assert r.status_code == 422
```

Line by line: `{**valid_ride, "minutes": -1}` copies the fixture and changes one field, and `r.status_code == 422` fails unless the status is exactly 422.

Write your own functions for your API, with at least one 404 or 422 test, each checking one behaviour. Between you, the squad's file must contain at least: one happy-path `/v1/predict` test (status 200), one 404 test (a route that does not exist, such as `client.get("/v1/nope")`), and one 405 test (the wrong verb on a real route, such as `client.get("/v1/predict")` when only POST is allowed). Agree who writes which before you start.

Test this stage by running one function by its name. Add `--no-cov`, because the coverage floor from `addopts` would fail a run of a single test:

```bash
pytest -q --no-cov tests/test_api.py::test_predict_rejects_negative_humidity_with_422
```

Use your own function name. The output ends with `1 passed`. Run the file next with plain `pytest`, and you should see your tests pass.

#### Y2-T41.4: one parametrized 422 test and the model_version check

**Goal:** one test function that runs several bad inputs, and a test that compares `model_version` with the metrics file.

Parametrize runs one function once per row. A fictional example:

```python
import pytest

@pytest.mark.parametrize("n, expected", [(2, 4), (3, 9), (-1, 1)])
def test_square(n, expected):
    assert n * n == expected
```

`@pytest.mark.parametrize` names two parameters, then gives a list of value pairs. pytest runs the function three times. Run it with `pytest -q` and expect `3 passed`.

For your 422 test, each row is one out-of-range or wrong-type case, and you need at least four. Build each request with `{**valid_payload, field: value}`.

For the model_version test, first confirm the file path from the folder where pytest runs:

```bash
find . -name "metrics_v1.json" -not -path "./.venv/*"
```

Open the file and note the key that holds the version (the example below assumes `version`). Then read the file with a `with` block, which closes it automatically. Put `import json` at the top of the test file:

```python
with open("models/metrics_v1.json") as f:
    expected = json.load(f)["version"]
```

Fill in the rest yourself: post a valid payload, then assert that `r.json()["model_version"]` equals `expected`. Replace the path or the key if `find` or the file shows something different.

#### Y2-T41.5: turn fuzz bugs into regression tests

**Goal:** one named test for each payload in `fuzz.py` that caused a bug in T40.

Find the payloads first:

```bash
grep -n -i "bug\|regress\|expected" fuzz.py
```

`grep -n` prints line numbers, `-i` ignores case, and the `\|` makes it match any of the three words. Each match tells you a payload and the code it should get.

For each payload, write one test. Name it after what broke, not after the payload's number:

```python
def test_regression_negative_pm25_returns_422(client, valid_payload):
    r = client.post("/v1/predict", json={**valid_payload, "pm25": -1})
    assert r.status_code == 422
```

The field name `pm25` is only an example; use the real fields and codes from your `fuzz.py`. A future failure should name what broke. Test with `pytest -q --no-cov -k regression`, where `-k` runs only the tests whose names match and `--no-cov` skips the coverage floor for a partial run.

#### Y2-T41.6: add the test job and branch protection

**Goal:** a CI job named `test` that runs on every pull request, and a branch rule that requires it.

```flow
TITLE: How a red check blocks a merge
NODES: Your laptop | GitHub | CI runner
STEPS:
1>2 :: git push :: Your branch travels to GitHub, and a pull request is opened.
2>3 :: start test job :: GitHub gives the code to a fresh Linux machine.
3>2 :: pytest result :: The runner reports pass or fail back to the pull request.
2>1 :: merge blocked or allowed :: Branch protection reads the result and decides whether the merge button works.
```

A workflow file is YAML. YAML uses spaces for indentation, never tabs, and each level sits two spaces further in. Your `.github/workflows/ci.yml` from T40 already has an `on:` section; check that it includes `pull_request`, or the job will not run on PRs. If the file already has a `jobs:` section, add `test:` beside the existing job instead of a second `jobs:`. Start with the job's first stage:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
```

`jobs:` holds the job list, and `test:` is the job name that TC2 reads. `runs-on` picks a fresh Linux machine. `actions/checkout@v4` copies your repository onto it, and `actions/setup-python@v5` installs Python. Use the version your lab prints from `python --version`.

Add the second stage yourself, with two `run:` lines: one that installs both requirement files, and one that runs `pytest`. Then push the branch and check the Actions tab. The job must be green.

Now enable branch protection. In the repository on GitHub, open Settings, then Branches, and add a rule for the pattern `main`. Tick require status checks, select the test job, and tick require a pull request with one approval. The check appears in the search only after the job has run once.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| `pytest` reports `no tests ran` or collects zero tests | The file or function names do not match pytest's pattern | Name files `test_*.py` and functions `test_*`, then run `--collect-only` again |
| `ModuleNotFoundError: No module named 'api'` only in CI | `pythonpath = ["."]` is missing | Add it to `pyproject.toml` and push |
| Coverage is below 60 per cent although every test passes | Too few lines in `api` ran | Read the Missing column and add tests for those lines |
| `FileNotFoundError` for `metrics_v1.json` in CI | The path is wrong from the folder pytest runs in, or the file is not committed | Check with `ls models/` and commit the file |
| TC2 prints `[]` or the wrong name | The job name in `ci.yml` does not match the required check | Make the rule select the exact job name, then run TC2 again |

### Defend it in the viva

**Question 1 (why): Why does the gate use a coverage floor when all tests already pass?**

:::answer Model answer
Passing tests only prove the code they call. A coverage floor forces tests onto code nobody has run, such as error handlers, so a change to the error envelope cannot slip through unnoticed.
:::

**Question 2 (trade-off): Why does the suite call the app with TestClient instead of starting a real server in CI?**

:::answer Model answer
TestClient runs in the same Python process, so it is fast and needs no open ports. The trade-off is that it skips the real server process, which a later ticket covers with a container.
:::

**Question 3 (what you did): Which tests did you write, and what does each check?**

:::answer Model answer
Name each function, the endpoint it calls and the status code or field it asserts. Then name its commit and show the `git blame` line that proves you wrote it. Say what would fail if the validator broke.
:::

**Question 4 (understanding): Why does the CI job need no secrets?**

:::answer Model answer
The tests use fixed sample payloads and the model file in the repository. They never call a real model, a cloud service or a production database. Secrets would make the check fail for pull requests that cannot read them.
:::

**Question 5 (why): Why does a red check alone not stop a merge?**

:::answer Model answer
A red check is only a report. Branch protection names the required checks, and GitHub reports `BLOCKED` until they pass.
:::

```quiz
Q: Which pytest option makes the run exit with code 1 when total coverage is under 60 per cent?
- --cov-report=term-missing
- --cov=.
* --cov-fail-under=60
- --collect-only
WHY: --cov-fail-under sets the floor, so pytest fails even when every test passed. --cov=. measures the test files too, and --collect-only does not run any tests.

Q: Why does the test fixture use `with TestClient(app) as c:`?
* So the app's lifespan runs and the model is loaded before the tests start
- So the tests run in parallel
- So requests are sent over HTTPS
- So pytest skips the test when the server is down
WHY: The lifespan is the startup code. Without the with block the model is never loaded.

Q: What makes GitHub stop a merge after a red test job?
- pytest prints a warning in the log
- The developer closes the PR by hand
- git blame marks the PR as unsafe
* Branch protection requires the test check to pass before merge
WHY: A check that fails is only a report. Only the branch protection rule, which names the check as required, stops the merge button.
```
