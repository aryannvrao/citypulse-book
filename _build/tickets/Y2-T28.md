#### Y2-T28.1 Aggregate the hourly data into daily station means

**Goal.** Produce one file, `daily_station.parquet`, with one row for each station and each IST day. Each row holds the mean PM2.5 for that day and `n_hours`, the number of real hourly readings behind it. Upload the file to `clean/agg/daily_station/`.

**Technique 1: IST dates.** Stored timestamps are in UTC. A reading at 20:00 UTC on 16 November happened at 01:30 IST on 17 November. If you group by the UTC date, that reading lands on the wrong day. So you convert to IST first. The trace below follows one such timestamp.

```trace
TITLE: Turning a UTC time into an IST date
CODE:
from datetime import datetime, timedelta, timezone
IST = timezone(timedelta(hours=5, minutes=30))
moment = datetime.fromisoformat("2026-11-16T20:00:00").replace(tzinfo=timezone.utc)
local = moment.astimezone(IST)
day = local.date().isoformat()
STEPS:
1 :: none yet :: The import brings in the datetime tools.
2 :: IST=UTC+05:30 :: IST is a fixed offset of five and a half hours. India has no daylight saving.
3 :: IST=UTC+05:30; moment=2026-11-16 20:00 UTC :: The text is read as a time and labelled as UTC.
4 :: IST=UTC+05:30; moment=2026-11-16 20:00 UTC; local=2026-11-17 01:30 +05:30 :: The same instant is shown in IST, so the clock moves past midnight.
5 :: local=2026-11-17 01:30 +05:30; day="2026-11-17" :: The date that comes out is 17 November.
5 :: day="2026-11-17" :: Grouping by this value puts the reading on the right day.
```

The fixed offset is enough for this ticket. A more general option is `zoneinfo.ZoneInfo("Asia/Kolkata")`. On Windows it also needs `pip install tzdata`. Either way, the test below checks the midnight case.

Test this idea with a standard-library check. Run it yourself with `python` before you use it:

```python test
from datetime import datetime, timedelta, timezone

IST = timezone(timedelta(hours=5, minutes=30))

def ist_date(utc_text):
    moment = datetime.fromisoformat(utc_text).replace(tzinfo=timezone.utc)
    return moment.astimezone(IST).date().isoformat()

assert ist_date("2026-11-16T20:00:00") == "2026-11-17"
assert ist_date("2026-11-16T18:00:00") == "2026-11-16"
assert ist_date("2026-11-16T00:00:00") == "2026-11-16"
```

Line by line: `IST` is a timezone object for plus five hours thirty minutes. `ist_date` takes text, turns it into a time, labels it as UTC, converts it, and returns the IST date as text. The three `assert` lines check the midnight crossing and two normal cases. A failed `assert` stops the script with an `AssertionError`. No output means every check passed.

**Stage 3: group and count.**

`groupby` makes one group per station and day. `.agg` builds two columns. The name `pm25_mean=("pm25", "mean")` means "take the pm25 column and average it, and call the result `pm25_mean`". In pandas, `count` counts only values that are not missing, so `n_hours` shows how many real readings sit behind each mean. `reset_index` turns the group labels back into ordinary columns. #### Y2-T28.2 Create the read-only dashboard identity

**Goal.** Make an IAM user named `citypulse-dashboard-ro` that can read `clean/agg/` and nothing else. Keep its keys out of Git.

**Technique: least privilege.** An IAM policy is a JSON document with statements. Each statement has an `Effect` (`Allow` or `Deny`), an `Action` (the S3 operation), and a `Resource` (the bucket or files it applies to). Anything not allowed is refused. Name only the actions you need. Never write `s3:*`, because that gives every write action too.

Here is the first statement, with placeholders. Write the second one yourself. It must allow `s3:ListBucket` on the bucket itself, limited to the `clean/agg/` prefix with a `Condition`. Without that statement, `aws s3 ls` on the prefix fails.

```json
{
  "Effect": "Allow",
  "Action": ["s3:GetObject"],
  "Resource": "arn:aws:s3:::<bucket>/clean/agg/*"
}
```

#### Y2-T28.4 Build the dashboard in stages

**Goal.** Write `app/dashboard.py` so that it loads the daily table, shows a date filter, shows three KPIs and two imported charts, and shows a detail table. Build it stage by stage. Run `streamlit run app/dashboard.py` after each stage and check the page.

**Technique: how Streamlit reruns.** Streamlit runs the whole script from the top every time a control changes. Caching stops the slow S3 read from repeating each time. Section Y2-T28.4 relies on the cache, so keep the S3 read inside a function.

**Stage 1: a page that renders.**

```python
import streamlit as st

st.set_page_config(page_title="CityPulse air quality", layout="centered")
st.title("CityPulse air quality")
```

`st.set_page_config` must be the first Streamlit call in the script. It sets the browser tab title and the layout. `layout="centered"` keeps the content readable on a narrow phone screen. `st.title` draws the heading. Expect a page with the heading and no errors.

**Stage 2: the cached loader.**

```python
import pandas as pd
import streamlit as st

@st.cache_data(ttl=600)
def load_daily():
    aws = st.secrets["aws"]
    return pd.read_parquet(
        f"s3://{aws['bucket']}/clean/agg/daily_station/daily_station.parquet",
        storage_options={"key": aws["access_key_id"], "secret": aws["secret_access_key"]},
    )

daily = load_daily()
st.write(f"{len(daily)} rows loaded")
```

`st.secrets["aws"]` reads the `[aws]` section of your local `secrets.toml`. Your key names must match the file exactly. `storage_options` passes the keys to s3fs, the helper that lets pandas read `s3://` paths. `@st.cache_data(ttl=600)` keeps the returned table for ten minutes. The first run is slow. Refresh the page and the row count appears at once. If it takes a long time every time, the decorator is missing. Remember that the cache is only the table, so the secrets must never be returned or printed.

The daily table is per station. Your city-wide numbers need a per-day city value. A simple choice is the mean of the station means for each day. Choosing how to weight the stations is one of the squad's decisions, so decide it together and write it in the README.

**Stage 3: a date filter with a guard.** Add these lines after `daily = load_daily()`. The guard handles an incomplete selection.

```python
from datetime import timedelta
import streamlit as st

daily["day"] = pd.to_datetime(daily["day_ist"]).dt.date
latest = daily["day"].max()
picked = st.date_input(
    "Date range",
    value=(max(daily["day"].min(), latest - timedelta(days=6)), latest),
    min_value=daily["day"].min(),
    max_value=latest,
)

if not isinstance(picked, tuple) or len(picked) != 2:
    st.info("Pick a start date and an end date to see the numbers.")
    st.stop()
start, end = picked
```

The `max(...)` in the default keeps the start date inside the data, so the page still opens if the data covers fewer than seven days. `st.date_input` with a pair of default dates returns a tuple. While the user has picked only one date, the tuple has one item. The `if` catches that case, shows a plain information box, and `st.stop()` ends the script run quietly. Nothing crashes and no `Traceback` appears. Test it: in the browser, click a start date and do not click an end date. Expect the blue information box. Then pick both dates and check that the box disappears.

**Stage 4: filter the rows and compute the previous period.** The comparison in each metric uses the same number of days just before the selected range. The rule is small, so test it first with the standard-library check below.

```python test
from datetime import date, timedelta

def previous_window(start, end):
    days = (end - start).days + 1
    return start - timedelta(days=days), start - timedelta(days=1)

prev_start, prev_end = previous_window(date(2026, 11, 10), date(2026, 11, 16))
assert (prev_start, prev_end) == (date(2026, 11, 3), date(2026, 11, 9))
assert previous_window(date(2026, 11, 10), date(2026, 11, 10)) == (date(2026, 11, 9), date(2026, 11, 9))
```

`(end - start).days + 1` counts the days in the range, with both ends included. Subtracting that count from the start gives the first day of the previous block. The first assert checks a seven-day range. The second checks a one-day range. Copy this idea into your dashboard as your own function, and use your squad's names.

Then filter the table and compute your KPIs. This pattern shows the shape. Replace the calculation with your squad's KPI formulas from T28.3.

```python
view = daily[(daily["day"] >= start) & (daily["day"] <= end)]
prev_start, prev_end = previous_window(start, end)
before = daily[(daily["day"] >= prev_start) & (daily["day"] <= prev_end)]
```

`view` keeps the rows inside the selected range. The comparison `>=` and `<=` includes both ends. Never change `daily` in place. Create a new variable instead, so the cached table stays intact.

The arguments are the label, the value, the change from the previous period, and the colour rule. `delta_color="inverse"` makes a rise red, which is correct for pollution. ### Defend it in the viva

**Q1. Why does the dashboard read the daily aggregate, and not the hourly table?**

:::answer Model answer
The daily table has one row per station per day, so the file is much smaller and the page loads inside the five-second limit on a phone. The KPIs are defined per day, so the daily table already has the level of detail they need. Reading the hourly table would make every click slower for no gain in what the officer sees. The trade-off is that an hourly spike is averaged into its day, so the dashboard cannot show it. That is acceptable here because the advisory decision is made per day.
:::

**Q2. What is the trade-off in setting the cache time to 600 seconds?**

:::answer Model answer
A longer time saves more S3 reads and makes the page faster for everyone. The cost is freshness: the dashboard can show data up to ten minutes old. A shorter time keeps data fresher but reads S3 more often. For a daily advisory, ten minutes is a sensible balance, and you should say so out loud. The choice is a decision you can explain, not a fact to memorise.
:::

**Q3. Which part of this ticket did you personally build, and how did you test it?**

:::answer Model answer
A strong answer names one subtask, the commits you made for it, and the test you ran for each stage. It also points to the exact output you pasted into the pull request. It does not claim work that a teammate did, and it does not say you did something you did not. Practise by naming your subtask, your commit messages in order, and the test case that proves your part.
:::

**Q4. Why does the dashboard use a read-only identity, and why must its keys stay out of Git?**

:::answer Model answer
The principle is least privilege. A dashboard only needs to read, so if its keys leak, the damage is limited to reading the aggregate files. If it used the pipeline keys, a leak could overwrite the data. Keys in Git are copied to every clone and stay in the history even after deletion, so rotation would be needed. The `AccessDenied` test and gitleaks check both parts of this.
:::

**Q5. How do you know the three KPIs really change when the date range changes?**

:::answer Model answer
Each KPI is computed from the filtered table `view`, not from the full daily table, so a new range gives new inputs. The comparison uses the previous block of equal length, which the `previous_window` rule computes. The trainer's TC5 check, and your own run in Y2-T28.5, show the values changing. If the numbers stayed the same, the code would be reading the unfiltered table.
:::
