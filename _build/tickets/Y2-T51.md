### The ticket in plain words

Healthcare.gov, the United States government health insurance website, failed badly when it was switched on. The description gives the reason: its parts were built separately and joined only at the end, so the faults appeared when there was no time left to fix them.

Your squad's mini-project has the same risk. Its data pipeline, its trained model and its web API have each worked on their own, but nobody has yet run all three together. This ticket is the first time they must work as one system, and it must happen a week before the deadline, not on it.

The morning goal is a single command that runs the whole chain: ingest the raw data, clean it, train the model, serve predictions through an API and show them in a small web page, the UI. It must work on a clean laptop, a copy of the project with none of your leftover files or settings.

The afternoon goal is personal. Your CRI 1 report on the LMS names your weakest dimension. You complete gap-bridge items that target it and submit a self-assessment. This guide does not expand CRI, so check the LMS for its meaning.

### How your trainer checks it

Your trainer will run four test cases, and will check five acceptance criteria. Each criterion is a sentence that someone can verify. The table below shows which test covers which criterion.

| Acceptance criterion | How it is checked |
|---|---|
| 1. Clean clone, `docker compose up --build`, both services healthy within 3 minutes | TC1 |
| 2. `curl -X POST` to `/predict` returns HTTP 200 and a number | TC2 |
| 3. The UI shows the prediction for a sample input | Open the UI in a browser and submit `tests/sample.json` contents (see below) |
| 4. README has 'How to run', 'What it does' and 'Known limits' with a number | Read the README on a clean clone |
| 5. Gap-bridge set at 80% or more and self-assessment submitted | TC4 |

**TC1: one-command start on the spare laptop.**

Steps: `git clone repo /tmp/t51 && cd /tmp/t51 && docker compose up --build -d && docker compose ps`

- `git clone repo /tmp/t51` copies the squad repository into `/tmp/t51`. Replace `repo` with the squad's GitHub address. Clone copies only committed files, so an uncommitted model is missing here.
- `&&` runs the next command only if the previous one succeeded.
- `docker compose up --build -d` builds each image, then starts every service in the background.
- `docker compose ps` lists each service with its state. The STATUS column is what the trainer reads.

Passing output:

```term
$ docker compose ps
NAME          IMAGE        SERVICE   STATUS                    PORTS
t51-api-1     t51-api      api       Up 3 minutes (healthy)    0.0.0.0:8000->8000/tcp
t51-ui-1      t51-ui       ui        Up 3 minutes
```

The API shows `(healthy)`, and the UI shows `Up`, which the ticket accepts as running. Both must appear within 180 seconds of the start.

Failing output and its usual cause. `(unhealthy)` means the health check keeps failing, often a model that did not load or a wrong path. `Exited (1)` means a crash at startup, so read `docker compose logs api`. `port is already allocated` means another program or an old container holds port 8000. Run `docker compose down`.

**TC2: health and prediction.**

Steps: `curl -s localhost:8000/health` and `curl -s -X POST localhost:8000/predict -H 'Content-Type: application/json' -d @tests/sample.json`

- `curl` sends an HTTP request from the terminal.
- `-s` hides the progress meter and error messages too, so drop it when debugging.
- `localhost:8000` means this machine, port 8000.
- `-X POST` sends a POST request. `-H` sets a header, here saying the body is JSON.
- `-d @tests/sample.json` sends the file's contents as the body. The `@` means "read from this file".

Passing output for the first command is exactly `{"status":"ok","model_loaded":true}`. For the second, the output is JSON that contains a numeric prediction, with the field name your API documents.

Failing output. `curl: (7) Failed to connect` means nothing listens on port 8000. `"model_loaded":false` means the model file was not found at startup. A 422 with a `detail` list means the request fields differ from the training features.

**TC3: `make smoke`.**

Steps: `make smoke`, with expected exit 0 and the text `SMOKE OK`.

- `make smoke` runs the `smoke` task in the `Makefile`. Its commands run in order, and the task succeeds only if every one succeeds.
- `echo $?` prints the exit code of the last command. 0 means success.

Passing output:

```term
$ make smoke
SMOKE OK
$ echo $?
0
```

Failing output. `make: *** No rule to make target 'smoke'.  Stop.` means the Makefile has no `smoke` task, or the file is named differently. `missing separator` means a recipe line is indented with spaces instead of a tab. `make: *** [Makefile:N: smoke] Error 1` means a command inside the recipe failed. The line number N tells you which one, so run that command by hand.

**TC4: gap-bridge report.**

There is no command. The trainer filters the platform's gap-bridge report by squad and checks that your completion is at least 80% and the self-assessment column is filled.

#### Y2-T51.2: API loads the model and answers health

**Goal.** Start the API with the model loaded from `MODEL_PATH`, make `/health` report whether the model is loaded, and make `/predict` accept only the fields the model was trained on.

**Technique first: a FastAPI endpoint.** Try this in a scratch folder, not the repository. It is a different problem.

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class Item(BaseModel):
    name: str
    count: int

@app.get("/ping")
def ping():
    return {"status": "ok"}

@app.post("/double")
def double(item: Item):
    return {"name": item.name, "double": item.count * 2}
```

The class lists the fields and their types. Each `@app` line attaches a function to an address, and FastAPI checks every request body against the class. Start it with `uvicorn main:app --port 8000` from the folder that holds the file. Then in a second terminal:

```term
$ curl -s -X POST localhost:8000/double -H 'Content-Type: application/json' -d '{"name": "bus", "count": 4}'
{"name":"bus","double":8}
```

A text value such as `"four"` for `count` would be rejected with a 422 and a `detail` list. That is the behaviour `/predict` relies on.

**Stage 1: load the model once, at startup.** Loading a model takes time, so do it once, not on every request. Open `api/main.py` and add this block above the route definitions. It needs `pip install joblib` in your environment if it is not there.

```python
import os
from contextlib import asynccontextmanager
import joblib
from fastapi import FastAPI

state = {}

@asynccontextmanager
async def lifespan(app):
    path = os.environ.get("MODEL_PATH", "models/model.joblib")
    state["model"] = joblib.load(path)
    yield
    state.clear()

app = FastAPI(lifespan=lifespan)
```

Line by line: `os.environ.get` reads `MODEL_PATH` and falls back to the default if it is unset. Code before `yield` runs at startup, and `joblib.load` reads the model file once. `state` holds the model for the routes.

Test this stage. From the repository root, run this in Git Bash:

```bash
MODEL_PATH=models/model.joblib uvicorn api.main:app --port 8000
```

`MODEL_PATH=...` sets the variable for that one command. `api.main:app` means the object `app` in `api/main.py`. Look for `Application startup complete`. A `FileNotFoundError` means the path is wrong for the folder you started in.

**Stage 2: report the model in health.** Add a route below the lifespan block:

```python
@app.get("/health")
def health():
    return {"status": "ok", "model_loaded": "model" in state}
```

`"model" in state` is `True` when the model is loaded, and FastAPI turns that into JSON `true`.

Test it. With the server still running, run `curl -s localhost:8000/health`. The output must be `{"status":"ok","model_loaded":true}`.

**Stage 3: match the predict schema to training.** Open `src/train.py` and find the feature columns the model is trained on. Search for the list of columns passed to the model, and for the line that drops the target column.

```bash
grep -n "drop\|features" src/train.py
```

`grep -n` prints each matching line with its number. The list you find is the source of truth. Write a Pydantic class with one field for each feature, with the same name and a matching type. Do not copy field names from this guide, because they belong to your squad's data.

Then write the route:

```python
@app.post("/predict")
def predict(req: PredictRequest):
    row = [[getattr(req, f) for f in FEATURE_NAMES]]
    return {"prediction": float(state["model"].predict(row)[0])}
```

Line by line: `getattr(req, f)` reads each field by name, in training order. `predict` expects a table of rows, so the outer brackets matter. `float(...)` turns the numpy result into a number JSON can write. If the order in `FEATURE_NAMES` differs from training, the predictions are wrong without any error.

Test this stage: `curl -s -X POST localhost:8000/predict -H 'Content-Type: application/json' -d @tests/sample.json`. Once `tests/sample.json` exists (Y2-T51.4), this must return a number. Until then, send a body with every feature filled in.

Commit the stage as you go, using the messages from the table above.

#### Y2-T51.3: Dockerfiles, compose and `make smoke`

**Goal.** Build an image for each service, describe both services in one compose file, make the UI wait for a healthy API, and write `make smoke`.

**Technique first: layer order.** Docker saves each Dockerfile step as a layer, and a changed layer forces every later layer to rebuild. Put slow, rarely changing steps first. This fragment shows the order only.

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
```

Line by line: `FROM` picks a base image with Python 3.11. `WORKDIR` sets the working folder. `COPY requirements.txt` and `RUN pip install` come before your code, so a code edit reuses the installed packages.

Your job is to add the code copy and the start command. The start command is `uvicorn` with the module and variable name from your `api/main.py`, the host `0.0.0.0` so that the port is reachable from outside the container, and the port 8000. Write it yourself, and check each part against your file.

Build it and check the result:

```bash
docker build -f api/Dockerfile -t t51-api .
```

`docker build` creates the image. `-f api/Dockerfile` says which Dockerfile to use. `-t t51-api` names the image. The final `.` is the build context, the folder Docker sends to the builder. Docker can only `COPY` files inside the context. With the context at the repository root, the Dockerfile can copy both `api/` and `models/`. If you used `./api` as the context, `models/` would be outside it and could not be copied. Adjust the `COPY` paths in the fragment above to match the context (for example `api/requirements.txt`).

Trap: if `.dockerignore` excludes `models/`, the image has no model and `model_loaded` is `false`. Decide whether the image carries the model (or whether compose mounts it as a volume), then make the Dockerfile and `.dockerignore` agree.

**Stage 2: health check and wiring in compose.** Compose files are written in YAML. YAML uses spaces for indentation and never tabs. Two spaces per level is the usual choice. Write the `api` service first. It builds from your API folder, publishes port 8000, and runs a health check that calls `/health`:

```yaml
services:
  api:
    build:
      context: .
      dockerfile: api/Dockerfile
    ports:
      - "8000:8000"
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"]
      interval: 5s
      retries: 20
      start_period: 10s
```

Line by line: `build` with `context: .` and `dockerfile:` mirrors the `docker build -f` command above. `ports` maps host port 8000 to container port 8000, host first. The health check runs inside the container, and a failed request counts as a failure. `start_period` protects model loading from counting.

This health check assumes `python` is inside the image, which is true for `python:3.11-slim`. If your base image has no Python, use `curl` only if the image installs it.

Then add the `ui` service yourself, with two things. Pass `API_URL` as `http://api:8000`, because `api` is the service name and Docker resolves it. Add a `depends_on` entry with `condition: service_healthy`, so the UI starts only after the API is healthy. Keep YAML indentation at two spaces, never tabs. The UI needs its own Dockerfile too (acceptance criterion 3): its code must read `API_URL` from the environment, for example with `os.environ["API_URL"]` in Python, and send the sample input to `API_URL` plus `/predict`.

The interval, retries and start period must let the API turn healthy within 180 seconds.

Test this stage: `docker compose config`. This command reads the file, checks it and prints the fully expanded version. If it prints an error with a line number, fix that line first.

**Stage 3: `make smoke`.** A Makefile task is a name followed by a colon, and each command under it is indented with a tab. Here is a toy example for a different project:

```make
hello:
	echo "hello from make"
```

Run `make hello`. Make prints the command, then its output: `hello from make`.

`&&` runs the next command only when the previous one exits with 0. Try `true && echo yes` in Git Bash, and you should see `yes`.

Write the `smoke` task yourself. It must check that the API is healthy, send the sample request, and print `SMOKE OK` only if both succeeded. `curl -f` makes curl exit with an error on any HTTP status of 400 or above, so a bad reply becomes a failed command.

**Test this stage.** Run `docker compose up --build -d`, then `docker compose ps`, then `make smoke`, then `echo $?`. The last line must print `0`.

#### Y2-T51.4: sample data that runs offline

**Goal.** Commit a sample of at least 500 rows in `data/sample/`, and a matching request file `tests/sample.json`, so that the pipeline and the API can run without the internet.

**Technique first: counting lines.** `head -n 501` prints the first 501 lines of a file, and `wc -l` counts lines. A CSV has one header line, so 501 lines means 500 data rows.

```bash
mkdir -p data/sample
head -n 501 data/raw/<your-source>.csv > data/sample/readings.csv
wc -l data/sample/readings.csv
```

Replace `<your-source>.csv` with the file your squad's ingest step writes. The `>` sends the output into a new file instead of the screen. `wc -l` should print `501 data/sample/readings.csv`.

Trap: the first 500 rows may all come from one station or day. If the data is ordered, take a random sample with a fixed seed instead. In Python:

```python
import pandas as pd
df = pd.read_csv("data/raw/<your-source>.csv")
df.sample(n=500, random_state=42).to_csv("data/sample/readings.csv", index=False)
```

Line by line: `sample(n=500, random_state=42)` picks 500 random rows, and the fixed seed makes the pick repeatable. `index=False` stops pandas writing a numbered first column. Expect 501 lines from `wc -l`.

**Stage 2: the request file.** The request body for `/predict` must match your Pydantic schema from Y2-T51.2. Build it from one row, without the target column. This snippet is for a Python file in a scratch folder, and it uses the target column name from `config.yaml` or `src/train.py`:

```python
import json
import pandas as pd
df = pd.read_csv("data/sample/readings.csv")
row = df.drop(columns=["<target>"]).head(1)
record = json.loads(row.to_json(orient="records"))[0]
json.dump(record, open("tests/sample.json", "w"), indent=2)
```

Line by line: `drop` removes the target, because the request must not contain the answer. The `to_json` and `json.loads` pair turns numpy values into plain numbers that `json.dump` can write.

Check the file with `python -m json.tool tests/sample.json`. It prints the formatted JSON, or an error with a line number.

**Test this stage offline.** Turn off Wi-Fi, then run your ingest, clean and train steps on the sample. Before you do, find out whether any step tries to reach the internet: `grep -rn "http" src/`. Any URL you find must be removed or switched to the local file.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| API shows `unhealthy` and never becomes healthy | The health check URL does not match the app, or the model failed to load | Run `docker compose logs api`, then `curl -i localhost:8000/health` |
| `/health` returns `model_loaded: false` in the container | `.dockerignore` excludes the `models/` folder, or `MODEL_PATH` points at a path that is not in the image | Check the Dockerfile `COPY` line, the `.dockerignore` file and the `MODEL_PATH` value |

| `/predict` returns 422 | Field names or types in the request do not match the Pydantic schema | Compare the JSON keys with the feature list in `src/train.py`, and fix the order and names |
| `make smoke` says `missing separator` | A recipe line is indented with spaces, not a tab | Replace the leading spaces with a single tab character |
| Clean clone works on your laptop but not for the mentor | A file was never committed, or it was excluded by `.gitignore` | Run `git status` and `git ls-files` in the clean clone, and commit the missing file |
| `docker compose up` fails with `port is already allocated` | Another container or program is using port 8000 | Run `docker compose down`, then `docker ps` to find the old container |
| Docker build fails with `COPY failed: file not found in build context` | The build context is `./api` but the Dockerfile copies `models/` or another folder outside it | Use the repository root as context with `-f api/Dockerfile`, and fix the `COPY` paths |

**Question 4: Why does the UI call the API by its service name rather than by localhost?**

:::answer Model answer
Each container has its own localhost, where no API runs. Compose gives each service a DNS name, so the UI reaches the API at `api:8000`.
:::

**Question 5: Why is the model loaded at startup rather than on every request?**

:::answer Model answer
Reading a model from disk is slow, and repeating it on every request wastes time. Loading once at startup lets the health check report `model_loaded` truthfully, and a missing file shows up when the service starts, not when a user first asks.
:::

Q: Which command shows whether each service has reached healthy?
- docker compose down
- docker compose build
- docker build -t api .
* docker compose ps
WHY: docker compose ps lists each service with its STATUS column. docker build only creates an image, and docker compose down stops the stack. Neither reports health.

Q: What character must start each recipe line under a Makefile task?
* A tab character
- Four spaces
- A semicolon
- A hash sign
WHY: make requires a tab at the start of each recipe line. Spaces produce a missing separator error, and a semicolon or hash sign is not a valid start for a recipe.
