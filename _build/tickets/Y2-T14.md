### The ticket in plain words

CityPulse keeps its air-quality readings in a database. The client, a public-health officer, does not want tables. They want answers, such as which hour of the day has the worst PM2.5 reading in each area.

Your squad must choose eight questions that a named person would pay to have answered. For each one you write a **view**, which is a named query stored inside the database. You then publish a README table that gives each answer as one number, with its unit, date range and sample size.

The ticket opens with the Netflix Prize, whose winning method Netflix never ran in full because it cost too much to build. A result is worth nothing unless someone changes a decision, so every question must name the person who decides.

### Words you need

| Term | Plain meaning |
|---|---|
| Database | A file that holds tables and answers questions about them. Here it is SQLite, in one `.db` file. |
| Table, row, column | A grid of records (rows) with named fields (columns). |
| Fact table | The large table of measurements, here `fact_air_quality`. |
| Dimension table | A small lookup table that describes things, such as `dim_location`. |
| Foreign key | A column holding the key of a row in another table, such as `location_id`. |
| JOIN | Combines rows from two tables where a condition matches. |
| LEFT JOIN | A JOIN that keeps every left-hand row, even with no match on the right. |
| CTE | A named intermediate step, written with `WITH`. |
| CASE | An expression that picks a value using `WHEN` tests. Used for bucketing. |
| Bucketing | Sorting numbers into named groups such as "Good" or "Poor". |
| GROUP BY | Makes one output row for each distinct combination of the listed columns. |
| COUNT | An aggregate function that counts rows in each group. |
| NULL | "No value". It equals nothing, not even another NULL. |
| View | A named `SELECT` stored in the database. Querying it runs the stored query again. |
| DROP VIEW IF EXISTS | Deletes a view if it is there, and does nothing otherwise. |
| sqlite_master | SQLite's catalogue table listing every table, index and view. |
| UTC, IST | UTC is the timezone of the stored readings. IST is UTC plus 5 hours 30 minutes. |
| date(), strftime() | SQLite functions that format timestamps. A modifier such as `'+330 minutes'` shifts the time. |
| EXPLAIN QUERY PLAN | Prints how SQLite plans to run a query, without running it. |
| SCAN, SEARCH | A plan step that reads every row (SCAN), or jumps to matching rows through an index (SEARCH). |
| Index | A sorted helper structure that speeds up lookups on one column. |
| Sample size (n) | The number of rows behind an answer. |
| Pull request (PR) | A request to merge your branch, reviewed by a squad-mate first. |

### How your trainer checks it

The six acceptance criteria are:

1. A fresh database, built from `schema.sql` and `load.py`, then `sql/views.sql`, runs with no errors and has exactly 8 views (TC1, TC4).
2. Each view returns at least one row (TC2).
3. At least 3 views contain `JOIN` and at least 2 contain `WITH` (TC3).
4. Every README Insights row gives a number with a unit, a date range and n (TC5).
5. Every hour or day view converts UTC to IST with `+330 minutes` and says so in a comment. The trainer reads it with `sqlite3 /tmp/v.db ".schema v_name"`. SQLite stores only the text from `CREATE VIEW` onwards, so put the IST comment after `CREATE VIEW ... AS`, not above the `DROP` line, or `.schema` will not show it.
6. `git log --author` on `sql/views.sql` shows at least one of your commits.

**TC1: build a fresh database and count the views.**

`rm -f /tmp/v.db; SQLITE_PATH=/tmp/v.db python -m citypulse.load && sqlite3 /tmp/v.db < sql/views.sql && sqlite3 /tmp/v.db "SELECT COUNT(*) FROM sqlite_master WHERE type='view'"`

- `rm -f /tmp/v.db` deletes the old test database. `-f` means no error if it is missing.
- `SQLITE_PATH=/tmp/v.db` sets a variable for the next command only, so the loader writes to the test database.
- `python -m citypulse.load` runs the loader module. `-m` runs a module by name.
- `&&` runs the next command only if the previous one succeeded.
- `sqlite3 /tmp/v.db < sql/views.sql` feeds the file to the shell, one statement at a time.
- The last command counts the views stored in `sqlite_master`.

Passing: no error text, then the line `8`. Failing: `Error: near line 14` is a typo or a missing `;`. `already exists` means a `CREATE VIEW` lacks its `DROP` line. `9` means a helper view is in the file.

**TC2: every view returns at least one row.**

`for v in $(sqlite3 /tmp/v.db "SELECT name FROM sqlite_master WHERE type='view'"); do echo $v; sqlite3 /tmp/v.db "SELECT COUNT(*) FROM $v"; done`

- `for v in ...; do ... done` runs the middle lines once for each view name.
- `$( ... )` runs the inner command and uses its output as the list.
- `echo $v` prints the name, and the next line counts that view's rows.

Passing: eight name-and-count pairs, each count at least 1. Failing: a count of `0`, usually a `WHERE` that removes everything or a join on the wrong key.

**TC3: the view text contains JOIN and WITH.**

`sqlite3 /tmp/v.db "SELECT SUM(sql LIKE '%JOIN%'), SUM(sql LIKE '%WITH %') FROM sqlite_master WHERE type='view'"`

- `sql` holds the text of each `CREATE VIEW` statement.
- `LIKE` matches a pattern, where `%` stands for any characters. Each view gives 1 or 0, and `SUM` adds them up.
- The trailing space in `'%WITH %'` matters, as the trap below explains.

Passing: two numbers separated by `|`, such as `4|2`, with the first at least 3 and the second at least 2. Failing: `4|1` usually means a CTE with `WITH` at the end of a line.

:::trap A CTE that breaks TC3
The test looks for `WITH ` followed by a space. If `WITH` ends a line, the next character is a newline, and the view is not counted. Write `WITH step_name AS (` on one line. `LIKE` ignores case, so avoid the word "with" followed by a space inside your comments, or a view without a CTE may be counted by mistake.
:::

**TC4: the file runs a second time without errors.**

Run `sqlite3 /tmp/v.db < sql/views.sql` again on a database that already has the views. Passing: no output, because a successful `CREATE VIEW` prints nothing. Failing: `already exists`, which means a `CREATE VIEW` has no `DROP VIEW IF EXISTS` above it.

**TC5: the README Insights table is complete.**

The trainer reads the table by hand. Passing: eight rows, each with an exact number, a unit (such as `hours`), a date range and n. Failing: `about 40`, or a row with no n.

**Git check (criterion 6).** `git log --author="Your Name" --oneline -- sql/views.sql`. Passing: at least one line. Failing: no output, usually a different Git name from `git config user.name`.

The animation below shows TC1 passing.

#### Y2-T14.2: Write v_coverage_by_location

The new tool is the **LEFT JOIN**. In this toy example, only location A has readings:

```sql
SELECT l.name, COUNT(f.fact_id) AS n_readings
FROM dim_location AS l
LEFT JOIN fact_air_quality AS f ON f.location_id = l.location_id
GROUP BY l.name;
```

- `FROM dim_location AS l` makes the location table the left side. `AS l` gives it a short name.
- `LEFT JOIN ... ON ...` adds the readings. The `ON` part is the matching rule, here on the integer key.
- Location B has no matches, so its readings are NULL, and `COUNT(f.fact_id)` gives 0. It still appears.

Build the real view in four stages.

1. **Read the columns.** Run `sqlite3 PATH_TO_LAB_DB ".schema fact_air_quality"`, and the same for `dim_location`. Your schema is the authority.
2. **Check the day maths.** Predict the output, then run this scratch query:

```sql
SELECT date(ts_utc, '+330 minutes') AS day_ist, COUNT(*) AS n
FROM fact_air_quality
GROUP BY day_ist
ORDER BY day_ist DESC
LIMIT 5;
```

`date(ts_utc, '+330 minutes')` shifts the UTC time by five and a half hours and keeps the day. If a date is a day out, check the modifier text.

3. **Add the location join.** Use the LEFT JOIN, grouped by location name and day. Check that a location with no readings still appears, with a NULL day and a count of 0.
4. **Wrap it in the file.** Write the header and the view yourself:

```sql
-- Q: <your question, one sentence>
-- Who decides: <the role>
DROP VIEW IF EXISTS v_coverage_by_location;
CREATE VIEW v_coverage_by_location AS
-- IST: ts_utc + 330 minutes (UTC+5:30).
-- your SELECT from stage 3 goes here
```

`DROP VIEW IF EXISTS` removes the old copy, so the file can run again. The IST comment sits inside the view so that `.schema` shows it. Test it with `rm -f /tmp/v.db; SQLITE_PATH=/tmp/v.db python -m citypulse.load && sqlite3 -bail /tmp/v.db < sql/views.sql`. The `-bail` option stops at the first error.

#### Y2-T14.3: Own one view end to end

First, learn CASE bucketing from this trace. The thresholds are fictional and only for the lesson. Your squad chooses its own, and says why in a comment.

```trace
TITLE: Bucketing three readings with CASE
CODE:
SELECT pm2_5,
       CASE WHEN pm2_5 <= 60 THEN 'Good'
            WHEN pm2_5 <= 120 THEN 'Moderate'
            ELSE 'Poor'
       END AS bucket
FROM readings;
STEPS:
1 :: row=none; bucket=none :: The query starts with its column list. Nothing has been read yet.
2 :: pm2_5=35; bucket=none :: The first reading is 35. The first test is pm2_5 <= 60.
2 :: pm2_5=35; bucket='Good' :: 35 is at most 60, so the first WHEN matches.
2 :: pm2_5=90; bucket=none :: The second reading is 90. The first test fails.
3 :: pm2_5=90; bucket='Moderate' :: 90 is at most 120, so the second WHEN matches.
2 :: pm2_5=150; bucket=none :: The third reading is 150. Both earlier tests fail.
4 :: pm2_5=150; bucket='Poor' :: No WHEN matched, so ELSE gives 'Poor'.
5 :: pm2_5=150; bucket='Poor' :: END closes the CASE. The bucket becomes a new column.
6 :: rows=3 :: The query returns one output row per reading.
```

SQL tests the `WHEN` lines in order and stops at the first true one, so put the lowest threshold first.

Next, the CTE. A `WITH` block names an intermediate step, which the outer query then uses as a table:

```sql
WITH buckets AS (
  SELECT location_id, pm2_5,
         CASE WHEN pm2_5 <= 60 THEN 'Good' ELSE 'Not good' END AS band
  FROM fact_air_quality
  WHERE pm2_5 IS NOT NULL
)
SELECT band, COUNT(*) AS n
FROM buckets
GROUP BY band;
```

`WITH buckets AS (` names the step. It adds a band with CASE and skips missing readings with `IS NOT NULL`. The outer query counts each band.

Write your view in this order: a scratch `SELECT` with `LIMIT 10`; a written prediction of the row count; a run, with one location and one day checked by hand; then the header, `DROP VIEW IF EXISTS`, `CREATE VIEW` and your query. The skeleton shows where each part goes. You write the lines that matter.

```sql
-- Q: <your question>
-- Who decides: <the role>
DROP VIEW IF EXISTS v_<name>;
CREATE VIEW v_<name> AS
-- IST: ts_utc + 330 minutes (UTC+5:30).
WITH <step_name> AS (
  -- your scratch query, with the IST conversion
)
SELECT <your columns>
FROM <step_name>
JOIN dim_location AS l ON l.location_id = <step_name>.location_id
GROUP BY <your columns>;
```

#### Y2-T14.5: Explain the slowest view

Time each view with `time sqlite3 /tmp/v.db "SELECT COUNT(*) FROM v_<name>"` and pick the slowest. Then ask SQLite for its plan:

```sql
EXPLAIN QUERY PLAN SELECT * FROM v_<name>;
```

The output looks like this:

```text
QUERY PLAN
|--SCAN fact_air_quality
`--SEARCH dim_location USING INTEGER PRIMARY KEY (rowid=?)
```

`SCAN` reads every row. `SEARCH` jumps straight to matching rows. Add an index only when a large table shows a SCAN on a filter that selects few rows, for example `CREATE INDEX IF NOT EXISTS idx_fact_ts ON fact_air_quality (ts_utc);`. An index on `ts_utc` helps only if the view filters on `ts_utc` itself, for example `WHERE ts_utc >= ...`. A filter on `date(ts_utc, '+330 minutes')` cannot use it. Then run the plan again and confirm the SCAN became a SEARCH. Record both plans in the PR.

#### Y2-T14.6: Write the README Insights table

Use one row per question:

| # | Question | View | Answer | Date range (IST) | n |
|---|---|---|---|---|---|
| 1 | `<question>` | `v_<name>` | `<number> <unit>` | `<first day>` to `<last day>` | `<count>` |

Get the range and n from the database:

```sql
SELECT date(MIN(ts_utc), '+330 minutes') AS first_day_ist,
       date(MAX(ts_utc), '+330 minutes') AS last_day_ist,
       COUNT(*) AS n
FROM fact_air_quality;
```

`MIN` and `MAX` find the first and last reading, and `date()` converts them to IST days. If your view has a filter, such as "last 30 days", copy it into this query so the range and n match the view.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| TC1 prints `already exists` on a fresh database | A `CREATE VIEW` has no `DROP VIEW IF EXISTS` above it, or two views share a name. | Put the DROP line above each CREATE. Rename the second view. |
| TC2 shows `0` for one view | The `WHERE` removes every row, or the join key is wrong. | Run the query without the filter, then add conditions back one at a time. |
| TC3 shows `4|1` | `WITH` ends a line, so no space follows it. | Write `WITH name AS (` on one line. |
| A location with no readings is missing | You used an inner JOIN, or filtered the right-hand table in `WHERE`. | Start from the location table with LEFT JOIN, and move right-hand conditions into `ON`. |
| Every count is 1 in a LEFT JOIN | You used `COUNT(*)`, which counts the location row itself. | Count a right-hand column, such as `COUNT(f.fact_id)`. |

### Defend it in the viva

**1. Why write views rather than leave the queries in a notebook?**

:::answer Model answer
A view is stored in the database, so every reader gets the same definition, and the dashboard can call it by name. A notebook query runs only when someone runs it, and an edited copy can give a different number.
:::

**2. What is the trade-off between a view and a summary table?**

:::answer Model answer
A view always reflects current data, but its work repeats on every read, so a slow view on a large table is slow to read. A summary table is fast to read but must be refreshed, and it goes stale if nobody refreshes it. SQLite has no materialised views, so a summary table is the only stored form.
:::

**3. Which view did you write, and how did you check its row count?**

:::answer Model answer
Give the question, the decision it supports, and your checks. For example: "I predicted the row count from the number of locations and days before I ran the scratch query. Then I checked ten rows, and one location and one day by hand against the raw table." Use your own question and checks.
:::

**4. Why state the IST rule explicitly?**

:::answer Model answer
Readings are stored in UTC, but the client's day and hour are in IST, which is UTC plus five and a half hours. Grouping by the UTC hour moves the "worst hour" by five and a half hours, so the answer is wrong even though the arithmetic is right.
:::

**5. When would you add an index to a view, and when would you leave it alone?**

:::answer Model answer
I add an index only when the plan shows a full SCAN on a large table with a selective filter. Otherwise it adds write cost and no benefit.
:::

### Check yourself

```quiz
Q: The trainer runs views.sql a second time on a database that already has the views. What must the file contain for that run to produce no errors?
- A CREATE VIEW statement for each view, with no other lines
* A DROP VIEW IF EXISTS line directly above each CREATE VIEW
- A SELECT at the top that counts the views
- A semicolon at the end of every comment line
WHY: DROP VIEW IF EXISTS removes an old copy and does nothing if the view is missing, so the CREATE VIEW that follows always succeeds. Without it, the second run fails with "already exists".

Q: A coverage view must list every location, including ones with no readings. Which pair of choices gives that result?
- An inner JOIN, and COUNT(*)
* A LEFT JOIN from the location table, and COUNT of a column from the readings table
- A CROSS JOIN, and a WHERE filter on the readings table
- A UNION of the two tables, and SUM of pm2_5
WHY: A LEFT JOIN keeps every location even when nothing matches, and counting a right-hand column gives 0 for those locations. COUNT(*) would count the location row itself and show 1, which is wrong.

Q: EXPLAIN QUERY PLAN shows SCAN fact_air_quality for a view that filters one location and a short date range on a table with millions of rows. What is the sensible next step?
- Leave it alone, because SCAN is always fine
- Delete the view and use a summary table instead
- Remove the LEFT JOIN, because it causes every SCAN
* Consider an index on the filter column, then run EXPLAIN QUERY PLAN again to confirm the SCAN becomes a SEARCH
WHY: An index on the filtered column lets SQLite search instead of reading every row, and running the plan again is the proof. Ignoring the SCAN or deleting the view skips the evidence, and removing the LEFT JOIN would change the answer.
```
