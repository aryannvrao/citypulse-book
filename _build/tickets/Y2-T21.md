### The ticket in plain words

Health officers want an alert when air stays poor for a while, not just in one hour. The measure is PM2.5, which means fine particles in the air that can reach the lungs. The alert looks at a **rolling window** of six hours. A rolling window is the group of the latest six readings. Each new hour adds a reading and pushes out the oldest one. For every window you need two numbers: the average and the maximum.

The slow way adds up all six readings again every hour. Most of those readings were already added an hour earlier, so the work repeats itself. The faster way keeps a **running sum**, a total that goes up by the new reading and down by the reading that left. For the maximum you use a **deque** (a double-ended queue, a list that is quick to add and remove at both ends). The deque keeps only the readings that could still be the maximum. Every reading enters and leaves once, so the work grows in a straight line with the number of readings. That is the O(n) in the ticket.

A fast answer is useless if it is wrong. The ticket therefore asks you to check your Python against a **SQL window view** from Y2-T15, a saved database query that computes values over neighbouring rows. The two must agree to two decimal places. Checking a new method against a trusted reference is what a data engineer does before a number reaches a dashboard.

The day also has six DSA-2 problems (DSA means data structures and algorithms), five homework problems on two pointers, and a pair mock interview, where you take turns as candidate and interviewer. Asking clarifying questions and giving hints are skills employers hire for, so they are marked too.

**TC4: the viva question.**

The trainer asks: "Why does each index enter and leave the deque at most once?"

A passing answer says that each index is pushed once and popped at most once, so the total number of pops is at most n. Because one step can pop many items, the cost is O(n) amortised, not O(1) per step. A failing answer describes a loop inside a loop without checking whether the inner loop's total is bounded. That is the trap in the chapter: one expensive step does not make the algorithm O(n²).

#### Stage 3: the running sum for the average (Y2-T21.4)

**Goal.** An average for each row that matches the SQL `avg6`.

**The technique.** Start with the first values. Each later step adds the new value and takes away the value that just left. The window never has to be rebuilt, so each value is handled twice in total. The divisor is the number of values in the window now, which is `min(i + 1, k)`.

**Step 3a. Write the loop with blanks.** Put this in `rolling_window.py` below the reader, and fill in each blank:

```python
total = 0.0
averages = []
for i, v in enumerate(values):
    total += v
    if i >= k:
        total -= ____          # hint: the value k positions back, at index i - k
    averages.append(total / ____)   # hint: min(i + 1, k)
```

- `enumerate(values)` gives the position `i` and the value `v` at each step.
- `total += v` adds the entering value.
- `if i >= k:` is true once the window is full, so there is a value to remove.
- The blank in the subtraction is the value that just left the window.
- The blank in the division is the number of values in the window now.

**Step 3b. Test the idea before you trust it.** This block checks the running totals on the ticket's example. It is standard library only, so it runs on its own.

```python test
values = [4, 2, 12, 3, 8, 1]
k = 3
running = []
total = 0
for i, v in enumerate(values):
    total += v
    if i >= k:
        total -= values[i - k]
    running.append(total)
assert running == [4, 6, 18, 17, 23, 12]
# each total must equal the sum of the last min(i + 1, k) values
expected = [sum(values[max(0, i - k + 1):i + 1]) for i in range(len(values))]
assert running == expected
```

Line by line, the first assert checks the running totals by hand. The second builds each window the slow way, with a slice and `sum`, and checks the fast version against it. Keep this habit. A slow, obvious version in a test is the cheapest proof that the fast version is right.

Expected: the block runs with no output. Any error means the running total is wrong.

#### Stage 4: the monotonic deque for the maximum (Y2-T21.4)

**Goal.** The maximum of each window in O(n), with the same partial windows.

**The technique.** The deque stores indexes, not values, and its values decrease from front to back. A new value removes every smaller value from the back, because those can never again be the maximum. The front index is the answer. When the front index leaves the window, remove it. An index is added once and removed at most once.

Here is the trace for `values = [2, 5, 1, 4]` with `k = 2`. It is a different list from the ticket's, so you can follow it without copying the answer.

```trace
TITLE: Monotonic deque on [2, 5, 1, 4] with k=2
CODE:
dq = deque()
out = []
for i, v in enumerate(values):
    while dq and values[dq[-1]] <= v:
        dq.pop()
    dq.append(i)
    if dq[0] <= i - k:
        dq.popleft()
    out.append(values[dq[0]])
STEPS:
1 :: dq=[]; out=[] :: Start with an empty deque of indexes and an empty output list.
3 :: i=0; v=2; dq=[]; out=[] :: The first value is 2, at index 0.
6 :: i=0; v=2; dq=[0]; out=[] :: The deque is empty, so index 0 joins the back.
9 :: i=0; v=2; dq=[0]; out=[2] :: With one value so far, the front gives 2.
3 :: i=1; v=5; dq=[0]; out=[2] :: The next value is 5, at index 1.
5 :: i=1; v=5; dq=[]; out=[2] :: The back value 2 is no bigger than 5, so index 0 is popped.
6 :: i=1; v=5; dq=[1]; out=[2] :: Index 1 joins the back.
9 :: i=1; v=5; dq=[1]; out=[2,5] :: The front is index 1, so the maximum is 5.
6 :: i=2; v=1; dq=[1,2]; out=[2,5] :: 5 is bigger than 1, so nothing is popped and index 2 joins the back.
9 :: i=2; v=1; dq=[1,2]; out=[2,5,5] :: Index 1 is still inside the window of two values, so the output is 5.
5 :: i=3; v=4; dq=[1]; out=[2,5,5] :: The back value 1 is no bigger than 4, so index 2 is popped.
6 :: i=3; v=4; dq=[1,3]; out=[2,5,5] :: Index 3 joins the back.
8 :: i=3; v=4; dq=[3]; out=[2,5,5] :: Index 1 has left the window, so it is removed from the front.
9 :: i=3; v=4; dq=[3]; out=[2,5,5,4] :: The maximum of the last two values, 1 and 4, is 4.
```

Read the `dq` column as the important part. The front is always the answer. Note that the output includes the partial windows at the start, which matches the SQL view.

**Homework: two pointers.** Two pointers means two positions move through a list, usually from opposite ends, so you avoid a nested loop. Here is the idea on a small sorted list. Look for a pair that sums to 8 in `[1, 3, 5, 8]`.

- Start with the left pointer on 1 and the right pointer on 8. The sum is 9, which is too big, so move the right pointer left, to 5.
- The sum of 1 and 5 is 6, which is too small, so move the left pointer right, to 3.
- The sum of 3 and 5 is 8. The pair is found.

Each pointer moves forward at most n steps, so the whole search is O(n) time with O(1) extra space. For the gate, be ready to show one of your five homework solutions, and to say that complexity in one sentence.

### Defend it in the viva

**Q1. Why is the running-sum average O(n) when the naive method is O(n·k)?**

:::answer Model answer
The naive method adds all k values again for every window, so the work is about n times k. The running sum adds the entering value and subtracts the leaving value, so each value is handled a fixed number of times in total. The work grows with n, not with n times k. The reasoning is that the window overlaps almost entirely with the one before it, so reusing the total avoids repeating the work.
:::

**Q2. What is the trade-off between the monotonic deque and a heap for the rolling maximum?**

:::answer Model answer
A heap can also find a window maximum, at O(n log n) in the worst case with lazy deletion (old entries stay in the heap until they reach the top), and it is often easier to write. The deque is O(n) overall and needs O(k) extra space, but you must store indexes and handle expiry correctly. The trade-off is speed and a tighter bound against code that is easier to get wrong. For a stream that must run quickly on many values, the deque is the better fit. For a quick prototype, a heap can be fine.
:::

**Q3. Which function did you write, and how did you show it matched the SQL export?**

:::answer Model answer
Name the function and the file you wrote, the test file you added, and the commit where you added each one. Then state the exact command you ran, the summary line it printed and the exit code. Say which bug you fixed first, if any, and what caused it. Only claim work that the commit history shows. The reviewer will check the commits, so your answer should match them.
:::

**Q4. Why does each index enter and leave the deque at most once, and why is that O(n) overall?**

:::answer Model answer
Each index is pushed to the back once, and it is removed at most once, either from the back when a bigger value arrives or from the front when it leaves the window. So the total number of pops cannot exceed the number of pushes, which is n. One step can pop many items, so that step is expensive. But the total over all steps is at most about 2n, so the cost per step is constant on average. That is the amortised O(n) bound.
:::

**Q5. Your six rows span more than six hours. Why does that happen, and what should you write in the note?**

:::answer Model answer
The window is defined by rows, not by time. If an hour is missing from the feed, six rows cover more than six hours. The note should state that the window is six rows, give the gap rule the squad uses, and say that the SQL view and the Python both use rows, so they agree. Naming the gap is better than hiding it, because the health officers rely on the alert time.
:::
