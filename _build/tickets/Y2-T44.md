### The ticket in plain words

Right now CityPulse images are built by hand, on whichever laptop happens to be free. Nobody can prove which code is inside a given image. This ticket replaces that habit with one automatic pipeline. A pipeline is a set of steps that a machine runs for you every time the code changes.

The pipeline runs in three stages, in order. First it checks the code style (lint). Then it runs the tests. Only if both pass does it build the container image, which is a packaged copy of the app, and push it to a registry, which is a storage shelf for images. The image is labelled with the git commit SHA, the unique code name of the exact code it was built from.

Why does this matter before cloud deployment? The team must know that what goes live is exactly what was tested. The ticket names the Knight Capital failure of 2012, where a trading firm's new code reached only some of its servers and the old code kept running on the rest. Deploying one SHA everywhere prevents that kind of mismatch.

The pipeline also logs in to the registry with a temporary token that GitHub creates for each run. No password is ever typed into a file that Git stores.

When you finish, the main branch has a green run, the registry holds an image tagged with the commit SHA, the health endpoint reports that SHA, and the README tells anyone how to pull and run it.

### How your trainer checks it

The trainer checks six acceptance criteria and runs four test cases. Read each one here, then run it yourself in the section "Prove it before review".

Acceptance criteria, and where each is proved:

- A merge to `main` runs lint, test and build-push in that order, and an image tagged with the full SHA appears in the registry within 10 minutes. Proved by TC1 and TC2. Check the time yourself: the run's total duration, shown on its page in the Actions tab, must be under 10 minutes.
- A pull request run skips build-push. Proved by TC3.
- A failing test stops build-push. You prove it on your own branch, not on `main`, by making one test fail and watching build-push not start. Then revert the change.

#### TC1: the latest main run is green and has three jobs

Run this on your laptop. The steps are:

`gh run list --branch main --limit 1 --json conclusion,headSha`, then `gh run view <id> --json jobs --jq '.jobs[].name'`.

The parts:

- `gh run list` lists recent workflow runs.
- `--branch main` keeps only runs on `main`.
- `--limit 1` keeps only the newest.
- `--json conclusion,headSha` prints those two fields as JSON. The second command also needs the run id, so add `databaseId` to the fields: `--json databaseId,conclusion,headSha`. The trainer's version leaves it out, and your version adds one field.
- `gh run view <id>` shows one run. `<id>` is the `databaseId`.
- `--json jobs` includes the list of jobs.
- `--jq '.jobs[].name'` is a jq filter. `.jobs[]` loops over the jobs, and `.name` prints each name on its own line.

Passing output looks like this. The values here are examples, and yours will differ:

```term
$ gh run list --branch main --limit 1 --json databaseId,conclusion,headSha
[{"conclusion":"success","databaseId":12345678901,"headSha":"4b1e9d0c7a2f83e6b59d1a0c4f7e2b9d3a6c1f58"}]
$ gh run view 12345678901 --json jobs --jq '.jobs[].name'
lint
test
build-push
```

Passing means `conclusion` is `success` and the three names appear. A failing run has `"conclusion":"failure"`. Open the run in the browser, find the red job, and read its first error. The usual cause is a failing test or lint error. If `conclusion` is `null`, the run is still going, so wait. If a job name is missing, check that the name in `ci.yml` is spelled exactly `build-push`, because `build_push` is a different name.

#### TC2: the image runs and reports its SHA

Run this on your laptop, using the `headSha` from TC1 in place of `<headSha>`:

`docker pull ghcr.io/org/citypulse-squadnn:<headSha> && docker run -d -p 8000:8000 --env-file .env.example ghcr.io/org/citypulse-squadnn:<headSha> && curl -s localhost:8000/v1/health`

The parts:

- `docker pull` downloads an image from the registry. `ghcr.io` is the registry host. `org` is your GitHub organisation. `citypulse-squadnn` is the image name, with `nn` replaced by your squad number. The part after the colon is the tag, which is the full SHA.
- `&&` runs the next command only if the previous one succeeded.
- `docker run -d` starts the container in the background.
- `-p 8000:8000` connects port 8000 on your laptop to port 8000 inside the container.
- `--env-file .env.example` loads `NAME=value` lines from that file. It must contain example values only, never real secrets.
- `curl -s localhost:8000/v1/health` fetches the health endpoint without a progress meter.

Passing output, where the container ID is an example:

```term
$ docker run -d -p 8000:8000 --env-file .env.example ghcr.io/org/citypulse-squadnn:4b1e9d0c7a2f83e6b59d1a0c4f7e2b9d3a6c1f58
7c2f9e4b1a0d
$ curl -s localhost:8000/v1/health
{"status":"ok","git_sha":"4b1e9d0c7a2f83e6b59d1a0c4f7e2b9d3a6c1f58"}
```

Passing means `git_sha` equals the `headSha`. Failing outputs and causes:

- `manifest unknown` means no image has that tag. Either the SHA is wrong or build-push was skipped on that commit.
- `denied` means your account cannot read the package. Check the package's visibility and access settings on GitHub, and that you have run `docker login ghcr.io` for a private package.
- `port is already allocated` means an old container still uses port 8000. Run `docker ps`, then `docker stop <container-id>`.
- `Failed to connect` from curl means the container stopped or the app is not listening. Run `docker logs <container-id>` and read the last lines.
- `"git_sha":"unknown"` means the build argument did not reach the runtime stage. See the step for subtask 44.4.

Stop the container when you finish with `docker stop <container-id>`.

#### TC3: a pull request run skips build-push

Run this on your laptop:

`gh run list --event pull_request --limit 1`, then `gh run view <id> --json jobs --jq '.jobs[] | select(.name=="build-push") | .conclusion'`.

The parts:

- `--event pull_request` keeps only runs started by a pull request.
- `.jobs[]` loops over the jobs. `select(.name=="build-push")` keeps only the job named build-push. `.conclusion` prints its result.

Passing output is the single word `skipped`. Failing output is `success`, which means the `if:` condition is missing or wrong. A `cancelled` result can mean a newer push cancelled the run, because of the concurrency rule. Push an empty commit to the branch and check again.

#### TC4: no credentials in the workflow files

Run this from the repository root:

`grep -rnE '(ghp_|github_pat_|AKIA|password:)' .github/`

The parts:

- `grep` searches text for a pattern.
- `-r` searches every file in the folder, and `-n` prints line numbers.
- `-E` allows the `|` inside the brackets to mean "or".
- The pattern lists the start of a GitHub personal token (`ghp_`, `github_pat_`), an AWS key prefix (`AKIA`), and the text `password:`.
- `.github/` is the folder searched.

`grep` prints nothing and exits with code 1 when no line matches. That is the pass, apart from the `password:` login line described in the trap below. Check the code with `echo $?`:

```term
$ grep -rnE '(ghp_|github_pat_|AKIA|password:)' .github/
$ echo $?
1
```

A failing run prints a line such as `.github/workflows/ci.yml:31: password: <value>`. Replace a real value with `${{ secrets.GITHUB_TOKEN }}`. If the value was real, revoke it, because deleting it does not remove it from Git history.

:::trap The password: key will match the grep
The docker login action needs an input key named `password`. The line `password: ${{ secrets.GITHUB_TOKEN }}` holds no secret, but it still contains the text `password:` and TC4 prints it. Do not rename the key or hide it to pass the search. Ask your trainer how they want this line handled, and show the output and the line in your PR.
:::

### Do it, step by step

The pipeline you are building looks like this. Each job starts on a fresh runner only after the one it needs has passed:

```flow
TITLE: One merge to main, three jobs
NODES: Your laptop | GitHub | Fresh runner
STEPS:
1>2 :: git push origin main :: Your merged commit reaches GitHub.
2>3 :: run lint :: ruff and hadolint check the code on a fresh machine.
3>2 :: lint passed :: The job reports success.
2>3 :: run test :: pytest runs with coverage, because needs: lint was satisfied.
3>2 :: tests passed :: Now build-push is allowed to start.
2>3 :: build-push :: The image is built, then pushed under the full SHA.
```

Work on a branch, never on `main`. Each subtask below is one part of that picture.

#### Subtask Y2-T44.1: Default permissions and concurrency

**Goal.** Give every job the smallest rights by default, and stop old runs of the same branch from wasting time.

**Stage 1: add two top-level keys.** Open `.github/workflows/ci.yml`. Keys at column zero sit beside `on:` and `jobs:`. Add these lines. Do not replace the file:

```yaml
permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
```

Line by line:

- `permissions:` at the top level sets the default rights for every job. `contents: read` lets jobs read the code and nothing else.
- `concurrency:` controls runs that share a group.
- `group: ci-${{ github.ref }}` gives each branch its own group. `github.ref` is the full ref of the run: `refs/heads/main` for a push to main, and `refs/pull/<number>/merge` for a pull request.
- `cancel-in-progress: true` cancels an older run in the same group when a new run starts.

:::trap Cancelling main
On `main`, a newer push cancels the older run. The older commit may never reach build-push. Keep this in mind for the viva.
:::

**Stage 2: test the file.** Run this on your laptop:

```bash
python3 -c "import yaml;d=yaml.safe_load(open('.github/workflows/ci.yml'));print(d['permissions'], d['concurrency'])"
```

Expected output:

```text
{'contents': 'read'} {'group': 'ci-${{ github.ref }}', 'cancel-in-progress': True}
```

`yaml.safe_load` reads the file and returns Python dictionaries. Python prints `True` with a capital T. A traceback instead means the indentation is wrong. Fix it before going on.

#### Subtask Y2-T44.2: The lint job, and test waits for lint

**Goal.** Make code style and Dockerfile errors stop the pipeline before tests run.

**The two linters.** ruff checks Python code. hadolint checks Dockerfiles. You will not install hadolint. The project publishes it as a container image, so Docker runs it:

```bash
docker run --rm -i hadolint/hadolint < Dockerfile
```

Line by line: `docker run` starts a container. `--rm` deletes the container when it finishes. `-i` keeps input open, so the file can be fed in. `hadolint/hadolint` is the image name. `< Dockerfile` sends the file into the container. A clean Dockerfile prints nothing. A problem prints a code such as `DL3008` with a line number.

**Stage 1: check locally.** Run:

```bash
ruff check .
```

Expected output is either a line saying `All checks passed!`, or a list of problems followed by a count. Fix each one. `ruff check . --fix` repairs the safe ones automatically. Read the diff before you commit it. Do not switch rules off to hide errors. Check your local version with `ruff --version`, and pin the same version in CI as in the `pip install` line, because different versions report different things.

**Stage 2: add the lint job.** Under `jobs:`, at the same indentation as `test:`:

```yaml
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install ruff==<your-version>
      - run: ruff check .
      - run: docker run --rm -i hadolint/hadolint < Dockerfile
```

Line by line: `lint:` names the job. `runs-on` gives it a fresh Ubuntu machine. `actions/checkout@v4` copies the repository onto the machine. The `pip install` line installs ruff. The next two `run:` lines are the checks from Stage 1. Each command exits with zero on success, and any other exit code fails the step.

**Stage 3: make test wait.** Under `test:`, add one line:

```yaml
  test:
    needs: lint
    runs-on: ubuntu-latest
```

`needs: lint` means test starts only after lint succeeds. Check the order with the same yaml command you used in subtask 44.1, but print `d['jobs']['test']['needs']`. Expected output is `lint`.

#### Subtask Y2-T44.3: The build-push job

**Goal.** Build the image and push it under its full SHA, but only for a push to `main` after tests pass.

**Stage A: the gate.** Add the job header. It names the job, says what it waits for, says when to run, and sets the rights:

```yaml
  build-push:
    needs: test
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
```

Line by line: `needs: test` makes the job wait for tests. `if:` is a condition. `github.event_name` is the event, `github.ref` is the branch, `==` means "equals", and `&&` means "and". On a pull request the condition is false, so the job is skipped. `permissions:` here is job level, which adds `packages: write` for this job only.

**Stage B: checkout and login.** Add these steps under `steps:`:

```yaml
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
```

`setup-buildx-action` prepares the builder that supports the cache options. `login-action` logs in to `ghcr.io`. `username` is the person who started the run. The `password` is the short-lived GITHUB_TOKEN, which you never type.

**Stage C: the tag names.** Add a step with an `id`, so later steps can read its output:

```yaml
      - id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha,format=long,prefix=
            type=sha
```

Line by line: `id: meta` names the step. `images:` is the registry path, which must be lowercase. `github.repository` is `owner/repo-name`, so the image is `ghcr.io/owner/repo-name`; with a repository called `citypulse-squadnn` that gives `ghcr.io/org/citypulse-squadnn`. `tags: |` is a YAML block: each indented line is one rule. `type=sha,format=long,prefix=` gives the full 40-character SHA with no prefix, which is what TC2 pulls. `type=sha` gives the short form, which by default gets the prefix `sha-`, as the ticket expects.

:::trap Forgetting prefix=
Without `prefix=`, the full tag becomes `sha-<40 characters>`. TC2 pulls the bare SHA, so the pull fails with `manifest unknown`.
:::

**Stage D: build and push.** Add the last step:

```yaml
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
          build-args: GIT_SHA=${{ github.sha }}
```

Line by line: `context: .` uses the current folder. `push: true` sends the image after building. `steps.meta.outputs.tags` reads the tags from step C. `cache-from` and `cache-to` with `type=gha` store the build layers in GitHub's cache, so the next run is faster. `build-args` passes the commit SHA into the Dockerfile as `GIT_SHA`.

**Test each stage.** Push the branch after each stage and run `gh run list --limit 1`. Each push must parse. Build-push will not push from a branch, which is correct. Check the dependency with:

```bash
python3 -c "import yaml;d=yaml.safe_load(open('.github/workflows/ci.yml'));j=d['jobs']['build-push'];print(list(d['jobs']), j['needs'], j['if'])"
```

Expected output, if you placed `lint` first in the file (the list follows file order): `['lint', 'test', 'build-push'] test github.event_name == 'push' && github.ref == 'refs/heads/main'`.

#### Subtask Y2-T44.4: Return git_sha from /v1/health

**Goal.** Let a running container say which commit it was built from.

**The idea.** An environment variable is a named value that a program reads when it runs. A build argument is a value passed while the image is built. The Dockerfile copies the first into the image so the app can read it. Watch how the value moves:

```trace
TITLE: Reading GIT_SHA when the route runs
CODE:
import os
def health():
    sha = os.environ.get("GIT_SHA", "unknown")
    return {"status": "ok", "git_sha": sha}
result = health()
STEPS:
1 :: env_GIT_SHA="4b1e9d0c" :: The os module is loaded. The container's environment already holds GIT_SHA, set by the Dockerfile ENV line.
2 :: env_GIT_SHA="4b1e9d0c" :: def stores the function, but nothing inside it runs yet.
5 :: env_GIT_SHA="4b1e9d0c" :: A request arrives, so health() is called.
3 :: sha="4b1e9d0c" :: os.environ.get finds the value, because it is read now, at request time.
4 :: sha="4b1e9d0c"; return={"status": "ok", "git_sha": "4b1e9d0c"} :: The dictionary is built with the SHA inside it.
5 :: result={"status": "ok", "git_sha": "4b1e9d0c"} :: The caller receives the dictionary.
```

**Stage 1: the Dockerfile.** Find the `FROM` line of the runtime stage, the last stage. Add these two lines directly below it:

```dockerfile
ARG GIT_SHA=unknown
ENV GIT_SHA=${GIT_SHA}
```

Line by line: `ARG GIT_SHA=unknown` declares a build argument with a fallback. `ENV GIT_SHA=${GIT_SHA}` copies it into an environment variable that the running app can read. Both lines must be in the runtime stage, because each stage starts empty.

**Stage 2: the route.** Keep the fields the route already returns, and add `git_sha`. Read the variable inside the function, not at the top of the module:

```python
import os

@app.get("/v1/health")
def health():
    return {"status": "ok", "git_sha": os.environ.get("GIT_SHA", "unknown")}
```

Line by line: `import os` loads the module. `@app.get("/v1/health")` connects the function to the address. `os.environ.get("GIT_SHA", "unknown")` returns the value, or `unknown` if it is not set.

**Stage 3: the test.** Add this test beside your existing TestClient tests from Y2-T41. Use your squad's module path in the import:

```python
from fastapi.testclient import TestClient
from app.main import app  # use your squad's module path

def test_health_has_git_sha(monkeypatch):
    monkeypatch.setenv("GIT_SHA", "abc123")
    client = TestClient(app)
    body = client.get("/v1/health").json()
    assert "git_sha" in body
    assert body["git_sha"] == "abc123"
```

`monkeypatch` is a pytest fixture that sets an environment variable for one test only. `TestClient` sends a request to the app without starting a server. Run `pytest -q` and expect a line such as `12 passed`.

**Stage 4: a real request.** Start the app in one terminal, then ask it in another:

```bash
GIT_SHA=abc123 uvicorn app.main:app --port 8000
curl -s localhost:8000/v1/health | jq -r .git_sha
```

Expected output of the second command: `abc123`. `-r` (raw) removes the quotes. `uvicorn` runs the ASGI app, and `app.main:app` is your squad's module and variable name.

:::trap Reading the variable at import time
If the line `GIT_SHA = os.environ.get(...)` sits at the top of the module and the test sets the variable afterwards, the test still sees `unknown`. Reading inside the function avoids this.
:::

#### Subtask Y2-T44.5: Merge to main and record the cold build

**Goal.** Prove that main builds and pushes an image, and record how long the first build took.

**Stage 1: merge.** The Tech Lead merges the approved PR. Follow the run:

```bash
gh run list --branch main --limit 1
gh run watch <id>
```

The first command prints the run id. `gh run watch <id>` shows that run live, until it ends. Without an id, `gh run watch` asks you to pick a run from a list.

**Stage 2: find the build time.** Use the run id from TC1:

```bash
gh run view <id> --json jobs --jq '.jobs[] | select(.name=="build-push") | [.startedAt, .completedAt]'
```

Expected output, with example times:

```text
["2026-11-16T10:02:11Z","2026-11-16T10:07:40Z"]
```

**Stage 3: work out the seconds.** On Linux and Git Bash, `date -d` reads a timestamp, and `+%s` prints it as seconds since 1970:

```bash
echo $(( $(date -d "2026-11-16T10:07:40Z" +%s) - $(date -d "2026-11-16T10:02:11Z" +%s) ))
```

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| build-push runs on a pull request | The `if:` line is missing, or its quotes or `==` are wrong | Copy the condition exactly, then check with TC3 |
| Image tag is `sha-<long SHA>` and TC2 gets `manifest unknown` | `prefix=` is missing from the full-SHA rule in the metadata step | Add `prefix=` to `type=sha,format=long` |
| Push fails with a permission error | `packages: write` is missing from the job, or the organisation blocks package writes | Add it at job level only, then check the organisation's package settings |
| Login step fails with `unauthorized` | `username` is not `github.actor`, or `secrets.GITHUB_TOKEN` is misspelt | Fix the two `with:` values |
| `git_sha` is `unknown` in the container | `ARG` and `ENV` are not in the runtime stage, or `build-args` is missing | Declare both lines under the runtime `FROM`, and check the build-push step |
| Test asserts `abc123` but gets `unknown` | The variable was read at import time, not in the function | Move `os.environ.get` inside the route |
| Lint passes locally but fails in CI | CI installed a different ruff version | Pin the version in CI to the one from `ruff --version` |
| Warm build is not faster than cold | The Dockerfile copies all source before installing dependencies, so every change rebuilds the install layer | Copy `requirements.txt` first, install, then copy the source |
| Workflow does not appear in the Actions tab | YAML indentation is wrong, so the file does not parse | Run the `yaml.safe_load` command and fix the traceback |

### Defend it in the viva

**Question 1: Why must build-push wait for test, and not just run on the same trigger?**

:::answer Model answer
Both jobs would start on the same push, so without `needs: test` a build could push an image before the tests finish. The `needs` line makes GitHub skip build-push when test fails, so a broken change never reaches the registry. That is the gate. Tests decide whether a part is allowed past inspection.
:::

**Question 2: What is a trade-off of `cancel-in-progress: true`?**

:::answer Model answer
It saves runner time and stops stale runs from finishing. The cost is that on `main`, a newer push can cancel an older run before its build-push job finishes, so that older commit never gets an image. For a release branch you might choose to keep every run, and accept the extra time, because every commit should be traceable.
:::

**Question 3: What did you personally do in this ticket?**

:::answer Model answer
Name the subtask you owned, the commits you made, and what each one changed. Then point to the evidence: the commit hash, the run id, and the output of the check you ran. A strong answer is specific and can be checked in Git. Do not describe work you did not do.
:::

**Question 4: Why tag the image with the full SHA rather than `latest`?**

:::answer Model answer
A SHA always points to one commit, so you can say exactly which code runs in a container. `latest` moves on every push, so two servers may run different code under the same name. The full SHA also makes rollback exact, because you redeploy the previous SHA rather than a guess.
:::

**Question 5: How does the pipeline log in to the registry without a password in the repository?**

:::answer Model answer
GitHub creates `secrets.GITHUB_TOKEN` for each run. It is short-lived, and it expires when the run ends. The workflow refers to it by name, so no value appears in the YAML, and GitHub hides it from logs. The rule is that a secret is never typed into a file that Git stores, because Git keeps history even after a line is deleted.
:::

```quiz
Q: The build-push job has if: github.event_name == 'push' && github.ref == 'refs/heads/main'. A squad-mate opens a pull request into main. What happens to build-push?
- It runs and pushes the image under the branch name.

* It is skipped, because the event is pull_request, not push.
- It runs on main as soon as the pull request is opened.
WHY: The condition is false for a pull_request event, so GitHub skips build-push. The tempting mistake is thinking any change to the code builds and pushes an image.

Q: The test job fails on a push to main. The build-push job has needs: test. Which statement is true?
- build-push runs first, and the test job is retried in the background.
* build-push does not start, because needs: test requires test to succeed.
- build-push runs, and the image is tagged latest so it can be undone.
- build-push runs on a second runner while the tests keep going.
WHY: needs makes build-push depend on the result of test, so a failed test skips build-push and no image reaches the registry. The tempting mistake is thinking needs only sets the order.
```
