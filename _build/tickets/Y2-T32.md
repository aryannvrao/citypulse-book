### The ticket in plain words

CityPulse is the Bengaluru city-data platform your squad is building. One of its jobs is to warn people when air pollution is about to get bad. This ticket asks a plain question: can a simple model predict tomorrow's PM2.5 better than a lazy guess? PM2.5 is the amount of very fine particles in the air, measured in micrograms per cubic metre. Too much of it harms health, especially for children and older people.

The lazy guess has a name. It is called **persistence**: tomorrow will be the same as today. A machine-learning model that cannot beat persistence is not worth the extra complexity in the alerts. The ward health officer in the user story needs an honest answer, not a flattering one.

You will train two simple models, a linear regression and a decision tree, on the saved split from Y2-T31. You tune the tree on validation only and look at the test set once. Before any test score exists, you write down which error measure you care about. Pick it by asking which mistake hurts the users more: a false alarm that gets ignored, or a missed spike that harms health.

The ticket rewards honesty. "We did not beat the baseline, and here is the evidence" earns more credit than a number that looks good only because the rules changed.

### How your trainer checks it

**Acceptance criteria.** Five checks: every model is evaluated on the T31 test split and a hash mismatch exits 1; the metric decision commit is older than the results commit; the results table has at least three rows with params, train, val, test, baseline and skill; one model beats persistence, or the verdict gives evidence why not; each student reproduced the numbers and wrote an initialled row.

**TC1: the trainer runs and the results file has the right shape.**

Steps: `python -m citypulse.train_v0 && cat reports/ml/results_v0.csv`. Run this on the lab machine from the repo root.

- `python -m citypulse.train_v0` runs your trainer as a module. `-m` means "run this module as a program", and dots replace the slashes in the path.
- `&&` runs the second command only if the first ends with exit code 0.
- `cat` prints the results file.

What passing looks like: the trainer finishes without an error message, then the CSV header is printed as `model,params,train,val,test,baseline,skill`, followed by at least three rows. The trainer's own printed lines depend on your code, so only the ending matters.

What failing looks like: `ModuleNotFoundError: No module named 'citypulse'`, usually because you are not in the repo root or the package is not on Python's path (see "What goes wrong"). A `test hash mismatch` line and exit code 1 mean the test file or manifest is not the one T31 saved.

**TC2: the metric decision came first.**

Steps: `git log --format='%h %ad %s' --date=iso -- docs/ml-log.md`. Run in Git Bash.

- `git log` lists commits, newest first.
- `--format='%h %ad %s'` prints the short hash, the date and the message for each commit.
- `--date=iso` prints the date as `2026-02-03 11:02:19 +0530`.
- `-- docs/ml-log.md` limits the list to commits that changed that file.

What passing looks like: the metric decision line is lower, so it is older. For example, with made-up hashes:

```text
9f3c2a1 2026-02-03 18:10:44 +0530 docs: add results table and verdict
4b7d0e8 2026-02-03 11:02:19 +0530 docs: record metric decision before test evaluation
```

What failing looks like: the results line is lower than the decision line. The usual cause is writing the results first and the decision afterwards. Do not rewrite history to fake the order. Commit order is evidence, and a trainer can see when a commit was rewritten.

**TC3: the tests pass, including the hash-mismatch case.**

Steps: `pytest -q tests/test_train_v0.py`. Run from the repo root.

- `pytest` runs the tests it finds in the file.
- `-q` means quiet: one dot per passing test, then a short summary.
- `tests/test_train_v0.py` is the file to run.

```term
$ pytest -q tests/test_train_v0.py
...                                                                [100%]
3 passed in 0.42s
```

Each dot is one passing test. Your count may differ, but the last line must say `passed` with no `failed` or `error`.

What failing looks like: `FAILED tests/test_train_v0.py::test_hash_mismatch_exits_1 - Failed: DID NOT RAISE <class 'SystemExit'>`. The trainer did not exit on a changed file. Running pytest from the wrong folder shows `file or directory not found` instead.

**TC4: the baseline matches the log.**

Steps: compare the `baseline` column in `reports/ml/results_v0.csv` with the T31 entry in `docs/ml-log.md`. Use Python's `csv` module, because a `params` value containing a comma would shift `cut`'s columns:

```text
$ python -c "import csv; print({r['baseline'] for r in csv.DictReader(open('reports/ml/results_v0.csv'))})"
{'12.47'}
$ grep -n "T31" docs/ml-log.md
```

`csv.DictReader` reads each row as a dictionary keyed by the header names. The set collapses repeats, so one value means every row has the same baseline.

What passing looks like: the set holds one value and it matches the log, here `12.47`. What failing looks like: two values, such as `{'12.47', '12.5'}`, or a number that differs from the log. The usual cause is different rounding, or a baseline computed on validation rows.

**TC5: the trainer asks you to explain overfitting.**

The trainer asks why your unconstrained tree's train score is so much better than its test score. Name overfitting, say the tree memorised training rows, and point to the `max_depth` you chose on validation. Rehearse this aloud with a squad-mate.

#### Y2-T32.2: write the trainer in stages

**Goal.** A script that checks the test file, trains two Pipelines on the training rows, and writes the results CSV. Build it in four stages, testing each one.

**Stage A: fingerprint a file.** Change one byte of a file and its sha256 fingerprint changes completely. Add this helper first:

```python
import hashlib

def file_sha256(path):
    h = hashlib.sha256()
    with open(path, "rb") as f:
        h.update(f.read())
    return h.hexdigest()
```

`hashlib.sha256()` creates an empty hasher. `"rb"` opens the file as raw bytes, because parquet is binary. `hexdigest()` returns the fingerprint as text. Keep the file safe to import: put the checking and training code inside functions and call them under `if __name__ == "__main__":`, otherwise importing the module (as the test and the command below do) would run the whole trainer. Test it from the repo root with `python -c "from citypulse.train_v0 import file_sha256; print(file_sha256('data/splits/test.parquet'))"`. Expect a 64-character string.

**Stage B: compare with the manifest and exit.** Read the expected hash from `manifest.json`, then compare. Find the key that T31 used for the test hash by opening the file with `cat data/splits/manifest.json`.

```python
import json
import sys

with open("data/splits/manifest.json") as f:
    manifest = json.load(f)
expected = manifest["YOUR_TEST_HASH_KEY"]   # the key T31 used
actual = file_sha256("data/splits/test.parquet")
if actual != expected:
    print("test hash mismatch", actual, expected)
    sys.exit(1)
```

`json.load(f)` turns the JSON text into a dictionary. `sys.exit(1)` ends the program with exit code 1, as the acceptance criterion requires. Wrap this in a function that takes the test path and the expected hash, so a test can call it with a modified copy. Test it once unchanged (silent finish), then with a wrong key in a copy of the manifest (mismatch line and failure).

**Stage C: train both models in Pipelines.** A Pipeline keeps the imputer and the model together, so the imputer learns its median from the training rows only. That is how you avoid leakage.

```python
from sklearn.pipeline import Pipeline
from sklearn.impute import SimpleImputer
from sklearn.linear_model import LinearRegression

linear = Pipeline([
    ("impute", SimpleImputer(strategy="median")),
    ("model", LinearRegression()),
])
linear.fit(train[FEATURES], train[TARGET])
```

Each `(name, step)` pair is one stage. `.fit(...)` runs the imputer and then the model, on training rows only. Expect no output. Test it with `linear.predict(val[FEATURES]).shape`, which should show the number of validation rows.

**Stage D: the tree, then the results file.** The tree follows the same pattern. `max_depth` comes from Y2-T32.3.

```python
from sklearn.tree import DecisionTreeRegressor

tree = Pipeline([
    ("impute", SimpleImputer(strategy="median")),
    ("model", DecisionTreeRegressor(max_depth=depth, random_state=42)),
])
```

The ticket needs at least three configurations: the linear model, the tree with the depth chosen on validation, and an overfit tree built with `max_depth=None` (no limit). Collect one dictionary per configuration in a list called `rows`, with the keys `model`, `params`, `train`, `val`, `test`, `baseline` and `skill`. Then save it:

```python
import os
import pandas as pd

os.makedirs("reports/ml", exist_ok=True)
pd.DataFrame(rows).to_csv("reports/ml/results_v0.csv", index=False)
```

`os.makedirs(..., exist_ok=True)` creates the folder if it is missing. `index=False` leaves out a numbered column. Keep `params` free of commas. Test with `cat reports/ml/results_v0.csv`.

**Stage E: the test score comes last.** Compute `test` only after every choice is made. Use the metric from your decision commit for train, val and test alike (for MAE, `from sklearn.metrics import mean_absolute_error`). The `baseline` column is the persistence error on the test rows, the same number as the T31 log entry. Skill is `1 - model_error / baseline_error` for an error metric. For example, a baseline MAE of 12.47 and a model MAE of 7.94 give skill of about 0.36.

#### Y2-T32.3: tune the tree on validation only

**Goal.** Choose `max_depth` from 2 to 8 using validation scores, and record each score.

The trace shows the keep-the-best pattern with three invented scores, where higher is better (like R squared). If your metric is an error such as MAE, lower is better: start from `float("inf")` and compare with `<`. Your real scores come from the validation set.

```trace
TITLE: Keeping the best depth
CODE:
best_depth = None
best_val = -1.0
val_scores = {2: 0.61, 3: 0.66, 4: 0.64}
for depth, val in val_scores.items():
    if val > best_val:
        best_val = val
        best_depth = depth
STEPS:
1 :: best_depth=None :: Start with no depth chosen.
2 :: best_depth=None; best_val=-1.0 :: Any real score beats -1.0, so the first depth wins at once.
3 :: val_scores={2: 0.61, 3: 0.66, 4: 0.64} :: Invented validation scores for the example.
4 :: depth=2; val=0.61 :: The loop takes the first pair.
5 :: depth=2; val=0.61; best_val=-1.0 :: 0.61 is greater than -1.0, so the test is true.
6 :: depth=2; val=0.61; best_val=0.61 :: Store the new best score.
7 :: depth=2; best_depth=2; best_val=0.61 :: Store the depth that earned it.
4 :: depth=3; val=0.66; best_depth=2 :: The next pair.
5 :: depth=3; val=0.66; best_val=0.61 :: 0.66 is greater than 0.61, so the test is true.
6 :: depth=3; val=0.66; best_val=0.66 :: Replace the best score.
7 :: depth=3; best_depth=3; best_val=0.66 :: Replace the best depth.
4 :: depth=4; val=0.64; best_depth=3 :: The last pair.
5 :: depth=4; val=0.64; best_val=0.66 :: 0.64 is not greater than 0.66, so lines 6 and 7 are skipped.
```

Use `for depth in range(2, 9):`, which includes 8, and fit a tree for each depth. Keep each depth with its validation score, then choose the highest. Print the list to check it has seven entries.
