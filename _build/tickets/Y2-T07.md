### The ticket in plain words

CityPulse collects air-quality readings for Bengaluru. Your squad's script, `scripts/fetch.sh`, asks an API for the latest readings and appends them as a row to a CSV file. A scheduler called cron runs it every 30 minutes. Ticket Y2-T06 made this work. This ticket makes it safe to leave alone.

The main risk is silence. A job can stop and print nothing, and nobody notices until the data has a gap. The ticket asks for five things:

1. A healthcheck: a script that looks at when the last successful fetch happened and reports `OK`, `WARN` or `CRIT`.
2. A disk guard and log rotation, so logs and the disk never fill up.
3. A second data source, such as a weather forecast, joined to the air-quality rows by timestamp and location.
4. Clean Git habits: small commits with clear messages, a pull request reviewed by a squad-mate, and a version tag.
5. A README section called Operations, which tells the next person how the system runs.

At the P1 demo your trainer will break the network or the source on purpose, and the healthcheck must report it. Your work is judged from commits in the squad repository, so every change must be your own and must carry your own Git name and email.

### How your trainer checks it

The trainer checks six acceptance criteria and five test cases. The criteria are: at least 96 data rows after 48 hours; a WARN or CRIT line with a non-zero exit when the source is broken, and OK with exit 0 when healthy; a merged CSV with both sources' columns and printed unmatched counts; a logrotate dry-run with no errors; at least 5 commits per student with imperative subjects; and the tag `v0.1-p1` plus an Operations heading in the README. The test cases are below. Run them yourself, in order, before review.

**TC1: healthcheck reports a broken source.**

The steps are `touch ops/STOP`, then `WARN_MIN=0 CRIT_MIN=0 scripts/healthcheck.sh; echo $?`.

- `touch ops/STOP` creates an empty file. Your `fetch.sh` sees it and does nothing, so no rows arrive.
- `WARN_MIN=0 CRIT_MIN=0` sets both thresholds to zero, so any age counts as a problem straight away.
- `scripts/healthcheck.sh` runs your script from the repository root.
- `; echo $?` runs after the script, even if it failed, and prints its exit code.

Passing output: a line starting with `WARN` or `CRIT`, then `1` or `2`. Failing output: a line starting with `OK`, or `0`. The usual cause is thresholds that ignore the environment, or a script that ends with `exit 0` whatever happens.

**TC2: a healthy system reports OK.**

The steps are `rm -f ops/STOP; scripts/fetch.sh; scripts/healthcheck.sh; echo $?`.

- `rm -f ops/STOP` deletes the kill switch. `-f` means no error if it is already gone.
- `;` separates the commands, so each runs even if the one before fails.
- `scripts/fetch.sh` appends an `INFO appended` line to the log, and the healthcheck then finds a fresh success.

```term
$ rm -f ops/STOP
$ scripts/fetch.sh
$ scripts/healthcheck.sh
OK: last success 0 min ago
$ echo $?
0
```

Your wording may differ, but the line must start with `OK` and the exit code must be `0`. If you see `WARN` or `CRIT` straight after a fetch, the fetch did not write its success line, so look at the end of `logs/fetch.log`.

**TC3: merge writes both sources with unmatched counts.**

The steps are `scripts/merge.sh $(date +%F); head -3 data/raw/merged_$(date +%F).csv`.

- `$(date +%F)` runs `date` and puts its output into the command. `+%F` prints today as `YYYY-MM-DD`.
- `scripts/merge.sh` receives that date as its first argument.
- `head -3` prints the first three lines: the header and two rows.

Passing output: a header with metric columns from both sources, and the unmatched counts printed. Failing output: only one source's columns, or `No such file`. The usual cause is a file name built with a different date format.

**TC4: commits by each student.**

The steps are `git shortlog -sne origin/main` and `git log --author='<name>' --format=%s origin/main`.

- `git shortlog -s` counts commits per author, `-n` sorts them and `-e` shows the email.
- `origin/main` is the copy of `main` on the remote, as last fetched.
- `--author` keeps the commits whose author matches the text, and `--format=%s` prints only the subject lines.

Passing output: 5 or more lines for each student under their own email, with subjects such as "Add disk guard to fetch.sh". Failing output: a count below 5, another email, or subjects like "update". The usual cause is a Git identity set after the commits were made.

**TC5: tag and README section.**

The steps are `git ls-remote --tags origin | grep v0.1-p1; grep -n '## Operations' README.md`.

- `git ls-remote --tags origin` lists the tags on GitHub without downloading anything.
- `| grep v0.1-p1` passes that list to `grep`, which keeps only the matching line. The pipe `|` sends the output of one command into the next.
- `grep -n` searches the README for the heading and prints its line number.

Passing output: a line with a hash and `refs/tags/v0.1-p1`, then a line number and the heading. Failing output: nothing, which means the tag was not pushed or the heading is spelled differently.

### Do it, step by step

Work on the lab unless a step says otherwise. Test each stage before you move on.

#### Stage 1 (Y2-T07.1): check the 48-hour gate

**Goal.** Show that the job has run long enough and that the data holds at least 96 rows.

First, learn `wc -l`, which counts lines:

```bash
printf 'a\nb\nc\n' | wc -l
```

`printf` writes three lines, and the pipe `|` sends them to `wc -l`. Expect `3`.

Each CSV has a header line, so data rows are the line count minus one. `tail -n +2` prints from line 2 onwards, which skips the header:

```bash
for f in data/raw/*.csv; do echo "$f $(tail -n +2 "$f" | wc -l)"; done
```

The loop visits each CSV. `echo` prints the file name and its row count, for example `data/raw/2026-11-15.csv 48`. Your numbers will differ. Once `merge.sh` has produced `merged_*.csv` files in the same folder, leave them out of the loop, or you will count rows twice.

Then count the successful runs:

```bash
grep -c 'INFO appended' logs/fetch.log
```

`grep -c` prints how many lines match. Expect a number near 96 after 48 hours.

**Test this stage.** Add up the rows. If the total is at least 96 for the window, the gate passes. If it is much lower, check `crontab -l` and the end of `logs/cron.out`, fix cron first, and tell your trainer. Never add fake rows.

#### Stage 2 (Y2-T07.2): write scripts/healthcheck.sh

**Goal.** Measure how many minutes ago the last success was, and print `OK`, `WARN` or `CRIT` with a matching exit code.

**2a. Time arithmetic.** Two commands turn dates into numbers:

```bash
date +%s
date -d "2026-11-17 09:30" +%s
```

`date +%s` prints the current time as seconds since 1 January 1970. `date -d "..."` reads a date you give it. The `-d` option is GNU date, which the lab and Git Bash have, but not every Mac does. Check your log's timestamp format with `head -2 logs/fetch.log`, and make sure `date -d` can read it.

**2b. The top of the script.**

```bash
#!/usr/bin/env bash
set -uo pipefail
WARN_MIN="${WARN_MIN:-60}"
CRIT_MIN="${CRIT_MIN:-120}"
LOG="${LOG:-logs/fetch.log}"
```

The first line tells the system to run the file with Bash. `set -uo pipefail` makes an unset variable an error and makes a pipeline fail if any part fails. There is no `-e` on purpose: the healthcheck must still print its status after a failed command. Each `${VAR:-default}` keeps a value passed in the environment, which is how TC1 sets `WARN_MIN=0`.

Test with `bash -n scripts/healthcheck.sh`. It checks syntax and prints nothing when the syntax is fine.

**2c. Find the last success.** Build the pipeline one command at a time:

```bash
grep ' INFO appended' "$LOG" | tail -1 | cut -d' ' -f1
```

`grep` keeps the success lines. `tail -1` keeps the newest one. `cut -d' ' -f1` splits the line at spaces and keeps field 1. That is the whole timestamp only if your log writes it without a space, such as `2026-11-17T09:30:00`. If it is `2026-11-17 09:30:00`, use `-f1,2`. Run the pipeline without the last part first, to see the line. Then store the result:

```bash
last="$(grep ' INFO appended' "$LOG" | tail -1 | cut -d' ' -f1 || true)"
```

`$(...)` runs the command and stores its output in `last`. `|| true` stops a failing pipeline from ending the script when there is no success yet. Test `[ -z "$last" ]` before using `last`: if it is empty, `date -d ""` silently means midnight today, not an error. Decide what the script prints when there is no success yet, and write that decision in the README, because the ticket leaves it to you.

**2d. Compute the age.**

```bash
now=$(date +%s)
last_ts=$(date -d "$last" +%s)
age=$(( (now - last_ts) / 60 ))
echo "age ${age} min"
```

`$(( ... ))` does integer arithmetic. Division rounds down, which is fine for minutes. Expect a line such as `age 14 min`.

**2e. Choose the status.** The trace shows how one age becomes one status.

```trace
TITLE: Choosing the status from the age
CODE:
age=75
WARN_MIN=60
CRIT_MIN=120
if [ "$age" -ge "$CRIT_MIN" ]; then echo CRIT; exit 2
elif [ "$age" -ge "$WARN_MIN" ]; then echo WARN; exit 1
else echo OK; exit 0; fi
STEPS:
1 :: age=75 :: The age of the last success is 75 minutes.
2 :: age=75; WARN_MIN=60 :: The warning threshold came from the default or the environment.
3 :: age=75; WARN_MIN=60; CRIT_MIN=120 :: The critical threshold is set the same way.
4 :: age=75; WARN_MIN=60; CRIT_MIN=120 :: Is 75 at least 120? No, so the CRIT branch is skipped.
5 :: age=75; WARN_MIN=60; CRIT_MIN=120 :: Is 75 at least 60? Yes, so this branch runs.
5 :: age=75; WARN_MIN=60; CRIT_MIN=120 :: echo prints WARN.
5 :: age=75; WARN_MIN=60; CRIT_MIN=120 :: exit 1 ends the script with code 1, and the else branch is never reached.
```

Now write your own `if`, `elif` and `else`. Test CRIT first, because a large age also passes the WARN test. Each branch prints one line starting with the status word and exits with 2, 1 or 0. Getting this order wrong is the most common mistake in this stage.

**Test this stage.** After `chmod +x scripts/healthcheck.sh`, run:

```bash
scripts/healthcheck.sh; echo $?
WARN_MIN=0 CRIT_MIN=0 scripts/healthcheck.sh; echo $?
```

The first should print OK and `0` after a fetch. The second should print CRIT and `2`.

**2f. Run it hourly.** Add this line with `crontab -e` on the lab, replacing the path with the output of `pwd`:

```bash
0 * * * * cd /home/yourname/citypulse-squad && scripts/healthcheck.sh >> logs/health.log 2>&1
```

`0 * * * *` runs at minute 0 of every hour. Cron starts in your home folder, so `cd` changes into the repository first. `&&` runs the rest only if the `cd` worked. `>> logs/health.log 2>&1` appends the output and any errors to the health log.

```flow
TITLE: One hourly healthcheck run
NODES: cron | scripts/healthcheck.sh | logs/fetch.log | logs/health.log
STEPS:
1>2 :: minute 0 :: cron starts the healthcheck with a minimal environment.
2>3 :: read last line :: The script searches the log for the newest INFO appended line.
3>2 :: timestamp :: The log returns the time of the last success.
2>4 :: OK, WARN or CRIT :: The status line is appended to the health log.
```

#### Stage 3 (Y2-T07.3): disk guard and log rotation

**Goal.** Stop `fetch.sh` writing when the disk is nearly full, and keep logs small.

**3a. Read the disk usage.**

```bash
df -P . | awk 'NR==2 {print $5}' | tr -d '%'
```

`df -P .` reports the disk holding the current folder, in a fixed layout. Line 2 is the disk you want. `awk 'NR==2 {print $5}'` prints field 5, the percentage used. `tr -d '%'` deletes the percent sign so you can compare numbers. Expect `42`.

**3b. Add the guard to fetch.sh.** Choose a threshold, for example 90, and keep it in a variable near the top of the script that an environment value can override, such as `DISK_MAX="${DISK_MAX:-90}"`. Then write an `if` that compares the number with the threshold using `-ge`, which means "greater than or equal". When the test is true, write a line to the log and exit with 1 before the fetch starts.

The log line must not contain `INFO appended`, or it would count as a success and hide the failure from the healthcheck. Use `ERROR` or `WARN`, following the format of your other lines.

**Test this stage.** Set the threshold to 0 for one run:

```bash
DISK_MAX=0 scripts/fetch.sh; echo $?
tail -1 logs/fetch.log
```

Expect exit code `1` and the disk message in the log. Make sure `ops/STOP` is absent first, or the script may stop before reaching the guard. The variable name is your choice, but the test above assumes it can be set from the environment.

**3c. The logrotate configuration.** This file describes what to rotate and how:

```
logs/*.log {
    weekly
    rotate 4
    compress
    missingok
    notifempty
    copytruncate
}
```

`weekly` rotates once a week, `rotate 4` keeps four old copies, `compress` gzips them, `missingok` ignores an absent file, and `notifempty` skips empty logs. `copytruncate` matters if a process keeps the log file open while it runs (for example a script that starts with `exec >> logs/fetch.log`). Without it, a rename would leave that process writing to the moved file. It is a safe choice for any log that scripts append to. Choose your own values, and run the commands from the repository root.

**3d. Dry run.** The ticket's check is:

```bash
logrotate -d -s ops/logrotate.state ops/logrotate.conf
```

`-d` is debug mode: it prints what logrotate would do and changes no file. `-s` names the state file that records past rotations. Expect lines that mention each log, such as `considering log logs/fetch.log`. Wording varies by version. Any message about a missing file or a bad directive is a failure. Some logrotate versions also complain about file permissions, for example a config or log folder that others can write to, or a path that is not absolute. If you see such a message, `chmod 644 ops/logrotate.conf` and `chmod go-w logs` often fix it. If it still fails, or if the lab's version rejects the relative `logs/*.log` pattern, ask your trainer rather than guessing.

**3e. Schedule it.** The ticket gives the command, and you choose the time. For example, `30 3 * * * cd /home/yourname/citypulse-squad && logrotate -s ops/logrotate.state ops/logrotate.conf` runs at 03:30 each day, outside the fetch times. Cron's PATH is short (usually `/usr/bin:/bin`) and `logrotate` often lives in `/usr/sbin`, so put the full path from `command -v logrotate` in the cron line.

#### Stage 4 (Y2-T07.4): second source and merge

**Goal.** Fetch a second source and join its rows to the air-quality rows by timestamp and location.

**4a. Look at the data first.** The ticket leaves the source to your squad and gives Open-Meteo as an example. Check its parameter names in the provider's documentation, then look at one reply:

```bash
curl -fsS 'https://api.open-meteo.com/v1/forecast?latitude=12.97&longitude=77.59&current=temperature_2m,relative_humidity_2m' | jq .
```

`curl -f` makes curl fail on HTTP errors such as a 404. `-s` hides the progress meter, and `| jq .` pretty-prints the JSON so you can see the field names. Use the names you see, not the ones in this example. Open-Meteo times are in GMT unless you add a `timezone` parameter, and the `current` time is a 15-minute slot, so check how it lines up with your air-quality timestamps before you join. Then `jq -r '... | @csv'` turns chosen fields into one CSV line, where `@csv` builds the quoted line and `-r` removes the quotes around the whole output.

**4b. Learn the join with two small files.** Practise in a folder outside the repository, such as `$HOME/join-practice`:

```bash
printf 'time,temp,humidity\n2026-11-17T09:00,24.1,58\n2026-11-17T10:00,24.8,55\n' > meteo.csv
printf 'time,station,pm25\n2026-11-17T09:00,S1,41\n2026-11-17T10:00,S1,44\n2026-11-17T11:00,S1,47\n' > air.csv
```

`printf` writes text, with `\n` for new lines, and `>` writes it to a file. The values are made up for practice.

```bash
awk -F, 'FNR==1 {next}
NR==FNR { temp[$1]=$2; hum[$1]=$3; next }
$1 in temp { print $0","temp[$1]","hum[$1]; next }
{ unmatched++ }
END { print "unmatched", unmatched+0 > "/dev/stderr" }' meteo.csv air.csv
```

`-F,` sets the separator to a comma. `FNR==1 {next}` skips each header. `NR==FNR` is true only while awk reads the first file, because `NR` counts all lines so far and `FNR` counts lines in the current file. The first file is stored in arrays keyed by time. For the second file, `$1 in temp` asks whether its time exists; if so, the row is printed with the extra columns, and if not, `unmatched` goes up. `END` runs once and prints the count to standard error, so it does not mix with the data. The ticket wants unmatched counts for both sources, so also count first-file rows that never matched, for example by marking keys in a `used` array.

Expected output:

```
2026-11-17T09:00,S1,41,24.1,58
2026-11-17T10:00,S1,44,24.8,55
unmatched 1
```

The 11:00 row has no partner, so it is unmatched.

**4c. Build merge.sh in three stages.** First, the argument. This stops with a usage message if the date is missing:

```bash
#!/usr/bin/env bash
set -uo pipefail
day="${1:?usage: scripts/merge.sh YYYY-MM-DD}"
```

`${1:?message}` uses the first argument, or prints the message and exits. Test with `scripts/merge.sh; echo $?`.

Second, the input files. Use the names your earlier tickets already write, and check each file exists, printing a clear error if one does not.

Third, the join and output. Use the awk pattern from 4b with the real key, which is timestamp and location together. Write a header with the column names from both sources yourself, then send the joined rows into `data/raw/merged_$day.csv`.

**Test this stage.** Run `scripts/merge.sh $(date +%F)` and then `head -3 data/raw/merged_$(date +%F).csv`. If nothing matches, the two timestamp formats probably differ, for example one has `+05:30` and the other `Z`.

**4d. Schedule the second fetch.** Give it its own script and cron line, with a different lock name from `fetch.sh`. A shared lock would make the two jobs block each other.

#### Stage 6 (Y2-T07.6): branch, atomic commits, push and pull request

**Goal.** Make at least five small commits on your branch, push them, and open a PR for a squad-mate to review.

```bash
git switch main
git pull
git switch -c yourname/p1-hardening
```

`git switch main` changes to `main`, and `git pull` downloads its latest commits. `git switch -c` creates your branch and switches to it.

For each change, stage only the files it touches, check what is staged, and commit:

```bash
git add scripts/healthcheck.sh
git diff --staged --stat
git commit -m "Add healthcheck script that reports minutes since last fetch" -m "Without this, a stopped cron job is silent. The script reads the last INFO appended line and prints OK, WARN or CRIT."
```

`git add` stages one file. `git diff --staged --stat` lists what will be committed, which catches stray files. The first `-m` is the subject, and the second adds a body paragraph that explains why the change exists. Expect a line such as `[yourname/p1-hardening 3f2a1c0] Add healthcheck script ...`.

Then push and link the branch with `git push -u origin yourname/p1-hardening`. The `-u` option means later pushes need no extra words. GitHub prints a link for opening the PR.

Write the PR description with these headings, in your own words:

**What**: one or two sentences on what changed.

**Why**: the problem this solves, in the ticket's words.

**How to test**: the commands a reviewer runs, in order.

**Evidence**: short log excerpts, command output such as the OK line and exit code, and a screenshot if useful.

**Checklist**: the definition-of-done items this PR covers, ticked only when you have run them.

A squad-mate must review your PR. You do not merge your own PR, and the Tech Lead merges reviewed work.

#### Stage 7 (Y2-T07.7): the annotated tag

**Goal.** Mark the merged `main` with a version tag. This is the Tech Lead's job. Everyone else should watch and learn.

```bash
git switch main
git pull
git tag -a v0.1-p1 -m 'P1: auto-fetch demo'
git push origin v0.1-p1
```

`git tag -a` creates an annotated tag, which records the tagger, the date and the message. A lightweight tag stores none of these. `git push origin v0.1-p1` is needed, because `git push` does not send tags on its own.

```bash
git fetch --tags
git cat-file -t v0.1-p1
```

`git cat-file -t` prints the object type. Expect `tag`. If it prints `commit`, recreate the tag with `-a`.

#### Stage 8 (Y2-T07.8): rehearse the live demo

**Goal.** Show the system working, then failing, in five minutes.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| Healthcheck prints OK while fetching has stopped | It checks that the log file exists, not the age of the last success line | Measure the age of the last `INFO appended` line |
| `WARN_MIN=0 CRIT_MIN=0` has no effect | Thresholds are hard-coded, so the environment is ignored | Use `${WARN_MIN:-60}` style defaults |
| `echo $?` always shows 0 | The script ends with `exit 0`, or the branches do not call `exit` | Put `exit 2`, `exit 1` and `exit 0` inside the matching branches |
| Healthcheck is OK right after a guard error | The guard wrote a line containing `INFO appended` | Log guard errors as `ERROR` or `WARN` |
| `date -d` fails, or the age is huge or negative | The timestamp format or timezone is not what `date -d` expects | Check `head -2 logs/fetch.log` and adjust the parsing |
| Logs stop growing after rotation | The file was renamed while `fetch.sh` kept writing to it | Add `copytruncate` to the config |
| merge.sh joins zero rows | Timestamps differ in format or timezone between sources | Print one line from each file and make the formats match |
| `git shortlog` shows commits under another email | `git config user.email` was not set before committing | Set it, redo the commits on your branch, and tell your trainer |
| `git cat-file -t v0.1-p1` prints `commit` | The tag is lightweight, made without `-a` | Delete it (`git tag -d v0.1-p1`, then `git push origin :refs/tags/v0.1-p1`), then recreate it with `-a` |

### Defend it in the viva

The viva scores your understanding and contribution. Answer in your own words, and use your own commits as evidence.

**1. Why does the healthcheck measure the age of the last success instead of checking that cron is running?**

:::answer Model answer
Cron can run happily while every fetch fails, for example with a bad URL or a blanked key. The client cares about data, so the healthcheck measures how old the last successful line is. If that age passes a threshold, the data is stale, whatever the cause. The check looks at the outcome, not the mechanism.
:::

**2. What is the trade-off between a 60-minute WARN and a 120-minute CRIT?**

:::answer Model answer
Lower thresholds find problems sooner but can raise false alarms, for example from one slow reply. Higher thresholds reduce noise but leave the data stale longer before anyone hears. With fetches every 30 minutes, 60 minutes means two missed runs, a reasonable first warning, and 120 minutes means four, which is serious. A strong answer says how many missed runs each threshold represents.
:::

**3. Why does logrotate need copytruncate for a log that fetch.sh writes with `>>`?**

:::answer Model answer
The script keeps appending to the same path. If logrotate only renamed the file, the running process could keep writing to the renamed copy, and the new file would stay empty. `copytruncate` copies the log and then empties the original, so writes continue to the same path. A strong answer also admits that a few lines written during the copy can be lost, and says why that is acceptable here.
:::

**4. Describe one commit you made. Why is it atomic, and what does its message tell a reviewer?**

:::answer Model answer
Your answer must describe your own commit. A good answer names the one thing it changes, says why it can be read or reverted alone, and quotes the subject and the first sentence of the body. It should show that the message explains the reason for the change, not only what changed. Practise with your own `git log` output.
:::

**5. How did you check that your work reached `main`, and what would you do if a PR was not reviewed?**

:::answer Model answer
Name the checks you ran, for example `git shortlog -sne origin/main` showing your commits under your email, and each PR showing a squad-mate's approval. If a PR is not reviewed, ask the reviewer directly or raise it with the Tech Lead. Never merge your own PR. A strong answer names that rule.
:::
