### The ticket in plain words

This ticket prepares you for a technical interview about CityPulse. CityPulse is the Bengaluru city-data platform your squad builds. Your trainer wants proof that you can explain it to a senior engineer in three ways: a one-page written note, a quick drawing of the system, and a live grill in which five peers ask "why" questions.

The reason is simple. An interviewer wants to know whether you own your part of the work or whether you repeat buzzwords. So every claim you make needs a number, and every number needs a file in your repository that proves it. When someone asks "Why serverless instead of a VM?", a good answer names the cost and the reliability figures from your own docs. It does not rely on memory or on a blog post.

The ticket has four parts. First, you build a numbers card, which is a list of the figures you will quote, each with the file it came from. Second, you write a one-page deep-dive note with six sections and one number per section. Third, you draw an architecture sketch in 60 seconds and star the parts you built. Fourth, you prepare five "why" questions with short answers, and you face a grill from your peers. After that you act as a griller for squadmates, upload your note, and confirm with your trainer that your technical mock interview is complete by 20:30.

The description does not mention a famous failure. Its story is the interview itself. Keep the note short. It is a map for the viva, not an essay.

#### TC1: the number matches its source

The trainer opens the note, picks one number, and opens the source file. Your number must match the file exactly.

The command below prints one line of a file. Run it in Git Bash in your repository. Replace `docs/cloud-cost.md` and `42` with your own file and line number. Your file name and line will be different.

```bash
# Runs in Git Bash, in the repository folder
sed -n '42p' docs/cloud-cost.md
```

The parts:

- `sed` is a stream editor. Here it only reads and prints.
- `-n` stops `sed` printing every line. Without it, the whole file would print.
- `'42p'` means "print line 42 only". The `p` is the print command.
- `docs/cloud-cost.md` is the file to read.

Passing output looks like this. The line contains the number from your card, unchanged. The example below is made up for the shape of the output; your line will hold your own figure.

```term
$ sed -n '42p' docs/cloud-cost.md
Invocations per month at one run every 30 minutes: 1440
```

Failing output has two usual causes. If the line is blank or shows different text, the line number has moved, because someone added or removed lines above it. Run `grep -n` again to find the new line number. If the number is different, the card was written from memory. Correct the card and the note so both use the value from the file.

#### TC2: the sketch in 60 seconds, owned parts starred

The trainer says "Draw your architecture" and starts a 60-second timer. You must draw a complete data-flow sketch in time, with your owned parts starred.

Passing means every box has an arrow in data-flow order, the sketch is finished before the timer stops, and each part you built carries a star. Failing means the drawing is missing arrows, is not finished, or has no stars. The usual cause is drawing without a timer, so the drawing grows to twenty small boxes. Practise with the timer below.

```bash
# Runs in Git Bash
start=$(date +%s)
# ...draw your sketch on paper now...
echo "$(( $(date +%s) - start )) seconds"
```

The parts:

- `start=$(date +%s)` saves the current time as a number of seconds since 1 January 1970. `date +%s` prints that number, and `$( )` puts the output into `start`.
- The comment line is a reminder that you draw between the two commands. A comment starts with `#` and does nothing.
- `$(( ... ))` does arithmetic. Here it subtracts `start` from the current time.

Expected output: a line such as `47 seconds`. Aim for 50 seconds or less in practice, so you have a margin in the live test. Run the commands in the same Git Bash window, because the variable `start` is kept only while that window stays open.

#### TC3: the 45-second answer with numbers from your own docs

The trainer asks "Why serverless over a VM?". Your answer must take 45 seconds or less, and it must cite a cost number and a reliability number, both from your own docs.

Passing means the answer is under 45 seconds, it names one cost figure and one reliability figure, and each figure comes with the file it came from. Failing means the answer runs long, has numbers without sources, or gives a general claim with no figures. The usual cause is starting with history, such as what a VM is. Start with the claim and the numbers.

Before the live test, find the numbers in your docs. The command below searches your docs folder for two words.

```bash
# Runs in Git Bash, in the repository folder
grep -En "cost|reliab" docs/*.md
```

The parts:

- `grep` searches text for a pattern and prints each matching line.
- `-E` turns on extended patterns, so the `|` between `cost` and `reliab` means "either word".
- `-n` prints the line number of each match.
- `docs/*.md` is every Markdown file in the docs folder.

Expected output: one line per match, in the form `file:line:text`. Pick one cost line and one reliability line from it. Time your spoken answer with a stopwatch.

#### TC4: the mock tracker shows a completed mock

The trainer opens the mock-interview completion tracker and filters it to your name at 20:30. The row must show status `completed`, the interviewer's name and a date on or before 22 April.

There is no command for this check. You look in the LMS tracker yourself, filter it to your name, and read the row. Passing means the status says `completed`, the interviewer is named, and the date is on or before 22 April. Failing means the status says booked or is blank, or the interviewer or date is missing. The usual cause is that the mock took place but the trainer has not updated the tracker yet. Ask the trainer before 20:30, and bring the date and interviewer name.

### Do it, step by step

#### 1. Fill the numbers card (Y2-T59.1)

Goal: a table in one file, where every number you will quote has a row, a value, a source file and a line number.

Stage 1: find the files. Run this in Git Bash, inside the repository.

```bash
ls docs
```

The parts: `ls` lists the names in a folder. `docs` is the folder to list.

Expected output: the file names in your docs folder. Look for the cost doc and the model report. If you cannot find one, check the README, which links to the other documents.

Stage 2: find the numbers. Teach this first with a small example. Suppose a file contains two lines, `Runs per day: 48` and `Memory: 128 MB`. Searching with `grep -nE "[0-9]+"` prints both lines with their line numbers, because the pattern `[0-9]+` means "one or more digits". Now run it on your own file.

```bash
grep -nE "[0-9]+" docs/cloud-cost.md
```

The parts: `[0-9]+` matches one or more digits. `-n` prints the line number. The output has the form `line-number:text`. For the example file above, the output would be `1:Runs per day: 48` and `2:Memory: 128 MB`. For your file, the output is longer. Pick the lines you want to quote.

Stage 3: read the exact line. Use `sed -n` with the line number, as in TC1.

```bash
sed -n '1p' docs/cloud-cost.md
```

Expected output: the text of line 1. If it matches the text you saw in the search, the line number is right.

Stage 4: write the card. Create a Markdown file for the card, for example `docs/deep-dive-numbers.md`. Use one row for each figure, in this shape:

| Figure | Value | Source file | Line |
|---|---|---|---|
| What the number measures | The number, with its unit | The path in the repository | The line number from grep |

Test before moving on. For each row, run `sed -n 'LINEp' PATH` and check that the output contains the value. Fix any row that does not match.

#### 2. Write the six-part arc (Y2-T59.2)

Goal: a one-page note with six sections in the order of the arc template. Each section uses one number from the card, and the "my part" section links to your merged PRs.

Start by listing your own merged PRs. Run this in Git Bash.

```bash
gh pr list --author @me --state merged --limit 30 --json number,title,url --jq '.[] | "#\(.number) \(.title) \(.url)"'
```

The parts:

- `gh pr list` lists pull requests in the repository you are in.
- `--author @me` keeps only the PRs you opened. `@me` means you.
- `--state merged` keeps only merged PRs.
- `--limit 30` shows at most 30.
- `--json number,title,url` asks for those three fields as JSON, which is structured text.
- `--jq '...'` is built into `gh`, so you do not need to install the separate `jq` tool (Git Bash on Windows does not include it). It reads the JSON and prints plain text. `.[] | ...` takes each PR and formats it with the `#` number, the title and the link.

Expected output: one line per PR, such as `#12 Add cost doc table https://github.com/...`. Copy the lines for the PRs that belong to your layer into the "my part" section.

Teach the shape of one section with a fictional example, about a different project, a library book-loan app. Your sections must use your own project's numbers.

> Section: Reliability. Claim: the overdue-reminder job sends each reminder once, even when it is run twice. Evidence: in the last 40 runs, 0 reminders were sent twice (source: `docs/reminder-log.md`, line 18). Trade-off: each run now checks a log before sending, which adds about a second per run.

Each section has the same three parts: a claim in one sentence, one number with its source, and a trade-off where one applies. Fill the six sections from your card.

Test before moving on. Open each link in your "my part" section and check it opens the right PR. Export the note to PDF from your editor, then open the PDF and check that it is one page. If it runs onto a second page, cut words, not sections.

#### 3. Draw the architecture sketch (Y2-T59.3)

Goal: a drawing in data-flow order, where the arrows follow the path the data takes from its source to where it is shown or stored. Each part you built carries a star.

Stage 1: list the parts. Write the parts in the order data passes through them. Use the README of your repository to get the names right. For each part, mark whether you built or changed it, and mark those with a star.

Stage 2: draw in order. Start with the source on the left or at the top. Draw one box per part and one arrow per hand-over. Label each arrow with what travels along it, such as "request" or "rows". Do not draw parts that are not in the data path, such as a document folder, unless the trainer asks for them.

Stage 3: practise against the clock. Use the timer from TC2. Draw the sketch three times, and stop when the time is 50 seconds or less each time.

Test before moving on. Cover your notes, redraw the sketch from memory, and count the boxes and arrows. Compare with your list from Stage 1. Any missing arrow means the redraw is not complete.

#### 4. Write the why questions (Y2-T59.4)

Goal: five questions, one for each layer you touched, each with a 2 to 3 sentence answer, and one answer of 45 seconds for a trade-off.

A layer is one part of the data path, such as the source, the fetch, the storage, the report or the monitoring. Write a question that asks "why" about a choice in that layer. Interviewers ask "why" again and again, so write your answers so that each one can be followed by a further question.

Teach the answer shape first. Use the three parts from the viva section: claim, evidence, trade-off. Fictional example for a book-loan app:

> Question: Why do you store loans in a database table rather than a spreadsheet?
> Answer: Loans need to be filtered by member and date, and a table can return just those rows. A spreadsheet would be read and filtered in full on every page load. The cost is that I must keep the table columns correct, and I check the columns with a test before each release.

Stage 1: write five questions, one for each layer. Stage 2: write each answer in 2 to 3 sentences, with one number where you can. Stage 3: choose one question that is about a trade-off, and write its answer so you can say it in 45 seconds.

Test before moving on. Read each answer aloud with a stopwatch. The 2 to 3 sentence answers should take 15 to 25 seconds. The trade-off answer must finish within 45 seconds.

#### 5. Run the grill (Y2-T59.5)

Goal: deliver the deep-dive, take five peer why questions, receive the rubric score, and revise the weak answers.

The loop works as follows.

```flow
TITLE: One round of the grill
NODES: You | Peer griller | Rubric sheet
STEPS:
1>2 :: deliver the deep-dive :: You talk through the note and the sketch, in about two minutes.
2>1 :: why question 1 to 5 :: The peer asks each question in turn. Answer in order, and say what you know first.
1>2 :: answer :: Give the claim, the number and the trade-off, then stop. Do not fill the time with history.
2>3 :: score :: The peer scores each answer on the rubric from the course page.
3>1 :: weak answers :: Any answer with a low score goes back on your list to revise before the next session.
```

Stages: deliver, answer, collect the score, then revise. Write the score down, and write the revised answer below the weak one. Do not change the note itself, unless a number on the card is wrong.

Test before moving on. Ask a peer to confirm the score you have recorded. The score must be 3 out of 5 or more. If it is lower, revise the weakest two answers and grill again.

#### 6. Grill your squad-mates (Y2-T59.6)

Goal: ask five bank questions to each squad-mate you grill, then score each answer with the rubric.

The ticket does not say where the "bank" questions come from: they may be the squad-mate's own five why questions or a list from your trainer. Ask your trainer which one to use before the grill starts.

Scoring is harder than asking. Score what the answer says, not how confident the speaker sounds. Give a reason for any score of 2 or less, in a few words, so the speaker knows what to fix.

Keep your scores in a file outside the repository, so they do not get committed by mistake. Run this in Git Bash.

```bash
echo "$(date +%F), squad-mate A, Q1: 4, reason: named the source file" >> ~/grill-notes.txt
```

The parts:

- `echo` prints the text it is given.
- `"$(date +%F)"` prints today's date in the form `2026-11-17`.
- `>> ~/grill-notes.txt` appends the line to a file in your home folder. One `>` would replace the whole file. Two `>>` add to the end.

Expected output: nothing on screen. Then `cat ~/grill-notes.txt` prints every line you have saved. Check that the list has one line per question.

Test before moving on. Read the notes back at the end of the session and check that you have five questions for each squad-mate.

#### 7. Upload and confirm (Y2-T59.7)

Goal: the note and sketch are uploaded to the LMS by 23:59 on the same day, and the technical mock is confirmed by 20:30.

Stage 1: put the note in the repository on its own branch, and open a PR. The commands below run in Git Bash.

```bash
git add docs/deep-dive.md docs/deep-dive-numbers.md
git commit -m "docs: add deep-dive note with numbers card"
git push -u origin y2-t59-deep-dive
```

The parts:

- `git add` stages the named files, so they are included in the next commit.
- `git commit -m` records the commit with the message in quotes.
- `git push -u origin y2-t59-deep-dive` sends the branch to GitHub, and `-u` links it so later pushes need no name.

Expected output: a line such as `Branch 'y2-t59-deep-dive' set up to track 'origin/y2-t59-deep-dive'.` The file names here are examples. Use your own.

Stage 2: upload the PDF of the note and a photo or PDF of the sketch to the LMS. Do this before 23:59 on the same day.

Stage 3: check the tracker. Confirm with the trainer by 20:30 that your technical mock is complete, and bring the interviewer's name and the date if you need them.

Test before moving on. Open the LMS upload and check the file opens and is the right version. Open the tracker, filter it to your name, and check the status reads `completed`.

|---|---|---|
| `sed -n 'LINEp'` prints a different line from the one on the card | Lines were added or removed above the number after the card was made | Run `grep -nE "PATTERN" FILE` again, find the new line, and update the row |
| The note runs onto a second page when exported | Too many words in the arc sections, or a long sketch pasted in | Cut words from the trade-off sentences first, then shorten the sketch notes |

### Defend it in the viva

Each question is followed by a model spoken answer. The model answers show the reasoning. They do not give you a history to copy. Replace the square-bracket parts with the numbers and files from your own repository.

**1. Why did you choose a serverless fetch instead of a virtual machine?**

:::answer Model answer
My claim is that the fetch runs as a serverless function, because it runs for a short time on a schedule and I pay only for those runs. My evidence is in [the cost doc path, line X]: the function runs [N] times a month, each run takes about [T] seconds, and the monthly cost is [amount] from the cost doc. A virtual machine would be switched on all month, so most of its hours would be idle. The trade-off is that the function has a time limit, so a long job would need a different service. I accept that because the fetch finishes well inside the limit.
:::

**2. What is the main trade-off in your design?**

:::answer Model answer
The main trade-off is [name the cost you accepted]. My evidence is [the number and its source]. I accepted it because [the benefit, with its number and source]. If the job grew past [the limit in your docs], I would move it to [the alternative your docs name]. Say the cost first, then the reason.
:::

**3. What did you personally build in this system?**

:::answer Model answer
I built [the component, named as it appears in the README] and I changed [the second piece, if any]. My evidence is [PR number and title, with its link]. I starred those parts on my sketch. For the part I built, I can explain what each function does, what it returns and how I tested it. A teammate built [the other parts], and I can explain how my part connects to theirs.
:::

**4. How do you know your numbers are right?**

:::answer Model answer
Every number on my card has a source file and a line. I check each one with the same command, `sed -n` on the line, and the value in the note matches the value in the file. If a number came from a run, such as a CI run or a monitoring figure, I name the run or the dashboard. If two sources disagree, I say so and explain which one I trust and why.
:::

**5. What would you do if you were asked about something you do not know, such as a service you have not used?**

:::answer Model answer
I would say what I know about the nearby idea, then say how I would find out. For example, I might say I know how a scheduled function is triggered, but I have not measured the exact start delay. I would check the provider's documentation for the start delay, and then measure it in the logs of my own runs. I would not guess a figure, and if I offered an estimate, I would label it as an estimate.
:::

### Check yourself

```quiz
Q: Your note says the monthly run count is 1440, and the trainer opens the source file. Which command shows the exact line you quoted?
- grep -c "1440" docs/cloud-cost.md
* sed -n '42p' docs/cloud-cost.md
- git log --oneline docs/cloud-cost.md
- gh pr list --state merged
WHY: sed -n '42p' prints exactly line 42, so you can compare the value with your card. grep -c only counts matching lines, and git log shows history, not the value on a line.
```
