### The ticket in plain words

CityPulse now runs on its own. A script fetches city data on a timer, and five students change the same code. Until now, anyone could push a change straight onto `main`, the shared main line of the repository. One careless push can break the data for the whole squad.

This ticket moves the squad to **GitHub flow**, the way most software teams work. Each student takes one small task card, called an **Issue**, and works on a **feature branch**, a separate line of work. When the change is ready, the student opens a **pull request** (PR), which asks for that branch to be merged into `main`. Two squad-mates read the change, run it and comment. The author answers with new commits, and only then does the change merge.

The Tech Lead also turns on **branch protection**, a GitHub rule that refuses direct pushes to `main` and requires an approval first. GitHub enforces it, so nobody can skip it under deadline pressure.

A comment that says only "LGTM" (short for "looks good to me") scores zero. A useful review says what you ran, what input you used and what you saw.

### Before you start

The spec says Y2-T07 must be complete: the tag `v0.1-p1` exists, `fetch.sh`, `healthcheck.sh` and `merge.sh` are on `main`, the Project board holds at least ten Issues, and the trainer has recorded the **baseline**, the commit hash of `main` at the end of Y2-T07.

You need a GitHub account with write access to the squad repository, Git and the GitHub command-line tool `gh` on your laptop, and your squad-mates' usernames. Run the commands in Git Bash, not PowerShell, because the quoting rules differ. Run these checks inside your clone of the squad repository.

### Words you need

| Term | Plain meaning |
|---|---|
| `main` | The shared main line of the code. Everyone builds from it. |
| Branch | A movable name that points at a line of commits. |
| Baseline | The commit hash that marks the end of Y2-T07. Later tests ignore everything before it. |
| Issue | A task card on GitHub with a number, such as #31. |
| Pull request (PR) | A request to merge one branch into another, with the diff, comments and checks on one page. |
| Review | A reader's verdict on a PR: comment, request changes or approve. |
| Thread | A group of comments on one point. A thread can be marked resolved. |
| Template | The file `.github/PULL_REQUEST_TEMPLATE.md`, which pre-fills every new PR description. |
| `Closes #n` | A phrase in the PR body. When the PR merges, GitHub closes Issue n. |
| Squash merge | Joining a PR as one new commit on `main`, which combines the PR's commits. |
| First parent | The line of commits that `main` itself follows, not the commits inside a merged branch. |
| Branch protection | A GitHub rule that refuses direct pushes and requires reviews before a merge. |
| `enforce_admins` | The protection setting that applies the rule to administrators too. |

:::key Why the baseline matters
The last two test cases look only at commits after the baseline hash. Earlier commits, from earlier tickets, are out of scope.
:::

### How your trainer checks it

The trainer checks five acceptance criteria with five test cases. Replace `<squad>` with your squad name and `<n>` with a PR number.

- **Criterion 1**: five merged PRs, one per student, each with `Closes #<n>` and the template sections. TC1 checks the count, the authors and `Closes #`. The trainer reads the template sections by eye.
- **Criterion 2**: at least two review comments per PR, and every thread resolved. TC2 counts the comments.
- **Criterion 3**: each student reviewed two PRs, with a comment that is not just "LGTM". Check with the reviews command in Y2-T08.5.
- **Criterion 4**: a direct push to `main` is rejected. TC5 tests this.
- **Criterion 5**: every commit after the baseline references a PR. TC4 tests this.

#### TC1: merged PRs with the closing keyword

```
gh pr list --state merged --search 'merged:>=2026-11-24' --json number,author,body --jq '.[] | [.number,.author.login,(.body|test("Closes #"))] | @tsv'
```

- `gh pr list` lists pull requests in the repository you are standing in.
- `--state merged` keeps only merged PRs.
- `--search 'merged:>=2026-11-24'` uses GitHub search syntax to keep PRs merged on or after the date in the ticket.
- `--json number,author,body` asks for three fields, as JSON.
- `--jq '...'` filters the JSON with a jq program. Single quotes stop the shell changing it.
- `.[]` takes each PR in turn. `[...]` builds a list of the number, the author's login and one true or false value.
- `.body|test("Closes #")` checks the body for the exact text `Closes #`. It is case sensitive, so `closes #` in lower case gives `false`.
- `| @tsv` prints each list as one tab-separated line.

Passing output has at least five rows, five distinct authors, and `true` on every row:

```term
$ gh pr list --state merged --search 'merged:>=2026-11-24' --json number,author,body --jq '.[] | [.number,.author.login,(.body|test("Closes #"))] | @tsv'
14	alex-k	true
15	meera-s	true
16	ravi-n	true
17	tara-v	true
18	dev-s	true
```

A failing `false` on a row means that PR's body lacks `Closes #`. Fix the PR description, and the trainer reads the new text. Write `Closes #` with a capital C, because the trainer's jq test is case sensitive.

#### TC2: at least two review comments per PR

```
gh api repos/citypulse-y2/citypulse-<squad>/pulls/<n>/comments --jq 'length'
```

- `repos/citypulse-y2/citypulse-<squad>` is the squad repository.
- `pulls/<n>/comments` lists the review comments on PR n, which are the comments attached to lines of the diff.
- `--jq 'length'` counts the items returned.

Passing output is `2` or more. A failing `0` or `1` usually means the reviewer wrote in the conversation box or in a review summary, and those are not counted.

TC2 does not check that threads are resolved, but criterion 2 does. Check it yourself on the PR page, where each thread shows a Resolved label, or run this and expect only `true` lines:

```
gh api graphql -f query='query { repository(owner:"citypulse-y2", name:"citypulse-<squad>") { pullRequest(number: <n>) { reviewThreads(first: 50) { nodes { isResolved } } } } }' --jq '.data.repository.pullRequest.reviewThreads.nodes[].isResolved'
```

#### TC3: one approval required on main

```
gh api repos/citypulse-y2/citypulse-<squad>/branches/main/protection --jq '.required_pull_request_reviews.required_approving_review_count'
```

- `repos/.../branches/main/protection` is the protection rule for `main`.
- `.required_pull_request_reviews` picks the review section of the JSON.
- `.required_approving_review_count` picks the number of approvals required.

Passing output is `1` (or more). Failing output is `null` or `0`, which means the rule does not require reviews. A not-found error that says the branch is not protected means no rule exists yet.

#### TC4: every commit after the baseline references a PR

```
git fetch origin
git log --first-parent --format='%h %s' <baseline>..origin/main
```

- `git fetch origin` downloads new commits without changing your files.
- `--first-parent` follows only the line that `main` follows, so each merged PR appears as one line.
- `--format='%h %s'` prints the short hash, a space and the subject line.

Passing output has every subject ending in `(#<n>)` or containing `Merge pull request #<n>`. A failing line has no PR reference, such as `a1b2c3d Fix typo in healthcheck.sh`. The usual cause is a commit pushed straight to `main`. Tell the Tech Lead at once, and do not rewrite `main` to hide it.

#### TC5: direct push rejected

```
git commit --allow-empty -m test && git push origin main
```

- `git commit --allow-empty` creates a commit that changes no files, and `&&` runs the push only if it worked.

Passing output is a refusal that contains the words `protected branch hook declined`. The exact wording depends on GitHub. A failing run says the push succeeded, which means the rule is missing or administrators are not covered. That also leaves a commit with no PR on `main`, which then fails TC4, so tell the Tech Lead at once. Run this only in a throwaway clone, never in your working clone.

### Do it, step by step

#### Y2-T08.1: Add the pull request template (Tech Lead)

**Goal.** Put a file at `.github/PULL_REQUEST_TEMPLATE.md`. GitHub reads this exact path and fills every new PR description with it.

**Stage 1: branch from main.**

```
git switch main
git pull --ff-only
git switch -c chore/pr-template
```

`git pull --ff-only` refuses if it cannot move your `main` forward in a straight line, for example when your `main` has commits of its own that origin lacks. You should see `Switched to a new branch 'chore/pr-template'`.

**Stage 2: create the folder and the file.**

```
mkdir -p .github
```

`-p` creates missing parent folders, and it does nothing with no error if the folder already exists. Create the file in your editor, with these headings in this order, and a short prompt under each in your own words:

```text
## What
## Why
## How to test
## Evidence
## Checklist
```

The Checklist should remind the author to write `Closes #<n>`, with a capital C.

**Stage 3: commit, push and open the PR.**

```
git add .github/PULL_REQUEST_TEMPLATE.md
git commit -m "Add pull request template"
git push -u origin chore/pr-template
gh pr create --fill --reviewer <name>
```

`git push -u` uploads the branch and links it to origin. `gh pr create --fill` builds the title and body from the commit message, and prints the PR URL.

**Stage 4: merge after one review.**

```
gh pr merge <n> --squash --delete-branch
```

`--squash` makes one commit on `main`, and `--delete-branch` removes the branch.

**How to test.** Run `gh api repos/<owner>/<repo>/contents/.github/PULL_REQUEST_TEMPLATE.md --jq .name`. It should print `PULL_REQUEST_TEMPLATE.md`.

:::trap Protecting main before the template is merged
The ticket orders the template first. Merge it, then protect `main`. If you protect first, the template PR still needs an approval, and a mistake in your first rule is harder to fix while every merge waits on a review.
:::

#### Y2-T08.2: Turn on branch protection (Tech Lead)

**Goal.** Make GitHub refuse direct pushes to `main` and require one approval.

**Stage 1: check the current state.**

```
gh api repos/<owner>/<repo>/branches/main/protection
```

Before any rule exists, this prints an error containing `Branch not protected` (HTTP 404). You need admin rights on the repository for this call.

**Stage 2: set the rule.** On the website, open Settings, then Branches, and add a classic branch protection rule for `main` (TC3 reads this kind of rule, not a newer "ruleset"). Tick the options to require a pull request before merging, to require one approval, and to include administrators. GitHub's newer wording for the last one is "Do not allow bypassing the above settings". Take a screenshot for the LMS.

**Stage 3: test.** Run TC3. It should print `1`.

:::key What include administrators means
Without `enforce_admins`, administrators could still push straight to `main`. TC5 checks this setting.
:::

#### Y2-T08.3: Take an Issue and branch

**Goal.** Have one Issue that is yours, on a branch that starts from the latest `main`.

**Stage 1: choose the Issue.** On GitHub, open an Issue from the board and assign yourself. Move its card to In progress in the browser.

**Stage 2: update main and create the branch.**

```
git status
git switch main
git pull --ff-only
git switch -c feat/<n>-<slug>
git branch --show-current
```

`git switch -c` creates the branch from the commit you are on, which is now the latest `main`. `git branch --show-current` prints the branch name so you can confirm it.

:::trap Branching from a stale main
A new branch starts at the commit you are on. If you skip the pull, your PR will include other people's old work.
:::

#### Y2-T08.4: Implement, commit, push and open the PR

**Goal.** Make small commits, push the branch and open a PR the reviewers can run.

**Stage 1: stage only your change.**

```
git add -p <file>
```

`-p` shows each changed block and asks whether to stage it. Type `y` or `n` for each block.

**Stage 2: commit and check.**

```
git commit -m "Add usage message when an option gets no value"
git show --stat HEAD
```

`git show --stat HEAD` lists the files in the latest commit. If an unexpected file appears, run `git reset --soft HEAD~1`, which undoes the commit but keeps your edits, and stage again.

**Stage 3: test on the lab machine.** Run the change exactly as the Issue describes, on the lab Linux machine where the scripts run. Save the command and its output for your PR evidence.

**Stage 4: push.**

```
git push -u origin feat/<n>-<slug>
```

**Stage 5: open the PR.** Write the PR body in a file first, which avoids quoting problems in Git Bash. Fill in the template in your own words, with `Closes #<n>`. Then run:

```
gh pr create --base main --title "<your title>" --body-file <file> --reviewer <name1>,<name2>
```

`--body-file` reads the description from your file. `--reviewer` takes two names with a comma and no spaces.

**Stage 6: check the body.**

```
gh pr view --json body --jq .body | grep -c "Closes #"
```

The output should be `1`.

```flow
TITLE: One pull request from push to merge
NODES: Your laptop | GitHub | Reviewer
STEPS:
1>2 :: git push -u origin feat/<n>-<slug> :: The branch travels to GitHub, and the PR opens against main.
2>3 :: review requested :: GitHub tells the reviewer that the PR is waiting.
3>2 :: request changes :: The reviewer runs the branch and posts a comment with evidence.
1>2 :: fix commit pushed :: You add a commit to the same branch, and the PR updates by itself.
2>3 :: re-review :: The reviewer runs the fix again.
3>2 :: approve :: The reviewer approves, and the PR can merge.
```

:::trap Opening a second PR for a fix
A PR follows its branch. Push fixes to the same branch, or the review history splits.
:::

#### Y2-T08.5: Review two PRs by running them

**Goal.** Give two PRs a substantive review, each with a verdict.

**Stage 1: find the PRs.**

```
gh pr list --search 'review-requested:@me'
```

**Stage 2: check out and run.**

```
gh pr checkout <n>
```

This downloads the branch and switches your clone to it. Run the PR's "How to test" steps, save the output, and return with `git switch` to your own branch.

**Stage 3: write the comment.** A useful comment states what you ran, the input, what you saw and what you suggest:

```text
I ran <command> with <input>. It printed <what you saw>. I suggest <change>, because <reason>.
```

**Stage 3b: attach it to a line.** TC2 counts only comments on lines of the diff. In the browser, open the PR's Files changed tab, click the `+` beside the line you tested, write your comment and choose Start a review. Add a second line comment if you can. The next stage then submits the review.

**Stage 4: post the verdict.** The `--body` text becomes the review summary, which TC2 does not count, so the line comments from stage 3b matter.

```
gh pr review <n> --comment --body "<your comment>"
gh pr review <n> --request-changes --body "<your comment>"
gh pr review <n> --approve --body "<your comment>"
```

Choose the verdict that matches what you found.

**How to test.**

```
gh api repos/<owner>/<repo>/pulls/<n>/reviews --jq '.[] | select(.user.login=="<your-login>") | .state'
```

`select(...)` keeps only your reviews, and `.state` prints each verdict: `APPROVED`, `CHANGES_REQUESTED` or `COMMENTED`.

:::trap Writing LGTM and nothing else
"LGTM" on its own earns no credit. Say what you ran, with what input, and what you saw.
:::

#### Y2-T08.6: Address comments, resolve, merge and clean up

**Goal.** Answer every comment, push fixes, resolve each thread and merge.

**Stage 1: fix and push.**

```
git add <file>
git commit -m "Address review: <short description>"
git push
```

**Stage 2: reply, resolve and re-request.** Reply on each thread, mark it resolved, and ask the reviewer to look again. A reviewer who requested changes must approve again.

**Stage 3: merge and clean up.**

```
gh pr merge <n> --squash --delete-branch
git switch main
git pull --ff-only
```

**How to test.**

```
git fetch origin
git log --oneline -1 origin/main
```

The subject should end with `(#<n>)`, the form TC4 checks.

:::trap Deleting the branch before the merge
Deleting a branch closes its PR without merging it. Merge first, then delete.
:::

#### Y2-T08.7: Confirm the Issues and the evidence (Scrum/Docs)

**Goal.** Every Issue is closed and every card is in Done.

For each Issue number, run:

```
gh issue view <n> --json state --jq .state
```

The answer should be `CLOSED`. Then move each card to Done on the board, and post the PR links and the protection screenshot to the LMS.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| TC1 shows `false` for your PR. | The body says `closes #` in lower case, or the line is missing. | Edit the PR description to use `Closes #<n>`. |
| TC1 shows four distinct authors, not five. | One student merged two PRs and another merged none. | Agree who merges next. |
| TC2 shows `0` or `1`. | The comments are in the conversation box, not on diff lines. | Ask the reviewer to comment on specific lines. |
| TC3 shows `null`. | The rule does not require reviews, or no rule exists. | Ask the Tech Lead to check Y2-T08.2. |
| TC4 shows a commit with no `(#n)`. | A commit was pushed straight to `main`. | Tell the Tech Lead at once. Do not rewrite `main`. |
| TC5 push succeeds. | `enforce_admins` is off. | Ask the Tech Lead to turn it on, then run TC5 again. |
| `git pull --ff-only` refuses. | Your local `main` has diverged: it has commits of its own and origin has new ones. | Stop and ask for help. Find out where the commits came from. |
| The Issue stays open after merge. | The PR body lacked `Closes #<n>`. | Edit the body, then close the Issue by hand and note why. |

### Defend it in the viva

**1. Why must branch protection include administrators?**

:::answer Model answer
The rule exists so that nobody skips the review. Without `enforce_admins`, the Tech Lead could push straight to `main` under deadline pressure. The setting applies the same rule to everyone, and TC5 proves it by refusing a direct push.
:::

**2. What is the trade-off between a squash merge and a normal merge commit?**

:::answer Model answer
A squash merge gives `main` one commit per PR, which keeps history short. The cost is that the branch's individual commits are no longer on `main`, so the detail lives on the PR page.
:::

**3. Walk me through one review you gave. What did you run, and why did you write what you wrote?**

:::answer Model answer
Name the PR, the exact command you ran after `gh pr checkout`, the input you used and what the output showed. Explain your verdict. A comment needs evidence, because "LGTM" alone earns nothing. Describe only a review you really gave.
:::

**4. A required approval slows every merge. Why is it still worth it?**

:::answer Model answer
The wait is short, and a second person reads the diff and runs the code before the change reaches the shared line. An error caught there is far cheaper than a broken fetch that nobody notices for a day.
:::

**5. What does `git log --first-parent` show, and why does TC4 use it?**

:::answer Model answer
It follows only the line of commits that `main` itself follows, so each merged PR appears as one line. TC4 can then check that each line references a PR number. Without the flag, commits inside merged branches would appear too, and some would have no PR reference.
:::

### Check yourself

```quiz
Q: A teammate approves your PR and writes only "LGTM". Under this ticket, what does that review earn?
- Full credit, because an approval is evidence.
- Half credit, because the approval was given.
* Zero, because it says nothing about what was run or seen.
- Credit for the PR, but not for the reviewer.
WHY: The ticket says "LGTM" alone scores zero. The approval is a verdict, but without what was run and seen it is not evidence. The tempting wrong answer is full credit, because an approval looks like a sign-off.

Q: Which flag makes gh pr merge combine all the PR's commits into one commit on main?
- --merge
* --squash
- --rebase
- --first-parent
WHY: The squash flag makes one commit on main, with the PR number added to its subject. The merge flag keeps every commit, and --first-parent is a git log option, not a gh merge option.

Q: The Tech Lead can push straight to main even though the rule requires one approval. Which setting closes that gap?
- required_approving_review_count
- --force-with-lease
- --first-parent
* enforce_admins
WHY: enforce_admins applies the protection rule to administrators. The approval count sets how many approvals are needed, but it does not stop an exempt administrator. The tempting wrong answer is the approval count, which is part of the rule but does not cover exempt users.
```
