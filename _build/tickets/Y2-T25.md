### Words you need

| Term | Plain meaning |
|---|---|
| Identity | The account that a program or person uses to ask AWS for something. |
| IAM | Identity and Access Management, the AWS service that defines identities and what they may do. |
| Profile | A named set of AWS credentials in your local AWS configuration, chosen with `--profile`. |
| ARN | Amazon Resource Name, a unique text address for an AWS identity or resource. |
| Scoped identity | An identity limited to the few actions it needs, and nothing more. |
| AccessDenied | The AWS error that means the identity is not allowed to do that action. |
| Access key | A pair of text values that let a program sign in as an identity. Long-lived keys are risky. |
| Static key | An access key stored in a file or setting that never changes, which is the thing to avoid on a VM or function. |
| Bucket | A container for stored files in Amazon S3. Its files sit under keys, which work like folder paths. |
| Object | One stored file in a bucket, identified by its key, which is its path inside the bucket. |
| Public-access block | A bucket setting that stops the bucket and its objects being made public. |
| Anonymous access | A request made with no identity at all, as an anonymous visitor on the internet would make it. |
| HTTP status code | The three-digit answer a web server sends, such as 200 for success or 403 for forbidden. |
| Security group | A set of firewall rules that control which network traffic may reach a virtual machine. |
| Port 22 | The network port used by SSH, the remote login protocol for Linux machines. |
| 0.0.0.0/0 | A network range meaning every address on the internet. Open port 22 to it is a serious risk. |
| Elastic IP | A fixed public IP address that AWS rents to you. It keeps billing when it is not attached to a running machine. |
| EBS volume | The disk attached to a virtual machine. It keeps billing even when the machine is stopped. |
| Secret | Any value that proves who you are, such as a key, a token or a password. |
| gitleaks | A tool that scans files and Git history for secrets. |
| Git history | The full list of commits in a repository, including commits that deleted something later. |
| Rotation | Replacing a secret with a new one, and disabling the old one, so that the old value no longer works. |
| Deactivate | Turn an access key off without deleting it, so that it can no longer sign in. |
| pre-commit hook | A check that runs automatically when you try to make a commit, and blocks the commit if it fails. |
| Teardown | Deleting the resources that cost money once the lab is finished. |
| Tag | A fixed name on one commit, such as `v0.4.0`, which marks a version. |
| GitHub Release | A published version attached to a tag, with a title and notes. Made with the `gh` command-line tool. |

### How your trainer checks it

Five test cases check most of the six acceptance criteria. The rest are checked from your repository and the LMS.

#### TC1: identity works and cannot write to the secret prefix

The trainer's steps are in two commands, which you run in your own account on screen.

```bash
aws sts get-caller-identity --profile citypulse-pipeline
aws s3 cp x s3://<bucket>/secret/x --profile citypulse-pipeline
```

- `aws` starts the AWS command-line tool.
- `sts` is the security token service. `get-caller-identity` asks AWS who you are right now. It is the first thing to show, so the trainer knows which identity is speaking.
- `--profile citypulse-pipeline` tells the tool to use the named set of credentials, not the default ones. Without it you may run as an administrator, which proves nothing.
- `s3 cp x s3://<bucket>/secret/x` copies the local file `x` into the bucket under the `secret/` prefix. The `<bucket>` is your bucket's name from your README.

Create the local file first with `echo "test" > x`. The copy must be refused. Lines starting with `$` are commands you type.

```term
$ aws sts get-caller-identity --profile citypulse-pipeline
{
    "UserId": "AIDAEXAMPLEID",
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/citypulse-pipeline"
}
$ aws s3 cp x s3://example-bucket/secret/x --profile citypulse-pipeline
upload failed: ./x to s3://example-bucket/secret/x An error occurred (AccessDenied) when calling the PutObject operation: Access Denied
```

The values are fictional; yours will differ. If the copy succeeds and prints `upload: ./x to s3://...`, the test fails. The usual cause is a policy from T17 that allows `s3:PutObject` on the whole bucket instead of only on the prefixes it needs. If the ARN shown is not `citypulse-pipeline`, you used the wrong profile. If you see `Unable to locate credentials`, the profile is missing from `~/.aws/credentials`.

#### TC2: anonymous access to an object returns 403

The trainer runs this command on a private object in your bucket, using the object's web address.

```bash
curl -s -o /dev/null -w '%{http_code}' <object-url>
```

- `curl` sends a web request with no login, so it is anonymous.
- `-s` hides the progress meter.
- `-o /dev/null` discards the response body. `/dev/null` is a place that throws away anything written to it.
- `-w '%{http_code}'` prints only the three-digit status code. The quotes stop the shell reading the braces.
- `<object-url>` has the form `https://<bucket>.s3.<region>.amazonaws.com/<key>`.

A passing run prints exactly this and nothing else:

```text
403
```

A 200 means the public can read the object, the public-bucket mistake from the case study. A 404 usually means the bucket name or address is wrong, so the test proved nothing. Note that on a private bucket a missing key also gives 403, so copy the URL of an object that really exists. `000` usually means no network or a mistyped domain.

#### TC3: gitleaks finds nothing in the whole history

The trainer runs the scan from the repository root.

```bash
gitleaks detect --source . --log-opts=--all
```

- `gitleaks detect` scans the contents and history of a repository for secrets.
- `--source .` scans the current folder.
- `--log-opts=--all` passes `--all` to `git log`, so every branch and commit is scanned. A key deleted later is still in the history.

A passing run prints a log line ending `no leaks found`. A failing run prints a line such as `leaks found: 1` with the file and commit. Never copy the secret into evidence. The fix is in the T25.3 section below: deactivate the key and show the rotation outside Git.

#### TC4: teardown leaves nothing that costs money

The trainer runs `bash scripts/teardown_check.sh` after your teardown. Read the script before the review so nothing surprises you on screen.

A passing run shows an empty Instances section, an empty unattached IPs list, and a bucket line ending `True`, which means its public-access block is on. No schedule from T23 may remain.

A failing run lists a stopped instance, which means the teardown skipped that machine, usually because its owner tag does not match the name you passed. A bucket line ending `False` means its public-access block is off.

#### TC5: the tag and the release exist

The trainer runs this on the main branch.

```bash
git tag -l v0.4.0 && gh release view v0.4.0
```

- `git tag -l v0.4.0` lists tags whose names match `v0.4.0`.
- `&&` runs the second command only if the first one exits without error.
- `gh release view v0.4.0` prints the release title, its tag and its notes.

`git tag -l` exits successfully even when nothing matches, so `&&` still runs `gh`. Read the first command's output too. Empty output means no tag. A `release not found` message means the tag exists but no Release was created.

#### The acceptance criteria that tests do not cover

- **Three labs working, 3/3.** The trainer watches live output, not an old screenshot.
- **Security proof for each lab.** AccessDenied, a 403, no port 22 open to 0.0.0.0/0, and no static keys. Check the port rule with `aws ec2 describe-security-groups --filters "Name=ip-permission.from-port,Values=22" "Name=ip-permission.cidr,Values=0.0.0.0/0" --query "SecurityGroups[].GroupId" --output text`. #### Y2-T25.3: gitleaks and the pre-commit hook

Do this first. A scanner that runs only once at the end finds mistakes too late.

**Stage 1. Check the scanner.** Run `gitleaks version`. If it fails, install gitleaks from its official releases page and reopen Git Bash.

**Stage 2. Write the hook configuration.** Create `.pre-commit-config.yaml` at the repository root. A pre-commit configuration lists the external hook repositories to run. Here is the structure. You fill in the two values marked with angle brackets.

```yaml
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: <release tag from the gitleaks releases page>
    hooks:
      - id: gitleaks
```

- `repos:` lists the hook sources. `repo:` is the address of one of them.
- `rev:` pins the hook to one release tag, so it cannot change without notice. Copy the tag from the gitleaks releases page.
- `hooks:` and `id: gitleaks` name the hook to run.

**Stage 3. Install the hook and test it.** Install pre-commit once, then install the hook into your local clone:

```bash
pip install pre-commit
pre-commit install
pre-commit run --all-files
```

- `pip install pre-commit` installs the tool.
- `pre-commit install` writes a hook into `.git/hooks`, so every commit runs the checks first.
- `pre-commit run --all-files` runs every hook now. The gitleaks line should end `Passed`.

**Stage 4. Run the scan on full history.** This is TC3. Run `gitleaks detect --source . --log-opts=--all`. The last line should end `no leaks found`. Run it live in front of the trainer, then paste the result into the pull request description.

**If gitleaks finds a leak.** Do not paste the secret anywhere. Use the AWS command line to find the key by its ID, deactivate it, and create a replacement outside Git:

```bash
aws iam list-access-keys --user-name <user> --profile <admin-profile>
aws iam update-access-key --user-name <user> --access-key-id <key-id> --status Inactive --profile <admin-profile>
```

- `list-access-keys` prints the key IDs and their status for one user. It never prints the secret part.
- `update-access-key` with `--status Inactive` turns the key off. The old value no longer works, even though it is still in the history.
- `--profile <admin-profile>` names a profile that has permission to manage keys. Your pipeline profile usually cannot do this, which is correct.

Show the status list with the key `Inactive`, and the new key set up in your local profile, never in the repository. Rerun gitleaks. The history keeps the old value, so the deactivation is the fix.

### Defend it in the viva

The trainer asks five questions. Answer in your own words, and use your own evidence. Do not copy the model answers as your personal history.

**Question 1: Why must the identity test show AccessDenied, rather than just a successful sign-in?**

:::answer Model answer
A sign-in shows only that the identity exists. AccessDenied shows that AWS actually refused a forbidden action, so the limit is proven, not assumed.
:::

**Question 2: Why do you keep the bucket but delete the function and the virtual machine? Name the trade-off.**

:::answer Model answer
The bucket holds data the analytics sprint needs. The function and VM cost money while idle. The trade-off is a small storage cost in exchange for keeping the data. The teardown check proves nothing else remains.
:::

**Question 3: Walk me through what you personally did in this ticket.**

:::answer Model answer
Name your own commits by SHA, the file each one changed, and the command you ran to check it. Prepare these from your own git log before the viva.
:::

**Question 4: Why is removing a leaked key in a new commit not enough?**

:::answer Model answer
Git keeps every earlier commit, so anyone who clones the repository can recover the key. Deactivating it in AWS stops it signing in. Rewriting history is a team decision and does not replace rotation.
:::

**Question 5: What does the 403 in TC2 prove, and what would a 200 mean?**

:::answer Model answer
The 403 means AWS refused a request with no identity, so the public cannot read the object. A 200 would repeat the public-bucket mistake from the case study.
:::
