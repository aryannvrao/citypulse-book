### The ticket in plain words

This ticket is the last freeze before the hiring day on 1 May. Your portfolio is a small website, hosted by GitHub, that shows the projects you built. Internship partners and the hiring panels will open the links you give them, and they must see exactly the version your trainer has checked. A portfolio that keeps changing after the check is a problem, because nobody can say what was approved.

The ticket solves this with two ideas. First, you freeze the portfolio at one commit. A commit is a saved set of changes in Git, the version-control tool you met on Day 1. Git gives each commit a long code called a SHA, which is a fingerprint of that exact content. If the SHA you submit still matches the newest version of your repository at 20:30, then the panels see what the trainer approved. Second, you prove the portfolio is in good shape before you freeze it. You go through the D08 checklist, mark each item yes with a link that opens, and fix whatever fails: broken links, a title that does not match your CV, numbers that are missing, or a page that breaks on a phone.

The ticket also asks for two pieces of writing that only you can produce: a 30-day internship plan with four weeks of dated actions, and a confirmation of the 1 May logistics on the LMS, the course's learning management system. Your submission is due before 20:30 and includes your portfolio URL, your SHA, the checklist and the plan. The squad's Scrum/Docs student then confirms that all five squad submissions are in before 20:15.

Your job in this guide is to learn the tools you need to check your own work, so that when your trainer runs the tests you already know the result.

### How your trainer checks it

Your trainer runs the tests on their own machine, after 20:30. You cannot run all of them, but you can run a version of each so that nothing surprises you. This section explains what the trainer does and what passing and failing look like.

The ticket has five acceptance criteria. Each one is a test you can check yourself before review.

1. **Checklist.** Every item on the D08 checklist is `yes` after the trainer verifies it, and every item has an evidence link that opens. Check this by opening each link in a private browser window, which behaves like a visitor who is not logged in.
2. **Freeze match.** The SHA you submitted equals what `git ls-remote origin HEAD` returns when the freeze script runs at 20:30. Check this yourself with the commands in TC1.
3. **Broken links.** A link checker finds 0 broken links on your portfolio. Check this with the script in TC2.
4. **Plan.** The 30-day plan has four weeks, and each week has at least two specific, dated actions.
5. **Timestamp.** The LMS submission time is before 20:30. You can see it in the LMS after you submit.

There are four test cases. Run them in this order.

**TC1: freeze match.** The trainer runs the freeze script on `freeze.csv` and then runs `grep '<roll>' freeze_audit.csv`. Expected result: `match = yes`.

The freeze script is the trainer's tool. You do not write it, and you do not run it. It reads `freeze.csv`, a CSV file that lists the submissions, and writes `freeze_audit.csv`, a second table with the result for each student. The line you need is found by `grep`.

Breaking down the grep line:

- `grep` searches a file for lines that match a pattern and prints those lines.
- `'<roll>'` is the pattern. The trainer replaces `<roll>` with your roll number. The single quotes stop the shell from interpreting any special characters inside.
- `freeze_audit.csv` is the file searched.

Passing output: a line with your roll number that also shows `match = yes`. The exact layout of the audit file belongs to the course. If the line you see looks different, the trainer's expected output is the authority.

Your own check, run in Git Bash inside your portfolio folder, after you have merged and switched to the default branch (on any other branch `git rev-parse HEAD` gives that branch's commit, not the default branch's):

```bash
git ls-remote origin HEAD | cut -f1
git rev-parse HEAD
```

The first command asks GitHub for the commit at the tip of the remote's default branch and keeps only the first column, which is the SHA. `cut -f1` keeps the first tab-separated field. The second command prints the SHA of your local commit. If the two codes are the same, you will get `match = yes` for TC1, unless the trainer's freeze file is wrong.

Failing output: no line for your roll number, which usually means a typo in the roll number or a row that is missing from `freeze.csv`. Or a line with `match = no`, which means the remote tip is not the SHA you submitted. The usual cause is that you pushed a new commit after you submitted, or that you submitted a commit on a branch that is not the default branch.

**TC2: link check.** The trainer runs a link checker against `https://<username>.github.io` and expects `0 non-200 links`.

The course link checker is the trainer's tool, and you should use it as its output, but you can run the same idea yourself with the script built in the step-by-step section. Once it is saved as `check_links.sh` and run from your `linkcheck` folder, a passing run looks like this:

```term
$ bash check_links.sh
checked 14 links
non-200 links: 0
```

The number of links will differ on your site. What matters is the last line. `non-200 links: 0` means every link you listed returned status `200`, after any redirects were followed.

Failing output: a line with `non-200 links:` followed by a number above 0, and the script prints each bad link above it as `CODE URL`. Common causes are:

- `404` means the page is not there. The cause is usually a renamed file, a changed folder, or a typo in the link.
- `301` or `302` means the link redirects. If your checker does not follow redirects, it reports them as failures. The fix is `-L` in the curl command, which the script already uses.
- `000` means curl could not reach the address at all. Check the spelling of the address, and whether the page is live in a browser.

**TC3: LMS checklist.** The trainer opens the LMS D08 form and reads the trainer column. Expected: every item is `yes`.

This test has no command. You can only check the parts you control: open each evidence link in a private window and confirm it shows what the item says. An item the trainer cannot open is marked `no`, even if the work is done. You cannot mark the trainer column yourself.

**TC4: 30-day plan.** The trainer opens your plan. Expected: weeks 1 to 4, each with at least two dated actions.

A rough self-check, if your plan is saved as a text file called `plan.md` with one action per line starting with `- `, is this count:

```bash
grep -c -E '^- .*[0-9]{1,2} [A-Z][a-z]+' plan.md
```

Breaking it down: `grep -c` counts matching lines. `-E` turns on extended patterns. `^- ` matches lines that start with a dash and a space. `[0-9]{1,2} [A-Z][a-z]+` matches a day number, a space and a month name such as `4 May`, so write dates as day then month (`4 May`, not `May 4`). The count should be at least 8, which is 4 weeks times 2 actions. This is only a rough check. It does not prove that each action is in the right week, so read the plan yourself as well.

Failing output: a count below 8, which means at least one action has no date, or a week has only one action. Also check that the plan reads as four weeks, not three or five.

### Do it, step by step

#### Subtask Y2-T62.1: run the checklist and link check

Goal: know exactly which items fail before you change anything.

Stage 1: make a working folder outside the repository. This keeps your scratch files out of Git.

```bash
mkdir -p ~/linkcheck
cd ~/linkcheck
```

`mkdir -p` creates the folder and does nothing if it already exists. `cd` changes into it. Your prompt is now inside `linkcheck`, so every file you create stays there.

Stage 2: list the checklist items. Open the D08 checklist on the LMS and copy each item into `~/linkcheck/checklist-notes.txt`. Keeping the notes outside the portfolio folder means they are never committed by accident.

Stage 3: list the pages to check. Create `pages.txt` with one full address per line, one for each page of your portfolio. For example:

```text
https://<username>.github.io/
https://<username>.github.io/projects.html
```

Write each address in full, starting with `https://`. Check that each line has no spaces at the end, since Windows editors sometimes add invisible carriage-return characters. Save the file in an editor set to LF line endings, such as VS Code, and not in an older Notepad setting that writes CRLF.

Stage 4: fetch each page and collect its links. A link in HTML looks like `<a href="https://...">`. The commands below download each page and collect the value of every `href`. Type them into a file called `check_links.sh` in `~/linkcheck`; you will add the later stages to the same file, so that `bash check_links.sh` runs everything in order.

```bash
: > links.txt
while read -r page; do
  curl -sS --fail "$page" -o tmp.html
  grep -o 'href="[^"]*"' tmp.html | sed 's/^href="//; s/"$//' >> links.txt
done < pages.txt
sort -u links.txt -o links.txt
```

Line by line:

- `: > links.txt` empties the file, or creates it if it does not exist. The colon is a command that does nothing, and `>` replaces the file's contents.
- `while read -r page; do` reads one line from the input at a time into the variable `page`. `-r` stops `read` from treating backslashes as special.
- `curl -sS --fail "$page" -o tmp.html` fetches the page and saves it as `tmp.html`. `-s` hides the progress meter, `-S` still shows errors, and `--fail` makes curl report an error for a page that does not exist.
- `grep -o 'href="[^"]*"' tmp.html` prints only the matching part of each line, which is each `href="..."` value.
- `sed 's/^href="//; s/"$//'` removes the `href="` at the start and the closing quote at the end, leaving only the address.
- `>> links.txt` appends the addresses to the file.
- `done < pages.txt` feeds the list of pages to the loop.
- `sort -u links.txt -o links.txt` sorts the file and removes duplicate lines, writing the result back to the same file.

Expected output: no message if every page loads. Then `links.txt` contains one address per line. Open it with `cat links.txt` to check it. You should see the links you expect. If a page fails, curl prints an error and the loop continues with the next page.

Stage 5: keep only the web links. Links like `mailto:` (an email link) or `#top` (a link within the same page) are not checked by the status test. Note that relative links such as `href="projects.html"` also do not start with `https://`, so this filter drops them. That is why every page of your site is listed in `pages.txt`: each one is checked as a page in its own right. Add `src="..."` links (images) to the grep yourself if your portfolio uses them.

```bash
grep '^https://' links.txt > web.txt
wc -l < web.txt
```

`grep '^https://'` keeps only lines that start with `https://`. `wc -l` counts the lines. Expected output: a number, which is how many web links you have.

Stage 6: check each link in the list. You will add this to `check_links.sh` in Subtask Y2-T62.2, and then run the complete check.

Stage 7: mark each checklist item. For each item on your notes, write down one evidence link that shows the item is true. Open each link in a private browser window. If the page asks you to log in, or it shows an error, the evidence is not good enough. Make the page public, or choose a different proof, and check again.

How to test this subtask before moving on: run the stage 4 and 5 commands (or `bash check_links.sh` so far), then `wc -l < web.txt`, and confirm the number is what you expect for your site. Then open three of the links in a private window by hand. If all three open, you are ready.

#### Subtask Y2-T62.2: fix every failed item

Goal: make each item that failed in Subtask 1 pass, and keep a record of what you changed.

Before any fix, create your branch in the portfolio folder: `git switch -c y2-t62-freeze`. All your fix commits go on it.

First, the link checker. Add this stage to `check_links.sh`, after the stage 5 commands. It checks each link in `web.txt` and records the status code.

```bash
: > results.txt
while read -r link; do
  code=$(curl -sL -o /dev/null -w '%{http_code}' --max-time 20 "$link")
  echo "$code $link" >> results.txt
done < web.txt
```

Line by line:

- `: > results.txt` empties the results file before you start.
- `while read -r link; do` reads one web link at a time.
- `curl -sL` fetches the link silently and follows redirects. `-L` is the important flag: without it, a `301` is reported as the final answer, and the check fails although the link works.
- `-o /dev/null` throws the page body away, because you need only the status.
- `-w '%{http_code}'` prints only the status code, and `code=$(...)` stores it in the variable `code`.
- `--max-time 20` stops curl after 20 seconds, so one slow link does not hang the run.
- `echo "$code $link" >> results.txt` writes the code and the link on one line.

Expected output: nothing is printed while it runs. Open `results.txt` with `cat results.txt`. Each line starts with a code, for example `200 https://<username>.github.io/`.

Now the summary. Add the three lines below at the end of `check_links.sh`, and run it from `~/linkcheck` with `bash check_links.sh`. The script runs all the stages in order.

```bash
echo "checked $(wc -l < web.txt) links"
echo "non-200 links: $(grep -vc '^200 ' results.txt)"
grep -v '^200 ' results.txt
```

Line by line: the first line counts the web links. The second counts the lines in `results.txt` that do not start with `200 `. `grep -v` inverts the match, and `-c` counts the matches. The third line prints the bad lines, so you can see which links to fix.

Expected output: `non-200 links: 0` when everything is fine. If the count is above 0, the lines printed below it show the code and the address for each bad link.

Second, fix the items. Go through the failed items one at a time. Make one commit per fix, so that each change is traceable.

- For a broken link, find every place the old address appears: `grep -rn 'projects/p2' .` searches the folder recursively (`-r`) and prints each match with its line number (`-n`). Then edit the link.
- For a title mismatch, find the title: `grep -n '<title>' index.html`. Make it match your CV and LinkedIn headline exactly.
- For missing numbers, find each claim without a figure. Add the measured number from your project, with its unit.
- For the mobile demo, open the page in Chrome or Edge, press F12 to open developer tools, then press Ctrl+Shift+M to turn on the device toolbar. Choose a phone width and check that the page does not scroll sideways. A sideways scroll means something is wider than the screen; find the widest element and shrink it.

After each fix, run `git status` and `git diff`, and look at what you changed. Then commit only the files you meant to change.

How to test this subtask before moving on: run `bash check_links.sh` again. Repeat until it prints `non-200 links: 0`.

#### Subtask Y2-T62.3: commit, push and copy the SHA

Goal: put the final version on the default branch, and copy its SHA.

Stage 1: commit and push your branch.

```bash
git switch y2-t62-freeze
git add index.html projects.html
git commit -m "Fix broken link to project 2 page"
git push -u origin y2-t62-freeze
```

Line by line: `git switch y2-t62-freeze` makes sure you are on the branch you created in the previous subtask. `git add` stages the files you named, which means it marks them to go into the next commit. Name the files, rather than using `git add .`, so that stray files are not included. `git commit -m` saves the commit with the message in quotes. `git push -u origin` sends the branch to GitHub, and `-u` remembers the link so later pushes need no extra words.

Expected output: a line such as `Branch 'y2-t62-freeze' set up to track remote branch`. Repeat the add, commit and push for each commit.

Stage 2: open a pull request for `y2-t62-freeze`, get the squad approval the brief asks for, and merge it. Do not merge your own work. Your portfolio is your own repository, so a squad-mate can review it on GitHub only if you add them as a collaborator or they can see the public PR; the ticket does not say which way your trainer wants it, so ask your trainer who reviews and how before you open the PR. After merging, the default branch on GitHub contains your fixes.

Stage 3: update your local default branch and read the SHA.

```bash
git remote show origin
git switch main
git pull origin main
git rev-parse HEAD
```

`git remote show origin` prints the remote's default branch, a line like `HEAD branch: main`. Use that name in place of `main` if yours is different. `git switch main` moves onto the default branch. `git pull origin main` brings in the merged changes. `git rev-parse HEAD` prints the full 40-character SHA of the commit at the tip.

Expected output: one line of 40 hexadecimal characters, for example `4b8e0d2c9a17f5e3d6b1c0a9e8f7d6c5b4a39281`. That is an example, not your code. Copy your own.

Stage 4: confirm that the remote agrees.

```bash
git ls-remote origin HEAD | cut -f1
```

The output must be the same SHA as stage 3. If it is, the remote tip matches your submission. If it is not, someone pushed after you read the SHA, or you read it from the wrong branch. Fix that before you submit.

How to test: the two SHAs match, and `git status` says `nothing to commit, working tree clean`.

```flow
TITLE: How the freeze is checked
NODES: Your laptop | Squad-mate | GitHub | Freeze script
STEPS:
1>3 :: git push :: Your branch reaches GitHub.
3>2 :: open PR :: A squad-mate reviews your pull request.

1>4 :: submit URL + SHA :: The LMS gives the script your SHA at 20:30.
4>3 :: git ls-remote HEAD :: The script asks GitHub for the current tip.
3>4 :: tip SHA :: If it equals your SHA, the audit says match = yes.
```

### Defend it in the viva

Your trainer will ask you about this ticket. Each answer below shows the reasoning. Your own answers must use your own facts.

1. **Why do you freeze at a SHA instead of at a date?** A date does not identify content. Two commits can share the same day, and a later commit can be made on the same day. The SHA identifies one exact set of files, so the panel sees a version that cannot change under them.

:::answer Model answer
A date is a moment, not a version. More than one commit can land on the same day, and a commit made after the freeze would still carry that date. A SHA is a fingerprint of the exact content and history, so it names one version. Git can check that a remote tip still equals it. That is why the freeze check compares SHAs and not dates. The reasoning is that the panel reviews exactly what the trainer approved.
:::

2. **What is the trade-off in merging your fixes through a pull request before the freeze?** A pull request adds a review step, which takes time and needs a squad-mate. It also means the default branch only moves when a reviewer has approved the change, so your SHA is the tip that the freeze check reads. Skipping the review would be faster, but it would break the team rule that nobody merges their own work.

:::answer Model answer
The trade-off is time against trust. Review takes a squad-mate's attention and can delay the freeze, so you plan the merge early. In exchange, the default branch holds only reviewed changes, and the SHA you freeze is the one a reviewer approved. Self-merging would save minutes but would remove the check that the team relies on. A good answer names the cost and says why it is worth paying.
:::

3. **What did you personally do to make your portfolio pass?** A strong answer names the specific links, pages or items you fixed, the commit that fixed each one, and the evidence you produced. It does not describe the team's work as your own.

:::answer Model answer
A strong answer is specific. It names the failed item, the file that held the problem, the commit message and SHA that fixed it, and the output that proves it now passes, such as the link checker summary. It also says which parts were your decision, such as the wording of the plan. The shape is what counts here. Replace every detail with your own facts before you answer.
:::

4. **How does the link checker decide a link is broken, and why use `-L`?** The checker sends a request and reads the status code. A `200` means the page loaded. A `404` means the page is missing. A `301` means the address moved, and the browser would follow it. Without `-L`, curl stops at the `301` and the checker would report a failure that a visitor never sees.

:::answer Model answer
A checker treats the status code as the signal. Only a `200` after any redirects counts as a working link. `-L` tells curl to follow each redirect to its final answer, which matches what a visitor's browser does. Without it, a moved page looks broken. The reasoning is that the check should measure what the reader experiences, not what one server reply says.
:::

5. **Why keep scratch files outside the repository?** Git tracks every file in the folder unless it is ignored. Scratch files such as `tmp.html` and `links.txt` would appear in `git status`, and a careless `git add .` could commit them. A clean working tree is the proof that the commit contains only what you meant.

:::answer Model answer
Git records whatever is in the folder, so scratch files would blur what the freeze contains. Keeping them in a separate folder keeps `git status` clean, and `git status` showing a clean tree is the evidence that the frozen commit holds only reviewed work. The reasoning is about making the frozen version easy to verify.
:::
