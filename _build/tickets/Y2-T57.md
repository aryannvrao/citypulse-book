### The ticket in plain words

This ticket closes your data-structures and algorithms (DSA) strand. Since Y2-T20 you have been building a personal repository called `dsa-<name>`, where each solved problem sits in its own folder with a test. Now you show that repository to the trainer, sit a timed contest, and run a 25-minute mock interview.

The reason is a real CityPulse problem. A nightly job, the program that refreshes the city's data each night, grew from 5 minutes to 90 minutes as the data grew. Profiling, which means measuring where a program spends its time, found a loop that gets slower in proportion to the square of the input size. That is an O(n²) loop, and it is the kind of problem this ticket trains you to spot and fix.

The ticket also tests whether you can explain your thinking out loud. The trainer wants evidence that your problem-solving works under time pressure, not only on problems you have had days to prepare. Your scores go into the CRI, the course's record of each student's progress.

Your job in this guide is to learn the techniques: writing tests, reading a complexity note, profiling, setting up continuous integration, and working through a timed problem. You then do the work yourself.

### How your trainer checks it

The trainer runs four test cases. Two are commands you can run yourself, and two are checks on the judge and the CRI sheet. Before the trainer runs them, you run every one of them yourself in the same order (see the section "Prove it before review").

Your submission is judged on the commit SHA you hand in. The trainer clones the repository, checks out that exact commit and runs the tests. The flow below shows that path.

```flow
TITLE: What the trainer's check does with your SHA
NODES: Your laptop | GitHub | Grading run
STEPS:
1>2 :: git push :: Your commits reach GitHub.
2>3 :: clone and checkout SHA :: The grading run downloads exactly the commit you submitted.
3>2 :: pytest and count :: The tests and the counts run on that fresh copy only.
2>1 :: gate result :: The result is recorded against your submission.
```

Each line of the flow explains where the result comes from. Nothing you have on your laptop but uncommitted is seen by the grader. This is why TC1 uses a clean clone.

**Acceptance criteria.** The ticket has five. Each is shown with the evidence that proves it.

1. The grading script at 09:00 runs on your SHA and reports problems of at least 40, zero failed tests, complexity notes present and an index present. Evidence: the grader's result line, which the trainer shows you.
2. The contest leaderboard at 12:30 shows at least 2 of 4 problems accepted for you. Evidence: your rows on the leaderboard.
3. The mock is complete and the rubric has six criteria scored 0 to 2, with a one-line feedback note on the CRI sheet. Evidence: your CRI row.
4. In the profiling exercise you name the O(n²) function from cumulative time and propose an O(n) or O(n log n) fix. Evidence: your answer when the trainer asks.
5. A "D11 review" issue exists in `dsa-<name>`. Evidence: the issue list on GitHub.

**TC1: the tests and the problem count.**

Steps: `git clone https://github.com/citypulse-y2/dsa-<name> && git checkout <SHA> && pytest -q --tb=no`

Broken into parts:

- `git clone <URL>` downloads the repository into a new folder with the repository's name.
- `&&` means the next command runs only if this one succeeds. If the clone fails, nothing else runs.
- `git checkout <SHA>` moves the folder to the exact commit you submitted. Git calls this a detached HEAD, which is normal here.
- `pytest` runs all the tests it finds.
- `-q` means quiet. It prints dots instead of a long report.
- `--tb=no` means no tracebacks, the long error descriptions printed for failures.

Expected: 0 failed, and at least 40 problem folders counted.

What passing looks like:

```term
$ pytest -q --tb=no
........................................
40 passed in 0.31s
```

The dots line may be longer or shorter on your machine. The last line is what matters. It says `40 passed` and no `failed`. The timing will differ.

The problem count is a separate check. The trainer counts problem folders. You can count yours with `find . -name "test_*.py" | wc -l` from inside the repository, as shown in T57.1.

What failing looks like: `1 failed, 39 passed`. The usual cause is a test that fails on the clean clone but passed on your laptop, because a file was never committed. Another failure is all tests passing but fewer than 40 problem folders, which the folder count shows. Note that pytest counts test functions, not problems, so `40 passed` does not by itself prove 40 problems.

Also note that the trainer's one-line command needs a `cd dsa-<name>` between the clone and the checkout, because `git checkout` must run inside the cloned folder.

**TC2: the complexity notes.**

Steps: `grep -ri 'time:' --include=*.py . | wc -l`

Broken into parts:

- `grep` searches text. Here it searches for the words `time:`.
- `-r` means recursive. It searches every folder under the current one.
- `-i` means case-insensitive, so `Time:` and `time:` both match.
- `'time:'` is the text pattern. The quotes stop the shell from reading the colon as anything special.
- `--include=*.py` restricts the search to Python files.
- `.` means the current folder.
- `|` pipes the matching lines into `wc -l`.
- `wc -l` counts the lines it receives and prints the number.

Expected: at least 40 complexity annotations.

What passing looks like:

```term
$ grep -ri 'time:' --include=*.py . | wc -l
42
```

What failing looks like: a number below 40, such as `37`. The usual cause is a problem with no `Time:` line in its docstring, or a line written as `Complexity:` with no `time:` word in it. The fix is to add a `Time:` line to every problem.

Be careful about the other way round too. A count of 52 for 40 problems can come from a test file that mentions `runtime:`, which also contains `time:`. Keep `time:` out of test files and comments that are not complexity notes. The command also searches folders such as a virtual environment (`.venv`), so a count far above your problem count may come from there; add `--exclude-dir=.venv` to leave it out.

**TC3: the contest leaderboard.**

Steps: export the contest leaderboard CSV from the judge.

You do not run TC3 in a terminal. The trainer exports a CSV file (a plain text spreadsheet) from the judge. The check is that each student has at least two rows showing Accepted. During the contest you can see your own count on the judge page. A CSV shows one line per submission, so count the different problems with an `Accepted` line for your name (two Accepted lines for the same problem are one problem).

Expected: Accepted ≥2 per student.

Failing looks like one Accepted for you. The usual cause is solutions that pass the sample inputs but fail hidden tests. You will see the verdict name for each attempt, such as Wrong Answer or Time Limit Exceeded, which tells you which problem to revisit.

**TC4: the CRI sheet.**

Steps: open the CRI sheet and look at the DSA columns.

Again, this is a manual check. Open the sheet and find your row. Each DSA column must have a value: the D11 score, the contest score and the mock rubric. Expected: D11, contest and mock rubric filled for every student.

What a pass looks like is simply a filled cell in each of those columns. A blank cell fails the check. The usual cause is a score you have not entered, or a mock rubric that you have recorded in your notes but not sent to the trainer.

#### Y2-T57.2: Pass pytest from a clean clone and make CI green

**Goal.** Your tests pass in a fresh clone, and a GitHub Actions workflow runs them on every push.

**Stage 1: run the tests in a clean folder.** Clone your repository into a new folder, check out the SHA and run the same command as TC1:

```term
$ git clone https://github.com/citypulse-y2/dsa-<name> clean-check
$ cd clean-check
$ git checkout <SHA>
$ python -m pytest -q --tb=no
40 passed in 0.31s
```

`clean-check` is a new folder name, so nothing from your working copy is used. `git checkout <SHA>` moves to your submitted commit. `python -m pytest` runs pytest using the Python you chose, which is the safest form on Windows. If it prints `failed`, look for a file you forgot to commit by running `git status` in your working copy.

**Stage 2: add the workflow file, one piece at a time.** GitHub Actions reads YAML files in the folder `.github/workflows/`. Read the chapter [D06: Continuous integration with GitHub Actions](D06.html) before you start. Build the file in four small steps, testing after each.

Step A creates the trigger, which says when the workflow runs. Create `.github/workflows/tests.yml` with a name and a trigger:

```yaml
name: tests
on:
  push:
  pull_request:
```

`name` is the label shown in the Actions tab. `on:` lists the events that start the workflow. `push` runs it when you push commits, and `pull_request` runs it when a pull request is opened or updated. Commit this and check that the Actions tab shows a run that does nothing yet.

Step B adds one job that runs on a fresh Linux machine. Add these lines under the trigger:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: echo "job started"
```

`jobs:` holds named jobs. `test` is the job name. `runs-on` names the kind of machine. `steps` is a list, and each `- run:` line runs one shell command. Push and check that the run shows `job started` in its log.

Step C checks out your code. Replace the echo step with this step, which copies your repository into the machine:

```yaml
      - uses: actions/checkout@v4
```

`uses:` runs a ready-made action. `actions/checkout` downloads your repository into the job. The `@v4` is the major version. Check the current major version in the D06 chapter before you rely on it.

Step D installs Python and runs pytest. Add a Python setup action and the two run steps, in that order:

```yaml
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: python -m pip install pytest
      - run: python -m pytest -q --tb=no
```

The `with:` block passes an option to the action, here the Python version. Pick the version your lab machine uses. Each `run:` step is a separate shell command. Push and check that the run goes green.

YAML is strict about spaces. Each nested level is indented by two spaces, and a tab character breaks the file. If the Actions tab shows an error before any step runs, the indentation is the usual cause.

**Stage 3: add the badge.** A badge is a Markdown image that GitHub fills in with the status of the latest run. Add this line near the top of `README.md`. It assumes your workflow file is `tests.yml`; change that part if you named yours differently:

```text
![tests](https://github.com/citypulse-y2/dsa-<name>/actions/workflows/tests.yml/badge.svg)
```

The part before `/badge.svg` is the URL of the workflow file on GitHub. The square brackets hold the text shown if the image fails to load. Open the repository page and check the badge is green on `main`.

#### Y2-T57.3: Profile the slow job and name the O(n²) function

**Goal.** Find the hot function in `citypulse-slowjob`, name its complexity and propose a faster version.

**Stage 1: learn the profiler on a toy.** A profiler records how long each function call took. Python's built-in one is `cProfile`. You run it as a module with `python -m cProfile`. The flag `-s cumtime` sorts the output by cumulative time, which is time spent in a function plus the functions it calls.

Make a tiny file called `toy.py` in a scratch folder:

```python
def count_pairs(values):
    total = 0
    for i in range(len(values)):
        for j in range(len(values)):
            total += 1
    return total

print(count_pairs(list(range(2000))))
```

Run it with the profiler:

```term
$ python -m cProfile -s cumtime toy.py
4000000
         4010 function calls in 0.250 seconds
   Ordered by: cumulative time
```

The first line is the program's own output, `4000000`. The count is 2000 times 2000. The number of function calls (about 4,000) and the seconds will differ on your machine; loop steps are not function calls, so they are not counted there. The output then lists the functions by cumulative time. The column `ncalls` is the number of calls and `tottime` is time spent inside the function's own body, excluding functions it calls. `cumtime` includes those calls. The row for `count_pairs` shows the time for the whole nested loop.

**Stage 2: find the hot function in the real job.** Run the profiler on the job's entry file, which the `citypulse-slowjob` README names. Run it on the lab machine, where the data is. Look at the top rows and skip the lines `<module>` and any built-in functions, since those wrap your code. The hot function is the first row that belongs to the job's own code. Write down its name, file, and its `cumtime`.

**Stage 3: read the complexity from the loops.** Look at the code of the hot function. A loop nested inside another loop, where both run over the same n items, is O(n²). Count the operations by hand. For `count_pairs`, the inner loop runs n times for each of n outer steps, so there are n × n steps. Your job's function may be different, but the reasoning is the same.

**Stage 4: a faster version of the same question.** A common O(n²) pattern is an inner loop that searches for a value. A hash set answers "is this present?" in about constant time, so one pass with a set replaces the search. Here is a fictional question, separate from the job, that asks whether any two values are equal:

```python
def has_duplicate_slow(values):
    for i in range(len(values)):
        for j in range(i + 1, len(values)):
            if values[i] == values[j]:
                return True
    return False
```

The two loops compare every pair, which is O(n²). Now the set version:

```python
def has_duplicate_fast(values):
    seen = set()
    for value in values:
        if value in seen:
            return True
        seen.add(value)
    return False
```

The single loop checks each value once. `value in seen` is the membership test that costs about constant time, and `seen.add(value)` remembers it. Together that is O(n). The trade-off is memory: the set holds up to n values.

Here is the same idea shown step by step on a three-value list:

```trace
TITLE: Checking a small list for a duplicate with a set
CODE:
seen = set()
for value in [4, 9, 4]:
    if value in seen:
        print("duplicate", value)
    seen.add(value)
STEPS:
1 :: seen=set() :: Start with an empty set.
2 :: value=4; seen=set() :: The loop takes the first value.
3 :: value=4; seen=set() :: 4 is not in the set, so the if is false.
5 :: value=4; seen={4} :: Remember 4 for later.
2 :: value=9; seen={4} :: The second value.
3 :: value=9; seen={4} :: 9 is not in the set yet.
5 :: value=9; seen={4, 9} :: Remember 9.
2 :: value=4; seen={4, 9} :: The third value is 4 again.
3 :: value=4; seen={4, 9} :: 4 is already in the set, so the if is true.
4 :: value=4; seen={4, 9} :: Report the duplicate.
```

Each step names the line that ran and the values at that moment. The third value finds 4 already in the set, which is the moment the answer is known.

**Stage 5: test that your fix is equal to the slow one.** Run both versions on the same small lists and check they agree. Add an assertion for each case, so a mismatch stops the program:

```python
assert has_duplicate_slow([1, 2, 3]) == has_duplicate_fast([1, 2, 3]) == False
assert has_duplicate_slow([1, 2, 1]) == has_duplicate_fast([1, 2, 1]) == True
```

Equal results do not prove speed, so also time the job before and after your change. Your write-up needs the function name, its file, its `cumtime` before the change, its complexity and the proposed fix in your own words. Save it as a notes file of your choice in the repository and commit it.

#### Y2-T57.5: Complete the 25-minute mock interview

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| `collected 0 items` or `no tests ran` from pytest | Test files are not named `test_*.py`, or the test functions do not start with `test_`. | Rename the files and functions to match pytest's naming rule, then run pytest again. |
| Tests pass on your laptop but fail on the clean clone | A file is untracked, so the clone does not contain it. | Run `git status`, add and commit the missing file, then re-clone at the new SHA. |
| TC2 count below 40 | One or more problems have no `Time:` line in the docstring. | Add a `Time:` line to every problem. Check with the grep command. |
| TC2 count higher than the number of problems | `time:` appears in test files or comments such as `runtime:`. | Remove those lines so only complexity notes contain `time:`. |
| CI badge is grey, or there is no run in the Actions tab | The workflow file is not on `main`, it is in the wrong folder, or its YAML indentation is wrong. | Check the path is `.github/workflows/tests.yml`, check the file is on `main`, and read the error shown in the Actions tab. |
| Profiler output's top row is `<module>` | `<module>` is the whole program, so it always has the largest cumulative time. | Skip it and look at the first row that belongs to your job's own functions. |

| Judge verdict is Wrong Answer on a problem that passes your samples | You did not test edge cases such as empty input or repeated values. | Test the edge cases in your own assertions, then resubmit. |
| `gh: not logged in` or an HTTP 404 from `gh` | The GitHub CLI is not authorised, or the repository name is wrong. | Run `gh auth login` in your terminal, check the name, or use the web page. |

### Defend it in the viva

The trainer asks you questions to check you understand the ticket. Answer from your own output and your own commits. Each model answer below shows the reasoning, not your personal details.

**1. Why does a complexity note matter if the tests already pass?**

Tests tell you that a function returns the right answer on the inputs you chose. They do not tell you how it behaves when the input grows. The complexity note records the growth rate, so a reader can see that a loop nested over the same n items will become slow, and can judge whether that matters for the data.

:::answer Model answer
Tests check correctness on chosen inputs. A complexity note tells you how the cost grows with n. A solution can pass every test and still be too slow for the real data. CityPulse's nightly job is the example: it was correct but took 90 minutes. Writing the growth rate down makes the risk visible before the job gets slow.
:::

**2. What is the trade-off in replacing a nested loop with a set?**

A set makes each membership check fast, about constant time, so the whole check becomes linear. The cost is memory, because the set stores the values it has seen. For n values that is roughly n stored items, which is the price for the speed.

:::answer Model answer
The set trades memory for time. The nested loop uses almost no extra memory but does n squared comparisons. The set version does about n checks and stores up to n values. For most data the saving in time is worth the extra memory, but if memory were the limit, the answer would change. You would name that limit and explain the choice.
:::

**3. Walk me through your profiling result. Which function was hot, and why?**

Answer from your own profile output. Say the command you ran, the function name from the `cumtime` column, the file it is in, and the loop structure that gives its complexity. Then say what you would change.

:::answer Model answer
Start with the command, `python -m cProfile -s cumtime` on the job's entry file. Name the first row that belongs to your job's own code, not `<module>`. Give its cumulative time from your run. Then explain the loop: which loop is nested inside which, over which list, so the cost is n squared. Finish with the fix you would try and why it is linear. Use only numbers from your own output.
:::

**4. How do you know your fix is O(n) and not just faster on your sample?**

Speed on one sample proves little, because a small sample hides growth. You reason from the code: count how many times each line runs as n grows. Then you check the timing on larger inputs, to see the curve bend.

:::answer Model answer
A faster result on one input does not prove the growth rate. I count the operations: a single loop with a constant-time membership test runs about n times. Then I test with inputs of increasing size, such as 1,000, 10,000 and 100,000 values, and check that the time grows roughly in step with n, not with n squared. The reasoning and the measurements together support the claim.
:::

**5. In your mock, what did you do when you got stuck?**

The answer should describe your own steps. Say which stage you were in, what you did first, and whether you asked for a hint. Explain that you went back to the clarify step or to the brute-force version when stuck, because a correct slow solution is a safe place to return to.

:::answer Model answer

Q: In the command python -m cProfile -s cumtime job.py, what does cumtime sort the rows by?
- The number of times each function was called
- The alphabetical order of the file names
* The time spent in a function plus the functions it calls
- The time spent only in the function's own lines
WHY: cumtime is cumulative time, which includes the functions a function calls. The most tempting wrong option is the time spent only in the function's own lines, which is tottime, a different column.

Q: A duplicate check compares every pair of 1,000 values with a nested loop. Roughly how many comparisons does it make?
* About 500,000, because n times (n minus 1) divided by 2 pairs are checked
- About 1,000
- About 2,000
- About 1,000,000, which is n squared
WHY: The inner loop only looks at later values, so each pair is checked once: 1,000 times 999 divided by 2, about 500,000. The most tempting wrong option is n squared, which describes the loop's growth but counts each pair twice.

Q: Why does a set membership check make the duplicate check O(n) instead of O(n²)?
- The set sorts the values before the loop starts
- The set removes repeated values from the input first
- The set uses less memory than a list
* Each membership test takes about constant time, so n tests cost about n steps
WHY: A set uses a hash to find a value directly, so each check is about constant time, and one pass over n values costs about n steps. The most tempting wrong option is the memory claim, which is not why the loop becomes linear.
