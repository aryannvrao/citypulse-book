### The ticket in plain words

Until now, CityPulse data and the trained model have lived inside your repository and your database. Only your squad can reach them. The client's dashboard team needs a stable front door instead. That front door is an **API** (a set of addresses on a server that other programs can ask questions of over the network). The ticket asks you to build version 0 of it with two working endpoints. An **endpoint** is one address the API answers at, such as `/v1/health`.

The first endpoint says whether the service is alive and can reach the database. The second returns a few aggregate numbers, such as a total count and the latest reading time, calculated from the stored readings.

The ticket cares a lot about **status codes**. A status code is the three-digit number the server sends with every answer. `200` means success. `404` means the thing you asked for does not exist. `422` means your input is wrong. `503` means the server is running but a service it depends on, here the database, is down. The description warns against one specific mistake: returning `200` with an empty body after something has gone wrong. The dashboard would then believe that everything is fine. The description does not name a particular incident, but this is the kind of silent failure it wants you to prevent.

The ticket also asks for a version number in every path, `/v1/...`. If a later change breaks what the dashboard expects, you publish `/v2` and leave `/v1` alone. This is why the ticket asks for a written contract in `docs/api.md`.

### How your trainer checks it

The trainer starts from the repository root, runs the server, and then runs the test cases below in order. Each test case shows a command, what it does part by part, what a pass looks like, and what a failure usually means. The acceptance criteria that are not test cases are covered after them.

#### TC1: health returns 200

```bash
DATABASE_URL=$URL uvicorn api.main:app --port 8000 & sleep 2; curl -i localhost:8000/v1/health
```

Read this in parts:

- `DATABASE_URL=$URL` sets the environment variable for this one command. `$URL` is replaced by the value of your shell variable `URL`, which holds the connection string.
- `uvicorn api.main:app` starts the server. `api.main` means the file `api/main.py`, and `:app` means the object called `app` inside it.
- `--port 8000` chooses the port.
- `&` runs the server in the background so the command line continues.
- `;` separates two commands. The second runs even if the first finished, and it runs after the server has had two seconds to start.
- `curl -i localhost:8000/v1/health` asks for the health endpoint and prints the headers as well as the body.

A pass looks like this:

```term
$ curl -i localhost:8000/v1/health
HTTP/1.1 200 OK
content-type: application/json
content-length: 15

{"status":"ok"}
```

A failure has these usual causes. `Connection refused` means the server did not start, often because you ran `uvicorn` from inside the `api/` folder, which hides the `api` package. A `500 Internal Server Error` with a traceback usually means `DATABASE_URL` is not set in that shell, because the code raised a `KeyError`.

#### TC2: health returns 503 when the database is down

```bash
docker stop <db-container>; curl -i localhost:8000/v1/health; docker start <db-container>
```

- `docker stop <db-container>` stops the database container. Replace the angle brackets with the name shown by `docker ps --format '{{.Names}}'`.
- `curl -i` asks the health endpoint again while the database is unreachable.
- `docker start` brings the database back. Wait a few seconds before the next test.

A pass shows `HTTP/1.1 503 Service Unavailable` and a body of `{"detail":"database unavailable"}`. Note that the answer can take up to three seconds, because `connect_timeout=3` caps how long the driver waits. If the port refuses the connection at once, the 503 comes back almost immediately. Both are fine.

A `200` means the health route does not really query the database. A `500` with a traceback means the database error was not caught. `Connection refused` on the curl line means the server itself has stopped, so read its terminal output.

#### TC3: stats returns valid JSON with aggregate fields

```bash
curl -s localhost:8000/v1/stats | python -m json.tool
```

- `curl -s` requests the stats endpoint silently, without the progress meter.
- `|` sends the body into the next command.
- `python -m json.tool` reads the JSON, checks it and prints it indented. If the text is not valid JSON, it stops with an error.

A pass prints a neat object with at least three fields. The timestamp looks like `"2026-11-16T10:00:00+05:30"`. A failure message such as `Expecting value: line 1 column 1` means the body was empty or was an HTML error page. Read the server terminal for the traceback. A timestamp without `+05:30`, or with `+00:00`, means the conversion step in the code is missing.

#### TC4: unknown station returns 404

```bash
curl -i localhost:8000/v1/stations/DOES_NOT_EXIST/readings
```

- `DOES_NOT_EXIST` is a path parameter. The API reads it from the URL.
- `curl -i` prints the status line.

A pass shows `HTTP/1.1 404 Not Found`. The ticket also accepts the case where you did not implement this endpoint, provided it is absent from `docs/api.md`. Choose one and be consistent. A `200` with an empty list is wrong, because it tells the dashboard the station exists with no data. A `500` means the lookup crashed.

#### TC5: no connection string or password in the code

```bash
grep -rn 'postgresql://\|password' api/
```

- `grep` searches for text.
- `-r` searches all files inside `api/`, including subfolders.
- `-n` prints the line number of each match.
- `'postgresql://\|password'` is the pattern. The `\|` means "or" in basic regular expressions, so it finds either text.
- `api/` is the folder to search.

A pass prints nothing. Run `echo $?` after it, and the number `1` means no match was found. A failure prints lines in the form `api/main.py:12: ...`. Usually a hard-coded connection string was pasted into the code, or the word `password` appears in a comment. Move the value into the environment and reword the comment. A harmless word in a comment still counts as a match, so avoid the word entirely in `api/`.

#### The other acceptance criteria

- **422 for bad hours.** Run `curl -i "localhost:8000/v1/stations/S1/readings?hours=0"` and then the same with `hours=500`. The double quotes stop the shell from treating `?` as a pattern. Both must print status `422`. The words after the number depend on the Python version: `Unprocessable Entity` on older ones, `Unprocessable Content` on newer ones. The number is what counts.
- **The OpenAPI page.** Open `http://localhost:8000/docs` in a browser. Every `/v1` endpoint must appear, with its parameters and their types. The raw description is at `http://localhost:8000/openapi.json`.
- **docs/api.md.** Each endpoint needs a method, path, inputs, an output example and status codes. A versioning section must also be present. Run `grep -n "^## \|^| " docs/api.md` to list the headings and table rows and check them against this list.

### Do it, step by step

#### Y2-T38.1: Set up the app and pin the dependencies

**Goal.** Install the three packages in an isolated environment, record their exact versions, and create an app that answers `/v1/health` without the database.

**Stage 1: create a virtual environment.** A virtual environment is a private folder of Python packages for this project. Run these from the repository root in Git Bash:

```bash
python -m venv .venv
source .venv/Scripts/activate
```

`python -m venv .venv` creates the folder `.venv`. `source .venv/Scripts/activate` loads it, and your prompt starts with `(.venv)`. On the lab's Linux machine, use `source .venv/bin/activate` instead, because the folder is named `bin` there and `Scripts` on Windows. Add `.venv/` to `.gitignore` later, so the folder is never committed.

**Stage 2: install the packages.**

```bash
pip install fastapi "uvicorn[standard]" "psycopg[binary]"
```

The quotes stop the shell from reading square brackets as a pattern. `uvicorn[standard]` adds extra speed-ups to Uvicorn. `psycopg[binary]` installs the Postgres driver with its compiled library already included, so you do not need a C compiler. Expect pip to finish with a line starting `Successfully installed`.

**Stage 3: pin the versions.**

```bash
pip freeze | grep -iE "^(fastapi|uvicorn|psycopg)"
```

`pip freeze` lists every installed package with its exact version. `grep -iE` keeps only the lines you want. `-i` ignores case, `-E` enables extended patterns, and `^(...)` matches the start of a line. It prints four lines, because `psycopg[binary]` also installs a package called `psycopg-binary`. Put three lines in `requirements.txt`, one per line, using the versions you saw and keeping the extras in square brackets: `fastapi==<version>`, `uvicorn[standard]==<version>` and `psycopg[binary]==<version>`. The `==` pins the exact version, so the same code installs the same packages on every machine. Check that pip accepts the file with `pip install -r requirements.txt`, which should report that everything is already satisfied.

**Test stage 3.** Run `python -c "import fastapi, uvicorn, psycopg; print('ready')"`. It must print `ready`. An error named `ModuleNotFoundError` means the install did not go into the active environment.

**Stage 4: create the package and a health route with no database.** Create the package marker and the app file:

```bash
mkdir -p api
touch api/__init__.py
```

`mkdir -p` creates the folder and does nothing if it already exists. `touch` creates an empty file. The empty `__init__.py` tells Python that `api` is a package, so `api.main` can be imported. Now create `api/main.py` with this first stage only:

```python
from fastapi import APIRouter, FastAPI

app = FastAPI(title="CityPulse API", version="0.1.0")
router = APIRouter(prefix="/v1")


@router.get("/health")
def health():
    return {"status": "ok"}


app.include_router(router)
```

Line by line:

- `from fastapi import APIRouter, FastAPI` takes two names from FastAPI. `FastAPI` creates the application. `APIRouter` groups routes under a shared prefix.
- `app = FastAPI(...)` creates the object that Uvicorn will serve. The title and version appear on the `/docs` page.
- `router = APIRouter(prefix="/v1")` means every route in this router starts with `/v1`.
- `@router.get("/health")` registers the next function for `GET /v1/health`.
- `def health():` is a plain function. FastAPI calls it when a request arrives.
- `return {"status": "ok"}` returns a Python dictionary. FastAPI sends it as the JSON body `{"status":"ok"}` with status `200`.
- `app.include_router(router)` attaches the router to the app. Without this line the route would not be served.

**Test stage 4.** From the repository root, start the server and ask it:

```bash
uvicorn api.main:app --port 8000 &
sleep 2
curl -i localhost:8000/v1/health
```

Expect `HTTP/1.1 200 OK` and `{"status":"ok"}`. Stop the server with `kill %1`, which works in the same terminal where you started it with `&`. Otherwise press Ctrl+C in the window where it runs.

#### Y2-T38.2: Write the q() helper

**Goal.** One function that runs a SQL query with the connection string from the environment, times out quickly, and returns a list of dictionaries.

**Teach the pieces first.** A `with` block opens a resource and closes it at the end, even if an error happens inside it. Here it guarantees that each connection is closed. A placeholder `%s` marks where a value goes in a query. The values are passed as a separate tuple, and the driver escapes them, so user input can never change the query's meaning.

Here is a small example with no database. It shows the difference between building a string and passing parameters:

```python
station_id = "S1"
unsafe = f"SELECT * FROM readings WHERE station_id = '{station_id}'"
safe = ("SELECT * FROM readings WHERE station_id = %s", (station_id,))
print(safe)
```

The first line stores a value. The second line builds a query by pasting the value into the text, which is unsafe if the value comes from a web request. The third line keeps the query text fixed and sends the value as the separate tuple `(station_id,)`. The comma makes it a one-item tuple. The last line prints the pair, which shows `('SELECT * FROM readings WHERE station_id = %s', ('S1',))`.

**Stage 1: add the helper to `api/main.py`.** Add these imports to the top of the file, above `app = FastAPI(...)`:

```python
import os

import psycopg
from psycopg.rows import dict_row
```

Then add the helper:

```python
def q(sql, params=None):
    with psycopg.connect(os.environ["DATABASE_URL"],
                         connect_timeout=3, row_factory=dict_row) as conn:
        with conn.cursor() as cur:
            cur.execute(sql, params)
            return cur.fetchall()
```

Line by line:

- `os.environ["DATABASE_URL"]` reads the connection string. If the variable is missing, Python raises a `KeyError`.
- `psycopg.connect(...)` opens a connection. `connect_timeout=3` gives up after three seconds.
- `row_factory=dict_row` makes each row a dictionary.
- `with ... as conn:` closes the connection at the end of the block.
- `conn.cursor()` creates a cursor, the object that runs statements.
- `cur.execute(sql, params)` runs the query. Passing `params` as a separate argument keeps the query safe.
- `return cur.fetchall()` collects every row into a list before the block closes. The list is returned as the function's result.

**Test stage 1.** Run this with the variable set:

```bash
python -c "from api.main import q; print(q('SELECT 1 AS ok'))"
```

The output must be `[{'ok': 1}]`. A `KeyError: 'DATABASE_URL'` means the variable is not set in this terminal, so run the `export` line from the start of this guide again.

**Stage 2: update the health route to ask the database.** Replace the body of `health()` with a call to the database:

```python
@router.get("/health")
def health():
    try:
        q("SELECT 1")
    except psycopg.OperationalError:
        raise HTTPException(status_code=503, detail="database unavailable")
    return {"status": "ok"}
```

You also need `HTTPException` in the import from `fastapi`. Add it to the same line as `APIRouter` and `FastAPI`.

The `try:` block runs the query. `except psycopg.OperationalError:` catches only connection-type errors from the driver. Other errors still show up as real bugs. `raise HTTPException(status_code=503, ...)` stops the function and makes FastAPI send `503` with a short message in the body. The final `return` only runs when the query worked.

Watch the whole journey of one request, with the database up and then down:

```flow
TITLE: One health request, database up and down
NODES: Dashboard | FastAPI app | Postgres
STEPS:
1>2 :: GET /v1/health :: The client asks whether the service is healthy.
2>3 :: SELECT 1 :: The health function runs the cheapest possible query.
3>2 :: one row :: The database answers, so the query worked.
2>1 :: 200 ok :: The app returns the status ok.
1>2 :: GET /v1/health :: Later the database container is stopped and the client asks again.
2>3 :: SELECT 1 :: The driver tries to connect.
3>2 :: no answer :: Connection refused or timed out after at most 3 seconds, so OperationalError is raised.
2>1 :: 503 unavailable :: The except block turns it into a 503 with a short message.
```

**Test stage 2.** Run TC1 and confirm `200`. Then run TC2 and confirm `503`. Do this before you move on, because the 503 path is the one most likely to be wrong.

#### Y2-T38.3: Write the /v1/stats SQL and check it in psql

**Goal.** Write one SQL query that returns a few aggregate numbers, check it in psql, and then wrap it in an endpoint whose timestamps carry the `+05:30` offset.

**Stage 1: write the query and check it.** The names `readings`, `station_id` and `recorded_at` below are placeholders. Replace them with the table, view and column names from your SQL phase. Use `\dt` and `\dv` inside psql to list them, and `\d <name>` to see the columns.

```bash
psql "$DATABASE_URL" -c "SELECT count(*) AS total_readings, count(DISTINCT station_id) AS stations, max(recorded_at) AS latest FROM readings;"
```

Each part does one job. `count(*)` counts all rows. `count(DISTINCT station_id)` counts the different stations. `max(recorded_at)` finds the latest timestamp. These are aggregates: each one combines many rows into one value. The `FROM` clause names the table. The semicolon ends the statement.

A sample output looks like this, with numbers from your own database:

```term
$ psql "$DATABASE_URL" -c "SELECT count(*) AS total_readings, ..."
 total_readings | stations |         latest
----------------+----------+------------------------
            480 |        6 | 2026-11-16 04:30:00+00
(1 row)
```

Save these values. The ticket says the API must match them. The `+00` at the end is the UTC offset that psql shows, and you will convert it in the next stage.

**Stage 2: learn the timestamp conversion.** A timestamp with a time zone is a single point in time. The API must show it in IST, which is `+05:30`. The next block shows the idea with the standard library only:

```python test
from datetime import datetime, timedelta, timezone

IST = timezone(timedelta(hours=5, minutes=30))
utc_time = datetime(2026, 11, 16, 4, 30, tzinfo=timezone.utc)
local = utc_time.astimezone(IST)
assert local.isoformat() == "2026-11-16T10:00:00+05:30"
assert local.utcoffset() == timedelta(hours=5, minutes=30)
```

`timedelta(hours=5, minutes=30)` is a length of time. `timezone(...)` turns it into a named offset, here IST. `tzinfo=timezone.utc` says the first datetime is in UTC. `astimezone(IST)` converts it, which adds five and a half hours. `isoformat()` prints ISO 8601 text, including the offset. Both `assert` lines must pass, and the block should finish without any output. Run it with `python`, and if it prints an `AssertionError`, check the arithmetic.

One warning. The `psycopg` driver returns a timezone-aware datetime for a `timestamptz` column. If your column has no time zone, `astimezone` assumes the machine's local time, and the result can be wrong on another machine. Check the column type with `\d` in psql.

**Stage 3: add the endpoint.** Add these imports at the top of `api/main.py`, next to the others:

```python
from datetime import timedelta, timezone
```

```python
from typing import Annotated

@router.get("/stations/{station_id}/readings")
def station_readings(station_id: str, hours: Annotated[int, Query(ge=1, le=168)] = 24):
    try:
        found = q("SELECT 1 FROM stations WHERE station_id = %s", (station_id,))
        if not found:
            raise HTTPException(status_code=404, detail="unknown station")
        rows = q(
            "SELECT recorded_at FROM readings "
            "WHERE station_id = %s AND recorded_at >= now() - make_interval(hours => %s) "
            "ORDER BY recorded_at",
            (station_id, hours),
        )
    except psycopg.OperationalError:
        raise HTTPException(status_code=503, detail="database unavailable")
    return [{"recorded_at": r["recorded_at"].astimezone(IST).isoformat()} for r in rows]
```

Line by line, the key ideas are these. `station_id: str` is a path parameter, and `hours` is a query parameter with a default of `24`. `Query(ge=1, le=168)` says `hours` must be between 1 and 168. Your squad may choose other bounds, but `0` and `500` must both fail. `if not found:` is true when the query returned an empty list, so the station does not exist and you raise a `404`. `make_interval(hours => %s)` is a Postgres function that builds a time span of that many hours. `now() - ...` subtracts it from the current time. The list comprehension converts each row into a dictionary whose timestamp has the IST offset.

Note that `HTTPException(404)` is not an `OperationalError`, so the `except` block does not catch it, and the 404 reaches the client. `hours` is validated before the function runs, so a bad value gives `422` with no database call.

The stations table name is a placeholder. If your squad stores stations differently, change the first query, and document the rule in `docs/api.md`. A known station with no readings should return `200` with an empty list, not a `404`.

### Defend it in the viva

**Q1. Why return 503 instead of letting the database error become a 500?**

:::answer Model answer
A 500 means the server had an unexpected bug. A 503 means the server is working but a service it needs is currently unavailable, so the client may retry later. Catching `psycopg.OperationalError` and raising `HTTPException(status_code=503)` gives the dashboard an accurate status and a short message. Letting the error escape would send a 500 with a traceback, which hides the cause and gives no retry guidance.
:::

**Q2. Why is the health route a plain `def` and not `async def`, when it calls psycopg?**

:::answer Model answer
psycopg waits for the database to reply, and that wait blocks the thread it runs on. In an `async def` function a blocking call stops the event loop, so other requests wait too. A plain `def` function is run by FastAPI in a thread pool, so the wait happens in a separate thread. The trade-off is that a thread pool has a limit on concurrent work, which is acceptable for version 0.
:::

**Q3. What is the trade-off in putting the version in the path, as `/v1/...`, instead of in a header?**

:::answer Model answer
A path version is visible in every URL, so it is easy to copy into a browser, to put in a `curl` command, and to see in logs. A header keeps URLs clean and is more flexible, but it is harder to test by hand and easier to forget. For a small dashboard team, visibility is worth more than cleaner URLs.
:::

**Q5. Why does the health check run `SELECT 1` and not just return `ok`?**

:::answer Model answer
Returning `ok` without touching the database would report the service as healthy even when the database is down, which is the silent failure the ticket forbids. `SELECT 1` is the cheapest query that forces a real connection to the database. If it fails, the health route can honestly return 503.
:::
