### The ticket in plain words

Until now, the CityPulse fetch step has run on a virtual machine (a rented computer that is switched on all the time). That machine sits idle most of the day and someone has to patch it. This ticket asks a plain question: for a job that runs every 30 minutes, is a serverless function cheaper and simpler? The honest answer is that it depends, so the client wants numbers rather than opinions.

You will move the fetch into an AWS Lambda function. Lambda runs your code only when something calls it. A timer will call it every 30 minutes. The function asks the Open-Meteo air-quality API for Bengaluru readings, checks the reply, and saves the raw JSON into your CityPulse bucket (a private storage container in S3). The function uses a role, which is a set of permissions AWS hands to the function for a short time. That means no password or access key is stored in its settings.

Then you prove it works from the logs. Two runs started by the timer, not by you, must leave lines in the logs and files in the bucket. Last, you compare the monthly cost of the virtual machine with the monthly cost of the function, using AWS's own pricing calculator. You then work out how many runs it would take before the two costs are equal.

The description does not name a specific failure. Its point is that teams have moved in both directions, so the decision must rest on measured cost.

### How your trainer checks it

The trainer runs five test cases and checks five acceptance criteria. The criteria are: at least two scheduled runs in the logs, each with a matching object in the bucket; the role is `citypulse-fetch-fn` and no access key appears; both monthly figures come from the calculator with arithmetic and a break-even statement; the account ID in the evidence is your own; and the schedule is `rate(30 minutes)` or disabled.

**TC1, the function configuration.**

```
aws lambda get-function-configuration --function-name citypulse-fetch --query '{Role:Role,Env:Environment.Variables,Timeout:Timeout,Mem:MemorySize}'
```

- `aws lambda get-function-configuration` reads the settings of the function.
- `--function-name citypulse-fetch` names the function.
- `--query` picks out fields. Inside the braces, `Role:Role` means "a field called Role, taken from the Role setting". The same pattern applies to the other fields.

Passing output:

```
{
    "Role": "arn:aws:iam::123456789012:role/citypulse-fetch-fn",
    "Env": {
        "CITYPULSE_BUCKET": "citypulse-example-k9x2"
    },
    "Timeout": 60,
    "Mem": 256
}
```

The role must end with `role/citypulse-fetch-fn`. `Env` must hold only `CITYPULSE_BUCKET`, and `AQI_URL` is allowed too. `Timeout` must be 60 and `Mem` must be 256. The bucket name and account number above are made up. Yours will differ.

A failing output usually has one of three causes. If `Env` contains `AWS_ACCESS_KEY_ID`, you stored a key, so remove it. If `Env` is `null`, the variable was never set, which means `deploy.sh` missed the `--environment` flag. If `Timeout` is 3, you created the function without `--timeout 60`.

**TC2, the scheduled runs in the logs.**

```
aws logs tail /aws/lambda/citypulse-fetch --since 1h | grep -c 'wrote s3://'
```

- `aws logs tail` prints the recent lines in one log group.
- `--since 1h` limits the output to the last hour.
- `|` is the pipe. It sends the lines into the next command as input.
- `grep -c` counts the lines that match the text.
- `'wrote s3://'` is the text to match. This is why your handler must print that exact text.

Passing output (the trainer needs a number of at least 2):

```term
$ aws logs tail /aws/lambda/citypulse-fetch --since 1h | grep -c 'wrote s3://'
2
```

A result of 0 means the handler does not print that text, or no run has happened. A result of 1 usually means only your manual invoke ran, so the schedule has not fired yet.

**TC3, the objects in the bucket.**

```
aws s3 ls s3://<bucket>/raw/openmeteo-aq/ --recursive
```

- `aws s3 ls` lists objects under a prefix.
- `--recursive` goes into every sub-folder, which here are the `date=` folders.

Passing output has at least two lines ending in `fetch_HHMM.json`, about five or thirty minutes apart. An example line looks like `2027-01-12 09:00:03  12345 raw/openmeteo-aq/date=2027-01-12/fetch_0900.json`. Replace `<bucket>` with your own bucket name. An empty result means the wrong bucket or a wrong prefix. One line only means both runs wrote the same minute, or only one run has happened.

**TC4, the schedule.**

```
aws scheduler get-schedule --name citypulse-fetch-30m --query '{s:ScheduleExpression,st:State}'
```

- `aws scheduler get-schedule` reads one schedule by name.
- The query returns the expression as `s` and the state as `st`.

Passing output is `{"s": "rate(30 minutes)", "st": "ENABLED"}` or the same with `"st": "DISABLED"`. If you see `rate(5 minutes)`, you forgot step Y2-T23.7. If you see `ResourceNotFoundException`, the name does not match exactly.

**TC5, the cost document.** Open `docs/cloud-cost.md` and check by eye. There must be two calculator links, two monthly totals in rupees or US dollars, arithmetic lines and a break-even statement. A missing date next to the links is a fail.

### Do it, step by step

#### Y2-T23.1: Create the function's role

**Goal.** A role named `citypulse-fetch-fn` that Lambda can take on, with permission to write the bucket prefix and to write logs. There is no access key.

**The idea.** A role has two parts. The trust policy says who may wear the role. The permission policies say what the role may do.

**Stage 1, the trust policy.** Save this as `infra/function/trust.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "lambda.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}
```

Each line says the following. `Effect` allows the statement. `Principal` names Lambda as the service allowed to wear the role. `Action` names the wearing action, `sts:AssumeRole`. Test it with `python -m json.tool infra/function/trust.json`. Expected output is the same JSON, reformatted. An error with a line number means a missing comma.

**Stage 2, create the role.**

```bash
aws iam create-role --role-name citypulse-fetch-fn \
  --assume-role-policy-document file://infra/function/trust.json \
  --query Role.Arn --output text
```

`create-role` makes the role. `file://` tells the CLI to read the JSON from a file. `--query Role.Arn --output text` prints only the ARN. Expected output: one line such as `arn:aws:iam::<your account>:role/citypulse-fetch-fn`.

**Stage 3, the logging permission.**

```bash
aws iam attach-role-policy --role-name citypulse-fetch-fn \
  --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole
```

This attaches AWS's standard logging policy. It prints nothing when it succeeds.

**Stage 4, the bucket permission.** Paste the ARN from the Before you start check into the command:

```bash
aws iam attach-role-policy --role-name citypulse-fetch-fn --policy-arn <ARN of citypulse-pipeline-s3>
```

The D15 walk-through writes an inline policy instead. Your ticket names the policy `citypulse-pipeline-s3`, so attach that one. Check that it allows `s3:PutObject` only on the `raw/openmeteo-aq/` prefix.

**Test.** Run `aws iam list-attached-role-policies --role-name citypulse-fetch-fn --query "AttachedPolicies[].PolicyName" --output text`. Expected output: both policy names. A role has no access key, so none is created.

:::trap A new role is refused
Lambda sometimes rejects a role that was created seconds ago. If `create-function` later says the role cannot be assumed, wait 20 seconds and run the command again.
:::

#### Y2-T23.2: Write the handler and its test

**Goal.** `infra/function/handler.py` that fetches, checks, saves and logs. `tests/test_handler_key.py` that tests the key format.

**Technique first: a date to text.** `strftime` turns a date into text using codes. `%Y` is the four-digit year, `%m` the month, `%d` the day, `%H` the hour and `%M` the minute.

```python
from datetime import datetime, timezone
now = datetime(2027, 1, 12, 9, 0, tzinfo=timezone.utc)
print(now.strftime("fetch_%H%M.json"))
```

Expected output: `fetch_0900.json`. The code is standard library only.

**Stage 1, imports and client.** Create `infra/function/handler.py` with these lines. Copy the API address string from your `src/citypulse/fetch.py` into `AQI_URL`:

```python
import json
import os
import urllib.request
from datetime import datetime, timezone

import boto3

AQI_URL = "<paste the address from fetch.py>"
s3 = boto3.client("s3")  # created once per container, reused on warm starts
```

`os.environ` reads the settings that Lambda passes in. `boto3.client("s3")` sits at module level, so it is built once when the container starts. Test with `python -c "import ast; ast.parse(open('infra/function/handler.py').read())"`. No output means the syntax is valid.

**Stage 2, the key.** Add this function. It is separate so that the test can call it without making a network request:

```python
def make_key(now):
    return now.strftime("raw/openmeteo-aq/date=%Y-%m-%d/fetch_%H%M.json")
```

The function takes a time and returns the key as text. The key depends only on the minute, so two runs in the same minute write the same object.

**Stage 3, fetch and check.** Add this function:

```python
def fetch_body():
    with urllib.request.urlopen(AQI_URL, timeout=20) as r:
        if r.status != 200:
            raise RuntimeError(f"API returned {r.status}")
        body = r.read()
    json.loads(body)  # raises ValueError if the body is not JSON
    return body
```

`urlopen` raises an error for most failed HTTP codes already. The `if` check makes the rule explicit for any non-200 reply. The `json.loads` line is only a check, and it raises an error if the body is not JSON. Errors must be raised, not caught, so that the run is marked as failed.

**Stage 4, the handler.** Fill in the three TODO lines. Try them yourself before you use the hints after the code:

```python

    key = make_key(datetime.now(timezone.utc))
    bucket = os.environ["CITYPULSE_BUCKET"]
    # TODO 1: call s3.put_object with Bucket=bucket, Key=key and Body=body
    # TODO 2: print one line in this exact shape: wrote s3://<bucket>/<key> bytes=<n>
    # TODO 3: return {"key": key, "bytes": len(body)}
```

The printed text must start with `wrote s3://`, because TC2 counts that text. Hints: `put_object` takes keyword arguments, and `len(body)` gives the byte count. An f-string can build the printed line.

**Stage 5, the test.** Create `tests/test_handler_key.py` at the repository root:

Add two more tests yourself, one for 17:05 UTC and one for 00:00 UTC. Run them from the repository root with `PYTHONPATH=infra/function python -m pytest tests/test_handler_key.py -q`. `PYTHONPATH` tells Python where to find `handler.py`. Expected output: `3 passed`. #### Y2-T23.3: Write the deploy script

**Goal.** `infra/function/deploy.sh` that zips the handler, creates the function the first time, updates it afterwards, and waits until it is active.

**Technique first: `set -euo pipefail`.** The three flags make a script stricter. `-e` stops at the first failing command. `-u` stops if you use a variable that is not set. `-o pipefail` makes a pipeline fail if any step fails. Without them, a broken deploy can look like a success.

**Stage 1, the header.** Create the file with:

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")"
FN=citypulse-fetch
```

`cd "$(dirname "$0")"` moves into the folder that holds the script, so the zip paths are right whatever folder you run it from. `FN` stores the function name in one place.

**Stage 2, the zip.**

```bash
python -m zipfile -c function.zip handler.py
```

`-c` creates an archive called `function.zip` containing `handler.py`. Test it with `python -m zipfile -l function.zip`. Expected output lists `handler.py`. Add `function.zip` to `.gitignore`, because the zip is a build product and should not be committed.

**Stage 3, create or update.** Lambda needs a different command the first time and every time after. Fill in the TODO:

```bash
if aws lambda get-function --function-name "$FN" >/dev/null 2>&1; then
  aws lambda update-function-code --function-name "$FN" --zip-file fileb://function.zip
else
  # TODO: aws lambda create-function with these flags:
  #   --runtime python3.12  --handler handler.handler
  #   --role <ARN of citypulse-fetch-fn>  --memory-size 256  --timeout 60
  #   --environment "Variables={CITYPULSE_BUCKET=<your bucket>}"
  #   --zip-file fileb://function.zip
fi
```

`get-function` succeeds if the function exists. The `>/dev/null 2>&1` part hides its output. `--handler handler.handler` means file `handler`, function `handler`. Get the role ARN with `aws iam get-role --role-name citypulse-fetch-fn --query Role.Arn --output text`. The `Variables={...}` syntax sets one environment variable. Do not add any AWS key here.

**Stage 4, wait.**

```bash
aws lambda wait function-updated-v2 --function-name "$FN"
echo "deployed $FN"
```

`wait` blocks until Lambda has finished creating or updating the function. This matters on the update path, because the function is already "active" while the new code is still being installed. Expected last line: `deployed citypulse-fetch`.

#### Y2-T23.5: Schedule two runs and save evidence

**Goal.** A schedule that calls the function every five minutes, two scheduled runs in the logs and bucket listing, and the evidence files.

**Technique first: an invoke role.** The scheduler calls the function with its own role. That role must trust `scheduler.amazonaws.com`. Its permission policy allows only `lambda:InvokeFunction` on your function.

```flow
TITLE: One scheduled run, end to end
NODES: EventBridge Scheduler | Lambda function | Open-Meteo | S3 bucket | CloudWatch Logs
STEPS:
1>2 :: invoke :: The scheduler calls the function with its scheduler role.
2>3 :: GET air quality :: The handler asks the API for Bengaluru readings.
3>2 :: JSON body :: The API returns the hourly values.
2>4 :: put_object :: The handler saves the body under raw/openmeteo-aq/.
2>5 :: log lines :: The handler prints the wrote line, and Lambda writes the REPORT line.
```

**Stage 1, the scheduler role.** Save this trust policy as `sched-trust.json`:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "scheduler.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}
```

Then run `aws iam create-role --role-name citypulse-scheduler --assume-role-policy-document file://sched-trust.json`. Write a policy file `sched-invoke.json` with `"Action": "lambda:InvokeFunction"` and `"Resource"` set to your function's ARN, then attach it with `aws iam put-role-policy --role-name citypulse-scheduler --policy-name invoke-fetch --policy-document file://sched-invoke.json`.

**Stage 2, the schedule.** Set the two ARNs as variables and create the schedule:

```bash
FN_ARN=$(aws lambda get-function --function-name citypulse-fetch --query Configuration.FunctionArn --output text)
ROLE_ARN=$(aws iam get-role --role-name citypulse-scheduler --query Role.Arn --output text)
aws scheduler create-schedule --name citypulse-fetch-30m \
  --schedule-expression "rate(5 minutes)" --flexible-time-window Mode=OFF \
  --target "Arn=$FN_ARN,RoleArn=$ROLE_ARN"
```

`$(...)` runs a command and stores its output in a variable. `Mode=OFF` means the run happens at the exact time. Expected output: a `ScheduleArn`. The name `citypulse-fetch-30m` is required by the ticket, even though the rate starts at five minutes.

**Stage 3, wait and look.** Wait at least ten minutes. Then run `aws logs tail /aws/lambda/citypulse-fetch --since 30m`. Look for `wrote s3://` lines about five minutes apart. Your manual invoke from T23.4 happened before the schedule existed, so the scheduled runs are the later ones.

`>` writes the output into a file instead of the screen. Take a screenshot of the log lines as well, and save it in the same folder.

#### Y2-T23.6: Write docs/cloud-cost.md

**Goal.** A document with two monthly figures from the AWS pricing calculator, with links, a date, arithmetic and a break-even statement.

**Technique first: the arithmetic.** Lambda bills GB-seconds. Work out the monthly GB-seconds with this trace, using made-up numbers. Replace them with your own measured figures.

```trace
TITLE: Monthly Lambda usage with made-up numbers
CODE:
invocations = 48 * 30
billed_s = 0.9
gb = 256 / 1024
gb_seconds = invocations * billed_s * gb
price = 0.00002
compute = gb_seconds * price
STEPS:
1 :: invocations=1440 :: 48 runs a day for 30 days gives 1,440 runs a month.
2 :: invocations=1440; billed_s=0.9 :: 0.9 is a made-up billed time. Use your own REPORT figure, divided by 1,000.
3 :: invocations=1440; billed_s=0.9; gb=0.25 :: 256 MB divided by 1,024 gives 0.25 GB.
4 :: gb_seconds=324.0 :: 1,440 times 0.9 times 0.25 is 324 GB-seconds.
5 :: price=0.00002 :: A placeholder price. Take the real price from the calculator, not from here.
6 :: compute=0.00648 :: Compute cost is GB-seconds times the price. Requests are added separately.
```

**Stage 1, the table.** Create `docs/cloud-cost.md` with a table that has one row per student: name, billed milliseconds, max memory used, Lambda monthly and VM monthly.

**Stage 2, the calculator.** Open calculator.aws. Choose the same region as your deployment (Asia Pacific (Mumbai) if you used ap-south-1). **Stage 3, the VM.** Add a second estimate in the same region for a `t3.micro` instance running 730 hours a month, with an 8 GB gp3 volume. Copy that link too, and write its date. Record both monthly totals and the currency.

### Defend it in the viva

**Q1 (why). Why is a scheduled function cheaper than a virtual machine for this fetch?**

:::answer Model answer
The fetch runs for about two seconds every 30 minutes. Lambda bills only for the GB-seconds and requests used, so the monthly cost is a small number. A virtual machine is billed for every hour it is switched on, which is about 730 hours a month, and it still needs patching when idle. For this workload, pay-per-use is much cheaper. The calculator figures show it, and the break-even count shows how far the workload is from the point where the VM would win.
:::

**Q2 (trade-off). What do you trade away by choosing Lambda, and how would you decide if the workload changed?**

:::answer Model answer
Lambda caps a run at 15 minutes and gives less control of the environment. Each cold start also adds a delay. In return you get no server to patch and no idle cost. If the job grew to run for longer than 15 minutes, or ran nearly all day, I would compare the monthly figures again and consider a container service or a VM. I would base that choice on the calculator numbers, not on habit.
:::

**Q3 (what you did). Which part did you build, and how do you know it works?**

:::answer Model answer
Describe the subtask you owned in your own words, name the file and the test that covers it, and give the command that proves it. For example, you might say you wrote the key function and its test, ran `pytest` in CI, and then checked TC3 in the bucket listing. Your viva answer should match your own commits in the PR, so review them before the viva.
:::

**Q4 (why). Why does the object key depend only on the minute, and what happens on a retry?**

:::answer Model answer
The key is built from the date and the minute. If a retry happens in the same minute, the same key is written again and the object is replaced, so the bucket does not fill with duplicates. This makes the write idempotent, meaning running it twice leaves the same result. A retry in a later minute does create a new object, and that is expected, because it is a new reading.
:::

**Q5 (why). Why must the handler raise an error on bad data, rather than catch it and return success?**

:::answer Model answer
If the handler catches the error and returns success, CloudWatch records a successful run, and the bad data goes unnoticed. When the handler raises the error, the invocation is marked as failed. The failure then shows in the logs and in the error metric. An honest failure is more useful than a quiet success, because the team can see it and fix it.
:::

### Check yourself

```quiz
Q: Which setting lets the fetch function write to the bucket without any access key?
- An access key stored in an environment variable
* The execution role, whose policy allows s3:PutObject on the raw prefix
- A public write permission on the whole bucket
- An administrator password written into handler.py
WHY: The execution role is an identity that Lambda takes on, and AWS gives temporary credentials for it. A stored key is forbidden. Public write access is unsafe, and a password in code leaks.

Q: TC2 prints 0, yet the logs show that the function ran. What is the most likely cause?
- The timeout is set to 60 seconds
- The memory is set to 256 MB
* The printed line does not contain the text wrote s3://
- The schedule is set to rate(30 minutes)
WHY: grep -c counts only lines that contain the exact text. A handler that prints a different message runs fine but scores 0. The timeout and memory settings are correct values, and the schedule has no effect on the text printed.

Q: A function runs 1,440 times a month, bills 0.5 seconds per run, and has 512 MB of memory. How many GB-seconds does it bill per month?
- 180
- 1,440
- 360,000
* 360
WHY: 512 MB is 0.5 GB. 1,440 times 0.5 seconds is 720 seconds, and 720 times 0.5 GB is 360 GB-seconds. The 360,000 answer forgets to convert megabytes to gigabytes, and 180 divides by the wrong factor.
```
