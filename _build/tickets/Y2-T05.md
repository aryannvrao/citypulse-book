### The ticket in plain words

CityPulse is a platform that tracks city data for Bengaluru. Its first job is the simplest one: fetch one real reading from an outside service, store it in a file, and do it the same way every time. Everything later in the course depends on this. If the data does not arrive reliably, the charts, alerts and forecasts built on top of it are wrong, and nobody notices until it is too late.

This ticket asks your squad for one script, `scripts/fetch_once.sh`. Run it once and it asks the source's web address for one reading. It takes out four things: the timestamp, the location and two measurements. Then it adds them as one new line to today's CSV file, which is a plain text table. Run it again and it adds another line.

The script must be strict. If the service answers with anything other than the normal success code, the script prints an error to the error channel, writes nothing and stops with a failure code. A quiet failure is how a dashboard ends up showing yesterday's air as today's.

The ticket also warns about keys. A key is a secret string that a service gives you to prove who is asking. The danger is simple. A key typed into a script gets committed to Git, and Git keeps every version forever. Deleting the line later does not remove the copy in the history. So keys come only from environment variables, and your trainer searches the whole history for them. The default source, Open-Meteo, needs no key at all.

### How your trainer checks it

Your trainer runs the five test cases in order on the lab machine, from a fresh clone. Each acceptance criterion is covered by one of them, except the cold-call one, which is a spoken question.

- **AC1, fresh clone:** after `git clone`, running `./scripts/fetch_once.sh` from the repo root exits with 0 and adds exactly one row to `data/raw/<today>.csv`. The file has four columns. This is checked by TC1 and by `echo $?` straight after a run.
- **AC2, run twice:** an empty day file, after two runs, has one header line and two data rows. This is TC1.
- **AC3, 404 endpoint:** the script prints `ERROR: HTTP 404` to stderr, appends nothing and exits non-zero. This is TC2.
- **AC4, no keys:** the whole history has zero matches for key-like text. This is TC3.
- **AC5, README:** a `How to fetch` section shows the run command and a sample row. This is TC5.
- **AC6, cold call:** the trainer points at a stage of your one-liner and asks what it outputs. There is no command for this. You prepare by explaining each pipe stage out loud, in your own words.

**TC1: two runs, then count the lines.**

The steps are: `rm -f data/raw/$(date +%F).csv; ./scripts/fetch_once.sh; ./scripts/fetch_once.sh; wc -l data/raw/$(date +%F).csv; head -1 data/raw/$(date +%F).csv`

Broken into parts:

- `rm -f data/raw/$(date +%F).csv` deletes today's day file if it exists. `-f` means "no error if it is missing". `$(date +%F)` runs `date +%F`, which prints today's date like `2026-11-17`, and puts that text into the path.
- `;` runs the next command whatever the result of the previous one. The trainer uses `;` rather than `&&` so that every command runs even when one fails.
- `./scripts/fetch_once.sh` runs your script from the current folder. The first run creates the file and the header.
- The second `./scripts/fetch_once.sh` run adds the second row.
- `wc -l file` counts the newline characters in the file. Each line ends with one newline, so this counts lines. It prints the count and then the file name.
- `head -1 file` prints the first line, which should be the header.

Passing output. The date below is the day you run it. Your script's success message may use different words, but there should be one line per run:

```term
$ rm -f data/raw/2026-11-17.csv
$ ./scripts/fetch_once.sh
OK: row added to data/raw/2026-11-17.csv
$ ./scripts/fetch_once.sh
OK: row added to data/raw/2026-11-17.csv
$ wc -l data/raw/2026-11-17.csv
3 data/raw/2026-11-17.csv
$ head -1 data/raw/2026-11-17.csv
timestamp,location,pm2_5,pm10
```

Failing outputs and their usual causes:

- `5 data/raw/...` or `4 data/raw/...`: the header was written again on the second run, or a row was written twice. Check the header test in your script.
- `2 data/raw/...`: one run added no row. The script probably stopped early or wrote nothing and still exited with 0.
- `curl: (6) Could not resolve host`: the machine has no network, or the host in your URL is mistyped. Compare it with the README.
- `head -1` shows something that is not a header, such as a JSON brace: the body was written to the day file by mistake, so check your redirect.

**TC2: a 404 must fail loudly and write nothing.**

The steps are: `URL=https://air-quality-api.open-meteo.com/v1/nope ./scripts/fetch_once.sh; echo "exit=$?"`

Broken into parts:

- `URL=... ./scripts/fetch_once.sh` sets the variable `URL` for this one command only. Your script must read `URL` from the environment, which is why the default must be written as `${URL:-...}`.
- `echo "exit=$?"` prints the exit code of the script. `$?` holds the exit code of the last command. The double quotes let the value appear inside the text.

Passing output: a line on stderr such as `ERROR: HTTP 404 from https://air-quality-api.open-meteo.com/v1/nope`, then `exit=1`. No new row is added.

Failing outputs:

- `exit=0`: the script does not stop after a bad status, or it reports success at the end regardless.
- No `ERROR:` line: the message was printed to standard output, or the status is never checked.
- A new row appears in the day file: the append runs before the status check. Move the check above the write.

**TC3: the history must hold no keys.**

The steps are: `git log -p --all | grep -nEi '(api[_-]?key|token|secret)\s*[:=]\s*[A-Za-z0-9]{16,}' | head`

Broken into parts:

- `git log -p --all` prints every commit on every branch, with the changes in each one (`-p` means patch, which shows the changed lines).
- `|` sends that long text into `grep`.
- `grep -nEi 'pattern'` searches for the pattern. `-n` prints line numbers, `-E` allows extended patterns, and `-i` ignores capital letters.
- In the pattern, `(api[_-]?key|token|secret)` matches the words `api_key`, `apikey`, `api-key`, `token` or `secret`. The `[_-]?` means an underscore or hyphen is optional.
- `\s*[:=]\s*` means optional spaces, then a colon or an equals sign, then optional spaces.
- `[A-Za-z0-9]{16,}` means at least 16 letters or digits in a row. Short placeholders such as `changeme` do not match.
- `| head` shows only the first ten matching lines.

Passing output: nothing at all.

Failing output: a line starting with a line number, a colon, then a plus sign and the matching text. The plus sign means the line was added in that commit. Do not paste the matched text anywhere. The cause is a real key in a commit. The fix is to rotate the key at the service, then tell your trainer. Deleting the line in a new commit is not enough, because the old commit still holds it.

:::trap Slow on long histories
`git log -p --all` can take a while on a repository with many commits. Wait for it to finish. Do not stop it halfway and assume the history is clean.
:::

**TC4: every row must have four fields.**

The steps are: `awk -F, 'NR>1 && NF!=4' data/raw/$(date +%F).csv | wc -l`

Broken into parts:

- `awk -F,` splits each line into fields at every comma.
- `NR>1` is true for every line after the first. `NR` is the line number, so this skips the header.
- `NF` is the number of fields on the line. `NF!=4` is true when the count is not four.
- The pattern with no action prints each line that is true.
- `| wc -l` counts how many lines were printed.

Passing output: `0`.

Failing output: a number above 0. The usual causes are a blank line (which has zero fields), a location name that contains an unquoted comma, or a row with an extra column. awk does not understand CSV quotes, so a quoted field containing a comma counts as two fields.

:::trap TC4 does not catch empty values
A missing value such as `null` still produces four fields, because `@csv` writes an empty field. TC4 passes, but the row is wrong. That is why your script checks the fields with `jq -e` before it writes anything.
:::

**TC5: the README needs a How to fetch section.**

The steps are: `grep -n '## How to fetch' README.md`

Broken into parts:

- `grep -n` searches the file and prints each matching line with its line number.
- `'## How to fetch'` is the text to find, in single quotes so the shell leaves the spaces and hashes alone.
- `README.md` is the file to search.

Passing output: a line such as `42:## How to fetch`. The number will differ.

Failing output: nothing. The heading is missing, or it is spelled with different capitals, because `grep` is case-sensitive without `-i`. Note that `### How to fetch` also matches, because it contains the same text. Your trainer then reads the section, so it must hold a run command and a sample row.

### Do it, step by step

#### Y2-T05.1 Explore the source

Goal: know exactly which fields the reply holds, before you write any code that uses them.

Stage 1. Put the verified URL from your README into a variable and fetch the reply. Run this in Git Bash:

```bash
URL="PASTE_YOUR_README_URL"
curl -s "$URL" | jq .
```

Line by line:

- `URL="..."` stores the text in a shell variable. Replace the placeholder with your URL, keeping the double quotes.
- `curl -s "$URL"` fetches the reply. `-s` hides the progress meter.
- `| jq .` pipes the body into jq. The filter `.` means "the whole input", so jq prints the JSON with indentation.

Expected output: a block of indented JSON with keys such as `latitude`, `longitude` and `current`, where `current` holds a time and the measurements.

The README URL must carry its query string, which for Open-Meteo looks like `...?latitude=12.97&longitude=77.59&current=pm10,pm2_5`. Without a `current=` part there is no `current` object in the reply, so Stage 2 would print `null`. If that happens, fix the URL in the README with your squad. Keep the double quotes, because `&` would otherwise end the command.

Stage 2. List the keys inside `current` so you know the exact names:

```bash
curl -s "$URL" | jq '.current | keys'
```

Line by line: `.current` selects the object inside the key `current`, and `| keys` returns its key names as a sorted list. Expected output is a list in square brackets, with one quoted name per line. Copy the names exactly. Case and underscores matter to jq.

Stage 3. Look at the timestamp value:

```bash
curl -s "$URL" | jq -r '.current.time'
```

`-r` prints the string without its JSON quotes. Expected output is one line such as `2026-11-17T14:00`. Note the format, because your CSV will hold this text.

Test this stage: you can name the time field, and you can name each measurement field. Post the names and the timestamp format in the squad thread, as the ticket asks.

#### Y2-T05.2 Build the one-liner

Goal: turn one JSON reply into one CSV line, and be able to explain every stage.

Teach it first with a small made-up reply from a different service, so that the names are not the ones you will use:

```bash
echo '{"reading":{"at":"2026-11-17T09:00","no2":18.5,"o3":40.2}}' | jq -r '[.reading.at, "Pune", .reading.no2] | @csv'
```

Line by line:

- `echo '...'` writes the JSON text to standard output.
- `|` sends that text into jq.
- `jq -r` prints raw text, without JSON quotes around the whole line.
- `[.reading.at, "Pune", .reading.no2]` builds an array of three values. `.reading.at` reads the key `at` inside `reading`. `"Pune"` is a fixed string.
- `| @csv` turns the array into one CSV line. It puts quotes around text values and leaves numbers bare.

Expected output: `"2026-11-17T09:00","Pune",18.5`

Here is how the pieces fit, drawn as the same kind of journey you will make with the real API:

```flow
TITLE: One reading from request to CSV row
NODES: Open-Meteo server | curl | jq | day file
STEPS:
1>2 :: GET request :: curl asks the server for the current reading over HTTPS.
2>1 :: status and body :: The server answers with a three-digit status and a JSON body.
2>3 :: saved body :: The script hands the saved body to jq for checks.
3>4 :: one CSV line :: jq builds the row only after the checks pass.
```

Now write your own one-liner with the real names from Y2-T05.1. The shape is the same:

```bash
curl -s "$URL" | jq -r '[FIELD_FOR_TIME, "Bengaluru", FIELD_1, FIELD_2] | @csv'
```

Replace the three capitalised placeholders with the names you found. Run it. Then write one sentence about each pipe stage in the PR conversation. The trainer will ask about one of them in the cold call, so you must be able to say what that stage receives and what it outputs.

:::tip Use the names, not the labels
The ticket asks for the location and the two metrics. Your location is text you choose, such as `"Bengaluru"`. The metric names must be the exact keys from Y2-T05.1, so copy them from the output and do not type them from memory.

#### Y2-T05.3 Write the script in stages

Goal: build `scripts/fetch_once.sh` one stage at a time. Test each stage before you add the next. The snippets below are parts of the script. You put them together, in order, in one file.

Stage 0. Create the branch and stop the data folder from being committed. Run these in the repo root:

```bash
git switch -c feat/fetch-once
echo "data/raw/" >> .gitignore
```

`git switch -c` creates a new branch and moves onto it. `echo "data/raw/" >> .gitignore` adds one line to the end of `.gitignore`. The `>>` adds rather than replaces, so the existing `.env` and `.venv/` lines stay.

Test: `git status` should not list anything under `data/raw/`. Then create the folder for scripts with `mkdir -p scripts` and open a new file at `scripts/fetch_once.sh` in your editor.

Stage 1. The first lines set the shebang and the defaults:

```bash
#!/usr/bin/env bash
set -u
URL="${URL:-PASTE_YOUR_README_URL}"
LOC="${LOC:-Bengaluru}"
```

Line by line:

- `#!/usr/bin/env bash` must be the very first line. It tells the system which program runs the file.
- `set -u` makes Bash stop if the script uses a variable that was never set. It catches typing mistakes.
- `URL="${URL:-...}"` uses the URL from the environment if one was given, and otherwise the default. TC2 depends on this, because it overrides `URL` on the command line.
- `LOC="${LOC:-Bengaluru}"` gives the location text a default in the same way.

Test: `bash -n scripts/fetch_once.sh` checks the syntax without running anything. Expected output: nothing, which means no syntax error.

Stage 2. Create the temporary file and make sure it is deleted:

```bash
TMP="$(mktemp)"
trap 'rm -f "$TMP"' EXIT
```

`TMP="$(mktemp)"` runs `mktemp`, which creates an empty file with a unique name, and stores its path in `TMP`. `trap '...' EXIT` registers a command that runs whenever the script exits, whether it succeeds or fails. The single quotes stop the shell from expanding `$TMP` too early.

Test: `bash -n` again, with no output expected.

Stage 3. Fetch the body and check the status. This is the core of the ticket:

```bash
STATUS="$(curl -s --max-time 20 -o "$TMP" -w '%{http_code}' "$URL")"
if [ "$STATUS" != "200" ]; then
  echo "ERROR: HTTP $STATUS from $URL" >&2
  exit 1
fi
echo "body bytes: $(wc -c < "$TMP")"
```

Line by line:

- `curl -s` runs quietly. `--max-time 20` gives up after 20 seconds, so a silent server cannot hang the script.
- `-o "$TMP"` writes the body into the temporary file, so it never reaches the screen.
- `-w '%{http_code}'` prints only the status code. `STATUS="$(...)"` captures that code.
- `if [ "$STATUS" != "200" ]; then` is true for any status other than 200. This includes `000`, which means curl could not reach the server at all.
- `echo "ERROR: ..." >&2` writes the message to standard error, so it cannot be mistaken for data.
- `exit 1` stops the script before anything is written.
- The last `echo` line is temporary. It proves the body arrived. Remove it in stage 5.

We do not use `--fail` here. That option would make curl exit with an error, but we want the status code itself to put in our message.

Test: run `bash scripts/fetch_once.sh` on your laptop with the default URL. Expected output: a line such as `body bytes: 512`. Then run `URL=https://air-quality-api.open-meteo.com/v1/nope bash scripts/fetch_once.sh; echo "exit=$?"`. Expected: the `ERROR: HTTP 404` line, then `exit=1`.

:::trap Status 000 is a failure
When curl cannot reach the server, it prints `000`. That is not a valid status. The check above treats it as a failure, which is correct. You can see it with `URL=https://no-such-host.invalid/ bash scripts/fetch_once.sh`, which should print `ERROR: HTTP 000` and exit with 1.
:::

Stage 4. Check that the fields you need are present, using jq with `-e`:

```bash
if ! jq -e '.current.FIELD_1 != null and .current.FIELD_2 != null' "$TMP" > /dev/null; then
  echo "ERROR: required field missing in response" >&2
  exit 2
fi
```

Line by line:

- `jq -e` sets jq's exit code from the result. If the filter returns `false` or `null`, the exit code is not 0. Without `-e`, jq exits with 0 even for a null result.
- The filter is true only when both fields exist and are not null. Replace `FIELD_1` and `FIELD_2` with the metric names from Y2-T05.1, and add the time field too if you wish.
- `! ... > /dev/null` inverts the result, so the block runs when the check fails. `> /dev/null` hides jq's output, because you only need the exit code.
- `exit 2` gives this failure its own code, so a caller can tell a bad body (2) from a bad status (1).

Test without the network. Use a here-string, which feeds text to a command as if it were a file:

```bash
jq -e '.current.pm2_5 != null' <<< '{"current":{"pm10":1}}'; echo $?
```

Expected output: `false` on one line, then `1` on the next, because `pm2_5` is missing (jq prints the result of the filter, and `-e` sets the exit code from it). Change the filter and the input to see the `0` case too. Replace `pm2_5` in this test with your own field name.

Stage 5. Write the header once and append the row. Then delete the temporary `echo` line from stage 3:

```bash
OUT="data/raw/$(date +%F).csv"
mkdir -p data/raw
[ -s "$OUT" ] || echo 'timestamp,location,METRIC_1,METRIC_2' > "$OUT"
jq -r --arg loc "$LOC" '[FIELD_FOR_TIME, $loc, FIELD_1, FIELD_2] | @csv' "$TMP" >> "$OUT"
echo "OK: row added to $OUT"
```

Line by line:

- `OUT="data/raw/$(date +%F).csv"` builds one file per day, named by today's date.
- `mkdir -p data/raw` creates the folder if it is missing. A fresh clone does not have it. `-p` means "no error if it exists".
- `[ -s "$OUT" ] || echo '...' > "$OUT"` writes the header only when the file is missing or empty. `-s` is true for a file with content. `||` runs the right side only when the left side is false. This is why the header appears once.
- `--arg loc "$LOC"` passes the shell variable into jq as `$loc`. Do not put `"$LOC"` inside the single quotes, because jq would read the quotes as part of the filter.
- `-r` prints raw text, and `>> "$OUT"` appends the row to the day file.
- `echo "OK: ..."` confirms the run.

Replace `METRIC_1`, `METRIC_2`, `FIELD_FOR_TIME`, `FIELD_1` and `FIELD_2` with your own names. The header text must match the names in your rows, because TC1 checks the header.

:::trap Forgetting -r
Without `-r`, the row is printed as a JSON string, with backslashes before each quote. No CSV reader can parse that. Keep `-r` on this line.
:::

Stage 6. Only if your squad's chosen source needs a key. Open-Meteo does not, so skip this stage for the default source. If you do need one, read it from the environment and stop with a clear message when it is missing:


### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| `Permission denied` when you run `./scripts/fetch_once.sh` | The file is not executable. | Run `chmod +x`, then `git update-index --chmod=+x scripts/fetch_once.sh` on Windows. |
| `$'\r': command not found` | The script was saved with Windows line endings (CRLF). | Run `sed -i 's/\r$//' scripts/fetch_once.sh` and save the file with LF endings in your editor. |
| `curl: (6) Could not resolve host` | No network, or a typo in the host name. | Compare the URL with the one in your README. |
| The header appears twice, so the file has 4 or 5 lines after two runs | The header test is missing or wrong. | Use `[ -s "$OUT" ] \|\| echo ... > "$OUT"` so the header is written only for an empty file. |
| Rows contain backslashes and quotes that break the CSV | The `-r` option is missing from the jq line. | Add `-r` to the jq command that writes the row. |
| The script exits 0 on a 404 | The status is not captured, or the check runs after the write. | Capture the status with `-w '%{http_code}'`, compare it with 200, and exit 1 before writing. |
| `No such file or directory` for `data/raw` on a fresh clone | The folder is not created. | Add `mkdir -p data/raw` before the write. |
| The script exits with 2 on a valid reply | A field name in the jq filter does not match the reply. | Run `curl -s "$URL" \| jq '.current \| keys'` and copy the names exactly. |
| TC3 prints a matching line | A key was committed at some point. | Rotate the key at the service, tell your trainer, and do not paste the value anywhere. |

### Defend it in the viva

**Q1. Why does the script read the status code before it looks at the body?**

:::answer Model answer
A body from an error response is not the data you asked for. A 404 or 500 can still come with an HTML or JSON error message. If the script parsed it, jq would fail in a confusing way, or worse, a valid-looking row could be written. Reading the status first lets the script stop with a clear message that names the status, and it writes nothing.
:::

**Q2. What is the trade-off between checking the status yourself and using curl's `--fail` option?**

:::answer Model answer
`--fail` makes curl exit with an error on any HTTP error, which is short and simple. The cost is that with `-s` curl prints no message, and its exit code (22) is the same for every HTTP error, so it does not tell you which status it was. Capturing the status with `-w '%{http_code}'` costs a few more lines, but it lets the script print the exact code, such as `ERROR: HTTP 404`, which the ticket asks for. It also lets the script treat code 000 as a failure in its own way.
:::

**Q3. Why does the script use two different exit codes, 1 and 2?**

:::answer Model answer
Exit code 1 means the request failed, so the source did not answer with 200. Exit code 2 means the request succeeded but the body did not have the fields we need. A caller, such as a future cron job or a monitor, can tell these apart. A bad status may be a temporary outage, while a missing field may mean the source changed its format. Different codes lead to different responses.
:::

**Q4. The script appends a row on every run, with no check for duplicates. What is the cost, and where is it fixed?**

:::answer Model answer
If the source has not updated since the last run, the new row repeats the same timestamp and values. That makes the file noisy and can distort counts later. This ticket only needs one append per run. Duplicate removal is part of Y2-T06, which adds retries, a lock and deduplication to the same script. Saying this clearly shows you know the limit of your own work.
:::

**Q5. Walk me through what you personally did on this ticket.**

:::answer Model answer
Point to your own commits and the stage each one covers, using the output of `git log --author` with your name. A strong answer names one stage you wrote, says what it does, shows the test output that proved it, and says what you would change. Do not describe work that is not in your commits. The trainer checks the history, so a true and specific answer is the only kind that scores.
:::
