### The ticket in plain words

Y2-D05 is the day the CityPulse model repository has to be good enough for a stranger. A stranger should be able to clone it, run two `make` commands and get the numbers your squad got. A forecast that nobody can reproduce cannot be trusted, and cannot be debugged when it goes wrong.

A peer squad audits your repository against a 20-item checklist. You need 14 items to pass, which is 70%. Each passed item needs a link to evidence. Each failed item becomes an Issue on your repository, so the problem is written down and owned.

The second half puts the trained model behind a web address. An API is a program that answers requests sent over HTTP, the protocol your browser uses. The client sends input features as JSON to `POST /v1/predict`, and the server replies with a prediction. Each reply also carries `model_version`, which names the saved model file that made the answer. Anyone can then trace a forecast to one artefact, and notice later if the model's behaviour changes.

The model is loaded once at startup, not once per request. That keeps replies fast, and the ticket asks the second call to finish in under 50 ms on a laptop.

### How your trainer checks it

The trainer checks six acceptance criteria. AC1 is the audit file, which must show at least 14 of 20 items passed, with an evidence link per pass and an Issue per fail. AC2 is covered by TC1. AC3 is covered by TC2, and needs a 200 reply with a finite numeric `prediction` and the `model_version` from `metrics_v1.json`. AC4 needs the second `latency_ms` under 50, which you check with `jq .latency_ms`. AC5 needs one call to write exactly one JSON log line to stdout with `model_version` and `latency_ms`. AC6 needs `v0.7-p7` to point to a commit on `main`, and `pytest tests/test_predict.py` to pass.

The four test cases follow. Each command is split into parts, and each part is explained.

**TC1: fresh clone, then make setup and make reproduce.**

The steps are `git clone ...`, `cd citypulse-<squad>`, `make setup` and `make reproduce`, joined with `&&`.

- `git clone <url>` copies the repository from GitHub into a new folder.
- `cd citypulse-<squad>` moves into that folder. Every later command runs from here.
- `make setup` runs the `setup` target, which installs the pinned packages.
- `&&` runs the next command only if the previous one exited with code 0, which means success.
- `make reproduce` runs the `reproduce` target, which re-runs the saved steps and prints the MAE.

**Passing:** the last command exits with code 0, and the printed MAE is within 1% of the stored value. If the stored MAE is 4.20, the printed value must lie between 4.158 and 4.242.

**Failing:** `make: *** No rule to make target 'reproduce'` means the Makefile lacks that target. `ModuleNotFoundError` for `sklearn` means the install is not pinned correctly. A MAE outside the band usually means the data path or the random seed differs from training. Check `config.yaml` first.

**TC2: start the server and send the reference payload.**

- `uvicorn api.main:app --port 8000` starts the app. `api.main` is the file `api/main.py`, and `app` is the variable inside it.
- `&` runs the server in the background, so the terminal stays free.
- `sleep 3` waits three seconds for startup.
- `curl -s` sends the request silently.
- `-X POST localhost:8000/v1/predict` sets the method and the address.
- `-H 'Content-Type: application/json'` says the body is JSON.
- `-d @docs/api/predict_example.json` reads the body from that file. The `@` means "read from a file".

**Passing:** the reply is 200, and the JSON has the keys `prediction`, `target_ts`, `model_version`, `expected_mae` and `latency_ms`, with `prediction` a number. To see the status code, replace `-s` with `-o /dev/null -w '%{http_code}\n'`.

**Failing:** `curl: (7) Failed to connect` means the server is not up yet, so increase the sleep. `422` means the JSON keys do not match `PredictRequest`. `500` means an exception in your code, so read the server's terminal.

The trainer's animation shows the test passing. Your values will differ:

```term
$ curl -s -X POST localhost:8000/v1/predict -H 'Content-Type: application/json' -d @docs/api/predict_example.json | jq -e 'has("prediction") and has("model_version") and (.prediction | type == "number")'
true
$ echo $?
0
```

The `jq -e` flag makes `jq` set its exit code from the answer, so `true` means exit code 0.

**TC3: search the code for joblib.load.**

- `grep -n` prints each match with its line number.
- `'joblib.load'` is the text to find. The quotes keep it as one argument. In a grep pattern the dot means "any character", which is harmless here.
- `api/ src/` are the folders to search, and `-r` searches them recursively.

**Passing:** every match is inside `load_model`, and `load_model` is called from `lifespan`. Typically this is one line in `src/predict.py`.

**Failing:** a match inside a route such as `predict_v1` means the model is read on every request. Move the call into `lifespan` and read from `app.state`.

**TC4: remove the model file and start the server on another port.**

- `mv models/model_v1.joblib /tmp/` moves the model out of the folder.
- `&&` starts the server only if the move worked.
- `--port 8001` avoids clashing with a server on 8000.

**Passing:** the server stops during startup with a clear message naming the missing file. Run `timeout 15 uvicorn api.main:app --port 8001; echo $?`. `timeout` stops the server after 15 seconds if it has not failed, and the number it prints is the exit code. `124` means `timeout` had to kill a server that was still running, so startup did not fail (bad). Another non-zero number, usually `3` from uvicorn, means startup failed (good).

**Failing:** `Application startup complete` means the lifespan does not check the file. Restore the file afterwards with `mv /tmp/model_v1.joblib models/`. On Git Bash, `/tmp` is a folder under your user profile, so run `cd /tmp && pwd` to find it.

### Do it, step by step

#### Y2-T39.1: Audit the paired repository

**Goal.** Prove that a stranger can reproduce another squad's model, then write down what fails.

**Stage 1: fresh clone.** Run this in an empty folder on the lab machine or in Git Bash:

```bash
git clone https://github.com/<their-org>/<their-repo>.git
cd <their-repo>
```

A new clone rules out files that exist only on someone's machine.

**Stage 2: run the two targets.** Run `make setup && make reproduce 2>&1 | tee reproduce.log`. `2>&1` sends errors into the same stream, and `tee` shows the output while saving it to `reproduce.log`.

**Stage 3: compare the MAE.** Suppose their metrics file says 4.20 and the printed MAE is 4.19:

```bash
awk -v printed=4.19 -v stored=4.20 'BEGIN { d = (printed - stored) / stored * 100; if (d < 0) d = -d; print d "%" }'
```

`-v` sets an awk variable. The formula gives the absolute difference as a share of the stored value. Expect `0.238095%`, which is inside 1%. Use the numbers you actually see.

**Stage 4: score four items and file failures.** For each item, note pass or fail, and the evidence link to a specific file or commit. Then create the label once and file one Issue per failed item:

```bash
gh label create audit-d05 --repo <their-org>/<their-repo> --color D93F0B
gh issue create --repo <their-org>/<their-repo> --label audit-d05 --title "Audit: <short description>" --body-file issue.md
```

`--body-file` reads the Issue text from a file.

**Test this stage.** Run `gh issue list --repo <their-org>/<their-repo> --label audit-d05`. You should see one line per failed item.

#### Y2-T39.2: Triage and record the final score

**Goal.** Turn the Issues into fixes, then record the result honestly.

**Stage 1: list and assign.** Run `gh issue list --label audit-d05 --state open`, then `gh issue edit <number> --add-assignee <github-user>` for each one.

**Stage 2: re-run after each fix.** Run `make reproduce` again. The MAE must stay within 1% of the stored value.

**Stage 3: record the score.** Score = passed items divided by 20, times 100. Check fourteen passes with `awk 'BEGIN { print 14/20*100 "%" }'`, which prints `70%`. Write the score and the open Issues in `docs/audit-d05.md`. Do not change a fail to a pass without evidence.

**Test this stage.** Each passed item in the file has a link, and each failed item has an Issue number.

#### Y2-T39.3: Makefile and pinned packages

**Goal.** Make the four targets work from a clean folder.

**Stage 1: learn the shape.** A target is a name, a colon, and indented commands. The indent must be a real tab, or `make` fails. This is the pattern only:


`setup:` names the target. The indented line runs `pip`, which installs the packages in `requirements.txt`.

#### Y2-T39.4: src/predict.py

**Goal.** Write the two helpers that the route calls.

**Stage 1: load_model.** Loading a file is one call:

```python
import joblib

def load_model(path):
    return joblib.load(path)
```

`def load_model(path):` defines a function that takes a file path. `joblib.load(path)` returns the fitted pipeline saved in that file. The startup code in T39.5 checks that the file exists.

**Stage 2: one-row DataFrames.** A list with one dictionary makes a table with one row. Here is an example with made-up columns:

```python
import pandas as pd

row = pd.DataFrame([{"a": 1, "b": 2.5}], columns=["a", "b"])
print(row)
```

`columns=[...]` sets the column order, and that order must match training. Expect one row and two columns. Replace the names with your training's raw columns.

**Stage 3: predict.** Build the row from `payload_dict`, convert the values with `astype(float)`, call `model.predict`, and wrap the first result in `float()` so it converts to JSON.

**Test this stage.** The helper that checks a number is finite is pure Python, so it can be tested without files:

```python test
import math

def is_finite_number(value):
    return isinstance(value, float) and math.isfinite(value)

assert is_finite_number(52.4)
assert not is_finite_number(float("nan"))
assert not is_finite_number(float("inf"))
assert not is_finite_number("52.4")
```

`math.isfinite` returns False for NaN and infinity. `isinstance(value, float)` rejects text such as `"52.4"`. Each `assert` checks one case. Write your own version of the idea in your own tests.

#### Y2-T39.5: lifespan loads the model once

**Goal.** Load the files at startup, and stop the server if they are missing.

**Stage 1: check the files.** Inside `lifespan`, before the load:

```python
import os

for path in ("models/model_v1.joblib", "models/metrics_v1.json"):
    if not os.path.exists(path):
        raise FileNotFoundError(f"model not found: {path}")
```

`os.path.exists` returns True if the file is there. `raise` stops startup with a message that names the file.

**Stage 2: load into app.state.** After the check:

```python
import json
from src.predict import load_model

app.state.model = load_model("models/model_v1.joblib")
with open("models/metrics_v1.json") as f:
    app.state.metrics = json.load(f)
```

Calling `load_model` (from T39.4) keeps `joblib.load` in one place, which is what TC3 wants. `with open(...) as f:` closes the file when the block ends. Then add `yield`, so the server starts accepting requests. The `lifespan` function is an `async def` decorated with `@asynccontextmanager` (from `contextlib`) and passed to `FastAPI(lifespan=lifespan)`.

**Stage 3: see why loading once matters.** This trace shows the counter staying at 1 across two requests:

```trace
TITLE: Load once, reuse on every request
CODE:
loads = 0
model = None
def startup():
    global model, loads
    loads += 1
    model = "pipeline"
def route(payload):
    return model + " answered " + payload
startup()
route("req 1")
route("req 2")
STEPS:
1 :: loads=0 :: Start with the counter at zero and no model.
9 :: loads=0; model=None :: Startup runs once, before any request arrives.
5 :: loads=1; model=None :: The startup code adds one to the counter.
6 :: loads=1; model="pipeline" :: The model is stored once, and nothing reloads it.
10 :: loads=1; model="pipeline" :: The first request reuses the stored model.
11 :: loads=1; model="pipeline" :: The second request reuses it, so the counter stays at 1.
```

**Test this stage.** Rename the model file, start the server, and read the error. This is TC4.

#### Y2-T39.6: request schema, route and log line

**Goal.** Accept a JSON body, call `predict`, return the keys, and write one log line.

**Stage 1: the request class.** Define the fields your features need, including `station_id` and the recent history for the lag features:

```python
from pydantic import BaseModel

class PredictRequest(BaseModel):
    station_id: str
    # add the raw inputs your features need, such as recent readings
```

Pydantic rejects bad input with a 422 reply before your route runs. Your squad chooses the field names and types from its own training code.

**Stage 2: the route.** Read the model from `app.state`, not from a file, and time the call:

```python
import time

@app.post("/v1/predict")
def predict_v1(body: PredictRequest):
    t0 = time.perf_counter()
    y = predict(app.state.model, body.model_dump())
    latency = round((time.perf_counter() - t0) * 1000, 1)
    # return the keys TC2 checks, and log one line (Stage 3)
```

`time.perf_counter()` gives a precise clock. `body.model_dump()` turns the checked request into a dictionary for `predict`. Finish the `return` with `prediction`, `target_ts`, `model_version` (from `app.state.metrics`), `expected_mae` and `latency_ms`.

**Stage 3: the log line.** Print one JSON object with `print(json.dumps({...}), flush=True)`. `json.dumps` turns a dictionary into JSON text, and `flush=True` writes it at once. Include `model_version`, `station_id`, `latency_ms` and `prediction`, and make sure your own code prints nothing else. Uvicorn writes its own access line (`POST /v1/predict ... 200`) as well, but it has no `latency_ms`, so it is not your log line.

**Test this stage.** Send the reference payload, then count the log lines. With the server output saved by `> server.log 2>&1`, `grep -c '"latency_ms"' server.log` should print `1` after one call.

This is the path one call takes:

```flow
TITLE: One call to /v1/predict
NODES: Your terminal | Uvicorn | predict route | app.state
STEPS:
1>2 :: POST body :: curl sends the JSON file to port 8000.
2>3 :: hand over request :: Uvicorn passes the request to FastAPI, which checks it.
3>4 :: read model :: The route reads the model already held in app.state.
4>3 :: stored model :: No file is opened here, which keeps the call fast.
3>2 :: JSON reply :: The route returns the keys and writes one log line.
2>1 :: response :: The terminal shows the reply.
```

### Defend it in the viva

**1. Why does the service load the model in lifespan rather than in each route?**

:::answer Model answer
Reading a model file takes far longer than one prediction. Inside the route, every request would pay that cost, and the second call would miss the 50 ms target. Lifespan runs once before the server accepts requests, so the model stays in `app.state`, and a missing file stops the server at startup.
:::

**2. What is the trade-off of pinning scikit-learn to the exact training version?**

:::answer Model answer
The pin means a reloaded model gives the same answers, so the forecast can be reproduced. The cost is that an upgrade needs a deliberate step: retrain or re-verify the model, record the new version, and change the pin.
:::

**3. What did you personally do in this ticket, and how can the trainer see it?**

:::answer Model answer
Name the subtask you owned, the files you changed, the commits that show them, and the test and evidence you added to the PR. Do not claim work that the commits do not show, because the trainer checks commit evidence.
:::

**4. Why does the audit use a tolerance of plus or minus 1% rather than an exact match?**

:::answer Model answer
Floating-point results can differ in tiny ways, such as the order of operations. A 1% tolerance accepts that noise but still catches a real change, such as a different data file or a missing step.
:::

**5. How would you show that a failure was recorded, not hidden?**

:::answer Model answer
Each failed item becomes an Issue labelled `audit-d05` on the repository that owns the code. The final score in `docs/audit-d05.md` counts only items that still pass, and open Issues stay open until they are fixed.
:::
