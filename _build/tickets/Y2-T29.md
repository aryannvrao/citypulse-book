### The ticket in plain words

Your squad already has charts and a dashboard. A busy decision-maker does not read a gallery of graphs, though. They read a recommendation: "do this, here, by this date, and we will know it worked when this number moves." This ticket asks you to draft a two-page mini-report that makes exactly that kind of recommendation, and backs every number with something a reader can open and check.

In 1854 the London physician John Snow mapped cholera deaths in Soho. The map pointed at one water pump on Broad Street. Local authorities removed the handle of that pump, and Snow later argued that cases fell afterwards. The ticket calls this your "pump handle": one specific action, with an owner, that the data supports.

The report follows the pyramid principle, so the answer comes first, then the reasons, then the detail. Every line with a digit must point at a chart in `reports/charts/`, a SQL view in `sql/views.sql`, or a KPI on the dashboard. The limitations must be honest. Two students from another squad will review your draft before the defence on Saturday.

### How your trainer checks it

The trainer checks five acceptance criteria and four test cases:

- The report renders to two pages or fewer (the 900-word limit in Y2-T29.5 is your working guide; also preview the rendered file on GitHub or in your editor and check the length); the ticket does not say how the trainer renders the report to count pages, so ask, and its first section is a recommendation naming an owner, an action, a location, a time window and a success measure.
- Every line with a digit has a link to `reports/charts/*.png`, a view name from `sql/views.sql`, or the dashboard KPI.
- The limitations section lists at least three limitations, each with its effect on the conclusion.
- The PR has exactly two reviewers from another squad, requested by 20:30.
- Each student has written one section, initialled it, and given at least five review comments on their assigned report before Saturday 30 January, 09:00.

**TC1: every numeric line cites evidence.** Run this from the repository root:

```
grep -nE '[0-9]' reports/mini-report.md | grep -vE '\]\(|v_[a-z0-9_]+|KPI'
```

Break it into parts:

- `grep` searches text for lines that match a pattern.
- `-n` adds the line number to each match.
- `-E` turns on extended regular expressions, so `|` and `+` need no backslash.
- `'[0-9]'` matches any single digit.
- `|` sends the first command's output into the second.
- The second `grep -vE` keeps lines that do **not** match. `-v` inverts the match.
- `\]\(` matches `](`, which sits between a link's text and its path.
- `v_[a-z0-9_]+` matches a view name: `v_` followed by lower-case letters, digits or underscores.
- `KPI` matches the word KPI.

So the test asks which lines contain a digit but no link, view name or KPI. Here is what passing looks like:

```term
$ grep -nE '[0-9]' reports/mini-report.md | grep -vE '\]\(|v_[a-z0-9_]+|KPI'
(no lines printed: every line with a digit cites evidence, so the test passes)
```

Passing output is **nothing**. A failing run prints the line number and text of each offending line, for example `14:Weekly readings rose 9% in March.` The usual cause is a number in plain words with no evidence on the same line. Add a link there. Do not add the word KPI just to silence the test, because the trainer reads the line too.

**TC2: two reviewers from another squad.** Run `gh pr view <n> --json reviewRequests`, with `<n>` replaced by your PR number. `gh pr view` shows one PR, and `--json reviewRequests` prints only the reviewer field. Passing output is a list of two logins from another squad. A failing output such as `"reviewRequests": []` means nobody was asked. Ask your trainer which logins are the assigned reviewers. Run the check before the reviewers submit their reviews: GitHub removes a person from `reviewRequests` once they have submitted a review, so the list shrinks as reviews arrive. The requests must also be made by 20:30.

**TC3: the recommendation can be defended aloud.** There is no command. The trainer reads your first section and asks who does what, where, by when, and measured how. Practise by reading the recommendation sentence aloud and answering those five questions from it alone. A vague success measure, such as "improve service", fails.

**TC4: at least five comments from each reviewer.** On Saturday at 09:00, run `gh pr view <n> --json reviews,comments`. It prints the submitted reviews and the conversation comments as JSON. Count the entries by each assigned reviewer. Note that this JSON holds review summaries and conversation comments only; inline comments on specific lines show on the PR's "Files changed" page, so the trainer may count them there. The ticket does not say whether the five must be inline comments or may be review summaries, so ask your trainer which they count. A common failure is a review left in draft. The trainer cannot see a draft until you press Submit.

### Do it, step by step

Work through these in order. Each step ends with a test you run before you move on.

#### Y2-T29.1 Stand-up and branch (Scrum/Docs, 10 min)

The goal is a branch and an empty report that the squad can see.

Stage 1. Start from an up-to-date `main`:

```
git switch main
git pull --ff-only
```

`git switch main` moves you to `main`. `git pull --ff-only` downloads the latest changes and refuses to continue if it would need a messy merge. Expect `Already up to date.` or a short list of changed files.

Stage 2. Create the branch:

```
git switch -c feat/T29-report
```

The `-c` flag means "create", so the branch is made and selected in one step.

Stage 3. Copy the squad template into the report. Ask your Scrum/Docs owner for the template's path, then run `cp <path-to-template> reports/mini-report.md`. Keep only the five section headings, with no body text yet.

Stage 4. Commit and push:

```
git add reports/mini-report.md
git commit -m "docs(T29): create mini-report skeleton with five sections"
git push -u origin feat/T29-report
```

`-u` links your local branch to the remote one, so later pushes need no extra words.

Test: run `git status`. Expected output:

```
On branch feat/T29-report
Your branch is up to date with 'origin/feat/T29-report'.

nothing to commit, working tree clean
```

#### Y2-T29.2 Recommendation and executive summary (Tech Lead, 15 min)

The goal is to decide the one action, the "pump handle", before any body text.

Stage 1. Write one sentence with five parts:

`[Owner] will [action] at [location] from [start] to [end], measured by [success measure].`

Each part answers one of the trainer's questions in TC3. The success measure must be a number the dashboard shows, or can show.

Stage 2. Study the shape of a clearly fictional example from a different project, a library network:

`The head librarian at the Harbour Town branch will extend Saturday opening to 18:00 from 1 March to 31 May, measured by weekly Saturday visits compared with the same weeks last year.`

Use your own data, threshold and location.

Stage 3. Write the five-sentence executive summary underneath: the question, the answer in short, the first reason with its evidence, the second reason with its evidence, and the main limitation.

Test: read the recommendation aloud and check that all five answers are in the sentence.

#### Y2-T29.3 Write your section (every student, 30 min)

The goal is one section, where every number links to evidence. Your trainer will say which section is yours: reason 1, reason 2, data and method, limitations, or next steps.

Stage 1. Learn the Markdown link. The text goes in square brackets and the path in round brackets:

```
Saturday visits rose by 18% after the change ([chart](reports/charts/saturday_visits.png)).
```

The path is relative to the repository root, so it works on GitHub too. This line passes TC1 because it contains `](`.

Stage 2. Cite a view by name, in backticks:

```
Weekly visits fell by 7% in February (see `v_weekly_visits`).
```

The name must exist in `sql/views.sql`, which Y2-T29.4 checks.

Stage 3. Put your initials under your section heading, in an HTML comment:

```
<!-- section author: AB -->
```

The comment is hidden on the rendered page but stays in the file. Replace `AB` with your own initials, and put no number inside it, because TC1 reads every line.

Stage 3b. If your section is Limitations, list at least three, each with its effect on the conclusion. Study the shape with a fictional library example: "Only one season of data: a summer rush could explain the rise, so the recommendation may be weaker in winter." Write your own limitations from your own data, and give any number in them a link.

Stage 4. Watch the headings. `## 2. Data and method` contains a digit and no link, so TC1 flags it. Name the headings in words.

Test: run `grep -nE '[0-9]' reports/mini-report.md` and read each line. Fix any number that has no link, view or KPI.

#### Y2-T29.4 Check every number (Data, 10 min)

The goal is that each number equals what the dashboard or a view shows.

Stage 1. List the view names:

```
grep -oE 'v_[a-z0-9_]+' sql/views.sql | sort -u
```

`-o` prints only the matched text, and `sort -u` sorts and removes duplicates. If it prints nothing, your view names do not start with `v_`, and TC1 cannot recognise them. Ask your trainer.

Stage 2. Run one view in your squad's database client, for example `SELECT * FROM v_weekly_visits;` with your own view name, and compare its rows with your sentences.

Stage 3. Compare each KPI card on the dashboard with the matching figure in the report. Rounding must agree, or the sentence must explain the rounding.

Test: pick three numbers at random and find each one in the view output or on the dashboard. All three must match. Commit fixes with `docs(T29): correct figures after dashboard check`.

#### Y2-T29.5 Grep and word-count checks (QA/DevOps, 10 min)

The goal is to run the two checks and paste the results in the PR.

Stage 1. Run the TC1 command from the trainer section. Passing output is nothing.

Stage 2. Count the words, leaving out image lines:

```
grep -vE '!\[' reports/mini-report.md | wc -w
```

`grep -vE '!\['` keeps lines that do not contain `![`, the start of a Markdown image. `wc -w` counts the words it receives. Markdown symbols are counted too, so the figure is an upper bound. The limit is 900. Expected output: one number, such as `845`. If you are over, cut body sentences, never the evidence links.

Stage 3. Paste both results under Evidence in the PR description, as shown in the template below.

Test: run both commands again after your last edit. The results must still match what you pasted.

#### Y2-T29.6 Open the PR and request reviewers (Scrum/Docs, 5 min)

The goal is a draft PR with two reviewers requested before 20:30.

Stage 1. Write the description in a file outside the repository, such as `~/t29-pr-body.md`, using the template below. Then open the PR:

```
gh pr create --draft --base main --head feat/T29-report --title "T29: draft mini-report" --body-file ~/t29-pr-body.md
```

`--draft` makes it a draft, `--base main` says where it will merge, and `--body-file` reads the description. The command prints the PR URL. The number at its end is `<n>`.

Stage 2. Request the two reviewers, using the logins your trainer gives you:

```
gh pr edit <n> --add-reviewer <login-1>,<login-2>
```

There is no space after the comma.

Stage 3. Make sure the rubric link and the deadline "Saturday 30 January, 09:00" are in the description. Re-send the file with `gh pr edit <n> --body-file ~/t29-pr-body.md` if they are missing.

Test: run `gh pr view <n> --json reviewRequests --jq '.reviewRequests[].login'`. Expected: two logins, one per line.

This is the path your PR takes:

```flow
TITLE: From your branch to a peer review
NODES: You and your branch | GitHub | Reviewer from another squad
STEPS:
1>2 :: git push -u :: Your commits travel to GitHub on the feat/T29-report branch.
1>2 :: gh pr create --draft :: GitHub opens a draft PR that shows your description.
2>3 :: review request :: GitHub tells the two requested reviewers about the PR.
3>2 :: review comments :: The reviewer submits a review with written comments and a score.
```

### Defend it in the viva

**1. Why does the report open with the recommendation rather than the method?**

:::answer Model answer
The report follows the pyramid principle: answer first, then reasons, then detail. The reader is a decision-maker who must act on the report or reject it, so they need the action, the owner and the measure first. The reasons and method then show why the recommendation holds. If the method came first, a busy reader might stop before reaching the action.
:::

**2. What is the trade-off of one clear recommendation?**

:::answer Model answer
A single recommendation is clear and owned, so it can be acted on. The cost is that it can hide other options and the uncertainty behind it. The report handles this with a limitations section that names each limitation and its effect on the conclusion, and with next steps that would test the recommendation. A clear message and an honest limitations section work together.
:::

**3. What did you personally do in this ticket?**

:::answer Model answer
Answer with facts from your own work. Name the section you wrote, the commits you made and their messages, the numbers you checked against the dashboard or view, and the review comments you wrote with the criterion each one used. The answer should match the Git history and the PR page. Describe only work you did. The trainer checks the commits against what you say.
:::

**4. How does a reader check that a number in your report is supported?**

:::answer Model answer
Every line with a digit links to a chart file, names a SQL view or cites a KPI. The reader opens the link or runs the named view and compares the figure. TC1 checks that every such line has one of the three. A person then checks that the link or view really shows that figure. A link that exists but shows a different number is still a failure.
:::

**5. Which limitation would most change your conclusion, and why?**

:::answer Model answer
Pick the limitation that would reverse the recommendation if it were wrong. For example, if the data covers one season, a seasonal effect could explain the trend, and the recommendation would then be unsafe. Explain the likely effect, how large it could be, and what data would settle it. A limitation with a named effect helps the reader; a list of caveats with no effect does not.
:::

### Check yourself

```quiz
Q: In the command grep -vE '\]\(|v_[a-z0-9_]+|KPI', what does the -v flag do?
- It prints only the matching text, not the whole line.
- It makes the pattern match letters without regard to case.
* It keeps the lines that do not match the pattern.
- It stops grep after the first match.
WHY: The -v flag inverts the match, so the second grep keeps only lines that lack a link, a view name and a KPI. -o would print just the matching text, and -i would ignore case, which this pattern does not need.

Q: A numeric line links to a chart, but that file does not exist at the path given. Does TC1 catch it?
* No, TC1 only checks that the line contains a link pattern, so a broken link still passes the grep.
- Yes, because grep reads the file on disk and checks each link.
- Yes, because the second grep matches any link that starts with reports.
- No, because the word count catches broken links.
WHY: TC1 is a text pattern check, so a link written with the right brackets passes even when the file is missing. You must check each path yourself with ls, because the trainer may open the link.

Q: Which command requests two reviewers on pull request 12?
- gh pr view 12 --json reviewRequests

- git push -u origin feat/T29-report
WHY: gh pr edit with --add-reviewer requests reviewers. gh pr view with --json reviewRequests only lists them. The review command posts a comment, not a request, and git push sends a branch without touching reviewers.
```
