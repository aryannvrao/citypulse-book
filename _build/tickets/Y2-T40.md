### The ticket in plain words

Your CityPulse API now answers good requests. The `/v1/predict` endpoint takes a station and some sensor values, and returns a forecast. The trouble is bad requests. A client can send the word "abc" where a number belongs, a humidity of -5, NaN (short for "not a number"), a station that does not exist, or a field nobody declared. The service may then crash with a 500 error, and the crash page can show internal file paths. Worse, the model may return a confident number for impossible input, and nobody notices until a chart looks wrong.

This ticket adds three things. First, explicit rules for what a request must look like, with limits taken from physics: humidity cannot be below 0 or above 100 per cent. Second, one error format, an error envelope, so every failure looks the same to a client. Third, one structured log line per request, so later monitoring work can filter by latency and status. A structured log line is one line of JSON, so a tool can search it by field.

You also attack your own API. A fuzzer is a script that sends many odd requests and records the replies. Peer fuzzing means your squad-mate attacks your API and you attack theirs. The goal is to find 500 errors before a client does.

Read [Day 24: Validation and testing with Pydantic and pytest](D24.html) first. [Day 23: Building REST APIs with FastAPI](D23.html) covers the endpoints you are changing.

#### Y2-T40.1: Request and response schemas

**Goal.** Every accepted field has a type and a range. Extra fields and NaN are refused.

**Stage 1: declare the fields with limits.** Start from the model your T39 endpoint already uses, and keep its field names. The fields below are illustrative.

```python
from pydantic import BaseModel, ConfigDict, Field

class PredictRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    station_id: str = Field(min_length=1, max_length=64)
    humidity: float = Field(ge=0, le=100)
    pm25: float = Field(ge=0, le=1000)
```

`extra="forbid"` rejects any key not declared here, so a misspelt field such as `humidty` cannot be silently ignored. `Field(ge=0, le=100)` allows 0 to 100 inclusive. Write each bound and its physical reason down, because `docs/api.md` needs them.

Test: `python3 -c "from api.schemas import PredictRequest; print(PredictRequest.model_fields.keys())"` lists your field names. Adjust the module path to your file.

**Stage 2: refuse NaN and infinity.** In Pydantic 2, a field with `ge` and `le` already rejects NaN and infinity, because NaN fails every comparison. A float field with no bounds accepts both. The ticket asks for an explicit finite check, so that the rule is visible and covers any unbounded field you add later. Add `import math` and `field_validator` to your imports, then add this inside the class and write its body:

```python
    @field_validator("humidity", "pm25")
    @classmethod
    def must_be_finite(cls, v: float) -> float:
        # your check: raise ValueError when math.isfinite(v) is False, otherwise return v
```

Test: after restarting uvicorn, a body with `"humidity": NaN` must return 422, not 500.

**Stage 3: the response model.** Add an optional warnings list to the reply:

#### Y2-T40.2: The error envelope and handlers

**Goal.** Every error has one shape, and no reply leaks internal text.

**Stage 1: the helper.** `JSONResponse` builds a response with a JSON body. `detail=None` is a default, so callers may leave it out.

```python
import json
from fastapi.responses import JSONResponse

def err(status, code, message, rid, detail=None):
    return JSONResponse(
        status_code=status,
        content={"error": {"code": code, "message": message,
                           "detail": detail, "request_id": rid}},
        headers={"X-Request-ID": rid} if rid else None,
    )
```

The `headers=` line puts the id on the reply even when the middleware cannot add it (the 500 case, see the warning in T40.3). Callers pass `getattr(request.state, "request_id", None)` as `rid`.

Test: calling `err(422, "x", "y", "r").status_code` gives `422`, and `err(422, "x", "y", "r").headers["x-request-id"]` gives `r`.

**Stage 2: the 422 handler.** `exc.errors()` can hold values JSON cannot write, so keep only the location and the message as text:

```python
from fastapi.exceptions import RequestValidationError

@app.exception_handler(RequestValidationError)
async def on_validation(request, exc):
    detail = [{"field": ".".join(str(p) for p in e["loc"] if p != "body"),
               "msg": str(e["msg"])} for e in exc.errors()]
    return err(422, "validation_error", "Request body is invalid",
               getattr(request.state, "request_id", None), detail)
```

`if p != "body"` removes the word `body` from the location path, so the field name is clean.

Test: TC1 returns 422, and `error.code` is `validation_error`.

**Stage 3: the 404 and 405 handler.** Unknown routes raise Starlette's `HTTPException`. Write a handler for it, following the same pattern. Use `exc.status_code` for the status. Use only the short message you raised yourself, never the text of a Python exception.

Test: `curl -s localhost:8000/does-not-exist` returns an envelope with status 404.

**Stage 4: the 500 handler.** It returns a generic message and ignores `exc`. Log the real error on the server if you need it.

Test: add a temporary route that raises `ZeroDivisionError`, call it, then delete the route before you commit. The body must not contain `Traceback` or `ZeroDivisionError`.

#### Y2-T40.3: Logging middleware

**Goal.** Each request writes one JSON line, and the reply carries the same id in a header.

**A short technique first.** `finally` runs its block whether the `try` block succeeded or raised. That is how a log line is always written.

```python
import json, time, uuid

@app.middleware("http")
async def log_requests(request, call_next):
    rid = request.state.request_id = str(uuid.uuid4())
    t0, status = time.perf_counter(), 500
    try:
        resp = await call_next(request)
        status = resp.status_code
        resp.headers["X-Request-ID"] = rid
        return resp
    finally:
        print(json.dumps({"method": request.method, "path": request.url.path,
                          "status": status,
                          "latency_ms": round((time.perf_counter() - t0) * 1000, 1),
                          "request_id": rid}), flush=True)
```

`uuid.uuid4()` makes a random id. The chained assignment stores it on the request, so the handlers can read it. `status` starts at 500, so a crash is still logged correctly. `json.dumps` turns the dictionary into one line, and `flush=True` writes it at once.

This flow shows where the log line comes from.

```flow
TITLE: One request, one log line
NODES: Client | Middleware | Endpoint
STEPS:
1>2 :: POST /v1/predict :: The request arrives and the middleware makes a request_id.
2>3 :: call_next :: The middleware hands the request to the endpoint.
3>2 :: response or error :: The endpoint returns a reply, or an error is turned into one.
2>1 :: header and log :: The X-Request-ID header is added, and one JSON line is printed.
```

Test: send one request. Exactly one JSON line appears in the uvicorn terminal. Then run TC4. The header value must match the `request_id` in the log.

**Warning.** Your 500 handler runs outside this middleware, so its reply may lack the header. `err()` already sets the header from the `rid` you pass in, so give your 500 handler `getattr(request.state, "request_id", None)` as `rid`, and test it with the temporary route.

```python
def range_warnings(values, limits):
    notes = []
    for name, lim in limits.items():
        v = values[name]
        if not lim["min"] <= v <= lim["max"]:
            notes.append(f"{name}: {v} is outside the training range {lim['min']} to {lim['max']}")
    return notes
```

The chained comparison is True only inside the range. This assumes each limit has `min` and `max` keys. Change it to match the real layout you printed.

#### Y2-T40.5: fuzz.py with your own nasty inputs

**Goal.** A script that sends cases, checks each status, and counts 500s.

**A short technique first.** `urllib.request` sends HTTP requests from the standard library. When the server replies 4xx or 5xx, `urlopen` raises `urllib.error.HTTPError`, and its `code` attribute holds the status.

**Stage 1: send one request.**

```python
import urllib.request, urllib.error

def send(base_url, body_bytes):
    req = urllib.request.Request(base_url + "/v1/predict", data=body_bytes,
                                 headers={"Content-Type": "application/json"},
                                 method="POST")
    try:
        with urllib.request.urlopen(req, timeout=5) as resp:
            return resp.status
    except urllib.error.HTTPError as e:
        return e.code
```

`timeout=5` stops a hung server from freezing the script. Test: `send('http://localhost:8000', b'{}')` returns `422`.

**Stage 2: the cases.** Each case is a name, a body in bytes, and the expected status:

### Defend it in the viva

**1. Why reject a humidity of -5 with a 422, rather than clamping it to 0?**

:::answer Model answer
Clamping changes the client's data without telling anyone, so the forecast would rest on a value the client never sent. A 422 names the field and the rule, so the client can fix its sensor. Negative humidity is impossible, so it is a client error, not a value to repair.
:::

**2. What is the trade-off of `extra="forbid"`?**

:::answer Model answer
The benefit is that a misspelt or unexpected field fails loudly instead of being ignored. The cost is that a client sending a new field early gets a 422 until the API is updated, so schema changes must be coordinated and documented. I would accept that, because a silently ignored field can produce a forecast nobody intended.
:::

**3. Walk me through what you personally did in this ticket.**

:::answer Model answer
Name your subtask id, then describe your commits in order using your history. Name the test case or fuzz case that proves your work, and show its output. Describe one problem you hit and how you found the fix. Base the answer on your own commits and terminal output, and do not claim work you did not do.
:::

**4. Why must the 500 handler never include `str(exc)`?**

:::answer Model answer
An exception's text can contain file paths, SQL or internal names, and sending it to a client tells an attacker about the system. The handler returns a generic message, and details go only to the server log. That is why TC2 and criterion 3 check for `Traceback` in the body.
:::

**5. Why return a warning for out-of-training-range values instead of rejecting them?**

:::answer Model answer
The training range is only the span of data the model saw. A real value outside it, such as a rare pollution spike, can be correct, and rejecting it would hide a real event. Values beyond physical limits are different, because no real sensor produces them, so those are refused. The warning tells the client to treat the forecast with care.
:::
