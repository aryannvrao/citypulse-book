### The ticket in plain words

CityPulse is the platform your squad is building. It collects Bengaluru city data, such as air quality, and keeps it in the cloud. Cloud services charge for everything that is running, so a forgotten virtual machine or a scheduled job can cost money while nobody is looking. This ticket asks for two things that protect the client from that and from bad conclusions.

The first is ops hygiene. Every resource you own gets a tag, which is a label such as `Owner` with your name, so you can find it later. You draw a diagram of what is really deployed, not what you planned. You also write a teardown script that removes your resources in a safe order, and a recreate script that builds them again. The teardown script starts in dry-run mode, which prints what it would delete and changes nothing.

The second is the first look at the data. Zillow Offers was a home-buying business that in 2021 bought houses using a pricing model that assumed a recent trend would carry on. The housing market changed, the company lost a great deal of money and it closed the business. The lesson is that a trend is not proof. You must check volatility, which is how much the numbers jump about, and regime change, which is when the underlying conditions shift and old patterns stop applying.

So every observation in your notebook needs a chart, a number and a "So what:" line that names the action someone should take.

The client's programme manager wants three things: a diagram that matches the account, a one-command teardown, and ten observations that each stand up to a hard question. Your trainer will check each of them.

Your trainer checks every acceptance criterion and runs every test case. Here is what each one means and what you will see.

**TC1: dry run and shellcheck.**
The command is:

`bash infra/teardown.sh <name> | head -20; shellcheck infra/teardown.sh infra/recreate.sh`

- `bash infra/teardown.sh <name>` runs your script with the name as its first argument. `<name>` is your own name as used in the tags.
- `| head -20` sends the output to `head`, which shows only the first 20 lines. The script may stop early with a "broken pipe" message once `head` has finished. That is expected.
- `;` runs the next command whether or not the first one succeeded.
- `shellcheck infra/teardown.sh infra/recreate.sh` checks both scripts. It prints nothing when they are clean.

Passing looks like this:

```term
$ bash infra/teardown.sh ananya | head -20
DRY [schedule] aws events remove-targets --rule citypulse-fetch-schedule --ids fetch-target --region ap-south-1
DRY [schedule] aws events delete-rule --name citypulse-fetch-schedule --region ap-south-1
DRY [function] aws lambda delete-function --function-name citypulse-fetch --region ap-south-1
DRY [instances] aws ec2 terminate-instances --region ap-south-1 --instance-ids i-0abc123example
DRY [bucket] aws s3api delete-object --bucket ananya-citypulse-raw --key raw/example.json --version-id 3HL4kqtJlcpXroDTDmJ
DRY [bucket] aws s3api delete-bucket --bucket ananya-citypulse-raw --region ap-south-1
DRY [roles] aws iam detach-role-policy --role-name ananya-citypulse-fetch-role --policy-arn arn:aws:iam::123456789012:policy/example
DRY [roles] aws iam delete-role --role-name ananya-citypulse-fetch-role
$ shellcheck infra/teardown.sh infra/recreate.sh
$ echo $?
0
```

The names, keys and IDs will be yours, and you will see one line per object version and per policy. The order must be schedule, function, instances, bucket and roles. `shellcheck` printed nothing, and the exit code `0` confirms that it passed.

A failing run looks different. If the file is missing, you see `bash: infra/teardown.sh: No such file or directory`. The usual cause is that you are in the wrong folder. Run `pwd` and move to the repository root. If shellcheck reports something like `SC2086 (info): Double quote to prevent globbing and word splitting`, a variable is not quoted. If it reports `SC1017`, the file has Windows line endings. Convert it to LF and run it again.

**TC2: the resources exist.**
The trainer runs two commands on your screen after you point at the diagram boxes:

`aws lambda get-function --function-name citypulse-fetch`
`aws s3api head-bucket --bucket <bucket>`

- `aws lambda get-function` asks Lambda for the function's details. `--function-name` gives the name.
- `aws s3api head-bucket` asks S3 whether the bucket exists and that you may access it. `--bucket` gives its name.

Passing means both print their details, or `head-bucket` prints nothing and exits with 0. Failing looks like `An error occurred (ResourceNotFoundException) when calling the GetFunction operation: Function not found`, or `An error occurred (404) when calling the HeadBucket operation: Not Found`. Either means the diagram draws something that is not in your account. Fix the diagram or deploy the missing resource.

**TC3: the notebook executes.**
The command is:

`jupyter nbconvert --to notebook --execute notebooks/eda.ipynb --output /tmp/eda_check.ipynb`

- `jupyter nbconvert` is the Jupyter converter.
- `--to notebook` writes a notebook as output.
- `--execute` runs every code cell from top to bottom.
- `--output /tmp/eda_check.ipynb` writes the executed copy to a temporary location. On Windows, Git Bash maps `/tmp` to a temporary folder, so the copy is written there.

Passing ends with a line such as `[NbConvertApp] Writing ... bytes to /tmp/eda_check.ipynb` and no error. Failing usually shows `FileNotFoundError: [Errno 2] No such file or directory: 'data/clean/aq_clean.parquet'`. This happens because nbconvert runs each notebook from its own folder. Use `../data/clean/aq_clean.parquet` in the notebook.

**TC4: the observation count.**
The command is:

`grep -c 'So what:' notebooks/eda.ipynb`

- `grep` searches for text.
- `-c` prints a count of matching lines, not of matches.
- `'So what:'` is the text searched for, with the exact capitals and colon.

Passing prints a number of 10 or more. Failing prints a smaller number. Check that every observation has `So what:` in its markdown cell, and that the spelling and capitals match exactly. Two `So what:` on one line count only once.

**TC5: the so-what question.**
The trainer asks "so what?" about one observation. Passing means you name a concrete action and who would take it, for example "the squad checks the sensor for that station before the next demo". Failing means you repeat the finding, or you say "monitor the data". The action must be something a named person could do.

#### Y2-T24.2: Tag all your resources

The goal is that every bucket, function, role and instance you own carries `Owner` and `Project` tags. Tags are how the teardown script finds your resources later, so this step matters for T24.4 and T24.5.

First, a small example of the tag filter. Suppose you tagged one bucket with `Owner=ananya`. The command below lists every tagged resource with that owner:

`aws resourcegroupstaggingapi get-resources --tag-filters Key=Owner,Values=ananya --region ap-south-1 --query 'ResourceTagMappingList[].ResourceARN'`

- `aws resourcegroupstaggingapi get-resources` asks the Tagging API for resources.
- `--tag-filters Key=Owner,Values=ananya` keeps only resources whose `Owner` tag is `ananya`. Replace `ananya` with your own name.
- `--region ap-south-1` names the region where you work.
- `--query 'ResourceTagMappingList[].ResourceARN'` prints only the ARN of each match. The square brackets make a list. The single quotes stop the shell from changing the expression.

Expected output is a JSON list of ARNs, for example `["arn:aws:s3:::ananya-citypulse-raw"]`. Resources without the tag will not appear, so this list tells you what still needs tagging.

Now produce the file the ticket asks for. The tag list needs the tags themselves, so change the query to show them:

`aws resourcegroupstaggingapi get-resources --tag-filters Key=Owner,Values=ananya --region ap-south-1 --query 'ResourceTagMappingList[].{ARN:ResourceARN,Tags:Tags}' --output json > docs/evidence/ananya/T24-tags.txt`

- `--query '...{ARN:ResourceARN,Tags:Tags}'` builds one object per resource, with its ARN and its list of tags.
- `--output json` prints JSON.
- `> docs/evidence/ananya/T24-tags.txt` writes the output to a file. Create the folder first with `mkdir -p docs/evidence/ananya`. The `-p` flag creates parent folders as needed.

Test: open the file and check that every bucket, function, role and instance you own appears with `Owner` and `Project` in its `Tags`.

Tagging: if a resource is missing, or lacks `Project`, add the tag with the command for its type. Use the `Project` value your squad agreed, for example `citypulse`.

- Lambda: `aws lambda tag-resource --resource <function-arn> --tags Owner=ananya,Project=citypulse`
- EC2 instance: `aws ec2 create-tags --resources i-0abc123example --tags Key=Owner,Value=ananya Key=Project,Value=citypulse`
- IAM role: `aws iam tag-role --role-name <role-name> --tags Key=Owner,Value=ananya Key=Project,Value=citypulse`
- S3 bucket: `aws s3api put-bucket-tagging --bucket <bucket> --tagging 'TagSet=[{Key=Owner,Value=ananya},{Key=Project,Value=citypulse}]'`

Warning on S3: `put-bucket-tagging` replaces the whole tag set. If the bucket already has tags, first read them with `aws s3api get-bucket-tagging --bucket <bucket>` and include them in your new `TagSet`. Otherwise you delete them.

If a resource type does not appear in the Tagging API output, read its tags with its own command, for example `aws iam list-role-tags --role-name <role-name>` or `aws lambda list-tags --resource <function-arn>`.

Note that IAM is a global service, so roles may not appear when you query `ap-south-1`; try `--region us-east-1` for roles, or use `aws iam list-role-tags` as above.

#### Y2-T24.4: Write the teardown and recreate scripts

The goal is a script that removes your resources in the order schedule, function, instances, bucket versions, then roles and policies. The recreate script does the reverse. The full order matters because some resources depend on others. A role cannot be deleted while a policy is attached to it.

Run this on the lab machine (Linux bash) or in Git Bash. Build the script in the stages below. Each stage is a fragment to add to the same file, `infra/teardown.sh`.

**Stage 1: the header and the dry-run switch.**

```bash
#!/usr/bin/env bash
set -euo pipefail

NAME="${1:?usage: teardown.sh <name> [--apply]}"
APPLY="no"
if [[ "${2:-}" == "--apply" ]]; then
  APPLY="yes"
fi
```

- `#!/usr/bin/env bash` tells the system to run the file with bash.
- `set -euo pipefail` makes the script stop on the first error (`-e`), stop on an unset variable (`-u`), and treat a failed command inside a pipe as a failure (`-o pipefail`).
- `NAME="${1:?...}"` stores the first argument, your name. The `:?` stops the script with the message if no argument is given.
- `APPLY="no"` is the default. Only `--apply` as the second argument changes it.
- `[[ "${2:-}" == "--apply" ]]` tests the second argument. The `:-` gives an empty value when no second argument exists, which avoids the error from `set -u`.

Test: run `bash infra/teardown.sh` with no argument. You should see your usage message and the script should stop.

**Stage 2: the run helper.** This is the key idea. Every change goes through one function, which either prints or does the change.

```bash
run() {
  local label="$1"; shift
  if [[ "$APPLY" == "yes" ]]; then
    echo "APPLY [$label]"
    "$@"
  else
    echo "DRY [$label] $*"
  fi
}
```

- `run()` defines a function named `run`.
- `local label="$1"; shift` stores the first argument as a label, such as `schedule`, and then removes it from the list. `shift` moves the other arguments down by one.
- In dry-run mode the `else` branch prints `DRY [label]` and the command. `$*` expands to the whole command as text.
- In apply mode, `"$@"` runs the command with its arguments kept separate.

Test: add one line below the function, `run schedule echo hello`, then run `bash infra/teardown.sh ananya`. You should see `DRY [schedule] echo hello`. Remove the test line before you go on.

**Stage 3: the schedule.** A rule must lose its targets before you delete it. Find the rule name first:

`aws events list-rules --name-prefix citypulse --region ap-south-1 --query 'Rules[].Name' --output text`

- `aws events list-rules` lists scheduled rules.
- `--name-prefix citypulse` keeps only rules whose name starts with `citypulse`.
- `--query 'Rules[].Name' --output text` prints the names one per line, without JSON.

Use the name from your T23 deployment. Then add the calls below, with your rule name in place of `citypulse-fetch-schedule`:

```bash
SCHEDULE="citypulse-fetch-schedule"
run schedule aws events remove-targets --rule "$SCHEDULE" --ids fetch-target --region ap-south-1
run schedule aws events delete-rule --name "$SCHEDULE" --region ap-south-1
```

- `SCHEDULE="..."` stores the rule name once, so you change it in one place.
- `remove-targets` detaches the function from the rule. `--ids` names the target; use the ID you saw with `aws events list-targets-by-rule --rule "$SCHEDULE"`.
- `delete-rule` removes the rule. It must come after `remove-targets`, or AWS refuses.

Test: run the script with a name. You should see two `DRY [schedule]` lines in that order.

**Stage 4: the function and the instances.** Deleting the function is one call:

```bash
run function aws lambda delete-function --function-name citypulse-fetch --region ap-south-1
```

- `delete-function` removes the function. Its name is the one from `get-function` in TC2.

For instances, look up your own VMs by their tag. This is a read-only lookup, so it is safe in dry-run mode:

```bash
mapfile -t IDS < <(aws ec2 describe-instances --region ap-south-1 --filters "Name=tag:Owner,Values=$NAME" "Name=instance-state-name,Values=running,stopped" --query 'Reservations[].Instances[].InstanceId' --output text | tr '\t' '\n')
for id in "${IDS[@]}"; do
  [ -n "$id" ] || continue
  run instances aws ec2 terminate-instances --region ap-south-1 --instance-ids "$id"
done
```

- `describe-instances` lists instances. `--filters "Name=tag:Owner,Values=$NAME"` keeps only instances tagged with your name, so the lookup depends on your T24.2 work.
- `Name=instance-state-name,Values=running,stopped` keeps only instances that are running or stopped.
- `--output text | tr '\t' '\n'` turns the tab-separated output into one ID per line.
- `mapfile -t IDS < <(...)` reads those lines into an array called `IDS`. `mapfile` needs bash 4 or newer, which the lab machine and Git Bash have.
- `[ -n "$id" ] || continue` skips an empty line, which some AWS CLI versions print when nothing matches.
- `for id in "${IDS[@]}"` loops over each ID. The quotes keep each ID as one word.

Warning: `terminate-instances` deletes the VM, unlike a stop. The ticket allows terminating only the T19 VM, and only when your D03 compute evidence is complete. Remember that as written, `--apply` would run every stage of the script, including the function, bucket and roles, so do not use it for this decision (see T24.5).

Test: run the dry-run. You should see one `DRY [instances]` line per instance, and none if the lookup finds no instance.

**Stage 5: the bucket versions.** In a versioned bucket, `aws s3 rm` only adds delete markers. The old versions remain, and S3 refuses to delete the bucket while they exist. So you must list and delete every version, and every delete marker (listed under `DeleteMarkers` in the same output, with the same Key and VersionId fields). First look at what is there:

`aws s3api list-object-versions --bucket "$BUCKET" --query 'Versions[].[Key,VersionId]' --output text | head -5`

- `list-object-versions` lists every stored version of every object.
- `--query 'Versions[].[Key,VersionId]'` prints the object key and version ID as a pair.
- `--output text` prints one pair per line.
- `| head -5` shows only the first five lines, so you can see the shape of the output.

Write your loop with `run bucket aws s3api delete-object --bucket "$BUCKET" --key <key> --version-id <id>` for each pair, then one final line with `run bucket aws s3api delete-bucket --bucket "$BUCKET" --region ap-south-1`. Set `BUCKET` near the top of your script, as you did for `SCHEDULE`. In dry-run mode the loop prints one line per version, and an empty bucket prints none for the versions.

Test: run the dry-run. The `DRY [bucket]` lines must come after the instance lines, and the delete-bucket line must come last among the bucket lines.

**Stage 6: roles and policies.** AWS refuses to delete a role that still has attached or inline policies, so detach them first. Find your roles with a tag filter:

`aws iam list-role-tags --role-name "$ROLE" --query "Tags[?Key=='Owner' && Value=='$NAME'].Value" --output text`

- `aws iam list-roles --query 'Roles[].RoleName' --output text` first gives every role name in the account; loop over those as `$ROLE`.
- `list-role-tags` returns one role's tags. The `Tags[?...]` part is a filter that keeps the `Owner` tag only if its value equals your name. The `$NAME` is expanded by the shell inside the double quotes.
- If this prints your name, the role is yours; if it prints nothing, skip that role. Use this check inside your loop.

For each role, you then need the commands:

```bash
run roles aws iam detach-role-policy --role-name "$ROLE" --policy-arn "$POLICY_ARN"
run roles aws iam delete-role-policy --role-name "$ROLE" --policy-name "$INLINE"
run roles aws iam delete-role --role-name "$ROLE"
```

- `detach-role-policy` removes a managed policy from the role. Its ARN comes from `aws iam list-attached-role-policies --role-name "$ROLE"`.
- `delete-role-policy` removes an inline policy, which is written in the role itself. Names come from `aws iam list-role-policies --role-name "$ROLE"`.
- `delete-role` removes the role. It must come last for that role.

Note that `list-roles` does not return tags, so a filter on tags inside it matches nothing. Use this instead: list the role names, then keep those whose `Owner` tag matches.

Write the loop over roles yourself, in the same style as the instances loop (read `Owner` for each role, then run the three commands only for yours). In dry-run mode you should see every detach and delete printed, in that order for each role.

#### Y2-T24.6: The notebook skeleton with a coverage table

The goal is `notebooks/eda.ipynb` with cell 1 as a coverage table. Coverage shows rows per location per day, so a day with gaps is not compared unfairly with a complete one.

Install the notebook tools if needed with `pip install jupyter pandas pyarrow matplotlib`. Start Jupyter with `jupyter notebook` from the repository root, then create `notebooks/eda.ipynb` with the New menu. Here is the coverage code for cell 1. It assumes your columns are named `location_id` and `ts_utc`. Check with `print(df.columns)` first, and change names to match yours.

```python
import pandas as pd

df = pd.read_parquet("../data/clean/aq_clean.parquet")
df["ts_ist"] = pd.to_datetime(df["ts_utc"], utc=True).dt.tz_convert("Asia/Kolkata")
coverage = (df.groupby(["location_id", df["ts_ist"].dt.date])
              .size().unstack(fill_value=0))
print(coverage.iloc[:, -7:])
print("incomplete location-days:", int((coverage < 24).sum().sum()))
```

- `../data/clean/aq_clean.parquet` starts with `../`. The notebook runs from its own folder, so the path must go up one level. This is the TC3 trap.
- `pd.read_parquet(...)` reads the clean file. It needs `pyarrow` installed.
- `pd.to_datetime(df["ts_utc"], utc=True)` turns the text into timestamps labelled UTC. `.dt.tz_convert("Asia/Kolkata")` shows the same moments in IST.
- `groupby([...])` groups rows by location and by the IST calendar date. `.size()` counts the rows in each group.
- `.unstack(fill_value=0)` makes one row per location and one column per date. Missing combinations show 0.
- `print(coverage.iloc[:, -7:])` prints the last seven date columns. `iloc` selects by position.
- `(coverage < 24).sum().sum()` counts the cells with fewer than 24 readings. It is a count of incomplete location-days.
- This assumes one row per location per hour. If your clean data holds several pollutants per hour in separate rows, the counts will exceed 24 and hide gaps, so count distinct hours per day instead (for example with `nunique` on the hour).

Expected output: a small table, then a line such as `incomplete location-days: 12`. Your number depends on your data.

Test: run the cell. It must print the table with no error.

#### Y2-T24.7: Two observations

The goal is two observations of your own, each with a chart directly above it, a number, n, the date range and a `So what:` line.

**The hour-of-day axis.** Any chart by hour must use IST. The ticket says to compute it from `ts_utc` plus five and a half hours. Here is one way:

```python
import pandas as pd

df = pd.read_parquet("../data/clean/aq_clean.parquet")
ts = pd.to_datetime(df["ts_utc"], utc=True)
df["hour_ist"] = (ts + pd.Timedelta(hours=5, minutes=30)).dt.hour
```

- `pd.to_datetime(df["ts_utc"], utc=True)` gives UTC timestamps.
- `pd.Timedelta(hours=5, minutes=30)` is a time gap of five hours and thirty minutes.
- `+` moves each timestamp forward by that gap.
- `.dt.hour` takes the hour from the shifted time, so `hour_ist` is the IST hour.

India has no daylight saving time, so this gives the same hours as `tz_convert("Asia/Kolkata")`. Use either, and say which in your notebook. Taking `.dt.hour` before the shift is the classic mistake. It puts the evening peak in the wrong hour.

**The chart.** Group by hour and draw a bar chart with the count and the mean:

```python
import matplotlib.pyplot as plt

by_hour = df.groupby("hour_ist")["value"].agg(["mean", "count"])
fig, ax = plt.subplots(figsize=(10, 4))
ax.bar(by_hour.index, by_hour["mean"], color="#0072B2")
ax.set(xlabel="Hour of day (IST)", ylabel="Mean value", title="Mean value by hour, IST")
plt.show()
```

- `groupby("hour_ist")` splits the rows by hour. `["value"]` picks the reading column. Use your own column name.
- `.agg(["mean", "count"])` gives two columns: the mean and the number of rows per hour. The count is your `n`.
- `plt.subplots(figsize=(10, 4))` creates one figure and one axes.
- `ax.bar(...)` draws one bar per hour.
- `ax.set(xlabel="Hour of day (IST)")` sets the x-axis label. This is the IST label the acceptance criterion checks.

Expected output: a bar chart, one bar per hour, with the axis labelled IST.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| `bash: infra/teardown.sh: No such file or directory` | You are in the wrong folder. | Run `pwd`, move to the repository root, then run again. |
| shellcheck prints `SC1017` or CRLF messages | The file was saved with Windows line endings. | Convert to LF in your editor, then rerun shellcheck. |
| Dry run lists a resource you do not own | Its tag is missing or wrong, so the filter picked it up, or the name is typed wrongly. | Check the tag with the list command, fix the tag or the variable, and rerun the dry run. |

| `aws s3api put-bucket-tagging` removes existing tags | It replaces the whole tag set. | Read the current tags with `get-bucket-tagging` and include them in the new `TagSet`. |

### Defend it in the viva

The trainer asks five questions. Each answer below shows the reasoning. Give your own examples from your work.

**Q1. Why does the teardown script run a dry run first, and why does it use the order it does?**

:::answer Model answer
The dry run prints every change without making it, so you can check each name against your tag list before anything is deleted. The order follows dependencies. The schedule goes first so nothing starts a new run while you remove things. Deleting the function while its trigger still exists would leave a rule firing at nothing, and roles go last because a role is still in use until the resources that depend on it are gone. The `--apply` switch makes the destructive step a deliberate second action.
:::

**Q2. What is the trade-off between stopping a VM and terminating it?**

:::answer Model answer
Stopping keeps the disk and the configuration, so you can start it again, but it still costs for storage. Terminating deletes the VM and its root disk, which stops most charges, but you cannot get it back, and you must recreate it from the scripts. This ticket allows terminate only for the T19 VM, and only after the compute evidence is complete, because that choice cannot be undone.
:::

**Q3. Why convert the timestamps to IST before grouping by hour, and how does the chart show that?**

:::answer Model answer
The readings are stored in UTC. If you group by the UTC hour, an evening peak in Bengaluru appears five and a half hours earlier than it really happened, so the story is wrong. Adding five hours and thirty minutes, then taking the hour, gives the local hour. India has no daylight saving time, so the shift is constant. The chart's x-axis is labelled "Hour of day (IST)" so a reader knows which clock it uses.
:::

**Q4. What did you personally do in this ticket, and how would someone check it in Git?**

A strong answer names the specific things you built, such as the dry-run helper, one ordered teardown step, your tag list, or your two observations, and the commit that holds each one. :::
