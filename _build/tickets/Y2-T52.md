### The ticket in plain words

Open-source projects often stall when one maintainer leaves. The code still exists, but nobody else knows how to run it, what its parts do, or which problems are already known. This ticket stops that from happening to your mini-project before sign-off on 10 April.

Your squad has four jobs. First, close the problems your mentor found in the dry-run, so each one is tracked as a GitHub issue and every blocker is either fixed by a merged pull request or deliberately marked as a won't-fix. Second, make sure no module depends on a single person: every module needs at least two people who can explain it. Third, add a minimum set of automated tests and make the continuous integration (CI) pipeline run them on every pull request to `main`. Fourth, write `HANDOVER.md`, a document that a stranger can follow to run the project.

Each student also writes a short contribution statement. The trainer checks every claim in it against the Git history, so the statement must describe only work you can show.

The point of the ticket is not paperwork. A handover works only if a person who did not build the project can start it, test it and explain it without asking you.

### How your trainer checks it

Your trainer runs four test cases, TC1 to TC4, in order, and checks the five acceptance criteria against what they find. Here is each test case, broken into its parts.

**TC1: no open blockers.**

```term
$ gh issue list -R atria-y2/industry-<squad> -l blocker --state open
```

- `gh issue list` asks GitHub for a list of issues.
- `-R atria-y2/industry-<squad>` names the repository. `-R` means repository, so you do not need to be inside the clone.
- `-l blocker` keeps only issues with the label `blocker`. `-l` is short for `--label`.
- `--state open` keeps only issues that are still open.

Passing output is an empty list. The terminal prints nothing, or a message such as `no issues match your search`. Failing output is a list of issue numbers and titles. The usual cause is a blocker that was closed in your head but never closed on GitHub, or a blocker with no link to the PR that fixed it.

**TC2: the tests pass on a fresh clone.**

```term
$ git clone https://github.com/atria-y2/industry-<squad>.git ~/handover-check
$ cd ~/handover-check
$ pytest -q
........                                                   [100%]
8 passed in 0.31s
```

- `git clone <url> <folder>` downloads the whole repository into a new folder. The folder must not exist yet.
- `cd` moves into that folder.
- `pytest -q` runs every test it finds. `-q` means quiet, so you see dots and a summary rather than every name.

Each dot is one passing test. The last line gives the count and the time. Your count will differ. Look for the words `test_api` and the 422 case in the verbose output if the trainer asks: `pytest -v` shows each name.

```term
$ pytest -q
.F......                                                   [100%]
FAILED tests/test_api.py::test_bad_payload_returns_422 - assert 200 == 422
1 failed, 7 passed in 0.40s
```

A failure tells you the name of the test and what it expected. Here, a request that should have been rejected was accepted. The usual cause is that the payload in the test is actually valid, or that the endpoint does not validate its input.

**TC3: the runbook works on a clean clone.**

The trainer deletes everything, clones the repository again and follows `HANDOVER.md` line by line. They do not ask anyone for help. Passing output is that the stack starts and `make smoke` ends with a success message. A failing step is usually a command that is missing from the runbook, a file that is created by a step you did not write down, or a command that works only on your laptop.

```term
$ make smoke
smoke: OK
```

The exact message depends on your Makefile. What matters is that it ends without an error.

**TC4: the contribution statement matches Git.**

```term
$ git log --author='<student>' --oneline | wc -l
23
```

- `git log --author='<student>'` lists only the commits made under that name. Use the name exactly as it appears in `git log`.
- `--oneline` prints one line per commit.
- `| wc -l` counts those lines. The pipe sends the output of the first command into the second.

Passing output is a number above zero. The trainer then opens each PR your statement cites. Failing output is zero, or a PR link that belongs to someone else, or a PR you only commented on and then described as authored.

**Acceptance criteria the trainer checks in the same run.** Every mentor finding has an issue. `HANDOVER.md` has the four sections Architecture, Runbook, Known issues and Next steps. A PR to `main` makes CI run the data, model and API tests, including a 422 case, and they pass. Each contribution statement matches `git log --author`. A non-author can explain an assigned module: its purpose, its inputs and outputs, its run command and one known issue.

Here is what a passing run looks like as a sequence of steps. Each one is a PR that CI checks before it merges into `main`.

```flow
TITLE: How a PR is checked before it reaches main
NODES: Your branch | GitHub pull request | CI runner
STEPS:
1>2 :: open PR to main :: You push your branch and open a pull request. GitHub shows it to the squad.
2>3 :: run ci.yml :: GitHub starts a fresh machine and runs the steps in ci.yml, including pytest.
3>2 :: all tests passed :: The result is reported back to the PR as a green tick.
```

### Do it, step by step

#### Y2-T52.1: one issue per mentor finding

**Goal.** Every mentor finding has a GitHub issue. Each issue has one label, `blocker`, `should` or `nice`, and one owner. Every blocker is closed by a merged PR or a documented won't-fix.

**New technique: GitHub CLI issues.** The command `gh issue create` makes an issue from the terminal. Each flag does one job. `-R` names the repository. `-t` sets the title, `-b` sets the body and `-l` sets a label. Run these commands on any machine where `gh` is logged in, such as Git Bash on your laptop.

**Stage 1: list the labels that exist.**

```term
$ gh label list -R atria-y2/industry-<squad>
blocker    Must close before sign-off    B60205
should     Fix before handover           FBCA04
nice       Optional                      0E8A16
```

The output shows the label names in the repository. If the names differ from `blocker`, `should` and `nice`, the trainer's filter will not find them. Do not invent new names.

**Stage 2: create a missing label.** Only do this if the list above lacks one of the three.

```term
$ gh label create blocker -R atria-y2/industry-<squad> --color B60205 --description "Must close before sign-off"
✓ Label "blocker" created in atria-y2/industry-<squad>
```

`--color` takes a six-digit hex colour without the `#`. `--description` is the text shown next to the label.

**Stage 3: create one issue per finding.** Copy the finding's wording from the squad channel, then write the owner's GitHub login in place of the placeholder.

```term
$ gh issue create -R atria-y2/industry-<squad> -t "T51 finding: API returns 500 on empty body" -l blocker -b "Mentor dry-run finding. Owner: <github-login>. Done when the 422 test passes on main."
https://github.com/atria-y2/industry-<squad>/issues/14
```

The output is the link to the new issue. Keep the number, because you will close the issue with it. Repeat for every finding. A quick way to check that you have one per finding is to count the findings in the channel and count the issues you created.

**Stage 4: close a blocker with the PR that fixes it.** When a PR fixes a blocker, write `Closes #14` in the PR description. GitHub closes the issue automatically when the PR merges. For a won't-fix, close the issue with a comment that gives the reason.

```term
$ gh issue close 14 -R atria-y2/industry-<squad> -c "Won't fix: the endpoint is internal and the mentor agreed in the channel."
✓ Closed issue #14
```

`gh issue close` takes the issue number. `-c` is short for `--comment`, and the comment is saved on the issue.

**Test this stage.** Run TC1 yourself. The output must be empty.

```term
$ gh issue list -R atria-y2/industry-<squad> -l blocker --state open
```

**Technique note: label filters.** The trainer's command is the same as yours. If it shows an issue you thought you had closed, check that the issue was closed with `gh issue view 14 -R atria-y2/industry-<squad>`, not just renamed.

#### Y2-T52.2: bus factor per module

**Goal.** For each module, find how many distinct people have changed it. Any module with one author gets a second owner who did not write it. The result goes in `docs/module-owners.md`.

**New technique: counting distinct lines.** Before the real command, try this small example. It shows how `sort -u` and `wc -l` work together.

```term
$ printf 'Asha\nBen\nAsha\n' | sort -u | wc -l
2
```

- `printf` prints the three lines. `\n` means a new line.
- The first `|` sends them to `sort -u`, which sorts them and keeps one copy of each name.
- The second `|` sends the result to `wc -l`, which counts lines. The answer is 2 because there are two distinct names.

**Stage 1: count the authors of one folder.** Run this from your clone, on your laptop or on the lab machine.

```term
$ git log --format='%an' -- api | sort -u | wc -l
1
```

- `git log --format='%an'` prints the author name of every commit that touched `api`. `%an` is the author name, and `--format` chooses which fields to print.
- `-- api` limits the history to that folder. The `--` separates the options from the path.
- `sort -u` and `wc -l` count the distinct names, as in the example above.

The output `1` means only one distinct author appears in the history of `api`. Check the count is right by listing the authors with how often each one committed:

```term
$ git log --format='%an' -- api | sort | uniq -c
     14 Asha
```

`uniq -c` counts repeated lines. Here Asha made 14 commits. A second line would mean a second author.

**Stage 2: loop over every module.** First list the module folders your repository has, using `ls` in the clone. Then run a loop. Replace the folder names in the first line with your own.

```bash
for m in src api tests; do
  n=$(git log --format='%an' -- "$m" | sort -u | wc -l)
  echo "| $m | $n |"
done
```

- `for m in src api tests; do` starts a loop. `m` takes each folder name in turn.
- `n=$(...)` runs the command inside the brackets and stores its output in `n`. The `$(...)` form is called command substitution.
- `echo "| $m | $n |"` prints one Markdown table row.
- `done` ends the loop.

Expected output:

```term
| src | 2 |
| api | 1 |
| tests | 3 |
```

Any module with a number of 1 needs a second owner.

**Stage 3: write the table to the file.** Add `| ... |` to the output file with `tee -a`, which shows the output and appends it.

```bash
for m in src api tests; do
  n=$(git log --format='%an' -- "$m" | sort -u | wc -l)
  echo "| $m | $n |  |  |"
done | tee -a docs/module-owners.md
```

The row now has four cells, so it matches the header below: the last two cells are empty for you to fill in by hand. `tee -a` appends, so running the loop again adds a second set of rows rather than replacing the first. Delete the old rows before you run it again. If the file is new, write the header first, with the columns Module, Distinct authors, Second owner and Notes, and the separator line under it:

```text
| Module | Distinct authors | Second owner | Notes |
|---|---|---|---|
```

`git shortlog` gives the same facts with counts. Give it a revision such as `HEAD`, or it waits for input when it is not run in a terminal: `git shortlog -sn HEAD -- api` prints one line per author, with the commit count first.

**Stage 4: assign the second owner.** For each module with a 1, choose a squad-mate who did not write it, and record that person in the same table. The second owner has to be able to explain the module, so the choice matters. Do not put yourself down as the second owner of a module you wrote.

**Test this stage.** Run the loop on a clean clone, not on your working copy with uncommitted changes. The numbers must match what `git log` gives you.

Commit it with a message such as `docs: add module bus-factor table (Y2-T52.2)`.

:::trap Commit count is not bus factor
A person with 200 commits can still leave a bus factor of 1, if nobody else can run or explain the module. The count of distinct authors is only the first test. The real test is whether a second person can explain and run it, which you check in Y2-T52.7.
:::

#### Y2-T52.3: draft a runbook for a module you did not write

**Goal.** Write the runbook section for one module that you did not author. Your author then corrects it in review. This is the part of `HANDOVER.md` that a stranger will use first.

**New technique: finding the author of a module.** Use the same command as before, for one folder, to find out who wrote the module you pick:

```term
$ git log --format='%an' -- src/ingest | sort | uniq -c
     9 Ben
     2 Asha
```

Pick a module where the author is not you.

**Stage 1: run the module on your own machine.** Read the module's code and the parts of the repository that call it. Then run it, following only the commands you find in the repository. Write down every command you had to guess. Each guess is a missing line in the runbook.

**Stage 2: write the section.** A runbook section for a module has five labelled parts. Use these headings, in this order, and fill them with your own words:

- Purpose: one sentence on what the module is for.
- Inputs: the files, tables or requests it reads, with their location.
- Outputs: what it writes or returns, with their location.
- Run command: one exact command, in a code block, that a stranger can copy.
- Known issue: one real problem and what happens when it occurs.

The run command must be one you actually ran from a clean state. A command that has never been run is a guess.

**Where the section goes.** `HANDOVER.md` as a whole must have four top-level sections, with exactly these headings: Architecture (what the modules are and how they connect), Runbook (the commands to start and check the system, with your module section inside it), Known issues (each linked to its issue number) and Next steps (what a new maintainer should do first). The trainer checks that all four exist, and TC3 runs the Runbook as written. So the Runbook must include the commands to start the stack with `docker compose` and to run `make smoke`, in order, from a fresh clone, including any file or setting a step needs.

**Stage 3: branch, commit and open a PR.** Create a branch from `main`, add your change and commit it.

```term
$ git switch -c y2-t52-runbook-ingest
Switched to a new branch 'y2-t52-runbook-ingest'
$ git add HANDOVER.md
$ git commit -m "docs: draft runbook section for ingest module"
[y2-t52-runbook-ingest 3f9e1ab] docs: draft runbook section for ingest module
 1 file changed, 24 insertions(+)
$ git push -u origin HEAD
```

- `git switch -c <name>` creates a new branch and moves onto it. `-c` means create.
- `git add <file>` stages the file, which means it is ready to commit.
- `git commit -m "<message>"` saves the staged change with a message.
- `git push -u origin HEAD` sends the branch to GitHub. `-u` remembers the link, so later pushes need no extra words. `HEAD` means the branch you are on.

Open the pull request. `--fill` takes the title and the body from your commit message.

```term

https://github.com/atria-y2/industry-<squad>/pull/52
```

Your author reviews the PR and comments. Make the corrections as new commits on the same branch. Do not rewrite history after a review has started.

**Test this stage.** Read your section aloud, then run its run command on a clean clone. If a step fails, the section is wrong, so fix the section and not the clone.

Do not ask the author "is this right?". Ask them to run your run command and tell you the first line where it fails. That is a question a reviewer can answer in one minute.

#### Y2-T52.4: tests in CI

**Goal.** Add three test files, run them in `ci.yml`, and make CI fail when they fail. The trainer's TC2 and the 422 criterion depend on this.

**New technique: pytest.** pytest finds every file named `test_*.py` and every function named `test_*`. Inside each function you write `assert`. If the condition is false, the test fails and pytest shows the values.

Here is a small example from a different project, so you can see the shape. It is not part of CityPulse.

```python
# test_units.py, a toy example from a different project
def to_celsius(fahrenheit):
    return (fahrenheit - 32) * 5 / 9

def test_freezing_point():
    assert to_celsius(32) == 0
```

- `def to_celsius(...)` is the function under test.
- `def test_freezing_point():` is one test. pytest runs it because the name starts with `test_`.
- `assert to_celsius(32) == 0` passes if the result is 0, and fails with the actual value if not.

Run it with `pytest -q test_units.py`. Expect one dot and `1 passed`.

**New technique: TestClient for the API.** FastAPI provides a test client that sends requests straight to the app. It needs the `httpx` package, so install it first if the test complains about a missing module.

```python
from fastapi.testclient import TestClient
from api.main import app

client = TestClient(app)
```

- `from fastapi.testclient import TestClient` imports the helper.
- `from api.main import app` imports the FastAPI application object from the file `api/main.py`.
- `client = TestClient(app)` wraps the app so that `client.post(...)` and `client.get(...)` can be called from a test.

**Stage 1: the data test.** In `tests/test_data.py`, write one test at a time. Start with the row count, because it is the simplest:

```python
import pandas as pd

def test_has_enough_rows():
    df = pd.read_parquet("<the file your pipeline writes>")
    assert len(df) >= 500
```

- `import pandas as pd` loads the table library and gives it a short name.
- `pd.read_parquet(...)` reads the file into a table. Replace the placeholder with the path your pipeline from Y2-T51 writes.
- `len(df) >= 500` counts the rows. The test fails if there are fewer than 500.

Then add the schema and the range checks, one test each. A schema test checks that the expected columns exist. A range test checks that each value lies between the limits your squad agreed. Write the limits in the test, not in your head, so the next person can see them.

**Stage 2: the model test.** In `tests/test_model.py`, pick one row whose correct output you know, and check the model returns it. Store the row in the test itself so it is always the same. The expected value must come from a run you recorded, not from a guess.

**Stage 3: the API test.** In `tests/test_api.py`, write two tests. The first sends a valid request and expects status code 200. The second sends a request with a missing field and expects 422.

```python
def test_missing_field_returns_422():
    r = client.post("<your endpoint>", json={})
    assert r.status_code == 422
```

- `client.post("<your endpoint>", json={})` sends an empty JSON body to the endpoint.
- `r.status_code` is the HTTP status code the server returned.
- `assert r.status_code == 422` passes only if the server rejects the body with 422.

422 means FastAPI checked the request and found required fields missing or of the wrong type. Use the endpoint name from `api/main.py`. The body must actually be invalid for your endpoint, or the test proves nothing.

**Stage 4: run the tests locally.**

```term
$ pytest -q
...........                                               [100%]
11 passed in 1.12s
```

If one fails, run `pytest -q tests/test_api.py` on its own, so the output is short, and read the message.

**Stage 5: add the tests to CI.** Open `.github/workflows/ci.yml`. Find the `steps:` list, which sits under a `job` in the file. Add a step that installs the requirements and a step that runs pytest, in that order. YAML is indentation sensitive, so each step starts with `- name:` at the same indent as the others.

```yaml
      - name: Run tests
        run: pytest -q
```

- `- name:` starts one step and gives it a label that appears in the GitHub Actions log.
- `run: pytest -q` is the shell command the step runs.

The pytest step must come after the step that installs the packages, or CI will fail with `pytest: command not found` or a missing module.

Two more things to check in the same file. #### Y2-T52.5: CHANGELOG and release notes

**Goal.** Add the changes since the last version to `CHANGELOG.md`, and draft the release notes for v1.0.

**New technique: reading merged PRs as JSON.** `gh pr list` can print the merged PRs as JSON. `jq` then turns that JSON into text lines.

```term
$ gh pr list -R atria-y2/industry-<squad> --state merged --limit 100 --json number,title | jq -r '.[] | "- \(.title) (#\(.number))"'
- docs: add module bus-factor table (#48)
- test: add 422 case for bad payload in test_api (#47)
```

- `--state merged` keeps only merged PRs. `--limit 100` sets the maximum number to read.
- `--json number,title` asks for two fields in JSON.
- `jq -r` prints raw text, without the quote marks JSON uses for strings.
- `'.[] | "- \(.title) (#\(.number))"'` loops over each PR and builds a bullet line with the title and the number.

Use this list as raw material. Group the lines under headings your changelog already uses, such as Added, Changed and Fixed. If the file is new, use the headings from a standard changelog layout. Do not copy lines you did not write without checking that the change is part of this version.

**Release notes.** Write three short parts: what v1.0 can do, what changed since the last version, and what is known to be missing. Link the known issues to their issue numbers.

### Defend it in the viva

The trainer asks five questions. Answer in your own words. The model answers show the reasoning. They do not describe your history, so use your own commits and PRs for the facts.

**Why must the runbook be run on a clean clone before it is merged?**

:::answer Model answer
A clean clone has none of your local files, environment variables or installed packages. If a command works only on your machine, the clone shows that. A command that has never been run is a guess, and a handover built on guesses fails the first time a stranger uses it. Running it fresh is the only test that matches what the next person will do.
:::

**What is the trade-off between leaving a known issue open and fixing it before handover?**

:::answer Model answer
Fixing everything before handover can delay sign-off and add risk late in the project. Leaving a problem open is acceptable when it is written down with its cause, its effect and the next step, and when it is not a blocker. A blocker must be closed by a merged PR or a documented won't-fix, because it would stop the next person from running the system. A should or nice issue can stay open in Known issues, as long as the reader can see it.
:::

**Why is a second owner who did not write the module better than the module's most active author?**

:::answer Model answer
The bus factor asks whether a second person can explain and run the module without the author. The most active author knows the module best, but that is the problem, because they are also the one who might leave. A second owner who did not write it has to read the code, the runbook and the tests to understand it. That is the test that proves the module can survive a departure, so the choice is deliberate.
:::

**Why does the test suite include a 422 case and not only a 200 case?**

:::answer Model answer
A 200 case shows that the API works when the input is good. A 422 case shows that it refuses bad input, which is how a client learns that its request was wrong. Without the 422 test, a change could make the API accept anything and still pass, and the first person to send a bad request would find the fault in production. Testing the rejection path protects the contract the client depends on.
:::

**What did you personally do for this ticket, and how can the trainer verify it?**

:::answer Model answer
Name the subtask you owned, the branch you made, the PRs you opened and the reviews you gave, with their numbers. Show that the trainer can verify each one: run `git log --author` for your commits, and `gh pr view` for each PR. The strongest answer names one thing you changed, why it was needed and how you tested it, so the trainer can see your reasoning as well as your name in the history.
:::

### Check yourself

```quiz
Q: Your bus-factor loop prints 1 for the module api. What does that number mean?
- The module has one file in it
- The module has passed one test
* Only one distinct author name appears in the history of api
- api has been committed exactly once
WHY: The number counts distinct author names in the history of the folder, not files, tests or commits. A count of 1 means a second person has not yet changed the module, so it needs a second owner.

Q: Which flag makes gh issue list show only the issues with the label blocker?
- --state blocker
* -l blocker
- -R blocker
- -t blocker
WHY: -l is short for --label. --state open filters by open or closed status, -R names the repository and -t sets a title when creating an issue, so none of those filters labels.

Q: A test posts an empty JSON body to /predict and expects 422, but gets 200. What is the most likely cause?
* The endpoint accepts an empty body, so the test body is not actually invalid
- The pytest command was run with -q
- The test client was not imported
- The CI runner has no internet access
WHY: A 422 response means the server rejected the body. If it returns 200 for an empty body, the endpoint does not require any fields, so the test has to send a body that is invalid for that endpoint.
```
