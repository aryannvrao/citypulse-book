### The ticket in plain words

Your squad has already set a **baseline** in an earlier ticket. A baseline is the simple rule the client uses today, and any model you build must beat it. This ticket asks you to build that model for the industry client, using the same training pattern as CityPulse's `train.py`, and to show the result in terms the client understands.

The description gives the reason. A hospital told "the estimate is off by about 12 minutes" cannot tell whether that helps patients or administrators. The client buys **business units**: minutes saved, cases caught or rupees avoided. So you train and save a model, test it on the same time-based holdout as the baseline, check what happens if it is 10% worse, and write an impact section whose numbers all come from `metrics.json`.

The trainer reruns your code on a clean copy, so everything must work from the repository alone.

#### Y2-T50.1 Move target, features and split date into config.yaml

**Goal.** The settings for the model live in `config.yaml`, not in the code, and the split date matches the baseline's split date.

**Teaching first.** YAML is a settings format. A line `key: value` sets one value, indentation nests keys, and `- ` starts a list item. This made-up delivery example shows the shape. Use your squad's own names and values.

```yaml
data:
  target: delivery_minutes
  date_col: order_date
features:
  - distance_km
  - day_of_week
split:
  holdout_from: 2027-01-01
```

Line by line: `data:` groups the target and the date column. `features:` is a list of input columns. `split:` holds the holdout start date.

**Stage 1: write the settings.** Move your target, feature list and split date into `config.yaml`, using the key names you chose.

**Stage 2: check that the file reads.** Run this from the repository root.

```term
$ python -c "import yaml; print(yaml.safe_load(open('config.yaml')))"
{'data': {'target': 'delivery_minutes', 'date_col': 'order_date'}, 'features': ['distance_km', 'day_of_week'], 'split': {'holdout_from': datetime.date(2027, 1, 1)}}
```

`yaml.safe_load` returns the date as a date object, not text, so the next stage converts both values to text before comparing.

**Stage 3: assert that the split matches the baseline.** Start `src/train.py` with this.

```python
import json, yaml
cfg = yaml.safe_load(open("config.yaml"))
base = json.load(open("reports/baseline.json"))
assert str(cfg["split"]["holdout_from"]) == str(base["split_date"]), "split differs from the baseline"
```

Line by line: the first line loads both libraries, the next two read the files, and the `assert` stops the script with the quoted message if the dates differ. Test it by changing the date in `config.yaml` once, seeing the error, and changing it back. If the assert fails even though the two dates look the same, check the format: `baseline.json` must hold `YYYY-MM-DD` text, so a value like `27/03/2027` fails, and the fix is to write it in ISO form in both files.

Commit with the message for Y2-T50.1.

#### Y2-T50.2 Write src/train.py

**Goal.** One script fits a Pipeline on the training rows, scores the holdout, saves the model and writes `metrics.json`.

**Teaching first.** A Pipeline runs its steps in order. Inside one, `fit` learns the preprocessing from the training rows only, so test rows cannot leak into training.

**Stage A: load the data and split by date.** Add these lines below the assert.

```python
import pandas as pd
date_col, target, features = cfg["data"]["date_col"], cfg["data"]["target"], cfg["features"]
df = pd.read_parquet("data/clean/dataset.parquet")
df[date_col] = pd.to_datetime(df[date_col])
cut = pd.Timestamp(cfg["split"]["holdout_from"])
train, test = df[df[date_col] < cut], df[df[date_col] >= cut]
print(len(train), len(test))
```

Line by line: `pd.read_parquet` reads the cleaned data (it needs `pyarrow`, which belongs in `requirements.txt`). `pd.to_datetime` makes the dates comparable. The `<` and `>=` test puts every row in exactly one group. The `print` shows two counts, both above zero, such as `4200 610`.

**Stage B: build the Pipeline.** The model class is your squad's choice. `Ridge` is only an example.

```python
from sklearn.pipeline import Pipeline
from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import OneHotEncoder, StandardScaler
from sklearn.linear_model import Ridge
numeric = [c for c in features if pd.api.types.is_numeric_dtype(train[c])]
categorical = [c for c in features if c not in numeric]
preprocessor = ColumnTransformer([
    ("num", Pipeline([("impute", SimpleImputer(strategy="median")), ("scale", StandardScaler())]), numeric),
    ("cat", OneHotEncoder(handle_unknown="ignore"), categorical),
])
model = Pipeline([("preprocessor", preprocessor), ("model", Ridge(alpha=1.0))])
```

Line by line: the `numeric` and `categorical` lists split the features by column type. The `ColumnTransformer` fills and scales numeric columns, and one-hot encodes text columns into 0 or 1 columns. `handle_unknown="ignore"` avoids a crash on a category the training rows never had. The last line joins the preprocessor and model into one Pipeline.

Run `python src/train.py` now. It should run without an error and print the same two counts as stage A, because nothing is fitted yet. Make sure `requirements.txt` lists every package used so far (for example `pandas`, `pyarrow`, `scikit-learn`, `pyyaml` and `joblib`).

**Stage C: fit, predict and score.** Add these lines.

```python
from sklearn.metrics import mean_absolute_error
model.fit(train[features], train[target])
pred = model.predict(test[features])
mae = mean_absolute_error(test[target], pred)
print(f"MAE on the holdout: {mae:.2f}")
```

Line by line: `fit` learns from training rows only, `predict` answers the test rows using features only, and `mean_absolute_error` returns the average size of the error.

**Stage D: save the model.** Add these lines.

```python
import os, joblib
os.makedirs("models", exist_ok=True)
joblib.dump(model, "models/model.joblib")
```

`exist_ok=True` makes the folder step safe to rerun. `joblib.dump` writes the whole fitted Pipeline to one file.

**Stage E: write metrics.json.** Section Y2-T50.4 adds the remaining keys.

```python
import json
primary = round(float(mae), 2)
baseline_value = float(base["value"])
metrics = {"model": primary, "baseline": baseline_value}
with open("metrics.json", "w") as f:
    json.dump(metrics, f, indent=2)
```

`float(...)` turns each value into a plain number that JSON can store. Check the key `base["value"]` against your baseline file.

**Stage F: report and exit.** Add a final `print` with a message of your own. Run `python src/train.py` and then `echo $?`. The exit code must be 0. Commit with the message for Y2-T50.2.

#### Y2-T50.4 Add sensitivity_10pct and segments_worse_than_baseline

**Goal.** `metrics.json` shows how the improvement is computed, what happens if the model is 10% worse, and which segments the model loses on.

**Teaching first.** For an error metric, the gain is (baseline minus model) divided by the baseline, times 100. The sensitivity check multiplies the model's error by 1.10. The trace uses fictional numbers.

```trace
TITLE: Working out the gain and the 10% worse case
CODE:
baseline = 20.0
model = 15.5
gap = baseline - model
improvement_pct = round(gap / baseline * 100, 1)
sens = round(model * 1.10, 2)
print(improvement_pct, sens)
STEPS:
1 :: baseline=20.0 :: The baseline's error, read from reports/baseline.json.
2 :: baseline=20.0; model=15.5 :: The model's error on the same holdout rows.
3 :: baseline=20.0; model=15.5; gap=4.5 :: The gap is how many units closer the model is.
4 :: baseline=20.0; model=15.5; gap=4.5; improvement_pct=22.5 :: The gap as a share of the baseline.
5 :: baseline=20.0; model=15.5; gap=4.5; improvement_pct=22.5; sens=17.05 :: The 10% worse case. It is still below 20.0, so the claim survives.
6 :: baseline=20.0; model=15.5; gap=4.5; improvement_pct=22.5; sens=17.05 :: The print shows both numbers.
```

**Direction matters.** If your metric is higher-is-better, the gain is the model minus the baseline, and the 10% worse case multiplies by 0.90.

**Stage G: add the two keys.** Replace the `metrics` dictionary from stage E with this version.

```python
improvement_pct = round((baseline_value - primary) / baseline_value * 100, 1)
sens = round(primary * 1.10, 2)
metrics = {
    "model": primary,
    "baseline": baseline_value,
    "improvement_pct": improvement_pct,
    "sensitivity_10pct": sens,
    "segments_worse_than_baseline": [],
}
```

The first line computes the gain and the second the 10% worse case. The dictionary now has all five keys. The empty list is a placeholder. Run the script and check with `python -m json.tool metrics.json`.

**Stage H: fill the segments.** A segment is worse when the model's error for that group is higher than the baseline's error for the same group. Add this before the `metrics` dictionary.

```python
segment_col = cfg["data"]["segment_col"]
seg_worse = []
for name, rows in test.groupby(segment_col):
    seg_mae = mean_absolute_error(rows[target], model.predict(rows[features]))
    if seg_mae > segment_baselines[name]:
        seg_worse.append(str(name))
```

`segment_col` is a setting you add to `config.yaml` under `data:`. `test.groupby` splits the test rows into groups. `segment_baselines` is a dictionary you must build first, mapping each group name to the baseline's error for that group on the same test rows. If `reports/baseline.json` has no per-group values, compute them with the same baseline rule on each group and agree the rule with your squad. Test it by printing `seg_worse` and checking one group by hand.

Then change the placeholder to `"segments_worse_than_baseline": seg_worse`. Commit with the message for Y2-T50.4.

:::trap Hiding the segments where the model loses
If the model is worse than the baseline for one group, that group must appear in `segments_worse_than_baseline`. Leaving it out is an overclaim, and the trainer treats it as a failure.
:::

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| `No module named 'sklearn'` | Environment not active, or package missing. | Activate `.venv`, then install `requirements.txt` again. |
| `split differs from the baseline` | `config.yaml` date differs from the baseline. | Copy the date from `reports/baseline.json`. |
| `TypeError` comparing a date with text | The date column was read as text. | Convert it with `pd.to_datetime`. |
| `could not convert string to float` | A text column went into the model unencoded. | Put text columns in the categorical list. |
| `improvement_pct` is negative | Model is worse, or the gain formula is reversed. | Check the direction in the trace. |
| `improvement_pct` suspiciously high (for example above 40) | Possible leakage, though not proof. | Remove the feature not known at prediction time, then rerun. |
| TC3 name not found | Git name differs from the table. | Match the table to `git config user.name`. |
| README number differs from `metrics.json` | README typed from an older run. | Rerun `python src/train.py` and copy again. |

### Check yourself

```quiz
Q: Your holdout starts on 2027-01-01, but your model's test rows start on 2026-12-01. Why is the comparison with the baseline unfair?
- It makes training slower
* The two scores are measured on different rows
- The metrics file cannot hold dates
- A later start date is always safer
WHY: Both scores must come from the same rows as reports/baseline.json. A different start date changes which rows are scored, so the gap may not come from the model.

Q: A model predicts delivery time at the moment an order is placed. Which feature must be removed?
- The distance from the warehouse to the address
- The day of the week of the order
* The actual delivery time recorded after the parcel arrives
- The courier's average speed from earlier orders
WHY: A feature must be known at prediction time. The actual delivery time is recorded after the outcome, so using it is leakage. The other three are known when the order is placed, or earlier.

Q: The baseline's value is 20.0 and the model's MAE is 15.5. Lower is better. What is improvement_pct, rounded to one decimal place?
- 4.5
- 0.225
- 77.5
* 22.5
WHY: The gain is (20.0 - 15.5) / 20.0 x 100, which is 22.5. 4.5 is the raw gap in minutes, not a percentage. 77.5 is the model's error as a share of the baseline, which is the reverse of the gain.
```
