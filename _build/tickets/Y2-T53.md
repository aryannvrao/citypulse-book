### The ticket in plain words

Theranos was a blood-testing company that promised more than its machines could show. It collapsed when outside checks found that its evidence did not back its claims. CityPulse has the same risk in a smaller form. A squad can say its model is better than it is, and one probing question from a mentor can expose the gap.

On 10 April your squad presents to the mentors who sign the project off. This ticket is the rehearsal. You run the whole talk in order (problem, approach, demo, impact, limits, next steps) to a peer squad acting as the client. The talk must fit in seven minutes, every number on the slides must match `metrics.json`, a backup video must be ready in case the live demo fails, and you need answers for at least ten likely questions.

The rehearsal exists to find overclaims, which are sentences that say more than the evidence shows. The fix is a number and a limit that someone can check.

### Before you start

These tickets must be merged to the squad's `main` branch: Y2-T50 (a model that beats the baseline, with its impact stated), Y2-T51 (the mini-project run end to end, with a demo recording) and Y2-T52 (`HANDOVER.md`, green tests, `metrics.json`).

Tools. Git, the GitHub CLI `gh`, `jq` (reads JSON), `pdftotext` (reads PDF text), `ffmpeg` and `ffprobe` (cut and measure video), Python 3, a screen recorder and a browser with a private window. On the laptop, use Git Bash and install what is missing.

Quick checks. Each should print what is shown.

- `git fetch origin && git log --oneline origin/main -5`: recent merge commits, including Y2-T50 to Y2-T52 if your squad names commits by ticket.
- `ls HANDOVER.md metrics.json`: both names print, with no error.
- `jq '.model.mae' metrics.json`: one number, such as `12.1`.
- `command -v pdftotext ffmpeg ffprobe`: a path for each tool. A tool that prints nothing is missing.

### How your trainer checks it

The trainer checks five acceptance criteria and runs four test cases. Each is listed with a command you can run yourself.

**Acceptance criterion 1 and test case 1 (TC1).** The trainer times one full run-through with a 7:00 timer. The result must be 7:00 or less, with five distinct speakers. A time of 7:12 fails, however good the content. You check the total in the timing step of Y2-T53.1 and by stopwatch in Y2-T53.5.

**Acceptance criterion 2 and TC2.** The trainer compares `docs/slides.pdf` with `metrics.json`. No number on the slides may be missing from the metrics file or different from it. Run this:

```term
$ mkdir -p ~/citypulse-check
$ pdftotext docs/slides.pdf - | grep -oE '[0-9]+(\.[0-9]+)?' | LC_ALL=C sort -u > ~/citypulse-check/slides-numbers.txt
$ jq -r '.. | scalars | tostring' metrics.json | grep -oE '[0-9]+(\.[0-9]+)?' | LC_ALL=C sort -u > ~/citypulse-check/metric-numbers.txt
$ LC_ALL=C comm -23 ~/citypulse-check/slides-numbers.txt ~/citypulse-check/metric-numbers.txt | wc -l
0
```

A passing result is `0`. A failing result lists the numbers (run `comm` without `wc` to see them). Some hits are harmless, such as page numbers, but read each one. A number written as `1,200` is read as `1` and `200`, and `34.2%` as `34.2`, so read those hits by hand.

**Acceptance criterion 3 and TC3.** The README demo link must open in an incognito window and play a 2 to 3 minute video that shows the one-command run to a prediction. Check the length with `ffprobe`:

```term
$ ffprobe -v error -show_entries format=duration -of default=noprint_wrappers=1:nokey=1 backup-demo.mp4
148.233000
```

The number is seconds, so 148 is 2:28, which passes. A value such as `215.000000` is over three minutes and must be trimmed. Also check playback yourself in a private window. A video that asks for a login fails.

**Acceptance criterion 4.** `docs/qa-prep.md` needs ten or more questions, each with an owner and an evidence link, covering data, model, API, impact, limits and process. The count is checked with the command in Y2-T53.4.

**Acceptance criterion 5 and TC4.** The peer form must record two fixes per squad, and both must be applied, which you show in Git. TC4 is an out-of-scope question. A pass is "I don't know; here is how I'd find out", with a concrete method and no bluffing.

### Do it, step by step

#### Y2-T53.1: draft the running order

**Goal.** A written plan that says who speaks and for how long, with the total at 420 seconds (7:00) or less.

**Technique: converting minutes and seconds.** A time such as `1:10` becomes seconds: 1 × 60 + 10 = 70. The rule is total = spoken seconds + handoff seconds × (parts − 1). This trace uses three fictional parts and 5-second handoffs.

```trace
TITLE: Adding up a running order with handoffs
CODE:
parts = ["1:10", "1:10", "1:20"]
spoken = 0
for p in parts:
    m, s = p.split(":")
    spoken += int(m) * 60 + int(s)
total = spoken + 5 * (len(parts) - 1)
ok = total <= 420
STEPS:
1 :: parts=["1:10", "1:10", "1:20"] :: Three parts, each written as minutes and seconds.
2 :: parts=["1:10", "1:10", "1:20"]; spoken=0 :: Start the spoken total at zero seconds.
3 :: p="1:10"; spoken=0 :: The loop takes the first part.
4 :: p="1:10"; m="1"; s="10"; spoken=0 :: split(":") cuts the text at the colon, leaving two pieces of text.
5 :: p="1:10"; spoken=70 :: One minute is 60 seconds, plus 10, gives 70.
5 :: p="1:20"; spoken=220 :: After all three parts, the spoken total is 70 + 70 + 80.
6 :: spoken=220; total=230 :: Two handoffs of 5 seconds are added, giving 230 seconds.
7 :: ok=True; total=230 :: 230 is at most 420, so the plan fits.
```

Line by line. `split(":")` makes two pieces of text, `int(...)` turns them into numbers, and `m * 60 + s` gives the seconds. `total` adds the handoffs, and `ok` is `True` when the total is at most 420.

**Stage 1: test the arithmetic.** Save this as `timing_check.py` and run `python3 timing_check.py`. It prints nothing when every assert passes. The numbers are fictional; use your own running order.

```python test
def to_seconds(text):
    minutes, seconds = text.split(":")
    return int(minutes) * 60 + int(seconds)

def total_with_handoffs(parts, handoff_seconds):
    spoken = sum(to_seconds(p) for p in parts)
    handoffs = max(len(parts) - 1, 0)
    return spoken + handoff_seconds * handoffs

assert to_seconds("7:00") == 420
assert to_seconds("0:45") == 45
assert total_with_handoffs(["1:10", "1:10"], 5) == 145
assert total_with_handoffs(["1:00"], 5) == 60
assert total_with_handoffs([], 5) == 0
```

Line by line. `sum` adds one value per part. `max(len(parts) - 1, 0)` stops the handoff count going below zero, which matters for the empty list. Each `assert` is a fact that must be true.

**Stage 2: write the table.** Create `docs/running-order.md` with one row per speaker. Fill the skeleton with your squad's own names and times, and add a total row:

```markdown
| Order | Speaker | Part | Minutes | Handoff seconds |
|---|---|---|---|---|
| 1 | | | | |
```

**Stage 3: commit.** Run `git add docs/running-order.md` and `git commit -m "docs: draft running order with timings for Y2-T53"`.

**Test.** Your helper's total is 420 or less, and every member appears once.

#### Y2-T53.2: build the slides

**Goal.** Eight to ten slides with full-sentence headlines and every number copied from `metrics.json`.

**Technique: reading one value with jq.** `jq '.model.mae' metrics.json` prints the value under `model`, then `mae`. A comma asks for two values: `jq '.model.mae, .baseline.value' metrics.json` prints two lines. Copy the printed values into the slides; do not type them from memory.

**Stage 1: write full-sentence headlines.** "Accuracy" is a label. A headline has a subject and a verb. A fictional bicycle-repair example, not your project, shows the shape: "Our repair-time estimate is closer by 4.0 minutes per job than the shop's usual rule." Write your own with your own numbers.

**Test.** After export (Y2-T53.7), run the TC2 commands. The result must be `0`.

#### Y2-T53.3: record the backup video

**Goal.** A 2 to 3 minute video of the one-command run to a prediction, linked in the README.

```flow
TITLE: From a recording to a link that plays in incognito
NODES: Your laptop | Video host | README on GitHub | Trainer's browser
STEPS:
1>2 :: upload :: The 2 to 3 minute backup video goes to the video host, with a link anyone can open.
2>3 :: paste link :: The link is written into the README under the Demo heading.
3>4 :: open in incognito :: The trainer opens the README link in a private window.
4>2 :: request video :: The browser asks the video host for the file.
2>4 :: video stream :: The video plays, and the trainer checks its length.
```

**Stage 1: record.** Capture the one-command run and the first prediction. Record a little more than you need, because trimming is easier than re-recording.

**Stage 2: trim and compress.**

```bash
ffmpeg -i raw-demo.mp4 -t 150 -vf "scale=1280:-2" -c:v libx264 -crf 26 -c:a aac -movflags +faststart backup-demo.mp4
```

Line by line. `-t 150` keeps 150 seconds. `-vf "scale=1280:-2"` sets the width to 1280 pixels and keeps the shape. `-c:v libx264` picks the H.264 codec, which plays in almost every browser. `-crf 26` sets quality: a higher number gives a smaller file. `-movflags +faststart` lets playback start before the download finishes.

**Stage 3: measure.** Run the `ffprobe` check from the trainer section and expect a value between 120 and 180.

**Stage 4: upload and link.** Upload to the host your squad agreed on, with sharing set to anyone with the link. In the README add this section, with your real link in place of the placeholder:

```markdown
## Demo

Backup video (2 to 3 minutes, one-command run to a prediction): URL-HERE
```

Then paste the same link on the demo slide (re-export the PDF afterwards, see Y2-T53.7), and record it in the LMS. Add one line to the README with your squad's code freeze plan, for example `Code freeze: Fri 9 Apr 23:59, after this only documentation fixes are merged`. Write the plan in your own words; the Definition of done checks for the words "Code freeze".

**Test.** Open the README in a private window, click the link and check that the video plays from the start.

#### Y2-T53.4: write the Q&A rows

**Goal.** Two or more rows in `docs/qa-prep.md` for your area. The file needs ten or more questions across the six areas.

**Technique: a table a command can count.** If every question row starts with a number inside pipes, `grep` can count them. Use this layout:

```markdown
| No. | Area | Question | Owner | Two-line answer | Evidence link |
|---|---|---|---|---|---|
| 1 | Data | (question) | (your name) | (line one, line two) | (link to file or commit) |
```

A fictional row for a different project, a bakery's queue estimate, shows the detail level. Do not copy it.

```markdown
| 1 | Limits | Does the estimate work on public holidays? | Lena | No, the model was trained on normal weekdays, and holidays are listed as a known limit. | docs/known-limits.md |
```

Line by line. Each column answers one requirement: the number, the area, the question, the owner, the two-line answer and the evidence link.

**Stage 1: count.**

```bash
grep -cE '^\| [0-9]+ \|' docs/qa-prep.md
```

Line by line. `-c` counts matching lines. `^` is the start of a line, `\|` is a literal pipe, and `[0-9]+` is one or more digits. The header and separator rows are not counted. The expected output is `10` or more across the squad.

**Test.** Each of your rows has an owner and a working evidence link.

#### Y2-T53.5: the full timed rehearsal

**Goal.** One complete, timed run to the peer client, with five minutes of hard questions, then a role swap.

**Technique: a timer someone else holds.** In rehearsal, one student holds a phone stopwatch and calls out each handoff. Note the total, and write down every question the peer squad asks for the qa-prep file.

**Test.** You have a total, the handoff times, and a list of questions.

#### Y2-T53.6: present your part and apply two fixes

**Goal.** Your part fits its time box, and two peer fixes are made and committed as separate changes.

**Technique: one commit per fix.** List each peer comment with the line it applies to, choose the two that cover your part, and commit each fix on its own:

```bash
git diff --stat
git add docs/running-order.md
git commit -m "docs: shorten handoff in my section after peer feedback"
```

Line by line. `git diff --stat` shows how many lines changed, so you can confirm the change is small. The commit records one fix with a one-line message.

**Test.** `git log --oneline` shows two fix commits that change only your section.

#### Y2-T53.7: rewrite the weakest claim and export the slides

**Goal.** Find the claim the evidence supports least, rewrite it with a number and a limit, export the slides to PDF and commit.

**Technique: three parts of a claim.** A claim states what changes, by how much, and where it stops. "Our estimate is always right" has none of these. "Our estimate is closer by 4.0 minutes per job on the test set, and it is untested on bank holidays" has all three. The sensitivity result in `metrics.json` gives the stress-test answer:

```bash
jq '.sensitivity_10pct' metrics.json
```

Line by line. `'.sensitivity_10pct'` selects that key. The output shows the stressed error and whether the claim still holds at 10% worse. Use the number and the answer in the rewrite.

**Stage 1: find the claim.** Look for "always", "never", "perfect", or a number with no source. Also run `jq '.segments_worse_than_baseline' metrics.json`: if it lists any segment, a slide that says the model beats the baseline everywhere is an overclaim.

**Stage 2: export the PDF.** If the slides are in a presentation tool, use its PDF export. If they are a `.pptx` file, LibreOffice converts them:

```bash
soffice --headless --convert-to pdf --outdir docs slides.pptx
```

`--headless` runs without a window, `--convert-to pdf` picks the output type, and `--outdir docs` writes into `docs`.

**Stage 3: check and commit.** Run the TC2 commands on the new PDF, expect `0`, then:

```bash
git add docs/slides.pdf
git commit -m "docs(slides): rewrite weakest claim with metrics.json numbers"
```

**Test.** TC2 prints `0`, and the commit shows your name.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| Rehearsal runs at 7:12. | Handoffs were not counted, or one part overran its time box. | Add handoff seconds with the helper, then cut the longest claim in the slowest part. |
| TC2 lists `12.2`, which is not in the metrics file. | Typed from memory, or the PDF was not re-exported after an edit. | Copy the value with `jq`, re-export and run TC2 again. |
| TC2 flags `12.20` against `12.1`. | A trailing zero the file does not have. | Copy the number exactly as the file prints it. |
| Video plays on your laptop but not in incognito. | Sharing requires a login. | Set sharing to anyone with the link and test in a private window. |
| `grep` counts 6 when there are 10 rows. | Rows lack the number in the first column. | Number every row and keep the table in one block. |
| A bluffed answer to an out-of-scope question. | A guess instead of a method. | Say "I don't know; here is how I'd find out" and name the file or owner. |

### Defend it in the viva

**Why did you replace the headline with a number and a limit?**

:::answer Model answer
A claim such as "always right" cannot be tested, so one question breaks it. A number from the metrics file can be reproduced, and a stated limit shows the scope.
:::

**What did you trade off to keep the talk within seven minutes?**

:::answer Model answer
Depth for time. A shorter talk explains the method less, so some detail moves to the Q&A or the README. The squad kept the demo and the limits, because mentors judge those.
:::

**What did you personally do, and how does Git show it?**

:::answer Model answer
Name the subtask you owned, the commits that show it and one decision you made. Never claim work another student did.
:::

**How do you know every number on the slides matches the metrics file?**

:::answer Model answer
Each slide number is copied from `metrics.json` with a command, then every number is extracted from the PDF and compared with `comm`. Any number that appears only on the slides is read before it is accepted.
:::

**A mentor asks about the data pipeline, which is not your part. What do you say?**

:::answer Model answer
I do not know that detail. I would name the owner who can answer it, and the file or check command where the answer lives. A clear method shows that I can find the answer without guessing.
:::

### Check yourself

```quiz
Q: In TC2, what does `LC_ALL=C comm -23 slides.txt metrics.txt` print?
- Lines that appear in both files
* Lines that appear only in the first file
- Lines that appear only in the second file
- Every line of both files
WHY: The option -23 hides the matching lines and the lines found only in the second file. What remains are the slide numbers missing from the metrics. Matching lines are the tempting wrong answer, but they are the passes.

Q: Which tool reads the length of an MP4 file for the TC3 check?
- pdftotext
* ffprobe
- jq
- comm
WHY: ffprobe reads the metadata of a media file, including its duration. pdftotext reads PDF text, jq reads JSON and comm compares sorted lists.

Q: A rehearsal runs for 7:12 on the timer. Which fix is most likely to pass TC1 next time?
- Add a fourth slide to explain the approach more fully
- Hide the timer from the speaker so they relax
* Measure each part, cut the longest claims, and recount the total with the handoffs
- Speak faster without changing the content
WHY: TC1 checks the total time, so measure each part and cut where the time goes. A new slide adds time, and a hidden timer changes nothing. Speaking faster without changing content may save seconds, but it can make the talk harder to follow and does not reduce the handoffs.
```
