### The ticket in plain words

CityPulse is a platform that shows Bengaluru city data. Each squad builds one product on top of public data from the city. Before anyone writes code, the company needs a team with clear roles, and a problem that is worth solving with data that really exists.

This ticket prevents two common failures. The first is a vague goal. "Analyse pollution" does not say who the product is for, what hurts them, which data you would use, or how you would know it worked. The second is a dead or HTML-only data URL. A URL is the web address your program asks for data. If the address is dead, it returns an error. If it returns an HTML web page (a page built for people to look at) instead of JSON (a text format for data, explained below), the automatic fetching work that starts in T05 cannot read it. You find both problems now, by checking the URLs yourself.

By tonight, your squad of five must set its first-month roles, shortlist two domains (broad topic areas), write a problem statement for each, and prove that both data sources answer with JSON. You also write a three-line working agreement and give a 60-second pitch.

### How your trainer checks it

The trainer checks six acceptance criteria. You can check each one yourself first.

1. **T0 completed.** Every student shows T0 as completed on the platform report. Check your status now. The programme deadline for T0 is 18:30. If a student cannot finish, the trainer logs a named recovery time for them.
2. **5 members, 5 distinct roles.** Checked by TC3.
3. **Each statement names a user, a pain, a data source and an outcome with a number and a unit.** Checked by TC4.
4. **Each URL returns HTTP 200 with JSON containing the recorded field path.** Checked by TC1 and TC2.
5. **No API key or token anywhere in the sheet.** Checked by TC5.
6. **Every student has a personal verified-by entry.** Check that your own cell holds your curl result.

The trainer then runs five test cases. Each command is split into parts below.

**TC1: the URL returns 200 and JSON.** For each URL in the sheet:

`curl -s -o /tmp/r.json -w '%{http_code}' --max-time 15 '<url>'; head -c 1 /tmp/r.json`

- `curl` sends the request.
- `-s` (silent) hides the progress meter.
- `-o /tmp/r.json` saves the response body to a file. Git Bash maps `/tmp` to a Windows folder; the lab uses the real `/tmp`.
- `-w '%{http_code}'` (write-out) prints the status code after the request. The single quotes stop the shell reading the braces.
- `--max-time 15` gives up after 15 seconds.
- `'<url>'` is the address. Keep the quotes, because an `&` in a URL would split the command.
- `;` runs the next command whether or not the first succeeded.
- `head -c 1` prints the first byte of the saved body.

Passing output is `200{` or `200[`. curl prints no newline after the code, so the body's first byte sits on the same line. `200<` means the source sent HTML. `404` followed by `<` means a not-found page. `000` means no answer within 15 seconds, a wrong host, or a blocked address. Without `--fail`, curl exits 0 even on a 404, so always read the status code.

**TC2: the recorded field path exists.**

`jq -e '<recorded jq path>' /tmp/r.json`

- `jq` reads the JSON file.
- `-e` sets the exit code from the value: 0 when the value is not null or false, 1 when it is, and 4 when nothing comes out.
- The filter in single quotes is the path copied from the sheet.

Passing output is a value, and `echo $?` then prints `0`. If the output is `null` with exit code 1, the path is wrong for this response. If you see `Cannot index array with "name"`, the response is a list, so the path needs `.[0]` first.

**TC3: 5 members, 5 distinct roles, no blanks.** Copy the role column, without the header, into `roles.txt`, then run:

`sort -u roles.txt | grep -c .`

- `sort -u` sorts the lines and keeps one copy of each.
- `|` passes that output to the next command.
- `grep -c .` counts lines containing at least one character, so blank lines are not counted.

Passing output is `5`. A `6` means the header was copied. A `4` means two members share a role.

**TC4: each outcome has a number and a unit.** This is a read-through. Highlight the outcome. "Alert residents at least 2 h before PM2.5 exceeds 60 µg/m³" passes: it has 2 with h, and 60 with µg/m³. "Improve the air" fails, because it has no number. Vague ones go back for rewrite before 20:30. This is an example of the shape only. Do not copy it, because your statement must use your own user, pain and data source.

**TC5: no keys or tokens.** Export the sheet as CSV from the LMS, then run:

`grep -n -i -E 'key=|token|apikey|[0-9a-f]{32,}' sheet-export.csv`

- `grep` prints lines that match a pattern.
- `-n` adds line numbers.
- `-i` ignores case, so `TOKEN` also matches.
- `-E` enables extended patterns: `|` means "or", and `{32,}` means 32 or more repeats.

Passing output is nothing. Run `echo $?` straight after: exit code 1 means no match. Failing output shows a line number and the text. The usual cause is a URL containing `apikey=`, or a long hex string pasted into a cell.

:::trap Passing TC5 is not enough
TC5 searches the sheet export only. A key inside a URL you paste is still a key in the sheet, so check each URL before you paste it.
:::

Here is a passing run of TC1 and TC2 on the lab machine, for an imaginary URL.

```term
$ curl -s -o /tmp/r.json -w '%{http_code}' --max-time 15 'https://api.example.test/air/latest'; head -c 1 /tmp/r.json
200{
$ jq -e '.records[0].pm25' /tmp/r.json
42
$ echo $?
0
```

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| curl prints `000` | No answer within 15 s, a mistyped host, or a blocked address | Check the spelling and retry; try the other URL |
| curl prints `200`, but `head -c 1` shows `<` | The source sent an HTML page, not data | This URL fails the ticket. Tell your squad and pick another source |
| `jq -e` prints `null` and exits 1 | The path does not match the response's names | Run `jq 'keys'` and `jq '.[0]'`, then correct the path |
| `jq` says `Cannot index array` | The top level is a list | Add `[0]` after the list name |
| curl prints `401` or `403` | The source needs a key or login | Record "key required: yes" and tell your trainer. Never paste the key |
| Only part of the command runs | An unquoted `&` in the URL split the command | Put the whole URL in single quotes |
| TC5 prints a line with `apikey=` | A URL holding a key was pasted into a cell | Delete it and record "key required: yes" |
| TC4 returns your statement | The outcome has no number or no unit | Rewrite the outcome with a measurable number and unit |
| TC3 prints `6` | The header row was counted | Remove the header and count again |

### Defend it in the viva

**1. Why check the URLs before writing any code?**

:::answer Model answer
The fetching work in T05 expects JSON from a live address. A dead or HTML-only source blocks that work, and the team would find out late. A live check now tests the one thing the later work depends on, so it is the cheapest point to catch the failure.
:::

**2. Why is a 200 status code alone not enough?**

:::answer Model answer
A 200 only says the request succeeded. It does not prove the body is JSON or that the field we need exists. So the check reads the first byte to confirm JSON, then uses `jq -e` to confirm the recorded path returns a non-null value.
:::

**3. What is the trade-off between a source that needs a key and one that does not?**

:::answer Model answer
A keyed source may hold richer data, but its key is a secret that must stay out of the sheet, the repository and the URLs. An open source is simpler to share, but may lack the field the outcome needs. I would record "key required: yes" honestly and choose the source that can measure the outcome.
:::

**4. Why must the outcome have a number and a unit?**

:::answer Model answer
Without a number and a unit, nobody can say whether the product succeeded. "Alert residents at least 2 h before PM2.5 exceeds 60 µg/m³" can be tested against data. The number sets the target and the unit makes it specific.
:::

**5. What did you personally do, and how do you show it?**

:::answer Model answer
Name the step you owned, such as your own statement or your live curl. Show the exact command, the status code, the path you used and the cell where you recorded it. Describe only what you actually did, and let the output be the proof.
:::

### Check yourself

```quiz
Q: A squad URL returns a 404 page. A teammate says the check is fine because curl finished without an error. What is wrong?
- curl always fails on a 404, so the teammate is wrong that it finished
- The 404 page is HTML, so the check passes only with a jq path
* curl exits 0 on a 404 unless you add --fail, so you must read the status code
- The -s flag hides the error, so nothing can be seen
WHY: curl does not treat a 404 as an error by default. --fail changes that. -s hides the progress meter (and error messages unless you add -S), but it does not change the status code.

Q: You run jq -e '.records[0].aqi' on a file and it prints null. What exit code does jq give?
* 1
- 0
- 4
- 2
WHY: With -e, a null or false final value gives exit code 1. 0 would mean a real value was found, and 4 means no valid result was produced at all.

Q: Which command finds 32 or more hex characters in a sheet export, in any case?
- grep -n token sheet-export.csv
- grep -c hex sheet-export.csv
- grep -n '32' sheet-export.csv
* grep -n -i -E '[0-9a-f]{32,}' sheet-export.csv
WHY: -E enables the {32,} repeat count, -i matches uppercase too, and -n shows line numbers. Searching for the word token or the number 32 misses the hex strings the ticket asks about.
```
