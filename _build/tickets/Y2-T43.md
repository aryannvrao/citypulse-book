### The ticket in plain words

Your squad's CityPulse API already runs in a Docker image, from ticket Y2-T42. The image works, but it has three problems. It is large, so it is slow to download and upload. It rebuilds slowly, because every build starts from scratch. And nobody has ever scanned it for known security holes.

The client's security team will not run an image they cannot audit. They want five things: a slim base image, exact dependency versions, a non-root user (a user with fewer powers than the administrator), a health check, and a vulnerability report that gives an action for every HIGH or CRITICAL finding. The client asks for this because of Log4Shell, a 2021 flaw in a Java logging library that let attackers run their own code on servers that had not been updated.

The ticket has a second half. Developers need to run the API and its Postgres database together with one command on a laptop. Settings must come from environment variables, not from code, so the laptop setup matches what will run in the cloud.

Your job is to make the image smaller and safer, measure the change, document every serious finding, and make the whole stack start from a fresh clone. The trainer will test each claim with a command, so every claim must be something you can run yourself.

### Words you need

| Term | Plain meaning |
|---|---|
| Image | A read-only package holding the app and everything it needs. |
| Container | A running copy of an image. Stopping it does not change the image. |
| Dockerfile | A text recipe that tells Docker how to build an image, one instruction per line. |
| Layer | The result of one Dockerfile instruction. Docker reuses unchanged layers. |
| Build context | The folder Docker can read files from during a build. The dot in `docker build .` names it. |
| Base image | The starting image named in `FROM`, for example `python:3.11.9-slim`. |
| Pin | Fix a version exactly, for example `fastapi==0.115.4`, so the same version is installed every time. |
| Multi-stage build | A Dockerfile with more than one `FROM`. Only the last stage becomes the image. |
| Builder stage | An early stage that installs tools and packages. Its contents are not shipped unless copied. |
| Virtual environment | A folder holding its own copy of Python packages, kept apart from the system. |
| Non-root user | A user with no administrator powers. `USER 10001` runs the container as this user. |
| UID | User ID, a number that identifies a user. `id -u` prints the current user's UID. |
| HEALTHCHECK | An instruction that runs a command on a timer. Docker marks the container healthy or unhealthy from the result. |
| Port publishing | Making a container port reachable from your machine. The flag `-p 8000:8000` does this. |
| Volume | Storage that outlives a container. Compose uses one for the database files. |
| Compose | A tool that starts several containers described in one file, `docker-compose.yml`. |
| Service | One container entry in a Compose file, for example `db` or `api`. |
| depends_on | A Compose setting that controls start order. With `condition: service_healthy`, it waits for a health check. |
| Environment variable | A named value a program reads at start, for example `DATABASE_URL`. |
| DATABASE_URL | The address of the database, including user, password, host, port and name. |
| .env | A file of local values read by Compose. It must never be committed. |
| .env.example | A committed template for `.env`, with placeholder values only. |
| .gitignore | A file that tells Git which paths to leave out of commits. |
| .dockerignore | A file that tells Docker which paths to leave out of the build context. |
| CVE | Common Vulnerabilities and Exposures. A public ID for one known security flaw, such as CVE-2021-44228. |
| Severity | How serious a finding is: LOW, MEDIUM, HIGH or CRITICAL. |
| Trivy | An open-source scanner that lists CVEs in an image. |
| SBOM | Software Bill of Materials. A list of every package inside an image. |
| CycloneDX | A standard file format for SBOMs. |
| Cold build | A build with no cache, run with `--no-cache`, so every step runs. |
| Postgres | The database server that CityPulse uses. |
| pg_isready | A Postgres tool that exits with 0 when the server accepts connections. |
| Tag | A label on an image, after the colon, for example `citypulse-api:hardened`. |
| Pipe `\|` | Sends the output of one command into the next. |
| tee | Shows output on screen and also writes it to a file. |

### How your trainer checks it

The trainer checks six acceptance criteria and runs five test cases. The table shows which test covers which criterion.

| Acceptance criterion | Checked by |
|---|---|
| The PR table shows a smaller size and both cold build times | Compared by hand against T42, with TC1 |
| The hardened container does not run as root | TC2 |
| HEALTHCHECK is defined and the container reaches healthy within 60 s | TC4 (status) and a `docker inspect` check |
| No CRITICAL is undocumented | TC3 |
| A fresh clone, `cp .env.example .env` and `docker compose up` return 200 from `/v1/stats` | TC4 |
| `.env` is gitignored and not committed | TC5 |

The trainer uses the short tag `cp:h` in the test cases. Your image is tagged `citypulse-api:hardened` in the acceptance criteria. Give the same image both names with `docker tag citypulse-api:hardened cp:h`. Both names then point to one image.

**TC1: size.** The steps are `docker build -t cp:h . && docker images cp:h --format '{{.Size}}'`.

- `docker build -t cp:h .` builds the image from the Dockerfile in the current folder and tags it `cp:h`.
- `&&` runs the second command only if the first succeeds.
- `docker images cp:h --format '{{.Size}}'` lists the image and prints only its size column.

Passing output looks like this.

```term
$ docker build -t cp:h . && docker images cp:h --format '{{.Size}}'
#9 naming to docker.io/library/cp:h done
148MB
```

The size, 148MB here, must be smaller than the T42 value. The number in this example is only an illustration. A failing result is a size equal to or larger than T42. The usual cause is that build tools or the pip cache were copied into the runtime stage, or that the builder stage was not separated at all.

**TC2: non-root.** The steps are `docker run --rm cp:h id -u`.

- `docker run --rm` starts a container and deletes it when the command finishes.
- `cp:h` names the image.
- `id -u` prints the numeric user ID the command runs as.

Passing output is a single number that is not zero, for example `10001`. A failing output is `0`. The usual cause is a Dockerfile with no `USER` line, or a `USER` line placed in the wrong stage.

**TC3: scan.** The steps are `docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy image --severity CRITICAL cp:h`.

- `docker run --rm` runs Trivy in a temporary container.
- `-v /var/run/docker.sock:/var/run/docker.sock` gives Trivy access to Docker, so it can read the image on your machine.
- `aquasec/trivy` is the Trivy image.
- `image --severity CRITICAL cp:h` scans the image and shows only CRITICAL findings.

On Git Bash, put `MSYS_NO_PATHCONV=1` in front of the command. Without it, Git Bash rewrites the socket path and Docker cannot find it. On Linux, leave it out.

Passing output lists zero CRITICAL findings, or lists each one, and every listed CVE ID appears in `docs/security/README.md` with an action. A failing output shows a CVE that is not in the README. The usual cause is that the README was not updated after the last scan.

**TC4: compose.** The steps are `cp .env.example .env && docker compose up --build -d && sleep 20 && curl -s localhost:8000/v1/stats && docker compose ps`.

- `cp .env.example .env` creates the real settings file from the template.
- `docker compose up --build -d` builds the images and starts the services in the background.
- `sleep 20` waits 20 seconds so the database and the API can start.
- `curl -s localhost:8000/v1/stats` requests the stats page. `-s` hides the progress meter.
- `docker compose ps` lists both services with their health.

Passing output is JSON from `/v1/stats`, and the `STATUS` column shows `(healthy)` for both `db` and `api`. A failing output is a connection refused error, or `(unhealthy)`, or a JSON error from the API. The usual causes are a wrong host in `DATABASE_URL` (see the troubleshooting table) or a database that was still starting after 20 seconds. The API health check runs every 15 seconds, so `api` can still say `(health: starting)` at the 20-second mark. If so, run `docker compose ps` again a few seconds later.

**TC5: git.** The steps are `git ls-files | grep -x .env`.

- `git ls-files` lists every file Git tracks.
- `|` sends that list to `grep`.
- `grep -x .env` keeps only lines that match `.env` exactly.

Passing output is nothing at all. Failing output prints `.env`, which means the file is committed. Remove it from Git without deleting your copy with `git rm --cached .env`, add it to `.gitignore`, and commit the change. A password that was committed stays in Git history, so change that password as well.

### Do it, step by step

Work in order. Each stage ends with a test. Do not start the next stage until the test passes.

#### Y2-T43.1: record the baseline

**Goal.** Know the size, build time and scan counts of the current image, so you can prove any improvement.

**Stage A: build the baseline with no cache.** Run in Git Bash, from the repository folder.

```bash
time docker build --no-cache -t citypulse-api:before .
```

- `time` is a Bash keyword. It prints how long the command took after it finishes. In PowerShell, use `Measure-Command` instead.
- `docker build` creates the image from the Dockerfile in the current folder.
- `--no-cache` ignores every saved layer, so every step runs. That is what a cold build means.
- `-t citypulse-api:before` names the image.

Expected output ends with a `real` line, for example `real 0m58.214s`. Your number will differ. Write it down.

**Stage B: record the size.**

```bash
docker images citypulse-api:before --format '{{.Size}}'
```

This prints one size, for example `312MB`. Write it down next to the build time.

**Stage C: record the scan counts.**

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy image --severity HIGH,CRITICAL citypulse-api:before | tee docs/security/trivy-before.txt
grep Total docs/security/trivy-before.txt || echo "no Total line: no findings"
```

- The first line scans the image and shows only HIGH and CRITICAL findings. `| tee` shows the report on screen and saves it to `docs/security/trivy-before.txt`. Create the folder first with `mkdir -p docs/security`.
- The second line finds the summary line that Trivy prints, which starts with `Total:` and gives the counts per severity.

The first Trivy run downloads its vulnerability database, so it needs internet access and takes longer. Expected output is a `Total:` line with counts for HIGH and CRITICAL. Trivy prints `Total:` only when it finds something, so on a clean image there is no such line; then record the count as 0.

**Stage test.** The three numbers exist: a build time, a size and a Total line. Commit only the report file in this subtask.

#### Y2-T43.2: pin the dependencies

**Goal.** Every line in `requirements.txt` has `==` and an exact version. Test-only packages move to a second file.

**Stage A: make a clean environment.** A clean virtual environment shows what installs from a fresh start, without packages left over from your machine.

```bash
python -m venv .venv-pin
source .venv-pin/bin/activate
pip install -r requirements.txt
pip freeze
deactivate
```

- `python -m venv .venv-pin` creates a new environment in the folder `.venv-pin`.
- `source .venv-pin/bin/activate` switches your shell to use that environment. On Git Bash on Windows, use `source .venv-pin/Scripts/activate` instead.
- `pip install -r requirements.txt` installs what the file names.
- `pip freeze` prints every installed package as `name==version`, including packages that other packages need.
- `deactivate` switches back to your normal Python.

Expected output lines look like `fastapi==0.115.4`. Do not copy every line blindly. Pin the versions your team tested. For scikit-learn, use the version the model was trained with, from your squad's notes. A wrong version can stop the saved model loading.

**Stage B: edit the file.** Each line becomes `name==version`. Move `pytest` and `httpx` out of `requirements.txt` into `requirements-dev.txt`. They are needed for tests, not for running the server. Start `requirements-dev.txt` with the line `-r requirements.txt`, so installing the dev file also installs the runtime packages that pytest needs. Also add `.venv-pin/` to `.gitignore` so the test environment is never committed.

**Stage C: pin the base image.** Use the base tag your T42 Dockerfile used, or the one your team agrees, and make sure it is a patch-level tag with three numbers, such as `python:3.11.9-slim` (the example used in this guide). Check that Docker can fetch it.

```bash
docker pull python:3.11.9-slim
```

Expected output ends with `Status: Downloaded newer image` or `Status: Image is up to date`.

**Stage test.** The first command must print nothing. It finds lines that are not comments or blank, and that have no `==`. The second installs the test tools and runs the tests.

```bash
grep -vE '^\s*(#|$)' requirements.txt | grep -v '=='
pip install -r requirements-dev.txt && python -m pytest -q
```

Expected output: the first command prints nothing. The second ends with a line such as `12 passed`. If it prints a failure, the pin for one package is wrong.

#### Y2-T43.3: write the Dockerfile in two stages

**Goal.** A builder stage makes the virtual environment. A runtime stage copies only that environment and the code, runs as user 10001, and checks its own health.

Build the file in stages. Type each stage yourself and save it into one `Dockerfile`. Do not paste a whole file from elsewhere.

**Stage A: the builder.** The first `FROM` names the builder with `AS`.

```dockerfile
FROM python:3.11.9-slim AS builder
COPY requirements.txt .
RUN python -m venv /opt/venv && /opt/venv/bin/pip install --no-cache-dir -r requirements.txt
```

- `FROM ... AS builder` starts the first stage and names it, so a later line can copy from it.
- `COPY requirements.txt .` copies only the requirements file. It comes before the code, so this layer stays cached when code changes.
- `RUN python -m venv /opt/venv` creates the virtual environment at `/opt/venv`.
- `&& /opt/venv/bin/pip install ...` runs the install with the pip that belongs to that environment. `&&` runs it only if the first command succeeded.
- `--no-cache-dir` stops pip keeping a download cache, which would make the layer bigger.

Expected output when you build later: a line saying the install step `DONE`.

**Stage B: the runtime stage starts clean.** A second `FROM` starts from an empty base again. Nothing from the builder comes with it.

```dockerfile
FROM python:3.11.9-slim
ENV PATH="/opt/venv/bin:$PATH" PYTHONUNBUFFERED=1
COPY --from=builder /opt/venv /opt/venv
WORKDIR /app
```

- `FROM python:3.11.9-slim` with no `AS` starts the final stage. Only this stage becomes the image.
- `ENV PATH=...` puts `/opt/venv/bin` first, so `python` and `uvicorn` come from the virtual environment. `PYTHONUNBUFFERED=1` makes logs appear at once.
- `COPY --from=builder /opt/venv /opt/venv` copies only the environment from the builder. The compiler and the pip cache stay behind.
- `WORKDIR /app` sets the working folder for the next lines and creates it.

**Stage C: the code, owned by the app user.** The code folders must be owned by user 10001, or the app cannot write files it needs.

```dockerfile
COPY --chown=10001:10001 api/ api/
COPY --chown=10001:10001 src/ src/
COPY --chown=10001:10001 models/ models/
```

The folder names above (`api/`, `src/`, `models/`) are only examples. Use the folder names that are really in your repository, and copy only what the app needs at run time. `--chown` sets the owner and group of copied files. A `COPY` without it leaves files owned by root.

**Stage D: the user and the health check.**

```dockerfile
USER 10001
HEALTHCHECK --interval=15s --timeout=3s CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/v1/health', timeout=2)"
CMD ["uvicorn", "api.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

- `USER 10001` runs everything after this line, and the container's process, as user 10001.
- `HEALTHCHECK --interval=15s --timeout=3s` runs the check every 15 seconds. Each check must finish within 3 seconds.
- `CMD python -c "..."` runs Python with a one-line program. `urlopen` requests `/v1/health` on localhost, inside the container. If the request fails or the server returns an error code, Python raises an error and exits non-zero. Docker then marks the container unhealthy.
- The check uses Python because `python:3.11.9-slim` does not normally include `curl`.
- `CMD ["uvicorn", ...]` starts the server. `--host 0.0.0.0` lets traffic from outside the container reach it.

Optionally add `--start-period=10s` to the `HEALTHCHECK` line, to ignore failures while the app starts. If you add it, be ready to explain it in the viva.

**Stage D2: keep the build context small.** Create a `.dockerignore` file next to the Dockerfile. It lists paths Docker must not send into the build, so they cannot leak into an image and builds start faster. Example lines, one per line:

```text
.git
.env
.venv*
__pycache__/
docs/
```

Each line is a path pattern. `.env` here matters: real passwords must never be baked into an image. Add what else your repository holds that the app does not need. Do not ignore a folder your `COPY` lines use.

**Stage E: build and test.**

```bash
docker build -t citypulse-api:hardened .
docker run --rm citypulse-api:hardened id -u
```

Expected output of the second command: `10001`. If you see `0`, the `USER` line is missing or placed in the wrong stage. If the build fails on a `COPY` line, check the folder names against the folders on disk.

**Stage test.** Run `docker history citypulse-api:hardened` in Y2-T43.4, where you compare sizes. Here, the build and the `id -u` check are enough.

#### Y2-T43.4: build, compare and scan

**Goal.** Measure the hardened image, prove that build tools are gone, and fix what can be fixed.

**Stage A: cold build time and size.** Repeat stage A and stage B of Y2-T43.1 with the new tag.

```bash
time docker build --no-cache -t citypulse-api:hardened .
docker images citypulse-api:hardened --format '{{.Size}}'
```

Write both numbers in the before and after table, which you will use in the PR.

**Stage B: check the layers.**

```bash
docker history citypulse-api:hardened
```

`docker history` lists each layer, the instruction that made it and its size. Look for `pip` or `apt` steps with large sizes in the runtime stage. Those layers should not be there. The layers from the builder appear only as the single `COPY --from=builder` layer that holds `/opt/venv`.

**Stage C: scan and read the Total line.**

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy image --severity HIGH,CRITICAL citypulse-api:hardened | tee docs/security/trivy-$(date +%F).txt
```

`$(date +%F)` prints today's date, for example `2026-11-17`, and puts it in the file name. Look at the table. Each row names a package, a CVE, a severity, the installed version and a fixed version if there is one.

**Stage D: bump fixable versions.** For each row with a fixed version, raise the pin in `requirements.txt`, or move the base image to a newer patch tag. Then rebuild and run the tests again.

```bash
docker build -t citypulse-api:hardened .
pip install -r requirements-dev.txt && python -m pytest -q
```

A bump can break the model, so the test run is not optional. If the tests fail after a scikit-learn bump, go back to the training version.

**Stage test.** Rerun the scan. Every fixable HIGH or CRITICAL row should be gone. The remaining rows go into the README in Y2-T43.5.

#### Y2-T43.5: the scan report, the SBOM and the decisions

**Goal.** Commit the evidence, and give each remaining finding one decision.

**Stage A: the SBOM.** Trivy can print the SBOM to standard output. Redirecting that output to a file avoids mounting folders, which is simpler on Git Bash.

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy image --format cyclonedx citypulse-api:hardened > docs/security/sbom.cdx.json
```

`--format cyclonedx` writes the CycloneDX format. The `>` sends the output into `docs/security/sbom.cdx.json`. Test it with `python -m json.tool docs/security/sbom.cdx.json > /dev/null && echo valid`. Expected output: `valid`.

**Stage B: list only fixable findings.** `--ignore-unfixed` hides findings that have no fixed version. Use it to check what you can still fix, but keep the full list for the README. Add it to the same scan command as before, for example `... aquasec/trivy image --ignore-unfixed --severity HIGH,CRITICAL citypulse-api:hardened`.

**Stage C: write the decisions table.** Create `docs/security/README.md` with a header and one row per remaining HIGH or CRITICAL CVE. The columns below are your structure. The row is a fictional example, so replace it with your real findings.

```text
| CVE | Package | Severity | Action | Reason |
|---|---|---|---|---|
| CVE-2099-0001 | example-lib 1.2.3 | HIGH | no fix available | Upstream has no release. Not reachable from the API routes. Recheck on every release. |
```

Allowed actions are `fixed`, `accepted with reason`, and `no fix available`. Every row needs a reason. The trainer checks that every CRITICAL in the scan appears in this file.

**Stage test.** Count the CVE IDs in the scan report and in the README. The trainer runs the same scan, so an ID in the scan but not in the README fails TC3.

```bash
grep -oE 'CVE-[0-9]+-[0-9]+' docs/security/trivy-*.txt | sort -u
grep -oE 'CVE-[0-9]+-[0-9]+' docs/security/README.md | sort -u
```

Both lists must match for every CRITICAL row.

#### Y2-T43.6: the compose file

**Goal.** One command starts Postgres and the API, and the API reads its database address from an environment variable.

**Stage A: the settings template.** Create `.env.example`. It holds placeholders only.

```text
POSTGRES_USER=citypulse
POSTGRES_PASSWORD=change-me-locally
```

Each line is a `NAME=value` pair. Compose reads the real `.env` and substitutes `${NAME}` in `docker-compose.yml`. Commit `.env.example`. Never commit `.env`.

**Stage B: the gitignore rule.** Add one line to `.gitignore`: `.env`. Then check that Git ignores it.

```bash
git check-ignore -v .env
```

Expected output is the `.gitignore` line that matches, with the file name `.env`. If nothing prints, the rule is missing or misspelt.

**Stage C: the database service.** Start a `docker-compose.yml` file with the `db` service. Indentation uses spaces, not tabs. Each level is two spaces.

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: citypulse
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./sql/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
```

- `services:` starts the list of containers. Each name below it is one service.
- `image: postgres:16-alpine` uses the official Postgres 16 image on Alpine Linux.
- `${POSTGRES_USER}` is replaced with the value from `.env` before Compose starts anything.
- `pgdata:/var/lib/postgresql/data` stores database files in a named volume, so data survives a container restart.
- The second volume copies your init SQL into a folder that Postgres runs on the first start. `:ro` makes it read-only. Use the path your squad uses, under `sql/` or `db/`.

**Stage D: the health check for the database.** Add this under `db`, at the same level as `volumes`.

```yaml
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d citypulse"]
      interval: 5s
      retries: 10
```

`pg_isready` exits with 0 when Postgres accepts connections. The double `$$` stops Compose replacing the variable, so the shell inside the container reads it. `depends_on` needs this check to wait properly.

**Stage E: the API service.** Add an `api` service at the same level as `db`.

```yaml
  api:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/citypulse
    depends_on:
      db:
        condition: service_healthy

volumes:
  pgdata: {}
```

- `build: .` builds the image from the Dockerfile in this folder.
- `ports: "8000:8000"` publishes port 8000, the same as `-p 8000:8000`.
- The host in `DATABASE_URL` is `db`, the service name. Inside the Compose network, `db` reaches the Postgres container. `localhost` would mean the API container itself.
- `depends_on` with `condition: service_healthy` waits for the `db` health check before starting the API.
- `volumes: pgdata: {}` at the bottom declares the named volume.

Your API code must read `DATABASE_URL` from the environment. The exact call depends on your code. Common forms are `os.environ["DATABASE_URL"]` and `os.getenv("DATABASE_URL")`. If the variable is missing, the first form raises an error, which is easier to notice.

### Defend it in the viva

**1. Why does the runtime stage start from a fresh base image instead of the builder?**

:::answer Model answer
The runtime stage is the only stage that becomes the shipped image. Starting it from a clean base means the compiler, the pip cache and build tools from the builder are not in the image, even though the builder used them. Copying with `COPY --from=builder` takes only the finished virtual environment. This makes the image smaller, and it removes tools an attacker could use if they got into the container.
:::

**2. What is the trade-off of pinning exact versions?**

:::answer Model answer
Exact pins make builds repeatable. The same code installs the same packages, so a test result today still holds next month. The cost is that pins do not receive security fixes automatically. You must rescan with Trivy on each release, raise the pins that have a fix, and rerun the tests after each change. A pin that is never updated is a known risk, which is why the scan report exists.
:::

**3. What did you personally do in this ticket?**

:::answer Model answer
Name the subtask you owned, the commits you made, and the command that proved each one. A strong answer is specific: which stage of the Dockerfile you wrote, which line you explained in the comment, and which output you checked, for example the `id -u` result. Do not describe work you did not do. The trainer checks commits, so your answer should match them.
:::

**4. How does the API find Postgres in compose, and why does the health condition matter?**

:::answer Model answer
Compose puts both services on a private network where each service name is a host name. The API uses `db` in `DATABASE_URL`, not `localhost`, because `localhost` inside the API container means the API container itself. `depends_on` with `condition: service_healthy` waits until `pg_isready` passes. Without the condition, Compose only sets the start order, and the API can start while Postgres is still starting and fail to connect.
:::

**5. A scan shows a CRITICAL finding with no fixed version. What do you do?**

:::answer Model answer
You do not ignore it. You add a row to `docs/security/README.md` with the CVE ID, the package, the severity, the action "no fix available", and a reason. The reason should say whether the vulnerable code is reachable from the API, and when you will check again. The finding is rescanned on each release, because a fix may appear later.
:::
