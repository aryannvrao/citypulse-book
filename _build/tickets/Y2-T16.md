### The ticket in plain words

Deliverable Y2-D02 is a defence. Your squad's CityPulse data pipeline is on trial. A pipeline is a set of scripts that run in a fixed order: fetch data from a source, clean it, load it into a database, then run data-quality (DQ) checks that decide whether the data is good enough to use. On the day, your trainer takes the code from a fresh copy on GitHub and runs it. They run it a second time to prove that the second run does not double the data. Then they break the data on purpose to show that the checks catch it. Finally they question every member, quietest first.

The second half of the ticket starts the cloud part of the course. Before any cloud lab, you lock down your own AWS account. Capital One showed in 2019 what happens when access is too broad. A misconfigured firewall and a role with far too many permissions let an outsider reach the personal data of over 100 million people. So you turn on multi-factor authentication (MFA, a second proof of identity such as a code from an app) for the root account, which is the all-powerful login made when the account was created. You set a budget alarm that emails you when spending goes up. You create a day-to-day admin user, and you set up the command-line tool with that user. The course rule is short: no alarm, no cloud lab.

### How your trainer checks it

The ticket has six acceptance criteria (AC). Each one is either a test case you can run or a judgement your trainer makes. Here is what each one means for you.

- **AC1, fresh clone runs twice.** Checked by TC1 below. Both runs must exit 0, and the fact-table count must be the same.
- **AC2, sabotage fails then passes.** Checked by TC2. A blocking DQ failure must give a non-zero exit, and the reload must give exit 0.
- **AC3, rubric total of at least 60%.** A trainer score for the whole squad. You cannot run it. You influence it by giving a clear, correct defence and answering questions well.
- **AC4, one correct individual answer.** Your trainer records each answer as correct, partial or incorrect. Section 6, Y2-T16.3, shows how to prepare.
- **AC5, v0.3.0 exists.** Checked by TC3.
- **AC6, cloud setup.** Checked by TC4 and TC5. Without them, cloud lab access stays locked.

The trainer runs five test cases. Each one below breaks the steps into parts, shows passing output and shows failing output with its usual cause.

#### TC1: fresh clone, run twice, same count

The trainer runs this on the lab machine, which is Linux. You can run it on your laptop in Git Bash to rehearse. It is one long line of steps joined by `&&`, so each step runs only if the one before it succeeded.

```bash
cd /tmp && rm -rf d02 && git clone https://github.com/citypulse-y2/citypulse-<squad>.git d02 && cd d02 && python3 -m venv .venv && . .venv/bin/activate && pip install -e . && cp .env.example .env && scripts/run_pipeline.sh && sqlite3 citypulse.db 'SELECT COUNT(*) FROM fact_air_quality' && scripts/run_pipeline.sh && sqlite3 citypulse.db 'SELECT COUNT(*) FROM fact_air_quality'
```

The parts, in order:

- `cd /tmp` moves into a temporary folder. The test starts in a folder with nothing in it. On Git Bash, `/tmp` is a folder inside your Windows profile, which is fine for rehearsal.
- `rm -rf d02` deletes an old folder called `d02`. `-r` means "including its contents" and `-f` means "without asking". Run it only inside `/tmp`, because it cannot be undone.
- `git clone <url> d02` copies the squad repository from GitHub into a new folder called `d02`. This is the "fresh" part. Files that exist only on your laptop are not copied.
- `cd d02` moves into the new copy.
- `python3 -m venv .venv` creates a virtual environment in a folder called `.venv`. It keeps this project's packages apart from the rest of your computer. On Git Bash, use `python -m venv .venv` if `python3` is missing.
- `. .venv/bin/activate` switches the shell to that environment. On Git Bash the script is in another place, so use `source .venv/Scripts/activate` there.
- `pip install -e .` installs the project. `pip` is the package installer. `-e` links the installed copy to your code. `.` means "the project in this folder".
- `cp .env.example .env` copies the example settings to `.env`, the file the code reads for local settings.
- `scripts/run_pipeline.sh` runs the whole pipeline once. On Git Bash, if you see `Permission denied`, run `bash scripts/run_pipeline.sh` instead.
- `sqlite3 citypulse.db 'SELECT COUNT(*) FROM fact_air_quality'` opens the database file and counts the rows in the fact table. It prints one number. Without the `sqlite3` tool, use `python3 -c "import sqlite3; print(sqlite3.connect('citypulse.db').execute('SELECT COUNT(*) FROM fact_air_quality').fetchone()[0])"`.
- The last two parts run the pipeline a second time and count again.

**Passing output.** Each `run_pipeline.sh` ends without an error message. Check its exit code with `echo $?` straight after it. The two counts are printed, and they are the same number.

**Failing output and usual causes.**

- `sqlite3: command not found`. The tool is not installed. Use the Python command above.
- `scripts/run_pipeline.sh: Permission denied`. The file is not marked as executable in Git. Fix it with `git update-index --chmod=+x scripts/run_pipeline.sh`, then commit the change.
- `ModuleNotFoundError`. The virtual environment is not active, or `pip install -e .` did not run.
- `no such table: fact_air_quality` (sqlite3 prefixes this with `Error:` or `Parse error:`, depending on its version). The load stage did not write to `citypulse.db`, or it wrote to a different file.
- The two counts differ. The load adds rows each time instead of replacing them, so it is not idempotent. Section 6, Y2-T16.1, explains the fix.

#### TC2: sabotage fails, then reload passes

The trainer runs `scripts/dq_sabotage.sh` on the lab machine. The script damages today's rows, runs the DQ checks, which must fail, and then reloads the data, which must pass. Run it on your laptop with the exit code printed:

```bash
scripts/dq_sabotage.sh; echo "exit=$?"
```

The parts: `scripts/dq_sabotage.sh` runs the script. The semicolon starts the next command whatever the first one returned. `echo "exit=$?"` prints the exit code of the command just before it. `$?` is a special bash variable that holds the last exit code.

**Passing output.** The script reports the DQ stage first: `FAIL` and exit code 1, which is the expected result because the sabotage is meant to fail the checks. Then it reloads and re-checks, and reports `PASS` and exit code 0. Those two codes are the ones your script prints for each stage. The `exit=` line from your own `echo` shows the script's final status, which should be 0 once the reload passed, because the script handles the expected failure itself.

**Failing output and usual causes.**

- The sabotage stage prints `FAIL` but reports exit code 0. The DQ entry point prints the failure and then returns nothing, so Python returns `0`. The fix is to return `1` from `main()` and call `sys.exit(main())`, as explained in Section 6, Y2-T16.1.
- The reload stays at `FAIL`. The sabotaged rows were not removed or the reload did not run. Read the first lines of the script output to see which stage stopped.
- The script stops at the first `FAIL` and never runs the reload. That is `set -e` working as designed. The script must wrap the expected failure in `if`, so the reload can run.

#### TC4: the CLI shows an IAM user, not root

The student shares their screen and runs the command. The trainer reads the ARN.

```bash
aws sts get-caller-identity
```

It prints JSON like this, with fictional values:

```text
{
    "UserId": "AIDEXAMPLEEXAMPLE",
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/example-admin"
}
```

The parts: `aws` is the CLI program. `sts` is the Security Token Service, the part of AWS that knows who is calling. `get-caller-identity` asks "who am I?" It reads the access key that `aws configure` stored on your laptop, so the answer shows which identity your CLI is using.

**Passing output.** The `Arn` ends in `:user/<name>-admin`, which is your IAM user. It does not end in `:root`.

**Failing output and usual causes.**

- `Arn` ends in `:root`. The CLI is still using root credentials. Run `aws configure` again with the access key of your IAM user, and delete any root access key.
- `Unable to locate credentials`. `aws configure` was never run, or the key file is in a different place.
- `InvalidClientTokenId` or `SignatureDoesNotMatch`. The access key or secret was copied wrongly. Create a new key for the IAM user and configure it again.
- `InvalidClientTokenId` can also mean the access key was made inactive or deleted in the console. `get-caller-identity` needs no permissions, so a permissions error here is not the cause.

Before screen sharing, close any window that shows the secret access key. The ARN is the only part the trainer needs.

#### Y2-T16.1: Check the fresh clone and the sabotage run

**Goal.** Before 09:00, you know that `main` is green, and that both scripts work from a clean copy. You are not the trainer, but you rehearse exactly what the trainer runs.

**Technique first: exit codes.** Every command returns a number when it ends. Try these in Git Bash.

```bash
true; echo "exit=$?"
false; echo "exit=$?"
```

The first line prints `exit=0`, because `true` succeeds. The second prints `exit=1`, because `false` fails. A script decides what to do from these numbers, not from the words printed on screen. Stage 3 uses this.

**Stage 1: check that `main` is green.** Run this on your laptop:

```bash
gh run list --branch main --limit 3
```

`gh run list` shows recent CI runs. `--branch main` limits the list to `main`. `--limit 3` shows the last three. Expected output: three lines, the newest with a `completed` status and `success`. If the newest says `failure`, fix that first, because the trainer will see it. The exact layout of the output can differ a little between a terminal and a pipe, so read the status and result words, not the column positions.

**Stage 2: a small idempotency example.** A load is idempotent when running it twice leaves the same rows. The trick is a key: each row has an identity, and a second load replaces the row instead of adding one. This test uses only the standard library and an in-memory database, so it needs no files.

```python test
import sqlite3

def load_once(conn, rows):
    conn.execute("CREATE TABLE IF NOT EXISTS fact (station TEXT, day TEXT, pm25 REAL, PRIMARY KEY (station, day))")
    conn.executemany("INSERT OR REPLACE INTO fact VALUES (?, ?, ?)", rows)
    conn.commit()

def count(conn):
    return conn.execute("SELECT COUNT(*) FROM fact").fetchone()[0]

conn = sqlite3.connect(":memory:")
batch = [("S1", "2026-01-01", 12.5), ("S2", "2026-01-01", 9.0)]
load_once(conn, batch)
first = count(conn)
load_once(conn, batch)
second = count(conn)
assert first == 2
assert second == 2
assert first == second
```

Line by line: `PRIMARY KEY (station, day)` makes each pair unique. `INSERT OR REPLACE` writes a row, and if the key already exists it replaces the old row. `executemany` runs the insert once per row. `conn.commit()` saves the change. `count` returns the number of rows. The batch goes in twice, and the count stays at 2. The three `assert` lines check that the count is 2, twice, and that the two counts match. If the insert were a plain `INSERT`, the second load would fail on the key, and if there were no key at all, the count would become 4.

Run the check on your own loader, not on this example. The point is the pattern: the key, and `INSERT OR REPLACE` or an equivalent delete-then-insert for the same period.

**Stage 3: make the DQ failure reach the shell.** A blocking check must return a non-zero exit code when it fails. The usual bug is a function that prints `FAIL` and then returns nothing. Here is the logic in a small trace, which you can step through.

```trace
TITLE: Why a failed DQ check must end with exit code 1
CODE:
checks = {"no_null_ids": 0, "in_range": 2}
failures = 0
for name, bad in checks.items():
    if bad > 0:
        print("FAIL", name)
        failures += 1
if failures:
    raise SystemExit(1)
print("PASS")
STEPS:
1 :: checks={"no_null_ids": 0, "in_range": 2}; failures=unset :: The check counts are set. Each name is paired with its count of bad rows.
2 :: checks={"no_null_ids": 0, "in_range": 2}; failures=0 :: The failure counter starts at zero.
3 :: name="no_null_ids"; bad=0; failures=0 :: The loop takes the first check.
4 :: name="no_null_ids"; bad=0; failures=0 :: Zero bad rows is not more than zero, so the body is skipped.
3 :: name="in_range"; bad=2; failures=0 :: The loop moves to the second check.
4 :: name="in_range"; bad=2; failures=0 :: Two bad rows, so the test is true.
5 :: name="in_range"; bad=2; failures=0 :: The failure is printed with its name.
6 :: name="in_range"; bad=2; failures=1 :: The counter records one failure.
7 :: failures=1 :: A non-zero counter means the gate must block.
8 :: failures=1 :: SystemExit(1) ends the program with exit code 1, so the shell sees a failure.
```

Read the animation as: the loop checks each rule, the counter records any failure, and the last `if` turns the counter into an exit code. Your DQ entry point must do the same. `main()` returns `1` on any failure, and the module calls `sys.exit(main())`. Without that, the shell sees `0`, and the sabotage run looks like a pass.

Test this stage by running the sabotage script on your laptop and reading the output:

```bash
scripts/dq_sabotage.sh; echo "exit=$?"
```

Expected output: a `FAIL` line with exit code 1 for the sabotaged stage, then a `PASS` line with exit code 0 after the reload, and a final `exit=0` from your `echo` if the script handles the expected failure itself.

**Stage 4: the fresh clone.** Run TC1 in `/tmp` on your laptop, as in section 4. If it fails, use the table in section 4 to find the cause, fix it on a branch, merge it through a PR and run again from a new clone. Never test on the folder where you develop, because it may hold files that a fresh clone would not have.

#### Y2-T16.4: Review comments, CHANGELOG, tag and release

**Goal.** Every review comment from the trainer becomes an Issue. Each fix goes through a PR. The CHANGELOG has a `[0.3.0]` section. The tag `v0.3.0` points at the merged commit, and a GitHub release uses the same notes.

**Technique first: annotated tags and awk.** A tag names one commit. An annotated tag also stores a message, who made it and when. Make a practice tag in a throwaway repository, not in your squad's, if you want to try it. The real command is:

```bash
git tag -a v0.3.0 -m 'D02: data ingestion & SQL pipeline'
```

`-a` creates an annotated tag. `v0.3.0` is the name. `-m` gives the message in quotes, so the `&` is safe. Check it with `git show --no-patch v0.3.0`. Expected output: the tagger, the date and the message. Do not run it yet, because the tag must point at the merged commit.

`awk` reads text line by line and can print the lines between two markers. Test it on a small example before you use it on the CHANGELOG:

```bash
printf 'a\n## [0.2.0]\nx\n## [0.3.0]\ny\n' | awk '/^## \[0\.3\.0\]/{f=1;next} /^## \[/{f=0} f'
```

Expected output: `y`. The first rule turns printing on at the `0.3.0` heading and skips that heading. The second rule turns it off at any other `##` heading. The last `f` prints each line while printing is on.

**Stage 1: turn each review comment into an Issue.** For each comment, run this on your laptop:

```bash
gh issue create --repo citypulse-y2/citypulse-<squad> --title "Trainer review: <short name>" --body "<what is wrong, where, and how to check it>"
```

The parts: `gh issue create` makes an Issue. `--repo` names the repository. `--title` and `--body` are the text, in quotes. Expected output: the link to the new Issue. Write the body so that someone else can check the fix without asking you.

**Stage 2: fix each Issue in a PR.** Create a branch, make the fix and open the PR:

```bash
git switch -c y2-t16-<your-name>-d02-fixes
git add <the files you changed>
git commit -m "fix(pipeline): exit non-zero when a blocking check fails"
git push -u origin y2-t16-<your-name>-d02-fixes
gh pr create --fill
```

`git switch -c` makes a new branch. `git add` stages named files, so you do not commit by accident. `git commit -m` saves with a message. `git push -u` sends the branch to GitHub. `gh pr create --fill` opens a PR, using the commit message as the title. Expected output: the PR link. A squad-mate must approve it before the merge, and you must not merge your own PR.

**Stage 3: write the CHANGELOG entry.** Find the existing heading format first:

```bash
grep -n "0.3.0" CHANGELOG.md
```

Expected output: the heading line, such as `12:## [0.3.0] - <date>`. Use the same heading style for your entry. Write the notes in your own words. Each line should say what changed and why, and link to the Issue or PR where it helps.

**Stage 4: tag the merged commit.** When `main` holds the final fixes and the CHANGELOG, switch to `main` and pull it. Then create and push the tag:

```bash
git switch main
git pull
git tag -a v0.3.0 -m 'D02: data ingestion & SQL pipeline'
git push origin v0.3.0
```

`git pull` brings the merged code into your copy. `git push origin v0.3.0` sends the tag to GitHub. Expected output: a line showing the tag was pushed to `origin`.

**Stage 5: create the release with the CHANGELOG notes.** Keep the notes file outside the repository, so it is never committed. Save it one folder up, then create the release:

```bash
awk '/^## \[0\.3\.0\]/{f=1;next} /^## \[/{f=0} f' CHANGELOG.md > ../notes-0.3.0.md
gh release create v0.3.0 --repo citypulse-y2/citypulse-<squad> --title "v0.3.0" --notes-file ../notes-0.3.0.md
```

`--notes-file` takes the release text from a file. Expected output: the release link. Test it with TC3 in section 4. If the notes file is empty, the awk pattern does not match the heading, so check Stage 3 again.

Open `../notes-0.3.0.md` before you publish. If your CHANGELOG ends with link lines such as `[0.3.0]: https://...`, awk copies them into the notes too, so delete those lines from the notes file.

#### Y2-T16.5: Root MFA and the budget alarm

**Goal.** The root account has an MFA device assigned, and a monthly budget with email alerts exists.

**Technique first: why MFA.** A password can be guessed, copied or leaked. An MFA device adds a code that changes every 30 seconds. Someone who has only your password cannot sign in. The root account can change anything, so it needs this protection most.

**Stage 1: sign in to root.** Sign in with the root email and password the course gave you. Never share them, and never type them into a squad document. The sign-in is done by you, on the AWS site, in your own browser.

**Stage 2: assign an MFA device.** Open the account menu, choose Security credentials, then the Multi-factor authentication (MFA) section, then Assign MFA device. Choose an authenticator app. Scan the code with the app, then enter two codes that the app shows one after another. Expected result: the device is listed under MFA, with a name you chose.

**Stage 3: create the budget.** In the console search box, type Budgets, and open Billing and Cost Management, then Budgets. Choose to create a budget, then choose Customize (advanced), because the simple template does not let you pick 80% and 100%. Choose a cost budget with a monthly period. Enter the amount: the ticket gives ₹500 and US$5. AWS budgets are normally in US dollars, so enter 5 unless the console offers rupees, then enter 500. Say which one you used in the viva. Add two alert thresholds, at 80% and 100% of the budget, each sent by email. Expected result: the budget is listed with both thresholds.

#### Y2-T16.6: The IAM admin user

**Goal.** An IAM user called `<name>-admin` exists, with console sign-in, MFA on that user, and admin permissions. You then sign out of root. You never create root access keys.

**Technique first: IAM users and least privilege.** IAM gives each person or program its own identity. A user has a name, a password for the console and optional access keys for the CLI. A policy lists what the user may do. An admin user has broad permissions, which is why it has its own name, its own MFA and its own password, separate from root. You use the admin user for daily work, so that the root login is rarely used.

**Stage 1: create the user.** In the console, open IAM, then Users, then Create user. Enter the name `<name>-admin`, using your own name. Choose to give console access. Set a custom password and untick the option that makes you change it on first sign-in, unless your trainer asks you to keep it. Expected result: the user appears in the Users list.

**Stage 2: attach the admin permission.** Choose to attach policies directly, then search for the managed policy AdministratorAccess and select it. Expected result: the policy shows on the user's Permissions tab.

**Stage 3: give the user MFA.** Open the user, then Security credentials, then assign an MFA device, as in Y2-T16.5. Expected result: the user's MFA device is listed.

**Stage 4: sign out of root.** Sign out of the root session. Then sign in with the IAM user at the account's sign-in page, using the account ID or alias shown in the console. Expected result: the console shows your IAM user name at the top right, not the root email.

Never create an access key for the root account. The root account's Security credentials page offers this option. Do not use it.

#### Y2-T16.7: Install and configure the CLI

**Goal.** The AWS CLI on your laptop uses the IAM user, and `aws sts get-caller-identity` shows the ARN ending `:user/<name>-admin`.

**Technique first: credentials and the CLI.** The CLI reads an access key and secret from a local file, usually `C:\Users\<you>\.aws\credentials` on Windows. These keys are as powerful as the user they belong to. Keep them out of Git, out of the squad chat and out of screenshots.

**Stage 1: install the AWS CLI.** Download the Windows installer from the official AWS CLI page, then run it. Close and reopen Git Bash after the install. Then run:

**Stage 2: create an access key for the IAM user.** Sign in as the IAM user, not as root. The command asks four questions. Enter the access key ID, then the secret access key, then the default region, such as `ap-south-1` for Mumbai, then the default output format, `json`. Expected result: the command returns to the prompt with no error.

### Defend it in the viva

The trainer asks five questions. Each model answer gives the reasoning. Your own answer must use your own commits and your own checks.

**1. Why must the second run leave the count unchanged?** This is the "why" question.

:::answer Model answer
A pipeline that runs on a schedule, or is run again after a failure, must not double the data. If the load is idempotent, the second run replaces the same rows, so the count stays the same. Without that, every retry inflates the facts, and the reports give wrong numbers. The trainer tests this by running the pipeline twice from a fresh clone and comparing the counts.
:::

**2. Why does the pipeline stop on a blocking DQ failure, instead of loading the rows with a warning?** This is the trade-off question.

:::answer Model answer
Stopping protects the reports. Bad rows that reach the fact table can change every query that reads them, and it is hard to remove them later. The cost of stopping is delay: the data arrives late until someone fixes the cause. A warning keeps the data flowing, but the people reading it may not notice the warning. The course chooses blocking for the checks that protect the client's answers, and a squad can discuss which checks should block.
:::

**3. What did you personally build or check in this ticket, and where can I see it in Git?** This is the "what you did" question. Replace the model answer with your own facts.

:::answer Model answer
Answer with one named fix, one commit, one check you ran and the output you saw. For example: "I changed the DQ entry point so a failure returns 1. The commit is on my branch, and I ran the sabotage script before and after. The shell showed exit 1, then exit 0 after the reload." Name the file, the commit and the output. Do not describe work you did not do. If a teammate did a part, say so, and say what you checked in it.
:::

**4. Why use an IAM admin user for daily work, and not the root account?** This is the "why" question about cloud security.

:::answer Model answer
The root account can do anything in the account, and it cannot be restricted by policy. If its password or key leaks, the whole account is exposed. An IAM admin user has broad permissions, but it can be given MFA, disabled or limited, and its actions are recorded under its own name. Daily work on the user, with root kept for the rare tasks that need it, follows least privilege and leaves a clearer audit trail.
:::

**5. What is the difference between a tag and a release, and why do you create the tag first?** This is the explanation question.

:::answer Model answer
A tag is a fixed name for one commit in Git. A release is a GitHub page built on a tag, with notes and optional files. The tag must come first, because the release is attached to it, and the tag fixes which commit is the version. Creating the release first would attach it to a tag that does not exist yet, so the commit would be chosen by accident. An annotated tag also records who made it and why, which helps in the viva.
:::

### Check yourself

```quiz
Q: The trainer runs scripts/dq_sabotage.sh. The output shows FAIL, but the shell reports exit 0. What is the most likely cause?
- The data was not broken, so the checks passed.
* The DQ entry point prints FAIL and returns nothing, so Python exits with 0.
- The reload was skipped, so the script ended early.
- The sqlite3 command is missing from the lab machine.
WHY: Python exits with 0 unless the program returns or exits with another number. A function that prints FAIL but returns nothing leaves the shell with a pass. A skipped reload or a missing sqlite3 would show a different symptom, such as an error message.

Q: Which command shows the exit code of the last command in bash?
* echo $?
- echo $$
- echo $#
- echo $!
WHY: $? holds the exit code of the last command. $$ is the process id of the shell, $# counts the arguments to a script, and $! is the process id of the last background job.

Q: Which change makes a load safe to run twice?
- Always INSERT new rows and never check for existing keys.
* Give each row a key, and replace the row when it is loaded again.
- Add the current time to the table name on each run.
- Append the same batch a second time and then remove duplicates by hand.
WHY: A key with a replace makes the second load write the same rows, so the count does not change. Adding rows, or changing the table name, or cleaning up by hand after each run leaves the data wrong until someone notices.
```
