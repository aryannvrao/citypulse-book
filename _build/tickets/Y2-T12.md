### The ticket in plain words

CityPulse collects readings about Bengaluru: air quality (PM2.5 and PM10), temperature and humidity. The fetcher from the last ticket saves them as raw CSV files in `data/raw/`. Those files are not yet fit for analysis. They contain duplicate rows, numbers stored as text, gaps where a value is missing, and impossible values such as negative PM2.5 or 60 °C in Bengaluru.

The ticket asks for one command, `python -m citypulse.clean`, that reads every raw file, fixes the types, removes duplicates, applies written rules for gaps and impossible values, and writes one Parquet file to `data/clean/`. Every row or value it drops must be counted, and the counts must be justified in `docs/data-quality.md`.

The story behind it is Google Flu Trends. That service estimated flu activity from search queries and overestimated it for several seasons, and the problems were found only after people had relied on it. The lesson the ticket draws is that analysis on unexamined data fails quietly. A clean, counted and documented step is the defence.

By the end, every chart and model downstream should be built on a file you can explain line by line.

### How your trainer checks it

The ticket has six acceptance criteria. The trainer checks them with the five test cases below and by reading the pull request.

| Criterion | Checked by |
|---|---|
| 1. `python -m citypulse.clean` exits 0 and writes `readings.parquet` in one command | TC1 |
| 2. Duplicates on the key are 0 in the Parquet output | TC2 |
| 3. `df.dtypes` shows `ts_utc` as `datetime64[ns, UTC]`, metrics as `float64`, and `location` and `source` as `category` | TC2, and the `df.dtypes` output in the PR |
| 4. `docs/data-quality.md` shows before and after counts, null percentage per column, removed counts per rule, and one null rule per column | TC4 and a reading check |
| 5. If more than 10% of rows are removed, the PR justifies each rule in writing | Reading the PR |
| 6. Out-of-range values go to `data/clean/quarantine.csv` and are not dropped silently | TC1 (the file exists) and reading the code |

**TC1: the command runs and writes both files.** The trainer runs:

```term
$ python -m citypulse.clean; echo $?; ls -l data/clean/
0
total 20
-rw-r--r-- 1 student student  1894 quarantine.csv
-rw-r--r-- 1 student student 14870 readings.parquet
```

The sizes are an example. Your numbers will differ.

- `python -m citypulse.clean` runs the `clean` module of the `citypulse` package from the repository root.
- The semicolon means "run the next command even if this one failed".
- `echo $?` prints the exit code of the clean command. `0` means success.
- `ls -l data/clean/` lists the folder. The `-l` option shows one line per file with its size.
- Passing: the exit code is `0`, and both `quarantine.csv` and `readings.parquet` are listed. Note that `ls -l` does not show `.gitkeep`, because names starting with a dot are hidden unless you add `-a`.
- Failing with `ModuleNotFoundError: No module named 'citypulse'` means the package is not installed in this environment. Activate it and run `python -m pip install -e .` from the root.
- Failing with `FileNotFoundError` about no CSV files means `data/raw/` is empty or the path is wrong.
- Failing because `quarantine.csv` is missing on a clean run is a real trap. Write the file on every run, even when it has only a header row.

**TC2: no duplicate keys, and the right types.** The trainer runs:

```bash
python -c "import pandas as pd; d=pd.read_parquet('data/clean/readings.parquet'); print(d.duplicated(subset=['ts_utc','location']).sum()); print(d.dtypes)"
```

- `python -c "..."` runs the text in quotes as a short program.
- `import pandas as pd` loads pandas under the short name `pd`.
- `pd.read_parquet(path)` loads the file. The types come back as they were written.
- `d.duplicated(subset=[...])` marks each row that repeats an earlier key. `.sum()` counts the marked rows.
- `print(d.dtypes)` prints the type of each column.

Passing prints `0` first, then the types. The list is trimmed here:

```term
$ python -c "...print(d.duplicated(subset=['ts_utc','location']).sum()); print(d.dtypes)"
0
ts_utc      datetime64[ns, UTC]
pm2_5                   float64
location               category
dtype: object
```

- Failing with a number above 0 means the cleaning did not remove duplicates on the key, often because the dedupe rule ran on the wrong columns or before the rows were stacked.
- Failing with `ts_utc` shown as `object` means the timestamps were never converted with `pd.to_datetime`.
- Failing with `datetime64[us, UTC]` means your pandas chose microseconds. Cast with `astype("datetime64[ns, UTC]")`, because the trainer expects nanoseconds.

**TC3: no impossible PM2.5 values.** The trainer runs:

```bash
python -c "import pandas as pd; d=pd.read_parquet('data/clean/readings.parquet'); print((d.pm2_5<0).sum(), (d.pm2_5>1000).sum())"
```

- `d.pm2_5<0` is a true or false answer for each row. `(...).sum()` counts the true answers.
- The same test is done for values above 1000.
- Passing prints `0 0`.
- Failing with `12 0` or similar means negative values survived. The range rule did not change the table, usually because it assigned to a copy of the DataFrame instead of the table you return.

**TC4: the report is generated and complete.** The trainer runs:

```bash
grep -nE 'Before|After|removed' docs/data-quality.md
```

- `grep` searches a file for lines that match a pattern.
- `-n` adds the line number to each match.
- `-E` turns on extended patterns, so `|` means "or".
- Passing prints the table header with `Before` and `After`, and the rule rows with `removed`.
- Failing with no output means the report was not written, or it was written somewhere else. Check the path.
- The search is case-sensitive. A header that says `Removed` with a capital letter does not match `removed`. Use the lower-case word in a line of text.

**TC5: running twice gives the same count.** The trainer runs the command, counts the rows, runs the command again, and counts again:

```bash
python -m citypulse.clean && python -c "import pandas as pd; print(len(pd.read_parquet('data/clean/readings.parquet')))" && python -m citypulse.clean && python -c "import pandas as pd; print(len(pd.read_parquet('data/clean/readings.parquet')))"
```

- The `&&` operators run the next step only if the previous one succeeded.
- Each `python -c` prints the number of rows in the file.
- Passing prints the same number twice.
- Failing with a number that grows means the output is appended, or the cleaning does not run from the raw files each time. Always read every raw file and overwrite the output.
- Do not fetch new data between the two runs. New raw rows would change the count legitimately.

:::trap Passing TC5 by appending
Opening the Parquet file in append mode, or writing a second file each run, makes the row count grow. The fix is simple: every run rebuilds the whole table from `data/raw/` and overwrites `data/clean/readings.parquet`.
:::

#### Y2-T12.2: load every raw file, and profile the "before"

**Goal.** Read every raw CSV into one table, remember which file each row came from, and measure the table before any rule runs.

**Technique: glob and concat.** `Path.glob("*.csv")` yields each file whose name ends in `.csv`. You loop over them, read each one, and stack the results with `pd.concat`. For example, two small tables with the same columns become one table with the rows of both, and `ignore_index=True` renumbers the rows from 0.

**Stage 1: write load_raw.** Replace the body of `load_raw`:

```python
def load_raw(raw_dir: Path) -> pd.DataFrame:
    """Read every raw CSV and return one table with a src_file column."""
    frames = []
    for path in sorted(raw_dir.glob("*.csv")):
        part = pd.read_csv(path)
        part["src_file"] = path.name
        frames.append(part)
    if not frames:
        raise FileNotFoundError(f"no CSV files in {raw_dir}")
    return pd.concat(frames, ignore_index=True)
```

Line by line:

- `frames = []` starts an empty list for the tables.
- `sorted(...)` puts the file names in alphabetical order. Raw file names usually include a timestamp, so this is also fetch order. Check how your T11 fetcher names its files; if the names do not sort in fetch order, sort by something else. The order matters later, because the duplicate rule keeps the last copy.
- `pd.read_csv(path)` reads one file. Every column is read as text or a number, and you will fix the types later.
- `part["src_file"] = path.name` records the file name on every row of that file. This is the value the rule sorts on.
- `frames.append(part)` adds the table to the list.
- `if not frames:` is true when the list is empty. The `raise` stops the run with a clear message, instead of a confusing error from `concat`.
- `pd.concat(frames, ignore_index=True)` stacks the tables into one and numbers the rows again.

Expected: the function returns a table with one more column than the raw files, `src_file`.

**Stage 2: write profile.** The profile is the "before" picture. It must be generated by code, because the report uses the same numbers.

```python
def profile(df: pd.DataFrame) -> dict:
    """Describe the table before any rule runs."""
    return {
        "rows": len(df),
        "key_duplicates": int(df.duplicated(subset=KEY).sum()),
        "null_pct": (df.isna().mean() * 100).round(2).to_dict(),
    }
```

Line by line:

- `len(df)` is the row count.
- `df.duplicated(subset=KEY).sum()` counts rows that repeat an earlier key. `int(...)` turns the result into a plain Python number, so it prints neatly.
- `df.isna()` gives true for each missing cell. `.mean()` gives the share of true values per column, which is a fraction between 0 and 1. Multiplying by 100 gives a percentage.
- `.round(2).to_dict()` rounds the numbers and turns the result into a dictionary from column name to percentage.

#### Y2-T12.3: one cleaning rule, with its count

**Goal.** Write one rule as a function that returns the cleaned table and the number it removed. The rule is the one you chose.

**Technique: a rule returns its count.** A rule takes a table, changes it and returns two things: the new table and a number. The caller stores the number in a dictionary. This keeps the count next to the change, so you cannot forget it.

The missing-timestamp rule is a small example:

```python
def drop_missing_ts(df: pd.DataFrame) -> tuple[pd.DataFrame, int]:
    """Remove rows with no usable timestamp. Return the table and the count removed."""
    before = len(df)
    df = df.dropna(subset=["ts_utc"])
    return df, before - len(df)
```

- `before = len(df)` records the row count first.
- `dropna(subset=["ts_utc"])` returns a new table without the rows whose `ts_utc` is missing. `subset` limits the check to one column.
- `before - len(df)` is the number removed.
- `return df, ...` returns both values together.

The timestamps must be converted before this rule works. Use `pd.to_datetime(..., utc=True, errors="coerce")`. Coercion turns an unreadable timestamp into `NaT`, which the missing-timestamp rule then removes and counts. Put this conversion in its own small function, `normalise_types`, and call it before the rules. Convert the metrics with `pd.to_numeric(df[col], errors="coerce").astype("float64")`, and the text columns with `.astype("category")`. Use your squad's column names for the metrics and for `location` and `source`.

**Stage 1: write the duplicate rule.** The duplicate rule keeps one copy of each key, the copy from the newest raw file. Sorting first is what makes that true.

```python
def dedupe(df: pd.DataFrame) -> tuple[pd.DataFrame, int]:
    """Keep one row per key, taken from the last raw file. Return the table and the count removed."""
    before = len(df)
    df = df.sort_values("src_file", kind="stable").drop_duplicates(subset=KEY, keep="last")
    return df, before - len(df)
```

- `sort_values("src_file", kind="stable")` puts rows in file order. `kind="stable"` keeps rows that tie in their original order, which makes the result repeatable.
- `drop_duplicates(subset=KEY, keep="last")` keeps the last row of each key in that order.
- The count is the same subtraction as before.

Read the trap below before you test this rule.

:::trap Deduplicating before dropping blanks
If a blank reading and a valid reading share a key, and the blank sorts last, `keep="last"` keeps the blank and throws away the valid value. Decide the order of rules in your squad and write it down. The ticket's usual order is: missing timestamp, duplicates, range, then the null rule. The ticket text does not fix an order, so this guide uses that one. Whichever order your squad chooses, write it down and count every rule.
:::

**Stage 2: the range rule and quarantine.** This rule finds impossible values, writes them to `data/clean/quarantine.csv`, and then replaces each bad value with a missing value. The row stays, and the impossible number does not reach the report.

A small trace shows the idea of a range test, with three values:

```trace
TITLE: Setting aside values outside the range
CODE:
values = [12.0, -3.0, 1500.0]
ok = []
bad = []
for v in values:
    if 0 <= v <= 1000:
        ok.append(v)
    else:
        bad.append(v)
STEPS:
1 :: values=[12.0, -3.0, 1500.0] :: Three PM2.5 readings. Two of them are not plausible.
2 :: values=[12.0, -3.0, 1500.0]; ok=[] :: An empty list will hold the good values.
3 :: values=[12.0, -3.0, 1500.0]; ok=[]; bad=[] :: An empty list will hold the values to set aside.
4 :: v=12.0; ok=[]; bad=[] :: The loop takes the first reading.
5 :: v=12.0; ok=[]; bad=[] :: 12.0 is between 0 and 1000, so the test is true.
6 :: v=12.0; ok=[12.0]; bad=[] :: The good value is kept.
4 :: v=-3.0; ok=[12.0]; bad=[] :: The loop takes the second reading.
5 :: v=-3.0; ok=[12.0]; bad=[] :: -3.0 is below 0, so the test is false.
8 :: v=-3.0; ok=[12.0]; bad=[-3.0] :: The value is set aside instead of disappearing.
```

Line by line, the important points are these. The test `0 <= v <= 1000` checks both limits in one expression. The `else` branch runs for every value that fails the test, so nothing is dropped without being recorded. In pandas you write the same test for a whole column at once, with `between`.

The pandas version looks like this:

```python
def quarantine_out_of_range(df: pd.DataFrame, ranges: dict, path: Path) -> tuple[pd.DataFrame, int]:
    """Set aside values outside their range. Return the table and the number of values set aside."""
    bad = pd.DataFrame({
        col: df[col].notna() & ~df[col].between(lo, hi)
        for col, (lo, hi) in ranges.items()
    })
    path.parent.mkdir(parents=True, exist_ok=True)
    df = df.copy()
    df[bad.any(axis=1)].to_csv(path, index=False)
    for col in ranges:
        df.loc[bad[col], col] = float("nan")
    return df, int(bad.to_numpy().sum())
```

Line by line:

- `ranges` is a dictionary from column name to `(lowest, highest)`. You choose the numbers, and they must be no looser than TC3 requires: for PM2.5 the lowest value must be 0 or more and the highest 1000 or less. You may choose tighter limits, and you need sensible limits for temperature too (60 °C in Bengaluru must not pass).
- `df[col].notna() & ~df[col].between(lo, hi)` is true for a value that is present and outside its range. `~` means "not", and `&` joins the two tests. A missing value is not flagged here, because the null rule handles it.
- The dictionary comprehension builds one true or false column per metric, in a table called `bad`.
- `path.parent.mkdir(parents=True, exist_ok=True)` creates `data/clean/` if it is missing, and does nothing if it exists.
- `df[bad.any(axis=1)].to_csv(path, index=False)` writes every row with at least one bad value. The file is written even when no row matches, and then it holds only the header. That keeps TC1 passing on clean data.
- `df = df.copy()` makes an independent table, so the assignment below does not trigger pandas' SettingWithCopyWarning.
- `df.loc[bad[col], col] = float("nan")` replaces each bad value with a missing value.
- `int(bad.to_numpy().sum())` counts bad values, not rows. Your report must say so.

Test the rule alone, in the interpreter, on a table of four rows that you make up in the command.

#### Y2-T12.4: wire the rules, assert, log the dtypes, and ignore the output

**Goal.** Connect the rules in one fixed order, prove there are no duplicate keys, log the column types, and keep data out of Git.

**Stage 1: the order.** The `clean()` function calls each rule in order, and stores each count in one dictionary:

1. Convert the types with `normalise_types`.
2. Drop missing timestamps, and store the count under `"missing_ts"`.
3. Remove duplicates on the key, and store the count under `"duplicates"`.
4. Set aside out-of-range values, and store the count under `"out_of_range_values"`.
5. Apply the null rules, and store the counts under their own names.

The first call looks like this:

```python
removed: dict[str, int] = {}
df, removed["missing_ts"] = drop_missing_ts(df)
```

This works because the rule returns a pair, and Python assigns the table to `df` and the count into the dictionary. Write the other calls in the same style, in the order above.

**Stage 2: the assertion and the dtype log.** At the end of `clean()`, add:

```python
assert df.duplicated(subset=KEY).sum() == 0, "duplicate keys left after cleaning"
log.info("dtypes:\n%s", df.dtypes)
```

- `assert` stops the run with an error if the condition is false. The message after the comma is shown in the error.
- `log.info` writes an INFO message. The `%s` is filled with the dtype table. You paste this log line into the PR.

**Stage 3: git-ignore the output.** Add these lines to `.gitignore`:


**Stage 4: make the module runnable.** `python -m citypulse.clean` runs the file as a program, so it needs an entry point. Add a `main()` function and, at the bottom of the file, the standard guard:

```python

    main()
```

`if __name__ == "__main__":` is true only when the file is run with `python -m`, not when it is imported, which is why `import citypulse.clean` stays harmless. Your `main()` should do these things in order, using your own code:

1. Call `logging.basicConfig(level=logging.INFO)`. Without it, `log.info` messages are not shown, so the dtype log line never appears for your PR.
2. Call `load_raw(RAW_DIR)` and `profile(...)` on the result, and keep the "before" numbers.
3. Call `clean(...)`, then `write(...)` to `CLEAN_DIR / "readings.parquet"`. Inside `write`, `df.to_parquet(out, index=False)` creates the file and overwrites any old one, which keeps TC5 passing. Create the folder first with `out.parent.mkdir(parents=True, exist_ok=True)`.

#### Y2-T12.5: the report, generated by code

**Goal.** Write `docs/data-quality.md` from the same numbers the cleaning used, so that no count is typed by hand.

**Technique: writing text from a list.** A Python list of lines, joined with `"\n"`, becomes a file. An f-string puts a variable's value inside the text. This is how the report stays honest: the numbers come from the `removed` dictionary and the `profile` results.

Add this function to `clean.py`:

```python
def write_report(stats: dict, removed: dict, path: Path) -> None:
    """Write docs/data-quality.md from the counts, so no number is typed by hand."""
    lines = [
        "# Data quality report",
        "",
        "Generated by src/citypulse/clean.py. Do not edit by hand.",
        "",
        "| Measure | Before | After |",
        "|---|---|---|",
        f"| Rows | {stats['rows_before']} | {stats['rows_after']} |",
        "",
        "Rows and values removed by each rule:",
        "",
        "| Rule | removed |",
        "|---|---|",
    ]
    lines += [f"| {rule} | {count} |" for rule, count in removed.items()]
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text("\n".join(lines) + "\n", encoding="utf-8")
```

Line by line:

- The `stats` dictionary carries `rows_before` and `rows_after`. Put both in it inside `clean()`.
- The lines starting with `|` form Markdown tables. The `|---|---|` line marks the header row.
- `f"| Rows | {stats['rows_before']} | ..."` puts the number into the table.
- `lines += [...]` adds one table row for each rule, using a list comprehension. `removed.items()` gives each rule name and its count.
- `path.write_text(..., encoding="utf-8")` writes the file. The encoding makes sure the file opens the same way on Windows and Linux.

For acceptance criterion 5, work out the total removed as a percentage of the input rows (`rows_before`). If it is above 10%, the PR needs a written justification for each rule. Counting values set aside by the range rule separately from rows dropped keeps this percentage honest.

Extend the report yourself. The ticket also needs null percentage for each column, and a sentence of justification for each null rule. Add a table in the same way, using the `null_pct` values from `profile`.


Expected: the grep prints at least the header line with `Before` and `After`, and one line per rule that contains `removed`.

**Test this stage.** Open the file. Every number in it must match the log output of the run. If a number is wrong, the bug is in the code, not in the report.

### Defend it in the viva

**1. Why does the ticket count every dropped row, even when the cleaning is correct?**

:::answer Model answer
A count is evidence. It shows what the rule did, and it shows whether the result is plausible. A large drop can mean the rule is too strict, and a zero drop can mean the rule is not running. Counts generated by code cannot drift from what the code did, so the report stays honest when the data changes. The answer should name the `removed` dictionary and the report that reads it.
:::

**2. What is the trade-off between dropping a row and setting one value aside?**

:::answer Model answer
Dropping a row removes all its other good values, such as a valid temperature sitting beside an impossible PM2.5 reading. Setting one value aside keeps the rest of the row, but it leaves gaps that later steps must handle. The cost is extra care in every analysis about missing values. The ticket accepts the cost because it keeps more good data, and the quarantine file keeps the original values so they can be inspected.
:::

**3. Why does `keep="last"` depend on the sort order, and what did you do to make it reliable?**

:::answer Model answer
`keep="last"` keeps whichever copy comes last in the current row order. If the order is not defined, the kept copy is not defined either. The answer should name the sort on `src_file`, the file names that follow fetch order, and the use of `kind="stable"` so ties keep their order. It should say that the sort happens before the duplicate rule and not after.
:::

**4. Suppose the command is run twice and the row counts differ. What would you check first?**

:::answer Model answer
The answer should first check whether the raw folder changed between runs, because new raw rows legitimately change the count. If it did not change, the next check is whether the output is appended or rebuilt, and whether every run reads all raw files in the same order. The answer should name TC5 as the test that catches this, and say that the fix is to overwrite the output from the full input every run.
:::

**5. What did you personally write in this ticket, and how do you know it is yours?**

:::answer Model answer
A good answer names the rule you wrote, the function it lives in, and the commit that added it, with its message. It then names the test you ran on that rule and the count it produced. You can show `git log --format='%an %s' -- src/citypulse/clean.py` if asked. Describe only the commits and the tests you ran, and do not invent how the work went.
:::
