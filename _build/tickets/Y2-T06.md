### The ticket in plain words

CityPulse is a Bengaluru city-data platform. Its air-quality readings come from a web service, an API that answers requests sent over HTTP. So far, a person runs `scripts/fetch_once.sh` by hand, which gives one snapshot and no history. The P1 demo on Saturday needs 48 hours of readings, so this ticket makes the fetch run by itself every 30 minutes.

An unattended job can fail quietly, as the ticket's example of a runaway automated system shows. Your version must retry short-lived failures, write timestamped log lines, never store the same reading twice, never run two copies at once, and stop when a file called `ops/STOP` exists. That file is the kill switch: anyone on the team can halt the job by creating it.

### How your trainer checks it

**Acceptance criteria.** (1) Cron runs the job, and `logs/fetch.log` shows at least three `INFO appended` runs. (2) The day's CSV has no duplicate rows on its first two columns. (3) The 404 test gives two WARN lines, one ERROR naming the HTTP failure, and exit code 1. (4) A second copy logs a WARN and exits 0 without appending. (5) With `ops/STOP` present, nothing is fetched and a WARN is logged. (6) The PR has an approval from a squad-mate who is not the author. TC1 to TC5 check criteria 1 to 5, and the trainer checks criterion 6 on GitHub.

**TC1: the cron entry and the run count.** `crontab -l | grep fetch.sh` prints your crontab and keeps only the lines containing `fetch.sh`. Passing output is one `*/30 * * * *` line with an absolute path. Nothing printed means the entry is missing, and two lines mean a duplicate. `grep -c ' INFO .*appended' logs/fetch.log` counts lines with INFO, then any text, then `appended`. `-c` prints the count. Passing output is 3 or more. A 0 usually means cron has not run the script, so check `logs/cron.out`. The trainer runs this after the session, once three scheduled runs have happened.

**TC2: the failure simulation.** The command is `URL=https://air-quality-api.open-meteo.com/v1/nope scripts/fetch.sh; echo "exit=$?"; tail -3 logs/fetch.log`. `URL=...` sets a variable for this one command. The semicolons run each command in turn, and `tail -3` prints the last three lines. Passing output is `exit=1`, then a WARN, a second WARN and an ERROR naming the HTTP failure. `exit=0` means the failure was not passed on, so check `-f` and the final `exit 1`. One WARN means the attempt counter is wrong. A `Permission denied` message means the file is not executable.

**TC3: duplicate rows.** The command is `cut -d, -f1,2 data/raw/$(date +%F).csv | sort | uniq -d | wc -l`. `cut -d, -f1,2` keeps columns 1 and 2, `sort` groups equal lines, `uniq -d` prints only lines that appear more than once, and `wc -l` counts them. `$(date +%F)` fills in today's date. Passing output is `0`. Any other number means the dedup check is missing or uses different columns. A passing run on the lab looks like this:

```term
$ cut -d, -f1,2 data/raw/$(date +%F).csv | sort | uniq -d | wc -l
0
```

**TC4: the overlap test.** The command is `(scripts/fetch.sh &) ; scripts/fetch.sh; tail -2 logs/fetch.log`. The brackets and `&` start the first copy in the background, so it still holds the lock when the foreground copy starts. Passing output has a WARN line, `previous run active; skipping`, in the last two lines. If you see `INFO appended`, the first copy had already finished, so run the test again. If the second copy appends, check the order of `exec 9>` and `flock -n 9`.

**TC5: the kill switch.** The command is `touch ops/STOP; scripts/fetch.sh; tail -1 logs/fetch.log; rm ops/STOP`. `touch` creates the flag, `tail -1` prints the newest line, and `rm` removes the flag. Passing output is `WARN STOP flag present; not fetching`. Use the ticket's exact wording. If the last line is `INFO appended`, the check comes after the fetch. Always run the `rm`, because a leftover flag stops every later run.

#### Y2-T06.1: copy the script and set up the basics

**Goal.** A safe starting file with strict mode, a fixed folder, `.env` settings and logging.

**Stage 1. Create the branch and the copy.**

```bash
git switch -c feat/fetch-cron
cp scripts/fetch_once.sh scripts/fetch.sh
```

`git switch -c` creates the branch. `cp` copies the file and leaves `fetch_once.sh` unchanged.

**Stage 2. The first lines.** Make the top of `scripts/fetch.sh` look like this, keeping the shebang line that the copy already has:

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.." && mkdir -p logs
```

`set -euo pipefail` is strict mode. `$(dirname "$0")` is the script's folder, and `/..` steps up to the repository root, because cron starts in your home folder. Test with `bash -n scripts/fetch.sh`. It should print nothing.

**Stage 3. Load settings from `.env`.** Add this line below the three above:

```bash
if [ -f .env ]; then set -a; . ./.env; set +a; fi
```

`[ -f .env ]` is true when the file exists. `set -a` exports the variables, `. ./.env` reads the file, and `set +a` turns exporting off. Do not put `URL` in `.env`, or it would overwrite the `URL=...` you type for TC2.

**Stage 4. The URL and the temporary file.** Keep the URL line from `fetch_once.sh`, changed to this form:

```bash
URL="${URL:-<the URL already in fetch_once.sh>}"
TMP="$(mktemp)"
```

`${URL:-...}` uses the environment value when one is set, which is how TC2 points the script at the 404 address. `mktemp` creates a temporary file for the download. In the next sub-task you replace the old `curl` line with a retry loop that saves the reply into `"$TMP"`, so make every later line (the `jq` check and the row-writing) read from `"$TMP"` instead of the old curl output.

**Stage 5. The log function.**

```bash
log() { printf '%s %s %s\n' "$(date -u +%FT%TZ)" "$1" "$2" >> logs/fetch.log; }
log INFO "script started"
```

`$1` is the level and `$2` the message. `date -u +%FT%TZ` prints UTC time, such as `2026-11-17T10:00:00Z`. Test with `bash scripts/fetch.sh`, then `tail -1 logs/fetch.log`. The last line should show the time, INFO and your message.

#### Y2-T06.2: retry, schema check and dedup

**Goal.** Retry up to three times, log each failure, exit 1 when all tries fail, and skip saved rows.

**Stage 1. The function.** Put this above the place where the fetch happens. The loop keeps retrying while curl fails, and the counter and wait double each time:

```bash
fetch_with_retry() {
  local attempt=1 delay=5
  until curl -sSf --max-time 20 -o "$TMP" "$URL"; do
    if [ "$attempt" -ge 3 ]; then
      log ERROR "HTTP fetch failed after 3 attempts: $URL"
      return 1
    fi
    log WARN "attempt $attempt failed; retrying in ${delay}s"
    sleep "$delay"
    attempt=$((attempt + 1))
    delay=$((delay * 2))
  done
}
fetch_with_retry || exit 1
```

`-s` hides the progress bar, `-S` shows errors, `-f` fails on HTTP errors such as 404, and `--max-time 20` gives up after 20 seconds. `local` keeps the variables inside the function. The last line makes the script exit 1 when the function fails, which is what TC2 checks.

:::trap The ticket's delays and three tries
The ticket lists 5, 10 and 20 seconds, but three tries give only two waits, so this stage uses 5 and 10. Ask your trainer before adding a 20-second wait.
:::

**Stage 1b. Keep the schema check.** Right after the retry call, keep the `jq -e` line from `fetch_once.sh`, pointed at the downloaded file, for example `jq -e '.hourly' "$TMP" > /dev/null || { log ERROR "response failed schema check"; exit 1; }`. Use the field names your own source returns instead of `.hourly`. `jq -e` exits non-zero when the result is `null` or `false`, so a reply with the wrong shape stops the run before any row is written.

**Stage 2. The dedup check.** Dedup means each reading is stored once. Add this check in front of each place that appends a row. Use your own variable names for the timestamp and location, and set `CSV` near the top:

```bash
CSV="data/raw/$(date +%F).csv"
key="${ts},${loc}"
if [ -f "$CSV" ] && grep -qxF "$key" <(cut -d, -f1,2 "$CSV"); then
  log WARN "duplicate reading skipped"
  continue
fi
```

`<(...)` feeds the `cut` output to `grep` as if it were a file. `-q` keeps `grep` quiet. `-x` matches the whole line and `-F` treats the key as plain text. The `-f` test avoids an error when today's file does not exist yet. The key must use the same two columns that TC3 checks. Use `continue` inside a loop; for a single row, wrap the append in an `if` block.

**Stage 3. Log the success.** After the rows are written, add:

```bash
log INFO "appended to $CSV"
```

TC1 counts the word `appended`, so log this line only on success. If every row in a run was skipped as a duplicate, log nothing here (or use a different word such as `no new rows`), because TC1 would count it as a real run.

#### Y2-T06.3: the lock and the kill switch

**Goal.** Stop two copies from running at once, and stop the job when `ops/STOP` exists.

**A short lesson on `flock`.** `flock` locks an open file. The lock lasts while the process runs, and Linux releases it when the process ends, even after a crash.

```flow
TITLE: Two copies start at the same time
NODES: First run | flock lock | Second run | logs/fetch.log
STEPS:
1>2 :: takes lock :: The first run holds the lock on file descriptor 9 while it works.
3>2 :: asks for lock :: A second copy starts while the first is still busy.
2>3 :: lock held :: flock -n refuses at once, because -n means do not wait.
3>4 :: WARN previous run active :: The second copy logs one WARN line and exits 0.
```

**Stage 1. The lock.** Put these lines after the `log` function, and before any fetch:

```bash
exec 9>"/tmp/citypulse-$(whoami).lock"
if ! flock -n 9; then
  log WARN "previous run active; skipping"
  exit 0
fi
```

`exec 9>file` attaches the file to descriptor 9 without running a program. `$(whoami)` gives each student their own lock file, and `/tmp` keeps it out of the repository. The `!` makes the block run when the lock was not obtained. Exit 0 is deliberate, because a skipped overlap is not an error. Run tests with `bash`, not `source`, because a sourced script keeps the lock in your terminal.

**Stage 2. The kill switch.** Add this after the lock, before the fetch:

```bash
mkdir -p ops
if [ -f ops/STOP ]; then
  log WARN "STOP flag present; not fetching"
  exit 0
fi
```

`mkdir -p ops` makes sure the folder exists for TC5. `[ -f ops/STOP ]` is true when the flag file exists.

**Test both.** Run `(bash scripts/fetch.sh &) ; bash scripts/fetch.sh; tail -2 logs/fetch.log` and look for `previous run active; skipping` (if you do not see it, the first copy finished too quickly; run it again). Then run `touch ops/STOP; bash scripts/fetch.sh; tail -1 logs/fetch.log; rm ops/STOP` and look for the STOP warning.

`grep -v fetch.sh` keeps every line that does not mention `fetch.sh`, so reinstalling does not duplicate the job. `|| true` stops the line failing when there is nothing to keep. `<<EOF` takes the text up to the next `EOF` line. `crontab FILE` replaces the whole crontab, which is why the other jobs were saved first. ### Defend it in the viva

**1. Why does the script exit 0 when another run is active, but exit 1 when the HTTP request fails?**

:::answer Model answer
An overlap is expected, so exit 0 says the job is fine. A failed request means no data was collected, so exit 1 tells cron and anything watching the exit code that the run failed. Mixing the two would hide failures or raise false alarms.
:::

**2. What trade-off did you accept by retrying three times instead of retrying until the request works?**

:::answer Model answer
Three short tries fix brief network faults and finish in a known time. Retrying forever could hold the lock for hours and block every later run. The cost is that a longer outage leaves a gap, which the log shows and the next scheduled run does not fill.
:::

**3. Which part did you write yourself, and how did you prove it works?**

:::answer Model answer
Name the subtask you owned, the stage you wrote and the test that proves it, with the command you ran and the log line it produced. Do not describe work you did not do.
:::

**4. Why does the dedup check use timestamp and location, and not the whole row?**

:::answer Model answer
A repeated reading can differ in another column, such as number formatting, so a whole-row comparison would miss it. Timestamp and location identify one reading at one time. The trade-off is that a genuine correction for the same time and place is skipped.
:::

**5. How do you know the job runs without you?**

:::answer Model answer
The evidence is in the logs. `crontab -l` shows the schedule, and the `grep -c` count shows the successes. WARN and ERROR lines explain failures.
:::
