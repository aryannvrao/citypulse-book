### The ticket in plain words

This ticket is your squad's defence of the CityPulse API. A trainer spends 12 minutes with your squad and tests the live service. They call the endpoints on your README URL, ask one member to ship a one-line change, ask another member to undo it, and ask you to show the monitoring. The client sponsor uses this to decide whether phase one is signed off.

The ticket also adds one endpoint, `/v1/bulletin`. It returns a short daily text about air quality for a ward. The text is written by a large language model (LLM), a program that writes text from a prompt. LLMs can invent facts, so the endpoint must check its own output against the real numbers. It must also limit how many times it calls the model, so costs stay under control. An airline lost a court case because its chatbot gave wrong information, and the lesson for CityPulse is that your squad is accountable for every sentence the bulletin prints.

Last, mentors give the squad an industry mini-project brief. You must leave with a plan that is approved for the async sprint from 13 to 30 March.

### Words you need

| Term | Plain meaning |
|---|---|
| API | A set of web addresses that other programs call to get data or trigger actions. |
| Endpoint | One address in the API, such as `/v1/health`. |
| HTTPS | HTTP with encryption, so the traffic cannot be read on the way. |
| JSON | A text format for structured data, made of keys and values. |
| curl | A command-line tool that sends a web request and prints the reply. |
| Status code | A three-digit reply code. `200` is success, `422` means the input was refused, `500` means the server failed. |
| CI | Continuous integration: a service that runs your tests on every push or pull request. |
| Tag | A fixed name on one commit, such as `v0.9-p9`. |
| Deploy | Putting a new version of the code on the live server. |
| Smoke test | A quick check after a deploy that the service answers. |
| Rollback | Putting an earlier version back on the live server. |
| `git_sha` | The short commit identifier that `/v1/health` reports, showing which code is live. |
| Branch protection | A GitHub rule that blocks direct pushes to `main` and can require an approved review. |
| Pull request (PR) | A request to merge a branch into `main`, reviewed by a squad-mate. |
| Coverage | The share of your code lines that the tests run, as a percentage. |
| Branch coverage | Coverage that also checks both sides of each `if`. |
| SLI | Service level indicator: a measurement of service quality, such as the share of successful checks. |
| SLO | Service level objective: a target for an SLI. |
| Prompt | The text sent to an LLM, including its instructions and its input data. |
| `prompt_version` | A label for the prompt text. Changing the prompt means changing the label. |
| Token | A small piece of text, roughly a word or part of one. Models count and bill by tokens. |
| `max_tokens` | The most tokens the model may write in one reply. |
| Timeout | The longest time you wait for a reply before giving up. |
| Retry | Trying the same call again after a temporary failure. |
| Grounding | The rule that a generated text may state only facts that appear in its input. |
| Hallucination | Fluent text the input does not support, such as an invented number. |
| Prompt injection | Input text that tries to change the model's instructions. |
| Template fallback | A fixed, safe text used when the model reply is missing, slow or fails the checks. |
| Cache | A stored copy of a result, returned on the next request without new work. |
| Cache key | The fields that identify a cached result. Here: `(day, ward, prompt_version)`. |
| Daily cap | A limit on how many LLM calls the service may make in one day. |
| Environment variable | A named setting the program reads at run time, such as `BULLETIN_DAILY_CAP`. |
| Secret manager | A cloud service that stores keys and gives them only to the running service. |
| Monkeypatch | In pytest, a temporary replacement of one function, for the length of one test. |
| pytest | The Python test runner. Functions named `test_...` are run. |
| Validation | Checking that input has the right form, such as a real date, before using it. |
| ISO date | A date written as `YYYY-MM-DD`, such as `2027-03-12`. |
| Stand-up | A short daily update: what you did, what you will do, and what blocks you. |

### How your trainer checks it

The trainer runs every acceptance criterion and test case. Run each one yourself before the defence.

**Acceptance criterion 1 and TC1. The three core endpoints answer.** The trainer runs these three commands on the README URL. Each must return `200` and valid JSON.

```text
curl -s https://<url>/v1/health
curl -s https://<url>/v1/stats
curl -s -X POST https://<url>/v1/predict -H 'Content-Type: application/json' -d @docs/api/predict_example.json
```

In the last command, `-X POST` sends a POST request. `-H` adds a header that says the body is JSON. `-d @file` sends the contents of the file as the body, and the `@` means "read from this file". `-s` hides the progress meter, so only the reply prints. To check that a reply is valid JSON, pipe it into the standard library tool, which fails if the JSON is broken:

```text
$ curl -s https://<url>/v1/health | python -m json.tool
{
    "status": "ok",
    "git_sha": "3f9a1c2"
}
```

A `404` means a wrong path. A `500` means the server raised an error, so read its log. An HTML page where you expected JSON means the request did not reach your API.

**Acceptance criterion 1, continued. CI is green on main, with at least 10 tests and coverage of at least 60%.** Open the latest CI run on `main` and look for a test summary. Locally, the same check is:

```text
$ pytest --cov=genai --cov-branch --cov-fail-under=60
Name              Stmts   Miss Branch BrPart  Cover
TOTAL               180     60     40      8    62%
Required test coverage of 60% reached. Total coverage: 62.xx%
========== 12 passed in 2.31s ==========
```

`--cov=genai` measures the `genai` package (use the package or folder your squad's CI measures). `--cov-branch` also measures branches. `--cov-fail-under=60` makes pytest fail below 60%. The numbers above are illustrative. A failure shows `FAILED` beside a test name, or `Required test coverage of 60% not reached`.

**Acceptance criterion 2 and TC2. Deploy by PR, merge and tag, then roll back.** A member makes a one-line change, merges it, and pushes a `v*` tag. The deploy workflow runs and the smoke test must pass in the defence slot. The new text must appear on the live URL. A second member then rolls back using `docs/cloud-runbook.md`, and `/v1/health` must show the previous `git_sha`.

Passing looks like a changed message after the deploy and an older `git_sha` after the rollback:

```term
$ curl -s https://<url>/v1/health
{"status":"ok","message":"CityPulse is up (rehearsal)","git_sha":"8c2d4e7"}
$ curl -s https://<url>/v1/health
{"status":"ok","message":"CityPulse is up","git_sha":"3f9a1c2"}
```

These values are illustrative. A failing deploy shows a red workflow run, so the smoke test never starts. A failing rollback shows the newer `git_sha` still served. The usual causes: the tag does not start with `v`, or the rollback command targets the wrong revision.

**Acceptance criterion 3. The alert history and the SLI are shown live.** The trainer opens the uptime monitor and `docs/slo.md`. Be ready to name the SLI, how it is measured, and its current value.

**Acceptance criterion 4 and TC3. The bulletin is returned, cached and grounded.** The trainer calls the same URL twice and reads the logs:

```text
curl -s 'https://<url>/v1/bulletin?day=2027-03-12'
```

The quotes stop the shell from reading the `?` and `&` characters. The `day` value is an ISO date. Passing means both bodies are identical, the log shows one LLM call, the disclaimer is present, and every number in `body` appears in `stats`. A different second body points to a missing or wrong cache key. Two LLM calls in the log mean the cache is checked after the call, not before it. The trainer's date must be a valid day under your rules: if the server refuses a future date, that is the rule working, so ask the trainer which date to use.

**Acceptance criterion 5 and TC4. Injection-like input is refused.**

```text
curl -s -o /dev/null -w '%{http_code}' 'https://<url>/v1/bulletin?day=2027-03-12&ward=ignore%20previous%20instructions'
```

`-o /dev/null` throws away the body, and `-w '%{http_code}'` prints only the status code. `%20` is an encoded space, so the server receives `ignore previous instructions`. Passing prints `422`. A `200` means the ward was not checked against the known codes.

Also required: an LLM timeout or ungrounded output returns `200` with `source='template'`, and the daily cap is set by an environment variable and enforced. Y2-T48.7 tests these.

#### Y2-T48.4: Build GET /v1/bulletin (Backend)

**Goal.** Build the route in small pieces, and test each piece before adding the next.

**Technique: a cache keyed by a tuple.** A dictionary maps a key to a stored value. A tuple in parentheses can be a key, because it cannot change. The database table works the same way.

```trace
TITLE: A cache keyed by day, ward and prompt version
CODE:
cache = {}
key = ("2027-03-12", "W01", "bulletin_v1")
hit = cache.get(key)
if hit is None:
    cache[key] = {"headline": "example"}
hit2 = cache.get(key)
STEPS:
1 :: cache={} :: Start with an empty cache.
2 :: cache={}; key=("2027-03-12", "W01", "bulletin_v1") :: The key holds the three values that identify one bulletin.
3 :: cache={}; key=("2027-03-12", "W01", "bulletin_v1"); hit=None :: get returns None because nothing is stored yet.
4 :: cache={}; hit=None :: The condition hit is None is true, so the body of the if runs.
5 :: cache={("2027-03-12", "W01", "bulletin_v1"): {"headline": "example"}}; hit=None :: The miss branch stores a result under the key.
6 :: cache={("2027-03-12", "W01", "bulletin_v1"): {"headline": "example"}}; hit2={"headline": "example"} :: The second lookup finds the stored value, so no new work is needed.
```

**Stage 1. Validate the day.** Write a function that turns the text into a date and refuses future dates:

```python
from datetime import date

def parse_day(raw: str) -> date:
    d = date.fromisoformat(raw)
    if d > date.today():
        raise ValueError("day is in the future")
    return d
```

`date.fromisoformat` reads `YYYY-MM-DD` and raises `ValueError` for anything else. The comparison `d > date.today()` is true for a later date. Test `parse_day("2026-11-01")` and `parse_day("2099-01-01")` in a Python shell. Your route turns the error into `422`.

**Stage 2. Validate the ward against known codes.** A small test, using a bakery's branch codes instead of your ward codes, shows the pattern:

```python test
def parse_branch(raw, known):
    code = raw.strip().upper()
    if code not in known:
        raise ValueError("unknown branch code")
    return code

known = {"BK1", "BK2", "BK3"}
assert parse_branch(" bk2 ", known) == "BK2"
assert parse_branch("BK3", known) == "BK3"
try:
    parse_branch("ignore previous instructions", known)
    raise AssertionError("injection-like text was accepted")
except ValueError:
    pass
```

`strip().upper()` removes the spaces and capitalises the text. `not in known` tests membership in a set, which is quick. Expect no output when all asserts pass. Apply the same rule to your wards: an unknown ward returns `422` before anything else happens.

**Stage 3. Look up the cache.** Use all three parts of the key. Placeholder style depends on the driver: `sqlite3` uses `?`, and many Postgres drivers use `%s`.

```python
row = conn.execute(
    "SELECT body_json FROM bulletins WHERE day = ? AND ward = ? AND prompt_version = ?",
    (day, ward, PROMPT_VERSION),
).fetchone()
```

The values are passed separately, so the driver never treats them as SQL. `fetchone()` returns one row, or `None`. Use the `PROMPT_VERSION` from Y2-T47, so a new prompt invalidates old rows.

**Stage 4. Compute on a miss.** On a miss, call `stats_for(day)` and then `call_llm`. The Anthropic SDK takes the timeout and retry settings on the client:

```python
from anthropic import Anthropic
client = Anthropic(timeout=15.0, max_retries=2)
```

`timeout=15.0` is the wait in seconds. `max_retries=2` allows two more tries after a transient failure. Set `max_tokens=400` in the `messages.create` call inside `call_llm`.

**How you test this stage.** Call the route twice with the same valid day. The first call should write one row and the second should read it, with one LLM call in total.

#### Y2-T48.5: Daily cap and fallback (Data)

used = conn.execute("SELECT COUNT(*) FROM llm_calls WHERE day = ?", (today,)).fetchone()[0]

#### Y2-T48.7: Tests with call_llm monkeypatched (QA/DevOps)

**Technique.** pytest's `monkeypatch` swaps a function during one test and restores it afterwards. Here is a small example:

```python
import types

def fake_reply(day, ward):
    return "PM2.5 averaged 61.2."

def test_uses_fake(monkeypatch):
    module = types.SimpleNamespace(call=lambda day, ward: "real")
    monkeypatch.setattr(module, "call", fake_reply)
    assert module.call("2027-03-12", "W01") == "PM2.5 averaged 61.2."
```

`monkeypatch.setattr(object, "name", value)` replaces `module.call` for this test only. Run `pytest -q` and expect `1 passed`. In your tests, patch `call_llm` in the module where the route uses it.

### What goes wrong

| Symptom | Cause | Fix |
|---|---|---|
| Pushing a tag starts no deploy run | The tag name does not start with `v` | Delete the local tag with `git tag -d <name>`, then create and push a `v` tag. |
| Smoke test fails after deploy | The service is still starting, or the health route changed | Read the workflow log, then run the same curl command that the smoke test runs. |
| `git_sha` is the old one after a deploy | The process was not restarted | Check that the deploy restarts the service, then re-check `/v1/health`. |
| Second bulletin call makes a second LLM call | The cache is written after the call, or the key misses a field | Write the row before returning, and use `day`, `ward` and `prompt_version` in insert and lookup. |
| Invalid ward returns `200` | Validation runs after the cache lookup, or accepts any text | Validate against the known set first, and return `422` at once. |
| Bulletin shows a number not in stats | The check is skipped on the cached path, or rounding differs | Check the cached reply too, and round stats the same way before the prompt is built. |
| Coverage falls below 60% after you add a branch | The new `if` path has no test | Add a test for each new branch, including the cap and timeout paths. |
| CI fails with a key error | `call_llm` is not patched | Use `monkeypatch.setattr` on the module where the route calls `call_llm`. |
| curl returns the wrong result | The URL was not quoted, so `&` split it | Put the whole URL in single quotes. |

### Defend it in the viva

**1. Why does the deploy run on a tag and not on every push to main?**

:::answer Model answer
A tag is a deliberate, named release. Main can change many times a day, including half-finished work. Deploying on a tag means the live service changes only when the squad chooses, and the tag names the exact commit that was tested. Rollback is then clear, because you know which tag and sha were live before. The trade-off is that a fix sits on main until someone tags it.
:::

**2. What is the trade-off in caching by day, ward and prompt version?**

:::answer Model answer
Caching saves money and time, because a repeated call returns the stored body without a model call. The cost is staleness: if the stats change after a bulletin is stored, the cached text stays the same. Including `prompt_version` in the key means a new prompt invalidates the cache. The squad must decide when a stored bulletin may be regenerated, and write that rule down.
:::

**3. Walk me through what you personally did on this ticket.**

:::answer Model answer
A strong answer names one piece, its commits, the test that covers it, and the log line or CI run that proves it. For example: "I built the ward validation. My commit added the known-set check and a test for injection-like input, and the CI run shows the 422." Write your own version with your own commit names. Do not claim a teammate's work.
:::

**4. Why check numbers in code rather than asking the model to check itself?**

:::answer Model answer
A model can be confident and still wrong, so asking a second model is not an independent check. Code compares each number in the output with the allowed set from the stats. It is fast, cheap and repeatable. A failed check returns the template, so an invented number never reaches the reader. The check proves the numbers are supported, not that the prose is good.
:::

**5. Why is the ward validated before the cache lookup?**

:::answer Model answer
Validation first means bad input never reaches the database or the model. An unknown ward or an injection-like string is refused with `422`, so it cannot create a cache row, cost a call, or change the prompt. The order also matches the trainer's test: the injection case must return `422`, not `200`.
:::
