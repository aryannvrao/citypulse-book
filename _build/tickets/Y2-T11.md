### The ticket in plain words

CityPulse collects weather and air-quality readings for Bengaluru and stores them in a CSV file (a plain text table with one row per reading and commas between the columns). Until now the fetcher that does this has been a bash script, `fetch_once.sh`. Bash works, but it is hard to test and hard for a teammate to extend. This ticket moves the fetcher into Python, in a package called `citypulse`, split into small named functions.

The ticket asks for four changes. First, the fetcher reports what it is doing with logging instead of `print`, so a failed run leaves an ERROR line you can find later. Second, it handles the errors you expect (no network, HTTP 404) instead of catching everything. Third, every timestamp is written as UTC in ISO-8601 form, for example `2026-12-01T13:00:00Z`. Fourth, every column has a documented type, unit and source in `docs/data-dictionary.md`.

The reason for the third and fourth changes is a famous failure. In 1999 NASA's Mars Climate Orbiter was lost because one team's software produced force values in pound-force seconds while another expected newton-seconds. Nothing crashed, so nobody noticed until the spacecraft was gone. CityPulse charts would fail in the same silent way if one column held IST times and another held UTC, or if µg/m³ and ppm were mixed.

By the end of this ticket, the fetcher should run from a clean virtual environment, write the same data as the bash fetcher for the same hour, and fail loudly when the API cannot be reached. Your squad still chooses its data source, column names and thresholds.

**TC1: a clean install and a successful run.** Runs on the lab Linux machine, or Git Bash on your laptop.

Command: `python -m venv /tmp/v && . /tmp/v/bin/activate && pip install -e . && python -m citypulse.fetch; echo $?`

Parts:

- `python -m venv /tmp/v` creates a fresh virtual environment in the folder `/tmp/v`. On Git Bash, `/tmp` is a real folder under your Windows temporary directory.
- `&&` runs the next command only if the previous one succeeded.
- `. /tmp/v/bin/activate` loads the environment, so `python` and `pip` now point inside it. On Git Bash the path is `. /tmp/v/Scripts/activate`, because Windows venvs use `Scripts`.
- `pip install -e .` installs the package in the current folder (`.`) in editable mode, reading `pyproject.toml`.
- `python -m citypulse.fetch` runs the module `fetch` inside the package `citypulse` as a program.
- `; echo $?` runs after the Python command, whatever its result, and prints its exit code.

Passing output looks like this. The log format is your own, so the wording may differ. The level and the final `0` matter:

```
INFO citypulse.fetch: wrote 24 rows to your output file
0
```

Failing output and causes:

- `ModuleNotFoundError: No module named 'citypulse'`. The editable install did not run in this environment. You may have activated a different venv, or your `pyproject.toml` does not point at `src`.
- A non-zero number at the end, with an ERROR line above it. The network is down, or the URL is wrong. Check the curl command in "Before you start".

Here is the same test as an animation of a passing run:

```term
$ python -m citypulse.fetch; echo $?
INFO citypulse.fetch: wrote 24 rows to your output file
0
```

**TC2: every timestamp is UTC ISO-8601.** Runs on the lab Linux machine.

Command: `awk -F, 'NR>1 && $1 !~ /^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}Z$/' <py output> | wc -l`

Replace `<py output>` with the path to your Python CSV.

Parts:

- `awk` scans the file one line at a time.
- `-F,` says the fields are separated by commas.
- `NR>1` skips line 1, the header. `NR` is the record (line) number.
- `$1` is the first field, the timestamp column in this ticket.
- `!~` means "does not match".
- `/^...$/` is the regex from AC1, written for awk.
- `| wc -l` counts the lines awk printed. Each printed line is a row with a bad timestamp.

Passing output: `0`.

Failing output: a number above 0. Usual causes: timestamps written with a space instead of `T`, with an offset such as `+05:30`, without seconds, or as local time without the `Z`. On an older awk that does not support `{4}` intervals, awk may print an error instead of a count. Use `gawk` if you see that.

**TC3: the parity diff.** Runs on the lab Linux machine, or Git Bash.

Command: `diff <(sort bash_utc.csv) <(sort py.csv)`

Parts:

- `sort bash_utc.csv` prints the lines of your bash output, converted to UTC, in sorted order. Row order does not matter for this test.
- `<( ... )` runs the command and gives its output to `diff` as if it were a file.
- `diff` prints every line that differs between the two sorted lists.

Passing output: nothing at all. The command prints no lines and the prompt returns. To see the exit code, add `; echo $?`, which should print `0`.

Failing output: lines starting with `<` (from the first file) and `>` (from the second file). Usual causes: one side still uses IST, one side has no `Z`, numbers are printed with different decimal places, or columns come in a different order. Fix the Python. Never edit `fetch_once.sh` to make the test pass.

**TC4: a 404 must be an error.** Runs on the lab Linux machine, or Git Bash.

Command: `AQ_URL=https://air-quality-api.open-meteo.com/v1/nope python -m citypulse.fetch; echo $?`

Parts:

- `AQ_URL=...` sets the environment variable for this one command only. Your `config.py` reads it, so the program calls the wrong URL.
- `/v1/nope` is a path the API does not have, so the server answers 404.
- `python -m citypulse.fetch` runs your fetcher.
- `; echo $?` prints the exit code.

Passing output: an ERROR log line that names HTTP 404 and the reason, then a non-zero number such as `1`.

Failing output and causes:

- A `0` at the end. This is the most common failure. Either `config.py` ignores `AQ_URL`, or `main()` returns nothing. A trap: `SystemExit(None)` exits with 0. Make `main()` return an `int` and call `raise SystemExit(main())`.
- No ERROR line. The exception is caught and not logged, or a bare `except:` hides it.

**TC5: every column is in the data dictionary.** Runs on the lab Linux machine, or Git Bash.

Command: `for c in $(head -1 <py output> | tr , ' '); do grep -q "| $c " docs/data-dictionary.md || echo MISSING $c; done`

Parts:

- `head -1` reads the first line of the CSV, the header.
- `tr , ' '` replaces each comma with a space, so the column names become separate words.
- `$( ... )` runs the pipeline and puts its output into the `for` list.
- `for c in ...; do ... done` repeats the body once for each column name, with `$c` set to that name.
- `grep -q "| $c "` searches the dictionary for a table cell that starts with the name. `-q` means quiet: grep prints nothing and only sets its exit code.
- `|| echo MISSING $c` runs the `echo` only when grep found nothing.

Passing output: no `MISSING` lines.

Failing output: `MISSING <name>`. Usual causes: a typo in the dictionary, a different name in the CSV, or backticks around the name in the table (`` `pm2_5` `` breaks the pattern `| pm2_5 `).

#### Y2-T11.3: Implement one function

**Goal.** One function with a type hint, a docstring and logging, committed under your own identity.

**The shape of the pipeline.** Each function does one step. The animation shows how a run passes through them.

```flow
TITLE: One run of the Python fetcher
NODES: Open-Meteo API | fetch_json | parse | save_rows | CSV file
STEPS:
1>2 :: GET request :: fetch_json asks the API for its JSON body and waits up to a timeout.
2>3 :: JSON dictionary :: parse picks the values it needs and converts times to UTC.
3>4 :: one row :: save_rows writes the header once, then adds each row.
4>5 :: file written :: The CSV on disk now holds the new rows.
```

**Technique 1: logging.** Logging is set up once, in `main()`. Each module only asks for a logger and writes to it. Try this small example:

```python
import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(name)s: %(message)s")
log = logging.getLogger("demo")
log.info("starting with %d rows", 3)
log.error("fetch failed for %s", "https://example.invalid/x")
```

Line by line:

- `basicConfig` sets the level and the format for the whole program. It is called once.
- `getLogger("demo")` makes a named logger. In your code you use `getLogger(__name__)`.
- `log.info(...)` writes a message at INFO level, and `log.error(...)` at ERROR level.
- `%d` and `%s` are placeholders. The values come after the message, not joined in with an f-string. Logging formats the text only when the message is actually written.

Expected output, on the error stream:

```
INFO demo: starting with 3 rows
ERROR demo: fetch failed for https://example.invalid/x
```

**Technique 2: a function with a hint, a docstring and a tested example.** Here is a worked example of the time conversion technique. It uses a fixed offset, so it runs without any extra packages. It is not the function your squad needs. Read it, then write your own version with your own names:

```python test
from datetime import datetime, timedelta, timezone

def shift_to_utc(local_text: str, hours: int, minutes: int) -> str:
    """Pure: a local time with a fixed offset becomes UTC text."""
    offset = timedelta(hours=hours, minutes=minutes)
    aware = datetime.fromisoformat(local_text).replace(tzinfo=timezone(offset))
    return aware.astimezone(timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")

assert shift_to_utc("2026-12-01T18:30:00", 5, 30) == "2026-12-01T13:00:00Z"
assert shift_to_utc("2026-12-01T00:10:00", -5, 0) == "2026-12-01T05:10:00Z"
```

Line by line:

- `def shift_to_utc(local_text: str, hours: int, minutes: int) -> str:` declares the inputs with their types, and says the result is a string.
- The docstring says the function is pure. It reads only its inputs.
- `timedelta(hours=hours, minutes=minutes)` is the offset as a duration.
- `fromisoformat(...)` reads the text as a naive datetime. `.replace(tzinfo=...)` attaches the offset, which makes the value aware.
- `astimezone(timezone.utc)` converts to UTC. `strftime(...)` writes the text, with the literal `Z` at the end to mark UTC.
- The two `assert` lines are the tests. If either is wrong, the block fails when the book is built.

**Named zones on Windows.** For a named zone such as `Asia/Kolkata`, use `zoneinfo.ZoneInfo("Asia/Kolkata")` instead of a fixed offset. On Windows, Python may not find the zone database, and then it raises `ZoneInfoNotFoundError`. The fix is `pip install tzdata`, and then pin `tzdata` in `requirements.txt` so that every squad member has it.

**Stage 1: write the signature and docstring first.** Before any logic, write the shape of your function. The template has the parts every function needs:

```python
def your_function_name(argument: str) -> str:
    """One sentence: what it does and what it returns."""
    # your steps go here
```

Choose the names and types that match your function. Keep it pure where you can. A pure function is easy to test, because the same input always gives the same output.

**Stage 2: add the steps and the logging.** Inside the function, write the steps one at a time. Use `log.info` for normal progress and `log.error` for a failure, with the reason in the message. Do not use `print`. Do not write `except:` on its own line. Name the exception you expect, for example `except requests.RequestException as exc:`.

The five assigned functions each have one job. `fetch_json` makes the HTTP request and returns the decoded JSON. `parse` picks the fields out of that JSON into rows. `to_utc_iso` converts one time to UTC text. `check_units` checks that values are in the units your data dictionary promises (for example, flags a value outside a plausible range), and logs a WARNING when one is not. `save_rows` writes the header and rows to the CSV. A sixth function, `main() -> int`, sets up logging once, calls the others, catches the expected errors, logs them at ERROR and returns 0 or 1. The file ends with `if __name__ == "__main__":` followed by `raise SystemExit(main())`, which is what makes `python -m citypulse.fetch` run it.

```trace
local = "2026-12-01T18:30:00"
offset = timedelta(hours=5, minutes=30)
aware = datetime.fromisoformat(local).replace(tzinfo=timezone(offset))
utc = aware.astimezone(timezone.utc)
text = utc.strftime("%Y-%m-%dT%H:%M:%SZ")
STEPS:
1 :: (nothing yet) :: The names datetime, timedelta and timezone are loaded.
2 :: local="2026-12-01T18:30:00" :: The local time is still plain text.
3 :: local="2026-12-01T18:30:00"; offset=5h30m :: The offset is the gap between IST and UTC.
4 :: aware=2026-12-01 18:30 at +05:30 :: The value now knows which zone it belongs to.
5 :: utc=2026-12-01 13:00 at UTC :: astimezone subtracts the offset, so 18:30 IST is 13:00 UTC.
6 :: text="2026-12-01T13:00:00Z" :: strftime writes the text, with the Z that marks UTC.
```

#### Y2-T11.4: Parity check against bash

**Goal.** The bash and Python outputs for the same hour match after sorting.

**Technique: converting bash times to UTC with GNU date.** The `-d` option reads a date and time text. The `TZ=` prefix sets the zone that the text is in, so a time without an offset is read in that zone:

```bash
TZ=Asia/Kolkata date -u -d "2026-12-01T18:30:00" +%Y-%m-%dT%H:%M:%SZ
```

Expected output: `2026-12-01T13:00:00Z`. Line by line: `TZ=Asia/Kolkata` sets the zone for this command. `date -u` prints in UTC. `-d` gives the time to read. The `+%Y-%m-%dT%H:%M:%SZ` part is the output format; the `Z` is written as plain text. If `TZ=Asia/Kolkata` is not understood on your Git Bash, use the POSIX form `TZ=IST-5:30` instead, where the sign is reversed on purpose and means five and a half hours ahead of UTC.

**Stage 1: produce the two files.** Run the bash fetcher for one hour, using the command your squad's README gives. Save its output as `bash_raw.csv`. Run the Python fetcher and copy its output file to `py.csv`. Do not edit the bash script.

**Stage 2: convert the bash timestamps.** Keep the header, convert each data line, and write the result to `bash_utc.csv`:

```bash
{
  head -1 bash_raw.csv
  tail -n +2 bash_raw.csv | while IFS=, read -r ts rest; do
    echo "$(TZ=Asia/Kolkata date -u -d "$ts" +%Y-%m-%dT%H:%M:%SZ),$rest"
  done
} > bash_utc.csv
```

Line by line:

- `{ ... } > bash_utc.csv` groups the commands and writes all their output to one file.
- `head -1` prints the header.
- `tail -n +2` prints from line 2 onwards, so the header is not converted.
- `while IFS=, read -r ts rest` reads each line, splitting only at commas. `ts` gets the first field and `rest` gets the others.
- The `date` call converts `ts` and `echo` writes the new timestamp, a comma and the rest of the line.

Check the result with `head -3 bash_utc.csv`. The timestamp column should now end in `Z`. If `date` prints an error, the timestamp in your bash output is not in a format `date -d` reads. Adjust the timezone part of the command, not the data.

**Stage 3: sort and diff until empty.** Run TC3:

```bash
diff <(sort bash_utc.csv) <(sort py.csv)
```

Expected output: nothing. If lines differ, fix the Python. Common fixes are the zone used for the Python timestamps, the number of decimal places, or the column order. Agree the number format with your squad and record it in the data dictionary. Run the command again after every fix until nothing prints.

### Defend it in the viva

**1. Why is your function a separate function rather than part of another one?**

:::answer Model answer
A good answer names the single responsibility. For example: "This function only converts one time string to UTC. It does not fetch or write anything. Because it has one job, I can test it with a fixed input and a fixed expected output, and a change to the time format touches only this function." Keep the answer to the job, the input, the output and the test.
:::

**2. What is a trade-off in raising an error from `fetch_json` instead of returning an empty result?**

:::answer Model answer
The trade-off is more code for the caller, because it must catch the error. The benefit is that a network failure cannot look like "no data". An empty result would let the run finish with exit code 0 and an empty file, and nobody would notice until a chart was wrong. Raising the error keeps the failure visible in the log and in the exit code.
:::

**3. What did you personally do in this ticket?**

:::answer Model answer
A strong answer names your function, its input and output, the one test you ran on it, and the commit that holds your change. Then it says what you changed after review and why. Use the commit hash and the test output as evidence. Do not describe work you did not do.
:::

**4. Why does the timestamp end in `Z`, and why is that not enough on its own?**

:::answer Model answer
The `Z` says the time is UTC, but it is only a label. If the value was local time when you wrote the `Z`, the label is wrong and the number is five and a half hours out for IST. The time must be converted to UTC first, and then the `Z` is correct. That is why the fix is to convert with an aware datetime and then format.
:::

**5. How do you know the fetcher fails correctly on a 404?**

:::answer Model answer
Run TC4 and read two things: the ERROR line, which must name HTTP 404 and the reason, and the exit code, which must be non-zero. The exit code comes from `main()`, which returns an integer that `SystemExit` passes to the shell. A common mistake is to return nothing, which exits with 0 and hides the failure.
:::
