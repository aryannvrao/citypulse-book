#### Y2-T22.1 Gate: trace binary search and state the invariant

**Goal.** Be able to explain, on a board, what each line of a binary search does and what stays true during the loop. This is the invariant: a fact that holds before and after every loop step.

**Technique.** The function below finds the first index where a value is at least `target` in a sorted list. The range from `lo` to `hi` is half-open: `hi` is one past the last index. The invariant is "the answer lies between `lo` and `hi`, and `hi` itself may be the answer". Follow the walk-through below to see the range shrink.

```python
def first_at_least(xs, target):
    lo, hi = 0, len(xs)
    while lo < hi:
        mid = (lo + hi) // 2
        if xs[mid] < target:
            lo = mid + 1
        else:
            hi = mid
    return lo
```

Walk through it with `xs=[1, 3, 3, 6, 9]` and `target=3`. The range starts as `lo=0`, `hi=5`. The middle is index 2, where `xs[2]` is 3. That is not less than 3, so `hi` moves to 2. The next middle is 1, where `xs[1]` is also 3, so `hi` moves to 1. The middle is 0, where `xs[0]` is 1, so `lo` moves to 1. Now `lo` equals `hi`, the loop stops, and the function returns 1.

Line by line: `while lo < hi:` repeats while the range is not empty. `mid = (lo + hi) // 2` picks the middle, and `//` drops any fraction. The `if` decides which side keeps the answer.

**Test it.** Trace on paper with `xs=[2, 4, 4, 7]` and `target=4`. You should get 1. Then try `target=8`. You should get 4, which means "past the end".

**State the invariant out loud.** Say it in one sentence: "Every index before `lo` holds a value less than the target, and the answer is never before `lo`."

#### Y2-T22.2 Solve six DSA-3 problems with recursion and search

**Goal.** Six small solutions, each with a clear signature, a complexity header, a base-case comment for any recursive function, and at least three tests: empty input, one item, and duplicates.

**Technique 1, recursion with a base case.** Write the base case first, then the smaller step. Here is a fictional example that counts values above a limit:

```python test
# Fictional example: count readings above a limit.
def count_above(values, limit):
    # Base case: an empty list has nothing above the limit.
    if not values:
        return 0
    first = 1 if values[0] > limit else 0
    return first + count_above(values[1:], limit)

assert count_above([], 5) == 0
assert count_above([7], 5) == 1
assert count_above([3, 6, 6, 1], 5) == 2
assert count_above([5, 5], 5) == 0
print("ok")
```

Line by line: `if not values:` is True for an empty list, so the function returns 0 without calling itself. `values[1:]` is the rest of the list, one item shorter. The asserts check the empty case, one item, duplicates and a value equal to the limit. The block prints `ok` and exits with no error.

**Technique 2, merge sort.** Merge sort splits a list in half, sorts each half the same way, then merges the two sorted halves. Practise the merge loop first, with `i` and `j` pointers, and check it with asserts such as `merge([1, 4], [2, 3]) == [1, 2, 3, 4]`.

**Technique 3, linked lists.** A linked list is a chain of nodes. Each node holds a value and a reference to the next node, and the last node's reference is `None`. Practise walking the chain with `while node is not None:` and moving on with `node = node.next`. Test the empty list (head is `None`), one node, and repeated values.

**Technique 4, binary search.** Use the invariant from stage 1. Test the empty list, one matching item, one non-matching item, and duplicates.

:::trap Recursion depth
Python stops after about 1000 nested calls with `RecursionError`, even when your base case is correct. A recursive function that peels one item at a time, like `count_above`, fails on a list of 5000 items. Recursion that halves the input, like merge sort, only goes about log n deep, so it is safe.
:::

For each problem, write the signature, a complexity header such as `# Complexity: O(log n) time, O(1) space`, the base case, the step, then the tests.

**Test it.** If you write your tests with `unittest` (files named `test_*.py`), run `python -m unittest discover` in that folder and the output ends with `OK`. #### Y2-T22.3 Build first_crossing.py

**Goal.** A file, `applied/first_crossing.py`, with three functions, `scan`, `build` and `query`. Running it prints `scan and bisect agree`.

**Technique 1, running maximum.** Passing `max` to `accumulate` gives the largest value so far at each step. Try it on fictional hourly readings:

```python
from itertools import accumulate

readings = [4, 2, 9, 5, 12]
print(list(accumulate(readings, max)))
```

Line by line: `accumulate(readings, max)` gives one output per item, each the maximum so far. `list(...)` turns it into a list. Expected output: `[4, 4, 9, 9, 12]`, which never goes down.

**Technique 2, bisect_left.** `bisect_left(sorted_list, x)` returns the first index where `x` fits in a sorted list, which for a monotonic list is the first index whose value is at least `x`. Try it:

```python
from bisect import bisect_left

levels = [4, 4, 9, 9, 12]
print(bisect_left(levels, 9))
print(bisect_left(levels, 13))
```

Expected output: `2`, then `5`. The index 5 is one past the end, which means the value is never reached.

**Technique 3, the skeleton.** Create `applied/first_crossing.py` with the three signatures. Leave the bodies for you to write:

```python
from bisect import bisect_left
from itertools import accumulate


def scan(values, ts, threshold):
    """Return the first timestamp whose value is at least threshold, or None. O(n)."""
    ...


def build(values):
    """Return the running maximum of values. O(n) once."""
    ...


def query(run_max, ts, threshold):
    """Use bisect_left on run_max. Return ts[i], or None when i is past the end. O(log n)."""
    ...
```

The `...` is a placeholder that does nothing. Write `scan` with a loop over `zip(values, ts)`, `build` with `accumulate`, and `query` with `bisect_left`. Check the index before you read `ts`.

```flow
TITLE: Build once, then answer many questions
NODES: Raw readings | Running maximum | bisect_left | Answer
STEPS:
1>2 :: build :: accumulate turns the readings into a list that never goes down.
2>3 :: query :: bisect_left searches that sorted list for the threshold.
3>4 :: index :: The index becomes a timestamp, or None if it is past the end.
4>3 :: next question :: The same running maximum answers the next threshold with no rebuild.
```

**Technique 4, the assertions.** Below the functions, add asserts that compare `scan` and `query` for thresholds 150, 200, 230 and 10000 on a small list you make yourself. End with `print("scan and bisect agree")`, which runs only when every assert passes.

**Test it.** Add an empty list case and a case where the first value already crosses. Both must still agree.

#### Y2-T22.4 Benchmark with timeit on 1M rows

**Goal.** Measured numbers, not estimates, for the build time, the scan time per query and the bisect time per query, on 1M rows.

**Technique 1, timeit.** `timeit.repeat(fn, repeat=5, number=100)` runs `fn` 100 times, five times over, and returns five totals in seconds. Take the minimum, because the lowest total is the least disturbed by other programs, and divide by `number`:

```python
import timeit

def double(x):
    return x * 2

totals = timeit.repeat(lambda: double(21), repeat=5, number=100)
per_call = min(totals) / 100
print(per_call)
```

Line by line: `lambda: double(21)` wraps the call so `timeit` can run it. `min(totals) / 100` gives the time for one call in seconds, printed as a small number such as `1.2e-07`.

**Technique 1b, the data.** Make 1M fictional rows yourself, for example with `random.seed(1)` and `random.randint(0, 300)` for each value, plus an increasing list of hourly timestamps. Seeding makes the data repeat on every run. Time the scan with a threshold that is reached late or never (such as 10000), because that is the slowest case for a scan. Keep the scan's `number` small (for example 5), since each call walks 1M rows.

**Technique 2, units.** Build time is one call, so use `number=1` and take the minimum as `build_s`. Multiply seconds by 1000 for `scan_ms` and by 1,000,000 for `bisect_µs`. For the break-even formula, every value must be in seconds:

q = build_s / (scan − bisect)

The formula holds because after `q` queries, scanning costs `q × scan` and the preprocessed version costs `build_s + q × bisect`. Those are equal at the break-even point. Fictional example: `build_s` 0.5, scan 0.002 seconds and bisect 0.000002 seconds give q = 0.5 / 0.001998, about 250. Mixing milliseconds and microseconds gives an answer a thousand times off, so convert first.

**Technique 3, the machine note.** Record `platform.platform()` and `sys.version` in the README, and close heavy programs before timing.

**Test it.** Run the benchmark twice and expect close numbers.

### Defend it in the viva

The trainer asks five questions. Each model answer explains the reasoning. Use your own experience in your own answer.

**Question 1. Why must the query use a running maximum rather than the raw readings?**

:::answer Model answer
Binary search needs a sorted or monotonic sequence. The raw readings go up and down, so searching them can return a wrong index with no error. The running maximum never goes down, so `bisect_left` finds its first crossing in O(log n).
:::

**Question 2. What is the trade-off of preprocessing once?**

:::answer Model answer
You pay the build cost once, and then each query is cheap. The break-even value q says how many queries it takes to pay off. Few queries favour a plain scan.
:::

**Question 3. What does the base case in a recursive function protect against?**

:::answer Model answer
The base case is where the function returns without calling itself. Without it, the calls never stop and Python raises `RecursionError`. Test the empty and single-item inputs to check it is reached.
:::

**Question 4. How did you make sure your benchmark numbers are real measurements?**

:::answer Model answer
Name the steps: `timeit` with at least 5 repeats, the minimum taken, units checked before the break-even formula, and the machine recorded. Say what you changed if the first run was noisy. Never present a number you did not measure.
:::

**Question 5. What did you personally write, and how would you test it?**

:::answer Model answer
Name the parts you wrote, the commits that show them, and the tests you added first. Then say what you would change next time. The examiner checks that you can explain each line you wrote.
:::
