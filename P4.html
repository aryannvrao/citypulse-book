What you are building

Someone opens a web page, picks one of six monitoring stations in the city and chooses how many hours ahead to look, from 1 to 48. The page draws a line of predicted PM2.5 values for each hour. PM2.5 means fine particles in the air, small enough to reach your lungs, and it is measured in micrograms per cubic metre (written µg/m³). The page shows the highest predicted value, a label such as Moderate or Unhealthy, and one plain sentence of advice.

Behind the page, a service answers requests with the same numbers. Every change you push to the shared code repository is tested, and if the tests pass, the service is rebuilt and put online without a manual step. The model, the tests and the live service all come from one set of files.

Starting from zero

This project uses many tools. Each one below is explained from nothing, with the Day chapter in this book that teaches it in depth. The source for this project does not state the day number for each tool, so each entry names the topic and the chapter that covers it.

Terminal, command and file. The terminal is a text window where you type instructions to your computer. Each instruction is a command. A file is a named block of data on disk, such as readings.csv, which is a plain-text table where each line is a row and each comma separates two columns. Almost every step in this project is typed into a terminal, so keep one open in the forecaster folder. Covered in the Day chapter on the terminal and Git.

Python, variables and functions. Python is the programming language the project is written in. A variable is a name that holds a value, such as horizon = 12. A function is a named block of code that takes inputs and returns an output. The project defines functions such as load() and forecast(). Covered in the Day chapter on Python for engineers.

pandas. pandas is a library, meaning a package of ready-made code you install and import. It works with tables, which pandas calls DataFrames. A DataFrame has named columns, and a single column is called a Series. The project uses pandas to read the CSV, filter rows and group numbers by station. Covered in the Day chapter on data with pandas.

matplotlib. matplotlib draws charts and can save them as image files. It is used in chart.py. Covered in the Day chapter on charts.

scikit-learn. scikit-learn is a library of machine-learning models. A model is a piece of code that learns a pattern from examples and then predicts a value for new inputs. Here, the examples are past readings with their features, and the prediction is the next hour's PM2.5. scikit-learn provides the two models compared in this project, a RandomForest and a GradientBoosting model, and the cross-validation tools. Covered in the Day chapter on machine learning.

FastAPI, Uvicorn and Pydantic. An API is a set of addresses on a server that other programs call to ask for data. A server is a program that sits and waits for requests. An endpoint is one address with a defined job, such as /stations. FastAPI is a library for writing endpoints in Python. Uvicorn is the program that runs FastAPI and listens for requests. Pydantic checks that incoming data has the right shape and values, and it is what returns the 422 errors you will see. Covered in the Day chapter on APIs.

Streamlit. Streamlit turns a Python script into a web page with widgets such as dropdown lists and sliders. Each time a user changes a widget, Streamlit runs the script again from the top. Covered in the Day chapter on dashboards.

transformers, torch and Qwen2.5. transformers is a library for language models. torch is the maths library underneath it. Qwen2.5-0.5B-Instruct is a small language model, with about half a billion parameters (the numbers inside the model that were learned during training), that is trained to follow instructions. It is small enough to run on a normal processor with no graphics card, and it is free. Covered in the Day chapter on language models.

joblib. joblib saves a Python object, such as a trained model, to a file and loads it back later. Covered in the Day chapter on saving models.

pytest. pytest runs functions whose names start with test_ and reports which ones passed. A test passes when every assert line inside it is true. Covered in the Day chapter on testing.

Docker. Docker builds a container, which is a sealed package containing an app, its libraries and the operating-system parts it needs. The same container runs the same way on your laptop and on a cloud machine. Covered in the Day chapter on containers.

GitHub Actions, CI and CD. Git records changes to files. GitHub is a website that hosts Git repositories. GitHub Actions runs a list of steps on a fresh machine each time something happens, such as a push. CI (continuous integration) means running the tests on every change. CD (continuous deployment) means automatically putting a tested change into use. Covered in the Day chapter on CI/CD.

curl and jq. curl sends a web request from the terminal. jq reads JSON, which is the text format used for API replies, made of key and value pairs in curly braces. Covered in the Day chapter on APIs.

Step 2: Ingest a month of readings. The goal is a known dataset with planted faults. The generator script is make_data.py. The source shows its core lines, with indentation restored:

rush = 1.35 if 6 <= hod <= 10 or 17 <= hod <= 21 else 0.8
temp = 18 + 7 * sin((hod - 9) / 24 * 2 * pi) + gauss(0, 1.2)
wind = max(0.2, 2.5 + gauss(0, 1.1))  # disperses PM2.5
for s, base in STATIONS.items():
    val = (base + 9 * gauss(1, .18) * rush
           + .25 * (humidity - 60) - 3.1 * wind + gauss(0, 3))
    rows.append([s, ts, "pm25", round(val, 1),
                 temp, humidity, wind])
rows += [["ST-02", ..., -4.0], ["ST-09", ...], ["ST-01", "not-a-date", ...]]

rush is a multiplier of 1.35 during the morning hours from 6 to 10 and the evening hours from 17 to 21, when traffic is heavy, and 0.8 at other times. if ... else is Python's way of choosing between two values. temp is a daily temperature curve: sin is the sine function, which rises and falls smoothly, and 2 * pi makes one full cycle per day. gauss(0, 1.2) draws a random number from a bell curve with mean 0 and spread 1.2, which adds natural-looking noise. wind is never below 0.2, because max returns the larger of its two inputs. The for loop visits each station and its base level. round(val, 1) keeps one decimal place. rows.append adds one row to a list, and rows += adds several rows at once.

The three bad rows use ... where the source omits the other columns. The first has a negative value, the second has a station code that does not exist, and the third has a timestamp that is not a date. These are the faults the cleaner must catch.

The source excerpt does not show a random seed. A seed is a fixed starting point for random numbers, and with one set, every run produces the same data. If your file differs from the course numbers in later steps, use the file you were given. Run the script with:

python make_data.py

You should see wrote data/readings.csv: 4323 rows. That is 4320 good rows (6 stations times 720 hours, which is 30 days) plus 3 bad ones. The file must be written into a folder called data, so create that folder first.

Step 3: Clean and validate. The goal is one function that loads the file and removes the bad rows. Here is load(), with indentation restored:

def load(path="data/readings.csv"):
    df = pd.read_csv(path)
    df["ts"] = pd.to_datetime(df["ts"], errors="coerce")
    before = len(df)
    df = df[df.station_id.isin(STATIONS)]
    df = df[df.value.between(0, 500)]
    df = df.dropna(subset=["ts"]) \
           .drop_duplicates(["station_id", "ts"])
    print(f"clean: {before} -> {len(df)} rows")
    return df.sort_values(["station_id", "ts"])

def load(path=...) defines a function called load. The value after = is a default, used when the caller gives no path. pd.read_csv reads the file into a DataFrame, and df is the usual name for it. pd.to_datetime turns text into real timestamps. errors="coerce" tells it to set any value it cannot read to NaT, which means "not a time", rather than stopping. before records the row count so it can be printed later. df[df.station_id.isin(STATIONS)] keeps only rows whose station is one of the six known ones. between(0, 500) keeps values from 0 to 500 inclusive. dropna(subset=["ts"]) removes rows whose timestamp is NaT. drop_duplicates keeps the first row for each station and time pair. The backslash at the end of a line tells Python that the statement continues on the next line, so the chained method calls read as one step. sort_values puts the rows in order by station, then by time.

Run it with python pipeline.py. The source shows the output clean: 4323 -> 4320 rows (3 dropped). This proves the cleaner removed exactly the three planted bad rows, and no good ones.

Step 4: Guard it with a data-quality gate. The goal is to turn your assumptions into checks that stop the program. Here is the gate:

def dq_gate(df):
    assert df.value.min() >= 0,   "negative reading"
    assert df.value.max() <= 500, "out-of-range"
    assert df.groupby(["station_id", "ts"]) \
             .size().max() == 1,  "duplicate"
    assert set(df.station_id) <= STATIONS, "unknown"
    print(f"data-quality checks: 4 passed")

assert is a Python statement that checks a condition. If the condition is false, Python stops with an AssertionError and shows the text after the comma, such as negative reading. The first two lines check the value range. The third groups by station and time and checks that no group has more than one row, using size() to count rows per group and max() to find the largest count. The fourth checks that every station code is in the set of six known codes. <= on sets means "is a subset of".

When you run python pipeline.py, you should see data-quality checks: 4 passed (4320 rows). Be aware that the printed code in the source says only 4 passed. The row count in the output does not come from this code, so if you want it, add len(df) to the print. The count of 4 is typed into the text, not calculated, so it prints 4 passed even if a check were removed. That is a trap, covered below.

Step 5: Aggregate per station. The goal is one summary row per station. Here is the function:

def per_station(df):
    return (df.groupby("station_id")["value"]
              .agg(["count", "mean", "max"]).round(1))

groupby("station_id") splits the rows into one group for each station. ["value"] selects the PM2.5 column. agg(["count", "mean", "max"]) calculates three summaries for each group, the number of rows, the average and the highest value. round(1) rounds the table to one decimal place. The parentheses around the whole expression let the chained calls run across several lines.

Run python pipeline.py and you should see a table:

            count  mean   max
station_id
ST-01         720  46.2  66.9
ST-02         720  59.4  76.0
ST-04         720  65.2  82.3
ST-06         720  74.6  90.7

Each station has 720 readings, which is 30 days of 24 hours. ST-06 has the highest mean, 74.6 µg/m³, so it is the dirtiest station in this dataset. This table is what the /stations endpoint returns later.

Part B: Visualise and model

Step 6: Chart the trends. The goal is a PNG chart of a six-hour average for each station. Here is chart.py:

import matplotlib; matplotlib.use("Agg")   # headless
import matplotlib.pyplot as plt
from pipeline import load
df = load().set_index("ts")
fig, ax = plt.subplots(figsize=(7.2, 3.1))
for sid, g in df.groupby("station_id"):
    ax.plot(g.value.resample("6h").mean(), label=sid)
ax.set_ylabel("µg/m³"); ax.legend(ncol=6, fontsize=7)
fig.tight_layout(); fig.savefig("trend.png", dpi=110)

The first line uses a semicolon to put two statements on one line. matplotlib.use("Agg") selects a drawing mode that writes to files and never opens a window, which is why it is marked # headless. A # starts a comment, which Python ignores. from pipeline import load reuses the cleaner, so the chart and the model share one definition of clean data. set_index("ts") makes the timestamp the row label, which resample needs. plt.subplots creates a figure, the whole image, and ax, the axes, the area with the lines. figsize=(7.2, 3.1) sets the width and height in inches. The for loop draws one line per station. resample("6h").mean() groups the readings into six-hour blocks and averages each block. label=sid names the line for the legend. ncol=6 puts the legend in six columns, and fontsize=7 makes its text small. tight_layout removes extra white space, and savefig writes the file, with dpi=110 setting its resolution in dots per inch.

Run python chart.py. The output shows the cleaning line from the import, then wrote trend.png. The source reports the file size as 124 KB. The import prints the cleaning line because load() prints when it runs. The result is a picture with six coloured lines across the 30 days.

Step 7: Engineer features. The goal is to turn each row into the numbers a model can learn from. Here is features.py:

FEATURES = ["hour", "dow", "lag1", "lag24", "roll3",
            "temp_c", "humidity", "wind_ms"]
def build_features(df):
    df = df.sort_values(["station_id", "ts"]).copy()
    g = df.groupby("station_id")["value"]
    df["hour"] = df.ts.dt.hour
    df["dow"]  = df.ts.dt.dayofweek
    df["lag1"]  = g.shift(1)         # previous hour
    df["lag24"] = g.shift(24)        # same hour, yesterday
    df["roll3"] = g.shift(1).rolling(3).mean()
    return df.dropna(subset=FEATURES)

A feature is an input column for the model. FEATURES is a list of their names, and it is written once so that training and forecasting use the same order. .copy() makes a separate copy, so the function does not change the caller's DataFrame. g is the PM2.5 column grouped by station. ts.dt.hour reads the hour of day from a timestamp, and dt.dayofweek gives the day of the week, with Monday as 0. shift(1) moves every value down one row, so each row sees the previous value. Because g is grouped, the shift happens inside each station, so one station's values never leak into another's. lag1 is the previous hour's reading and lag24 is the reading from the same hour yesterday. rolling(3).mean() averages each set of three values, and it is applied after shift(1), so the average covers the three hours before the current row, not the current row itself. dropna removes rows that are missing any feature, which are the first rows of each station where there is no history yet.

The weather columns temp_c, humidity and wind_ms are already in the file, so they are listed in FEATURES and used as they are.

Run the example with:

python -c "from features import *; from pipeline import load; print(build_features(load())[['hour','lag1','lag24','roll3','value']].head(4))"

python -c runs the code inside the quotes, instead of a file. Each part separated by a semicolon is a statement. import * brings in every name from a module. head(4) shows the first four rows. The source shows the output as a small table of hour, lag1, lag24, roll3 and value. The values depend on your data, so compare the shape of the table rather than each number. The source reports 4176 rows. That is 4320 minus 144, which is 24 rows removed for each of the six stations, because each station needs 24 hours of history before lag24 exists. This is the arithmetic you should be able to explain at the viva.

Step 8: Cross-validate two models. The goal is to compare the two models on data they were not trained on, using ordered time folds. Here is the comparison:

tscv = TimeSeriesSplit(n_splits=5)
cands = {
  "RandomForest": RandomForestRegressor(
      n_estimators=200, max_depth=12, random_state=20),
  "GradientBoosting": GradientBoostingRegressor(
      n_estimators=300, max_depth=3,
      learning_rate=0.05, random_state=20)}
for name, est in cands.items():
    cv = -cross_val_score(est, Xtr, ytr, cv=tscv,
            scoring="neg_mean_absolute_error")
    print(f"{name} CV MAE {cv.mean():.3f} +/- {cv.std():.3f}")

Cross-validation means splitting the data into parts, training on some and testing on the rest, and repeating so every part is tested once. TimeSeriesSplit(n_splits=5) makes five splits in time order. Each test block comes after its training block, so the model is only scored on hours later than the ones it learned from. cands is a dictionary, which maps a name to a model object. n_estimators is the number of trees in a forest or boosting model. max_depth limits how deep each tree can grow. learning_rate controls how much each new tree corrects the previous ones. random_state=20 fixes the random choices, so results repeat. cross_val_score runs the five folds. scoring="neg_mean_absolute_error" asks for the negative of the mean absolute error, which is the average size of the miss, in the same units as the target. scikit-learn always maximises scores, so the minus sign in front turns it back into a positive error where lower is better. cv.mean() and cv.std() give the average and spread over the five folds. The :.3f in each f-string prints three decimal places.

The excerpt uses Xtr and ytr, which are the training inputs and targets. They are created by the chronological split in step 9. The loop in the source also needs a line that stores each mean in a dictionary called scores, because step 9 reads from it. The source excerpt does not show that line, so add scores[name] = cv.mean() inside the loop and create scores = {} before it.

Run python train.py. The source shows:

RandomForest      CV MAE 3.928 +/- 0.116
GradientBoosting  CV MAE 3.689 +/- 0.115

GradientBoosting has the lower average error, so it wins on cross-validated error. The spread of about 0.115 shows how much the score moved between folds.

Step 9: Train the winner and evaluate it. The goal is an honest score on the last 20 per cent of time. Here is the code:

best = min(scores, key=scores.get)
model = cands[best].fit(Xtr, ytr)
pred = model.predict(Xte)
mae = mean_absolute_error(yte, pred)
r2  = r2_score(yte, pred)
print(f"best={best}  holdout MAE {mae:.2f}  R2 {r2:.3f}")

min(scores, key=scores.get) returns the key, which is the model name, with the lowest value. fit trains the model on the inputs and targets, and returns the trained model. predict returns the model's guesses for new inputs. Xte and yte are the last 20 per cent of the rows in time order, which the model never saw. mean_absolute_error gives the average miss in µg/m³. r2_score is the R-squared value, a score that is 1.0 for perfect predictions, near 0 for a model no better than always guessing the average, and can be negative for a worse one.

Run python train.py. The source shows best=GradientBoosting holdout MAE 3.55 µg/m³ R2 0.864. On future hours, the model is on average 3.55 µg/m³ away from the true reading, and it explains 86.4 per cent of the variation in the data. That is the number you quote in the viva.

Step 10: Write the model card. The goal is to save the model together with a record of how it was chosen. Here is the code:

imp = dict(sorted(zip(FEATURES,
    model.feature_importances_.round(3)),
    key=lambda kv: -kv[1]))
card = {"model": best, "features": FEATURES,
        "cv_mae": round(scores[best], 3),
        "holdout_mae": round(mae, 2),
        "holdout_r2": round(r2, 3), "importances": imp}
joblib.dump({"model": model, "features": FEATURES},
            "model.joblib")
json.dump(card, open("model_card.json", "w"), indent=2)

zip pairs each feature name with its importance score. sorted orders the pairs, and key=lambda kv: -kv[1] sorts by the importance, largest first. lambda is a short anonymous function, here one that returns the negated importance. dict(...) turns the sorted pairs back into a dictionary. card is a dictionary that will become the JSON file. joblib.dump saves the model and its feature list to model.joblib, so the service can load them later without retraining. json.dump writes the card as JSON, and indent=2 adds two spaces of indentation to make it readable.

Two details matter. The open("model_card.json", "w") call opens the file for writing and never closes it, which is a common trap; the safer form is with open(...) as f:, which closes the file automatically. Also, indent=2 only changes the layout, not the content.

Run cat model_card.json. The source shows:

 "holdout_mae": 3.55, "holdout_r2": 0.864,
 "importances": {"roll3": 0.587, "lag24": 0.26,
   "wind_ms": 0.086, "lag1": 0.027, "hour": 0.019}}

The source shows only five of the importances. Your file will list all eight features. The 3-hour trend, roll3, carries 0.587 of the importance, and yesterday's same hour, lag24, carries 0.26. Together they explain most of the forecast.

Step 11: Recursive multi-hour forecast. The goal is a forecast of many hours from one model. The model predicts one hour ahead, so the code feeds each prediction back in. Here is forecast.py:

def forecast(df, station, horizon=12):
    h = df[df.station_id == station]
    hist = list(h.value.tail(24)); last = h.iloc[-1]
    ts = last.ts; out = []
    for _ in range(horizon):
        ts = ts + timedelta(hours=1)
        row = {"hour": ts.hour, "dow": ts.dayofweek,
               "lag1": hist[-1], "lag24": hist[-24],
               "roll3": mean(hist[-3:]), **weather}
        p = round(float(_model.predict([row])[0]), 1)
        out.append({"ts": ts, "pm25": p}); hist.append(p)
    return out

horizon=12 is a default argument, so the function forecasts 12 hours unless told otherwise. h holds one station's rows. tail(24) takes the last 24 readings, which is the history needed for lag24. hist is a list that holds the past values, and it grows as predictions are added. iloc[-1] takes the last row. timedelta(hours=1) is a time step of one hour, and ts = ts + ... moves the time forward. Inside the loop, hist[-1] is the newest value, which becomes lag1, and hist[-24] is the value 24 steps back, which becomes lag24. **weather adds the weather values held in a dictionary named weather, using the double star to spread the dictionary's keys into the row. float(...) converts the model's numpy number into a normal Python number, and [0] takes the first prediction from a list of one row. out.append records the forecast, and hist.append(p) feeds the prediction back in, so the next hour's features are built from it.

The source excerpt uses weather, _model, mean and timedelta without showing where they are defined. timedelta comes from the datetime module, mean from the statistics module, and _model and weather are set elsewhere in the file. Check that each one exists before you run this.

The source shows the output as two lines:

ST-06 next-6h: 69.8, 67.1, 65.8, 63.0, 60.1, 59.1
ST-03 next-6h: 40.7, 37.5, 35.1, 35.5, 35.9, 36.2

The ST-06 curve falls steadily from its starting level, which is the decay the source describes. The weather values are held at the last known reading for every hour, which is a simplification you should mention in the viva.

Trap: Feeding predictions forward

A forecast this far ahead rests on earlier guesses. Each error is passed into the next hour's features, so small mistakes can build up. This is why the forecast gets less reliable as the horizon grows.

Here is the loop in a simplified form, with a toy stand-in for the model, which is the average of the last three values. Watch how hist grows and how each prediction becomes the input for the next one.

Step 14: Forecast, with validation. The goal is a POST endpoint that checks its input. Here is the code:

class ForecastIn(BaseModel):
    station: str = Field(pattern=r"^ST-0[1-6]$")
    horizon: int = Field(default=12, ge=1, le=48)
@app.post("/forecast")
def do_forecast(q: ForecastIn):
    fc = forecast(_df, q.station, q.horizon)
    peak = max(fc, key=lambda r: r["pm25"])
    return {"station": q.station, "peak":
            {**peak, "category": category(peak["pm25"])},
            "forecast": fc}

class ForecastIn(BaseModel) defines the shape of the request body. BaseModel comes from Pydantic. station: str says the value must be text. Field(pattern=...) adds a rule. The pattern ^ST-0[1-6]$ is a regular expression, a compact rule for text. ^ means the start, $ means the end, and [1-6] means one character from 1 to 6, so only ST-01 to ST-06 are accepted. horizon: int must be a whole number. ge=1 means greater than or equal to 1, and le=48 means less than or equal to 48. @app.post is like get, but for requests that send data in their body. The parameter q: ForecastIn tells FastAPI to read the body, check it against the class, and pass the checked result in as q. max(fc, key=...) finds the forecast point with the highest value. {**peak, "category": ...} copies the peak dictionary and adds a category. The category is set by a helper function named category, which the source does not show in this step.

Send a valid request with:

curl -s -XPOST localhost:8000/forecast -d '{"station":"ST-06","horizon":12}'

-XPOST sets the request method to POST. -d sends the text in quotes as the body, and giving -d makes curl use POST anyway, so -X makes the choice explicit. You should see a reply beginning {"station":"ST-06", "peak":{"ts":"...","pm25":69.8,"category":"Unhealthy"}, followed by the twelve hourly values.

Now send two invalid requests. {"station":"ST-99"} fails the pattern, so the server returns status 422. {"horizon":99} fails in two ways, because station is missing and horizon is above 48, and it also returns 422. A 422 response contains a message that says which field failed and why. A status code is the number the server returns with every reply, where 200 means success, 422 means the input was not acceptable, and 500 means the server itself failed.

Trap: Quoting on Windows

In Windows PowerShell, the double quotes inside the JSON are read by the shell, and the request can fail with a message that looks like a server error. Run these commands in Git Bash, which is the Bash shell installed with Git for Windows, or escape each inner quote as \".

Part D: Plain-English advice

Step 15: Summary from a free CPU language model. The goal is one sentence of advice for each forecast peak. Here is insight.py:

tok = AutoTokenizer.from_pretrained(M)
llm = AutoModelForCausalLM.from_pretrained(M)
def summarise(station, peak, cat, horizon):
    msgs = [{"role": "system",
             "content": "Reply in ONE short sentence."},
            {"role": "user",
             "content": f"Next {horizon}h at {station} peaks at "
                        f"{peak} ug/m3 ({cat}). Advise residents."}]
    p = tok.apply_chat_template(msgs,
          tokenize=False, add_generation_prompt=True)
    ids = tok(p, return_tensors="pt")
    out = llm.generate(**ids, max_new_tokens=50,
                       do_sample=False)
    return tok.decode(out[0][ids.input_ids.shape[1]:],
                      skip_special_tokens=True).strip()

M is the model's name, Qwen/Qwen2.5-0.5B-Instruct. The source excerpt does not define it, so set M to that name before this code. AutoTokenizer splits text into the pieces, called tokens, that the model reads, and AutoModelForCausalLM loads the language model itself. from_pretrained downloads the files the first time you use it, which needs an internet connection once, and then reuses them. The msgs list is a conversation, where each entry has a role and content. The system message sets the behaviour, and the user message is the request. The f-strings insert the station, peak and category into the text. apply_chat_template formats the conversation the way this model expects. add_generation_prompt=True adds the marker that tells the model it should now answer. return_tensors="pt" returns PyTorch tensors, which are the numeric arrays the model uses. max_new_tokens=50 caps the reply at 50 new tokens. do_sample=False makes the model pick the most likely next token each time, so the same question gives the same answer. The last line cuts off the prompt from the output, decodes the rest back into text, skips special markers, and removes spaces at the ends.

The source runs python insight.py and shows two sentences, one for ST-06 at 69.8 (Unhealthy) and one for ST-03 at 40.7 (Moderate). Wording may differ on your machine, because the exact text depends on the model's version. What must hold is that the reply is a single short sentence that mentions the level.

Step 19: CI on every push. The goal is for GitHub to run the tests on each push. Here is the workflow, with indentation restored. YAML is a text format where indentation shows structure, and each indent must be made of spaces, not tabs.

  test:

name is the label shown in GitHub. on says what starts the workflow. Each item under steps is one action. uses runs a ready-made action, such as actions/checkout@v4, which downloads your code. The @v4 is the version. with passes settings to an action, here the Python version. run runs a shell command. Step 20: Continuous deployment. The goal is to build the image and publish it when the tests pass. Here is the second job, with indentation restored:

  deploy:
    needs: test                 # only if green
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "$TOKEN" | docker login ghcr.io
          -u ${{ github.actor }} --password-stdin

      - run: ./deploy.sh ghcr.io/$REPO:$SHA

This job sits at the same level as test, under jobs. needs: test means this job starts only after test finishes green, which is how the deployment is gated on the tests. The indented lines that wrap are plain YAML continuations, so each run: is one command. echo "$TOKEN" | docker login ghcr.io sends a password into the Docker login through the pipe, and --password-stdin tells Docker to read that password from standard input, rather than from the command line where it could be seen. ${{ github.actor }} is the user who pushed the change. $REPO and $SHA are the repository name and the commit identifier. ghcr.io is GitHub's container registry, a store for images. docker push uploads the image there, and ./deploy.sh runs a script that moves the running service to the new image.

The source shows $TOKEN without defining it. The token should come from GitHub's secrets store, written as ${{ secrets.NAME }} in the workflow, so the value never appears in the file. The source's deploy.sh is also not shown, so check what it does before you rely on it.

Challenge 1: Add a second pollutant (DATA, easy)

What is asked. Extend make_data.py and pipeline.py to also carry NO2 (nitrogen dioxide, a gas from vehicle exhaust), and make /stations aggregate per station and pollutant.

Done when test. "Done when: GET /stations returns both pm25 and no2 rows for every station, and the data-quality gate still passes."

Ideas you need. A long-format table with one row per reading, a pollutant column, and grouping by two columns.

Plan of attack. 1. Add NO2 rows to the data generator, using the same timestamps and stations, with its own pollutant label. 2. Mistakes that fail the test. Leaving the key as ["station_id", "ts"]. With two pollutants, drop_duplicates silently deletes every NO2 row, and if you fix only that call, the gate's duplicate check fails on every timestamp. The fix is to add the pollutant to every key. Another mistake is to return only the pm25 summary, which passes the tests but not the done-when.

Challenge 2: Beat the cross-validated error (MODEL, medium)

What is asked. Add lag48 and an is_weekend feature to features.py, and retrain so the winner's mean cross-validated error drops below the current baseline.

Done when test. "Done when: train.py prints a CV MAE under 3.689 µg/m³ and the model card records the improved score."

Ideas you need. How shift creates lag features, how a weekend flag is made from dow, and how FEATURES controls what the model sees.

Plan of attack. 1. Write lag48 the same way as lag24, using a shift inside each station's group. 2. Derive is_weekend from the day-of-week value, using a comparison that gives 1 or 0. 3. Add both names to FEATURES, and remember that dropna will remove more early rows. 4. Run train.py and compare the printed CV MAE for the winner against 3.689. 5. Check that model_card.json shows the new score and the new feature list.

Mistakes that fail the test. Changing FEATURES without making forecast.py supply the new columns. forecast() builds its own row, so a new feature missing from that row causes an error or a wrong prediction. Keep the two in step. The other trap is an is_weekend value that is a true/false column rather than 1 or 0, which some models handle badly. Finally, the health test expects the winner to be GradientBoosting, so if RandomForest wins, the test fails, and you must explain that in your viva rather than hide it.

Viva preparation

The capstone viva scores four things from 0 to 5 each: whether the acceptance criteria are met, your technical depth, your contribution and ownership of the work, and your understanding. What does your forecaster do, from the CSV to the chart on the page?

It loads 30 days of hourly readings for six stations, cleans them and checks them with a data-quality gate. It builds eight features per reading, trains a RandomForest and a GradientBoosting model, and keeps whichever has the lower cross-validated error. The winner is saved with a model card and served by FastAPI, and the Streamlit page calls the /forecast endpoint and draws the curve. The advice sentence comes from a small local language model.

Why use TimeSeriesSplit rather than a shuffled split?

A shuffled split would let the model train on hours that come after the hours it is tested on, which is cheating for a forecast. TimeSeriesSplit keeps the order, so each test block sits after its training block. This gives an honest estimate of how well the model predicts the future. The holdout test on the last 20 per cent of time adds a second, separate check.

Why did GradientBoosting win, and how do you know it is not luck?

On five time-ordered folds, its mean absolute error was 3.689 against 3.928 for the RandomForest, and its spread across folds was small, about 0.115. It was then trained on the first 80 per cent of time and scored on the last 20 per cent, where it reached a mean error of 3.55 µg/m³ and an R-squared of 0.864. Two separate checks agreeing is the reason I trust the choice. I would still say that five folds on one month of data is a small test.

How does the recursive forecast work, and what is its weak point?

The model predicts one hour ahead, and each prediction is added to the history. The next hour's lag1, lag24 and roll3 features are then built from the history, which includes the earlier predictions. Its weak point is that errors can build up over the horizon, and the weather values are held at their last known level, so long forecasts are less reliable than short ones.

What does the data-quality gate protect against, and what does it miss?

It stops the pipeline when a value is negative or above 500, when a station and time appear twice, or when a station code is unknown. This means a broken feed fails loudly before it can train a model or serve a forecast. It does not catch values that are plausible but wrong, such as a sensor stuck at a constant value, and the printed count of checks is typed text rather than a calculated result.

Why does the API load the data and model once at start-up?

Loading means reading a file from disk, and doing that on every request would make each reply slow. The data and card are read once when main.py starts, and the same objects serve every request afterwards. The trade-off is that a changed file is not seen until the server restarts, which is why --reload is used during development.

What does a 422 mean, and who decides it?

A 422 means the request was received but its content did not pass the rules, and the server returns a message naming the field. FastAPI decides it, using the Pydantic class ForecastIn, before my function runs. So ST-99 or a horizon of 99 never reaches the forecasting code, which is the point of validation at the edge.

Which part would you change for production, and what did you build yourself?

For production I would pin exact library versions, store secrets properly, add monitoring of the live error, and replace the file-based model card with a versioned store. What goes wrong

Mistake Symptom Fix
Running scripts from the wrong folder FileNotFoundError for data/readings.csv or model_card.json Open the terminal inside the forecaster folder and check with pwd (or cd on Windows) before running anything.
No data folder before make_data.py The script cannot write the CSV Create a folder called data first.
Shuffled cross-validation A CV error that looks much better than the holdout error Use TimeSeriesSplit, which keeps time order.
Lag columns made without shift Perfect-looking scores, because the model sees the answer Build lags with shift(1) and above, grouped by station.
Changing FEATURES in one file only Errors in forecast() or wrong predictions Keep training and forecasting on the same list, and update the row built in forecast().
Running Python with the -O flag The gate silently passes bad data, because asserts are removed Never use -O with this project. Use an explicit if and raise for checks that must always run.
Changing code but not the model /health and the card show stale results Run python train.py again after any change to features or models.
Binding the server to 127.0.0.1 in Docker Browser cannot reach localhost:8000 from outside the container Use --host 0.0.0.0 in the CMD line.
Quoted JSON in PowerShell curl returns an error reply instead of the forecast Use Git Bash, or escape the inner quotes.
Wrong YAML indentation GitHub rejects the workflow before any step runs Indent with spaces only, and keep each key under its parent.
