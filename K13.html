How to use these ticket guides

These chapters walk through the real tickets on your squad's capstone board, in the order the board schedules them. The ticket text (story, acceptance criteria, test cases, subtasks and definition of done) comes from the course site. The guides teach you how to do each ticket yourself and how your trainer will check it.

How the board works:

  • A ticket moves Backlog, To Do, In Progress, Review, Done. Only a trainer can move it to Done, after running its test cases, and gives it a gate score from 0 to 3.
  • Every ticket is judged from commit evidence: your commits, pull requests and reviews in the squad repository. Work done on someone else's laptop does not count for you.
  • Each ticket has a points value (the "pts" column). Defence tickets (marked D01, D02 and so on) are where you present and answer questions.
  • Your viva scores acceptance criteria met, technical depth, contribution and ownership, and understanding, each 0 to 5. The final capstone grade shown on the platform is 60% your own contribution and 40% your team's.
Tip: How to use a ticket guide

Read the guide the evening before the session that ticket is scheduled for. Do the work yourself, in your squad's repository, and run every test case in "How it is checked" before you ask the trainer to review it.

Y2-T47 · Prototype grounded GenAI city bulletin with number checker and policy

Session 47 · phase E9 · 3 points

The ticket in plain words

CityPulse turns Bengaluru's air-quality readings into daily statistics: averages, maximums and changes from the day before. BBMP's communications officer wants a short bulletin, in plain language, that residents can read. This ticket is a spike, a short experiment with one question: can a language model (LLM, a program that writes text from a prompt) write that bulletin safely?

The risk is that an LLM writes fluent sentences containing numbers that are not in the data. An invented figure is harder to spot than clumsy text. In 2023, Samsung staff pasted confidential code into a public chatbot, so the squad must also decide what data may leave CityPulse.

You will build three things: a function that computes the statistics, a prompt template and a call wrapper that records token usage, and a number checker that fails any bulletin with an unsupported number. You also write the squad's GenAI policy and estimate what one call costs. The output feeds /v1/bulletin in Y2-T48. If the checker fails, the endpoint serves a plain template bulletin instead.

Before you start

Merged to main before you begin:

  • Y2-T44: the continuous integration (CI) pipeline. Your grounding test must run inside it.
  • Y2-T45: the deployed API, with secrets read from environment variables and the cloud secret manager.
  • Y2-T46: the uptime alert and one service level objective (SLO).
  • The CityPulse SQL views for daily and ward aggregates, which supply your statistics.

Tools and accounts: Git for Windows (it includes Git Bash, where the commands below run; the lab's Linux machine works the same way), Python 3 with python -m pip install pandas pytest anthropic, GitHub access to the squad repository, and the key and approved model id your trainer issued. The key and the model id go only in a local .env file that Git ignores, as lines LLM_API_KEY=... and LLM_MODEL=.... The ticket names only LLM_API_KEY and not the provider, so the code here assumes Anthropic. Confirm the provider with your trainer before you install anything. If it is another provider, only the client lines in genai/llm.py change. If your approved model rejects the temperature argument, remove that one line and ask the trainer what to do.

How your trainer checks it

The six acceptance criteria are: at least three samples for three dates, each with stats, output, check and usage; each sample passes the checker or is a labelled FAIL; the grounding test passes offline; no key appears in the repository; the policy covers its required points; and the PR records tokens and cost per call with max_tokens set. TC1 to TC4 below prove most of them.

TC1: the checker on every sample. Run from the repository root:

for f in genai/samples/*.json; do python -m genai.check $f; done
  • for f in genai/samples/*.json; do loops over each sample file. The shell expands the pattern, and f takes each name in turn.
  • python -m genai.check $f runs the module genai.check with the file as its argument. -m finds the module from the repository root.
  • ; done ends the loop.

This is Bash syntax, so it works in Git Bash and on Linux, not in PowerShell. Passing looks like this, with one line per sample:

A labelled FAIL is also accepted. For example it prints FAIL ungrounded: 180, listing the numbers (the exact wording is your checker's own). Failures with other causes: a FileNotFoundError naming 'genai/samples/*.json' means no samples exist yet, so the shell passed the pattern through unchanged, and No module named genai means you are in a subfolder.

TC2: every bulletin number is in the stats or the date. The trainer lists the numbers and compares them with the stats block. To prepare, run grep -oE '[0-9]+(\.[0-9]+)?' genai/samples/DATE.json. -o prints each match on its own line, -E enables extended regular expressions, [0-9]+ matches digits, and (\.[0-9]+)? matches an optional decimal part. This lists every number in the whole file, including the stats, the date and the token counts, so look only at the ones that come from the bulletin text and tick each off against the stats block. Any number with no source is a failure, usually an invented figure or a rounding mismatch.

TC3: the grounding test runs offline.

env -u LLM_API_KEY pytest -q tests/test_grounding.py
  • env -u LLM_API_KEY runs the command with that one variable removed. Your shell keeps its key. Git Bash's env supports -u.
  • pytest -q runs the tests quietly. The path names the file.

Passing shows a summary such as 3 passed in 0.10s. ModuleNotFoundError: No module named 'genai' means bare pytest cannot see the repository root: add an empty conftest.py in the root, or a pytest.ini containing [pytest] and pythonpath = .. KeyError: 'LLM_API_KEY' during collection means the key is read at import time, so move the client into a function. A connection error means a test reaches the real provider.

TC4: no key in the repository.

git grep -nE '(sk-[A-Za-z0-9]{20,}|LLM_API_KEY=.+)' -- . ':!*.example'
  • git grep searches tracked files only, so git add new files first.
  • -n prints line numbers, and -E uses extended regular expressions.
  • The pattern matches sk- followed by twenty or more letters or digits, or LLM_API_KEY= followed by a value.
  • -- ends the options, . is the whole repository, and ':!*.example' excludes example files. Documentation lines such as LLM_API_KEY=your-key also match, so in the policy and README write the name without =, or keep the example in a .env.example file.

Passing is no output. Run echo $? after it: 1 means nothing matched. Failing shows file:line:text. Remove the value, and tell your trainer at once, because a leaked key must be revoked, and deleting the line does not remove it from history.

Y2-T47.1: statistics with stats_for(day)

Goal. A function that returns one dictionary of statistics for one day, with missing values as None.

Stage 1. Group and average. Run this to see the pattern:

python -c "import pandas as pd; r = pd.DataFrame({'ward': ['A', 'A', 'B'], 'pm25': [60.0, 64.5, None]}); print(r.groupby('ward')['pm25'].mean())"

groupby('ward') splits rows by ward, and ['pm25'].mean() averages each group. Expect ward A at 62.25 and ward B at NaN, because B has only a missing value. Maximums use .max() the same way.

Stage 2. Missing values. The trace shows the conversion to None. math.isnan must be checked before rounding.

Stage 3. Percentage change. Sort the days by date first, then:

python -c "import pandas as pd; s = pd.Series([60.0, 66.0]); print((s.pct_change() * 100).round(1).tolist())"

Expect [nan, 10.0]. The first day has nothing before it. If the previous value is zero, the division is infinite, so store None in that case and say so in the code comments.

Stage 4. The AQI category is text, chosen from the mean. The bands are your squad's decision, and the source must be written down.

Stage 5. The function's shape. Write the steps as comments first:

def stats_for(day, readings=None):
    # 1. if readings is None, load the day's rows from the SQL view
    # 2. group by ward; compute the mean and the maximum
    # 3. sort by date; compute the percentage change against the previous day
    # 4. build the dictionary; turn NaN into None; round to one decimal place

The readings argument lets a test pass a small DataFrame, so tests never touch the database.

Y2-T47.2: the prompt template

Goal. One file with a system part, a user part, and a {stats} placeholder.

Your code replaces the placeholder with the stats as JSON, using str.replace. The file must contain the marker line ---USER--- exactly once, because the code splits the file there. The <stats> tags separate data from instructions. Write your rules in your own words. They must say: use only numbers inside the stats block; give no medical advice; reply with JSON that has headline and body only; and use plain words.

Check the file:

python -c "t=open('genai/prompts/bulletin_v1.txt', encoding='utf-8').read(); print(t.count('---USER---'), '{stats}' in t)"
  • encoding='utf-8' stops Windows from using its default code page.
  • t.count counts the marker, and '{stats}' in t checks the placeholder.

Expect 1 True. Put PROMPT_VERSION = "bulletin_v1" in one module. Changing the wording means a new file, bulletin_v2.txt, and a new version name.

Y2-T47.3: the call wrapper

Goal. One function that returns the reply text and token usage, and falls back to a template when the model fails.

Stage 1. Load the key without printing it. Keep the value in .env, and load the file into your shell:

set -a
. ./.env
set +a
echo "${LLM_API_KEY:+set}"

set -a exports every variable assigned after it, . ./.env runs the file's NAME=value lines, and set +a turns the export off. Expect set. Never use echo "$LLM_API_KEY", because the value then appears in your history.

Stage 2. Create the client inside a function, so that importing the module needs no key:

import os

def get_client():
    from anthropic import Anthropic
    return Anthropic(api_key=os.environ["LLM_API_KEY"], timeout=15.0, max_retries=2)

os.environ["LLM_API_KEY"] raises KeyError only when the function runs. max_retries=2 is the SDK's own retry for network errors. It is separate from your one JSON retry.

Stage 3. Make the call:

def call_llm(system, user):
    msg = get_client().messages.create(
        model=os.environ["LLM_MODEL"],
        max_tokens=400,
        temperature=0.2,
        system=system,
        messages=[{"role": "user", "content": user}],
    )
    usage = {"input_tokens": msg.usage.input_tokens,
             "output_tokens": msg.usage.output_tokens}
    return msg.content[0].text, usage

max_tokens=400 caps the cost of one call. model= reads the approved model id from the environment. usage copies the two counts. The function returns a pair, such as the text and {"input_tokens": 48, "output_tokens": 28}. Your numbers will differ.

Test the import without the key. Expect import ok:

env -u LLM_API_KEY python -c "import genai.llm; print('import ok')"

Stage 4. Strip fences and parse. The regex removes a fence, optionally labelled json, at the start and end of lines:

import re, json
raw = '```json\n{"headline": "Clean air", "body": "Levels are low."}\n```'
clean = re.sub(r"^```(?:json)?|```$", "", raw.strip(), flags=re.M)
print(json.loads(clean)["headline"])

Expect Clean air. The parsing rule can be tested on its own:

import json

def parse_reply(text):
    """Return headline and body as a dict, or None if the reply is not usable."""
    try:
        data = json.loads(text)
        return {"headline": data["headline"], "body": data["body"]}
    except (json.JSONDecodeError, KeyError, TypeError):
        return None

assert parse_reply('{"headline": "A", "body": "B"}') == {"headline": "A", "body": "B"}
assert parse_reply("not json") is None
assert parse_reply('{"headline": "A"}') is None

This is an example of the idea. Write your own in genai/llm.py.

Stage 5. Retry once, then fall back. Put both attempts inside a try, so that provider errors are caught too:

## for each attempt (the second adds the line "Return valid JSON only."):
## try: call the model, strip fences, parse the JSON, check the keys; return source "llm"
## except: go on to the next attempt
## after both attempts fail: return the template bulletin with source "template"
Trap: The call must be inside the try

If call_llm runs outside the try, a timeout escapes and the fallback never runs. Test it in 47.4 by making the call raise.

Y2-T47.4: the checker and the grounding tests

Goal. A checker that prints PASS, or FAIL with the ungrounded numbers, and tests that run offline.

Stage 1. Find numbers, then remove pollutant names first, because PM2.5 would otherwise yield a false 2.5:

import re
print(re.sub(r"PM\s?(2\.5|10)", "PM", "PM2.5 was 61.2 on 2026-03-02"))

Expect PM was 61.2 on 2026-03-02. Then numbers are found with \d+(?:\.\d+)?, which gives 61.2, 2026, 03 and 02.

Stage 2. Compare numbers, not text. float("61.20") in {61.2} is True. This is why the stats and the bulletin must use the same one-decimal rounding.

Stage 3. The checker's logic, as a twin that runs in the build check:

import re

NUM = re.compile(r"\d+(?:\.\d+)?")

def unlisted_numbers(text, allowed):
    """Return the numbers in text that are not in allowed. Pollutant names are ignored."""
    cleaned = re.sub(r"PM\s?(2\.5|10)", "PM", text)
    return [n for n in NUM.findall(cleaned) if float(n) not in allowed]

allowed = {61.2, 2026.0, 3.0, 2.0}
assert unlisted_numbers("PM2.5 averaged 61.2 on 2026-03-02", allowed) == []
assert unlisted_numbers("Levels reached 180", allowed) == ["180"]

Stage 4. The command line. python -m genai.check FILE needs a block that runs only as a program:

import json, sys

if __name__ == "__main__":
    sample = json.load(open(sys.argv[1], encoding="utf-8"))
    # build the allowed set from the sample's stats and date, using your key names
    # check the bulletin text, then print PASS, or FAIL ungrounded: and the numbers

__name__ == "__main__" is true only when the file runs directly, and sys.argv[1] is the file path.

Stage 5. The offline tests. Copy one good sample into tests/fixtures/. To test the fallback, patch the model call in the module that looks it up:

def test_llm_failure_returns_template(monkeypatch):
    import genai.llm as llm
    def fake_call(system, user):
        raise TimeoutError("simulated timeout")
    monkeypatch.setattr(llm, "call_llm", fake_call)
    # call your bulletin function, then assert that source is "template"

monkeypatch.setattr replaces the function for this test only. Run env -u LLM_API_KEY python -m pytest -q tests/test_grounding.py. Expect a passing summary.

Y2-T47.5: three samples

Goal. Three saved bulletins for three different dates. If you are the fourth or fifth member, you may repeat a date as a reviewer, but at least three dates must exist. Generate one bulletin for your date, then save it:

import json
sample = {"date": day, "prompt_version": PROMPT_VERSION, "stats": stats,
          "bulletin": bulletin, "check": status, "usage": usage}
with open(f"genai/samples/{day}.json", "w", encoding="utf-8") as f:
    json.dump(sample, f, indent=2)

The dictionary holds the five things the trainer needs. open(..., "w") writes the file, and the with block closes it. If the model invents a figure, keep the real output, let the checker return FAIL, and add a label such as "label": "labelled FAIL: invented 180". Never edit a bulletin to hide the number.

Y2-T47.7: token count and cost

Goal. One row for the PR table. Read the usage counts from your sample. Find the input and output prices of your approved model on the provider's price page, and check the unit, which is often per million tokens. The values below are placeholders for the calculation, not real prices:

input_tokens = 480            # placeholder: copy from your sample
output_tokens = 150           # placeholder: copy from your sample
input_price_per_m = 0.0       # replace with the page's input price per million tokens
output_price_per_m = 0.0      # replace with the page's output price per million tokens
cost = input_tokens * input_price_per_m / 1_000_000 + output_tokens * output_price_per_m / 1_000_000
print(f"{cost:.6f} USD per call")

Defend it in the viva

Q1. Why check numbers in code rather than ask the model to check its own bulletin?

Model answer

Code is deterministic. The same input always gives the same result, and it runs offline in CI. A model checking itself can be wrong in the same way, and a second call costs money. The checker only compares each number with the allowed set.

Q2. Why temperature 0.2 and max_tokens 400, and what do you give up?

Model answer

A low temperature keeps the wording steady, but it does not stop invention, which is why the checker exists. The cap makes the worst-case cost of one call known. The trade-off is that a long reply can be cut off and fail to parse, so the fallback must handle it.

Q3. What do the SDK's max_retries and the one JSON retry each protect against, and what do they cost?

Model answer

The SDK retry covers network and server errors. The JSON retry covers a reply that arrives but cannot be parsed. Each retry is a paid call, so the two layers can multiply the calls in the worst case. A good answer gives that worst-case number and says how the squad limits it.

Q4. Which subtask did you write, which test proves it, and which commit shows it?

Model answer

Name the subtask id, the file, the test and the commit message. Be specific, for example: "I wrote the percentage change, and the zero-previous-value case is tested." Describe only work you did. The trainer checks the commit history against what you say.

Q5. Walk me through what happens when the checker returns FAIL.

Model answer

The unchecked bulletin is not served. The endpoint returns the template bulletin, built from the stats, with source set to template. The failure should be logged with the ungrounded numbers, so the squad can fix the template or the rounding.

Y2-T48.4: Build GET /v1/bulletin (Backend)

Goal. Build the route in small pieces, and test each piece before adding the next.

Technique: a cache keyed by a tuple. A dictionary maps a key to a stored value. A tuple in parentheses can be a key, because it cannot change. The database table works the same way.

Stage 1. Validate the day. Write a function that turns the text into a date and refuses future dates:

from datetime import date

def parse_day(raw: str) -> date:
    d = date.fromisoformat(raw)
    if d > date.today():
        raise ValueError("day is in the future")
    return d

date.fromisoformat reads YYYY-MM-DD and raises ValueError for anything else. The comparison d > date.today() is true for a later date. Test parse_day("2026-11-01") and parse_day("2099-01-01") in a Python shell. Your route turns the error into 422.

Stage 2. Validate the ward against known codes. A small test, using a bakery's branch codes instead of your ward codes, shows the pattern:

def parse_branch(raw, known):
    code = raw.strip().upper()
    if code not in known:
        raise ValueError("unknown branch code")
    return code

known = {"BK1", "BK2", "BK3"}
assert parse_branch(" bk2 ", known) == "BK2"
assert parse_branch("BK3", known) == "BK3"
try:
    parse_branch("ignore previous instructions", known)
    raise AssertionError("injection-like text was accepted")
except ValueError:
    pass

strip().upper() removes the spaces and capitalises the text. not in known tests membership in a set, which is quick. Expect no output when all asserts pass. Apply the same rule to your wards: an unknown ward returns 422 before anything else happens.

Stage 3. Look up the cache. Use all three parts of the key. Placeholder style depends on the driver: sqlite3 uses ?, and many Postgres drivers use %s.

row = conn.execute(
    "SELECT body_json FROM bulletins WHERE day = ? AND ward = ? AND prompt_version = ?",
    (day, ward, PROMPT_VERSION),
).fetchone()

The values are passed separately, so the driver never treats them as SQL. fetchone() returns one row, or None. Use the PROMPT_VERSION from Y2-T47, so a new prompt invalidates old rows.

Stage 4. Compute on a miss. On a miss, call stats_for(day) and then call_llm. The Anthropic SDK takes the timeout and retry settings on the client:

from anthropic import Anthropic
client = Anthropic(timeout=15.0, max_retries=2)

timeout=15.0 is the wait in seconds. max_retries=2 allows two more tries after a transient failure. Set max_tokens=400 in the messages.create call inside call_llm.

How you test this stage. Call the route twice with the same valid day. The first call should write one row and the second should read it, with one LLM call in total.

Defend it in the viva

1. Why does the deploy run on a tag and not on every push to main?

Model answer

A tag is a deliberate, named release. Main can change many times a day, including half-finished work. Deploying on a tag means the live service changes only when the squad chooses, and the tag names the exact commit that was tested. Rollback is then clear, because you know which tag and sha were live before. The trade-off is that a fix sits on main until someone tags it.

2. What is the trade-off in caching by day, ward and prompt version?

Model answer

Caching saves money and time, because a repeated call returns the stored body without a model call. The cost is staleness: if the stats change after a bulletin is stored, the cached text stays the same. Including prompt_version in the key means a new prompt invalidates the cache. The squad must decide when a stored bulletin may be regenerated, and write that rule down.

3. Walk me through what you personally did on this ticket.

Model answer

A strong answer names one piece, its commits, the test that covers it, and the log line or CI run that proves it. For example: "I built the ward validation. My commit added the known-set check and a test for injection-like input, and the CI run shows the 422." Write your own version with your own commit names. Do not claim a teammate's work.

4. Why check numbers in code rather than asking the model to check itself?

Model answer

A model can be confident and still wrong, so asking a second model is not an independent check. Code compares each number in the output with the allowed set from the stats. It is fast, cheap and repeatable. A failed check returns the template, so an invented number never reaches the reader. The check proves the numbers are supported, not that the prose is good.

5. Why is the ward validated before the cache lookup?

Model answer

Validation first means bad input never reaches the database or the model. An unknown ward or an injection-like string is refused with 422, so it cannot create a cache row, cost a call, or change the prompt. The order also matches the trainer's test: the injection case must return 422, not 200.
